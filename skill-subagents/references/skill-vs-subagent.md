# Skill vs 子代理：怎么选

> ⭐ **一句话比喻**：
> **Skill 是装在主机里的应用程序，按需调用；
> SubAgent 是虚拟机，独立跑完再把结果交回来。**

## 本质区别

| 维度 | Skill | SubAgent |
|---|---|---|
| **是什么** | 可复用的指令 / 知识 / 工作流 | 隔离的工作者，有自己的上下文 |
| **核心收益** | **跨上下文共享内容** | **上下文隔离**——工作独立发生，只回传摘要 |
| **上下文影响** | 加到你的主窗口 | 用独立窗口，有自己的输入/输出 token |
| **适合** | 参考资料、可调用的工作流 | 读大量文件、并行工作、专职工作者 |

> ⭐ **主智能体的上下文是宝贵资源——要像管理内存一样谨慎管理它。**

---

## 两步决策法

**第一步：要不要"记住这个过程"？**

```
需要历史上下文 / 长期连续性 / 反复迭代   → 优先考虑 Skill
  □ 长期维护一个知识库 / 技术栈助手
  □ 持续打磨一篇长文、一个 PRD、一份教程
  □ 需要频繁回顾"之前我们怎么做的"

不需要记住整个过程、只要结果            → 直接上 SubAgent
  □ 临时生成一份脚本、一次性报告
  □ 跑一次批处理分析
  □ 把脏活累活（大规模检索、批量处理）丢出去做一轮
```

**第二步：需不需要「并行 / 隔离 / 特殊权限」？**

```
需要并行、权限隔离、工具集不同、风险更可控 → SubAgent
  □ 某个 agent 只能访问特定目录或特定 API
  □ 某些操作希望"在沙盒里执行完再把结果拿回来"
  □ 希望同时让多个 agent 各跑各的

权限差不多、工具差不多、不强调隔离        → 只写一个 Skill
```

**合并成一张表**：

| 诉求 | 选 |
|---|---|
| 任务简单、主 agent 全程掌控 | **Skill** |
| 知识可复用、想省上下文按需加载 | **Skill** |
| 跨多个 agent 共享能力 | **Skill**（本质就是文件） |
| 工具集很大，怕 token 膨胀 | **Skill** |
| 子任务复杂、耗时长、中间过程繁琐 | **SubAgent** |
| 需要并行处理多个独立任务 | **SubAgent** |
| 想保持主 agent 的"思维清晰" | **SubAgent** |
| 为特定任务提供专属工具集 | **SubAgent** + 精简工具 |

## 官方对照表

**Skill vs SubAgent**（来自官方文档）：

```
用 Skill：参考资料、可调用的工作流
用 SubAgent：需要上下文隔离，或主上下文快满了

⭐ SubAgent 可能读了几十个文件或跑大量搜索，
   但你的主对话只收到一份摘要。
   由于子代理的工作不消耗主上下文，
   当你不需要中间过程保持可见时，这也很有用。
```

**CLAUDE.md vs Skill**：

| | CLAUDE.md | Skill |
|---|---|---|
| **加载** | 每会话自动 | 按需 |
| **能否触发工作流** | 否 | 是（用 `/`） |
| **适合** | "总是做 X"的规则 | 参考资料、可调用的工作流 |

```
放 CLAUDE.md：Claude 应该永远知道的
  ——编码约定、构建命令、项目结构、"绝不许做 X"
放 Skill：Claude 只是有时需要的内容
  ——API 文档、风格指南；或用 / 触发的工作流（deploy/review/release）

经验法则：CLAUDE.md 保持在 200 行以内。
变长了就把参考内容移到技能，或拆进 .claude/rules/
```

**三者完整对照**：

| | CLAUDE.md | .claude/rules/ | Skill |
|---|---|---|---|
| 加载 | 每会话 | 每会话，**或打开匹配文件时** | 按需调用或相关时 |
| 作用域 | 整个项目 | **可按文件路径限定** | 任务特定 |
| 适合 | 核心约定与构建命令 | 语言或目录专属指南 | 参考资料、可重复工作流 |

**MCP vs Skill**：

```
MCP    把 AI 连到数据
Skill  教 AI 拿这些数据做什么
```

## 组合用法

> ⭐ **这不是非此即彼。很多系统同时用两者**：

```
□ Skill 定义流程
□ SubAgent 执行复杂的多步骤工作
□ ⭐ 你的 SubAgent 甚至可以使用 Skill 来管理它自己的上下文窗口
```

**推荐路径**：

```
先从 SubAgent 做上下文管理开始
→ 加入 Skill 做渐进式披露
→ 再按需求扩展
```

**具体组合形式**：

```
SubAgent（隔离、记忆、可恢复）
  ├── 预加载：领域 Skill（完整逻辑、阶段、模板）
  ├── 拥有：跨会话的持久记忆
  └── 产出：交付物（spec.md / plan.md / tasks.md）
```

**决策流程图**：

```
需要持久记忆或可恢复性？
  是 → 自定义 SubAgent（并用 skills: 预加载）
  否 → 是否是"产出交付物的独立任务"？
        是 → Skill + context: fork
        否 → 是否是"供主对话参考的知识"？
              是 → Skill（不 fork，内联运行）
              否 → 内置 SubAgent（Explore / Plan / 通用）
```

> 注意跨工具差异：**自定义子代理在部分客户端是独占能力**，
> 而技能通过 AGENTS.md 指令文件在各处可用。
> 呼应 `skill-selection` 的 `cross-model.md` 与 `skill-crafting` 的 `skill-structuring` 的 `directory-contract.md`。

## 别过度设计

> ⭐ **不要为了"酷炫"和"概念完整"而过度设计。**

```
□ 权限差不多、工具差不多、不强调隔离 → 完全可以只写一个 Skill
□ 任务简单、主 agent 全程掌控 → Skill
□ 一个技能能解决的事，不要拆成一堆子代理
```

**一个反面清单**：

```
❌ 为了"架构看起来完整"把简单流程拆成多 agent 编排
❌ 明明只是参考资料，却做成独立 agent
❌ 明明需要长期记忆与迭代，却只做一个无状态技能
❌ 工具集很小却用子代理隔离（白白多一轮摘要损失）
```

## 自查

```
□ 是否需要记住过程（是→Skill）还是只要结果（是→SubAgent）？
□ 是否需要并行/隔离/特殊权限（是→SubAgent）？
□ 是否只是参考资料或可调用工作流（是→Skill）？
□ 是否同时用了两者（Skill 定流程 + SubAgent 执行）？
□ SubAgent 是否预加载了领域 Skill？
□ 是否为了概念完整而过度设计？
□ CLAUDE.md 是否超过了 200 行（是→移部分到 Skill 或 rules/）？
□ 需要"按文件类型生效"的规则是否用了 paths 限定？
□ 跨客户端分发时，是否避开了独占的子代理能力？
```
