> 子代理能显著加速复杂工作流，

## 核心机制

> ⭐ **子代理共享父会话的工具和文件，
> 但各自维护独立的会话历史。**

```
□ 共享：工具、文件
□ 独立：⭐ 上下文窗口、对话历史
□ ⭐ 不继承：父对话里已加载的技能（必须在 skills: 显式声明）
```

最后一条呼应 `subagents.md`：
**编排总是一层深**。

## 什么时候并行

**✅ 适合并行**：

```
□ 分析三个独立的文件
□ 生成报告的不同章节
□ 跑独立的测试套件
□ ⭐ 静态分析 / 安全扫描 / 架构评审 / 性能分析（互不依赖）
```

**❌ 不适合并行**：

```
□ ⭐ 有顺序依赖的任务
□ ⭐ 共享大量上下文的子代理
□ ⭐ 过度细粒度地拆分
```

> ⭐ **"避免 spawn 需要等待彼此结果子代理"**——
> 那只增加了协调开销，没有并行收益。

## 指令要窄

```
❌ "Review this codebase"
✅ ⭐ "Identify all uses of eval() and suggest safe alternatives"
```

> 呼应 `composition.md` 与 `multi-agent-review.md`：
> **每个专家只带自己领域的规则**，
> 也呼应 `guidance-forms.md`（**`skill-crafting`**）的
> **给具体判据，不给抽象任务**。

## 五种模式

**① 基础并行**

```
"分析这三个文件的安全漏洞、性能问题和测试覆盖"
→ spawn 三个子代理，各管一类
→ 父代理汇总
```

**② 结合专用技能**

```
/subagent: 用 tdd 技能为用户认证模块写单元测试
/subagent: 实现符合测试要求的认证端点
```

> ⭐ **子代理 + 技能组合**——
> 技能给方法，子代理给隔离。
> 呼应 `skill-vs-subagent.md`：
> **Skill 是应用程序装在主机里；SubAgent 是虚拟机**。

**③ 层级子代理**

```
主任务：把单体应用迁移到微服务

Level 1：
  - 分析当前架构
  - 设计服务边界
  - 规划迁移顺序

Level 2（每个服务）：
  - 抽取服务代码
  - 配置 CI/CD
  - 写集成测试
```

> ⭐ **两层是上限**——
> 呼应 `subagents.md` 的"编排总是一层深"。

**④ 并行评审循环**

```
/subagent: 静态分析（lint、类型检查）
/subagent: 安全扫描（OWASP Top 10）
/subagent: 架构评审（设计模式、SOLID）
/subagent: 性能分析（复杂度、数据库查询）
```

> 这个模式与 `security-pipeline.md` 的多 Agent 并行扫描一致：
> ⭐ **按"心智模型"切，不按"数据块"切**。

**⑤ 条件分支**

```
/subagent: 跑测试套件并给失败分类
按结果分支：
  有失败 → /subagent: 修失败的测试
  全通过 → /subagent: 跑性能基准
```

## 四个坑

**① 过度 spawn**

```
□ ⭐ 同时创建太多子代理会撑爆上下文窗口并降低质量
□ ⭐ 从 2–4 个起步，证明确实有效再往上加
```

呼应 `skill-composition-patterns.md` 的甜蜜点 5–8：
**数量上限是真实约束，不是保守建议**。

**② 所有权不清**

```
□ ⭐ 多个子代理改同一批文件会产生冲突
□ 修法：⭐ 给每个子代理排他的文件所有权，
        或实现协调协议
```

呼应 `multi-agent-review.md`：
**必须明确"谁能改盘、谁只能提议"**。

**③ 上下文管理**

```
□ ⭐ 子代理从父会话的上下文窗口消耗 token
□ 长流程要用更小的上下文子代理或显式管理：
   - 在子代理之间传递结果前先摘要
   - ⭐ 大数据用基于文件的通信
   - 在子代理调用之间清理无用上下文
```

呼应 `context-budget.md`（**`skill-refining`**）与
`performance.md`（**`skill-selection`**）的
**"长工具输出回灌前先做摘要"**。

**④ 依赖没理清**

```
□ ⭐ 有依赖却并行 → 产出互相矛盾的结果
□ 呼应 composition.md 的并行前提：各技能输出互不依赖
```

## 成功标准

> ⭐ **事先为每个子代理定义"完成"长什么样。**

```
❌ "Refactor the data processing module"
✅ "重构数据处理模块以降低内存占用。
    目标：10K 记录下 <100MB。
    交付物：更新后的代码 + 基准对比"
```

**三要素**：

```
□ 可度量的目标（<100MB）
□ 明确的交付物（代码 + 基准对比）
□ ⭐ 边界（只动数据处理模块）
```

> 呼应 `grounding-verification.md`（**`skill-crafting`**）：
> **写明证明完成的具体命令、什么证据够什么不够**。

## 自查

- [ ] 任务真的互相独立吗？
- [ ] 从 2–4 个起步了吗？
- [ ] 每个子代理的指令够窄吗（有具体对象）？
- [ ] 文件所有权是排他的吗？
- [ ] 每个子代理有可度量的成功标准吗？
- [ ] 层级超过两层了吗？
- [ ] 大数据用文件通信而非上下文传递了吗？
- [ ] 子代理需要的技能在 `skills:` 里显式声明了吗？
