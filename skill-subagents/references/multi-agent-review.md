# 多角色审查编排

> ⭐ **核心设计**：
> **每个团队都必须包含一个 `challenge_agent`——这个角色不是可选的。**
> 它通过质疑假设、发现盲点来提升质量，那些是专家们会漏掉的。

## challenge_agent 为什么是必需的

```
职责：
□ 质疑其他成员所做的假设
□ 找出别人漏掉的盲点与边界情况
□ 从不同角度挑战设计决策
□ ⭐ 充当"红队"，压力测试结论

为什么重要：
□ ⭐ 专家专注自己的领域 → 会漏掉横切关注点
□ 一个专职怀疑者能抓到所有人都忽略的东西
□ ⭐ 迫使显式推理，而不是隐含假设
```

**示例 prompt**：

```
challenge_agent:
"复核 security_auditor、performance_engineer、
 maintainability_expert 的全部发现。质疑他们的结论：
 他们做了什么假设？漏了哪些边界情况？
 什么会让这段代码在生产中失败？
 输出：challenges.md，按严重程度排序的关切点。"
```

## 按任务类型选团队结构

**代码审查 / 审计（4–5 个成员）**：

```
security_auditor        OWASP Top 10、注入、认证授权、依赖漏洞
performance_engineer    复杂度、N+1 查询、内存、缓存、包体积
maintainability_expert  SOLID、DRY、命名、错误处理、测试覆盖
challenge_agent         ⭐ 专职怀疑者（必需）
qa_specialist（可选）   边界情况、竞态、错误路径

协调：独立工作 → challenge_agent 质疑所有人的发现
     → 互相交叉核对 → 合并成一份报告
```

**功能开发（按复杂度扩展）**：

```
简单（4 角色）   fullstack_developer · ui_reviewer · challenge_agent · code_reviewer
标准（5–6）     system_architect · frontend · backend · integration_tester · challenge_agent · code_reviewer
复杂（6–8）      + database_engineer · devops_engineer

协调：架构师定契约 → 专家并行实现 → 测试验证 → 评审把关 → 合并
```

**调试 / 调查（3–4 个）**：

```
log_analyst         轨迹重建、时间线、模式
code_auditor        静态分析、状态一致性、根因假设
reproduction_lead   最小复现、环境模拟
challenge_agent     ⭐ 质疑每个调查者的假设，要求更多证据

协调：各查一个假设 → challenge_agent 质疑结论 → 辩论与证伪 → 收敛根因
```

**研究 / 评估（3–4 个）**：

```
advocate_a   深挖方案 A——优劣、真实案例
advocate_b   深挖方案 B
synthesizer  客观对比、评分矩阵、推荐
challenge_agent  ⭐ 质疑每位倡导者的推理

协调：各自独立研究 → challenge_agent 质疑 → synthesizer 出最终分析
```

> ⭐ **研究类的"双倡导者 + 怀疑者 + 综合者"结构特别值得抄**——
> 它天然对抗单一视角偏差。

## 代码审查的四类角色

> 一个成熟实现的分工（每个角色只输出固定字段）：

| 角色 | 视角 |
|---|---|
| **code reviewer**（战术） | 模式合规、lint、最佳实践 |
| **solution architect**（战略） | 架构一致性、关注点分离、设计连贯 |
| **语言特定架构师** | 该语言的惯用法（如 Go 的 stuttering、接口设计、错误包装、context 传播、包结构） |
| **challenge_agent** | 质疑以上所有人 |

> ⭐ **"战术 + 战略 + 语言特定"三视角**是最小可行组合。

**七步流程**：

```
1. 确定审查范围
   PR → git diff；文件/目录 → 给的路径；暂存 → git diff --cached
   ⭐ 无参数默认审查未提交改动；没有参数就问用户

2. 并行派三个 agent

3. 综合发现
   □ 一致项——多个 agent 都报的
   □ 独特发现——只有一个 agent 抓到的
   □ ⭐ 分歧——互相矛盾的建议

4. 化解分歧
   把冲突观点发回给各持方 → 要求给出推理 → 请求达成共识
   ⭐ 无共识则把两种视角都呈现给用户

5. 汇总统一发现（用模板）

6. ⭐ 与用户协作决定解决方案（先批准，不自动修）

7. 派发已批准的修复
```

> ⭐ 第 4 步"化解分歧"很关键——
> 呼应 `composition.md`：多 agent 的真正难点是协调，不是派活。

## 汇总规则比分工更重要

> ⭐ **一段好提示词的价值在于：它把"分工"和"汇总规则"一起写出来了。**
> **没有汇总规则，主任务只会收到几份互相独立的长报告。**

**每个 agent 只输出固定字段**：

```
□ 严重程度
□ 文件和位置
□ 触发条件
□ 影响
□ ⭐ 证据
□ 修复方向
```

**汇总时的处理**：

```
□ 去掉重复问题
□ ⭐ 标出相互矛盾的判断
□ 按 P0 / P1 / P2 排序
□ ⭐ 单独列出必须人工确认的事项
□ ⭐ 不要直接改文件
```

**去重与交叉验证**：

```
□ 先按文件去重，再按问题影响排序
□ 两个 agent 发现同一问题 → 保留更完整的证据，
   ⭐ 另一个结果作为交叉验证
□ ⭐ 如果子代理意见相反，不要让主任务投票
  ——回到需求、测试与真实运行条件，必要时补一个最小复现
```

> ⭐ **"不要投票"这条反直觉但正确**——
> 多数决会掩盖分歧，而分歧往往正是关键信息。

**第一轮只做只读审查**：

```
□ 审查发现 ≠ 最终结论
  一个 agent 认为某段逻辑危险，
  另一个可能发现那是兼容旧版本的必要处理
□ ⭐ 第一轮不适合多人同时写代码
```

## 并行并不总是更快

> ⭐ **子代理会消耗更多 token，启动与汇总也有成本。**

**适合并行**：

```
□ 文件多、关注点分明
□ 各个检查互不依赖
□ 任务本身需要较长阅读时间
□ 你能接受等待所有结果回来
```

**不适合**：

```
□ 一个小函数的审查
  ⭐ 直接让一个 agent 读差异更省事
□ 大 PR、跨服务改动或安全敏感任务，拆分才有明显收益
```

**另外两条成本控制**：

```
□ 最小化团队规模
  ⭐ 每个成员 = 一个独立上下文窗口 = 更多 token
  用能覆盖工作的最少成员数
□ 避免文件冲突
  给不同成员分配不同文件/目录
  ⭐ 绝不让两个成员编辑同一个文件
```

**spawn prompt 要给足上下文**：

```
□ 具体文件路径
□ 相关标准
□ ⭐ 期望输出格式
□ 模糊的 prompt 产出模糊的结果

✅ security_auditor: "审计 src/auth/ 的安全漏洞。
   聚焦：src/auth/token.ts 里的 JWT 存储、
         src/auth/session.ts 的会话管理、
         CSRF 防护、密码哈希、限流。
   输出：security_review.md，发现按 CVSS 严重程度排序。"
```

> ⭐ 呼应 `subagents.md` 与 `composition.md`：
> **每个子代理都要有明确的所有权和输出契约。**

## 自查

```
□ 每个团队是否都包含了 challenge_agent（必需，非可选）？
□ 团队结构是否按任务类型选（审查/开发/调试/研究）？
□ 团队规模是否最小化（每成员 = 一个上下文窗口）？
□ 是否给不同成员分配了不同文件（避免编辑冲突）？
□ spawn prompt 是否含具体路径、标准、期望输出格式？
□ ⭐ 是否写了汇总规则（去重/标矛盾/排序/人工确认项）？
□ 每个 agent 的输出字段是否固定（含"证据"）？
□ ⭐ 分歧时是否避免了"投票"（改为回到需求与最小复现）？
□ 第一轮是否只做只读审查？
□ 是否判断过"这个任务其实不值得并行"？
□ 修复是否先获用户批准（不自动改）？
```
