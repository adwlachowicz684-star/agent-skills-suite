## 1. 它做什么

读一次代码变更（diff），输出风险等级，以及"能否自动合入"的建议。

```
输入：一段 diff（或 PR 号）
输出：等级（L0–L3）+ 依据 + 是否建议自动合入
```

它是判定型而不是产物型：**不生成内容、不改文件**，只产出一个分类。
这个区别决定了后面所有的设计。

## 2. 完整源码

````markdown
---
name: change-risk
description: 判定一次代码变更的风险等级（L0–L3）并给出是否可自动合入的建议。当要决定是否放行一个 PR、要做发布前风险筛查、或用户问"这个改动风险大吗"时使用。只读分析，不修改任何文件、不发起合并。
  Do NOT use for 实际执行合并（用 release 流程）、安全审计（用 security-review）。
---

# 变更风险分级

## 输出契约

先写等级，再写依据。依据必须在等级之前可读到。

```
风险等级：L2
判定依据：修改了 `payment/` 下的 3 个文件，涉及金额计算（规则 R2）
是否建议自动合入：否 —— 需人工评审 `payment/refund.go:47`
本次判定覆盖：12 个变更文件 / 共 12 个
```

## 判定规则

按以下顺序取**第一个**匹配的规则，不再继续。

| 规则 | 条件 | 等级 |
|---|---|---|
| R1 | 仅改动注释、文档、格式化 | L0 |
| R2 | 改动涉及金额、权限、鉴权、删除操作 | L2 |
| R3 | 改动涉及数据库 schema 或迁移文件 | L3 |
| R4 | 其他 | L1 |
| ⭐ R5 | 信息不足以判定（diff 不完整 / 无法定位文件归属） | 无法判定 |

⭐ 五条规则互斥且穷举。走不到任何一条时，输出"无法判定"，不得输出 L1。

## 必须做的事

- 逐文件判定，再取所有文件中的**最高**等级
- 每个文件都要能回答：它命中了哪条规则
- 判定完成后报告分母："本次判定覆盖 N 个文件 / 共 M 个"
- ⭐ 读到不完整的 diff 时，按 R5 处理，不得按 R4 处理

## 不得做的事

- 不得在依据里写"看起来风险较高"——必须指向具体文件和规则号
- 不得输出 L1 作为默认兜底（L1 是一个真实等级，不是"不知道"）
- 不得因为"大部分文件安全"而把整体等级下调
- ⭐ 不得建议自动合入 L2 及以上

## 示例

````
输入：diff 修改了 `docs/README.md` 与 `payment/refund.go`
输出：
风险等级：L2
判定依据：payment/refund.go 命中 R2（涉及金额）；docs/README.md 命中 R1；取最高 → L2
是否建议自动合入：否
本次判定覆盖：2 个文件 / 共 2 个
````

> Rationale：⭐ 两个文件命中不同规则，等级取最高而不是平均。
> 这是本技能最容易做错的地方——"平均"会产出一个两个文件都不支持的等级。

- 未指定范围 → 当前 diff 的全部文件，不扩展到未改动的相关文件
- "这个改动风险大吗" → 只读分析，不改任何文件、不发起合并
````

## 3. 逐处点评：每一处在堵什么

| 处 | 堵的是什么 |
|---|---|
| description 里写"只读分析，不修改任何文件、不发起合并" | ⭐⭐⭐⭐⭐ `user-input-omissions.md`：用户没说的"改不改"是最贵的未言明项 |
| 输出契约里"依据必须在等级之前可读到" | ⭐⭐⭐⭐ 排在第一位的字段会被当成最重要的；依据放最后会被省略 |
| "本次判定覆盖 N/M" | ⭐⭐⭐⭐⭐ 没有分母就没有完成（截断类失败唯一可见信号） |
| R5 存在 | ⭐⭐⭐⭐⭐ 没有"无法判定"这一档，所有输入都会被强行分进某一类 |
| "走不到任何一条 → 无法判定，不得输出 L1" | ⭐⭐⭐⭐⭐ **L1 是一个真等级，不是"不知道"**——这是判定型最典型的污染 |
| "取最高，不得平均" | ⭐⭐⭐⭐⭐ `merge-conflict-resolution.md`：平均产生一个没有任何来源支持的值 |
| "不得因为大部分安全而下调" | ⭐⭐⭐ 覆盖率错觉："大部分"的正确用法是加覆盖，不是稀释等级 |
| 示例带 Rationale | ⭐⭐⭐⭐ 正文只有一个示例，必须用 Rationale 换取它占的位置 |
| Gotchas 留空并写明原因 | ⭐⭐⭐⭐⭐ **填满它才是缺陷**——那意味着填进了没验证过的东西 |
| "未言明时的默认"章节 | ⭐⭐⭐⭐ 把项目惯例从人的脑子里搬进技能（模型先验填补的正是这个位置） |

## 4. ⭐⭐⭐⭐⭐ 判定型独有的三处设计

这三点在产物型技能里都不需要，是判定型特有的：

**① 类别集合必须封闭，且必须包含"无法判定"**

```
❌ L0 / L1 / L2 / L3            ← 开放：任何输入都会被塞进某一档
✅ L0 / L1 / L2 / L3 / 无法判定  ← 封闭
```

> ⭐⭐⭐⭐⭐ **没有"无法判定"这一档，模型就永远不会输出它——
> 而它恰恰是唯一诚实的答案。**

**② 必须报各类别的单独统计**

测试集里如果 90% 是 L0，那么"永远答 L0"就能拿 90 分。
所以判定型的评测必须按类别分别报（见 `output-kind-three.md`），
而测试集要**刻意做均衡**——⭐⭐⭐⭐⭐ 它测的是"能不能分辨"，不是"猜得准不准"。

**③ 判定与变更之间必须有阈值 + 人工确认点**

```
本样本：L2 及以上 → 不得建议自动合入
```

> ⭐⭐⭐⭐⭐ **判定错了会被变更固化。**
> 判定"低风险"而实际高风险 → 自动合入已经发生 → 判定错误变成了一个既成事实。
> 产物型抄错了还有机会改，判定型抄错了会立刻被下游的动作吃掉。

## 5. 这份样本刻意没做的事

```
❌ 没有写"分析 diff 的总体思路"  → 模型本来就会，写了只是替换掉它的默认解
❌ 没有列所有可能的风险类型      → 超 5 项的枚举会被当成穷举（实际是举例）
❌ 没有写"失败时重试"            → 本技能唯一的失败是 diff 读不全，重试不会改变它
❌ 没有 Gotchas                  → 它是采集的，第一版还没有素材
❌ 没有写"要谨慎、要全面"        → 无具体判据的词等于没有约束
```

最后一条值得强调：判定型技能最容易被写成一份"注意事项清单"，
而⭐⭐⭐⭐⭐ **清单里的每一条都能被模型用一个默认值满足——
于是清单越长，判定越像合规仪式，而不是判定。**

---

## 如何判断你的判定型技能是有效的

> ⭐⭐⭐⭐⭐ **把"无法判定"这一档删掉，跑一遍测试集。
> 如果通过率几乎没变，说明它从来没有被使用过——
> 也就是说，你的技能在它最该说话的时候一直在猜。**
