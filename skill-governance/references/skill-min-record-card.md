## 1. ⭐ 最小档案卡（9 字段）

| 字段 | 要回答的问题 |
|---|---|
| `skill_id` / 名称 | 稳定标识是什么？**名称会不会造成误用？** |
| 任务目的 | 它解决哪一类任务，**不解决什么**？ |
| 输入 / 输出 | 接收什么材料，必须交付什么格式？ |
| 触发条件 | 自动触发、路由选择，还是用户明确调用？ |
| ⭐ 工具与权限 | ⭐ 能读什么、写什么、对外执行什么？ |
| ⭐ 评测证据 | ⭐ 用哪些样本测过，**最近结果怎样**？ |
| 版本与状态 | Candidate / Active / Deprecated / Archived？ |
| ⭐ Owner | ⭐ 谁能批准启用、修改和下线？ |
| ⭐ 回滚点 | ⭐ 最近一个稳定版本在哪里？ |

> ⭐ 这张卡不需要一开始就做得很复杂。
> ⭐ **它的作用是让一个技能不再只靠文件名和作者记忆存在。**

> ⭐ 特别注意"名称会不会造成误用"这一问——
> 对应的是跨平台那条硬约束：**名字里不能含 claude / anthropic**。

## 2. ⭐ Owner：贯穿始终的责任线

> ⭐ **Owner 不一定亲手写技能，
> 但要对它的准入、适用边界、评测标准、权限变化和下线决定负责。**
>
> ⭐ **否则每个技能都"由 Agent 自己维护"，
> 出问题时却没有人能解释为什么它仍处于启用状态。**

**回滚那条同样关键**：

> ⭐ **如果技能被自动优化后表现变差，
> 团队要能看到改动前后差异、选择上一个稳定版本、并暂停继续改写。
> ⭐ 没有版本记录、评测证据和停止开关的"自我改进"，更像不可控覆盖。**

## 3. 六个清理触发点

不必每天扫描全部技能。**设置几个具体触发点**：

```
① ⭐ 同一任务连续出现多个候选技能
② ⭐ 技能的工具、权限或上游知识发生变化
③ ⭐ 评测结果连续下降，人工修正明显增加
④ ⭐ 自动改写准备进入 Active 状态
⑤ ⭐ 旧技能长期未使用，但仍被工作流依赖
⑥ ⭐ 发生越权、误发、错误写入或无法回滚的异常
```

> ⭐ 第 ⑤ 条最微妙：**长期未用 ≠ 可以删**，
> 它可能仍被某个工作流依赖。这正是"先软下线再决定删除"的理由。

## 4. ⭐ 清理不等于全自动删除

```
Agent 可以负责：
  · 发现疑似重复
  · 生成差异
  · 重跑评测
  · 给出建议

⭐ 仍应进入明确的人审门：
  · 权限扩大
  · 生产启用
  · 存量依赖
  · ⭐ 最终删除
```

> ⭐ 这与 `library-ops.md` 那条"清库这件事不该让 LLM 来做"一致，
> 但给出了更精确的切分：**发现与建议可以自动，决定不行**。

## 5. 准入四点评审

新技能要过这四条才能进库：

```
① ⭐ 重复（repeats）——这个工作流真的会重复出现吗
② ⭐ 受规则约束（rule-bound）——是否有明确的规则可依
③ ⭐ 非冗余（non-redundant）——与现有技能不重叠
④ ⭐ 具体（concrete）——能落地到真实路径与清单
```

**库地图要持续更新**：

| 技能 | 一句话职责 |
|---|---|
| `native-screen-scaffold` | 一次就把原生页面搭对 |
| `skill-governance` | ⭐ 这个元技能——治理整个库 |
| …… | |

> ⭐ 每次新增或退役技能都要更新这张表。
> **一张只有 10 行的库地图，胜过 100 份没人读的技能说明。**
