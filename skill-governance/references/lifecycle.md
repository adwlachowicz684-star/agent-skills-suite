## 五个阶段

```
DRAFT → ACTIVE → MATURE → DEPRECATED → ARCHIVED
 测试    在用     稳定      逐步淘汰     只读归档
```

| 阶段 | 版本 | 特征 | 任务 |
|---|---|---|---|
| **DRAFT** | `0.x.x` | 开发中，功能可能不完整，未验证 | 写 SKILL.md · description 含关键词 + NOT 子句 · **至少 1 条反模式** · 跑校验脚本 · **10+ 条查询测激活** |
| **ACTIVE** | `1.0.0+` | 已验证在用，接受反馈 | 监控激活精确率 · 发现就补反模式 · 更新时效性知识 · 保持 CHANGELOG |
| **MATURE** | `2.0.0+` | 稳定、文档齐全、反模式完整、很少需要改 | 季度评审 · 检查时效性知识新鲜度 · 对最新模型行为验证 · **长大了就拆子技能** |
| **DEPRECATED** | — | 有更好替代，仍可用但不推荐 | 头部加弃用声明 · 记录迁移路径 · 指向替代技能 · **设终止支持日期** |
| **ARCHIVED** | — | 不再维护，仅供历史参考 | 移到 `archived/` · 更新引用 · **记录为什么归档** |

**弃用声明写法**：

```markdown
> ⚠️ **DEPRECATED**：本技能自 v2.3.0 起弃用。
> 请改用 `new-skill-name`。迁移指南：`references/migration.md`
> 终止支持：2026-06-01
```

## 版本号怎么打

**SemVer**：`MAJOR.MINOR.PATCH`

| 变化 | 打哪一位 | 例子 |
|---|---|---|
| **破坏性变更**（改触发语义、删字段、改输出格式、审查标准大改） | **MAJOR** | 1.x → 2.0.0 |
| **新功能**（新增一个审查维度、新增反模式、向后兼容） | **MINOR** | 2.0.0 → 2.1.0 |
| **Bug 修复**（修误报、改错别字、无接口变化） | **PATCH** | 2.1.0 → 2.1.1 |

**frontmatter 写法**：

```yaml
---
name: code-review
version: 2.1.0
description: 代码审查技能……
updated: 2026-07-10
author: 开发者A
---
```

> 一个现实痛点：**没有版本管理，项目 A 用 v1.0 的 code-review，
> 项目 B 用 v2.0——两人的审查标准不一致。**

## CHANGELOG 写什么

> 遵循 **Keep a Changelog**，六个标准分类：
> `Added` · `Changed` · `Deprecated` · `Removed` · `Fixed` · `Security`

```markdown
## [2.1.0] - 2026-07-06
### Added
- 支持 Kubernetes OOMKill 类型的部署故障识别
### Fixed
- 修复 flaky test 判定逻辑：阈值从"最近 5 次构建"改为"最近 10 次"

## [2.0.0] - 2026-06-01
### Breaking Changes
- 输出 JSON 结构变更：`diagnosis.root_cause` 从字符串改为结构化对象
### Migration Guide
- 调用方需更新 output schema 的解析逻辑
```

**三种维护位置**（选一）：

```
□ 独立的 CHANGELOG.md（推荐）
□ frontmatter 里的 changelog 字段
□ SKILL.md 顶部的版本历史注释
```

**Git 提交前缀**：

```
feat:     新功能
fix:      Bug 修复
docs:     文档更新
refactor: 重构（无功能变化）
perf:     性能优化
```

> ⚠️ 一个关键提醒（呼应 `skill-distribution` 的 `team-workflow.md`）：
> **CHANGELOG 要记 why，不是 git log。**
> "阈值从 5 次改为 10 次"要说明**为什么**。

## 破坏性变更

**处理原则**：

```
1. 提前公告弃用（至少 30 天）
2. 过渡期同时支持新旧行为（通过 flag）
3. 提供迁移指引
```

**例子**——从 Jest 切到 Vitest：

```yaml
---
name: "Unit Test Generator (Legacy)"
version: "1.5.0"
description: "生成 Jest 单测 —— DEPRECATED，请用 Unit Test Generator v2.x"
stability: "deprecated"
deprecation_notice: |
  本技能仅提供安全修复至 2026-12-31。
  请迁移到 v2.x（使用 Vitest）。
---
```

**MIGRATION.md 该写什么**：

```
□ 什么变了
□ 为什么变
□ 逐步迁移步骤
```

> 独立的 MIGRATION.md 能显著降低支持负担。

## 退役四阶段时间线

| 阶段 | 时长 | 动作 |
|---|---|---|
| **公告** | 破坏性变更**前至少 30 天** | 加 `deprecation_notice` · 写进 CHANGELOG |
| **并行支持** | **60–90 天** | 通过 flag 同时支持新旧行为 |
| **软移除** | **30 天** | 移除旧行为，发布 legacy 技能，迁移文档定稿 |
| **硬移除** | 弃用窗口关闭后 | 归档 legacy 技能，关闭旧 issue |

> **企业级或高流量技能，并行支持期建议延长到 6 个月。**

## 健康指标

| 指标 | 健康 | 警告 | 危险 |
|---|---|---|---|
| **激活精确率** | >90% | 70–90% | <70% |
| **反模式数量** | 3+ | 1–2 | **0** |
| **距上次更新** | <3 个月 | 3–6 个月 | >6 个月 |
| **校验错误数** | 0 | 1–2 | >2 |

> 注意"反模式数量为 0"被列为**危险**——
> 说明你还没遇到过真实的失败，或者没把失败记录进去。

## 维护节奏

| 频率 | 做什么 |
|---|---|
| **每月** | 查激活日志有无异常 · 回顾用户反馈 · 修失效链接 |
| **每季** | 验证时效性知识 · 跑完整测试套件 · 找新的反模式 · 更新依赖 |
| **每年** | 完整审计 · 考虑重构 · **评估是否还需要它** |

**创建 vs 扩展**：

| 场景 | 动作 |
|---|---|
| 新的领域专长 | 新建技能 |
| 现有技能的延伸 | 扩展该技能 |
| **技能 >500 行** | **拆成聚焦的多个技能** |
| 跨领域 | 用组合模式（见 `skill-orchestration` 的 `composition.md`） |
| 实验性的 | 在 DRAFT 建，**失败就删** |

## 自查

```
□ 是否有 version 字段且遵循 SemVer？
□ CHANGELOG 是否记了 why（而非 git log）？
□ 破坏性变更是否有 30 天公告 + 60–90 天并行支持 + 迁移指南？
□ 是否有弃用声明与终止支持日期？
□ 激活精确率是否在 90% 以上？
□ 是否记录了 3 条以上反模式？
□ 距上次更新是否超过 6 个月（时效性知识可能已腐烂）？
□ 是否做过年度"这个技能还有必要存在吗"的评估？
□ MATURE 阶段是否考虑过拆子技能？
```
