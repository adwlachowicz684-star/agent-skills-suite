## 为什么常规可观测性不够

通用 agent 可观测工具追踪的是**模型调用、工具调用、span、延迟、成本**。

但技能调试要回答的是一个**更窄的问题**：

> **在某一次具体运行里，一个自然语言技能
> 到底有没有被激活、被声明、并被视为有影响？**

> ⭐ **技能是自然语言指令，不是函数调用**——
> 它不会在 trace 里留下一行 `skill.activate(name=...)`。
> 这就是为什么"为什么没触发"这事这么难查。

**定位**：这类工具**不是** LangSmith / Langfuse / Phoenix / Braintrust / Weave / OpenTelemetry 的替代品，
而是一个**互补的本地探针**，专门调试技能使用本身。

## 四条证据流

| 证据流 | 说明 |
|---|---|
| **① 被动文件访问轨迹** | 哪些指令文件被真实读过 |
| **② MCP 语义声明** | agent 自己声明"我用了哪个技能" |
| **③ 运行后结构化反思** | 技能被视为有多大影响 |
| **④ 隐私过滤后的本地执行日志** | Codex CLI / Claude Code / Gemini CLI |

**运行快照**：变更过的指令文件会在面板里高亮，
点开能看到**那次运行实际捕获到的纯文本原文**（未提交的变更行也会高亮）。

> 快照与运行元数据一起存——**删掉运行也就删掉了它的来源证据**。

**预检**：

```bash
skilltrace diagnostics            # 快速预检
skilltrace diagnostics --verbose  # 紧凑输出报警时用
skilltrace daemon start           # 连不上 server 时先起守护进程
```

## 排查：没有事件

```
□ 优先用 skilltrace run -- ...，它在启动子进程前就开始追踪
□ 手动生命周期下，确认 skilltrace start 在启动 agent 前已完成
□ macOS：确认 shared probe 在跑（首次启动可能要一次管理员密码，因用 fs_usage）
□ Linux：装 inotify-tools，确认运行状态说 probe 在跑
□ 确认目标仓库有所需的指令面：
     AGENTS.md + .agents/skills/   或   CLAUDE.md + .claude/skills/
```

> ⚠️ **一个高频陷阱**：
> 如果仓库**同时有** AGENTS.md/.agents/skills/ 和 CLAUDE.md/.claude/skills/，
> 追踪工具**可能默认走 agents**，而 Claude 读的是它原生的 `.claude/skills/`。
>
> 解法：`--instruction-profile claude-code`，
> 或拷贝测试仓库时**保留符号链接**（`cp -RP`）。

## 排查：没有语义事件

```
□ 确认 MCP server 注册给了你正在测的那个命令（skilltrace mcp status）
□ 用 skilltrace mcp install 注册 PATH 上找到的所有受支持客户端
□ 改了 MCP 注册后重启 agent
□ 换更强的模型或重跑同一场景
```

> ⚠️ **语义报告和反思依赖 agent 遵循被注入的指令**——
> **小模型有时会忘记调用 MCP 工具的指令**。

检查时间线第一条有没有 instrumentation 警告。

**运行模式**：

| 模式 | 语义声明 |
|---|---|
| `full` | 有 |
| `passive_reflection` | 有 |
| **`passive_only`** | **故意不记录** |

## Trace ID 要贯穿始终

> 从用户进入会话起生成一个任务 ID，
> 贯穿感知、推理、工具调用、输出的所有环节。
>
> **排查问题时，一个 ID 就能捞起整条链路的全部现场。
> 没有这个 ID，任何监控工具都只能看到碎片。**

```python
with trace("production-agent", group_id=request_id,
           metadata={"request_id": request_id}):
    return await Runner.run(agent, user_input)
```

**Agent 系统可观测性五根柱子**：

| 柱子 | 记什么 |
|---|---|
| Span 执行追踪 | 每次 LLM 调用、提示版本、工具输入/输出、RAG 片段、中间推理——**挂在唯一 run ID 下的子 span** |
| Trace ID 贯穿 | 一个 ID 捞起全链路 |
| token / 成本 | 从响应里统一提取 usage 写进 span |
| 工具调用白名单 | 独立鉴权层，禁止 agent 直达高权限接口 |
| 评估层 | 基准评测集 + 线上按比例采样 |

> ⚠️ **最常见的错**：**把模型调用当普通接口来监控**。
> 语义失败（它跑完了但结果是错的）在普通接口监控里完全看不见——
> **必须有评估层**。

## 常见故障对照表

| 现象 | 可能原因 | 排查与解法 |
|---|---|---|
| 看不到任何 trace | Collector 未启动 / 端口不通 / 导入延迟 | 查容器是否在听 4317，查网络 |
| 有 span 但缺模型调用 | 埋点只在部分代码路径执行 | **用装饰器或中间件统一埋点**，别每个分支手写 |
| 提示/响应在日志里泄露 | 未配脱敏 processor | **在 Collector 层统一删除 Prompt 和 Response 文本** |
| token 成本统计不出 | 未记录 usage 字段 | 模型调用后统一提取 usage 写入 span |
| **Agent 循环链路断裂** | 子 span 未挂到父 span 下 | 用 `trace.set_span_in_context(root)` 传递上下文 |
| 工具调用越权 | 缺策略控制层 | 增加工具白名单与操作授权校验 |
| **语义失败发现不了** | 缺评估层 | 建基准评测集，线上按比例采样评估 |

> 最后两条对技能尤其重要：
> **技能跑完了但做错了**，在 trace 里看起来是**一片绿色**。

## 隐私

> ⚠️ **追踪数据里出现敏感内容**：内容录制已启用，
> 而提示、工具参数、输出含敏感数据。

**生产环境**：

```
□ 关闭内容录制（NO_CONTENT 或 false）
□ 敏感数据在进入遥测系统前遮蔽
□ 缩短 BigQuery 之类的保留时长
□ 成本过高就切 NO_CONTENT 模式，并禁用未使用的层级
```

**本地探针也要隐私过滤**——技能正文可能含内网路径、内部约定。

## 自查

```
□ 是否有贯穿全链路的 Trace ID？
□ 埋点是否用统一中间件（而非每分支手写）？
□ 是否区分了"跑完了"和"做对了"（有没有评估层）？
□ 生产环境是否关闭了内容录制？
□ 是否知道目标仓库用的是哪一套指令面（agents 还是 claude）？
□ 语义声明依赖 agent 遵循指令——是否用了足够强的模型？
□ 是否记录了每次运行的指令文件快照（用于事后归因）？
```
