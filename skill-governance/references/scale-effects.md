## 临界点一：技能库规模

> 一份对 1,236 个技能的实测（mega repo，23.7k stars）：

### 目录税（catalog tax）

```
规范建议渐进式披露：每会话开头加载所有已装技能的 name + description
规范估算每条 50–100 tokens

实测：1,234 个可解析的技能
     平均 38 tokens/条
     总计 46,851 tokens
     ⭐ = 128k 上下文的 36.6%，
        在任何一个技能被激活、用户打第一个字之前就已消耗
```

> ⭐ **最讽刺的部分**：
> **38 tokens/条低于规范估算，恰恰因为这些描述写得很差**——
> 简略、堆砌关键词、缺少触发引导。
>
> **如果把描述写好（详细、明确触发条件、与邻近技能消歧），
> 每条会更长，总目录税反而更贵。**
>
> → 这个仓库为一份"没干好活的目录"付了 37% 的上下文税，
> 而修好描述会让税更重。

**对照组**：精心挑选 5 个知名技能，目录内容共 **126 tokens**
（约 0.2–0.4% 的 128k 窗口）。

### 目录税只是地板

```
激活一个技能时，会加载完整的 SKILL.md 正文
中位技能 1,728 tokens，激活 5 个 ≈ +8,600 tokens

⭐ 合计约 55,000 tokens 的技能开销
  = 128k 上下文的 43%
  ——在 agent 读过你项目的任何文件、处理过你提示的任何一行之前
```

### 触发打架

```
主题堆积：
  84 个技能提到 security · 74 个提到 documentation
  60 个提到 React · 47 个提到 debugging

用户说"创建 API 文档"  → 20 个技能是合理匹配
用户说"修复这个安全漏洞" → 10 个技能竞争

→ agent 必须靠描述文本消歧，
  而很多描述用的是近乎相同的措辞
```

** outright 重复**：13 组（26 个）技能内容 85–100% 相同，
且是仓库自己的组织方式产生的内部副本。

> 呼应 `skill-evaluating` 的 `metrics.md` 的"候选池 5 → 100 精确率掉 10 倍"、
> `skill-refining` 的 `discovery-ux.md` 的"装太多描述被压缩"、
> `skill-distribution` 的 `library-ops.md` 的清库——**这里是同一结论的量化版**。

## 临界点二：代码库规模

> 一份 1,281 次评分运行、覆盖 40+ 最大开源仓库的基准研究：

```
只用本地工具（grep / 读文件 / glob）的 agent
在代码库超过约 400,000 行后开始系统性吃力

低于这条线：加代码智能工具，收益 delta = −0.080
            ⭐ "工具带来开销；grep 通常就够用"
400K–2M 行之间：翻转为 +0.259
```

> ⭐ **"厂商公布对自己产品品类的负数"值得信任**，
> 而且这句话对多数读者最有用——**它告诉你：你可能根本没有这个问题**。

**另一个实证**（500 个 SWE-bench Verified 实例、61 种上下文配置）：

```
⭐ 头号发现：更多上下文并不持续改善修复表现

真正重要的：
  · ⭐ 文件级定位是主导因素——比"无文件基线"提升 15–17 倍
  · 成功的修复集中在约 6–10 个相关文件的配置里
  · ⭐ 行级上下文扩展常因噪声放大而降低表现
```

```
6–10 个文件 ≈ 一个"范围良好的任务"的形状
```

## 真正的变量：分散度

> ⭐ **后续研究把这条线移动了**：

```
"答案更少取决于代码库大小，而取决于相关工作如何分布其中。"

检索难度权重（在查看结果前就固定）现在把
"仓库跨度"和"目录分散度"排在"总行数"之上：

  ⭐ 4000 万行的 monorepo，若相关代码都在一个目录里，
     表现得像个小仓库
  ⭐ 200 万行的资产，若答案散落在四个服务里，
     才是更难的检索问题
```

**一个清醒的补充**：

```
288 个两组都能到达相同代码的任务中：
  结构化检索把文件级 F1 从 0.091 提到 0.240
  recall 从 0.120 提到 0.272
  ⭐ 但"总体任务完成奖励基本没有变化"

后续普查发现：该语料约 74% 用 grep 就能解决
```

> ⚠️ **正确读法**：
> **行数是你最容易测的代理指标，但真正伤人的是"相关代码隔多远"。**
> 而**分散度恰恰是你能移动的变量**。

## 对技能写法的直接含义

**① 技能要主动收窄扫描范围**

```
□ 在 .gitignore 基础上配置工具专属忽略规则
  （.cursorignore / allowed-tools 限制文件访问范围）
□ ⭐ 这不是可选优化，是"能用"和"不能用"的分界线
□ 排除构建产物、测试 fixture、历史备份、大型静态资源
  ——多数项目里有效代码占比不到 15%
```

**② 单文件粒度**

```
□ 超过上下文处理上限的文件会被强制截断，
  agent 拿到的是残缺代码
□ 过度碎片化又让跨文件引用成本飙升
□ ⭐ 合理粒度：单文件 300–800 行，职责单一，
   有清晰的模块级文档字符串
```

**③ 为 agent 提供结构化项目摘要，替代全量加载**

```
□ 核心逻辑与配置模板分离
□ 复杂模块加简短的 module-level docstring
□ ⭐ 这些在传统开发里是"好习惯"，
    在 agentic coding 里是"必需品"
```

**④ 技能库要保持小，或者分层**

```
□ 精心挑选的 5 个技能 = 126 tokens 目录
□ 1,234 个技能 = 46,851 tokens 目录
□ ⭐ 差距 370 倍，而后者描述质量还更差

□ 定期审计描述差异化程度
□ 合并功能重叠的技能
□ ⭐ 分类分组，而非扁平列表
□ 用向量预筛 description（见 skill-vs-rag.md 的精巧混合）
```

**⑤ 别假设"更多上下文更好"**

```
□ 行级上下文扩展常因噪声放大而降低表现
□ ⭐ 技能里写"把整个文件读进来"可能是负优化
□ 优先写"定位到相关文件"的步骤
```

## 自查

```
□ 技能库目录税是否量过（多少技能 × 平均多少 token）？
□ 是否存在主题堆积（同一领域十几个技能）？
□ 是否有内容 85%+ 相同的重复技能？
□ 是否按域分组而非扁平列表？
□ 技能是否主动限制了扫描范围？
□ 是否排除了构建产物与 fixture？
□ 是否提供了结构化项目摘要替代全量加载？
□ 单文件是否控制在 300–800 行？
□ 是否写"定位相关文件"而非"读入整个文件"？
□ 是否评估过"分散度"而非只看总行数？
□ 是否知道自己其实可能没到 400K 行这条线（不必过度采购）？
```
