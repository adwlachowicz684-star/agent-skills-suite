## 1. ⭐ 退役信号

| 信号 | 具体表现 |
|---|---|
| 调用量持续下降 | 近 30 天比上月下降 80% 以上 |
| ⭐ 被替代 | 功能更完善的技能已上线并接管流量 |
| 外部依赖下线 | 依赖的 API 或服务不再存在 |
| 业务场景消失 | 团队不再用该平台，或业务线被裁撤 |
| ⭐ **Owner 缺失** | 原 Owner 离职，长期无人认领维护 |

**另一个口径的退役标准**（团队级）：

```
· 90 天没有更新
· 与当前工具版本存在兼容问题
· ⭐ 存在更好的替代方案
```

> ⭐ **这套标准存在的意义是防止"僵尸技能"问题——
> 过时的工作流滞留在库里，把新成员搞糊涂。**

## 2. ⭐ 退役四阶段（约 35–42 天）

以 `pipeline-diagnosis` 被 `pipeline-diagnosis-v3` 替代为例：

**阶段 1：标记 deprecated（14 天）**

```
├─ frontmatter 增加 deprecated: true
├─ ⭐ description 开头加 [DEPRECATED] Use pipeline-diagnosis-v3 instead.
├─ 通知所有已知调用方
└─ ⭐ 日志中对每次调用增加 deprecation warning
```

> ⭐ 第 2 条最巧妙：**把替代方案写进 description，
> 模型读到的那一刻就知道"不该用我"**。

**阶段 2：流量迁移（7–14 天）**

```
├─ ⭐ 把原本匹配到旧版的请求透明重定向到新版
├─ 监控重定向后的任务完成率是否正常
└─ ⭐ 不正常就暂停重定向、排查原因
```

**阶段 3：灰度下线（7 天）**

```
├─ 逐步降低旧版流量 100% → 50% → 20% → 5% → 0%
├─ ⭐ 每降一级观察 2 天确认无异常
└─ ⭐ 同时监控"找不到技能"的错误——说明有未迁移的调用方
```

**阶段 4：归档**

```
├─ 从技能注册中心注销
├─ ⭐ SKILL.md 和相关文件移至 archive/ 目录，⭐ 不删除
├─ 保留历史日志和评测数据
└─ 更新 CHANGELOG，记录退役原因和替代方案
```

## 3. ⭐ 归档 ≠ 删除

```
skills/
├── daily-brief/        ← 在用
├── summarize/          ← 在用
└── archived/
    └── old-search/     ← ⭐ 已归档，不加载但保留备用
```

> ⭐ **扫描器只扫 skills/ 的直接子目录，
> ⭐ archived/ 里的技能不会被加载、不占上下文，
> 但随时可以拿回来。**

**彻底删除标准**：

```
⭐ 归档超过 6 个月，且确认不会再用到
```

**另一条硬规则**：

> ⭐ **绝不留一个指向已移动/已重命名文件的技能——要么修，要么退役。**

## 4. 删除前的降级诊断

一次没有隐式触发，可能只是配置或 description 问题。**按顺序排查**：

```
① 确认技能位于当前环境支持的位置
② 检查 SKILL.md 文件名、目录和元数据
③ 检查 description 是否明确写出了触发场景
④ ⭐ 显式调用一次，区分"未发现"和"未隐式触发"
⑤ 用既有验证器或检查清单验收输出
```

确认**不是**配置问题后，再选择迁移位置：

```
· 项目常驻约束       → 移入 AGENTS.md
· ⭐ 确定性步骤       → 拆成脚本
· 一次性要求         → 回到任务提示词
· ⭐ 有价值但频率低   → 先停用观察，⭐ 保留版本记录
```

**删除前至少记录六项**（没有数据时先观察，不急着下结论）。

> ⭐ **一个技能是否该退出，不应由模型版本或单次 token 决定。
> 更可靠的判断是：它是否在特定任务中反复出现、
> 是否包含模型无法自行知道的约束、是否能够明确验收。**

## 5. 六个定期审计项

对每个 SKILL.md：

```
① ⭐ 文件路径漂移：每个被引用的路径是否仍存在
   grep -oE '[a-zA-Z0-9_./-]+\.(swift|ts|tsx|mjs)' .claude/skills/*/SKILL.md
   然后逐个确认能解析
② ⭐ 规则漂移：技能的规则是否仍与 CLAUDE.md / AGENTS.md 一致
③ 约定漂移：frontmatter 完整、allowed-tools 最小权限、清单存在
④ ⭐ 覆盖缺口：有没有重复出现却没有技能的工作流 → 标记为待创建
⑤ 重叠未合并
⑥ 陈旧技能已退役（不是留着指向死路径）
```

**产出一份短报告**：

```
OK / fix-needed / retire，每项一行原因
```

**维护节奏**（可执行日历）：

```
每次修改（即时）：  更新版本号与 changelog · 备份旧版本 · 更新注册表
每月（20 分钟）：   跑一遍所有技能的正向触发测试 · 标注使用频率
                   ⭐ 把超 2 个月未用的标为"待复查"
每季度（1 小时）：  复查"待复查"→ 决定优化还是归档
                   检查 description 是否需要更新
                   做一次拆分/合并审查
```

## 速查

```
退役信号：
□ 30 天调用降 80%
□ ⭐ 被替代
□ 外部依赖下线
□ 业务场景消失
□ ⭐ Owner 缺失

四阶段：
□ 1 标记 deprecated 14 天（⭐ description 开头写替代方案）
□ 2 流量迁移 7-14 天（透明重定向 + 监控完成率）
□ 3 灰度下线 7 天（100→50→20→5→0，每级观察 2 天）
□ 4 归档（⭐ 不删除，移 archive/）

□ ⭐ archived/ 不被扫描 → 不占上下文但可恢复
□ ⭐ 归档 >6 个月且确认不用 → 才删
□ ⭐ 删除前先做五个降级诊断
□ ⭐ 绝不留指向已移动文件的技能
□ 六项定期审计，产出 OK/fix/retire 三态报告
□ ⭐ 退役判断看"反复出现 + 模型不知的约束 + 可验收"
```

**一句话**：

> ⭐ **退役不是直接删除 SKILL.md——
> 一个负责任的退役流程要确保所有依赖方都有时间迁移。**
