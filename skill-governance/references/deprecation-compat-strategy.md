## 1. ⭐ 向后兼容的四条原则

> **向后兼容 = 新版本能正确处理旧版本的所有输入。**

**① 只增加不删除**

```
✅ 可以增加新的可选参数，旧 agent 不传时用默认值
✅ 可以增加新的输出字段，旧 agent 会忽略不认识的字段
❌ 不能删除已有的参数或字段——旧 agent 仍然需要它们
❌ 不能修改已有参数的类型或语义
```

**② ⭐ 可选参数优先**

```
⭐ 设计时尽量把参数设为可选，而不是必选。

可选参数 → 后续可增加，不破坏兼容性
必选参数 → ⭐ 一旦增加，⭐ 所有旧 agent 都会失败
```

> ⭐ 这条最容易被忽略：**今天新增一个必选参数，等于让所有存量调用方立刻崩溃。**
> 所以"这个参数大多数场景不需要"就应当设为可选。

**③ 版本协商**

```
⭐ 当接口需要不兼容变更时，用版本协商：
   技能声明支持的版本列表 → agent 选择使用的版本
   → 不同版本的 agent 可以用不同的接口格式
```

**④ 先标记 deprecated，不要直接删**

```
当某个参数或字段不再推荐：
   先标记为 deprecated
   ⭐ 文档中说明废弃原因和替代方案
   ⭐ 测试用例可以保存和复用
```

## 2. ⭐ 自动升级的分界线

```
patch / minor 版本：⭐ 不破坏兼容性 → 平台可以透明升级
major 版本：⭐ 含 breaking changes → ⭐ 必须用户主动确认才能迁移
```

**平台侧要做什么**：

```
⭐ 维护每套技能的兼容性矩阵
⭐ 提前标注哪些版本之间是 "safe to auto-upgrade"
```

> ⭐ 这个矩阵是"能不能自动升级"的唯一依据——
> 没有它就只能一律保守（全部手动确认），或一律激进（迟早出事）。

**MAJOR 版本的两个硬性交付物**：

```
① Breaking Changes 说明
② ⭐ Migration Guide（迁移指南）
```

**Migration Guide 该写什么**（一个具体例子）：

```markdown
### Breaking Changes
- `output.root_cause` 从字符串改为结构化对象
- Step 4 的依赖回滚行为从"自动执行"改为"需用户确认"

### Migration Guide
- 调用方需更新 output schema 的解析逻辑
- 详见 docs/migration-v1-to-v2.md
```

**CHANGELOG 格式**：遵循 Keep a Changelog 规范，六个分类：

```
Added · Changed · Deprecated · Removed · Fixed · Security
```

## 3. ⭐ 废弃三阶段

> 平台若不提供清晰的 Deprecation 流程，
> **会导致用户依赖悬空、任务无法执行**。

**第一阶段：公示期**

```
· 在技能页面、版本列表、用户 Dashboard 明确标注废弃版本
· ⭐ 显示 EOL（End of Life）倒计时
· ⭐ 通过 Webhook 或邮件通知所有引用了该版本的用户
· 提供"迁移到哪个具体版本"的建议
```

**第二阶段：引导迁移**

```
· ⭐ 为每个废弃版本生成 Migration Guide
   ——API 变更对照表、代码迁移示例、常见问题排查
· ⭐ 最好提供自动化迁移工具（如 AST 重写脚本），降低迁移成本
```

**第三阶段：强制下线**

```
· 公示期结束后，⭐ 执行时拒绝加载废弃版本
· ⭐ 返回明确的错误信息，并⭐ 重定向到最新稳定版
```

> ⭐ 第三阶段那两个"⭐"很关键：
> **拒绝但给明确错误 + 指向新版本**，而不是静默失败。
> 与《governance》的"静默失败是元问题"完全一致。

## 4. ⭐⭐ 跨版本循环依赖

> ⭐ **这是依赖解析里最容易漏的一种环。**

```
平台维护一个有向无环图（DAG）：
   每次提交新版本时，对新增的依赖声明做拓扑排序
   检测到环则拒绝发布
```

**检测算法本身不复杂**（DFS 或 Kahn），**容易忽略的是依赖版本范围**：

```
即使 Skill A@1.0 和 Skill B@1.0 之间不循环，
⭐ 也可能出现这种跨版本循环：
   Skill A@1.0  依赖  Skill B@2.0
   Skill B@2.0  反向依赖  Skill A@1.0
```

> ⭐⭐ **只看"名字"维度没有环，但加上版本号就有环了。**
> 所以检测必须在 **（名字, 版本）** 这个二维空间上做，不能只在名字上做。

> 这与《patterns》的 `solid-for-skills.md` 呼应：
> **技能依赖图是 DAG，要防环**——这条给出了"防环要防到版本这一层"。

## 5. 灰度发布

```
⭐ Canary Release：把新版本逐步推给一部分用户，观察效果后再全量。
这是降低发布风险的关键手段。
```

**MAJOR 版本必须**：提供迁移指南 + **通过灰度发布逐步生效**。

## 速查

```
向后兼容：
□ ⭐ 只增加不删除；不修改已有参数的类型或语义
□ ⭐⭐ 参数尽量可选——新增"必选"会让所有旧调用方崩溃
□ 版本协商处理不兼容变更
□ ⭐ 先标记 deprecated 并写明原因 + 替代方案

自动升级：
□ patch/minor → 可透明升级
□ ⭐ major → 必须用户主动确认
□ ⭐ 平台维护兼容性矩阵，标注 safe to auto-upgrade
□ ⭐ MAJOR 必须交付：Breaking Changes 说明 + Migration Guide
□ CHANGELOG 六分类（Keep a Changelog）

废弃三阶段：
□ ① 公示期：标注 + ⭐ EOL 倒计时 + ⭐ 主动通知引用方
□ ② 引导迁移：⭐ Migration Guide + ⭐ 自动化迁移工具
□ ③ 强制下线：⭐ 明确报错 + ⭐ 重定向到最新稳定版（绝不静默）

依赖：
□ DAG + 拓扑排序，有环则拒绝发布
□ ⭐⭐ 环的检测要在（名字, 版本）二维上做，不能只看名字

□ ⭐ MAJOR 走灰度发布
```

**一句话**：

> ⭐ **只看"名字"没有环，加上版本号就有了——
> A@1.0 依赖 B@2.0、B@2.0 依赖 A@1.0 同样是环。**
