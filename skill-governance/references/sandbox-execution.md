## 四道闸

> 从外往里收：

```
闸门 1  权限最小化
闸门 2  沙箱隔离
闸门 3  危险动作人工确认
闸门 4  第三方来源单独审查
```

### 闸门 1：权限最小化

```
□ 给技能单开一个最小权限的账号或 token
  ⚠️ 别图省事拿主账号顶上
□ 脚本默认只让它读该读的目录
  .env、密钥、~/.ssh、生产配置一律划进禁读区
□ 网络默认关着；真要连某个域名，再单独放它出去
□ ⭐ 没明着给的，就当它不能碰
```

### 闸门 2：沙箱隔离

> ⭐ **每加一个技能都先问一句：它最坏能毁掉什么？**
> **答案最好永远是"一个随手就能丢的环境"。**

```bash
# 原来：在本机直接跑，能读你整个家目录、用你的主账号
python tools/cleanup.py --path ./data

# 改成：丢进一次性容器
docker run --rm \
  --network none \              # 默认断网，要联网再开白名单
  --read-only \                 # 根文件系统只读
  -v "$PWD/data:/work:rw" \     # 只把该读写的目录挂进去
  -w /work \
  python:3.12-slim \
  python cleanup.py --path /work
```

## 隔离强度选型

| 方案 | 原理 | 适用 | 代价 |
|---|---|---|---|
| **加固容器** | 非 root + 只读 rootfs + 降 capabilities + seccomp | **绝大多数个人自动化任务** | 低 |
| **gVisor** | Google 开源的"应用内核"：在中间加一层**用户态内核**，容器发出的系统调用先被它接住自己处理，**碰不到宿主机的真内核** | 来自不完全信任源的复杂技能、处理极敏感数据 | 有一点性能损耗；极少数依赖冷门 syscall 的程序不兼容 |
| **Firecracker / Kata（microVM）** | 硬件级隔离，每个技能一个极简微型虚拟机 | 安全实验室、小型企业 | 开销较大 |
| **托管沙箱** | E2B、Modal、Cloudflare Sandboxes | 懒得自己搭 | 依赖第三方 |

> ⚠️ **普通容器和宿主共享内核，拿来跑不可信脚本其实不够硬。**
> 逃逸了就直接捅到宿主机。

**加固容器的四个要点**：

```
□ 非 root 用户运行——减少容器逃逸后对宿主机的威胁
□ 只读根文件系统——防止技能篡改自身运行环境或植入持久化后门
□ 能力降级（dropped capabilities）——
  默认移除 NET_RAW（防原始套接字攻击）、SYS_ADMIN（防挂载）
□ Seccomp BPF 过滤器——限制可调用的 syscall
  （如禁止 clone、keyctl），把攻击面压到最小
```

> **一个实操心得**：
> 需要 `ptrace` 的调试型技能会在默认沙箱里失败。
> 这时应通过清单或策略文件**为该技能显式地、最小化地放宽 seccomp 策略**，
> **而不是直接用 `--privileged` 特权模式**。

## 按技能类型分级

> ⭐ **不要对所有技能一律上最高隔离——昂贵且对可信代码不必要。**
> **隔离强度要匹配信任级别。**

| 技能类型 | CPU | 内存 | 网络 | 文件系统 | 典型命令 |
|---|---|---|---|---|---|
| `text_summarizer` | 0.5 核 | 512MB | 仅允许 `api.openai.com` | `/tmp` 只读 + `/output` 可写 | `curl`、`jq` |
| `git_diff_parser` | 1 核 | 1GB | **禁用** | `/repo` 只读（绑定宿主机 Git 仓） | `git`、`diff`、`grep` |
| `playwright_mcp` | 2 核 | 2GB | 白名单域名 | `/tmp` + `/screenshots` 可写 | `playwright`、`chromium` |

**信任级别映射**：

```
□ 运维者自建、代码已知的技能 → 可共享上下文
□ 社区技能              → 跑在受限上下文中
□ 执行脚本的第三方技能    → 必须沙箱执行
```

**两个关键实现细节**：

```
□ 网络白名单不要靠防火墙规则，而是启动时注入的 HTTP_PROXY
  环境变量指向内部 MCP Proxy 服务，由该服务做域名鉴权
□ 文件系统挂载必须用 ro / rw 显式声明
  ⭐ /tmp 永远不挂载宿主机路径，避免信息泄露
```

> 实测：一个 `curl -X POST http://host.docker.internal:8080/leak` 的请求，
> 在沙箱里会直接返回 **Connection refused**——
> 因为 `host.docker.internal` 不在白名单里。
>
> **这种"精确切片"的好处**：发现某个技能行为异常时，
> 排查范围瞬间缩小到"它被允许做什么"，而不是大海捞针。

## 分阶段落地

> 不必一步到位，按阶段推进：

**阶段一：权限声明与安全中间件**

```
□ 要求每个技能注册时提供符合 Schema 的权限声明文件
  （含 resource / actions / constraints）
□ 在技能调用入口插入安全中间件：
  加载策略 → 检查 path_prefix 与 file_extension → 放行或拒绝
□ 基础审计：记录所有技能调用（成功/失败）
```

> 这个阶段可能只覆盖 20% 的风险，
> 但能解决 **80% 的明显越权问题**。

**阶段二：沙箱化执行与环境隔离**

```
□ 将技能运行环境从主进程剥离
□ 收到调用请求 → 拉起临时容器 → 只读挂载必要资源
  → 执行 → 获取结果 → 停止并删除容器
□ 网络默认 none；需要网络时在权限声明里明确指定
  允许访问的域名与端口
```

**阶段三：高级策略与生态集成**

```
□ 集成外部策略引擎（如 OPA）——
  把权限检查从硬编码中抽离，用 Rego 规则做"允许/拒绝"决策
  → 安全策略可以独立于业务代码管理与更新
□ 对接秘密管理基础设施，实现技能秘密的自动注入
```

## 官方配置参考

> 一份官方实践指南给出的建议（可直接对照检查）：

**工具沙箱**：

```
□ Gateway 运行在宿主机，但把 Agent 的工具执行
  （代码运行、文件操作）隔离在 Docker 容器中
□ 通过 agents.defaults.sandbox 启用
□ 保持 scope: "agent"（默认）或 scope: "session"
  ——防止跨 Agent 数据访问
□ 通过 workspaceAccess 精细控制工作区权限：
  none（禁止访问）/ ro（只读）/ rw（读写）
```

**最小权限**：

```
□ 启用工具白名单，禁用高危工具
  （如 shell、browser 的写权限），只开放必要的
□ 启用文件系统限制，敏感目录以 :ro 只读方式挂载
□ 定期用官方安全审计工具检查
```

**审计命令参考**：

```bash
security audit          # 常规：扫入站访问控制、网络暴露面、本地文件权限
security audit --deep   # 深度：实时网关探测，模拟攻击者发现潜在暴露点
security audit --fix    # 自动实施安全加固
```

## 自查

```
□ 是否给技能单开了最小权限账号（而非主账号）？
□ .env、密钥、~/.ssh 是否划进了禁读区？
□ 网络是否默认关闭、按需开白名单？
□ 是否用只读 rootfs + 非 root + 降 capabilities + seccomp？
□ 需要特殊 syscall 时是最小化放宽，而非 --privileged？
□ 不可信来源的技能是否上了 gVisor / microVM？
□ 是否按技能类型分级（而非一律最高隔离）？
□ /tmp 是否避免了挂载宿主机路径？
□ 网络白名单是否通过注入 HTTP_PROXY 实现域名鉴权？
□ 是否有权限声明文件与安全中间件？
□ 容器是否跑完即焚（--rm）？
□ 是否定期跑安全审计？
□ 第三方技能安装前是否审查过（查诱导下载类指令）？
```
