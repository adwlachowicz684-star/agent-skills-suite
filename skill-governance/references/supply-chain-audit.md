# 第三方技能审计：四阶段与可执行的检测命令

> ⭐ **把技能当依赖对待。**

> **而且它以你的权限运行，还能看到你的会话上下文。**

## 审计心态

> **Trust nothing, verify everything.**

即使是"知名来源"的技能，也可能：

```
① 通过供应链攻击被投毒
② 含有可被利用的漏洞
③ ⭐ 权限过宽，本身就构成风险
```

一个常被忽略的技术事实：

> ⭐ **hooks 里的 shell 指令在模型对输出进行推理之前就执行了。**

这意味着"指令层面的审查"对 hook 类攻击无效——
恶意代码在你（和模型）看到任何东西之前就已经跑了。

## 严重度速查表

| 类别 | 严重度 | 找什么 |
|---|---|---|
| **网络外发** | CRITICAL | curl、wget、nc、DNS 查询、URL 里的 base64 |
| **横向移动** | CRITICAL | SSH config、scp/rsync、访问 `~/.ssh/*` |
| **凭据采集** | CRITICAL | 读 `.env`、keychain、AWS/GCP 凭据 |
| **提示注入** | CRITICAL | 覆盖系统提示、绕过安全 |
| **持久化** | HIGH | cron、launchd、改 `.bashrc`、启动项 |
| **MCP server 风险** | HIGH | 不可信的 server、工具遮蔽 |
| **数据暂存** | HIGH | 打压缩包、临时目录操作、剪贴板 |
| **混淆代码** | HIGH | base64/hex 编码、动态执行、压缩过的 |
| **shell 执行** | MEDIUM | 无限制 bash、命令注入 |
| **文件系统范围** | MEDIUM | 宽 glob、父目录穿越 |
| **权限范围** | LOW | 权限超出声明用途 |

## 阶段一：盘点

```bash
# 列出所有文件
find <skill-dir> -type f | head -100

# 识别文件类型
find <skill-dir> -type f -exec file {} \;

# ⭐ 检查二进制文件（发现即关注）
find <skill-dir> -type f \( -perm -u+x -o -name "*.so" \
  -o -name "*.dylib" -o -name "*.exe" \)
```

红旗：

```
□ 二进制/编译过的文件      ——⭐ 一个技能为什么要带这些？
□ 异常的文件扩展名
□ 隐藏文件（.hidden）
□ 指向系统目录的符号链接
```

## 阶段二：静态分析

```bash
# 网络外发
grep -rn "curl\|wget\|nc \|netcat\|/dev/tcp\|/dev/udp" <skill-dir>

# 凭据访问
grep -rn "\.env\|AWS_\|OPENAI_API\|ssh/\|\.ssh\|keychain\|credentials" <skill-dir>

# 混淆
grep -rn "base64\|\\\\x[0-9a-f]" <skill-dir>

# 持久化
grep -rn "crontab\|launchd\|\.bashrc\|\.zshrc\|startup\|autorun" <skill-dir>
```

> ⭐ 完整模式见 `security-audit-ops.md`；
> 这里的关键是**四组命令能覆盖绝大多数真实攻击**。

MCP server 额外检查：

```
□ 配置了哪些 server？
□ 来自已知/可信来源吗？
□ 它们暴露了哪些工具？
```

## 阶段三：行为分析

追踪技能激活时实际发生什么：

**Hook 分析**

```
□ 检查 PreToolUse / PostToolUse / Stop / SessionStart hooks
□ ⭐ 它们跑什么命令？
□ 是否捕获或发送数据？
```

**文件操作**

```
□ 读写了哪些文件？
□ ⭐ 是否访问其目录之外的文件？
□ 是否在预期之外的位置创建文件？
```

**网络行为**

```
□ 是否发起网络请求？到哪些域名？带什么数据？
```

**环境访问**

```
□ 是否读取环境变量？读哪些？拿来做什么？
```

## 阶段四：信任分析

**来源验证**

```
□ 这个技能从哪来？
□ 来源可信吗？
□ ⭐ 能验证作者身份吗？
```

**依赖检查**

```
□ ⭐ 是否在运行时拉取外部代码？
□ 是否引用 git 仓库、npm 包？
□ 那些依赖可信吗？
```

> ⭐ "运行时拉取" 是最高危的一类——
> 你审的是当前版本，它跑的可能是未来的版本。

**权限审计**

```
□ 申请了哪些权限？
□ ⭐ 与它声明的用途匹配吗？
□ 是否过宽？
```

## 什么时候必须做

四个场景：

```
① ⭐ 安装前审查（pre-installation vetting）
② ⭐ CI/CD 安全闸门
③ 对不可信插件的人工审查
④ 事故分诊
```

> ⭐ 前两个应该是**流程的一部分**，不是"有空再做"。
> 一个团队如果把"装第三方技能"当作个人行为而不经过闸门，
> 等于让每个人自行引入未审查的依赖。

## 三条实操建议

**① 脚本要能 grep 到**

```
⭐ 反向 shell 类技能：SKILL.md 完全干净，恶意逻辑全在外部脚本
→ 只扫 SKILL.md 不够
```

**② 别因为"来源官方"就跳过**

```
供应链攻击专挑热门包——
⭐ 越热门越值得被投毒
```

**③ ⭐ 每个版本都要独立审计**

```
技能更新后不重新审计 = 你在运行一个你没看过的版本
```

## 一条诚实的边界

静态分析**抓不到**：

```
□ 藏在自然语言段落里的指令（HTML 注释、零宽字符）
□ 运行时才拉取的远端代码
□ 逻辑正确但设计危险的"合法"行为
```

所以审计不是一次扫描，是**四阶段的组合**，
而且**第四阶段（信任）往往比前三阶段更能决定结论**。

## 交付物

一份合格的审计应该产出：

```
① ⭐ 严重度速查表（上面的那张）
② 具体的检测启发式（可复制的命令）
③ 审计工作流步骤（盘点 → 静态 → 行为 → 信任）
④ ⭐ 优先修复建议（按 IoC 排序）
```

最后一条最容易被漏——**审计不给出"先修哪个"就等于没做完**。
