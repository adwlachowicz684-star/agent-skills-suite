## 三个 token 桶

> ⭐ **装任何省 token 的技能之前，先把账单拆成三桶。**
> **输出压缩只碰得到其中一桶。**

| 桶 | 包含 | 最优策略 |
|---|---|---|
| **输入** | 你的 prompt、仓库上下文、工具输出、技能指令、日志 | 缩小上下文、更好的文件选择、压缩项目记忆 |
| **推理 / thinking** | 模型内部推理预算（暴露或计费的部分） | 任务范围收敛、更简单的模型路由、减少重试 |
| **输出** | agent 可见的回答、摘要、解释、计划 | 简洁响应模式、更短的报告 |

> **输出压缩只动第三桶**——这是它效果有限的根本原因。

## Caveman 的真相

> Caveman 是流行的压缩风格技能，让 agent 用低填充词风格回答，
> 保留代码、命令和错误信息。

**它自己的文档就写明了边界**：

```
□ 主要压缩输出 token
□ 输入与推理 token 不减
□ ⚠️ 技能本身每轮增加约 1–1.5K 输入 token
```

**独立测试的结论**：

| 来源 | 声称 | 实测 |
|---|---|---|
| 宣传 | 65–75% | — |
| **JetBrains 真实 agentic 任务** | — | **约 8.5%** |

> ⭐ **这意味着输出压缩是"中小的优化"，不是完整的成本策略。**
> 它在**冗长、输出密集**的工作流里省钱，
> 在**本来就简短**的会话里**反而亏钱**（技能自身 1–1.5K 输入 > 省下的输出）。

**正确的使用方式**：

```
□ 设为可开关——面向客户的内容、演示时关掉
□ 只在输出厚重的工作流里开
□ 压缩率从 50% 起步，验证输出后再加大
```

## 一个 16x 的真实案例

> 关键在于：**省钱的大头不在技能内容，而在会话与上下文管理。**

```
起点（Sonnet）              $0.400/query
改用 Haiku + 内联 TOOLS.md  $0.140   -65%
修复会话模型锁定            $0.150   （暴露了真实成本）
清空 116K 会话历史          $0.024   -84%
热缓存（重复查询）          $0.005   -99%
```

**最戏剧性的一步**：

```
会话上下文累积到 116K token
按 Haiku 的 cache_write 价 $1.25/MTok
→ 光冷启动写缓存就要 $0.145/次

清空后：116K → 14K（只剩系统提示与框架开销）
冷启动成本 $0.145 → $0.019
```

**还有一个"彩蛋"**：

> 调查中发现框架**默认加载了 9 个没人要的技能**：
> weather、iMessage、Slack、GitHub……
> 而这个 bot **只跑分析脚本，不需要看天气也不需要发 iMessage**。
>
> ⭐ **九个没用的技能 = 每次请求都在白白烧几百 token。**

> 呼应 `skill-distribution` 的 `library-ops.md` 的清库与 `/skill-doctor`：
> **每个技能都在为每一轮付费，不管你有没有用过它。**

## 技能本身会增加成本

> ⭐ **技能不是免费的——它通常就是注入模型的额外指令。**

一份 2026 年的 SkillReducer 研究扫描了数以万计的技能，发现系统性低效：

```
□ 许多技能缺少好的路由描述
□ 大量正文内容不可操作（non-actionable）
□ 引用文件可能注入非常大的 token 负载
```

> **教训不是"别用技能"，而是"谨慎路由技能"。**

一个好技能应该是：

```
□ 短的触发描述
□ 紧凑的核心正文
□ 可选的 references，只在需要时加载
```

> 这也解释了为什么 `skill-refining` 的 `context-budget.md` 强调**按需加载**——
> **技能是成本项，不是纯收益项。**

## 五个真正有效的杠杆

**① 别让 agent 每次重新发现仓库**

```
□ 维护一份紧凑的仓库地图：主要目录、数据文件、
  路由约定、测试命令、部署说明
□ 给任务局部上下文：指向具体文件或功能区域，
  而不是让它搜整个仓库
□ 变更后留简短决策日志，让下个会话不必重新推导
□ 限制日志：贴失败的那一段，而不是整个终端回滚
```

**② 模型路由 > 一个模型打天下**

| 任务 | 推荐 |
|---|---|
| 找文件、摘要日志、分类错误 | **便宜/快模型** |
| 实现复杂代码改动 | 强编码模型 |
| 安全或架构权衡评审 | 旗舰模型 |
| 每天都重复的同一工作流 | **脚本 / CI / 确定性重放** |

> 实测：**分层路由通常比全部走旗舰省 70–80%**，
> 而简单技能的质量差异可以忽略——
> **便宜模型处理结构化、定义良好的任务并不比旗舰差。**

**③ 确定性重放是最强的省钱形式**

> ⭐ **如果任务重复且稳定，最便宜的 agent 调用就是"不调用 agent"。**
> 记录一次成功的工具调用轨迹，之后用参数确定性重放——
> 后续运行绕过完整的 LLM 推理。

**④ 响应缓存**（适合重复操作）

```
✅ 适合：代码格式化（同输入同输出）、样板生成、
        FAQ/文档查询、lint 与风格检查
❌ 不适合：代码审查（每次代码不同）、
          创意内容生成（多样性本身就是目的）、
          实时数据分析（陈缓存比没有更糟）

预期：减少 20–40% 的 API 调用
```

**⑤ MCP 返回精简**

```
□ 设检索上限——默认返回全列？改成只返回需要的列
  20 列 → 5 列，单次查询上下文可减 75%
□ 用摘要响应——返回计数、关键统计、最相关的前 5 行，
  需要时再取全量
□ 结果分页——一次处理一页，避免单次吃掉巨额 token
```

## 审计清单

```
□ 是否核对了 API 响应里的实际模型（配置说的可能不是实际用的）？
□ 是否测量了上下文窗口大小（简单 agent 超过 20K 就是膨胀）？
□ 是否定期清理会话历史（无状态任务跑完就清）？
□ ⭐ 是否移除了没用过的工具和技能？
□ 是否把每次都要读的文件内联进了系统提示（省一次工具往返）？
□ 是否用了能完成任务的最便宜模型？
□ 是否理解了缓存模式（突发查询保温，分散查询每次冷启动）？
□ 是否维护了紧凑的仓库地图，避免重复发现？
□ 重复工作流是否已脚本化 / 可重放？
□ MCP 返回是否已做列裁剪、摘要与分页？
□ 省 token 技能是否只在输出密集的工作流里开？
□ 每个加载的技能是否"配得上它的上下文重量"？
```

## 一句总结

> ⭐ **最好的 token 优化不是一个技能，而是一套系统**：
> 压缩输出 · 防止重问 · 用代码代替 Markdown · 裁剪连接 · 缓存上下文。
> **每一项省一点，合起来改变经济模型。**
>
> 而**做加法容易，做减法才是真正的功力**。
