## 为什么会膨胀

权限只增不减，因为：

```
① 加权限是为了解决一个当下的问题（有明确动力）
② ⭐ 减权限没有当下收益（只有风险降低，而风险没发生）
③ 没人知道某个权限还在不在被用
```

> ⭐ 第三条是关键：
> **你不敢回收，是因为你不知道回收会不会弄坏什么。**

所以复核的第一件事不是"减"，是**建立可见性**。

## 复核什么

```
□ 每个 agent 能调用哪些工具
□ ⭐ 每个技能声明的 allowed-tools 是否仍与用途匹配
□ 已连接的 MCP server（都还在用吗？还可信吗？）
□ 凭据的发放范围与有效期
□ ⭐ 长期记忆的写入权限（可撤销吗？）
□ 谁有权停用/修改技能
```

## 四个问题的检查法

对每一项权限，问：

```
① 它上一次被使用是什么时候？
② ⭐ 没有它，当前的工作流会断吗？
③ 它的爆炸半径是什么（最坏能造成什么）？
④ ⭐ 有没有更窄的方式达成同样的目的？
```

第 ④ 条呼应 `least-privilege.md`：
**多数过宽的权限都能被一个更窄的工具取代。**

处置：

```
①② 都没被用 / 不用也行   → ⭐ 回收
③ 爆炸半径大且①②不明确   → 优先降级
④ 有更窄的替代           → 替换
```

## 频率

```
□ ⭐ 高权限（写、外发、花钱）：每季度
□ 只读权限：半年
□ ⭐ 触发式：人员变动、agent 职责变更、事故发生后
```

> ⭐ 第三条比固定频率更重要：
> **换人、换职责、出事之后必须立即复核**——
> 这三个时刻权限最可能与现实脱节。

## 回收的阻力

常见的反对意见与回应：

```
❓ "万一以后要用呢？"
→ ⭐ 需要的时候再加。加的成本是几分钟，
   而长期持有过宽权限的成本是不可见的。

❓ "回收会不会弄坏什么？"
→ 先降级观察（记录但不阻止），确认无影响再回收。

❓ "没人有时间做"
→ ⭐ 至少做"高权限 + 长时间未使用"这一小类，
   通常不超过 10 项。
```

> ⭐ **先做"零使用 + 高权限"的交集**——
> 这一类的收益/成本比最高，几乎没有误伤风险。

## 与技能的关系

技能让权限复核变复杂了一点：

```
□ ⭐ 技能可能在运行时请求它自己没声明的工具
□ 技能的 allowed-tools 是"免确认"，不是"限制"
□ ⭐ 一个技能被更新后，可能开始用新的工具
```

第三条最值得注意：
**复核要覆盖"当前版本"，不是"当初审核通过的版本"。**

## 自查

```
[ ] ⭐ 有"每个权限上次被使用"的数据吗？
[ ] 高权限项每季度复核？
[ ] ⭐ 人员变动/职责变更/事故后做过复核？
[ ] MCP server 列表是现行的且都可信？
[ ] ⭐ 做过高权限 × 零使用这一小类？
[ ] 回收前做过"记录但不阻止"的观察期？
[ ] ⭐ 有没有更窄的替代工具已被纳入计划？
[ ] 复核动作进审计日志了吗？
```

## 一条提醒

> ⭐ **权限复核的成果要可见。**

"我们每季度做权限复核" 这句话没有说服力；
**"本季度回收了 7 项权限，其中 2 项是写权限"** 才有。

把数字记下来，和 `usage-analytics.md` 的数据一起看——
**权限的膨胀与技能的使用应该同步变化**，
如果技能在减少而权限不变，那就是复核没到位。
