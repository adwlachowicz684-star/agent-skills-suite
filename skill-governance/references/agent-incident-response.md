# Agent 事故响应 Runbook

> 生产环境里，**问题不是 agent 会不会失败，而是失败会变成
> 一起被控制住的事故，还是一次公开的自我表演（附带 token 账单）**。

## 核心心态

```
□ ⭐ 默认会失败。设计的是"失败后怎么样"
□ ⭐ 回滚优先，不要顺手做清理
□ ⭐ 每次事故都要让系统更难被同样的方式伤到
```

## 事故清单

按顺序执行：

```
 1. ⭐ 有任何风险就先暂停外部动作（outbound）
 2. 记录当前的 deploy / prompt / model 版本
 3. 开事故记录：时间戳 + 影响范围
 4. ⭐ 保存失败运行的凭据（receipts）
 5. 确定爆炸半径
 6. 检查输入、检索、工具、控制流、校验
 7. 选择回滚或降级模式
 8. 需要时发出基于事实的客户通知
 9. ⭐ 保存证据包
10. ⭐ 把失败转成回归测试或护栏
```

> ⭐ **第 1 步和第 10 步是这套 runbook 的灵魂**：
> 前者限制损失，后者保证不复犯。

## 对外沟通的措辞

**要覆盖四点**：

```
□ 什么受影响
□ ⭐ 什么不受影响
□ 是否已暂停该工作流
□ 下一次更新什么时候来
```

**两条禁令**：

```
❌ 假装什么都没发生
❌ ⭐ 对未验证的根因做过度的解释
```

**语气**：平静且具体。

**模板**：

```
我们确认了一个影响部分工作流的自动化 agent 更新问题。
在核实范围并恢复安全运行期间，出站动作已暂停。
我们将在 60 分钟内提供下一次更新。
```

> ⭐ **"这在不撒谎的前提下争取到了时间"**
> ——不要为了显得掌控全局而编一个还没验证的原因。

呼应 `grounding-verification.md`（**`skill-crafting`**）：
**未验证就声称成功是不诚实，不是高效**。
同一条原则在对外沟通上同样成立。

## 回滚决策

> ⭐ **如果事故发生在一次部署之后，回滚是默认选项
> ——除非你有硬证据表明回滚没用。**

**回滚候选**（不止是代码）：

```
□ ⭐ prompt 版本
□ 编排逻辑
□ 检索设置
□ 工具包装器改动
□ ⭐ 模型路由变更
□ ⭐ 校验器变更
```

> ⭐ 这份清单的价值在于提醒：**agent 系统的"部署"不只有代码**。
> 很多人回滚了代码却忘了 prompt 版本，问题依旧。

**一条铁律**：

```
❌ 把事故响应和顺手清理混在一起
✅ ⭐ 先回滚 → 稳定 → 再打补丁
```

## 证据包

每起有意义的事故都要存：

```
□ 事故摘要
□ ⭐ 受影响的 run ID
□ 相关日志
□ 输入/输出样例
□ ⭐ 工具响应
□ 截图或对外部可见的消息链接
□ 部署的 commit hash
□ ⭐ prompt / 版本标识符
□ 采取的遏制动作
□ 恢复决策
```

> ⭐ **"如果你需要向客户、同事或未来的自己解释这起事故，
> 这个包比记忆重要。"**

呼应 `telemetry-schema.md` 与 `compliance-audit.md`：
**你必须能在事后证明"哪个 agent 做了什么"**。

## 把事故变成永久防御

> ⭐ **如果这起事故真的痛到值得记，它就值得配一个回归测试。**

恢复后至少创建以下之一：

| 防御 | 适用 |
|---|---|
| **重放测试** | 用同样的输入/上下文/工具响应模式，验证系统现在行为正确 |
| **校验规则** | ⭐ 如果输出本不该漏出去，写下一条下次能拦住它的校验器 |
| **工具健康断言** | ⭐ 如果工具返回了垃圾，加检测：空、部分、畸形结果在到达模型前拦下 |
| **路由或批准规则** | 如果任务对自主执行太危险，收紧门控让同类任务需人工批准 |
| **告警** | ⭐ 如果信号可见却被忽略，把它编码出来 |

**告警该编码的六种信号**：

```
□ 重试尖峰
□ ⭐ 成本尖峰
□ ⭐ 异常的空检索结果
□ 反复的校验失败
□ ⭐ 预期窗口内零完成任务
```

> 最后一条很少有人想到——**"太安静"也是一种故障信号**。

## 复盘该问的五句

> ⭐ **有用的复盘不是问"模型做了什么"。**

```
1. ⭐ 为什么 agent 被允许在那个状态下行动？
2. 事故完全浮现之前，已经存在什么信号？
3. ⭐ 本该有什么东西自动拦住它？
4. 缺少什么证据拖慢了诊断？
5. ⭐ 哪一种单一控制最能缩小爆炸半径？
```

**收尾纪律**：

```
❌ 留下十条含糊的改进项
✅ ⭐ 留下一两条能实质提升安全性的硬控制
```

呼应 `refine-with-execution.md`（**`skill-refining`**）：
**确认失败模式是"减少"而非"转移"**——
一两条硬控制比十条软建议有用得多。
