## 为什么需要单独设计

技能出问题的方式和代码不同：

```
代码出 bug  → 通常立刻可见（报错、崩溃）
技能出问题  → ⭐ 可能是"安静地做错"
              ——每次都在产生错误结果，但看起来在正常工作
```

这种"安静的失败"意味着**发现得晚**，
所以**从发现到停用**的延迟必须尽可能短。

## 四个层级的开关

从粗到细：

```
① 全局停用        ——关掉整个技能系统
② 单个技能停用    ——⭐ 最常用
③ 单个工具禁用    ——停掉它调用的那个危险工具
④ 单个参数设闸    ——如 refund.issue(amount) 上限设为 0
```

选择依据：**你要停的是"这个技能"还是"这类动作"？**

```
技能本身有问题  → ②
某个动作危险    → ⭐ ③④（因为别的技能也可能调用它）
```

第 ③④ 条常被忽略——**只停技能是不够的**，
如果这个动作本身危险，任何技能调用它都应该被拦。
（呼应 `least-privilege.md`：控制在工具层。）

## 多久能停

设计一个 kill switch 时，先问这个数字：

```
从"决定停用"到"生效"，需要多少分钟？
```

分解：

```
① 决策时间（需要谁批准？）
② ⭐ 配置传播时间（改了之后多久到所有机器？）
③ ⭐ 生效条件（要不要重启？要不要重载？）
```

第 ③ 条是关键陷阱：

```
❌ 改了配置但要等下次会话才生效
   ——当前正在跑的任务还在做错事
```

> ⭐ 好的 kill switch **对正在运行的任务也生效**。

具体手段（按运行时而异）：

```
· skillOverrides 设为 disabled（见 runtime-controls.md）
· 从启用列表移除并重载
· 工具层禁用该工具
· ⭐ 网络层断开出口（这是唯一无法被绕过的）
```

最后一条呼应 `sandbox-execution.md`：
**控制点落在 agent 无法绕过的边界上**。

## 停用之后

停用不是结束：

```
① ⭐ 确认它真的停了（不要假设）
   ——用一条会触发它的请求验证

② ⭐ 处理已排队/进行中的工作
   ——"禁用候选时必须同时停掉排队的工作，
      或确保排队项保留正确的版本与政策"
   （见 canary-release.md）

③ 保留现场：日志、transcript、输入
   ——用于事后分析

④ ⭐ 通知使用者
   ——他们需要知道自己刚才拿到的结果可能有问题
```

第 ④ 条最容易被漏，但它是**信任修复**的一部分：
用户自己发现"结果不对"和被告知"结果可能不对"，
后者对信任的损伤小得多。

## 演练

> ⭐ **没演练过的 kill switch 不算 kill switch。**

每季度一次：

```
① 宣布一次"模拟事故"
② 从发现到停用，计时
③ ⭐ 记录实际耗时与异常情况
④ 对照目标耗时，找出瓶颈
```

常见的演练发现：

```
· 不知道该找谁批准
· 配置文件在没人有权限的地方
· ⭐ 改了但没生效（因为要重载/重启）
· 没人知道当前跑的是哪个版本
```

最后一条最致命：**不知道当前版本 = 不知道该回滚到哪**。

## 清单

```
[ ] ⭐ 上一版可部署（有 git tag 或备份）？
[ ] 停用开关独立于应用二进制/技能内容？
[ ] ⭐ 四个层级都有手段（不只是"删技能"）？
[ ] 对正在运行的任务也生效？
[ ] 从决策到生效的目标耗时是多少？实测过吗？
[ ] ⭐ 能处理已排队的工作？
[ ] 有停用后的通知机制？
[ ] 保留了现场数据？
[ ] ⭐ 演练过吗（本季度）？
[ ] 知道当前跑的是哪个版本吗？
```

## 一条边界提醒

> ⭐ **kill switch 也应该是最小权限的。**

一个能一键停掉所有人所有技能的人/系统，
本身就是一个新的风险点。

所以：
```
□ 停用操作要被记录（审计日志）
□ ⭐ 谁能停用要有明确授权
□ 理想情况下可恢复（disable ≠ delete）
```
