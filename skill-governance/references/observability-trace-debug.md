## 1. ⭐ 黑盒效应与唯一解

```
Agent 系统出问题时最头疼的是"黑盒效应"：
   模型做了很多步决策，但没有留下决策依据和过程记录，排障全靠猜。
```

> ⭐ **唯一解法：从第一天就开始构建可观测性体系。**

> ⭐ 为什么是"从第一天"：你无法在出事之后补记已经发生的东西。
> 这与 `retirement-pipeline.md` 的"退役才有清单"是同一类教训。

## 2. ⭐ 调用日志该记什么

**强制字段**（三层）：

```
① ⭐ 请求上下文
   用户原始请求
   模型当前轮次的消息摘要
   ⭐ 路由层召回的候选技能 ID 列表
      ——⭐ 没有这个，你没法复盘"为什么选中了这个技能"

② 执行记录
   request_id · session_id · user_id
   skill_name · skill_version
   input · output_status · error_type
   latency_ms · retry_count · timestamp

③ ⭐ trace_id（贯穿所有后续技能调用）
```

**一条硬要求**：⭐ **敏感信息要脱敏，或不记明文**。

**trace 的价值**（这个比喻很好）：

```
⭐ 有了 trace ID，排查从"大海捞针"变成"按图索骥"。

用户说"自动退款流程走到一半卡住了"：
   拿 trace ID 一查 → 立刻看到卡在哪一步、
   那一步调了哪个技能、技能返回了什么异常。

⭐ 没有这套能力，你可能连问题出在模型决策还是技能执行都分不清。
```

## 3. ⭐⭐ 决策日志：每个决策点都做快照

> ⭐⭐ **trace 信息不能只记一次——整个链路中的每次"决策点"都要做快照。**

```
例：模型决定调用技能 A 而不是 B
    ⭐ 这条决策连同它的"理由"（如果模型输出了 reasoning）都要记下来
```

**为什么**：

```
⭐⭐ 很多问题不是执行失败，而是⭐ 选错技能。
   所以决策日志和调用日志同样重要。
```

```json
{"selected_skill": "web_search", "reason": "用户询问最新信息"}
```

> ⭐ 这与 `skillsbench-vs-realworld.md` 那条硬数据接上了：
> **加载率只有 16%–49%——"选错/没选"是最大的失效源，
> 而决策日志是唯一能观测它的东西。**

## 4. ⭐⭐ 用技能调试技能（自举）

Arize 团队的实践，一个三技能链：

```
① alyx-traces     从生产拉完整 trace（每个 span、每次工具调用、
                   每次 LLM 输入/输出，导出为结构化 JSON）
                   ⭐ 还能在 Playground 里重放出错的那一瞬
② datadog-debug   按时间窗搜后端 span（jq 配方重建调用树、
                   抽取错误、识别瓶颈）
③ gcloud-logs     同时间戳关联 K8s pod 日志
                   ⭐ 有些 bug 根本不出现在 span 里
                      ——OOMKill、容器重启、gRPC 超时
```

**一个真实排障链条**（值得抄的是它的顺序）：

```
"Alyx 在会话 XYZ 给了错误答案"
  → alyx-traces 拉完整 trace，定位失败的工具调用，记下 trace ID
  → datadog-debug 搜后端 span，发现某 GraphQL resolver 的 500
  → gcloud-logs 发现 500 之前两分钟有 OOMKill
  → ⭐ 几分钟定位根因，而不是半小时
```

**四条经验**（每条都可直接迁移）：

```
① ⭐ 技能只是 markdown——低成本、高价值
   "写一个 markdown 文件不是传统工程工作，
    但它极大扩展了你的编码 agent 能做的事"（他们仓库里有 13 个）

② ⭐ 可组合性来自共享约定，而不是编排代码
   技能之间按名字互相引用，并假定共享约定：
     输出到 .agents/tmp/、用 jq 分析、通过 env-context 解析环境
   → ⭐ LLM 自然就把它们串起来了，⭐ 不需要写编排代码

③ ⭐⭐ 在你需要之前就建好可观测性
   ——凌晨两点出问题时，你希望调试工具已经在位

④ ⭐⭐ Agent 调试本身就是一个 agent 形态的问题
   筛 trace、span、日志，关联 ID 和时间戳，
   按流程收窄根因——⭐ 这正是 agent 擅长的事
   → ⭐ "用你造的东西去修你造的东西"
```

**发现方式也值得一提**：

```
⭐ 技能通过一个规范目录 symlink 出去，
   Cursor / Claude Code / Codex 都能自动发现。
   → ⭐ Write once, debug everywhere.
```

> ⭐ 这与 `cross-agent-portability.md` 的"中性目录 + symlink，绝不手抄副本"
> 完全一致——**同一结论在两个不同来源独立出现**。

## 5. ⭐⭐ 护栏放在包装脚本里，不在提示里

```
safe-kubectl.sh   ⭐ 拒绝所有变更类动词
                  （apply/delete/edit/patch/scale/exec/rollout restart）
safe-gcloud-logs.sh  只允许 gcloud logging read

⭐ 生产环境下：技能生成命令，⭐ 然后让工程师先审再跑
⭐ 所有 bash 脚本 source 一个共享库（common.sh），
   统一处理环境解析、凭据管理、安全强制
```

> ⭐⭐ **LLM 会照着你给的指令做，所以护栏要放在包装器里——
> 不在提示里，在代码里。**

> ⭐⭐ 这与 `determinism-boundary.md` 完全同源：
> **"把破坏性命令拦截写进技能是表演"**——
> 这里是同一个结论的**正面实现样板**。

还有一条架构细节很值得抄：

```
⭐ 环境别名（如 "prod"）→ GCP 项目 ID / K8s context 的映射，
   ⭐ 单一事实来源，各个脚本绝不硬编码环境细节。
```

## 6. 监控指标与"评估 ≠ 监控"

**常用监控指标**：

```
调用次数 · 调用成功率 · 失败率
平均耗时 · P95 耗时 · 超时率
⭐ 空结果率 · 错误类型分布 · 重试次数 · 调用成本
```

**评估 ≠ 监控**（这个区分很重要）：

```
监控关注⭐ 系统运行是否稳定
评估关注⭐ 能力效果是否好

例：搜索技能不只看成功率，还要看
    结果相关性、来源可信度、新鲜度、空结果率
```

**不同技能的不同指标**：

| 技能 | 评估指标 |
|---|---|
| 搜索 | 结果相关性、来源可信度、新鲜度、空结果率 |
| RAG | 召回率、top-k 相关性、引用准确性、幻觉率 |
| 文件解析 | 解析成功率、文本完整性、表格识别准确率 |
| 邮件 | 草稿成功率、收件人识别准确率、⭐ 误发送率 |

**任务级评估**（不能只看技能层）：

```
⭐ 技能调用成功 ≠ 用户任务成功。还要看：
   最终任务是否完成 · 答案是否准确 · 用户是否满意
   ⭐ 是否需要人工修改 · ⭐ 是否多次重试

⭐ Agent 系统应同时评估技能层和任务层
```

**测试集设计**（四类，可复制）：

```
正例   用户询问最新新闻 → 应调用 web_search
反例   用户要求翻译文本 → ⭐ 不应调用 web_search
边界例 用户问题含糊     → 需要追问
异常例 搜索结果为空
```

## 速查

```
⭐ 调用日志：
□ 用户原始请求 + 当前轮次消息摘要
□ ⭐ 路由层召回的候选技能 ID 列表（没有它无法复盘选择）
□ request_id/session_id/user_id/skill_name/skill_version
□ output_status/error_type/latency_ms/retry_count/timestamp
□ ⭐ trace_id 贯穿所有调用
□ ⭐ 敏感信息脱敏或不记明文

⭐⭐ 决策日志：
□ ⭐ 每个决策点都做快照（含 reasoning，如果有）
□ ⭐ 很多问题不是执行失败，是选错技能

⭐⭐ 自举调试：
□ 三技能链：trace → 后端 span → 基础设施日志
□ ⭐ 有些 bug 只在基础设施日志里（OOMKill/重启/超时）
□ ⭐ 可组合性来自共享约定，不需要编排代码
□ ⭐⭐ 在需要之前就建好可观测性
□ ⭐⭐ 用你造的东西去修你造的东西
□ ⭐ 规范目录 + symlink：Write once, debug everywhere

⭐⭐ 护栏：
□ ⭐ 放在包装脚本里，不在提示里
□ 生产环境：生成命令 → 让工程师先审再跑
□ ⭐ 环境映射单一事实来源，脚本不硬编码

评估 vs 监控：
□ 监控=稳定性，评估=效果好坏
□ ⭐ 技能调用成功 ≠ 任务成功（⭐ 是否需人工修改 / 是否多次重试）
□ 测试集四类：正例 / 反例 / 边界例 / 异常例
```

**一句话**：

> ⭐⭐ **"LLM 会照着你给的指令做，所以护栏要放在包装器里——
> 不在提示里，在代码里。"**
