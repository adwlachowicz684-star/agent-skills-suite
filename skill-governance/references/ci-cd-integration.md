## 五类能力：从提交前自检到结果通知

> ⭐ **补齐这五类，流程才真正连起来**（否则 agent 能跑 CI，
> 但查状态、找错误、继续处理仍落回人手里）：

```
① ⭐ 提交前自检
   先同步主干最新代码，再按项目要求完成编译、测试、
   单测覆盖率检查
   ⭐ 这些检查在本地执行，但规则要和 CI 保持一致
   ⭐ 这一步不过，代码就不提交

② 主动触发 CI
   本地自检通过、代码提交完成后，由 agent 调用技能触发对应流水线
   ⭐ 代码提交仍属于研发 workflow，CI 技能不必越界接管所有 git 操作

③ ⭐ 跟踪运行状态
   触发后能查询排队/执行/成功/失败
   ——让 agent 知道任务走到哪，而不是发起调用后就没了下文

④ 可选的结果通知
   有 webhook 就主动通知；没有就让 agent 定时查询

⑤ ⭐ 失败证据按需取回
   开发人员不再负责打开 CI 页面、复制错误日志、回来告诉模型"这里失败了"
   ⭐ 证据由技能取回，agent 根据证据判断原因
```

> ⭐ 实践效果：把"编译不过、测试卡点、覆盖率不够、
> 没合并主干"这些检查补进技能后，**真正触发 CI 时已很少因这些基础问题失败**。
> 这不意味着 CI 没用——**恰恰说明本地自检与 CI 用的是同一套标准**：
> 前者尽早发现问题，后者在独立环境里再验一次。

## CI 失败闭环（真正的卖点）

> ⭐ **CI 与 AI agent 结合的力量在于反馈闭环**：

```
CI fails
  ↓
Copy the failure output
  ↓
Feed it to the agent:
  "The CI pipeline failed with this error: [具体错误]
   Fix the issue and ⭐ verify locally before pushing again."
  ↓
Agent fixes → pushes → CI runs again
```

> ⭐ **"在本地验证通过后再推送"这一句很重要**——
> 避免把 CI runner 当调试环境反复消耗配额。

**CI 失败后只保留两个出口**：

```
□ agent 先判断问题归属
□ 属于本技能能修的 → 修 + 本地验证 + 重推
□ 属于架构层面决策的 → ⭐ 停止并升级（不硬修）
```

**管道里的四类产出去向**（结构化报告的写法）：

```
□ 范围内阻塞问题   直接影响当前任务
□ 后续改进项       可在后续迭代优化
□ ⭐ 停止并升级项   需要架构层面决策
□ 建议/警告        安全提示、性能机会
```

## 按失败类型的处置模式

| 失败类型 | 处置 |
|---|---|
| Lint 失败 | 跑 `lint --fix` 并提交 |
| 类型错误 | 读错误位置，修类型 |
| ⭐ 测试失败 | ⭐ **显式路由到调试技能的五步分诊**：reproduce → localize → reduce → fix → guard |
| 构建失败 | 检查配置与依赖 |

> ⭐ **"测试失败时路由到调试技能"这条值得单独学**——
> 它演示了技能之间**通过路由协作，而不是各自为政**。
> 呼应 `skill-orchestration` 的 `composition.md` 与 `skill-refining` 的 `architecture-layering.md` 的 Router 模式。

**本地复现命令表**（写进技能让 agent 直接查）：

| 失败 | 命令 |
|---|---|
| 类型检查 | `pnpm typecheck` / `npx tsc --noEmit` |
| Lint | `pnpm lint` 然后 `pnpm check:fix` |
| 测试 | `pnpm test -- --filter=<name>` |
| 构建 | `pnpm build` |

**GitHub CLI 的用法**：

```
gh run list · gh run view <id> · gh run watch <id>
gh run rerun <id> · gh pr checks
```

## 安全与隔离

> ⭐ **审查过程必须多重隔离**：

```
□ ⭐ 配置隔离——审查引擎不加载被审查项目的本地配置
□ 工具限制——限制审查过程中的工具访问
□ 沙箱环境——在受控环境中执行
□ ⭐ 只读访问——审查期间代码库为只读
□ 工具白名单——只允许必要工具
□ 网络访问限制——控制外部资源访问
```

> 呼应 `sandbox-execution.md`：
> **审查引擎尤其需要切片**，因为它会读大量不可信内容
> （见 `skill-selection` 的 `untrusted-repo-content.md`）。

## 增量、缓存与性能

**增量审查**（只分析变更部分，效率提升显著）：

```bash
"$AUTOREVIEW" --mode commit --commit HEAD~1..HEAD
```

**三种缓存**：

```
□ 结果缓存——存储审查结果供后续参考
□ 依赖分析缓存
□ 配置缓存
```

**三个实际运行中发现的性能点**：

```
□ ⭐ 需要缓存技能包（减少克隆时间）
□ ⭐ 应当设置超时机制（防止卡死）
□ ⭐ 建议分阶段执行（先快速检查，再深度分析）
```

> ⭐ 呼应 `skill-scripting` 的 `script-engineering.md` 的"绝不交互"与超时纪律，
> 以及 `skill-selection` 的 `performance.md` 的并行 IO。

## 三阶段实施路线

```
第一阶段 基础集成
   安装技能库
   配置基础 CI/CD 流水线
   实现自动化代码审查

第二阶段 高级功能
   集成多引擎审查
   实现并行测试执行
   配置自定义审查规则

第三阶段 全面优化
   性能调优与缓存优化
   安全加固与权限细化
   监控与报告系统完善
```

**三个常见问题与解法**：

| 问题 | 解法 |
|---|---|
| 审查时间过长 | 启用增量审查 · 配置合适的引擎 · 优化审查范围 |
| ⭐ 误报过多 | 调整敏感度 · 配置忽略规则 · 训练审查引擎 |
| 集成复杂度高 | 用标准配置模板 · 分阶段实施 |

> ⭐ **"误报过多"必须认真对待**——
> 呼应 CI/CD 流水线那条决策：**安全扫描只警告不阻断**，
> 因为误报率高时自动阻断会侵蚀团队信任。

**预提交钩子的写法**（本地即时反馈）：

```bash
# .husky/pre-push
pnpm generate-schema-docs    # 每次 push 前跑
git add docs/schema          # 自动提交，确保文档与 schema 同步
```

> ⭐ 这是个很好的 hook 用例：
> **机器能确定性检查的事，交给 hook，不写进提示词**。

**发布自动化的类型映射**：

| 类型 | 何时用 |
|---|---|
| patch | Bug 修复、文档、重构 |
| minor | 新功能、非破坏性增强 |
| ⭐ major | 破坏性变更、API 改动 |

## 自查

```
□ 是否把"提交前自检"与"CI 验收"用同一套标准？
□ ⭐ 是否明确"CI 不是远程调试器"？
□ 五类能力是否齐全（尤其"跟踪运行状态"与"失败证据取回"）？
□ ⭐ 是否要求"本地验证通过后再推送"？
□ CI 失败后是否只有两个出口（修 / 升级）？
□ ⭐ 测试失败是否显式路由到调试技能（而非盲试）？
□ 是否有本地复现命令表？
□ 审查是否只读 + 工具白名单 + 沙箱？
□ ⭐ 是否用了增量审查（避免全量分析）？
□ 是否设了超时机制？
□ 是否分阶段执行（快检 → 深析）？
□ ⭐ 误报问题是否有解法（而不是放任）？
□ 破坏性变更是否映射为 major？
□ 机器可确定性检查的事是否用了 hook（而非提示词）？
```
