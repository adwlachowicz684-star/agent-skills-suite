## 1. 为什么必须埋点

技能用不用，靠感觉是判断不了的。两个典型误判：

```
误判一："这个技能很重要"  →  实际三个月没人触发过（description 没写好）
误判二："这个技能没用"    →  实际高频触发，只是没人抱怨（它在默默干活）
```

> ⭐ 而且每个技能**无论有没有被用过，都在为每一轮付费**（见 `context-budget.md`）。
> 所以"没人用"不只是浪费，是**持续成本**。

## 2. 三层采集方式

### L1：触发日志（最便宜，必做）

用 **PreToolUse hook** 记录哪个技能在什么时间被触发。

采集字段最小集：

| 字段 | 用途 |
|---|---|
| `skill_name` | 谁被触发 |
| `timestamp` | 频次与趋势 |
| `session_id` | 区分会话 |
| `trigger_query`（可选，脱敏后） | ⭐ 反查"用户实际怎么说的" |

> ⚠️ `trigger_query` 是可选且需脱敏的——它会包含用户的真实措辞，
> 可能含业务敏感信息。见《skill-governance》的 `telemetry-schema.md`。

### L2：纠正信号

光有触发次数不够，还得知道**触发之后顺不顺利**。信号来源：

- 用户在同一会话内的**重提/修正**（"不对，我要的是…"）
- 技能执行后的**回退/重做**
- 人工反馈按钮（如有）

### L3：官方诊断命令

```
/skill-doctor   显示每个技能占多少上下文、被调用多频繁
/doctor         完整设置体检
```

`/skill-doctor` 是**清库的第一工具**——它直接把"哪些技能从没被用过却一直占着上下文"摆出来。

## 3. 三类处置决策

跑满一个月后，按**使用频率 × 满意度**交叉分成三类：

| 象限 | 判定 | 处置 |
|---|---|---|
| **高使用 + 高满意** | ⭐ 你最好的技能 | **记录它的模式，照着多做几个** |
| **高使用 + 频繁纠正** | 差一点就对 | ⭐ **优先投入改进**——这是 ROI 最高的一类 |
| **低使用** | 两种可能 | ⭐ **要么 description 错了（模型从没触发），要么没人需要它 → 修或砍** |

> ⭐ **第三类的判断是关键**：低使用不等于没价值。
> 先按《skill-evaluating》的 `trigger-debugging.md` 排查是不是触发问题，
> **确认不是之后才砍**。

## 4. 判读陷阱

### 陷阱一：把"没被投诉"当成"好用"

沉默的大多数可能是**从没被触发**，而不是一直好用。
⭐ **低使用 + 零反馈，是最容易被误读成"稳定运行"的一类。**

### 陷阱二：只看总数不看趋势

一个技能总量高但**趋势下滑**，往往是代码库变了、description 不再匹配。
⭐ **看斜率，不看绝对值。**

### 陷阱三：样本太短

技能使用天然有周期性（月末报表、季度评审）。
⭐ **不足一个完整业务周期的样本，不要下"没人用"的结论。**

### 陷阱四：用平均值掩盖分布

20 个技能平均触发 5 次，可能是 1 个触发 96 次、19 个各触发 0.2 次。
⭐ **看分布，别看均值。**

## 5. 最小实现

不必一上来就搭完整可观测体系。最小可用版本：

```bash
# PreToolUse hook：把技能调用追加到日志
echo "$(date -u +%FT%TZ) ${SKILL_NAME} ${SESSION_ID}" >> ~/.claude/skill-usage.log
```

一个月后：

```bash
cut -d' ' -f2 ~/.claude/skill-usage.log | sort | uniq -c | sort -rn
```

输出直接就是"哪些技能真的在用"的排行。

**再往上加一层**：把日志按 `skill_name` 聚合出趋势（周环比），
就能同时看出第三类（低使用）和陷阱二（趋势下滑）。

## 速查

| 现象 | 先查 | 再决定 |
|---|---|---|
| 某技能零触发 | `trigger-debugging.md`（触发链路） | 修 description，不是砍 |
| 零触发且确认无人需要 | 业务必要性 | 砍 |
| 高频 + 常被纠正 | 正文质量 | ⭐ 优先改 |
| 高频 + 无反馈 | 无需动作 | 记录模式，复制它 |
| 总量高但下滑 | 代码库是否变更 | 更新正文或 description |
