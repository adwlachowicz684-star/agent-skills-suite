## 为什么策略救不了宽工具

一个能跑任意 shell 的工具，你没法给它写一条有意义的策略——
它的行为空间是无界的。

> **留着宽工具，然后靠策略拦**：走错的那一步会**从宽工具里穿出去**。
>
> ⭐ 所以正确顺序是：**先删宽工具，再用窄工具替换它**，
> 最后才在这些窄工具上写策略。

这一条改动，对访问控制的贡献**超过任何策略**。

## 窄工具之上的四层控制

工具面窄了之后，访问控制才变得可处理：

**① 每 agent 工具白名单**

```
研究 agent：web.search + doc.read
            ——不是 db.write
```

工具集就是第一道权限边界。

**② 每用户作用域**

```
⭐ agent 的权限是"它所代表的那个已验证用户"权限的严格子集
实习生 → 实习生的 agent 继承实习生权限
管理员 → 继承管理员权限
身份要流到每一次工具调用
```

> ⭐ "这次是代谁在行动"必须**永远可回答**——
> 不能是一个共享服务账号。

**③ 每参数策略**

窄工具有可以设闸的参数：

```
refund.issue(amount)
  ≤ $50    → 允许
  > $50    → 升级
```

> **你没法对 bash 写这条规则。**
> 这就是为什么"工具面优先"。

**④ 委派链上权限只减不增**

```
⭐ 一个 agent 把任务交给另一个时，作用域与预算只能沿链收缩
子 agent 不能获得它的调用者没有的能力
```

这四层**全部依赖"工具窄到策略有意义"这个前提**。

## 最小权限够不到的边界

要诚实承认一个极限：

```
有些 agent 真的需要跑任意代码
  ——编码 agent、带 Python 沙箱的数据分析 agent
```

你没法把这个面变窄。这时候：

> ⭐ **不是方法的失败，是你站错了边界。**

对**本质上开放的执行**，正确的控制是**隔离**：

```
在沙箱里跑
  · 爆炸半径被限制
  · ⭐ 网络出口走唯一一扇你控制的门
```

> **控制点落在 agent 无法绕过的边界（网络）上，而不是工具调用上。**

所以结论不是二选一：

```
窄的类型化工具  用于一切你能窄化的
隔离            用于本质上宽的那部分
```

## 混乱副手：最经典的 agent 漏洞

> **Confused deputy**：agent 带着自己的高权限运行，
> 却代表一个低权限用户行动。

如果**授权检查的是 agent 的身份而不是请求用户的身份**：

```
一个普通用户只要让 agent 去取
→ 就能拿到他本不该看到的数据
```

修法就一句：**每次调用都按请求用户校验，永不按 agent 校验。**

配套的几类威胁，值得一起记住：

```
无界循环与成本
  ——卡在重试循环里，或被诱导发起 fork bomb 式的工具调用
  ⭐ 可用性与花费也是威胁模型的一部分

长期记忆投毒
  ——写入被固化进未来行为
```

## 清单

```
[ ] 每个工具单一职责，输入有类型且校验过
[ ] ⭐ agent 不持有本任务不需要的常设访问权
[ ] 破坏性与不可逆操作需要人工批准
[ ] ⭐ 授权按请求用户执行，不是按 agent
[ ] 工具代码在沙箱中运行，无环境凭据
[ ] ⭐ 工具输出与检索内容被当作不可信内容，而非可信指令
[ ] MCP server 与工具定义白名单化并 pin 住
[ ] 长期记忆写入有作用域、被审阅、可撤销
[ ] ⭐ 每次运行的步数、时间、花费上限，且 fail closed
[ ] 每次工具调用都被记录且可告警
```

**"fail closed"** 那条容易写错：
到达上限时是**停止**，不是"记录下来继续"。

## 与技能的关系

三条直接可用：

**① 技能里的权限声明不是安全边界**

```
allowed-tools 是"免确认"字段，不是"限制"字段
```

> ⭐ 真正的安全控制必须在**工具层**做。
> 技能里写了"只读"，不等于它真的只读。

**② 沙箱要按技能类型切片**

具体分级见 `sandbox-execution.md`——
summarizer 只放行 api.openai.com，git parser 禁网。

**③ MCP server 要 pin 并审阅**

工具定义本身可以是攻击面：
一个被替换的 MCP server 可以在工具描述里塞指令。

```
✅ 白名单 + pin 到版本
❌ 运行时动态拉取未审查的 server
```

## 一条投入产出判断

> ⭐ **回报最高的两个控制是：
> 最小权限工具 + 对不可逆操作的硬批准门。**

这两件做对了，多数注入尝试会**以审计日志里一次被拒绝的调用告终**，
而不是变成一次事故。清单上其余的都是纵深防御。

顺序建议：**先发窄工具集，只在任务确实需要时才加能力，
并且让每一个新工具都配得上它的爆炸半径。**
