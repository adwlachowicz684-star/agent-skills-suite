## 1. ⭐⭐⭐⭐⭐ "谁写的就归谁"撑不过三个月

```
第 1 个月：作者很清楚，随时能改
第 3 个月：⭐⭐⭐⭐⭐ 作者换了项目，但技能还在被 12 个人用
第 6 个月：⭐⭐⭐⭐⭐ 有人发现它错了，不知道该找谁；于是绕过它
```

> ⭐⭐⭐⭐⭐ 而"绕过"没有任何痕迹——
> ⭐⭐⭐⭐⭐ 技能仍在触发、仍在消耗判断预算，只是不再被信任。

这与 `skill-authoring/references/forty-skills-lessons.md` 那条完全对应：

> ⭐⭐⭐⭐⭐ "我不止一次对技能做了破坏性改动，静默地影响了整个团队"
> ——⭐⭐⭐⭐⭐ 反过来同样成立：**没人改，也是静默地影响整个团队。**

## 2. ⭐⭐⭐⭐⭐ 四种无人区

**① ⭐⭐⭐⭐⭐ 作者已离开**（最常见）

```
离职 / 转岗 / 换项目，而技能仍在库里
```

**② ⭐⭐⭐⭐⭐ 复制来的**

```
从别人的仓库拷过来 → ⭐⭐⭐⭐⭐ 没有人认为自己是作者
```

> ⭐⭐⭐⭐⭐ 这类最典型：⭐⭐⭐⭐ 拷贝者觉得"我只是用了一下"，
> ⭐⭐⭐⭐⭐ 原作者根本不知道它被复制了。

**③ ⭐⭐⭐⭐⭐ 团队共有的**

```
"这个是大家的" → ⭐⭐⭐⭐⭐ 等于没有人的
```

**④ ⭐⭐⭐⭐⭐ 生成出来的**

```
用 skill-creator 或让模型生成的 → ⭐⭐⭐⭐⭐ 没有人类作者
```

> ⭐⭐⭐⭐⭐ 第四种正在变多，而它最彻底：
> ⭐⭐⭐⭐⭐ 连"去问谁"这个动作都没有起点。

---

## 3. ⭐⭐⭐⭐⭐ 无人拥有的具体代价

不是"维护不好"，是三种更具体的失败：

**① ⭐⭐⭐⭐⭐ 错误不会被修，只会被绕过**

```
发现它错了 → 不知道找谁 → ⭐⭐⭐⭐⭐ 自己手动补一下 → 继续用
```

> ⭐⭐⭐⭐⭐ 于是使用数据看起来正常（仍在被调用），
> ⭐⭐⭐⭐⭐ 而信任度在持续下降——这是一个没有任何指标会记录的过程。

**② ⭐⭐⭐⭐⭐ 问题报告无处可去**

```
用户反馈 → 提给谁？ → ⭐⭐⭐⭐⭐ 通常是提给"最近改过它的人"
→ 那个人也不认为自己负责 → 工单沉淀
```

**③ ⭐⭐⭐⭐⭐ 没人有权删除**

```
⭐⭐⭐⭐⭐ 删除需要有人能回答"删了会怎样"，
⭐⭐⭐⭐⭐ 而这个问题恰恰需要 Owner 才能回答。
```

> ⭐⭐⭐⭐⭐ 这是一个死锁：**没有 Owner 就没人敢删，没人敢删库就越长，
> 库越长越没人愿意当 Owner。** 这是技能库必然膨胀的组织机制。

---

## 4. ⭐⭐⭐⭐⭐ 为什么没人主动认领

三条，第二条最关键：

**① ⭐⭐⭐⭐⭐ 认领一个技能 = 认领一份无限期的责任**

> ⭐⭐⭐⭐⭐ 而收益（"它更好用了"）是分散的、延迟的、不可归因的。

**② ⭐⭐⭐⭐⭐ 认领需要理解它，而理解它的成本高于重写它**

```
读完一个 300 行的陌生技能：30 分钟
从零写一个：40 分钟
→ ⭐⭐⭐⭐⭐ 理性选择是重写，于是库里出现第二个做同样事的技能
```

> ⭐⭐⭐⭐⭐ 这解释了变体密度高的真正成因：
> ⭐⭐⭐⭐⭐ 不是团队懒，是**认领成本高于复制成本**。

**③ ⭐⭐⭐⭐⭐ 没有认领的入口**

> ⭐⭐⭐⭐⭐ 技能里没有写"这个技能归谁"，
> ⭐⭐⭐⭐⭐ 于是想认领的人不知道它是不是已经有人了。

## 5. ⭐⭐⭐⭐⭐ 修法一：Owner 是一个字段，不是一个记忆

```yaml
---
name: xxxx
description: ...
⭐⭐⭐⭐⭐ owner: team-infra
⭐⭐⭐⭐⭐ review_after: 2026-12-01
---
```

> ⭐⭐⭐⭐⭐ 关键是它**必须在文件里**，不是在 wiki 里、不是在大脑里。

三个理由，第三个最关键：

```
① ⭐⭐⭐⭐⭐ 读技能的人能立刻知道找谁
② ⭐⭐⭐⭐⭐ 可以 grep / 可以 CI 校验（无 owner 拒绝注册）
③ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ **owner 字段的存在，把"谁负责"从一个需要打听的问题
     变成了一个读文件就能回答的问题**
```

> ⭐⭐⭐⭐⭐ 这与 `skill-versioning/references/adr-lightweight.md` 那条完全同构：
> ⭐⭐⭐⭐⭐ **记在哪比记什么重要——它必须在"你会看到它"的地方。**

配套：⭐⭐⭐⭐ **owner 写团队而不是个人**（个人会走，团队不会），
⭐⭐⭐⭐⭐ 且必须是**能收到通知的实体**（一个 slack 频道，不是一个名字）。

## 6. ⭐⭐⭐⭐⭐ 修法二：无人认领的技能不应该存在

两条硬规则：

```
① ⭐⭐⭐⭐⭐ 无 owner 拒绝注册（准入门禁，不是建议）
② ⭐⭐⭐⭐⭐ 无 owner 且超过 N 天 → 自动进入"待认领"，到期归档
```

> ⭐⭐⭐⭐⭐ 第 ② 条是关键：⭐⭐⭐⭐ 它给"无人区"设了一个终点，
> ⭐⭐⭐⭐⭐ 否则无人认领是一个**可以无限持续的状态**。

与"不删除只调整作用域"不矛盾：

```
归档 ≠ 删除
⭐⭐⭐⭐⭐ 归档保留恢复路径；⭐⭐⭐⭐⭐ 没有恢复路径的空壳才是没人承认的删除
```

而归档在这里有额外好处：⭐⭐⭐⭐ **它创造了一个可见的"待认领"队列**——
于是认领变成一个可以主动做的动作，而不是需要等别人来问。

---

## 7. ⭐⭐⭐⭐⭐ 修法三：交接与失联处理

三条，成本都很低：

**① ⭐⭐⭐⭐⭐ Owner 变更时，交接包里必须包含"为什么是这样"**

```
不是交接文件，是交接⭐⭐⭐⭐⭐ 那些没有写在技能里的判断依据
```

> ⭐⭐⭐⭐⭐ 与 `skill-versioning/references/adr-lightweight.md` 一致：⭐⭐⭐⭐ 新 Owner 会重新做一遍已被否决的决策，
> ⭐⭐⭐⭐⭐ 因为否决的理由没有跟着交接。

**② ⭐⭐⭐⭐⭐ 失联判定要有日期，不要靠感觉**

```
review_after 到期 → 自动发通知 → N 天无响应 → 升级到团队
```

> ⭐⭐⭐⭐⭐ **"会不会过期"应该是一个有日期的机制，不是需要人记得想的事**。

**③ ⭐⭐⭐⭐⭐ 认领的门槛要低到可以当场做**

```
改一行 owner 字段 → 就是认领
⭐⭐⭐⭐⭐ 不要求"先通读全部内容"
```

> ⭐⭐⭐⭐⭐ 针对第 4 节的第 ② 条：⭐⭐⭐⭐ 认领成本高于复制成本，
> ⭐⭐⭐⭐⭐ 所以唯一有效的办法是**把认领成本降到接近零**。

---

## 8. ⭐⭐⭐⭐⭐ 自检

```
① ⭐⭐⭐⭐⭐ 每个技能都有 owner 字段吗？（没有 → CI 拒绝）
② ⭐⭐⭐⭐⭐ owner 是能收到通知的实体吗？（一个名字不是）
③ ⭐⭐⭐⭐⭐ 有 review_after 吗？到期会发生什么？（没有 → 永不过期）
④ ⭐⭐⭐⭐⭐ 库里有没有"谁写的就归谁"但作者已离开的？（第 3 个月起就会开始出现）
⑤ ⭐⭐⭐⭐⭐ 认领一个技能需要几步？（超过 1 步 → 门槛太高）
```

一个十秒判断：

> ⭐⭐⭐⭐⭐ **随便挑一个技能，问"它错了该找谁"。
> 答不上来 → 它错了就不会被修，只会被绕过，
> ⭐⭐⭐⭐⭐ 而绕过不留下任何痕迹——使用数据看起来完全正常。**

---

> ——这是技能库必然膨胀的机制。破解点不在内容，在一个字段。**
