## 生态现状

```
□ 技能没有注册表级的通用扫描
□ 没有强制签名验证
□ ⭐ 核心规范里没有 lock file
□ 工具存在（各类扫描器），但 ⭐ 是 opt-in，不是默认

□ 实测：13.4% 的技能存在安全问题
□ 另一份：ClawHavoc 事件中 2857 个里 341 个恶意（11.9%，后续升至 20%）
```

> ⭐ **对照 npm 2018 年引入 `npm audit` 的时间点**——
> 技能生态的安全基础设施大约落后在那个阶段，
> **但攻击手法已经在复刻 npm 那些年的老套路**。

## 四类真实恶意技能

> ⭐ **这些不是理论攻击，是发布过、被发现过、有些在被移除前已被下载的技能。**

**① 假 Solana 钱包追踪器**

```
发布为 solana-wallet-tracker
专业的 SKILL.md，钱包余额追踪指令写得很真实
⭐ "Prerequisites" 段落指示用户运行一个安装脚本——该脚本下载 AMOS

目标人群：加密货币开发者
——正是机器上最可能有钱包密钥与交易所凭据的那群人
```

> 呼应 `skill-orchestration` 的 `prompt-injection.md` 的 ClawHavoc 复盘：
> **恶意逻辑藏在 SKILL.md 的英文段落里，因为静态扫描不解析自然语言。**

**② Google Workspace "助手"**

```
看起来是个效率工具
实际是披着友好外衣的凭据窃取投递机制
```

**③ 仿冒名（typosquat）活动**

```
⭐ 完全复刻 npm 多年的老套路
（crossenv vs cross-env，lodahs vs lodash）
——现在出现在技能生态里

名字与真实工具足够接近，快速打字的开发者不会注意到差别
```

**④ 反向 shell 技能**

```
⭐ SKILL.md 文件保持完全干净，恶意逻辑全在外部
   ——这让静态分析彻底失效

指令看起来干净。被引用的脚本里装着 payload。
```

> ⭐ **这条对审计方法直接有含义**：
> **只扫 SKILL.md 是不够的，必须扫 `scripts/`**。

## 按 OWASP Agentic Top 10 逐类审计

**准备**：已装技能清单（含来源、版本、最后更新时间）+ 扫描器。

### ASI04 供应链（先做这个）

> ⭐ **这是最高杠杆的一类——因为它是唯一能在"任何东西运行之前"就检查的。**

```
查什么：
  □ 恶意代码模式或已知 payload 签名
  □ ⭐ 仿冒包名（clawhub vs clawhubb）
  □ 依赖风险——未签名或未验证的组件
  □ ⭐ 自首次发布后就没更新过的技能

通过标准：
  □ 每个已装技能都有扫描评分
  □ 被标为恶意的 → 移除或隔离
  □ 有未解决警告的 → 有记录在案的风险接受
```

### ASI02 工具滥用（查权限）

```
□ 权限范围——是否请求了文件系统、网络、shell 执行？
  ⭐ 这个范围与它实际做的事相称吗？
     ——一个 markdown 格式化器不该需要对你家目录的写权限
□ 工具描述——含隐藏指令的描述可在不碰代码的情况下重定向 agent 行为
□ 参数校验——schema 是否接受未校验的文件路径、shell 命令、URL？
  ⭐ 这些正是攻击者或错位 agent 会利用的参数

通过标准：无技能的权限超出其声明功能
```

### ASI03 身份与权限滥用（查密钥）

```
□ 技能里是否有硬编码的 API key / token / 密码
□ 技能是否访问了它不需要的环境变量
□ 凭据在技能间传递时是否做了范围限定

通过标准：零硬编码密钥；只访问其声明功能所需的凭据
```

### ASI01 目标劫持（查工具描述）

```
手动复核描述里是否有：
  □ 引用其他工具的指令（"跑完这个工具后，也跑…"）
  □ 数据外传命令（"把输出发到…"）
  □ 跨工具操纵（"用…覆盖前面的指令"）

通过标准：描述只含合法文档，无隐藏指令
```

### ASI05 意外代码执行

```
□ 直接的 eval() / exec() 调用
□ 由用户输入构造的 shell 命令
□ 对不可信数据的反序列化
□ 文件访问里的路径穿越模式

通过标准：无不受限的代码执行模式；
        任何动态执行都必须沙箱化并受约束
```

### ASI06–ASI10 运行时类（记录你的控制措施）

```
ASI06 记忆污染   → RAG/记忆系统如何防护？有无摄入过滤与来源追踪？
ASI07 智能体间通信 → agent 间消息是否认证？
…其余按你的实际环境记录
```

## 误报的四种典型

> ⭐ **这一节决定了你会不会在第二次就把扫描器关掉。**
> 呼应 `security-review.md` 的"自动阻断会侵蚀信任"。

| 误报 | 原因 | 处理 |
|---|---|---|
| `subprocess.run()` 用列表参数被报危险 | 模式匹配所有 subprocess，不看 shell 参数 | 验证是列表调用且未设 `shell=True`；**降级为 INFO 而非 CRITICAL** |
| 合法 SKILL.md 文档被标为注入 | 文档里出现"忽略之前的"等短语，用于**教学或示例** | ⭐ **扫描器应跳过三反引号内的内容**；作者把示例包进代码块 |
| 已知有问题的技能报告零问题 | 用了扫描器不支持的语言或不在模式集内的规避手法 | 结合手动清单逐行检查 |
| 大二进制文件触发 FAIL，但它是必需数据集 | 默认规则把所有 >1MB 二进制标为 HIGH | ⭐ 独立验证文件内容（`file` 命令、hex dump），**在报告里记录明确例外** |

**两个额外的实操坑**：

```
□ 仿冒包检查漏报 —— 短包名的编辑距离阈值过宽
  → 批准前手动与官方 PyPI / npm 注册表交叉验证

□ 单仓库 PR 的 CI 审计步骤超时 —— 扫描器依次处理所有变更技能
  → ⭐ 用 git diff 路径过滤器，只扫 PR 中修改过的技能

□ 默认模式下 HIGH 只产生 WARN，但团队策略要求 PASS
  → 启用 --strict
```

## 成功标准与 CI 门

**审计侧**：

```
□ 安装时零 CRITICAL
□ 新技能审计覆盖率 ≥100%，且报告存档
□ ⭐ 误报率 <15%（手动复核后确认误报的比例）
□ 平均审计时间 <5 分钟/技能（<20 个文件的标准包）
□ CRITICAL/HIGH 修复周转 <24 小时（或被明确接受风险）
```

**CI 侧**：

```
□ 托管技能的仓库，每个 PR 都跑审计工作流（采用率 100%）
□ ⭐ 重新审计合规率 ≥95%
  ——版本更新后一个发布周期内完成重新审计
```

**五件今天就能做的事**：

```
1. 审计每个已装技能（扫描器自动发现配置，不用手动指目录）
2. ⭐ 读一遍你装过的每个 SKILL.md
   ——不是扫读，是读
   ——若任何技能指示 agent 运行你不理解的 shell 命令、
     读取项目目录之外的文件、或向你无法控制的域名发请求
     → 立即移除
3. 移除来自未扫描市场的技能
4. 固定所有依赖版本
5. 维护一份已批准技能列表（团队预审计过、可信任的）
```

**常见误区**（值得贴在墙上）：

```
❌ 因为"官方来源"就不审计      ——供应链攻击专挑热门包
❌ 跳过"小技能"的审计          ——⭐ 10 行脚本里一个 eval() 就够造成危害
❌ ⭐ 只审代码不审 Markdown     ——SKILL.md 里的注入是真实攻击向量
❌ 忽略 INFO 级问题            ——它们会累积，反映安全卫生状况
❌ ⭐ 技能更新后不重新审计      ——每个版本都需要独立验证
```

## 自查

```
□ 是否知道技能以你的完整用户权限运行？
□ 是否有已装技能清单（含来源、版本、最后更新）？
□ 是否扫过 scripts/（而非只扫 SKILL.md）？
□ 是否检查过仿冒包名（与官方注册表交叉验证）？
□ 权限范围是否与声明功能相称？
□ 是否检查过硬编码密钥与越权环境变量？
□ 参数 schema 是否限制了路径/命令/URL？
□ 是否手动复核过描述里的跨工具指令与外传命令？
□ ⭐ 扫描器的仿冒与二进制误报是否有降级处理（不误伤合法内容）？
□ CI 是否用 git diff 只扫变更技能（防超时）？
□ 是否记录了 INFO 级问题（而非忽略）？
□ 技能更新后是否重新审计？
□ 是否维护了已批准技能列表？
□ 是否真的读过（而非扫过）你装的每个 SKILL.md？
```
