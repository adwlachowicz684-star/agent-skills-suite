## 1. ⭐⭐⭐ 层级腐烂的四个症状

**技能数量增长到一定规模后，"层级腐烂"会反噬 agent 的决策质量**：

```
① ⭐⭐⭐ 早期技能是"凑合能用"的粗糙产物
   ⭐⭐⭐ 几个月后仍被加载，⭐⭐ 给出过时建议

② ⭐⭐⭐ 描述里⭐ 没有有效期声明
   ⭐⭐ 场景变了，技能仍被调用

③ ⭐⭐⭐ 删除是⭐ 物理删除——无审计日志、无版本控制、⭐⭐⭐ 无法回滚

④ ⭐ 命名空间随意膨胀，无 grouping 机制，⭐⭐ 同类技能重复建设
```

> ⭐⭐⭐ 症状 ① 特别值得警惕，因为它揭示了技能库的一个⭐ 结构性问题：
> **你的技能库里质量最差的那部分，恰恰是你最早写的那部分**——
> 而它们⭐ 和最新的技能享有同等的被触发机会。
>
> ⭐⭐ 症状 ③ 与 `retirement-pipeline.md` 的"归档 ≠ 删除"完全对应：
> 那里给了解法（移 `archived/`），这里给出了⭐ 病因（物理删除无法回滚）。

## 2. ⭐⭐⭐ 五条最低限度治理清单

```
① ⭐⭐⭐ 软删除 + 归档
   delete → ⭐ 移到 .archive/
   ⭐⭐⭐ 保留⭐ 删除原因和日期

② ⭐⭐⭐ 有效期声明
   frontmatter 加 ⭐⭐ review_after
   ⭐⭐⭐ ⭐ 到期自动审计

③ ⭐⭐⭐ 强制 grouping
   ⭐⭐⭐ ⭐ 无 category 的技能⭐ 拒绝注册

④ ⭐⭐⭐ 依赖声明
   ⭐⭐ 技能 A 依赖 B 要⭐ 显式声明
   ⭐⭐⭐ ⭐ 删 B 时警告

⑤ ⭐⭐ 定期审计
   ⭐ 扫描失效 API/URL
   ⭐⭐ 验证 trigger 准确性
```

**逐条说为什么值得做**：

**② `review_after`** —— 这是本份最原创也最有用的一条。

```
⭐⭐⭐ 它把"这个技能会不会过期"从一个⭐ 需要人记得去想的问题，
      ⭐⭐ 变成了一个⭐ 有日期、可自动触发的机制。
```

> ⭐⭐ 对照 `dead-skill-detection.md` 的"低使用 + 零反馈最容易被误读成稳定运行"——
> **过期和低使用是两种不同的死法，需要两种不同的探测器**：
> 低使用靠遥测，⭐⭐ 过期靠 `review_after`。

**③ 无 category 拒绝注册** —— 强硬的注册门禁。

```
⭐⭐⭐ 它把"归类"从⭐ 事后整理变成⭐⭐ 准入条件
```

> ⭐⭐⭐ 这又是"把书面规则编码成校验器"的一个实例——
> 不是建议"最好分类"，而是⭐ **不分类就注册不了**。
> 与 `feedback-loop-design.md` 那条完全同型。

**④ 删 B 时警告** —— 与已有内容直接咬合：

```
⭐⭐ 与 deprecation-compat-strategy.md 的"跨版本循环依赖"
   ⭐⭐⭐ 和 dependency-lockfile.md 的"36.6% 隐藏依赖、仅 1.4% 声明"
   三者是同一件事的三个面：
   ⭐⭐⭐ ⭐ 你不知道谁依赖 B，所以你不敢删 B，所以 B 一直留着腐烂
```

## 3. ⭐⭐ 与"退役"的关系

```
本份（腐烂治理）        retirement-pipeline.md（退役）
─────────────────────────────────────────────
识别"哪些该退"          确认要退之后⭐ 怎么退
日常机制（review_after） 一次性流程（四阶段灰度）
预防                    处置
⭐ 只要还有价值就继续用   ⭐ 用空壳保留恢复路径
```

> ⭐⭐ 两者共同的底层原则：
> **⭐⭐⭐ 淘汰必须⭐ 可逆**——软删除 + 归档 + 保留原因和日期。
> 硬删除让"误判"无法挽回，而⭐ 误判在技能治理里是常态
> （`dead-skill-detection.md`：低使用 ≠ 没价值）。

## 4. ⭐⭐ 一个诚实的规模判断

**这份清单自称"最低限度"**——也就是说它不是完整治理方案，
而是⭐ **技能库开始腐烂时的止血带**。

```
⚠️ 适用前提：⭐ "技能数量⭐ 增长到一定规模后"
   ⭐ 个人 5–10 个技能：这些机制是⭐ 过度设计
      （呼应 directory-growth-path.md 的"过早分目录"）
   ⭐⭐ 团队 20+ 个技能：⭐ 这五条基本都该有
```

**一个与已有数字的对照**：

```
· trigger-tuning-loop.md：⭐ 10 个技能，误触发成为主要维护负担
· 本份：⭐ "一定规模后"开始层级腐烂
· routing-tiers-and-arbitration.md：>50 要上模型精排
· enterprise-registry.md：>50 个技能才需要注册中心
```

> ⭐⭐⭐ 四个独立来源给出的门槛量级是 10 / 20 / 50 三档，
> 可以串成一条**治理投入随规模递增的阶梯**：
> **<10 只需描述质量 · 10–20 加触发评测 · 20–50 加腐烂治理 · >50 加注册中心与路由编排。**

## 速查

```
□ ⭐⭐⭐ 腐烂四症状：
   ① ⭐⭐⭐ 早期粗糙产物仍在加载，⭐ 给出过时建议
   ② ⭐⭐ 无有效期声明 → 场景变了仍被调用
   ③ ⭐⭐⭐ 物理删除 = 无审计/无版本/⭐ 无法回滚
   ④ ⭐ 命名空间膨胀，⭐⭐ 同类重复建设

□ ⭐⭐⭐ 五条治理：
   ① ⭐ 软删除+归档（⭐⭐⭐ 保留原因和日期）
   ② ⭐⭐⭐ frontmatter 加 review_after → ⭐⭐ 到期自动审计
   ③ ⭐⭐⭐ ⭐ 无 category 拒绝注册（准入门禁，非建议）
   ④ ⭐⭐⭐ A 依赖 B 显式声明 → ⭐⭐⭐ ⭐ 删 B 时警告
   ⑤ ⭐⭐ 定期审计失效 API/URL + ⭐⭐ 验证 trigger 准确性

□ ⭐⭐ 过期 ≠ 低使用：⭐ 过期靠 review_after，低使用靠遥测
□ ⭐⭐⭐ 淘汰必须可逆（软删除+归档）——⭐ 误判在治理里是常态
□ ⭐⭐ 规模阶梯：<10 描述质量 · 10–20 触发评测 · 20–50 腐烂治理 · >50 注册中心

□ ⭐⭐⭐ "不是给 agent 更多技能就会更强；
         ⭐⭐⭐ 能主动淘汰过时技能的 agent，才是真正进化的"
```

**一句话**：

> ⭐⭐⭐ **技能库里质量最差的部分恰恰是你最早写的那部分，而它们和最新技能享有同等的被触发机会；
> 所以最低限度要有五条治理——软删除归档、review_after 到期审计、无 category 拒绝注册、
> 依赖显式声明（删 B 时警告）、定期审计失效 API 与触发准确性。**
