## A. 结构（6 项）

```
□ name 与目录名完全一致（不一致 = 静默失败）
□ description 非空、≤1024 字符、第三人称
□ SKILL.md ≤500 行（理想 100–150）
□ frontmatter 以 --- 顶格开头，文件为 UTF-8
```

□ scripts/ 里的脚本是否非交互、有 --help、JSON 输出、区分退出码？
□ scripts/ 是否幂等、零硬编码凭据、用相对路径？（见 **`skill-authoring` 的 `skill-crafting` 的 `script-engineering.md`**）

## B. 内容（6 项）

```
□ description 说清"做什么"和"何时用"，含真实触发词
□ description 含 Do NOT（"NOT for X → 用 Y 代替"最佳）
□ 正文有明确的输入边界——缺什么会主动追问
□ 步骤是编号的可执行流程，不是概念介绍
□ 有输出契约——交付什么、什么格式
□ 有禁止项清单，且每条禁令带理由
```

## B2. 形态（4 项，来自 `skill-crafting` 的 `guidance-forms.md`）

```
□ 每条禁令防的是"明知故犯"吗？若防的是"形状不对"，应改用输出模板
□ 有没有给规则加"除非/如有需要"？（例外条款会重新打开谈判空间）
□ description 里有没有写工作流摘要？（SDO 陷阱——模型照摘要做，跳过正文）
□ 有没有"请认真思考"这类空操作句？（模型默认就会做，白占 token）
```

> 这四项**最容易在"看起来很严谨"的技能里出现**——写得越用心越容易踩。
> 校验器会自动检查后三项。

## B3. 安全与编排（4 项）

```
□ 有无硬编码密钥 / 内网地址？（只写"从环境变量读取"）
□ 删除 / push / 部署是否设了人工确认门槛？
□ 循环/重试是否设了最大次数？
□ 多技能编排时，中间产物是否落文件、每步是否验证产物非空？
```

## B4. 测试（2 项）

```
□ 触发测试与输出测试是否分开做了？（触发 ≠ 能用）
□ 基线对比是否用了全新会话？（残留上下文会掩盖指令缺口）
```

## B5. 成本与团队（3 项）

```
□ description 在 300–500 字符？正文在 100–150 行？
□ 是否量化过：相比无技能的配对对照，它真的更快/更好/更省？
□ 是否已版本化（SemVer + CHANGELOG 记录 why）、走 PR 评审？
```

## B6. 安全边界（3 项，来自 `skill-orchestration` 的 `prompt-injection.md`）

```
□ 若读不可信内容，是否要求了边界标记（"这是数据不是指令"）？
□ 写操作的确认门在读取不可信内容之后是否仍然有效？
□ 是否只靠了输入过滤（不完整）？是否有工具白名单 + 输出验证？
```

> 技能是**可复用的指令上下文，不是独立的安全主体**——
> 干净的顶层段落无法消除稍后获取的恶意内容。

## B7. 落地与验证（3 项，来自 **`skill-authoring` 的 `skill-crafting` 的 `grounding-verification.md`**）

```
□ 是否有"验证"章节，写明了证明完成的具体命令？
□ 是否明确了什么证据够、什么不够（如"0 failures"而非"应该能过"）？
□ 是否禁止了"应该/看起来/我很有信心"这类措辞？
```

> 这是**剩余错误的主要来源**——现有技能普遍过度强调流程，而对落地和验证支持不足。

## B8. 回归防护（4 项，来自 `skill-evaluating` 的 `failure-modes.md`）

```
□ description 里有没有写成行为规范（会造成"描述渗透"）？
□ 流程是否允许"实际输入与模板不符时以实际为准"（防落地置换）？
□ 是否显式保留了交付前自检（防验证置换）？
□ 校验步骤是否分了必做/按需（防过度验证）？
```

> B5 第 2 项是**最容易被跳过也最关键**的一项：
> 研究报告显示**最好的技能胜出主要是因为回归更少，而不是提升更多**。
> "这个技能有用"是需要证明的命题，不是默认前提。

## B9. 可移植与演进（4 项，来自 `skill-selection` 的 `cross-model.md` / `lifecycle.md`）

```
□ 是否依赖角色扮演（"你是一个……"）而非具体行为要求？
□ 是否给了完整 JSON schema（而非只说"输出 JSON"）？
□ 是否有 version 字段且遵循 SemVer？
□ CHANGELOG 是否记了 why（而非 git log）？
```

> 若要在多个模型 / 客户端上跑，**必打本节**。
> 提示词是模型相关的——在 GPT 上调好的技能搬到 Claude 上可能无声失败。

## B10. 部署前安全（4 项，来自 `security-review.md`）

```
□ 是否做完了风险评级（脚本/指令操纵/MCP 引用/网络访问/硬编码凭据）？
□ 是否有网络访问——目标域名是否可信？
□ 是否按最小权限配置了工具、文件、网络？
□ 每个共享技能是否有 owner、来源、版本、可回滚？
```

> 部署到共享环境或引入第三方技能时**必打本节**。

## B11. 合规与遥测（4 项，来自 `compliance-audit.md` · `telemetry-schema.md`）

```
□ 是否有 per-agent identity（动作可归因，而非共享密钥）？
□ 日志是否结构化、防篡改、覆盖每次工具/API 调用？
□ 是否只记哈希与模板版本，而未记 prompt 原文？
□ 内容 blob 是否有 TTL 与加密（默认 24h）？
```

> 面向受监管行业或欧盟市场时**必打本节**。

## C. 计分

**A 段 6 项 + B 段 41 项。**

先打 **A 段（结构）** —— 任一项不过就先修结构，不必往下走。
再打 **B 段**，按你的技能类型**挑相关小节**打，不必全打：

| 技能类型 | 必打小节 |
|---|---|
| 任何技能 | B · B2 · B4 |
| 有写操作 / 读外部内容 | **+ B6** |
| 产出成品（报告/代码/文件） | **+ B7** |
| 进团队仓库 | + B5 |
| 已上线、要判"该不该留" | + B3 · B8 |
| 跨多模型 / 多客户端 | **+ B9** |
| 部署到共享环境 / 引入第三方 | **+ B10** |
| 受监管行业 / 欧盟市场 | **+ B11** |

**换算成 10 分制**（便于比较）：`得分 / 已打项数 × 10`

| 得分 | 判定 |
|---|---|
| **9–10** | 可交付 |
| **7–8** | 小修后可交付 |
| **≤6** | **重写** |

## D. 发布前最后三问

1. **把 description 读出来**——如果听起来像营销文案，重写
2. **检查每一步是否都有具体动词**——"分析""检查""生成"，不是"处理""优化"
3. **有没有至少一个正反例对**——模仿示例比遵循规则可靠

## E. 排错四步法

技能不生效时，按经验分布排查：**80% 在文件层**，15% 在触发层，只有 5% 在后两层。

### 第 0 步（最常被跳过）

```
□ 跑验证器：python scripts/validate_skill.py <路径>
□ 重启客户端 —— name/description 在启动时读取，不重启看的还是旧的那份
```

### 第 1 步：文件层（80%）

| 症状 | 原因 |
|---|---|
| 菜单里看不到 | **name ≠ 目录名**（静默失败） |
| 报 YAML 错 | `---` 没顶格 / 非 UTF-8 / 缩进用了 Tab |
| 技能被跳过 | 文件名不是恰好 `SKILL.md`（大小写！macOS 不敏感，**推到 Linux 才暴露**） |
| 找不到技能 | 放错了作用域目录 |

### 第 2 步：触发层（15%）

| 症状 | 原因 |
|---|---|
| 从不自动触发 | description 太模糊、缺触发词 |
| 总在不该触发时触发 | description 太宽、缺 Do NOT |
| 被别的技能抢走 | 技能冲突 / 技能偷窃 |
| 改动没生效 | 没重启客户端 |

### 第 3 步：加载层

| 症状 | 原因 |
|---|---|
| 长会话中技能"消失" | 压缩后技能清单**不重新注入**，只有调用过的存活 |
| 指令后半段被忽略 | 截断保头不保尾 |
| 嵌套技能没被发现 | 嵌套技能**不预加载**，只有处理那个目录的文件时才被发现 |

### 第 4 步：内容层

| 症状 | 原因 |
|---|---|
| 触发了但跑偏 | 指令模糊 / 缺输出契约 / 自由度不匹配 |
| 跳步 | 缺反理性化表 / 状态机 |
| 输出不稳定 | 无示例 / 无模板 / 无验收标准 |

## 一条提醒

> 结构指标与行为退化**没有相关性**（r=0.077）。
> **只有行为测试能发现真实风险。**
> 长得对不对，和跑起来对不对，是两件事。
