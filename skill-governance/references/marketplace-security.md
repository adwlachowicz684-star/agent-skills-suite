## 三个市场对照

| | SkillsMP | Skills.sh（Vercel） | ClawHub |
|---|---|---|---|
| 技能数 | 66,500+ | 83,600+ | ~3,200 |
| 审核 | 社区评审 | **人工维护者逐个审** | 人工评审 |
| 支持 agent | Claude Code / Codex CLI | 18+ | Claude Code / OpenClaw |
| 安装追踪 | 无 | 有（跨 agent） | 有（带版本） |
| 语义搜索 | 基础 | 良 | 优 |
| 版本 | semver | semver | **semver + lockfile** |
| 安全事件 | 未见公开 | 未见公开 | ⚠️ **2026-03** |

两点值得注意：

- **规模最大的不是审核最严的**。83,600 个技能靠人工逐个审，
  这个承诺的强度要打折理解——它约束的是**流程**，不保证每个都深审过。
- **只有 ClawHub 有 lockfile**。可复现安装这件事，
  在另外两家基本靠你自己 pin。

## ClawHub 2026-03 事件

**386 个技能**被发现含供应链攻击。手法：

```
把隐藏指令写进 HTML 注释
→ agent 在执行"dry run"类任务时
→ 把环境变量与 API key 外发到外部端点
```

几个值得记的细节：

- ⭐ **触发场景是 "dry run"** —— 用户以为只是预演、不会真干事，
  而外发就发生在这时候。**"看起来无害的命令"是最佳的攻击载体**。
- ⭐ **指令藏在 HTML 注释里** —— 用户翻 `.md` 文件时**肉眼不可见**，
  但模型会完整读进去。这再次印证：**静态扫描器不解析自然语言文档**。

平台的响应：

```
① 下架全部 386 个
② 审计全部 3,200+ 条目
③ ⭐ 2026-04 起要求 Ed25519 签名的技能包
```

## 签名这件事意味着什么

Ed25519 签名解决的是**"这个包确实来自它声称的作者、且未被篡改"**。

它**不解决**：

```
❌ 作者本人就是恶意的
❌ 上游作者被入侵后签了名
❌ 内容合法但设计危险（提示注入、过度权限）
```

> ⭐ 签名验的是**身份与完整性**，不是**善意与安全性**。
> 这两件事经常被混为一谈。

## 装技能前的四道检查

```
① 固定到精确版本（写进 skills.lock / 锁文件）
   ——分支会漂移，tag 或 SHA 才不动

② ⭐ 提交前人工过一遍 .skills/*.md
   ——特别留意 HTML 注释、零宽字符、与正文语气不符的段落

③ 用最小权限跑 agent
   ——⭐ 别让技能能碰到凭据存储

④ 敏感工作流优先用官方示例仓库的技能
```

第 ③ 条是**唯一能在技能已经恶意的情况下仍然止损**的措施。
前两条都可能被绕过（注释你看不见、pin 的是恶意版本本身）。

## 别把"上架"当"已审核"

这是全文最该记住的一条：

```
❌ "它在市场上架了，所以审过了"
```

三个反证：

1. ClawHub 是**人工评审**最严的一家，仍然混进 386 个恶意技能
2. 社区评审型市场，上架门槛约等于"有人提交"
3. **审核发生在上架那一刻，不是你安装的那一刻**——
   之后每次更新都是新的内容

所以正确的心智模型是：

> ⭐ **上架 = 有人在某个时间点看过一眼**
> 你装的时候，它是什么样，得你自己再看一眼。

## 一条配套的制度建议

如果团队要用市场技能，最低限度的流程是：

```
装之前  → 记录来源 URL、版本、内容哈希
装之后  → 提交到内部仓库（而不是每人各自 npx install）
更新时  → 走 PR，diff 必须被人看过
定期    → 重算哈希，与锁文件比对
```

把外部依赖**固化成内部资产**，是这类风险的唯一结构性解法。
