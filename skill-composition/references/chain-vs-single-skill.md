## 1. 链的代价是接缝，单技能的代价是步数

```
链：    A → | → B → | → C      代价 = 2 个接缝
单技能：1 2 3 4 5 6            代价 = 6 个步骤
```

两种代价的性质完全不同：

| | 链（接缝） | 单技能（步骤） |
|---|---|---|
| 失效方式 | ⭐⭐⭐⭐ 传丢 / 传错 / partial | ⭐⭐⭐⭐ 跳过某个步骤 |
| 谁付代价 | 交接的两侧 | 只有这个技能 |
| 能被复用吗 | ⭐⭐⭐⭐⭐ 能（这是链的收益） | 不能 |

> ⭐⭐⭐⭐⭐ **所以判据不是"哪个更好"，是"把接缝换成步骤，是赚还是亏"**——
> 一个接缝换掉三个步骤，通常赚；一个接缝换掉半个步骤，通常亏。

量化一下直觉（不追求精确，只为了可比）：

```
链的可靠性   ≈ p^n            （n = 环节数）
单技能可靠性 ≈ 1 - 跳步率 × 步数
```

> ⭐⭐⭐⭐ 前者是乘积，后者是线性——**环节越多，链的劣势增长得越快**，
> 而单技能只是慢慢变差。这解释了为什么短链通常没问题，长链会突然崩。

## 2. 反直觉：链的失败更静默

普遍直觉是"拆开更可控，因为每块都能单独测"。
单独测确实更容易，但⭐⭐⭐⭐⭐ **链的失败恰恰发生在"每一块都单独测过"之后**：

| | 单技能出错 | 链出错 |
|---|---|---|
| 症状 | ⭐⭐⭐⭐ 输出缺一块（可见） | ⭐⭐⭐⭐⭐ 输出完整，但少了一路（不可见） |
| 谁报错 | 没人 | ⭐⭐⭐⭐ 报错的那个不是出错的那个 |
| 定位 | 看输出就知道缺哪步 | ⭐⭐⭐⭐⭐ 要二分定位（见 chain-failure-localization） |

> ⭐⭐⭐⭐⭐ **"模块化"带来的是可替换性，不是可观测性**——
> 这两件事常被当成一件。

一条具体的中间形态：链上每一环都成功、产物都在，
但产物是**上一环按自己的理解生成的**——
`skill-chain-failure/references/chain-failure-shapes.md` 里的"形状三：错误被逐级改写"，
⭐⭐⭐⭐⭐ 它只在链里可能发生，单技能里没有"下一级"可以改。

## 3. 三条必须保留链的判据

```
① ⭐⭐⭐⭐⭐ 权限集合不同（唯一的安全判据，见 merge-signals-five）
② ⭐⭐⭐⭐ 某一环需要被别的地方单独复用
③ ⭐⭐⭐⭐ 某一环需要 fork（隔离上下文、跑很久、返回摘要）
```

第①条一票否决其余所有信号——合并后低权限场景被迫获得高权限。

第②条要真的成立才算：**"可能被复用"不算，要"已经被复用"**。
`skill-composition/references/composition.md` 里那条升级阈值（手动搬运 3 次以上）
在这里同样适用：⭐⭐⭐⭐ 没被复用过的环节，拆开只是提前支付了接缝的代价。

## 4. 三条必须合并的判据

```
① ⭐⭐⭐⭐⭐ 两环之间共享大量中间状态（传过去的比留在本地的多）
② ⭐⭐⭐⭐⭐ 顺序强耦合：B 单独跑没有意义
③ ⭐⭐⭐⭐ 需要原子性：要么都做，要么都不做
```

第①条最常被忽略，也最容易被误判成"只是数据格式问题"：

> ⭐⭐⭐⭐⭐ **如果需要传的东西比留在本地的东西还多，
> 那不是两个技能在协作，是一个技能被网络延迟隔开了。**

第②条的镜像在 `skill-refining/references/merge-signals-five.md`（顺序耦合 = 一个技能被拆成两半）。
这里是同一判据的正面表述：**A→B 永远这个顺序，且 B 的输入只有 A 能产出 → 合。**

第③条在写入型链上最致命：

```
A 改了配置，B 校验失败 → 配置处于"改了一半"的状态
```

> ⭐⭐⭐⭐⭐ 链没有事务。两个技能都成功 ≠ 系统处于合法状态——
> 中间态本身就是一种产物，而它不在任何一环的输出里。

## 5. 合并之后真正的风险

合并不是免费的。它把"接缝的代价"换成了"步骤的代价"：

```
合并后 SKILL.md 变长 → ⭐⭐⭐⭐ 步骤被跳过的概率上升
                    → ⭐⭐⭐⭐⭐ 而"跳过"这件事比"传丢"更不可见
```

参见 `skill-execution/references/partial-following.md`：
⭐⭐⭐⭐⭐ **没有后果的步骤就是可选步骤**——校验、去重、过滤这三类最先被跳。

所以合并时必须同时做一件事：**给不可跳过的步骤加一个输出字段**（`checks_run`），
或者⭐⭐⭐⭐⭐ **让被跳的步骤成为下一步的输入**（跳了它下一步就没有输入）。

> ⭐⭐⭐⭐⭐ 不这么做，合并只是把一种静默失败换成了另一种静默失败。

一条分寸：**合并的终点不是"一个技能"，是"一个 SKILL.md 装得下"**。
超过 500 行就该停——那时它不是太碎，是太大，
正确做法是拆成"主技能 + 参考文档"，不是拆成"两个技能"。

## 6. 自检

| 检查 | 不通过的信号 |
|---|---|
| ⭐⭐⭐⭐⭐ 环与环之间传的东西，比各自留下的多吗？ | 是（该合） |
| ⭐⭐⭐⭐⭐ B 单独跑有意义吗？ | 没有（该合） |
| ⭐⭐⭐⭐ 这条链上，某一环被别处复用过吗？ | 没有（保留链的理由不成立） |
| ⭐⭐⭐⭐⭐ 两环权限集合一样吗？ | 不一样（**不许合**） |
| ⭐⭐⭐⭐ 中间态算一种产物吗（写入型链）？ | 算，但没人定义它（该合或加事务） |
| ⭐⭐⭐⭐⭐ 合并后 SKILL.md 多少行？ | ⭐⭐⭐ >500（停，改拆参考文档） |
| ⭐⭐⭐⭐ 合并后有没有 `checks_run` 之类的输出字段？ | 没有（跳过不可见） |
