## 1. 嵌套是最合理的复用，所以不该禁止

嵌套几乎总是由一个正当理由引发的：

```
"这条 A→B→C 已经跑通了，现在有个更大的任务，
 我想把它当成一个步骤用。"
```

> ⭐⭐⭐⭐ **这是复用，不是过度设计——所以"不要嵌套"是一条坏规则，它不会被遵守。**

正确的做法是给它边界而不是禁令。真正会出问题的不是"嵌了一层"，而是⭐⭐⭐⭐⭐ **嵌了之后，所有为平链设计的机制（链路 ID、二分定位、覆盖率）都只覆盖了最外层**。

---

## 2. ⭐⭐⭐⭐⭐ 二分定位在嵌套下只剩一半

平链的定位：从后往前二分，复杂度 O(log n)，前提是**失败沿一条线传播**。

嵌套下：

```
父链：P1 → [子链 S] → P3
子链 S：S1 → S2 → S3
```

二分能告诉你的只有：**"子链整体失败了"**。然后你必须进到子链里再二分一次。

> ⭐⭐⭐⭐⭐ **定位成本不是相加，是逐层相乘的——你要先找到哪条链，再在链里找哪一级。**

而第二趟的前提是子链的内部日志还在。**它通常不在**：

> ⭐⭐⭐⭐⭐ 子链返回给父链的只有产物，没有日志。于是父链日志里，子链是一个黑盒节点，
> 它的失败只表现为"返回了空"或"返回了 partial"——**而这两者都指向"子链不行"，
> 不指向"子链的 S2 失败"**。

修法只有一条：⭐⭐⭐⭐ **子链必须把自己的内部摘要（哪一级失败、覆盖率多少）写进交接包**，而不是只返回产物。

---

## 3. ⭐⭐⭐⭐⭐ 链路 ID 在嵌套时会分叉

平链里 `chain_id` 是一次运行的唯一标识，一次 grep 拿到全部痕迹。嵌套下有三种可能，两种是坏的：

| 做法 | 结果 |
|---|---|
| 子链生成新 ID，不记父 ID | ⭐ **grep 父 ID 只拿到"子链入口"一条记录，看不到内部** |
| 子链沿用父 ID | ⭐⭐⭐ 能 grep 到全部，但**同一次运行里出现多个同级 span，无法区分是哪个子链的第几级** |
| ✅ 子链生成新 ID + 记 `parent_chain_id` | 一次 grep 拿到树状全部痕迹 |

> ⭐⭐⭐⭐⭐ **链路 ID 的作用是把"一次运行"拼起来。嵌套下"一次运行"是树不是线，
> 而线状的 ID 拼不出树。**

最常见的是第一种，因为它不需要额外设计——子链本来就会生成自己的 ID，只是没人想到要回写父 ID。

## 4. 代次：唯一的深度刹车

```
每进入一层子链，generation += 1
超过上限 → 停止并报错
```

> ⭐⭐⭐⭐⭐ **没有 generation 就没有终止条件。**

这与环路检测里的代次计数是同一个机制（`dependency-cycles.md`），但在嵌套里它防的不是环，是**深度失控**——而深度失控最通常的形态就是递归（见第 6 节）。

字段要随交接包传递，且⭐⭐⭐⭐ **必须由编排层写入，不能由子链自己决定**（子链不知道自己被嵌了几层）。

---

## 5. ⭐⭐⭐⭐⭐ 封装的代价：子链内部对父链不可见

封装是好设计：父链只看到子链的输入输出，于是子链可被整体替换。

> ⭐⭐⭐⭐⭐ **代价是：父链看不到子链的 status。**
> 于是子链返回 partial 时，父链按 ok 处理——因为父链不知道子链里面有 3 级，其中一级失败了。

症状很有辨识度：

```
子链：S1 ✅  S2 ❌  S3 跳过  → 返回 partial（coverage 2/3）
父链：看到"子链完成"        → P3 正常执行 → 最终输出 status: ok
```

三条规则：

```
① ⭐⭐⭐⭐⭐ 子链的 status 与 coverage 必须原样透传到最终输出，父链不得加工
② ⭐⭐⭐⭐⭐ 父链不得把 partial 改写成 ok——哪怕它"看起来大部分是好的"
③ ⭐⭐⭐⭐ 子链的产物要带自己的 stage 路径（如 S/S2），便于定位
```

第②条与 `partial-aggregation.md` 同构，但更难守：⭐⭐⭐⭐ **在平链里 partial 是"我自己算出来的"，在嵌套里它是"别人告诉我的"——而人倾向于相信自己被告知的东西，且倾向于把它转述得更好听一点。**

## 6. 递归：编排器调用自己

递归最常不是"写错了"，而是：

```
子链的某个分支，其输入恰好又匹配了父链的触发条件
→ 父链被自己调用
```

> ⭐⭐⭐⭐⭐ **触发是按 description 匹配的，没有人会想到它会匹配到自己。**

于是它比普通环更隐蔽：环里至少有两个不同的技能，看依赖图时可能被发现；**递归里只有一个，依赖图上看不出任何异常**。

唯一的防线就是第 4 节的 generation：

```
gen > 3 → 立即停止，报"疑似递归调用"，保留现场
```

> ⭐⭐⭐⭐⭐ 注意停止时要**保留现场**（写产物 + reason），不是静默返回——
> 按 `missing-input-upstream-failure.md` 那条：失败而没有 reason，上游只能猜，而它猜的方向是"格式不对"。

## 7. 深度上限为什么是 3

常见理由是"太复杂了"，这个理由不成立——复杂是主观的。真正的理由：

> ⭐⭐⭐⭐⭐ **超过 3 层后，没有人能在脑子里同时持有整条链。**
> 于是排障只能依赖日志，而日志在嵌套下恰恰是分叉的（第 3 节）。

也就是说，3 不是"复杂度上限"，是⭐⭐⭐⭐ **"人的理解力"与"日志的完整性"两条曲线的交点**。

超过 3 层的唯一正当理由：

```
⭐⭐⭐⭐ 子链是独立产品：有独立 owner、独立日志、独立版本
```

这时候它对外是一个服务，不是一个步骤——嵌套关系变成调用关系，可观测性由它自己负责。

## 8. 自检

**① 把子链替换成一个假的成功节点，父链行为不变吗？**
变了 → ⭐⭐⭐⭐⭐ **父链依赖了子链的内部细节，封装已经破了——而这种依赖不会写在任何地方**，它只会在子链重构那天突然发作。

**② grep 父链 ID，能看到子链内部吗？**
不能 → 缺 `parent_chain_id`。这是嵌套里最便宜也最常被省的一个字段。

**③ 让子链返回一次 partial，看最终输出是什么。**
如果最终是 `ok` → 第 5 节的透传规则没生效，而这条链路上的错误**永远不会被发现**。

**④ 有没有任何一处写着"最多几层"？**
没有 → ⭐⭐⭐⭐⭐ 递归没有终止条件。而递归不是理论风险，它是"触发词恰好匹配到自己"时必然发生的事。
