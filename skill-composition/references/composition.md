## 什么时候该拆成多个技能

单技能解决不了一个完整流程时。**判断信号**：

```
□ 步骤超过 5 步，且每步产出不同形态的东西
□ 有一步你想单独调用（"只搜热点，不写文章"）
□ 有一步会独立演进（换了更好的工具，只想换那一步）
□ 单文件已经超过 120 行
```

**关键收益**：一次只换一个模块。

> 一个真实的四技能博客流水线：换了更好的研究工具 → 只换 `research-collector`；
> 风格指南变了 → 只改 `quality-checker`。
> **如果是单体 SKILL.md，每次改动都是整体重写。**

## 五种编排模式

| 模式 | 结构 | 适用 |
|---|---|---|
| **线性管道** | A → B → C → D | 有严格先后依赖（选题→写稿→审稿→发布） |
| **分支管道** | A → 判定 → B 或 C | 有质量门禁（通过→发布；不通过→修复→再审） |
| **并行管道** | A+B 同时 → C 合并 | 多源聚合（同时搜中英文热点再合并去重） |
| **工具箱** | 不串联，主入口是路由表 | 功能彼此独立（Git 操作、文件管理） |
| **循环带守卫** | A → B 判定 → 回到 A | 自动修复直到通过（**必须设最大次数**） |

**判断口诀**：

```
有严格先后顺序 → 线性管道
有质量门禁     → 分支管道
需要多源聚合   → 并行管道
功能独立无依赖 → 工具箱
需要反复修正   → 循环带守卫
```

## Orchestrator 怎么写

主入口技能本质上是个**调度员**——它的"工具"就是调用其他技能。

```yaml
---
name: blog-orchestrator
description: 运行完整的研究→提纲→初稿→评审流水线产出博客文章。
  只要用户说写一篇博客、出一篇长文，就使用它。
  Do NOT use for 已有草稿只需要润色的场景。
---

## 顺序
1. research-collector（topic → research.md）
2. outline-builder（research.md → outline.md）
3. draft-writer（outline.md → draft.md）
4. quality-checker（draft.md → review.md）

## 规则
- 每步之后确认目标文件存在且非空，再继续
- review.md 若标记 3 条以上 critical，重新调用 draft-writer 修订
- 完成后返回最终 draft.md 路径
```

**三条硬性约束**：

1. **Orchestrator 控制在 120 行以内**
   > 超过这个长度，维护者就不再仔细阅读它，开始靠猜——
   > 而**这正是微妙的顺序 bug 溜进来的时候**。
2. **每步之后验证产物存在且非空**——不要假设上一步成功了
3. **用自然语言描述编排即可**，条件分支、并行、错误处理都能被理解

## 中间产物落文件

> **所有中间结果都保存成本地文件。**

三个好处：

| 好处 | 说明 |
|---|---|
| **可追溯** | 出问题能看到每一步的输出 |
| **可断点续传** | 中途停了，下次从上次的位置继续 |
| **可人工干预** | 不满意某一步，手动改完让 agent 继续 |

```
source.md → analysis.md → outline-a.md → draft-outline-a.md → final.md
```

> 这不只是工程习惯——它是第 4 章讲的**接力棒模式**的物理基础：
> **上下文窗口是易失的、有损的、会截断的**，文件不是。

## 冲突优先级

当两个技能的指令冲突时，按此顺序裁决：

```
1. 用户明确要求         ← 最高
2. 安全和数据保护
3. 主任务技能
4. 更具体的技能
5. 仍无法判断 → 询问用户
```

**在技能里显式声明边界**，能省掉大部分冲突：

```markdown
## 边界
- 我只负责逻辑审查，风格和性能交给别的技能
- 与 code-style 冲突时以 code-style 为准
```

## 三个必踩的坑

### 坑一：循环依赖

```
subagent-a → subagent-b → subagent-a   ❌ 无限循环
```

✅ 编排者可以调专家，**专家之间不互相调用**。

### 坑二：技能过载

一次挂五个技能浪费上下文，且决策开销变大。

✅ **只调用相关的那一个**，并注明"简单请求不要激活全部技能"。

### 坑三：循环没有守卫

> 见过生产事故：某个技能的终止判定写得太宽松，**循环了 200 多次烧光 token**。

✅ **必须设置最大循环次数和超时**：

```markdown
最多重试 3 次。3 次仍失败就停止并报告，不要继续尝试。
```

## 可观测：每技能的最小测试输入

> 编排流水线坏了，问题永远是"**哪个技能失败了，为什么**"。

**每个技能自带一个最小规范输入**，放在 `_skill_tests/`：

```
_skill_tests/
├── research-collector.input.txt    # 一个 topic 字符串
├── outline-builder.input.md        # 一份最小 research.md
└── ...
```

**配套做法**：编排时每步验证产物存在且非空，失败就指向具体那一步——
而不是让整条链静默产出半成品。

---

## 自查

```
□ 主入口是否 ≤120 行？
□ 每步之后是否验证了产物存在且非空？
□ 中间结果是否都落文件了？
□ 循环是否设了最大次数？
□ 是否存在专家互相调用的循环依赖？
□ 是否避免了技能过载？
□ 是否声明了与其他技能的冲突裁决顺序？
□ 每个子技能是否有 _skill_tests/ 最小输入？
```
