## 1. 乘积

```
A（最多重试 3 次）→ B（最多 3 次）→ C（最多 3 次）
```

最坏调用次数不是 9，是 **27**：

> ⭐⭐⭐⭐⭐ 因为 B 的每一次重试，都会让 A 的一次产物被重新消费，
> 而 A 自己也可能失败重试——**两层的上限是相乘，不是相加。**

三层还只是 27。加上扇出（3 个并行分支各 3 次）就已经是三位数。
而这类配置最典型的来源是：

> ⭐⭐⭐⭐⭐ **每个技能的重试都是独立配置的，写它的人只看到了自己那一层。**

这跟"每个技能单独跑都对，合起来错"完全同构——
⭐⭐⭐⭐⭐ 重试是最典型的例子，因为它有一个明确的、看起来无害的局部理由：
"失败了就再试一次，很合理。"

## 2. ⭐⭐⭐⭐⭐ 重试成功会抹掉失败记录

这条比乘积更危险，因为它影响的是正确性，不是成本。

```
A 第 1 次调用失败 → 第 2 次成功
→ 交接包里 status: ok
→ ⭐⭐⭐⭐⭐ 没人知道它失败过
```

> ⭐⭐⭐⭐⭐ **重试成功之后，"失败"这件事在输出里完全消失了。**

后果沿两条路扩散：

| 路径 | 后果 |
|---|---|
| ⭐⭐⭐⭐⭐ 覆盖率 | "3 个来源全成功"——实际是 5 次调用里 3 次成功 |
| ⭐⭐⭐⭐⭐ 延迟 | 报告里没有任何时间异常，只是"有点慢" |

> ⭐⭐⭐⭐⭐ 第一条直接命中"部分成功的汇总是静默的"——
> 那份讲的是**汇总把 partial 变成了完整报告**；
> ⭐⭐⭐⭐⭐ 这份讲的是一个更前置的动作：**重试把 partial 变成了 ok**，汇总根本没机会看到 partial。

而且慢下来的那两倍时间不会被归因：

> ⭐⭐⭐⭐ "这次怎么这么慢" → 查性能 → 查不到（单次调用都正常）
> ⭐⭐⭐⭐⭐ 真实原因是它跑了两次，而"跑了两次"这件事没有被记录在任何地方。

## 3. ⭐⭐⭐⭐⭐ 重试在写入链上不是浪费，是重复副作用

只读链上，重试最坏是浪费。写入链上：

```
A: 创建工单（超时，不确定是否成功）
A 重试 → 又创建一个
→ ⭐⭐⭐⭐⭐ 两个工单，而用户只看到一个
```

> ⭐⭐⭐⭐⭐ 这正是"重试要区分'没写入' vs '已写入但回应丢失'"那条规则**唯一真正关键的场景**。
> 在单技能里它只是条好习惯，在链上它是数据损坏与浪费的分界。

判据一句话：

> ⭐⭐⭐⭐⭐ **重试前必须先查状态，不能凭"没收到成功响应"就判定没写入。**
> 这与"行动前先查状态"（`skill-recovery/references/state-check.md`）是同一条，
> ⭐⭐⭐⭐⭐ 只是这里的触发条件是"上一次失败了"，而失败恰恰是最容易让人跳过查状态的时刻。

在并行链上还要叠加一层：⭐⭐⭐⭐ **幂等在串行里是加分项，在并行里是准入条件**——
并行分支各自失败重试时，彼此不知道对方也在重试同一个对象。

## 4. ⭐⭐⭐⭐⭐ 预算必须在链级统一分配

局部预算的算术永远算不对，因为：

> ⭐⭐⭐⭐⭐ **收益随层数递减，成本随层数指数增长。**

第 3 层的重试收益已经很小（前两层都成功了，它成功的概率本来就高），
而它的成本要乘以前两层的全部重试次数。

正确的形状是**链级预算**：

```
链总预算：call_budget = 12（不是每层 3）
分配规则：先到先得，用完即停
⭐⭐⭐⭐⭐ 停止动作：报告"预算耗尽，已取得 N/M"，不是继续
```

三条实现要点：

```
① ⭐⭐⭐⭐⭐ 预算由编排器持有，不从各技能的上限推导（推导不出来）
② ⭐⭐⭐⭐⭐ 每层调用前先扣减，扣完就停 —— 让"还能不能重试"变成一次查预算
③ ⭐⭐⭐⭐ 剩余预算随交接包传递，让下游知道自己还剩多少
```

> ⭐⭐⭐⭐⭐ 第 ② 条是关键：**把"是否重试"从各技能的自主决定，变成一次对共享预算的查询。**
> 这与"确定性判断要用确定性机制承载"是同一条原则——
> 重试与否是一个可以在链级被唯一确定的事实，不该交给每个技能各自判断。

## 5. ⭐⭐⭐⭐ attempts 必须进交接包

交接包五项必填里没有 attempts，而它恰恰是让重试可见的唯一手段：

```yaml
status: ok
attempts: 2           # 第 1 次失败，第 2 次成功
coverage: 3/3
```

三条用法：

```
① ⭐⭐⭐⭐⭐ attempts > 1 且 status: ok → 报告里必须出现"N 次中 M 次一次通过"
② ⭐⭐⭐⭐⭐ 汇总时 attempts 求和 → 真实调用次数，而不是"成功的条数"
③ ⭐⭐⭐⭐ attempts 普遍 > 1 → 上游有系统性问题，重试在掩盖它
```

> ⭐⭐⭐⭐⭐ 第 ③ 条最有价值：**重试率是一个领先指标。**
> 它在事情变成失败之前就亮了——
> 因为重试成功的东西看起来是好的，而它之所以需要重试，说明有什么东西在变差。

> ⭐⭐⭐⭐⭐ 反面也一样重要：**一个从不重试的技能，很可能不是因为它稳定，
> 而是因为它没有失败检测。** 所以 attempts 恒为 1 不是好消息，要确认它真的在检查。

## 6. 三类不该重试的失败

重试只在"失败是暂时的"时有效。三类失败重试零收益，而它们最常被自动重试：

| 失败 | 为什么重试无用 | ⭐ 正确动作 |
|---|---|---|
| ⭐⭐⭐⭐⭐ 401 / 403 权限 | ⭐⭐⭐⭐⭐ 重试不会改变权限 | 停止并报告 |
| ⭐⭐⭐⭐⭐ 输入不合法 | ⭐⭐⭐⭐⭐ 同样的输入会得到同样的错误 | 停止并报告输入问题 |
| ⭐⭐⭐⭐ 目标不存在 | 重试 N 次都是 404 | ⭐⭐⭐⭐⭐ 报告"不存在"，不要当成"暂时取不到" |

> ⭐⭐⭐⭐⭐ 中间那条在链上尤其重要：**上游传下来的错误输入，会被下游重试 N 次**，
> 每一次都失败，N 次之后整条链超时——
> ⭐⭐⭐⭐⭐ 而真正的失败原因在第一层第一次调用时就出现了。

所以每层的失败处理必须带⭐⭐⭐⭐⭐ **"可重试 / 不可重试"分类**，
而不只是"失败了怎么办"。没有这个分类，重试机制会自动去重试那些永远不可能成功的调用，
并且**把一次可立即定位的输入错误，加工成一次无法定位的超时**。
