## 五类瓶颈

| 类别 | 典型问题 | 优化方向 |
|---|---|---|
| **冷启动** | 首次加载慢、抖动 | 预热预加载、懒加载模型、内存缓存 |
| **并发** | 线程争抢、队列堆积、下游限流、超时雪崩 | 租户级配额、异步、批量合并、优先级调度、熔断 |
| **内存** | 大量技能常驻、上下文膨胀、OOM | 冷热分离、上下文裁剪、对象池、分页/流式 |
| **IO** | 频繁调外部接口，耗时占比最高 | 并行化、批量、就近/内网、精细超时 |
| **缓存** | 重复昂贵调用 | 多层缓存（**提升最明显**） |

> ⚠️ **注意区分**：这里的"性能"是**服务侧**的（延迟/吞吐/并发）；
> 上下文 token 优化见 `skill-authoring` 的 `skill-refining` 的 `context-budget.md`。

## 冷启动：两级预热

**Level 1 —— Worker 预热池**

```
传统：用户消息 → fork Worker (~500ms) → 处理
预热：用户消息 → 取池中 Worker (<10ms)  → 处理
```

**Level 2 —— 技能内容预加载**

```
传统：首次激活 → 读磁盘 → 解析 Markdown → 递归展开引用 → 缓存
预热：首次激活 → 内存缓存命中 (0ms)
```

**实测**（部分实施）：

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 新会话首条消息延迟 | 500ms–2s | **<50ms** |
| 首次技能激活延迟 | 50–200ms | **<5ms** |
| 额外内存开销 | 0 | 50–100MB（5 个预热 Worker） |

**关键设计点**：

```
□ 预热池要有淘汰——空闲超阈值的 Worker 自动销毁释放内存
□ 预热 Worker 是通用的——不绑定特定会话，首次分配时才懒加载配置
□ 规模动态调节——按当前并发量与历史峰值自动调整池大小
```

**其他冷启动手段**：

```
□ 预加载常用技能（基于历史访问模式预测常用组合）
□ 模型懒加载
□ 规则编译缓存——状态机与校验规则预编译为内存对象，避免运行时解析
□ 连接池复用——数据库/向量库/HTTP 全局复用，不每次新建
```

## IO：并行与批量

> ⭐ **把串行 N×T 改成并发 max(T)，是最直接的提速手段。**

```python
# 可并行的查询不要串行
order, logistics = await asyncio.gather(
    self.tools.query_order(ctx.user_id),
    self.tools.query_logistics(ctx.user_id),
)
```

**清单**：

```
□ 减少串行 IO——订单+物流+库存这类可并行的并发调用
□ 批量 IO——批量查用户、批量校验、批量向量检索
□ 就近调用、内网调用，减少跨网络延迟
□ 超时精细化——每个工具独立短超时 + 整体总超时兜底
□ 避免重复查询——同一次执行内相同数据只查一次
□ HTTP 连接复用 + DNS 缓存
□ 大数据用生成器/流式处理，不要一次性加载
```

**更进一步的思路——请求编排并行化**：

> 到达推理引擎之前有一串前置步骤：
> 安全意图检测 → 会话获取 → 历史消息加载 → 画像查询 → 权限校验。
> **其中很多步骤之间没有数据依赖**——安全检测不依赖会话已创建，
> 历史消息加载不依赖画像已查到。
> 从"串行流水线"改成**有向无环图（DAG）**即可并行。

## 缓存：最大的杠杆

**三层缓存**：

| 层 | 内容 | TTL |
|---|---|---|
| **L1 本地缓存** | 技能元数据、热门 SKILL.md、工具契约摘要 | 短 |
| **L2 Redis 分布式** | 技能包压缩内容、会话摘要、工具结果 | 30s–5min |
| **L3 对象存储** | 大型资源文件、模板、测试样本 | 长 |

**按作用域分**（另一种切法）：

```
全局缓存  —— 热点商家、商品库存、天气、通用规则、向量检索结果
租户级    —— 租户专属配置、常用技能规则，减少 DB 读取
会话内    —— 单次执行内复用中间结果
```

**设计要点**：

```
□ 元数据 TTL 短一些，技能包 TTL 长一些
□ 对高频技能做预热，避免冷启动抖动
□ 大资源用懒加载与分块加载
□ ⚠️ 工具结果缓存必须严格区分是否具备幂等语义
□ 防击穿/雪崩：过期时间打散、互斥锁、空值缓存
□ 实时可变数据短 TTL，静态知识长缓存
```

> ⚠️ **"工具结果缓存要区分幂等语义"这条最容易出事**：
> 把非幂等调用（下单、发消息）的结果缓存下来，会静默吞掉副作用。

**参考量级**：某案例缓存命中率 72%，100 并发下 P99 从 2.3s 降到 0.8s。

## 并发与隔离

> **不同技能的资源消耗差异很大，必须做隔离。**

```
□ 租户级隔离并发配额——避免大租户抢占资源
□ 异步非阻塞执行——IO 密集型技能用异步，释放线程
□ 批量合并请求
□ 优先级调度——付费/核心租户优先，普通租户削峰排队
□ 熔断隔离——单个技能异常不影响全局
□ 失败恢复——技能执行失败时自动回滚到最近稳定状态
```

**高并发下的四类放大效应**（值得警惕）：

```
1. Registry 访问放大——大量请求同时拉元数据，把注册中心打爆
2. Prompt 装配放大——每次都重新拼接完整上下文，CPU/内存/token 都高
3. 工具调用风暴——高频技能声明多个外部工具，峰值拖垮下游
4. 会话状态竞争——多轮对话多实例时，Session Memory、
   Tool Result Cache、Skill Cache 容易竞争与穿透
```

## 排查速查表

| 现象 | 可能原因 | 排查方向 |
|---|---|---|
| 额度掉得比预期快 | 固定开销过大 | 看系统提示词与工具定义总长度 |
| 任务越跑越慢越费 | 历史线性累积 | 是否有长循环未清理中间过程 |
| 技能不触发 | 索引描述太模糊 | 补充触发条件与典型例子 |
| 子代理反复重试 | 回传格式不一致 | **强制 schema，去掉自由文本** |
| 工具选错频繁 | 工具数量过多 | 按对象合并工具，减少数量 |
| 单轮消耗突然暴涨 | 某工具返回超长内容 | 检查工具返回是否做了裁剪 |
| 多 Agent 死循环 | 缺少轮次限制 | 加 `max_rounds` 与调用计数 |
| 上下文 token 超限 | 多轮全量传递 | 精简上下文、用摘要替代历史 |
| 批量任务卡住 | 限流或单任务超时 | 加超时、重试与指数退避 |
| 输出质量不稳定 | 技能边界太大 | 缩小范围、补充约束 |

> ⭐ **排查顺序**：
> **先看日志，再看输入输出，最后才怀疑"模型不行"。**
> 很多"模型不聪明"的实际情况，是**任务描述有歧义或技能输入输出不匹配**。

## 自查

```
□ 是否先做了测量（而非凭感觉优化）？
□ 是否优化了最慢的那部分（而非最容易的部分）？
□ 是否有两级预热（Worker 池 + 技能内容）？
□ 可并行的 IO 是否已并行（asyncio.gather）？
□ 是否在 async 函数里调了同步阻塞操作？
□ 是否有多层缓存（L1/L2/L3）？
□ 工具结果缓存是否区分了幂等语义？
□ 是否有租户级并发配额与熔断隔离？
□ 每个工具是否独立短超时 + 整体超时兜底？
□ 是否记录了 P95/P99 基线与 SLA？
□ 是否有性能退化的持续监控与自动告警？
```
