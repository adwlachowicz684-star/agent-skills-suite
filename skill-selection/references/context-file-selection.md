## 1. ⭐ 一句话规则

```
常驻的事实     → CLAUDE.md / AGENTS.md
⭐ 按需的程序   → SKILL.md
```

**判据只有一个问题**：

> ⭐ **agent 在每一个任务上都需要这条指令吗？**

```
"我们用 pnpm，不是 npm"                    → 每个任务 → 上下文文件
"API 路由返回 { data, error }"             → 几乎每个任务 → 上下文文件
"40 步的发布检查清单"                       → ⭐ 一类任务、一周一次 → 技能
"如何生成数据库迁移，含命名约定和三个坑"     → ⭐ 一类任务 → 技能
```

---

## 2. ⭐⭐ 五问决策流程

**按顺序问，第一个"是"就定位**：

```
Q1 ⭐ 这条对本项目⭐ 每一个任务都相关？
    是 → AGENTS.md（或纯 Claude Code 用 CLAUDE.md）

Q2 它是一个⭐ 多步骤的专业工作流吗？
    是 → .claude/skills/ 下的 SKILL.md

Q3 ⭐ 它需要跑脚本或执行命令吗？
    是 → SKILL.md（⭐ 唯一支持脚本执行的选项）

Q4 你们用多个 AI 编码工具吗？
    是 → AGENTS.md 放共享上下文，CLAUDE.md 放 Claude 专属，
         SKILL.md 放任务工作流

Q5 它是 Cursor 专属的编辑器行为吗？
    是 → .cursor/rules/ 下的 .mdc 文件（⭐ 与 agent 上下文文件分开）

都不匹配 → ⭐ 默认放 AGENTS.md（覆盖面最广）
```

> ⭐ Q3 那条是关键约束：**只有技能能带脚本。**
> 需要执行的流程放别处，你就只能靠模型现想（有失败率）。

## 3. 三个文件各管什么

**AGENTS.md**（工具无关的项目上下文，常驻）

```
✅ 构建与测试命令 / 项目架构 / 编码约定 / Git 工作流 / ⭐ 安全边界
❌ 任务专属工作流（→ SKILL.md）
❌ 个人偏好（→ CLAUDE.md）
❌ 长篇架构描述（⭐ 保持在 150 行以内）
```

> ⭐⭐ **AGENTS.md 是对冲工具锁定的保险**：
> 今天用 Claude Code，明天可能换 Copilot CLI 或 Codex CLI。
> **把全部上下文堆进 CLAUDE.md 就产生了锁定。**

**CLAUDE.md**（Claude 专属个人配置，常驻）

```
✅ 回复风格偏好 / 语言偏好 / 跨项目的个人编码习惯 / 工具使用偏好
❌ 项目架构（→ AGENTS.md）
```

**SKILL.md**（按需能力）

```
✅ 特定任务的逐步流程 / 检查清单与决策框架 / 输出格式要求
   / 好与坏的输出示例 / ⭐ 边界情况处理
❌ 项目专属构建命令（→ AGENTS.md）
❌ 个人编码偏好（→ CLAUDE.md）
❌ 常驻约定（→ AGENTS.md）
```

> ⭐ **15+ 个 agent 支持技能格式——它是可移植性最好的格式。**

**协作方式**：⭐ **AGENTS.md + SKILL.md 一起用，是互补不是竞争。**
Claude Code 两个文件都读。

## 4. ⭐⭐⭐ 五个常见错误

**错误 1：把所有东西塞进 CLAUDE.md**（头号失败模式）

```
开发者写出 300+ 行的 CLAUDE.md：编码规范 + 架构文档 + 工作流 + 风格指南

⭐ ETH Zurich 的研究直接证明了危害：
   ⭐⭐ 更长的上下文文件损害表现
   ——agent 遵循其中一部分、忽略另一部分
   ⭐⭐⭐ 而这种"不一致"比完全没有上下文文件更糟
```

> ⭐⭐⭐ "不一致比没有更糟"是这段话里最重要的六个字——
> **因为你无法预测它这一次会遵循哪几条**。

修法：**无情修剪**。专业工作流移到技能，跨工具上下文移到 AGENTS.md。
⭐ **CLAUDE.md 剩下的应该能装进一屏。**

**错误 2：完全不用技能**

```
很多开发者知道了 CLAUDE.md 就停在那里。
```

> ⭐ 这个对比很锋利：
> **CLAUDE.md 让 agent 知道你的架构；
> 技能让 agent 知道⭐ 怎么执行你的具体工作流。**

**错误 3：⭐ 跨文件重复内容**

```
CLAUDE.md 说"用 Vitest 测试"
AGENTS.md 说"用 Vitest 测试"
测试技能也说"用 Vitest 测试"

⭐ 三份副本 = 换测试框架时要改三处 → ⭐ 必然漏掉一处
```

修法：**单一事实来源**。

```
AGENTS.md 持有权威项目上下文
CLAUDE.md 引用它
技能引用它
⭐ 技能需要项目级信息时说"遵循 AGENTS.md 里的测试约定"，
   ⭐ 而不是复述一遍
```

**错误 4：⭐⭐ 用 LLM 生成上下文文件**

> ⭐⭐ **ETH Zurich 的研究专门测了这一点：
> 让 LLM 生成你的上下文文件，⭐ 结果比你自己写的更差。**
>
> 原因是 LLM 生成的文件**冗长、笼统，
> 而且充满 agent 已经能在代码库里看到的复述信息**。

修法：**手写**。⭐ 你比你任何 LLM 推断出的更了解项目的怪癖、约束与约定。
（模板可以参考，但要改，**不要生成**。）

> ⭐⭐ 这条跟"技能里不要写模型已经知道的信息"是完全同源的——
> **同一个错误在两个载体上各犯一次**。

**错误 5：忽视跨工具兼容**

```
今天用 Claude Code，明天可能用 Copilot CLI 或 Codex CLI
⭐ 全部堆进 CLAUDE.md = 制造锁定
⭐ AGENTS.md 是对冲
```

## 5. ⭐ 为什么分错代价很大

**机制上的原因，不是风格上的**：

```
⭐ 常驻文件在会话开始时⭐ 整个注入上下文窗口，无论是否相关

一份放在 CLAUDE.md 里的 200 行发布手册
= ⭐ 每一个"修个 typo"的请求上都有 200 行噪音
  ⭐ 你付出了 token，更糟的是付出了被稀释的注意力

同样这份手册作为 SKILL.md：
⭐ 在你真的要发版之前，它只花大约一句话（它的 description）
```

> ⭐⭐ **"被稀释的注意力"** 比 token 更重要——
> 这与 `skill-reducer-study.md` 的"减少干扰 +2.8%"
> 和 `library-size-effect.md` 的结论完全一致。

## 速查

```
□ ⭐ 常驻事实 → CLAUDE.md/AGENTS.md；⭐ 按需程序 → SKILL.md
□ ⭐ 唯一判据："每个任务都需要它吗？"

五问流程：
□ Q1 每个任务都相关 → AGENTS.md
□ Q2 多步骤专业工作流 → SKILL.md
□ ⭐ Q3 要跑脚本 → SKILL.md（⭐ 唯一支持脚本执行）
□ Q4 多工具 → AGENTS.md 共享 + CLAUDE.md 专属 + SKILL.md 工作流
□ Q5 Cursor 专属 → .cursor/rules/*.mdc（分开）
□ 都不匹配 → 默认 AGENTS.md

三文件：
□ AGENTS.md：构建命令/架构/约定/Git/⭐ 安全边界（⭐ 150 行内）
□ CLAUDE.md：回复风格/语言/跨项目个人习惯
□ SKILL.md：逐步流程/检查清单/输出格式/示例/⭐ 边界处理
□ ⭐ AGENTS.md + SKILL.md 互补；技能是 15+ agent 支持的最可移植格式

⭐⭐⭐ 五错误：
□ ⭐ 塞满 CLAUDE.md（⭐⭐ 不一致比没有更糟；ETH 研究）
□ 完全不用技能（CLAUDE.md 知架构，技能知怎么执行）
□ ⭐ 跨文件重复（三副本必漏一处 → 单一事实来源 + 引用）
□ ⭐⭐ 用 LLM 生成上下文文件（⭐ 比手写更差：冗长、笼统、复述）
□ 忽视跨工具兼容（AGENTS.md 是对冲）

□ ⭐⭐ 常驻文件无条件整个注入 → ⭐ 被稀释的注意力比 token 更贵
□ ⭐ 200 行手册放 CLAUDE.md = 每次修 typo 都带着；放技能 = 一句话
```

**一句话**：

> ⭐⭐ **300 行的 CLAUDE.md 会让 agent 遵循一部分、忽略一部分——
> 而这种"不一致"比完全没有上下文文件更糟。**
