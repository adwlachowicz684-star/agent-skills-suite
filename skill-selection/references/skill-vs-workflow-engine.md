# 技能 vs 工作流引擎：什么时候不该用技能

> ⭐ **有些东西看起来像"复杂技能"，
> 其实是一个工作流，应该用工作流引擎。**

## 根本区别

```
技能        ⭐ 概率性执行——模型读指令，尽量照做
工作流引擎  ⭐ 确定性执行——图/状态机，每次路径相同
```

> 这个区别决定了：**需要保证的事情不能靠技能。**

一个有用的类比：

```
技能      = 给一个聪明但自主的同事一份 SOP
工作流引擎 = 一条流水线，每步都由代码保证
```

## 五问判据

按顺序问：

```
① ⭐ 每一步都必须成功吗？
   是 → 工作流引擎（或至少 hook/CI）
   
② 需要长时间运行（跨小时/天）吗？
   是 → 工作流引擎（有持久化状态与重试）
   
③ ⭐ 需要精确的重试、补偿、幂等语义吗？
   是 → 工作流引擎
   
④ 路径需要可审计、可重放吗？
   是 → 工作流引擎
   
⑤ 步骤之间有严格依赖与并行编排吗？
   是 → 工作流引擎
```

**全部为否 → 技能是合适的。**

## 对照表

| | 技能 | 工作流引擎 |
|---|---|---|
| 执行保证 | 概率性 | ⭐ 确定性 |
| 状态 | 会话内（易失） | ⭐ 持久化 |
| 重试/补偿 | 靠指令描述 | ⭐ 内建 |
| 长时运行 | ❌ | ⭐ ✅ |
| 可重放 | ❌ | ⭐ ✅ |
| 灵活性 | ⭐ ✅ 高 | 较低（要预先定义） |
| 适合 | 程序性知识、判断 | ⭐ 关键业务流程 |

## 混合用法

> ⭐ **最常见的正确用法是混合：
> 引擎管骨架，技能管判断。**

```
工作流引擎：
  步骤 1 → 步骤 2 → 步骤 3（保证每步都跑、可重试、可审计）
              ↑
         这一步内部调用技能
         （技能负责需要判断的部分）
```

分工原则：

```
骨架（顺序、重试、超时、状态）  → 引擎
每个节点内部"怎么做"          → 技能
```

> **入口确定性，过程智能化**——
> 和 `skill-vs-command.md` 的组合思路一致。

## 迁移信号

一个技能该被迁移到工作流引擎的信号：

```
□ ⭐ 你开始在技能里写"如果失败，重试三次"
□ 你开始手工实现状态持久化（写文件记录做到哪一步）
□ ⭐ 你需要"从中断处继续"
□ 你需要"这一步跑了几次"的统计
□ ⭐ 失败的代价很高（钱、不可逆操作）
□ 流程步骤超过 10 步且顺序严格
```

> ⭐ 最明显的信号是第一条：
> **当你在自然语言里重新实现重试语义时，
> 说明你需要的是一个有重试语义的执行环境。**

## 一个具体对照

**适合技能**：

```
"代码评审" —— 输出是判断，错了可以再看一遍
"生成发布说明" —— 错了可以重生成
"调查事故" —— ⭐ 探索性，路径不确定
```

**适合工作流引擎**：

```
"处理退款" —— 涉及钱，必须幂等、可审计
"用户开户" —— 多系统、有补偿、不可逆
"定时对账" —— ⭐ 长时运行、需重试、需精确
```

判据很直接：**错了能重来吗？**
能 → 技能；不能 → 引擎。

## 自查

```
[ ] ⭐ 每一步都必须成功吗？
[ ] 有不可逆或涉及钱的操作吗？
[ ] ⭐ 需要长时间运行吗？
[ ] 需要"从中断处继续"吗？
[ ] 需要精确的重试/补偿吗？
[ ] ⭐ 是不是已经在技能里手写重试逻辑了？
[ ] 路径需要可重放/可审计吗？
[ ] ⭐ 混合用法是否更合适（引擎骨架 + 技能节点）？
```

## 一条提醒

> ⭐ **不要用技能去实现你本来可以用代码保证的东西。**

技能的价值在**判断与程序性知识**，
不在**执行保证**。

当你发现自己在一个 SKILL.md 里
写"必须""一定""确保"这类词的时候，
先问一句：**这个保证，是靠模型读到这句话实现的吗？**
如果是，那它就不是保证。
