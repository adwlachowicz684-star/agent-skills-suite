## 1. ⭐⭐⭐⭐⭐ 为什么必须拆到单个技能

现状通常是**只看总账**：

```
这个月 API 花了 X 元，比上月涨了 20%
```

这句话**无法指导任何行动**，因为你不知道该改哪个技能。

> ⭐⭐⭐ **没有归因的成本数据，只能用来焦虑，不能用来决策。**

而且总成本上涨有个坏属性：**它是所有技能共同造成的，
所以没有人觉得是自己的责任**——这和"技能库退化没人负责"是同一个治理问题。

---

## 2. ⭐⭐⭐⭐ 单位任务成本公式

单个技能在一次任务中的成本：

```
单位任务成本 = C_load + C_body + C_ref + C_out_delta + C_side

C_load      ⭐ 常驻元数据成本（每次判断都收，见 §3）
C_body      正文加载（触发时一次性）
C_ref       读进来的 references
C_out_delta ⭐ 输出 token 相对无技能基线的增量
C_side      ⭐⭐⭐ 副作用成本：重试、循环、脚本输出塞爆上下文
```

`C_out_delta` 这一项最容易漏，也最有信息量：

| delta | 判读 |
|---|---|
| 明显为负 | ⭐ 技能让输出更简洁——真省了 |
| 接近 0 | ⭐ 它没改变输出量，价值要另找（质量？稳定性？） |
| ⭐ 明显为正 | ⭐⭐ 带技能跑比不带还贵 → 见 §4 |

> ⭐⭐⭐ **`C_side` 是唯一会突然爆掉的项。**
> 前面四项都是线性的、可预测的，只有它会因为一次失控（重试 9 次、
> 脚本输出 3 万字）把整个月的账翻倍——
> 所以**它必须单独埋点**，不能被平均掉。

## 3. ⭐⭐⭐⭐⭐ 常驻成本：没触发也在收费

```
C_load = 元数据 tokens × 每次判断的次数
```

这一项的性质和另外四项完全不同：

| | 触发才发生 | ⭐ 每次都发生 |
|---|---|---|
| C_body / C_ref / C_out | ✅ | |
| ⭐ C_load | | ⭐⭐⭐ ✅ |

> ⭐⭐⭐ **一个从没被触发过的技能，成本不是零。**
> 它在每一次判断里都作为候选被读了一遍——
> 这正是"僵尸技能仍在损害其他技能"的可量化版本。

具体数字（来自 `three-tier-token-math.md` 与 `skill-portfolio-audit.md`）：

```
元数据  30–50 tokens/技能
候选评估 40–80 tokens/技能（认知切换）
→ ⭐ 100 个技能 × 每次判断 ≈ 10K tokens
```

对比：**一个技能被真正触发一次，正文 2K–5K**。
也就是说——⭐ **库存 100 个时，光是"考虑要不要用"这件事
就比"真的用一次"还贵。**

## 4. ⭐⭐⭐ 四类高成本技能与处方

| 类型 | 特征 | ⭐ 处方 |
|---|---|---|
| **胖正文** | C_body 高，正文 >300 行 | 拆 references、沉示例、按命中率分层 |
| **贪参考** | C_ref 高，每次读 3+ 个文件 | ⭐ 加路由表与 STOP 指令，一次只读一个 |
| ⭐ **话痨** | C_out_delta 显著为正 | ⭐⭐ 输出契约钉死格式；给模板不给描述 |
| ⭐⭐ **爆雷** | C_side 偶发极大 | ⭐⭐⭐ 加预算上限与无进展检测器 |

第三类的判据很实用：**如果技能的主要作用是"让输出更规范"，
而 delta 却是正的，那它的格式要求一定写得比需要更长**
（《skill-execution》的 `output-stability-contract.md` 同源）。

第四类不是"优化"能解决的——**必须加终止条件**，
因为偶发极大的分布意味着它不是一个可以调优的参数，是一个缺失的机制。

## 5. ⭐⭐⭐ 归因的三种实现层次

由粗到细，成本递增：

**L1 · 估算（零成本，今天就可做）**

```
用 estimate_tokens.py 算每个技能的 C_body，
乘以日志里的触发次数
```

**L2 · 日志埋点（需要改调用侧）**

```
每次调用记录：技能名 · 是否触发 · 读了几个 reference · 输出 token
⭐ 关键字段是"读了几个 reference"——不记就永远不知道 C_ref
```

**L3 · 缓存视角（最准，但要改架构）**

```
⭐⭐⭐ 用提示缓存的命中/失效来反推每个技能的真实边际成本
```

> ⭐⭐⭐ L3 的价值在于它**自动包含了 C_load 和缓存破坏**——
> 这正是前两层算不出来的部分（见 `prompt-caching-and-skills.md`：
> 技能声明 allowed-tools 会改变工具集，从而让整段历史缓存失效）。

建议：**L1 立刻做，L2 一个月内做，L3 只在成本真的成问题时做。**

## 6. ⭐⭐⭐⭐ 归账之后：四象限处置

把每个技能放到这张表上：

|  | 成本低 | ⭐ 成本高 |
|---|---|---|
| **价值高** | ✅ 保持 | ⭐ 优化（先砍 C_ref，再砍 C_body） |
| **价值低** | 观察 | ⭐⭐⭐ 优先下线 |

> ⭐⭐⭐ **"价值低 + 成本高"必须优先于其他一切处理。**
> 它是唯一一个"做了就一定赚"的格子——
> 删掉它同时省了钱、减少了候选噪音。

但有一个例外必须记住（来自 `skill-portfolio-audit.md`）：

```
⭐ 低频高价值的"专家型"技能，成本高也该留
   → 留在库里，⭐ 但不装进项目
   （见《skill-selection》的 `project-level-overload.md`）
```

## 7. ⭐⭐ 一个容易算错的项

**误算：把"技能文件大小"当成"技能成本"。**

脚本源码默认**不进上下文**——只有它的输出进
（《skill-execution》的 `three-crash-scenes.md`）。

```
❌ 脚本 2000 行 → 成本 2000 行
✅ 脚本 2000 行 → 成本 ≈ 0；⭐ 它的输出才是成本
```

> ⭐⭐⭐ 这直接导致一个反直觉结论：
> **把逻辑从正文搬进脚本，是唯一一种"代码变长、成本下降"的改动。**

反过来也一样要小心：**一个只有 20 行的脚本，如果每次吐 3 万字，
它比一个 500 行的正文贵得多。**
