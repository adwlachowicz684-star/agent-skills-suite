## 1. ⭐⭐⭐⭐⭐ 第一次失败的两种死法

**死法 A ⭐⭐⭐⭐⭐ 选了一个太难的任务**

```
"帮我写代码审查技能"
→ 边界模糊、需要判断、没有客观标准
→ 第一版必然令人失望 → "这东西不行"
```

**死法 B ⭐⭐⭐⭐⭐ 选了一个不需要技能的任务**

```
"帮我把 JSON 格式化"
→ ⭐⭐⭐⭐⭐ 模型本来就会做，技能没有任何增量
→ "这东西没用"（正确结论，但被推广成了"技能都没用"）
```

> ⭐⭐⭐⭐⭐ **两种死法的结论不同，但后果一样**：
> 一次尝试后放弃整套体系。
> 而⭐⭐⭐⭐ **关键在于：失败的是"选题"，不是"技能"这个机制**——
> 但没人会这么区分。

## 2. ⭐⭐⭐⭐⭐ 选第一个技能的四条

| 条件 | ⭐ 为什么 |
|---|---|
| ⭐⭐⭐⭐⭐ 你做过 ≥3 次 | ⭐⭐⭐⭐⭐ 三次法则；少于三次说明模式还没稳定 |
| ⭐⭐⭐⭐⭐ 有明确的"对/错" | 能判断成功与否，才有反馈信号 |
| ⭐⭐⭐⭐⭐ 你现在会做但嫌烦 | ⭐⭐⭐⭐⭐ 你脑子里已经有完整流程——它就是正文 |
| ⭐⭐⭐⭐ 错了无损失 | ⭐⭐⭐⭐⭐ 低风险：错了只是烦人，不是灾难 |

> ⭐⭐⭐⭐⭐ 第三条最实用于起步，因为它同时给了**内容来源**：
> ⭐⭐⭐⭐⭐ **"你会做但嫌烦"意味着流程在你脑子里，
> 写技能只是把它倒出来**——你不需要发明任何东西。

第四条与 `skill-adoption/references/adoption-playbook-six-steps.md` 那条
"工程师把 agent 用在手上最棘手的任务上，于是断定这工具还不行"
是同一结论：**第一个用例必须选错了也无所谓的。**

判据一句话：

> ⭐⭐⭐⭐⭐ **第一个技能应该是"你已经能闭着眼做、但不想再做的事"，
> 而不是"你希望有人帮你做的事"。**
> 后者意味着你自己也不知道该怎么做——技能无法替你补上这一课。

## 3. ⭐⭐⭐⭐ 三个好的起步候选

**① ⭐⭐⭐⭐⭐ 格式转换 / 模板填充**

```
把会议记录套进周报模板 · 把 issue 描述套进模板
```

> ⭐⭐⭐⭐⭐ 有明确对错、有模板、错了无害。
> 且⭐⭐⭐⭐ 它天然教你会"输出契约"这件事——
> 这是整套体系里最核心、也最常被忽略的部分。

**② ⭐⭐⭐⭐⭐ 你已经写了三遍以上的提示词**

```
⭐⭐⭐⭐⭐ 直接把它变成技能，不改内容
```

> ⭐⭐⭐⭐⭐ **这是唯一一个"零设计成本"的起步方式**——
> 它已经被验证过三次了（三次法则自动满足），
> 且⭐⭐⭐⭐ 你会立刻体会到"不用每次重打"这个最直观的收益。

**③ ⭐⭐⭐⭐ 团队里有明确规范的重复性动作**

```
提交信息的格式 · 分支命名 · PR 描述
```

> ⭐⭐⭐⭐ 规范已经存在（不是你要发明的），
> ⭐⭐⭐⭐⭐ 而它的价值在于"agent 会遵守"——
> 这恰好是技能相对提示词的核心优势（跨会话一致）。

## 4. ⭐⭐⭐⭐ 三个最糟的起步候选

| 候选 | ⭐ 为什么糟 |
|---|---|
| ⭐⭐⭐⭐⭐ "帮我写代码" / "帮我做架构" | ⭐⭐⭐⭐⭐ 边界无限、标准主观 → 必然失望 |
| ⭐⭐⭐⭐⭐ 需要外部系统的复杂流程 | ⭐⭐⭐⭐ 调试成本高，且失败原因常不在技能上 |
| ⭐⭐⭐⭐ 你没做过的任务 | ⭐⭐⭐⭐⭐ 你不知道什么是"对"，无法写验收 |

> ⭐⭐⭐⭐ 第二条的机制值得记：
> **起步阶段你会把所有失败归因于"技能写得不好"**，
> 而如果失败其实来自网络/权限/外部服务，
> ⭐⭐⭐⭐⭐ 你会花大量时间改一个本来就对的技能。
> （与"排错顺序按常见度排，不是按容易改排"同理。）

## 5. ⭐⭐⭐⭐⭐ 第一次跑的预期管理

> ⭐⭐⭐⭐⭐ **第一版会不好用，这是正常的，不是信号。**

三条预期：

**① ⭐⭐⭐⭐⭐ 前三次大概率要改描述**

```
⭐⭐⭐⭐ 触发不准是默认值，不是缺陷
```

> ⭐⭐⭐⭐⭐ 这是"技能默认欠触发"的直接推论：
> 排障第一反应应该是"我的描述和用户实际打的字不匹配"。
> ⭐⭐⭐⭐ 所以第一次跑就不触发，不要改正文——改描述。

**② ⭐⭐⭐⭐⭐ 不要在第一版加 Gotchas 和示例**

> ⭐⭐⭐⭐⭐ Gotchas 是采集的，不是写的——
> 第一版你还没有素材。
> ⭐⭐⭐⭐ 先写一个能跑的版本，之后每纠正一次加一条。

**③ ⭐⭐⭐⭐ 一次只修一个地方**

```
改了描述 → 跑 → 再改正文 → 跑
```

> ⭐⭐⭐⭐⭐ 同时改两处，你就不知道是哪处起了作用——
> 而这正是"复合失效"里那种
> ⭐⭐⭐⭐ "改了只改善一点点 = 有第二个故障"的廉价版。

## 6. ⭐⭐⭐⭐ 第二个技能什么时候做

> ⭐⭐⭐⭐⭐ **判据不是"想到了第二个点子"，
> 是"第一个已经被用了 ≥5 次"。**

理由三条：

```
① ⭐⭐⭐⭐ 用了 5 次才说明它真的解决了问题（不是新鲜感）
② ⭐⭐⭐⭐⭐ 用过之后你才知道"技能该长什么样"——
     第二个会比第一个好很多
③ ⭐⭐⭐⭐⭐ 过早做第二个 = 过早编排（那条已被反复验证的原则）
```

> ⭐⭐⭐⭐ 第三条是关键：
> ⭐⭐⭐⭐⭐ **只有一个技能时，你不会想去写"编排器"、
> 不会想去分目录、不会想建注册中心**——
> 这三个"过早"都发生在有 2–3 个技能、但还没用熟的时候。

一个观察可以作为自检：

> ⭐⭐⭐⭐⭐ **如果你在做第二个技能时开始设计"技能库的结构"，
> 说明你还没把第一个用够。**
