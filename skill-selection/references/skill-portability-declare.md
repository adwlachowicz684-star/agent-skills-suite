## 1. ⭐ 可移植的验收定义

```
⭐ 可移植意味着同一个技能应当在
   ⭐ Claude.ai、Claude Code 和 API 中产生一致的行为。
```

> ⭐ 注意这里的可移植定义**不是"能装上"，而是"行为一致"**。
> 一个能装上但在三个地方表现不同的技能，**不算可移植**。

---

## 2. ⭐ 依赖特定环境就要声明

```
⭐ 如果技能依赖特定环境（如某个系统包或网络条件），
⭐ ⭐ 应在 frontmatter 的 compatibility 字段中明确声明。
```

**该声明的典型内容**：

```
· 依赖的系统包（python3 / ffmpeg / imagemagick …）
· 依赖的网络条件（能否访问某个 API）
· 依赖的平台能力（能否 fork、能否用某类工具）
· ⭐ 依赖的模型能力（某些步骤需要较强模型）
```

---

## 3. 与"三条件"的关系

`three-conditions-rule-of-three.md` 的三条件是**该不该做**的判断；
这份的可移植性是**做出来能不能交付**的判断。

```
三条件（该不该做）：
   触发场景稳定 · 步骤可复用 · 输出标准明确

可移植（能不能交付）：
   ⭐ 跨产品行为一致 + ⭐ 环境依赖已声明
```

> ⭐ 一个技能可以三条件全满足，却因未声明依赖而在别人机器上静默失效。
> **"该做"和"能交付"是两道独立的关。**

---

## 4. 不声明的代价

> ⭐ **换一个环境出问题时，使用者无法判断是技能坏了还是环境不满足——只能靠猜。**

三种具体后果：

```
① ⭐ 误判为"技能写得烂"，实际只是缺个系统包
② ⭐ 使用者自己硬改，改出一份与上游漂移的本地副本
③ ⭐ 静默降级——技能跳过失败步骤继续执行，产出缺一块但不报错
```

> ⭐ 第 ③ 条最危险，与 `three-failure-modes.md` 的
> "引用不存在的文件 → 模型自己补内容"是同一类静默失败。

---

## 速查

```
□ ⭐ 可移植 = 行为一致，不只是能装上
□ ⭐ 三处应一致：Claude.ai / Claude Code / API
□ ⭐ 依赖系统包/网络/平台能力/模型能力 → 写进 compatibility
□ ⭐ "该做"和"能交付"是两道独立的关
□ ⭐ 不声明 → 使用者只能猜 → 硬改出漂移副本 / 静默降级
```

**一句话**：

> ⭐ **你没声明的依赖，在别人那里会变成"你的技能有问题"。**
