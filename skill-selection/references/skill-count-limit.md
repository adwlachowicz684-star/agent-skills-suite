## 两条硬约束

```
① ⭐ API 请求最多支持 8 个技能
② ⭐ 每多一个技能，它的 name+description 都在争夺注意力
```

第 ① 条是硬上限，第 ② 条是软性但更关键——
**它在远未到 8 个的时候就开始起作用**。

## 召回为什么会退化

回顾 `library-size-effect.md` 的分解：

```
技能遮蔽   最多占 68%（唯一置信区间排除零的成分）
上下文开销 与零无显著差异
```

机制：

```
候选变多
→ 每个候选与请求的语义重叠度都在变小
→ ⭐ 路由从"选对的"退化为"选一个差不多的"
→ 选中的那个"看起来对但实际不对"
→ 填错或漏掉必需元素
```

> ⭐ **危险不是来自无关技能，
> 而是来自被过度信任的正确相关性。**

## 怎么测量

用 eval 套件量化，而不是凭感觉：

```
步骤 1  当前技能集下跑触发 eval，记召回率 R1
步骤 2  加入新技能
步骤 3  重跑同一套 eval，记 R2
步骤 4  ⭐ R2 明显低于 R1 → 新技能带来了遮蔽
```

⚠️ 要点：**eval 必须包含 near-miss 负例**
（见 `trigger-eval-set.md`）——
正例的召回率往往到很晚才掉，
**负例先崩**。

## 什么时候停止添加

> ⭐ **用 eval 套件测量"加了之后召回有没有掉"，
> 掉了就停止添加。**

这句话看似简单，但它意味着一个反直觉的操作含义：

```
❌ "这个技能也有用，加上吧"
✅ "加上之后召回掉了 8%，不加"
```

配套的三条做法：

```
① ⭐ 按任务开，而不是全局常开
   用 skillOverrides / 停用机制（见 runtime-controls.md）

② 定期清库
   ⭐ 零调用的技能不产生收益，只进候选池
   （见 usage-analytics.md）

③ 近义技能先消除歧义，再考虑是否都留
   "NOT for X → 用 Y 代替" 是唯一不减能力而降遮蔽的手段
```

## 合并的闸门

把几个窄技能合并成一个宽技能，看起来更整洁。
但：

> ⭐ **只有在合并后的技能的 eval
> 确认与被它取代的那些表现相当时，才合并。**

这是个硬闸门，不是建议。理由：

```
合并会改变 description 的语义范围
→ 触发边界随之改变
→ ⭐ 可能合并后两边都不如以前
```

所以合并的流程是：

```
① 记录被合并的每个技能的 eval 结果（基线）
② 写合并后的技能
③ ⭐ 跑同样的 eval
④ 表现相当 → 合并
   表现下降 → ⭐ 撤回，保持分开
```

## 三个常见误解

**① "上下文大了就能多装"**

```
❌ 更大的窗口不解决遮蔽
   ⭐ 裁剪包有用；换大窗口没用
```

**② "装了不用就不占成本"**

```
❌ ⭐ 每个加载的技能都在为每一轮付费，不管有没有用过
   而且它一直在候选池里参与竞争
```

**③ "技能越多 agent 越强"**

```
❌ 真正厉害的 agent 通常只有 3–5 个技能
   ⭐ 能力 = 调度策略的质量 × 技能数量（相乘）
```

最后一条的乘法关系很关键：
**调度质量为 0 时，装 100 个技能也没用。**

## 一个具体建议

如果你的技能集已经超过 8 个且必须都留：

```
① ⭐ 按工作流阶段分组，每个阶段只启用该阶段需要的
② 用 Router 技能做分发
   （一个极短的触发技能，负责判断该调哪个）
③ ⭐ 定期跑"共存测试"
   ——单独跑得好不代表在 20 个技能里还能被选中
```

第 ③ 条呼应 `trigger-eval-set.md` 的五维：
**隔离行为与共存是两个独立维度，必须各测一遍。**

## 自查

```
[ ] 当前启用的技能数是多少？超过 8 了吗？
[ ] ⭐ 每个都真的被调用过吗？（查使用数据）
[ ] 有没有触发词重叠的技能对？
[ ] ⭐ 加新技能时测过召回变化吗？
[ ] ⭐ 做过共存测试吗（不只是单独测）？
[ ] 需要合并时，跑过合并前后的 eval 对照吗？
```
