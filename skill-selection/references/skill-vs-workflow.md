## 1. ⭐ 一句话定位

```
Skill      定义⭐「怎么做一件事」  → ⭐ 原子能力单元
Workflow   定义⭐「先做 A 再做 B」 → ⭐ 业务流程编排
```

> ⭐⭐ 一句更锋利的总结：**"一个管流转，一个管怎么做。"**
> 再配一个比喻：**Workflow 定骨架，每个环节点进去的"血肉"是 Skill 写的。**

---

## 2. ⭐⭐ 决策树

```
需求来了
├─ 偶尔做一次？
│    └─ 是 → ⭐ 直接对话，别固化
└─ 高频重复
     ├─ 单件事 → ⭐ Skill
     └─ 多步流程
          ├─ ⭐ 顺序可靠"模型自觉"就够 → Skill（SKILL.md 写软指引）
          └─ ⭐⭐ 顺序必须强制 / 要并行 → ⭐ Workflow
```

> ⭐⭐ 最关键的是最下面那个分叉，它给了个此前没有的判据：
> **"顺序是否必须强制"**。
>
> 因为⭐ **Skill 靠模型自觉执行，它没有强制力**——
> 模型哪天理解偏了，顺序就乱了。
> **你想保证顺序，就该用 Workflow，别指望模型每次都记得。**

> ⭐ 这与 `determinism-boundary.md` 那条
> "Hooks 用于模型不可被信任去遵守的事；Skills 用于模型需要知道的事"
> 是同一原则：**需要保证 → 交给有强制力的层**。

## 3. ⭐⭐ 两个方向的坑

**坑 1：把流程硬塞进 skill**

```
有人想让 skill"既管怎么做、又管流程顺序"
→ 于是在 SKILL.md 里写"第一步做 A、第二步做 B、做完 B 再做 C"
→ ⭐ 结果：skill 靠模型自觉执行，模型理解偏了顺序就乱
   ⭐⭐ 它没有强制力
```

**坑 2：用 workflow 做一件小事**

```
有人听说 workflow 很强大
→ 给"写一篇文章"这种⭐ 单点任务也写个编排脚本
→ ⭐ 凭空多出仪式感，收益为零
```

> ⭐ 坑 2 正是 `orchestrator-timing.md` 的
> "过早编排是新的过早抽象"在工作流层面的表现。

---

## 4. ⭐ 不是二选一，是配合

> ⭐⭐ **最容易被忽略的一点：skill 和 workflow 不是互斥的，经常是配合的。**

```
workflow 内容发布：
   阶段1 审核 → 调「审核 skill」的做法
   阶段2 配图 → 调「配图 skill」的做法
   阶段3 发布 → 调「发布 skill」的做法

⭐ workflow 定「先审核、再配图、再发布」这个骨架
⭐ 每个环节点进去，具体怎么审、怎么配图、怎么发 = 各自 skill 的血肉
```

> ⭐⭐ **"Workflow 定骨架，Skill 写血肉"** —— 这是两者关系最好的表述。
>
> 这也解释了为什么 `orchestrator-timing.md` 说
> "编排器不干活，它只说明顺序"。

在一个更大的技术栈视角里：

```
⭐ Skill    = ⭐ 能力层（可复用的原子能力）
⭐ Workflow = ⭐ 编排层（智能化的流程管理）
两者结合 → 更灵活、更强大的自动化系统
```

## 5. 选型补充：三个条件化判据

```
① 业务复杂度   简单任务 → Skill；复杂流程 → Workflow
② 团队技能     开发资源充足、熟微服务 → Skill
               需快速落地、缺开发资源 → Workflow
③ ⭐⭐ 变更频率  ⭐ 流程需频繁调整（如促销规则）→ Workflow
               ⭐ 能力需独立迭代（如算法优化）  → Skill
```

> ⭐⭐ 第 ③ 条最有用，因为它把"变更的是什么"变成了判据：
> **改的是流程 → Workflow；改的是能力 → Skill**。
> 这跟 `version-changelog-practice.md` 的 MAJOR/MINOR 判据思路一致。

**两边共有的风险**（三类，都要防）：

```
· 数据一致性（Skill 调用失败时的回滚）
· 权限控制（防止未授权 Skill 访问敏感数据）
· ⭐ 监控告警（流程超时 / Skill 调用失败）
```

## 速查

```
□ ⭐ Skill = 「怎么做一件事」（原子能力）
   Workflow = 「先做 A 再做 B」（流程编排）
□ ⭐⭐ 一个管流转，一个管怎么做；⭐ Workflow 骨架 + Skill 血肉

⭐⭐ 决策树：
□ 偶尔一次 → 直接对话，别固化
□ 高频 + 单件事 → Skill
□ ⭐⭐ 高频 + 多步 + 顺序可靠自觉 → Skill（软指引）
□ ⭐⭐ 高频 + 多步 + ⭐ 顺序必须强制或要并行 → Workflow

⭐⭐ 两坑：
□ ⭐ 把流程硬塞进 skill（⭐ skill 没有强制力，顺序会乱）
□ 用 workflow 做单点小事（凭空多仪式感）

□ ⭐⭐ 不是二选一，是配合：能力层 + 编排层
□ ⭐⭐ 变更频率判据：改流程→Workflow；改能力→Skill
□ 共有风险：数据一致性 / 权限控制 / ⭐ 监控告警

**一句话**：

> ⭐⭐ **Skill 靠模型自觉执行，没有强制力——
> 你想保证顺序，就该用 Workflow，别指望模型每次都记得。**
