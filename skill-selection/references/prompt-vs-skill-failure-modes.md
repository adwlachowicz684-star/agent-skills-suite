## 1. ⭐⭐⭐ Prompt 的四种失败

```
① ⭐⭐ Drift（漂移）
   ⭐ 你每次都稍微改一点提示词，⭐ 输出就跟着漂
   ⭐⭐⭐ ⭐ 到第三个月，⭐ 没有任何两次输出形状相同

② ⭐⭐⭐ Recall failure（想不起来用）
   ⭐⭐ ⭐ 你忘了用那个本来有效的提示词
   ⭐⭐⭐ 因为另一个⭐ 更容易想起的提示词浮在脑顶，你用了那个更差的

③ ⭐⭐ Copy-paste rot（复制腐烂）
   ⭐⭐⭐ 同一个提示词活在⭐ 五个地方
      ——笔记应用、项目自定义指令、三个聊天标签页
   ⭐⭐⭐ ⭐ 每份副本都⭐ 略微过期

④ ⭐⭐ Context loss（上下文丢失）
   ⭐⭐⭐ 提示词依赖⭐ 活在对话里的上下文
   ⭐⭐ ⭐ 开一个新对话，它就不好使了
```

> ⭐⭐⭐ 这四条有个共同根源，值得点明：
> **提示词⭐ 没有单一权威来源、没有版本、没有记忆。**
> ⭐ ①②③ 都是"多份/易变"的直接后果，
> ⭐⭐ ④ 是"依赖隐式上下文"的后果。
>
> ⭐⭐ 这也解释了为什么 `worth-skillifying.md` 把"稳定"列为硬标准——
> **不稳定的东西做成技能，只是把漂移从五个地方搬到一个文件里。**

## 2. ⭐⭐⭐ 技能的五种失败

```
① ⭐⭐ Over-invocation（过触发）
   描述太宽，⭐ 每个相邻任务都调用
   ⭐⭐ 症状：⭐⭐⭐ 你想简单点，它⭐ 一直做那一件特定的事

② ⭐⭐ Under-invocation（欠触发）
   描述太窄，永远够不着
   ⭐⭐⭐ 症状：⭐⭐⭐ ⭐ 你打了触发词，什么也没发生

③ ⭐⭐⭐ Stale references（过期引用）
   ⭐⭐⭐ 技能加载了一份⭐ 六个月前的 reference 文件
   ⭐⭐⭐ ⭐⭐⭐ 输出错得⭐ 自信而正确——这是最危险的一条

④ ⭐⭐⭐ Skill collision（技能碰撞）
   ⭐⭐ 两个技能都认为该自己接这个活
   ⭐⭐⭐ ⭐ agent ⭐ 不一致地挑其中一个

⑤ ⭐⭐ Dependency rot（依赖腐烂）
   跑脚本的技能⭐ 依赖的库被从底下改掉了
```

**修法**（一句顶全部）：

> ⭐⭐⭐ **"多数技能失败的修法都是⭐  sharpening the description field。
> ⭐⭐⭐ 那一行——⭐ 从 agent 的视角写、⭐ 点名准确的意图——
> ⭐ 就是'稳定触发'与'幽灵般不出现'之间的全部差别。"**

> ⭐⭐⭐ 但要诚实标注边界：
> **di ①②③ 靠改描述能修，④⑤ 不能**——
> ③ 要靠 `review_after`（`skill-decay-governance.md`），
> ④ 要靠仲裁（`collision-arbitration.md`）与唯一命名，
> ⑤ 要靠 lockfile（`dependency-lockfile.md`）。
>
> ⭐⭐⭐ 第 ③ 条尤其值得单独记：**"输出错得自信而正确"**
> ——这与 `priority-override-layers.md` 的"结构正确的废话"、
> `skill-rot-rollback-discipline.md` 的"自信的漂移读起来就像改进"
> 是⭐ 同一现象的第四个说法。四份独立来源反复命中它，
> 说明⭐ **这是技能最难被发现的失败模式**。

## 3. ⭐⭐⭐ 混合模式：技能载方法，提示载请求

> ⭐⭐⭐ **最有效的配置⭐ 不是"全用技能"或"全用提示"，⭐⭐ 而是两者并存、有清晰分工。**

```
⭐⭐⭐ 技能处理⭐ 工作中重复出现的形状
   约定 · 结构 · 参考资料 · 工具
   ——那些⭐ 你不想再重新描述一遍的东西

⭐⭐⭐ 提示处理⭐ 当天的具体请求
   主题 · 受众 · 交付物 · 约束
   ——那些⭐ 会变的东西
```

**具体例子**：

```
内容团队：
   技能 = blog-post-writer（语气、结构、联盟链接、交叉引用约定）
   提示 = "给我写一篇 3000 字的榜单，关于最好的 Postgres 备份工具，
          面向 infra 工程师，含价格对比表"
   ⭐⭐⭐ ⭐ 技能加载约定，提示点名工作

代码：
   技能 = 评审技能（你们团队怎么审 PR：严重度分级、跳过什么、升级什么）
   提示 = 要审哪个 diff
```

> ⭐⭐⭐ 一句总结：
> **"技能加载约定；提示点名工作。⭐ 单独哪个都不如两者合起来好。"**

**一条很好用的规则**（三个来源一致表述）：

```
⭐⭐⭐ "如果你⭐ 已经把同样的指令打了两遍，
      ⭐⭐ 那不是提示词的问题，⭐⭐⭐ 是⭐ 缺一个技能。"
```

> ⭐⭐ 数字上的张力我们此前仲裁过：
> 五层选型说"复制 2 次"，三次法则说"出现 3 次"——
> ⭐⭐⭐ 这里是⭐ 第三个来源说"两次"，
> 所以"2 次看成本、3 次看模式"的仲裁仍然成立，
> ⭐ 但"两次就该警惕"这个信号⭐ 又多了一票。

## 4. ⭐⭐ 七步转换

> ⭐⭐⭐ **不要把提示词粘进技能文件就完事。**

```
① ⭐⭐ Extract the repeated job
   给它命名：customer-research-brief · code-review-risk-scanner

② ⭐⭐⭐ Define when to use it
   加触发条件 ⭐⭐ 和⭐⭐⭐ 负向条件（防止它到处适用）

③ ⭐⭐⭐ Move current facts out
   ⭐⭐ 把"这一次"的事实移出去：
       某个客户的名字 · 某个分支 · 某个活动截止日期
   ⭐⭐⭐ ⭐ 这是⭐ 从提示转为技能⭐ 最关键的一步

④ ⭐⭐ Preserve the method
   保留：步骤 · 清单 · 示例 · 输出格式 · 质量门槛

⑤ ⭐⭐ Add one test case
   ⭐⭐⭐ 拿真实输入跑一次，⭐ 看结果⭐ 是否比原来的提示更好

⑥ ⭐ Version the change
   当技能开始影响真实工作，记录改了什么

⑦ ⭐ 更进一步：⭐⭐⭐ 提示是草图本，技能是存档的操作规程
```

> ⭐⭐⭐ 第 ③ 步"把当前事实移出去"是这份文档最实用的一条——
> **提示词里塞着本次任务的具体信息，这正是它不能被复用的原因**；
> 而很多人的做法正是"把整个提示粘进去"（也就是
> `token-cost-optimization.md` 说的⭐ **伪技能陷阱**）。

**何时该保留为提示**（四条，别过度技能化）：

```
⭐ 探索期：你在试三种不同做法，提示该保持流动
⭐⭐ 一次性上下文：一次客户通话摘要、一份文档、一个临时规划问题
⭐ 快速变体：想要五个标题选项或一次快速改写
⭐⭐ ⭐ 技能之前：⭐⭐⭐ 技能的第一版⭐ 往往就是一个"被证明好用了几次"的提示
```

## 5. ⭐⭐ 一个极简起步模板

**挑一个你本月重复解释过的任务，写七行**：

```
Name:        大白话（PR Review / Client Update / Bug Triage）
When to use: ⭐⭐ 2–3 句⭐ 真人会说的原话
Steps:       ⭐ 你已经在用的那份真实清单
Never do:    ⭐⭐ 2–3 个⭐ 过去犯过的错
Done means:  ⭐⭐⭐ 那条能证明它做成了的检查
```

> ⭐⭐⭐ 注意最后一行 **"Done means"**——
> 它正是 `judgment-branches-acceptance.md` 三件套里的"验收"，
> ⭐⭐ 也是七个契约里的"验收契约"。
> **三个独立来源都把"何时算完"列为必写项。**

## 速查

```
□ ⭐⭐⭐ Prompt 四失败：① Drift（三月后无两次同形）
   ② ⭐⭐⭐ Recall failure（⭐ 用了更容易想起的那个更差提示）
   ③ ⭐ Copy-paste rot（五处副本各自过期）
   ④ ⭐⭐ Context loss（⭐ 换对话就失效）
   ⭐⭐⭐ 共同根源：⭐ 无单一权威来源、无版本、无记忆

□ ⭐⭐⭐ Skill 五失败：① 过触发 ② 欠触发
   ③ ⭐⭐⭐ Stale references——⭐⭐⭐ "错得自信而正确"（最难发现）
   ④ ⭐⭐⭐ Skill collision（⭐ 不一致地挑一个）⑤ ⭐ 依赖腐烂
   ⭐⭐⭐ ①②③ 靠 sharpen description；⭐⭐ ④⑤ 不能，要靠 review_after/lockfile/仲裁

□ ⭐⭐⭐ 混合模式：⭐⭐⭐ 技能载方法（重复的形状），提示载请求（当天的具体）
   ⭐⭐⭐ "技能加载约定；提示点名工作"
□ ⭐⭐⭐ "同样的指令打了两遍 = 缺一个技能"

□ ⭐⭐ 七步转换，⭐⭐⭐ 第③步最关键：⭐⭐ 把本次的事实移出去
   （不做这步 = ⭐ 伪技能陷阱 = 把提示粘进去）
□ ⭐⭐ 保留为提示的四种：探索期 · 一次性上下文 · 快速变体 · ⭐ 技能之前
□ ⭐⭐⭐ 极简七行模板含 ⭐⭐⭐ "Done means"——三个独立来源都列为必写
```

**一句话**：

> ⭐⭐⭐ **Prompt 失败于漂移/想不起来/副本腐烂/换对话失效，技能失败于过触发/欠触发/过期引用/碰撞/依赖腐烂——
> 而"输出错得自信而正确"（过期引用）是四个独立来源反复命中的、最难被发现的失败模式；
> 最优解是混合：技能载方法，提示载请求。**
