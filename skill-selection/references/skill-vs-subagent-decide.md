## 1. ⭐⭐⭐ 判断轴是隔离，不是大小

**常见（错误）的判断方式**：

```
❌ "任务看起来很大 → 用子代理；
    其他情况 → 用技能"
```

> ⭐⭐⭐ **"大小"不是问题所在。⭐ 隔离才是。**
>
> ⭐ 这个纠正很重要，因为按"大小"判断会导致一个具体错误：
> **把需要上下文的大任务丢给子代理，答案反而变差**——
> 因为隔离扔掉的正是任务需要的信息。

---

## 2. ⭐⭐ 一句话区分

```
技能   = ⭐ 改变⭐ 当前 agent 知道什么、怎么做
子代理 = ⭐ 改变⭐ 谁在做、在哪里做
```

```
技能   = 一个⭐ 程序，加载进当前上下文
         （同一个会话、同一份之前所有内容的记忆）
子代理 = ⭐ 一个独立的上下文，自己干活，⭐ 只回报结论
```

| 维度 | 技能 | 子代理 |
|---|---|---|
| 改变什么 | 当前 agent 的知识与程序 | ⭐ 谁执行、在什么上下文里 |
| 上下文 | ⭐ 加载进现有对话 | ⭐ 独立窗口 |
| 成本 | ⭐ 便宜（空闲时只有 name+description） | ⭐ 更高（新上下文 + 交接开销） |
| 擅长 | 以特定一致的方式做一件事 | ⭐ 并行 / 隔离噪音探索 |
| 输出 | 直接塑造主对话 | ⭐ 返回结果；⭐⭐ 内部步骤不回来 |
| 可组合 | ⭐ 也能被子代理加载 | ⭐ 能加载自己的技能 |

## 3. ⭐⭐⭐ 那个测试：这个任务需要"忘掉其余一切"吗

> ⭐⭐⭐ 直白地问一句：
> **⭐ 这个任务会不会因为"看不到其余对话"而受益？**

**用技能**（任务需要上下文里已有的东西）：

```
· 调试一个你们已经讨论了十轮的失败
· 对照会话早期做出的决定来审查一个 diff
· 写一段必须匹配三轮前定下的语气的东西
```

> ⭐⭐⭐ **这些在隔离上下文里都会变差，
> 因为⭐ 隔离扔掉的正是任务需要的那份信息。**

**用子代理**（否则会把上下文灌满你不需要的噪音）：

```
· 搜两百个文件来回答"代码库里是不是已经有 X"
  → 产生一大堆中间读取与 grep
  ⭐⭐ 你不想要那座山留在主会话里，你只想要那个答案
· ⭐ 对抗性的第二意见
  → ⭐⭐ 不被它本该检查的那套推理污染，才更有用
```

> ⭐⭐ 第二条例外漂亮：**"不被污染才更有用"** ——
> 这是"隔离"作为⭐ 质量手段（而非仅仅是成本手段）的论据。
> 呼应 `multi-agent-review.md` 的 challenge_agent 需要全新视角。

## 4. 两种常见错误

**错误 A（常见）：出于反射，对任何"看起来费劲"的任务先用子代理**

```
⭐⭐ 这会丢掉那个本可以让答案变好的上下文
```

> ⭐⭐ 而且有个不可逆的代价：
> **子代理的输出是一个"结论"，⭐ 产生它的那条推理链已经被扔掉了。**
> 如果下一步需要"你为什么这么判断"，你已经没有了。

**错误 B（少见但代价更高）：因为"委派更麻烦"而在主会话里跑极宽的搜索**

```
⭐⭐ 你读的每一个文件都留在上下文里，不管它有没有用
⭐⭐ 到第 40 条消息时，agent 正对着一整个会话的死重量做推理
```

> ⭐⭐ 这两个错误方向相反，但根因相同：**都在用"看起来麻不麻烦"做判断，
> 而不是用"这个任务需不需要看得见其余对话"。**

## 5. ⭐⭐ 组合模式：子代理挂技能

> ⭐⭐⭐ **强的模式不是二选一，而是⭐ 派一个子代理并给它挂上技能——
> 这样被隔离的工作⭐ 依然在遵循一套经过锤炼的程序，而不是即兴发挥。**

**一个具体场景**（40 个文件、前后端都有、团队有固定审查清单）：

```
只用子代理：
   前端一个、后端一个，并行返回摘要
   ⭐ 快、不互相纠缠
   ⭐⭐ 但每个子代理各按自己的方式审查——
       没人保证它检查了"迁移是否可回滚"或用了团队的实际标准

只用技能：
   pr-review 技能带着团队的确切清单
   ⭐ 保证无论谁审都走同样的步骤
   ⭐⭐ 但如果审查横跨 40 个文件，所有这些读取都发生在一个上下文窗口里

⭐⭐⭐ 组合：
   按代码库区域派子代理（隔离 + 速度）
   ⭐ 每个子代理加载同一个 pr-review 技能
   → ⭐⭐ 同时得到并行性和一致性
```

**一句完美的总结**：

> ⭐⭐ **子代理决定工作在哪里发生；技能决定它到了那里之后怎么做才算做好。**

**多阶段流水线的通例**：

```
⭐⭐ 每个阶段为了上下文卫生而隔离；
⭐⭐ 每个阶段自带程序，这样被委派的那个步骤
    ⭐ 就不会是主步骤的一个"监督得更差的版本"。
```

> ⭐⭐⭐ 最后半句是这套方法论里对"委派质量"最精准的警告——
> **委派不等于降标准**。这与 `subagent-skill-inheritance.md` 的
> "子代理不继承技能，必须显式列 skills:"是配套的：
> **不显式挂技能，你的子代理就是在裸奔。**

## 速查

```
□ ⭐⭐⭐ 判断轴是⭐ 隔离，不是大小
□ 技能 = 当前 agent 知道什么/怎么做
   子代理 = ⭐ 谁在做、在哪做

□ ⭐⭐⭐ 测试：⭐ 这个任务会因为"看不到其余对话"而受益吗？
   否 → 技能（调试已讨论十轮的失败、对照早期决定审 diff、匹配既定语气）
   是 → 子代理（搜 200 个文件只想要答案、⭐ 对抗性第二意见不被污染）

□ ⭐⭐ 错误A（常见）：出于反射先派子代理 → ⭐ 丢掉本该有用的上下文
   ⭐⭐ 子代理只回结论，⭐ 推理链已被扔掉
□ ⭐⭐ 错误B（少见但更贵）：在主会话里跑极宽搜索
   → 每读一个文件都留下，⭐ 到第 40 轮全是死重量

□ ⭐⭐⭐ 组合：⭐ 派子代理 + 给它挂技能
□ ⭐⭐ 子代理决定工作在哪发生；技能决定到了那儿怎么做才算好
□ ⭐⭐⭐ 委派 ≠ 降标准；⭐ 不显式挂技能 = 子代理裸奔
```

**一句话**：

> ⭐⭐⭐ **别按"任务大不大"选——按"这个任务需不需要忘掉其余一切"选。
> 子代理决定工作在哪里发生，技能决定它到了那里之后怎么做才算做好。**
