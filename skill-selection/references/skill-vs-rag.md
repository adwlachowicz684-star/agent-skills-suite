## 核心区分

| 维度 | Skills | RAG |
|---|---|---|
| **知识类型** | **程序性知识（How-to）** | **陈述性知识（What）** |
| 加载时机 | 任务触发时 | 每次请求检索 |
| 复用性 | 高（可跨项目） | 中（依赖知识库质量） |
| 确定性 | 高（脚本可确定执行） | 低（检索有随机性） |
| 核心模块 | 技能库、调度器、执行引擎 | 检索模块、生成模块、知识库 |
| 开发重点 | 技能接口定义、执行逻辑 | 知识库构建、检索调优 |
| 运维重点 | 版本管理、执行状态监控 | 知识库更新、召回率监控 |

> ⭐ **一句话经验法则**：
> **流程固定、可脚本化的用 Skill；动态变化、海量文档类的用 RAG。**

**心智模型**：

> Skills 像**程序性记忆**（procedural memory）——
> 你会骑自行车、会调试代码，是"怎么做"的知识，
> **需要连贯、不容易碎**。

## 按文档类型选

> **最实用的判断框架**：文档不是铁板一块。

| 文档类型 | 适合 | 原因 |
|---|---|---|
| 教程 / 操作指南 | **Skills** | 过程性、需完整步骤、连贯性要求高 |
| 架构 / 概念设计 | **Skills** | 需整体理解，**碎片化检索会丢失全局** |
| 工作流 / SOP | **Skills** | 纯过程性，能编码"先做什么后做什么" |
| 内部最佳实践 / 编码规范 | **Skills** | 需要被**遵守**而非**引用** |
| **API Reference**（数千端点） | **RAG** | 体量太大、查询是精确事实查找 |
| Changelog / Release Notes | **RAG** | 高频更新、时间敏感 |
| 产品目录 / 工单库 | **RAG** | 体量巨大、关联式查找 |
| Troubleshooting / FAQ | **两者皆可** | 看体量：几十条用技能，几千条用 RAG |

## 三维判断法

**用技能替代 RAG 的条件**（四条全满足才划算）：

```
□ 知识高度流程化——如"如何提交代码""邮件格式规范""会议纪要模板"
□ 体量可控——能归纳成有限数量的技能文件，不必建大向量库
□ 需精确遵循——希望模型严格按既定步骤或格式输出，减少自由发挥
□ 成本敏感——省掉 embedding、检索和上下文 token
```

**仍应使用 RAG**：

```
□ 知识量大且分散——成百上千文档，难以全部写成技能
□ 强动态性——文档频繁更新，需从最新内容检索
□ 开放问答——用户问题多样，难以用固定技能覆盖
□ 需引用溯源——要返回具体文档来源和引用片段
```

## 为什么不能用技能替代 RAG

> ⚠️ **一个常见误区**："RAG 知识库直接内置到 SKILL.md 里，
> 是不是可以直接替代 RAG，而且准确性更高？"

**三大核心障碍**，第一条是致命的：

**① 效率灾难**

> 模型输入按 token 计费。**把整个知识库塞进技能，等于每次都为全部内容付费。**
> 而 RAG 只给你那 **20 token** 的相关片段。
> **对于精确事实查找，用技能是杀鸡用牛刀，还白占上下文。**

**② 更新成本**——知识库变了就得改技能、发版本。

**③ 无溯源**——技能里的知识无法告诉你"这句话出自哪份文档"。

## 混合架构

> ⭐ **纯 Skills 或纯 RAG 都不是最优解——分层混合才是。**

```
上层：Skills 管理人工 curate 的过程性知识
      （教程、架构、工作流、最佳实践），几十到一百个
下层：RAG 兜底大体量的事实性文档
      （API reference、changelog、知识库），百万级自动检索
```

**一种更精巧的混合——用 RAG 检索 Skills**（两阶段）：

```
阶段一：把所有技能的 description 做 embedding，
        查询时向量检索 top-k 相关技能
阶段二：只把这几个技能的完整内容加载进上下文
```

> ⭐ **这打破了"技能数量受索引规模约束"的限制**——
> 因为索引不再需要全部塞进上下文，而是用向量检索**预筛**。
> 呼应 **`skill-evaluating` 的 `metrics.md`** 里"候选池 5 → 100 精确率掉 10 倍"的问题：
> **这是那个问题的解法之一。**

**配合干活的实际例子**：

```
用户需求：根据本月销售合同，生成业绩报告并推送到企业群

1. AI 读 Skill 手册，明确流程：查数据 → 统计分析 → 生成报告 → 推送
2. 按 Skill 要求，调 RAG 检索本月销售合同与业绩数据
3. RAG 返回切片后的精准数据
4. AI 按 Skill 的固定流程整理、生成标准报告、完成推送
```

## 迁移注意事项

```
□ 数据兼容性——从 RAG 迁到 Skills，要把事实性知识转化为执行逻辑
  （如"某产品价格"查询 → 封装成"获取产品价格"技能）
□ 接口标准化——定义统一的输入/输出规范，
  避免因技能差异导致集成困难
  （有项目因各模块格式不兼容，浪费了 30% 开发时间在转换上）
□ 稳定性监控——技能可能依赖外部 API，需熔断与降级
□ 版本管理——技能更新要版本化，避免行为不一致
```

## 自查

```
□ 这段知识是"怎么做"还是"是什么"？（前者→技能，后者→RAG）
□ 体量是否可控（几十条 vs 几千条）？
□ 是否需要精确遵循步骤（而非自由发挥）？
□ 是否需要引用溯源（需要→RAG）？
□ 更新频率高吗（高→RAG）？
□ 是否考虑了分层混合（上层技能、下层 RAG）？
□ 技能数量多到影响检索时，是否考虑用向量检索预筛技能？
□ 是否有统一的输入输出接口规范？
```
