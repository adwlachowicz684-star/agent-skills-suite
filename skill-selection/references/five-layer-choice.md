## 1. ⭐ 一句话区分

```
Prompt      当场给的"口头指令"        —— 一次性、低风险、不需要长期复用
Skill       反复用的"标准作业程序"     —— 重复、需要清单/示例/参考/模板
Project     项目文件夹（文档+历史）    —— 规则适用于整个仓库/团队，而非单一任务类型
MCP         连到外部系统的"接线"      —— 需要实时访问系统、API、数据库
Subagent    有角色和权限的"专员"       —— 需要独立角色、独立评审、或有界的专业推理
```

---

## 2. 六维对比表

| 维度 | Skills | Prompts | Projects | MCP | Subagents |
|---|---|---|---|---|---|
| 提供内容 | **程序性知识** | 即时指令 | 背景知识 | 工具连接 | 任务委托 |
| 持久性 | **跨对话** | 单次对话 | 项目内 | 持续连接 | 跨会话 |
| 包含内容 | 指令+代码+资源 | 自然语言 | 文档+上下文 | 工具定义 | 完整 agent 逻辑 |
| 加载时机 | **动态按需** | 每轮 | 项目内始终 | 始终可用 | 调用时 |
| 可执行代码 | 是 | 否 | 否 | 是 | 是 |
| Token 效率 | ⭐ 高 | 中 | 低（始终占） | 中 | ⭐ 低（3–4 倍） |

## 3. ⭐ 决策指南

> ⭐ **选能解决问题的最小那一层。**

```
规则需要被强制执行      → ⭐ 技能本身太软 → Hook
工作流需要可复用的判断  → ⭐ 单靠 shell 脚本太窄 → 技能
任务需要外部数据        → ⭐ 光靠提示文字很快会过期 → MCP
```

具体场景：

| 场景 | 推荐 |
|---|---|
| 一次性咨询 | Prompts |
| ⭐ **每次都要解释同一套做法** | **Skills** |
| 围绕特定产品/项目的长期讨论 | Projects |
| 想按角色分离权限 | Subagents |
| 需要直连 GitHub 或数据库 | MCP |

**一条很实用的升级信号**：

> ⭐ **如果你已经把同一段指令复制了两次以上，
> 那就是把它从 prompt 提升为 skill 的信号。**

**上手顺序**（从简到繁）：

```
① 只用 Prompts，识别重复任务
② ⭐ 把重复任务提升为 Skills
③ 长期/团队项目用 Projects
④ 权限分离/并行用 Subagents
⑤ 内部系统与外部 SaaS 用 MCP
```

> ⭐ **别一上来就建一堆技能。先做 3–5 个，
> 只把你真正重复的流程提升上来。**

## 4. ⭐ 两条最容易搞混的边界

**① Skill vs MCP**

> ⭐ **如果你的指令里出现了 query、fetch、look up、current state
> 这类词，你几乎肯定需要 MCP——
> ⭐ 因为技能是程序性知识，无法触及上下文中不存在的数据。**

```
⭐ MCP 把 Claude 带到数据那里
⭐ 技能告诉 Claude 拿到数据之后该怎么做
⭐ 两者是搭档，不是替代品
```

**② Skill vs Subagent**

> ⭐ **如果同一份专业知识被不止一个 agent 或对话需要，
> 它就应该在技能里，而不是 baked 进某个子代理的系统提示。**

```
⭐ 子代理是专家，技能是它们共用的专业知识库
```

反面：

> ⭐ **把评审清单或分析方法硬编码进某个子代理的提示里，
> 就把它困在那儿了。第二个 agent 需要同样的知识时，
> 你就在维护两份副本。**

## 5. 组合：层是要叠加的

> ⭐ **生产系统很少只用一层。这些块是层，最强的架构会把它们组合起来。**

一次竞品分析请求可以穿过全部五层：

```
Project   常驻上下文  —— 保存这项研究的研究资料与指令
MCP       实时数据    —— 从 drive 拉取当前简报、从仓库拉数据
Skill     方法框架    —— ⭐ 应用分析方法，让每次分析口径一致
Subagents 并行工作    —— ⭐ 同时跑几个离散部分，各自加载它需要的技能
Prompt     refinement —— 针对眼前这个具体问题微调结果
```

> ⭐ **每一层都做了其他层 genuinely 做不到的事。**

**协同的具体形态**：

```
· 子代理可以加载技能
· Agent Teams 可以给不同成员分配不同技能
· MCP 集成配上捕获其使用工作流的技能后，会变得更完整
· 一个 command 可以调用一个技能
· ⭐ 一个 hook 可以在技能执行前拦下危险命令
· 一个插件可以打包技能 + 命令 + hooks + MCP 配置
```

## 速查

```
□ ⭐ 指令里有 query/fetch/lookup/current state → 要 MCP，不是技能
□ ⭐ 知识被多个 agent 需要 → 放技能，不要写进子代理提示
□ ⭐ 同一段指令复制 ≥2 次 → 升级为技能
□ 规则要强制执行 → 技能太软，用 Hook
□ 先做 3–5 个技能，别一上来铺开
□ ⭐ 层是叠加的，不是二选一
□ Subagent token 3–4 倍，谨慎使用
```

**一句锋利的**：

> ⭐ **如果一条规则需要被强制执行，单靠技能太软。
> 如果一个工作流需要可复用的判断，单靠 shell 脚本太窄。**
