## 1. ⭐⭐⭐⭐ 三种"规则"的加载差别

| 维度 | CLAUDE.md | `.claude/rules/` | Skill |
|---|---|---|---|
| ⭐⭐⭐ 何时加载 | ⭐ 每次会话 | ⭐ 每次会话，**或**当匹配文件被打开 | ⭐⭐⭐ **按需**——被调用或相关时 |
| 作用域 | ⭐ 整个项目 | ⭐⭐ 可按文件路径限定 | ⭐ 任务特定 |
| 最适合 | ⭐ 核心约定与构建命令 | ⭐⭐ 语言特定 / 目录特定的指引 | ⭐⭐⭐ 参考资料、可重复工作流 |

> ⭐⭐⭐⭐ 这张表第一次把⭐ 三者的⭐ 本质差别说清了：
> **它们存的东西很像（都是指令），差别只在⭐ 什么时候加载、⭐ 对多大范围生效。**
>
> ⭐⭐⭐⭐⭐ 而 `.claude/rules/` 那格⭐ 特别值得注意——
> ⭐⭐⭐⭐⭐ **它拿回了 CLAUDE.md 的一部分场景，且是⭐ 唯一能按路径触发的**：
> 带 `paths` frontmatter 的规则⭐ 只在 Claude 处理匹配文件时加载，⭐ 省上下文。
> ⭐⭐⭐⭐ 这与技能的 `paths:` 字段⭐ 是同一机制——
> ⭐⭐⭐ 差别在于⭐⭐⭐ **rules 每次会话都在（只是按文件省），
> ⭐⭐⭐⭐ ⭐ 而技能是⭐ 默认不加载**。

**CLAUDE.md 与技能的经典分工**（官方原话）：

> ⭐⭐⭐⭐ **"如果 Claude 应该⭐ 始终知道它，放进 CLAUDE.md：
> ⭐ 编码约定、构建命令、项目结构、'绝不做 X' 规则。
> ⭐⭐⭐⭐ 如果是 Claude ⭐ 偶尔才需要的⭐ 参考资料（API 文档、风格指南），
> ⭐⭐⭐ 或⭐ 你用 `/` 触发的⭐ 工作流（部署、评审、发布），放进技能。"**

> ⭐⭐⭐⭐⭐ 注意后半句那个⭐ 常被忽略的并列：
> ⭐⭐⭐⭐⭐ **技能同时承载两种东西——"偶尔要查的参考资料"和"用 / 触发的工作流"。**
> ⭐⭐⭐ 这解释了为什么⭐ 有些技能⭐ 既难触发又难写：
> ⭐⭐⭐⭐ ⭐ 它们其实是⭐ 两类东西混在了一起（这与"伪技能陷阱"同源）。

## 2. ⭐⭐⭐ 技能 vs 子代理：官方原话

```
技能   = ⭐⭐⭐ 可加载到⭐ 任意上下文的⭐ 可复用内容（⭐ 跨上下文共享内容）
子代理 = ⭐⭐⭐ ⭐ 独立运行的⭐ 隔离工作者（⭐ 上下文隔离）
```

| 维度 | 技能 | 子代理 |
|---|---|---|
| 它是什么 | ⭐ 可复用指令 / 知识 / 工作流 | ⭐ 带自己上下文的隔离工作者 |
| ⭐ 关键收益 | ⭐⭐⭐ **跨上下文共享内容** | ⭐⭐⭐ **上下文隔离** |

> ⭐⭐⭐⭐⭐ 官方这个"关键收益"的对比⭐ 极其干净，
> ⭐⭐⭐⭐ 而且⭐ 和 `skill-vs-subagent-decide.md` 的结论⭐ 完全吻合：
> 那份说⭐ 判断轴是⭐ 隔离而不是大小
> （"这个任务会因为⭐ 看不见其余对话⭐ 而受益吗？"），
> ⭐⭐⭐⭐⭐ 这里则给出⭐ 反向的那一半——⭐⭐⭐⭐ **技能的关键收益是"共享"**，
> ⭐⭐⭐⭐ ⭐ 所以⭐ 需要共享的东西⭐ 就不该放进子代理。
>
> ⭐⭐⭐⭐ 两者合起来，判据就对称了：
> ```
> ⭐ 要隔离 → 子代理（代价：拿不到共享）
> ⭐ 要共享 → 技能（代价：占主上下文）
> ```

## 3. ⭐⭐⭐ 输出风格与 CLAUDE.md 的分工

| 维度 | CLAUDE.md | 输出风格（output style）|
|---|---|---|
| 装什么 | ⭐ 关于项目的事实与规则 | ⭐⭐⭐ 一个角色、语气、响应格式 |
| 切换 | ⭐ 始终加载 | ⭐⭐ 一次只有一个生效，⭐ 可随时切换 |
| 最适合 | 构建命令、约定、"绝不做 X" | ⭐⭐⭐ 更短的回复 / 解释多寡 / ⭐ 非工程角色 |

> ⭐⭐⭐⭐ 判据很实用：
> ⭐⭐⭐⭐ **"如果它⭐ 在你用什么风格时⭐ 都成立 → CLAUDE.md；
> ⭐⭐⭐⭐ ⭐ 如果它是⭐ 关于'回复本身'的、⭐ 而且你可能想⭐ 关掉它 → 输出风格。"**
>
> ⭐⭐⭐ 三条通用规则：
> ```
> · ⭐⭐⭐ 它们会⭐ 叠加（CLAUDE.md 无论什么风格⭐ 都在）
> · ⭐⭐⭐ Claude ⭐ 两者都当指令遵循，⭐⭐⭐⭐ ⭐ 所以⭐ 两者都不被强制
> · ⭐⭐⭐⭐⭐ ⭐ 任何⭐ 必须每次都发生的事 → ⭐ 用 hook
> ```
>
> ⭐⭐⭐⭐⭐ 第三条是"确定性判断要用确定性机制承载"的
> ⭐⭐⭐⭐⭐ **第八个独立来源**，且⭐ 官方表述最直白：
> **"For anything that has to happen every time, use a hook."**

## 4. ⭐⭐⭐⭐ 三句判据

```
① ⭐⭐⭐⭐ 每条会话都需要 → CLAUDE.md（或 rules，若可按路径/语言细分）
② ⭐⭐⭐⭐ 偶尔要查、或要能被调用 → 技能
③ ⭐⭐⭐⭐ 需要隔离上下文 → 子代理（⭐ 想并行/怕污染主上下文时也用它）
```

**子代理 vs 动态工作流**（一个容易混的点）：

```
子代理：⭐⭐⭐ Claude ⭐ 逐轮决定⭐ 下一步跑什么；每个回报一份摘要
工作流：⭐⭐⭐ ⭐ 脚本决定——跑很多子代理，⭐ 后台执行，⭐ 返回一个结果
```

> ⭐⭐⭐ 这个对比⭐ 此前完全没覆盖过：
> ⭐⭐⭐⭐ **差别在于"谁决定下一步"**——⭐ 模型还是脚本。
> ⭐⭐⭐⭐⭐ 又是⭐ 同一条主线的⭐ 又一个场景：
> ⭐⭐⭐⭐ **顺序/调度是⭐ 确定性的 → 该由脚本决定；
> ⭐⭐⭐⭐ ⭐ 需要判断力的 → 才交给模型。**

## 5. ⭐⭐ 两条此前没收过的硬约束

```
① ⭐⭐⭐ CLAUDE.md ⭐ 保持在 200 行以内；⭐⭐⭐⭐ 超了就把参考内容⭐ 移到技能或拆进 rules
② ⭐⭐⭐ MCP 工具名⭐ 始终用⭐ 完全限定名：ServerName:tool_name
```

> ⭐⭐⭐⭐ 第 ① 条给了一个⭐ 具体的数字（此前我们只有"300 行 CLAUDE.md 的代价"），
> ⭐⭐⭐⭐ 且⭐ 它与"技能正文 <500 行"⭐ 形成了一套⭐ 完整的尺寸阶梯：
> ```
> CLAUDE.md  <200 行
> SKILL.md   <500 行
> reference  >100 行需带 TOC
> ```
>
> ⭐⭐⭐ 第 ② 条虽小但⭐ 会导致静默失败——
> ⭐⭐⭐⭐ 与 `naming-conventions.md` 里"camelCase 技能注册后⭐ 全部失效"
> ⭐⭐⭐ 同类：⭐⭐⭐ **名字形式的错误不报错，⭐ 只是永远匹配不上。**

## 速查

```
□ ⭐⭐⭐⭐ 三种"规则"差别只在⭐ 何时加载 + 对多大范围生效：
   CLAUDE.md 每次会话/整个项目 · rules 每次会话⭐或按路径/可限定 · 技能⭐按需/任务特定
   ⭐⭐⭐⭐⭐ rules 是⭐ 唯一能按路径触发的（带 paths frontmatter）
□ ⭐⭐⭐⭐ 分工：⭐ 始终要知道 → CLAUDE.md；⭐ 偶尔查 或 ⭐ /触发的工作流 → 技能
   ⭐⭐⭐⭐⭐ ⚠️ 技能同时承载"参考资料"和"工作流"两类东西
      → ⭐⭐⭐ 一个技能里混了这两类 = ⭐ 既难触发又难写（与伪技能陷阱同源）
□ ⭐⭐⭐⭐⭐ 技能关键收益=⭐共享；子代理关键收益=⭐隔离 → ⭐⭐⭐⭐ 判据对称了
□ ⭐⭐⭐⭐ 输出风格 vs CLAUDE.md：⭐ 用哪种风格都成立→CLAUDE.md；⭐ 关于回复本身且想能关掉→风格
   ⭐⭐⭐⭐⭐ ⭐ 两者都只是指令，都⭐ 不被强制 → ⭐ 必须每次发生的事⭐ 用 hook（第八个来源）
□ ⭐⭐⭐ 子代理 vs 工作流：⭐⭐⭐ 差别是"谁决定下一步"——模型（子代理）还是脚本（工作流）

□ ⭐⭐⭐⭐ 尺寸阶梯：CLAUDE.md<200行 · SKILL.md<500行 · reference>100行带TOC
□ ⭐⭐⭐ MCP 工具名⭐ 始终写完全限定名 ServerName:tool_name（形式错=永远匹配不上，不报错）
```

**一句话**：

> ⭐⭐⭐⭐ **三种"规则类"载体的差别不在存什么、而在"何时加载、对多大范围生效"——CLAUDE.md 每次会话整个项目、rules 可按路径触发、技能完全按需；而技能的关键收益是"跨上下文共享"、子代理是"上下文隔离"，判据因此对称：要隔离就用子代理（代价是拿不到共享），要共享就用技能（代价是占主上下文）。**
