# 库规模效应：真正伤人的是遮蔽，不是上下文

> 直觉是"技能装多了占上下文，所以变笨"。
> ⭐ **实测结论正好相反：上下文开销在任何库规模下都与零无显著差异。**

## 两个被混淆的假设

装了很多技能之后表现变差，有两种解释：

```
假设 A（上下文税）
  目录本身吃掉窗口 → 留给任务的空间变少 → 表现下降
  推论：换个大窗口就能救

假设 B（技能遮蔽 / skill shadowing）
  候选变多 → 路由选错 → 调用了"看起来对但实际不对"的技能
  推论：⭐ 换大窗口完全没用，只能减少候选
```

这两种解释开的药方完全不同。前者让人去买更长上下文的模型，后者让人去删技能。

## SkillsBench 的分解结果

在 Haiku 4.5 与 Sonnet 4.6 上，从"oracle 技能集"扩展到 **202 个技能**的库：

```
通过率下降        21%
```

把这个下降拆开归因：

| 成分 | 贡献 | 置信区间是否排除零 |
|---|---|---|
| ⭐ **技能遮蔽** | **最多 68%** | ✅ **是（唯一一个）** |
| 上下文开销 | — | ❌ **任何库规模下都不排除零** |

> ⭐ **这是本条最重要的一句话**：
> 遮蔽是**唯一**统计上站得住的降解成分。
> 上下文开销的贡献**测不出来**。

所以前面常说的"1,236 个技能吃掉 36.6% 上下文"是**真实存在的成本**，
但它**不是表现下降的原因**。两件事都真，因果关系不成立。

## 为什么整形无效

这个结论对采购决策有直接含义：

```
❌ "表现差是因为上下文不够 → 换 1M 窗口的模型"
   ——窗口变大，遮蔽一个不少

✅ "表现差是因为候选太多 → 减少同时可见的技能"
```

具体数字：裁剪包**有用**；加大窗口**没用**。

这也解释了为什么"把描述写长写全"会有反效果——
描述变长意味着**每个候选携带更多可匹配的表面积**，
反而增加了被错误匹配命中的机会。

## 对装技能的直接含义

三条可执行的：

```
1. 只装当前阶段真的会用的技能
   批量装一个"团队标准包"是最常见的自伤方式

2. ⭐ 每装一个，问：它会和谁抢同一批触发词？
   冲突检测比数量控制更重要

3. 用 skillOverrides / 停用机制做"按任务开"
   而不是"全局常开"
```

配套的一条：**不要因为"以后可能用到"而预装**。
未被调用的技能不产生收益，只进入候选池。

## 怎么测自己的库

最简单的配对对照：

```
步骤 1  只启用目标技能，跑 N 个任务，记通过率 P1
步骤 2  启用全部技能，跑同样 N 个任务，记通过率 P2
步骤 3  P2 << P1  → 存在遮蔽，开始裁
        P2 ≈ P1   → 你的库规模还没到临界点
```

⚠️ 判定要点：**任务集必须是你真实会做的任务**，
不能用"你写 description 时的那套措辞"构造——那样天然会命中正确技能。

如果发现遮蔽，处理顺序：

```
① 删掉从未被调用的技能（用 /skill-doctor 看调用频次）
② 合并触发词重叠的技能
③ 给冲突的技能写显式的 "NOT for X → 用 Y 代替"
④ 最后才考虑拆包分发
```

> 第 ③ 条是唯一能"在不减少能力的前提下"降低遮蔽的手段：
> 它不是把候选移出池子，而是**在池子里给路由一条更强的判据**。

## 一条提醒

这个结论（arxiv:2605.24050v2）来自 **SkillsBench 的特定设置**，
模型的路由能力会持续变化。别把它当物理定律，
把它当**"先查遮蔽再查上下文"的排查顺序**来用 ——
这个顺序本身是稳的，具体百分比会变。
