## 前缀匹配：唯一的核心原理

> **Prompt caching 是 agentic 系统里影响力最大的单项优化。**
> Claude Code 靠它把成本降了约 **90%**。

```
API 缓存与之前请求匹配的最长前缀。
在位置 N 处任何改动，都会使 N 之后的所有缓存失效。
```

**渲染顺序（顺序很重要）**：

```
[System Prompt] → [Tool Definitions] → [System Reminders] → [会话消息]
                    ↑ 稳定前缀                                ↑ 动态后缀
```

**计费**：

| 操作 | 倍率 |
|---|---|
| 缓存写入（5 分钟 TTL） | **1.25×** |
| 缓存写入（1 小时 TTL） | **2×** |
| **缓存读取** | **约 0.1×** |

> ⭐ **你不是每轮都在为完整上下文付费。**
> 全价付一次（写入），之后每次读取约 10%。
> **稳定前缀越长，省得越多。**

**最小长度**：小模型约 1024 tokens，大模型约 2048 tokens 才进入缓存。

## 稳定前缀 vs 可变后缀

```
[稳定前缀 —— 缓存一次，读 N 次]
  系统提示
  工具定义
  技能（预加载）
  项目 CLAUDE.md
  参考文件（会话开始时读）

[可变后缀 —— 每轮都是新的]
  会话历史
  当前用户消息
  最新工具结果
```

**实测结构**（一个真实项目会话）：

| 组成 | tokens |
|---|---|
| Claude Code 系统提示 | 9,300 |
| **预加载的技能正文** | **6,800** |
| CLAUDE.md + 项目上下文 | 4,200 |
| 会话历史（变化） | 2,400 |
| 当前消息 + 工具结果（变化） | 800 |
| **合计** | **约 23,500** |

```
稳定前缀 20,300（约 95%）    可变后缀 3,200（约 5%）

有缓存：20,300 × 0.1 + 3,200 × 1.0 = 5,230 有效输入 token
无缓存：23,500 × 1.0               = 23,500

节省 78%
```

## 什么会打破缓存

| ❌ 做法 | 为什么失效 | ✅ 替代 |
|---|---|---|
| **把时间戳 / 当前日期写进静态系统提示** | 前缀每天甚至每分钟都变 | 把日期放进当轮的用户/系统**消息**里 |
| **工具顺序不确定** | 同样的工具、不同的字节 = miss | **排序并冻结**工具定义 |
| **会话中途增删改工具 schema** | 工具定义一变，其后全部失效 | **启动时声明全部工具**；用 `tool_choice` / `allowed_tools` 限制，而不是删除定义 |
| **中途切换模型** | 缓存是**按模型**隔离的 | 留在父模型上；把活交给**子代理**或新会话 |
| **中途改 effort / thinking 设置** | 这些渲染在内容之前，属于缓存前缀 | 保持不动（Opus 5 / Fable 5.1 可在会话中改 effort 而不破缓存） |
| **切换开关（如 web search / 引用 / 速度）** | 会使工具块之外的部分失效 | 翻转开关前先看官方失效表 |
| **工具结果插入顺序不确定** | 并行调用返回快慢不一，结果落在了更早的用户消息之上 | 保证插入顺序确定 |

> ⚠️ **最经典的自摆乌龙**：
> 开发者为了记日志，在系统提示里放了个**实时时间戳**——
> 这保证了**缓存命中率永远是 0%**。

## 技能加载是头号杀手

> 三种中途失效里，**只有这一种你能控制，也最贵**。

```
技能触发 → 正文注入系统提示区 → 前缀变长
→ 之前缓存的版本（不含技能）不再匹配
→ 下一轮为更长的新前缀支付缓存创建成本
```

**解法**：

> ⭐ **在会话开始就预加载你会用到的所有技能。**
> **缓存在 5 次以上读取后就能回本。**

算一笔账（1,500 token 的技能在 turn 1 加载）：

```
前期成本：约 1,875 缓存创建 token
之后每轮节省：约 9,000 缓存读取 token
→ 在第 2–3 轮之间转正，之后 60 轮持续净赚
```

> **注意这与渐进式披露的张力**：
> 按需加载省的是**上下文窗口**，预加载省的是**缓存命中率**。
> 两者不矛盾，但**适用场景不同**——
> 长会话、多轮、技能确定会用到 → 预加载更划算；
> 短会话、技能不确定 → 按需加载更划算。

**渐进式工具加载**（官方解法之一）：

```
启动时声明所有工具，但把很少用的标记为 defer_loading：
它们不进入缓存前缀，只在 agent 用工具搜索查到时才追加进会话
→ 缓存得以保留
```

## 子代理的缓存病理

> ⭐ **子代理拿到的是全新上下文窗口，不继承父级的缓存前缀。**

```
一个要读 12 个文件的研究子代理
→ 全部按未缓存输入计费
→ 返回后，这份缓存被丢弃（子代理上下文是临时的）
```

**技能触发的 post-edit hook 同理**：每次加载都创建新上下文、运行、销毁。

**实测后果**：

```
40 次调用的任务里 30 次是子代理或技能调用
→ 即使父代理自己保持 80% 命中率，
  整个任务的有效命中率可能只有 15–25%
```

**成本对照**（一天、一位开发者）：

| 状态 | 命中率 | 日总成本 |
|---|---|---|
| 优化缓存 | 80% | $48.90 |
| 默认缓存 | 50% | $79.50 |
| **缓存崩坏**（并行 agent + 技能churn） | **20%** | **$106.50** |

> **token 量相同，产出相同，唯一差别是命中率。**
> 20 人团队 × 20 工作日，首尾相差约 **$23,000/月**。

**对策**：

```
□ 并行 agent 限制在缓存经济能支撑的数量
  ——技术上能开 8 条，经济上最优通常是 2–3 条
□ 临时子代理路由到更便宜的模型
  ——反正它的缓存会被丢弃，冷输入的绝对成本更要紧
  读 50K token：Opus $0.25 / Sonnet $0.15 / Haiku $0.05
  "浏览并总结"类任务，Haiku 才是对的
```

## 恢复命中率的手段

```
□ 把 CLAUDE.md / 系统提示 / 工具定义冻结成稳定布局
  ——如果每周重新生成 CLAUDE.md 并带"最后更新"时间戳，
    你每周都在烧毁缓存。在 CI 里用脚本校验大前缀文件的
    逐字节稳定性
□ 固定子代理与技能配置里的工具顺序
□ 会话间隔超过 5 分钟时用 1 小时 TTL
  ——写入 2× 而非 1.25×，但同一前缀复用约 4 轮即回本
□ 系统提示的更新用"消息"方式注入，而不是编辑系统提示
□ 缓存预热：会话开始时发一个 max_tokens: 0 的带显式断点请求
  ——处理并写入缓存但不生成内容（可在用户还在打字时做）
□ 别超过 TTL：5 分钟从请求开始计时；
  若 agent 阻塞在超过 5 分钟的工具调用/子代理上，
  父级缓存会在结果回来前过期 → 改用 1 小时 TTL
□ 压缩（compaction）时必须共享前缀，否则用官方 compaction API
□ 按工作流审计命中率，而不是按月看总额
  ——API 返回里 cache_creation_input_tokens /
    cache_read_input_tokens / input_tokens 是分开的
```

> ⭐ **一个聪明的时机选择**：
> **某些操作（如压缩）本来就会重写大部分缓存，
> 那正是切换模型或 effort 的好时机**——反正你已经要为 miss 付费了。

## 附：工具数量与动态增删

> 两条来自生产实践的硬教训，与缓存直接相关。

**① 工具不是越多越好**

```
工具超过 10 个时，准确率开始下降
超过 20 个，边际收益急剧递减
接入多个 MCP server 时，90+ 个工具定义轻松超过 50,000 token
——模型还没开始思考，上下文窗口就已经被塞满了
```

> 信息的过载不会带来更好的决策，只会带来更差的决策。
> 这呼应 `skill-evaluating` 的 `metrics.md` 的"候选池越大精确率越低"。

**② ⭐ 动态增删工具会让 KV-Cache 完全失效**

```
在 agent 运行过程中动态添加或删除工具，
会导致 KV-Cache 从变更点开始完全失效。
```

**成本差距**：

```
缓存命中    $0.30 / 百万 token
缓存未命中  $3.00 / 百万 token
差距 10 倍
```

> **KV-Cache 命中率是生产级 agent 的第一指标。**

**正确做法**：

```
□ ⭐ 尽一切可能避免在迭代过程中动态增删工具
□ 如果必须改变可用工具集，用 token logit masking
  在解码层面控制，而不是修改上下文
□ 启动时声明全部工具；很少用的标记为 defer_loading
  （它们不进缓存前缀，只在被查到时才追加进会话）
```

> 这与 `caching-economics.md` 主线一致：
> **缓存要求前缀稳定，任何中途变更都要付出 10 倍代价。**

**③ 一个容易犯的致命错误**

> ⚠️ **把 agent 之前犯过的错误日志也压缩掉了**——
> 结果就是**同样的错误反复出现**。
>
> 上下文压缩时应保留失败记录（呼应 `skill-authoring` 的
> `skill-orchestration` 的 `memory-state.md` 与 `skill-crafting` 的
> `anti-rationalizations.md`）。

## 自查

```
□ 是否在会话开始就预加载了确定会用的技能？
□ 系统提示里是否有时间戳、会话 ID、随机数等易变内容？
□ 工具定义是否已排序冻结，且不在中途增删？
□ 是否避免了会话中途切换模型 / effort / 开关？
□ 并行子代理数量是否在缓存经济能支撑的范围（2–3 条）？
□ 临时子代理是否路由到了更便宜的模型？
□ 长时间阻塞的调用是否改用了 1 小时 TTL？
□ 是否做过缓存预热（max_tokens: 0）？
□ 是否按工作流（而非按月）审计命中率？
□ 是否在 CI 里校验了大前缀文件的逐字节稳定性？
```
