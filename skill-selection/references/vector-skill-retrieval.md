## 1. 为什么需要它

模型的激活决策是**纯 LLM 推理**（见 `activation-rate.md`），
当技能数量增长，元数据层变嘈杂，**路由质量下降**——
⭐ 即使没有任何单个技能发生变化（微软渐进式披露研究）。

实测：候选池 5 → 精确率 29.6%；候选池 100 → **3.3%**。

> ⭐ **更好的技能内容，不保证对的技能会被选中。**
> 所以需要在决策前**缩小候选集**。

---

## 2. 检索流程

```
用户请求
   ↓
意图分类器（轻量模型/微服务）→ 分类（如 data_analysis）
   ↓
向量检索（meta DB）→ ⭐ Top-K（推荐 3–8）
   ↓
Rerank / GraphRAG（结合工具依赖与知识图谱）→ Shortlist
   ↓
技能遮蔽（deny 其他）+ 执行循环
```

**Top-K 通常 3–8**——这个数字在多份实践中反复出现。

## 3. 实现要点

| 环节 | 做法 |
|---|---|
| Embedding 源 | 每个技能的 `name` / `description` / `example` |
| 模型选择 | ⭐ 短文本用小型 embedding 模型即可（省成本） |
| 权重策略 | ⭐ 按工具的历史成功率与频次加权 |
| 更新频率 | ⭐ 建议每周，或每次技能变更时重建 |
| 规则补充 | ⭐ 对明确关键字（"PDF"、"Excel"）做硬匹配，降低漏召回风险 |

> 最后一条重要：**纯向量会有漏召回**，
> 所以要用关键词硬匹配兜底。

---

## 4. ⭐ 冷启动：先别上向量检索

> ⭐ **初期工具少时，先用规则分组**（文档/数据/API），再逐步细化。

理由：向量检索需要维护索引、处理更新、调权重——
在技能只有几个时，这套开销远大于收益。

渐进路径：

```
少量技能 → 规则分组
中等     → 关键词硬匹配 + 规则
较多     → ⭐ 加向量检索 + Rerank
```

---

## 5. 边界

向量检索解决的是**候选集太大**，
它**不解决**：

```
技能描述本身写得差  → 见 description-patterns.md
技能之间语义重叠    → 见 namespace-collision.md（要先拆职责）
```

> ⭐ **先拆职责、写好 description，再上检索。**
> 顺序反了，检索只会更高效地选到错的那个。

---

## 速查

| 问题 | 处置 |
|---|---|
| 技能多了选不准 | ⭐ 先减候选（拆/合并），再考虑检索 |
| Top-K 取多少 | 3–8 |
| embedding 源 | name + description + example |
| 怕漏召回 | ⭐ 关键词硬匹配兜底 |
| 技能很少 | 规则分组就够，别上向量 |
