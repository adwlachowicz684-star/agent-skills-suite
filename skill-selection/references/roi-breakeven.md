## 1. ⭐ 回本公式

```
B = 一次性构建与验证成本（工程师小时）
S = 每次运行的节省（人工分钟 + 回收的 token 成本）
N = 每月运行次数

⭐ 回本月数 = B / (S × N)
```

```
⭐ 一季度内回本      → 轻松 yes
⭐ 超过一年才回本    → ⭐ 值得审视
```

> ⭐ **公式里那个"非显然的杠杆是 N（运行频率）"——
> ⭐ 团队一贯高估它。**
> 一个一年只用两次的任务，**无论多巧妙都摊销不掉构建成本**。

**具体算例**：

```
重复任务：人工 12 分钟，每周 30 次 = 每周 6 小时
技能 + MCP 改成：30 秒提示 + 快速复核 ≈ 2 分钟
→ ⭐ 每周回收 5 小时

构建：技能 3 天 + MCP server（若不存在）1 周
→ ⭐ 回本在"周"这个量级，而不是"月"
   ⭐ 但仅仅因为该任务每周重复 30 次
```

> ⭐ **同一个算式，换成"每月两次"的任务——构建成本永远回不了本。**

## 2. ⭐ 四把尺子打分表

| 尺子 | 5 分 | 3 分 | 1 分 |
|---|---|---|---|
| ⭐ **频次** | 每周 ≥5 次 | 每周 2–4 次 | 每周 ≤1 次 |
| **标准化** | 格式与质量标准都明确 | 有大致标准，允许灵活 | 完全主观 |
| **可拆解** | 能拆成 3–7 个清晰步骤 | 能拆但步骤模糊 | ⭐ 完全是黑盒 |
| **价值** | 显著省人力或规避重大风险 | 有一定效率提升 | ⭐ 只是"尝鲜" |

```
⭐ 总分 ≥12  → 放心去做，大概率不亏
⭐ 8–11 分   → 做个简化版试试水
⭐ <8 分     → ⭐ 直接用 Prompt，别费那个劲
```

> ⭐ **"可拆解"是基础**：拆不开就写不了执行逻辑、做不了测试、给不了兜底。

**另一套公式**（同样强调频率）：

```
价值 = 频率 × (节省时间 + 学习成本)
⭐ 阈值：年节省 50 小时
```

**实测对照**：

| 任务 | 频率 | 单次 | 年耗时 | 学习成本 | 值得？ |
|---|---|---|---|---|---|
| 微信爬取 | 每天 | 30 分钟 | 182 小时 | 高 | ✅ |
| 亮点总结 | 每天 | 20 分钟 | 121 小时 | 中 | ✅ |
| 知识库索引 | 每天 | 10 分钟 | 61 小时 | 低 | ✅ |
| ⭐ Git 提交 | 每天 | 1 分钟 | 6 小时 | 低 | ⭐ ❌ |

> ⭐ **最反直觉的是最后一行**：
> **Git 提交频率极高，但单次只省 1 分钟——用 Git alias 就够了。**
> 这印证了那句"⭐ 高 ROI 技能几乎总是枯燥的高频流程"，
> 但也说明：**高频是必要条件，不是充分条件。**

**不值得做的三种情况**：

```
① ⭐ 学习成本太低   —— date +"%Y-%m-%d" 太简单，不需要技能
② ⭐ 频率太低       —— 一年后用一次，到时候已经忘了怎么用
③ ⭐ 现有工具已够好 —— prettier --write 已经很好，不必重做
```

## 3. ⭐ 三个被忘掉的成本

> ⭐ **这三个比 token 开销更能摧毁 ROI 预测。**

**① 验证开销**

```
⭐ 如果人必须仔细检查每一份输出，你就没有消除工作，
   ⭐ 只是把它从"做"搬到了"审"——而审有时更慢。

⭐ 节省只有在"能廉价验证"时才真实存在，
   理想情况是一个自动化检查或看一眼就行。
```

**② 维护漂移**

```
MCP server 指向真实系统，而真实系统会改 schema、轮换凭据、废弃端点
编码了某个流程的技能，在该流程变更时就过时了

⭐ 把维护当作经常性支出列预算，而不是一次性构建成本
   ⭐ 否则你的 ROI 会随着自动化腐烂而悄悄流失
```

**③ ⭐ 失败尾部**

```
⭐ 多数运行会成功；但那次罕见的坏运行，
   ⭐ 如果它碰到了钱、客户或生产环境，
   ⭐ 代价可能超过所有省下来的时间之和。

→ 工具范围收窄
→ ⭐ 破坏性动作要求确认
→ ⭐ 为了省几秒而给 agent 放开写权限
   = ⭐ 用一个小节省换了一个大的、低概率的负债
```

**第四个（库成熟后最重要的）**：

```
⭐ 重叠——三个团队各写一份略有不同的技能做同一件事：
   构建与维护成本 ×3，还引入了不一致。

⭐ 正解：把热门技能当作⭐ 有 owner 的共享内部基础设施，
        而不是个人草稿。
⭐ ⭐ 一旦技能库成熟，"合并重复"是杠杆最高的成本动作之一。
```

## 4. ⭐ 别把模型的功劳算进来

> ⭐ **技能的贡献 = 相对于"一个称职的工程师直接给 Claude 写提示词"的边际提升，
> ⭐ 不是产出的全部。**

**诚实的测法**：

```
① ⭐ 挑几个代表性任务，做"前后对比"埋点
② 先用临时提示词做一遍，计时
③ 再走技能做一遍，计时
④ 记录 delta
⑤ ⭐ 乘以真实频率
```

> ⭐ **对你的前五大技能做这件事，你会得到一个能辩护的数字，
> 外加一个关于哪些技能是死重的清晰信号。**

**别信厂商数字**：把厂商报的生产力数字当方向性参考，不是你的商业论证。

**让节省可见**：

```
⭐ 从第一天就开始埋点：
   · 每个技能触发了多少次
   · 它做了多少次工具调用
   · ⭐ 在可能的情况下，人工替代方案的粗略估算

⭐ 一个月后你就能用实测数据替换掉预测
   ——在预算对话里，这比任何厂商的说法都有说服力
```

> ⭐ **把每个自动化当作一个带 P&L 的小产品，而不是一个聪明的 demo。**
> 干掉不挣钱的，加倍投入挣钱的。

## 5. 频率门槛

> ⭐ **这是唯一最重要的过滤器：频率，不是炫酷程度，决定 ROI。**

```
⭐ 一条有用的纪律：在任何人构建自动化之前，先要求一个频率门槛。
⭐ 如果一个任务在团队范围内不是至少每周重复一次，
   构建成本很难摊销，
   而维护负担——⭐ 每个技能都是一个 API 变更时就会坏掉的小负债——会把它推向负值。
```

**多 agent 的额外成本**（常被漏算）：

```
⭐ 编排器派生多个子 agent 的工作流，
   ⭐ token 用量可能是单 agent 的数倍——
   ⭐ 因为每个子 agent 自带上下文，而编排器还要付费读取它们的所有输出。

✅ 任务真的需要并行研究时：值得
❌ 单 agent 就够时：浪费
```

## 速查

```
回本：
□ ⭐ 回本月数 = B / (S × N)
□ ⭐ 一季度内 = yes；>1 年 = 审视
□ ⭐ N（频率）是最被高估的杠杆
□ 高频是必要非充分（Git 提交：高频率但只省 1 分钟 → 不做）

四尺子（≥12 做 / 8-11 简化 / <8 用 Prompt）：
□ 频次（≥5 次/周 = 5 分）
□ 标准化
□ ⭐ 可拆解（拆不开就写不了逻辑/测试/兜底）
□ 价值

不值得：
□ ⭐ 学习成本太低
□ ⭐ 频率太低
□ ⭐ 现有工具已够好

三个被忘的成本：
□ ⭐ 验证开销（从"做"搬到"审"有时更慢）
□ ⭐ 维护漂移（把维护当经常性支出）
□ ⭐ ⭐ 失败尾部（碰钱/客户/生产时，一次坏运行 > 所有节省）
□ 重叠（三份略不同的技能 = 成本 ×3）

□ ⭐ 只算边际提升，不算模型原始能力
□ ⭐ 前后对比埋点 × 真实频率
□ ⭐ 从第一天就埋点：触发次数/工具调用/人工替代估算
□ ⭐ 每个自动化当作带 P&L 的小产品
□ ⭐ 频率门槛：至少每周一次
□ ⭐ 多 agent 可能是单 agent 数倍 token
```

**一句话**：

> ⭐ **为了省几秒而给 agent 放开写权限，
> 是用一个小节省换了一个大的、低概率的负债。**
