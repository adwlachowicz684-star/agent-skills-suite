## 1. ⭐ 判断标准不是难不难，是会不会再来

> ⭐ **别为只过一次的河搭桥，要为天天都要走的路修路。**
> **难不是标准，重复才是。**

一个对照：

```
小李：花一小时调 prompt 生成周报模板 → ⭐ 只用了一次就换了岗位
老张：花半小时把常用邮件回复分类写成技能 → ⭐ 每次五秒搞定
```

## 2. 三条硬标准

```
① ⭐ 是不是"高频重复"？
   过去三个月发生过多少次？超过十次，说明你在同一个坑里反复填土。

② ⭐ 触发场景是否足够清晰？
   能不能一句话说清"什么时候用它"？
   "新客户初次沟通后，要发一封跟进邮件" —— 明确
   ⭐ 如果说不清"到底什么情况用、什么情况不用"，
      说明流程还不够固化，还没到写技能的时候。

③ ⭐ 输出格式是否可预期？
   是不是每次都需要同样的交付结构？
   "议题 + 结论 + 待办 + 责任人" —— 有固定骨架
   ⭐ 如果你自己都不知道最终长什么样，AI 更不知道。
```

> ⭐ **三个都满足才值得写。少一个，就再等等。**

**明确不做的两类**：

```
· 简单问答就能搞定 —— 一句话能说清，不需要写成流程
· 边界模糊、无法测试 —— 你也不知道"成功完成"长什么样
```

## 3. ⭐ 五维矩阵

| 维度 | 适合做成技能 | ⭐ 不适合做成技能的信号 |
|---|---|---|
| **高频** | 每天、每周或批量重复发生 | 一次性、偶发、背景变化大 |
| **稳定** | 输入、步骤、规则、输出相对固定 | 每次都要重新判断路径 |
| **可复用** | 多人、多团队或多场景都能用 | 只服务个人偏好或临时表达 |
| **可验证** | 有指标、格式、清单或人工复核点 | 结果好坏主要靠感觉判断 |
| **可授权** | 能明确读写权限和确认边界 | 会影响真实业务但责任不清 |

> ⭐ **"可授权"这一维最常被忽略**：
> 技能往往会调用文件、数据、脚本或业务系统，
> 如果它要接触真实信息，**就必须明确能读什么、能写什么、
> 什么动作需要确认、什么动作不能自动执行**。

**矩阵解释了一个常见疑问——为什么有些需求该被拆小**：

```
❌ "完整经营分析"      太大
✅ "生成销售日报初稿"   可以做

❌ "自动优化投放策略"    风险太高
✅ "识别异常渠道并给出待确认建议"   更适合先做
```

> ⭐ **技能的边界越清楚，落地越稳。**

## 4. ⭐ 一个反直觉的判断

> ⭐ **不是越复杂的任务越值得封装，而是越重复的简单任务越值得封装。**

算账：

```
每天要做的数据报表    → 封装后每天省 10 分钟 → ⭐ 一年省 60 小时
季度做一次的竞品分析  → 封装后省半天       → 一年省 2 天
```

**投入产出比完全不在一个量级。**

另一个角度：

```
三问：高频？标准化？可容错？
  → 高频、标准化、可容错 —— 值得
  → ⭐ 低频 / 高度依赖创意 / 零容错 —— 不值得
```

## 5. 五步选择法

```
① 写下这个任务过去一个月发生了多少次
   ⭐ 少于 3 次先不要急
② 列出固定输入、固定步骤、固定输出
   ⭐ 写不出来 → 流程还不稳定
③ 判断是否至少有两类人或两个场景会复用
   ⭐ 否则先做个人模板
④ 确认好坏标准能不能说清楚
⑤ 确认权限边界能不能说清楚
```

**另一条参考线**：

> ⭐ **"这个任务未来一个月会不会重复出现三次以上？"**
> 否 → 优先普通对话；是 → 继续评估。

> ⭐ **但频率不是唯一标准**——
> 有些任务频率不高但**一旦发生就非常重要**
> （"重大版本发布前的合规检查"、"上线前风险清单检查"），
> 它们也适合做成技能，**因为需要稳定标准和可审查输出**。

## 速查

```
□ ⭐ 三条硬标准：高频重复 / 触发清晰 / 输出可预期
□ ⭐ 五维：高频 稳定 可复用 可验证 可授权
□ ⭐ "可授权"最常被漏
□ ⭐ 不是越复杂越值得——越重复越值得
□ 一个月 <3 次 → 先别做
□ 低频但高风险 → 可以做（需要可审查输出）
□ 边界清楚比功能完整更重要
```

**一句话**：

> ⭐ **Skill 的价值不取决于它有多复杂，取决于你用了多少次。**
> **一次建，千次用，才叫值。**
