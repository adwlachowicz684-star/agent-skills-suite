## 1. ⭐ 三条件（同时满足才做）

```
① ⭐ 触发场景稳定 —— 能用清晰的短语描述"何时使用"
② ⭐ 处理步骤可复用 —— 流程相对固定，不需要每次重新设计
③ ⭐ 输出标准明确 —— 产出结果有清楚的格式或质量要求
```

> ⭐ **三个必须同时满足。**
> 满足 → 技能才真正减少重复劳动；
> ⭐ **不满足 → 它可能只是把混乱固化下来。**

> ⭐ 这句话是全套判断的收口：**不适合封装的东西做成技能，
> 产出不是"自动化"，而是"一个看起来权威的错误流程"。**
> 与 `when-not-to-use-skill.md` 的"制造伪稳定"同源。

## 2. ⭐ 三次法则

```
⭐ 同一流程重复出现 3 次，才值得抽成技能。
⭐ 别第 1 次就抽。
```

配套做法：**先有 2–3 个真实使用方再封装**。

> 这不是保守，是因为——**第 1 次看到的"共性"往往是巧合**。
> 三次之后你才知道哪些步骤是稳定的、哪些只是这次恰好相同。

**与五层选型的衔接**：

```
同一段指令复制两次以上 → ⭐ 该从 prompt 升为 skill
```

> 注意两处数字不同（2 次 vs 3 次），判据也不同：
> **"复制两次"看的是你已经在重复劳动（成本已发生）**；
> **"出现三次"看的是模式是否已稳定（避免抽错）**。
> ⭐ 保守起见取 3 次——多等一次的代价，远小于抽错一个技能。

## 3. ⭐ 过度抽象治理速查表

| 现象 | 根因 | ⭐ 解决方案 |
|---|---|---|
| 技能没人用，白封装了 | 脱离真实需求 | ⭐ 三次法则，先有 2–3 个真实使用方再封装 |
| ⭐ 过度抽象，为复用而复用 | ⭐ 把只出现 1 次的东西也封装了，反增复杂度 | 复用度评估，低复用不封装 |
| 技能改坏了，下游全崩 | 无版本管理 + 无灰度 | ⭐ 版本化 + 破坏性变更灰度切换 |
| 技能依赖一团乱 | 循环依赖 / 依赖不明 | ⭐ 依赖显式声明 + 依赖图检查（防循环） |
| ⭐ 技能和工具职责不清 | ⭐ 粒度错位 | ⭐ 单动作 → 工具；多步流程 → 技能 |

**四条实战提示**（可直接抄进团队规范）：

```
· ⭐ 三次法则：同一流程出现 3 次才封装
· ⭐ 技能是"装配好的部件"：工具是零件，技能是 SOP——粒度别搞反
· ⭐ 版本化是底线：技能改了会波及所有使用者，版本 + 灰度缺一不可
· ⭐ 描述决定复用率：写清"何时用"，模型和同事才知道什么时候该用它
· 注册表是能力资产：维护技能目录，让能力可见、可治理、可复用
```

## 4. 粒度：单动作 vs 多步流程

```
⭐ 单动作  → 工具（Tool）
⭐ 多步流程 → 技能（Skill）
```

两个方向的错误：

```
❌ 把单动作封装成技能  → 过度
❌ 把流程硬塞进工具    → 不足
```

> ⭐ **"工具是零件，技能是 SOP"**——这句比喻是判据。
> 一个 `git diff` 是零件；"怎么审一个 PR"是 SOP。

**技能的四个组成部分**（对应到文件）：

```
① 元信息   —— name / description / version
② 依赖     —— 用到的工具与其他技能
③ 执行逻辑 —— run 流程
④ ⭐ 输出契约 —— schema
```

> ⭐ 第 ④ 项最常被漏，但它决定下游能不能自动消费这个技能的产出。

## 5. 可移植性声明

```
⭐ 可移植意味着同一个技能应当在 Claude.ai、Claude Code 和 API 中
   ⭐ 产生一致的行为。
```

> ⭐ **如果技能依赖特定环境**（某个系统包、网络条件），
> ⭐ **应在 frontmatter 的 `compatibility` 字段中明确声明。**

原因很实际：不声明的话，换一个环境出问题，**使用者无法判断是技能坏了
还是环境不满足**——只能靠猜。
