## 1. ⭐ 三种误用后果

一个不该封装的任务被做成技能，会带来三个后果：

```
① 增加复杂度
   原本一次对话能解决的，被包装成"能力模块"，
   ⭐ 反而需要维护说明、输入格式、输出格式和触发条件

② ⭐ 制造伪稳定
   ⭐ 任务本身并没有稳定方法，但技能会让使用者
      误以为结果是标准化的、可信的、可复用的

③ 削弱判断力
   ⭐ 把本应由人判断的问题交给技能，
      导致 AI 输出看起来规范，实际缺少业务判断、用户证据或风险意识
```

> ⭐ 第 ② 条最隐蔽也最危险：
> **技能自带一种"权威感"，而它可能并不配。**
> 这与 `research-skills.md` 那条"研究技能能悄无声息地制造权威感"同源。

## 2. 六条不该做成技能

| 不该做 | 该用什么 |
|---|---|
| ⭐ **一次性任务** | 直接告诉 agent |
| ⭐ **实时数据或外部 API** | ⭐ **MCP**——技能是静态文件 |
| ⭐ **快速变化的流程** | ⭐ 等流程稳定后再技能化 |
| ⭐ **需要 100% 确定性** | ⭐ 传统代码或 CI 检查——技能引导行为，不强制执行 |
| **一句话能说完的指令** | 系统提示词——技能有开销 |
| ⭐ **每步都要人工审批** | 脚本或 CI 流水线——技能假设自主执行 |

逐条展开：

**② 实时数据**：

```
⭐ 技能是静态文件。
需要查数据库、拉实时指标、调 API → 用 MCP。
⭐ MCP 负责动态工具执行；技能负责静态知识与工作流。
```

**③ 快速变化**：

> ⭐ **如果你的约定每周都变，你更新技能的时间会比它省下的还多。**

**④ 确定性**：

> ⭐ **技能引导 agent 行为——它们不强制执行。**
> 如果需要 100% 确定，写传统代码或 CI 检查。

**⑥ 人工环路**：

> ⭐ **技能假设 agent 自主执行。**
> 如果每一步都需要人工批准，脚本或 CI 流水线更合适。

## 3. ⭐ 四条常见误区

**误区一：技能是某家专属**

```
⭐ 自 2025-12-18 成为开放标准后，它已是跨平台通用格式。
   Markdown 写下的能力可在不同宿主间迁移
   ——⭐ 这是它相比各家私有插件体系最大的长期优势。
```

**误区二：有了技能就不需要 MCP**

```
⭐ 两者维度不同。技能再详细，也变不出一个数据库连接。
   ⭐ 技能管"怎么做"，MCP 管"能碰到什么"。
```

**误区三：技能越多越好**

```
⭐ 二十个界限清晰的技能好用，
⭐ 六十个语义重叠的技能只会让模型选错。
```

**误区四：技能 = 保存好的 Prompt**

```
⭐ 它不是一段 prompt，
   而是一个含指令、脚本、模板的可复用能力模块，
   ⭐ agent 可以自动发现和按需加载。
```

## 4. 三条风险提醒

```
① ⭐ 过度依赖一个技能，缺乏异常兜底
   遇到技能未覆盖的极端情况时，应设计安全兜底（如自动转人工），
   ⭐ 而不是硬着头皮给出错误结论
② 忽略权限控制
   赋予写权限时必须严格限制范围并记录审计日志
③ ⭐ 认为开发完就结束了
   ⭐ 业务规则会变，数据格式会变——
      技能需要像软件一样持续迭代，否则会从资产变成技术债务
```

> ⭐ 第 ① 条对应 `error-handling.md` 的降级路径；
> 第 ③ 条对应 `library-ops.md` 的技术债务。

## 速查

```
不该做成技能：
□ 一次性任务
□ ⭐ 要实时数据 / 外部 API → 用 MCP
□ ⭐ 流程每周变 → 先等稳定
□ ⭐ 要 100% 确定 → 用代码 / CI
□ 一句话能说完 → 系统提示词
□ ⭐ 每步都要人工审批 → 脚本 / 流水线

误用后果：
□ ⭐ 增加复杂度
□ ⭐ 制造伪稳定（最危险）
□ ⭐ 削弱判断力

四条误区：
□ 不是某家专属（开放标准）
□ ⭐ 有了技能 ≠ 不需要 MCP
□ ⭐ 不是越多越好（20 清晰 > 60 重叠）
□ ⭐ 不是"保存好的 prompt"
```

**一句话**：

> ⭐ **知道什么时候不该使用技能，比会用技能更重要。**
