## 1. ⭐⭐⭐⭐⭐ 反直觉：装多了反而更不会干活

> ⭐⭐ **可用技能越来越多之后，agent 反而更"不会干活"了。**
> 技能列表一长，它在选择调用什么时会出现混乱，
> **有时还会把几个不相关的技能叠加组合，产生令人哭笑不得的结果。**

注意它和我们已有结论的差别：

| 已有 | 说的 |
|---|---|
| `three-skill-ceiling.md` | ⭐ 一个任务同时挂载 >3 个，成功率下滑 |
| `skill-portfolio-audit.md` | 库存里 34% 是僵尸 |
| ⭐⭐ 本份 | ⭐⭐⭐ **同一个项目里装太多，会产生"错误组合"** |

第三条是新的一类失败：**不是选错一个，是把几个拼成一个谁都没要的东西。**

> ⭐⭐⭐ 机制上，当候选多到超出可靠区分能力时，
> agent 会倾向于"多叫几个更保险"——而叠加恰恰是最坏的解。

## 2. ⭐⭐⭐⭐⭐ 一次性技能：用完就删

这是本份最值得单独记住的概念：

> ⭐⭐⭐ **那些一次性用过的"一次性技能"，用完就删。**
> **不然它躺在目录里，还会干扰后续调用。**

它和"僵尸技能"不是一回事：

| | 一次性技能 | 僵尸技能 |
|---|---|---|
| 曾经有用吗 | ⭐ 有，且成功过 | 有，但已经不增值 |
| 会再用吗 | ⭐ 大概率不会 | 本该会，实际没有 |
| 判断时机 | ⭐ **写它的那一刻就知道** | 要跑一段时间才看得出来 |
| 处理 | ⭐ 立即删 | 缩作用域或归档 |

> ⭐⭐⭐⭐ **关键差别在第三行**：一次性技能**不需要积累数据来判断**——
> 你在写它的时候就知道它是为一次任务写的。
> 所以它可以、也应该**零延迟清除**，不用等审计。

一个容易踩的坑：**"留着说不定以后用得上"**。
而这句话的代价不是存储，是**后续每一次判断都要为它付费**
（`skill-portfolio-audit.md` 的认知切换成本：每个候选 40–80 token）。

## 3. ⭐⭐⭐ 三层数量阈值的分工

整理一下，别混用：

| 层 | 阈值 | 管什么 |
|---|---|---|
| ⭐ **单项目装载** | **2–3 个核心** | ⭐ 本份：防错误组合 |
| 单任务挂载 | ≤3 | `three-skill-ceiling.md`：防成功率下滑 |
| 库存总量 | 10–20（质量）· 50（路由） | `skill-portfolio-audit.md` / `routing-tiers` |

> ⭐⭐⭐ 前两条常被当成一条，其实不是：
> **项目里只装 3 个，但一个任务上同时挂了 5 个**——
> 这种事在编排场景下会发生（编排器按阶段挂载），
> 所以两条要分别守。

## 4. ⭐⭐⭐⭐ 备份目录而非删除

> ⭐ **把不用的移出到备份目录。**

这跟我们已有的"归档 ≠ 删除"（`retirement-pipeline.md`）完全一致，
但这里有个**更轻的形态**——它不是退役流程，是日常整理：

```
.claude/skills/          ← 只留 2–3 个核心
.claude/skills-archive/  ← 其余（不被扫描，不占上下文，随时拿回）
```

> ⭐⭐⭐ **重点：备份目录必须放在不会被扫描的位置。**
> 放在 `skills/` 下的子目录会被当成嵌套技能发现
> （《skill-loading》的 `nested-scope-discovery.md`），
> 那样"归档"就完全没起作用。

---

## 5. ⭐⭐⭐ 三条实操习惯

| # | 习惯 | 防什么 |
|---|---|---|
| 1 | ⭐ 每个项目只保留 2–3 个真正核心、常用的 | 错误组合 |
| 2 | ⭐ 一次性技能用完立即移走 | 噪音累积 |
| 3 | 移走而非删除，且放到不扫描的目录 | 误删 + 归档失效 |

配一句总结可以直接用：

> ⭐⭐⭐ **技能的核心价值不在多，而在准、稳、可复用。**

## 6. ⭐⭐ 与"中间地带"说的矛盾及仲裁

`skill-portfolio-audit.md` 说：

```
✅ 昂贵 + 高价值（专家型）→ 恰恰最该留
❌ 中间地带 = 技能死去的地方
```

本份说"每项目只留 2–3 个"——看起来在劝你删掉专家型技能。

**仲裁**：两者管的不是同一个容器。

```
⭐ 库存（你的技能库）   → 可以留专家型，哪怕低频
⭐ 装载（单个项目）     → 只装这个项目真会用的
```

> ⭐⭐⭐ **低频高价值的技能应该"留在库里、不装进项目"。**
> 这正是备份目录这个形态存在的理由——它解决了"留"和"装"的分离。

顺带一句：这条也呼应了 `three-skill-ceiling.md` 的配套发现——
**库存 20+ 时 agent 每次随机加载好几个，精简到 <10 后效果立刻好转**。
三个来源都指向：**少即是准。**
