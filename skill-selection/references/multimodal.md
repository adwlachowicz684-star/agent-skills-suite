## 技能 vs MCP server 的分工

> 观察 Qwen-MM-Plugins 这类项目能看清结构：
> **每个能力打包成"一个技能定义 + 一个可选 MCP server"。**

```
技能（SKILL.md）   告诉模型这套工具能做什么 —— 指令层
MCP server        提供实际的工具 —— 能力层
```

> ⭐ **这个分离很重要**：
> 一个模型可以在"能接受图片"这个狭义上是多模态的，
> **但 agent 仍然可能无法裁剪区域、定位物体、检查渲染结果、
> 或把视频操作作为更大计划的一部分来调用。**
>
> → **把视觉能力做成可发现的运行时能力，而不是一个大提示词。**

> ⚠️ **一个战略判断**（值得记住）：
> 这些插件的工具调用的是厂商自己的云端端点，
> **而竞品的 harness 同样可以路由到其他地方**。
> → **真正的采用单位是 MCP server，不是模型。**

## 能力矩阵与选型

> 写多模态技能时，先把能力矩阵列清楚——
> 它同时是给模型的能力声明，也是给用户的边界说明。

| 任务 | 音频 | 图像 | 视频 | 文档 | 生成 |
|---|:---:|:---:|:---:|:---:|:---:|
| 转写 | ✓ | — | ✓ | — | — |
| 摘要 | ✓ | ✓ | ✓ | ✓ | — |
| 问答 | ✓ | ✓ | ✓ | ✓ | — |
| 目标检测 | — | ✓ | ✓ | — | — |
| 文字提取 | — | ✓ | — | ✓ | — |
| 结构化输出 | ✓ | ✓ | ✓ | ✓ | — |
| 创作 | TTS | — | — | — | ✓ |
| 时间戳 | ✓ | — | ✓ | — | — |
| 分割 | — | ✓ | — | — | — |

**模型选型的写法**（给 agent 明确的路由规则，而不是让它猜）：

```
□ 高质量全功能      → pro 级
□ 最佳性价比        → flash 级
□ 轻量（含分割）    → flash-lite
□ 仅图像生成        → 专用 image 模型

功能门槛（必须写清）：
  分割      需要 2.5+ 模型
  目标检测  需要 2.0+ 模型
  多视频    需要 2.5+ 模型
```

> ⭐ 这类"哪档模型能做哪件事"的表格，
> 正是 `skill-authoring` 的 `skill-types.md` 里"库和 API 参考"类的典型内容——
> **gotchas 与能力门槛是最有价值的**。

## 上下文成本：多模态的真实开销

> ⚠️ **写多模态技能必须算这笔账**，否则会静默烧穿窗口。

```
2M tokens  ≈ 6 小时视频（低分辨率）或 2 小时（默认）
1M tokens  ≈ 3 小时视频（低分辨率）或 1 小时（默认）

音频   32 tokens/秒          （1 分钟 = 1,920 tokens）
PDF    258 tokens/页         （固定）
图像   258–1,548 tokens      （按尺寸）
```

> 对照 `skill-refining` 的 `context-budget.md`：
> **一个 1 小时的音频就是 115K tokens**——
> 比一份完整技能库还大。所以"先算再用"不是优化，是必需。

**分级压缩策略**（多模态上下文不够用时的解法）：

```
□ UI 树简化
□ 图文摘要
□ 音频只保留转写文本
```

## 工程要点：不是堆模型

> ⭐ **多模态不是"堆模型"，是"补管线、强工程、重体验"。**

| 维度 | 关键抓手 |
|---|---|
| **视觉** | ⭐ 预处理管线 > 模型大小 · **结构化输出 > 自由文本** · 分块流式 > 整图硬吞 |
| **音频** | 降噪 + VAD 前置 · 流式首包 |
| **交互** | 坐标点击 · 多后端降级 · 无障碍首选 · **用户可控可审计** |
| **融合** | 统一 Agent Loop · 分级模型路由 · 静默失败兜底 · 可观测性全链路 |

**几个具体的坑与解法**：

```
坑：坐标点击在不同分辨率/缩放下偏移，录制坐标回放点偏了
解：⭐ 严禁硬编码坐标，全部用 xpath / resource-id / text 语义定位

坑：权限缺失导致静默失败
解：checkPermission()，缺失则引导或降级

坑：多模态上下文窗口不够用（图+音+文+UI树 > 32K）
解：分级压缩（见上）
```

> ⭐ **"结构化输出 > 自由文本"** 与 `skill-crafting` 的 `output-contract.md` 完全一致——
> 多模态尤其如此，因为自由文本描述图像会丢掉大量可验证信息。

## 试点路径

> 一个务实的落地顺序：

```
□ 如果你的 agent 已能处理文本与工具，
  但一旦证据变成视觉或空间性的就崩 —— 就该试点了

□ ⭐ 从一个只读工作流 + 一个确定性答案或产物开始
□ ❌ 不要从自主视频编辑、CAD 改动或生产写入开始
```

**主要新增风险**（加眼睛和手也会加这些）：

```
□ 工具选择错误
□ 延迟
□ 权限
□ 系统依赖（ffmpeg、LibreOffice、Blender、TeX Live、Chromium…）
□ ⭐ 需要评估的全新证据面
```

> ⚠️ 一个重要的现实边界：
> **"装上插件" ≠ "整个能力在生产可用"。**
> 原生读图/视频/文档可能不需要 API key，
> 但基于 API 的视觉、搜索、转写、生成需要；
> 且部分能力依赖外部二进制。

**每个能力该先验证什么**（这张表很值得抄）：

| 能力 | 先测的产品边界 |
|---|---|
| core（动态分辨率读取 / OCR / 定位 / 分割 / ASR） | agent 能否在搜索或回答前**提取到正确的视觉证据**？ |
| video-memory | 时间范围、人物、事件、引用是否保留得足以复核？ |
| omni-av | agent 是否选对了片段，并在正确的时间戳返回证据？ |
| video-edit | ⭐ 每个编辑在到达用户前**是否可预览、可回滚**？ |
| blender / freecad | agent 能否做出**有界改动**而不破坏可编辑的源产物？ |

## 技能写法要点

**① 依赖声明要写清"哪些必需、哪些可选"**

```
必需：ffmpeg
可选：LibreOffice · Blender · TeX Live · Chromium
需要 API key：视觉 · 搜索 · 转写 · 生成
不需要 API key：原生图像/视频/文档读取
```

**② 密钥查找顺序要写死**（别让 agent 猜）

```
1. 进程环境变量
2. 项目根 .env
3. .claude/.env
4. .claude/skills/.env
5. .claude/skills/<技能名>/.env
```

> 呼应 `skill-scripting` 的 `script-engineering.md` 与 security：**走环境变量，绝不写进文件。**

**③ 统一入口 + 任务参数**

```bash
python scripts/gemini_batch_process.py \
  --files video.mp4 \
  --task analyze \
  --prompt "Summarize key points with timestamps" \
  --output docs/assets/ \
  --model <档位>
```

> ⭐ **一个脚本覆盖转写/分析/提取/生成**，
> 靠 `--task` 分派——这正是"内置脚本让 Claude 组合"的做法。

**④ 跨宿主安装要写四条路径**

```
Claude Code（插件市场）· Cursor（克隆 + 设置路径）
Codex（克隆 + 软链到 ~/.agents/skills）
OpenCode（克隆 + 软链全部）
```

> 呼应 `skill-crafting` 的 `skill-structuring` 的 `directory-contract.md`：**`.agents/skills/` 是跨客户端的互操作路径。**

## 自查

```
□ 是否分清了技能（指令）与 MCP server（能力）？
□ 是否列了能力矩阵（哪些模态能做哪些任务）？
□ 是否写了模型档位门槛（哪个版本能做哪件事）？
□ 是否算了上下文成本（音频/视频/PDF/图像的 token 数）？
□ 是否有分级压缩策略？
□ 是否禁止了硬编码坐标（改用语义定位）？
□ 是否优先结构化输出而非自由文本？
□ 是否声明了必需/可选依赖与 API key 需求？
□ 密钥查找顺序是否写死？
□ 是否从只读工作流开始试点（而非自主编辑/写入）？
□ 每个能力是否定义了"先验证什么"？
□ 是否提供了跨宿主的安装路径？
```
