## 1. 无限循环：一个逻辑错误，不是模型问题

> ⭐ **根因**：技能指示 Claude 重试直到成功，
> **却没有给最大重试次数，也没有兜底退出条件**。

Claude 会一直试下去——消耗 token，不产出任何有用结果。

```markdown
❌ "修复错误直到测试通过"
✅ "最多重试 3 次；3 次仍失败则停止并向用户报告失败原因"
```

这是 `error-handling.md` 里"每个循环都要有出口"这条的具体写法。

---

## 2. 三类循环的终止条件写法

| 循环 | 终止条件 |
|---|---|
| 修复-测试 | 最多 3 次修复尝试；仍失败则报告 |
| 全量测试 | ⭐ **单次任务内全量测试套件不超过 5 次** |
| 探索/检索 | 结果数达阈值或尝试轮次上限 |

```markdown
- 每个失败测试最多 3 次修复
- 3 次后仍失败 → 报告失败并停止
- ⭐ 每个任务全量套件重跑不超过 5 次
```

> ⭐ **"5 次"那条容易被漏**——
> 单个测试重试有上限，但整体重跑没有上限的话，成本照样失控。

## 3. 超时：不能一刀切

真实差异极大：

```
数据量大的脚本   几分钟
简单报告生成     几秒钟
```

统一 timeout 的后果二选一，都是坏的：

```
快技能等太久      → 浪费时间
慢技能被频繁掐断  → 永远跑不完
```

**正确做法**（与 `namespace-collision.md` 第 5 节一致）：

```
① 每个技能单独配 timeout
② ⭐ 在 description 里写明"这是长耗时技能"
③ 让模型执行前先告知用户需要等待
```

第 ③ 条属于 `progress-reporting.md`——**长任务必须先预告**。

---

## 4. 慢技能的三个成因

| 成因 | 修法 |
|---|---|
| **正文过大** | ⭐ 每次调用都要处理全部 → 拆成聚焦的子技能 |
| **串行工具调用** | ⭐ 逻辑允许时改并行调用 |
| **加载外部数据慢** | 减少每轮加载的上下文量 |

另外：脚本里要**加超时退出**，避免卡死（与 `script-engineering.md` 一致）。

## 5. 上下文溢出的四个预防手段

当技能正文 + 会话历史 + 工具输出 + 处理的文档把窗口填满，
模型开始退化：**丢掉早期指令、丢失任务状态、或直接报上下文溢出**。

四个手段，按有效性排序：

### ① 保持正文精简

> ⭐ **技能文件的每个字节，从第一个 token 起就在占用预算。**
> 用渐进式披露：顶部简要，细节只在需要时出现。

### ② ⭐ 激进地摘要

```
10,000 token 的数据库查询结果
→ 通常可压缩成 200 token 的相关数据
```

**长工具输出在回灌上下文之前先摘要**——这是单项收益最大的动作。

### ③ 外部状态

> 不要把任务状态全放在会话里。
> **把中间结果写到文件或数据库，按路径引用。**

技能在开始和结束时读写这个外部存储。
这与 `memory-state.md` / `cross-session-artifacts.md` 一致。

### ④ 工具调用用对

| 场景 | 用 | 不用 |
|---|---|---|
| 搜代码模式 | `Grep` | `Read` 整个文件 |
| 定向修改 | `Edit` | `Write` 整个文件 |
| 找文件 | `Glob` | `Bash` + find |

> ⭐ **一次改 3 行的 Edit 只传输那 3 行；
> 用 Write 替换同一文件要传输整个文件内容。**

## 速查

| 症状 | 处置 |
|---|---|
| 一直重试不产出 | ⭐ 加最大次数 + 兜底退出 |
| 成本失控但结果对 | 全量套件重跑次数加限 |
| 快技能等太久 | 每技能单独 timeout |
| 长任务被掐断 | 同上 + 执行前预告用户 |
| 越用越慢/丢指令 | ⭐ 摘要工具输出 + 状态外置 |
| 反复读同一大文件 | 改 Grep / Edit |
