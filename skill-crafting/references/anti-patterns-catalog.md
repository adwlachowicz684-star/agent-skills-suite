## 1. 命名与描述

```
❌ 含糊的技能名，如 "helper" / "utils"
❌ 描述里没有使用触发条件
❌ 缺少"什么时候用"的上下文
```

> ⭐ 一个具体判据：**名字应能猜出它做什么**。`utils` 猜不出。

---

## 2. ⭐ 内容与组织

| 反模式 | 说明 |
|---|---|
| ⭐ **包含模型训练里已有的信息** | ⭐ 最常见的浪费 |
| ⭐ **时间敏感的条件句** | ⭐ 改用 "Old patterns" 章节 |
| ⭐ **深度嵌套的文件引用** | ⭐ 从 SKILL.md 起只保持一层 |
| 一个技能塞多个无关能力 | 违反单一职责 |
| ⭐ **对 Opus 过度解释** | 它能从上下文推断 |
| ⭐ **对 Haiku 解释不足** | 它需要显式指导 |

**"时间敏感"这条值得展开**：

```
❌ "如果你用的是 2024 年之前的版本……"（会变错）
✅ ⭐ 用 "Old patterns" 章节承载历史上下文
   ——提供历史背景，又不污染主内容
```

> ⭐ 这与 `versioning-compat.md` 的"旧迁移逻辑永不删除"是互补的：
> 历史信息要留，但要**放在不干扰主流程的位置**。

**模型差异那条**很实用：

```
⭐ 同一个技能，面向不同模型档位需要不同的详细程度
⭐ 过度解释 → 浪费上下文；解释不足 → 小模型做不到
```

## 3. 文件路径与跨平台

```
❌ Windows 风格反斜杠路径（C:\Users\...）
   ⭐ 一律用正斜杠
❌ 带用户名的绝对路径（/Users/john/...）
   ⭐ 用相对路径或 ~ 路径
❌ 各文件间路径分隔符不一致
```

> ⭐ 与 `nine-checks-not-working.md` 那条一致：
> **本地一切正常、CI 才暴露**——因为 macOS/Windows 默认不敏感而 Linux 敏感。

## 4. 工具与依赖

```
❌ 提供很多等价选项却没有默认值
❌ 假设包已安装但不写文档
❌ ⭐ 不说明环境约束（claude.ai / API / Code 的差异）
❌ 通过 allowed-tools 不必要地限制工具
```

> ⭐ 第三条常被漏：**同一个技能在不同运行环境能力不同**，
> 不写清就会在另一个环境静默降级。

---

## 5. ⭐ 逻辑与复杂度

```
❌ 把复杂逻辑推给模型，而不是在脚本里解决
❌ ⭐ 不用脚本处理 token 密集型操作
❌ ⭐ 造"巨型技能"，而不是可组合的小技能
```

> ⭐ 后两条已经反复出现过（确定性进 scripts、5–8 个甜蜜点），
> ⭐ 这里给它们一个统一的归类：**这三条本质是同一件事——
> 把"该由代码承担的"和"该由模型承担的"分错层了。**

---

## 6. 安全

```
❌ 硬编码凭据、API key、密钥
❌ 脚本里不校验/清洗输入
❌ ⭐ 通过 allowed-tools 授予过多权限
❌ 技能文件里包含敏感数据
```

---

## 速查（14 项）

```
命名描述：
□ 名字不含糊（不用 helper/utils）
□ 描述含触发条件
□ 有"什么时候用"

内容组织：
□ ⭐ 不含模型已知的信息
□ ⭐ 时间敏感内容放 "Old patterns" 章节
□ ⭐ 引用只嵌套一层
□ 一个技能一个职责
□ ⭐ 按模型档位调整详细度（Opus 少写 / Haiku 多写）

路径：
□ ⭐ 一律正斜杠
□ 不用带用户名的绝对路径

工具依赖：
□ 多选项要给默认值
□ 依赖写进文档
□ ⭐ 写明环境约束

逻辑：
□ ⭐ 复杂逻辑进脚本，不推给模型
□ ⭐ token 密集操作用脚本
□ ⭐ 可组合小技能，不造巨型技能

安全：
□ ⭐⭐ 无硬编码凭据
□ 脚本校验输入
□ ⭐ allowed-tools 最小化
□ 不含敏感数据
```

**一句话**：

> ⭐ **最贵的浪费是"包含模型训练里已有的信息"——
> 你为每个 token 付了钱，却什么都没改变。**
