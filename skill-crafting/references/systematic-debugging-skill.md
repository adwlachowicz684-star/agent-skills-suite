## 1. 为什么值得单独拆讲

这是被复刻次数最多的技能之一（superpowers 起源，多个市场都有变体）。
它值得研究不是因为内容多高深，而是**它把"方法论"编码得非常干净**。

---

## 2. 核心规则

> ⭐ **NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST**
> （没有根因调查就没有修复）

一句变体同样锋利：

> **Symptom fixes are failure.**（修症状就是失败）

> ⭐ 这是 `guidance-forms.md` 那条"禁令必须配替代"的反面教材吗？
> 不是——因为这里禁令**同时给出了完整配方**（下面四阶段），
> 所以它是有效的。这正是那条规则的实证。

---

## 3. ⭐ 四阶段

```
Phase 1  INVESTIGATE   读错误、复现、收集证据
Phase 2  ANALYZE       对照能工作的例子
Phase 3  HYPOTHESIZE   陈述假设，⭐ 只改一个变量
Phase 4  IMPLEMENT     先写测试，修根因
```

### Phase 1：根因调查

```
① 完整读错误信息（完整堆栈、行号、错误码）
② ⭐ 稳定复现（记录步骤、何时发生、何时不发生）
③ 检查近期改动（git diff/log）
④ 收集证据（日志、截图、状态转储）
```

**多层调试法**——在每一层的边界打点：

| 层 | 手段 |
|---|---|
| Input | 记录进入的数据 |
| Processing | 记录中间状态 |
| Output | 记录最终结果 |
| Storage | 记录读/写 |

> ⭐ 多组件链路（UI → API → service → DB）时尤其有效：
> **记录进入每个边界什么、离开每个边界什么，
> 找出第一个"现实与预期分叉"的层**。

### Phase 2：模式分析

```
找一份能工作的例子（相似代码、上一可用版本、文档示例）
逐行对比，⭐ 记下所有差异，不做假设
```

关键提问：

```
能工作的代码做了什么而坏掉的没做？
坏掉的代码做了什么假设？
数据流在哪分叉？
```

### Phase 3：假设检验（科学方法）

```
1. 陈述具体假设  "错误因为 X 而发生"
2. 设计最小测试  ⭐ 只改一个变量
3. 预测结果      "如果我是对的，Y 会发生"
4. 测试并观察    Y 发生了吗？
5. 结论          是 → 进入修复；否 → 新假设
```

### Phase 4：实施

```
1. ⭐ 先写失败的测试（捕获 bug、防回归）
2. ⭐ 只修根因（单一聚焦改动，⭐ 不做顺手修复）
3. 验证修复有效（测试通过、复现尝试失败）
```

> ⭐ "No drive-by fixes"（不做顺手修复）这一条很重要——
> 顺手改的东西会让验证失去归因。

---

## 4. ⭐ 三次修复规则

> ⭐ **如果 3 次以上独立修复每次都暴露出新问题：
> 这标志是架构问题，不是孤立的 bug。**

```
STOP 停止继续修
→ 记录发现
→ 讨论架构
```

变体表述（两三次失败就该重新审视）：

```
这个架构对这个路径是不是错了？
失败是不是隐藏耦合或无效假设的症状？
你是不是在修结果而不是修原因？
```

> 这条特别值得抄进任何调试类技能——
> **它给了一个可判定的停止条件**，而不是靠感觉。

---

## 5. 红旗清单

| 信号 | 问题 |
|---|---|
| "先试试改 X" | 没有假设 |
| 一次改多处 | ⭐ 无法隔离原因 |
| "我以后再查" | 技术债 |
| "在我机器上是好的" | 环境问题 |
| 修复破坏了别的东西 | ⭐ 根因没找对 |
| "能跑但我不知道为什么" | 继续调查 |

---

## 6. 反模式对照

| ❌ 不要 | ✅ 要 |
|---|---|
| 猜测 + 试 | 假设 + 检验 |
| 一次改多个东西 | 一次改一个 |
| 跳过复现 | ⭐ 总是先复现 |
| 忽略错误信息 | 仔细读 |
| 修症状 | 修根因 |

> ⭐ 注意这张表的形态——**每行都是"禁令 + 替代"**，
> 正是 `guidance-forms.md` 说的"配方"而非"禁令清单"。
> 这是它有效的第二个原因。

---

## 7. ⭐ 为什么它有效（写法分析）

| 手法 | 体现 |
|---|---|
| ⭐ **一句话核心规则** | 放在最顶部，加粗 |
| ⭐ **可判定的阶段划分** | 四阶段，每步有具体动作 |
| ⭐ **可判定的停止条件** | 三次修复规则 |
| **禁令配替代** | 反模式对照表 |
| ⭐ **分层清单** | 多层调试表（Input/Processing/Output/Storage） |
| **作用域** | allowed-tools 只给 `Read, Glob, Grep, Bash`——只读 |

> 最后一条容易被忽略：
> **一个调试技能不该有写权限**（至少调查阶段不该）。
> 这与 `least-privilege.md` 的"不需要写就只给只读"一致。

---

## 速查

```
□ 先复现，再动手
□ 假设一次只验一个
□ 先写失败测试
□ 只修根因，不顺手改
□ ⭐ 三次失败 → 停下来谈架构
□ 多组件链路 → 在边界打点，找第一个分叉层
□ 调查阶段只给只读权限
```
