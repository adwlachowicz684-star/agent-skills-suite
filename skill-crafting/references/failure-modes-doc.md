# 逐步写失败模式：只有 happy path 的技能会在生产里断

> ⭐ **对每个可能失败的步骤，写清"失败长什么样"和"该怎么办"。**
> 只写顺利路径的技能，在真实环境里一定会断。

## 为什么 happy path 不够

写技能时，你脑子里跑的是**顺利的那一次**。
但 agent 遇到的是：文件不存在、权限不够、网络超时、
输入格式不对、上一步的产物是空的。

> ⭐ 更关键的是：**没有失败模式说明时，agent 不会停下来，它会自己编一个继续方式。**

这比直接报错糟糕得多——报错你还能看见，
编造的继续方式会**静默产生错误结果**。

## 每一步该写三件事

```
步骤 N：<做什么>

  ✅ 成功的样子：<可观察的判据>
  ❌ 失败的样子：<具体会看到什么>
  →  怎么办：<下一步动作>
```

⚠️ 要点：**"失败的样子"必须可观察**。

```
❌ "如果出错，处理一下"
✅ "如果 stdout 为空且退出码为 10，说明输入文件没有匹配的行"
```

## 失败模式从哪来

不要凭空想象，三个来源按可靠性排序：

```
① ⭐ 真跑一遍，把实际遇到的错误记下来（最可靠）
② 让第二个 agent 只用这份技能做任务，看它在哪卡住
③ 按类别自查（下表）
```

自查清单：

| 类别 | 典型失败 |
|---|---|
| 输入 | 文件不存在 / 格式不对 / 编码问题 / 为空 |
| 权限 | 只读文件系统 / 无写权限 / 凭据过期 |
| 环境 | 依赖未安装 / 命令不存在 / 网络不通 |
| 依赖 | 上一步产物为空 / 中间文件被清理 |
| 规模 | 文件太大 / 超时 / 内存不足 |
| ⭐ 语义 | **跑通了但结果是错的**（最危险） |

最后一行特别重要：**成功退出 ≠ 结果正确**。
脚本返回 0 但输出为空，agent 会认为成功。

## 回退的三层

```
Level 1  重试（瞬时故障：网络抖动、锁冲突）
Level 2  ⭐ 降级（换个更保守的方式达成同一目标）
Level 3  停下并上报（交给用户，不要猜）
```

三条纪律：

```
□ ⭐ 重试必须设上限——无限重试是挂死
□ 降级要说明"降级了"，不能静默换个方式
□ ⭐ 不确定就停下——猜测原因是最坏的选择
```

最后一条值得强调：**脚本返回非零退出码时，
把错误信息交给用户确认，不要猜测原因。**

## 一个完整例子

```
### 步骤 2：提取表单字段

运行：
  python scripts/extract_fields.py input.pdf

✅ 成功：stdout 为 JSON，含 fields 数组（可为空数组）

❌ 失败与处理：
  · 退出码 20，stderr "FileNotFoundError"
    → 输入路径不对。检查上一步传来的路径，不要猜一个新路径

  · 退出码 10，stderr "No AcroForm found"
    → ⭐ 这不是错误，是不可填写的 PDF。
      改走"文本提取"分支（见 references/text-fallback.md）

  · stdout 为空但退出码 0
    → ⚠️ 异常，视为失败。重跑一次，仍为空则上报

  · 超时（>90s）
    → 文件过大。提示用户拆分页范围，不要加大超时
```

注意这个例子里的几个讲究：

```
· 区分了"真错误"和"另一种情况"（退出码 10 走分支而非报错）
· ⭐ 把"退出码 0 但输出为空"单独列出来——这是最容易被漏的
· 超时给了明确动作，而不是"再等等"
```

## 常见的漏项

**① 只写了脚本会失败的情况，没写模型会失败的情况**

```
脚本失败是确定的、可枚举的
模型失败是概率性的：读错文件、跳步骤、理解偏了
```

后者要写**自检点**：

```
□ 步骤 3 完成后，确认 output.json 的字段数 == 输入记录数
  ⭐ 不等 → 停下，不要继续
```

**② 写了"失败了怎么办"，没写"怎么知道失败了"**

顺序不能反：**先有可观察的判据，才有处理动作**。

**③ 所有失败都指向同一个处理**

```
❌ "任何错误都重试三次"
```

不同失败要不同处理——把网络超时和输入格式错误
用同一套逻辑处理，只会把一个错误变成两个。

**④ 没记新遇到的失败**

> ⭐ 每次真实遇到一个新的失败模式，就补进技能。
> 这份记录是技能里**最不可能通过 no-op 测试**的内容之一，
> 和 Gotchas 一样，**修剪时永远别动它**。
