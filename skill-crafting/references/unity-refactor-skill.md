## 1. 一个真实实例

`unity-code-optimize`：简化并优化 Unity C# 代码，
提升清晰度、一致性、性能，**但不改变行为**。

触发词写得很具体：

```
'optimize code' · 'simplify this' · 'clean up code'
'improve readability' · 'reduce allocations' · 'code optimization'
```

---

## 2. ⭐ 范围怎么定

```
默认：git diff --name-only HEAD~1  ⭐ 最近修改过的 .cs 文件
用户指定了文件 → 用用户指定的
```

> ⭐ **默认范围 = 最近改动**，这个设计很聪明：
> 重构类操作的正确作用域几乎总是"我刚动过的东西"，
> 而不是整个仓库。

配套规则：**零新增错误、零新增警告**。

---

## 3. ⭐ 八条规则

| 规则 | 说明 |
|---|---|
| ⭐ **行为保全绝对优先** | ⭐ 不做功能性改动。⭐ 不确定就跳过 |
| **匹配本地约定** | 若文件/项目已有风格，不强行套外部风格 |
| **清晰优于取巧** | 可读代码胜于紧凑代码；不用嵌套三元 |
| **最近改动范围** | 只动最近改动的文件，除非用户覆盖 |
| ⭐ **不做投机优化** | ⭐ 只优化可测量或明显浪费的部分 |
| ⭐ **一次编辑只做一件事** | ⭐ 不在同一处混合清晰度重构与性能改动 |
| **保全公开 API** | 绝不重命名或改变 public/protected 成员签名 |
| **跳过测试文件** | 除非明确要求 |

> ⭐ 第五条最值得抄：**"不做投机优化"**
> 直接对应 `performance-optimization.md` 的"先测量再优化"。

> ⭐ 第六条也很关键：**混合改动会让验证失去归因**——
> 与 `systematic-debugging-skill.md` 的
> "一次只改一个变量"是同一条原则。

## 4. 工作流

```
① 确定目标文件（默认 git diff HEAD~1）
② 逐条按规则处理
③ ⭐ 报告：改了哪些文件、改了什么、为什么、⭐ 跳过了什么及原因
```

> ⭐ **报告里必须包含"跳过了什么及原因"**——
> 这与 `research-skills.md` 的
> "要求 agent 说明哪些它没有验证"是同一条设计：
> **不报告沉默的跳过，用户会以为都处理了**。

## 5. 输出格式

```
内联文件修改（通过 edit 工具）
+ 所有文件处理完之后的变更摘要
```

参考文件的组织方式值得抄——**按关注点分目录**：

```
references/code-standards/
  naming.md                 大小写、前缀、字段约定
  formatting.md             花括号、间距、region
  linq.md                   ⭐ 热路径规则、分配安全的替代方案
  collections.md            集合选择、预分配大小、池化
  null-safety.md            ⭐ null 检查模式、TryGet
  refactoring-patterns.md   提取、分解、组合
references/review/
  performance-checklist.md  分配、Update、物理、渲染
```

> ⭐ 注意 `linq.md` 和 `null-safety.md` 的标题形态——
> **"热路径规则 + 分配安全的替代方案"**、
> **"null 检查模式 + TryGet"**——
> 都是"问题 + 解法"成对出现，不是纯禁令。

## 6. ⭐ 可迁移的四条

| 设计 | 通用化 |
|---|---|
| ⭐ **默认范围 = 最近改动** | 任何修改类技能都可这样定范围 |
| ⭐ **不确定就跳过** | ⭐ 明确写出"不确定时的默认动作" |
| ⭐ **报告跳过项及原因** | 不沉默跳过 |
| ⭐ **一次只做一件事** | 混合改动无法归因 |

> 第二条尤其值得强调：
> **多数技能没写"不确定时怎么办"**，
> 于是模型自己猜，通常是硬着头皮改。

---

## 速查

```
□ 默认范围是否限定（而非全仓库）
□ "不确定就跳过" 是否写明
□ 是否禁止投机优化
□ 是否禁止混合改动类型
□ 是否保全公开 API
□ ⭐ 报告是否含"跳过项及原因"
□ references 是否按关注点分目录
```

**配套的硬门槛**：零新增错误、零新增警告。
这与 `code-review-skill-instance.md` 的"三档判词"互补——
**审查是报告，重构是修改，但共用同一套标准**。
