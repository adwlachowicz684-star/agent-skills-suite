## 1. ⭐⭐⭐⭐⭐ 一个真实的 30 行

已有案例（`skill-ownership-changeflow.md`）：

```
老张给 code-review 技能加了条"函数不超过 30 行"的规则
听起来非常合理
跑完 eval：pass_rate 0.85 → 0.72（掉 13 个点）
```

> ⭐⭐⭐⭐⭐ **30 是从哪来的？**
> 没人问过。它在评审里看起来是"具体、可执行、专业"的，
> 而它的实际来源是"一般感觉函数不该太长"。

而代价落在边界情形上：有些函数**就是需要 40 行**（一个完整 switch-case 状态机）。

---

## 2. ⭐⭐⭐⭐⭐ 具体性 ≠ 有依据

这是本份的核心，也是与含糊词那份的对照：

| | 例子 | 模型的行为 | 谁会发现 |
|---|---|---|---|
| ⭐⭐⭐ 含糊词 | "适当精简" | 按先验填 | ⭐⭐⭐ 读者会说"这说了等于没说" |
| ⭐⭐⭐⭐⭐ 无出处数字 | "不超过 30 行" | 严格执行 | ⭐⭐⭐⭐⭐ **没人发现，因为它看起来是对的** |

> ⭐⭐⭐⭐⭐ 含糊词的缺陷是可见的（空），
> 无出处数字的缺陷是不可见的（**看起来具体、可执行、有决断力**）。

> ⭐⭐⭐⭐⭐ 所以当我们说"把含糊词改成具体数字"时，
> 如果不加后半句，你只是把一种可见的病换成一种不可见的病。

完整规则应该是：

```
❌ "适当精简"
❌ "不超过 30 行"
✅ ⭐⭐⭐⭐⭐ "不超过 30 行（依据：本项目历史函数长度的 P90；
              超过时应先判断是否可拆分为独立函数，不可拆分则保留并说明）"
```

## 3. ⭐⭐⭐⭐⭐ 三条 derivation 路径

数字要站得住，必须有出处。三条合法来源：

**① ⭐⭐⭐⭐⭐ 测量得来**

```
"超过 8 行只保留前 8 行"
→ 依据：⭐⭐⭐⭐⭐ 下游表格渲染的实测上限
```

> ⭐⭐⭐⭐⭐ 这类最可靠，因为⭐⭐⭐⭐ **它可被重新测量**——
> 条件变了可以重测，而不是靠人记得改。

**② ⭐⭐⭐⭐⭐ 外部约束倒推**

```
"description ≤ 1024 字符"
→ 依据：⭐⭐⭐⭐⭐ 平台限制
"正文 ≤ 500 行"
→ 依据：⭐⭐⭐⭐⭐ 压缩只保留前 5000 token 倒推
```

> ⭐⭐⭐⭐⭐ 这类最强：**它是物理边界，不是意见**。
> 而且它的好处是⭐⭐⭐⭐ 不需要维护——平台改了才会变。

**③ ⭐⭐⭐⭐⭐ 事故得来**

```
"同一问题最多问一次"
→ 依据：⭐⭐⭐⭐⭐ 曾因二次提问让用户以为自己的回答被推翻
```

> ⭐⭐⭐⭐⭐ 这类最不该省，因为⭐⭐⭐⭐⭐ **被推翻的规则及其 eval 数据，
> 是团队最值钱的资产之一**——它同时给出了数字和反面证据。

⭐⭐⭐⭐⭐ 共同判据：**这个数字能被重新推导出来吗？**
不能 → 它是偏好伪装成了规格。

## 4. ⭐⭐⭐⭐⭐ 无出处数字的三个代价

**① ⭐⭐⭐⭐⭐ 它会被当成硬边界执行**

```
"最多重试 3 次"
→ ⭐⭐⭐⭐⭐ 模型会真的在第 3 次停下，即使第 4 次就能成功
```

> ⭐⭐⭐⭐⭐ 具体数字是最强的一类指令——模型不会质疑它，
> ⭐⭐⭐⭐⭐ **因为它看起来像是有人算过的。**

**② ⭐⭐⭐⭐⭐ 它无法被重新评估**

```
半年后：还该是 30 吗？
→ ⭐⭐⭐⭐⭐ 没人知道当初为什么是 30，于是没人敢改
```

> ⭐⭐⭐⭐⭐ 这就是"过时的限制比没有限制更有害"的数字版本：
> ⭐⭐⭐⭐ 用户会绕开一个不存在的限制，且永远没人报 bug。

**③ ⭐⭐⭐⭐⭐ 它会扩散**

```
A 技能写了 30 → B 技能抄成 30 → 团队规范固化成 30
→ ⭐⭐⭐⭐⭐ 出处在第一跳就丢了，之后每跳都在增加可信度
```

> ⭐⭐⭐⭐⭐ 数字传播时，出处不跟着传播——
> ⭐⭐⭐⭐⭐ **而可信度反而随传播增加**。这是一个反向的损耗。

## 5. ⭐⭐⭐⭐⭐ 写法：数字 + 出处 + 越界动作

三件套，缺一不可：

```markdown
- 单次输出 ≤ 40 行
  ⭐⭐⭐⭐⭐ 依据：下游解析脚本的实测上限（2026-08 测得）
  ⭐⭐⭐⭐⭐ 超出时：只保留前 40 行，并注明"共 N 项"
```

> ⭐⭐⭐⭐⭐ 第三行最常被省，而它是⭐⭐⭐⭐⭐ 唯一能防止
> "模型为了不越界而悄悄丢信息"的那一条。
> （与 `output-length-budget.md` 的结论一致。）

轻量写法（不想展开时）：

```
- ⭐⭐⭐⭐ 阈值：缺失率 > 5%（经验值，未实测）
```

> ⭐⭐⭐⭐⭐ **括号里那五个字就是全部价值。**
> 它把一个看起来是规格的数字，诚实地标记成了估计值。
> ⭐⭐⭐⭐ 于是后来者知道它可以被推翻——这正是 `adr-lightweight.md` 说的
> "记录被否决的方案更值钱"在数字层面的对应物。

## 6. ⭐⭐⭐⭐⭐ 自检与 grep

```bash
# 找出所有孤立数字（前后没有"依据/来源/实测"等字样）
grep -nE "[0-9]+ *(行|次|个|条|项|字符|天|%)" SKILL.md
```

> ⭐⭐⭐⭐⭐ 对每一条问：**这个数字能被重新推导出来吗？**
> 答不出 → 要么补出处，要么标"经验值"。

判据与含糊词那份一致（且理由相同）：

> ⭐⭐⭐⭐⭐ 说了很多次的规则，只有变成一条 grep 才会真的被执行。

一个更快的自检（不跑命令也能做）：

> ⭐⭐⭐⭐⭐ **随机挑一个数字，问自己"如果改成 2 倍或一半，会怎样"。
> 答"不知道" → 这个数字没有依据。**

## 7. ⭐⭐⭐⭐ 例外

两种数字不需要出处：

**① ⭐⭐⭐⭐⭐ 枚举值而非阈值**

```
"问题分四类：A / B / C / D"
```

> ⭐⭐⭐⭐⭐ "四"是分类的结果，不是限制。它没有"越界"这回事。

**② ⭐⭐⭐⭐⭐ 结构性常量**

```
"skill.md 三段：frontmatter / 正文 / references"
```

> ⭐⭐⭐⭐ 同上——它是结构定义，不是判断阈值。

判据收口：

> ⭐⭐⭐⭐⭐ **有"越界"概念的数字需要出处，没有的不必。**
> 换句话说：⭐⭐⭐⭐⭐ 会被用来做**判断**的数字要有依据，
> 用来做**描述**的不必。

---

## 一句可贴在墙上

> ⭐⭐⭐ **含糊词的缺陷是可见的，无出处数字的缺陷是不可见的——
> 它看起来具体、可执行、有决断力。所以把含糊词改成数字时，必须连出处一起写。**
