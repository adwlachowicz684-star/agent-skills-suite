# 幂等、恢复与回滚

> 一个生产级技能链的完整可靠性契约。
> 长任务的核心问题不是"能不能跑完"，是**跑一半崩了怎么办**。

## 状态文件

> ⭐ **每个已完成的单元都记录在状态文件里。**

```
□ 单元（unit）是恢复的粒度
□ ⭐ 每个单元完成即写盘——不是最后统一写
□ ⭐ 状态文件自包含（见下"编排层的三条保证"）
```

## Dry-run 先行

> ⭐ **每个会改变外部状态的技能都应支持 `--dry-run`。**

**dry-run 该做什么**：

```
□ ⭐ 输出完整计划
□ ⭐ 模拟每一次写入（打印将要发送的 payload）
□ ⭐ 绝不触碰目标
□ 如有助于规划，可更新状态文件
```

**硬性顺序**：

> ⭐ **当流程以 agent 方式运行时，
> 每次 commit-run 之前都必须先 dry-run。**

对应到提示词层的写法：

```
"dry-run this migration"
"show me what would change"
```

呼应 `cli-design-skills.md`（**`skill-domain-eng`**）：
**破坏性操作默认 dry-run**——
同一条原则在 CLI 设计与技能编排上的应用。

## 恢复模式

**当一个技能跑到一半失败**：

```
1. 读状态文件（每个已完成单元都有记录）

2. 枚举剩余单元：pending + 未耗尽重试次数的 failed

3. ⭐ 用同样的输入重新调用技能
   ——技能在每个单元前检查状态，跳过已完成的，
     尝试 pending 与 failed 的

4. 可选参数：
   --only-failed   只重试失败的单元
   --from-unit=    显式从某个单元恢复

5. ⭐ 如果某个单元反复失败，停下来交人工
```

**反复失败的常见根因与处理**：

```
□ 认证过期    → 换新 token，重跑
□ schema 不匹配 → 修好后重跑
□ ⭐ 源数据损坏 → 修源数据，重跑
```

**重试要有上限**：

```
□ ⭐ 更高的重试值会触发限流-重试循环
□ 呼应 error-handling.md 的熔断与抖动：
   系统级错误才触发熔断，业务级错误不触发
```

## 回滚

**模式**：破坏性变更前先存 `-before.json` 快照。

```
回滚 = 读 -before.json 快照
     → 按相反顺序回退已完成的步骤
     → 把 schema / 条目 / 绑定恢复到运行前状态
```

> ⭐ **"并非每次变更都可逆"必须写明**：

```
删除某字段的数据是破坏性的：
  回滚能恢复字段结构，⭐ 但恢复不了值
```

**技能必须显式文档化它的回滚范围**：

```
□ 能回滚到什么程度
□ ⭐ 什么回不去
□ "Assume nothing"（不要假设可逆）
```

呼应 `database-sql-skills.md`（**`skill-domain-eng`**）与
`legacy-modernization.md` 的同一条：
**每一步都要有回滚，且必须带验证查询**。

## 编排层的三条保证

当 agent 串联多个技能时：

```
① ⭐ 每个技能都可原子恢复
   ——第 4 步崩溃不需要重跑第 1–3 步

② ⭐ 每个技能的状态文件自包含
   ——第 3 步的状态不泄漏进第 4 步的文件

③ ⭐ 跨技能状态提交到 git
   ——构建表、站点计划、状态文件全部可在客户仓库里追踪
```

外加一条边界规则：

> ⭐ **任何技能都不静默修改另一个技能的产物。**

```
import-content 不动 composition 条目
author-composition-via-api 不动 entry 内容
```

> 呼应 `multi-agent-review.md` 的**文件所有权排他**原则，
> 与 `composition.md` 的 I/O 契约——
> **关注点分离要匹配状态文件分离**。

## 安全保证

> ⭐ **没有技能会在破坏性步骤之间缺少显式用户批准的情况下
> 删除或破坏生产数据。**

```
□ 增量变更：plan-then-execute 模式，按计划推进
□ ⭐ 破坏性变更（删字段、切换绑定、发布到生产）：
    需要额外确认
□ ⭐ 状态文件记录批准，这样重跑不会反复询问
```

> 最后一条很关键——**批准也要进状态文件**，
> 否则恢复时会卡在重新询问上，自主流程就断了。

**整个契约的总结**：

> **每一次变更都被记录，每一个破坏性变更都被门控，
> 每一次失败都可恢复。
> 这就是让这些技能能自主运行仍然安全的原因。**

## 可迁移的做法

```
1. ⭐ 单元级状态文件，完成即写盘
2. ⭐ 所有会改外部状态的技能默认 dry-run
3. ⭐ 恢复用"同样输入重新调用"，靠状态跳过已完成
4. ⭐ 反复失败停下来交人工，且给出根因分类
5. ⭐ 破坏性变更前存快照，并写明回滚范围
6. ⭐ 跨技能状态提交到 git
7. ⭐ 批准也要记录在状态文件里
```
