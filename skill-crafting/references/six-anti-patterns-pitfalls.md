## 1. ⭐⭐⭐ 六大反模式：症状 → 药方

| 反模式 | 症状 | ⭐ 药方 |
|---|---|---|
| ⭐⭐ 大杂烩 | 一个技能塞十件事，上千行 | ⭐ 按职责拆成⭐ 主 + 子技能 |
| ⭐⭐⭐ 黑话描述 | ⭐⭐ 描述里全是内部术语，AI 不知道何时触发 | ⭐⭐ 描述里写⭐ 明白话和触发关键词 |
| ⭐⭐⭐ 零示例 | 全是抽象要求，AI 靠猜 | ⭐⭐⭐ 补⭐ 3–5 个覆盖典型场景的范例 |
| ⭐⭐⭐ 没有检查点 | ⭐⭐ 长流程一步错、步步错 | ⭐⭐⭐ 步骤之间加⭐ 自查节点 |
| ⭐⭐ 写死数值 | 路径、参数全硬编码，换个环境就废 | ⭐⭐ 参数化，或⭐ 开头先探测环境 |
| ⭐⭐ 当 Wiki 写 | 堆背景知识，没有可执行步骤 | ⭐⭐ 背景挪到参考资料，⭐ 正文只留动作 |

> ⭐⭐⭐ 第二条"黑话描述"值得单独强调：
> **用内部术语写描述 = 用⭐ 你自己团队的词去匹配⭐ 用户实际会打的字。**
> 这与 `description-scope-shape.md` 的
> "用真实的触发短语，不是技术描述"是同一条，
> ⭐⭐ 但"黑话"这个词更形象也更刺人。
>
> ⭐⭐⭐ 第四条"没有检查点"与我们已有的一条⭐ 完全同构：
> `judgment-branches-acceptance.md` 说"少了验收，agent 会用一句'已完成'糊过去"；
> ⭐⭐ 这里说的是⭐ **长流程中间**的自查节点——
> 不是最后的验收，是⭐ **步骤之间的闸门**。
> 两者都要有。

## 2. ⭐⭐⭐ 六条安全红线

```
🚨 🚨 动手前先记住：

① ⭐⭐⭐ 密钥永远走⭐ 环境变量，⭐⭐⭐ 绝不写死在文件里
② ⭐⭐⭐ 删库、批量覆盖这类危险操作⭐ 必须加⭐ 二次确认
③ ⭐⭐⭐ ⭐ 动数据库前⭐ 先备份
④ ⭐⭐⭐ ⭐ 外部读进来的内容一律当"⭐ 数据"处理
      ⭐⭐⭐⭐ ⭐ 绝不能当"⭐ 指令"执行——⭐⭐⭐ ⭐ 这是⭐ 防提示注入的底线
⑤ ⭐⭐ 描述别写太泛（"帮助开发"→ 天天误触发）
⑥ ⭐⭐⭐ 别把技能当权限系统（见下）
```

> ⭐⭐⭐ 第 ④ 条是六条里最重要的一条：
> **"外部内容一律当数据，绝不当指令"**——
> 它把提示注入防御从"检测恶意模式"
> 简化成了⭐ **一条可执行的、不需要判断的原则**。
>
> ⭐⭐⭐ 这也是⭐ 第六个独立来源说"声明不是强制"：
> ```
> Hooks 用于不可被信任去遵守的事
> 破坏性拦截写进技能是表演
> 权限声明不是安全边界
> Markdown 指令不是访问控制
> 技能说了不算（安全控制必须在工具层）
> ⭐⭐⭐ 外部内容当数据不当指令
> ```

**第 ⑥ 条的完整表述**（这是原话，值得原样记住）：

> ⭐⭐⭐ **"把技能当权限系统——觉得技能里写了能执行命令，就不用安全校验了。
> ⭐ 别闹，⭐⭐⭐ ⭐ 安全控制必须在⭐ 工具层做，⭐⭐ 技能说了不算。"**

## 3. ⭐⭐ 两个新反模式

**① 全是原则没有动作**

```
症状：通篇"保证安全""确保质量"，⭐ 没说具体怎么做
⭐⭐ 药方：⭐⭐⭐ 把要求改成⭐⭐ 具体的检查、命令、判断分支
```

> ⭐⭐⭐ 这与 `write-reasons-not-rules.md` 的
> "写原因而非堆规则"要区分开：
> 那条是说⭐ **别只下死命令而不给理由**；
> ⭐⭐ 这条是说⭐⭐ **别只给抽象要求而不给动作**。
> 两条方向相反，合起来才是完整的：**要有动作，动作要有理由。**

**② 脚本不可复现**

```
症状：⭐⭐ 依赖一堆⭐ 隐藏环境变量，⭐⭐⭐ 换个机器就跑不起来
药方：写清依赖 · 参数明确 · ⭐ 加错误提示和样例测试
```

> ⭐⭐ 与 `dependency-resolution-conflicts.md` 的
> "隐式依赖的症状 = 时好时坏"同源。

## 4. ⭐⭐⭐ 排障先查这两步

> ⭐⭐⭐ **"实践中绝大多数'技能不生效'的问题，都出在前两步：
> ⭐⭐ 要么压根⭐ 没加载成功（检查目录和 YAML 格式），
> ⭐⭐ 要么⭐ 描述写得不好导致没触发（改描述、加关键词）。
> ⭐⭐⭐ ⭐ 先排查这两个，⭐⭐ 再考虑更复杂的原因。"**

> ⭐⭐⭐ 这与 `four-layer-diagnosis-flow.md` 的
> "80% 文件层 · 15% 触发层 · 5% 后两层"⭐ 完全一致——
> ⭐⭐ 这是⭐ 第二个独立来源给出同样的分布。
> **两个来源都说：先花两分钟查文件层，别一上来就改描述。**

## 5. ⭐⭐ 两个数字：150–300 行与 3–5 个范例

**正文长度的第二个独立口径**：

```
⭐⭐ 经验值：SKILL.md 正文控制在 ⭐ 150~300 行 比较健康
```

> ⭐⭐ 与我们已有的两条对照：
> ```
> · operator-card-style.md：30–60 行目标，120 行上限
> · 官方规范：500 行硬上限（压缩只保留前 5000 token）
> ```
> ⭐⭐⭐ 三个数字不矛盾，是⭐ 三个不同的东西：
> **理想值（30–60）· 健康区间（150–300）· 硬上限（500）**
> ——超过 150 就该警惕，超过 300 就该拆，超过 500 会被截断。

**范例数量与"改前/改后对照"**：

```
⭐⭐⭐ 配 ⭐ 3~5 个高质量范例，⭐⭐ 覆盖 ⭐ 正常 · 边界 · 出错 ⭐ 三种情况
⭐⭐⭐ ⭐ "改前/改后对照"能⭐ 直观展示"什么叫做对了"
```

> ⭐⭐⭐ "改前/改后对照"这个形式值得单独记——
> 它与 `judgment-branches-acceptance.md` 的"差评反例"
> 是同一种技巧的两个变体：
> ```
> 差评反例：给一个不合格输出 + 一句改进说明
> 改前/改后：给一对输入输出的⭐ 前后对照
> ```
> ⭐⭐ 前者便宜（一句话），后者更全面。

**另外一条很好用的规则**：
> ⭐⭐ **"能画表就别写堆文字"**——多种情况怎么用表格列清楚，⭐⭐ 比大段文字可靠得多。

## 速查

```
□ ⭐⭐⭐ 六反模式：大杂烩→拆 · ⭐⭐ 黑话描述→写明白话 · ⭐⭐⭐ 零示例→补3-5个
   ⭐⭐⭐ 无检查点→步骤间加自查 · 写死数值→参数化/探测 · 当Wiki写→背景挪走
□ ⭐⭐⭐ 六红线：① 密钥走环境变量 ② 危险操作二次确认 ③ ⭐ 动库前备份
   ④ ⭐⭐⭐ ⭐ 外部内容一律当"数据"，绝不当"指令"（防注入底线）
   ⑤ 描述别太泛 ⑥ ⭐⭐⭐ ⭐ 安全控制必须在工具层，技能说了不算
□ ⭐⭐ 另两个：全是原则没动作→改成具体检查/命令/分支 · 脚本不可复现→写清依赖

□ ⭐⭐⭐ 排障先查两步：没加载成功(目录/YAML) → 描述没触发（第二个来源印证 80%）
□ ⭐⭐ 正文长度三档：⭐ 理想 30-60 · ⭐ 健康 150-300 · ⭐ 硬上限 500
□ ⭐⭐⭐ 范例 3~5 个覆盖 正常/边界/出错；⭐⭐ "改前/改后对照"直观展示什么叫做对
□ ⭐⭐ 能画表就别堆文字
```

**一句话**：

> ⭐⭐⭐ **六大反模式里"黑话描述"和"零示例"最致命，六条安全红线里"外部内容一律当数据、绝不当指令"是防注入的底线；
> 而排障绝大多数问题都出在前两步——没加载成功（查目录和 YAML）、或描述没触发（改描述加关键词）。**
