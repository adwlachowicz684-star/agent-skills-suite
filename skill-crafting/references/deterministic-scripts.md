## 1. ⭐ 脚本四条原则

```
① ⭐ 自愈性     ⭐ 脚本内部处理所有异常，始终正常退出
                 ⭐ 绝不阻断技能主流程
② 结构化输出   统一输出 JSON，方便 agent 解析和流转
③ ⭐ 幂等性     ⭐ 多次执行结果一致
                 ⭐ 预检脚本只追加缺失项，不覆盖已有配置
④ 安全边界     只操作指定文件，不触碰其他系统资源
```

> ⭐ 第 ① 条容易被误解为"吞掉所有错误"——
> 不是。是**处理并回报**（结构化错误信息），而不是把异常抛给主流程中断它。

**什么时候该写成脚本**：

> ⭐ **如果这件事让 LLM 做有概率出错，但让脚本做能 100% 确定性完成，
> 那就该封装成脚本。**
>
> ⭐ **如果发现自己在 SKILL.md 里写公式让 agent 计算，
> 该逻辑也应该被挪到脚本中。**

| 场景 | 纯指令的局限 | 脚本的优势 |
|---|---|---|
| 配置文件读写 | LLM 可能写入格式错误的 JSON | ⭐ 格式正确、原子写入 |
| 环境检测 | LLM 无法可靠检测系统状态 | ⭐ 直接查询，返回结构化结果 |
| 日志采集 | LLM 不应直接处理网络请求 | 封装 HTTP 调用，异常自处理 |
| 复杂计算 | ⭐ LLM 算术不可靠 | ⭐ 精确计算 |

## 2. ⭐ 确定性验证：跑两次 diff

```bash
python3 core-inspection.py --region X --project Y --time-range last_1h > /tmp/run1.json
python3 core-inspection.py --region X --project Y --time-range last_1h > /tmp/run2.json
diff /tmp/run1.json /tmp/run2.json
```

> ⭐ **任何 diff 输出都意味着脚本未达成纯函数保证，
> ⭐ 需要排查随机数、当前时间依赖或全局状态。**

**纯函数约束**（可复现性的三条硬规则）：

```
① ⭐ 不用 datetime.now()
   需要时间窗口时用 CLI 参数显式传入（如 --time-range）
   ⭐ "今天"作为隐式参数会破坏可回放性
② ⭐ 不依赖隐式排序
   没有 ORDER BY 时行序是未定义的
③ ⭐ 浮点比较用容差
   绝不要求精确相等，写明 abs(actual - expected) < 1e-6
```

**数据溯源**：

```
⭐ 写明用了哪些输入文件、数据库表、过滤条件、外部知识源
```

## 3. ⭐ 该不该脚本化

```
⭐ 模型推理（根因假设排序、跨域关联、经验综合）→ ⭐ 不需要脚本化
⭐ 脚本化只针对数值计算：单位换算 · 聚合 · 阈值判断 · Diff
```

判据很干净：

```
任务是"从 Y 算出 X，其中 X 是数字、Y 是结构化数据" → ⭐ 脚本
任务是"用自然语言解释 X"                          → ⭐ LLM
```

## 4. 五个"脚本胜 LLM"的模式

| 模式 | 理由 |
|---|---|
| **严格格式契约** | LLM 给你"大体正确"的 JSON，少一个键或差一分钱；脚本每次精确 |
| ⭐ **确定性回归测试** | ⭐ 脚本行为稳定所以能写单元测试；LLM 行为依赖当天温度，写不了 |
| ⭐ **钱在环路里** | ⭐ 涉及真实金额时，0.1% 幻觉率不可接受，底线是 0% |
| **延迟预算 <1s** | LLM 300ms–3s；脚本 5–50ms。热循环里延迟会累积 |
| ⭐ **审计与可复现** | ⭐ 脚本同输入永远同输出；LLM 明天模型更新可能不同 |

> ⭐ 第 5 条对金融/合规/任何被审计的工作流是**硬要求**。

**反过来，这五种别用脚本**：

```
· 开放式摘要
· 自然语言理解（用户说的 "misc" 指什么）
· 模糊分类（这是个人还是公司支出？）
· 生成解释性文字
· 多源综合
```

## 5. 数据驱动声明 + 公共引擎

架构模式（巡检类技能为例）：

| 文件 | 职责 |
|---|---|
| `{skill}_common.py` | ⭐ **公共引擎**：查询、解析、评估、格式化、聚合 |
| `{skill}-core-inspection.py` | ⭐ **业务声明**：若干 InspectionCase 数据项，**零计算逻辑** |
| `{skill}-security-inspection.py` | 同上 |

> ⭐ **新增巡检项 = 新增一个数据项，不写新的计算代码。**

**分界线判据**：

```
公共引擎承载"怎么算"（查询、解析、评估、格式化）
业务脚本承载"算什么"（巡检项配置、阈值、单位）

⭐ 判定标准：⭐ 业务脚本里不出现 if/else 数值判断逻辑
```

> ⭐ 这条判据的价值：
> 它把"这段逻辑该放哪"从审美变成了**可检查的事实**——
> 业务文件里出现了 `if 数值 > 阈值`，就是放错了。

## 速查

```
四原则：
□ ⭐ 自愈（内部处理异常，不阻断主流程）
□ 结构化输出（统一 JSON）
□ ⭐ 幂等（多次一致；只追加不覆盖）
□ 安全边界（只碰指定文件）

确定性：
□ ⭐ 跑两次 diff，任何差异都要排查
□ ⭐ 禁 datetime.now()（用 --time-range 参数）
□ ⭐ 不依赖隐式排序（显式 ORDER BY）
□ ⭐ 浮点用容差，不比相等
□ 写明数据溯源

该不该脚本化：
□ ⭐ 数值计算 → 脚本；自然语言 → LLM
□ 模型推理/根因排序/跨域关联 → 不脚本化

五模式：
□ 严格格式契约
□ ⭐ 确定性回归测试
□ ⭐ 涉及钱
□ 延迟 <1s
□ ⭐ 审计与可复现

架构：
□ ⭐ 公共引擎"怎么算" + 业务声明"算什么"
□ ⭐ 业务脚本里不出现 if/else 数值判断
□ 新增项 = 加数据项，不写新代码
```

**一句话**：

> ⭐ **CLI 保证"每次都一样"，技能保证"每次都对"——
> 这两句答的不是同一个问题，所以不是二选一。**
