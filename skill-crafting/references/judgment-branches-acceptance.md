## 1. ⭐⭐⭐ 流程 / 判断 / 验收 三件套

**看一个技能，我一般只看三样东西**：

```
⭐⭐ 流程  管⭐ 顺序
⭐⭐ 判断  管⭐ 分支
⭐⭐ 验收  管⭐⭐ 什么时候可以交付
```

**缺了会怎样**（三句都很准）：

```
少了流程 → ⭐ 执行会散
少了判断 → ⭐⭐ 遇到分支就乱
少了验收 → ⭐⭐⭐ agent 很容易用一句"已完成"糊过去
```

> ⭐⭐⭐ 第三条最锋利：**"已完成"是最廉价的转义**。
> 只要没有验收标准，模型总能输出"已完成"并停在那里——
> 而它确实做了什么，只是没做对。
> 这正对应 `seven-contracts.md` 的"把'做了'与'做对了'分开"。

## 2. ⭐⭐ 线性步骤为什么不够

**典型初稿**（看起来清楚，实际不够）：

```
1. Read the file.
2. Summarize the file.
3. Rewrite the file.
4. Return the result.
```

**真实任务里它覆盖不到的分支**：

```
· 来源不完整怎么办
· 用户要摘要还是改写
· 是否要保留引用
· 结果是写进文件还是直接回复
· ⭐⭐ 什么时候该停下来问
```

> ⭐⭐⭐ **"这些都不是线性步骤能覆盖的。"**

**好的写法是把⭐ 判断点写出来**（写作类技能的例子，可直接借鉴形状）：

```
· 用户只要求润色时 → 不改结构
· 用户要求长文时 → 先列大纲再起草
· 材料里有 URL 时 → ⭐ 先保存来源，再写作
· ⭐⭐ 缺少事实来源时 → ⭐⭐⭐ 不补编，标出缺口
· 中文稿交付前 → 运行中文标点检查
```

> ⭐⭐⭐ 一句总结这些规则的作用：
> **"这些规则没有把模型绑死，只是把⭐ 容易出错的选择⭐ 提前定好。
> 模型仍然负责理解语境、组织语言和权衡取舍，
> ⭐⭐ 但不用⭐ 每次都重新发明工作流。"**
>
> ⭐⭐ 这与 `write-reasons-not-rules.md` 的"给判断依据而不是死命令"
> 是同一条——**约束的是选择点，不是全部行为**。

## 3. ⭐⭐⭐ 差评反例：看着改错

> ⭐⭐⭐ **示例可以⭐ 故意展示一个"差评案例"加上改进说明。**

```
不用写太长，一句话就行：
"上表中的'继续跟进'缺少截止时间，属于不合格输出，
 应修正为'跟进 B 客户合同审批，预计 10 月 24 日完成'"
```

> ⭐⭐⭐ **"这种'看着改错'的例子，
> ⭐⭐ 比再多的正向示例都更能让模型理解什么算合格。"**

> ⭐⭐⭐ 这条是对 `few-shot-examples.md` 的⭐ 重要补充：
> 那份讲"示例要有 Rationale 字段"（讲为什么这么处理），
> 这份讲⭐ **配一个反例 + 一句改进说明**——
> 两者方向不同但都指向同一件事：**让模型看见边界在哪**，
> 而不是只看见中心在哪。
>
> ⭐⭐ 而且它成本极低：**一句话**。

**另一处也印证了同类做法**：写作类技能在示例里有意识地展示
"本周完成"与"风险项"是⭐ 分开的区块、
下周计划里⭐ 每个事项必须带预计完成日期——
> ⭐⭐ **"这些结构化的约定⭐ 通过示例传递，
> ⭐⭐ 比在规则正文里用文字解释一百遍都管用。"**

## 4. ⭐⭐⭐ 用示例锁死输出格式

**一个真实事故**：

```
让 agent 生成一份部署检查清单：
   一会儿输出 "1. 2. 3." 的有序列表
   一会儿输出 "- xxx" 的无序列表
   一会儿又把检查项写在段落里
⭐⭐⭐ 下游解析脚本被折磨得⭐ 改了三版
```

**修法**（在规则里用示例锁死）：

```
每个检查项必须：
  · ⭐ 开行
  · ⭐ 以 [ ] 或 [x] 开头
  · ⭐ 必须包含"检查命令"和"预期结果"两列
  · ⭐ 必须用二级标题分隔不同分组
```

**结果**：

```
⭐⭐ 从那以后输出格式基本稳定
⭐⭐⭐ ⭐ 偶尔有偏差，示例也能把模型⭐ 拉回来
```

> ⭐⭐⭐ "示例能把模型拉回来"这个观察很重要——
> 它说明**示例不只是初始指令，还是⭐ 纠偏装置**。
> 这与 `imperative-style.md` 的
> "输出格式钉死 + 一个填好的示例"一致，
> 但这里给了⭐ 后果证据（脚本改了三版 → 稳定）。

**更严格的做法**：

```
⭐⭐ 让模型直接输出 JSON，⭐⭐⭐ 再用代码负责渲染
   —— ⭐⭐⭐ ⭐ 这种模式⭐ 容错率最高
```

> ⭐⭐ 这与 `script-cli-contract.md` 的
> "stdout 只放结果、stderr 放调试"是配套的：
> **结构化输出 + 代码渲染** 把"格式稳定性"从模型手里彻底拿走。

## 5. ⭐⭐ 脚本 vs 模型的分工表

**一句朴素的社区说法**：

> ⭐⭐⭐ **"例行处理放脚本，判断留给 AI。"**
> ⭐⭐ 它几乎适用于所有技能。

| 交给脚本 | 留给模型 |
|---|---|
| 格式化和 lint | ⭐ 判断用户意图 |
| 文件转换 | 选择信息取舍 |
| URL 抓取 | 解释含混需求 |
| frontmatter 校验 | 综合多个来源 |
| 字数和链接统计 | 调整语气 |
| 文档渲染 / 截图 | ⭐⭐ **发现流程之外的异常** |
| JSON schema 检查 | |
| 批量生成目录结构 | |

> ⭐⭐ "发现流程之外的异常"留在模型这一侧很关键——
> 脚本只能检查你预设的检查项，⭐ 异常是预设之外的。

**脚本也要按 agent 的使用方式来写**：

```
· ⭐ 能独立运行，参数清楚
· ⭐ 提供 --help
· ⭐⭐⭐ ⭐ 错误信息能⭐ 指导修复（不只是"失败了"）
· 复杂命令放进 scripts/，⭐ 不要散落在正文里
· ⭐ stdout 和 stderr 分清
· ⭐ 外部依赖写明
· ⭐⭐ 能做 dry run 的地方用安全默认值
```

## 速查

```
□ ⭐⭐⭐ 三件套：流程(顺序) · 判断(分支) · ⭐⭐ 验收(何时可交付)
   缺流程→执行散 · 缺判断→遇分支乱 · ⭐⭐⭐ 缺验收→一句"已完成"糊过去

□ ⭐⭐ 线性步骤覆盖不到的：来源不完整/要摘要还是改写/保留引用/写文件还是回复/⭐何时停下问
□ ⭐⭐⭐ 判断点写法：把⭐ 容易出错的选择提前定好（⭐ 不绑死行为）
   ⭐⭐ "缺少事实来源 → ⭐ 不补编，标出缺口"

□ ⭐⭐⭐ ⭐ 差评反例（一句话："继续跟进"缺截止时间 → 修正为…）
   ⭐⭐⭐ "看着改错"比再多正向示例都有效
□ ⭐⭐⭐ 示例是⭐ 纠偏装置，不只是初始指令
□ ⭐⭐⭐ 输出格式锁死 → ⭐⭐ 偏差时示例能把模型拉回来
   ⭐⭐ JSON 输出 + 代码渲染 = ⭐⭐⭐ 容错率最高

□ ⭐⭐⭐ "例行处理放脚本，判断留给 AI"
   ⭐⭐ ⭐ 异常发现留在模型（脚本只能查预设项）
□ ⭐⭐⭐ 脚本写法：⭐⭐⭐ 错误信息能指导修复 · --help · stdout/stderr 分清 · dry run
```

**一句话**：

> ⭐⭐⭐ **正文要写三样不同的东西——流程管顺序、判断管分支、验收管何时可交付（缺了验收，agent 会用一句"已完成"糊过去）；
> 而"故意展示一个差评案例加一句改进说明"这种看着改错的例子，比再多的正向示例都有效。**
