## 1. ⭐⭐ 三个必覆盖的分支

```
① ⭐ Happy Path   理想场景
② ⭐ Edge Case    不寻常但合法
③ ⭐ Error Scenario 失败长什么样
```

**每个例子的四段格式**：

```
### Example [N]: [场景名]
**Input:**           具体输入数据
**Expected Output:**  ⭐ 带真实内容的预期结果
**Rationale:**       ⭐⭐ 为什么这个例子重要
```

> ⭐⭐ **"Expected Output: 带真实内容"** 是个容易偷懒的地方——
> 写成"输出一份报告"等于没写。**要写出实际内容**。

## 2. ⭐⭐⭐ Rationale：为什么这个例子重要

> ⭐⭐⭐ 多数示例只有 Input / Output 两项，
> **Rationale 这一项几乎没人写，而它恰恰是让示例产生泛化的东西。**

**为什么它重要**：

```
没有 Rationale：模型学到的是"这个输入 → 这个输出"（模仿）
⭐⭐ 有 Rationale：模型学到的是"⭐ 为什么在这个场景下该这么处理"（迁移）
```

> ⭐⭐⭐ 这与 `few-shot-examples.md` 那条
> "示例只给输入→输出，模型学到的是格式；加上思考过程，它学到的才是判断"
> 是⭐ 同一个原则的独立佐证——**格式里专门留一个字段来装它**。

**写法**（一句话就够，但要说出"如果不这么处理会怎样"）：

```
✅ Rationale: 数据为空时必须明说"无数据"，
   因为模型倾向于编造一个看起来合理的结论来填满输出。
❌ Rationale: 展示空数据的处理方式。
```

## 3. ⭐ 判断/分类类技能的特殊要求

> ⭐ **如果技能涉及判断、分类、分级输出，
> 放 3–5 个⭐ 有差异的高质量示例，⭐ 覆盖主要分支。**

**代码审查的例子**（三组，正好对应三档严重度）：

```
① 严重安全问题
② 中等风险
③ 轻微规范问题
```

> ⭐⭐ 目的不是"给三个例子"，而是让模型知道
> **"不同问题该怎么判断、怎么表达、怎么排序"**——
> 排序这一点很重要：**严重度分级技能的失败模式常常是"把轻微问题说得很重"**。

## 4. ⭐⭐ gotchas 是最值钱的部分

> ⭐⭐ **这是很多技能里⭐ 最值钱的部分。**

**定义**：

```
⭐⭐ 那些⭐ 违背常识、⭐ 模型不被告知就一定会踩的坑
```

**两个典型例子**（形态很标准，值得照抄）：

```
例 1："users 表用软删除，查询必须带 WHERE deleted_at IS NULL"
例 2："同一个用户在数据库叫 user_id、在鉴权服务叫 uid、
      在账单 API 叫 accountId"
```

> ⭐⭐ 第 2 例尤其典型：**它不是知识，是⭐ 跨系统的命名映射**，
> 模型不可能靠推理得出，只能被告知。
> 这与 `official-lessons.md` 官方举的例子完全同构
> （"这个字段在 API 网关叫 @request_id，在账单服务叫 trace_id"）。

**维护方式**（这条让技能能自我进化）：

> ⭐⭐ **每当你纠正了模型一个错误，就把这个纠正写进 gotchas。
> 这是把技能越用越好的⭐ 最直接方式。**

> ⭐⭐⭐ 这与 `skill-evolution-loop.md` 的"用每一次失败喂养它"、
> `forty-skills-lessons.md` 的"先做一遍再写"是同一条主线的三种说法：
> **技能的价值来自真实错误的积累，不来自设计。**

## 5. ⭐⭐ 亲手写：模型自生成是负效果

SkillsBench 的反直觉发现：

```
⭐ 人工编写的技能    平均 +16.2%
⭐⭐ 模型自生成的    平均 ⭐ -1.3%（负效果）
```

**原因**：

```
模型能识别"这里需要领域知识"
⭐ 但生成的步骤往往⭐ 太笼统、缺细节、错重点
```

> ⭐⭐⭐ 这组数字非常关键，因为它**直接否定了"让 AI 帮我写技能库"这个想法**——
> 至少在"从零生成"这一环是否定的。
>
> ⭐ 但要注意边界：这与 `self-evolution-three-levels.md` 的
> "外循环 agent 可以⭐ 提议修改、由人审核"并不矛盾——
> **生成（从零）是负效果，提议（基于真实轨迹）是有价值的**。
> 区别就在于⭐ 有没有真实反馈信号。

> ⭐ 另有一致证据：`context-file-selection.md` 引的 ETH 研究也说
> "让 LLM 生成你的上下文文件，结果比你自己写的更差"。

**拆分的三个信号**（与 `split-signals-five.md` 互补）：

```
· 正文超过 500 行
· ⭐ 包含多个⭐ 可独立执行的流程
· ⭐ 不同部分⭐ 更新频率差异很大
```

## 速查

```
□ ⭐⭐ 三分支：Happy Path · Edge Case · Error Scenario
□ 每个例子四段：Input / ⭐ Expected Output（带真实内容）
   / ⭐⭐ Rationale（为什么重要）
□ ⭐⭐⭐ Rationale 让示例产生⭐ 泛化（学判断而非学格式）
   ⭐ 写法要说出"不这么处理会怎样"

□ ⭐ 判断/分类类：3–5 个⭐ 有差异的示例，覆盖主要分支
   → 让模型知道"怎么判断·怎么表达·⭐ 怎么排序"

□ ⭐⭐ gotchas = ⭐ 违背常识、不被告知必踩的坑（最值钱）
   ⭐ 典型形态：跨系统命名映射
   ⭐⭐ 每纠正一个错误就写进去 = 最直接的自进化方式

□ ⭐⭐ 人工 +16.2% vs ⭐⭐ 模型自生成 -1.3%（负效果）
   ⭐ 边界：从零生成是负效果；⭐ 基于轨迹提议 + 人审 = 有价值
□ 拆分三信号：>500 行 · ⭐ 多个可独立流程 · ⭐ 更新频率差异大
```

**一句话**：

> ⭐⭐ **每当你纠正了模型一个错误，就把这个纠正写进 gotchas——
> 这是把技能越用越好的最直接方式。**
