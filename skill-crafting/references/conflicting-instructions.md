## 1. ⭐⭐⭐⭐⭐ 两份都读起来对的指令

```markdown
## 输出要求
- 详尽覆盖所有相关方面

## 风格
- 简洁，每条不超过一行
```

> ⭐⭐⭐⭐⭐ 两句单独读都是好建议。
> ⭐⭐⭐⭐⭐ 放在一起，它们要求的是两件不同的事。

而技能里几乎一定同时存在这两句——因为它们写在**不同章节**，
写"输出要求"时想的是完整性，写"风格"时想的是可读性。

## 2. ⭐⭐⭐⭐⭐ 模型不是"选一个"，是"折中"

这是本份最关键的一条事实：

```
遇到冲突，模型的默认动作不是选一个、也不是报错
⭐⭐⭐⭐⭐ 而是各取一部分——输出一份"中等长度、覆盖中等、每条两行"的东西
```

> ⭐⭐⭐⭐⭐ 折中的结果两边都不满足，⭐⭐⭐⭐⭐ 而它看起来"兼顾了两个方面"。

三个后果：

```
① ⭐⭐⭐⭐⭐ 没有任何一方的要求被违反到会被注意到的程度
② ⭐⭐⭐⭐⭐ 用户觉得"还可以但不够好"，说不清哪里不对
③ ⭐⭐⭐⭐⭐ 修的时候不知道该改哪一句——因为两句都是对的
```

> ⭐⭐⭐⭐⭐ 第 ③ 条是这类问题最贵的地方：⭐⭐⭐⭐ 它不是"修不好"，
> ⭐⭐⭐⭐⭐ 是**不知道该修哪一边**，于是通常两边都改，越改越含糊。

## 3. ⭐⭐⭐⭐⭐ 五类高频冲突

**① ⭐⭐⭐⭐⭐ 详尽 vs 简洁**（最常见）

```
"全面分析" + "每条不超过一行"
```

**② ⭐⭐⭐⭐⭐ 自主 vs 询问**

```
"不要为细节打扰用户" + "遇到不确定时必须确认"
```

> ⭐⭐⭐⭐⭐ 这条后果最严重：⭐⭐⭐⭐⭐ 它让"该不该问"变成一个随机事件——
> 有时问有时不问，于是输出不稳定（失败四象限的②格）。
> 而《skill-input》的 `inference-vs-asking.md` 只解决了"缺什么时该怎么办"，
> ⭐⭐⭐⭐⭐ 没解决"技能同时说了要问和不要问"。

**③ ⭐⭐⭐⭐⭐ 严格 vs 容错**

```
"格式必须严格符合 schema" + "数据不全时用合理默认值填充"
```

> ⭐⭐⭐⭐⭐ 两者结合的典型产物：**用编的值填出一个合格的结构**
> ——正是"结构正确的废话"的成因之一。

**④ ⭐⭐⭐⭐⭐ 完整流程 vs 快速完成**

```
"逐步执行，每步确认" + "一次性输出结果，不要分步汇报"
```

**⑤ ⭐⭐⭐⭐⭐ 局部 vs 全局**

```
"每个文件独立处理" + "保持跨文件一致性"
```

> ⭐⭐⭐⭐⭐ 第 ⑤ 条在并行时尤其致命：⭐⭐⭐⭐ "独立处理"鼓励并行，
> ⭐⭐⭐⭐⭐ "跨文件一致"要求全局信息——两者不能同时做
> （见《skill-execution》的 `parallel-and-concurrency.md`）。

## 4. ⭐⭐⭐⭐⭐ 为什么写的时候发现不了

三个原因，第二个最根本：

**① ⭐⭐⭐⭐ 冲突的两句不在同一屏**

```
"输出要求" 在第 12 行
"风格"     在第 48 行
⭐⭐⭐⭐⭐ 写第 48 行时，第 12 行已经不在工作记忆里了
```

**② ⭐⭐⭐⭐⭐ 章节划分本身就是"分开想"的机制**

```
⭐⭐⭐⭐⭐ 分章节的目的是让每部分可独立阅读，
⭐⭐⭐⭐⭐ 而"独立可读"恰恰意味着写的时候不考虑其他章节
```

> ⭐⭐⭐⭐⭐ 这条让冲突**系统性地**发生：
> ⭐⭐⭐⭐⭐ **结构越清晰，跨章节冲突越难被发现**——
> 因为清晰的结构正是在鼓励你分块思考。

**③ ⭐⭐⭐⭐⭐ 冲突的两句通常不共用词**

```
"详尽覆盖" vs "简洁"
⭐⭐⭐⭐⭐ 没有一个共同的关键词，grep 找不到它们
```

> ⭐⭐⭐⭐⭐ 这也是"沉积"检测方法（把提到同一件事的放在一起）在这里**部分失效**的原因：
> 沉积的冲突通常共用词（新旧两版说同一件事），
> ⭐⭐⭐⭐⭐ 而这里的冲突是**反义但不同词**——它们从不会被排到一起。

## 5. ⭐⭐⭐⭐⭐ 检测：把所有提到同一件事的句子放在一起

既然 grep 不管用，用另一种分组：

```
按"这句子在约束输出的哪个属性"分组：
  长度 · 覆盖范围 · 是否询问 · 严格程度 · 是否并行 · 顺序
```

> ⭐⭐⭐⭐⭐ 关键差别：⭐⭐⭐⭐ 不是按**主题**分组（主题不同所以分不到一起），
> ⭐⭐⭐⭐⭐ 而是按**被约束的维度**分组——"详尽"和"简洁"约束的都是**长度**。

操作形式（可以做成一张小表）：

| 维度 | 涉及的句子 | 冲突？ |
|---|---|---|
| 长度 | 第 12 行"全面" · 第 48 行"每条一行" | ⭐⭐⭐⭐⭐ 是 |
| 询问 | 第 20 行"不要打扰" · 第 55 行"必须确认" | ⭐⭐⭐⭐⭐ 是 |

> ⭐⭐⭐⭐⭐ 六个维度就能覆盖绝大多数技能。
> ⭐⭐⭐⭐⭐ 而"填这张表"这个动作，比任何一条检查清单都更能发现冲突——
> 因为它强制把不相邻的句子放到一行里。

## 6. ⭐⭐⭐⭐⭐ 修法：给冲突一个优先级，而不是删掉一句

最常见的错误处理是删掉一句（"简洁"或"全面"二选一）。这是错的：

> ⭐⭐⭐⭐⭐ 两句通常都有存在的理由——
> ⭐⭐⭐⭐⭐ 删掉"全面"会得到一份短但不完整的输出，问题只是换了形状。

正确写法是**显式排序**：

```markdown
- ⭐⭐⭐⭐⭐ 优先级：完整性 > 简洁
  → 所有相关方面必须覆盖；在此前提下每条尽量不超过一行
```

> ⭐⭐⭐⭐⭐ 成本一行，而它把"折中"变成了"有方向的取舍"。

三条配套写法：

```
① ⭐⭐⭐⭐⭐ 用"在此前提下"连接，不要用"但是"（但是 = 未排序）
② ⭐⭐⭐⭐⭐ 冲突不可调和时，写明触发条件：
   "默认详尽；用户明确要求'简短'时，改为只输出结论"
③ ⭐⭐⭐⭐ 不要用"尽量""适当"来调和冲突——那只是把冲突藏进含糊词里
```

> ⭐⭐⭐⭐⭐ 第 ③ 条值得单独记：⭐⭐⭐⭐⭐ **用含糊词解决冲突，
> 是把一个"模型会折中"的问题，换成一个"模型会自己定义"的问题——后者更糟。**

还有一种结构性解法：**把冲突的两句放进同一节**。

```
## 输出（长度与覆盖）
- 完整性优先……
```

> ⭐⭐⭐⭐⭐ 物理相邻至少让模型读到时能看到两句，
> ⭐⭐⭐⭐⭐ 而分处两节时，它可能只读到其中一节（参考文件常被部分加载）。

## 7. ⭐⭐⭐⭐⭐ 自检

六个维度逐一过一遍：

```
① ⭐⭐⭐⭐⭐ 长度：有没有同时要求"详尽"和"简洁"？排了序吗？
② ⭐⭐⭐⭐⭐ 询问：有没有同时说"不要打扰"和"必须确认"？
③ ⭐⭐⭐⭐⭐ 严格度：有没有同时要求"严格 schema"和"缺了就补默认值"？
④ ⭐⭐⭐⭐⭐ 流程：有没有同时要求"逐步确认"和"一次性输出"？
⑤ ⭐⭐⭐⭐⭐ 并行：有没有同时要求"独立处理"和"保持一致"？
⑥ ⭐⭐⭐⭐⭐ 顺序：有没有同时要求"按此顺序"和"给约束不给流程"？
```

> ⭐⭐⭐⭐⭐ 第 ⑥ 条是新增的、也是这类冲突里最微妙的一条：
> "给约束不给流程"与"顺序必须强制"确实矛盾，
> ⭐⭐⭐⭐⭐ 正确解法不是二选一，是**顺序真的重要时改用脚本/工作流**（已有结论）。

一个十秒判断：

> ⭐⭐⭐⭐⭐ **挑一句技能里的要求，问"有没有另一处在要相反的东西"。
> 找到一处 → 模型正在折中，而你看到的是折中结果，不是任一方的要求。**
