## 1. ⭐ 它消灭的缺陷类型

> ⭐ **一个技能跑到一半才来问你要东西——
> 或者更糟，⭐ 默默即兴发挥一条替代路径——
> ⭐ 而这都发生在你已经走开之后。**

这是 STEP 0 存在的唯一理由。它不是形式主义。

---

## 2. ⭐ 声明：Prerequisites 章节

`## Prerequisites` 紧跟标题块，列出技能完成工作所需的**一切**：

| 类别 | 例子 |
|---|---|
| 工具 / CLI | `gh`、`jq`、测试运行器、语言运行时（**版本重要时写明版本**） |
| 凭据 / 环境变量 | API key、token、已登录的 CLI |
| 文件 / 路径 | 配置文件、输入产物、预期目录 |
| 服务 / 连通性 | 可达的 API、MCP server、数据库连接 |
| ⭐ **用户输入与决策** | ⭐ **运行期间需要的每一个回答、选择或批准** |

> ⭐ **没有需求的技能要显式写 `Prerequisites: none`。
> ⭐ 缺失该章节是缺陷，不是默认值。**

> 最后一行最容易被漏：**"运行期间你会需要问用户什么"也属于前置条件**，
> 应该在用户还在场的时候一次问完。

---

## 3. ⭐ 验证：STEP 0 Preflight

```
技能的 ⭐ 第一个可执行步骤 ⭐ 就是 ## STEP 0: Preflight
```

它用**廉价的、无副作用的检查**逐项探测：

```
--version        版本检查
file-exists      文件存在
env-var set      环境变量已设置
read-only ping   只读连通性探测
```

**并且**：

> ⭐ **在用户仍在你面前时，⭐ 一次性收集全部声明过的用户输入与决策。**

---

## 4. ⭐ 拦截：三条 MUST NOT

```
① ⭐ 不得在已知缺少前置条件的情况下开始执行
② ⭐ 不得在运行中途暂停，去要一个 STEP 0 本可收集到的输入
③ ⭐ 不得即兴发挥一条未声明的回退路径
   ⭐ 回退阶梯只有在 SKILL.md 里已声明、
      且不需要中途用户输入时才被允许
```

**缺失时的处理**：

```
· ⭐ 一次性报告所有缺失项（⭐ 绝不是一次报一个）
· 请用户现在就补齐或修复
· 只有全部转绿才继续
· ⭐ 无法解决 → HARD-STOP，给出完整清单 + 每项该怎么办
```

> ⭐ "一次性报告所有缺失项"这条极重要——
> 一次报一个会让用户来回五六轮，而这正是 STEP 0 要消灭的体验。

## 5. 一个完整的实现样本

**Step 0：Git 仓库验证**

```bash
git rev-parse --git-dir 2>/dev/null || echo "NOT_A_GIT_REPO"
```

- 输出路径 → 成功（`.git` 或 submodule 的绝对路径）
- 输出哨兵 `NOT_A_GIT_REPO` → 终止并提示：
  > "This directory is not a git repository. Initialize with `git init` or navigate to a repo."

> ⭐ `2>/dev/null` 不只是"静音"——
> **它确保输出干净可解析，防止 stderr 噪音干扰结果判读。**
> ⭐ **哨兵字符串是给 agent 的判定信号，不是给人看的报错。**

**Step 1：CLI 可用性** —— 三种场景的分支设计很值得学：

| 场景 | 检测 | 动作 |
|---|---|---|
| **一个都没有** | `GEMINI_NOT_FOUND` `CODEX_NOT_FOUND` | 立即终止，给出安装指引 |
| ⭐ **只有一个** | `/usr/bin/gemini` `CODEX_NOT_FOUND` | ⭐ **跳过路由分析**（Step 3–5），直接执行 |
| 两个都有 | 两个路径 | 完整路由分析 |

> ⭐ **"只有一个"时跳过路由步骤**是这个设计最漂亮的地方：
> **只有一个选择时，路由逻辑是不必要的，跳过它能提速**。
> 这不是偷懒，是**按条件裁剪流程**。

## 与 fail-fast 的关系

通用决策规则：

```
⭐ 前置条件失败 → 快速失败
⭐ 运行时失败   → 优雅降级
```

| 错误类型 | 模式 |
|---|---|
| 配置缺失 | ⭐ Fail Fast |
| 输入非法 | ⭐ Fail Fast |
| 权限不足 | ⭐ Fail Fast |
| 资源分配失败 | ⭐ Fail Fast |
| 数据库超时 | 优雅降级（重试 → 缓存） |
| API 不可用 | 优雅降级（备用端点） |
| 被限流 | 优雅降级（指数退避） |

**失败信息必须可执行**：

```bash
# ❌
[ -f "$CONFIG" ] || exit 1
# ✅
[ -f "$CONFIG" ] || { echo "Config file not found: $CONFIG. Create it from config.example.yml"; exit 1; }
```

**四个反模式**：

```
① 延迟验证    —— 在副作用已经发生之后才校验
② ⭐ 吞掉错误 —— 失败了还继续
③ ⭐ 部分执行 —— 没检查完所有前置条件就开始动手
④ 含糊报错    —— 快速失败了但不说为什么
```

## 速查

```
□ ⭐ ## Prerequisites 紧跟标题块
□ 五类：工具/凭据/文件/服务/⭐用户输入与决策
□ ⭐ 无需求也要显式写 "Prerequisites: none"
□ ⭐ 缺失该章节 = 缺陷，不是默认

□ ⭐ STEP 0: Preflight 是第一个可执行步骤
□ 用无副作用的廉价检查（--version / file-exists / env / ping）
□ ⭐ 一次收集全部用户输入（趁用户还在）

□ ⭐ 缺失项一次性全报（不是一次一个）
□ ⭐ 无法解决 → HARD-STOP + 完整清单 + 每项怎么办
□ ⭐ 三条 MUST NOT
□ ⭐ 回退阶梯必须预先声明且不需中途输入

□ ⭐ 哨兵字符串给 agent 判定；2>/dev/null 保证可解析
□ ⭐ 只有一个可选时 → 跳过路由步骤（不是偷懒）
□ ⭐ 前置失败→快速失败；运行时失败→优雅降级
□ ⭐ 报错要可执行（给修复动作，不只说"没找到"）
□ 四反模式：延迟验证/吞错/部分执行/含糊报错
```

**一句话**：

> ⭐ **在用户还坐在屏幕前的时候，把所有你会需要的东西一次问完。**
