## 1. ⭐⭐⭐⭐⭐ 两种"看不出对错"

```
A. ⭐⭐⭐⭐ 结果错：结论与事实不符 → 靠追溯源发现
B. ⭐⭐⭐⭐⭐ 结果对但依据错：结论对，理由是错的
```

> ⭐⭐⭐⭐⭐ **B 更危险**：它这次通过了，下次同样的推理就会错——
> 而因为这次对了，没有人会去查。

一个现场：

```
输出："建议采用方案 B"
理由：未写
真相：它其实是随机挑的，只是碰巧 B 是对的
```

> ⭐⭐⭐⭐⭐ **用户无法区分"有依据的 B"和"碰巧的 B"**——
> 因为输出里没有依据，两者长得一模一样。

> ⭐⭐⭐⭐ 这正是"结构正确的废话"那条结论的推论：
> ⭐⭐⭐⭐⭐ **一个没有依据的结论，无论对错，都是不可审的。**

## 2. ⭐⭐⭐⭐⭐ 决策依据 vs 解释

两者常被混为一谈，而价值相反：

| | ⭐⭐⭐⭐⭐ 决策依据 | ⭐⭐ 解释 |
|---|---|---|
| 内容 | ⭐ 用了什么输入、走了哪条规则 | 为什么这个方案好 |
| 可验证 | ⭐⭐⭐⭐⭐ 能查 | 不能查 |
| 长度 | 一行 | 一段 |
| 价值 | ⭐⭐⭐⭐⭐ 让人能判断信不信 | 让人看得舒服 |

> ⭐⭐⭐⭐⭐ **"解释"是可以编的，"依据"很难编**——
> 因为依据必须指向具体的输入和具体的规则。

```
❌ 解释："这个方案更好，因为它更简洁、更易维护。"   ← 无法验证
✅ 依据："按规则 3（成本优先），A 需 3 人日 / B 需 1 人日 → 选 B"
```

> ⭐⭐⭐⭐⭐ 后者的价值在于：**如果规则 3 用错了，人一眼就能看出来。**
> 而前者再读三遍也看不出问题。

## 3. ⭐⭐⭐⭐ 四类必须写依据的判断

不是所有输出都要写。四类必写，判据是**"错了要回滚"**：

**① ⭐⭐⭐⭐⭐ 分类/路由判断**

```
"归为 P2" → 依据：影响 1 个模块、可降级、无数据丢失
```

> ⭐⭐⭐⭐ 分类错了下游全错，且**错误会传播很远才被发现**。

**② ⭐⭐⭐⭐⭐ 阈值/取舍判断**

```
"保留 3 条，丢弃其余 9 条" → 依据：按置信度 ≥0.7 阈值
```

> ⭐⭐⭐⭐⭐ **丢弃动作必须有依据**——否则用户不知道被丢的是什么，
> 也不知道该不该质疑这个丢弃。

**③ ⭐⭐⭐⭐⭐ 不确定时的选择**

```
"这里填了默认值 X" → 依据：输入未提供，按规则 5 取默认
```

> ⭐⭐⭐⭐⭐ 这一条最该写，也最常不写：
> ⭐⭐⭐⭐ **默认值是静默编造的高发区**，
> 而写一句"输入未提供，取默认"就把它变成了可见的事实。

**④ ⭐⭐⭐⭐ 冲突消解**

```
"两个技能都适用，选了 A" → 依据：A 更具体（特异优于通用）
```

> ⭐⭐⭐⭐ 这与编排里"真的有歧义时记 --decision 日志"是同一件事，
> ⭐⭐⭐⭐⭐ 只是这里记在**输出里**——因为用户也需要看见。

## 4. ⭐⭐⭐⭐⭐ 写法：三件套

最小可用格式，每条判断一行：

```
决策 → 依据 → 例外
```

```markdown
- 归类：P2
  依据：影响 1 个模块 · 可降级 · 无数据丢失（规则 3b）
  ⭐ 例外：若涉及支付链路则升为 P1
```

三件套的分工：

| 件 | ⭐ 作用 |
|---|---|
| 决策 | 结论本身 |
| ⭐⭐⭐⭐⭐ 依据 | ⭐⭐⭐⭐⭐ **让人能验证**——指向具体输入与具体规则 |
| ⭐⭐⭐⭐ 例外 | ⭐⭐⭐⭐ 说明什么情况下这个决策不成立 |

> ⭐⭐⭐⭐⭐ 第三件最容易被省，但它正是让依据"可证伪"的部分：
> ⭐⭐⭐⭐ 写了例外，人才知道该查什么。

结构化输出里就是三个字段：

```json
{"decision":"P2","basis":"rule_3b: 1 module, degradable","exception":"支付链路→P1"}
```

> ⭐⭐⭐⭐⭐ `basis` 字段还有一个额外好处：
> **它让"依据"成为可解析、可统计的数据**——
> 于是你可以统计"哪些规则被引用得最多"。

## 5. ⭐⭐⭐⭐ 成本：写多少才够

> ⭐⭐⭐⭐⭐ 依据写长了会变成解释，而解释是可以编的。

三条纪律：

```
① ⭐⭐⭐⭐⭐ 一条判断一行依据，不超过 20 词
② ⭐⭐⭐⭐⭐ 依据必须指向可查的东西（规则编号 / 输入字段 / 阈值）
③ ⭐⭐⭐⭐ 只给四类判断写，不是所有输出都写
```

> ⭐⭐⭐⭐⭐ 第 ② 条是核心判据：
> **"因为它更好"不是依据；"因为规则 3b"才是。**
> 前者不可查，后者可查。

成本上很便宜：一个 8 步的技能，通常只有 2–3 处真正的判断点，
⭐⭐⭐⭐ 三行字，不到 60 token。

## 6. ⭐⭐⭐⭐⭐ 副作用：它同时是最好的调试数据

> ⭐⭐⭐⭐⭐ **写了依据的输出，排错时不需要重跑。**

对比：

```
没有依据：结果不对 → 重跑 → 看它这次怎么做 → 还得猜上次为什么那样
⭐⭐⭐⭐⭐ 有依据：结果不对 → 看依据 → "它在第 3 步用了规则 3b"
        → ⭐⭐⭐⭐⭐ 直接定位到规则 3b 用错了
```

> ⭐⭐⭐⭐⭐ 这就是 trace-debugging 里"失败点 ≠ 出错点"的解法：
> ⭐⭐⭐⭐⭐ **依据让出错点可见**——
> 否则你只能从失败点往回推，而推的过程全靠猜。

还有一个复用价值：

```
⭐⭐⭐⭐⭐ 统计所有输出的 basis 字段
→ 某条规则从未被引用 → 它可能是死规则
→ ⭐⭐⭐⭐ 某条规则被引用但结果常错 → ⭐⭐⭐⭐⭐ 它该进 Gotchas
```

> ⭐⭐⭐⭐⭐ 最后一行闭环了 `gotchas-mining.md`：
> **Gotchas 是采集的，而依据字段是一个自动的采集信号**——
> 比人工回忆可靠得多（与 `stopped_at` 那条同理）。

---

## 一句可贴在墙上

> ⭐⭐⭐ **"因为它更好"不是依据，"因为规则 3b"才是。
> 前者不可查，后者可查——而不可查的依据等于没有依据。**
