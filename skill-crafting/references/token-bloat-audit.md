## 1. ⭐ 性能的两个组成部分

```
API 延迟      模型生成响应所需时间，⭐ 随上下文窗口大小增长
工具执行时间  Bash / 文件读 / 外部进程的实际耗时
```

> ⭐ **两者都会让技能感觉慢，但修法完全不同。**
> ⭐ 多数开发者盯着工具执行，而**真正的瓶颈是上下文大小**。

---

## 2. ⭐ 瘦身：一个具体数字

```
⭐ 技能文件里的每个词，在每次调用时都会加载进上下文。
⭐ 一个 1500 词的定义 ≈ 每次请求多 2000 tokens。
⭐ 会话里有 3 个活跃技能 → 你还没写一个字，就有 6000 tokens 的静态开销。
```

**自查命令**：

```bash
wc -w ~/.claude/skills/*.md
```

```
⭐ 超过 400 词就值得复查。
```

**膨胀的四个常见来源**：

```
① 技能文件里的扩展示例，其实在重复同一个要点
② ⭐ 解释"为什么这么做"的说明性散文，而不是"做什么"
③ 重复同一约束的冗余指令
④ ⭐ 早期版本遗留的旧指令
```

**一个具体的前后对比**：

```
❌ 前：
   "什么是 TDD？测试驱动开发（TDD）是一种软件开发方法，
    在编写实现之前先编写测试。这有助于确保你的代码是可测试的，
    并且所有需求在开始编码之前都已被捕获为测试……"
    （200 词的解释）

✅ 后：
   "方法
    先写失败的测试。然后写最小实现让它通过。然后重构。
    JavaScript 用 Jest，Python 用 pytest。"
```

> ⭐ 差别在于：**前者在教模型已知的概念，后者在给行为指令。**
> 也正是 `anti-patterns-catalog.md` 的第一条——包含模型训练里已有的信息。

## 3. ⭐⭐ 六个优化动作

**Fix 1：砍技能定义**（上面已述）

```
⭐ 砍到"能改变模型行为的最小指令集"。
```

**Fix 2 ⭐ 减少工具往返**

```
⭐ 每次工具调用（Bash/读/写）都是一次独立的 API 请求。
   20 次串行调用能 5 次做完的，你多付了 15 次往返。
```

```
❌ 慢：Read src/auth.ts → Read src/user.ts → Read src/session.ts
✅ 快：一次读三个文件，各用一句话总结

❌ 慢：npm run lint / npm run typecheck / npm test（分开跑）
✅ 快：npm run lint && npm run typecheck && npm test
```

**Fix 3：长任务前用 `/compact`**

```
⭐ /compact 压缩前面的轮次，释放上下文预算。
⭐ 之后每个请求要处理的内容都更少。
```

> 时机建议：**每个组件完成后就 compact，而不是整个会话结束时才做**。

**Fix 4 ⭐ 收紧会话范围**

```
❌ 慢：一个超长会话，/supermemory + /tdd + /frontend-design 全塞进去
✅ 快：拆成专注的会话
   会话 1：/tdd 写 UserService 的全部测试
   会话 2：/tdd 实现 UserService
   会话 3：/frontend-design 构建 UserForm
```

> ⭐ 之前的历史越长，每个新响应生成越慢。
> **每个会话都从小上下文开始，全程都更快。**

**Fix 5：限制记忆读取范围**

```
❌ 读整个记忆库（可能几百条）
✅ /supermemory 只读最近 30 天、标签为 project:myapp 的条目
✅ 或清理超过 60 天的旧条目
```

**Fix 6 ⭐ 抑制冗长的工具输出**

```
⭐ 工具输出会进入上下文窗口。
   一个 dump 500 行日志的 Bash 命令会加入数千 tokens，
   ⭐ 并拖慢之后的每一个响应。
```

```
❌ npm test（完整输出）
✅ npm test 2>&1 | tail -20
```

**另一个相关技巧（动态注入）**：

```
⭐ !`command` 在技能加载前执行 shell 命令。
⭐ 如果命令慢（API 调用、大文件解析），会阻塞技能加载。
⭐ 保持输出小——用 head / jq / wc 过滤，不要注入完整文件内容。
⭐ 目标：2 秒内完成。
```

## 4. ⭐ 慢的不是工具，是上下文

> ⭐ **多数开发者关注工具执行，而真正的瓶颈是上下文大小。**

配套的体量红线（多个来源一致）：

```
⭐ SKILL.md < 5,000 tokens（约 500–700 行）
⭐ 压缩后每个技能只保留前 5,000 tokens
   → ⭐⭐ 关键指令必须在顶部，详细示例沉底
```

> ⭐ 最后这条是瘦身的**结构性结论**：
> **不是"少写一点"，而是"重要的写在前面"**——
> 因为超出部分会在压缩时被静默裁掉。

**一个可用的逃生阀**（谨慎使用）：

```
SLASH_COMMAND_TOOL_CHAR_BUDGET 环境变量可以抬高默认描述预算。
⭐ 但这是用上下文空间换技能可发现性——
   ⭐ 描述占得越多，留给实际对话的越少。
```

## 速查

```
□ ⭐ 两个瓶颈：API 延迟（随上下文增长）+ 工具执行
□ ⭐ 瓶颈通常在上下文，不在工具

瘦身：
□ wc -w 查词数，⭐ >400 词就复查
□ ⭐ 1500 词 ≈ 2000 tokens/次；3 个活跃技能 = 6000 静态开销
□ 砍掉：重复示例 / ⭐"为什么"的散文 / 冗余指令 / ⭐ 旧版本遗留
□ tdd 技能只需说"先写测试"+ 指定框架，不必解释什么是 TDD

六个动作：
□ ① 砍到最小指令集
□ ② ⭐ 合并工具调用（一次读三个文件、&& 串起命令）
□ ③ 长任务前 /compact（⭐ 每个组件后就做，别等到最后）
□ ④ ⭐ 拆成专注会话，不跑马拉松
□ ⑤ 限制记忆读取范围
□ ⑥ ⭐ 抑制冗长输出（| tail -20）；⭐ !`cmd` 输出要小且 <2s

□ ⭐ SKILL.md <5,000 tokens（约 500–700 行）
□ ⭐⭐ 压缩只保留前 5,000 tokens → 关键指令必须在顶部
□ SLASH_COMMAND_TOOL_CHAR_BUDGET 可抬预算，但会挤占对话空间
```

**一句话**：

> ⭐ **一个 dump 500 行日志的命令，会拖慢之后每一个响应——
> 因为那些输出从此留在上下文里。**
