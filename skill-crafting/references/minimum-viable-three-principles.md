## 1. ⭐⭐⭐ 坑一：SKILL.md 写成了产品文档

**现场**：

```
第一个技能写了 ⭐ 800 字 SKILL.md
把⭐ 背景 · 动机 · 架构理念⭐ 全写进去了

⭐⭐⭐ 结果：Agent 读完之后，⭐⭐⭐ 前 3 次调用⭐ 都跑偏了
      ⭐⭐⭐⭐ 因为它在⭐ 找"为什么做"而不是"怎么做"
```

**原则**：

> ⭐⭐⭐⭐ **"SKILL.md 是⭐ 执行契约，不是产品宣发。"**

四项写清楚，其他都是噪音：

```
① ⭐⭐ 触发条件
② ⭐⭐ 输入格式
③ ⭐⭐⭐ 输出格式
④ ⭐⭐⭐ 错误处理
```

**一句很到位的解释**（这是本份最有价值的部分）：

> ⭐⭐⭐⭐ **"Agent 不会因为你知道'为什么'而做得更好，
> ⭐⭐⭐⭐ ⭐ 只会因为你没写清'怎么做'而做错。"**

> ⭐⭐⭐⭐ 这条精确地区分了两件常被混为一谈的事：
> ```
> · write-reasons-not-rules.md：⭐ 规则要写⭐ "为什么"（讲后果/例外）
> · 本份：            ⭐⭐⭐ 不要写⭐ "背景/动机/架构理念"
> ```
> ⭐⭐⭐⭐ **不矛盾——区别在于"为什么"指的是什么**：
> ```
> ✅ 要写：⭐⭐⭐ "用 X，因为 Y 已废弃会报错"（⭐ 可迁移的因果，能举一反三）
> ❌ 别写：⭐⭐⭐ "我们为了解决 Z 问题而设计了这个技能"（⭐ 背景叙事）
> ```
> ⭐⭐⭐⭐ 判据：**这段"为什么"，能改变 agent 下一步的动作吗？**
> 能（比如换 API）→ 写；不能（只是交代来龙去脉）→ 删。

**"800 字不如 200 字"**：

> ⭐⭐⭐ **"技能开发的核心不是'写得全面'，是'写得够用'。
> ⭐⭐⭐ ⭐ 先跑通最小闭环，再迭代加功能。
> ⭐⭐⭐ 800 字的 SKILL.md 不如 200 字但每个字都精确。"**

## 2. ⭐⭐⭐ 坑二：一个技能管三件事

**现场**：

```
把 ⭐ PDF 转换 + OCR + 摘要 ⭐ 塞进一个技能
⭐⭐⭐ 结果：Agent 经常⭐⭐⭐ 跳过 OCR 直接摘要，
      或者⭐⭐⭐ 对图片做文本摘要——⭐⭐⭐⭐ 它分不清三个功能的边界
```

**原则**：

> ⭐⭐⭐ **一个技能只做一件事，做好做透。**

**复杂流程怎么办**（这里有个具体的归属指引）：

```
⭐⭐⭐ 复杂流程用 ⭐ sessions_spawn ⭐ 编排，
⭐⭐⭐⭐ 而不是在 SKILL.md 里⭐ 堆分支逻辑
```

> ⭐⭐⭐⭐ **"粒度小的技能⭐ 组合起来 ⭐⭐⭐ 比一个万能技能⭐ 稳定 10 倍。"**

> ⭐⭐⭐ 这与我们已有的三条完全一致，但⭐ 补上了⭐ 此前缺失的因果：
> ```
> · scope-multiplication：失败模式是⭐ 笛卡尔积（为什么拆）
> · 双向无知：互相需要对方细节 = 其实是一个（边界在哪）
> · 重启测试：人从哪里重启（怎么拆）
> · ⭐⭐⭐⭐ 本份：⭐⭐⭐⭐ "它分不清边界" → ⭐ 模型会⭐ 跳过某一段
> ```
> ⭐⭐⭐⭐ 最后一条最具体：⭐ **一个技能管多件事的典型症状不是"都做得差"，
> 而是"⭐ 随机跳过其中某一步"**——因为分支逻辑没有强制力。

## 3. ⭐⭐⭐ 坑三：路径硬编码

**现场**：

```
写死了 /Users/clp/.openclaw/skills/xxx/scripts/run.sh
⭐⭐⭐ 换了台机器⭐ 直接报错
⭐⭐⭐⭐ 而且错误信息⭐ 只说 "command not found"
      ⭐⭐⭐ ⭐ 排查了 20 分钟才发现是路径问题
```

**原则**：

```
① ⭐⭐⭐ 所有路径用 ⭐ ~/<配置目录>/ ⭐ 或⭐ 环境变量
② ⭐⭐⭐⭐ ⭐ 在 SKILL.md ⭐ 开头⭐ 声明⭐ 工作目录约定
③ ⭐⭐⭐ ⭐ 依赖的外部工具⭐ 用字段声明（如 bins），⭐⭐⭐ 别让用户猜为什么跑不起来
```

> ⭐⭐⭐ 第 ② 条"⭐ 开头声明工作目录约定"很实用——
> 与 `argument-substitution.md` 的 `${CLAUDE_SKILL_DIR}` 是⭐ 同一问题的两个解法：
> ```
> 引用⭐ 技能自带的脚本 → ⭐⭐⭐ 用 ${CLAUDE_SKILL_DIR}（相对、可移植）
> 引用⭐ 外部路径       → ⭐⭐⭐ 开头声明约定 + 环境变量
> ```
> ⭐⭐⭐ 两者缺一不可：前者解决"技能被装到别处"，后者解决"换机器/换人"。

**第 ③ 条尤其值得记**：

> ⭐⭐⭐⭐ **"别让用户猜为什么跑不起来"**——
> 一个未声明的外部依赖，其⭐ 失败信息（command not found）
> ⭐⭐⭐ **完全不指向真正的原因（缺依赖）**。
>
> ⭐⭐⭐ 这与 `dependency-lockfile.md` 的 36.6% 隐藏依赖、
> `team-admission-criteria.md` 的"脚本必须支持 `--help` 并说明副作用"
> ⭐⭐⭐⭐ 是⭐ 同一条原则的第三个说法：
> **声明不是礼貌，是让失败可诊断。**

## 4. ⭐⭐ 一句总结

> ⭐⭐⭐⭐ **"技能开发的核心不是'写得全面'，是'写得够用'。
> ⭐⭐⭐ ⭐ 先跑通最小闭环，再迭代加功能。"**

> ⭐⭐⭐ 三条原则的共同点：**都是"少写"而不是"多写"**——
> ```
> 少写背景叙事   → 只留执行契约四要素
> 少管一件事     → 一技能一职责
> 少硬编码       → 路径与依赖都声明化
> ```
> ⭐⭐⭐ 与我们已有的"三过早"（过早编排 / 过早分目录 / 过早通用化）
> 合起来，是一组⭐⭐ **关于克制的完整清单**。
> **"最小可用"不是起步阶段的妥协，而是贯穿始终的原则——
> 因为每一项多加的东西都要在整个会话里被反复付费。**
