## 1. ⭐⭐⭐⭐⭐ 标题不只是导航，它是唯一的权重信号

标题有两个作用，第二个几乎没人管：

```
① 导航：让人找到要改的地方
② ⭐⭐⭐⭐⭐ 权重：告诉模型"这部分有多重要、能不能跳过"
```

> ⭐⭐⭐⭐⭐ **模型没有别的信号可用。它不知道作者心里哪条是红线——
> 它只能从"这条写在什么标题下"来推断。**

于是同一条约束，换个位置，命运完全不同：

```markdown
## 红线
- 不得写入生产库

## 提示
- 不得写入生产库
```

内容一字不差。⭐⭐⭐⭐ **第二份会被当成"建议"来执行，而且没人会发现。**

## 2. 五类降权标题

| 标题类型 | 典型词 | 模型读到的潜台词 |
|---|---|---|
| ⭐⭐⭐⭐⭐ 提醒类 | 注意 / 提示 / 说明 / 备注 / 补充 | "不是必须，知道一下就好" |
| ⭐⭐⭐⭐⭐ 可选类 | 可选 / 高级 / 进阶 / 高级用法 | "新手场景可以跳过" |
| ⭐⭐⭐⭐ 附录类 | 附录 / 背景 / 附 / FAQ | "正文之外，按需" |
| ⭐⭐⭐⭐ 示例类 | 示例 / 例子 / 样例 | "这是示范，不是约束" |
| ⭐⭐⭐ 历史类 | 变更记录 / 历史 / 旧版 | "已经过去了" |

第四类最容易被误伤：

> ⭐⭐⭐⭐ **作者把"格式示范"和"格式要求"放在同一个"## 示例"标题下，
> 于是要求被读成了示范。**

正确做法：示例标题只放示例，⭐⭐⭐ **要求必须在示例之外单独出现一次**
（"以下为格式要求：`…`；示例：`…`"），不能只在示例里体现。

第五类的机制也值得记：

> ⭐⭐⭐⭐ **"变更记录"里往往写着"自 v2 起不再支持 X"——
> 而这恰恰是当前最有效的一条约束，它却躺在"历史"标题下。**

## 3. ⭐⭐⭐⭐⭐ "注意事项"是垃圾场，而它恰恰是模型会读完的少数章节之一

这是本份最反直觉的一条。

写作时的真实心理：

```
"这条我不确定算不算重要，但又不想删"
→ 放进"## 注意事项"
```

于是"注意事项"的真实内容构成是：

```
✅ 真的重要的（不敢放进正文怕打断流程）
❌ 想删又舍不得的
❌ 只有一次出过问题的
❌ 跟主题有点关系但说不清的
```

> ⭐⭐⭐⭐⭐ **而模型对它的处理是：读完，并且全部按同一权重读。**

后果是双向的：

```
真红线被稀释（和噪声同权重 → 平均下来像建议）
噪声被升级（三条无关提示被当成三条约束 → 上下文被占、行为被干扰）
```

> ⭐⭐⭐⭐⭐ 这与"把不确定是否重要的内容写进技能"是同一个动作的两种代价：
> **你省下了一次判断，付出的是每次运行都在替你重新判断，且判断得不准。**

修法不是删掉这个章节，是**给它做分流**：

| 内容 | 该去哪 |
|---|---|
| ⭐ 违反会造成损失的 | `## 红线`（或 `## 禁止`） |
| 不满足就要停下的 | `## 前置条件` |
| 只在特定分支才成立的 | ⭐ 并进那个分支的正文里 |
| 说不清有没有用的 | ⭐⭐⭐⭐⭐ 删 |

最后一行最重要：**"说不清有没有用"意味着你在要求模型替你判断它有没有用。**

## 4. ⭐⭐⭐⭐⭐ "可选"标题下写着必读的约束

```markdown
## 可选步骤：发送通知

若发送，收件人必须是审批人本人，不得发给整个部门。
```

作者的意图：⭐ **"发送"这个动作是可选的。**
模型的读取：⭐⭐⭐⭐⭐ **整节都是可选的，包括那句"不得发给整个部门"。**

> ⭐⭐⭐⭐⭐ **"可选"修饰的是动作，不是该节里所有文字。
> 但标题的作用范围在模型眼里是整节。**

它的危险在于**只在特定时刻发作**：

```
模型没发通知 → 一切正常，这节确实不重要
⭐⭐⭐⭐⭐ 模型决定发通知 → 它已经跳过了这节 → 约束不存在
```

> ⭐⭐⭐⭐⭐ **于是这条缺陷只在"技能做得更多"的时候才出现，
> 而"做得更多"通常发生在更复杂的任务上——也就是最需要约束的时候。**

修法（两行，成本极低）：

```markdown
## 发送通知（可选动作）

⭐ 以下约束在"决定发送时"生效：
- 收件人必须是审批人本人
- 不得发给整个部门
```

⭐⭐⭐⭐ 关键不是加粗，是**把作用域显式写出来**（"在决定发送时生效"）——
否则模型仍然可以按标题把整节降权。

## 5. 标题与内容不匹配

三种常见错配，第二种最难自查：

| 标题说 | 里面实际是 | 后果 |
|---|---|---|
| `## 输出格式` | 还有一条红线 | ⭐ 红线只被当作格式要求 |
| ⭐⭐⭐⭐ `## 流程` | 混着验收标准 | ⭐⭐⭐⭐ 验收被当成流程的一步，做完了就算过了 |
| `## 示例` | 唯一的格式要求 | 要求被当示范 |

> ⭐⭐⭐⭐⭐ **第二种最贵**：验收标准藏在流程里，就变成了"流程的一个步骤"——
> 而步骤是可以被跳过的，且跳过它不影响产出任何东西。
> 这正是"没有后果的步骤 = 可选步骤"的结构版本。

判据一句话：**这节里每一条，都配得上这个标题吗？**
不配的，要么改标题，要么把它挪出去。

## 6. ⭐⭐⭐ 层级与加粗：不是标题就不带权重

```
## 红线            ← 二级标题：明确的章节
### 写入前          ← 三级：二级的下属
**重要：必须先备份** ← ⭐⭐⭐ 加粗：**不是标题**
```

> ⭐⭐⭐⭐ **加粗在模型眼里是"语气强调"，不是"结构声明"。**
> 它能让句子更醒目，但不能让内容变成一章。

于是常见错误是：

```markdown
## 流程
1. 备份
2. 修改
3. **⚠️ 注意：必须先确认环境为 staging，否则禁止执行**
```

⭐⭐⭐⭐ 那条警告写在步骤 3 里，它就**只在步骤 3 生效**——
而它本该是覆盖全流程的前置条件。

规则很省：

> ⭐⭐⭐⭐⭐ **覆盖范围超过一步的约束，不能写在步骤里，也不能靠加粗——
> 它必须有自己的标题。**

## 7. ⭐⭐⭐⭐⭐ 判据与改造

**主判据**（一条就够，成本十秒）：

> ⭐⭐⭐⭐⭐ **把标题遮住，只看这一条内容——你还看得出它是强制的吗？**

```
看得出（内容自带"必须/不得/否则"）→ 标题怎么写都不太影响
⭐⭐⭐⭐⭐ 看不出 → 它的权重完全由标题决定 → 危险
```

这与"禁令要带正面对应物"是同一思路：
⭐⭐⭐⭐ **不要把重要性寄托在排版上，寄托在句子本身。**

**次判据**（查降权）：

```bash
grep -nE "^#{2,3}.*(注意|提示|说明|备注|补充|可选|高级|进阶|附录|背景|FAQ|示例|历史|变更)" SKILL.md
```

命中后逐条问：**这节里有没有"违反会造成损失"的内容？** 有 → 搬走。

**改造顺序**（按性价比）：

```
① ⭐⭐⭐⭐⭐ 红线/禁止类内容，从任何降权标题下搬出来，单独成节
② ⭐⭐⭐⭐ "可选"节里补一句作用域声明
③ ⭐⭐⭐ 覆盖多步的约束从步骤里提出来
④ ⭐⭐⭐ "注意事项"里说不清用途的，删
⑤ ⭐⭐ 示例标题下补一次显式要求
```

## 8. 检查清单

- [ ] 没有任何"违反会造成损失"的约束写在 注意/提示/可选/高级/附录/示例/历史 标题下
- [ ] `## 红线`（或同等标题）存在，且位于正文前部
- [ ] 标题含"可选"的章节，都写明了约束的作用域（"在决定 X 时生效"）
- [ ] 覆盖多步的约束不写在单个步骤里，也不靠加粗
- [ ] `## 示例` 下只有示例，要求在其之外单独出现过一次
- [ ] 变更记录里的"不再支持 X"已搬进正文（不是只留在历史里）
- [ ] ⭐ 遮住标题后，每条红线仍看得出是强制的
- [ ] ⭐⭐⭐⭐⭐ "注意事项"里没有"说不清有没有用"的条目

## 一句话

> ⭐⭐⭐⭐⭐ **位置决定它有没有被看到，标题决定它被当成什么。
> 你把一条红线放进"## 注意事项"，就等于在内容没变的情况下，
> 把它从"禁止"降成了"建议"——而且没有任何报错。**
