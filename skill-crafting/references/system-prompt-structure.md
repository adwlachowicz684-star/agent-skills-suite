## 1. ⭐⭐⭐ 结构优于长度

> ⭐⭐⭐ **"最常见的错误，是试图⭐ 用一堵文字墙覆盖所有可能的场景。
> ⭐⭐⭐ ⭐ 模型对⭐ 结构化提示的响应⭐ 更好。"**

> ⭐⭐⭐⭐ 这句把"惜字如金"和"要写全面"之间的张力解开了：
> ⭐⭐⭐ **问题不在于长短，在于⭐ 有没有分节。**
> 一堵文字墙里的每一句都在互相竞争注意力；
> ⭐⭐⭐ 分成节之后，模型⭐ 知道当前该看哪一类。
>
> ⭐⭐ 与我们已有的 `token-bloat-audit.md` 不矛盾：
> 那份说的是⭐ **删掉不产生价值的内容**，
> ⭐⭐⭐ 这份说的是⭐ **留下来的内容要分节**。
> 先删，再分。

## 2. ⭐⭐⭐ 五个分节

| 节 | ⭐ 内容 | 示例 |
|---|---|---|
| ⭐ **角色** | 它是谁 | "You're a code reviewer specializing in Python" |
| ⭐⭐ **流程** | 按什么顺序检查什么 | "For each file, check for: unused imports, missing type hints, security issues, performance concerns" |
| ⭐⭐⭐ **输出** | 长什么样 | "Present findings as a numbered list with severity ratings" |
| ⭐⭐⭐ **约束** | 别做什么 | "Don't suggest stylistic changes unless they affect readability" |
| ⭐⭐ **示例** | 好输出长什么样 | — |

**为什么分节有效**（原文给了两个理由，第二个常被忽略）：

```
① ⭐⭐ 帮模型⭐ 理解什么重要、⭐ 每个处理阶段该关注什么
② ⭐⭐⭐ ⭐ 也让⭐ 提示更易被⭐ 人类审查、修改和维护
```

> ⭐⭐⭐ 第 ② 条与 `writing-style-rfc2119.md` 的"语义换行让 git diff 精确到行"
> ⭐⭐⭐ 是⭐ 同一条的第二个说法：**结构不只是给模型的，也是给维护者的。**
> 一份分节的技能，半年后你还能改得动；一堵文字墙你只能重写。

## 3. ⭐⭐⭐ 具体性：每一处模糊都是一次判断

```
❌ "Analyze the code"（⭐ 可以意味着任何事）
✅ "Check each function for missing error handling,
    identify any database queries that don't use parameterized inputs,
    and flag any hardcoded credentials"
```

> ⭐⭐⭐⭐ **"你提示里的⭐ 每一处模糊，⭐⭐⭐⭐ 都是⭐ 模型会做出判断的地方，
> ⭐⭐⭐⭐ 而⭐ 那些判断⭐ 未必符合你的预期。"**

> ⭐⭐⭐⭐ 这是"要具体"这条建议⭐ 见过最好的论证——
> 它不是说"具体更好"，而是⭐ **把模糊重新定义成了"授权模型替你决定"**。
>
> ⭐⭐⭐⭐ 推论：⭐ **你不写清楚的地方，就是你在授权模型自由发挥的地方。**
> 所以"省略"不是中性动作，⭐⭐ 它是一次⭐ 默认授权。
>
> ⭐⭐⭐ 与我们已有的 `skill-review-checklist-ten.md`、
> `judgment-branches-acceptance.md`（判断分支要写死）
> 同源，⭐ 但这里给出了⭐ 一个更强的因果表述。

## 4. ⭐⭐ 示例替代段落

```
⭐⭐ 不要⭐ 抽象描述你想要的格式 → ⭐⭐⭐ 直接展示一个好输出
⭐⭐ 不要⭐ 用文字解释边界情况   → ⭐⭐⭐ 给出它们该如何处理的示例
⭐⭐⭐ ⭐ 两三个精心挑选的示例 ⭐ 可以替代⭐ 数段指令
```

> ⭐⭐⭐ **"模型从⭐ 模式⭐ 中学习，比从⭐ 规则⭐ 中学习更有效。
> ⭐⭐⭐ ⭐ 一个展示棘手输入正确响应的示例，
> ⭐⭐⭐ ⭐ 教会模型处理类似输入，⭐ 而无须为每种情况都写规则。"**

> ⭐⭐⭐ 这与 `few-shot-examples.md`（3 个高质量 = 5 个普通）、
> `examples-three-branches.md`（Rationale 字段让示例产生泛化）
> ⭐⭐⭐ 是⭐ 同一条的第三个来源，
> ⭐⭐⭐ 且这里⭐ 点明了机制：**模式 > 规则**。
> ⭐⭐ 也因此解释了为什么 Rationale 字段有效——⭐ 它让"模式"可被迁移。

## 5. ⭐⭐⭐⭐ 边界：一条需要仲裁的张力

原文说：

> ⭐⭐ **"'不要'指令在⭐ 约束行为上⭐ 出奇地有效。"**
> ```
> "Don't suggest changes to the code architecture"
> "Don't include information that isn't directly supported by the data"
> "Don't apologize or use filler phrases"
> ```

⭐⭐⭐⭐ **这与我们已有的核心结论直接冲突**：

```
crafting 核心原则：
  ⭐⭐⭐ "禁令可能比不写还糟"——禁令说"不能做什么"，但没说应该做什么
  ⭐⭐⭐ 实测中⭐ 禁令组比配方组产生了更多不想要的内容，
        ⭐⭐⭐⭐ 甚至比⭐ 不写指导的对照组⭐ 更差
```

**仲裁（我认为两者都成立，差别在禁令是否自带替代方向）**：

```
❌ 裸禁令："不要猜测"                     → 反噬（没说做什么）
❌ 裸禁令："别改架构"                     → ⭐ 实测更差
✅ 有替代的禁令："别改架构；只报告 bug"     → 有效
✅ ⭐⭐⭐ 本份这三条其实⭐ 都自带隐含替代：
   "Don't suggest architecture changes"
     → 隐含"只做你要做的那件事（bug 识别）"
   "Don't include info not supported by data"
     → ⭐⭐⭐ 隐含"只写数据支持的"（有明确正面对应）
   "Don't apologize or use filler"
     → ⭐⭐⭐ 隐含"直接说结论"（有明确正面对应）
```

> ⭐⭐⭐⭐⭐ **判据（第三次出现，这次是第四个来源）：**
> ⭐⭐⭐⭐⭐ **禁令有没有⭐ 一个明确的正面对应物？**
> ⭐⭐⭐ 有 → 它是⭐ 有效的边界收紧
> ⭐⭐⭐ 没有 → 它是⭐⭐⭐⭐ 让模型"知道不能做 A，但不知道该做什么"的反噬源
>
> ⭐⭐⭐⭐ **"Don't include information that isn't directly supported by the data"
> 之所以有效，正因为它的正面形式（"只写有数据支持的"）是完全确定的。**
> 而"别猜测"的正面形式（？）没那么清楚，所以会反噬。
>
> ⭐⭐⭐ 实操结论：⭐⭐ **写禁令时，强制自己把正面形式也写出来**
> （哪怕只写半句："……；只报告 bug"）。

**另一条也值得记**：

> ⭐⭐⭐ **"没有边界，模型会以⭐ 你不想要的方式⭐ 去'帮忙'。"**
> ```
> 代码审查技能 → 你只要 bug 识别，它开始⭐ 提重构建议
> 数据分析技能 → 你只要描述统计，它开始⭐ 给推荐
> ```
> ⭐⭐⭐ 这精确描述了 `description-scope-shape.md` 里那个
> "typo 修复被加上五段无关架构反馈"的 scope creep。

## 6. ⭐⭐⭐ 版本历史防止转圈

```
⭐ 测试：用⭐ 多样化输入⭐ 暴露提示的不足
⭐⭐ 简单用例好但边界用例差？格式对短输入成立、对长输入就崩？
⭐⭐⭐ ⭐ 每次测试失败都是⭐ 关于"提示哪里需要改进"的⭐ 信息

⭐⭐⭐⭐ 保留⭐ 提示的版本历史，让你能⭐ 追踪⭐ 哪些改动改善了结果、
        ⭐⭐⭐⭐ ⭐ 哪些没有
⭐⭐⭐⭐⭐ 这避免了⭐⭐⭐ "转圈迭代"这个常见陷阱——
        ⭐⭐⭐⭐ 修好一个问题的改动，⭐ 又重新引入了另一个
```

> ⭐⭐⭐⭐ **"转圈迭代"（fix one issue, reintroduce another）是我们此前⭐ 完全没覆盖过的失败模式。**
>
> ⭐⭐⭐⭐ 它解释了为什么"改了很多次还是老样子"——
> 因为⭐ 每次改动都只针对⭐ 当下那一个失败，
> ⭐⭐⭐ 而⭐ 没有记录⭐ 上一次是因为什么才改成现在这样。
>
> ⭐⭐⭐⭐ 解法就是⭐ **版本历史 + 每次改动记下"为什么改"**：
> 与 `version-changelog-practice.md` 的
> "Changelog 随文件走，一个孤立拿到文件的人不需要 git 权限就能看见历史"
> ⭐⭐⭐⭐ 是⭐ 完全同一条的第二个来源——
> ⭐⭐⭐ 而且这里⭐ 给出了它的⭐ 具体收益：⭐⭐ **防止转圈**。
>
> ⭐⭐⭐ 也与 `skill-rot-rollback-discipline.md` 的"歧义时默认回滚"配套：
> **有历史才能回滚，能回滚才敢改。**

## 速查

```
□ ⭐⭐⭐⭐ 问题不在长短，在⭐ 有没有分节（一堵文字墙里每句都在竞争注意力）
   ⭐⭐ 先删无价值内容（token-bloat-audit），⭐⭐⭐ 再给剩下的分节
□ ⭐⭐⭐ 五节：角色 · 流程 · ⭐⭐⭐ 输出 · ⭐⭐⭐ 约束 · 示例
   ⭐⭐⭐ 结构不只给模型，⭐⭐⭐ 也给维护者（半年后还改得动）

□ ⭐⭐⭐⭐ 每一处模糊 = ⭐⭐⭐⭐ 一次⭐ 授权模型替你决定
   ⭐⭐⭐⭐ ⭐ 省略不是中性动作，是⭐ 默认授权
□ ⭐⭐⭐ 模型从⭐ 模式⭐ 学习 > 从⭐ 规则⭐ 学习（第三个来源）
   ⭐⭐⭐ 两三个好示例可以替代数段指令；⭐ 棘手输入的示例能泛化

□ ⭐⭐⭐⭐⭐ 禁令仲裁（第四个来源）：
   ⭐⭐⭐⭐⭐ ⭐ 判据 = ⭐⭐⭐ 禁令有没有⭐ 明确的正面对应物？
      有 → 有效收紧；没有 → ⭐⭐⭐⭐ 反噬（比不写更差）
   ⭐⭐⭐ 实操：⭐ 写禁令时强制把正面形式也写出来（"……；只报告 bug"）
   ⭐⭐⭐ 无边界 → 模型会以你不想要的方式去"帮忙"（scope creep）

□ ⭐⭐⭐⭐⭐ 版本历史防止⭐ 转圈迭代（修好一个又引入另一个）
   ⭐⭐⭐⭐ 有历史才能回滚，能回滚才敢改
```

**一句话**：

> ⭐⭐⭐⭐ **正文的问题不在长短而在有没有分节（分成角色/流程/输出/约束/示例五节），而"每一处模糊都是一次授权模型替你决定"意味着省略不是中性动作；
> 关于禁令的第四个来源给出的仲裁是：禁令有没有明确的正面对应物决定了它有效还是反噬——所以写禁令时要强制把正面形式也写出来。**
