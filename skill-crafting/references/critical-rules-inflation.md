# 红线膨胀：条数越多，每条越弱

> 前置：`skill-crafting/references/section-heading-weight.md`（标题是唯一的权重信号）
> 分工：那份讲**放在哪**（位置决定权重）；本份讲**标多少**（数量决定稀释）。
> 两者是同一个机制的两个维度：注意力预算。

---

## 1. ⭐⭐⭐⭐⭐ 一条会自己变弱的规则

```
v1: Critical Rules（3 条）
v2: Critical Rules（8 条）   ← 出了两次事故
v3: Critical Rules（20 条）  ← 又出了几次
```

每次事故都加一条，每次都觉得"更保险了"。而实际发生的是：

> ⭐⭐⭐⭐⭐ **`Critical` 这个标签的价值来自对比——它标记的是"这几条 vs 其余"。**
> 当它标记了 40% 的内容，标签就失去了区分力。

判据很直接：

> ⭐⭐⭐⭐⭐ **数一下：Critical Rules 占正文的比例。超过 10%，它就已经不是"红线"了，**
> **只是第二份正文。**

---

## 2. ⭐⭐⭐⭐⭐ 三个机制，第三个最贵

### ① 稀释：每条获得的注意力 ∝ 1/N

模型的注意力是有限预算。20 条红线里，每条平均分到的权重是 3 条时的 1/7。

### ② 冲突概率随 N² 增长

```
3 条  → 3 对
8 条  → 28 对
20 条 → 190 对
```

> ⭐⭐⭐⭐⭐ 而根据 `skill-precision/references/conflicting-instructions.md`，
> 模型遇到冲突不二选一，是**折中**——于是每条都被稀释成"部分执行"。

### ③ ⭐⭐⭐⭐⭐ 违反成本不可见

```
3 条时违反 1 条 → 立刻被发现
20 条时违反 1 条 → ⭐⭐⭐⭐⭐ 包括评审时也发现不了
```

> ⭐⭐⭐⭐⭐ **第三条才是真正的杀手**：不是模型不遵守，
> 是**没人有能力检查 20 条里有没有漏掉 1 条**——于是违反不产生后果，
> 于是"红线"退化成"建议"，而它仍然顶着红线的名字。

---

## 3. ⭐⭐⭐⭐⭐ 最常见的"修 bug"动作，本身在削弱防线

```
出事故 → 加一条红线 → 感觉更安全 → 红线变多 → 每条变弱 → 更容易出事故
```

> ⭐⭐⭐⭐⭐ **这是一个正反馈。修复动作在削弱防线，而它看起来完全像在加强防线。**

它与"禁令可能反噬"是同一族的问题，但机制不同：

```
禁令反噬：禁令没给正面对应物 → 模型不知道该做什么
红线膨胀：禁令太多 → 模型不知道哪条优先
```

---

## 4. ⭐⭐⭐⭐⭐ 判据：违反它，用户会发现吗？

这是区分"红线"与"偏好"的唯一可靠方法：

| 违反后 | 归类 |
|---|---|
| ⭐⭐⭐⭐⭐ 用户立刻发现（数据错、文件被改、钱被花） | 红线 |
| ⭐⭐⭐⭐⭐ 排查时才能发现（静默、延迟、只在某类输入上） | 红线 |
| 只有作者会发现（格式、措辞、顺序） | ⭐⭐⭐⭐⭐ 偏好，不是红线 |

> ⭐⭐⭐⭐⭐ 第三类占多数人 Critical Rules 的一半以上。
> 它们被写成红线，是因为作者很在意——**但"作者在意"不是权重信号，模型读不到。**

---

## 5. ⭐⭐⭐⭐⭐ 排序法：按"违反后的排查成本"取前 5

不是按重要性（重要性是主观的、无法排序），按**排查成本**（可估计、可比较）：

```
估算：这条被违反了，定位要多久？

几分钟   → 不是红线（能发现就能修）
半天     → ⭐⭐⭐⭐ 红线候选
⭐⭐⭐⭐⭐ 几天 / 无法定位 → 必选红线
```

> ⭐⭐⭐⭐⭐ "无法定位"那一类必须进红线——因为违反后连错误都不会被注意到。
> 典型：静默编造、partial 当 ok、旧数据当新数据。

取前 5 条（**上限 5，不是建议 5**）：

```
理由：5 条是"能被逐条检查"的上限。
超过 5 条，评审者开始跳读——⭐⭐⭐⭐⭐ 而跳读意味着这个清单在评审环节已经失效。
```

---

## 6. 剩下 15 条怎么办：不是删，是归位

删掉会丢失信息。正确做法是**移到它们该在的位置**——就近原则：

| 内容 | ⭐ 该在哪 |
|---|---|
| 触发相关的禁令 | description / 触发条件章节 |
| 某个步骤的禁令 | ⭐⭐⭐⭐⭐ 紧跟该步骤（不要集中） |
| 输出相关的禁令 | 输出契约章节 |
| 反复被违反的 | ⭐⭐⭐⭐⭐ 改成 hook（机器保证，不占注意力） |
| 只在某类输入上成立的 | 该分支里，不是全局 |

> ⭐⭐⭐⭐⭐ 集中存放是最自然的写法，也是最错的——
> 因为集中的代价是"所有红线脱离了它们生效的上下文"。

第二条尤其反直觉：**"某个步骤的禁令"放进 Critical Rules 后，
模型会把它当成全局约束**——于是它在不该生效的地方也生效了。

---

## 7. ⭐⭐⭐⭐⭐ 事故之后的三条路（按优先级）

```
① ⭐⭐⭐⭐⭐ 能用机器检查吗？→ 改成 hook / 校验器（零注意力成本，且必然执行）
② 是某个具体场景的坑吗？  → 写进 Gotchas（带场景，可被检索到）
③ 两者都不是            → 才考虑加红线，且必须同时移除一条旧的
```

> ⭐⭐⭐⭐⭐ **第三条里的"必须同时移除一条"是本份最该被执行的规则。**
> 没有它，清单只增不减，而增长本身就是退化。

这与"反复被违反的书面规则应编码成校验器"是同一结论——
本份补的是：**在编码成校验器之前，它先经历了"被加成红线"这一步，而那一步是有害的。**

---

## 8. ⭐⭐⭐⭐⭐ 自检清单

```
□ Critical Rules 条数 ≤ 5
□ ⭐⭐⭐⭐⭐ 每条都能回答"违反了用户/排查会发现吗"——不能就不是红线
□ 每条都按排查成本排序过（不是按写作顺序）
□ ⭐⭐⭐⭐⭐ 最近一次加红线时，移除了哪一条？（答不出 = 清单在膨胀）
□ 有没有"某步骤的禁令"被错误地全局化了？
□ 有没有能用机器检查却写成了红线的？
□ ⭐⭐⭐⭐⭐ 评审者会逐条读完吗？——不会，就是太多了
```

## 9. 何时不用

```
Do NOT 用于：
❌ 红线放在哪个标题下 —— `skill-crafting/references/section-heading-weight.md`
❌ 两条指令冲突时模型会折中 —— `skill-precision/references/conflicting-instructions.md`
❌ 禁令要不要配正面对应物 —— `skill-crafting/references/imperative-style.md`
❌ ⭐⭐⭐⭐⭐ 红线只有 2–3 条 —— 不膨胀，本份不适用；该检查的是"位置"（见上）
```
