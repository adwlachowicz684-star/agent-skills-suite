# 术语一致性：一个词两个意思就够糟了

> ⭐ **同一个概念在技能里有两个名字时，
> 模型会认为它们是两个概念。**

## 为什么要紧

模型是**按字面关联**来理解的：

```
技能里同时出现 "工单" 和 "问题单"
→ ⭐ 模型不知道它们是一回事
→ 它可能只处理其中一半的情况
```

而且这个错误**静默**——
不会报错，只是覆盖不全。

## 三类不一致

**① 同一概念两个名字**

```
❌ "PR" / "拉取请求" / "合并请求" 混用
✅ 全文统一用 "PR"
```

**② 同一名字两个概念**

```
❌ "环境" 有时指 dev/staging/prod，有时指环境变量
✅ 分别叫 "部署环境" 与 "环境变量"
```

> ⭐ 第二条更危险——
> 它会让模型在错误的上下文里应用正确的规则。

**③ 与代码库/领域既有术语冲突**

```
❌ 技能里叫 "用户"，代码里叫 "account"
✅ ⭐ 跟随代码库的叫法
```

## 怎么建立术语表

短技能不需要；**超过 200 行或有多个 references 时应该有一份**：

```markdown
## Terminology

| 术语 | 含义 | 不要说成 |
|---|---|---|
| PR | pull request | 合并请求 / 拉取请求 |
| 部署环境 | dev / staging / prod | 环境 |
| 环境变量 | env var | 环境 |
| 产物 | 技能生成的输出文件 | 结果 / 输出文件 |
```

三列里**第三列最关键**：
它明确禁止了哪些易混说法。

放置位置：

```
□ 短技能 → 正文里的一个小节
□ 长技能 → ⭐ references/terminology.md（一层深）
□ 跨多个技能 → CLAUDE.md（见 instruction-layering.md）
```

## 与既有术语冲突时

> ⭐ **优先跟随代码库/团队的既有叫法，不要用你更喜欢的。**

理由：

```
模型会同时读到 CLAUDE.md 和技能
→ 两个术语表冲突时，它无法确定哪个优先
→ ⭐ 结果是不确定的行为
```

所以：**技能是既有约定的延伸，不是重新定义。**

## 机械检查

```bash
# 找出同一概念的不同叫法
for term in 工单 问题单 单据; do
  echo -n "$term: "; grep -ro "$term" skill-name/ | wc -l
done
```

> ⭐ 更实用的做法：
> **先定术语表，再写脚本检查"禁止说法"是否出现。**

这比事后人工通读可靠得多——
而且它能被放进 CI（见 `ci-cd-integration.md`）。

## 自查

```
[ ] ⭐ 全文对同一概念只用了一个词？
[ ] 有没有"一个词指两件事"的情况？
[ ] ⭐ 术语与代码库/团队的既有叫法一致？
[ ] 术语表有"不要说成"这一列吗？
[ ] ⭐ 术语表放在了正确的层（正文 / references / CLAUDE.md）？
[ ] 有没有用脚本检查禁止说法？
```

## 一条延伸

术语一致性还影响**触发**：

```
description 里写 "工单"
用户说 "问题单"
→ ⭐ 不匹配
```

所以术语不仅要一致，还要**和用户的词汇一致**
（见 `description-patterns.md`）。

> ⭐ 最理想的状态是：
> **技能内部用一个词，但 description 里把所有用户会说的说法都写上。**

内部一致保证模型理解正确，
外部多样保证路由命中——两者不矛盾，因为作用在不同位置。
