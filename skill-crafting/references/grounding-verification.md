# 落地与验证

> ⭐ **这是全篇最该读的一章。**
>
> 回归研究发现：现有技能**过度强调流程指导**（而这恰恰是最少导致失败的阶段），

## 先分清楚：落地 vs 验证

| | 含义 | 例子 |
|---|---|---|
| **验证（Verification）** | 检查 agent 的**输出**是否正确 | 跑测试套件 |
| **落地（Grounding）** | 把输出**锚定到现实**——对照真实系统和数据检查 | 看真实测试结果、调真实 API、查真实数据库 |

**四种验证策略**：

| 策略 | 做法 |
|---|---|
| **执行并验证** | 代码最好的验证就是执行：改完 → 跑测试 → pass 才算验证 |
| **事实核查** | 声称"这个 endpoint 返回用户数据" → 查文档 + 真调一次 + 比对格式 |
| **自审** | agent 复查自己的输出（弱，见下） |
| **多 agent 交叉验** | A 写、B 审安全、C 审性能、D 测——全部通过才提交 |

**四种落地技术**：函数调用结果 · 外部数据源 · API 验证 · **人工批准**（关键操作）。

## 证据先于声明

> **没有在本会话中跑过的验证 = 不准声称"完成了"。**
>
> 未运行验证就声称成功，是**不诚实**，不是高效。

**五步门**：

```
1. 识别：哪条命令能证明这个说法？
2. 运行：完整执行它（全新的、完整的）
3. 读取：完整输出，检查退出码，统计失败数
4. 验证：输出真的支持这个说法吗？
5. 只有这时：才做出声称
```

**跳过任何一步 = 说谎，不是验证。**

### 禁用措辞

出现这些词说明**还没验证**：

```
❌ "应该可以了"  "应该修好了"
❌ "我很有信心没问题"
❌ "看起来没问题"
❌ "太棒了！完成了！"（在跑验证之前）
❌ "测试过了"（没贴输出）
```

### 红绿验证循环（回归测试）

> 声称"我写了回归测试"——**不算**。

```
✅ 写测试 → 运行(通过) → 回滚修复 → 运行(必须失败) → 恢复 → 运行(通过)
❌ "我写了回归测试"（没有红绿验证）
```

> 这一步的意义：**证明这个测试真的覆盖了新增行为**。
> 否则 agent 很容易先写完代码，再补一份**天然会通过**的测试。

## 建造者不能当审计员

> ⭐ **别让 AI 给自己的作业打分。**

agent 默认行为就是这种"幻觉式合规"（hallucinated compliance）：

```
你写了严格的 AGENTS.md
agent 读完，做任务，报告："完成。我遵守了所有规则。"
你信了。
—— 它没检查。它只是假设。
```

**根因**：做活的那个 agent **锚定在"它本来打算做什么"上，
而不是"它实际做了什么"**。

### 解法：派一个新的只读子代理

```markdown
## 完成后
主任务结束后，派一个**全新子代理**：
- 传给它：所有被修改文件的路径 + 完整强制规则清单
- 要求：重新读文件，逐条对照规则检查
- 输出：清单表格——每条规则一行、PASS/FAIL、**该条的确切证据**
- 任何 FAIL 就阻断完成；先修再声明
- 子代理**只给只读工具**（Read / Grep / Glob），不许改任何东西
```

**四个好处**：

| 好处 | 说明 |
|---|---|
| **独立验证** | 新子代理没有"做过这些改动"的记忆，审计无偏 |
| **强制真读** | 必须打开实际文件搜违规，不能靠记忆 |
| **杜绝幻觉合规** | **不给确切证据就不能标 PASS** |
| **可重复** | 每次任务后同一套检查，不用额外提示 |

> **上下文隔离是关键**：建者和审计员不能共用同一个上下文窗口
> ——同一个窗口既装着任务又装着合规报告，那它就不是真在审计自己。

**复杂度越高，风险越大**：三步的任务容易自检；
20 条规则 + 几十个文件改动就不可能了。

## 三种验证回路

| 模式 | 谁验 | 成本 | 适用 |
|---|---|---|---|
| **① Self-Verifier** | 同一 agent 同会话自验 | 低（共享上下文） | 轻量关卡：命名、注释、明显笔误 |
| **② Critic-Approver** | **另一个 agent** 判 | 中 | 需要真实判断时 |
| **③ Test-Driven** | **机器**判（测试/脚本） | 低 | 有明确对错时 |

> ⚠️ **Self-Verifier 的已知弱点**：对自己宽容。
> 实测**约 20% 声称 `compiles: true` 的输出其实编译不过**。
> **不要把它当正确性的最终关卡。**

**Critic 的提示词要把它塑造成挑剔的 QA**——
同样的模型，让它"写一个好函数"和"找出这个函数里所有 bug"，
**进入的是两种完全不同的模式**。这正是 reflection 起作用的机制。

### Reflection 的适用范围

| 适合 | 不适合 |
|---|---|
| 代码生成（能跑测试） | 快速对话回复 |
| 研究总结（有来源可核） | 单事实查询 |
| 合规草稿（有清单当 rubric） | 延迟敏感交互 |
| 多步分析（早期错误会累积） | 创作（迭代会磨掉独特声音） |

**⚠️ 两个约束**：

1. **自批判有个陷阱**——天真的自批判会掉进"连贯性陷阱"，
   只是让自己的输出更连贯，而不是更正确。
   **有效的批判必须 grounded**：靠测试、执行、检索，或独立的 critic。
2. **收益集中在第 1–2 轮**——**要设迭代上限**。

## 分层验证：什么够、什么不够

> 这表可直接抄进技能的验收部分。

| 声称 | 需要的证据 | **不够的** |
|---|---|---|
| 测试通过 | 测试命令输出：**0 failures** | 之前跑过 · "应该能过" |
| Lint 干净 | Linter 输出：**0 errors** | 部分检查 · 推测 |
| 构建成功 | 构建命令：**exit 0** | Lint 通过 · 日志看着正常 |
| **Bug 修复** | **复现原始症状的测试通过** | 代码改了 · 假定修好了 |
| 回归正常 | 红绿循环验证过 | 测试通过了一次 |
| Agent 完成 | **VCS diff 显示变更** | agent 报告"success" |
| 需求满足 | **逐项检查清单** | 测试通过 · 阶段完成 |

> ⭐ **"Bug 修复"那一行最容易被糊弄**：
> "测试过了"不等于**这个症状真的没了**——
> 必须**针对原始症状验一遍**，并给**改前/改后对比数据**。

## 计划-验证-执行

对**批量或破坏性**操作，让 agent 先产出结构化中间计划，
**对照真相源验证计划**，然后才执行：

```markdown
1. 抽取表单字段 → form_fields.json
2. 创建 field_values.json（字段名 → 值）
3. **验证**：字段名存在吗？类型兼容吗？必填没漏吗？
4. 失败则修订 field_values.json，重新验证
5. 只有验证通过才填表
```

> **关键在第 3 步**：一个把计划对着真相源检查的脚本。
> 好的错误信息能让它自我纠正：
> `Field 'signature_date' not found — available: customer_name, order_total`

**参考文档也能当"验证器"**——指示 agent 定稿前对照参考文档检查自己的工作。

## 把检查清单放进技能

多步工作流用显式清单帮 agent 跟踪进度、避免跳步，
尤其当步骤间有依赖或验证门时：

```markdown
Progress:
- [ ] Step 1: 分析表单    (run `scripts/analyze_form.py`)
- [ ] Step 2: 创建字段映射 (edit `fields.json`)
- [ ] Step 3: 验证映射    (run `scripts/validate_fields.py`)
- [ ] Step 4: 填充表单    (run `scripts/fill_form.py`)
- [ ] Step 5: 验证输出    (run `scripts/verify_output.py`)
```

### 何时该把逻辑固化成脚本

> **观察 agent 的执行轨迹**：如果你发现它
> **每次运行都在独立地重新发明同一段逻辑**
> ——画图、解析某个格式、校验输出——
> 那就是信号：**把这段逻辑写成测试过的脚本，放进 `scripts/`。**

### ⚠️ 别过度

> 上一章说过：**过度验证是最大的单一成本源（67/182 退化）**。

```
□ 校验分"必做"和"按需"
□ 写"若改动涉及核心逻辑则跑完整套件；否则只跑相关测试"
□ 小任务能跳过部分仪式
□ 迭代设上限（收益集中在前 1–2 轮）
```

## 自查

```
□ 技能里是否有"验证"章节，且指明了具体命令？
□ 是否明确了"什么证据够、什么不够"？
□ 是否禁止了"应该/看起来/我很有信心"这类措辞？
□ 是否有红绿验证循环（证明测试真的覆盖）？
□ 高风险技能是否要求派只读子代理做独立审计？
□ 是否要求给"改前/改后"对比数据？
□ 是否区分了必做校验和按需校验（防过度验证）？
□ 迭代是否设了上限？
□ 验证是否 grounded（真实执行/检索/独立 critic），而非纯自批判？
```
