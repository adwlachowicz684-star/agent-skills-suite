## 1. 不必一步到位

> ⭐ **你的第一个技能可以只有 10 行 Markdown。**
> **你不需要脚本、assets 或复杂流程就能获得价值。**

一个"跑测试"或"部署到 staging"的技能，
只要有 5 个清晰的步骤，**就能给团队省下数小时**。

---

## 2. 最小可行形态

```markdown
---
name: weekly-report
description: 专门用于生成符合公司规范的周报、月报
---

## 执行流程
1. 拉取本周 commit 记录
2. 归类为核心产出 / 数据亮点 / 问题与风险 / 下周规划
3. 按模板排版输出

## 注意事项
- 严禁编造数据
- 不用第一人称"我"，改用"项目组"
```

> 就这样。不需要 references/、scripts/、assets/。

## 3. 四条黄金法则

### ① ⭐ 明确触发边界

```
❌ description: "处理各种文档"      —— 太宽泛
✅ description: "专门用于生成符合公司规范的周报、月报"
```

### ② 结构化思维（SOP > Prompt）

```
❌ "请写好一点"
✅ ## 执行流程 → 1、2、3 步；异常（如缺数据）怎么处理
```

> ⭐ **像教新员工一样写**：第一步做什么、第二步做什么、遇到异常怎么办。

### ③ 资源解耦

```
❌ 几千字的模板或规范全塞进 SKILL.md
✅ 模板放 assets/、规范放 references/
```

> 好处：SKILL.md 保持轻量，**只有在真正需要时 AI 才去读那些大文件**，
> 省 token、提高响应速度。

### ④ ⭐ 防御性指令（Guardrails）

```
- 严禁编造数据
- 不要使用第一人称"我"，改用"项目组"
```

> ⭐ 这能大幅减少幻觉和错误。

⚠️ 但注意 `guidance-forms.md` 的实测：
**禁令在正文里可能反噬**——
所以禁令要**配上明确的替代**（这里"改用项目组"就是替代），
而不能只说"不要"。

## 4. 有需要再加脚本

想更强大就加 `scripts/`：

```
场景：自动从 Git 仓库拉取本周的 Commit 记录作为周报素材
文件：scripts/fetch_git_log.sh
```

> ⭐ 顺序是**先跑通纯指令版，再按需加脚本**——
> 与 `catalog-shape.md` 的"渐进复杂度三版本"一致。
