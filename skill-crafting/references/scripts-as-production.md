## 1. 核心分工

```
脚本  → 产生事实与结构
模型  → 产生语言与选择
人类  → 在几个闸门批准
```

> ⭐ **模型只在真正需要判断的地方介入。**

反例：让语言模型去做数据整形——
**又慢、又不稳定（每次跑不一样）、又烧 token、还容易幻觉**。

## 2. 一个真实流水线

文档 PR 生成器要做大量机械工作：

```
拉 PR 和 diff
沿链接 issue 向上追到父 epic、向下追到子 issue
去重
分类：这个特性是否需要 release note
找候选文档路径与相邻页面
```

> ⭐ **这些没有一项是判断——全是数据整形。**

所以每一步都是一个小 Python 脚本（**仅用标准库，运行时不 pip install**），
契约稳定：**从 CLI flags 读输入，往 stdout 吐 JSON**。

```bash
PYTHONPATH="${CLAUDE_SKILL_DIR}" python3 -m scripts.fetch_pr --pr <n> > /tmp/bundle.json
```

SKILL.md 像 Unix 管道一样把它们串起来。

**整条流水线里只有一个步骤标记为"模型步骤"：Generate。**

> 到这一步，模型读脚本产出的 JSON，
> 再加几篇相邻页面学语气，然后写真正的文档正文。
>
> ⭐ **边界很干净**：分类脚本决定需不需要 release note 及什么形状，
> 但**模型来写那条 entry**。

## 3. ⭐ JSON over stdout 契约

一个很值得抄的设计，附带三个收益：

```
① ⭐ 每个阶段都能独立运行
② ⭐ 每个阶段都能单元测试
③ ⭐ 整条流水线可以用冻结的 fixture 跑通（无需网络）
```

> 这个技能自带 unittest 套件 + 冻结的 `gh` 输出 fixture，
> 所以**整条管线可以在没有网络的情况下被完整演练**。

这与 `test-pyramid.md` 第 1 层"确定性检查不用 LLM"完全同构——
**把可测性当作设计目标，而不是事后补测试。**

## 4. 两条纪律

```
⭐ 脚本是生产代码（skill scripts are production code）
   ——按生产标准写：可读、有注释、错误处理、可测试

⭐ 发布前移除调试代码与冗长日志
```

## 5. ⭐ 两种极端都是对的

同一个作者的两个技能，做法完全相反，但都成立：

| 技能 | 形态 |
|---|---|
| 文档 PR 生成器 | ⭐ 一整条 Python 脚本流水线 |
| `agent-session-resume` | ⭐ **纯指令，零运行时代码** |

> ⭐ **反差本身说明了关键**：
> **形态应由任务性质决定，不是由"好技能应该长什么样"决定。**

判据回到 `skill-structuring` 的 `references-vs-assets.md` 那条：
这段是需要被**理解**、被**使用**、还是需要被**执行**？

## 速查

| 任务性质 | 形态 |
|---|---|
| 数据整形、机械重复 | ⭐ 脚本（确定性） |
| 需要判断、写作、选择 | 模型 |
| 纯流程指引、无副作用 | 纯指令技能也可以 |
| 脚本间通信 | ⭐ CLI flags 进 / JSON 出 |
| 测试 | ⭐ 冻结 fixture，无网络可跑 |
