# 指导的形态要匹配失败的形态

> **反直觉结论**：在 Superpowers 的措辞对照测试中，**禁令组比配方组产生了更多不想要的内容**
> （分布完全分离），甚至比**完全不写指导的对照组**还有变差的趋势。
>
> 限定条件：这是在特定场景（dispatch-prompt guidance + 让 prompt 自包含的竞争性激励）下的测试，
> 不是普适定律。**但结论是：永远不要默认伸手拿禁令。**

## 四类失败 → 四种形态

**在写指导之前，先分类基线失败（baseline failure）的类型。**
因为能防住一种失败的写法，在另一种失败上会**可测量地反噬**。

| 基线失败类型 | ✅ 正确形态 | ❌ 错误形态（也是多数人的默认选择） |
|---|---|---|
| **压力下违反规则**（明知故犯） | **禁令 + 合理化表 + 红旗列表** | 软指导（prefer、consider） |
| **遵守了，但输出形状不对**（臃肿 prompt、埋没结论、复述 spec） | **正面配方**：说明输出是什么，按顺序列出组成部分 | **禁令清单**（don't restate、never narrate） |
| **漏掉必需元素** | **结构性**：模板里的 REQUIRED 字段或槽位 | 模板附近的散文式提醒 |
| **行为应依条件而定** | **基于可观察谓词的条件句**（if the brief exists, reference it） | 无条件规则 + 例外条款 |

**关键在"错误形态"那一列**：每一行的错误形态，恰好是很多人写规则时的**默认选择**。

> 禁令只在**明知故犯**那一行是正确的选择。

## 为什么禁令会反噬

> **配方不留谈判空间——输出要么符合声明的形状，要么不符合。**
> 而禁令（`don't X`）给了 agent 在竞争性激励下**谈判的余地**。

"谈判"不是拟人化。它指：当 agent 同时面对多个目标时（比如"让 prompt 自包含"和"不要复述 spec"），
禁令是一个**负面约束**——它说不能做什么，但**没说应该做什么**。
于是 agent 自己决定怎么平衡这两个目标，而这个平衡往往不是你要的。

**配方相反**：它是**正面契约**——输出必须包含这几个部分、按这个顺序。agent 没有自由发挥的空间，只能照着填。

## 配方长什么样

假设你想让评审报告结构清晰，不要写成散文。

**❌ 禁令形态**：

```
不要写成长篇大论。
不要复述 spec。
不要在开头铺垫太多。
```

——给了 agent 一堆"不要"，但**没说报告应该长什么样**。

**✅ 配方形态**（真实模板）：

```markdown
## Output Format

### Spec Compliance
- ✅ Spec compliant | ❌ Issues found: [what's missing/extra/misunderstood, with file:line references]
- ⚠️ Cannot verify from diff: [...]

### Strengths
[What's well done? Be specific.]

### Issues
#### Critical (Must Fix)
#### Important (Should Fix)
#### Minor (Nice to Have)

### Assessment
**Task quality:** [Approved | Needs fixes]
**Reasoning:** [1-2 sentence technical assessment]
```

## 两条铁律

**① 不要加细微差别条款（nuance clause）**

`Don't X unless it matters` 这类写法**会重新打开谈判空间**。
给一个有效的配方加一个"除非"，在同样的测试里让它**从一致退化到嘈杂**。

**② 例外条款无法限定作用域（exemption clauses don't scope）**

"这条限制不适用于代码块"这种话，**实际上仍然会抑制代码块**。

> 如果输出的一部分必须豁免，**重新组织结构，让规则够不到它**。

**两条的本质相同**：一旦你写了规则，agent 就会**按字面执行，包括你写的例外**——例外本身也是一种干扰。

## SDO 陷阱

> **SDO（Skill Discovery Optimization）陷阱**：当 description 写了**工作流摘要**时，
> agent 可能**跟着 description 做，跳过技能正文**。

description 里如果已经包含"怎么做"，agent 就没有动机去读正文里的详细流程。

**检测**：description 里是否出现"第一步""然后""接着""步骤 1"这类流程词？

```yaml
# ❌ 摘要式——模型照摘要执行，不加载正文
description: 用于分析 CSV。第一步读取文件，第二步计算统计量，第三步生成图表。

# ✅ 路由式——只说何时用，不说怎么做
description: 用于分析 CSV 数据并生成统计摘要与可视化图表。
  只要用户提到销售趋势、数据分布、环比增长，就使用本 skill。
  Do NOT use for 数据库 ETL 或 Excel 格式编辑。
```

## 怎么用 micro-test 选形态

**不要靠直觉。**

1. 写一个最小场景，准备 3 个版本：**禁令版 / 配方版 / 无指导对照组**
2. 每个版本跑 3–5 次（模型非确定性）
3. 比较**不想要内容的出现率**
4. 选赢的那个——**别假设禁令有效**

> 源码原话：**micro-test 你自己的场景，别假设，但永远不要默认伸手拿禁令。**

## 对本技能包自检的影响

这条结论**直接约束本技能包自己的写法**。检查你自己写的技能：

| 你写的这条规则 | 防的是哪种失败 | 该用什么形态 |
|---|---|---|
| "不要在 SKILL.md 里塞大段代码" | 输出形状不对 | ❌ 应改成配方：给出目录结构模板 |
| "必须先跑 RED 阶段" | 明知故犯（赶工） | ✅ 禁令 + 借口反驳表，正确 |
| "description 必须含 Do NOT" | 漏掉必需元素 | ⚠️ 更适合做成模板里的 REQUIRED 槽位 |
| "如无 references 则跳过本步" | 依条件而定 | ✅ 条件句，但要用**可观察谓词**（"如果目录存在"而非"如有需要"） |

**一条自检问句**：

> 我写的这条规则，防的是**明知故犯**，还是**形状不对**？

防明知故犯 → 禁令 + 反驳表。
防形状不对 → 给模板，让输出**必须填满槽位**。

## 速查

```
失败：压力下违反规则        → 禁令 + 合理化表 + 红旗列表
失败：输出形状不对          → 正面配方（输出模板 + 顺序）
失败：漏掉必需元素          → 模板里的 REQUIRED 槽位
失败：行为依条件而定        → if <可观察谓词> then ...

禁忌：
❌ 给配方加"除非"（重新打开谈判空间）
❌ 写"本条不适用于 X"（例外无法限定作用域）
❌ description 里写工作流摘要（SDO 陷阱）
❌ 默认伸手拿禁令
```
