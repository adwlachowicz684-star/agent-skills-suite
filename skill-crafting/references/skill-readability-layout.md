## 1. ⭐⭐⭐⭐⭐ 两类读者，两套需求

| | ⭐ 模型 | ⭐⭐⭐⭐ 下一个改它的人 |
|---|---|---|
| 读法 | 从头到尾（但只看开头 5000 和结尾） | ⭐ 扫描：找要改的那一处 |
| 需要 | 无歧义、无冗余 | ⭐⭐⭐⭐ **定位快、能看懂上下文** |
| 伤害它的 | 模糊词、干扰、矛盾 | ⭐⭐⭐⭐⭐ **一大段没有小标题的文字** |

> ⭐⭐⭐⭐⭐ **冲突点只有一个：冗余。**
> 模型怕冗余（消耗 token、引入干扰），
> ⭐⭐⭐ 而人需要一定冗余（标题、目录、说明）来定位。

仲裁原则：

> ⭐⭐⭐⭐⭐ **结构性冗余（标题、目录、分隔）保留，解释性冗余（同义复述）删除。**

```
✅ 保留：## 输出格式 / 目录 / 表头
❌ 删除："请注意，这一点非常重要，务必牢记……"
```

## 2. ⭐⭐⭐⭐ 扫描性：让人 10 秒找到要改的地方

三条硬规则：

**① ⭐⭐⭐⭐⭐ 每 30 行一个小标题**

```
❌ 80 行连续正文，中间没有任何标记
✅ 每 20–40 行一个 `##` 或 `###`
```

> ⭐⭐⭐⭐⭐ 好处是双份的：人能扫到，⭐⭐⭐ 模型也更容易定位——
> 因为模型引用常写"见输出格式那一节"。

**② ⭐⭐⭐⭐ 用一致的层级表达一致的东西**

```
❌ 有时用 ## 步骤，有时用粗体 **步骤**，有时用编号
✅ 全库统一：## 是什么 / ## 怎么做 / ## 输出 / ## 红线
```

> ⭐⭐⭐⭐ 一致性 > 形态（命名约定那条原则的排版版）。

**③ ⭐⭐⭐⭐ 目录只在长文件里加**

```
<100 行：不要目录（占空间、模型会因为它而以为内容更多）
⭐ >100 行：⭐⭐⭐⭐ 必须加——因为模型会用 head -100 预览
```

> ⭐⭐⭐⭐⭐ 后者是关键：目录的作用是⭐⭐⭐⭐ **在被截断时仍能指路**。
> 这也是 `skill-structuring/references/reference-file-practices.md` 那条规则的真实机制。

## 3. ⭐⭐⭐⭐⭐ 可 diff 性：让改动精确到行

> ⭐⭐⭐⭐⭐ **git 历史是定位回归的第一工具。**
> 而它好不好用，取决于排版的粒度。

**① ⭐⭐⭐⭐⭐ 一个从句一行（语义换行）**

```
❌ 一段话写成一整行 → 改一个词，diff 显示整段变了
✅ 一句一行          → diff 精确到那一行
```

**② ⭐⭐⭐⭐ 列表项不合并**

```
❌ "支持 pdf、docx、xlsx、pptx 和 csv"
✅ 五项各占一行
```

> ⭐⭐⭐⭐ 除了可 diff，还有第二个好处：
> ⭐⭐⭐ **增删一项不会引起句子结构变化**（"和"的位置、"、"的处理），
> 于是不会出现那种"只是加了一项，整句重写"的噪音 diff。

**③ ⭐⭐⭐⭐⭐ 表格慎用**

```
表格改一个单元格 → ⭐ 整行 diff，且对齐空格变化会污染 diff
```

> ⭐⭐⭐⭐ 但表格在**横向比较**上不可替代——
> 仲裁见 §5。折中：**表格里的单元格内容尽量短**。

**④ ⭐⭐⭐ 版本号和日期不要写在多处**

```
❌ 标题里 1.2.0，正文里 v1.2.0，footer 里 2024-01
✅ ⭐⭐⭐ 只在一处（frontmatter 或 Changelog）
```

> ⭐⭐⭐⭐ 多处必漏（这是 `skill-versioning/references/version-changelog-practice.md` 里
> "文件写 1.2.0 但 tag 是 v1.1.0"那个错误的排版版，建议加 pre-commit 检查）。

## 4. ⭐⭐⭐⭐ 位置纪律

已有结论：**开头是黄金位置，结尾次优，中间是黑洞**
（四个独立来源：压缩只保留前 5000、`head -100` 预览、首因/近因效应、五段式骨架）。

放在这里对应的排版要求：

| 内容 | ⭐ 位置 |
|---|---|
| ⭐⭐⭐⭐⭐ 红线 / 不可做什么 | **最前** |
| 触发该做什么（主流程） | 前部 |
| 详细示例 | ⭐ 中部或 references |
| ⭐⭐⭐⭐⭐ 验证 / 验收 | **最后** |

> ⭐⭐⭐⭐⭐ **验证之后不要再放任何东西**——
> 否则近因区被无关内容占据，而验证是执行完立刻要做的动作。

还有一条特别值得做：**把"最容易被违反的那一两条"在首尾各写一遍**。
⭐⭐⭐ 这不是冗余（结构性冗余保留），⭐⭐⭐⭐ 而是利用首因+近因双效应。

## 5. ⭐⭐⭐⭐ 表格 vs 列表的仲裁

我们已经有判据：**要被执行的用列表，要被比较的用表格**。
这里补两个执行细节：

| 判据 | 用 |
|---|---|
| ⭐⭐⭐⭐ 读者要逐条打勾 / 执行 | 列表 |
| ⭐⭐⭐⭐ 读者要横着看（同维度对比） | 表格 |
| ⭐⭐⭐ 列数 > 3 | ⭐⭐⭐ 拆成多个小表或改列表 |
| ⭐⭐⭐ 单元格里有长句 | ⭐⭐⭐⭐ 改列表（表格里的长句没人会读） |

> ⭐⭐⭐⭐ 最后一条最实用：
> **表格的价值在于扫一眼就能比，长句破坏了这个价值。**
> 如果你发现自己在表格单元格里写长句，那它其实该是列表。

另有一条：⭐⭐⭐ **星级（⭐）适合放在表格里**——
因为它是典型的横向比较信号（一眼看出哪份最值钱）。

## 6. ⭐⭐⭐ 常见破坏可读性的写法

| 写法 | ⭐ 为什么坏 | 改法 |
|---|---|---|
| ⭐⭐⭐⭐ 一大段无小标题 | 人找不到、模型引用不了 | 加 `##` |
| ⭐⭐⭐⭐ 同义复述同一条规则 | 模型看到矛盾风险；人分不清哪个是新的 | ⭐⭐⭐⭐ 合并为一处（这是"沉积"） |
| ⭐⭐⭐⭐ "重要："/"注意：" 前缀 | ⭐⭐⭐⭐⭐ 零信息量，只增加权威感 | 删掉；若删后没约束力，问题在句子本身 |
| ⭐⭐⭐ 编号嵌套到 3 层（1.2.3） | 改一处要重编所有号，diff 爆炸 | ⭐⭐⭐ 改列表 + 缩进 |
| ⭐⭐⭐ 混合中英文标点 | 搜索和 grep 都会漏 | 统一 |
| ⭐⭐⭐⭐ 长行不换行 | diff 整段；手机上读不了 | 语义换行 |

> ⭐⭐⭐⭐ "同义复述"那一行值得单独强调：
> 它是⭐⭐⭐⭐⭐ **"沉积"的排版表现**——
> 新增内容和旧内容互相矛盾，但分别读都合理。
> ⭐⭐⭐ 检测方法也一致：**把所有提到同一件事的地方放在一起看。**

## 一句可贴在墙上

> 前者帮第二个人找到要改的地方，后者只会让模型看到两处可能矛盾的话。**
