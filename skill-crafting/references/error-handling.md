# 失败模式与回退策略

> ⭐ **任何技能都不是 100% 可靠的。**
> 真正的区别不在于"会不会失败"，而在于**失败时有没有设计好的出路**。

## 七种典型失败模式

| 失败模式 | 表现 | 根本原因 | 回退策略 |
|---|---|---|---|
| **静默失活** | 从未被触发 | description 与用户措辞不匹配 | 增加触发词同义词、定期 A/B 测 description |
| **过度触发** | 不该调时被调用 | description 太宽泛 | 缩小 scope、加入"不适用场景" |
| **上下文污染** | 加载后主 agent 行为偏移 | 内容含强约束 | **用隔离子代理包裹执行** |
| **执行卡死** | 内部逻辑死循环 | 缺少终止条件 | 超时 + 最大重试 + watchdog |
| **依赖缺失** | 引用了不存在的 MCP | MCP 未正确注册 | **启动时自检依赖**、优雅降级到本地实现 |
| **版本漂移** | 在新模型上效果变差 | description 对老模型有效、新模型偏好变了 | 模型升级时跑回归测试集 |
| **权限越界** | 做了超出 description 的事 | 技能文件被篡改 | 签名校验 + 沙箱执行 + 操作审计 |

> 其中 **"上下文污染"** 值得单独注意——
> 解法不是改技能内容，而是**改变执行位置**（隔离子代理）。
> 呼应 **`skill-evaluating` 的 `failure-modes.md`** 里的"描述渗透"：技能**仅仅因为存在于上下文中**就会改变行为。

## 三层回退

```
第 1 层  技能内回退   —— 技能自身提供 fallback 路径
                        （主路径失败时调简化版）
第 2 层  编排层回退   —— 编排器发现超时/错误，跳过它或替换为等价技能
第 3 层  平台层回退   —— 整条链路降级到无技能的基础模式，保证核心功能可用
```

> 设计原则：**每一层都假设上一层已经失败。**

## 重试：先分类再决定

> ⭐ **不是所有失败都值得重试。**

**错误分类器**：

| 判定 | 类型 |
|---|---|
| ✅ **可重试** | 429 Rate Limit · 502/503/504 · 408 超时 · 网络错误 · 数据库连接超时/死锁 |
| ❌ **不可重试** | 400 参数错误 · 401 认证失败 · 403 权限不足 · 404 不存在 · 工具未找到 · 上下文过长 |

> ⚠️ **关键区分（和熔断共用）**：
> **系统级错误**（超时、500）触发熔断；
> **业务级错误**（"图片格式不支持"）**不触发**——
> 那是输入的问题，不是技能坏了。

**指数退避 + 去相关抖动**：

```
delay = min(base * 2^attempt + random_jitter, max_delay)
示例：1s → 2.3s → 4.7s → 8.1s（max 60s）
抖动：±20% 随机偏移
```

> ⭐ **抖动不是可选项**：
> 假设 100 个 agent 同时遇到 503，没有抖动它们会在第 1/2/4 秒**精确同步重试**，
> 服务端恢复瞬间再次被打垮（**惊群效应**）。

**重试预算**：每次工具调用给一个总时间预算（如 10 秒），超预算就放弃重试，进入下一层策略。

## 熔断：三态机

```
CLOSED  ──[失败阈值]──▶  OPEN  ──[冷却结束]──▶  HALF_OPEN
   ▲                                              │
   └────────[探测成功]─────────────────────────────┘
                    HALF_OPEN ──[探测失败]──▶ OPEN
```

**一个可用的配置示例**（配置思路，非代码）：

```yaml
技能名称: 图片处理
失败阈值: 5        # 连续失败 5 次触发熔断
冷却时间: 60秒      # 熔断后等 60 秒再尝试
半开超时: 10秒      # 半开态下调用必须在 10 秒内成功
降级响应: "图片处理服务暂时不可用"
```

**实际运行效果**：

```
10:00:00 调用 → 超时失败（计数 1）
10:00:30 重试 → 超时失败（计数 2）
10:01:00 重试 → 超时失败（计数 3）
10:01:30 调用 → 立即返回降级响应（熔断已开启）
10:02:30 冷却结束 → 半开，放行一次 → 成功 → 关闭
```

> 熔断开启后，后续调用**不经过真实接口**，几乎零耗时。

**三个陷阱**：

**① 失败怎么定义？** → 区分系统级 / 业务级（见上）。

**② 冷却时间怎么设？**
太短 → 反复熔断恢复，浪费试探请求；
太长 → 技能恢复了还被关着。
→ **指数退避**：首次 30s → 60s → 120s，最多 5 分钟；同时允许管理员手动重置。

**③ 要不要考虑"慢调用"？**
有些服务没完全挂，但响应从 200ms 变成 15s。
→ 把**慢调用也算作失败**计入阈值。

## 降级链

> 当所有努力都失败时，按优先级依次尝试：

```
1. 用缓存的上次成功结果（静态降级）
   "天气服务暂不可用，这是您 2 小时前查询的结果"
2. 切换到功能相似的替代工具（功能降级）
3. 切换到备选模型 Provider
4. 跳过此能力，明确告知用户当前限制
5. 最后手段：用 LLM 常识生成近似回答（语义回退）
   "虽无法获取实时股价，但根据公开信息，科技板块近期整体呈上升趋势"
```

> ⚠️ **第 5 条有风险**——它很容易滑向编造。
> 用的时候必须**明确标注这是近似值而非实时数据**。

**其他最佳实践**：

```
□ 快速失败——尽早校验输入
□ 保留上下文——错误要带堆栈与元数据
□ 有意义的消息——说清"出了什么问题、怎么修"
□ 日志分级——错误才记，预期内的不要刷屏
□ 在能真正处理的层级捕获
□ 不要吞掉错误——记录或重抛
□ 类型化错误
```

## 迭代硬上限

> 软性检测（循环检测、重试计数）**可能失效**，
> 所以必须有**不会被绕过的硬上限**。

```
80%  发出预警
95%  准备终止
100% 强制停止
```

**时钟截止（wall_clock_deadline）** 建议值：

```
单步 2min | 任务 10min | 工作流 30min
```

**配置要点**：

```
□ 三者同时配置，取最先触发的
□ 触发后必须保存状态，支持从断点恢复
□ 避免同步工具调用/子代理活过缓存 TTL（见 **`skill-evaluating` 的 `skill-selection` 的 `caching-economics.md`**）
```

> 一个真实教训：`quality-check` 一开始没有最大重试限制，
> 遇到边缘 case 反复重试，**烧光 token**；加上 2 次限制后稳定。
