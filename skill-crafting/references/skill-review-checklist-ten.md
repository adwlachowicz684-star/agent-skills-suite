## 1. ⭐⭐⭐ 十条检查项

| 检查项 | ⭐ 判断标准 |
|---|---|
| ⭐⭐⭐ 触发条件是否在 description 中 | ⭐⭐⭐ 不依赖正文里的 "When to use" |
| ⭐⭐ name 是否规范 | 小写、数字、连字符，语义明确 |
| ⭐⭐⭐ 职责是否单一 | ⭐ 一个技能只解决一个核心任务 |
| ⭐⭐ 输入输出是否结构化 | 明确需要什么、返回什么 |
| ⭐⭐⭐ 步骤是否可执行 | ⭐⭐⭐ 用⭐ 指令式语言，⭐ 而不是抽象原则 |
| ⭐⭐ 失败策略是否完整 | 明确停止 · 重试 · 报错 · 降级 |
| ⭐⭐⭐ 资源是否分层 | ⭐ 细节放 references，⭐⭐ 确定性逻辑放 scripts |
| ⭐⭐ 是否避免重复 | ⭐⭐ 同一信息不要同时出现在 SKILL.md 和 references |
| ⭐⭐⭐ 是否有评测用例 | ⭐⭐ 至少覆盖⭐⭐⭐ 黄金路径 ⭐⭐⭐ 和⭐ 误触发场景 |
| ⭐⭐ 是否去掉无关文档 | ⭐⭐ 不放 README、安装指南、更新日志等噪音 |

**逐条说哪几条最容易挂**：

**第 1 条**——与 `skill-anatomy-antipatterns.md` 的
"正文里不要写 When to Use 章节"⭐ 完全同一条。
> ⭐⭐⭐ 两个独立来源：触发信息⭐ 只能在 description，写在正文等于马后炮。

**第 7 条**——"确定性逻辑放 scripts"：
> ⭐⭐⭐ 与 `deterministic-scripts.md` 的
> "从 Y 算出 X，X 是数字 → 脚本"一致，
> ⭐⭐ 但这里把它放进了⭐ 资源分层的框架里：
> **references 装"要读的"，scripts 装"要算的"，assets 装"要用的"。**

**第 9 条**——"至少覆盖黄金路径和误触发场景"：
> ⭐⭐⭐ 这就是 `eval-set-two-dimensions.md` 的
> 触发评测 + 执行评测两维度，以及 `eval-case-design.md` 的负向用例。
> ⭐⭐ 三个来源一致：**只测"该触发时能触发"是不够的。**

**第 10 条**——"不放 README/安装指南/更新日志"：
> ⭐⭐ 与 `operator-card-style.md` 的
> "安装/贡献/隐私章节一律删"完全同一条（第二个来源）。

## 2. ⭐⭐⭐ 如果只能记住三条

```
① ⭐⭐⭐ ⭐ 触发条件写进 description
② ⭐⭐⭐ ⭐ 脆弱操作交给 scripts
③ ⭐⭐⭐ ⭐ 每条规则都要能⭐ 对应一个失败场景
```

**第 ③ 条是本份最有价值的一条，值得展开**：

> ⭐⭐⭐ **"每条规则都要能对应一个失败场景。"**

这意味着：⭐⭐ **写下的每一条规则，你都应该能回答"没有这条会出什么事"**。
答不上来的规则，就是⭐ 空话——删掉。

```
可回答：  "重试时区分'没写入'与'已写入但回应丢失'"
         → 没有它 → ⭐ 创建重复对象
答不上来："保持专业、温暖、有洞察力"
         → 没有它 → ❓ → ⭐ 这是空话
```

> ⭐⭐⭐ 这条与我们已有的一条⭐ 强力互证：
> `five-design-patterns.md` 的⭐ **反转测试**——
> "把每条规则反过来读一遍，如果反过来也说得通，那就是空话"。
>
> ⭐⭐⭐ 两个独立来源给出⭐ 同一个判据的两种问法：
> ```
> 反转测试：反过来也说得通吗？
> 本份：    它能对应一个失败场景吗？
> ```
> ⭐⭐ 两种问法都指向：**无法证伪的规则 = 无效规则。**

## 3. ⭐⭐⭐ 正面原则改成反模式

> ⭐⭐⭐ **技能不是越详细越好。**

**一个具体转换示范**：

```
❌ 正面原则：
   "保持专业、温暖、有洞察力"

✅ 改成反模式：
   · ⭐ 不要使用空泛鼓励
   · ⭐⭐ 不要在没有具体证据时给结论
   · ⭐ 不要连续使用多个抽象形容词
```

> ⭐⭐⭐ **"后者通常更适合模型执行，因为它⭐ 更具体、⭐ 更容易检查。"**

**但这与我们已有的一条要仔细区分**（避免误用）：

```
⚠️ 我们记过：⭐⭐⭐ 禁令可能反噬——
   正文里的"不要做 X"因为⭐ 没说该做什么，反而让输出更差

⭐⭐⭐ 仲裁：
   ❌ "不要使用空泛鼓励"  ← 纯禁令，无替代 → 可能反噬
   ✅ "不要使用空泛鼓励，改为给出具体数字或事实" ← ⭐⭐⭐ 带替代 → 有效
```

> ⭐⭐⭐ 所以正确写法是⭐ **禁令 + 具体替代**，
> 而不是任一单独一侧。
> 这与 `write-reasons-not-rules.md` 的
> "禁令必须配替代方案"、以及 `activation-rate.md` 的
> "NOT for X → 用 Y 代替"是⭐ 同一规则的第三次出现。

## 4. ⭐⭐ 与 20 项清单的分工

| | `publish-checklist-20.md` | 本份 |
|---|---|---|
| 形式 | ⭐ 20 项，0–2 分制 | ⭐⭐ 10 项，定性判定 |
| 用时 | 较长，⭐ 适合发布前 | ⭐⭐⭐ 极短，⭐ 适合每次写完随手过 |
| 用途 | ⭐ 打分、横向比较 | ⭐⭐ 快速卡住最致命的几条 |

> ⭐⭐ 两者不重复：20 项是⭐ 量化审计，十项是⭐ 定性门禁。
> ⭐⭐⭐ 建议顺序：**写完 → 过十项 → 发布前 → 过 20 项。**

## 速查

```
□ ⭐⭐⭐ 十条：触发在description(不靠正文) · name规范 · 职责单一
   输入输出结构化 · ⭐⭐⭐ 步骤用指令式而非抽象原则
   失败策略完整(停止/重试/报错/降级) · ⭐ 资源分层(细节→refs，确定性→scripts)
   ⭐ 避免重复(同一信息别两处出现) · ⭐⭐⭐ 评测覆盖黄金路径+误触发 · ⭐ 删噪音文档

□ ⭐⭐⭐ 只记三条：
   ① 触发条件写进 description
   ② 脆弱操作交给 scripts
   ③ ⭐⭐⭐ ⭐ 每条规则都要能对应一个失败场景

□ ⭐⭐⭐ "每条规则对应一个失败场景" = 反转测试的另一种问法
   ⭐⭐⭐ 两个来源同一判据：⭐⭐ 无法证伪的规则 = 无效规则
□ ⭐⭐⭐ 正面原则 → 反模式（更具体、更容易检查）
   ⭐⭐⭐ 但必须⭐ 带替代方案，纯禁令会反噬（第三次出现此规则）
□ ⭐⭐ 顺序：写完过十项 → 发布前过 20 项
```

**一句话**：

> ⭐⭐⭐ **写完只需记三条：触发条件写进 description、脆弱操作交给 scripts、每条规则都要能对应一个失败场景——
> 第三条与"反转测试"是同一判据的两种问法（无法证伪的规则就是无效规则），而把正面原则改成反模式时务必带上替代方案，否则禁令会反噬。**
