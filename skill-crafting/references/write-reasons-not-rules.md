## 1. ⭐ 对照：烂技能 vs 好技能

```
❌ 烂技能
   "对超过 2000 个词元的内容进行压缩处理。
    优先保留最近 3 轮对话。
    遇到模糊指令时返回澄清问题。"

✅ 好技能
   "对超过 2000 个词元的内容进行压缩处理——
    ⭐ 因为模型在这个长度之后注意力开始分散，
    ⭐ 压缩的目的是保护关键信息的召回质量，而不是节省 token。"
```

> ⭐ **看起来只是多了一句话，但这句话彻底改变了模型的执行逻辑。**

**另一个同型对照**（同样是要求用某个库提 PDF 文本）：

```
❌ 生硬："必须使用 pdfplumber，禁止使用其他库。"

✅ 讲理："提取文本用 pdfplumber，
        ⭐ 因为它对表格和多栏排版的处理比其他库更稳；
        ⭐ 遇到扫描件（纯图片）时它会失效，这种情况改走 OCR。"
```

> ⭐ 后者多说了"为什么"和"什么情况下例外"——
> 模型拿到的就不只是一条规则，而是**一套可迁移的判断依据**。
> 碰到你没预料到的扫描件，它知道该怎么办；前者只会一条道走到黑。

## 2. ⭐ 五个维度的差别

| 维度 | 只写规则 | ⭐ 写规则 + 原因 |
|---|---|---|
| 规则形态 | "对超过 2000 词元的内容进行压缩" | "压缩超过 2000 词元——因为模型此后注意力开始分散" |
| **遇到边界情况** | ⭐ 模型僵住，或随机选一种执行方式 | ⭐ **按背后的意图自行推导，给出合理判断** |
| **维护成本** | 每新增一个场景，就要手动补一条规则 | ⭐ **意图没变，规则自动覆盖未预见的新场景** |
| **规模趋势** | ⭐ 越写越多，最终臃肿到模型无从选择 | ⭐ **越精炼越稳定，覆盖范围反而更广** |
| 本质 | 在控制模型的行为 | ⭐ **在向模型解释你的意图** |

> ⭐ 最后两行是这套方法的核心收益：
> **规则会随场景线性膨胀，原因不会。**
> 一个讲清了意图的技能，能覆盖你写的时候根本没想到的场景。

## 3. ⭐ 满屏 ALWAYS/NEVER 是一张黄牌

```
⭐ 一旦你发现自己在疯狂下硬命令，往往说明你没把"为什么"讲清楚。
```

两个具体的失效原因：

```
① ⭐ 用多了就疲了——模型不会因为写三个 MUST 就更听话
② ⭐⭐ 它只说"不能做什么"没说"为什么"，
   ⭐ 而模型在遇到边界情况时，恰恰是靠"为什么"来类推的
```

> ⭐ 第 ② 条与 `guidance-forms.md` 的"禁令反噬"是同一件事的两面：
> **禁令缺的不是力度，是替代方案和理由。**

**可操作建议**（两条，都能立刻执行）：

```
· 写完一条规则，习惯性追问一句"为什么"，把答案也写进去
· ⭐ 数一数你的 SKILL.md 里有多少个"必须/禁止/一定/永远"
  ⭐ 如果一屏好几个，回头把大部分改写成"因为……所以建议……"
```

> ⭐ "数一数"这条特别实用，因为它把抽象的"别写太硬"
> 变成了一个**可执行的自查动作**。

## 4. ⭐ 例外：关键路口仍要下狠手

> ⭐ **讲理是默认策略，但不是说完全不用硬约束。**

判断标准：

```
⭐ 默认讲道理（让模型理解、灵活应对）
⭐ 只在"一旦做错代价很大、且模型有倾向做错"的关键路口才下硬命令
```

**官方自己的例子**：

> skill-creator 保留了少数全大写强命令，其中最典型的一处是——
> **先把测试结果摆到人面前，再动手改技能。**
>
> ⭐ 因为它太了解模型的"坏习惯"了：模型容易自己跑完测试、
> 自己看一眼、自己就把技能改了，**跳过了"让人审一下"这一步**。
> 这一步一旦被跳过，整个迭代就失去了人的把关。
> 所以它这里不讲理，直接下死命令。

> ⭐ **硬约束要省着用，用在刀刃上。**
> 这与 `golden-rules-failure-modes.md` 那条
> "反复被违反的指令升级为校验函数"是同一条原则的不同阶段：
> 先讲理 → 仍被违反 → 下硬命令 → 仍被违反 → 变成代码。

## 5. ⭐ 三成原则：多少约束该转成代码检查

```
⭐ 一个成熟的技能，至少 30% 的约束应该被转成机器可校验的检查点。
```

分工判据：

```
自然语言  → ⭐ 无法穷举的语义判断
代码      → ⭐ 格式、数值、存在性、幂等性
```

**按风险分级**（这张表把"自由度"落到了具体写法）：

| 风险 | 典型场景 | 推荐写法 | 校验方式 |
|---|---|---|---|
| **高** | 数据库迁移、删除操作、生产写入、权限变更 | 精确脚本 + 强约束 + 审批门 | 脚本校验 + 人工确认 |
| **中** | 部署、批量重构、配置变更 | 伪代码 + 参数化步骤 | dry-run + 检查点 |
| **低** | 代码审查、文案润色、信息总结 | ⭐ 自然语言指令，留出判断空间 | 输出格式约定 |

> ⭐ 一句话收口：**就看这一步做错了代价多大**——
> 不可逆的，脚本化 + 审批；
> 可逆但影响面大的，dry-run + 检查点；
> 随便改改就行的，给个方向让它自己发挥。

> ⭐ 这与 `degree-of-freedom.md` 完全对上，但这里给了**具体的三档映射**
> 和"30%"这个可自查的数字。

## 速查

```
□ ⭐ 每条规则后面追问"为什么"，把答案写进去
□ ⭐ 数"必须/禁止/一定/永远"的个数，一屏好几个就该改
□ ⭐ 写原因能让模型在边界情况自行推导，且规则不随场景膨胀
□ ⭐ 满屏 ALWAYS/NEVER = 你没讲清为什么（黄牌信号）
□ ⭐ 但关键路口（做错代价大 + 模型倾向做错）仍要下死命令
□ ⭐ 至少 30% 约束转成机器可校验的检查点
□ ⭐ 高/中/低风险 → 脚本+审批 / dry-run+检查点 / 自然语言+留空间
□ 自然语言管语义，代码管格式数值存在性幂等
```

**一句话**：

> ⭐ **今天的模型不缺服从，它缺的是对规则背后意图的理解。**
