## 1. ⭐⭐⭐ 描述写不好，一切白搭（50%）

**一组正反对**（可以直接照抄这个句式）：

```
❌ "帮助处理文档"
✅ "创建、编辑和分析 .docx 文件，用于批注追踪、格式化或文本提取"

❌ "API 辅助工具"
✅ "在编写调用 Gemini API 的代码时使用，包括文本生成、多轮对话、
   图片生成或流式输出"
```

> ⭐⭐⭐ **实测数据：⭐ 仅仅改善描述，就能带来 ⭐⭐ 50% 的效果提升。**
>
> ⭐⭐⭐ 推论很直接：**如果你的技能表现不好，⭐ 先别急着改指令——先把描述改清楚。**

> ⭐⭐ 这与 `four-layer-diagnosis-flow.md` 的"80% 在文件层、15% 在触发层"
> 要合起来看才完整：
> ```
> 彻底不工作 → 先查文件层（80%）
> ⭐⭐⭐ 能工作但效果差 → ⭐⭐ 先改描述（50% 的提升空间在这里）
> ```
> ⭐⭐⭐ **不是同一件事**：前者是"能不能用"，后者是"用得好不好"。

## 2. ⭐⭐⭐ 给约束，不给流程

这是本份⭐ 最有价值、也⭐ 最需要小心的一条。

```
❌ 别这样写：
   "Step 1: 读配置文件。Step 2: 找到数据库 URL。
    Step 3: 更新端口。Step 4: 写回文件。"

✅ 应该这样写：
   "把配置文件中的数据库端口更新为用户指定的值。"

❌ "Step 1: 创建分支。Step 2: 改代码。Step 3: 跑测试。Step 4: 开 PR。"
✅ "开 PR 前必须跑测试。不允许直接 push 到 main。"
```

**理由**：

> ⭐⭐⭐ **"当你规定了每一步，就⭐ 剥夺了 agent ⭐ 自我调整、错误恢复
> 和⭐ 寻找更优路径的能力。"**

**一句话总结**：

> ⭐⭐⭐ **给约束，不给流程。**
> ⭐⭐⭐ **如果顺序真的很重要，那就⭐ 写脚本，不是写技能。**

> ⭐⭐ 这与我们已有的两条完全咬合：
> ```
> · degree-of-freedom：窄桥给护栏，开阔地给方向
> · prompt-vs-skill-failure-modes：Skill 靠模型自觉执行，没有强制力
>   → 想保证顺序就得用 Workflow 或脚本
> ```
> ⭐⭐⭐ 三条独立来源，同一个结构：
> **顺序 = 确定性 = 该交给代码；判断 = 不确定性 = 才留给模型。**

## 3. ⭐⭐ 写指令，不写论文

```
❌ "Interactions API 是推荐方案"（⭐ 这是知识点，agent 不会"执行"它）
✅ "始终使用 interactions.create()"

⭐⭐ 先放示例：⭐⭐⭐ 5 行代码比 5 段解释管用
⭐⭐ 说清楚 why："使用 model X，model Y 已废弃会报错"
   ⭐⭐⭐ → 这让 agent 能⭐ 举一反三，而不是死记规则
```

> ⭐⭐ 后两条与我们已有的 `few-shot-examples.md`（示例优先）
> 和 `write-reasons-not-rules.md`（说清后果比命令更有约束力）
> ⭐⭐ 完全一致——**第三个独立来源**。

## 4. ⭐⭐ 别过度拟合

> ⭐⭐ **"不要为了通过你手里那三条测试 prompt 做微调。
> ⭐⭐⭐ 好的技能要能⭐ 扛住百万次调用。"**

> ⭐⭐⭐ 这与 `description-tuning-official-loop.md` 的
> "按测试集分数选、防止过拟合到那 20 个查询"是⭐ 同一条原则，
> ⭐ 但这里给出了⭐ 一个更直观的量级对照：
> **三条测试 vs 百万次调用。**
> ⭐⭐ 你为三条 prompt 做的每一次微调，都是在⭐ 从百万次调用里借钱。

## 5. ⭐⭐⭐ 别忘了写"不该触发"

```
❌ "用于任何编码任务" → ⭐⭐⭐ 你的技能会⭐ 劫持每一个请求
✅ "用于处理 PDF 文件。⭐ 不用于普通文档编辑、电子表格或纯文本文件。"
```

> ⭐⭐⭐ **"只想着什么时候该触发，不想什么时候不该触发，很容易翻车。"**
> ⭐⭐ "测试也一样——⭐⭐⭐ 否则你只会在⭐ 一个方向上优化。"

> ⭐⭐ 这与 `description-scope-shape.md` 的"写不出三条反触发就别发布"、
> `hit-rate-four-questions.md` 的"只在一个方向上优化"同源。
> ⭐⭐ "劫持"这个词比"误触发"更形象。

## 6. ⭐⭐ 六步评测

```
① ⭐⭐ 手动跑几轮不同 prompt，观察哪里出错
   （是否假设某个依赖存在？是否跳过步骤？）
② ⭐⭐⭐ 定义可衡量的成功标准
   ⭐⭐⭐ ⭐ 评的是⭐ 结果，不是路径
③ ⭐⭐ 准备 10–20 条测试 prompt（该触发/不该触发/边界，每条有自己的验收标准）
④ ⭐⭐⭐ 每条跑 ⭐ 3–5 次（⭐ 看分布而不是单次结果）
⑤ ⭐⭐⭐ ⭐ 隔离每次运行（干净环境，避免上下文污染掩盖真实问题）
⑥ ⭐⭐ 出了问题？⭐⭐⭐ 先改描述
```

**第 ② 条的"评结果不评路径"值得单独记**：

> ⭐⭐⭐ 如果你断言的是"是否按步骤执行"，你测的是⭐ **是否听话**；
> 断言"输出能编译吗？用了正确的 API 吗？"，测的才是⭐ **有没有用**。
>
> ⭐⭐ 这与 `assert-on-environment.md` 的
> "断言打在环境状态上，而不是模型'说了正确的话'"同源，
> ⭐⭐ 但这里是在⭐ 技能评测的语境下说的，更具体。

**第 ⑤ 条"隔离每次运行"** 是我们此前没收过的一条：

> ⭐⭐⭐ **上下文污染会掩盖真实问题**——
> 上一轮留下的东西可能恰好补上了技能缺失的信息，
> ⭐⭐ 于是它在你的测试里通过，在用户那儿失败。

**实测结果**：通过系统化评测，一个 Gemini API 技能的**通过率从 66.7% 提到 100%**。

## 7. ⭐⭐⭐ 知道什么时候该退役

```
⭐⭐⭐ 定期跑一下⭐ 不带技能的评测
⭐⭐⭐ ⭐ 如果结果依然通过 → ⭐⭐ 说明模型已经⭐ 内化了这个技能的能力 → 可以退役
```

> ⭐⭐⭐ 这与 `outgrowth-regression-detection.md` 的
> "Outgrowth：基线无技能 88%，你的技能 89% → 归档"
> ⭐⭐⭐ 是⭐ 完全同一条判据的第二个来源——
> 两份独立来源用几乎相同的操作定义"退役时机"，
> ⭐⭐ 说明这是⭐ 目前最可靠的退役判据。

**两类技能的退役逻辑不同**（与 `capability-vs-preference.md` 一致）：

```
能力型：⭐⭐⭐ 随模型进步会过时 → ⭐ 用评测判断何时退役
偏好型：更持久，⭐⭐ 但要⭐⭐⭐ 定期检查是否与⭐ 实际流程仍一致
```

> ⭐⭐⭐ 注意偏好型的失效方式完全不同：
> 它不会"被模型追上"，它只会⭐ **与真实流程脱节**——
> 而⭐⭐ 这件事⭐ 没有任何自动信号，只能靠人定期核对。

## 8. ⭐⭐ 一个反直觉的仲裁

我们已有 `structure-modes-abcde.md` 等文档把"多主题拆成多个 reference"当成标准做法，
而本份第 4 条讲"精简、按主题拆 reference"——一致。

但第 2 条"给约束不给流程"与 `operator-card-style.md`（操作卡：极短、强约束）
放在一起时要小心一个边界：

```
⭐⭐⭐ 仲裁：
   约束 = 不可协商的边界（"不允许 push 到 main"）  → 写死
   流程 = 达成目标的路径（"先读配置再改端口"）      → ⭐ 不写或只给检查点
   ⭐⭐⭐ 中间态 = 有明确成功判据的多步骤（评测类）  → 写，但每步带验收
```

> ⭐⭐⭐ 判据是⭐ **"如果 agent 换一条路走，你介意吗？"**
> 不介意 → 只给约束；介意 → 那其实是要脚本/工作流。

## 速查

```
□ ⭐⭐⭐ 只改描述就能带来⭐ 50% 效果提升 → ⭐⭐⭐ 效果差时先改描述，别急着改指令
   ⭐⭐ 注意区分：⭐ 彻底不工作→查文件层(80%)；⭐⭐ 能用但效果差→改描述
□ ⭐⭐⭐⭐ ⭐ 给约束，不给流程
   ⭐⭐⭐ 规定了每一步 = ⭐ 剥夺了自我调整/错误恢复/找更优路径的能力
   ⭐⭐⭐ ⭐ 顺序真的重要 → ⭐ 写脚本，不是写技能
□ ⭐⭐ 指令式表达 · ⭐⭐ 5行代码>5段解释 · ⭐⭐ 说清 why（能举一反三）
□ ⭐⭐⭐ 别过度拟合：⭐⭐ 三条测试 vs ⭐⭐⭐ 百万次调用
□ ⭐⭐⭐ 写"不该触发"，否则⭐ 劫持每一个请求，且⭐⭐ 只在一个方向上优化

□ ⭐⭐ 六步评测，⭐⭐ 每条跑 3–5 次看分布，⭐⭐⭐ ⭐ 隔离每次运行（防上下文污染）
   ⭐⭐⭐ 评⭐ 结果不评路径；⭐⭐⭐ 出问题先改描述
   实测：66.7% → 100%
□ ⭐⭐⭐ ⭐ 退役判据：⭐ 跑一次不带技能的评测，仍通过 → 模型已内化 → 退役
   ⭐⭐⭐ 偏好型不会"被追上"，只会⭐ 与实际流程脱节（无自动信号，只能人核对）
□ ⭐⭐⭐ 仲裁："如果 agent 换一条路走，你介意吗？"——介意就是脚本/工作流
```

**一句话**：

> ⭐⭐⭐ **八条里最值钱的是"给约束，不给流程"——规定了每一步就剥夺了 agent 自我调整和错误恢复的能力，顺序真的重要时应该写脚本而不是写技能；
> 而"只改描述就能带来 50% 的效果提升"意味着效果差时先改描述，别急着改指令。**
