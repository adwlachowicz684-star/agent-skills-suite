## 1. ⭐ 先观察重复模式，再决定沉到哪一层

> ⭐ **如果你发现模型在多次任务里总在重复同一类动作，那就是信号。**

四种典型信号：

```
· 总在重复写某个解析脚本
· 总在重复做某种检查
· 总在重复引用某份资料
· 总在重复套某种模板
```

> ⭐ 这时真正要做的，**不是继续在提示词里提醒它**，
> ⭐ 而是判断：**这些东西该沉到技能的哪一层**。

---

## 2. ⭐ 四层映射

```
⭐ 行为原则   → 正文（SKILL.md）
⭐ 细节知识   → references/
⭐ 模板骨架   → assets/
⭐ 机械动作   → scripts/
```

**逐层解释**：

| 层 | 装什么 | 判据 |
|---|---|---|
| **正文** | ⭐ 行为原则：做事的方式、优先级、判断依据 | ⭐ 每次执行都要遵守的 |
| **references** | 细节知识：API 文档、规则表、领域细节 | ⭐ 需要时才读、读了要理解 |
| **assets** | 模板骨架：HTML/DOCX/LaTeX 骨架、图片 | ⭐ 按路径引用、零 token 成本 |
| **scripts** | 机械动作：确定性的、不该让模型自由发挥的 | ⭐ 执行即可、不该进上下文 |

> ⭐ 与 `directory-decision-matrix.md` 的"进不进上下文"判据一致，
> ⭐ 但这里多给了**语义视角**：
> **原则是"每次都要"，知识是"按需查阅"，模板是"拿来填"，动作是"叫它做"。**

## 3. 为什么分层比"写更多"重要

```
⭐ 技能设计真正的工程感，就在这里：
   ⭐ 不是"写更多"，而是"把不同类型的信息放到最合适的层里"。
```

三条具体收益：

```
① ⭐ 正文保持精简 → 激活后持续占用的上下文少
   （呼应 context-budget-math.md：指令会留在对话里持续消耗）
② 知识按需加载 → 不相关的细则不占用注意力
③ ⭐ 机械动作脚本化 → 结果确定、可测试、不依赖模型遵守
```

## 4. ⭐ 与自由度分级的配合

`write-reasons-not-rules.md` 给了三档风险分级，与四层是配套的：

| 风险 | 该沉到哪层 |
|---|---|
| 高（不可逆） | ⭐ `scripts/` + 审批门 |
| 中（影响面大） | 正文 + dry-run 检查点 |
| 低（随便改改） | ⭐ 正文自然语言，留判断空间 |

> ⭐ **分级决定"用什么形式写"，分层决定"写在哪个文件"。**
> 两个维度正交，一个技能要在两个方向上都做对。

---

## 5. 边界清晰 > 功能最多

```
⭐ 真正好用的技能，往往不是功能最多的，而是边界最清晰的。
```

> ⭐ 如果"这个技能到底管什么"没定义清楚，
> ⭐ 它很快就会越写越散，最后变成"大而全"的杂物箱。

**回归判据**：

```
行为原则放正文 · 细节知识放 references
模板骨架放 assets · 机械动作放 scripts

⭐ 放不进任何一层的内容 = 它不属于这个技能
```

---

## 速查

```
□ ⭐ 重复出现的动作类型 = 该沉淀的信号，不要在提示词里反复提醒
□ ⭐ 行为原则 → 正文（每次都遵守）
□ ⭐ 细节知识 → references/（按需读、要理解）
□ ⭐ 模板骨架 → assets/（按路径引用、零成本）
□ ⭐ 机械动作 → scripts/（执行、不进上下文）
□ ⭐ 工程感 = 把信息放到合适的层，不是写更多
□ ⭐ 风险分级定"形式"，四层定"位置"，两者正交
□ ⭐ 边界清晰 > 功能最多
□ ⭐ 放不进任何一层的 = 不属于这个技能
```

**一句话**：

> ⭐ **不是写更多，而是把不同类型的信息放到最合适的层里。**
