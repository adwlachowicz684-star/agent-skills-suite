# 范围章节：同时防"用太多"和"用太少"

> 一个常常被省略的章节，但它防的是**两种**失败：
> 用在不该用的地方、以及该用时没意识到。

## 为什么需要单独一节

description 只解决"要不要触发"这一个二元判断。
但当技能被触发后，agent 还需要知道**边界在哪**：

```
失败 1（过度应用）：不该用的时候用了
失败 2（应用不足）：该用的时候没意识到
```

> ⭐ Scope 章节同时防这两个，而且它是**正文里的**，
> 所以可以比 description 写得详细得多。

## 模板

```markdown
## Scope

Use this Skill when you need to:
- [situation 1]
- [situation 2]

Out of scope:
- [thing that sounds related but isn't — and what to use instead]
```

## 三条写法规则

**① 描述情境，不描述动作**

```
✅ "当你需要在修改代码后快速获得信心时"
❌ "运行测试"          ← 这是动作，属于 Procedure
```

Scope 回答的是"什么时候"，不是"做什么"。

**② ⭐ Out of scope 要指向正确的替代方案**

```
❌ "Out of scope: 性能测试"
✅ "Out of scope: 性能基准测试 —— 用 perf-benchmark 技能"
```

> ⭐ **"NOT for X → 用 Y 代替" 是最强的路由提示**
> （见 `triggering.md`）——一条同时治"用错"和"不知道该用谁"两个病。

**③ 领域特定的要说出来**

```
✅ "仅限 React 项目；Vue 项目请用 vue-testing"
```

## Out of scope 是本节最值钱的部分

多数人只写"适用"不写"不适用"。但：

> ⭐ **"适用"通常已经说在 description 里了；
> "不适用"才是正文能额外提供的信息。**

而且它直接缓解 `library-size-effect.md` 说的**技能遮蔽**：
与其把候选移出池子，不如**在池子里给路由一条更强的判据**。

写 Out of scope 的三步：

```
① 列出听起来相关但其实不相关的场景
② ⭐ 对每个，写出"那该用什么"
③ 如果答不出该用什么，说明你可能该把它并进范围
```

第 ③ 条是个很好的自检——**答不出替代方案的排除项往往是错的排除项**。

## 示例必须与描述对上

```
⭐ 如果 description 声明了 "use when X"，
   那么示例里必须逐字包含 X。
```

为什么：示例是**对 description 契约的测试**。
如果示例和描述不一致，模型会学到两套触发条件。

反过来说：**描述里提到的每个触发场景，都应该能在示例中找到。**

## 反面：常见的坏 Scope

**① 只写适用，不写不适用**

```
❌ "Use this skill when: 需要分析代码时"
```

等于没写——没有任何边界信息。

**② 用的是动作不是情境**

```
❌ "Use this skill when: 运行 ESLint"
```

**③ 排除项没给替代方案**

```
❌ "Out of scope: 安全审查"
   ——那安全审查怎么办？agent 会自己硬上
```

**④ 范围与 description 矛盾**

```
❌ description 说 "用于所有前端代码"
   Scope 说 "仅限 React"
   ⭐ 模型不知道该听谁的
```

> 冲突时**以 description 为准**（它先被读到），
> 所以 Scope 只能是 description 的**细化**，不能是**收窄**。

## 一个完整例子

```markdown
## Scope

Use this Skill when you need to:
- 修改代码后想快速确认没弄坏东西
- 在提交前判断该跑哪些测试
- 一个测试失败了，想定位是哪里的问题

Out of scope:
- ⭐ 性能基准测试 —— 用 perf-benchmark 技能
- ⭐ 覆盖率报告生成 —— 用 coverage-report 技能
- 跨服务的集成测试编排 —— 那是 CI 配置的职责

仅限 Node/TypeScript 项目；Python 项目请用 pytest-selector。
```

注意"跨服务的集成测试编排"那条——
它**没有**指向另一个技能，而是指向"那不是技能该做的事"。
这也是合法的排除：**有些东西不该是技能**。

## 自查

```
[ ] 描述的是情境，不是动作？
[ ] ⭐ 每个排除项都给了替代方案（或说明了为什么不该做）？
[ ] 与 description 一致，没有收窄或放宽？
[ ] ⭐ 示例里能找到 description 提到的每个触发场景？
[ ] 领域限制写清楚了吗？
```
