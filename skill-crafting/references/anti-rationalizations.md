## 为什么会跳步

> LLM 会**像人一样为自己的跳过找理由**。

这不是随机的。模型倾向于走最短路径到达"看起来完成了"的状态，
于是会生成听起来合理、实则规避了必要步骤的解释。

**对策**：**预演 10–12 种借口，在技能里逐条反驳。**

## 通用借口反驳表

直接抄进你的技能：

| Agent 说 | 技能回应 |
|---|---|
| "这个改动太小，不用测" | 每个改动都要测。规模不是豁免。 |
| "我已经手动验证过了" | 手动验证不能替代。跑工具。 |
| "用户没要求这一步" | 技能要求这一步。用户沉默不是放弃。 |
| "这一步用户肯定已经做过了" | 用命令验证，不要凭印象。 |
| "时间不够，先交付" | 漏掉必要步骤的交付不是交付。 |
| "这个场景不适用这条规则" | 规则没有例外条款。照做。 |
| "我记得上次是这样的" | 读文件确认。记忆不可靠。 |
| "跳过校验也能跑" | 零错误才继续。能跑不等于对。 |
| "文档里有，不用再写" | 写在这里，模型才会在需要时看到。 |
| "这是常识，不用解释" | 如果真是常识就删掉；否则写清约束。 |

## 状态机防跳步

给有明确顺序的流程定义**合法转换**：

```
INIT → ANALYZED → PLANNED → EXECUTED → VERIFIED → DONE

合法转换：
  INIT     → ANALYZED     （必须先读输入）
  ANALYZED → PLANNED
  PLANNED  → EXECUTED
  EXECUTED → VERIFIED     （必须跑校验）
  VERIFIED → DONE         （校验零错误才允许）

非法：EXECUTED → DONE（跳过 VERIFIED）❌
```

**写法**：在技能里显式列出合法转换，并声明
"任何未列出的转换都是错误，回退到上一个合法状态"。

## 执行契约

**确认后不许再问**：

```
用户输入已满足前置条件
  → 记录"已确认"
  → 后续步骤不得再请求同一信息
```

这条防止模型在长流程里反复打断用户要同一个东西。

## 怎么写你自己的反驳表

**来源不是想象，是 RED 阶段的实测记录**：

1. 在阶段 1（先手工跑一遍）时，**把模型说过的每一句"我不用做 X 因为……"记下来**
2. 这些原话就是反驳表的条目
3. 每条配一句**明确的、无例外的**回应

> **关键**：反驳要**具体**，不要写"请仔细思考"。
> 写"每个改动都要测。规模不是豁免。"

**再加一个红旗清单**：

```
如果你发现自己正在想以下任何一条，停下来，照清单执行：
- "这次可以例外"
- "应该没问题"
- "大概够了"
- "用户不会在意"
```

## 红线清单

写技能时的绝对禁止：

| 红线 | 说明 |
|---|---|
| ❌ 模糊词 | "尽量""酌情""合适即可""适当"——对模型等于没有约束 |
| ❌ 条件+模糊 | "Consider running X when appropriate" —— 必被忽略 |
| ❌ 中段关键规则 | 中间是模型的盲区，放顶部或底部 |
| ❌ 多段论证 | 模型需要规则，不需要来龙去脉。理由最多一句 |
| ❌ 二十个边缘案例 | 给一个例子，模型能推断其余 |
| ❌ "要彻底""要小心" | 这是氛围不是指令。说清"彻底"具体指什么 |
| ❌ 与 CLAUDE.md 重复 | 同一条指令花两次 token |
| ❌ 工作流摘要式 description | 模型会照摘要执行，而不是加载完整技能 |
| ❌ 未关闭的逃生舱 | 用明确的"无例外"语言封死 |

## 交付前检查

```
□ 是否先跑过 RED 阶段并记录了失败？
□ 技能是否针对那些具体失败，而非假想的问题？
□ description 是否以"Use when..."开头并列触发条件（而非工作流摘要）？
□ 总行数是否在 200 以内？
□ 强制行为是否在顶部或底部的编号清单里？
□ 每个工具/命令是否都写了确切名字（无"appropriate"）？
□ 是否没有模糊措辞（consider / when appropriate / if needed）？
□ 是否至少有一组正反例对？
□ 是否与 CLAUDE.md 或其他技能重复？
□ 逃生舱是否用"无例外"语言封死了？
□ 是否重跑过 GREEN 阶段并确认模型现在遵守了？
```
