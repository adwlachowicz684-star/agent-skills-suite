## 1. ⭐⭐⭐⭐⭐ 高度：太低 / 正好 / 太高

| 层级 | ⭐ 例子 | ⭐⭐⭐⭐ 问题 |
|---|---|---|
| ⭐⭐⭐⭐⭐ 太低 | ⭐⭐⭐⭐⭐ "如果文件是 .ts 且含 'async' 且行数 > 100…" | ⭐⭐⭐⭐ **脆弱**，遇到边界情形就崩 |
| ⭐⭐⭐⭐⭐ **正好（金发姑娘区）** | ⭐⭐⭐⭐⭐ "审查 TypeScript 异步模式中的常见陷阱" | ⭐⭐⭐⭐⭐ 清晰、灵活、可执行 |
| ⭐⭐⭐⭐⭐ 太高 | ⭐⭐⭐⭐⭐ "做一个好的代码审查者" | ⭐⭐⭐⭐⭐ 含糊，结果不稳定 |

> ⭐⭐⭐⭐⭐ 配套的⭐ 检验方法⭐ 是⭐ 本条⭐ 最值钱的⭐ 部分：
> ⭐⭐⭐⭐⭐ **"⭐ 你能想象出 ⭐ 三种 ⭐ 不同的 ⭐ 合理诠释吗？"**
> ```
> 能   → ⭐⭐⭐⭐⭐ 太高了（含糊）
> 不能 → ⭐⭐⭐⭐⭐ ⭐ 再看：⭐ 它会不会⭐ 因为一个⭐ 没预料的输入⭐ 就失效？
>        会   → ⭐⭐⭐⭐⭐ 太低了（脆弱）
>        不会 → ⭐⭐⭐⭐⭐ ⭐ 正好
> ```
>
> ⭐⭐⭐⭐⭐ 这⭐ 与⭐ 我们已有的⭐ 多条⭐ 精确对应，⭐⭐⭐⭐⭐ ⭐⭐⭐ 值得⭐ 串起来看：
> ```
> "给约束不给流程"   ←→ ⭐ 规定了每一步 = 太低（剥夺了自我调整与错误恢复）
> "写原因而非堆规则" ←→ ⭐⭐⭐ 纯 MUST = ⭐ 没有给出⭐ 可迁移的⭐ 判断依据
> "把形容词换成规格" ←→ ⭐⭐⭐⭐⭐ "做一个好的审查者" = ⭐⭐⭐⭐⭐ 典型的⭐ 太高
> ```
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐⭐ **三条⭐ 从不同角度⭐ 描述⭐ 同一个⭐ 失败：
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 抽象层级⭐ 没选对。**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 而⭐ 本条⭐ 第一次⭐ 给出了⭐ 一个⭐ 双向的⭐ 检验法
> （⭐ 一边是"太含糊"，⭐ 一边是"太脆弱"）。

## 2. ⭐⭐⭐⭐⭐ 三条律

**律一：高度合适（Right Altitude）** —— 见上节的检验法。

**律二：⭐⭐⭐⭐⭐ 给逃生口（Escape Hatches）**

```
⭐⭐⭐⭐⭐ "如果你遇到 ⭐ 这些指令 ⭐ 没有覆盖的情况：
   ① ⭐⭐⭐⭐ 说明 ⭐ 你不确定的是什么
   ② ⭐⭐⭐⭐ 给出 ⭐ 你的最佳判断
   ③ ⭐⭐⭐⭐⭐ ⭐ 需要就 ⭐ 请求澄清"
```

> ⭐⭐⭐⭐⭐ 这条⭐ 之所以重要，⭐⭐⭐⭐⭐ ⭐⭐⭐ 是因为⭐ 它⭐ 解决了⭐ 一个⭐ 我们反复遇到的⭐ 困境：
> ⭐⭐⭐⭐⭐ **技能⭐ 不可能⭐ 覆盖⭐ 所有情况，⭐⭐⭐⭐⭐ ⭐⭐⭐ 而⭐ 不写⭐ "没覆盖怎么办"，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐ 模型⭐ 就会⭐ 即兴发挥——⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 或者⭐ 编造。**
>
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这⭐ 与我们已有的⭐ 至少三条⭐ 直接相关：
> ```
> 幻觉的合法出口："给'我不知道'留一个合法选项"（output-stability-contract）
> ⭐⭐⭐⭐⭐ 别编造：    "参考不存在→模型自补内容"（three-failure-modes）
> ⭐⭐⭐⭐⭐ 前置门禁：  "不得即兴发挥未声明的回退路径"（preflight-gate）
> ```
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ **三条都在说⭐ "模型⭐ 遇到盲区⭐ 会犯错"，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 而⭐ 本条⭐ 给出了⭐ 那个⭐ 缺失的机制：
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ **明确告诉它⭐ 盲区里⭐ 该做什么——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 不是"别猜"，⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 而是
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ "⭐ 说出不确定 → ⭐ 给最佳判断 → ⭐ 必要时问"。**
>
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 换句话说：⭐ **逃生口⭐ 把⭐ "沉默的即兴发挥"
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 变成了 ⭐ "可被看见的、带置信度的判断"。**

**律三：⭐⭐⭐⭐ 内置验证步骤**

```
完成前：
  ☐ ⭐⭐⭐ 验证输出符合预期格式
  ☐ ⭐⭐⭐ 检查安全隐患
  ⭐⭐⭐⭐ ☐ ⭐⭐⭐⭐⭐ 确保改动最小且聚焦
```

> ⭐⭐⭐⭐⭐ 第三项⭐ 最值得⭐ 单独记：⭐ **"确保改动⭐ 最小且聚焦"**。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 它⭐ 与 `description-scope-shape.md` 那条
> "⭐ 没有反触发，⭐⭐⭐⭐⭐ ⭐⭐⭐ 代码评审技能⭐ 被叫去审 typo 修复时
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 会⭐ '好心'加上⭐ 五段无关的⭐ 架构反馈"⭐ 是⭐ 同一个病。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 而⭐ 这里⭐ 把它⭐ 变成了⭐ 一条⭐ 收尾时的⭐ 自检项。

## 3. ⭐⭐⭐⭐ 结构：前置 / 分节 / 逃生口

**① ⭐⭐⭐⭐⭐ 关键信息前置**

```
## CRITICAL: [最重要的指令]
[次重要的上下文放在下面]
```

> ⭐⭐⭐⭐⭐ 这⭐ 是⭐ "开头是黄金位置"⭐ 的⭐ 又一个⭐ 独立来源，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 而且⭐ 它⭐ 给了一个⭐ 具体做法：⭐ **用一个显式的 `## CRITICAL:` 标题。**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 我们已有的⭐ 三个来源⭐ 分别是：
> ```
> 压缩只保留开头 5000 tokens（three-tier-token-math）
> ⭐⭐⭐⭐⭐ 模型用 head -100 预览长文件（reference-file-practices）
> ⭐⭐⭐⭐⭐ 首因/近因效应，关键规则两端重复（prompt-layering-positional-bias）
> ```
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 本条⭐ 是⭐ 第四个，⭐⭐⭐⭐⭐ ⭐⭐⭐ 且⭐ 直接⭐ 给了⭐ 实现手段。

**② ⭐⭐⭐⭐ 用结构化小节**

```
## Input Format      [Claude 会收到什么]
## Output Format     [Claude 必须产出什么]
## Processing Rules  [如何把输入转成输出]
```

> ⭐⭐⭐⭐⭐ 这三段⭐ 与我们⭐ 已有的⭐ `seven-contracts.md` 的
> "⭐ 输入契约 / 输出契约"⭐ 是⭐ 同一个⭐ 划分，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 而⭐ 这里⭐ 补上了⭐ 第三块——⭐ **"如何转换"**。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 三块齐全，⭐⭐⭐⭐⭐ ⭐⭐⭐ 才是一份⭐ 完整的⭐ 执行契约。

**③ ⭐⭐⭐ 反模式要成对写**（`Don't` + `Instead`），见 `six-pitfalls-selfcheck.md`。

## 4. ⭐⭐⭐⭐⭐ 按模型档位调

| 档位 | ⭐⭐⭐⭐ 写法 |
|---|---|
| ⭐⭐⭐ Haiku（快、便宜） | ⭐⭐⭐ 提示要简洁；⭐ 用于简单、定义明确的任务；⭐⭐⭐⭐ 避免要求复杂推理链 |
| ⭐⭐⭐ Sonnet（均衡） | ⭐⭐⭐ 标准详细度；⭐ 适合多数 agent 任务；⭐ 可处理中等复杂度 |
| ⭐⭐⭐ Opus（最强） | ⭐⭐⭐⭐⭐ 复杂任务值得⭐ 多花上下文；⭐ 适合细微判断；⭐⭐⭐ 用于关键、高风险工作 |

> ⭐⭐⭐⭐⭐ 这条⭐ 补上了⭐ 我们⭐ 此前⭐ 完全没覆盖的⭐ 一个维度：
> ⭐⭐⭐⭐⭐ **同一份技能，⭐⭐⭐⭐⭐ ⭐⭐⭐ 在⭐ 不同档位的模型上⭐ 应该有⭐ 不同写法。**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 而⭐ 它⭐ 与⭐ 两条⭐ 已有结论⭐ 直接咬合：
> ```
> ⭐⭐⭐⭐⭐ "提示性能跨模型只弱相关"（model-migration-audit）
>    → ⭐⭐⭐⭐⭐ ⭐⭐⭐ 所以⭐ 为一档调好的⭐ 不能外推到另一档
> ⭐⭐⭐⭐⭐ "弱模型有技能反而更差"（skillsbench-vs-realworld）
>    → ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 无关技能⭐ 消耗 token ⭐ 去遵循⭐ 无用指令
>    → ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 对 Haiku ⭐ 尤其要⭐ 精简
> ```
>
> ⭐⭐⭐⭐⭐ 一个⭐ 相关的⭐ 实践提醒（来自另一来源）：
> ⭐⭐⭐⭐⭐ **"⭐ 如果你的技能⭐ 有⭐ 依赖模型能力的⭐ 代码路径，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 就在正文里⭐ 显式分支，⭐⭐⭐⭐⭐ ⭐⭐⭐ 而⭐ 不要⭐ 让模型⭐ 隐式降级。"**
> ```
> ✅ "如果代码库超过 50K token，⭐ 先逐个模块总结，⭐ 再组合成重构方案"
> ```
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这⭐ 正是⭐ "⭐ 显式 ⭐ 优于 ⭐ 隐式"⭐ 这条⭐ 老原则的
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 一个⭐ 新应用场景：⭐ **不仅要⭐ 显式写规则，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 还要⭐ 显式写 ⭐ 能力不足时的 ⭐ 降级路径。**

## 5. ⭐⭐⭐ 三个常见错误

**① ⭐⭐⭐⭐⭐ 过度规定（Overly Prescriptive）**

```
❌ "如果错误含 'undefined' 且文件是 JavaScript：检查空指针
   ⭐⭐⭐⭐ 否则如果错误含 'type' 且文件是 TypeScript：检查类型不匹配……"

✅ "通过以下方式诊断错误：
   ① ⭐ 仔细阅读错误信息
   ② ⭐ 识别错误类别（类型、null、异步等）
   ③ ⭐ 在代码库中定位来源
   ④ ⭐⭐⭐⭐⭐ ⭐ 先理解根因再修"
```

> ⭐⭐⭐⭐⭐ 这个例子⭐ 极其典型：⭐ **❌ 那个版本⭐ 看起来⭐ 更"具体"、更"可执行"，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 但⭐ 它⭐ 恰恰是⭐ "太低"——⭐⭐⭐⭐⭐ ⭐⭐⭐ 因为它⭐ 穷举了⭐ 两种情况，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 而⭐ 真实情况⭐ 有⭐ 几十种。**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ **"看起来更具体" ⭐ 和 ⭐ "实际上更稳健" ⭐ 不是一回事。**

**② ⭐⭐⭐⭐⭐ 没有例子**

```
❌ "审查代码的质量问题。"
✅ "审查代码的质量问题。问题类型举例：
   · ⭐ 未使用的变量（删掉）
   · ⭐ 复杂条件（提取成具名函数）
   · ⭐⭐⭐ 缺失的错误处理（加 try/catch 或校验）"
```

> ⭐⭐⭐⭐⭐ 这⭐ 与 `judgment-branches-acceptance.md` 的"流程/判断/验收三件套"
> ⭐⭐⭐⭐ ⭐ 是⭐ 同一件事的⭐ 最短版本：⭐ **"审查质量问题"⭐ 只有流程，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 没有⭐ 判断标准，⭐⭐⭐⭐⭐ ⭐⭐⭐ 于是⭐ 每次结果都不一样。**

**③ ⭐⭐⭐⭐⭐ 指令互相冲突**

```
❌ "要彻底，把所有东西都检查一遍。⭐ 同时要快，要高效。"
```

> ⭐⭐⭐⭐⭐ 这⭐ 与 `conflict-precedence-four-types.md` 的
> "⭐ 避免跨层矛盾 ⭐ 比 ⭐ 记住优先级顺序 ⭐ 更根本"⭐ 完全同源。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 而⭐ 这里⭐ 给出了⭐ 最常见的⭐ 具体形态：
> ⭐⭐⭐⭐⭐ **"彻底" ⭐ 和 ⭐ "快" ⭐ 同时出现——⭐⭐⭐⭐⭐ ⭐⭐⭐ 这是⭐ 一对⭐ 天然冲突的
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 质量/成本目标，⭐⭐⭐⭐⭐ ⭐⭐⭐ 写在一起⭐ 就是⭐ 让模型⭐ 自己挑。**

## 速查

```
□ ⭐⭐⭐⭐⭐ 高度检验（双向）：能想象出三种不同合理诠释？→ 太高（含糊）
   ⭐⭐⭐⭐⭐ ⭐ 会因为没有预料的输入而失效？→ 太低（脆弱）
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ 太低=规定了每一步；太高="做一个好的审查者"；正好="审查 TS 异步常见陷阱"
□ ⭐⭐⭐⭐⭐ 律一 高度合适 · ⭐⭐⭐⭐⭐ 律二 给逃生口 · ⭐⭐⭐⭐ 律三 内置验证
□ ⭐⭐⭐⭐⭐ 逃生口是缺失的机制：说不确定 → 给最佳判断 → 必要时问
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 它把"沉默的即兴发挥"变成"可见的带置信度的判断"
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 别只写"别猜"——⭐⭐⭐⭐⭐ ⭐⭐⭐ 要写盲区里具体做什么
□ ⭐⭐⭐⭐ 律三第三项：⭐⭐⭐⭐⭐ "确保改动最小且聚焦" ←→ 审 typo 却加五段架构反馈
□ ⭐⭐⭐⭐⭐ 前置：用显式的 ## CRITICAL: 标题（"开头是黄金位置"的第四个来源 + 实现手段）
□ ⭐⭐⭐⭐ 三分节：Input Format / Output Format / ⭐⭐⭐⭐⭐ Processing Rules（转换规则别漏）
