# 从系统提示词迁移到技能

> ⭐ **很多人把 SKILL.md 理解为"用 Markdown 写角色设定"，
> 结果只是把一团乱的 Prompt 变成了一团乱的 Markdown。**
> 真正的 SKILL.md 是一份**技能封装协议**。

## 什么时候该迁

> 不是所有提示词都该变成技能。先分级：

```
个人实验        → 留在个人配置
单项目规则      → 留在项目配置（CLAUDE.md）
⭐ 跨项目、跨团队、高频复用的经验 → 才做成技能
```

> **不要从"最酷"的开始，从"最常被用错、最需要统一"的开始。**

**先盘点**：把高频使用、多人复制、已经影响交付质量的 prompt 找出来。

## 典型症状：提示词堆积困境

> 一个真实案例：

```
三个月前搭了个代码审查助手，起初效果惊艳。
随着业务规则增加，System Prompt 从 200 行膨胀到 2000 行。

□ 加一条规则，旧行为开始漂移
□ 改一处措辞，另一个功能莫名失效
□ 新人接手根本不敢动那段"祖传提示词"
□ 审查规范、SQL 生成规则、文档风格要求全揉在一起
  ——每次对话都携带全部上下文，既浪费 token 又互相干扰
```

**这类提示词模板的典型死法**：

> 项目刚开始效果还行，稍微跑复杂一点就崩，
> **而且你不知道该往哪个方向调**——
> 是加检查项？加角色描述？还是重新排一下顺序？**全凭感觉。**

## 迁移五步

**第一步：抽取技能边界，确定触发条件**

```
原 Prompt 里混杂了"审查逻辑错误""输出 SQL 优化建议""检查命名规范"
三类任务 → 只抽取"逻辑审查"这一项做成独立技能
```

```yaml
---
name: code-review-logic
description: 当用户要求审查代码逻辑、排查潜在 bug 或评估代码正确性时使用。不适用于风格审查和性能优化。
---
```

> ⭐ **从用户可能说的原话反推触发词，同时写清楚"不要做什么"。**
> **这一步值得多花时间，因为调度不准，后面全白搭。**

**第二步：声明能力域，每域只写可执行指令**

```
❌ "全面审查代码质量"         —— 一句正确的废话
✅ "只审查逻辑错误，不做风格建议" —— 清晰的边界
```

> **模型对模糊指令的解读方差极大。能力声明越具体，输出越可预期。**

写成"检查什么 + 输出什么格式"：

```
### 空指针与未定义访问
- 检查所有对象属性访问前是否有空值判断
- 特别关注链式调用和可选链混用场景
- 发现问题时输出：文件路径:行号 + 风险描述 + 修复建议
```

**第三步：编写执行工作流，固定顺序**

> ⭐ **规则是"禁止做什么"，工作流是"按什么顺序做"。**
> **只写规则不写工作流，模型知道边界却不知道路径，输出质量依然不稳定。**

```
1. 先扫描全部代码，列出所有可疑点
2. 对每个可疑点追踪数据流，确认是否构成真实风险
3. 输出审查报告，按严重程度排序，每条含定位和修复建议
```

**第四步：设定硬性规则**

> ⭐ **这里写清楚"不做什么"比"做什么"更重要。**

```
- 不修改用户代码，只输出建议
- 不审查代码风格和命名规范
- 不确定的风险点标注"需人工确认"，不臆断
```

**第五步：挂载并验证**

```
在项目级 CLAUDE.md 中声明技能位置，然后实测三类输入：
□ 有明显 bug 的代码
□ 边界模糊的代码
□ 正常代码

⭐ 重点观察模型是否在"不需要该技能"时保持沉默
   如果误触发率高于 10%，回到第一步收紧 description
```

## 三层结构

> SKILL.md 不直接写"你要做什么"，
> 而是通过三段式让模型理解**"你是什么、能干什么、怎么干"**。
> **理解这一点，是区分"提示词搬家"和"技能封装"的分水岭。**

```
第一层  元信息      name + description
第二层  能力声明    ## 分技能域，### 下用短句写可执行边界指令
第三层  执行约束    规则（禁止做什么）+ 工作流（按什么顺序做）
```

**产出目录**：

```
code-review-skill/
├── SKILL.md              # 核心入口
├── references/           # 详细 API 文档、规范、案例
├── scripts/              # 可执行脚本、检查程序
├── assets/               # 报告模板、固定输出结构
└── examples/             # 示例执行结果
```

> 注：`examples/` 是部分实现的约定；跨客户端分发建议用 `assets/examples/`。

## 不是银弹：三个局限

**局限一：SKILL.md 不是运行时，它不保证模型一定遵守**

> ⚠️ **规则是"建议性约束"而非"硬编码逻辑"。**
> 你写了"不修改用户代码"，模型在用户强烈要求时**仍可能直接给出修改后的代码块**。
>
> → **关键逻辑不能只靠 SKILL.md 约束，必要时应配合代码层面的校验**
> （呼应 `skill-governance` 的 `injection-defense.md` 的层 4：确定性门禁优于提示词约束）。

**局限二：写成百科全书反而稀释关键约束**

```
❌ 每个能力点下附三段解释 → 模型抓不住重点，关键约束被稀释
✅ 写技能文件不是写技术文档
   ——解释性文字越少越好，可执行指令越多越好
```

**局限三：能力域之间职责重叠会让模型不知道听谁的**

```
❌ "逻辑审查"和"安全审查"都写了"检查空指针" → 输出随机性大增
✅ 每个技能文件只做一件事；
   域之间有重叠时通过 description 明确分工
```

## 迁移顺序建议

```
1. 盘点——找高频、多人复制、影响交付质量的
2. 分级——个人 / 项目 / 跨团队（只有后者做成技能）
3. 拆结构——哪些是 skill，哪些是 command，
            哪些需要 hook，哪些必须通过 MCP server 接系统
   ⭐ 不要把所有东西都塞进 SKILL.md
   ——Agent 需要的是清晰边界，不是长篇训话
4. 补治理——元数据、README、版本策略、审查记录、
            权限说明、测试方法
   ⚠️ 对能执行命令或连接外部系统的，审查要更严
5. 建目录——哪怕只是一个内部 Git 仓库
   ⭐ 没有目录，能力会继续靠私聊传播
```

> **一个更深的变化**：
> Agent 的能力不再只来自模型厂商——**模型提供通用推理，企业和社区提供领域能力**。
> 谁更了解内部系统，谁就更适合维护相关 MCP server；
> 谁更懂业务流程，谁就更适合写对应 skill；
> **谁承担安全责任，谁就该定义 hook 和权限边界。**

## 自查

```
□ 是否按"跨项目/跨团队/高频"标准筛过（而非什么都迁）？
□ 是否只抽取了一类任务（而非什么都塞）？
□ description 是否从用户原话反推、并写清了"不用于"？
□ 能力声明是否都是可执行边界（而非"正确的废话"）？
□ 是否既有规则也有工作流（而非只有其一）？
□ 是否写清了"不做什么"？
□ 是否实测了"不需要时保持沉默"（误触发 <10%）？
□ 是否有能力域重叠（有则通过 description 分工）？
□ 关键约束是否配合了代码层校验（而非只靠提示词）？
□ 是否拆清了 skill / command / hook / MCP 的边界？
□ 是否进了 Git 版本管理？
□ 是否有目录让团队能发现安装更新反馈？
```
