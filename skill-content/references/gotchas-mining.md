## 1. ⭐⭐⭐⭐⭐ 空白页问题

写技能时，Gotchas 章节几乎总是**最后写、也最先空着**：

```
## Gotchas
（待补充）
```

原因不是懒，是**这一类内容的获取方式和正文其他部分完全不同**：

| 章节 | 来源 | 能不能坐着想出来 |
|---|---|---|
| 流程步骤 | 你自己知道 | ⭐ 能 |
| 输出模板 | 你自己定 | ⭐ 能 |
| ⭐ **Gotchas** | ⭐⭐⭐ **只有踩过才知道** | ⭐⭐⭐ **不能** |

> ⭐⭐⭐⭐⭐ **所以"坐下来把技能写完"这个动作，
> 天然产不出 Gotchas。** 它必须靠采集，不能靠构思。

这就是空白页问题的根：我们把一个采集任务当成了写作任务。

## 2. ⭐⭐⭐⭐⭐ 六个矿脉

按"信息密度 × 获取成本"排序：

**① ⭐⭐⭐⭐⭐ 你自己的纠错记录**

```
翻聊天记录，找你说过的话：
"不对，这里应该用 X 而不是 Y"
"你漏了 Z"
"这样不行，因为……"
```

> ⭐⭐⭐⭐ **每一句纠错 = 一条 Gotcha，而且是已经验证过的**
> ——因为它曾经真的让模型做错了。

**② ⭐⭐⭐⭐⭐ Code Review 里的重复评论**

```
同一个问题你评论过三次以上 → ⭐ 那是 Gotcha，不是 reviewer 耐心的问题
```

判据很好用：**重复次数 = 信号强度**。评论过一次是偏好，三次是规律。

**③ ⭐⭐⭐⭐ 新人提问 / 上手文档**

```
新人卡住的地方，正是"所有人都默认知道"的地方
⭐ 而这些恰恰是模型最可能不知道的
```

**④ ⭐⭐⭐⭐ 事故复盘与 on-call 记录**

```
"又忘了 X" → ⭐ 双"又"字是最高纯度的矿脉信号
```

**⑤ ⭐⭐⭐ 跨系统命名映射**（3 类来源里最常被漏）

```
同一个东西在不同系统里的名字：
  数据库 user_id · 鉴权 uid · 账单 accountId
```

> ⭐⭐⭐⭐ **模型不可能靠推理得出这个**——
> 它不是知识问题，是你们系统的历史遗留。这类 Gotcha 的
> **替换价值最高**：没有它，模型会猜，而且猜得很自信。

**⑥ ⭐⭐⭐ 上游变更日志 / 已废弃接口**

```
"用 X，因为 Y 已废弃会报错"
```

⭐ 这类带**时间维度**，也正因如此最容易腐烂
（见《skill-refining》的 `skill-refining/references/memory-layering-and-skills.md`：
程序记忆层没有时间维度）。

## 3. ⭐⭐⭐⭐ 三条筛选标准

挖出来的不能全写——**Gotchas 章节本身也占 token**。三条筛子：

| 筛子 | 通过条件 |
|---|---|
| ⭐ **反直觉性** | ⭐⭐⭐ 反过来写也说得通吗？——能，就删（反转测试） |
| ⭐ **不可推理性** | ⭐⭐⭐ 模型能靠常识推出来吗？——能，就删 |
| **可操作性** | 能直接改变下一步动作吗？——不能，就删 |

> ⭐⭐⭐ **第二条最锋利，也最常违反。**
> "这个函数会抛异常"是可推理的；
> "这个接口在月结期间会静默返回上个月的数据"不是。

一个快速自检：**把这条 Gotcha 给一个没用过你们系统的聪明人看，
他会说"这我知道"吗？** 会 → 删。

## 4. ⭐⭐⭐ 从"事实"到"可执行的 Gotcha"

挖到的原始材料通常是事实，不是指令。要过一道转换：

```
❌ 事实："payment 表有软删除"
✅ Gotcha："查询 payment 表必须带 deleted_at IS NULL，
           否则会统计到已取消的订单——软删除是本表默认行为"
```

转换公式：

```
[触发条件] + [必须做什么] + [不做的后果]
```

> ⭐⭐⭐ **"不做的后果"是转换的关键。**
> 没有它，模型知道这条规则存在，但不知道违反的代价，
> 于是在"看起来可以省一步"的时候就会省。

配一条对照（来自 `skill-crafting/references/write-reasons-not-rules.md`）：

```
禁令版："不要忘记过滤软删除"        ← 依赖遵守
因果版："必须过滤，否则金额会虚高"  ← ⭐ 有代价，可迁移
```

## 5. ⭐⭐⭐ 采集节奏：不要一次挖完

> ⭐⭐⭐ **Gotchas 是一个 append-only 的章节，不是一个要写完的章节。**

推荐节奏：

```
第 1 版：只写 3–5 条（从矿脉①里挑最痛的）
之后：   ⭐ 每纠正模型一次，就加一条
上限：   ⭐⭐ 超过 15 条就该拆进 references/gotchas.md
```

理由有两个：

1. **一次性挖完会导致你写进一堆没验证过的"可能是坑"** —— 反直觉性筛子失效
2. ⭐ **维护方式本身就是质量保障**：只有真踩过的才进得来，
   而这个门槛在一次性采集时是不存在的

> ⭐⭐⭐ 这和 `skill-content/references/examples-as-contract.md` 是同一个道理：
> **来源决定可信度。** 来自真实纠错的 Gotcha 天然比来自想象的高一个等级。

## 6. ⭐⭐ 三个会污染矿脉的坑

**坑一：把"我的偏好"当成 Gotcha**

```
❌ "我喜欢函数不超过 30 行"
✅ 反例见 `skill-scoping/references/scope-multiplication.md`：
   老张加了这条"看起来正确"的规则，pass_rate 从 0.85 掉到 0.72
```

判据：**它是反直觉事实，还是风格主张？** 后者进编码规范，不进技能。

**坑二：把"当时如此"当成 Gotcha**

```
❌ "目前只支持 A 和 B"（没有日期）
✅ "截至 2026-09 只支持 A 和 B，C 在排期中"
```

⭐ 没有时间锚的时敏信息是未来的谎言。

**坑三：把"背景"当成 Gotcha**

```
❌ "这个模块历史上重构过三次，当时是为了解决……"
✅ 能改变下一步动作吗？不能 → 删
```

## 一句可贴在墙上

> ⭐⭐⭐⭐ **Gotchas 不是写出来的，是采集出来的。**
> **如果你的 Gotchas 章节是坐着想出来的，那它大概率一条都不该留。**
