## 1. ⭐⭐⭐⭐⭐ 省略不是留白

写技能时的默认心态是：

```
"这个细节没写，模型应该会自己处理吧"
```

> ⭐⭐⭐⭐⭐ **它确实会自己处理。问题是：它处理的依据不是你的意图，
> 而是它的先验——而它的先验是"通用互联网文本里的常见做法"。**

我们已有一条同源结论：

> ⭐⭐⭐⭐ **"你提示里的每一处模糊，都是模型会做出判断的地方。"**

这份给它补上具体清单：**哪些省略、会被填成什么**。

## 2. ⭐⭐⭐⭐⭐ 一张默认值表

| 你省略了 | ⭐ 模型的默认 | 后果 |
|---|---|---|
| 输出格式 | 自由 Markdown 散文 | 下游无法解析 |
| 输出长度 | ⭐ 中等偏长 | 挤占上下文、稀释重点 |
| 不确定时怎么办 | ⭐⭐ 猜一个继续 | ⭐⭐⭐ 静默编造 |
| 失败时怎么办 | ⭐⭐⭐ 换条路继续 | ⭐⭐⭐ 绕过你的约束 |
| 数据缺失时 | ⭐⭐ 跳过或填 0 | ⭐⭐⭐ 伪造数据 |
| 只处理第一个还是全部 | ⭐ 处理"看起来主要的"那个 | 漏项，且不报告 |
| 要不要写入 | ⭐⭐⭐ 会尝试写入（如果工具可用） | ⭐⭐⭐ 意外副作用 |
| 顺序是否重要 | 按它觉得合理的顺序 | ⭐ 顺序敏感时错乱 |
| 犯错了要不要说 | ⭐⭐⭐ 不说（倾向于呈现成功） | ⭐⭐⭐ 自信的错误 |
| 用中文还是英文 | ⭐ 跟随用户输入 | 通常 OK，但术语会漂 |

> ⭐⭐⭐⭐⭐ **第三、四、五行是三兄弟**：
> 它们都指向同一个默认——⭐⭐⭐ **"流程要走完"**。
> 模型有强烈的完成倾向，因此在遇到阻碍时的默认动作
> **不是停下报告，而是想办法绕过去**。

## 3. ⭐⭐⭐⭐ 默认值从哪来

三个来源，按影响力排序：

```
① ⭐⭐⭐⭐⭐ 预训练先验（"报告应该长这样""要给出有帮助的答案"）
② ⭐⭐⭐ 系统提示（助手人设：乐于助人、详尽）
③ ⭐⭐ 对话上下文（前面几轮它自己是怎么做的）
```

> ⭐⭐⭐⭐ 第三条解释了那个常见现象：
> **同一个技能，在对话前 3 轮和后 3 轮表现不同。**
> 不是技能变了，是上下文给了它新的默认。

而第一条意味着：⭐⭐⭐ **默认值对所有人是同一个，
但它不一定是你要的那个**——
它大概率是"网上最常见的那个"。

## 4. ⭐⭐⭐⭐ 最贵的三处省略

**① ⭐⭐⭐⭐⭐ 没写"不确定时怎么办"**

```
默认：猜
⭐⭐⭐ 修法成本最低、收益最高的一句：
   "不确定时写'存疑：<具体哪里不确定>'，或明确写'无'。不得用占位内容填充。"
```

> ⭐⭐⭐⭐⭐ 注意后半句"或明确写无"——
> 只写"要说明不确定"会让它**每次都编一段"存疑"**，
> 而多数时候其实没有存疑。**给它一个"无"的出口，它才不会为了填这个字段而编。**

**② ⭐⭐⭐⭐⭐ 没写"失败时怎么办"**

```
默认：换条路继续
⭐⭐⭐⭐⭐ 修法："任何一步失败 → 报告并停止。不得跳过、不得估算、不得改用替代方案。"
```

**③ ⭐⭐⭐⭐ 没写"要不要写入"**

```
默认：能写就写
⭐⭐⭐⭐ 修法："只读。不写入任何文件。"（且默认 dry-run）
```

> ⭐⭐⭐ 这三处的共同点：**都是"异常/边界"路径**。
> 而我们已经反复看到——**异常路径的规格通常只有一句话，
> 于是模型就用一句话的方式去补**（见 `skill-recovery/references/execution-error-protocol.md`）。

## 5. ⭐⭐⭐⭐⭐ 主动设默认 vs 被动留空

关键区别不是"写不写"，是**谁在设默认**：

| | 被动留空 | ⭐ 主动设默认 |
|---|---|---|
| 决策者 | 模型（按先验） | 你 |
| 一致性 | 随上下文漂移 | 稳定 |
| 可审计 | ❌ | ✅ 写在文件里 |
| ⭐ 成本 | 零 | ⭐ 每个默认一行，通常 ≤10 行 |

> ⭐⭐⭐⭐⭐ **这是性价比最高的一类改动**：
> 十条"默认动作"声明，总共可能不到 10 行、不到 200 token，
> ⭐⭐⭐ 但它们覆盖的是**所有你没预料到的情况**。

对比一下：写 20 条具体规则只能覆盖 20 种情况；
⭐⭐⭐ **写 10 条默认动作，覆盖的是"所有情况里你没写到的部分"**。

一个可直接抄的最小集：

```markdown
## 默认动作（未特别说明时按此执行）
- 不确定 → 写"存疑：…"或"无"，不得填充占位内容
- 任一步失败 → 报告并停止，不跳过、不估算、不改方案
- 数据缺失 → 标记 null 并在报告里说明，不得填 0
- 只读，不写入任何文件
- 输出只含要求的部分，不附加解释与建议
```

## 6. ⭐⭐⭐ 检查方法

一份技能写完后，逐条自问（每条 5 秒）：

```
□ 输出格式写了吗？
□ 不确定时怎么办写了吗？      ← ⭐ 最常漏
□ 失败时怎么办写了吗？        ← ⭐⭐ 次常漏
□ 数据缺失时怎么办写了吗？
□ 处理全部还是第一个？
□ 会不会写入？
□ ⭐ 犯错了要不要告诉用户？
```

> ⭐⭐⭐⭐ **最后一条几乎没人写，也几乎没人意识到自己没写。**
> 而它正是"自信的错误"的来源——
> 模型不是故意隐瞒，是 ⭐⭐⭐ 没有人告诉它"报告自己的失误"是一个被期待的行为。

这与 `skill-crafting/references/eight-practical-lessons.md` 的"给约束不给流程"不冲突：
⭐ **默认动作不是流程，是边界条件**——
它不规定怎么做，只规定"做不动时怎么办"。

## 一句可贴在墙上

> ⭐⭐⭐ **你没写的地方，模型不是留空——它是按自己的默认值填满了。**
