## Validation 回答什么

> **"agent 怎么知道这个技能跑成功了？"**

格式：

```markdown
## Validation
- [确切命令] → [预期输出或通过判据]
- [可观察行为] 确认成功
```

关键：**命令要确切，判据要可观察**。

```
❌ "运行测试确认没问题"
✅ "运行 `npm test -- --testPathPattern=auth`
    → 期望输出：0 failures
    ⭐ 非零则停下，不要继续下一步"

❌ "检查文件是否生成"
✅ "确认 dist/report.html 存在且字节数 > 0"
```

## Escalation 回答什么

> **"什么时候该停下并找人帮忙？"**

格式：

```markdown
## Escalation
- If [具体条件]: [该做什么]
- If [失败模式]: 交给 [具体的人/agent]
```

## 为什么"有问题就问人"不算升级规则

```
❌ "If something goes wrong: ask for help"
```

三个问题：

```
① ⭐ "something goes wrong" 不是可判定的
   模型不会知道自己"出了问题"

② 没说交给谁
③ 没说在停之前要留下什么
```

对照可判定版本：

```
✅ "If 3 次远程排查都失败: 停止自动处理，
    转交值班工程师，并附上已尝试的步骤清单"

✅ "If 出现硬件异常码 E-2xx: 不走软件路径，
    直接派单"
```

> 判据：**这条规则里的条件，能不能被脚本判定？**
> 能 → 合格；不能 → 还是废话。

## 三条写法纪律

**① 条件必须是可观察谓词**

```
✅ 退出码非零
✅ 输出中不含 "0 failures"
✅ 连续 3 次失败
✅ 出现特定错误码
❌ "感觉不对" / "不确定" / "有问题"
```

**② ⭐ 升级包要带东西**

停下来的时候不能空手上交：

```
□ 已尝试的步骤与结果
□ ⭐ 当前状态（做到哪一步、产物在哪）
□ 失败的原始错误信息（不要转述）
□ 已排除的可能性
```

最后一条最容易被漏——**没记下"已排除什么"，
接手的人会把你试过的再试一遍**。

**③ 升级目标要具体**

```
❌ "交给人工"
✅ "转交值班工程师（#oncall）"
✅ "派单给硬件组"
✅ "交给 code-reviewer 子代理复核"
```

## 完整示例

```markdown
## Validation

- `npm test -- --testPathPattern=auth` → 期望 `0 failures`
- `ls -la dist/report.html` → 文件存在且 > 0 字节
- ⭐ 报告中的记录数 == 输入记录数（不等则视为失败）

## Escalation

- If 测试失败且错误信息含 `ECONNREFUSED`:
  → 数据库未启动，先跑 `docker compose up -d db`，重试一次
- If 重试后仍失败:
  → ⭐ 停止，转交 #backend-oncall，附带：
     测试输出原文、已尝试的修复、当前 git sha
- If 输入记录数 > 10,000:
  → 分批处理，不要一次性加载（见 references/batch.md）
- If 报告生成成功但记录数不匹配:
  → ⭐ 视为失败，删除产物，不要交付
```

注意最后一条——**它把"跑通了但结果是错的"显式定义为失败**。
这正是 `failure-modes-doc.md` 强调的那类最危险的失败。

## 自查

```
[ ] Validation 每条都是"确切命令 → 可观察判据"？
[ ] ⭐ Escalation 的条件都能被脚本判定吗？
[ ] 每条 Escalation 都指明了交给谁？
[ ] ⭐ 升级包里要带的东西写清楚了吗？
[ ] 有"跑通但结果错"这一类被显式定义为失败吗？
[ ] 没有任何 "if something goes wrong" 式的措辞？
```

## 一条延伸

> ⭐ **Validation 章节是"证据先于声明"的落地方式。**

`grounding-verification.md` 说"未验证就声称成功是不诚实"——
Validation 章节就是让这个要求**可执行**的地方：
**它明确定义了什么算证据。**

没有这一节，agent 会把"步骤走完了"当成"任务完成了"。
