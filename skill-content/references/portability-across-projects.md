## 1. ⭐⭐⭐⭐⭐ 三种耦合

| 类型 | ⭐ 例子 | 搬到别处会怎样 |
|---|---|---|
| **环境** | 绝对路径、内部命令、特定目录结构 | ⭐⭐⭐⭐ 直接跑不了（响的失败） |
| ⭐⭐⭐⭐⭐ **组织** | 缩写、内部系统名、团队惯例 | ⭐⭐⭐⭐⭐ **照跑，结果错（静的失败）** |
| ⭐⭐⭐⭐ **模型** | 依赖某模型的默认行为 | ⭐⭐⭐⭐ 换模型后行为漂移 |

> ⭐⭐⭐⭐⭐ **中间那一行最危险**——
> 这跟"依赖缺失是响的失败，假设不成立是静的成功"完全同构：
> ⭐⭐⭐⭐⭐ **环境耦合会报错，组织耦合不会。**

## 2. ⭐⭐⭐⭐ 环境耦合：写死的路径与命令

三种典型写法，都应替换：

```
❌ /Users/alice/project/config.yaml
✅ ⭐⭐⭐⭐ 相对仓库根，或用 ${CLAUDE_SKILL_DIR}（引用自带资源）

❌ "先跑 internal-tool sync"
✅ ⭐⭐⭐⭐ "先同步数据（命令见 README）"
   → ⭐⭐⭐⭐⭐ 更好：写成"如果没有同步命令，停下来问"

❌ "src/main/java/com/company/..."（假定目录结构）
✅ ⭐⭐⭐⭐ "先定位配置目录（常见位置：./config、./conf）"
```

> ⭐⭐⭐⭐ 第二条的第二选项值得记：
> ⭐⭐⭐⭐⭐ **"找不到就停下来问"比"写死一个命令"可迁移得多**，
> 而且它同时是 `default-actions.md` 的正确姿势——
> 给一个显式出口，而不是让模型猜。

一个额外的坑：**技能里写"运行 `npm test`"是对 npm 项目的假设**
（项目可能用 pnpm/bun/make）。
⭐⭐⭐⭐ 可迁移写法："运行项目的测试命令（先查 `package.json` 的 scripts）"。

## 3. ⭐⭐⭐⭐⭐ 组织耦合：只有这里才懂的词

> ⭐⭐⭐⭐⭐ **这是技能里价值最高、也最不可迁移的部分。**

```
"按 SOP 走"        → 哪份 SOP？
"同步到 CRM"        → 哪个系统？字段叫什么？
"走审批流"          → 谁批？
"用上周的做法"      → ⭐⭐⭐⭐⭐ 完全不可迁移
```

矛盾在于：⭐⭐⭐⭐⭐ **恰恰是这些内容让技能有用**
——去掉它们，技能就退化成通用提示词。

所以结论不是"删掉"，而是：

> ⭐⭐⭐⭐⭐ **把它们集中到一个明确标记为"本项目特有"的章节，
> 而不是散落在流程各处。**

理由有三个，都指向可维护性：

```
① ⭐⭐⭐⭐ 迁移时只需替换这一节
② ⭐⭐⭐⭐ 散落时你不知道哪句是组织特有的
③ ⭐⭐⭐⭐⭐ 术语表那一份已经证明：
   模型不会做同义消解，缩写必须显式定义
```

配套动作：⭐⭐⭐⭐ **给每个缩写第一次出现处补全称**
——这也是术语表那份的第三列（"不要用的说法"）要解决的问题。

## 4. ⭐⭐⭐⭐⭐ 模型耦合：只对某个模型成立

> ⭐⭐⭐⭐ **"提示性能跨模型只弱相关"**——
> 所以在一个模型上调优出的写法，换模型后未必有效。

三类典型耦合：

**① ⭐⭐⭐⭐⭐ 依赖"模型自己会想到"的默认行为**

```
"检查是否有问题"  → 强模型会展开检查项，弱模型只扫一眼
```

> ⭐⭐⭐⭐⭐ **强模型上表现好的技能，往往正是因为省略多**——
> 那些省略在弱模型上变成漏洞。
> ⭐⭐⭐⭐ 这就是"弱模型有技能反而更差"的一个机制解释。

**② ⭐⭐⭐⭐ 依赖某模型的啰嗦/简洁倾向**

```
不加长度约束，在 A 模型上刚好，在 B 模型上膨胀 3 倍
```

**③ ⭐⭐⭐⭐⭐ 升级模型后遗留的验证指令**

```
旧模型需要"再检查一遍"，新模型本身会验证
→ ⭐⭐⭐⭐⭐ 保留会导致过度验证（官方明确建议：升级时做减法）
```

对策：⭐⭐⭐⭐⭐ **在正文里显式写"能力不足时的降级路径"**，
而不是让模型隐式降级（见 `prompt-altitude-three-laws.md`）。
这也是唯一能让同一份技能跨模型档位可用的写法。

## 5. ⭐⭐⭐⭐ 分层：把不可迁移的部分隔离出去

三层结构，越靠上越可迁移：

```
⭐⭐⭐⭐⭐ L1 通用方法（可迁移）
   "先定位配置，再校验，再写入"

⭐⭐⭐⭐ L2 组织约定（半可迁移）
   术语表、系统名、审批人

⭐⭐⭐ L3 环境细节（不可迁移）
   路径、命令、版本号
```

| 层 | 放哪 | ⭐ 为什么 |
|---|---|---|
| L1 | SKILL.md 正文 | ⭐⭐⭐⭐ 每次都要读 |
| L2 | ⭐⭐⭐⭐ `references/` 或术语表 | 按需加载，迁移时替换 |
| L3 | ⭐⭐⭐⭐⭐ **不写进技能，改为运行时探测** | ⭐⭐⭐⭐⭐ 写进去必腐烂 |

> ⭐⭐⭐⭐⭐ L3 那条是最有价值的一条：
> **环境细节的正确处理方式不是"写清楚"，是"不写，改为查"。**
>
> 写清楚 → 换个环境就错，而且不会报错（模型会照着找一个不存在的路径）。
> 运行时探测 → 找不到就停下来问。

这也呼应"依赖声明"那份：⭐⭐⭐⭐
**L3 里只有少数几条该被声明为真依赖（缺了就快速失败），
其余都该是"运行时探测 + 找不到就问"。**

## 6. ⭐⭐⭐⭐ 迁移测试

> ⭐⭐⭐⭐⭐ **可迁移性不需要专门测，一次"第二读者测试"就能暴露大半。**

三个动作，按成本排序：

**① ⭐⭐⭐⭐⭐ 让没参与编写的人读一遍**

```
他问的每个问题 = 一处组织耦合
```

> ⭐⭐⭐⭐ 这是 `second-reader-test.md` 的结论在新维度的复用：
> ⭐⭐⭐⭐⭐ **agent/人提出的每个澄清问题，都是一处缺失的语境。**

**② ⭐⭐⭐⭐ 换一个仓库跑一次（或做思想实验）**

```
全新克隆、CI 环境、没有本地 .env
→ 环境耦合会立刻暴露（响的失败）
```

**③ ⭐⭐⭐⭐ 换一个模型档位跑一次**

```
弱档跑一遍 → 模型耦合会暴露（省略变漏洞）
```

> ⭐⭐⭐⭐ 三个动作分别对应三种耦合，且**成本都很低**。
> ⭐⭐⭐⭐⭐ 最该做的是第 ① 个——它零成本，
> 而组织耦合正是唯一会静默出错的那一类。

---

## 一句可贴在墙上

> ⭐⭐⭐ **环境耦合会报错，组织耦合不会——
> 所以把"只有这里才懂的词"集中到一节，
> 并让没写过它的人读一遍。**
