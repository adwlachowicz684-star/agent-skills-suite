## 1. ⭐⭐⭐⭐⭐ 不要陈述显然

> ⭐⭐ **Claude 已经会写代码，也能读你的代码库。**
> 一个只是复述"Claude 本来就会做的事"的技能，**增加了上下文却没有增加价值**。

```
❌ "先读懂代码，再定位相关文件，然后修改"
✅ 只写把它⭐ 推出常规思维方式的信息
```

> ⭐⭐⭐ **如果你在发布一个"知识型"技能，重点是那些
> 能让 Claude 摆脱默认行为的信息。**

官方举的例子是 frontend design skill：它不是教 Claude 怎么写 CSS，
而是把"避免 Inter 字体和紫色渐变"这类**设计品味**编码进去——
那是工程师跟客户反复迭代才沉淀出来的，模型自己不会。

**判据**：⭐ **这段内容，一个没装技能的 Claude 会自己想到吗？**
会 → 删掉。

## 2. ⭐⭐⭐⭐⭐ Gotchas 是最高信号内容

> ⭐⭐⭐ **任何技能里信号最高的内容就是 Gotchas 章节。**

它应该从"Claude 用这个技能时反复踩的坑"里长出来，并持续更新。
官方给的三条样例，每一条都是**模型不可能推理出来的**：

```
① "subscriptions 表是 append-only。
   你要的那行是 version 最大的那行，不是 created_at 最近的那行。"

② "这个字段在 API gateway 里叫 @request_id，
   在 billing service 里叫 trace_id。它们是同一个值。"

③ "Staging 即使 Stripe webhook 根本没处理也返回 200。
   真实状态要去 payment_events 里查。"
```

三条的共同结构值得照抄：

| 成分 | 例 |
|---|---|
| 表面现象 | 有个 subscriptions 表 |
| ⭐ 反直觉的真相 | 最新的一行不是你要的 |
| ⭐ 正确的替代动作 | 取 version 最大的 |

> ⭐ **这也顺带解释了为什么"别把 HTTP 200 当成功"要单独写一条**——
> 第 ③ 条就是它的具体形态。

与我们已有的呼应：**"每纠正模型一个错误就写进 gotchas"**（`eval-case-design.md`）
在这里得到了官方确认，并被定位为**最高信号**，不是可选项。

## 3. ⭐⭐⭐⭐ 避免 railroading

> ⭐⭐ **Claude 一般会努力照你说的做；而技能又极其可复用——
> 所以你要小心把指令写得过细。**
> 给它需要的信息，但**给它适应现场情况的余地**。

```
❌ Step 1 读配置 Step 2 找 URL Step 3 改端口 Step 4 写回
✅ 把配置文件中的数据库端口更新为用户指定的值
```

这与我们已有的"给约束不给流程"（`eight-practical-lessons.md`）**同源**，
但官方给了一个更强的理由：**技能的可复用性越高，过度具体化的代价越大**——
一次写死的流程会在下一个场景失效。

> ⭐⭐⭐ 顺序真的重要时，**写脚本，不是写技能**
> （这是"确定性判断要用确定性机制承载"的又一个来源）。

## 4. ⭐⭐⭐ 想清楚 setup

有些技能需要用户提供上下文才能工作（比如"把站会内容发到 Slack"——
发到哪个 channel？）。

> ⭐ **好做法：把 setup 信息存在技能目录下的 `config.json`。**
> 没配置 → agent 去问用户 → 需要结构化多选时用 `AskUserQuestion`。

```json
{ "slack_channel": "#eng-standup" }
```

这跟我们已有的 `preflight-gate.md`（STEP 0 前置门禁）是**同一件事的两个面**：

| | 时机 | 做法 |
|---|---|---|
| setup 配置 | 首次使用时 | 存 `config.json`，缺失就问 |
| 前置门禁 | 每次执行前 | 声明 + 验证 + 拦截 |

> ⭐ **差别在于：setup 问一次就记住，前置条件每次都要查。**
> 把"每次都要查"的东西做成 setup，会让技能在第二次就跑错。

## 5. ⭐⭐⭐⭐⭐ 描述写给模型，不是写给人

> ⭐⭐ **会话启动时，Claude 会列出所有可用技能及其描述。**
> **这个列表就是它判断"这个请求有没有对应技能"的唯一依据。**
> → ⭐⭐⭐ **description 不是摘要，是"什么时候触发"的描述。**

```
❌ "React skills."（这是摘要）
✅ "Creates and builds React components using Tailwind CSS.
    Use when the user wants to update component styles or UI logic.
    Don't use it for Vue, Svelte, or vanilla CSS projects."
```

注意最后那句**反触发**——没有它，
你的 Angular 迁移技能会在 React 项目上触发，
你的 Python 测试技能会在 Go 代码上触发。

⭐ **把 "babysit" 这类用户真的会说的词写进去。**

## 6. ⭐⭐⭐⭐ 帮 Claude 记住

这是本份最反直觉的一条：

> ⭐⭐⭐ **技能本身可以携带记忆。**
> 可以是 append-only 的 txt 日志、JSON，也可以是 SQLite。

官方例子：一个站会发布技能维护 `standups.log`，记录它每次写过的站会。
**下次运行时，Claude 会读自己的历史，于是能说出"相比昨天有什么变化"。**

用 `${CLAUDE_PLUGIN_DATA}` 拿一个**稳定的存储目录**。

> ⭐⭐⭐ 这给"技能是无状态的"（`four-design-principles-io-contract.md`）
> 补上了精确边界：**指令层无状态，数据层可以有状态。**
> 状态放在数据文件里，不藏在"指令留在对话里"这个事实里——后者不可控。

**三个适用判断**：

```
✅ 适合：需要跨次对比（"这次比上次多了什么"）、累计计数、去重
❌ 不适合：一次性的上下文、会腐烂的事实（见下）
```

⚠️ **别把"容易过期的事实"写进技能**——
程序记忆层没有时间维度（`memory-layering-and-skills.md`）。
**日志天然带时间戳，事实不天然带。**

## 7. ⭐⭐⭐ 存脚本，让它现场生成代码

> ⭐⭐ **你能给 Claude 的最强工具之一就是代码。**
> 给了它脚本和库，它就能把回合花在**组合**上——决定下一步做什么，
> 而不是每次重建样板代码。

做法：

```
在数据技能里放一组取数的 helper 函数
⭐ 把 gotchas 写进 docstring
Claude 现场拼出分析脚本去回答"周二发生了什么"
```

> ⭐⭐⭐ **docstring 是 gotchas 的第二投放点**——
> 它会跟着函数一起被读到，而 references 里的 gotchas 要靠"恰好去读那个文件"。

## 8. ⭐⭐ 自检：七条过一遍

| # | 检查 | 不合格的信号 |
|---|---|---|
| 1 | 没陈述显然 | 大段是模型本就知道的操作 |
| 2 | ⭐ 有 Gotchas 且持续更新 | 一个坑都没写，或写完再没动过 |
| 3 | 没 railroading | 步骤细到 Step 4，但其实可以一句话说清 |
| 4 | setup 想清楚了 | 每次都问同一个问题 |
| 5 | ⭐ 描述是触发条件，不是摘要 | 读起来像产品宣传语 |
| 6 | 需要跨次对比的有日志 | "上次是什么"永远答不出 |
| 7 | 确定性工作有脚本 | 模型每次现写同一段解析 |

---

## 一条诚实的边界

> ⭐⭐ **技能让你的指令稳定，但不会让模型稳定。**
> 同一个技能换一个模型跑，或在同一次模型更新之后跑，输出仍可能不同。

→ 稳定性重要时：**固定你测过的模型 + 升级后重测**
（与 `model-migration-audit.md` 一致）。
