## 1. ⭐⭐⭐⭐⭐ 技能从不说"不适用"

一份典型的技能写了：触发条件、步骤、输出模板、红线。

> ⭐⭐⭐⭐⭐ 它从没写：**"如果你做到一半发现这件事不该用这套流程，怎么办。"**

于是遇到"技能触发了，但实际场景和它设想的不一样"时，
唯一被定义过的动作是：**继续照流程跑完。**

---

## 2. ⭐⭐⭐⭐⭐ 三条不适用，第二条最常见

**① ⭐⭐⭐⭐ 前置不成立**（输入类型不对、环境缺依赖）

已有覆盖：前置门禁、快速失败。这类基本有解。

**② ⭐⭐⭐⭐⭐ 中途发现前提不成立**（最常见，且几乎无覆盖）

```
技能假定"项目使用 pnpm"
做到第 3 步发现其实是 npm，且这个差异会影响输出
```

> ⭐⭐⭐⭐⭐ 这类最危险：⭐⭐⭐⭐ 它不是"跑不动"（会报错，会被处理），
> ⭐⭐⭐⭐⭐ 而是**跑得动，只是结果是另一个场景的结果**。

**③ ⭐⭐⭐⭐⭐ 任务本身不需要这个技能**（触发是对的，但用户真正要的更简单）

```
用户："把这个 typo 修一下"
代码评审技能被触发 → 输出五段架构反馈
```

> ⭐⭐⭐⭐⭐ 这类与"反触发条件"有关，但反触发管的是**不该触发**，
> ⭐⭐⭐⭐⭐ 而它已经触发了——⭐⭐⭐⭐⭐ **触发之后发现不该做，没有任何文档覆盖。**

---

## 3. ⭐⭐⭐⭐⭐ 为什么模型不会自己停

三条，第一条最根本：

**① ⭐⭐⭐⭐⭐ 触发本身是一次"authorization"**

```
系统判定"这个技能适用于当前任务"并加载了它
→ ⭐⭐⭐⭐⭐ 对模型来说，这是**已经做过的一次适用性判断**
→ 它没有理由在加载之后重新判断一次
```

**② ⭐⭐⭐⭐⭐ 停止意味着"我没有完成任务"**

```
按《skill-content》的 `skill-content/references/default-actions.md`：
⭐⭐⭐⭐⭐ 遇到阻碍时默认动作不是停下报告，而是想办法绕过去
```

**③ ⭐⭐⭐⭐⭐ 照做完总是能产出东西**

```
宁可给一份"按流程做出来但可能不适用"的输出
也不给"我认为不适用"——后者看起来像什么都没做
```

> ⭐⭐⭐⭐⭐ 第 ③ 条揭示了这个问题的形状：
> ⭐⭐⭐⭐⭐ **它不是"不知道该停"，是"停下来的产出看起来更差"**——
> 而评分（无论人还是 eval）都偏向于"有东西"。

## 4. ⭐⭐⭐⭐⭐ 判据：照做会不会产生一份看起来有效的错误产物

一句话判据：

> ⭐⭐⭐⭐⭐ **如果照做完，用户会拿到一份格式正确、内容属于另一个场景的产物吗？**

```
会 → ⭐⭐⭐⭐⭐ 必须定义"不适用"的出口
不会（照做完会明显错误/报错）→ 可以不写，让它撞墙
```

三类高命中场景（对照判据自测）：

```
① ⭐⭐⭐⭐⭐ 技能对输入的性质有隐含假定（格式、语言、规模、时效）
② ⭐⭐⭐⭐⭐ 技能的输出会被下游直接消费（改名字段、发通知、写库）
③ ⭐⭐⭐⭐⭐ 技能包含不可逆动作
```

> ⭐⭐⭐⭐⭐ 第 ② 条尤其值得记：⭐⭐⭐⭐ 这类技能照做完不会"看起来不对"，
> ⭐⭐⭐⭐⭐ 它会"看起来对"并进入下游——于是错误在别处发作。

## 5. ⭐⭐⭐⭐⭐ 写法：前置不适用声明

成本约 30 token，放在正文最前（开头是黄金位置）：

```markdown
## 不适用（满足任一则不要执行，直接说明原因）
- 输入不是单个文件，而是整个目录
- 项目中不存在 lockfile（无法判断包管理器）
- 用户明确表示只需要一个快速修复
```

三条写法要求：

```
① ⭐⭐⭐⭐⭐ 每条必须**可判定**（能查、能数、能比对），不是"情况复杂时"
② ⭐⭐⭐⭐⭐ 每条必须**给出动作**——"说明原因"也是动作，不能只写"不适用"
③ ⭐⭐⭐⭐⭐ 条款数量 3–5 条；超过 5 条说明范围本身有问题
```

> ⭐⭐⭐⭐⭐ 第 ② 条最常被省，而省略的后果是模型"决定不适用"但什么都不说，
> ⭐⭐⭐⭐⭐ 用户看到的是它没做——比做错更难排查（至少做错有产物可看）。

一个额外收益：

> ⭐⭐⭐⭐⭐ **写不出三条不适用条件 = 你对这个技能的范围理解还不够**
> （已有结论，此处再次印证：⭐⭐⭐⭐⭐ 它同时也是"发现该做什么"的方式）

## 6. ⭐⭐⭐⭐⭐ 写法：中途发现不适用

前置声明挡不住第 ② 类（中途发现），需要单独一条运行时规则：

```markdown
- ⭐⭐⭐⭐⭐ 执行过程中若发现任一前置假定不成立，
  停止当前流程，报告"不适用：<具体哪一条不成立>"，
  ⭐⭐⭐⭐⭐ 不得继续按流程产出结果。
```

> ⭐⭐⭐⭐⭐ 关键在最后半句："不得继续产出结果"。
> ⭐⭐⭐⭐⭐ 只写"报告不适用"时，模型会**先做完再报告**——
> 于是你拿到一份"按错误前提做出来"的产物 + 一句"顺便说一下可能不适用"。

配套两条：

```
① ⭐⭐⭐⭐⭐ 已完成的写入动作必须报告（不因"不适用"而省略）
② ⭐⭐⭐⭐⭐ 不适用 ≠ 失败：不要写成"若失败则……"，否则它会试图"修复"后继续
```

> ⭐⭐⭐⭐⭐ 第 ② 条的措辞差别很关键：⭐⭐⭐⭐ "失败"触发重试与绕路，
> ⭐⭐⭐⭐⭐ "不适用"触发停止——两者在模型看来是完全不同的指令类别。

---

## 7. ⭐⭐⭐⭐⭐ 三种"不适用"的处置不同

| | 处置 | 说明 |
|---|---|---|
| ⭐⭐⭐⭐⭐ 前置不成立 | 停止，快速失败 | 还没产生任何副作用 |
| ⭐⭐⭐⭐⭐ 中途不适用 | 停止 + 报告已完成的动作 | ⭐⭐⭐⭐⭐ 副作用可能已发生 |
| ⭐⭐⭐⭐⭐ 任务不需要它 | ⭐⭐⭐⭐⭐ 降级到更简单的做法，仍然完成 | 不是停止，是换一条更短的路 |

> ⭐⭐⭐⭐⭐ 第三行是这份最容易被写错的地方：
> ⭐⭐⭐⭐⭐ "任务不需要这个技能"不该导致"什么都不做"——
> 用户仍然要那个 typo 被修好，只是不需要五段架构评审。

对应到 typo 例子：

```
❌ "不适用，停止"          → 用户还得自己修
✅ ⭐⭐⭐⭐⭐ "这是单行拼写修复，不适用完整评审流程；
            已直接修改该 typo，未做其他改动"
```

> ⭐⭐⭐⭐⭐ 差别在于：⭐⭐⭐⭐⭐ **"不适用"指的是流程不适用，不是任务不成立。**
> 混淆这两者，是所有"它明明可以做却什么都没做"的成因。

## 8. ⭐⭐⭐⭐⭐ 自检

```
① ⭐⭐⭐⭐⭐ 技能有没有"不适用"一节？（没有 → 只会照做完）
② ⭐⭐⭐⭐⭐ 写了几条？可判定吗？（3–5 条，能查能数）
③ ⭐⭐⭐⭐⭐ 每条都给了动作吗？（只写"不适用"→ 模型会静默不动）
④ ⭐⭐⭐⭐⭐ 中途发现不适用，是停止还是继续产出？（必须写"不得继续产出"）
⑤ ⭐⭐⭐⭐⭐ 区分了"流程不适用"和"任务不成立"吗？
```

一个十秒判断：

> ⭐⭐⭐⭐⭐ **找一个"技能会被触发但其实不该用它"的真实场景，跑一次。
> 它是照做完了，还是说了"不适用"？
> 照做完了 → 那个场景的每一次触发都在产生一份看起来有效的错误产物。**

---

## 一句可贴在墙上

> ⭐⭐⭐ **技能定义了什么时候用，几乎从不定义什么时候中途放弃。
> 而"照做完"总能产出东西，"停下来"看起来像什么都没做——
> 于是默认动作永远是照做完。**
