# 示例即契约：为什么改技能时不能动它

> ⭐ **记录边界情况的示例，
> 是对 description 契约的测试——不是装饰。**

## 示例做三件事

```
① 展示输出长什么样（形状）
② ⭐ 定义边界（什么算"这种情况"）
③ ⭐ 充当回归测试（改动后还能对上吗）
```

多数人只看到第一件，
**而第三件才是它在工程上的真正价值**。

## 为什么一两份干净范例胜过一堆

```
❌ 几十个杂乱的例子
   ⭐ 互相干扰，模型学到的是"平均值"

✅ 一两份干净、完整、典型的范例
```

理由：模型从示例中提取的是**模式**，
多个不一致的示例会让模式模糊。

> ⭐ 判据：**这份示例能单独回答"输出长什么样"吗？**
> 能 → 保留；不能 → 它只是噪声。

## 示例必须与描述对上

```
⭐ 如果 description 声明了 "use when X"，
   那么示例里必须逐字包含 X。
```

为什么：**示例是描述契约的测试**。
如果示例和描述不一致，模型学到两套触发条件。

反向也成立：

```
□ ⭐ description 里提到的每个触发场景，
   都应该能在示例里找到对应
□ 示例里出现的场景，
   ⭐ 如果 description 没提到，应该补上而不是删掉示例
```

第二条容易做反——
发现不一致时**优先补 description**，
因为示例通常来自真实使用，比描述更可信。

## 哪些示例不能删

重构技能时（见 `refactor-pass.md`），
以下属于**行为**，不能动：

```
□ ⭐ 记录边界情况的示例
□ 展示"不该触发"的负例
□ 演示降级路径的示例
□ ⭐ 展示错误处理的示例
```

> ⭐ 判据：**删掉这条示例后，
> 某个场景的行为会不会变得不确定？**
> 会 → 它是行为，不能删。

## 一个完整示例该含什么

```
### 示例：审查一个含认证的 PR

输入：
  PR #4821，改动 auth/session.ts（+47/-12）

过程要点：
  · 第 2 步识别出 token 校验缺失
  · ⭐ 第 4 步走了"安全 → BLOCK"分支

输出：
  BLOCK  auth/session.ts:42
         未校验 token 过期时间
         Fix: 在 decode 后加 exp 检查

⭐ 为什么这是好示例：
   它同时展示了形状、边界（走 BLOCK 分支）和过程
```

注意最后一节"为什么这是好示例"——
**给示例加一句说明，能让模型理解该学什么**，
而不只是模仿格式。

## 四类该有的示例

```
① 典型场景        ——最常见的情况
② ⭐ 边界场景      ——刚好在触发线附近
③ ⭐ 负例          ——不该触发时什么样
④ 失败/降级        ——出错时输出什么
```

多数技能只有 ①，
⭐ **而 ②③④ 才是防止行为漂移的部分**。

## 自查

```
[ ] ⭐ 示例里能找到 description 提到的每个触发场景？
[ ] ⭐ 描述里的 "use when X"，示例里有 X 的原话？
[ ] 示例数量适中（1–3 份完整范例，不是几十个片段）？
[ ] ⭐ 覆盖了边界场景？
[ ] ⭐ 有负例（不该触发）？
[ ] ⭐ 有失败/降级示例？
[ ] 每份示例都完整（含输入、过程要点、输出）？
[ ] ⭐ 重构时，边界示例被保留了吗？
```

## 一条延伸

> ⭐ **示例是最容易被误删的高价值内容。**

它看起来像"可以精简的部分"——
尤其在你想把技能缩短的时候。

但对照 no-op 测试（见 `pruning.md`）：

```
删掉这条示例，行为会变吗？
→ ⭐ 对边界示例来说：会。
```

所以：**修剪时先删形容词和重复规则，最后才考虑示例，
而且边界示例永远不动。**
