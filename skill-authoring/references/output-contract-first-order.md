## 1. ⭐⭐⭐⭐⭐ 默认顺序是反的

多数人（包括多数教程）的顺序：

```
① 想这个技能要做什么
② 写流程步骤
③ 写输入输出
④ 写示例
⑤ 跑一下看看
```

> ⭐⭐⭐⭐⭐ 问题出在第 ② 步先于第 ③ 步。
> 因为⭐⭐⭐⭐⭐ **流程一旦写定，输出就被流程反向决定了**——
> 你会倾向于把流程跑出来的东西当作输出，而不是你真正需要的那个东西。

一个典型症状：

```
流程写完了，写输出时才发现：
"哦，其实我要的是一句结论，不是一份过程报告"
→ ⭐⭐⭐⭐ 但流程已经定了，于是输出被写成流程的日志
```

> ⭐⭐⭐⭐⭐ 这是"伪技能陷阱"的一个入口：
> 技能确实做了事，但产出的是⭐⭐⭐⭐⭐ **过程的副产品，不是你要的结果**。

## 2. ⭐⭐⭐⭐⭐ 流程是模型能推的，输出不是

核心判据（一句话）：

> ⭐⭐⭐⭐⭐ **模型不知道你要什么形状的结果，
> 但它很擅长自己想办法达成一个明确的目标。**

两条推论：

**① ⭐⭐⭐⭐⭐ 流程写得越细，收益越低**

```
"Step 1 读配置 Step 2 找 URL Step 3 改端口"
→ ⭐⭐⭐⭐ 这些模型本来就会
```

> ⭐⭐⭐⭐⭐ 已有结论支撑：**给约束，不给流程**——
> 规定每一步会剥夺它自我调整和错误恢复的能力。

**② ⭐⭐⭐⭐⭐ 输出不写清，就没有第二次机会**

```
输出格式没定义 → 模型按先验给一个
→ ⭐⭐⭐⭐⭐ 下游按它给的解析 → 你的技能被这个偶然的输出形状锁死
```

> ⭐⭐⭐⭐⭐ 真实教训：格式不锁死，下游解析脚本**被折磨得改了三版**。
> ⭐⭐⭐⭐ 而锁死后"偶尔有偏差，示例也能把模型拉回来"——
> **示例不只是初始指令，还是纠偏装置。**

## 3. ⭐⭐⭐⭐⭐ 写不出输出契约 = 不该做技能

这是本份最硬的一条，也是与《skill-selection》的接入口：

`hard-thresholds-matrix.md` 第①问是"输出该是什么"。

> ⭐⭐⭐⭐⭐ 如果把那道题提前到动笔之前，
> ⭐⭐⭐⭐⭐ **它就不是一道评估题，而是一道准入题。**

判据：

```
坐下来，不做任何调研，试着写出输出契约
· 写得出 → 开工
· ⭐⭐⭐⭐⭐ 写不出 → 说明你不知道自己在要什么
           → ⭐⭐⭐⭐⭐ 这时候写流程只会把含糊固化成 300 行
```

> ⭐⭐⭐⭐⭐ 关键差别：写不出输出契约时继续写，
> 你会写出一个⭐⭐⭐⭐ **流程清晰、输出含糊**的技能——
> 而那正是最难改进的一种，因为流程看起来是对的。

自检三问（三问答不出就不要开工）：

```
① ⭐⭐⭐⭐⭐ 跑完之后，交付物是一个文件 / 一段话 / 一次写入？
② ⭐⭐⭐⭐⭐ 它包含哪几个字段或小节？
③ ⭐⭐⭐⭐⭐ 什么情况下算"这份输出是合格的"？
```

## 4. ⭐⭐⭐⭐⭐ 推荐顺序

```
① ⭐⭐⭐⭐⭐ 输出契约（要什么形状的结果）
② ⭐⭐⭐⭐⭐ 验收标准（什么算合格，含反例）
③ ⭐⭐⭐⭐  输入与前置条件（缺什么就不能跑）
④ ⭐⭐⭐⭐⭐ 红线与失败处理（禁止什么、失败时说什么）
⑤ ⭐⭐⭐⭐  流程（能简则简，给约束不给步骤）
⑥ ⭐⭐⭐⭐⭐ 示例（采集，不编）
⑦ ⭐⭐⭐    Gotchas 留空，只写 3–5 条，之后 append
```

> ⭐⭐⭐⭐⭐ 三个值得注意的排序理由：

**① 验收紧接输出**，因为⭐⭐⭐⭐ **验收是输出契约的另一半**——
分开写会导致"输出的字段"和"合格的标准"对不上。

**② 红线和失败处理在第 ⑤ 步之前**，因为⭐⭐⭐⭐⭐ **一旦流程写好，
失败处理会被写成流程的附属**（"第 3 步失败则重试"），
而不是独立的一层。

**③ Gotchas 最后且留空**，因为⭐⭐⭐⭐⭐ **Gotchas 是采集的，不是写的**——
坐下来写产不出它。第一版只写 3–5 条，之后每纠正一次加一条。

## 5. ⭐⭐⭐⭐ 中途发现的两种情况

按推荐顺序写，会在第 ① 步就遇到两种卡壳，各自的应对不同：

**① ⭐⭐⭐⭐⭐ 完全写不出 → 停下来**

```
不知道要什么形状
→ ⭐⭐⭐⭐⭐ 这不是"还没想清楚"，是需求本身不成立
→ ⭐⭐⭐⭐⭐ 先去跑一次真实任务，看实际交付了什么，再回来写
```

> ⭐⭐⭐⭐⭐ 关键：**不要用写技能来代替想清楚。**
> 技能固化的是你已有的理解，它不能替你产生理解。

**② ⭐⭐⭐⭐⭐ 写得出但很含糊 → 那是信号，不是障碍**

```
"输出一份分析报告"
```

> ⭐⭐⭐⭐⭐ 含糊本身告诉你一件事：
> ⭐⭐⭐⭐⭐ **这个技能的价值不在"报告"，而在报告里的某一个判断。**
> 找到那个判断，把它单独写成输出契约的第一项。

一个判据能帮你找它：

> ⭐⭐⭐⭐⭐ **如果去掉技能的这一部分，模型的默认输出里就已经有它了——
> 那这部分不值得写进输出契约。**
> （与 `no-op-and-value.md` 的"没有这个技能也会做的事没有价值"同源。）

## 6. ⭐⭐⭐⭐⭐ 一个十分钟的自检

写完输出契约后，做这一件事：

```
⭐⭐⭐⭐⭐ 不看技能正文，只看输出契约，
        假装自己是下游，问：我能用它吗？
```

三个常见的"不能用"：

| 症状 | ⭐⭐⭐⭐⭐ 缺什么 |
|---|---|
| 不知道有多少项 | ⭐⭐⭐⭐⭐ 分母（见 `enumeration-and-completeness.md`） |
| 不知道哪些是确定的 | ⭐⭐⭐⭐⭐ 置信度标记或来源标注 |
| 不知道有没有漏 | ⭐⭐⭐⭐⭐ 覆盖率或"未覆盖"字段 |

> ⭐⭐⭐⭐⭐ 三个都指向同一件事：
> **输出契约里缺的不是内容，是"这份输出的可信边界"。**

而这条边界⭐⭐⭐⭐⭐ **必须在输出契约里定义，
不能留给流程去"顺便产生"**——流程不会产生它，
因为流程只负责做事，不负责声明做事的结果有多可靠。

> 所以先写输出，再写流程——否则你会得到流程的日志，而不是你要的结果。**
