## 1. 核心判据

> ⭐ **"这一段配得上它的 token 成本吗？"**

每一段常驻内容都在为每一轮付费。
**写之前先问：它是否真的改变了模型行为？**

---

## 2. ⭐ no-op 测试的操作法

```
删掉这一段，模型行为会变吗？
```

- 会变 → 保留
- 不会变 → ⭐ 整段删掉

> 注意是**整段删**，不是改写精简。
> no-op 内容的正确处置是删除，不是压缩。

---

## 3. 三类几乎总是 no-op 的内容

| 类型 | 例子 |
|---|---|
| ⭐ 复述模型已知 | "写代码要遵循良好命名规范"、"改文件前先读" |
| 通用最佳实践 | "要注意代码质量"、"保持简洁" |
| ⭐ 只描述不规定 | "输出结构化的评审结果"（没给结构） |

```
❌ "写代码时要遵循良好的命名规范"        → no-op
❌ "修改文件前先读取文件内容"            → no-op
✅ "subscriptions 表是 append-only，取 version 最高的那行"  → 改变行为
```

---

## 4. ⭐ 一个例外：Gotchas 永远不是 no-op

> ⭐ **Gotchas 是唯一几乎不可能通过 no-op 测试的部分。**

```
✅ "createPayment() 余额不足返回 null，不是抛错——必须显式检查"
✅ "staging DB 在 UTC 午夜重置——23:30 之后别跑迁移"
✅ "deploy-service 在服务名含大写时会静默失败"
```

> ⭐ **修剪时永远别动 Gotchas。**（与 `skill-types.md` 一致）

理由：这些内容**模型不可能自己知道**，删掉它行为一定会变（变差）。

## 5. 知识性技能的门槛

如果你发布的技能**主要是知识性的**，
那它的价值必须来自**"把 Claude 推出它默认的思维方式"**。

> 官方例子：前端设计技能专门避开 Inter 字体和紫色渐变这类套路。

判据：

```
这段知识是模型"知道但不会主动做"，还是"本来就不知道"？
前者 → 有价值（改变默认行为）
后者 → 有价值（补充信息）
⭐ "大家都知道、模型也会做" → 无价值
```

---

## 速查

| 内容 | 处置 |
|---|---|
| 复述模型已知 | 删 |
| 通用最佳实践 | 删 |
| 只描述不规定 | 改成明确格式 |
| ⭐ Gotchas | ⭐ 永远保留 |
| 改变默认行为的知识 | 保留 |
