## 1. 改写前

```yaml
description: "用于检查代码和帮助修复 bug 的工具。"
```

**命中率问题**：几乎不触发。

---

## 2. 三个问题

```
① ⭐ 范围过宽——几乎所有编程类技能都符合这个描述
② ⭐ 与通用能力冲突——系统更倾向于调用"通用代码助手"
③ ⭐ 缺少触发场景和边界——没说擅长什么、何时使用
```

> 第 ② 条最值得注意：
> **写得宽 = 在和模型的默认能力竞争**，而默认能力通常赢。

---

## 3. 改写后

```yaml
description: "当用户要求审查 Python 代码性能、查找内存泄漏或优化 SQL 查询时触发；
              专注后端服务代码的深度分析与重构建议。"
```

---

## 4. 三个改进点

| 改进 | 效果 |
|---|---|
| ⭐ **锁定高权重触发词** | Python / 性能 / 内存泄漏 / SQL |
| **边界清晰** | 后端服务、深度分析、重构建议 |
| ⭐ **降低误调用** | 明确"这类问题优先使用本技能" |

---

## 5. ⭐ 六条常见错误清单

| 错误 | 表现 |
|---|---|
| **描述过长** | ⭐ 超过 200 字，关键信息被稀释，扫描成本增加 |
| **用形容词** | "强大/智能/好用"——缺少实质性动词和名词 |
| ⭐ **忽略文件夹命名** | `skill-01` 的匹配效果远不如 `review-code` |
| ⭐ **正文与描述不一致** | 描述声称做 A，正文在做 B → 执行混乱 |
| **输入输出不稳定** | 字段和格式频繁变化，降低系统调用意愿 |
| 缺触发场景与边界 | 见第 2 节 |

第三条容易被忽略：**目录名本身就是信号**。
`skill-01` 对模型毫无信息量，`review-code` 有。

第四条更危险——**它会通过所有结构校验，
但每次执行都不对**。这正是 `skill-structuring` 的 `frontmatter-pitfalls.md` 说的
"第一阶段的 loaded 只代表文件存在"。

---

## 6. ⭐ 一个强烈推荐的实验

```
① 挑一个调用率最低的技能
② ⭐ 只改 description（不动正文）
③ 按"对象词 + 动作词 + 约束词"的公式重写
④ 测调用率变化
```

> ⭐ **只改一个变量**是这个方法有效的前提——
> 与 `claude-ab-loop.md` 的"每次只改 1–2 个变量，否则无法归因"一致。

---

## 速查

| 检查 | 处置 |
|---|---|
| 超过 200 字 | 砍 |
| 有"强大/智能" | 换成动词 + 名词 |
| 目录名是 skill-01 | ⭐ 改成有意义的 kebab-case |
| 描述与正文不符 | ⭐ 对齐（否则执行混乱） |
| 想验证效果 | ⭐ 只改 description，测调用率 |
