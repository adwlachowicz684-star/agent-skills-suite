## 五种架构模式

从顶级仓库提炼，每个都给了代表案例与典型行数。

### ① 线性流程（77 行）

**代表**：OpenAI `vercel-deploy`

```
步骤 1 → 2 → 3 → 完成
```

**技巧**：安全默认值 + 超时提示 + 负面指令。适合固定步骤、一次走完。

### ② 决策树 + 按需加载（224 行）

**代表**：OpenAI `cloudflare-deploy`

```
判断类型 → 分支 A / B / C → 各分支按需读 references/
```

**技巧**：用"我需要运行代码"这类**用户真实说法**做分支条件，
不要用"计算产品"这种术语。

### ③ 循环迭代（371 行）

**代表**：obra `test-driven-development`

```
跑 → 检查 → 修 → 再跑 → 直到通过
```

**技巧**：强硬语气 + 借口反驳表。适合有明确通过条件的任务。

### ④ 接力棒循环（203 行）

**代表**：Google `stitch-loop`

```
会话 N 结束 → 写 next-prompt.md → 会话 N+1 读它继续
```

**技巧**：**文件即状态**。不是比喻——上下文窗口是易失的、有损的、会截断的。

### ⑤ 多阶段 + 检查点（502 行）

**代表**：`discovery-process`

```
阶段 1 → CONFIRM（人工确认）→ 阶段 2 → CONFIRM → …
```

**技巧**：把 CONFIRM 节点单独抽出，让长流程可控。

## 决策树

```
任务有明确的通过条件吗？
├─ 有，需要反复修正     → ③ 循环迭代
└─ 无
   ├─ 有多种输入类型？   → ② 决策树
   └─ 单一输入
      ├─ 步骤少于 5 步？  → ① 线性流程
      ├─ 跨多次会话？     → ④ 接力棒
      └─ 很长且需人工确认 → ⑤ 多阶段+检查点
```

## 四种约束型模式

渐进式披露只解决**上下文**问题。这四种分别解决别的问题：

| 模式 | 解决什么 | 怎么做 |
|---|---|---|
| **模板驱动** | 输出漂移 | 给固定输出模板，模型填空 |
| **脚本增强** | 计算可靠性 | 确定性逻辑放 `scripts/`，不占上下文且结果确定 |
| **知识分层** | 领域知识过载 | `references/` 按需加载 |
| **工具隔离** | 权限越界 | `allowed-tools` 白名单只给必需项 |

## 自由度校准

> **约束强度要匹配任务脆弱性。** 这是最核心也最易忽略的原则。

| 档位 | 形式 | 何时用 |
|---|---|---|
| **高** | 文本指令、启发式 | 多种方法有效；决策依赖上下文 |
| **中** | 伪代码 / 带参模板 | 有首选模式；可接受一些变化 |
| **低** | 精确脚本，参数少或无 | 脆弱易错；一致性关键；必须按序 |

**低自由度示例**：

```bash
python scripts/migrate.py --verify --backup
```

> 不要修改这条命令或添加额外参数。

**高自由度示例**：

```
分析代码结构与组织
检查潜在 bug 或边界情况
建议可读性改进
```

**比喻**：把 Claude 想成探路的机器人——
**两侧悬崖的窄桥**（只有一条安全路径）→ 给精确护栏；
**无危险的开阔地**（多条路都通）→ 给大方向，信任它找路线。

**判断问句**：*这件事做错了有多严重？有多少种正确做法？*

## 组合与编排

多个技能怎么配合：

| 方式 | 适用 |
|---|---|
| **串行** | 输出接输入，链式 |
| **并行** | 互相独立，同时跑 |
| **条件** | 按判断选分支 |
| **循环** | 直到满足条件 |
| **嵌套** | 大流程里调子技能 |

**三条硬性原则**：

1. **I/O 契约明确**——上游给什么格式，下游要什么格式
2. **超时设为 90 秒**——别让一个环节挂死整条链
3. **分支条件必须可执行**——写成能判定的检查，不写"视情况而定"

## 与其他机制的配合

> **MCP server 处理认证、连接管理、原子操作；
> 技能提供领域智能、工作流逻辑、编排这些工具的用户交互层；
> Hooks 把它们接成事件驱动的自动化。**

战略判断：**MCP 趋向商品化，技能才是差异化所在。**
站在现有 MCP 上建，别重造连接层。

## 七个交互微模式

> ⭐ **这些出现在设计良好的技能里，直接抄**：

| 模式 | 作用 | 例子 |
|---|---|---|
| **标志解析** | 从 `$ARGUMENTS` 解析命名参数 | `depth:deep` · `file:path` · `quick` |
| **分阶段执行** | 多步 + 用户检查点 | Discover → Plan → Implement |
| **深度校准** | 按上下文调整细致程度 | Light / Standard / Deep |
| ⭐ **批评者姿态** | 显式切换 agent 角色 | "你现在是批评者，不是规划者" |
| **输出模板** | 固定格式保证一致 | 状态面板、审查格式 |
| **迭代闸门** | 继续前暂停等反馈 | "应用这些改动？还是要调整？" |
| **默认动作** | ⭐ 无参数也要有用 | 零参数 = 最常用的工作流 |

**错误处理**（预见会出什么问题）：

```markdown
## Error Handling
- 没有提供输入：显示用法示例并退出
- 文件未找到：报告缺失路径并给出替代建议
- ⭐ MCP 不可用：说明缺什么，并询问是否继续
```

**输出格式要显式**：

```markdown
### Output Display
| Column 1 | Column 2 |
|----------|----------|
| [data]   | [data]   |

Then ask: "Apply these changes? Or provide feedback to adjust."
```

**几条设计原则**：

```
□ ⭐ 一个技能一件事——试图做三件事的技能会脆弱且难改
     三个专注的技能好过一个
□ 复杂度匹配任务——5 行的格式化技能没问题，
     200 行的全面审查技能也没问题
     ⭐ 不要过度设计简单任务，也不要低估复杂任务
□ 默认动作——无参数也要有用，且零参数 = 最常见场景
□ ⭐ 优雅失败——出错时说明发生了什么并给修复建议，
     不要静默崩溃
□ 版本化并写文档
```
