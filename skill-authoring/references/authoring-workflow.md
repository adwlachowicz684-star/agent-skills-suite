## 六阶段闭环

```
阶段一 需求捕获  → 理解意图 · 明确触发场景 · 确定输出格式
   ↓
阶段二 编写      → SKILL.md + 辅助资源
   ↓
阶段三 测试执行  → 设计用例 → A/B 测试（with_skill vs without_skill）
   ↓
阶段四 评估评审  → Grader 评分 → 聚合基准 → Analyzer 分析 → 用户评审
   ↓
阶段五 迭代改进  → 分析反馈 → 泛化改进（避免过拟合）→ 重写
   ↓
阶段六 优化发布  → Description 优化 → 训练/测试集分割 → 打包发布
   ↓
   └──────────────── 回到阶段三（循环）
```

## 阶段一：需求捕获

**起点不是"我要一个技能"，是"agent 在哪里反复失败"。**

```
□ 在代表性任务上跑 agent，观察它在哪里挣扎或需要额外上下文
□ 记录失败模式和共性问题
□ ⭐ 增量式构建技能来弥补这些不足——不要一次造大的
```

判据：如果你说不出"它上次具体错在哪"，就还没有需求。

## 阶段二：编写

**先写 description，再写正文。**

```
1. 写 description：What + When + 差异点
2. ⭐ 读回来：agent 看了这句话，知道该不该触发吗？
3. 写能工作的最小正文
4. 测试暴露缺口时才补充——不要预先堆内容
5. 正文太长时把细节移到 references/
```

## 阶段三：测试执行

两类测试分开做：

| 测试 | 怎么测 | 判据 |
|---|---|---|
| **触发测试** | 不指名调用，问一个该技能该处理的问题 | 不触发 → 修 description |
| **执行测试** | 指名调用 | 输出错 → 修正文 |

> ⭐ **这个分离是排查的核心**：不触发修 description，触发了做错修正文。
> 混在一起测，你不知道该改哪里。

正式评估还要有 **A/B 测试**：`with_skill` vs `without_skill` 两遍对比。

## 阶段四：评估与评审

三个角色分工见下节。产出：

```
Grader 评分 → 聚合基准 → Analyzer 分析 → 用户评审
```

## 阶段五：迭代改进

**这一阶段最大的风险是过拟合。**

```
□ 遇到顽固问题，换个隐喻或推荐不同的工作模式
□ ⭐ 解释"为什么"而非堆砌"必须"——LLM 有良好的推理能力
□ ⭐ 泛化而非过拟合：技能要面对无数种 prompt
   ——只为特定测试用例做针对性修改，技能会失去通用性
```

**提取重复模式**：如果多个测试里 agent 都独立写了类似的辅助脚本
（如每次都创建 `create_docx.py`），这是强信号——
**应该把这个脚本放进 `scripts/` 让技能直接调用**。

## 阶段六：优化与发布

```
□ Description 优化（用训练集/测试集驱动，见下）
□ 训练/测试集分割（防过拟合）
□ 打包发布
```

**Description 优化流程**：

```
1. 准备训练集 + 测试集（触发/不触发的 prompt 对）
2. 自动迭代改进描述文本
3. 校验触发准确率
4. ⭐ 防止过拟合特定测试用例
```

## 三个专业化评估角色

| 角色 | 职责 | 核心设计 |
|---|---|---|
| **Grader** | 评估断言是否通过 | **自我批评**——指出断言本身的问题 |
| **Comparator** | 盲比较两个版本的输出 | **双盲实验设计**，去偏见化 |
| **Analyzer** | 事后分析为什么赢家赢了 | 生成**按优先级排序**的改进建议 |

> ⭐ **Comparator 的"盲"很关键**：知道哪个是新版本就会带入偏见。
> 双盲才能测出真实差异。

## Grader 的评分标准

**PASS 的要求**：

```
□ 不仅要有证据
□ ⭐ 还要证据反映"真正的任务完成"，而非"表面合规"
```

**FAIL 包含了一种极易漏掉的情况**：

> ⭐ **"巧合通过"**——断言技术上满足了，但底层任务结果是错的。

最该记住的一句，来自官方指南：

> **"对一个薄弱断言给出'通过'的评级，其危害比毫无用处还要糟糕
> ——它会制造出虚假的信心。"**

这跟 `grounding-verification.md`（**`skill-crafting`**）里
"未验证就声称成功是不诚实"是同一条原则在评估侧的体现。

## 贯穿全程的两条纪律

**① 从 Claude 的视角思考**

```
□ 监控 agent 如何在真实场景中使用你的技能
□ 观察是否有意料之外的执行路径，或对某些上下文的过度依赖
□ ⭐ 特别关注 name 和 description 的效果
```

**② 与 Claude 协作迭代**

```
□ 让 agent 把成功经验和常见错误捕获为可复用的技能内容
□ 当 agent 使用技能偏离预期时，让它自我反思哪里出了问题
□ ⭐ 这个过程帮你发现 agent 实际需要什么上下文，而非提前猜测
```
