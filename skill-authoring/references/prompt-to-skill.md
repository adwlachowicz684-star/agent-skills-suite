## 三个信号

> 出现任一信号，就该把这个工作流固化成技能。

| 信号 | 例子 |
|---|---|
| **重复** | 同一条指令在 **3 次以上**不同会话里出现（如"格式化 Markdown、中英之间加空格、标注代码块"） |
| **纠正** | 你反复纠正同一类错误（"不要用 emoji"、"表格用竖线对齐"） |
| **协作** | 另一个人需要遵循同一流程，或你需要跨会话保持一致标准 |

> ⚠️ **纠正超过两次就成了一条可复用规则**——
> 把它写进技能，而不是每次口头纠正。

> **知识只留在你脑子里，它的生命周期就随会话结束而结束。**
> 外化成技能才保得住。

## 录屏生成技能

> 官方能力（Claude for Mac 的 Cowork）：**不用手写，让 Claude 看你做一遍。**

你给 Claude 一段**屏幕录像**（点击、输入、语音），
Claude 据此提议一个技能，你确认后保存。

**录制前**：
- 更新到最新版 Claude for Mac
- 授予 macOS 权限（辅助功能、屏幕录制）— 可能要重启
- **关掉不想被录到的文件、应用、对话**

> 🚨 **录制期间不要输入密码或密钥、不要显示敏感信息。**
> 整个会话期间**屏幕上的一切和你说的一切都会被采集**。

**录制中**：
- 单次约 **10 分钟**，剩 1 分钟时倒计时，归零自动停止
- ⭐ **边做边解说**——解说提供了屏幕看不到的上下文：
  *你为什么跳过这一步、你如何在两个选项间做选择*

**录制后**：
- 视频和音频**不保留**；保留的是一组**截图**（存在 Cowork 任务里，删任务即删）
- 结果有两种：**新建技能**（标 NEW）或**更新已有技能**（显示基于哪个技能）

> 这个方法最妙的地方：**它捕捉到了你认为理所当然、但从未写下来的判断。**

## 三步转换法

> 你收藏的那些提示词，都可以转成技能。

**Step 1 · 加元数据**

```yaml
---
name: weekly-report
description: 根据本周工作日志和 git 提交生成周报。
  当用户说"周报""写周报""本周总结"时使用。
---
```

> ⭐ **诀窍：把触发词写进 description。**
> 原提示词里的"什么时候用"要**显式写出**，否则自动命中率很低。

**Step 2 · 结构化**

网上收集来的提示词通常是一大段话——**一坨文字 AI 读起来容易走神**。
转换时用标题拆成结构：有标题、有层级、有步骤。

**Step 3 · 放对位置**

```
.claude/skills/<技能名>/SKILL.md     # 一个技能一个文件夹
```

> ⚠️ 一个现实预期：**默认激活率只有 20% 左右**，
> 所以 description 要按 **`skill-evaluating` 的 `triggering.md`** 认真打磨。

## 七步 SOP 制作法

| # | 步骤 | 要点 |
|---|---|---|
| **1** | **收集真实案例** | 找 **3–10 次**真正做过的任务，记录输入、操作顺序、易错点、优秀输出。**来自有效经验，不是凭空想象一套复杂流程。** |
| **2** | **写清边界、输入、输出** | 一句话说"负责什么"，一句话说"不负责什么"。列必要输入 / 可选输入 / 最终交付结构。**能合理推断的信息不必强迫用户补充**；会明显改变结果的缺口才提问 |
| **3** | **改成编号流程** | 把"仔细分析"换成可执行动作（理解目标→读取资料→验证事实→执行工具→整理结果→QA）。分支要明确写 `if` / `when` / `before` / `after` |
| **4** | **拆出 references / scripts / assets** | 每次都要知道的 → SKILL.md；偶尔查阅的长规范 → `references/`；确定性检查 → `scripts/`；固定报告格式 → `assets/` 模板 |
| **5** | **定义验收标准** | **不要以"完成分析"收尾。**明确检查：必要章节齐全？事实有来源？脚本通过？文件生成？符合模板？ |
| **6** | **触发与任务测试** | 至少 **5 个该触发 + 5 个不该触发**的自然表达；再用 **3–5 个没参与编写的真实任务**测最终结果 |
| **7** | **真实使用中迭代** | 每次你纠正 AI 时问：**这是一次性例外，还是该进技能的新规则？** |

> ⚠️ **常见错误**：一个技能包办所有事情——
> **触发条件、输入和成功标准不同的流程应该拆开。**

## 拆分：步骤 vs 规则

> 记录时把两者分开归类，**步骤和规则放不同文件**。

| | 特征 | 例子 |
|---|---|---|
| **步骤** | 有序动作 | 格式化 Markdown → 生成图片 → 转 HTML |
| **规则** | 对**每一步**都生效的约束 | 中英之间加空格、图片用 WebP、标题不超过 20 字 |

**两种常见架构**：

| 风格 | 结构 | 适用 |
|---|---|---|
| **知识库式** | md 层级，每个文件一个知识点（`knowledge/api-spec.md`），SKILL.md 当索引 | 知识密集 |
| **工作流式** | 指挥官 SKILL.md 定义步骤顺序，指向 `workflow/` 每步 + `rules/` 约束 | 流程密集 |

> **多数真实技能是两者混合**：一个工作流，**按需**加载规则文件，
> 保证每个文件只做一件事。

## 分工：Rules / Skill / 提示词

> **持久风格用 Rules，临时任务用提示词，固定流程用 Skill。**

转换时这样分流：

```
原提示词里"永远成立"的部分  → Rules（如"始终用中文、用列表呈现"）
"本次特定"的细节           → 留在对话提示词
"固定流程"                → SKILL.md 的指令
```

**同一个任务可以是"Rules 定基调 + Skill 走流程 + 提示词补细节"**。

> 这也呼应 `skill-crafting` 的 `instruction-layering.md`：
> 别把"日常都要遵守的"塞进技能（技能激活前它可能已经错过了），
> 也别把长流程塞进 AGENTS.md（每个会话都背着无关指令）。

## 三种验证

| 测试 | 做法 | 抓什么 |
|---|---|---|
| **冷启动测试** | 在**没有任何上下文的全新会话**里调用 | 指令缺口——残留上下文会掩盖它们 |
| **边界测试** | 喂畸形、不完整的输入 | 是否优雅处理 |
| **第三方测试** | 让**不熟悉设计的人**跑一遍 | 缺失的解释 |

> ⭐ **如果 AI 误解了意图，简化结构，而不是加更多散文。**

## 自查

```
□ 是否来自真实做过的 3–10 次任务（而非凭空设计）？
□ 步骤与规则是否分开了？
□ "永远成立"的部分是否移到了 Rules？
□ description 是否写进了真实触发词（而非"何时用"的抽象描述）？
□ 是否定义了验收标准（而非以"完成分析"收尾）？
□ 是否做了冷启动测试（全新会话）？
□ 是否有 5 正 / 5 负的触发测试？
□ 是否让不参与编写的人跑过？
□ 是否拆出了 references / scripts / assets？
□ 每次纠正后是否问了"这该进技能吗"？
```
