# 九种技能类型

> Anthropic 的 Claude Code 团队在管理**几百个内部技能**后总结的分类法。
> ⭐ **最好的技能干净地落在某一类里；想兼顾太多事情的反而会跨越几个类别，把 agent 搞糊涂。**

## 九种类型

| # | 类型 | 内容 | 例子 |
|---|---|---|---|
| 1 | **库和 API 参考** | 怎么正确使用某个库/CLI/SDK，含参考代码片段文件夹与 gotchas 清单 | `billing-lib`（内部计费库的边界情况）、`internal-platform-cli`、`sandbox-proxy` |
| 2 | **产品验证** | 怎么测试或验证代码是否正常工作，常配合 Playwright、tmux | 让 Claude 录视频输出、每步做程序化断言 |
| 3 | **数据获取与分析** | 连接数据源与监控栈，含带凭证的获取库、仪表盘 ID、常见工作流 | `funnel-query`、`cohort-compare`、`grafana`、`datadog` |
| 4 | **业务流程与团队自动化** | 把重复工作流自动化成一条命令 | 好习惯：**把上次结果存进日志，下次能对比"什么变了"** |
| 5 | **代码脚手架与模板** | 为特定功能生成框架样板 | 脚手架涉及自然语言需求时特别有用（纯代码解决不了的部分） |
| 6 | **代码质量与审查** | 强制执行质量标准并协助审查，可含确定性脚本 | `adversarial-review`（**起一个 fresh-eyes 子代理来批评代码**）、`code-style`、`testing-practices` |
| 7 | **CI/CD 与部署** | 拉取、推送、部署代码 | `babysit-pr`（监控 PR、重试 flaky CI、解冲突、启用自动合并） |
| 8 | **Runbook** | 接收症状（Slack 线程、告警、错误签名），走多工具排查流程，输出结构化报告 | `service-debugging`、`oncall-runner`、`log-correlator` |
| 9 | **基础设施运维** | 日常维护与操作流程，**涉及破坏性操作的需要护栏** | `resource-orphans`、`dependency-management`、`cost-investigation` |

> ⭐ **验证类技能对输出质量影响最大**——
> 团队认为**值得让一个工程师花一周时间把验证技能做到极致**。

## Gotchas 才是最高信号

> ⭐ **任何技能里最有价值的内容就是 Gotchas 部分。**
> 这些应该来自 **Claude 实际踩过的坑**，而且要不断补充。

**真实的例子**（注意它们有多具体）：

```
□ "subscriptions 表是 append-only 的，你要找的是 version 最高的那行，
   不是最新 created_at 的那行。"

□ "这个字段在 API 网关里叫 @request_id，在计费服务里叫 trace_id，
   它们是同一个值。"

□ "Staging 环境返回 200 不代表 Stripe webhook 真的处理了，
   去查 payment_events。"
```

> ⭐ 对照 `skill-refining` 的 `pruning.md` 的 no-op 测试：
> **Gotchas 是唯一几乎不可能通过 no-op 测试的部分**——
> 删掉它行为一定会变。修剪时**永远不要动这一节**。

## 九条实践建议

**① 不要写 Claude 已经知道的东西**

> Claude 会写代码，也能读你的代码库。
> **一个把本来就会做的事复述一遍的技能，只会增加上下文而不创造价值。**

> 好例子：前端设计技能**专门避开 Inter 字体和紫色渐变这类 AI 模式**——
> 它针对的是"怎么帮 Claude 提升设计品味"，而不是教它写 CSS。

**② Gotchas 是最高信号**（见上）

**③ 用文件系统做渐进式披露**

> 技能是个文件夹，**整个文件系统都应该是上下文工程的一部分**。
> 告诉 Claude 里面有什么文件，它会在合适的时候自己读。
> 详细函数签名拆到 `references/api.md`，输出模板放 `assets/`。

**④ 不要过度约束 Claude**

> 技能可复用性很强，**指令太具体反而会适得其反**。
> **给足信息，留够灵活度**（呼应自由度校准）。

**⑤ 为模型写描述，不是为人写**

> 启动时扫描所有技能的 description，用它决策"有没有技能能处理这个请求"。
> 所以 description 是告诉 Claude **什么时候该触发**，不是给人看的摘要。

**⑥ 帮 Claude 记住东西**

> 技能可以在自身存数据——从简单文本日志到 SQLite。
> 如 `standup-post` 维护 `standups.log`，下次运行知道昨天以来什么变了。
> `${CLAUDE_PLUGIN_DATA}` 提供了稳定的存储目录（呼应 `skill-orchestration` 的 `memory-state.md`）。

**⑦ 内置脚本，让 Claude 生成代码给 Claude**

> 给脚本和库，让它把精力花在**组合脚本**上，而不是从头写样板。
> 如 `data-science` 含一组数据获取函数库，Claude 随时生成脚本组合它们。

**⑧ 使用按需钩子**

> 有些钩子开着烦人但关键时刻极其有用：
> `/careful` 在 Bash 上拦截 `rm -rf` 和 `DROP TABLE`（只有动生产时才需要）；
> `/freeze` 禁止编辑指定目录之外的文件（调试时很管用）。

**⑨ 度量与组合**

> 用 `PreToolUse` 钩子记录每个技能的使用情况——
> 看出**哪些受欢迎、哪些比预期用得少**。
> 技能可以互相引用——只要装了，模型就能按名字调用。

## 分发：有机生长

```
1. 创建后上传到沙箱文件夹
2. 在 Slack 里告诉大家
3. 有了 traction 再提 PR 移入正式市场
```

> ⭐ **Anthropic 没有中央团队决定哪些技能进市场。**
> 这种有机生长的模式让**最实用的技能自然浮现出来**。

**分享的两种方式**：

```
□ 检入代码仓库（./.claude/skills）
  适合仓库少的小团队
  ⚠️ 每个检入的技能都会增加一点模型上下文开销

□ 发布到插件市场
  规模上去之后能自由分发，团队成员自己选装什么
```

## 选型速查

> 一个很好用的判断法——**先用自然语言写出第一版，然后读一遍**：

```
读起来像"流程"        → 技能（skill）
读起来像"函数签名"    → 工具（tool）
读起来像"API 契约"    → MCP server
读起来像"岗位描述"    → 子代理（subagent）
```

**反过来看也一样**：

```
□ 发现自己在往技能正文里塞函数逻辑 → 该放进 scripts/
□ 发现自己在往工具描述里塞流程散文 → 该放进技能
```

## 自查

```
□ 这个技能是否干净地落在九种类型中的一类（而不是横跨几类）？
□ 是否有 Gotchas 章节，且都来自真实踩坑？
□ 是否写了 Claude 本来就会的东西（应删）？
□ 是否过度约束（该给自由度的地方给了死指令）？
□ description 是为模型写的（触发条件）而非给人看的摘要？
□ 是否需要跨会话记忆（需要则用数据文件 + ${CLAUDE_PLUGIN_DATA}）？
□ 是否该内置脚本而非让 Claude 从零写样板？
□ 是否该配按需钩子（只在特定场景才开）？
□ 是否有使用度量（知道它在不在用）？
□ 用自然语言读一遍——它像流程、函数、契约还是岗位描述？
```
