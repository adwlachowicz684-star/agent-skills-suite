## 1. 激活决策的真实机制

这是理解后面所有数据的前提：

> ⭐ **技能激活是纯 LLM 推理，不是 embedding 检索、不是分类器、不是关键词匹配。**

机制是这样的：

```
启动时 → 所有技能的 name + description 注入系统提示（每个约 100 tokens）
       → 模型用普通推理判断"这个请求有没有对应的技能"
       → ⭐ 判定之后，才加载完整 SKILL.md 正文
```

**直接推论**：

1. ⭐ **description 是控制激活的唯一杠杆**——正文写得再好，如果没被激活，等于不存在
2. **判定发生在正文加载之前**——所以"把触发条件写在正文里"是**结构性错误**，太晚了
3. 激活失败最常见的表现是：模型**直接把活干了**，压根没想起有这个技能

## 2. 四档实测数据

多个独立来源的激活率分档（社区实测，非官方基准）：

| 写法 | 激活率 | 说明 |
|---|---|---|
| 基础描述（"Helps with PDFs"） | ~20% | 太模糊，模型判断不了范畴 |
| 优化描述（动作 + 对象） | ~50% | 知道了做什么，仍不知何时用 |
| 含 "Use when..." 从句 | 72–90% | 给出触发场景 |
| ⭐ 祈使句 + 否定约束 | ~100% | 见下一节 |

**从 20% 到 100% 的跨越，全部来自 description 这一个字段的写法。**

对照示例：

```
❌ 20%：  description: Helps with PDFs
❌ 50%：  description: Extracts text and tables from PDF files, fills PDF forms.
✅ 72%：  description: Extracts text and tables from PDF files, fills PDF forms,
          merges multiple PDFs. Use when working with .pdf files, document
          extraction, forms, or 'convert PDF'.
```

## 3. 650 次对照实验

一份较系统的自动测试：三个 description 变体 × 四种环境条件，每格重复 3 次，共 650 次。

**三个变体**

| 变体 | 写法 | 激活率 |
|---|---|---|
| A（被动） | "Use when …" | 77% |
| B（扩写） | 同 A 风格，额外堆触发词 | 与 A 相当 |
| C（祈使） | **"ALWAYS invoke … Do not <直接做 X>"** | **100%** |

**C 的模板**

```yaml
description: >
  <领域标识> expert. ALWAYS invoke this skill when the user asks about <触发清单>.
  Do not <直接执行该任务> directly — use this skill first.
```

**为什么 C 有效**

> ⭐ **正向路由（ALWAYS invoke）与否定约束（Do not …directly）必须成对出现。**
> 单独任一个都无效。

原因是失败的根因不是"模型不知道有这个技能"，而是**模型选择了更省事的直接执行路径**。否定约束的作用是把那条退路堵死；正向路由告诉它该走哪条。**两者合起来才是排他性指令。**

**统计口径**：用了 Fisher 精确检验、逻辑回归、Cochran-Mantel-Haenszel 分层分析。

## 4. 一组矛盾证据（重要）

另一份中文实践记录给出**相反结论**：

> "我把所有技能的 description 都统一成了'当……时使用本技能。如果……，不要使用本技能'的格式……
> ⭐ **实测下来，这种做法对提升触发率的帮助很有限，反而会增加调度时的匹配噪音。**
> 触发条件写得精准，比写得宽泛有效得多。"

**两方分歧在哪**

| | 650 次实验（C） | 中文实践（否定排除） |
|---|---|---|
| 否定对象 | **堵住模型的直接执行退路** | **排除别的任务误触发** |
| 目标 | 提高**召回**（别漏） | 提高**精确**（别滥） |
| 结论 | 有效（100%） | 无效且有害 |

> ⭐ **这不是真正的矛盾，是两个不同的否定。**
> - "**不要直接执行 X，先用本技能**" → 治**欠触发**
> - "**如果用户没提 JSON，不要用本技能**" → 治**过触发**
>
> 两者可以同时存在，治的病不同。中文实践那份测的是后者，且它真正想说的是"**别把边界不清的技能靠否定词救回来**"——那条是对的。

**但请注意作用域**：这条否定约束写在 **description** 里（路由层，模型唯一能看到的），
**不是**写在正文里的禁令清单。后者的问题见 `skill-crafting` 的 `guidance-forms.md`——
正文里的"不要做 X"因为没有给出"该做什么"，反而会让输出更差。

> ⚠️ **同一个句式，在 description 里有效，在正文里可能反噬。位置决定效果。**

## 5. 无效手段清单

以下手段实测**没有 measurable change**，甚至有害：

| 手段 | 结果 |
|---|---|
| 填充 frontmatter 的 `keywords` 字段 | ⭐ **无变化，模型忽略它做路由** |
| Pre-prompt hook 强制注入命令 | ⭐ **被动变体下降最多 30pp**（注入指令与技能意图冲突）；对祈使变体无影响 |
| 单纯堆更多触发词（B 变体） | 与 A 相当，无提升 |

**唯一有正向作用的环境改动**：仓库根加 CLAUDE.md 描述项目用途 → **+15pp**（65%）。
推测原因是项目上下文让模型更容易判断"这个请求属于哪类工作"。

## 6. 可执行的收敛建议

1. **默认写祈使句路由 + 堵退路**，模板见第 3 节。这是目前证据最强的单一手段。
2. **别指望 `keywords` 字段**——它不是路由输入。
3. **别用 hook 强制激活**——它会和被动词描述打架，适得其反。
4. **否定词要区分用途**：堵退路（召回）与排误触发（精确）分开写，别混。
5. ⭐ **改完必须自己测**：这些数字来自特定模型、特定环境。
   方法见《skill-evaluating》的 `trigger-eval-set.md`——**用同事的原话测，不要用你写 description 时的措辞**。
6. **边界不清的技能别靠否定词救**——那是粒度问题，应按 `splitting.md` 拆开。
