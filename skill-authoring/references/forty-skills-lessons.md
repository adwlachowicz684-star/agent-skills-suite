## 1. ⭐⭐ 技能默认是欠触发的

> ⭐⭐ **Claude 对加载技能是保守的。**

**排障时的第一反应纠正**：

```
❌ "Claude 坏了 / 技能不生效"
✅ ⭐⭐ "你的 description 和用户实际打的字不匹配"
```

**修法**（三步，立刻见效）：

```
① ⭐ 用⭐ 用户真正会输入的字面触发词重写 description
② ⭐ 稍微强势一点（对应 `pushy-description.md` 的官方建议）
③ ⭐ 触发率会立刻跳上去
```

> ⭐⭐ **"几乎从来不是 Claude 坏了"** 这句话值得当作排障第一条。
> 这与 `trigger-fix-nine-causes.md` 的"不触发九项排查"、
> `library-size-effect.md` 的"激活率基础描述只有 20%"完全同源——
> **欠触发是默认状态，不是故障。**

## 2. 500 行上限

```
⭐ 把 SKILL.md 控制在 500 行以内
⭐ 每个人都无视这一条
```

超了怎么办：**把参考资料移到单独文件，从 SKILL.md 链接过去**——
Claude 只在需要时才加载那些文件。

> ⭐ 这条与主套件里 `budget-truncation.md` 的物理原因对上了：
> **压缩后每个技能只留前 5,000 tokens**，500 行 × 4 字符 ≈ 20,000 字符 ≈ 5,000 tokens。
> **500 行不是风格建议，是物理边界。**

## 3. ⭐⭐ 先做一遍，再写技能

> ⭐⭐ **最好的技能来自一次真实成功的执行。**

```
做法：
① ⭐ 先手动把这件事做一遍
② ⭐ 留意每一步
③ ⭐ 然后让 Claude 来写这个技能
```

> ⭐⭐ **凭想象写出来的技能总是有点不对。**
>
> "有点不对"（slightly wrong）这个措辞很准——
> **它不是明显错误，是⭐ 差那么一点，你会一直觉得别扭却说不出哪里错**。

> ⭐ 这一条与 `skill-evolution-loop.md` 的"从几行字 + 一条踩坑记录起步"、
> `seven-step-authoring.md` 的流程完全一致：
> **技能是经验的沉淀，不是设计的产物。**

## 4. 别用技能教事实

```
⭐ "我们的数据库 schema" 属于 CLAUDE.md
⭐ 技能是给⭐ 程序的，不是给参考资料的
```

> ⭐ 这与 `context-file-selection.md` 的"常驻事实 → 上下文文件，
> 按需程序 → 技能"是同一条界线，且**第二句给了更好的记忆法**：
> **技能 = 怎么做（procedure）；事实 = 上下文文件（reference material）。**

---

## 5. ⭐⭐ 像代码一样版本化

> ⭐⭐ **如果技能放在仓库的 `.claude/skills/` 里，它就该在 PR 里被评审。**

**理由来自作者自己的事故**：

```
⭐⭐ "我不止一次对技能做了破坏性改动，⭐ 静默地影响了整个团队。"
```

> ⭐⭐⭐ **"静默地影响了整个团队"** —— 这是技能在团队环境里最危险的属性：
> 你改了一个文件，**没有 CI 报警、没有构建失败、没有 changelog 通知**，
> 但所有人的 agent 行为都变了。

这与 `skill-overrides-audit.md` 那起 deploy 事故是同一类问题
（**没人知道当前生效的是哪一份**），也与
`skill-ownership-changeflow.md` 的"没跑 eval 的 PR 不接受"直接呼应。

## 速查

```
□ ⭐⭐ 技能默认欠触发 → 排障第一反应是"description 不匹配"
      ① 用户字面触发词 ② 稍强势 ③ 触发率立刻跳
□ 500 行上限（⭐ 人人都无视）
      → 参考资料移出 + 链接；⭐ 500 行是物理边界不是风格建议
□ ⭐⭐ 先手动做一遍再写技能；⭐ 凭想象写的"总是有点不对"
□ 技能管程序，事实放上下文文件
□ ⭐⭐ 放仓库里就该走 PR 评审
      ⭐⭐ 破坏性改动会⭐ 静默影响整个团队
```

**一句话**：

> ⭐⭐ **技能默认是欠触发的——如果它没在你认为该触发时触发，
> 几乎从来不是 Claude 坏了，而是你的 description 和用户实际打的字不匹配。**
