## 编写质量清单

```
□ name 和 description 是否准确反映功能？
□ ⭐ description 是否包含足够的触发关键词？
□ 正文是否有清晰的分步骤说明？
□ 是否明确了输入输出格式？
□ 边界情况和错误处理是否覆盖？
□ 大段内容是否已拆分到 references/ ？
□ scripts/ 中的脚本是否自包含且有错误提示？
□ ⭐ 是否告诉了 agent 何时加载哪些额外文件？
```

最后一条最常被漏：**写了 `references/api-errors.md` 却没说什么时候读，
等于没写**。正确写法是给可判定的触发条件：

```
❌ 详见 references/（等于没说）
✅ 当 API 返回非 200 时，读 references/api-errors.md
```

## 常见反模式对照表

| 反模式 | 问题 | 改进 |
|---|---|---|
| **单体式巨型 SKILL.md** | 消耗大量 token，噪声多 | 拆为 L2 核心 + L3 按需引用 |
| **纯指令无解释** | agent 无法灵活应对边界情况 | ⭐ 解释 why，不只堆砌 must/never |
| **过度依赖关键词匹配** | 漏触发率高 | 聚焦用户意图，覆盖多种表述 |
| **没有测试评估** | 无法验证效果 | A/B 测试 + Grader 评估 |
| **脚本无错误处理** | agent 遇错后迷失 | ⭐ 脚本输出有用的错误提示 |
| 重复教模型已知的东西 | 白占 token，还挤掉关键内容 | 只写模型缺的上下文 |
| 技能里放 README/CHANGELOG | 技能是给 agent 的，不是给人看的 | 移出去 |
| 粘贴库源码 | 会过时，且体积大 | 用 npm/pip 装 |
| 只改语气或格式 | 属于用户偏好或系统提示 | ⭐ 别做成技能 |
| 含时间敏感信息 | "截至 2024 Q4…" 很快腐烂 | 用脚本取实时数据，或干脆不写 |
| 用绝对路径 | 换机器就断 | ⭐ 一律相对路径，正斜杠 |

> ⭐ **"纯指令无解释"那条值得单独记**：
> LLM 推理能力很好，给 why 它就能泛化到没写到的边界；
> 只给 must/never，遇到没覆盖的情况它只能瞎猜。

## 五个高频陷阱

**① 技能过约束**
症状：agent 变瘫痪，一次普通 git push 也要确认三遍。
修法：**护栏只拦不可逆操作**（force push、生产部署、删库）。

**② 技能与提示词冲突**
症状：技能要求 TDD，用户提示词说"先快点写完，测试以后补"。
修法：**建立优先级规则——技能约束 > 单次提示词指令**。

**③ 忽略版本管理**
症状：团队成员跑不同版本的技能，AI 行为差异巨大。
修法：**项目技能必须随代码库版本控制**；个人技能放独立仓库管理。

> 呼应 `release-versioning.md`（**`skill-distribution`**）。

**④ 技能膨胀但没用**
症状：装了一堆，实际触发的没几个。
修法：**三触发法则——过去一周被触发三次以上的才留下**。

**⑤ 忽略失败模式**
症状：中间一步失败了，agent 不知道，继续往下走。
修法：**对每个可能失败的步骤，写清"如何识别失败"和"失败后做什么"**。

## 最小可用版本

别被上面吓到。**第一个技能可以只有 10 行 Markdown**：

```markdown
---
description: 跑完整测试套件并报告失败
---

运行 `pnpm test`，报告任何失败，带上文件路径和行号。
```

> ⭐ **不需要脚本、assets 或复杂工作流就能产生价值。**
> 一个"跑测试"或"部署到 staging"的技能，
> 只要有 5 个清晰步骤，就能给团队省下数小时。

**先做出来，再在真实使用中按上面的清单逐步补。**
