## 1. ⭐⭐⭐ 失败模式是笛卡尔积

```
一个 PDF 转码技能，加点 OCR、加点翻译、加点摘要
看上去很美，实际一上线就翻车
```

**原因**：

> ⭐⭐⭐ **每加一项能力，失败模式的数量是⭐ 乘法叠加的，不是加法。**

```
OCR 的失败模式 × 翻译的失败模式 × 摘要的失败模式
= ⭐⭐ 最终的失败空间是三项的⭐ 笛卡尔积
```

> ⭐⭐⭐ 这是"一技能一职责"到目前为止**最强的论证**。
> 此前我们收集到的理由都是"触发更准""更好维护"（定性）；
> 这条给了**量化的机制**：**组合爆炸**。
>
> 推论很直接：**一个能力 = n 种失败模式；三个能力 ≠ 3n，是 n³ 量级的交互空间**。
> 而这些交叉情形**你一个都不会去测**。

> ⭐ 这也为 `granularity-atomic-workflow.md` 的"重启测试"、
> `skill-families-nine.md` 的"一类做到底"提供了共同的理论基础。

## 2. ⭐⭐ 70% 的事故来自未经评估的微调

```
一次"成功"的 prompt 调优，
⭐ 可能让技能在某个⭐ 长尾 case 上的成功率从 90% 跌到 60%
⭐⭐ 而这种下滑很难被一眼发现
```

> ⭐⭐ **Anthropic 内部数据：70% 的技能线上事故
> 来自"未经评估的 prompt 微调"。**

> ⭐⭐⭐ 这条值得单独记住，因为它推翻了一个常见直觉——
> 大家以为事故来自"大改"，实际来自⭐ **看起来最无害的小改**。
>
> 而且它解释了为什么"总体 pass rate 没变"是不够的：
> **均值会掩盖长尾的崩塌**。
> 这与 `comparator-ab-eval.md` 的"两组都通过的断言没有区分度"、
> `quality-rubric-nine-dims.md` 的"异常路径短板"是同一类问题。

## 3. ⭐⭐⭐ 优先级：可回滚 > 评估集 > 性能调优

```
① ⭐ 每次改动必须可回滚
   SKILL.md 进 git + 语义化版本
   git tag skill/docx-to-pdf/v1.4.2 && git push --tags
   ⭐ 出问题：git checkout skill/docx-to-pdf/v1.4.1

② ⭐ 评估集先跑，再上线
   python eval/run.py --skill X --version v1.4.2 \
                      --baseline v1.4.1 --threshold 0.95
   ⭐ 阈值不达标 → 版本号打回

③ 性能调优
```

> ⭐⭐⭐ **版本可回滚是技能工程化的⭐ 入场券——
> 没这张票，剩下的一切优化都只是在⭐ 沙地上盖楼。**

**为什么这个顺序不能反**（原文给的理由很实在）：

```
⭐⭐ 顺序反了，团队会在第 3 个月陷入
   "⭐ 不知道哪个版本是对的"的困境
```

> ⭐ "不知道哪个版本是对的"——这与 `skill-overrides-audit.md` 的
> deploy 事故、`forty-skills-lessons.md` 的
> "破坏性改动静默影响整个团队"是同一问题的三个侧面：
> **技能没有构建产物，所以"当前生效的是哪份"必须靠流程来保证。**

**多用户场景的补充**：

```
⭐ 先给 5% 流量开新版本，观察 24 小时异常率，再扩到 100%
```

## 4. ⭐ 崩溃半径比传统服务大

> ⭐⭐ **技能的崩溃半径往往比传统服务大，
> 因为它输出的是⭐ "内容"，不是 HTTP 状态码。**

```
一次 prompt 漂移可能让 1% 的用户收到
⭐⭐ "结构正确的废话"
⭐⭐ 这比 500 错误难发现得多
```

> ⭐⭐⭐ **"结构正确的废话"** —— 这是对技能故障最精准的描述。
>
> 传统服务挂了会报错、会触发告警；
> 技能"挂了"的表现是**输出一份格式完美、字段齐全、但内容是错的产物**——
> 监控系统全绿，用户拿到废话。
>
> ⭐ 这直接解释了 `skill-observability.md` 那条
> "高调用次数但没有质量审查 = 负债"：
> **调用量指标对这类故障完全无感。**

## 5. ⭐ 边界怎么写才有效

既然边界这么重要，那"边界章节"该怎么写？

**三条**（结合 `scope-section.md` 与本文档）：

```
① ⭐ 写"不做什么"必须带替代方案
   ❌ "不做图表"
   ✅ "不做图表（用 dataviz）"

② ⭐ 边界是减法，不是加法
   加一项能力的成本 = ⭐ 失败空间的乘法，不是加法

③ ⭐ 边界要在 description 里就出现
   ——触发阶段就该挡掉，而不是加载进来再判断
```

> ⭐ 第 ③ 条与 `description-by-collision-risk.md` 的
> "高碰撞风险 → description 要写完整 NOT"对上了：
> **边界的第一道闸在路由层。**
