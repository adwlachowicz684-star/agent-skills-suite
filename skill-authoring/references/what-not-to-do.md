# 不能做的事

> ⭐ **这一份是"禁令清单"。**
> 但记住 `skill-crafting` 的 `guidance-forms.md` 的发现：**禁令只说"不能做什么"，没说该做什么。**
> 所以每条都配了对应的正面做法。

## 六个翻车现场

> ⭐ **大家做技能最容易踩的坑，按出现频率排序**：

| # | 坑 | 后果 | 修法 |
|---|---|---|---|
| 1 | **描述写太泛**（"帮助开发"） | 啥任务都触发，天天误触发 | ⭐ 加明确的对象、动作、场景；太泛就拆成多个 |
| 2 | **SKILL.md 写太长** | 激活后上下文被占满，关键步骤被淹没 | 正文只留工作流，长规范扔 `references/` |
| 3 | ⭐ **全是原则没有动作**（"保证安全""确保质量"） | 模型不知道做什么 | 把要求改成具体的检查、命令、判断分支 |
| 4 | **脚本不可复现**（依赖隐藏环境变量） | 换台机器就跑不起来 | 写清依赖、参数明确、加错误提示与样例测试 |
| 5 | ⭐ **把技能当权限系统** | 以为写了就能执行，绕过安全校验 | ⭐ **安全控制必须在工具层做，技能说了不算** |
| 6 | **不做负向测试** | 带关键词就触发，不相干的任务也往里凑 | 加负向用例，测召回率与误触率 |

> ⭐ 第 3 条和第 5 条最值得单独记：
> **"确保质量"对模型等于没有约束**；
> **技能里的权限声明不是安全边界**。

## 七个新手坑

**坑 1：把业务逻辑写进技能里**（排第一的错误）

```
❌ 把"用户说'发货'就先查库存再查物流再更新状态"
   这么复杂的调度逻辑全写进技能
✅ ⭐ 调度逻辑写进系统 Prompt（告诉 agent 怎么调度）
   技能只写"能力怎么实现"
⭐ 判据：一个技能里的逻辑超过 50 行代码，基本就是写错地方了
```

**坑 2：技能越多 agent 越强**

```
❌ 以为堆数量
✅ ⭐ 真实公式：能力 = 调度策略的质量 × 技能数量
   （相乘，不是相加）
   技能太多 → agent 光搞清楚"用哪个"就消耗大量上下文
⭐ 真正厉害的 agent 通常只有 3–5 个技能，
   但每个都被系统 Prompt 精确调度
```

**坑 3：以为跑通就是对了**

```
❌ 调用成功、没报错、有输出 = 做对了
✅ ⭐ 它可能用错误的方式调用了正确的技能，
   给了你一个看起来对但完全不是你想要的结果
⭐ 测输出质量，永远比测"能不能跑"更重要
```

**坑 4：上下文塞太满**

```
❌ 系统 Prompt 写几千字规则，然后抱怨越来越慢越来越贵
✅ ⭐ 好的系统 Prompt 通常不超过 500 字
   超过 1000 字 → 你想让它做太多事，或没把任务拆清楚
```

**坑 5：成本完全没感觉**

```
⭐ 多步 agent 任务的 token 消耗是单步的 5–10 倍
```

**坑 6：没有版本管理**

```
❌ 直接改 SKILL.md，改坏了想回退找不到旧版本
✅ ⭐ 用 Git 管理技能目录；或每次改前复制一份
```

**坑 7：技能间规则冲突**

```
症状：同时加载"去 AI 味"和"排版"两个技能，输出格式乱了
原因：两个技能都对段落格式有要求，互相矛盾
修法：⭐ 设优先级（冲突时高优先级覆盖）；或合并成一个
```

## 五个工程反模式

```
❌ 循环依赖
   技能 A 要求先加载 B、B 又要先加载 A
   → 初始化循环，调试噩梦

❌ ⭐ 硬编码密钥
   绝不在技能文件或脚本里写 API key / 密码 / token
   → 文件会进 Git 历史，泄露风险极高
   ✅ 用环境变量，并在文档里写明如何设置
      export XYZ_API_KEY="your-key-here"

❌ 过度通用的技能
   general-helper 这种"啥都做"的
   → ⭐ 如果它什么都做，就等于什么都做不好
   ✅ 拆成专注的单一职责技能

❌ ⭐ 把 L3 全塞进 L2
   正文膨胀到接近或超过建议规模
   → 触发即大额占上下文，渐进式披露名存实亡

❌ ⭐ 在正文里内联大段脚本
   每次触发都为源码付 token
   ✅ 改成 `scripts/` + 执行
```

**另外三条容易忽略的**：

```
❌ 用技能代替 MCP
   需要稳定 RPC / 资源访问时 → ⭐ 先暴露 tool，
   再在技能里写调用顺序

❌ 跳过审计直接装社区包
   ⭐ 指令可诱导 bash 与文件操作
   → 按官方建议"当作安装软件"来对待

❌ ⭐ 把动态会话状态写进技能
   技能是可复用知识包，不是当前 ticket 的草稿
   会话专属路径、临时密钥、单次分支名
   → 应留在对话或环境变量，避免污染可分享目录
```

## 三条红线

> ⭐ **这些必须显著声明，且默认禁止**：

**① 脚本不得改动用户的原始输入文件**

```
□ ⭐ 凡是会改动原始数据的脚本，必须在 SKILL.md 里显著声明
□ ⭐ 默认禁止写回源文件
□ 这是脚本级检查清单里"最关键的一条"
```

**② 敏感凭据与高危流程**

```
□ ⭐ 不要在技能中写入密码、Token 或私钥
□ ⭐ 高风险且需要人工审批的流程（如生产环境数据变更）
  必须保留人工确认环节，不要让技能自动执行
□ 需要预览 / 确认 / 回滚机制
```

**③ 运行面差异**

```
□ API 环境可能无网、不可随意 pip
□ Claude Code 权限更大
   → ⭐ 同一个脚本可能一边能跑一边不能
□ ⭐ 改了本地目录 ≠ claude.ai 或 API workspace 已同步
```

## 五个思维误区

> ⭐ **这些不是操作错误，是认知错误，更难纠正**：

```
❌ "技能是代码封装，要写很多代码"
✅ ⭐ 技能是"规则封装"——核心是把你的经验和规则
   写成模型能理解的指令

❌ "一上来就写技能"
✅ ⭐ 先手动再自动化——先手动做几次确认流程和规则没问题

❌ "贪大求全"
✅ ⭐ 小而精准

❌ "全靠模型发挥"
✅ ⭐ 用流程保障结果

❌ "技能是一段随便写写的提示词"
✅ ⭐ 把它当成"可测试的流程产品"来做
```

**一句话总结本质**：

> **把隐性的经验变成显性的规则，再把显性的规则变成可执行的流程。**

**四个转变**（这四句值得贴在墙上）：

```
从写提示词        → 设计流程
从一次性方案      → 可复用模块
从贪大求全        → 小而精准
从全靠模型发挥    → 用流程保障结果
```

## 五个必过场景（体面失败）

> ⭐ **交付前问自己**：
> **如果这技能交给一个完全不认识的人，他遇到异常输入时，能体面地失败吗？**

```
① 正常输入 → 结果符合预期格式？
② 空输入   → 输出明确的"无结果"提示？
③ 超长输入 → 脚本能短时间返回而不卡死？
④ 错误格式 → 给"输入不符"的提示，而不是崩溃报错？
⑤ ⭐ 用户话术模糊 → agent 能主动追问关键信息？
```

> ⭐ 第 ⑤ 问最关键——
> 它考验的不是脚本能力，而是 SKILL.md 里
> **"信息不足时怎么处理"** 这个约定有没有写到位。

## 自查

```
□ description 是否具体（有对象/动作/场景）而非泛泛？
□ 正文是否全是可执行动作（无"确保质量"类空话）？
□ 脚本是否可复现（依赖写明、参数明确、有样例测试）？
□ ⭐ 是否把技能当成了权限系统（安全应在工具层）？
□ 是否做了负向测试？
□ ⭐ 是否把业务逻辑写进了技能（应放系统 Prompt）？
□ 技能数量是否合理（而非堆量）？
□ 是否验证过输出质量（而非只是"跑通"）？
□ 系统 Prompt 是否 <500 字？
□ 是否知道多步任务的 token 是单步的 5–10 倍？
□ 是否用了 Git 做版本管理？
□ 多个技能是否有规则冲突（优先级/合并）？
□ 是否存在循环依赖？
□ ⭐ 是否硬编码了密钥（应用环境变量）？
□ 是否有 general-helper 式过度通用技能？
□ ⭐ 是否把 L3 塞进了 L2、或在正文内联大段脚本？
□ ⭐ 是否把会话状态写进了技能？
□ 脚本是否会改原始输入（红线，需显著声明且默认禁止）？
□ 高危流程是否保留了人工确认？
□ 是否考虑了运行面差异（API 无网 / 权限差异）？
□ ⭐ 五个必过场景是否都跑过（尤其"话术模糊会追问"）？
```
