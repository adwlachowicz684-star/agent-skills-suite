## 阶段 0：判断该不该做成技能

先确认这个需求**不是**别的东西：

| 需求 | 正确载体 |
|---|---|
| 永不改变的项目硬规则 | `CLAUDE.md` |
| 会变的经验与坑（**由 Claude 自己写**） | Auto Memory |
| 完整操作流程（**你写**） | **Skill** |
| 关键流程，必须 100% 触发 | Slash Command（技能**可能不被触发**） |
| 够不着外部系统 | MCP server（**技能不能授予工具访问权**） |
| 强制阻止某操作 | Hooks / `PreToolUse`（技能只是建议，可能被绕过） |

**一个信号**：当 `CLAUDE.md` 里某个章节从"事实描述"膨胀成"操作流程"，它就长成了一个技能。

## 阶段 1：RED——先手工跑一遍

> **不要先写技能。** 先不用任何技能，把任务完整做一遍。

记录三件事：

1. **你反复提供了什么上下文** —— 那就是技能该承载的内容
2. **模型在哪里出错** —— 那就是需要显式约束的地方
3. **哪些判断你无法用文字说清** —— 那是技能管不了的，别硬写

**为什么这步不可省**：不知道会失败在哪里，就写不出针对性的约束。写完才发现漏了，等于重写。

## 阶段 2：分类基线失败

> **先分类失败，再伸手拿形态。**
> 因为能防住一种失败的写法，在另一种失败上会**可测量地反噬**。

| 基线失败类型 | ✅ 正确形态 | ❌ 错误形态 |
|---|---|---|
| 压力下违反规则（明知故犯） | 禁令 + 合理化表 + 红旗列表 | 软指导（prefer、consider） |
| 遵守了，但输出形状不对 | **正面配方**：输出模板 + 槽位 | 禁令清单 |
| 漏掉必需元素 | 模板里的 REQUIRED 槽位 | 散文式提醒 |
| 行为依条件而定 | `if <可观察谓词> then` | 无条件规则 + 例外条款 |

**默认不要伸手拿禁令**——禁令只在防"明知故犯"时才是对的选择。
详见 `skill-crafting` 的 `guidance-forms.md`。

## 阶段 3：定边界

**先写"不做什么"，再写"做什么"。**

```
□ 不处理什么场景
□ 不延伸到哪些领域
□ 不回答哪类问题
□ 输出不做什么（不代写代码、不替人决策……）
```

边界的两个层次：

- **技能边界**：写在 `description` 的 Do NOT 里（路由层用）
- **执行边界**：写在正文的"何时不用 / 红线"里（专家层用）

> 没有边界的技能会在边缘场景乱跑。**这是新手最常见的错。**

## 阶段 4：选模式

见 `patterns.md` 的决策树。五种架构模式：

| 模式 | 适用 |
|---|---|
| 线性流程 | 固定步骤，一次走完 |
| 决策树 + 按需加载 | 有多种分支，分支内容大 |
| 循环迭代 | 需要"跑 → 检查 → 修 → 再跑" |
| 接力棒循环 | 多轮会话，靠文件传递状态 |
| 多阶段 + 检查点 | 长流程，需要人工确认节点 |

---

## 阶段 5：定自由度

**约束强度要匹配任务脆弱性**：

| 脆弱性 | 自由度 | 形式 |
|---|---|---|
| 错一点就炸、只有一种对法 | **低** | 精确脚本，参数少或无 |
| 有首选模式、可接受变化 | **中** | 伪代码 / 带参数模板 |
| 多种方法都行、依赖上下文 | **高** | 文本指令、启发式 |

**比喻**：两侧悬崖的窄桥 → 给精确护栏；无危险的开阔地 → 给大方向。

## 阶段 6：写 SKILL.md

**SKILL.md 是路由层，不是全部内容。**

固定骨架（目标 100–150 行）：

```
1. 何时使用 / 何时不用        ← 边界
2. 核心原则                    ← 3–10 行
3. 路由表                      ← 指向 references/
4. 强制工作流                  ← 编号，标 MANDATORY
5. 输出契约                    ← 交付什么、什么格式
6. Critical Rules              ← 逐条列举
7. 常见借口表                  ← 反理性化
8. 脚本调用                    ← 指向 scripts/
```

写作纪律：

- 用**祈使句**下指令，并**解释为什么**（一句，不要多段）
- 每个工具/命令**写确切名字**，不写"合适的工具"
- **不留逃生舱**：不要用"如有需要""可以考虑"
- 关键规则放**顶部或底部**——中间是模型的盲区

## 阶段 7：拆分与脚本化

**该移出 SKILL.md 的**：长篇解释、API 文档、历史背景、10+ 个示例。
**该进 `scripts/` 的**：校验、格式化、复杂计算、重复任务。

```
SKILL.md (120 行)：入口 + 路由 + 关键规则
references/api.md (300 行)：完整文档
references/examples.md (250 行)：完整示例
scripts/helper.py (80 行)：确定性逻辑
```

详见 `skill-refining` 的 `splitting.md`。

## 阶段 8：校验与测试

**① 结构校验**

```bash
python scripts/validate_skill.py ./my-skill
```

零错误才继续。

**② 触发测试**

20 条查询：10 条应触发 + 10 条**近失样本**（共享关键词但实际是别的任务）。
每条跑 3 次（模型行为非确定性），算触发率。

- 正例触发率 **>0.5**
- 负例触发率 **<0.5**

详见 **`skill-evaluating` 的 `triggering.md`**。

**③ 执行测试**

用真实数据走一遍完整流程，验证：产出符合预期 · 脚本能跑 · 输出格式稳定。

**④ 量成本**

```bash
python scripts/estimate_tokens.py ./my-skill
```

看三层成本：启动常驻（描述）· 正文 · 按需加载（references）。
description 目标 **300–500 字符**；正文 **100–150 行**理想、**500 行**硬上限。

> ⭐ 别忘了**配对对照**：同一个任务跑「有技能」和「无技能」两遍。
> 优化好的技能应该**比不用技能更省**（0.7x）——
> 因为它阻止了 agent 探索不必要的路径。写得差则会**翻倍**（1.7x）。

详见 `skill-refining` 的 `context-budget.md`。

## 阶段 9：修剪

> 逐句跑 **no-op 测试**：这个句子删了，Agent 的行为会有变化吗？
> 没有 → 整句删除，不要从中修剪词。

**修剪顺序**：

```
□ 先删空操作句（"请认真思考"这类，零风险纯收益）
□ 再删重复（合并到单一真相源）
□ 再删沉淀（过时的规则）
□ 最后处理蔓延（拆分）
```

详见 `skill-refining` 的 `pruning.md`。

## 阶段 10：交付

用 **`skill-evaluating`** 按 `skill-governance` 的 `audit.md` 打分。**≤6 分重写。**

汇报包含：目录树 · description 全文 · 触发测试结论 · validate 结果 · 审计得分。

## 一条贯穿的经验

> 技能的难点从来不是写 markdown，是**界定边界**。
> 如果你说不清"什么时候不用它"，那它还没设计完。
