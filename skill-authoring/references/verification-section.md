# 验证章节怎么写

> 每个技能都要有验证章节，但**大多数人写的是废话**。
> 这份讲它该长什么样。

## 三种常见的废话写法

```
❌ "确保输出质量"
   ——"确保"不是动作，模型不知道做什么

❌ "检查是否成功"
   ——什么算成功？没说

❌ "妥善处理错误"
   ——"妥善"是模糊词，等于没约束
```

> 呼应 `what-not-to-do.md`（**`skill-authoring`**）：
> **"确保质量"对模型等于没有约束**。

## 该有的四段

**① 具体命令**

```
□ ⭐ 写明跑什么命令
□ 不是"运行测试"，是 `npm test -- --coverage`
```

**② 通过标准**

```
□ ⭐ 可判定的：退出码 0 / 输出含 "0 failures" / 覆盖率 ≥85%
□ 不是"看起来没问题"
```

**③ 失败时做什么**

```
□ ⭐ 每个可能失败的步骤写清"如何识别失败"与"失败后做什么"
□ 呼应 authoring-checklist.md 的"忽略失败模式"反模式
```

**④ 交付前声明**

```
□ ⭐ 没有在本会话跑过的验证 = 不准声称"完成了"
```

## 什么证据够、什么不够

| 声称 | ⭐ 需要的证据 | 不够的 |
|---|---|---|
| Bug 已修复 | ⭐ 复现原始症状的测试通过 | 代码改了 · 假定修好了 |
| Agent 完成 | ⭐ VCS diff 显示变更 | agent 报告 "success" |
| 测试通过 | 输出：**0 failures** | 之前跑过 · "应该能过" |
| 文档生成 | ⭐ 文件存在且能解析 | "我写了" |
| 迁移完成 | ⭐ 验证查询返回预期 | 脚本没报错 |

呼应 `grounding-verification.md`（**`skill-crafting`**）。

**红绿循环**（防"先写代码后补天然通过的测试"）：

```
1. 写测试
2. 通过
3. ⭐ 回滚修复 → 必须失败
4. 恢复
5. 通过
```

## 分必做与按需

> ⭐ **过度验证是最大的单一成本源（67/182 退化）。**

```
必做（每次都要）：
  □ 阻断性的、错了就要重来的
  □ 例：类型检查、迁移后的验证查询

按需（满足某条件才做）：
  □ 例："若改动涉及公共 API，则跑契约测试"
  □ ⭐ 写"若 X 则检查 Y"，不是"总是检查 Y"
```

## 禁用词

```
❌ 应该 / 看起来 / 我很有信心 / 应该没问题
❌ 确保 / 妥善 / 适当 / 尽量
❌ "已验证"（没给证据时）
```

替换方式：

```
"应该没问题"  → ⭐ "npm test 输出 0 failures（见上）"
"妥善处理错误" → ⭐ "捕获 X 异常，重试 3 次后返回错误给用户"
```
