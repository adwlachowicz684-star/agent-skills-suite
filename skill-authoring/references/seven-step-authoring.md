## 1. 前提：动手前先确认四件事

```
□ 一个**有名有姓的重复任务**——不是"我们应该有些技能"这种模糊愿望
□ 环境已启用 Agent Skills
□ 对该技能要读的表/文件/API 有读权限
□ ⭐ 5–10 条测试查询，⭐ 其中至少一条不该触发
```

> 最后一条最容易被省，但它是后面所有评估的地基。

## 2. 七步

| 步 | 做什么 | 关键 |
|---|---|---|
| 1 | **识别能力缺口** | ⭐ 一句话说出那个重复任务；说不出 = 还不够窄 |
| 2 | **写 frontmatter** | name / description |
| 3 | **正文用渐进式披露** | <500 行，激活后 <5,000 tokens |
| 4 | **打包 scripts 与 references** | 确定性逻辑进 scripts/ |
| 5 | ⭐ **验证数据源** | 见下节 |
| 6 | **用 eval 提示测试** | 5–10 条该触发 + 3–5 条不该触发 |
| 7 | **版本化迭代** | 像维护代码一样维护 |

### 第 1 步的关键动作

```
① 一句话命名那个重复任务（README 生成器、commit message 生成器）
② 写 3–5 条用户真会输入的查询，含一条负例
③ ⭐ 确认"技能"是对的层次——而不是工具调用或子代理
```

> ⭐ **跳过第 ③ 条是技能最终写得含糊的最常见原因。**

### 第 3 步的自由度匹配

```
判断类任务        → 高自由度
脆弱/不可逆操作   → ⭐ 明确脚本，不交给模型自由发挥
```

## 3. ⭐ 第五步：验证数据源（几乎所有人跳过）

> ⭐ **这一步，本研究所见的每个 how-to 来源都跳过了，
> 包括官方的最佳实践文档。**

问三个问题：

```
① 谁拥有这个数据源？
② 它最后一次被认证/核验是什么时候？
③ ⭐ 别处是否存在冲突的定义？
```

为什么必须问：

> **评估优先的测试能确认流程产出正确输出，
> 但它对"它取的数据是否正确"一言不发。**
>
> ⭐ **一个技能可以通过每一条评估查询，
> 却依然自信地从一个过期表里报出错误数字。**

而且风险比一次性脚本高得多——

> ⭐ **技能会被调用数百次，且每次都不经复核。**

这与 `grounding-verification.md` 那章的结论完全一致：
**流程和落地是两件事，现有技能普遍对后者支持不足。**

## 4. 字段限制速查

| 字段 | 限制 | 规则 |
|---|---|---|
| `name` | **64 字符** | 小写字母、数字、连字符；无 XML 标签；⭐ 不含 "anthropic"/"claude" |
| `description` | **1,024 字符** | 非空、无 XML 标签、⭐ **第三人称**、说明 what 与 when |

最小可正确工作的 frontmatter：

```yaml
---
name: release-notes-writer
description: >-
  Generates release notes from a git commit log. Use when the user asks
  to summarize recent commits into a changelog entry.
---
```

## 速查

| 步骤 | 最容易犯的错 |
|---|---|
| 1 | 任务不够窄（一句话说不出） |
| 2 | 用了第一人称 / 写了"是什么"而非"何时用" |
| 3 | 把所有细节堆在正文 |
| 4 | 确定性逻辑写在正文而非脚本 |
| 5 | ⭐ **完全跳过**——数据错了流程再对也没用 |
| 6 | 没有负例 |
| 7 | 写完就丢，不随项目演进 |
