## 1. 为什么单独成一章

技能的评估（Outcome / Process / Style / Efficiency）
全部建立在**流程正确**之上，**没有一条覆盖"数据源正确"**。

```
流程对 + 数据错  =  自信地给出错误答案
流程错 + 数据对  =  至少能被评估抓到
```

> ⭐ **前者更危险，因为它每一条评估都会通过。**

---

## 2. 三个必问

| 问题 | 追问 |
|---|---|
| **谁拥有这个数据源？** | 出问题找谁？有负责人吗？ |
| **何时最后一次核验？** | 有认证日期吗？过期了吗？ |
| ⭐ **别处有冲突定义吗？** | 两张表都叫"活跃用户"，口径一样吗？ |

第三条最常出事：**同名不同义**。
技能按名字取数，取到的是另一套口径。

---

## 3. ⭐ 与评估的关系

```
评估优先的测试 → 确认流程产出正确输出
              → ❌ 不能确认它取的数据是对的
```

所以两者必须分开做：

| 层 | 验什么 |
|---|---|
| 四层测试金字塔 | 流程 |
| ⭐ 数据源验证 | **输入本身** |

> 一个技能可以 100% 通过 eval，
> 却每次都从一张过期表报出错误数字。

---

## 4. 建议动作

```
① 在 SKILL.md 里写明数据源及其负责人
② 写上"最后核验时间"（并定期更新）
③ ⭐ 若存在同名冲突定义，显式写清本技能用哪个口径
④ 输出里带上数据源与取数时间，便于人工核对
```

第 ④ 条很实用——**让答案自带出处**，
人工一眼就能看出是不是取错了表。

> 这与（已移至 _parked 领域实例库）的 `research-skills.md` 里
> "区分证据与解读、禁止编造引用"是同一条原则在数据层的延伸。

| ⭐ 同名冲突 | ⭐ 显式写明本技能用哪套口径 |
