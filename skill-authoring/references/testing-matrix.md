## 为什么要跨模型测

官方清单里有一条常被跳过：

```
⭐ Tested with Haiku, Sonnet, and Opus
```

跳过它的代价是：**你不知道这个技能的能力边界在哪**。

原因很实际——同一份指令在不同模型上的表现差异，
不是"好一点/差一点"，而是**会不会触发**这种量级。

## 矩阵怎么搭

```
         Haiku    Sonnet    Opus
任务 1    ?        ?         ?
任务 2    ?        ?         ?
任务 3    ?        ?         ?
```

任务集建议 **3–10 个**，覆盖：

```
□ 最典型的触发场景（至少 2 个）
□ ⭐ 边界场景（改述说法、隐含意图）至少 1 个
□ ⭐ 不该触发的场景（负例）至少 1 个
□ 需要读 references/ 的深路径场景 1 个
```

## 三个指标

每个格子记三项，不要只记"成功/失败"：

```
触发率        该触发的触发了吗？不该触发的触发了吗？
步骤执行率    流程走完了吗？在哪一步断的？
输出合格率    产物符合输出契约吗？
```

为什么要分开：**这三者的失败原因完全不同**。

```
触发率低    → description 问题
步骤执行率低 → 正文指令问题
输出合格率低 → 模板/验收标准问题
```

只记一个总分，你就只能"重写一遍再看"，无法定位。

## 差异最大处就是最含糊处

> ⭐ **跨模型差异最大的那一项，就是你的指令最含糊的地方。**

这是个非常好的定位工具。举例：

```
Haiku 触发 2/5，Sonnet 5/5
→ 说明触发靠的是"模型自己脑补"，而不是 description 里写明的关键词
→ ⭐ 修法：把触发词显式写进 description，不要让模型推断
```

```
三个模型都在第 3 步断
→ 说明第 3 步的指令有歧义或有隐藏前提
→ 修法：拆成更小的步骤，或补上缺失的前置条件
```

## 常见的模型差异

几类稳定出现的差异：

**① 模糊指令的容忍度**
小模型更"字面"——你说"检查"，它真的只检查，不会顺带修。
大模型会自行补全，反而掩盖了指令的含糊。

**② 长指令的后半段遵守度**
⭐ **有的模型在工具调用时会"遗忘"指令里的约束**。
表现：流程前半段规规矩矩，后半段开始自由发挥。

**③ 否定式的处理**
"不要做 X" 在不同模型上的遵守度差异很大。

**④ 输出格式的严格度**
JSON/schema 合规性的差距可以是数量级的：
明确 schema 下，**不同模型间可靠性差距可达 25 个百分点**。

## 最低限度该做什么

如果没法跑完整矩阵，至少做这两条：

```
① ⭐ 在最弱的目标模型上跑一遍
   ——如果你的技能要在小模型上用，小模型就是验收标准

② 三个评估是底线
   ——不是"三个任务"，是三个**有明确通过条件的评估**
```

⚠️ 注意区分：**"跑了三个任务" ≠ "建了三个评估"**。
评估要有通过条件，任务只是输入。

## 一条纪律

**改完必须重跑整个矩阵，不能只重跑失败的那个格子。**

理由：修触发可能伤到输出，修输出可能改变触发。
只测一处会漏掉回归。

这与 `skill-evaluating` 里"配对对照"的原则一致——
**技能是一个整体，不是几个独立可调的旋钮。**

## 记录格式建议

```
技能名 / 版本 / 日期
模型版本（写清具体版本号，不只是"Sonnet"）

| 任务 | Haiku | Sonnet | Opus |
|---|---|---|---|
| T1 典型 | ✅ 3/3 | ✅ 3/3 | ✅ 3/3 |
| T2 改述 | ❌ 1/3 | ✅ 3/3 | ✅ 3/3 |
| T3 负例 | ✅ 不触发 | ✅ 不触发 | ✅ 不触发 |

结论：T2 在 Haiku 上触发失败 → description 缺改述说法 → 已补充
```

> ⭐ 记版本号这条别省。
> 换模型版本本身就是换测量系统，不记录就无法比较历史结果。
