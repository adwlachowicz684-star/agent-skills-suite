## 四个操作：写 / 选 / 压 / 隔

### 1. Write —— 存到上下文窗口之外

```
Scratchpad  执行中记笔记（如 TodoWrite）
Memory      ⭐ 跨会话持久记忆，三种：
            情景式  发生过的事（"上次用户要求 JSON 格式"）
            语义式  事实知识（"本项目用 TypeScript + Hono"）
            ⭐ 程序式 怎么做（"部署流程是 build → test → push"）

⭐ 关键原则：Write 是延迟的 Select
  现在存下的，是为了将来某一刻被精确取回
```

> ⭐ 呼应 `skill-orchestration` 的 `memory-state.md` 的记忆分层——
> **程序式记忆正是技能该承载的东西**。

### 2. Select —— 把对的信息拉进来

```
□ 从 Memory 选：embedding 检索相关历史记忆
  ⭐ 不要把所有记忆都塞进去——只选与当前任务相关的
□ 从工具选：50 个工具不必全塞进上下文
  ⭐ 用 RAG 对工具描述做语义检索，只挂载相关的
□ 从知识库选：RAG 的核心

⭐ 混合策略最有效：
   预加载（系统提示、核心工具）+ 运行时探索（RAG、记忆、读文件）
```

> ⭐ **"从工具选"直接呼应 caching-economics 的发现**：
> 工具超过 10 个准确率开始下降，超过 20 个边际收益急剧递减。

### 3. Compress —— 只保留关键 token

```
□ 摘要压缩：上下文用到 95% 时自动触发
  ⭐ 保留架构决策与未解决问题，丢弃冗余工具输出
□ 剪枝规则：只保留最近 N 轮 / 删掉完整工具输出只留摘要
```

### 4. Isolate —— 把上下文分到不同空间

```
□ 多 agent 隔离：子 agent 有独立干净上下文，
  ⭐ 只返回 1000–2000 token 的简洁摘要
□ 沙箱隔离：代码执行在沙箱里，返回结构化结果
  ⭐ 而不是把整个执行环境塞进上下文
□ 状态 schema 隔离：用带类型的状态字段分别管理不同上下文
```

## 为什么压缩重要

> ⭐ **Anthropic 指出的反直觉现象**：
> **更长的上下文不一定带来更好的质量。**

```
□ 注意力机制是 O(n²)——每多一个 token，
  都要与所有其他 token 计算相关性
□ ⭐ 注意力有预算，无关的 token 会稀释对重要信息的聚焦
□ 目标：找到"能最大化期望结果的最小高信号 token 集合"
```

```
□ ⭐ 上下文用到 20–40% 时质量就开始打折扣
   （呼应"运行时真相"那章）
□ ⭐ 所以"压缩后依然差"的原因是——压缩前就退化完了
```

## 工具设计就是上下文工程

> ⭐ **工具的名字、描述、参数 schema 都是上下文的一部分**：

```
□ ⭐ 自包含：每个工具的描述要足以让 agent 知道
   "何时用"和"怎么用"
□ ⭐ 最小重叠：工具功能不应重叠，否则 agent 会选错
□ ⭐ 对错误友好：返回清晰错误信息，让 agent 能自我纠正
□ ⭐ 数量克制：超过 20 个工具会显著提高选择错误率
```

**系统提示的组织**（"合适的高度"）：

```markdown
## Role
## Behavioral Rules
## Output Format
## Tool Usage Guidelines
```

```
□ ⭐ 用 XML 标签或 Markdown 标题划出清晰分区，不要写成一大块
□ ⭐ "合适的高度"——足够具体以指导行为，
    又足够灵活以留给 agent 判断空间
   ⭐ 避免写成穷举的 if-else 规则
```

**即时加载（Just-In-Time）**：

```
□ ⭐ 不要预先塞进 agent 可能需要的一切
□ 保留轻量指针（文件路径、URL、查询串）
□ 让 agent 在需要时才拉取
```

> ⭐ 这正是渐进式披露的另一种表述——
> 呼应 `skill-authoring` 的 `patterns.md` 与 `context-budget.md`。

## 生产级上下文流水线

> ⭐ **七个阶段，每阶段都要可观测、可单测**：

```
1. 归一化输入    把请求解析成结构化字段（意图、实体 ID、约束）
2. ⭐ 作用域解析  确定租户、用户与策略作用域；按 ID 取规范记录
3. 候选检索      ⭐ 先过滤，再在允许的索引内做语义检索；附引用
4. 蒸馏          把与行动相关的事实抽到紧凑 schema，⭐ 带证据 ID
5. Scratchpad 构建  最小计划 + 已知事实 + 待确认问题
6. ⭐ 预算检查    强制 token 与步数上限；低价值上下文剪枝；
                 触及上限时的回退行为
7. 模型调用     系统提示 + 工具 + scratchpad + 蒸馏事实 + 引用
8. 动作与写回    执行工具、更新 scratchpad、⭐ 带脱敏与 TTL 写记忆
9. 观测          记录结构化 trace（上下文哈希、预算、结果）以便重放
```

```
□ ⭐ 每个阶段都要暴露指标，且可单测
□ ⭐ 如果你不能离线用夹具跑某个阶段，
     那它在生产里就很难调试
□ 把每个昂贵步骤放在廉价检查之后
```

## 隐私、租户与治理

> ⭐ **上下文承载敏感数据——必须从第一步就强制隔离与隐私**：

```
Scope first   请求开始就确定租户与用户作用域，
              ⭐ 并应用到每一次检索、记忆访问与工具调用
Minimize      ⭐ 脱敏模型下一步不需要的 PII；
              尽量传引用而非原始值
Provenance    ⭐ 给事实附上来源与访问路径元数据，
              让审计能追溯"谁看到了什么、为什么"
Consent       按策略要求，记忆写入需显式同意
```

```
□ ⭐ 当上下文跨越边界时，事故随之而来
□ ⭐ 让 scope 与 provenance 成为上下文本契约里的
     一等字段，统一强制
```

> 呼应 `skill-governance` 的 `telemetry-schema.md` 的"什么不该记"与
> `skill-governance` 的 `compliance-audit.md` 的 per-agent identity。

## 像代码一样发布上下文

> ⭐ **改动上下文要像改动代码一样，走评审、测试与灰度**：

```
□ ⭐ 一个小的提示词改动，就可能改变工具选择率或错误模式
   → 发货前必须证明它改善了结果

□ Golden tasks   固定输入 + 期望动作与输出；
                 ⭐ 含对抗性与长尾用例
□ Ablations      ⭐ 逐个禁用选择器/记忆写入/压缩步骤，
                 记录 delta，找出 dead weight
□ Trace 断言     检查 agent 是否引用了来源、
                 用了正确的工具、该追问时是否追问
□ ⭐ Token 与步数审计  ⭐ 按"每次成功解决"统计，
                      而不是按每次调用——这才暴露上下文膨胀
□ 灰度           预发 → shadow → canary → 全量，带 guard SLO
□ ⭐ 把 context diff 附到每次部署，
   才能把行为变化关联到具体改动
```

**反面模式**：

```
❌ 一次性提示词魔法
   靠一句巧妙的话，而不是选择器、预算与测试
   ⭐ 在真实用户面前活不下来
```
