## 三层成本表

| 层 | 内容 | 何时加载 | 成本 |
|---|---|---|---|
| **L1 元数据** | `name` + `description` | ⭐ **始终，每轮** | ~30–50（或 50–100）tokens/技能 |
| **L2 正文** | SKILL.md 主体 | 判定相关时，一次性整篇 | 通常 2K–5K tokens（200–500 行） |
| **L3 资源** | `references/` `scripts/` `assets/` | 按需 | ⭐ **未访问前为零，无实际上限** |

同样的模式也适用于：

```
MCP 工具        ——启动时只加载工具名，完整 schema 延迟
带 paths: 的规则 ——读到匹配文件才加载
子目录 CLAUDE.md ——在该目录工作时才加载
```

## 一个真实目录的实测

某公开技能包，34 个技能：

```
所有 description 之和   ~15,800 字符 ≈ 3,900 tokens
所有 SKILL.md 正文之和  ~349,000 字符 ≈ 87,000 tokens

平均正文   ~10,900 字符 ≈ 2,725 tokens
最大正文   ~17,800 字符 ≈ 4,450 tokens
```

如果每次会话都加载所有正文：**87,000 tokens** 常驻。
渐进式披露只付 **3,900 tokens** 买元数据，把另外 83,000 延后。

```
⭐ 常驻成本降低约 22 倍，且随目录规模线性放大
```

目录越宽，收益越大。

## 非对称性才是设计的核心

> ⭐ **一个 100-token 的描述，可以 Gate 住
> 一个 5,000-token 的正文和一个 50,000-token 的资源包。**

agent 先付一次成本（"哪个技能可能相关"），
第二次成本只在答案是"这个"的时候才付。
其余一切保持沉默。

这也解释了技能与"系统提示词里的一段"有什么**结构性**区别：

```
系统提示词里的一段   每一轮都付全额 token
技能正文            只在描述匹配的那些轮付
```

> ⭐ 这不是"效率差一点"，是**数量级差异**。

## 论点已经变了

旧论点："省 token，因为窗口不够。"

> ⭐ **Sonnet 4.6 与 Opus 4.7 都已默认 1,000,000-token 窗口，
> 且与之前 200K 档同价。**
> 87,000 tokens 的正文膨胀放得下了。

**所以 raw token 预算很少再是杀死你的东西。**

新的杀手是：

> ⭐ **注意力稀释——随常驻表面增大而增长，
> 这个成本是二次的，不是线性的。**

> 而渐进式披露正是针对它的架构性答案。

⚠️ 这也和 `library-size-effect.md` 那条实测对上了：
**上下文开销在各种库规模下都与零无显著差异，**
真正伤人的是**技能遮蔽**（路由选错）。
所以：

```
分层加载   → 解决常驻膨胀与注意力稀释
减少候选   → 解决遮蔽
⭐ 两者不是同一件事，不能互相替代
```

## 对技能的直接含义

三条：

**① description 是唯一每轮都在付费的东西**
它既决定可发现性（要全），又决定常驻成本（要短），
还决定遮蔽概率（要区分度）。三者都要兼顾，这就是它最难写的原因。

**② 正文控制在 500 行 / 5,000 tokens 以内**
不是因为放不下，而是**正文一旦触发就是整篇加载**。

**③ ⭐ L3 可以放心做大**
一份 50 页的参考文档，在被引用之前成本约等于零。
**该拆就拆，别把大块内容压在正文里。**

## Token 预算表

```
字段              预算            说明
name             5–15 tokens     唯一标识，必须与目录名一致
description      50–200 tokens   ⭐ 主要触发机制
license          5–20 tokens     可选
metadata         可变             作者、版本等任意键值对

小计             ~100 tokens/技能
```

装载量估算：

```
10 个技能  ≈ 1,000 tokens  ≈ 128k 窗口的 0.5–1%
30 个技能  ≈ 1,200–1,500 tokens
100 个技能 ≈ 30–50 × 100 = 约 5,000 tokens
```

对照：一个典型 200K 会话启动时加载约 **8K 开销**
（系统提示 + 记忆 + 技能元数据 + CLAUDE.md），
占窗口 **4%**，留 96% 给实际对话。

❌ 如果破坏分层（启动时加载所有正文）：

```
30 个技能 × 3K tokens = 90K
⭐ 在第一条用户消息之前，半个窗口就没了
```

## 一条写作纪律（源自成本结构）

> ⭐ **正文里每一段都要回答："它配得上自己的 token 成本吗？"**

如果某段没有提供 agent 本来没有的信息：

```
→ 移到 references/
→ 或直接删掉
```

这是 no-op 测试（见 `pruning.md`）的成本版表述。
