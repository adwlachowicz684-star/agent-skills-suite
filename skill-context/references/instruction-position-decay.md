## 1. ⭐⭐⭐⭐⭐ 加载那一刻，它在最好的位置上

技能被触发时发生的事情，从上下文角度看是这样的：

```
[系统提示] [历史对话……] [用户这句话] [技能正文] ← 刚加载，在这里
                                        ↑
                                   上下文的末尾
```

> ⭐⭐⭐⭐⭐ **末尾是权重最高的位置之一（近因效应）。**
> 也就是说，技能刚被加载的那一刻，它的指令处在**执行力最强的位置**。

这不是巧合，是渐进式披露的一个隐藏红利：正文在需要它的那一刻被插入，天然落在近因区。很多技能"第一次用效果很好"，有一部分功劳在这里——不完全是内容写得好。

而这也是为什么⭐⭐⭐ **刚写完的技能在测试时几乎总是表现良好**：测试环境里，触发和加载几乎同时发生，指令永远处在最佳位置。

> ⭐⭐⭐⭐⭐ **测试测到的，是指令在最优位置时的表现。**
> 生产里它大部分时间不在那个位置。

## 2. 对话每推进一轮，它就往后退一点

加载之后，会话继续：

```
轮次 1:  [……] [技能正文] [模型输出 1] [用户消息 2]     ← 正文已在中间偏后
轮次 2:  [……] [技能正文] [输出 1] [消息 2] [输出 2]     ← 又退一格
轮次 3:  [……] [技能正文] [输出 1] [消息 2] [输出 2] [消息 3]
...
轮次 N:  [……] [技能正文] […… 一大堆]                  ← 正文已在中间
```

> ⭐⭐⭐⭐⭐ **指令一个字都没少，也没有被截断——它只是从"末尾"变成了"中间"。**

而中间（所谓"lost in the middle"区）是注意力权重最低的区域。已有文档里那句"开头是黄金位置，结尾次优，中间是黑洞"说的就是这个分布，但此前它被当成**排布建议**（"把重要内容放开头"），而不是**动态过程**。

关键差异在这里：

| | 截断 | ⭐ 位置退化 |
|---|---|---|
| 内容还在吗 | ❌ 没了 | ⭐⭐⭐⭐⭐ **全在** |
| 发生在什么时候 | 压缩那一刻 | ⭐⭐⭐⭐ 每一轮都在发生 |
| 能观测吗 | 能（`/context` 变小了） | ⭐⭐⭐⭐⭐ **不能** |
| 有恢复手段吗 | compact hook 重注入 | ⭐⭐⭐⭐ 有，但不同 |

> ⭐⭐⭐⭐⭐ **压缩是一次事件，退化是一个过程。**
> 事件有解决方案（订阅它、重注入）；过程没有对应事件，所以没有钩子可以挂。

## 3. ⭐⭐⭐⭐⭐ 症状：第 1 轮严格遵守，第 5 轮开始走样

退化的表现不是"突然失效"，是一条平滑的下滑曲线：

```
第 1 轮：严格遵守（输出 3 行、未修改文件、报错就停）
第 3 轮：基本遵守，偶尔漏一条次要约束
第 5 轮：⭐⭐⭐⭐ 主要流程还在，约束开始被跳过
第 8 轮：⭐⭐⭐⭐⭐ 输出格式已变形，红线被"理解成"建议
```

最难识别的特征：

> ⭐⭐⭐⭐⭐ **技能的正文一个字没变，用户的输入类型没变，模型没变——
> 唯一变的是它在这条对话里跑了多久。**

于是排查方向天然指向别处：

```
"是不是这个 case 特殊？"   → 加示例
"是不是描述不够清楚？"     → 改正文
"是不是模型退化了？"       → 换模型
```

> ⭐⭐⭐⭐ 三个方向都不对，而**每一个都会让技能更长**——
> 更长的正文 = 更大的面积处在中间 = ⭐⭐⭐⭐⭐ **退化得更厉害**。

这与 `skill-crafting/references/token-bloat-audit` 那条膨胀循环是同一个环，只是入口不同：

```
膨胀循环：正文变长 → 稀释 → 加内容 → 更长
⭐ 退化循环：对话变长 → 正文退到中间 → 表现变差 → 加内容 → 更长（且退得更快）
```

## 4. 为什么它比截断更难发现

截断有一个非常明显的信号：上下文突然变小，且技能内容真的不见了（可以用"重新调用一次"来二分诊断，见 `compression-truncation.md`）。

退化**没有任何信号**：

| 检查 | 截断 | 退化 |
|---|---|---|
| `/context` 大小 | 突降 | ⭐ 正常增长（看不出异常） |
| 技能是否在列表里 | 可能消失 | ⭐⭐⭐⭐⭐ 一直在 |
| 重新调用一次能恢复吗 | ✅ 能 | ⭐⭐⭐ 能（但只是暂时的） |
| 新会话里正常吗 | ✅ | ⭐⭐⭐⭐⭐ ✅ 完全正常 |

最后一行是它最致命的地方：

> ⭐⭐⭐⭐⭐ **退化只在长会话里出现，而所有测试都在短会话里做。**

于是形成一个完美的盲区：
- 测试（短会话）→ 通过
- 复现（需要跑 8 轮）→ 没人做，因为慢
- 用户报告 → "有时候不太对"（说不清条件）
- 归因 → 归到"模型不稳定"或"这个 case 特殊"

还有一层：`repeat-invocation-same-session.md` 讲的是"同一会话内第二次调用会被第一次的输出污染"。那份讲的是**污染**，这份讲的是**权重**——两者叠加时最难分辨：第二次调用时，正文既被推远了（权重下降），又面临第一次输出的竞争（污染）。

## 5. ⭐⭐⭐⭐⭐ 作者控制不了位置，只能控制"重新出现"

这里必须接受一个硬约束：

> ⭐⭐⭐⭐⭐ **正文被插入的位置不由作者决定，它由"什么时候被触发"决定。**
> 你不能把正文"钉"在末尾——每次用户说话，它就自动往后退一格。

所以所有"把关键内容放开头"的建议，解决的是**静态排布**（在正文内部谁在前谁在后），解决不了**正文整体在上下文里的位置**。

这意味着防御手段必须换一个思路：

```
❌ 让指令待在好位置   → 做不到（位置不受控）
✅ ⭐⭐⭐⭐⭐ 让指令反复出现在好位置 → 做得到（每次输出时复述）
```

> ⭐⭐⭐⭐⭐ **这是本份最核心的一条推论：**
> 既然位置会退化，那么对抗退化的唯一手段是**刷新**，不是排布。

"刷新"的意思是：让关键约束在**每一轮的输出里重新出现一次**，于是它每次都重新落在近因区。

## 6. 四种防御，从便宜到贵

**① 输出自带关键约束**（最便宜，约 10–30 tokens/次）

```
不写："报告已生成。"
写：  "报告已生成（3 项，均来自 A/B/C 三个来源；未覆盖 D）。下一步：等待确认后再写入。"
```

> ⭐⭐⭐⭐ 后半句不是给用户看的，是给**下一轮的自己**看的——
> 它让"覆盖率要求"和"写入前必须确认"这两条在下一轮重新出现在末尾。

代价是可控的（几十 tokens × 轮次），收益是指令的有效期从"一轮"延长到"全程"。

**② 每步输出复述当前约束**（中等，适合长流程）

在流程类技能里，要求每一步的输出都以同一句约束开头：

```
[约束：不修改任何文件] 第 3 步：分析完成，发现 2 处问题……
```

> ⭐⭐⭐⭐ 看起来是冗余（正文里已经写了），而它买的正是⭐⭐⭐⭐⭐ **位置**——
> 正文里的那一份已经退到中间了，这一份在末尾。

**③ compact hook 重注入**（贵，但解决的是另一件事）

`compression-truncation.md` 里那条：SessionStart + matcher `compact` 可以把关键约束写回去。它解决的是"被切掉了"，⭐⭐⭐ **不能解决"被推远了"**——压缩不发生时它不触发，而退化一直在进行。

所以 ③ 和 ①/② 是**互补**的，不是替代：前者管"没了"，后者管"远了"。

**④ fork 子代理**（最贵，也最彻底）

`context: fork` 时，技能正文是子代理提示词的**开头**，而子代理的上下文是干净的：

```
子代理上下文：[技能正文] [任务]     ← 正文在最前，且没有历史要往后推它
```

> ⭐⭐⭐⭐⭐ 子代理的会话短、无历史，于是⭐⭐⭐⭐ **退化问题在结构上不存在**——
> 不是被缓解了，是那个让正文后退的机制（对话累积）根本没启动。

这与《skill-subagents》里"fork 的关键收益是隔离"是同一件事的另一面：此前讲的是**上下文隔离**（不污染主会话），这里讲的是**位置保证**（正文不会退到中间）。
