## 1. ⭐⭐⭐⭐⭐ 只测一个数的优化，等于没测

一次典型瘦身结束时的验账方式：

```
before: 正文 3.2K tokens
after:  正文 2.1K tokens
结论：省 34% ✅
```

这个数字是真的。问题在于它测的是**单价**，而总开销是：

```
总成本 = 单价 × 触发次数 × 每次的轮次数 + 返工
```

> ⭐⭐⭐⭐⭐ **瘦身只作用于第一个因子，而另外两个因子会自己动。**

三个因子里，只有"单价"是作者能直接控制的。另两个会因为这次改动而变化——而且⭐⭐⭐⭐ **它们通常朝坏的方向变**：

| 因子 | 瘦身对它做了什么 |
|---|---|
| 单价 | ⭐ 下降（这是有意的） |
| 触发次数 | ⭐⭐⭐⭐ 常常上升 |
| 轮次数 | ⭐⭐⭐⭐⭐ 常常上升（质量下降 → 追问/返工） |

## 2. ① 触发率上升：省了单价，涨了次数

瘦身几乎总是伴随改 description——因为正文精简后，description 也要跟着改，否则会承诺正文里已经没有的东西（见《skill-structuring》的 `frontmatter-body-consistency.md`）。

而改 description 有两种方向：

```
改窄 → 触发率下降 → 总成本下降，但漏触发变多（另一种损失）
⭐⭐⭐⭐⭐ 改准 → 触发率上升 → ⭐ 总成本可能不降反升
```

第二种是最常见的，也是最讽刺的：

> ⭐⭐⭐⭐⭐ **一次成功的触发优化（命中率从 40% → 85%），
> 会让这个技能的总开销翻倍——因为它现在真的在干活了。**

而验收时看到的是"触发率提升了 45 个点"，这是一个纯利好指标；没人会把它和"这个月 token 涨了"联系起来，因为两件事在不同的报表里。

算一下就很清楚：

```
before: 0.4 × 3.2K = 1.28K/任务
after:  0.85 × 2.1K = 1.79K/任务   ← ⭐⭐⭐⭐ 涨了 40%
```

> ⭐⭐⭐⭐ **瘦身成功、触发成功、成本上升。** 三个都是真的。

这不是说不该优化触发——触发率 40% 意味着 60% 的任务没按你的流程走，那个损失更大。这里要说的是⭐⭐⭐⭐⭐ **这两件事必须放在一起算，否则你会把一次净成本上升当成两次成功**。

验账方式（很便宜）：优化前后各跑同一批输入，记录两个总数——`总触发次数` 和 `总 token`。只看第二个。

## 3. ② 挪进 reference：从一次付费变成按次付费

瘦身最常见的动作是把内容从正文挪到 `references/`。账面上：

```
正文 3.2K → 2.1K（省 1.1K）✅
```

实际发生的是**付费方式变了**，不是消失了：

```
挪之前：1.1K 每次触发必付（在正文里）
⭐⭐⭐⭐ 挪之后：1.1K 每次"读到它"才付
```

问题在于"读到它"的频率：

| 内容类型 | 被读频率 | 挪走划算吗 |
|---|---|---|
| 只在某个分支用到 | 20% | ⭐⭐⭐⭐⭐ 划算 |
| ⭐⭐⭐⭐ 几乎每次都用 | 90%+ | ⭐⭐⭐⭐⭐ **不划算** |
| 只有人需要，模型不需要 | ~0 | ⭐⭐⭐⭐ 划算（且不占上下文） |

> ⭐⭐⭐⭐⭐ **判断标准不是"这段长不长"，是"这段被用到的比例高不高"。**
> 一段 1.1K、几乎每次都被读的内容挪进 reference，
> 等于把"每次 1.1K"换成"每次 1.1K + 一次文件读取 + 一次判断要不要读"。

第二种情况里，它还额外增加了两样成本：
- ⭐⭐⭐ **判断成本**：模型每次要决定是否读它（而判断依据只有目录里那一行描述）
- ⭐⭐⭐⭐ **漏读风险**：读不到不是错误（《skill-structuring》的 `skill-structuring/references/reference-discoverability.md` 那条），于是它静默地不生效

> ⭐⭐⭐⭐ 于是"瘦身"把一个确定生效的东西，换成了一个可能生效的东西，
> 而账面上只记录了省下的那部分。

验账方式：挪走之后，跑 10 次典型任务，数一数**这个 reference 被实际读取了几次**。
- ≥ 8 次 → 它该回正文（挪错了）
- ≤ 2 次 → 挪对了

这个数通常没人测，因为⭐⭐⭐⭐ **文件读取不产生日志**（与"僵尸 reference 比僵尸技能更隐蔽"是同一个盲区）。

## 4. ③ 缓存失效：一次性的节省，反复的重算

这一条单位最小、但复利最大。缓存是前缀匹配（见 `prompt-caching-and-skills.md`）：

```
改了技能正文 → 前缀变了 → 该点之后的所有内容重算
```

于是：

```
一次性收益：省 1.1K × 每次触发
⭐⭐⭐⭐⭐ 持续性成本：每个长会话的前缀重算一次
```

在长会话里，重算的部分远大于 1.1K——它包含改点之后的**全部对话历史**。所以：

> ⭐⭐⭐⭐⭐ **一次省 1.1K 的改动，如果它在一个 50K 上下文的第 5K 处，
> 那么每个这样的会话都要多付 45K 的重算。**

这正是那条"技能加载不是一次性开销，是阶跃的重算"的具体算术。

验账方式：优化前后各跑一个**长会话**（≥ 20 轮），比总 token。短会话测不出这一项，因为短会话里前缀本来就短。

三种改动的缓存代价不同，值得分开看：

| 改动 | 改点在上下文哪里 | 重算范围 |
|---|---|---|
| 改 reference 内容 | 触发后才插入 | ⭐ 小（只影响那次会话的后续） |
| 改正文 | 触发时插入 | ⭐⭐⭐ 中 |
| ⭐⭐⭐⭐⭐ 改 allowed-tools / 触发方式 | 影响工具集 | ⭐⭐⭐⭐⭐ 大（工具集变化影响整个会话） |

## 5. ⭐⭐⭐⭐⭐ ④ 返工：省 300，赔 3000

前三项都还是 token 账。这一项不是。

瘦身删掉了什么，决定了会发生什么：

```
删了示例        → 判断质量下降
删了失败处理     → 异常时静默编造
删了验收标准     → "完成"由模型定义
删了约束的原因    → 边界情况自行适配
```

> ⭐⭐⭐⭐⭐ 每一项的节省都在 100–300 tokens 量级，
> 而它触发的返工在 1000–5000 tokens 量级（用户追问 + 重跑 + 解释）。

关键的不对称：

```
节省：每次运行 100–300 tokens，发生 N 次
返工：每次 1000–5000 tokens，发生 ⭐⭐⭐⭐⭐ 在最重要的那次
```

这跟 `context-budget-per-skill` 那条"红线永不删除"是同一个算术：

> ⭐⭐⭐⭐⭐ **省下的是线性收益，代价是尾部风险，两者差四五个数量级。**
> 而尾部风险不会出现在任何报表里——它表现为"用户这次多问了两句"。

为什么它不被记录：**返工不会被归因到瘦身**。用户多问一句，记录里是"一次正常的多轮对话"。没有人会把三个月前的那次删减和今天这次追问连起来。

验账方式（唯一需要一点诚实的）：优化后跑"失败类"输入，看是否出现静默编造。如果只跑成功路径，这一项永远是绿的——⭐⭐⭐⭐⭐ **而这恰恰是它不被发现的原因**。

## 6. 三个数一起测

结论不是"不要优化"，是⭐⭐⭐⭐⭐ **优化后的验账必须同时测三个数**，缺一个就会得出错误结论：

```
① 单价（正文 tokens）        ← 所有人都在测
② 总量（一批任务的总 token）  ← ⭐⭐⭐⭐⭐ 很少有人测
③ 质量（成功 + 失败路径）      ← ⭐⭐⭐⭐⭐ 几乎没人测
```

| 只测 | 会得出什么结论 | 漏掉什么 |
|---|---|---|
| ① | "省了 34%" | ⭐⭐⭐ 触发上涨、缓存、返工 |
| ①+② | "总量降了/涨了" | ⭐⭐⭐⭐ 质量下降（总量降可能是因为它少干活了） |
| ⭐⭐⭐⭐⭐ ①+②+③ | 真实的 | — |

第三种里最容易漏的一句：**总量下降也可能是因为技能在少干活**——触发率掉了、跳步了、静默失败了。所以②必须和③一起看。

最省事的实现：

```
优化前：跑 10 个成功输入 + 3 个失败输入，记录 总量 + 通过数
优化后：同样跑一遍
判定：总量下降 且 通过数不降 → 真的省了
     ⭐⭐⭐⭐⭐ 总量下降 但 通过数也降 → 它只是少做了事
```

以及一条该写进流程的纪律：

> ⭐⭐⭐⭐⭐ **优化类改动不单独看 diff，要看这三个数。**
> diff 只能证明"删掉了什么"，不能证明"省下了什么"——
> 而这两件事在大约一半的情况下不一致。
