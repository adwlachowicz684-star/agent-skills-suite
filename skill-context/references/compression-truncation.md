## 1. ⭐⭐⭐⭐⭐ 压缩带回的是"开头 5000"，不是"最重要的 5000"

```
会话超过阈值 → 系统压缩历史 → 带回一段摘要
⭐⭐⭐⭐⭐ 那段摘要是"开头 5000 token"，不是"最重要的 5000 token"
```

> ⭐⭐⭐⭐⭐ **系统没有能力判断哪 5000 重要，它只能取开头。**

这一条把此前几个分散观察统一成了机制：

| 观察 | 现在有了同一解释 |
|---|---|
| 关键指令放开头更可靠 | 开头是唯一被保证保留的位置 |
| 模型用 `head -100` 预览长文件 | 同一偏好，在文件读取上重演 |
| 长技能"中途失效" | 尾部被截掉了，而红线常常写在尾部 |

> ⭐⭐⭐ 推论：⭐⭐⭐⭐ **一份 400 行的技能，第 300 行那条"不要编造"，
> 在压缩后的会话里可能从未存在过**——而没有任何日志会记录这件事。

---

## 2. ⭐⭐⭐⭐⭐ 二分诊断：真失忆 vs 假失灵

长会话后期觉得技能"失效了"，只有两种可能，**修法完全不同**：

| | 真失忆 | ⭐ 假失灵 |
|---|---|---|
| 内容还在吗 | 被压缩挤出去了 | ⭐⭐⭐⭐⭐ **还在，模型选了别的路径** |
| 修法 | 重新调用一次 | 改描述 / 用 hooks 定死 |
| 常见度 | 低 | ⭐⭐⭐⭐⭐ **高得多** |

> ⭐⭐⭐⭐⭐ **诊断方法就是"重新调用一次"**——
> 回来了是真失忆，没回来就是假失灵。

零成本、十秒可完成，而它把两类完全不同的故障分开了。在此之前，多数人直接开始改描述——**而描述往往不是问题所在**。

## 3. 三种消失方式

```
① ⭐⭐⭐ 整体挤出：技能正文在加载列表里，但被更新的内容顶掉
② ⭐⭐⭐⭐⭐ 尾部截断：保留了前 N 行，红线/验收在尾部 → 丢了
③ ⭐⭐⭐⭐ 中间掏空：压缩摘要保留了首尾，中间的流程细节没了
```

第 ② 种最常被误判为"模型不听话"。第 ③ 种最隐蔽——**首尾都在，读起来是完整的**。

识别信号：

```
⭐⭐⭐⭐ "新鲜会话好用、跑到中途就不行了" → 尾部截断的特征信号
⭐⭐⭐⭐ 输出结构完整但漏掉中间某一步   → 中间掏空
```

> ⭐⭐⭐ 前者应该先削长度（<1,500 词），而不是先改描述。

## 4. ⭐⭐⭐⭐⭐ 防御：四层，从便宜到贵

```
① ⭐⭐⭐⭐⭐ 关键指令放在前 5000 token 内（免费）
② ⭐⭐⭐⭐ 红线在首、验证在尾，两端重复（免费）
③ ⭐⭐⭐⭐⭐ compact hook 重注入（便宜，一次配置）
④ ⭐⭐⭐ 缩短正文 / 拆到 references（要动结构）
```

第 ③ 条是关键——**压缩是可订阅事件**：

```yaml
# SessionStart / matcher: "compact"
# 你的命令写到 stdout 的任何文本，都会被加进 Claude 的上下文
```

> ⭐⭐⭐⭐⭐ 这比"把关键指令放开头"可靠得多：
> 后者被动顺应截断，前者主动重注入。

分寸要对：⭐⭐⭐ **每会话都需要的注入用 CLAUDE.md，不是 hook**。hook 只用于"压缩后必须恢复"的那几条。

---

## 5. 一个反直觉的结论

> ⭐⭐⭐⭐⭐ **技能越长，它在长会话里越不可靠——不是因为模型读不完，
> 而是因为它越容易被部分保留。**

一份 150 行的技能可能完整地留下来；一份 500 行的技能大概率只留下前 200 行，**而那 200 行里通常没有验收标准**。

> ⭐⭐⭐⭐ 所以"500 行上限"不是审美，⭐⭐⭐⭐⭐ **它是压缩机制的物理边界倒推出来的**。
