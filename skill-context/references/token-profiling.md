## 三笔账

```
① ⭐ 目录税（常驻）
   所有技能 description 的总和
   ⭐ 每一轮都在付，不管用没用过

② 正文加载（触发时）
   被激活技能的 SKILL.md 全文
   ⭐ 每次触发都要付

③ references 与工具输出（按需）
   按需读取的详解 + 回灌上下文的工具输出
   ⭐ 长会话里这一项常常超过前两项
```

**典型分布**（`context-budget.md` 的数据）：

```
100 个技能全量加载   = 715K tokens
三层渐进式           = ⭐ 3.4%
```

呼应 `scale-effects.md`（**`skill-governance`**）：
**1,236 个技能吃掉 36.6% 上下文**——
那是纯粹的目录税。

## 测量方法

```bash
python scripts/estimate_tokens.py ./my-skill
```

**三个口径要分开看**：

```
□ description 字符数 → 目录税（目标 300–500 字符）
□ ⭐ SKILL.md 正文行数 → 加载成本（理想 100–150）
□ references 总 token → 按需成本（每次只读需要的）
```

**一个测量陷阱**（我们实际踩过）：

> ⭐ **中文信息密度远高于英文**。
> 用单一系数估算会得出"140 行超 800 tokens"这种错误结论。
> 正确做法是 **CJK 与 ASCII 分别估算**，
> 且**告警基于行数**（与 validate 同口径），token 只作参考。

## 启动常驻的复利效应

**目录税的特殊性**：

```
□ ⭐ 它不是一次性成本——每一轮都在重复发送
□ 装 300 个技能 ≈ 9.9k token 常驻
□ ⭐ 这个数字在 60 轮对话里会被付 60 次
```

呼应 `failure-modes.md` 与 `/skill-doctor`：
**列表里每一个技能每一轮都在消耗上下文，不管有没有用过**。

**一个反直觉的推论**：

> ⭐ **把 description 写得更好（更长更具体），
> 目录税反而更贵。**
>
> 某库 1,234 个技能 × 平均 38 tokens = 46,851 tokens；
> 38 这么低恰恰是因为描述写得差。
> **写好描述会让税更重**——所以"写详细"和"多装"是冲突的，
> 必须靠**少装**来解决。

## 瘦身顺序

按单位收益排序：

```
1. ⭐ 清掉从未被触发的技能
   ——直接砍掉目录税，收益最大、风险最小
   用 /skill-doctor 看调用频率

2. ⭐ 压缩 description 到必要长度
   ——只留触发词，删掉描述性散文

3. ⭐ 正文 no-op 测试
   ——删掉删了也不影响行为的句子
   ⭐ 但 Gotchas 永不删

4. ⭐ 长工具输出回灌前摘要
   ——10,000 token 的查询结果通常能压成 200 token

5. references 按需化
   ——确认每个文件都写了"何时加载"
```

呼应 `pruning.md` 与 `runtime-failures.md`。

**第 3 条那条禁令值得重复**：

```
□ ⭐ Gotchas 是唯一几乎不可能通过 no-op 测试的部分
□ ⭐ 它是技能里信号最高的内容——永远别动
```

## 什么时候该拆而不是瘦

**三个信号**（呼应 `architecture-layering.md`）：

```
1. ⭐ 正文 >150 行且路由表无可合并项
2. ⭐ 合并已经开始牺牲可发现性
   （把异类条目硬塞进同一行）
3. references 里某一类内容明显自成一体
```

**一次真实的教训**：

```
□ 我们连续七轮靠"合并路由行"把正文压在 150 行内
□ ⭐ 每次合并都是可发现性的损失
□ 到第七次没有可合并项了——那时该拆，不是继续挤
```

> **合并同类项是可以的；合并异类项是透支。**
