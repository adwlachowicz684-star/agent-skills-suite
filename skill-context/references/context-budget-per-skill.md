## 1. ⭐⭐⭐⭐⭐ 成本可见 ≠ 成本受控

技能成本可以算得很细（常驻、触发、执行三段），但典型结果是：

```
算出"这个技能每月花 40 万 token"
→ 记在文档里
→ ⭐⭐⭐ 然后什么都没发生
```

> ⭐⭐⭐⭐⭐ **原因和"指标没有后果就等于没有指标"完全一样**：
> 成本数据没有绑定任何一个决策点，所以它是**描述性的，不是约束性的**。

对照我们已有的两条，这是同一个洞的第三次出现：

```
· 指标没有后果 = 没有指标
· 安全扫描只警告不阻断 = 会被忽略
· ⭐⭐⭐ 成本可见但没有预算 = 只是个仪表盘
```

> ⭐⭐⭐⭐ **让成本起作用的唯一方式是把它变成"能不能过"的判据。**

## 2. ⭐⭐⭐⭐ 预算的三层

| 层级 | 约束什么 | ⭐ 谁说了算 |
|---|---|---|
| **单次执行** | 一个技能跑一次最多花多少 | 技能作者 |
| **单任务挂载** | 一次任务最多挂几个技能 | ⭐ 编排/使用者 |
| **库存常驻** | 库里所有技能的元数据总量 | 库管理员 |

三层互不替代：

```
⭐⭐⭐ 只管第一层 = 每个技能都很省，但库里有 300 个
        → 常驻成本照样爆炸
⭐⭐⭐ 只管第三层 = 库很小，但一个技能单次吃掉 30K
        → 触发一次就毁掉整个会话
```

> ⭐⭐⭐⭐⭐ **第二层最常被漏，而它恰恰是收益最高的一层**——
> 因为已有硬数据：**每个任务挂载超过 3 个技能，成功率下滑**。
> 所以 ⭐⭐⭐ **第二层的预算不是一个经济数字，是一个质量上限**。

一个可执行的数字：**每次会话启动开销的健康基线 ≈ 8K tokens（200K 窗口的 4%）**，
留给对话 96%。破坏它的典型做法是全量预加载：30 × 3K = 90K。

## 3. ⭐⭐⭐⭐⭐ 单个技能的预算怎么定

不按绝对值定，按**用途**定（这正是"中间地带是技能死去的地方"的成本版）：

| 类型 | ⭐ 单次预算 | 理由 |
|---|---|---|
| **主力型**（便宜 + 高频） | 1K–2K | 每天跑几十次，贵一点就是大钱 |
| **专家型**（昂贵 + 高价值） | 8K–15K | 每周几次，但每次省下 1000+ 手工 token |
| ⭐ **中间型** | — | ⭐⭐⭐⭐ **它不该存在** |

> ⭐⭐⭐⭐⭐ **预算的用途之一，是让"中间地带"显形**：
> 一个技能说不清自己是主力型还是专家型，
> ⭐⭐⭐ 它的预算就定不出来——**这本身就是该处理的信号**。

具体算法：

```
单次预算 ≈ (这个技能替代的手工 token) × 0.3
```

> ⭐⭐⭐⭐ 系数 0.3 的理由：技能必须明显比手工便宜才有价值，
> 且要给重试和偏差留余量。超过 0.5 就该质疑这个技能的价值。

## 4. ⭐⭐⭐⭐ 超预算时的四个动作

按"先省什么"排序——**顺序很重要，因为砍错地方会让技能失效**：

**① ⭐⭐⭐⭐⭐ 砍输出，不砍指令**

```
脚本输出 3 万字塞爆上下文（真实事故）
→ 压缩到 2000 字符，⭐ 回复质量反而更高
```

> ⭐⭐⭐⭐⭐ **这是第一选择，因为输出是纯成本、零价值密度**
> ——而且"压缩后质量反升 2.8%"说明噪音本身就在损害质量。

**② ⭐⭐⭐⭐ 把长内容挪进 references**

```
触发时必读的留下；只在边界情形用到的 → 按需加载
```

**③ ⭐⭐⭐ 把逻辑搬进脚本**

```
⭐⭐⭐ 脚本源码默认不进上下文，只有输出进
→ 这是唯一一种"代码变长、成本下降"的改动
```

**④ ⭐⭐ 砍示例**

```
⭐ 注意：示例是"教判断"的部分（见 few-shot-examples.md）
   砍到 2–3 个，⭐ 不要全砍
```

> ⭐⭐⭐⭐ 排序的依据是**单位 token 的价值密度**：
> 输出 < 参考文档 < 正文逻辑 < 示例。
> ⭐⭐⭐ 反过来砍（先砍示例）会让技能变蠢且成本没降多少。

## 5. ⭐⭐⭐⭐⭐ 唯一不能砍的部分

> ⭐⭐⭐⭐⭐ **红线、失败处理、验收，永不为了省 token 删除。**

理由不是"它们重要"这种空话，是一个具体的经济对比：

```
省下的：每次触发 100–300 token
代价：  ⭐⭐⭐⭐ 一次静默编造的排查成本（半天到几天）
        ⭐⭐⭐⭐⭐ 一次错误写入的回滚成本（可能是不可逆的）
```

> ⭐⭐⭐⭐⭐ **这个比值差了四五个数量级。**
> 而"为了省几秒/几个 token 而删掉约束"正是我们反复记录的事故来源。

一个可操作的检查：

```bash
# 如果为了瘦身删掉这些内容，应当被评审拦下
grep -nE "^(## 红线|## 失败|## 验证|## Critical)" SKILL.md
```

> ⭐⭐⭐ 判据一句话：**省下来的 token 是线性的，
> 而删掉约束的风险是尾部的**——永远不要用尾部风险换线性收益。

## 6. ⭐⭐⭐ 三个反模式

| 反模式 | 表现 | ⭐ 为什么错 |
|---|---|---|
| ⭐⭐⭐ 只设总量不设单项 | "全库不超过 20K" | 一个大技能吃光，其余全饿死 |
| ⭐⭐⭐ 预算设了不检查 | 写在文档里 | ⭐⭐⭐⭐ 又变回仪表盘 |
| ⭐⭐⭐⭐ 用平均值判健康 | "平均 800 token，很健康" | ⭐⭐⭐⭐ 平均掩盖分布——见 10% 流量全挂只掉 1–2 点 |

第三条和灰度那份完全同源：**平均值是分布 badly 的 summary**。
正确做法是看 **P95 和最贵的那一个**。

> ⭐⭐⭐ 还有一个容易忽略的：**预算也要给"失败路径"**。
> 一个技能成功时花 2K，失败重试三次花 8K——
> ⭐⭐⭐ 而失败恰恰是你最不想再被收费的时候。
> 所以重试预算（见 `skill-recovery/references/budget-caps-no-progress.md`）应当独立于单次预算设定。
