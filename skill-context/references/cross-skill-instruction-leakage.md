## 1. ⭐⭐⭐⭐⭐ 没有"技能退出"这个事件

变量有作用域，函数有返回，进程有退出。技能有什么？

```
加载：有（触发时正文被插入上下文）⭐
退出：⭐⭐⭐⭐⭐ 没有任何机制
```

正文一旦进入上下文，它就是**一段普通的上下文文本**。没有任何标记表明"这段来自技能 X"，也没有任何时刻会把这段标记为"已失效"。

> ⭐⭐⭐⭐⭐ **指令的生命周期 = 上下文的生命周期，而不是任务的生命周期。**

这在短会话里看不出来（任务结束 = 会话结束）。在长会话里，一个会话里会依次做很多件不同的事：

```
① 用"只读审计"技能看代码      → 注入：不得修改任何文件
② 讨论                        → 那条仍在
③ ⭐⭐⭐⭐ 用户说"把这两处改掉"  → 那条仍在
```

而③里模型的行为有三种，没有一种是正确的：

```
A 严格遵守"不得修改"   → 拒绝一个用户明确要求的合法操作
B 忽略它              → 运气好，但同一会话里下一次又可能遵守
C ⭐⭐⭐⭐⭐ 折中       → 改一部分、用"建议"的形式给 diff、或者先问一堆问题
```

> ⭐⭐⭐⭐⭐ **C 最常见，因为它同时满足了两个矛盾的约束——
> 而用户看到的是一个莫名其妙地犹豫和啰嗦的助手。**

没有报错、没有日志、没有"这个技能现在还生效吗"的提示。用户只会觉得"它今天有点怪"。

## 2. 三类残留，按危险程度排序

| 类型 | 例子 | 残留后 | 危险度 |
|---|---|---|---|
| ① ⭐⭐⭐⭐⭐ 约束类 | "不得修改文件""不得发送""输出不超过 3 行" | 后续任务被无谓地限制 | 最高 |
| ② ⭐⭐⭐⭐ 格式类 | "用表格输出""每条一行""先给结论" | 后续输出格式不对 | 中 |
| ③ ⭐⭐⭐ 流程类 | "先读 A 再读 B""每次都要校验" | 后续多做无用步骤 | 低 |

**① 之所以最高**，是因为它是唯一会**阻止**事情的那一类。②和③只是让输出变难看或变慢，①会让一个本该发生的动作不发生——而"没发生"不会留下任何痕迹。

三类里只有 ① 会触发模型给用户一个"我不能这样做"的解释，而这个解释通常不会提到技能的名字：

> ⭐⭐⭐⭐⭐ **"出于安全考虑，我不建议直接修改文件"——
> 用户不知道这句话来自 20 分钟前那个已经结束的审计任务。**

**② 有个特别的表现形式**，值得单独记：

```
用了 A（输出表格）→ 后续聊别的 → 输出仍是表格
用户："别用表格了" → 下一轮是表格
```

用户会认为模型"没听懂"。而实际上模型听懂了、也执行了，**只是那句"用表格输出"还在上下文里，且在下一轮重新参与竞争**。

## 3. ⭐⭐⭐⭐⭐ 最危险的形状：约束比授权活得久

这一条值得单独拿出来，因为它是本份最重要的发现：

```
授权（"你是一个只读审计助手"）  → 任务结束时应失效
约束（"不得修改文件"）          → ⭐⭐⭐⭐⭐ 它不会失效
```

> ⭐⭐⭐⭐⭐ **授权和约束写在同一个正文里，而它们的有效期不同：
> 授权在任务结束时到期，约束永远不到期。**

因为约束是**禁止性**的，而禁止性指令在上下文里的权重天然更高（可以参考《skill-crafting》里"'不要'指令出奇地有效"那条——禁令有效是好事，但它有效得**太久**就是问题）。

具体的失效链：

```
只读审计任务（合法约束：不得修改）
  ↓ 任务结束
用户要求修复（合法需求：修改）
  ↓
模型处于"被禁止修改"状态
  ↓
⭐⭐⭐⭐⭐ 它既不能改，也不能说"因为审计任务要求我不改"
        （因为没有机制告诉它那个任务已经结束了）
  ↓
输出：一堆 diff 建议 + "请确认后手动应用"
```

> ⭐⭐⭐⭐⭐ **这个输出看起来是"谨慎"，实际上是"残疾"。**
> 而它不会报错——用户拿到的是一堆正确但没用的建议。

## 4. 为什么用户修正只生效一轮

用户发现了不对，于是纠正：

```
用户："这个项目里可以直接改，不用问我。"
模型："好的。" → 改了 ✅
下一轮：又问一遍 ❌
```

用户此时会认为模型"没记住"。模型确实记住了——那句"好的"和用户的授权都在上下文里。问题在另一侧：

> ⭐⭐⭐⭐⭐ **"不得修改文件"也还在上下文里，而且它是⭐ 明确写下的技能指令，
> 而用户的授权是一句对话。**
> 当两者冲突时，明确写下的结构化指令通常权重更高。

于是形成这个形状：

```
[技能指令：不得修改]  ......  [用户：可以改] ...... [当前轮]
        ↑ 远                              ↑ 近但权重低
```

> ⭐⭐⭐⭐⭐ 用户的修正只在**紧邻的那一轮**压过技能指令。
> 再过一轮，它自己也退到中间去了，而技能指令的绝对权重更高——于是约束复活。

这条解释了那个非常常见的抱怨："我明明说了可以，它怎么又不行了"。排查时通常归因为"模型记忆差"或"上下文丢了"，而真相是⭐⭐⭐⭐ **两条都在，只是权重关系随时间变化**。

**与之对比**：`instruction-position-decay` 讲的是"同一份指令往后退"，这份讲的是"两份冲突的指令里，权重低的那份先退"。两者叠加时最难诊断——因为它表现为"有时遵守有时不遵守"，会被归进失败四象限的第 ④ 格（对但不稳），然后按"加示例"去修，方向完全错了。

## 5. 判据：删掉它，当前轮次会变吗

有没有残留，用一个思想实验就能判定：

> ⭐⭐⭐⭐⭐ **把那个技能的正文从上下文里删掉，当前这一轮的行为会变吗？**
> **会 → 它正在残留地生效，而它不是为当前任务设计的。**

这个判据的价值在于它把"感觉它有点怪"变成了一个可回答的问题。三种答案：

| 答案 | 含义 |
|---|---|
| 会明显变 | ⭐⭐⭐⭐⭐ 强残留，正在扭曲当前任务 |
| 会变一点 | 格式/流程类残留（低危） |
| 不变 | 已自然失效（通常因为话题已完全转换） |

执行上不需要真的删——问一句"你现在还在按哪个技能的规则做事？"通常就能让模型说出来，而它说出的那个技能名如果不是当前任务该用的，就是残留。

> ⭐⭐⭐ 这是"问模型它在用什么技能"那一类低成本诊断的又一个用法，
> 与 `skill-triggering` 里的"When would you use X"同族。

## 6. 四种收束手段

**① 在正文里写清适用范围**（最便宜，约 20 tokens）

```
❌ "不得修改任何文件。"
✅ ⭐⭐⭐⭐⭐ "本条仅适用于本技能执行的审计任务；任务结束后不再约束其他操作。"
```

看起来是废话（"当然是这个任务"），而它恰恰是把作用域**写进了文本**——于是它在上下文里带着自己的失效条件一起存在，而不是裸着。

> ⭐⭐⭐⭐ 判据：把这条单独抽出来读，能看出它什么时候失效吗？
> 看不出 → 它会一直生效。

**② 任务结束时显式注销**（中等）

在技能末尾加一段收尾指令：

```
任务完成后输出："本次审计结束，以下约束（不得修改文件）不再适用。"
```

它的作用不是告知用户，是⭐⭐⭐⭐ **在上下文里留下一条"作用域终止"的记录**——后续轮次里，模型面前同时有"禁止"和"禁止已解除"两条，后者在后、更近，通常能赢。

**③ 新任务显式覆盖**（需要用户或编排层配合）

切换任务时把旧约束明确否定掉，而不是靠"话题自然转换"。最省的形式：

```
"换一个任务，不受前面的限制。"
```

> ⭐⭐⭐⭐ 这一点必须写进使用习惯，因为⭐⭐⭐⭐⭐ **话题转换本身不产生任何上下文事件**——
> 没有任何东西会因为"现在在聊别的"而被移除或被降权。

**④ fork 子代理**（最彻底）

```
子代理上下文：[技能正文] [任务] → 子代理结束 → ⭐ 整个上下文丢弃
```

> ⭐⭐⭐⭐⭐ **fork 是唯一一种"技能真的会退出"的机制**——
> 它的指令随子代理的上下文一起消失，不存在残留。

这与《skill-subagents》"fork 的关键收益是隔离"是同一结论的第三个应用面：前两个是"不污染主会话"和"位置保证"，这里是⭐⭐⭐⭐⭐ **作用域终止**。三个好处来自同一个机制，而第三个此前没有被单独说过。
