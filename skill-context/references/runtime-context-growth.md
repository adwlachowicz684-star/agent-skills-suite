## 1. ⭐⭐⭐⭐⭐ 预算里算的是入场费，不是占地费

所有上下文预算文档算的都是同一件事：

```
L1 元数据（常驻）+ L2 正文（触发时加载）+ L3 参考（按需读取）= 这个技能的成本
```

这是一次**入场费**。它算完之后，模型就开始干活了——而干活这件事本身会往上下文里写东西：

```
进度汇报 · 工具输出 · 日志 · 重试记录 · 中间结果 · 最终输出
```

> ⭐⭐⭐⭐⭐ **没有一个预算文档把这部分算进去，而它在长任务里通常远大于入场费。**

一个具体对照：一个技能正文 2K tokens；它跑 12 步、每步输出 100 tokens 的进度 + 调用 12 次工具、每次返回 800 tokens——**运行产出 10.8K，是入场费的 5 倍**。

```
入场费：2K    ← 被预算、被审计、被反复优化
产出：  10.8K ← 没人算过
```

> ⭐⭐⭐⭐⭐ 优化入场费省下 500 tokens 会被写进周报；
> 产出里随手多打一行日志，12 步就是 12 行，没人会注意到。

**为什么它一直没被算**：入场费发生在**加载时**，是一个可以在不运行的情况下测量的数（量一下文件就知道了）；产出发生在**运行时**，只有跑完才知道，而跑完之后上下文已经满了，没人会回头去数"这 10K 是哪来的"。

## 2. 六类产出，按"留在上下文里多久"排序

关键变量不是"多大"，是**它会不会参与后续所有轮次**。留到最后的东西会被反复读、反复参与注意力分配、并且反复作为前缀被缓存和重算。

| 产出 | 典型大小 | ⭐ 会不会留到最后 |
|---|---|---|
| ① 最终输出 | 200–2K | ✅ 必然 |
| ② ⭐⭐⭐⭐⭐ 工具/脚本返回值 | 100–30K | ✅ 必然（除非落盘） |
| ③ ⭐⭐⭐⭐ 进度汇报 | 30–200 / 步 | ✅ 必然，且**逐条累积** |
| ④ 错误与堆栈 | 200–2K | ✅ 通常（重试时会重复） |
| ⑤ 中间结果 | 视实现 | ⭐ 取决于是否落盘 |
| ⑥ 子代理返回 | 500–5K | ✅ 必然（且是压缩后的） |

三类值得单独说：

**② 是唯一的极端值。** 一次全表扫描、`cat` 一个大文件、抓一个网页——几百到几万 tokens 一次性进入上下文，且它们**在后续每一轮都被完整保留**。《skill-structuring》的三起翻车现场里那起 3 万字事故就是它。

**③ 是唯一会线性累积的。** 其余五类都是一次性事件，只有进度汇报是**步数的函数**。一个 12 步的技能，光进度就是 12 条；如果每步还带一句"已完成，接下来……"，就是 24 条。

**④ 是最容易被低估的。** 堆栈通常在失败时出现，而失败常常伴随重试——于是同一段堆栈出现 2–3 次，且⭐⭐⭐⭐ **它出现在上下文里的位置正是模型最需要冷静判断的地方**。

## 3. ⭐⭐⭐⭐⭐ 进度汇报：看起来最省，实际最贵

进度汇报的每一条单独看都是"好实践"：

```
正在读取配置……（32 tokens）
已读取 3 个文件，接下来分析……（48 tokens）
分析完成，发现 2 处问题，正在生成报告……（55 tokens）
```

三条合计 135 tokens，占窗口 0.07%。问题不在单条，在**它是步数的函数**：

```
12 步 × 45 tokens = 540
30 步 × 45 tokens = 1350
```

> ⭐⭐⭐⭐⭐ 而**步数恰恰是"任务变复杂"的直接体现**——
> 也就是说，产出最大膨胀发生在最需要省的时候。

更关键的是它**不能用完即弃**：

> ⭐⭐⭐⭐⭐ **进度汇报是上下文里唯一一类"已经没有用但仍在参与后续每一轮"的内容。**

第 3 步的"已读取 3 个文件"在第 12 步已经没有任何价值——但它还在，还在被注意力分配计算，还在作为前缀的一部分被缓存计费。

**为什么"少汇报"又是错的**：完全不汇报会让用户在长任务里失去可见性，而⭐⭐ **静默的长任务会诱发用户中断**——中断的代价远大于那 540 tokens。

所以修法不是删，是**改形状**：

| | 每条独立留在上下文 | ⭐ 覆盖式进度 |
|---|---|---|
| 12 步后占用 | 12 条 | ⭐ 1 条（当前状态） |
| 历史可见吗 | ✅ | ⭐⭐⭐⭐ 通常不需要 |
| 中断后能续吗 | 靠读全部历史 | ⭐⭐ 靠读当前状态 |

覆盖式进度的实现很朴素：**每步输出"当前：第 N 步 / 共 M 步 · 状态"，而不是"已完成第 N 步"**。前者在语义上是"当前值"，后者在语义上是"一条新记录"——⭐⭐⭐⭐ 模型对两者的处理方式不同：新记录会被追加保留，当前值会被后续同名字段替换。

> ⭐⭐⭐⭐⭐ 判据一句话：**这条输出在三步之后还有人需要读它吗？**
> 没有 → 它应该被覆盖，不应该被追加。

## 4. ⭐⭐⭐⭐ 返回值的形状由作者决定，代价由会话承担

工具返回多少，通常被认为是"工具的事"。但返回值的形状几乎总有一个人决定：

```
写了 extract(path)          → 返回全文
写了 extract(path, fields=) → 返回字段
写了 extract(path) > file   → 返回路径 + 摘要
```

> ⭐⭐⭐⭐ **第三种和第一种的差别不在工具能力，在作者写调用时多打了几个字。**
> 而这两种选择在上下文账本上差一到两个数量级。

`skill-recovery/references/three-crash-scenes.md` 里那起事故的修复就是把第一种改成第三种：3 万字 → 不到 2000 字符，且⭐⭐⭐⭐ **回复质量反而更高**。

这里有个容易被忽略的对称：

```
脚本源码 → 默认不进上下文（便宜）
脚本输出 → 必进上下文（贵）
```

> ⭐⭐⭐⭐⭐ 所以"把逻辑从正文搬进脚本"是唯一一种**代码变长而成本下降**的改动——
> 而这个结论成立的前提是**脚本输出也被管住了**。
> 只搬逻辑不管输出，等于把入场费换成了产出费，总量可能更大。

三条硬规则，按有效性排序：

1. ⭐⭐⭐⭐⭐ **超过 2K 的返回值先落盘，只回传路径 + 摘要 + 计数**
2. ⭐⭐⭐⭐ 摘要里必须包含"总量"字段（否则下游无法判断有没有被截断）
3. ⭐⭐⭐⭐ 分页结果必须报"已取 N / 共 M"（见《skill-aggregation》的 `skill-aggregation/references/fan-out-fan-in.md`）

第 2 条尤其重要：**没有总量字段的摘要，会把"截断了"伪装成"就这么多"**——又是"0 与未获取"那个老问题的另一个入口。

## 5. ⭐⭐⭐⭐⭐ 产出的三个去向，只有两个能止损

产出一旦产生，只有三个去处：

| 去向 | 后续轮次还要付吗 | 可恢复吗 |
|---|---|---|
| ⭐ 留在上下文 | ⭐⭐⭐⭐⭐ 每一轮都付 | 压缩后可部分找回 |
| 落盘为文件 | ❌ 不付（只有路径在） | ✅ 随时读回 |
| 丢弃 | ❌ 不付 | ❌ 不可恢复 |

> ⭐⭐⭐⭐⭐ **留在上下文是唯一一个"持续计费"的选项，而它是默认选项。**

默认会发生，是因为产出只要被打印出来就自动进入上下文——**没有任何一步需要作者决定"这个要留"**。而另两个去向都需要一个显式动作（写文件 / 不打印）。

所以它需要的不是"记得清理"，是**把默认反过来**：

```
默认：产出 → 上下文
⭐ 改为：产出 → 文件 + 回传（路径 + 摘要 + 计数）
          只有"用户需要当场看到的内容" → 上下文
```

判据很干净：**这段内容是给用户看的，还是给后续步骤用的？**
- 给后续步骤用 → 落盘（后续步骤能读文件，不需要它在上下文里）
- 给用户看 → 进上下文（且要短，见 `output-length-budget.md`）

## 6. 给产出也定预算

入场费有预算，产出没有。补上它的方式不是再加一套表格，是把现有预算表多写一行：

```
这个技能：
  L1 元数据      ≈ 40 tokens
  L2 正文        ≈ 2K tokens（触发时）
  ⭐ 运行产出     ≈ ? tokens/次运行   ← 这一行通常没人填
```

填不出来时用一个粗糙但有效的估计：

```
产出 ≈ 步数 × 每步汇报 + 工具调用次数 × 平均返回 + 最终输出
```

> ⭐⭐⭐⭐⭐ 只要有人填过一次，就会发现大多数技能里**产出 > 入场费**。
> 而此前所有的优化工作都集中在较小的那一项上。

三个最有效的动作，按性价比排序：

| 动作 | 省在哪 | 代价 |
|---|---|---|
| ⭐⭐⭐⭐⭐ 大返回值落盘 | ② 唯一能到 30K 的项 | 写几行代码 |
| ⭐⭐⭐⭐ 进度改覆盖式 | ③ 唯一线性累积的项 | 改措辞 |
| ⭐⭐⭐ 摘要带总量字段 | 防止截断被当成完整 | 一个字段 |

以及一条反向提醒：

> ⭐⭐⭐⭐ **产出的可见性不能为了省 token 而被牺牲。**
> "什么都不打印"确实最省，但它换来的是⭐⭐⭐⭐⭐ **静默的长任务**——
> 而静默会诱发中断，中断会让整次运行的产出全部作废。
> 省下的 token 在作废面前是零。
