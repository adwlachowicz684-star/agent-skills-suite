## 实测：各项技术省多少

一份按技术逐项测量的报告（单位 tokens）：

| 技术 | 优化前 | 优化后 | 节省率 |
|---|---|---|---|
| **Progressive Disclosure** | **35,803** | **1,789** | **95.0%** |
| Observation Masking | 2,222 | 95 | 95.7% |
| Handoff Summary | 3,777 | 255 | 93.2% |
| Hierarchical Summarization | 3,777 | 428 | 88.7% |
| Context Partitioning + Budget | 3,682 | 435 | 88.2% |
| Filesystem Offloading | 1,250 | 203 | 83.8% |
| Selective Retention | 904 | 145 | 84.0% |
| Tool Schema Optimization | 1,571 | 292 | 81.4% |
| Format Optimization | 493 | 136 | 72.4% |
| **合计** | **56,415** | **4,012** | **92.9%** |

> ⭐ **关键发现：Progressive Disclosure 是单项最大的节省（34K tokens）。**
> 启动时加载 15 个技能描述只要 1,789 tokens；
> 而加载全部技能正文 + references 要 35,803。

**这正好解释了为什么"按需加载"不是优化技巧而是架构基础**——
它一个人贡献了整套优化里最大的一块。

另一个值得记的数字：**Tool Schema Optimization 实测 5.4x 膨胀**
（比技能文档里常说的 2–3x 更严重）——所以**工具描述也要精简**。

## 预算模型：2% 规则

> 技能描述的总预算是**上下文窗口的 2%**。

| 上下文窗口 | 描述总预算 | 单技能目标 | 可容纳技能数 |
|---|---|---|---|
| 200k tokens | ~16,000 字符 | 300–500 字符 | ~40 |
| 1M tokens | ~80,000 字符 | 300–500 字符 | ~200 |

**推论**：

1. 这个预算是**所有技能共享**的，不是每个技能独占
2. **单个技能描述控制在 300–500 字符**是硬道理
3. 装 40 个技能就吃满 200k 窗口的 2%

**分级策略**（按技能大小）：

| 规模 | token 范围 | 策略 |
|---|---|---|
| Minimal | <150 | 单文件即可 |
| Standard | 150–300 | 核心 + 少量 references |
| Large | 300–800 | 必须拆模块 |
| **超大** | **>1,500** | **必须拆成多个独立技能** |

## 四桶策略

> **Write / Select / Compress / Isolate**

| 桶 | 做法 | 典型节省 |
|---|---|---|
| **Write** | 把上下文存到外部（草稿板、文件） | — |
| **Select** | 只拉相关的（检索、过滤） | — |
| **Compress** | 压缩（摘要、masking） | 50–70% |
| **Isolate** | 分给子代理（分区） | 视任务 |

### Compress 的优先级

```
工具输出   → 用摘要替换
早期对话轮次 → 摘要掉
检索到的文档 → 若有更新版本则摘要掉
系统提示    → 永不压缩
```

**按类型保留什么**：

| 类型 | 保留 |
|---|---|
| 工具输出 | 发现、指标、结论 |
| 对话 | 决策、承诺、上下文转折 |
| 文档 | 关键事实，去掉支撑证据 |

### Observation Masking

> **工具输出可以占到 80%+ 的 token。**

```python
if len(observation) > max_length:
    ref_id = store_observation(observation)
    return f"[Obs:{ref_id} elided. Key: {extract_key(observation)}]"
```

| 决策 | 内容 |
|---|---|
| **永不 mask** | 当前任务关键、最近一轮、活跃推理 |
| **考虑 mask** | 3 轮以上、关键点可提取、目的已达成 |
| **总是 mask** | 重复输出、样板文字、已摘要过的 |

## 预算分区

> 设 `fillPercentage` 策略，`warning: 0.7`、`hardLimit: 0.9`
> **这一个实践能防住 90% 的上下文腐烂事故。**

| 区间 | 状态 | 动作 | 影响 |
|---|---|---|---|
| **0–50%** | 绿 | 正常运作 | 完整推理质量 |
| **50–70%** | 注意 | 压缩工具输出 | 响应时间 −10% |
| **70–85%** | 警告 | 驱逐低价值历史 | 成本 −20%，质量不变 |
| **85–100%** | 严重 | 保存 + 派生子代理 | 防止彻底劣化 |

**KV-cache 目标**：稳定负载 **70%+ 命中率**。

> **忽略缓存经济学会浪费 10 倍 token 成本。**
> 对输入:输出 = 100:1 的 agent，这是**单项最大的成本优化**。
> 重构上下文以稳定缓存，**应该在所有其他优化之前做**。

**缓存友好排序**：稳定内容在前，独特内容在后。

```
[系统提示, 工具定义, 复用模板]  ← 可缓存
[独特内容]                      ← 唯一
```

避免在缓存前缀里放时间戳等动态内容。

## 优化后的技能比没有技能还便宜

一个代码评审任务的实测对比：

| 方案 | tokens | 相对成本 |
|---|---|---|
| 无技能，冗长提示 | ~15,000 | 1.0x（基线） |
| **未优化的技能** | ~25,000 | **1.7x** |
| **优化后的技能** | ~10,000 | **0.7x** |
| 优化技能 + 拆分子技能 | ~7,000 | **0.47x** |

> ⭐ **优化后的技能比不用技能还便宜**——
> 因为它**阻止了 Claude 去探索不必要的路径**。

这直接反驳了"技能增加成本"的直觉：**成本取决于技能写得怎么样，不是装不装**。

**也提醒**：写得差的技能会让成本**翻倍**（1.7x）。

## 瘦身重构清单

已有技能太耗 token 时，**按此顺序**处理：

```
□ 1. 精简文件：删掉所有"You should + 模型默认就会做"的句子
□ 2. 共享上下文移到 CLAUDE.md：出现在多个技能里的内容集中化
□ 3. 重排章节：约束和工作流步骤放顶部，背景说明放底部
□ 4. 审查工具指令：把 Read 改成 Grep-first
□ 5. 加迭代上限：每个"keep trying until…"都加明确最大次数
□ 6. 加输出格式指令：说清成功和失败各输出什么样，让它交付即停
□ 7. 检查拆分机会：覆盖多个主工作流就拆
□ 8. 表格化：配置/选项类内容用表格压缩（60%+ 空间）
```

> 对成熟但未优化的技能应用这份清单，
> 通常能**减少 40–60% token 占用，而不改变它产出什么**。

**迁移四阶段**：发现（`wc -l`、`grep "^##"`）→ 规划 → 实施 → 优化 → 验证。

## Token 效率金字塔

```
┌─────────┐
│  必要的 │ ← 保留：触发词、核心知识
├─────────┤
│  有用的 │ ← 精简：最佳实践、常见错误
├─────────┤
│  美化的 │ ← 移除：ASCII 艺术、装饰性图表
├─────────┤
│  范例化 │ ← 外连：模板、完整示例、checklist
└─────────┘
```

| 策略 | 节省估计 |
|---|---|
| 分层加载（核心 + 扩展分离） | 40–60% |
| 外连参考（大示例移到独立文件） | 20–30% |
| 精简表达（去冗余修饰语） | 10–15% |
| 图表简化（ASCII → 简洁描述） | 5–10% |

> 注意：**ASCII 框图在"美化"层，是优先删除对象**——
> 但对人可读性有帮助。**权衡点**：SKILL.md 是给模型读的，
> 装饰性图表留给 README。

## 真正的开销大户

按可控性排序（**从上到下是你最能控制的**）：

| 项 | 量级 | 控制手段 |
|---|---|---|
| **CLAUDE.md** | 72KB 文件 ≈ **20,000 tokens/请求** | 压到 ≤200 行，当索引用 |
| **子代理 fan-out** | 1 任务分 2 个子代理：**121k → 513k（4.2x）** | 只在并行收益 > 成本时用 |
| **闲置 MCP server** | 每个 1–1.4k；5 个 ≈ **4,900–6,967/请求** | 断开不用的 |
| **读整个文件** | ~2,400 vs 精确读 ~300 | `Read(offset, limit)` / Grep-first |
| **小改动用 Write** | ~5,000 vs Edit ~200（**96%**） | 优先 Edit |
| 会话重启 | 重扫代码库，$1–2+ | 尽量保活；用 CLAUDE.md 交接文件 |

**技能本身的启动开销反而不大**：

| 技能数 | 启动开销 |
|---|---|
| 30 个 | ~1,500 tokens |
| 100 个 | ~5,000 tokens |
| 4 个（仅描述） | ~155 tokens |

> 符号链接 10+ 个技能只 ~500 tokens 开销——**放心链**。

**一条反直觉的建议**：

> 别去优化那个 ~33k 的启动前缀——它是**稳定的、被缓存的**，
> 你只付一次全价，之后都是缓存读取。
> **优化真正每轮都在增长的部分**：CLAUDE.md、MCP 输出、对话历史。
