## 1. ⭐⭐⭐⭐⭐ 模型只看到一条新消息

用户在同一轮里说：

```
"帮我整理这 20 条记录"
（跑了 6 条）
"哦对了，只要最近一周的"
```

> ⭐⭐⭐⭐⭐ **模型不会区分"补充信息"和"改变主意"——
> 它只看到一条新消息。**

两者的处理完全相反：

| | 补充信息 | ⭐⭐⭐ 改变主意 |
|---|---|---|
| 已完成部分 | 仍有效 | 可能要作废 |
| 正确动作 | 继续 | ⭐⭐⭐⭐ 先判断哪些受影响 |

而默认的默认是"继续"——
⭐⭐⭐⭐⭐ **因为继续是唯一不需要判断的动作。**

这个不对称就是全部问题的根源：
**判断"哪些受影响"很难，"全部重跑"很容易。**

## 2. ⭐⭐⭐⭐⭐ 四问与四答

收到中途变更时，先判类型：

| 类型 | 信号 | ⭐ 正确动作 |
|---|---|---|
| ⭐⭐⭐⭐ 扩大范围 | "也把 X 加上" | 新任务 → 重新规划 |
| ⭐⭐⭐⭐⭐ 缩小范围 | "只要最近一周的" | ⭐⭐⭐⭐⭐ **已完成部分仍然有效，筛掉即可，不要重做** |
| ⭐⭐⭐⭐⭐ 换目标 | "算了，改成做 Y" | ⭐⭐⭐⭐ **已完成的写入动作必须报告** |
| ⭐⭐⭐⭐⭐ 改细节 | "日期用 ISO 格式" | ⭐⭐⭐⭐⭐ **只重做受影响部分** |

> ⭐⭐⭐⭐⭐ 第二条最常被违反，且违反的代价最不对称：
> **重做 6 条的成本是浪费，但它是"安全的浪费"——
> 没人会抱怨结果不对。**
> 于是这个错误永远不会被发现，永远不会被修。

第三条最危险：

> ⭐⭐⭐⭐⭐ **目标换了，但已经写入的部分不会因为目标变更而消失。**
> 模型倾向于"转向新目标"而不提已经做了什么——
> 因为那部分在它的叙事里已经"不算了"。

## 3. ⭐⭐⭐⭐⭐ 改细节时不要从头再来

这是最高频、也最浪费的一种：

```
"日期用 ISO 格式"
→ 模型重新处理全部 20 条
→ ⭐⭐⭐⭐⭐ 但它只需要改已经产出的那 6 条的日期字段
```

> ⭐⭐⭐⭐⭐ **模型倾向于全部重跑，
> 因为"判断哪部分受影响"比"全部重跑"难得多。**

而这个倾向的代价，在能重跑的场景下是浪费，
在⭐⭐⭐⭐⭐ **不可重跑的场景下是数据损坏**：

```
如果那 6 条已经写入了目标文件 → 重跑会产生重复条目
如果那 6 条已经发出去了     → 重跑会发第二遍
```

（这与 `idempotency-resume.md` 里"重试要区分'没写入'和'已写入但回应丢失'"是同一条原则。）

判据一句话：

> ⭐⭐⭐⭐⭐ **问一句"哪些已完成的部分不受这次改动影响"，
> 比默认全部重跑安全，也比它快。**

## 4. ⭐⭐⭐⭐ 已完成的写入动作必须报告

目标变更时的报告格式：

```
目标已变更：从"整理 20 条"改为"生成 Y"。
⚠️ 变更前已完成且不可撤销的写入：
   - 已写入 /tmp/report.md（第 1–6 条）
   - 未发出任何通知
已完成的可撤销部分：无
接下来按新目标执行。
```

> ⭐⭐⭐⭐⭐ **"已完成的写入"这一节是这份报告里唯一不能省的部分。**
> 省了它，用户会以为什么都没发生——
> 而实际上文件系统里已经有一个半成品。

> ⭐⭐⭐⭐⭐ 这与 `human-checkpoint-design.md` 那条
> "不可逆的部分"是同一件事的两种出现时机：
> 那份是**做之前**展示，这份是**目标变了之后**补报。

一个容易漏的点：

> ⭐⭐⭐⭐ **未发出任何通知** 这句话要显式写出来。
> 用户最担心的往往不是文件，**是"有没有已经发出去的东西"**——
> 而发通知是唯一一个错误会跑到组织外部、且无法收回的动作。

## 5. ⭐⭐⭐⭐⭐ 同一任务内只问一次

反向的纪律：

> ⭐⭐⭐⭐⭐ **同一任务内，同一个问题最多问一次。**

违反的情形很常见：

```
问"用哪个模板？" → 用户答 A → 跑到一半 → 又问"用哪个模板？"
```

> ⭐⭐⭐⭐⭐ **第二次问不是谨慎，是三重失败**：
> ① 它没读到自己的上下文
> ② ⭐⭐⭐⭐⭐ **它暗示用户刚才的回答可能被推翻了**
> ③ 用户会开始怀疑是不是自己表达不清

> ⭐⭐⭐⭐⭐ 这与 `human-checkpoint-design.md` 那条
> "无脑确认会摧毁检查点的全部价值"是同一条：
> **重复确认把安全机制变成仪式。**

配套做法（很便宜）：

```
⭐⭐⭐⭐⭐ 把已确认的参数写进进度汇报
   "已确认：模板 A、范围最近一周、格式 ISO"
```

一句话的成本，换来的是：
**后续每一步都能看到这些，不需要再问，也不需要去翻前面的对话。**

## 6. ⭐⭐⭐⭐ 三行模板

把上面四节压成一个可抄的格式：

```markdown
## 处理中途变更

1. ⭐⭐⭐⭐⭐ 判类型：扩大 / 缩小 / 换目标 / 改细节
2. ⭐⭐⭐⭐⭐ 说清哪些已完成部分受影响（不是"重新来一遍"）
3. ⭐⭐⭐⭐ 若涉及已写入：列出不可撤销的部分
```

三行，不到 60 token，覆盖的是
⭐⭐⭐⭐⭐ **"每一次用户中途插话"**——
而这在真实对话里是高频事件。

> ⭐⭐⭐⭐⭐ 性价比论证（与"默认动作"那份同构）：
> 写 20 条具体规则只能覆盖 20 种变更；
> 写这 3 行，覆盖的是**所有你没预料到的变更**。
