## 1. ⭐⭐⭐⭐⭐ 一个没有编号的顺序

```markdown
- 读取配置
- 提取字段
- 归一化日期
```

> ⭐⭐⭐⭐⭐ 三条都写了，⭐⭐⭐⭐⭐ 但"必须先归一化再提取"这个约束
> ⭐⭐⭐⭐⭐ **在任何一行里都没有出现**——它只存在于列表的排列中。

而列表的排列顺序，模型会当作**一种建议**，不是约束。

---

## 2. ⭐⭐⭐⭐⭐ 三种隐式顺序

**① ⭐⭐⭐⭐⭐ 清洗 → 使用**（最常见）

```
归一化日期 → 才能按日期排序
去重 → 才能计数
```

> ⭐⭐⭐⭐⭐ 反了也不报错：⭐⭐⭐⭐ 先排序再归一化，输出仍然是一份排好序的列表，
> ⭐⭐⭐⭐⭐ 只是顺序是**按字符串**排的——而它看起来完全正确。

**② ⭐⭐⭐⭐⭐ 校验 → 写入**

```
先检查 → 再写文件
```

> ⭐⭐⭐⭐⭐ 反了就不可逆。这一类是唯一"顺序错了会响"的，
> ⭐⭐⭐⭐⭐ 但它的失败形状是"东西已经写进去了"，而不是"顺序错了"。

**③ ⭐⭐⭐⭐⭐ 收集全部 → 判断**

```
遍历完所有文件 → 才能说"没有遗漏"
```

> ⭐⭐⭐⭐⭐ 这一类的顺序错表现为**过早下结论**：
> 看了前三个就判断"都符合"，因为这看起来像归纳，不像错误。

## 3. ⭐⭐⭐⭐⭐ 为什么写出来时看不出顺序

**① ⭐⭐⭐⭐⭐ 顺序藏在"常识"里**

```
"先归一化再排序" 对作者是显然的
⭐⭐⭐⭐⭐ 于是它没有被写——因为作者不认为它是一个需要说明的点
```

> ⭐⭐⭐⭐⭐ 与 `skill-content/references/default-actions.md` 完全同源：
> ⭐⭐⭐⭐⭐ **凡是"看起来显然"的东西，都是最先丢掉的**。

**② ⭐⭐⭐⭐⭐ 列表语法只表达"这是一组"**

```
Markdown 的列表不表达顺序（见 `skill-precision/references/list-item-relations.md`）
⭐⭐⭐⭐⭐ 编号列表看起来表达了顺序，但"1. 2. 3."也被读作"三项并列要做的事"
```

**③ ⭐⭐⭐⭐⭐ 步骤名的语义里带着顺序，但只在人看来**

```
"归一化"在语义上应该在"提取"之前（因为要先统一格式）
⭐⭐⭐⭐⭐ 而模型看到的是两个动词，没有任何一个词表示先后
```

## 4. ⭐⭐⭐⭐⭐ 失败形状：不报错，只是结果不对

| | 显式顺序错 | ⭐⭐⭐⭐⭐ 隐式顺序错 |
|---|---|---|
| 报错 | 会（引用了不存在的东西） | ⭐⭐⭐⭐⭐ 不会 |
| 输出 | 明显缺失 | ⭐⭐⭐⭐⭐ 完整、格式正确 |
| 发现者 | 用户立刻发现 | ⭐⭐⭐⭐⭐ 通常没人发现 |

> ⭐⭐⭐⭐⭐ 这是本份最重要的一条事实：
> ⭐⭐⭐⭐⭐ **隐式顺序错的产物，与正确产物的差别只在值上，不在形式上。**

与"部分遵循"的关系：

```
partial-following： 步骤被跳 → 少做了一步
本份：              步骤都做了，⭐⭐⭐⭐⭐ 只是顺序不同 → 一样多，但不同
```

> ⭐⭐⭐⭐⭐ 后者更难发现，因为⭐⭐⭐⭐ "少做"留下了缺口，
> ⭐⭐⭐⭐⭐ 而"顺序不同"什么都不缺。

## 5. ⭐⭐⭐⭐⭐ 检测：顺序敏感性测试

一个不需要知道依赖在哪的方法：

```
按 A→B→C 跑 → 记 R1
按 C→B→A 跑 → 记 R2
⭐⭐⭐⭐⭐ R1 ≠ R2 → 存在隐式顺序依赖，且它没有被写明
```

> ⭐⭐⭐⭐⭐ 价值在于：⭐⭐⭐⭐ **你不需要事先知道依赖在哪**。
> 顺序敏感性是一个可观测的现象，而依赖是一个需要推理的结论。

三条实操：

```
① ⭐⭐⭐⭐⭐ 至少跑两次，且两次都在干净会话（否则测的是自洽，见
   `skill-execution/references/repeat-invocation-same-session.md`）
② ⭐⭐⭐⭐⭐ 只改顺序，不改任何其他东西
③ ⭐⭐⭐⭐⭐ 顺序不同但结果相同 → 说明顺序其实不重要 → 可以声明"无顺序要求"
```

> ⭐⭐⭐⭐⭐ 第 ③ 条是正向用法：⭐⭐⭐⭐ 多数技能的顺序要求比作者以为的少，
> ⭐⭐⭐⭐⭐ 而写明"无顺序要求"能换来并行能力。

## 6. ⭐⭐⭐⭐⭐ 修法：把顺序变成数据依赖

最有效的修法不是写"必须先 A 再 B"，而是：

```markdown
1. 归一化日期 → 输出 `normalized`（记为 N1）
2. ⭐⭐⭐⭐⭐ 排序：输入必须是 N1（不得使用未归一化的原始字段）
```

> ⭐⭐⭐⭐⭐ 跳了第 1 步，第 2 步就没有输入——
> ⭐⭐⭐⭐⭐ 于是顺序错在**结构上不可能**，而不是靠提醒。

三条配套：

```
① ⭐⭐⭐⭐⭐ 给中间产物起名（N1、raw_list、validated），顺序依赖随之显式化
② ⭐⭐⭐⭐⭐ 顺序真的重要时，写明"不得在 X 之前执行 Y"，而不只靠排列
③ ⭐⭐⭐⭐ 校验类步骤放在边界上并带后果（"不通过则停止，不得进入下一步"）
```

> ⭐⭐⭐⭐⭐ 第 ① 条的成本只有几个字，收益覆盖本份全部问题：
> ⭐⭐⭐⭐⭐ **叫得出名字的东西才能被引用，能被引用才能形成依赖。**

## 7. ⭐⭐⭐⭐⭐ 与"给约束不给流程"的边界

这两条看起来矛盾，其实判据清楚：

```
给约束不给流程 → ⭐⭐⭐⭐⭐ 说的是"不要规定实现路径"
顺序依赖       → ⭐⭐⭐⭐⭐ 说的是"不要省略因果依赖"
```

判据：

> ⭐⭐⭐⭐⭐ **如果换一条路走，你介意吗？**
> 介意 → 这是因果依赖，必须写明；
> 不介意 → 这是实现路径，不该写。

以及更硬的一条：

> ⭐⭐⭐⭐⭐ **顺序真的重要时，应该写成脚本或工作流，不是技能。**
> 因为技能靠模型自觉执行，⭐⭐⭐⭐⭐ 而"顺序"恰恰是模型没有强制力保证的东西。

## 8. ⭐⭐⭐⭐⭐ 自检

对每一个多步骤技能：

```
① ⭐⭐⭐⭐⭐ 步骤之间有没有"必须先/后才能"？写了吗？
② ⭐⭐⭐⭐⭐ 每个中间产物有名字吗？（没名字 → 无法形成依赖）
③ ⭐⭐⭐⭐⭐ 反序跑一次，结果一样吗？（不一样 → 有未写明的依赖）
④ ⭐⭐⭐⭐⭐ 哪些顺序其实不重要？声明"无顺序要求"了吗？
⑤ ⭐⭐⭐⭐⭐ 校验步骤有"不通过则停止"吗？
```

一个十秒判断：

> ⭐⭐⭐⭐⭐ **把技能的步骤列表随机打乱，问自己"有没有哪一步会因此做错"。
> 有 → 那个依赖只存在于排列顺序里，而排列顺序不是约束。**

---

## 一句可贴在墙上

> ⭐⭐⭐ **列表的排列顺序是一种建议，不是约束。
> 顺序要成为依赖，必须让后一步的输入是前一步的产出。**
