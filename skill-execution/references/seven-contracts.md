# 七个契约：从"说明书"到"责任契约"

> 相关：《skill-execution》的 `output-contract.md` · `preflight-gate.md` ·
> `error-handling.md` · `idempotency-resume.md` · `state-check.md` ·
> 《skill-crafting》的 `output-control.md`

> 核心论点是⭐⭐⭐ **"单一职责、准确描述、惜字如金"都不足以让技能进生产**。

## 1. ⭐⭐⭐ 为什么三个美德不够

```
"单一职责 · 准确描述 · 惜字如金" 都是对的
⭐⭐⭐ 但还不足以让一个技能⭐ 进入生产环境
```

> ⭐⭐⭐ **到这里，技能才从一份"如何做事的说明书"，
> ⭐ 变成一份"⭐⭐ 什么结果才算交付的责任契约"。**

> ⭐⭐ 这句转换值得记：**说明书回答"怎么做"，契约回答"做到什么算完、谁负责"。**
> 我们此前收集的大量内容（惜字如金、渐进披露、一职责一技能）
> 都在优化"说明书"这一侧，
> ⭐ 而这七个契约补的是另一侧。

---

## 2. ⭐⭐ 契约一：触发

```
明确：
  · 什么输入应该触发
  · 什么输入不应该触发
  · ⭐⭐⭐ ⭐ 显式调用时是否还需要检查必备条件
```

最后一条最关键：

> ⭐⭐⭐ **显式调用⭐ 不等于可以跳过安全边界。**

> ⭐ 这与 `preflight-gate.md` 的三条 MUST NOT 一致，
> 但这里给了一个更简明的表述——
> **用户亲口说"用这个技能"也不豁免前置检查**。
> 很多人会以为 `/deploy` 是用户明确意图于是可以少查一步，恰恰相反。

---

## 3. ⭐⭐ 契约二：输入

```
写清楚：必需输入 · 可选输入 · 支持格式 · 路径规则 · ⭐ 缺失信息的处理策略
```

> ⭐⭐ **不要让 Agent 在一个关键参数缺失时⭐ 默默猜测，
> ⭐⭐⭐ 然后在⭐ 任务末尾才暴露身份错误。**

> ⭐⭐⭐ "在任务末尾才暴露"是这类失败的特征——
> 前 90% 的输出看起来都对，最后发现处理的是错的对象。
> 这正对应 `preflight-gate.md` 说的
> "跑到一半才来问你要东西，或者更糟，默默即兴发挥一条替代路径"。

---

## 4. ⭐⭐⭐ 契约三：输出

```
定义：产生哪些文件 · 返回哪些字段 · ⭐ 保留哪些中间证据
     ⭐⭐ 哪个产物是"清洁源稿 / 发布副本 / 远端回读版"
```

> ⭐⭐⭐ **"如果产物不可定位，完成也就不可验证。"**

> ⭐⭐ 这条与 `assert-on-environment.md` 的
> "断言要打在环境状态上"是同一原则的⭐ 上游版本：
> **先让产物可定位，才谈得上断言。**
> 一个只说"已完成"的技能，你连该去查什么都不知道。

**"清洁源稿 / 发布副本 / 远端回读版"这组区分值得直接抄**——
它解决的是"我到底该校验哪一个产物"这个常被含糊掉的问题。

---

## 5. ⭐⭐⭐ 契约四：权限与安全

```
明确边界：网络 · 文件系统 · 密钥 · Cookie · 外部账号 · 远端写操作

⭐⭐⭐ 删除 / 覆盖 / 发布 / 发送消息等高风险操作
   ⭐⭐⭐ 应该有⭐ 明确门禁
   ⭐⭐⭐ ⭐ 不能被"完成任务"这个宽泛目标⭐ 自动授权
```

> ⭐⭐⭐ 最后半句极其重要，且是⭐ 第五个独立来源说同一件事：
> **"我要完成任务"不是一个能推导出"我可以删文件"的目标**，
> 但模型会这么推导。
>
> 这也是为什么门禁必须是⭐ 显式的、独立于任务目标的
> （呼应 `determinism-boundary.md` 的 Hooks、
> `allowed-tools-reference.md` 的执行侧强制）。

---

## 6. ⭐⭐⭐ 契约五：执行

```
说明：主流程 · 依赖 · ⭐ 幂等性 · ⭐ 重试上限 · 备用数据源 · ⭐ 降级路径
```

**最具体、最容易漏的一条**（远端操作时）：

> ⭐⭐⭐ **重试时要区分
> "上一次没写入" 与 ⭐⭐ "上一次已写入但回应丢失"，
> ⭐⭐⭐ 否则会⭐ 创建重复对象。**

> ⭐⭐⭐ 这条比通用的"要注意幂等"高一个层次——
> 它指出了⭐ **幂等失败的具体形态**：不是报错，是⭐ 静默的重复。
> 对应到 `idempotency-resume.md`，这里补的是
> **"重试"这个动作特有的陷阱**（区别于"断点续跑"）。

---

## 7. ⭐⭐⭐ 契约六：失败

```
⭐⭐⭐ 把 无网络 / 缺依赖 / 输入非法 / 权限不足 / 上游限流 / 部分成功
   ⭐⭐ ⭐ 当成⭐ 正式分支，而不是异常文案
```

**失败契约必须回答三个问题**：

```
① ⭐⭐⭐ 哪一步失败
② ⭐⭐⭐ 哪些状态已改变
③ ⭐⭐⭐ 用户怎样恢复或重试
```

> ⭐⭐⭐ "失败不是异常文案，而是⭐ 工作流的正式分支"——
> 这句话是这份文档的灵魂。
>
> ⭐⭐ 与我们已有的对照：
> `error-handling.md` 讲"错误怎么报"（退出码分级），
> `fault-injection-eval.md` 讲"失败怎么造"，
> ⭐⭐⭐ 这里讲的是**失败在契约里的地位**——
> 它是⭐ 流程的一部分，不是⭐ 兜底的备注。

---

## 8. ⭐⭐⭐ 契约七：验收

> ⭐⭐⭐ **把"做了"与"做对了"⭐ 分开。**

```
本地文件：检查 路径 · 数量 · 格式 · schema · ⭐ 哈希
远端交付：⭐⭐ 回读 状态 / 标题 / 正文 / 标签 / 图片 / 访问性
```

> ⭐⭐⭐ **验收证据要能够⭐ 被用户或下一个工作流⭐ 独立复核。**

两条特别具体的判据：

```
"确保两份文件字节一致" → ⭐⭐ 应该比较哈希
"确保远端草稿保存成功" → ⭐⭐ 应该⭐ 读回远端状态与正文
   ⭐⭐⭐ ⭐ 而不是把 HTTP 200 或本地输出当成成功
```

> ⭐⭐⭐ "不要把 HTTP 200 当成成功"这条太常见了——
> 它正是 `state-check.md` 讲的"验证要查状态而非听汇报"在网络层的具体版本，
> 而这里给出了⭐ 更精确的失败形态：**200 只代表请求被接受，不代表状态已变更。**

---

## 9. ⭐⭐ 一个贯穿全局的判据

> ⭐⭐ **语言模型擅长：语义判断 · 归纳 · ⭐ 异常情境推理**
> ⭐⭐ **脚本擅长：精确 · 重复 · 可测量操作**
>
> ⭐⭐⭐ **好技能不会站队"全部写 Prompt"或"全部写代码"，
> ⭐⭐ 而是把⭐ 每一类工作交给⭐ 更适合的执行介质。**

> ⭐⭐ 这与 `deterministic-scripts.md` 的
> "从 Y 算出 X，X 是数字、Y 是结构化数据 → 脚本"
> 是同一判据，但这里的表述⭐ 更对称、更好记——
> **不是"能脚本化就脚本化"，而是"各归各位"。**

**七个契约的完整回路**（可直接当作自查顺序）：

```
① 路由（description 匹配 WHAT+WHEN）
② 输入契约（必需参数 + 缺失时怎么办）
③ 执行（指令 + 确定性脚本 + 重试与降级）
④ 验证（schema / hash / test + 状态与内容回读）
⑤ 交付证据（产物路径 + 报告 + ⭐ 部分成功如实报告）
```

## 速查

```
□ ⭐⭐⭐ 三美德（单一职责/准确描述/惜字如金）⭐ 不足以进生产
   ⭐⭐⭐ 说明书→"怎么做"；⭐ 契约→"做到什么算完、谁负责"

□ ①触发：⭐⭐⭐ 显式调用⭐ 不等于可以跳过安全边界
□ ②输入：⭐⭐ 别让它在参数缺失时默默猜，⭐⭐⭐ 到任务末尾才暴露
□ ③输出：⭐⭐⭐ 产物不可定位 → 完成不可验证
   ⭐ 区分"清洁源稿/发布副本/远端回读版"
□ ④权限：⭐⭐⭐ ⭐ 不能被"完成任务"这个宽泛目标自动授权（第五个来源）
□ ⑤执行：⭐⭐⭐ ⭐ 重试要区分"没写入"vs"写入了但回应丢失"→ 否则重复对象
□ ⑥失败：⭐⭐⭐ 无网络/缺依赖/非法/权限/限流/部分成功 = ⭐ 正式分支
   ⭐⭐⭐ 三问：哪一步失败 · 哪些状态已改变 · 用户怎样恢复
□ ⑦验收：⭐⭐⭐ "做了"与"做对了"分开
   ⭐⭐ 字节一致→比哈希；远端成功→⭐ 回读正文；⭐⭐⭐ 别把 HTTP 200 当成功

□ ⭐⭐ 模型：语义判断/归纳/⭐ 异常情境推理
   脚本：精确/重复/可测量 → ⭐⭐ 各归各位，不站队
```

**一句话**：

> ⭐⭐⭐ **"单一职责、准确描述、惜字如金"都不足以让技能进生产——
> 还要补齐七个契约（触发/输入/输出/权限/执行/失败/验收），
> 技能才从"如何做事的说明书"变成"什么结果才算交付的责任契约"；
> 其中"把 HTTP 200 当成功"和"重试不区分是否写入"是两类最典型的静默失败。**
