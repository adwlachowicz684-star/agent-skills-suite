## 1. ⭐⭐⭐⭐⭐ 两类产物，两类事故

技能执行过程中会写出两类东西：

| | 例子 | 出技能之外吗 |
|---|---|---|
| ⭐⭐⭐⭐ 交付物 | 报告、修改后的源文件 | 是（用户要的） |
| ⭐⭐⭐⭐⭐ **中间产物** | 抓取的原始数据、中间 JSON、临时补丁 | 否 |

> ⭐⭐⭐⭐⭐ 交付物有输出契约管着，
> ⭐⭐⭐⭐⭐ **中间产物谁都不管**——它不在输出契约里，也不在接口契约里。

两类事故都来自这个空白：

```
① ⭐⭐⭐⭐⭐ 第二次运行读到了第一次的中间产物（陈旧数据）
② ⭐⭐⭐⭐⭐ 失败后中间产物留在磁盘上，成为"看起来跑过"的证据
```

## 2. ⭐⭐⭐⭐⭐ 临时文件该写在哪

三条候选，各有各的坑：

**① ⭐⭐⭐⭐ 写在项目目录里**

```
❌ 会被 git 看到、会被提交、会污染工作区
⭐⭐⭐⭐⭐ 而且它会成为"项目的一部分"，下次运行就在那里
```

**② ⭐⭐⭐⭐ 写在技能目录下（`${CLAUDE_SKILL_DIR}/tmp/`）**

```
✅ 不污染项目
⭐⭐⭐⭐⭐ 但技能目录常被版本控制/同步 → 产物随技能一起传播
```

**③ ⭐⭐⭐⭐⭐ 写在系统临时目录 + 本次运行专属子目录**

```
✅ 不污染项目、不随技能传播
⭐⭐⭐⭐⭐ 路径带运行 ID → 第二次运行天然不会读到第一次的
```

> ⭐⭐⭐⭐⭐ 推荐 ③，关键不在"临时"而在**专属**：
> ⭐⭐⭐⭐⭐ **只要路径里带本次运行的唯一标识，
> "读到上次残留"这个事故在结构上就不可能发生。**

写法（一行）：

```markdown
- 中间产物写入 `${TMPDIR}/<skill-name>/<run-id>/`，不得写入项目目录
```

## 3. ⭐⭐⭐⭐⭐ 命名：临时文件会被第二次运行读到

这是最具体、也最容易犯的一条：

```
fetch_raw.json    ← 固定名
```

> ⭐⭐⭐⭐⭐ 第一次运行留下了 `fetch_raw.json`，
> ⭐⭐⭐⭐⭐ 第二次运行"文件已存在"→ 直接读它 → 用的是上一次的数据。

> ⭐⭐⭐⭐⭐ 而它不会报错：文件确实存在、格式确实对，
> ⭐⭐⭐⭐⭐ 只是内容是旧的。这正是"陈旧引用"的一种形态。

两条硬规则：

```
① ⭐⭐⭐⭐⭐ 文件名必须带运行标识或时间戳
② ⭐⭐⭐⭐⭐ 读之前必须校验新鲜度（写入时间 / 内容哈希 / 源版本）
```

> ⭐⭐⭐⭐⭐ 第 ② 条不能省：⭐⭐⭐⭐ 就算路径带 run-id，
> 脚本里如果写的是"存在就用，不存在才抓"，仍然会命中缓存——
> **因为这两条规则管的是不同环节：① 管路径，② 管读取逻辑。**

顺带一条：

> ⭐⭐⭐⭐ **不要用"文件存在"判断"这一步已经做过"**。
> 要用存在 + 新鲜度。这与"不要用 HTTP 200 判断成功"是同一条规则的又一场景。

## 4. ⭐⭐⭐⭐⭐ 清理：不清理会累积，清理错了会删掉证据

两个方向的错误，第二个更贵：

**① ⭐⭐⭐⭐ 从不清理**

```
/tmp/<skill>/ 累积 400 个文件 → 磁盘、同步、备份都被拖慢
⭐⭐⭐⭐ 而且没人知道哪些能删
```

**② ⭐⭐⭐⭐⭐ 失败时也清理**

```
第 3 步失败 → finally 块删掉临时目录 → 现场没了
```

> ⭐⭐⭐⭐⭐ 中间产物是⭐⭐⭐⭐⭐ **唯一能回答"它到底跑了什么"的东西**——
> 报告只告诉你结果，中间产物告诉你过程。

正确的策略只有一句：**成功才清理，失败保留并报告路径。**

```markdown
- 成功：清理本次运行目录
- 失败：⭐⭐⭐⭐⭐ 保留，并在输出中报告路径（用户可自行删除）
```

> ⭐⭐⭐⭐⭐ 这与《skill-recovery》的 `reversibility-and-undo.md` 完全同构：
> ⭐⭐⭐⭐⭐ **输出会随会话消失，文件不会——所以要写文件，不只是写"完成"。**

## 5. ⭐⭐⭐⭐⭐ 中间产物不得进上下文

这是与上下文预算直接相关的一条：

```
脚本源码   → 默认不进上下文（便宜）
脚本输出   → ⭐⭐⭐⭐⭐ 必进上下文（昂贵）
```

而中间产物有个很容易踩的坑：

```
❌ 把 3 万字的抓取原文直接返回
✅ ⭐⭐⭐⭐⭐ 写入临时文件，只返回路径 + 摘要
```

> ⭐⭐⭐⭐⭐ 这是 `three-crash-scenes.md` 里那起 3 万字事故的正面解法：
> ⭐⭐⭐⭐⭐ **中间产物存在的意义之一，就是让它可以不进上下文。**

判据：

> ⭐⭐⭐⭐⭐ **这段内容，模型需要"看到原文"才能处理，
> 还是只需要"知道它存在 + 关键字段"？**
> 后者 → 写文件，不要回传。

还有一个反直觉的收益：

> ⭐⭐⭐⭐ 中间产物写成文件，顺带让"重跑这一步"成为可能——
> 不必从头再来（与 `idempotency-resume.md` 直接相关）。

## 6. ⭐⭐⭐⭐⭐ 失败时要留下现场

三条最小要求，成本都很低：

```
① ⭐⭐⭐⭐⭐ 中间产物目录路径写进输出（失败时必写）
② ⭐⭐⭐⭐⭐ 每一步的产出写一个 `status` 文件（ok / partial / failed）
③ ⭐⭐⭐⭐⭐ 失败步骤的输入保留，不要覆盖
```

> ⭐⭐⭐⭐⭐ 第 ③ 条最常被违反：脚本习惯性地把中间文件覆盖写，
> ⭐⭐⭐⭐ 于是失败后连"它是拿着什么输入失败的"都不知道。

这三条合起来解决的是一个已有文档的痛点：

```
《skill-governance》的 `observability-trace-debug.md`：
⭐⭐⭐⭐⭐ "失败点 ≠ 出错点"，于是排查要重跑
```

> ⭐⭐⭐⭐⭐ 有了现场，⭐⭐⭐⭐⭐ **排错从"重跑并观察"变成"读文件"**——
> 这跟 `decision-rationale-output.md` 的"写了依据的输出排错时不用重跑"是同一个收益。

## 7. ⭐⭐⭐⭐⭐ 自检

对任何会写中间产物的技能：

```
① ⭐⭐⭐⭐⭐ 写在哪？是项目目录吗？（应该是专属临时目录）
② ⭐⭐⭐⭐⭐ 路径带运行标识吗？第二次运行会读到第一次的吗？
③ ⭐⭐⭐⭐⭐ 读之前校验新鲜度了吗？（不只是"存在就用"）
④ ⭐⭐⭐⭐⭐ 失败时保留了现场并报告路径吗？
⑤ ⭐⭐⭐⭐⭐ 中间产物有没有被回传进上下文？
```

> ⭐⭐⭐⭐⭐ 第 ② 和第 ④ 条命中率最高：
> ⭐⭐⭐⭐ 前者是"时好时坏"最常见的成因之一，
> ⭐⭐⭐⭐ 后者直接决定一次线上事故能不能被定位。

一个十秒判断：

> ⭐⭐⭐⭐⭐ **连着跑两次，第二次的结果会不会依赖第一次留下的文件？
> 会 → 中间产物没有隔离。**

---

## 一句可贴在墙上

> ⭐⭐⭐ **不要用"文件存在"判断"这一步已经做过"——要用存在加新鲜度。
> 而失败时清理临时目录，等于删掉了唯一能回答"它到底跑了什么"的东西。**
