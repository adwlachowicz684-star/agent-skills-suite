## 1. ⭐⭐⭐⭐⭐ 现象：错误被吞掉了

> ⭐⭐⭐ **技能返回一个错误码，但模型在最终回复里仍然描述"查询成功"，
> 或者编造一个和返回结果不一致的答案。**

这是整套库里**最危险的一类失败**，因为：

```
· 技能确实失败了 ✓
· 错误确实返回了 ✓
· ⭐ 但用户看到的是一段流畅的、错误的、自信的答复
```

对比另外两种失败的可见度：

| 失败 | 可见吗 |
|---|---|
| 技能崩溃、无输出 | ⭐ 可见（用户会追问） |
| 输出格式错 | ⭐ 可见（一眼看出） |
| ⭐ **错误被改写成功** | ⭐⭐⭐ **完全不可见** |

> ⭐⭐⭐ 这是"错得自信"（`three-failure-modes.md`）最纯粹的形态——
> 因为连模型自己都不知道自己在编（它认为技能成功了）。

---

## 2. ⭐⭐⭐⭐⭐ 根因：错误没有占住输出的形状

模型拿到错误后的默认行为是**继续完成它认为自己该完成的任务**——
说一句"查询成功，结果如下"。它不是在撒谎，它是在补全。

> ⭐⭐⭐⭐ **根因不在模型的诚实度，在于错误没有像成功那样
> 明确地规定"输出长什么样"。**

对照一下我们给成功路径和失败路径的规格量：

```
成功路径：输出模板 · 字段定义 · 示例 · 验收标准   ← 写得很细
失败路径："如果失败就报告错误"                    ← 一句话
```

**一句话的规格，模型就会用一句话的方式去补。**

这与 `seven-contracts.md` 那条"失败契约"是同一件事，
但这里给的是**最小可执行版本**。

## 3. 结构化错误协议

核心就一条：

> ⭐⭐⭐ **技能执行失败时，返回的 content 里明确标记 `[SKILL_EXECUTION_ERROR]`。**

```json
{
  "status": "error",
  "marker": "[SKILL_EXECUTION_ERROR]",
  "stage": "fetch_policy",
  "code": "UPSTREAM_TIMEOUT",
  "message": "售后政策服务 8 秒无响应",
  "safe_reply": "暂时无法查询售后政策，请稍后重试或联系人工客服。"
}
```

四个字段各自的作用：

| 字段 | 作用 |
|---|---|
| ⭐ `[SKILL_EXECUTION_ERROR]` | ⭐⭐⭐ 一个不可能被误读成成功的字符串锚点 |
| `stage` | 让模型知道哪一步挂了，而不是笼统"出错了" |
| `code` | ⭐ 让 SKILL.md 能按码分支（超时重试 / 权限直接停） |
| ⭐ `safe_reply` | ⭐⭐⭐ **把"该说什么"直接给出来** |

> ⭐⭐⭐ **`safe_reply` 是全份最关键的字段。**
> 你不给，模型就得自己组织语言——而组织语言正是它开始编的时候。

---

## 4. ⭐⭐⭐⭐ 三条硬约束

写进 SKILL.md 的 Error Handling 章节：

**① 输出限制在"模板回复 + 技能返回内容"的拼接模式**

```
✅ [模板开头] + [技能返回的 safe_reply] + [模板结尾]
❌ 模型自由组织一段解释
```

**② 禁止解释错误**

```
❌ "根据我的分析，可能是网络波动导致服务不可用，
    建议您检查防火墙设置……"        ← 全是编的
✅ "暂时无法查询售后政策，请稍后重试或联系人工客服。"
```

> ⭐⭐⭐ 这条最反直觉——我们通常觉得"多解释一点"更好。
> 但**解释的内容不在技能返回里，只能来自模型的猜测**。

**③ 不确定时走安全回复，不走最佳猜测**

```
查不到 → "查不到"，不是"应该是 7 天无理由"
超时   → "暂时查不了"，不是"通常这类情况按 X 处理"
```

## 5. ⭐⭐⭐ 模板回复 + 技能返回内容

一个可直接抄的正文写法：

```markdown
## 错误处理

技能返回含 `[SKILL_EXECUTION_ERROR]` 时：

1. ⭐ 停止当前流程，不要继续后续步骤
2. ⭐ 输出 = 下面模板，把 {safe_reply} 换成返回里的同名字段
3. ⭐ 不得补充任何解释、推测、建议或"可能的原因"

模板：
  抱歉，{safe_reply}
  （错误代码 {code}，如需人工处理请提供此码。）

⚠️ {code} 与 {safe_reply} 必须原样取自技能返回，
   不得改写、不得概括、不得添加。
```

> ⭐⭐⭐ **"不得改写、不得概括"** 这句必须写——
> 因为它防的正是**模型的默认善举**（把生硬的话说得更通顺）。

## 6. ⭐⭐⭐ 为什么"写一条禁令"不够

```
❌ "不要编造结果"
✅ "输出 = 模板 + safe_reply；不得补充任何内容"
```

这是我们反复遇到的同一条规律的又一次出现
（禁令必须带正面对应物，第 N 次）：

> ⭐⭐⭐ **"不要编造"没有规定输出长什么样，
> 于是模型只能用它默认的方式（补全）去填。**
> 而协议版本直接把形状给定了——没有需要即兴发挥的空隙。

对应的实现层次：

| 层次 | 可靠性 |
|---|---|
| 正文写"别编造" | 低（段落，依赖遵守） |
| ⭐ 技能返回 `safe_reply` 字段 | ⭐⭐ 中（模型照抄即可） |
| ⭐⭐⭐ 脚本侧直接生成完整回复文本 | ⭐⭐⭐ 高（模型连抄都不用） |

> ⭐⭐⭐ **能往前推一层就往前推一层**——
> 这是"把判断前移"的又一次应用。
