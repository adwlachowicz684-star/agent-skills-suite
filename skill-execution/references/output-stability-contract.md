## 1. ⭐⭐⭐ 目标：同样的输入，差不多的输出

> ⭐⭐ **"虽然不能 100% 一样（AI 本身就有随机性），
> ⭐⭐⭐ 但可以通过⭐ 设计让结果尽可能稳定。"**

**手段一：把格式变成"确切章节"**

```
按此顺序生成以下确切章节：
  执行摘要（3–5 个要点）
  主题分析（每个主题一个子章节）
  建议（编号列表，最多 5 项）
  方法论（一个段落）
```

> ⭐⭐ 注意写法是⭐ **"按此顺序生成以下确切章节"**——
> 不是"建议包含以下内容"。
> ⭐⭐⭐ 前者是⭐ 可判定的（数一数章节、看顺序），后者不是。

**手段二：用参考文件定标准**

```
⭐⭐ 把⭐ 分类标准写到单独的文件里，SKILL.md ⭐ 只负责引用
```

> ⭐⭐ 这与 `directory-decision-matrix.md` 的
> "要被执行的用列表、要被比较的用表格/文件"一致：
> 分类标准是⭐ 要被查的表，放进 reference；
> SKILL.md 只留"先读哪份、判断什么、检查哪些输出条件"。

## 2. ⭐⭐⭐ 跑两遍测试法

```
① ⭐⭐ 对样本数据跑一次技能 → ⭐⭐⭐ 保存结果
② ⭐⭐⭐ ⭐ 清除会话（/clear）
③ ⭐⭐ 对⭐ 同一份数据⭐ 再跑一次
④ ⭐⭐ 比较两次结果
```

**判据很关键**（不是要求完全一致）：

```
⭐⭐⭐ 不用追求完美一样
   ⭐⭐ ⭐ 结构相同、主题相似⭐ 就行
   ⭐⭐ 具体用词会有变化，但⭐⭐⭐ 关键内容应该稳定
```

> ⭐⭐⭐ **如果两次结果差很多，说明⭐ 技能写得不够细——⭐⭐ 加更明确的格式或质量标准。**

> ⭐⭐⭐ 这个方法便宜到几乎没有理由不做：
> ⭐ **一次 /clear + 一次重跑**，不需要任何工具、不需要 eval 框架。
> ⭐⭐ 但它测的恰恰是最难用断言覆盖的东西——**整体结构的稳定性**。
>
> ⭐⭐ 与我们已有的 `assert-on-environment.md` 的 pass^5、
> `description-tuning-official-loop.md` 的"跑 3 次"
> 是同一思路的⭐ 三个不同应用点：
> ```
> 触发稳定性 → 跑 3 次
> 执行正确性 → 跑 5 次
> ⭐⭐⭐ 整体结构稳定性 → ⭐ 清会话跑 2 次（更重，因为要重置上下文）
> ```

**"必须 /clear"这个细节是本份最容易被漏的一点**：

> ⭐⭐⭐ 不清理会话就重跑，第二次是在⭐ **已经看过第一次结果**的上下文里跑的，
> ⭐⭐ 它会倾向于自洽——于是两次很像，⭐⭐⭐ 但那⭐ 什么都没证明。

## 3. ⭐⭐⭐ 质量标准的写法

**一份可以直接抄的质量标准**：

```
质量标准
  · ⭐ 执行摘要包含⭐ 恰好 3–5 个要点
  · ⭐⭐ 每个主题章节包含⭐ 频率计数和百分比
  · ⭐⭐⭐ 所有引文均来自源数据的⭐ 逐字记录
  · ⭐⭐ 建议按名称⭐ 引用特定主题
```

> ⭐⭐⭐ 这四条的共同点：**每一条都能被机械检查**。
> ```
> "恰好 3–5 个"     → 数一下
> "包含计数和百分比" → 查有没有
> "逐字记录"        → 比对源数据
> "按名称引用主题"   → ⭐⭐ 查引用是否存在（防幻觉）
> ```
> ⭐⭐⭐ 最后一条尤其值得单独记——
> **"建议必须引用特定主题名"是一条防幻觉的低成本断言**：
> 如果它引用了数据里不存在的主题，立刻暴露。

> ⭐⭐ 对照 `skill-review-checklist-ten.md` 的
> "每条规则都要能对应一个失败场景"——
> 这四条⭐ 每条都能立刻说出"违反它会出现什么"。

## 4. ⭐⭐⭐ 模糊情况必须预先规定

**一份可以直接抄的边缘情况表**：

```
边缘情况
  · ⭐⭐ 如果一条反馈可归入多个主题 → ⭐⭐⭐ 归入⭐ 最具体的主题
  · ⭐⭐ 如果情感倾向不明确 → ⭐⭐⭐ 标记为"混合"，⭐⭐ 而非猜测
  · ⭐⭐ 如果条目过短无法分类（少于 10 个词）→ ⭐⭐⭐ ⭐ 计入但⭐ 不引用
```

> ⭐⭐⭐ 第三条最妙：**"计入但不引用"**——
> 既保持了统计完整性，又避免了从不完整信息编造引文。
> ⭐⭐⭐ 这是一个⭐ **在不编造的前提下保持完整** 的标准解法，
> 比"跳过它"或"尽力分类"都好。
>
> ⭐⭐⭐ 而第二条"标记为'混合'而非猜测"——
> ⭐⭐⭐ **给了一个⭐ 除了"必须猜一个"之外的出路**。
> 这是⭐ 抑制幻觉最有效的一招：**提供"我不知道"这个合法选项。**
> 与我们已有的 `outgrowth-regression-detection.md` 的 inconclusive 档同源。

## 5. ⭐⭐⭐ 三分法：现在告诉 / 能被找到 / 不该生成

> ⭐⭐⭐ **"写技能的核心问题不是'我要告诉模型多少东西'，
> ⭐⭐⭐⭐ 而是——
>   ⭐⭐⭐ ① 哪些东西⭐ 必须现在告诉它
>   ⭐⭐⭐ ② 哪些东西⭐ 只要能被找到
>   ⭐⭐⭐ ③ 哪些东西⭐ 根本不该让模型临场生成"**

> ⭐⭐⭐ 这是本份最有价值的一条，而且⭐⭐ 它把我们此前分散的几条
> 收进了一个⭐ 单一决策框架：
> ```
> ① 必须现在告诉 → SKILL.md 正文（判断规则、输出契约）
> ② 只要能被找到 → references/（分类标准、字段定义、领域规则）
> ③ ⭐⭐⭐ 不该临场生成 → ⭐ scripts/（命名规则、SQL 模板、命令拼接）
>    ⭐⭐⭐ ⭐ 这条最常被漏：⭐⭐ 凡是"无论谁跑结果都必须一致"的，
>        ⭐⭐⭐ 就不该让模型生成
> ```
> ⭐⭐⭐ 与我们已有的 `deterministic-scripts.md`
> （"从 Y 算出 X，X 是数字 → 脚本"）完全对上，
> ⭐⭐ 但这里把它放进了⭐ 一个三选一的分类里——
> **每写一段之前，先问它属于哪一类。**

**配套的两条**：

```
· ⭐⭐ 让⭐ 脚本校验输入，⭐⭐⭐ 不要把所有格式约束都交给⭐ 自然语言提醒
· ⭐⭐⭐ 把⭐ 最终验收条件写进 SKILL.md
    （文件是否生成 · JSON 是否可解析 · 列表是否包含必要字段）
```

## 6. ⭐⭐ 输入输出契约怎么定死

```
⭐ 给出⭐ 最小输入示例 + ⭐ 完整输出示例
⭐⭐ 明确字段名 · 类型 · 必填项 · 默认值 · ⭐ 边界条件
```

**脚本侧的四条稳定性要求**：

```
· ⭐⭐⭐ 输入参数、输出路径、错误信息和⭐ 退出码都应该稳定
· ⭐⭐ ⭐ 让脚本只做一件事，⭐⭐ 能用⭐ 一两个代表性命令验证它是否工作
· ⭐⭐ ⭐ 用命令行参数定义输入，⭐⭐⭐ 不要依赖隐藏状态
· ⭐⭐ 输出⭐ 固定格式（JSON / 固定文件路径 / 清晰的 stdout 摘要）
```

**一条流程纪律**：

> ⭐⭐⭐ **新增脚本后⭐ 实际运行一次，确认结果和预期一致。**

> ⭐⭐ 这条看起来是废话，但它对应的失败很具体：
> 技能里引用了一个⭐ **从未被运行过的脚本**，
> 而 `three-failure-modes.md` 记过——
> "技能引用了不存在的模板文件 → 模型读取失败后自己补内容 → 这是幻觉的来源之一"。
> ⭐⭐⭐ **脚本存在但跑不通，比脚本不存在更危险**——
> 因为不存在会立刻暴露，跑不通可能只是"偶尔出错"。

## 速查

```
□ ⭐⭐⭐ 目标：同样输入→差不多输出（不追求 100%，但⭐ 结构必须稳）
□ ⭐⭐⭐⭐ 跑两遍测试法：跑 → ⭐⭐ /clear → 再跑 → 比较
   ⭐⭐⭐ ⭐ 必须清会话，否则第二次自洽，什么都证明不了
   ⭐⭐⭐ 判据：⭐ 结构相同、主题相似即可；⭐⭐⭐ 差很多 = 写得不够细
□ ⭐⭐⭐ 质量标准要能机械检查（恰好3-5个 · 含计数与百分比 · 逐字引用 · 按名引用主题）
   ⭐⭐⭐ "建议必须引用特定主题"是⭐ 低成本防幻觉断言
□ ⭐⭐⭐ 边缘情况预先规定：归最具体 · ⭐⭐⭐ 不明确就标"混合"而非猜测
   ⭐⭐⭐ 过短 → ⭐ 计入但不引用（不编造的前提下保持完整）
   ⭐⭐⭐ ⭐ 提供"我不知道"这个合法选项 = 抑制幻觉最有效的一招

□ ⭐⭐⭐⭐ 三分法：① 必须现在告诉(正文) ② 只要能被找到(references)
   ③ ⭐⭐⭐ 根本不该让模型临场生成(scripts)
□ ⭐⭐ 契约：最小输入示例 + 完整输出示例；字段名/类型/必填/默认值/边界
□ ⭐⭐ 脚本：退出码稳定 · 只做一件事 · ⭐⭐⭐ 不依赖隐藏状态 · 输出固定格式
□ ⭐⭐⭐ 新增脚本必须⭐ 实际跑一次——⭐⭐⭐ 跑不通比不存在更危险
```

**一句话**：

> ⭐⭐⭐ **让输出稳定的最便宜方法是：跑一遍、/clear、再跑一遍、比较两次结果（不清会话就重跑等于什么都没测，第二次会自洽）；
> 而写技能的核心不是"告诉模型多少"，而是分清楚三类——必须现在告诉正文的、只要能被找到放 references 的、以及根本不该让模型临场生成而应锁进 scripts 的。**
