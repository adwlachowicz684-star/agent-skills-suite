## 1. ⭐⭐⭐⭐⭐ 暂停 ≠ 结束

| | 结束 | ⭐ 暂停 |
|---|---|---|
| 意图 | 交付 | ⭐⭐⭐⭐⭐ **交出控制权，等回应后继续** |
| 输出 | 最终产物 | ⭐⭐⭐ 中间产物 + 明确的问题 |
| 常见写法 | "完成" | ⭐⭐⭐⭐⭐ **几乎没人写** |

> ⭐⭐⭐⭐⭐ **技能把"暂停"和"结束"混为一谈的结果，是它从不暂停**——
> 因为"结束"是它一直在追求的目标，而"暂停"看起来像是没做到。

一个典型的缺失现场：

```
技能跑完 8 个步骤，第 3 步发现两种方案且后果不同
→ 它挑了一个继续
→ 最终交付
→ 用户看到结果才知道有另一个选择，且已经太晚（改了文件）
```

> ⭐⭐⭐⭐⭐ **问题不在它挑错了，在它挑的时候没有问——
> 而"该不该问"这个判断，只能由技能预先写死**（模型不知道自己不知道什么）。

## 2. ⭐⭐⭐⭐⭐ 三种必须暂停的点

**① ⭐⭐⭐⭐⭐ 不可逆动作之前**

```
发外部通知 · 删除 · 部署 · 提交 · 发邮件 · 数据库写入
```

> ⭐⭐⭐⭐ 这类已反复强调，但这里要补一句常被忽略的：
> ⭐⭐⭐⭐⭐ **"暂停"要发生在动作之前，不是"做完再告诉用户"**。
> 很多技能的写法是"发送后报告发送结果"——那不是暂停，是通知。

**② ⭐⭐⭐⭐⭐ 多个合理方案且后果不同**

```
判据：⭐⭐⭐⭐⭐ 如果选错了需要回滚，就该问。
```

> ⭐⭐⭐⭐ 模型的默认动作是挑一个继续（见 `default-actions.md`），
> ⭐⭐⭐⭐⭐ 而这个默认动作在"后果不同"的场景里是错的。
> 注意判据不是"有多个方案"——**方案多但后果相同时不必问**（挑一个即可）。

**③ ⭐⭐⭐⭐⭐ 信息缺失且无法推断**

```
"不知道目标是 staging 还是 production"
"找不到配置文件"
```

> ⭐⭐⭐⭐⭐ 缺失时模型的默认动作是⭐⭐⭐⭐ **猜一个继续**（填默认值），
> 而⭐⭐⭐⭐⭐ **默认值是作者的世界观，不是用户的。**
> 这与禁写"请提供更多信息"是同一条纪律的两面。

## 3. ⭐⭐⭐⭐⭐ 暂停时要展示什么

> ⭐⭐⭐⭐⭐ **"确认要继续吗？"是不够的——
> 它把判断成本完全推给了人，而人没有信息可做判断。**

四要素：

```
1. ⭐⭐⭐⭐⭐ 将要发生什么（具体动作，不是"执行操作"）
2. ⭐⭐⭐⭐ 影响范围（几个文件 / 发给谁 / 哪张表）
3. ⭐⭐⭐⭐⭐ 不可逆的部分（哪些撤不回来）
4. ⭐⭐⭐⭐ 选项（含"取消"和"只做只读部分"）
```

对比：

```
❌ "确认要发邮件吗？"
✅ "将向 3 人发送周报（a@、b@、c@）。
    发送后无法撤回。
    回复：发送 / 先看草稿 / 取消"
```

> ⭐⭐⭐⭐⭐ **第 3 条最容易被省，也是唯一真正区分"确认"和"告知"的一条。**
> 一个动作如果可逆，其实不必暂停——
> ⭐⭐⭐⭐ 所以"哪些撤不回来"既是展示内容，也是**决定要不要暂停的判据本身**。

第 4 条里的"只做只读部分"值得单独提：
⭐⭐⭐⭐ 它给了一个中间选项，避免用户被迫二选一
（要么全做、要么什么都不做）——
这正是禁令要带替代方案那条原则的应用。

## 4. ⭐⭐⭐⭐ 不该暂停的地方

> ⭐⭐⭐⭐ **过度暂停和从不暂停一样糟**——它会训练用户无脑点"继续"。

不该暂停的四种情况：

| 情况 | ⭐ 为什么不该暂停 |
|---|---|
| ⭐⭐⭐⭐ 动作可逆 | 撤得回来，问了只是增加摩擦 |
| ⭐⭐⭐⭐⭐ 信息可推断 | ⭐⭐⭐⭐ 有唯一合理答案时问 = 把成本推给人 |
| ⭐⭐⭐ 方案多但后果相同 | 挑一个即可，不必问 |
| ⭐⭐⭐⭐ 在同一个任务里已经问过 | ⭐⭐⭐⭐⭐ 重复询问是最伤体验的（用户会开始无脑确认） |

> ⭐⭐⭐⭐⭐ 最后一行最值得记：
> ⭐⭐⭐⭐ **无脑确认会摧毁检查点的全部价值**——
> 它把一个安全机制变成了一个仪式。

对策：⭐⭐⭐⭐ **同一任务内每个检查点只问一次**，
且如果后续有同类决策，⭐⭐⭐ 沿用第一次的答案并说明
（"按你前面选的 B 方案处理"）。

## 5. ⭐⭐⭐⭐ 暂停之后的三种结果

技能必须处理全部三种，而不只是"继续"：

| 结果 | ⭐ 处理 |
|---|---|
| 继续 | ⭐⭐⭐ 按确认的方案执行 |
| ⭐⭐⭐⭐ 修改 | ⭐⭐⭐⭐ **丢弃已生成的中间产物，不要"部分沿用"** |
| ⭐⭐⭐⭐⭐ 取消 | ⭐⭐⭐⭐⭐ **必须报告已发生的副作用** |

> ⭐⭐⭐⭐⭐ 第三行最常被漏：
> **取消不等于什么都没发生**——前半程可能已经写入过。
> 这与 `intent-drift-midflight.md` 那条一致：
> ⭐⭐⭐⭐ 已发生的写入动作必须报告，不因目标变更/取消而省略。

第二行的"丢弃"也值得强调：
⭐⭐⭐⭐ **用户改了主意后，模型最常见的错误是"保留大部分、改一小部分"**
——正是那份文档里"混合体"的成因。

## 6. ⭐⭐⭐⭐ 写法

一个可抄的检查点章节（不到 120 token）：

```markdown
## 检查点

以下情况必须暂停并展示：将要做什么 / 影响范围 / 不可逆部分 / 选项
- ⭐ 不可逆动作之前
- ⭐ 多个方案且后果不同（选错需回滚）
- ⭐ 信息缺失且无法推断

不暂停：动作可逆 · 可唯一推断 · 后果相同 · 同一任务内已问过

暂停后：继续 / 修改（丢弃中间产物重来）/ 取消（报告已发生的副作用）
```

> ⭐⭐⭐⭐⭐ 三条"不暂停"和三条"必须暂停"同样重要——
> ⭐⭐⭐⭐ **只写前者会变成从不暂停，只写后者会变成过度暂停。**

与相邻文档的分工：

```
preflight-gate        进入执行前，条件不满足就快速失败
⭐⭐⭐⭐⭐ 本份          执行中，条件满足但后果需要人拍板
exit-conditions       跑不动 / 跑不完 / 目的地变了 → 结束
```

> ⭐⭐⭐⭐⭐ 三者的差别在**时机**：
> 前置门禁在最前，检查点在中间，结束在最后。
> ⭐⭐⭐⭐ 而"检查点"是唯一一个**需要人来参与**的——
> 其余两个都是技能自己决定。

---

## 一句可贴在墙上

> ⭐⭐⭐ **"确认要继续吗？"不是检查点，是把判断成本推给了一个没有信息的人。
> 检查点要展示：要做什么、影响多大、哪些撤不回来。**
