## 1. 三种入口

| | 入口 | 触发者 | 输入形态 |
|---|---|---|---|
| ① | 斜杠命令 `/skill-name args` | 用户显式 | ⭐ 自然语言参数（可能残缺、可能带口语） |
| ② | 自动触发 | 模型（匹配 description） | ⭐⭐⭐⭐ 散落在上下文里的整段对话 |
| ③ | 被其他技能 / 编排器 / 子代理调用 | 另一个技能 | ⭐⭐⭐⭐⭐ 上游产物（结构化，没有"用户"） |

同一个技能、同一份正文，在三种入口下**面对的输入完全不同**，
而正文几乎总是按其中一种写的。

---

## 2. ⭐⭐⭐⭐⭐ 差别不在"谁触发的"，在"输入是什么形态"

直觉以为差别是"谁发起的"，于是认为只影响权限。真正的差别在输入侧：

```
① "分析这个文件"        → 参数在 ARGUMENTS 里
② 用户聊了十轮后说"那帮我看看" → ⭐⭐⭐⭐ 要分析什么？在十轮前的某句话里
③ 上游交来 analysis.json  → ⭐⭐⭐⭐⭐ 输入是一个文件路径，没有一句话
```

> ⭐⭐⭐⭐⭐ **②的输入是"推断出来的"，③的输入是"传进来的"。**
> 前者可能推断错（模型以为的目标 ≠ 用户想要的），后者根本不给你推断的机会——
> 它已经确定了，你要么用它，要么报错。

②的失败形态与"同一会话内第二次调用"同源：上下文里已有很多话，
⭐⭐⭐⭐ **其中一句是真正的目标，而模型选的是最近的一句**（近因偏差）。

---

## 3. ⭐⭐⭐⭐⭐ "根据用户的要求" 在第三种入口下没有指代对象

正文里最常见的句式：

```
"根据用户的要求，选择对应的处理方式"
"按用户指定的格式输出"
"如果用户没有说明，则……"
```

在 ③ 里：

> ⭐⭐⭐⭐⭐ **根本没有一个"用户"，也没有一句"要求"。**
> 调用者是一个技能，它传来的只有产物。

于是模型的默认动作接管——而它的默认动作不是报错，是⭐⭐⭐⭐⭐ **从上游产物里推断"用户大概想要什么"**。
这跟"省略不是留白"完全同构：**没写的地方由模型补，它补的依据是它手上唯一有的东西（产物）**。

修法不是删掉这类句式，是补上第三种入口下的分支：

```
✅ 输入来自上游产物时：以产物中显式声明的字段为准；
   产物未声明且正文无默认值 → 报错退出，不得从产物内容推断意图。
```

> ⭐⭐⭐⭐⭐ 最后半句是关键：**产物里没有的字段就是没有，不是"可以从数据里看出来"**——
> 那正是"输出编造"的入口。

## 4. ⭐⭐⭐⭐ 第三种入口下不能"询问用户"

正文写"如信息缺失，询问用户"——

```
① ✅ 能问，用户就在那儿
② ✅ 能问（但可能打断自动流程）
③ ❌ ⭐⭐⭐⭐⭐ 调用者是技能，它没有能力回答问题，也不会把问题转达给用户
```

③下这句话的两种实际走向，都不好：

```
A 卡住：等一个永远不来的回复（表现为超时）
B ⭐⭐⭐⭐⭐ 自行决定：模型自己答了自己的问题，然后继续
```

> ⭐⭐⭐⭐⭐ **B 更常见，而且它和"询问用户"是同一个句子导致的**——
> 正文只说了"问"，没说"问不到怎么办"，于是"问不到"这个分支由模型定义。

必须写全三档：

```
信息缺失时：
  ① 有默认值 → 使用并标注"输入未提供，取默认"
  ② 无默认值但可推断 → 推断并标注推断依据
  ③ ⭐⭐⭐⭐⭐ 均无 → 报错退出（返回结构化错误），不得继续
```

## 5. 权限与工具集也不同

| | 谁能调 | 工具集 |
|---|---|---|
| ① 斜杠命令 | 用户（即使 `disable-model-invocation: true` 也能用） | ⭐ 技能自带的 `allowed-tools` |
| ② 自动触发 | ⭐⭐⭐⭐⭐ 仅当未设 `disable-model-invocation: true` | 同上 |
| ③ 被技能调用 | ⭐⭐⭐⭐ 编排器必须自己声明 `Skill` 权限 | ⭐⭐⭐⭐⭐ 取交集 |

两条最常被漏：

```
⭐⭐⭐⭐ 编排类技能忘了写 allowed-tools: Skill → 正文写了 /pdf 也调不动
⭐⭐⭐⭐⭐ ③ 下有效权限是⭐ 调用链的交集，不是被调用技能自己声明的那份
```

> ⭐⭐⭐⭐⭐ 第二条的后果：技能在 ① 下能做的事，在 ③ 下做不了——
> 而失败表现为"工具被拒绝"，看起来像是权限配错了，实际是交集变小了。

## 6. ⭐⭐⭐⭐⭐ 测三种入口，各一次

多数技能只在 ① 下测过（因为那是最自然的测试方式），于是：

> ⭐⭐⭐⭐⭐ **在 ③ 下的表现从未被验证过，而它恰恰是组合场景里唯一会发生的入口。**

最低成本的三组测试：

```
① /skill-name 半个句子（残缺参数）
② 在一段无关对话后，用一句间接的话触发（测推断）
③ ⭐⭐⭐⭐⭐ 传一个最小上游产物（只含必需字段，不含任何"用户要求"）
```

第③组的判据：⭐⭐⭐⭐⭐ **产物里没有的字段，输出里不应该出现关于它的任何判断**——
出现了，就说明正文在让模型从数据里推断意图。

## 7. 检查清单

- [ ] ⭐⭐⭐⭐⭐ 正文里出现"用户要求/用户指定"时，写明输入来自上游产物时以什么为准
- [ ] ⭐⭐⭐⭐⭐ "询问用户"必须带"问不到怎么办"三档（默认值 / 推断并标注 / 报错退出）
- [ ] ⭐⭐⭐⭐ 产物未声明的字段，不得从产物内容推断
- [ ] ⭐⭐⭐⭐ 编排类技能声明了 `allowed-tools: Skill`
- [ ] ⭐⭐⭐⭐ 三种入口各测一次，第③组用最小产物
- [ ] ⭐⭐⭐ `disable-model-invocation` 只影响②，不影响①——别用它来"禁用技能"
