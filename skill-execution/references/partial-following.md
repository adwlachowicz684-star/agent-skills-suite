## 1. ⭐⭐⭐⭐⭐ 一个真实形状

技能写了五步：

```
1. 读取输入文件
2. 校验必填字段
3. 查询外部数据
4. 计算指标
5. 按模板输出
```

实际执行了 1、3、4、5——第 2 步没做，而**输出完整、格式正确、字段齐全**。

> ⭐⭐⭐⭐⭐ 用户拿到的是一份看起来做完的报告，
> ⭐⭐⭐⭐⭐ 它只是少了一道校验，而校验恰恰在没有问题时看不出差别。

---

## 2. ⭐⭐⭐⭐⭐ 为什么看不出来

三个条件同时成立才会被跳过而不留痕：

```
① ⭐⭐⭐⭐⭐ 被跳的那步不产生可见产出（校验类、过滤类、去重类）
② ⭐⭐⭐⭐⭐ 后续步骤在它没执行的情况下仍然能跑通
③ ⭐⭐⭐⭐⭐ 输出模板里没有它的位置
```

> ⭐⭐⭐⭐⭐ 第 ③ 条最关键：⭐⭐⭐⭐ **输出契约决定什么会被看见。**
> 模板里没有"校验结果"这一栏，模型就没有理由报告它做过还是没做。

这与《skill-output》的 `skill-output/references/numbers-in-output.md` 同源：
**不可见的东西不会被报告**，而"没报告"被读成"没问题"。

---

## 3. ⭐⭐⭐⭐⭐ 被跳的总是同一类步骤

按被跳概率排：

| 步骤类型 | 被跳概率 | 原因 |
|---|---|---|
| ⭐⭐⭐⭐⭐ 校验 / 前置检查 | 最高 | 成功时不产生差别 |
| ⭐⭐⭐⭐⭐ 去重 / 过滤 / 归一化 | 高 | 输出看起来"更全"反而像更好 |
| ⭐⭐⭐⭐ 排序 / 分组 | 中 | 结果差异需要细看 |
| ⭐⭐⭐ 主计算 | 低 | 不做就没有输出 |
| ⭐⭐ 输出格式化 | 最低 | 不做立刻可见 |

> ⭐⭐⭐⭐⭐ 规律很干净：**越"锦上添花"的步骤越容易被跳，
> 而它们恰恰是区分"能用"和"可靠"的那部分。**

反直觉的一条：⭐⭐⭐⭐ **去重被跳时输出更长，而用户常把"更全"当成"更好"**——
于是错误方向上还有正向反馈。

---

## 4. ⭐⭐⭐⭐⭐ 成因一：步骤排序诱导

```
1. 读取输入
2. 校验字段
3. 查询数据
```

> ⭐⭐⭐⭐⭐ 第 2 步夹在"读"和"查"之间，
> ⭐⭐⭐⭐ 而"读完之后去查"是一个连贯的动作。
> ⭐⭐⭐⭐⭐ 校验是插在连贯动作中间的停顿——它最容易被"顺过去"。

修法不是加粗，是**把校验放在边界上**：

```
1. 读取输入
2. ⭐⭐⭐⭐⭐ 校验（不通过则停止，不得进入第 3 步）
3. 查询数据
```

> ⭐⭐⭐⭐⭐ 关键在"不通过则停止"这五个字：
> ⭐⭐⭐⭐⭐ 它给这一步制造了一个**可观测的后果**，于是跳过它变成一件需要"决定"的事，
> 而不是一个无声的省略。

这与 `skill-precision/references/conditional-branch-writing.md` 的"没有 else 的 if"同源：
⭐⭐⭐⭐⭐ **没有后果的步骤，等于可选步骤。**

---

## 5. ⭐⭐⭐⭐⭐ 成因二：小步骤被读成修饰语

```markdown
3. 查询数据（注意去重）
```

> ⭐⭐⭐⭐⭐ 括号里的内容在语法上是补充说明，
> ⭐⭐⭐⭐⭐ 而模型对括号的处理优先级低于句子主干。

三种降级写法（从强到弱），越往后越容易被跳：

```
⭐⭐⭐⭐⭐ 独立成行：  "3. 对查询结果去重"
⭐⭐⭐⭐ 分号连接：    "3. 查询数据；查询结果必须去重"
⭐⭐⭐ 括号补充：      "3. 查询数据（注意去重）"    ← 最弱
⭐⭐ 形容词：          "3. 查询数据，输出干净的列表" ← 最弱且含糊
```

> ⭐⭐⭐⭐⭐ 判据：⭐⭐⭐⭐ **这一步能不能被单独打勾？**
> 不能独立成行的步骤，在模型的执行计划里通常不是一个步骤。

这也解释了 `skill-precision/references/list-item-relations.md` 里那条——
⭐⭐⭐⭐⭐ **列表项如果只是"一组相关内容"而不是"一组动作"，模型会自己决定做几项。**

---

## 6. ⭐⭐⭐⭐⭐ 成因三：验证步骤被合并进输出

技能常见这种写法：

```
5. 输出前检查覆盖率是否 ≥ 90%
6. 按模板输出
```

> ⭐⭐⭐⭐⭐ 模型会在生成输出的同时"顺便检查"，
> ⭐⭐⭐⭐⭐ 而"顺便检查"的检查是在**已经写好的文本上**做的——
> 它检查的是自己刚写的东西，于是必然通过。

这跟《skill-execution》的 `skill-execution/references/self-verification-trap.md` 是同一件事的不同侧面：
那份讲验证为何失效，这份讲**验证被跳过或被合并后，流程完整性本身失去了一个信号源**。

修法只有一条：**验证必须有独立产出**。

```
5. 输出检查结果：{"覆盖率": "87%", "达标": false}
6. ⭐⭐⭐⭐⭐ 若第 5 步达标为 false，输出中必须包含"未达标"一节并列出缺失项
```

> ⭐⭐⭐⭐⭐ 没有独立产出，⭐⭐⭐⭐ 就无法区分"做了且通过"和"没做"——
> 因为两种情况下输出里都没有异常。

---

## 7. ⭐⭐⭐⭐⭐ 修法：让跳过的代价可见

三条，按性价比排：

**① ⭐⭐⭐⭐⭐ 给不可跳过的步骤加一个输出字段**

```markdown
| 字段 | 说明 |
|---|---|
| `checks_run` | ⭐⭐⭐⭐⭐ 实际执行的检查项列表 |
```

> ⭐⭐⭐⭐⭐ 成本一行，效果是把"有没有做"变成可判定的事实。
> 这是本份最值得抄的一条——它不靠语气、不靠加粗，靠**契约**。

**② ⭐⭐⭐⭐⭐ 让被跳的步骤成为后续步骤的输入**

```
2. 校验 → 输出 `validation_result`
4. ⭐⭐⭐⭐⭐ 计算时必须使用 `validation_result` 中标注的有效记录
```

> ⭐⭐⭐⭐⭐ 跳了第 2 步，第 4 步就没有输入——
> 于是跳过在结构上不可能，而不是靠提醒。
> 这与 `skill-precision/references/positional-references.md` 的"给中间产物起名"是同一手法，这里是**用于强制依赖**。

**③ ⭐⭐⭐⭐ 在输出模板里留一格**

```markdown
## 校验
- 已校验字段：___
- 发现的问题：___（无则写"无"）
```

> ⭐⭐⭐⭐ 空着会被注意到；⭐⭐⭐⭐⭐ 而不留这一格，模型连"写无"的机会都没有。

---

## 8. ⭐⭐⭐⭐⭐ 自检

对技能里每一个步骤：

```
① ⭐⭐⭐⭐⭐ 跳过这一步，输出会不一样吗？（不会 → 高危）
② ⭐⭐⭐⭐⭐ 它独立成行了吗？（在括号里 → 高危）
③ ⭐⭐⭐⭐⭐ 输出模板里有它的位置吗？（没有 → 高危）
④ ⭐⭐⭐⭐⭐ 跳过它会让后续步骤失去输入吗？（不会 → 建议加依赖）
```

> ⭐⭐⭐⭐⭐ 第 ① 条是根因：⭐⭐⭐⭐ 一个步骤如果跳过了也没差别，
> ⭐⭐⭐⭐⭐ 它要么本就不该存在，要么它的产出应该被放进输出——
> 二者必居其一，不存在"写了就好"的第三种。

一个十秒判断：

> ⭐⭐⭐⭐⭐ **把技能的每一步依次删掉，问"用户能发现吗"。
> 有一步删了用户发现不了 → 那一步正在被静默跳过，只是你还没观察到。**

---

> ⭐⭐⭐ **没有后果的步骤就是可选步骤。
> 越"锦上添花"的步骤越容易被跳，而它们恰恰是"能用"和"可靠"的分界。**
