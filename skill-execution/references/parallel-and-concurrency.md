## 1. ⭐⭐⭐⭐⭐ 默认不该并行

我们的库里已有两条独立结论：

```
· 无序并行 = 比只跑一个还差（conflict-three-types-degradation）
· 同时挂载 >3 个技能，成功率下滑（three-skill-ceiling）
```

> ⭐⭐⭐ **所以默认答案是"串行"，并行是需要证明的例外。**

但实践中并行往往是被"看起来更快"吸引过去的——
而**技能并行的收益通常远小于它的风险**，因为：

```
串行：一次错一次
⭐ 并行：一次错 N 次，且 N 个错的组合方式超出你的测试能力
```

## 2. ⭐⭐⭐⭐ 四条准入条件

**全部满足**才允许并行：

| # | 条件 | ⭐ 为什么 |
|---|---|---|
| 1 | ⭐ 任务之间**无共享状态** | 有共享就必然有竞态 |
| 2 | ⭐ 无**顺序依赖**（含隐式） | ⭐ 隐式依赖单独测试测不出来 |
| 3 | ⭐ 每个任务**可独立失败** | 一个失败不能拖垮其余 |
| 4 | ⭐⭐ 有**汇聚点**与合并规则 | 没有汇聚点，结果就是一地碎片 |

> ⭐⭐⭐⭐ **第 2 条最容易假通过**：
> "A 和 B 之间没有依赖"——直到你发现两者都要写同一个文件。
> 检验方法：**把 A 单独跑一遍（不清 B 的结果），看它还对吗？**

第 3 条的具体含义：

```
❌ "三个都跑完再一起报结果"  ← 一个挂了就全挂
✅ "每个独立记录成功/失败，失败的给出部分结果"
```

## 3. ⭐⭐⭐⭐⭐ 并行的失败形状变了

这是全份最该记住的一节。串行 vs 并行的失败对比：

| | 串行 | ⭐ 并行 |
|---|---|---|
| 失败时状态 | 明确（卡在第 3 步） | ⭐ **N 个半成品** |
| 报错 | 一个 | ⭐ 可能 0 个（都"成功"了但组合错） |
| 可重入 | 从头跑 | ⭐ 要判断每个分支跑到哪 |
| 日志 | 一条时间线 | ⭐ 交错，难读 |

> ⭐⭐⭐⭐⭐ **最危险的是"N 个半成品"：
> 每一个单独看都是成功的，合起来是错的。**
> 没有任何一个组件会报错——因为没有一个组件失败了。

> ⭐⭐⭐ 这跟我们反复强调的那条完全一致，只是换了个场景：
> **局部成功，整体失败，且静默。**

**可重入是并行独有的成本**：

```
串行失败 → 从头重跑（简单）
⭐ 并行失败 → ⭐ 有些分支已经写入了，不能重跑（重复写入）
           → 必须先查状态，再决定跳过还是重做
```

所以并行**强制要求幂等**（`idempotency-resume.md`）——
串行里幂等是加分项，并行里它是**准入条件**。

## 4. ⭐⭐⭐ 三种并行与各自的坑

| 类型 | 坑 |
|---|---|
| **多子代理并行** | ⭐ 子代理`隔离`了上下文，但也隔离了"别的分支做了什么"——协作靠显式传参 |
| **多工具调用并行** | ⭐ 有写操作的不能并行（顺序未定义） |
| **同一技能多次并行** | ⭐⭐ 最容易产生重复写入（同一份报告写两遍） |

第三类的防护：⭐ **给每次并行实例一个唯一 ID**，
写入前检查该 ID 是否已存在（`state-check.md`）。

## 5. ⭐⭐⭐⭐ 必须有汇聚点

> ⭐⭐⭐ **并行不是"都跑完就结束了"，是"都跑完之后必须有一个合并步骤"。**

汇聚点要做三件事，缺一件就是半成品：

```
1. ⭐ 清点：N 个分支，几个成功几个失败？
2. ⭐ 合并：按什么规则合？（冲突时谁赢？）
3. ⭐ 报告：⭐⭐ 部分失败时必须明确说哪部分缺失
```

第三条最常被漏，也最伤人：

```
❌ "分析完成"（其实 3 个分支挂了 1 个）
✅ "分析完成（3 个来源中 2 个成功；
    ⚠️ 日志来源超时未纳入，覆盖率 67%）"
```

> ⭐⭐⭐⭐ **部分成功必须报覆盖率。**
> 不报的话，"分析完成"就是一句谎言——
> 而这正是 `execution-error-protocol.md` 描述的"错误被吞掉"的并行版本。

## 6. ⭐⭐⭐ 顺序敏感性的检测

一个便宜的测试（来自 `composition-patterns-types.md` 的同源思路）：

```
1. 按 A→B 跑，记结果 R1
2. ⭐ 按 B→A 跑，记结果 R2
3. R1 ≠ R2 → ⭐⭐ 存在隐式顺序依赖 → 禁止并行
```

> ⭐⭐⭐ 这个测试的价值在于**它不需要你事先知道依赖在哪**。
> 你不用理解为什么，只要看到 R1≠R2 就知道不能并行。

配一条：⭐ **同一个技能集，加载顺序不同结果就不同**
（来自 `solid-for-skills.md`）——
所以顺序敏感性不止存在于执行，也存在于加载。

## 7. ⭐⭐ 与子代理 fork 的关系

子代理 fork 天然是并行的（多个 fork 同时跑），所以上面四条准入
**对 fork 全部适用**，且额外多一条：

> ⭐⭐⭐ **fork 出去的子代理看不到主上下文**
> ——所以"共享状态"在 fork 场景下几乎必然存在
> （它们都要写回同一个地方）。

对策就是我们已有的：**fork 正文必须写成独立可执行的工单**
（`fork-token-economics.md`），且**回传格式要统一**——
否则汇聚点上无法合并。
