## 1. ⭐⭐⭐⭐ 结构化 ≠ 正确

> ⭐⭐⭐⭐⭐ **"约束解码⭐ 保证响应符合 schema 的⭐ 类型和结构，
> ⭐⭐⭐⭐⭐ ⭐ 它不保证⭐ 值是正确的。
> ⭐⭐⭐⭐⭐ 如果源文本有歧义，模型⭐ 完全可以返回
> ⭐ `{"sentiment": "positive"}` ⭐ 来描述一条⭐ 负面评价。"**

> ⭐⭐⭐⭐ **"⭐ 永远在 schema 校验⭐ 之后、⭐ 在应用代码里⭐ 再做⭐ 语义校验。"**

> ⭐⭐⭐⭐⭐ 这条把 `output-stability-contract.md` 的验收三问
> （文件生成？JSON 可解析？字段齐全？）
> ⭐⭐⭐⭐ 推到了⭐ 第四问——⭐⭐⭐⭐⭐ **值是对的还是只是"长得对"？**
>
> ⭐⭐⭐⭐⭐ 这是一条⭐ 特别危险的失败，因为⭐ 它在所有门禁上都是绿的：
> ```
> ✅ JSON 解析成功
> ✅ schema 校验通过
> ✅ 字段一个不少
> ❌ ⭐⭐⭐⭐⭐ 值是模型⭐ 猜的
> ```
> ⭐⭐⭐⭐⭐ 与 `three-failure-modes.md` 的"结构正确的废话"、
> `conflict-three-types-degradation.md` 的"错得自信而正确"
> ⭐ 是⭐⭐⭐⭐⭐ 同一件事在⭐ 结构化输出这个具体场景里的⭐ 精确形态——
> ⭐⭐⭐⭐⭐ **这是该结论的⭐⭐ 第六个来源，也是最可操作的一个**
> （因为⭐ 它给了明确的修法：⭐ 语义校验放在应用代码里）。

**语义校验该查什么**（举例）：

```
· ⭐ 总额 == 各行之和（不变量）
· ⭐ 币种一致
· ⭐ ID 确实存在（不是编的）
· ⭐ 枚举值在业务上说得通（不只是"在枚举里"）
```

> ⭐⭐⭐ 第三项尤其重要：⭐ **"ID 存在"是无法靠 schema 表达的**，
> ⭐ 它只能靠⭐ 查一次数据库。

## 2. ⭐⭐⭐ 防御管线六步

```
① ⭐⭐ 严格解析：尽早拒绝畸形 JSON，⭐⭐ 保留原始文本⭐ 供调试
② ⭐⭐⭐ 强校验：跑 JSON Schema，⭐⭐⭐ 记录每一条失败路径与规则
③ ⭐⭐⭐ 本地修复：⭐ 确定性地修小问题（去尾逗号、字符串转数字、统一日期格式）
          ⭐⭐⭐ ⭐ 且只在⭐ 安全限度内
④ ⭐⭐⭐ 请模型修：⭐⭐⭐ 把⭐ 无效载荷 + ⭐ 校验器报错⭐ 一起给它，
          ⭐⭐⭐⭐ 要求返回⭐ 同 schema 的对象，⭐⭐ ⭐ 不加任何说明
⑤ ⭐⭐⭐⭐ 受控重试：⭐⭐⭐⭐ ⭐ 设上限，需要时⭐ 引入变化（如仅修复轮提高温度）
          ⭐⭐⭐ ⭐ 稳定失败就停
⑥ ⭐⭐⭐ 兜底：⭐⭐⭐ 幂等无操作 → 安全默认对象；⭐⭐⭐⭐ 关键动作 → ⭐ 转人工
```

> ⭐⭐⭐ 第 ④ 步那条"不加任何说明"⭐ 值得单独记——
> ⭐⭐⭐⭐ 因为模型⭐ 最自然的反应是⭐ 解释它错在哪，
> ⭐⭐⭐⭐ 而那段解释⭐ 会再次破坏格式。
> ⭐⭐⭐⭐ 这与 `script-cli-contract.md` 的"stdout 只放结果"是⭐ 同一条纪律的⭐ 第二个场景。

**每一步都要发遥测**：

> ⭐⭐⭐ **"每一步都要发出遥测：⭐ 哪种策略成功了、⭐ 尝试了几次、⭐ 最终状态。"**

> ⭐⭐⭐⭐ 这补上了 `skill-observability.md` 的一个盲区：
> 那份讲⭐ 调用日志 vs 决策日志，
> ⭐⭐⭐ 这里讲的是⭐ **输出校验层的日志**——
> ⭐⭐⭐⭐ 没有它，你只知道"最终失败了"，不知道⭐ 卡在哪一步。

## 3. ⭐⭐⭐ 重试的三条纪律

```
① ⭐⭐⭐⭐ 每次重试必须带上⭐ 具体的错误反馈，⭐ 不能只说"再试一次"
② ⭐⭐⭐⭐ ⭐ 设上限（如 3 次），⭐ 稳定失败就停
③ ⭐⭐⭐⭐ ⭐ 重试之间⭐ 引入变化（否则会得到⭐ 同样的错误两次）
```

> ⭐⭐⭐⭐⭐ 第 ① 条与 `output-stability-contract.md` 的"跑两遍要 /clear"、
> `trace-debugging.md` 的"循环根因是没有明确的成功判据"
> ⭐⭐⭐⭐ 三者指向⭐ 同一件事：
> ⭐⭐⭐ **没有具体反馈的重试 = 换个随机数再撞一次墙。**
>
> ⭐⭐⭐⭐ 第 ③ 条尤其反直觉——⭐ **重试时提高温度**，
> 因为⭐ 同样的输入和同样的温度大概率得到同样的错误。
> ⭐⭐⭐ 这是"确定性机制承载确定性判断"的⭐ 又一次体现：
> ⭐⭐⭐⭐ **重试的"变化"应该是⭐ 被显式引入的，不是⭐ 指望运气。**

## 4. ⭐⭐⭐ 该记的五个指标

```
· ⭐⭐⭐ 解析成功率（首次尝试即合法 JSON 的比例）
· ⭐⭐⭐ 校验成功率（解析后通过 schema 的比例）
· ⭐⭐⭐ 修复成功率与各策略使用次数
· ⭐⭐⭐⭐ 字段级错误热力图（⭐ 最常失败的路径与规则）
· ⭐⭐⭐⭐ Schema 漂移（提示/模型变更后，⭐ 类型、枚举、长度的⭐ 分布变化）
```

> ⭐⭐⭐⭐ 第 4 项最实用——⭐ **它会直接告诉你该改哪一条描述**。
> 比如 `status` 字段总填错，说明⭐ 它的描述有歧义（见第 5 节）。
>
> ⭐⭐⭐⭐ 第 5 项则是一个⭐ 此前没收过的信号类型：
> ⭐⭐⭐⭐ **"模型没坏，但它填东西的方式变了"**——
> ⭐⭐⭐ 这正是 `skill-rot-rollback-discipline.md` 里"模型变了、指令没变、行为可能变了"
> ⭐⭐⭐⭐ 的⭐ 可量化版本。⭐⭐ 建议：⭐⭐⭐ **换模型后先看漂移指标，再看通过率。**
>
> ⭐⭐⭐ 另外要⭐ 把这些指标和⭐ 延迟、成本⭐ 放在一起看——
> ⭐⭐⭐⭐ **反复修复是在⭐ 悄悄加延迟和加 token 的**（每次重试都要钱）。

## 5. ⭐⭐ Schema 怎么写模型才填得准

| 手法 | ⭐ 说明 |
|---|---|
| ⭐⭐⭐⭐ **枚举优先于自由字符串** | 类别、状态、动作⭐ 收敛到小的规范集合 |
| ⭐⭐⭐ **判别联合（discriminated union）** | 用 `type` 字段⭐ 选择不同子 schema |
| ⭐⭐⭐ 格式提示 | `date-time` / `uri` / `email` / 国家码——⭐ 收紧校验且简化下游 |
| ⭐⭐⭐⭐ **有界数组与数字** | ⭐ `minItems` / `maxItems` / `minimum` / `maximum` |
| ⭐⭐ 必需 vs 可选 | ⭐ 只把真正需要的标 required，⭐⭐ 但可选项要有⭐ 默认值或兜底 |
| ⭐⭐⭐ 嵌套对象表示工具结果 | ⭐ 每次工具调用一个⭐ 类型化对象 → ⭐ 支持部分成功与⭐ 定向重试 |

> ⭐⭐⭐⭐ ⭐ 原则一句话：**"要显式但不要脆弱。"**
> ⭐⭐⭐ ⭐⭐ **避免⭐ 庞大而含糊的 schema（逼模型去猜）；
> ⭐⭐⭐ 倾向⭐ 紧凑、⭐ 按动作划分的形状，⭐ 然后用多步把它们串起来。**
>
> ⭐⭐⭐⭐⭐ 这与 `four-design-principles-io-contract.md` 的
> "单一职责 + 可组合"⭐⭐⭐⭐ ⭐ 完全同构——
> ⭐⭐⭐⭐ **schema 也要单一职责**：⭐ 一个大而全的 schema 等于⭐ 一个大而全的技能。

**几个具体的坑**（都是⭐ 静默或⭐ 报错位置误导的）：

```
① ⭐⭐⭐⭐ 定义了字段却不写 description
   ⭐⭐⭐⭐⭐ "一个叫 status 却没有描述的字段，
             ⭐ 可以指 HTTP 状态、订单状态、或评审状态。
             ⭐⭐⭐⭐⭐ ⭐ 模型把字段描述当作⭐ 抽取指令在用。
             ⭐⭐⭐⭐ ⭐ 省略描述 = ⭐ 省略了你一半的提示。"
   → ⭐⭐⭐⭐⭐ 这是"每一处模糊都是一次授权模型替你决定"的⭐ 完美实证

② ⭐⭐⭐ 枚举大小写不匹配的硬失败
   enum 定义 ["Active","Inactive"]，模型返回 "active" → 校验失败
   → ⭐ 要么⭐ 全部小写，要么⭐ 加一道归一化

③ ⭐⭐⭐ 数组字段返回 [] 但数据其实存在
   ⭐⭐⭐⭐ ⭐ 根因常是⭐ 字段描述太含糊
   → 修法：⭐⭐⭐ 把描述写成⭐ 规定性的
     "文本中提到过的所有产品名。⭐ 只要提到任何一个，就至少返回一个。"

④ ⭐⭐⭐ 超长源文本 → 模型读不完 → 抽取不全
   → ⭐⭐⭐ 分块抽取再合并，⭐⭐ ⭐ 别指望一次处理 50 页

⑤ ⭐⭐⭐ 递归或超过 3 层嵌套
   ⭐⭐⭐ ⭐ 显著增加解码延迟，⭐⭐⭐ 且更容易在写完 JSON 前撞上 max_tokens
   → ⭐⭐⭐ ⭐ 尽量摊平

⑥ ⭐⭐⭐⭐ 模型返回 refusal 而不是数据
   ⭐⭐⭐⭐ ⭐ 先查 refusal 字段再访问 parsed，否则⭐⭐ 拿到 None 然后抛错
```

## 6. ⭐⭐⭐ 与已有原则的关系

```
"结构化输出 ≠ 正确输出"  ←→ 结构正确的废话 / 错得自信 → ⭐ 第六个来源
"省略描述 = 省略一半提示" ←→ 每一处模糊都是一次授权 → ⭐ 完美实证
"重试要带具体反馈"       ←→ 跑两遍要 /clear、循环根因无成功判据
"schema 也要单一职责"    ←→ 四项设计原则
```

> ⭐⭐⭐⭐ 本份还顺带⭐ 补上了一个此前⭐ 只有结论没有机制的空白：
> `judgment-branches-acceptance.md` 说"结构化输出 + 代码渲染把格式稳定性
> 从模型手里彻底拿走"，
> ⭐⭐⭐⭐ 而这里给出了⭐ **拿走之后那条完整管线长什么样**。

## 速查

```
□ ⭐⭐⭐⭐⭐ 结构化 ≠ 正确：schema 合规只保证⭐ 类型和结构，⭐⭐⭐⭐⭐ 不保证值
   ⭐⭐⭐⭐⭐ ⭐ 永远在 schema 校验之后、在应用代码里⭐ 再做语义校验
   ⭐⭐ 语义校验查：总额==行和？币种一致？⭐ ID 真存在？枚举业务上说得通？
□ ⭐⭐⭐ 管线六步：严格解析(⭐保留原文) → 强校验(⭐记录每条失败路径)
   → 本地修复(⭐安全限度内) → 请模型修(⭐⭐⭐ 同schema、⭐不加任何说明)
   → 受控重试(⭐上限+⭐引入变化) → 兜底(幂等→安全默认；关键→转人工)
□ ⭐⭐⭐⭐ 重试三纪律：⭐ 带具体反馈(不是"再试一次") · ⭐ 设上限 · ⭐ 重试间引入变化
   ⭐⭐⭐⭐ 重试时⭐ 提高温度——同样输入同样温度大概率得到同样错误
□ ⭐⭐⭐ 五指标：解析成功率 · 校验成功率 · 修复成功率 · ⭐⭐⭐⭐ 字段级错误热力图
   ⭐⭐⭐⭐ Schema 漂移（换模型后⭐ 先看漂移再看通过率）
   ⭐⭐⭐⭐ 反复修复在⭐ 悄悄加延迟和 token

□ ⭐⭐⭐⭐⭐ 字段不写 description = ⭐⭐⭐⭐⭐ 省略了一半的提示
   ⭐⭐⭐⭐⭐ 模型把⭐ 字段描述当抽取指令在用（"status"可指三种东西）
□ ⭐⭐⭐ schema 手法：枚举>自由字符串 · 判别联合 · 格式提示 · ⭐有界数组/数字
   ⭐⭐⭐⭐ 原则："显式但不脆弱"；⭐⭐⭐ schema 也要单一职责（大而全=逼模型猜）
□ 坑：枚举大小写 · ⭐⭐⭐ 数组返回[]但数据存在(描述写规定性) · 超长分块
   ⭐ 嵌套>3层摊平 · ⭐⭐⭐⭐ 先查 refusal 再访问 parsed
```

**一句话**：

> ⭐⭐⭐⭐⭐ **约束解码只保证响应符合 schema 的类型和结构，不保证值是对的——模型完全可能给一条负面评价返回 `{"sentiment":"positive"}`，所以永远要在 schema 校验之后、在应用代码里再做语义校验；
> 而"一个没有 description 的字段等于省略了一半的提示"，因为模型是把字段描述当作抽取指令在用的。**
