## 1. ⭐⭐⭐⭐⭐ 依赖不止是包

说到"技能的依赖"，多数人想到的是：

```
python >=3.11 · jq · node 18+ · 某个 npm 包
```

但技能真正依赖的东西，还有另一大类：

| 类型 | 例子 |
|---|---|
| ⭐⭐⭐ 文件 | `.eslintrc`、项目配置、schema 文件 |
| ⭐⭐⭐⭐ 环境变量 | `ANTHROPIC_API_KEY`、`CI`、内网地址 |
| ⭐⭐⭐⭐ 外部服务 | 内部 API、数据库、知识库索引 |
| ⭐⭐⭐⭐⭐ **前置产物** | "另一个技能已经跑过并生成了 X" |

> ⭐⭐⭐⭐⭐ **第四类是最隐蔽、也最致命的**——
> 它让技能之间产生**隐式依赖**，
> 而单独测试这个技能**完全测不出来**。

---

## 2. ⭐⭐⭐⭐⭐ 为什么数据依赖不被声明

三个原因，都很合理，也都很坑：

**① ⭐⭐⭐ 作者的环境里它们天然存在**

```
作者写技能时，那个配置文件就在项目里、那个环境变量早就 export 了
→ ⭐⭐⭐ ⭐ 他看不见它们，就像鱼看不见水
```

**② ⭐⭐⭐ 它们不是"安装"来的**

包依赖有 `pip install` 这个显式的获取动作；
⭐ **环境变量和配置文件没有**——它们是"环境的一部分"。

**③ ⭐⭐⭐⭐ 技能格式里没有放它们的位置**

> ⭐⭐⭐⭐ 这是最关键的一条：
> **frontmatter 没有 `data_dependencies` 字段**，
> `allowed-tools` 也只描述工具不描述输入。
> 于是即使作者想声明，⭐⭐⭐ 他也只能写进正文——
> **而正文是触发之后才加载的。**

对比一下脚本依赖：36.6% 隐藏、仅 1.4% 声明——
**数据依赖的声明率只会更低**，因为连想声明的地方都没有。

## 3. ⭐⭐⭐⭐ 四类数据依赖

**① 配置文件**（最易发现）

```
.eslintrc / tsconfig.json / pyproject.toml
```

**② 环境变量**（中等）

```
⭐ 常见坑：不只在本地，CI 里也常常没有
```

**③ 外部服务**（中等）

```
⭐⭐ 常见坑：有网络但没权限（401/403），或指向了错误的环境（staging vs prod）
```

**④ ⭐⭐⭐⭐⭐ 前置产物**（最难发现）

```
"先跑 analyze 生成 analysis.json，再跑 report 读它"
```

> ⭐⭐⭐⭐ 第四类的特征症状是**"时好时坏"**——
> 有人先跑了 A 就成功，有人直接跑 B 就失败。
> 而这正是 `dependency-lockfile.md` 里"隐式依赖"那条特征症状的来源。

## 4. ⭐⭐⭐⭐⭐ 声明格式

因为 frontmatter 没有标准字段，**写在正文开头，格式固定**（这样可 grep、可校验）：

```markdown
## 数据依赖（必读）

| 依赖 | 类型 | 缺失时 |
|---|---|---|
| `.eslintrc` | 配置文件 | 停止并说明，不假设默认规则 |
| `ANTHROPIC_API_KEY` | 环境变量 | 停止；⭐ 不要请求用户粘贴 |
| 内部 API `/v1/meta` | 外部服务 | 停止；不得用缓存数据替代 |
| `analysis.json` | ⭐ 前置产物 | ⭐⭐ 由 `analyze` 技能生成；不存在则先跑它 |
```

> ⭐⭐⭐⭐⭐ **第三列是关键，而且必须写"停止"或"降级"二选一。**
> 不写，模型就会自行决定——而它默认会选"继续"。

第四行的写法值得单独记：**前置产物要写清"由谁生成"**。
这把隐式依赖变成了显式的一条边——
⭐⭐⭐ 顺便也让"这两个技能该不该合并"（见 `merge-signals-five.md`）有了数据依据。

## 5. ⭐⭐⭐⭐ 缺失时的失败形状

| 依赖类型 | ⭐ 失败形状 | 为什么危险 |
|---|---|---|
| 配置文件 | ⭐⭐ 用"通用默认规则"跑完 | 输出看着正常，规则是错的 |
| 环境变量 | 报错（稍好） | ⭐ 但可能被当成"测试未通过" |
| 外部服务 | ⭐⭐⭐ 401 被当成"无数据"→ 输出空分析 | ⭐⭐⭐ 空分析不是错误，是"结论：无" |
| ⭐ 前置产物 | ⭐⭐⭐⭐⭐ 读不到 → 模型自己造一份 | ⭐⭐⭐⭐⭐ 完全静默的编造 |

> ⭐⭐⭐⭐⭐ **最后一行是最严重的**：
> 它同时命中"错误被吞掉"和"局部成功整体失败"两条已有结论，
> 而且是其中**唯一会主动产生假数据的一种**。

对照第三行也值得警惕：
**"分析完成，未发现异常"和"分析根本没拿到数据"在输出上很难区分**——
所以报告必须带 ⭐ **样本量与数据来源说明**（这与 `bad-skill-anatomy.md`
里"输出四项 REQUIRED 含数据说明"是同一条要求）。

## 6. ⭐⭐⭐ 与前置门禁的配合

`preflight-gate.md` 的 STEP 0 说"不要在缺前置条件时开始执行"。
数据依赖就是 ⭐⭐⭐ **STEP 0 最该检查、却最常被漏掉的一类前置条件**。

具体做法（三条）：

```
① ⭐ 数据依赖章节放在正文最前（黄金位置，见 instruction-ordering.md）
② ⭐⭐ 每项都要有可执行的检查动作（test -f / env | grep / curl -I）
③ ⭐⭐⭐ 缺失项一次性全报，不要一项一项问
```

第三条与前置门禁的"缺失项一次性全报"完全同源——
⭐ **一次报一个会让用户来回五六轮**。

## 7. ⭐⭐ 检查方法

**人工**（写完后）：

```
⭐⭐⭐ 假装你在一个全新克隆的仓库里、CI 环境、没有本地 .env
   逐个问：这个技能还能跑吗？
```

> ⭐⭐⭐ **这个思想实验几乎必然能找出 2–3 条没声明的依赖**，
> 成本不到一分钟。

**机械**（可进 CI，检查声明而非存在性）：

```bash
# 有正文提到文件或环境变量，却没有"数据依赖"章节 → 可疑
grep -qE '## 数据依赖' SKILL.md || \
  (grep -qE '\$\{?[A-Z_]{3,}\}?|\.eslintrc|tsconfig|\.env' SKILL.md && echo "WARN: 疑似未声明的数据依赖")
```

> ⭐⭐⭐ 这是"WARN 不阻断"级别的检查——
> 判"要不要声明"需要理解，机器只能提示。
> 但 ⭐⭐ **提示就够了**，因为作者缺的从来不是判断力，是**被提醒**。
