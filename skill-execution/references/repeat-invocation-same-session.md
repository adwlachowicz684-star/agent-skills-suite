## 1. ⭐⭐⭐⭐⭐ "再跑一次"不是同一个输入

```
用户：「分析一下这个模块」
（技能跑完，输出 40 行）
用户：「再跑一次」
```

> ⭐⭐⭐⭐⭐ 字面输入完全相同，
> ⭐⭐⭐⭐⭐ 但实际输入多了一样东西：**第一次的 40 行输出。**

这就是本份的出发点：

> ⭐⭐⭐⭐⭐ **技能的"无状态"假设在第二次调用时不成立——
> 指令是无状态的，但上下文不是。而模型读的是上下文。**

---

## 2. ⭐⭐⭐⭐⭐ 第一次的结果会污染第二次

污染沿三条路径发生：

**① ⭐⭐⭐⭐⭐ 锚定**

```
第一次说"主要风险是 A"
→ 第二次会倾向于再说一次"主要风险是 A"
```

> ⭐⭐⭐⭐⭐ 这不是随口一说：⭐⭐⭐⭐⭐ **上下文里已有的结论会成为最强的少样本示例**——
> 按《skill-examples》的 `example-values-become-defaults.md`，模型对示例的信任度高于指令。

**② ⭐⭐⭐⭐⭐ 省略**

```
第一次已经读过 12 个文件
→ ⭐⭐⭐⭐⭐ 第二次可能只扫一眼，因为它"已经知道了"
```

> ⭐⭐⭐⭐⭐ 后果是覆盖率悄悄下降，而输出看不出区别
> （和第一次一样长、一样有条理）。

**③ ⭐⭐⭐⭐⭐ 趋同**

```
两次结果高度相似
→ ⭐⭐⭐⭐⭐ 你会以为"很稳定"
→ ⭐⭐⭐⭐⭐ 实际上它可能只是复制了自己
```

> ⭐⭐⭐⭐⭐ 第三条的危害最大，因为它**伪造了稳定性**。
> 而我们已经有结论：⭐⭐⭐⭐⭐ 判定稳定性必须在干净环境跑两遍
> （《skill-evaluating》的 `test-doubles-fixtures.md`）——
> 同一会话内的"跑两次"测不出稳定性，它测的是自洽。

## 3. ⭐⭐⭐⭐⭐ 三种第二次，行为应不同

用户说"再跑一次"时，想要的可能是三种不同的事：

| 用户意图 | ⭐⭐⭐⭐⭐ 正确行为 |
|---|---|
| ⭐⭐⭐⭐⭐ 重做（上次的不对） | 明确丢弃第一次结果，从原始输入重跑 |
| ⭐⭐⭐⭐⭐ 继续（上次没跑完） | 沿用第一次的中间状态 |
| ⭐⭐⭐⭐⭐ 换个对象（同样的分析，另一个模块） | ⭐⭐⭐⭐⭐ 复用方法，不复用结论 |

> ⭐⭐⭐⭐⭐ 第三种最容易被做错：模型会带上第一次的结论
> （"主要风险是 A"）去分析另一个模块——
> ⭐⭐⭐⭐⭐ **而那正是最典型的"看起来专业、实际是抄"。**

判据很实用：

> ⭐⭐⭐⭐⭐ **用户的第二次指令里有没有新的实体？**
> 有（另一个模块、另一个客户）→ 方法可复用，结论必须重算。

而技能该做的：

```
□ ⭐⭐⭐⭐⭐ 在正文写明：同一会话内重复调用时，不得引用上一次的输出作为依据
□ ⭐⭐⭐⭐ 若用户明确说"继续"，才沿用中间状态
```

## 4. ⭐⭐⭐⭐⭐ 相对时间在第二次会被重新解析

与 `relative-time-resolution.md` 的冲突点，也正是在这里被触发：

```
第 1 轮："分析最近一周" → 解析为 09-22 ~ 09-29
第 8 轮："再看一下最近一周" → ⭐⭐⭐⭐⭐ 又解析一次
```

那份要求"同一会话内相对时间只解析一次"，理由是：

> ⭐⭐⭐⭐⭐ 否则同一份报告里的两处"最近"会指向不同区间，
> ⭐⭐⭐⭐ 而输出里看不到（两处都不写区间）。

但反过来有个容易做错的情形：

```
⭐⭐⭐⭐ 用户明确说"更新到今天" → ⭐⭐⭐⭐⭐ 此时必须重新解析，沿用旧区间才是错的
```

判据：**"再跑一次"沿用旧区间，"更新"重新解析**。
两者在字面上只差一个词，所以⭐⭐⭐⭐ 技能里最好写明这两种触发语。

## 5. ⭐⭐⭐⭐⭐ 已发生的副作用不会因为第二次而消失

这是与跨会话那份**完全对称**的一条：

```
跨会话：进度没了，副作用还在
⭐⭐⭐⭐⭐ 会话内：第一次的输出还在上下文，而副作用也还在
```

> ⭐⭐⭐⭐⭐ 换句话说：会话内是⭐⭐⭐⭐ **两者都还在**——
> 于是它同时具有两种污染。

最容易出事的形态：

```
第一次已写入文件 / 已发送 / 已创建
第二次"重做"
→ ⭐⭐⭐⭐⭐ 旧的副作用没有被撤销，新的又叠加了一次
```

> ⭐⭐⭐⭐⭐ 这就是"重试前必须查状态"的会话内版本：
> ⭐⭐⭐⭐ 幂等防止的是重复执行，
> ⭐⭐⭐⭐⭐ **而这里需要的是"重做前先报告已存在的副作用"**。

写法：

```markdown
## 重做时
1. ⭐⭐⭐⭐⭐ 先列出上一次已产生的外部变更（文件/记录/消息）
2. ⭐⭐⭐⭐⭐ 询问是回滚后重做，还是在其基础上继续
3. ⭐⭐⭐⭐⭐ 不得静默叠加
```

## 6. ⭐⭐⭐⭐ 该不该主动说明"上下文里有什么"

一个反直觉的建议：**让模型在第二次调用时说清楚它依据了什么**。

```
❌ 第二次直接给结果
✅ ⭐⭐⭐⭐ "基于本次重新读取的 12 个文件（未沿用上一轮的结论）"
```

> ⭐⭐⭐⭐⭐ 这一句的作用和 `relative-time-resolution.md` 里的
> "把解析结果写进输出首行"完全相同：
> ⭐⭐⭐⭐⭐ **不是为了更正确，是为了让"它到底重跑了没有"变成可见的。**

成本仍然是一行：

```
一行 ≈ 15 token
覆盖：⭐⭐⭐⭐⭐ 一次"看着很稳、其实是复制自己"的伪稳定
```

## 7. ⭐⭐⭐⭐⭐ 自检

对任何可能被反复调用的技能：

```
① ⭐⭐⭐⭐⭐ 正文写了"重复调用时不得引用上次输出"吗？
② ⭐⭐⭐⭐⭐ 区分了"重做 / 继续 / 换对象"三种意图吗？
③ ⭐⭐⭐⭐⭐ 换对象时，结论会重算吗？
④ ⭐⭐⭐⭐⭐ 重做前会报告已存在的副作用吗？
⑤ ⭐⭐⭐⭐ 相对时间沿用还是重新解析，写了吗？
```

> ⭐⭐⭐⭐⭐ 第 ① 条最便宜也最常被违反——
> ⭐⭐⭐⭐⭐ **因为作者只想过"第一次被调用"这个场景，
> 而"第二次"从来没在他的脑子里出现过。**

一个十秒判断：

> ⭐⭐⭐⭐⭐ **让用户在同一个会话里连说两次同样的指令，
> 看他会不会得到两份几乎一样、但都"没说明依据来源"的结果。
> 会 → 这个技能在伪造稳定性。**

---

## 一句可贴在墙上

> ⭐⭐⭐ **同一会话内跑两次，第二次的输入多了一样东西：第一次的输出。
> 所以它测不出稳定性，它测的是自洽——要测稳定，必须在干净环境里跑。**
