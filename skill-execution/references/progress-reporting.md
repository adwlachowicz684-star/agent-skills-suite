# 长任务的进度报告

> 一个跑了 20 步的技能，中途什么都不说，
> ⭐ 用户无法判断它是在正常工作还是卡住了。

## 为什么需要中间输出

两类失败都源于"沉默"：

```
① 用户以为卡住了，中途打断
   ——其实它在正常工作

② 它早就跑偏了，但用户不知道
   ——直到最后拿到错误结果
```

> ⭐ **第二种更贵**：早一点暴露偏差，代价小得多。

## 三条节奏规则

**① 按阶段报，不按步骤报**

```
❌ 每执行一个子步骤都输出一次   —— 太吵
✅ 每完成一个阶段输出一次
```

判据：**这一步的产出对用户有意义吗？**
"读取了文件"没意义，"解析完成，共 47 条记录"有意义。

**② 长操作前先说明要做什么**

```
✅ "接下来会用 gh pr diff 拉取完整 diff（约 30 秒）"
```

让用户知道**等待是预期的**。

**③ ⭐ 状态变化时立即报**

```
· 走了回退路径
· 触发了升级条件
· 超过了预期时间
```

> ⭐ **"静默降级"是最坏的一种沉默**——
> 用户以为走的是主路径，实际拿到的是降级结果。

## 报告该含什么

```
① 当前在哪个阶段（第 3/7 阶段）
② ⭐ 这一步产出了什么（可观察的结果）
③ 与预期的偏差（如果有）
④ 下一步要做什么
```

示例：

```
[2/5] 解析完成：47 条记录，其中 3 条缺字段（已标记为跳过）
      下一步：对 44 条完整记录做校验
```

注意它**主动报了 3 条缺字段**——
这就是偏差，早报比晚报好。

## 不该含什么

```
❌ 完整的中间产物（会污染上下文）
❌ 工具调用的原始输出
❌ ⭐ 每一步的内心独白
```

判据：**这条信息会改变用户接下来的决策吗？**
不会 → 不输出。

> ⭐ 长任务里，中间输出本身也是上下文成本。
> **"让用户安心"和"不浪费上下文"之间要取平衡**——
> 做法是**报状态和偏差，不报过程**。

## 与验证的关系

进度报告 ≠ 验证：

```
进度报告  告诉用户"在哪了"
验证      告诉用户"对不对"
```

但两者有个交集值得利用：

> ⭐ **每个阶段的报告里带上"这一步的验证结果"**，
> 就不需要单独再输出一份验证报告。

```
[3/5] 校验完成：44 条通过，0 条失败 ✅
```

一行同时完成了进度与验证。

## 自查

```
[ ] 阶段数在开头就说清楚了吗（第 N/M）？
[ ] ⭐ 走了回退/降级路径时会明确说出来吗？
[ ] 每个阶段报告都含可观察的产出？
[ ] ⭐ 偏差会在发生的那一刻报告，而不是最后汇总？
[ ] 长操作前有预告？
[ ] 中间输出没有包含完整产物或原始工具输出？
```

最后一条容易违反——**"我把中间结果打印出来方便调试"**
是长任务上下文爆炸的常见原因。
调试信息应该进日志，不进对话。
