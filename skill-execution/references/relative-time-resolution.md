## 1. ⭐⭐⭐⭐⭐ "最近"的基准在漂移

```
用户："分析最近一周的数据"
```

> ⭐⭐⭐⭐⭐ **"最近一周"是相对于谁的？**

三种都合理的解读：

```
① 相对于今天（运行日）
② 相对于数据里最后一条记录的时间
③ 相对于用户上一次分析覆盖到的时间点
```

> ⭐⭐⭐⭐⭐ 模型的默认动作是选 ①，
> ⭐⭐⭐⭐⭐ **而用户真正想要的常常是 ②或③**——
> 因为用户脑子里的"最近"是相对于他看到的数据，不是相对于日历。

---

## 2. ⭐⭐⭐⭐⭐ 它不会报错，只会静默换一批数据

这是最要紧的一点：

```
解析错 → 时间窗口错
→ ⭐⭐⭐⭐⭐ 查询成功返回，数据量正常，格式正确
→ ⭐⭐⭐⭐⭐ 只有内容是另一段时间的
```

> ⭐⭐⭐⭐⭐ 与"结构正确的废话"完全同构：
> 每一个环节都是成功的，⭐⭐⭐⭐⭐ **唯独答案对应的是另一个问题。**

而它的不可见性比别的失败更强：

```
数据缺失   → 结果为空，会被发现
字段名错   → 可能报错
⭐⭐⭐⭐⭐ 时间窗口错 → ⭐⭐⭐⭐⭐ 有结果、有数字、有趋势，全都是另一个时段的
```

> ⭐⭐⭐⭐⭐ 用户会拿这份结果去做决策，
> ⭐⭐⭐⭐⭐ **而没有任何东西会告诉他这份结果讲的是上个月。**

## 3. ⭐⭐⭐⭐⭐ 解析规则：一次算清，写进输出

两条硬规则：

**规则一 ⭐⭐⭐⭐⭐ 相对时间必须在执行开始时解析成绝对区间**

```markdown
## 前置
1. ⭐⭐⭐⭐⭐ 把输入中的相对时间解析为绝对区间（起止日期，含时区）
2. ⭐⭐⭐⭐⭐ 把解析结果写进输出的显眼位置
```

**规则二 ⭐⭐⭐⭐⭐ 把解析结果写进输出（不是写在思考里）**

```
❌ （内部算出 2026-09-22 ~ 2026-09-29，输出里没提）
✅ ⭐⭐⭐⭐⭐ 输出首行："统计区间：2026-09-22 ~ 2026-09-29（共 7 天）"
```

> ⭐⭐⭐⭐⭐ 第二条是本份最实用的一条，理由与 `decision-rationale-output.md`
> 那句"写了依据的输出，排错时不需要重跑"完全相同：
> ⭐⭐⭐⭐⭐ **时间窗口错了，看一眼输出首行就知道；不写，就得重跑一遍才知道。**

成本对比：

```
一行输出 ≈ 10 token
覆盖：⭐⭐⭐⭐⭐ 一次静默的时段错误（可能导向一个错误决策）
```

## 4. ⭐⭐⭐⭐⭐ 三类高危相对时间

**① ⭐⭐⭐⭐⭐ "最近 / 近期 / 这段时间"** —— 没有长度，也没有起点

```
"最近的数据" → 3 天？7 天？30 天？
```

> ⭐⭐⭐⭐⭐ 这一类必须追问或直接给默认值并标出。
> ⭐⭐⭐⭐ 推荐做法：**给默认值 + 在输出里标注"未指定，默认取 7 天"**——
> 这比追问便宜，且⭐⭐⭐⭐⭐ 标注让默认值变成可见的事实。

**② ⭐⭐⭐⭐⭐ "上周 / 上月 / 本季度"** —— 边界有歧义

```
"上周" = 周一到周日？还是过去 7 天？
"上月" = 自然月？还是过去 30 天？
```

> ⭐⭐⭐⭐⭐ 判据很简单：**自然周期 vs 滚动窗口，两者相差可达 40%**。
> 模型默认取自然周期，而很多业务系统按滚动窗口统计。

**③ ⭐⭐⭐⭐⭐ "之后 / 以来 / 从 X 开始"** —— 有起点无终点

```
"3 月以来" → 到什么时候为止？
```

> ⭐⭐⭐⭐ 这一类通常终点是"现在"，而⭐⭐⭐⭐⭐ **"现在"在数据里
> 往往不等于"今天"**——数据可能只到两天前。
> ⭐⭐⭐⭐⭐ 于是"3 月以来实际只到 9 月 27 日"，而输出不会说。

## 5. ⭐⭐⭐⭐⭐ 时区与"今天"属于谁

一个容易被忽略的分岔：

```
⭐⭐⭐⭐⭐ "今天"是谁的今天？运行者的？数据所属业务的？还是服务器 UTC 的？
```

三种都出现过，且差别不是理论上的：

```
UTC 与本地相差 8 小时
→ ⭐⭐⭐⭐⭐ "今天"涵盖的记录可能完全不同
→ ⭐⭐⭐⭐⭐ 在日切附近（如 00:00–08:00）运行时，差别是整整一天
```

写法（简短，但必须有）：

```markdown
- ⭐⭐⭐⭐⭐ 所有日期按 <业务时区> 解析；不确定的区间按"含左不含右"处理
```

> ⭐⭐⭐⭐⭐ 第二句同样重要：**区间端点开闭没写，
> 模型会自己定，而两种定法会差一天的数据。**

## 6. ⭐⭐⭐⭐ 会话内一致性与重跑

两条衍生纪律：

**① ⭐⭐⭐⭐⭐ 同一会话内，相对时间只解析一次**

```
用户在第 5 轮又提到"最近"
→ ⭐⭐⭐⭐⭐ 沿用第 1 轮算出的区间，不要重新解析
```

> ⭐⭐⭐⭐⭐ 否则同一份报告里的两处"最近"会指向不同区间，
> ⭐⭐⭐⭐ 而这在输出里完全看不出来（两处都不写区间）。

**② ⭐⭐⭐⭐⭐ 重跑是检验解析是否正确的最快方法**

```
隔一天重跑同一条指令
→ 结果变了？→ ⭐⭐⭐⭐⭐ 时间窗口是相对"运行时刻"算的
→ 结果没变？→ ⭐⭐⭐⭐⭐ 是相对数据算的，或已被缓存
```

> ⭐⭐⭐⭐⭐ 这不需要分析代码，⭐⭐⭐⭐ 也不需要跑 eval——
> 等一天，再跑一次，看结果是否漂移。
> ⭐⭐⭐⭐⭐ 这正是"同一输入跑 3 次"那个思路在时间维度上的对应物。

## 7. ⭐⭐⭐⭐ 自检

写完技能后逐条问：

```
① ⭐⭐⭐⭐⭐ 输入里可能出现哪些相对时间？（最近 / 上周 / 以来）
② ⭐⭐⭐⭐⭐ 每个都有解析规则吗？
③ ⭐⭐⭐⭐⭐ 解析结果会写进输出吗？
④ ⭐⭐⭐⭐ 时区写了吗？
⑤ ⭐⭐⭐⭐ 区间端点开闭写了吗？
```

> ⭐⭐⭐⭐⭐ 第 ③ 条最常被省，也最便宜：
> 它是⭐⭐⭐⭐⭐ 唯一一条"错了能立刻看见"的防线。
> 前四条都是在防止出错，第③条是在让错误可见——
> ⭐⭐⭐⭐⭐ **而对静默失败，可见性比正确性更值得优先投入。**

---

## 一句可贴在墙上

> ⭐⭐⭐ **时间窗口错了，查询会成功、数据会返回、格式会正确——
> 只有答案讲的是另一个时段。所以把解析结果写进输出首行，
> 那一行让你不用重跑就能发现它。**
