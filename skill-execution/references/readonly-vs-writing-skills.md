## 1. ⭐⭐⭐⭐⭐ 一个没被显式做出的选择

写技能时几乎没人先问：

```
这个技能会不会改变外部世界的状态？
```

于是大量技能是**隐式混合**的：主体是分析（只读），
但顺手写了个文件、发了个请求、改了个配置。

> ⭐⭐⭐⭐ **后果是：你用只读技能的写法去写了一个写入技能。**
> 而只读写法的所有简化（不用查状态、不用幂等、失败重跑即可）
> 在写入场景下**每一个都是缺陷**。

---

## 2. ⭐⭐⭐⭐ 对比表

| 维度 | 只读技能 | ⭐ 写入技能 |
|---|---|---|
| 失败后 | ⭐ 从头重跑，无副作用 | ⭐⭐⭐ 必须先查状态 |
| 重复运行 | 无害 | ⭐⭐⭐ 可能重复创建/重复写入 |
| 并发 | 通常安全 | ⭐⭐⭐ 需准入条件（见 `skill-execution/references/parallel-and-concurrency.md`） |
| 权限 | 读即可 | ⭐⭐⭐ 最小权限 + 人工确认门槛 |
| 验证 | 看输出对不对 | ⭐⭐⭐ **看环境状态对不对** |
| 撤销 | 不需要 | ⭐⭐⭐ 必须有回滚路径 |

> ⭐⭐⭐⭐ 第五行最容易被漏，也最有价值——
> 它和 `skill-evaluating/references/assert-on-environment.md` 是同一条：
> **只读技能可以断言"输出里说了什么"，写入技能必须断言"世界变成了什么样"。**

## 3. ⭐⭐⭐⭐⭐ 写入技能多出来的四件事

只读技能只需要"读取 → 处理 → 输出"。写入技能多四件事：

**① ⭐⭐⭐⭐⭐ 行动前先查状态**

```
❌ "创建报表文件"
✅ "先检查报表文件是否存在；存在则读取并报告，不覆盖"
```

**② ⭐⭐⭐⭐⭐ 幂等键**

```
⭐ 每次写入要有一个可判定的"这次已经做过了吗"
   同一幂等键 → 跳过或更新，不重复创建
```

**③ ⭐⭐⭐⭐ 部分失败的记录**

```
写 A 成功、写 B 失败
→ ⭐⭐⭐ 必须记录 A 已写，否则重跑会重复写 A
```

> ⭐⭐⭐ 这一条在串行里是加分项，在并行里是准入条件——
> 因为并行失败必然留下部分写入。

**④ ⭐⭐⭐⭐ 回滚路径**

```
⭐⭐⭐ 没有回滚路径的写入技能，不该进入生产
```

配一条我们已有的硬规则：**删除 / push / 部署必须设人工确认门槛**
——"先输出命令清单，确认后再执行"。

## 4. ⭐⭐⭐⭐ 混合技能：最危险的一类

```
"分析代码并修复发现的问题"
```

> ⭐⭐⭐⭐⭐ **这是最危险的形状**，因为：
> ⭐⭐ **它的只读部分会让人放松警惕**——
> 用户以为自己在"看分析"，其实它在改文件。

三个具体的失效：

| 失效 | 机制 |
|---|---|
| ⭐ 用户没预期会被改 | 只读的信任被借用了 |
| ⭐⭐ 分析错了就改错了 | 只读阶段的错误被写死了 |
| ⭐⭐⭐ 无法只跑只读部分 | 想"只看不改"时做不到 |

> ⭐⭐⭐⭐ **解法：拆成两个技能，或用参数显式的 `--dry-run` 默认开。**
> 而默认必须是 dry-run——
> 因为"默认写"意味着每次想看一眼都得记得加参数。

判据一句话：**如果用户会在没有备份的情况下运行它，它就不该默认写。**

## 5. ⭐⭐⭐⭐ 幂等的三个层次

不是所有幂等都一样，按强度排：

| 层次 | 含义 | 适用 |
|---|---|---|
| ⭐ 天然幂等 | 写什么都是同一个结果（覆盖写） | 配置文件、状态更新 |
| ⭐⭐ 幂等键幂等 | 同键跳过 | 创建类操作 |
| ⭐⭐⭐ 补偿幂等 | 靠回滚/撤销实现 | ⭐ 发送类（邮件、消息）不可撤销 |

> ⭐⭐⭐ **第三层是硬约束：不可撤销的写入必须有预发送确认。**
> 因为它没有 undo，所以唯一的防线是"发之前让人看一眼"。

这与 `skill-security/references/allowed-tools-least-privilege.md` 的权限分级是配套的：
**权限决定它能做什么，幂等层次决定做错了能不能收回。**
两者都不该靠"模型会小心"。

## 6. ⭐⭐⭐ 边界：什么叫"写入"

几个容易误判的：

| 动作 | 算写入吗 | 为什么 |
|---|---|---|
| 读文件 | ❌ | — |
| ⭐ 写临时文件 | ⭐ 算 | 会覆盖别人的临时文件 |
| ⭐ 发 HTTP GET | ❌（通常） | 但 GET 也可能有副作用（日志、计数） |
| ⭐⭐ 调 webhook | ⭐⭐⭐ 算，且不可撤销 | 第三方会收到 |
| 改数据库 | ⭐⭐⭐ 算 | — |
| ⭐ 发通知/邮件 | ⭐⭐⭐⭐ 算，且最危险 | ⭐ 不可撤销 + 外部可见 |

> ⭐⭐⭐ 最容易被漏的是"发通知"。
> 它看起来只是"告诉你结果"，
> 但**它是唯一一个错误会跑到组织外部、且无法收回的动作**。

判据：**这个动作的影响在本次会话结束之后还存续吗？** 是 → 写入。

## 7. ⭐⭐⭐ 一张检查表

写入技能发布前，六条全过：

```
1. 有"行动前查状态"的步骤吗？
2. 有幂等键吗？重复运行会怎样？
3. ⭐ 部分失败时记录了已完成的部分吗？
4. ⭐⭐ 有回滚路径吗？不可撤销的有预发送确认吗？
5. ⭐⭐⭐ 断言打在环境状态上吗（不是打在输出文本上）？
6. ⭐⭐⭐ 权限是最小集吗？有人工确认门槛吗？
```

> ⭐⭐⭐ **第 5 条是最容易伪装的一条**：
> 输出里写"文件已创建"不算——要真的去查文件在不在。
