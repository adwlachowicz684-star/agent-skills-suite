## 1. ⭐⭐⭐⭐⭐ 一句永远通过的检查

```markdown
输出前，检查是否覆盖了所有重要方面
```

> ⭐⭐⭐⭐⭐ 这句话从未阻止过任何一份糟糕的输出。
> ⭐⭐⭐⭐⭐ 它每次都通过——因为它是**在已经写好的文本上**执行的。

这是本份的起点：**验证的对象决定了验证有没有意义。**

---

## 2. ⭐⭐⭐⭐⭐ 三种失效，第二种最常见

**① ⭐⭐⭐⭐ 验证被跳过**（见 `skill-execution/references/partial-following.md`）

**② ⭐⭐⭐⭐⭐ 验证在自己刚生成的内容上做**（最常见）

```
生成报告 → 检查报告是否完整 → 完整
```

> ⭐⭐⭐⭐⭐ 它检查的是"我写的东西读起来是不是完整"，
> ⭐⭐⭐⭐⭐ 而不是"该有的东西是不是都在"。
> ⭐⭐⭐⭐⭐ 这两件事在文本层无法区分。

**③ ⭐⭐⭐⭐⭐ 验证标准不可判定**

```
❌ "检查是否准确"
✅ ⭐⭐⭐⭐⭐ "检查每行金额之和是否等于总计（容差 0.01）"
```

> ⭐⭐⭐⭐⭐ 第 ③ 种与《skill-crafting》的 `skill-precision/references/vague-word-blacklist.md` 同源，
> ⭐⭐⭐⭐⭐ 但后果更严重：含糊词在流程里只是执行不准，
> ⭐⭐⭐⭐⭐ 含糊词在验证里会**产生一个假的通过信号**。

---

## 3. ⭐⭐⭐⭐⭐ 为什么"自检"天然倾向于通过

三条机制叠加：

**① ⭐⭐⭐⭐⭐ 自洽性偏见**

```
输出说"共 12 项"，正文列了 12 项
→ 检查"数量是否一致" → 通过
→ ⭐⭐⭐⭐⭐ 而实际有 15 项，第 13–15 项从未被列出过
```

> ⭐⭐⭐⭐⭐ 一致性检查只能发现**内部矛盾**，
> ⭐⭐⭐⭐⭐ 发现不了**整体缺失**——缺失的东西不产生矛盾。

**② ⭐⭐⭐⭐⭐ 完成倾向**

```
按《skill-content》的 `skill-content/references/default-actions.md`：
⭐⭐⭐⭐⭐ 遇到阻碍时默认动作不是停下报告，而是想办法绕过去
→ 验证遇到"不确定"时，默认给"通过"
```

**③ ⭐⭐⭐⭐⭐ 检查发生在生成之后，此时修改成本已高**

```
写完了 40 行 → 发现第 3 行有问题 → 要重写
⭐⭐⭐⭐⭐ 而"没发现问题"是不需要付出任何成本的选项
```

> ⭐⭐⭐⭐⭐ 注意这不是模型在偷懒：⭐⭐⭐⭐ 它真的检查了，
> ⭐⭐⭐⭐⭐ 只是在一个"通过"和"推翻自己"不对称的局面下检查。

## 4. ⭐⭐⭐⭐⭐ 判据：验证对象必须独立于被验证的东西

这是本份唯一的判据，一句话：

> ⭐⭐⭐⭐⭐ **验证所依据的信息，是否来自输出之外？**

```
❌ "检查报告是否完整"              ← 依据 = 报告自身
✅ ⭐⭐⭐⭐⭐ "检查报告中的条目数是否等于第 2 步清单的长度"
                                     ← 依据 = 另一个产物
```

判据的操作形式：

> ⭐⭐⭐⭐⭐ **能不能删掉输出，仍然执行这个验证？**
> 能 → 验证是独立的；不能 → 它是自我确认。

三种独立来源，可靠性递减：

```
① ⭐⭐⭐⭐⭐ 可数的分母（清单长度、文件数）  — 最可靠
② ⭐⭐⭐⭐ 外部真值（API 返回、schema）      — 可靠
③ ⭐⭐⭐ 另一份产物（上游输出、中间文件）    — 可靠但可能同源
```

> ⭐⭐⭐⭐⭐ 第 ① 条正是 `skill-output/references/enumeration-and-completeness.md` 的核心：
> ⭐⭐⭐⭐⭐ **没有分母，所谓的"完整"只是一个感觉。**

## 5. ⭐⭐⭐⭐⭐ 修法一：把验证改成可判定的检查

对照表（左侧永远通过，右侧可能失败）：

| 永远通过 | ⭐⭐⭐⭐⭐ 可判定 |
|---|---|
| "检查是否完整" | "条目数 == 第 2 步清单长度，不等则列出缺失项" |
| "检查是否准确" | "总额 == 各行之和（容差 0.01）" |
| "检查格式是否正确" | "可被 `json.loads` 解析，且含 `items` 键" |
| "检查是否有遗漏" | ⭐⭐⭐⭐⭐ "遍历目录，未出现在 `processed` 中的文件列出" |

> ⭐⭐⭐⭐⭐ 关键差别不在措辞，在⭐⭐⭐⭐⭐ **有没有一个可以失败的对照物**。
> ⭐⭐⭐⭐⭐ 一条"不可能失败"的检查，不是保守，是无效。

这与《skill-evaluating》的"baseline 会不会也通过？会就毫无价值"完全同构：
**验证和断言的失效方式是同一个。**

## 6. ⭐⭐⭐⭐⭐ 修法二：验证失败必须改变输出

```
✅ 验证
❌ 验证；若不通过，输出中必须包含"未通过项：<列表>"
```

> ⭐⭐⭐⭐⭐ 前者允许模型用"已验证通过"结束；
> ⭐⭐⭐⭐⭐ 后者要求它**具体说明哪一项没通过**——而这很难编。

成本约 15 token，收益是把"通过"变成一个**需要举证的状态**。

三条配套：

```
① ⭐⭐⭐⭐⭐ 不通过时不得静默修正后继续（要报告，否则你永远不知道它改了什么）
② ⭐⭐⭐⭐⭐ 部分通过必须报覆盖率（"8/12 通过"）
③ ⭐⭐⭐⭐⭐ "未获取"不等于"通过"——不可判定的项状态是 unknown，不是 pass
```

> ⭐⭐⭐⭐⭐ 第 ③ 条最常被违反：⭐⭐⭐⭐ 一项检查没做成，
> ⭐⭐⭐⭐⭐ 模型会把它当成"没发现问题"，于是 unknown 被写成 pass。
> 这正是《skill-input》的 `skill-input/references/inference-vs-asking.md` 里"0 与未获取"的翻版。

## 7. ⭐⭐⭐⭐⭐ 修法三：让验证发生在生成之前

这是三种修法里最根本的，但最常被忽略：

```
❌ 生成报告 → 检查报告
✅ ⭐⭐⭐⭐⭐ 清点清单（独立步骤）→ 生成报告 → 检查条目数 == 清单长度
```

> ⭐⭐⭐⭐⭐ 差别在于：⭐⭐⭐⭐⭐ **先有分母，再写内容，最后比对**。
> 而"生成完再检查"时，分母是从产物里数出来的——它必然等于自己。

这与 `skill-authoring/references/output-contract-first-order.md` 的排序原则咬合：
⭐⭐⭐⭐⭐ **输出契约先定，验证才有可比对的对象；
验证先定，生成才知道要满足什么。**

一个便宜的做法：**把清单写进中间文件**（`skill-execution/references/partial-following.md` 的成名手法），
验证时读文件比对，而不是读自己的输出。

## 8. ⭐⭐⭐⭐⭐ 自检

对技能里的每一处"检查/验证/确认"：

```
① ⭐⭐⭐⭐⭐ 删掉输出，这条验证还能执行吗？（不能 → 自我确认）
② ⭐⭐⭐⭐⭐ 它有没有可能失败？（不可能 → 无效）
③ ⭐⭐⭐⭐⭐ 失败时输出会变吗？（不变 → 等于没写）
④ ⭐⭐⭐⭐⭐ 不可判定的项是写成 unknown 还是 pass？（写成 pass 是 bug）
```

一个十秒判断：

> ⭐⭐⭐⭐⭐ **把技能里所有"检查"都删掉，跑一次。
> 输出有任何不同吗？
> 没有 → 那些检查一条都没在起作用，而它们一直给你"已验证"的安全感。**

---

## 一句可贴在墙上

> ⭐⭐⭐ **一条不可能失败的检查不是保守，是无效。
> 而"生成完再检查自己写的东西"，检查的只是自洽，不是完整。**
