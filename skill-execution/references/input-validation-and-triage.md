## 1. ⭐⭐⭐⭐⭐ 三类问题输入

| 类型 | 例子 | ⭐⭐⭐⭐⭐ 默认动作（模型会做什么） |
|---|---|---|
| ⭐⭐⭐⭐⭐ **残缺** | "分析一下" （没说分析什么） | 猜一个范围，继续 |
| ⭐⭐⭐⭐⭐ **矛盾** | "要简洁，但把所有细节都写上" | ⭐⭐⭐⭐⭐ 悄悄选一个，不告知 |
| ⭐⭐⭐⭐ **超范围** | 用 A 技能处理 B 领域的事 | ⭐⭐⭐⭐ 尽力做，产出不可用但不报错 |

> ⭐⭐⭐⭐⭐ **三类的默认动作是同一个：继续。**
> 而"继续"在这里意味着⭐⭐⭐⭐⭐ **用自己的先验补齐缺失的部分**。

这与默认动作那份完全同构，但有一个关键差别：

> ⭐⭐⭐⭐⭐ **残缺输入是最常见的一类，而且它发生在任务的最开始——
> 于是它污染的是后面所有步骤。**
> 猜错一个范围，之后每一步都是在错误范围上做的正确工作。

## 2. ⭐⭐⭐⭐⭐ 缺什么就说缺什么

错误写法：

```markdown
## 输入
- 用户提供的分析范围
```

> ⭐⭐⭐⭐⭐ 这不算输入声明——⭐⭐⭐⭐⭐ 它只声明了"有个东西叫分析范围"，
> 没说缺失时怎么办。

正确写法要带上缺失分支：

```markdown
## 输入
- 分析范围（必需）
  ⭐⭐⭐⭐⭐ 缺失时：停止，问"要分析哪个时间段/哪个模块？"
  ⭐⭐⭐⭐⭐ 不要：默认全量（代价不可控）或默认最近一周（猜的）
```

> ⭐⭐⭐⭐⭐ 中间那句"不要"是关键。
> 只写"缺失时提问"，模型仍可能为了完成而选一个默认值——
> ⭐⭐⭐⭐⭐ 因为"提问"和"继续"之间，它倾向于继续。
> **显式写"不要默认 X"，才是把那条路封死。**

（这与 `conditional-branch-writing.md` 的"没有 else 的 if"是同一条规则，
只是那份讲流程分支，这份讲输入字段。）

一个廉价的高收益做法：

> ⭐⭐⭐⭐⭐ **把必需输入列成一张表，每行带"缺失时"一列。**
> 三行表格，覆盖的是⭐⭐⭐⭐⭐ 每一次用户没说全的情况——
> 而"没说全"是真实使用里的常态，不是例外。

## 3. ⭐⭐⭐⭐⭐ 矛盾输入：不要选一个

```
"要简洁，但把所有细节都写上"
```

> ⭐⭐⭐⭐⭐ **模型的默认动作是选一个，而且不告诉你它选了哪个。**

这比猜范围更危险，因为⭐⭐⭐⭐⭐ **用户明确表达过两个需求，
而其中一个被静默丢弃了**——用户会以为两个都满足了。

正确写法：

```markdown
- ⭐⭐⭐⭐⭐ 输入内部矛盾时：指出矛盾，让用户选择，不要自行取舍
- ⭐⭐⭐⭐ 若用户未回应：按 [默认档] 执行，并在输出的显眼位置标注
  "已按 X 处理，另一项需求 Y 未满足"
```

> ⭐⭐⭐⭐⭐ 第二行的"标注"是这份最值钱的一条：
> ⭐⭐⭐⭐⭐ **被丢弃的需求必须出现在输出里。**
> 否则它就从对话里彻底消失了——用户不记得自己提过，就不会追问。

这与 `human-checkpoint-design.md` 那条
"已完成的写入动作必须报告"是同一原则：
**任何被静默处理掉的东西，都必须在输出里留痕。**

## 4. ⭐⭐⭐⭐ 超范围输入：不是"尽力做"

```
用 code-review 技能去评审一份产品设计文档
```

> ⭐⭐⭐⭐⭐ 这不是"技能能不能做"的问题，
> 是⭐⭐⭐⭐⭐ **它会做，而且产出的东西看起来是评审意见**。

三种常见的超范围：

| 类型 | ⭐ 表现 |
|---|---|
| ⭐⭐⭐⭐ 领域超范围 | 用 A 领域的技能处理 B 领域 |
| ⭐⭐⭐⭐ 规模超范围 | 技能假设 10 个文件，来了 500 个 |
| ⭐⭐⭐⭐⭐ 抽象层级超范围 | 要"战略判断"，技能只写到了"战术步骤" |

> ⭐⭐⭐⭐⭐ 第三种最隐蔽：技能确实在这个领域，
> 但用户要的东西在更高的抽象层——
> ⭐⭐⭐⭐ 于是它产出一堆正确的战术细节，而用户要的那个判断一个字都没有。
> 这和"只定义怎么开始"那份的失败形状很像，成因不同。

修法（一段即可）：

```markdown
## 不适用（明确列出）
- 不适用于 [领域 B]，原因是 [具体原因]
- 遇到时：说明不适用，并指出 [该用什么]，不要尝试适配
```

> ⭐⭐⭐⭐⭐ 最后半句"不要尝试适配"必须写——
> 不写的话，模型会"好心"地改造流程去覆盖它，
> ⭐⭐⭐⭐⭐ 而适配出来的东西既不在你的测试范围内，也没有验收标准。

## 5. ⭐⭐⭐⭐⭐ 分诊顺序

收到输入后按这个顺序判，**先判超范围**：

```
① ⭐⭐⭐⭐⭐ 超范围？→ 说明不适用并指出该用什么（最优先）
② ⭐⭐⭐⭐⭐ 矛盾？  → 指出矛盾让用户选（不要自行取舍）
③ ⭐⭐⭐⭐⭐ 残缺？  → ⭐⭐⭐⭐⭐ 一次性问完所有缺失项（不要问一个补一个）
④ 合格           → 继续
```

> ⭐⭐⭐⭐⭐ 第 ① 步最优先的理由：
> 如果领域都不对，后面两步的判断是浪费——
> 而且⭐⭐⭐⭐ 在错误领域里做分诊，会问出一堆无关的问题。

第 ③ 步的"一次性问完"值得单独强调：

> ⭐⭐⭐⭐⭐ **问一个补一个，是最消耗用户耐心的形态。**
> 它把"缺 3 项"变成 3 轮对话，而每一轮用户都要重新进入上下文。
>
> ⭐⭐⭐⭐ 而且它与 `change-questions.md` 的"同一任务内只问一次"是互补的：
> 那份禁止⭐⭐⭐ **重复问同一个问题**，
> 这份要求⭐⭐⭐⭐⭐ **不同问题要一次问完**——
> 合起来是：**一个任务，一轮提问，之后不再问。**

## 6. ⭐⭐⭐⭐⭐ 为什么这一步值得单列

一个反直觉的成本论证：

```
输入分诊的代码：约 10 行 / 不到 150 token
它覆盖的时刻：  ⭐⭐⭐⭐⭐ 每一次调用的开始
```

而跳过它的代价是⭐⭐⭐⭐⭐ **污染整条执行链**：

```
猜错范围 → 每一步都是在错误范围上做的正确工作
→ ⭐⭐⭐⭐⭐ 每一步单独看都没错
→ 最终输出格式正确、内容错
→ ⭐⭐⭐⭐⭐ 这是"结构正确的废话"最主要的成因之一
```

> ⭐⭐⭐⭐⭐ 这是"结构正确的废话"的第八个来源，
> 也是⭐⭐⭐⭐⭐ 唯一一个可以在第一句话就拦住的。

还有一个理由：

> ⭐⭐⭐⭐⭐ **输入分诊是唯一一个"用户能感知到"的质量环节。**
> 输出格式、上下文成本、分支穷尽，用户都看不见；
> ⭐⭐⭐⭐⭐ **但"它问我缺什么"和"它自作主张猜了一个"，用户的感受完全不同。**
