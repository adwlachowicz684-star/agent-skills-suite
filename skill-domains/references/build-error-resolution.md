# 构建错误定位与修复

> 构建/编译错误是"信号明确但容易被瞎改"的场景。
> 技能要做的是**禁止猜测式修改**。

## 先读完整错误

> ⭐ **不要只读第一行。**

```
□ ⭐ 编译/构建错误常有多条——第一条不一定是根因
□ ⭐ 级联错误：修好第一个，后面五个可能一起消失
□ ⭐ 用 --verbose / 完整输出，而不是被截断的摘要
```

**一条实用规则**：

```
□ ⭐ 从最后一条错误往前看
   ——某些工具链把根因放在最后
```

## 定位顺序

```
1. ⭐ 确认能稳定复现（命令 + 参数固定）
2. ⭐ 确认改动范围——"上一次能构建"和现在的差别是什么
3. ⭐ 读完整错误输出，定位到文件:行
4. 判断是配置问题、依赖问题还是代码问题
5. ⭐ 一次只改一处，改完立刻验证
```

> ⭐ 第 5 条最关键：
> **同时改三处，修好了也不知道是哪处修的，
> 而那三处里可能有一处是不必要的破坏性改动。**

呼应 `refine-with-execution.md`（**`skill-refining`**）：
**每次只改 1–2 个变量——否则无法归因**。

## 四类常见根因

| 类别 | 症状 | 定位 |
|---|---|---|
| **依赖** | 找不到模块、版本冲突 | ⭐ 看 lockfile 与依赖树 |
| **配置** | 路径不对、环境变量缺失 | ⭐ 对比能构建的环境 |
| **代码** | 类型错误、语法错误 | 文件:行直接定位 |
| **工具链** | 版本不匹配、缓存脏 | ⭐ 清缓存、核对版本 |

**工具链类的特殊处理**：

```
□ ⭐ 清缓存是最容易被跳过、也最常有效的一步
□ ⭐ 但要先确认不是代码问题——无脑清缓存会掩盖真问题
```

## 禁止的做法

```
❌ ⭐ 不看完整错误就改代码
❌ ⭐ 同时改多处
❌ ⭐ 降级依赖来"解决"版本冲突
   ——除非明确记录这是临时方案且有跟进项
❌ ⭐ 加 // @ts-ignore / # type: ignore 绕过类型错误
   ——除非写明为什么，且这是唯一可行路径
❌ 删除失败的测试让它通过
❌ ⭐ 改 CI 配置让失败的步骤不再运行
```

> ⭐ 最后两条是"让红灯变绿"的两种典型作弊，
> 必须显式禁止。
>
> 呼应 `grounding-verification.md`（**`skill-crafting`**）：
> **表面合规是最危险的失败模式**。

## 修完的验证

```
□ ⭐ 完整构建通过（不是只跑刚才失败的那一步）
□ ⭐ 测试通过
□ ⭐ 说明改了什么、为什么这样改能解决问题
□ ⭐ 如果用了临时方案，记录跟进项
```

**"为什么这样改能解决"这一条很重要**：

```
❌ "改了之后能构建了"
✅ "根因是 X 依赖升级后 API 变了；
    调用点从 a() 改为 b()，签名差异见…"
```

呼应 `debugging-recovery.md`（**（领域实例库·已归档）**）的
**根因已定位 + 5 Whys 已完成**——
动手前要说明白为什么。
