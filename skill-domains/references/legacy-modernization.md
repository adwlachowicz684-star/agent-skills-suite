# 遗留系统迁移类技能

> ⭐ **一句话定位**：
> **把"大泥球"架构改造成干净、现代、高性能的系统——同时不破坏已有的业务价值。**

## 五阶段工作流

```
1. 评估        量化技术债，建立迁移路线图
2. 稳定核心    ⭐ 先修遗留系统的关键 bug，再谈迁移
3. 建安全网    特征化测试 + 监控
4. 抽取        用绞杀者模式，一次挪一个特性
5. 影子测试    对比遗留与新版的输出
6. 全量切换    切全部流量，删除遗留代码
```

**每阶段都有验证检查点**（这是这类技能的骨架）：

```
阶段 2  □ 每个阶段都有明确的回滚触发条件与责任人
阶段 3  ⭐ 在未经修改的遗留系统上跑特征化测试，确认全绿才能继续
阶段 4  ⭐ 每次流量递增后验证错误率与延迟仍在基线内
          （如 5% → 25% → 50% → 100%）
阶段 6  ⭐ 新代码必须在 100% 流量下稳定至少一个发布周期
       才能移除遗留路径
```

> ⭐ **"先修关键 bug 再迁移"这条反直觉**——
> 带着已知故障迁移，你会分不清问题是新的还是旧的。

## 安全网先行：特征化测试

> ⭐ **核心策略"测试先行"**：
> **在改任何代码之前，先为现有行为写测试。**

```
□ 特征化测试（characterization test）
  把现有行为捕获成"黄金母版"安全网
□ ⭐ 目标：现有行为覆盖率 80%+
□ ⭐ 关键：在未经修改的遗留系统上先跑通全绿
```

**特征化测试的样子**：

```python
@pytest.mark.parametrize("order_id,expected_status", [
    ("ORD-001", "SHIPPED"),
    ("ORD-002", "PENDING"),
    ("ORD-003", "CANCELLED"),
])
def test_order_status_golden_master(order_id, expected_status):
    """⭐ 若遗留行为意外改变，响亮失败。"""
    result = service.get_order(order_id)
    assert result.status == expected_status
```

> ⭐ **"响亮失败"**
> ——呼应 `testing-skills.md` 与 `skill-evaluating` 的 `trigger-debugging.md` 的边界校验。

## 绞杀者模式与特性开关

**绞杀者模式三步**：

```
1. 识别边界    找到清晰的服务或模块边界可供抽取
2. 代理层      ⭐ 用 API 网关或代理在旧新系统间路由流量
3. 增量抽取    ⭐ 一次挪一个特性，
               只有新的 100% 稳定后才让遗留部分下线
```

**Facade 示例**（按特性开关路由）：

```python
class OrderServiceFacade:
    def get_order(self, order_id):
        if flag_enabled("USE_NEW_ORDER_SERVICE"):
            return self._new.fetch(order_id)
        return self._legacy.get_order(order_id)
```

**依赖升级的正确姿势**：

```
□ 资产审计——盘点所有过时的第三方库
□ 破坏性变更——审查主版本跳跃的 changelog
□ ⭐ 逐级升级（v1 → v2 → v3），而不是一步跳
```

**代码迁移手段**：

```
□ 自动化重构——用 jscodeshift 之类做批量重命名或语法更新
□ 模式转换——Class 组件转 Hooks、jQuery 转原生 JS
□ ⭐ 类型引入——给 JS 项目增量加 TypeScript，
   在构建期逐步保证类型安全
```

**框架迁移类型**：

```
Angular → React/Vue   映射组件逻辑与状态管理
单体 → 微服务          把领域逻辑抽成独立服务
SSR → 流式            现代化数据获取模式
```

## 必须做 / 绝不做

> ⭐ **这类"MUST DO / MUST NOT DO"清单是迁移技能的主体**：

**必须做**：

```
□ 全程保持生产零中断
□ ⭐ 重构前建立全面测试覆盖（目标 80%+）
□ 所有增量发布都用特性开关
□ 实现监控与回滚程序
□ ⭐ 记录所有迁移决策及其理由
□ 保留现有业务逻辑与行为
□ 透明沟通进展与风险
```

**绝不做**：

```
□ ⭐ 大爆炸式重写或替换
□ ⭐ 改之前不测遗留行为
□ 没有回滚能力就部署
□ 破坏现有集成或 API
□ 在新代码里继续累积技术债
□ ⭐ 没有充分验证就赶进度
□ ⭐ 新代码被证明稳定之前就删除旧代码
```

> ⭐ 呼应 `skill-crafting` 的 `guidance-forms.md`：
> 这些**禁令都配了对应的正面做法**（特性开关、特征化测试、回滚能力），
> 不是光说"不要"。

## 六个常见错误

```
❌ 大爆炸式重写，而不是增量迁移
❌ ⭐ 没有覆盖现有行为的测试就重构
❌ ⭐ 所有消费者迁移完成前就移除向后兼容
❌ ⭐ 每个迁移阶段都不做回滚规划
❌ 忽略数据迁移的复杂性与状态同步
❌ 废弃时间表不让利益相关者参与
```

**几个额外的实践建议**：

```
□ 大型遗留代码库从哪开始？
  ⭐ 从"高价值 + 低风险"的模块入手，建立成功案例后再扩展
  优先：安全漏洞修复 · 阻塞业务的瓶颈 · 维护成本最高的模块
  ⭐ 每个迁移完成后复盘，优化流程再做下一批

□ 怎么保证重构不破坏现有功能？
  ⭐ 测试先行 + 持续跑测试 + 特性开关控制上线，出问题可快速回滚

□ 完全重写为什么风险高？
  ⭐ 容易丢失业务逻辑细节，且新系统可能产生新问题
```

**验证与稳定阶段**：

```
□ 跑全量回归套件
□ 审查监控仪表盘
□ ⭐ 确认业务行为被保留，才退役遗留代码
□ 视觉回归——确保重构后 UI 看起来完全一致
□ ⭐ 并排运行——在生产中对一部分用户同时跑两套系统
□ ⭐ 回滚策略——永远要有切回遗留系统的开关
```

> ⭐ **"并排运行"值得特别注意**——
> 它是影子测试的工程实现，也是"证明新代码稳定"的唯一可靠方式。
