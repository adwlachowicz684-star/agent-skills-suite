# AI 代码评审：信任层设计

> AI 评审 PR 的成熟形态不是"自动合并"，
> 是**一个分层的信任工作流**。这份讲怎么设计这一层。

## 不该做什么

> ⭐ **不要让 agent 自动合并代码**，
> 除非以下都已定义：仓库权限、token 作用域、
> 测试命令、回滚步骤、人工升级规则。

**五件明确不该做**：

```
❌ 静默批准架构决策
❌ 合并代码
❌ 改仓库设置
❌ 处理密钥
❌ 以上任何一项，除非被 scoped token +
   仓库策略 + 人工升级路径显式允许
```

## 能做 vs 不能做

```
✅ 能：读 PR、跑检查、汇总结论、写评审评论
❌ 不能：合并、发布、生产回滚——⭐ 这些权限归具名的人
```

> ⭐ **"agent 可以评论，不能合并"** 是整个设计的中心句。

**推广节奏**：

```
第一步：让 AI 先只写评审评论
第二步：⭐ 合并权保留在人类手里，直到证据质量稳定
```

呼应 `security-pipeline.md`（**`skill-orchestration`**）的
**基线感知质量门禁**——只对新引入的问题失败。

## 五层技能栈

一个完整的 AI 评审栈不是单一技能，是分层：

| 层 | 组件 | 作用 |
|---|---|---|
| 1 | **GitHub MCP** | ⭐ 基础：读 diff、文件、评论、PR 状态；发评论 |
| 2 | **Sentry MCP** | 生产错误关联——改的文件有没有正在报错 |
| 3 | 静态分析技能 | SonarQube / ESLint：代码异味、漏洞、覆盖率、重复 |
| 4 | 语义理解 | 综合以上信号，写出人能直接行动的评论 |
| 5 | ⭐ 人工批准门 | 架构与安全决策 |

**为什么 1 和 2 是 MCP 而不是技能**：

```
□ 需要连外部系统 → MCP（见 mcp-vs-skill-decision.md，
  **`skill-selection`**）
□ ⭐ 评论权限属于"需要用户授权"——技能没有 auth 概念
```

**技能负责的是 3–5**：机械检查、综合判断、批准门。

> 这正是"薄 server 提供访问 + 技能提供工作流"的实例。

## 证据要求

> ⭐ **每条发现都要有证据。**

```
❌ "这里可能有性能问题"
✅ "utils/parse.ts:42 在 10k 行输入下是 O(n²)；
    相关 Sentry 事件 1a2b3c 显示 p99 达 4.2s"
```

**可接受的证据来源**：

```
□ 改动的文件（file:line）
□ 失败的测试
□ lint 输出
□ ⭐ Sentry 事件
□ 依赖告警
□ 策略规则
```

**不可接受的**：

```
❌ "通常来说这样更好"
❌ "建议考虑重构"
❌ 任何不指向具体锚点的通用意见
```

呼应 `grounding-verification.md`（**`skill-crafting`**）：
**落地 = 把输出锚定到现实**。

也呼应 `security-pipeline.md` 的反幻觉验证：
**结论必须挂在一个可独立验证的锚点上**。

## Token scope 是安全边界

> ⭐ **先用"仓库读权限 + 评审评论权限"。**

**避免授予**：

```
❌ 宽泛的 write
❌ admin
❌ secret
❌ 部署
❌ 组织级作用域
```

> 呼应 `skill-structuring` 的 `frontmatter-fields.md`（**`skill-crafting`**）的
> `allowed-tools` 最小授权原则，与
> `sandbox-execution.md`（**`skill-governance`**）的按技能类型切片：
> **权限边界在工具层，不在提示词层。**

## 什么叫生产就绪

**上线前必须定义的五件事**：

```
□ 仓库权限
□ ⭐ token 作用域
□ 测试命令（评审要能真的跑测试）
□ ⭐ 回滚步骤
□ ⭐ 人工升级规则（什么情况必须人来）
```

**两个可衡量的收益**（用来判断要不要继续投入）：

```
1. 常规 PR 的合并时间变短
   机械问题在人工评审开始前就被发现并修掉
2. ⭐ 人工评审质量更高
   评审者到场时代码已经 lint-clean 且错误安全，
   可以专注在设计和产品正确性上
```

第 2 条常被低估——**AI 评审的价值不只在省时间，
更在于把人的注意力从格式挪到设计上**。
