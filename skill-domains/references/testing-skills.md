## 为什么 agent 需要测试技能

> 没有技能时，agent 会产出**能跑但不对味**的测试：

```
□ 文件命名错
□ 断言风格错
□ 分组策略错
□ ⭐ 漏掉你的团队真正在意的边界条件
```

> ⭐ **技能把团队的测试标准编码进去，
> agent 产出的测试能直接并入现有套件，不需要清理。**

---

## 必须编码进去的三件事

**① 框架检测**

```
□ 先查项目用的是 Jest / Vitest / Mocha / Pytest / Go testing / RSpec
□ 生成符合该框架的测试，不需要手动配置
```

**② 模式匹配**

```
□ 现有测试用 describe/it 还是 test()？沿用
□ 用 testing-library 的 screen 查询还是 Enzyme 的 wrapper？沿用
□ ⭐ 落在 SKILL.md 里就是：
   "读现有测试文件，沿用其结构、命名与断言风格"
```

**③ 边界覆盖**

> ⭐ **通用 agent 只测 happy path。好的测试技能明确要求测**：

```
□ null / undefined 输入
□ 空数组
□ 边界值（0、最大值、最小值）
□ 错误状态
□ 竞态条件
□ 类型强制转换问题
```

> 实测价值：AI 生成的测试**经常暴露开发者漏掉的
> 空引用错误、差一错误、未处理的 promise rejection**。

## 测试金字塔与覆盖率分层

```
      / \
     /E2E\        10%  完整用户流程，走真实 UI
    /------\
   / 集成   \      20%  真实数据库与服务，⭐ 不用 mock
  /----------\
 /   单元测试  \    70%  快速、隔离，测业务逻辑
/--------------\
```

**覆盖率目标按代码类别分层**（而不是一个统一数字）：

| 代码类别 | 目标 |
|---|---|
| **关键路径**（支付、认证、数据校验） | **100%** |
| 业务逻辑与用例 | **≥85%** |
| 简单 getter/setter、生成代码 | **可跳过** |
| 集成测试 | 关键路径 70% |
| E2E | 覆盖产生收入或信任的用户旅程 |

> ⭐ **"简单 getter/setter 可跳过"这条很重要**——
> 统一 80% 覆盖率目标会逼 agent 补无意义的测试。

## AAA 与 FIRST

**AAA 模式**（每个测试三段分明）：

```
Arrange  准备测试数据、mock、fixture
Act      执行被测的那一个操作
Assert   验证具体的预期结果
```

> ⭐ **混合这三段（动作之后再设 mock，或边准备边断言）
> 会产生脆弱、不可读的测试。**

**FIRST 五属性**（这本身就是一份"测试质量验收标准"）：

```
Fast           单元测试每个 <100ms
Isolated       不依赖其他测试或共享状态
Repeatable     每次跑结果一样，不 flaky
Self-validating 通过或失败，无需人工检视
Timely         与代码同时或提前写，而不是几个月后补
```

**命名即文档**：

```
❌ test_user1
✅ test_register_user_with_valid_email_creates_user
```

**参数化测试**（覆盖多边界的最高效方式）：

```
密码校验、金额校验、输入清洗是最佳候选
一个参数化函数覆盖：0 金额、负数、最小有效值、最大值
——共享 setup，各自的断言
```

> 呼应 `skill-crafting` 的 `output-contract.md` 与 `skill-authoring` 的 `examples.md`：
> **这些都是"可观察谓词"，不是形容词**——所以模型能执行。

## 团队测试技能示例

> 一份可直接抄的最小团队测试技能：

```yaml
---
name: team-testing
description: Use when writing tests, generating test files, or checking test coverage. 编写单元/E2E 测试、生成测试文件、检查覆盖率时使用。不用于编写被测代码本身。
---
```

```markdown
## Framework
单元测试用 Vitest，E2E 用 Playwright
文件命名：`*.test.ts`，与源码同目录

## Conventions
- 用 describe/it 块，不用 test()
- ⭐ 每个测试尽量一个断言
- 必须测：null 输入、空数组、错误状态、边界值

## What to avoid
- ❌ 不用快照测试
- ❌ 不测实现细节（测行为，不测内部）
- ❌ 不用 sleep——用 waitFor() 或正确的异步模式
```

> ⭐ **`What to avoid` 这节尤其值钱**——
> "不用快照测试""不测实现细节""不用 sleep"
> 全是你团队踩过才知道的坑，正是 `skill-authoring` 的 `skill-types.md` 说的 **Gotchas**。

**E2E 技能的额外要点**：

```
□ 用有韧性的选择器（data-testid，而不是 CSS class）
□ 正确等待异步操作
□ 处理认证流程
□ ⭐ 清理测试数据
```

**覆盖率分析类技能**（与生成类不同）：

```
它不写新测试，而是审计现有套件：
□ 读源码与测试文件
□ 找出零覆盖的函数与未走到的分支
□ ⭐ 给出具体建议，而不是一个百分比

❌ "你现在 72% 覆盖率"
✅ "这 8 个函数零测试，这 3 个分支从未被执行"
```

> ⭐ **这条对比本身就是好技能与坏技能的分界线**——
> 呼应 `skill-crafting` 的 `grounding-verification.md`：可行动的证据，而不是笼统数字。

## 自查

```
□ 是否编码了框架检测（而非写死某个框架）？
□ 是否要求沿用现有测试的结构与命名？
□ ⭐ 是否明确列出了必须测的边界条件？
□ 覆盖率目标是否按代码类别分层（而非一刀切）？
□ 是否写了 AAA 与 FIRST？
□ 是否有命名规范（测试名即文档）？
□ 是否推荐参数化测试覆盖边界？
□ ⭐ 是否有 What to avoid 小节（团队特有的坑）？
□ E2E 是否要求 data-testid 与异步正确等待？
□ 覆盖率报告是否给出具体函数/分支（而非百分比）？
```
