# 干系人沟通类技能：周报、进展同步、升级通报

> ⭐ **这类技能最大的风险是"看起来专业但内容不对"。**
> 因为它很容易生成流畅但无依据的陈述。

## 为什么这类技能容易出问题

```
模型很擅长写"听起来对"的进展报告
⭐ 而进展报告的价值恰恰在于它必须准确
```

三个典型失败：

```
① 把"计划做"写成"在做"
② ⭐ 把没验证的事写成已完成
③ 用模糊措辞掩盖不确定性（"进展顺利"）
```

> ⭐ 这正是 `grounding-verification.md` 说的：
> **未验证就声称成功是不诚实，不是高效。**

## 可自动化 vs 必须留人

```
可自动化：
  □ 从工单/提交/日历聚合事实
  □ ⭐ 按受众重新组织（不同人看不同重点）
  □ 格式化与术语统一
  □ ⭐ 标出"哪些没有证据支撑"

必须留人：
  □ ⭐ 对外承诺（时间、范围、交付物）
  □ ⭐ 风险升级的决策
  □ 对他人工作的评价
  □ 未经确认的进度判断
```

## 每种受众看什么

```
执行层   ⭐ 结论 / 风险 / 需要他们做什么（3 句以内）
同级     进展 / 阻塞 / 接口变更
执行者   细节 / 下一步 / 谁负责什么
外部     已交付什么 / 下一步 / ⭐ 不含内部风险讨论
```

> ⭐ **同一份事实，四种组织方式——
> 这是这类技能最实在的价值。**

判据：**读者需要据此做出什么决策？**
据此决定放什么、放多细。

## 禁止编造

三条硬规则：

```
① ⭐ 每个进展陈述都要有来源（工单号/提交/日期）
② ⭐ 没有证据的部分标为"未确认"，不能省略也不能编
③ ⭐ 不确定的用显式措辞（"预计"vs"已确认"）
```

反面：

```
❌ "本周完成了支付模块重构"
   ——没有来源

✅ "支付模块重构：PR #4821 已合并（2026-09-20）
     ⭐ 剩余：灰度验证（未开始，无排期）"
```

> ⭐ 注意第二条里的"未开始，无排期"——
> **明确写出"没有信息"比含糊过去有价值得多**。

## 输出结构

```
## 一句话结论
[本周期最重要的那件事]

## 进展
- [事项]：[状态] ⭐ [证据：PR #xx / 工单 #xx / 日期]

## 风险与阻塞
- [风险]：[影响] ⭐ [需要谁做什么]

## ⭐ 无证据/未确认的部分
- [事项]：目前无法确认，需要 [谁] 提供 [什么]

## 下一步
- [事项] · [负责人] · ⭐ [预期时间或"未排期"]
```

> ⭐ "无证据/未确认的部分"这一节是这类技能的核心——
> **没有它，读者会默认所有内容都已确认。**

## 自查

```
[ ] ⭐ 每条进展都有可追溯的来源？
[ ] ⭐ 有"未确认"清单？
[ ] "预计"与"已确认"用词区分了？
[ ] ⭐ 没有对外承诺（时间/范围）被自动生成？
[ ] 按受众组织（不是一份报告给所有人）？
[ ] ⭐ 结论在前（执行层能只读第一句）？
[ ] ⭐ 内部风险讨论没有出现在对外的版本里？
[ ] 风险项都写了"需要谁做什么"？
```

## 一条通用原则

适用于周报、月报、项目进展、事故通报、客户同步：

```
模型可以：聚合、组织、格式化、标记不确定性
模型不能：承诺、评价、为没有证据的事背书
```

> ⭐ 判据很简单：
> **这条陈述发出去之后，如果它是错的，谁负责？**
> 如果是模型负责——那它就不该被写出来。

## 一个延伸判断

> ⭐ **这类技能的价值上限是"节省组织时间"，
> 不是"替你思考进展"。**

它能把"从 6 个系统里收集事实再排版"这件事自动化，
这是实打实的收益。

但它判断不了"这个风险该不该升级"——
**那是责任，不是信息处理。**
