# 中间产物是 API，不是便签

> 前置：《skill-execution》的 `skill-execution/references/intermediate-artifacts.md`（命名、run-id、失败留现场）
> 分工：那份写**产物怎么产生与清理**；本份写**产物被别人读时要满足什么**。

---

## 1. ⭐⭐⭐⭐⭐ 便签和 API 的区别不在内容，在有没有读者

```
便签：写的时候只有自己会看 → 省略、缩写、靠记忆补全，都是合理的
API ：写的时候有未知读者 → 任何一处省略都会被补，而补的方式不由你决定
```

> ⭐⭐⭐⭐⭐ **中间产物有两种写法，而多数人按第一种写第二种的东西。**

判据一句话：

> ⭐⭐⭐⭐⭐ **把这个文件给一个没参与过这次运行的人（或模型），它能用吗？**

不能 → 它是便签，而它正在被当 API 用。

---

## 2. ⭐⭐⭐⭐⭐ 四个字段，少一个就降级成便签

```
schema   —— 有哪些字段、什么类型
version  —— 这份结构是哪一版
status   —— 这次运行的结果状态
partial  —— ⭐⭐⭐⭐⭐ 部分成功的标记
```

前三个是常识，⚠️ **第四个几乎从不写**，而它恰恰是链式静默的主要来源。

### 为什么 partial 最容易被漏

```
作者心智：这个产物"生成出来了" → status: ok
实际情况：8 个来源里 2 个 401 → 覆盖率 75%
```

> ⭐⭐⭐⭐⭐ **"生成成功"和"内容完整"是两件事，而产物的存在只能证明前者。**

下游读到 `status: ok` 会做什么？**把它当完整数据用**。
它不会去检查"是不是真的全"——因为契约里没有这个字段，它无从检查。

参见 `skill-interfaces/references/what-a-handoff-carries.md` §2：
`{"count": 42}` 看起来最健康，而它可能只覆盖 67%。

---

## 3. ⭐⭐⭐⭐⭐ "文件存在"不等于"内容可用"

存在性检查是最常用的前置检查，也是最容易骗过自己的：

| 情况 | 存在检查 | ⭐ 实际 |
|---|---|---|
| 存在但为空 | ✅ 通过 | 上游失败后写了空文件 |
| ⭐⭐⭐⭐⭐ 存在但是旧的 | ✅ 通过 | 上一次运行的数据（固定文件名） |
| ⭐⭐⭐⭐⭐ 存在但 partial | ✅ 通过 | 缺一路，且没有任何标记 |

> 三种都通过存在性检查。**第二、三种最贵，因为它们有内容。**

第二类尤其隐蔽：

```
fetch_raw.json  ← 固定名 → 第二次运行"文件已存在" → 用的是上一次的数据
```

> ⭐⭐⭐⭐⭐ 文件确实存在、格式确实对，只是内容是旧的——**不会报错**。

两条规则管的是不同环节，不能互相替代：

```
① 路径带 run-id          —— 防止读到旧文件
② ⭐⭐⭐⭐⭐ 读取前校验新鲜度 —— 防止读到"今天的旧文件"
```

只做①，脚本里写"存在就用"仍会命中缓存。

---

## 4. ⭐⭐⭐⭐⭐ 三个读者，三套要求

一个中间产物通常同时被三方读，而它们的要求是冲突的：

| | 下游技能 | 脚本 | ⭐ 人（调试时） |
|---|---|---|---|
| 结构 | 严格 | 严格 | 无所谓 |
| 冗余 | 越少越好 | 无所谓 | ⭐⭐⭐⭐ 需要上下文说明 |
| 单位/口径 | ⭐⭐⭐⭐⭐ 必须随值带 | 必须 | 无所谓 |
| 缺失表示 | ⭐⭐⭐⭐⭐ `null` + reason | 枚举值 | 无所谓 |

> ⭐⭐⭐⭐⭐ **冲突集中在"冗余"这一行**——
> 给人看的说明会增加 token、干扰机器解析；给机器看的紧凑结构让人无法调试。

解法不是折中，是**分层**：

```
产物文件（机器读，紧凑，带 schema）
  + 同名 .meta.md（人读，说明这次为什么是这样）
```

> ⭐⭐⭐⭐⭐ 折中的结果通常是"给人看的话写进了产物"——
> 于是下游要在解析时跳过一段自然语言，而它跳过的可能是唯一写着口径的地方。

## 5. version 字段：三种写法与它们的失败方式

```
① 无 version                    → 改结构后下游静默错
② version: 2                    → 能发现"变了"，但不知道变了什么
③ ⭐⭐⭐⭐⭐ version: 2 + changed: [...] → 能定位
```

> ⭐⭐⭐⭐⭐ 只写版本号而不写变更点，等于告诉下游"有东西变了，你自己找"。

而下游找的方式是**逐个字段试**——它试的时候不报错，只是某些字段的值含义不同了。

参见 `skill-interfaces/references/contract-evolution.md`：
改语义（毫秒→秒）比改字段名静默得多，因为字段名没变、类型没变、schema 校验通过。

推荐的最小写法：

```json
{
  "schema_version": "2",
  "changed_from_v1": ["duration → duration_s（单位：秒）"],
  "status": "partial",
  "coverage": {"actual": 6, "expected": 8}
}
```

## 6. ⭐⭐⭐⭐⭐ 自检：三问

```
① 一个没参与这次运行的人，能看懂这个文件吗？
   不能 → 缺 schema 或 meta

② 下游能判断"这份内容完整吗"？
   不能 → ⭐⭐⭐⭐⭐ 缺 status/partial/coverage

③ 半年后有人改了上游，下游会报错吗？
   不会 → 缺 version，或者改的是语义而字段名没变
```

三个问题都不需要跑代码，读一遍就能答。

最便宜的一条机械检查：

```
把产物里的所有值清空（保留结构），下游会报错吗？
不报错 → ⭐⭐⭐⭐⭐ 它在用默认值兜底，契约没在起作用
```

---

## 7. Critical Rules

```
MUST NOT 用"文件存在"判断"上游做过" —— 空/旧/partial 三种都能通过
MUST NOT 把 status 写成二态 —— 必须能表达 partial 与 skipped
MUST NOT 改语义而不改字段名 —— duration → duration_s，让下游报错而不是照旧用
MUST NOT 把给人读的说明混进机器读的字段 —— 分层：产物 + .meta.md
MUST NOT 只写 version 不写变更点 —— 等于让下游逐个字段试
MUST NOT 用固定文件名 —— 带 run-id，且读取前校验新鲜度
```
