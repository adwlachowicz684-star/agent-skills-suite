## 1. ⭐⭐⭐⭐⭐ 一次善意的补全天

```
上游 A：{"count": null, "status": "partial", "note": "源不可用"}
下游 B：{"count": 0,   "status": "ok"}
```

> ⭐⭐⭐⭐⭐ B 没有出错。它只是"处理了一下" A 的输出。

> ⭐⭐⭐⭐⭐ 而 A 的全部信息——"我不知道，且我告诉了你我不知道"——
> 在 B 这里变成了"我知道，是 0"。

---

## 2. ⭐⭐⭐⭐⭐ 三种改写，第二种最多

**① ⭐⭐⭐⭐⭐ 未知 → 默认值**

```
null → 0 · "" · [] · false
```

> ⭐⭐⭐⭐⭐ 与《skill-output》的"0 与未获取"同源，
> ⭐⭐⭐⭐⭐ 但发生位置不同：那份是**生成输出时**，这份是**传递过程中**——
> ⭐⭐⭐⭐⭐ 后者更难发现，因为每一级都在"正常完成自己的工作"。

**② ⭐⭐⭐⭐⭐ 部分成功 → 成功**（最多）

```
status: "partial" → status: "ok"
```

> ⭐⭐⭐⭐⭐ 原因很实际：⭐⭐⭐⭐ 下游的模板里通常只有 ok / failed 两态，
> ⭐⭐⭐⭐⭐ partial 没有位置，于是被归并到最近的那个——ok。

**③ ⭐⭐⭐⭐⭐ 推测 → 事实**

```
{"likely_reason": "网络问题"} → {"reason": "网络问题"}
```

> ⭐⭐⭐⭐⭐ 上游保留的"这是我的推测"这一层，在下游变成了断言。

> ⭐⭐⭐⭐⭐ 三种改写的共同点：⭐⭐⭐⭐⭐ **不确定性在传递中单调递减，
> 而信息量并没有增加**。链条越长，末端越确定，也越可能错。

---

## 3. ⭐⭐⭐⭐⭐ 为什么会补：字段存在就有填的冲动

三条机制：

**① ⭐⭐⭐⭐⭐ schema 要求字段存在**

```
"count" 是必填 → null 不合 schema → 填 0
```

> ⭐⭐⭐⭐⭐ **"必填"是这类改写的主要推手**：⭐⭐⭐⭐ 作者为了让 schema 校验通过，
> ⭐⭐⭐⭐⭐ 把"未知"变成了一个合法但错误的值——
> 这正是"schema 合规不保证值"在链条上的形态。

**② ⭐⭐⭐⭐⭐ 下游代码/模板里没有 null 分支**

```
f"共 {count} 条"  → null 会渲染成 "共 None 条"
⭐⭐⭐⭐⭐ 于是有人（或模型）在入口处把它补成 0
```

**③ ⭐⭐⭐⭐⭐ 完成倾向**（见《skill-content》的 `skill-content/references/default-actions.md`）

> ⭐⭐⭐⭐⭐ 遇到"缺一块"时默认动作不是停下报告，而是想办法补上。

## 4. ⭐⭐⭐⭐⭐ 修法一：nullable 与"未获取"必须可达

两条规则，缺一不可：

```
① ⭐⭐⭐⭐⭐ schema 里必须显式允许 null（nullable: true）
② ⭐⭐⭐⭐⭐ 必须有配套的 status 字段说明"为什么是 null"
```

只有①没有②的后果：

```
count: null → 下游不知道这是"没查"还是"查了确实是空"
⭐⭐⭐⭐⭐ 于是它还是得猜——问题只是换了个位置
```

> ⭐⭐⭐⭐⭐ **null 本身不携带原因，status 才携带。
> 两者必须一起传，否则 null 会被下游重新解释。**

三条写法：

```
✅ {"count": null, "status": "unavailable", "reason": "源返回 401"}
❌ {"count": null}
❌ {"count": 0}
```

> ⭐⭐⭐⭐⭐ 判据：⭐⭐⭐⭐⭐ **下游能不能区分"没有数据"和"没拿到数据"？**
> 不能 → 契约不完整，无论字段多全。

---

## 5. ⭐⭐⭐⭐⭐ 修法二：类型与单位随值一起传

值会在传递中被改写，另一种是"看起来没改写但意思变了"：

```
A: {"duration": 1500}      ← 毫秒
B: {"duration": 1500}      ← 下游当成秒
```

> ⭐⭐⭐⭐⭐ 数字一模一样，语义差 1000 倍，而**没有任何环节会报错**。

与《skill-crafting》的 `skill-precision/references/terminology.md`（同义消解）同源，但后果更硬：

```
字段名一致 ≠ 含义一致
⭐⭐⭐⭐⭐ 单位、时区、币种、基准（相对谁）都必须随值传递
```

最常被省的三项：

| 项 | ⭐⭐⭐⭐⭐ 不传的后果 |
|---|---|
| 单位 | 差 1000 倍，不报错 |
| 时区 | 差一天，不报错 |
| ⭐⭐⭐⭐⭐ 基准（相对于谁/何时） | "最近 7 天"基准漂移，见 `skill-input/references/relative-time-resolution.md` |

> ⭐⭐⭐⭐⭐ 与"示例里的具体值会被当成默认值"是同一族的：
> ⭐⭐⭐⭐⭐ **凡是"看起来显然"的东西，都是传递中最先丢掉的**——
> 因为它在源处不需要写明，于是从来没被写明。

## 6. ⭐⭐⭐⭐⭐ 修法三：下游校验上游，而不是信任上游

三个便宜的检查，按性价比：

**① ⭐⭐⭐⭐⭐ 入口处检查 null 与 partial**

```
if upstream.status != "ok": ⭐⭐⭐⭐⭐ 不得继续按全量处理
```

> ⭐⭐⭐⭐⭐ 这一条同时解决"改写"和"部分成功汇总"——
> 因为多数改写发生在下游没有检查上游状态的时候。

**② ⭐⭐⭐⭐⭐ 范围合理性检查**

```
count < 0 ？ · count == 0 但 status == "ok" ？ · 覆盖率 > 100% ？
```

> ⭐⭐⭐⭐⭐ 第二条最有用：⭐⭐⭐⭐ "0 且成功"是高度可疑的组合——
> 真实数据极少恰好为 0，而补全出来的 0 非常多。

**③ ⭐⭐⭐⭐⭐ 在输出里保留来源标记**

```
"count": 120, "count_source": "source_a"
```

> ⭐⭐⭐⭐⭐ 成本一个字段，收益是⭐⭐⭐⭐ **出错时能回溯到是哪一级改的**
> ——这直接解决"出错的地方 ≠ 报错的地方"。

## 7. ⭐⭐⭐⭐⭐ 自检

对每一处技能间传递：

```
① ⭐⭐⭐⭐⭐ schema 允许 null 吗？有配套 status 说明原因吗？
② ⭐⭐⭐⭐⭐ 下游能区分"没有"和"没拿到"吗？
③ ⭐⭐⭐⭐⭐ partial 在下游模板里有位置吗？（没有 → 会变 ok）
④ ⭐⭐⭐⭐⭐ 单位/时区/基准随值传递了吗？
⑤ ⭐⭐⭐⭐⭐ 输出的每个数字能追溯到来源吗？
```

一个十秒判断：

> ⭐⭐⭐⭐⭐ **把链路里的每个中间产物都打出来，从上游到下游逐字段比对。
> 只要有一处 null 变成了 0，或 partial 变成了 ok——
> 那条链正在把不确定性加工成确定性，而末端的人会完全信任它。**

---

> ⭐⭐⭐ **不确定性在传递中单调递减，而信息量并没有增加。
> 链越长，末端越确定，也越可能错。**
