## 1. ⭐⭐⭐⭐⭐ 交接包里到底要有什么

一个技能交给下一个的最小数据包，五项：

```json
{
  "from": "analyze",
  "artifact": "analysis.json",
  "summary": "12,480 行，3 个 cohort，留存中位数 41%",
  "failures": [{"step":"fetch","ok":false,"reason":"source_b 401"}],
  "confidence": {"overall":"medium","note":"source_b 缺失，覆盖率 67%"},
  "exceptions": ["2024-03 cohort 样本 <30，已标记"]
}
```

| 字段 | ⭐ 为什么必须有 |
|---|---|
| `artifact` | ⭐⭐⭐ 产物可定位 → 完成可验证（七个契约之一） |
| `summary` | 下游不该为了知道结论去读整个产物 |
| ⭐⭐⭐⭐⭐ `failures` | ⭐⭐⭐⭐⭐ 见 §2 |
| ⭐⭐⭐⭐ `confidence` | 见 §3 |
| ⭐⭐⭐⭐ `exceptions` | 见 §4 |

> ⭐⭐⭐⭐⭐ **`failures` 是最重要也最常缺的一项。**
> 没有它，下游看到的是一个"正常的结果"——
> ⭐⭐⭐⭐ 而实际上那是 ⭐⭐⭐⭐⭐ **一个降了级、缺了数据源的结果**。

## 2. ⭐⭐⭐⭐⭐ 最常缺的一项：失败与降级

典型交接（坏的）：

```
"分析完成，共 12,480 行，留存中位数 41%。"
```

> ⭐⭐⭐⭐⭐ **这句话在技术上完全真实，而且完全误导。**

它省略的是：

```
source_b 返回 401 → 只用了 source_a → 覆盖率 67%
```

> ⭐⭐⭐⭐⭐ **下游拿到"12,480 行"会当成全量，
> 而"41% 的中位数"其实只来自 67% 的数据。**
> 没有任何一方在撒谎——⭐⭐⭐⭐ **是交接协议里没有 `failures` 这个字段。**

为什么它总是被省略？三个原因：

```
① ⭐⭐⭐ 技能倾向于"呈现成功"（模型的默认动作，见 default-actions.md）
② 输出格式里没有这一项 → 就不会被填
③ ⭐⭐⭐⭐ 作者觉得"部分失败不值得说"
```

> ⭐⭐⭐⭐⭐ **第三条是最根本的**：
> 作者把"部分成功"当成"成功"了。
> 而 `skill-execution/references/parallel-and-concurrency.md` 已经给过结论——
> ⭐⭐⭐⭐⭐ **部分成功必须报覆盖率，否则就是谎言。**

修法很便宜，一行输出契约：

```markdown
## 输出（必填第五项）
5. **失败与降级**：任何未成功的步骤 + 实际覆盖率。没有就写"无"。
```

> ⭐⭐⭐⭐ **"没有就写无"这半句同样关键**——
> 不给这个出口，它就会编一段"降级说明"。

## 3. ⭐⭐⭐⭐ 次常缺：置信度

下游**无法**自己判断上游结果有多可信——它只看到产物。

| 上游知道 | 下游看到的 |
|---|---|
| 这条是从残缺数据推断的 | 一个字段值 |
| 这个映射是我猜的 | 一个映射 |
| 这 3 条几乎一样，我合并了 | 1 条 |

> ⭐⭐⭐⭐ **信息在上游产生，在下游丢失。**
> 而 ⭐⭐⭐⭐⭐ 下游恰恰是那个要拿它做决定的地方。

最低成本的实现：**三档 + 一句原因**。

```
confidence: low / medium / high
note: 一句话说明为什么是这个档（≤ 20 字）
```

> ⭐⭐⭐⭐ 三档而不是百分数的理由：
> ⭐⭐⭐ **模型给的"置信度 0.73"是假精度**——
> 它没有校准过。三档足够，且不会诱导下游做算术。

## 4. ⭐⭐⭐⭐ 第三缺：边界与例外清单

```
"2024-03 cohort 样本 <30，已标记但不参与统计"
"有 7 行 user_id 为空，已排除"
```

> ⭐⭐⭐⭐ **这些"被排除的东西"不会出现在产物里**——
> 因为它们被排除了。⭐⭐⭐⭐⭐ **所以下游根本不知道它们存在过。**

后果很具体：下游算出"总计 12,480"，
而实际输入是 12,487——⭐⭐⭐ 7 行的差异没人能解释，
于是有人花半天去查。

> ⭐⭐⭐⭐ `exceptions` 这个字段的作用不是"说明"，
> ⭐⭐⭐⭐⭐ **是让下游能对账**。

一个可推广的判据：**产物里的任何聚合数字，
都要能追溯回输入总数**（输入 − 排除 = 参与计算）。

## 5. ⭐⭐⭐⭐ 格式：可解析优于自然

交接内容两种写法：

```
A) "分析完成了，数据挺全的，留存中位数是 41%"
B) {"summary":"...","coverage":0.67,"confidence":"medium"}
```

> ⭐⭐⭐⭐⭐ **A 是给人看的，B 是给下一个技能看的。
> 而交接的读者是下一个技能。**

我们已经有一条同源结论：**"输出可解析"而非"看起来一样"**
（四项工程化原则里的输入输出稳定）。这里是它的具体形态。

折中做法（推荐）：**机器字段 + 一句人话**。

```json
{"confidence":"medium","note":"source_b 401，覆盖率 67%",
 "human":"分析完成，但 source_b 未取到，结果基于 67% 的数据。"}
```

> ⭐⭐⭐ `human` 字段的用途是 ⭐⭐ **当交接被打断、需要人来接手时**——
> 那时读者变成了人，而人不需要 JSON。

## 6. ⭐⭐⭐⭐ 校验：下游能不能拒绝

> ⭐⭐⭐⭐⭐ **一个不能拒绝上游产物的下游，等于把上游的每个错误都继承下来。**

三个最低限度的校验（下游侧）：

```
① ⭐⭐⭐ 产物存在且可解析
② ⭐⭐⭐⭐ 必需字段齐全（尤其是 confidence / failures）
③ ⭐⭐⭐⭐⭐ 覆盖率是否可接受（低于阈值 → 停止并说明，不要继续）
```

> ⭐⭐⭐⭐⭐ 第三条最关键，也几乎没人做：
> ⭐⭐⭐⭐ **下游"尽力用残缺数据继续跑"是一个默认的、错误的行为。**
> 正确的默认应该是：**覆盖率不足就停**——
> 因为下游跑出来的结果会被当成完整的，而它不完整。

这正好是"默认动作"那份的直接应用：
⭐⭐⭐⭐ **没写"数据不全时怎么办"，默认就是继续**。

配一条双向纪律：

```
上游：⭐⭐⭐ 不得为了"交接成功"而省略 failures
下游：⭐⭐⭐⭐ 不得为了"流程走完"而接受残缺产物
```

> ⭐⭐⭐⭐ 这两条一起，才构成一个闭环。
> ⭐⭐⭐⭐⭐ 只有上游写、下游不看 → 等于没写；
> 只有下游查、上游不写 → 永远触发。

## 一句可贴在墙上

> ⭐⭐⭐ **交接协议里没有 `failures` 字段，下游看到的就是一个
> "技术上真实、实质上误导"的结果。**
