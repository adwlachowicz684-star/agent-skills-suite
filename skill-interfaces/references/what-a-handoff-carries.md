# 交接携带什么：状态、分母、来源

> 前置：`skill-interfaces/references/handoff-payload-contract.md`（交接包五项字段）
> 分工：那份写**字段清单与格式**；本份写**为什么是这三样**、缺了会怎样、以及怎么验证下游真的在用它们。

---

## 1. ⭐⭐⭐⭐⭐ 最常见的交接定义是错的

```
"上游的输出就是下游的输入"
```

这句话只覆盖了**值**。而下游真正需要的判断，一个都不在值里：

```
① ⭐⭐⭐⭐⭐ 状态 —— 这次是成功、部分成功、失败，还是根本没执行？
② ⭐⭐⭐⭐⭐ 分母 —— 应该有多少，而不只是实际有多少
③ ⭐⭐⭐⭐⭐ 来源 —— 这个值从哪来、什么时候取的、怎么算的
```

> ⭐⭐⭐⭐⭐ **少了任何一样，下游都会自己补一个。
> 而补的那个一定是"看起来最正常"的，不是正确的。**

这不是猜测，是有机制的：模型遇到缺失字段时只有三个动作——

| 动作 | 选中概率 | 结果 |
|---|---|---|
| 填该字段最常见的值 | ⭐⭐⭐⭐⭐ 最高 | `status: ok`、`coverage: 100%` |
| 从邻近字段推断 | ⭐⭐⭐⭐ 高 | 有 `count` 就推断 "都拿到了" |
| 跳过该字段 | ⭐⭐⭐ 中 | 字段消失，下游模板里留空 |

> ⭐⭐⭐⭐⭐ **三个动作都不会报错。** 而"填最常见的值"恰好总是填上"成功/完整"——
> 因为训练语料里的状态字段绝大多数是 ok。

---

## 2. ⭐⭐⭐⭐⭐ 状态：不是"有没有值"，是"值可不可信"

最容易做错的一处：**用值本身表达状态**。

```
{"count": 0}      ← 是真的 0，还是没查到？
{"count": null}   ← 明确是"没有值"，但下游读成 0
{"count": 42}     ← 看起来最健康，可能是 partial
```

> ⭐⭐⭐⭐⭐ **第三行才是真正的陷阱**——它有值、类型对、范围合理，
> 于是所有校验都通过，而它只覆盖了 67%。

四态必须区分（不是三态）：

```
ok        —— 完整执行，结果可用
partial   —— 执行了，但覆盖不全（⭐⭐⭐⭐⭐ 必须有 coverage）
failed    —— 执行失败（必须有 reason）
skipped   —— ⭐⭐⭐⭐⭐ 根本没执行（前置不满足）
```

> ⭐⭐⭐⭐⭐ **`skipped` 是第四态，也是最常被省略的一态。**
> 它和 `failed` 的差别是"这次根本没跑"，而下游按 `failed` 处理会去找错误日志——
> 日志里什么都没有，因为没有任何东西失败。

参见 `skill-interfaces/references/artifact-mutation-in-chain.md`：
`null → 0`、`partial → ok` 是链上最常见的两种静默改写。

## 3. ⭐⭐⭐⭐⭐ 分母：没有分母，"完整"就不是可判定的

```
"分析完成，12,480 行"
```

这句话缺少的不是一个数字，是**判定完成的能力**：

```
12,480 / 12,480  → 完整
12,480 / 18,600  → 67%，partial
```

> ⭐⭐⭐⭐⭐ 只有分子时，下游无法区分这两种情况——
> 而它们的处理方式应该完全不同。

分母的三个来源，可靠性依次递减：

```
① 枚举结果（列表里数出来的）      —— 最可靠
② 上游声明（expected 字段）        —— 依赖上游诚实
③ ⭐⭐⭐⭐⭐ 推断（"应该就这些"）  —— 不能用作分母
```

> ⭐⭐⭐⭐⭐ 第三类不能叫分母。它是模型补的"看起来最正常的数"，
> 而它一旦被写进 `expected`，就获得了和真实分母相同的地位——
> 于是 `coverage` 永远显示 100%。

判据（可直接问下游）：

> ⭐⭐⭐⭐⭐ **下游能回答"这份数据完整吗"吗？**
> 不能 → 分母缺失，无论字段多全。

## 4. ⭐⭐⭐⭐⭐ 来源：可回溯性决定了错误能不能被发现

一个值要能被质疑，必须能回答三个问题：

```
从哪个来源取的？（source）
什么时候取的？（as_of）
怎么算出来的？（derivation）
```

> ⭐⭐⭐⭐⭐ **没有来源的值，无法被证伪——而无法被证伪的值在链上会逐渐变成事实。**

这与 `skill-output/references/output-becomes-fact.md` 是同一机制的两个位置：
那份讲输出进入**对话上下文**后获得事实地位；
这份讲值进入**交接链**后获得事实地位。
两者都不可见、都不可逆。

第三条最常被省：

```
留存中位数 41%
```

> ⭐⭐⭐⭐⭐ "中位数"是一个算法声明，**而它通常不写出来**。
> 下游拿到 41% 会按自己的口径二次计算，于是两个口径在同一个链上并存，
> 且没有任何一步报错。

最小写法成本很低（约 15 token）：

```
{"median": 41, "derivation": "按 user_id 去重后取中位数", "as_of": "2026-09-29"}
```

## 5. ⭐⭐⭐⭐⭐ 第四样：原因（reason）

状态说"是什么"，原因说"为什么"。它常被省，因为"失败了"看起来已经够用。

> ⭐⭐⭐⭐⭐ **`status: failed` 对下游毫无帮助——
> 下游需要知道的是"数据为什么没来"，而它只能看到"没来"。**

于是下游的猜测方向是**"格式不对"**（因为那是它唯一能观察到的可能性），
接着它会尝试清洗、尝试兼容、尝试跳过——

> ⭐⭐⭐⭐⭐ **每一步都合理，每一步都离真相更远。**
> 真相在上游，而它已经成功退出了。

失败原因必须区分三类，因为下游的处理完全不同：

| reason 类型 | 下游该做什么 |
|---|---|
| ⭐⭐⭐⭐⭐ 上游没跑（skipped） | 触发上游，不要自己补 |
| 上游失败（failed） | 报告并停止，不要绕过 |
| ⭐⭐⭐⭐⭐ 上游 partial | 带 coverage 继续，并在自己的输出里保留 partial |

> ⭐⭐⭐⭐⭐ 第二类最危险：**"报告并停止"是唯一正确的动作，
> 也是模型最不愿意做的动作**——它的完成倾向会推动它找一个能成功的路径。

## 6. 验证方法：删字段测试

一个零成本、且能同时验证"下游是否在用"的检查：

```
① 在交接包里删掉 status，跑一次
② 观察下游是否报错 / 输出是否变化

下游毫无察觉 → ⭐⭐⭐⭐⭐ 它从来没读过这个字段
                （它在自己补，而你一直以为契约生效）
```

> ⭐⭐⭐⭐⭐ **契约写在文件里 ≠ 契约在运行。** 渐进式披露决定了
> 没有任何环节会同时检查"上游写了什么"和"下游读了什么"。

三个字段各测一次，约十分钟。它比评审有效得多——
评审看的是字段在不在，删字段测试看的是字段有没有被用。

顺带一个反向测试：

```
把 coverage 从 100% 改成 67%，下游输出不变
→ ⭐⭐⭐⭐⭐ 它没有 partial 的处理路径，契约是装饰
```

## 7. ⭐⭐⭐⭐⭐ 自检清单

```
□ status 是四态（ok/partial/failed/skipped），不是二态
□ partial 必带 coverage（分子 + 分母），分母不是推断值
□ 每个值带 derivation（算法声明），不只是值
□ 时间类值带 as_of
□ failed 必带 reason，且 reason 能被下游区分三类
□ ⭐⭐⭐⭐⭐ 删掉 status 后下游会报错 —— 不报错说明字段没在用
□ ⭐⭐⭐⭐⭐ 下游能回答"这份数据完整吗"
```
