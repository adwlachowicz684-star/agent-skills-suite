## 1. 三类变更，只有一类安全

| 变更 | 字段名 | 类型 | 值 | ⭐ 后果 |
|---|---|---|---|---|
| ⭐⭐⭐ 加字段 | 新 | 新 | 新 | ⭐⭐⭐ 安全（下游忽略未知字段） |
| ⭐⭐⭐⭐⭐ 改语义 | 不变 | 不变 | 变了 | ⭐⭐⭐⭐⭐ **完全静默** |
| ⭐⭐⭐⭐ 删字段 | 消失 | — | — | ⭐⭐⭐⭐ 下游拿到 null，然后自己补一个 |

> ⭐⭐⭐⭐⭐ **改语义是最危险的一类，而且它最常被当成"小改"。**
> 字段名没变、类型没变、schema 校验通过、JSON 解析通过——
> ⭐⭐⭐⭐⭐ 唯一变的是那个数字代表什么，而没有任何一个环节在检查这个。

真实形态：

```
v1: duration = 毫秒
v2: duration = 秒（"更直观"）
下游：阈值判断 if duration > 5000 → 现在永远不成立
```

> ⭐⭐⭐⭐⭐ 没有报错、没有 null、没有类型错误。
> 它只是**安静地不再成立**，而且输出看起来完全正常。
> 这正是"传值不传单位"的升级版——那份讲的是交接时忘了带单位，
> ⭐⭐⭐⭐⭐ 这份更糟：**单位一直带着，只是中途被改了，而没人知道它曾被带过。**

三条硬规则：

```
① ⭐⭐⭐⭐⭐ 改语义必须改字段名（duration_ms → duration_s），禁止原地改含义
② ⭐⭐⭐⭐⭐ 字段名里带单位/基准/时区，让"改语义"在物理上不可能悄悄发生
③ 加字段必须标 optional，下游不得假定它一定存在
```

> ⭐⭐⭐⭐⭐ 第 ① 条的代价看起来很大（要改下游），
> ⭐⭐⭐⭐⭐ 而它恰恰是唯一能让"改语义"变成"可见的破坏"的办法——
> 下游读到不认识的 `duration_s` 会报错，读到熟悉的 `duration` 会照旧用。

## 2. ⭐⭐⭐⭐⭐ 删字段：没人知道谁在用它

删字段时你面对的问题不是"要不要删"，是：

> ⭐⭐⭐⭐⭐ **你无法枚举谁在读这个字段。**

原因在渐进式披露本身：

```
下游技能只有在被触发时才加载自己的正文
→ 它"消费哪些字段"这件事，写在一份平时没人读的文件里
→ ⭐⭐⭐⭐⭐ 于是上游改字段时，没有任何机制会去读那份文件
```

对比一下两个粒度就很清楚：

| 粒度 | 有没有依赖声明 | 能不能自动发现 |
|---|---|---|
| 技能 vs 技能 | 有（说明里写"需要 A 先跑"） | ⭐⭐⭐ 勉强 |
| ⭐⭐⭐⭐⭐ 字段 vs 字段 | ⭐⭐⭐⭐⭐ **没有** | ⭐⭐⭐⭐⭐ **不能** |

于是删字段的失败形状是：⭐⭐⭐⭐ **在改的那一刻完全正常，在被调用的那一刻才出错**——
而这两点之间可能隔了几周，且中间那段时间它"看起来是好的"。

它和改名是同一个病：`rename-alias-deprecation.md` 里那句
⭐⭐⭐⭐⭐ **"改名不会报错，它会静默降级"**——删字段也是，而且更彻底，因为连旧名都不留。

## 3. ⭐⭐⭐⭐⭐ 消费声明把静默破坏变成报错

解决办法不是"改之前记得查"，是让消费关系变成机器可读的：

```yaml
# 下游技能里声明
consumes:
  from: upstream-skill
  fields: [status, coverage, failures]
  optional: [basis]
```

> ⭐⭐⭐⭐⭐ 有了这个声明，"删字段"就从⭐⭐⭐⭐⭐ **一次运行时的静默破坏**，
> 变成了⭐⭐⭐⭐⭐ **一次 lint 时的报错**。

三条实现要点：

```
① ⭐⭐⭐⭐⭐ 声明写在下游，不是上游 —— 上游永远不知道谁在消费它
② ⭐⭐⭐⭐⭐ 必填与可选分开（optional 的字段被删不报错）
③ lint 在改上游时跑，不是改下游时跑
```

> ⭐⭐⭐⭐⭐ 第 ① 条是关键，也是反直觉的地方：
> 我们习惯让"生产者"声明它提供什么，而**这里需要的恰恰是消费者声明它需要什么**——
> 因为生产者那一侧的声明永远不完整。

最低成本版本（没有工具链也能做）：

```
在交接包文档里维护一张表：字段 → 消费方列表
改字段时 grep 这张表
```

> ⭐⭐⭐⭐ 它不如自动 lint 可靠（会漏更新），但⭐⭐⭐⭐⭐ **它把"无法枚举"变成了"有一处可查"**——
> 从不可能变成不精确，这已经是最有价值的一步。

## 4. 废弃的两步与版本协商

删字段不能一步做完。两步顺序不能反：

```
① ⭐⭐⭐⭐⭐ 先停写（上游不再产出该字段），但下游仍兼容缺失
② ⭐⭐⭐⭐⭐ 再停读（下游移除对该字段的依赖）
```

> ⭐⭐⭐⭐⭐ 反过来做必炸：先改下游不读，再改上游不写 → 中间窗口里下游会去读一个还在写但即将消失的字段，
> 而它已经不再处理这个值了 —— 这个窗口不会有任何报错，只会让结果悄悄变。

版本协商三档，按成本递增：

| 档 | 做法 | 何时用 |
|---|---|---|
| ⭐⭐⭐ 宽容读取 | 缺失就用默认值并标注 | 可选字段 |
| ⭐⭐⭐⭐ 显式版本字段 | 交接包带 `contract_version` | ⭐⭐⭐⭐⭐ 有外部消费方时必做 |
| ⭐⭐⭐⭐⭐ 双写过渡期 | 新旧字段同时写，过期后删旧 | 无法协调下游升级时 |

> ⭐⭐⭐⭐⭐ 中间那档的关键不在"带版本号"，在⭐⭐⭐⭐⭐ **下游读到不认识的版本时要报错，而不是猜**。
> 带一个没人检查的版本号，等于没有版本号——它只是把静默失败推迟了。

## 5. ⭐⭐⭐⭐ 与"同一阈值多份"的关系

`shared-thresholds-single-source.md` 讲的是同一个值抄在多个技能里。
字段契约是同一件事的⭐⭐⭐⭐⭐ **更隐蔽的版本**：

| | 抄阈值 | ⭐ 抄字段契约 |
|---|---|---|
| 复制了什么 | 一个值 | ⭐⭐⭐⭐⭐ 一组字段名与语义 |
| 不同步时 | 数值打架 | ⭐⭐⭐⭐⭐ 字段名还在、含义分岔 |
| 发现难度 | 至少能 grep 数字 | ⭐⭐⭐⭐⭐ grep 不到，因为拼写完全一样 |

> ⭐⭐⭐⭐⭐ 所以那个"立 canonical + 引用"的修法在这里同样适用，
> 只是 canonical 从"一个数字"变成"一份 schema 文件"：
> **引用时要把当前字段名也写出来——只给链接，等于把定义换成了一次可能不发生的跳转。**
