## 1. ⭐⭐⭐⭐ 上下文不是黑板

> ⭐⭐⭐⭐⭐ **"早期我图省事，在⭐ 全局上下文里塞各种临时字段，
> ⭐⭐⭐⭐⭐ 技能之间⭐ 互相读取彼此的结果——
> ⭐⭐⭐⭐⭐ ⭐ 上下文变成了一块⭐ 所有人都在涂改的黑板，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ ⭐ 改一处，崩一片。"**

> ⭐⭐⭐⭐⭐ 这是我见过的⭐ 对"共享可变状态"问题⭐ 最好的比喻，
> ⭐⭐⭐⭐ 而且它⭐ 精确解释了为什么这个错误⭐ 在技能系统里特别容易犯：
> ⭐⭐⭐⭐ **上下文看起来就是一个⭐ 天然的共享空间**——
> 反正大家都在同一个对话里，⭐ 顺手往里一放多方便。
>
> ⭐⭐⭐⭐⭐ 而它的⭐ 失败特征也很有辨识度：
> ⭐⭐⭐⭐ **"改一处，崩一片"**——⭐⭐⭐ 你没有改那个坏掉的技能，
> ⭐⭐⭐⭐ 你改的是⭐ 另一个往上下文里写字段的技能。
> ⭐⭐⭐⭐⭐ 这类 bug 极难定位，因为⭐ 出错的地方和改动的地方⭐ 不是同一个。
>
> ⭐⭐⭐⭐ 与 `composition-patterns-types.md` 的"隐式依赖
> ⭐ 单独测试完全看不出来，只在生产被单独调用时暴露"
> ⭐⭐⭐⭐ 是⭐ 同一件事的两个说法——这里⭐ 补上了⭐ 它的成因（黑板）和⭐ 修法。

## 2. ⭐⭐⭐ 三条原则

```
① ⭐⭐⭐⭐ 技能之间⭐ 显式传参
   ⭐⭐⭐⭐ A 需要 B 的结果时，⭐ 用参数传递，⭐⭐ 不靠"隐式环境变量"
   ⭐⭐⭐⭐⭐ ⭐ "隐式依赖一旦多起来，⭐ 排查链路时的成本⭐ 极高"

② ⭐⭐⭐⭐ 会话级状态⭐ 写入⭐ 专门存储
   ⭐⭐⭐ 临时状态写进会话级存储（如 conversation_state.set(...)），
   ⭐⭐⭐⭐ ⭐ 由⭐ 编排层统一管理，⭐⭐ 技能不直接操作

③ ⭐⭐⭐ 依赖⭐ 显式声明（见第 3 节）
```

> ⭐⭐⭐⭐ 第 ② 条最关键：⭐ **"由编排层统一管理，技能不直接操作"**。
> ⭐⭐⭐⭐ 这与 `skill-dependency-injection.md` 的"双向无知"是⭐ 同一原则：
> ⭐⭐⭐ 技能⭐ 不该知道⭐ 自己的输出会被谁用、被放在哪。
>
> ⭐⭐⭐⭐ 三条合起来的⭐ 收益说得很好：
> ⭐⭐⭐⭐ **"让技能之间的耦合度降到最低，也让技能⭐ 能独立复用和测试，
> ⭐⭐⭐⭐⭐ ⭐ 不至于'⭐ 离开那个环境就跑不起来'。"**
>
> ⭐⭐⭐⭐⭐ 最后这句是⭐ 最好的检验标准——
> ⭐⭐⭐⭐ **把你的技能单独拿到一个新会话里跑，它还能跑吗？**
> ⭐⭐⭐ 跑不了 → 它对上下文有⭐ 隐式依赖。

## 3. ⭐⭐⭐ 依赖声明：让编排层知道谁在等谁

```yaml
dependencies:
  required:
    - name: data-validation
      version: "^1.0.0"
    - name: file-io
      version: ">=2.3.0 <3.0.0"
  optional:
    - name: visualization
      version: "*"
  conflicts:
    - name: legacy-pdf
      version: "<2.0.0"
```

> ⭐⭐⭐ 注意 `conflicts` 这一节——⭐⭐ **显式声明"我和谁不能共存"**，
> 这与 `description-scope-shape.md` 的"排除声明互相点名"、
> `collision-arbitration.md` 的 `exclusive_group`
> ⭐ 是⭐ 同一条原则在⭐ 三个不同载体上的⭐ 第三次出现。
>
> ⭐⭐⭐⭐ **"让编排层知道谁在等谁"**——这句话点出了⭐ 依赖声明的真正用途：
> ⭐⭐⭐⭐⭐ 不是给人类看的文档，⭐⭐⭐⭐⭐ 是⭐ 给调度器用的⭐ 输入。
> ⭐⭐⭐ 所以⭐ 它必须是⭐ 结构化的（`^1.0.0` 而不是"新版本"），
> ⭐⭐⭐⭐ 这与 `dependency-resolution-conflicts.md` 的
> "需要 Python 环境"不是声明，`python: ">=3.11"` 才是
> ⭐⭐⭐⭐ 是⭐ 同一条的第三个场景。

**解析算法四步**（可作实现参考）：

```
① ⭐⭐ 拓扑排序：确定技能加载顺序
② ⭐⭐⭐ 冲突检测：⭐ 版本冲突 + ⭐⭐ 循环依赖
③ ⭐⭐ 解决方案生成：给出冲突解决建议
④ ⭐⭐⭐ 回滚机制：⭐ 依赖安装失败时自动回滚
```

## 4. ⭐⭐⭐⭐ 不要为了组合而组合

> ⭐⭐⭐⭐⭐ **"如果⭐ 一个技能是另一个技能的⭐ 唯一调用者，就没必要拆开。"**

```
❌ "生成图片说明" 只有 "文章配图处理" 会用
   → ⭐⭐⭐⭐ ⭐ 直接把逻辑写进去，不要额外建一个技能
✅ ⭐⭐⭐⭐⭐ 原则：⭐⭐⭐⭐⭐ "能被⭐ 两个以上⭐ 场景复用，才拆成技能；
   ⭐⭐⭐⭐⭐ ⭐ 否则它只是⭐ 一个普通函数。"
```

> ⭐⭐⭐⭐⭐ **这条补全了我们拆分判据的⭐ 关键半边。**
> 此前我们有：
> ```
> · 重启测试       → 找"⭐ 该拆没拆"
> · 双向无知       → 找"拆错地方"
> · 一动作一技能   → 找"⭐ 拆过头"（粒度下限）
> · 五信号         → 找"该拆了"
> ```
> ⭐⭐⭐⭐ ⭐ 而这里给的是⭐⭐⭐⭐⭐ **一个数字化的下限：⭐⭐ "复用 ≥2 个场景"**。
> 它比"一动作一技能"更⭐ 可判定——⭐⭐ 数一下有几个调用方就行。
>
> ⭐⭐⭐⭐ 而且它⭐ 给出了"过度拆分"的⭐ 具体代价：
> ⭐⭐⭐⭐ **"⭐ 增加维护成本，还会让⭐ 模型的调用链变长，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ ⭐ 任何一环判断失误，都会导致⭐ 整个流程失败。"**
>
> ⭐⭐⭐⭐ 最后半句最重要：⭐⭐⭐ **它不是线性变慢，是⭐ 串联可靠性衰减**——
> n 个环节、每环 p 的可靠度，整链是 pⁿ。
> ⭐⭐⭐⭐ 这与 `scope-multiplication.md` 的"失败模式是⭐ 笛卡尔积"
> ⭐⭐⭐⭐ ⭐ 是⭐ 同一数学直觉的⭐ 第二个场景：
> ⭐⭐⭐⭐ **多一个环节（技能）不是多一份风险，是⭐ 乘一次风险。**

> ⭐⭐⭐ 顺带一个相关判据：⭐ **模型运行时先加载主技能，
> ⭐ 遇到依赖再加载子技能**，这样⭐ 不会出现"不知道下一步调哪个"。
> ⭐⭐ 与 `frontmatter-full-reference.md` 的
> ⭐ "子代理的 skills 字段是⭐ 启动时全量加载，没有按需档"
> ⭐⭐⭐ 形成对比：⭐ 主链路可以按需，⭐⭐⭐ 子代理目前不行。

## 5. ⭐⭐ 并行只有只读技能才能安全做

```
"对比三款手机配置" → ⭐ 并行调用三次"商品详情查询" → 再让模型综合对比
⭐⭐⭐ 这个模式能⭐ 显著降低整体时延
⭐⭐⭐⭐ ⭐ 但要⭐ 注意技能是否有⭐ 副作用——⭐⭐⭐⭐ ⭐ 只有只读技能⭐ 才能安全并行
```

> ⭐⭐⭐ 这与 `conflict-precedence-four-types.md` 的
> "⭐ 只读优于写入"仲裁规则、
> `allowed-tools-least-privilege.md` 的最小权限
> ⭐⭐⭐ 是⭐ 同一条的⭐ 第三个场景，而且⭐ 给出了一条⭐ 新的理由：
> ⭐⭐⭐⭐ **并行的收益（降时延）只在⭐ 只读时成立**——
> ⭐⭐⭐⭐ ⭐ 有副作用的技能并行会⭐ 互相踩踏，⭐⭐ 而且⭐ 失败后无法安全回滚。

## 6. ⭐⭐⭐ 四类链与四种上下文策略（速查）

```
链：顺序链（前一个输出=后一个输入）· 并行链（结果合并）
   条件链（按条件选路径）· 循环链（重复直到满足——⭐ 必须有退出条件）

上下文：压缩 · 分块加载 · ⭐⭐⭐ 状态持久化（中间结果存库）· ⭐⭐⭐ 检查点（失败从检查点恢复）
错误：  超时控制 · 指数退避重试 · ⭐⭐⭐ 降级（主技能失败用备用）· 监控告警
```

> ⭐⭐⭐ 其中"⭐ 检查点"与 `fault-injection-eval.md` 的
> "⭐⭐ 恢复前检查点缺失/过期 → ⭐ 安全停止，⭐ 绝不编造进度"
> ⭐⭐⭐ 完全一致——⭐⭐ 那份讲⭐ 检查点坏了怎么办，这里讲⭐ 检查点该怎么设计。

## 速查

```
□ ⭐⭐⭐⭐⭐ 上下文是"所有人都在涂改的黑板"——⭐ 改一处崩一片
   ⭐⭐⭐⭐⭐ 特征：⭐ 出错的地方 ≠ 你改动的地方（极难定位）
□ ⭐⭐⭐⭐ 三原则：① ⭐ 显式传参（不靠隐式环境变量）
             ② ⭐⭐ 会话级状态写专门存储，⭐⭐⭐ 由编排层统一管理，技能不直接操作
             ③ ⭐ 依赖显式声明
   ⭐⭐⭐⭐⭐ 检验：⭐ 拿到新会话单独跑，还能跑吗？跑不了 = 有隐式依赖

□ ⭐⭐⭐ 依赖声明是⭐⭐⭐⭐ 给调度器用的输入，不是给人看的文档 → 必须结构化
   ⭐ `conflicts` 节 = "排除声明互相点名"的⭐ 第三个载体
□ ⭐⭐⭐⭐⭐ 不要为了组合而组合：⭐⭐⭐⭐⭐ 复用 ≥2 个场景才拆成技能，否则只是普通函数
   ⭐⭐⭐⭐ 过度拆分的代价不是线性变慢，是⭐⭐⭐ 串联可靠性衰减（pⁿ）
   ⭐⭐⭐⭐ 与"失败模式是笛卡尔积"同一数学直觉的第二个场景
□ ⭐⭐⭐⭐ 并行只有⭐ 只读技能⭐ 才能安全做（有副作用会互相踩踏且难回滚）

□ 链四类：顺序·并行·条件·循环（⭐ 循环必须有退出条件）
  上下文四策略：压缩·分块·⭐状态持久化·⭐检查点
  错误四手段：超时·退避重试·⭐降级·监控
```

**一句话**：

> ⭐⭐⭐⭐ **把上下文当共享空间用会让它变成"所有人都在涂改的黑板"（改一处崩一片，且出错的地方不是你改动的地方），正确做法是显式传参 + 会话级状态由编排层统一管理；而"能被两个以上场景复用才拆成技能，否则只是普通函数"补上了拆分判据缺失的下限——因为多一个环节不是多一份风险，而是乘一次风险。**
