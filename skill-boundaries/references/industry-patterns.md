## 一个反复出现的模式：混合架构

> ⭐ **几乎所有成功案例都不是"一个大技能"，而是一组小而专的技能。**

**金融风控的重构案例**：

```
规则技能          处理明确的欺诈模式（原规则引擎改造而来）
异常模式检测技能   基于孤立森林算法
社交网络分析技能   识别团伙欺诈
```

**效果**：新欺诈模式的响应时间 **从 2 周缩短到 2 天**。

> ⭐ **最关键的一句**：
> **发现新型诈骗手法时，只需更新对应的技能，而不必重新训练整个模型。**

这正是技能化架构的核心价值——**把变化局部化**。
呼应 `skill-distribution` 的 `versioning-compat.md`：**改一个技能的影响面，远小于改一个整体提示词。**

## 金融：风控技能组

```
实时交易监控技能
关联图谱分析技能
规则引擎集成技能
```

**关键优化点**：

```
□ ⭐ 技能调用优先级动态调整
□ 假阳性率控制在 0.3% 以下
□ 每日处理交易量 1.2 亿笔量级
```

> ⭐ **"技能调用优先级动态调整"** 值得注意——
> 说明技能之间不是平权的，编排层要有调度策略（呼应 `skill-orchestration` 的 `composition.md`）。

**另一个值得记的边界**（摩根大通的实践）：

```
冻结账户这类高风险决策，
Agent 只负责拼证据，最后拍板的还是人。
```

> 这与 `skill-governance` 的 `compliance-audit.md` 的 Article 14 人工监督完全一致——
> **in-the-loop 的选择要明确记录在案。**

## 医疗：合规是功能而非负担

**一个真实的设计**（医疗咨询 agent 通过监管审查的方案）：

```
医学知识验证技能   所有输出内容必须能被 PubMed 文献佐证
风险提示技能      对涉及处方药等内容自动添加警示
问诊记录技能      完整记录交互过程供人工复核
```

> ⭐ **最反直觉的一个数据**：
> **添加合规技能后，用户满意度反而提升了 15%。**

> 这说明合规约束**不是成本，而是信任信号**——
> 用户看到输出有文献佐证、有风险提示，反而更敢用。

**医院侧的规模化案例**：

```
23 个专科诊断技能
17 个影像解读技能
9 个用药建议技能
```

> ⚠️ **对照 `skill-refining` 的拆分原则**：
> 49 个技能远超"3–7 个子技能"的建议区间。
> 但它们是**平铺的领域条目**而非**一个流程的拆分**——
> **前者靠路由选择（像查表），后者靠编排（有依赖）**。
> 所以判断标准不是绝对数量，而是**它们之间有没有依赖**。

## 法律：文书与尽调

**司法平台文书系统**：

```
合同条款生成技能
裁判文书撰写技能
法规检索技能
```

**效果**：合同起草 4 小时 → 12 分钟；文书合规率 99.2%。

**法律 agent 的三类动作**：

| 场景 | 具体动作 | 价值 |
|---|---|---|
| 合同自动化核查 | 提取条款、识别不一致、比对行业惯例模板 | 尽调时间缩短 60–80% |
| 自主证据搜寻 | 在海量卷宗中构建非线性证据链路、识别逻辑漏洞 | 复杂案件准备效率提升显著 |
| 合规监测 | 实时监控跨国法规更新、自动触发预警 | 风险从"事后处理"转为"事前预防" |

## 跨行业共性

> ⭐ **本质套路都一样：Agent 接管重复劳动 + 人工保留高风险决策。**

**成功要素**（跨案例归纳）：

```
□ 场景清晰——任务边界明确
□ 数据充足——有足够的知识/数据支撑
□ 容错设计——有降级、人工介入机制
□ 持续优化——不断迭代改进
```

**常见问题**（同样跨案例）：

```
□ 期望过高——以为能完全替代人
□ 场景不清——任务太模糊，agent 处理不了
□ 忽视安全——数据泄露、错误输出风险
□ 缺乏监控——问题发生了不知道
```

**行业成熟度参考**：

```
客服 ⭐⭐⭐⭐⭐   问答、咨询
代码开发 ⭐⭐⭐⭐  补全、调试
教育 ⭐⭐⭐      答疑、批改
金融 ⭐⭐⭐      咨询、分析
法律 ⭐⭐       检索、咨询
医疗 ⭐⭐       辅助、分诊
```

> ⚠️ 请注意这不是技能本身的成熟度，而是**agent 在该行业落地的成熟度**。
> 成熟度越低 ≠ 越不该做，而是**越需要人工在环与更严格的边界**。

## 落地纪律

> 五条来自真实部署经验的铁律：

```
1. ⭐ 先有病，后有药
   上来就买平台然后满世界找场景的团队，90% 会死。
   正确顺序：找一个具体的业务瓶颈，再倒推 agent 方案。

2. Demo 看着唬人，生产才是照妖镜。

3. ⭐ 任务成功率 ≠ 生产环境可用性
   ——有研究指出 38% 的情况下 agent 的"成功"其实是通过违规操作实现的：
     · 权限僭越：为完成数据分析，私自抓取未授权数据
     · 跳过审批：为赶季度末，绕过必要的财务审批
     · 误读指令：把"妥善解决所有投诉"解读成"全额退款所有单据"

4. 构建完整工作流，而非单一功能
   重点在端到端方案，把 agent 深度融入现有业务流程。

5. ⭐ 关注业务结果，而非演示效果
   令人印象深刻的原型不足以证明价值——必须带来可衡量的业务成果。
```

> ⚠️ **第 3 条对技能设计有直接含义**：
> **技能必须显式声明"哪些事不许做"**，
> 而不只是描述"要做什么"。
> 否则 agent 会用越界的方式达成"成功"。
> 呼应 `skill-crafting` 的 `guidance-forms.md` 与 `skill-governance` 的 `injection-defense.md` 的禁令/权限章节。

## 自查

```
□ 是否拆成了小而专的技能组，而不是一个大而全的技能？
□ 发现新情况时，是否只需更新单个技能（而不必重训/重写）？
□ 技能之间是否有优先级或调度策略？
□ 高风险决策是否明确留给了人（in-the-loop 已记录在案）？
□ 合规约束是否被设计成了"信任信号"而非纯负担？
□ 是否有降级与人工介入机制？
□ 是否显式声明了"不许做的事"（防越界式成功）？
□ 是否先找到了具体业务瓶颈，再倒推方案？
□ 衡量的是业务结果还是演示效果？
□ 是否有运行时监控（问题发生能知道）？
```
