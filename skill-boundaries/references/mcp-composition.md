## 三层栈各管什么

> 2026 年的 agent 生态收敛到了**三层互补的协议层**：

| 层 | 回答什么 | 本质 |
|---|---|---|
| **Skills** | **做什么（what to do）** | 流程性知识 |
| **MCP** | **怎么连（how to connect）** | 系统连接器 |
| **A2A** | **跟谁说（who to talk to）** | agent 间协作 |

> 一个 agent 可能：用 MCP server 查数据库 →
> 加载领域技能解读结果 → 通过 A2A 协调另一个 agent 触发下游动作。

**Skill vs Tool vs Plugin**：

| | 粒度 | 谁控制 |
|---|---|---|
| **Tool** | 原子函数（算复利、格式化货币） | agent 完全控制何时怎么用 |
| **Skill** | **可含多个工具 + 决策逻辑 + 提示模板 + 微工作流** | 调用即**把相当一部分控制权委托给技能内部逻辑** |
| **Plugin** | **分发机制**，把多个工具/技能捆一起 | — |

> **关键区分**：技能是**架构模式**，插件是**分发机制**。

## 五问决策树

> 走一遍能解决约 90% 的真实案例。
> **按"每个关注点走一次"，而不是"每个问题走一次"。**

```
Q1 需要实时外部数据吗？
   → 是：数据层用 MCP
Q2 流程本身是"配方/工作流/rubric"吗（不需要新鲜状态）？
   → 是：工作流放进 Skill
Q3 要碰"记录系统"吗（Linear / Notion / Stripe / GitHub / 生产库）？
   → 是：读写面必须 MCP
Q4 需要持久鉴权 / 超出单次会话的能力吗？
   → 是：MCP
Q5 是代码风格、文章结构、转录清洗这类吗？
   → 是：**几乎总是纯 Skill**
```

**例子**——"总结这个 PR 的改动并发一条带清单的评论"：

```
Q1: 需要真实 PR diff        → MCP（数据层）
Q2: 总结与生成清单是流程性的 → Skill（工作流）
→ 自然得到混合方案
```

**快速对照**：

| 需求 | 用什么 |
|---|---|
| "按我们的方式审 PR" | **Skill** |
| "在 GitHub 上打开这个 PR" | **MCP** 或 `gh` CLI |
| "每周审一次博客 SEO" | **Skill + GSC MCP** |
| "记住我们的 TypeScript 约定" | **CLAUDE.md + skills** |

## Skill stack（技能栈）

> **技能栈 = 为某个工作流预先配好的一组 MCP server + 技能组合。**

就像 Web 开发者选 React + Postgres + Vercel，
AI 增强的开发者选一组 MCP server，
**在一次配置里给助手数据库访问、代码管理、部署能力**。

**为什么用栈而不是逐个挑**：

| 好处 | 说明 |
|---|---|
| **内聚** | 栈里的 server 是互补的——Full-Stack Dev 栈把 Neon（数据库分支）+ GitHub（PR）+ Sentry（错误追踪）配一起，因为三者天然串成一条线 |
| **降低决策疲劳** | MCP 生态已有**上万 server**，从栈开始而不是逐个评估 |

**选型三因素**：主工作流 · 团队规模 · 愿意承受的配置复杂度。

| 团队 | 建议 |
|---|---|
| 单人 | **紧凑栈，3 个组件** |
| 5 人以上 | 加 Slack（沟通）+ Linear（项目管理）类集成 |

> ⚠️ **MCP server 控制在 3–5 个**——多了会 token 膨胀。
> 读密集型操作**优先用 Bash/CLI**，更省 token。

## 三种已跑通的混合模式

> 共同主线：**MCP 持有对实时状态的访问；Skill 持有"拿它做什么"的主张。**

### ① Stripe MCP + 财务报告技能

- MCP = API 网关：鉴权、限流、实时数据
- 技能 = 流程层：*"当用户说'退他们上一笔款'，先查客户、找到最近一次成功扣款、确认后再退"*
- **没有技能**，模型每次都要自己推流程；**没有 MCP**，你真退不了款
- 实测：47 步人工提示 → 技能 + MCP，**平均 14 轮降到 4 轮，30 次试跑零错误**

### ② Notion hosted MCP + PRD 转原型技能

- MCP 持有记录系统（真实文档）
- 技能编码"如何把 PRD 翻译成脚手架代码、生成哪些文件、要标注哪些假设"

### ③ GitHub MCP + 代码审查技能

- MCP 取 diff、文件上下文、已有评论
- 技能是审查者的剧本：**什么要标、什么可忽略、用什么严重度 rubric、最终评论怎么排版**

## 技能是新式工作流节点

**传统工作流**：

```
Trigger → API 节点 → 条件 → API 节点 → Done
静态图，确定性执行
```

**基于技能的工作流**：

```
Agent 收到目标
  → 加载相关技能（渐进式披露）
  → 技能引用 MCP 工具（数据库/API/文件系统）
  → Agent 对结果推理
  → 依据上下文调整下一步
  → 重复直到达成目标
```

> ⚠️ **根本区别**：在 Zapier 里**工作流图就是产品**——你画好它，它严格照画的执行。
> 在技能模型里，**agent 才是编排者**。

**一个技能可以编排多个 MCP server**——客服技能可能同时用 CRM、知识库检索、工单管理三个 server。

**实测落地情况**（混合但在增长）：企业报告**工作流周期快 20–30%**，尤其后台运营场景。

## 趋势：MCP 直接分发技能

> MCP 工作组正在标准化**通过 MCP 提供 SKILL.md**
> （`skill://` resources）——
> **一个包同时分发流程 + 工具**给 Claude Code、Cursor、Copilot。

这意味着技能与 MCP 的分层会更模糊，但**职责划分不变**：

```
MCP = 手（连接）
Skill = 脑（流程）
```

> 上一版提到的战略判断依然成立：
> **MCP server 趋向商品化**（第十五个 Postgres MCP 增量很小）；
> **技能才是差异化所在**——两个技能用同样的 MCP，可以编码完全不同的专业知识。
