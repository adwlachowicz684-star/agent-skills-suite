## 六类不该做成技能的事

**① 一次性任务**

```
□ 只做一次的事 → 直接写提示词
□ ⭐ 技能的启动门槛：过去做过 5 次以上、未来还做 10 次以上
```

**② 纯风格与语气偏好**

```
□ ⭐ 只改语气或格式的东西属于用户偏好或系统提示，
   不是技能
□ 例："回复要简短" → 用户偏好
```

**③ 通用概念解释**

```
□ 教模型"什么是 PDF/HTTP/JSON" → 白占 token
□ ⭐ 技能提供的是模型缺的上下文
```

**④ 会过时的具体信息**

```
□ "截至 2024 Q4…" 很快腐烂
□ ⭐ 用脚本取实时数据，或干脆不写
□ 同理：不要把库源码粘进技能
```

**⑤ 大而无当的"全能"技能**

```
□ 捆绑设计、规划、实现、测试、部署
□ ⭐ 拆成聚焦的原语，靠组合完成工作流
```

**⑥ 只是把 prompt 换个地方放**

```
□ ⭐ "把 SKILL.md 理解成用 Markdown 写角色设定"
   → 只是把一团乱的 Prompt 变成一团乱的 Markdown
```

呼应 `prompt-migration.md`（**`skill-authoring`**）：
真正的 SKILL.md 是**技能封装协议**，不是 Markdown 化的角色设定。

## 判据：一致性 vs 创造性

> ⭐ **判断标准：一致性是否比创造性重要？**

```
是 → 做成技能
要的是创意 → ⭐ 别做，会束缚它
```

**一致性优先的典型**：

```
□ CRM 字段填写规范
□ 代码评审检查单
□ 报告结构
□ ⭐ 强依赖组织内部语境的（脱离就失真）
```

**创造性优先的典型**：

```
□ 头脑风暴
□ 创意文案的第一稿
□ 探索性分析
□ ⭐ 需要"意外之喜"的场合
```

呼应 `domain-biz` SKILL.md 主文件的同一条原则。

## 该用别的机制的四种情况

| 情况 | 用什么 |
|---|---|
| ⭐ 每轮都要生效的硬规则 | **CLAUDE.md / AGENTS.md** |
| ⭐ 含"绝不"且机器可检查 | **Hook**（不是提示词） |
| ⭐ 需要连外部系统 | **MCP server** |
| ⭐ 需要补领域知识（事实性） | **RAG / references 检索** |

呼应 `claude-md-vs-skill.md`（**`skill-crafting`**）的四选一判据：

```
每轮为真          → CLAUDE.md
当做 X 时         → Skill
含"绝不"          → Hook
该读不该守        → docs
```

以及 `mcp-vs-skill-decision.md`（**`skill-selection`**）的五问决策法。

**还有一个常被忘的**：

```
□ ⭐ 关键流程必须用 Command（100% 触发）
   ——辅助能力才用 Skill（可能不触发）
```

## 一条反向检查

> ⭐ **"如果这件事没有技能，agent 会做得多差？"**

```
几乎一样好 → ⭐ 别做技能（做了也不产生 lift）
明显更差   → 值得做
```

呼应 `skill-lift-eval.md`（**`skill-evaluating`**）与
`failure-modes.md` 的实证：

```
□ 39/49 个技能零提升（SWE-Skills-Bench）
□ ⭐ 无技能 vs 全技能在 CTF 上只差 8.9pp
□ ⭐ 环境反馈带宽高时，技能反而成了干扰
```

**推论**：

> ⭐ **你的工具输出越保真，技能库就该越薄。**

**以及一条关于组织语境的**：

```
□ ⭐ 强依赖组织内部语境的东西尤其适合做成技能
   ——因为通用模型不知道你们的口径
□ 反过来：完全通用的流程，模型的先验已经够用
```
