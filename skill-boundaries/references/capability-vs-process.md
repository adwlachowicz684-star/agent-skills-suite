# 能力原语 vs 流程原语

> 判断"该不该做成技能"之后，还有第二问：
> **做成哪一类技能？**

## 两类原语

```
能力原语（capability primitive）
  ⭐ 需要新工具/新能力才能做到
  ——原本完全做不到的事

流程原语（process primitive）
  ⭐ 需要更好的方法论
  ——能做到，但做得不对/不稳定
```

呼应 `authoring-workflow.md`（**`skill-authoring`**）阶段一：
**先判断是能力缺口还是流程缺口**。

## 判定方法

> ⭐ **问："没有这个技能，agent 是做不到，还是做不好？"**

```
做不到 → 能力原语 → ⭐ 多半需要工具/MCP，不是纯技能
做不好 → 流程原语 → ⭐ 正是技能的用武之地
```

> ⭐ **这个区分很重要**：
> 如果你的需求是"做不到"，那你需要的其实是工具连接，
> 光写技能解决不了。
>
> 呼应 `mcp-vs-skill-decision.md`（**`skill-selection`**）的
> 五问第 1、2 问——需要连外部系统就倾向 server。

**"做不好"的三种表现**：

```
□ 漏步骤
□ 输出形状不对
□ ⭐ 用了通用做法而不是你们的做法
```

第三项是最有价值的技能目标——
呼应 `frontend-ui-skills.md`（**`skill-domain-eng`**）：
**"模型会写但写得像所有人"**。

## 两类的写法差异

| | 能力原语 | 流程原语 |
|---|---|---|
| 主体内容 | ⭐ 工具怎么调、参数怎么传 | ⭐ 步骤顺序、判定条件 |
| 关键风险 | 工具不可用/参数错 | ⭐ 跳步、形状不对 |
| 该放哪 | `scripts/` + MCP | SKILL.md 正文 + `references/` |
| 验证 | ⭐ 工具返回成功 + 输出校验 | ⭐ 每一步的可判定检查点 |
| 失败处理 | 重试、熔断、降级 | ⭐ 回退到上一检查点 |

## 一个容易搞混的例子

**"分析这份 CSV 并画图"**：

```
拆开看：
  □ 读 CSV、画图   → 模型本来就会（能力已具备）
  □ ⭐ 但"用我们公司的配色、按我们的口径算同比"
     → ⭐ 这是流程/规范缺口

判定：流程原语 → 适合做成技能
```

**"查询我们的订单数据库"**：

```
□ 模型连不到库 → ⭐ 做不到
判定：能力缺口 → ⭐ 需要 MCP server
                + 一个流程技能教它"查什么、怎么解读"
```

> ⭐ 后者正是 `mcp-vs-skill-decision.md` 说的
> **"薄 server 提供访问 + 技能提供工作流"**。

## 与九种类型的关系

呼应 `skill-types.md`（**`skill-authoring`**）的九种分类：

```
偏能力的：
  库和 API 参考、数据获取与分析、基础设施运维

偏流程的：
  产品验证、业务流程自动化、质量审查、CI-CD 部署、Runbook

两者都强的：
  ⭐ 代码脚手架（既需要工具，也需要"按我们的模板"）
```

## 对创作顺序的影响

```
流程原语：
  ⭐ 先手工跑一遍，记录你反复补充的上下文 → 那就是技能内容

能力原语：
  ⭐ 先确认工具可用（脚本能跑、MCP 能连），再写技能
```

呼应 `how-to-guide.md`（**`skill-authoring`**）的
**先手动，再封装**。
