## 1. ⭐⭐⭐⭐ 一句话判据

```
⭐⭐⭐⭐⭐ "想让 agent ⭐ 表现得不同 → 用技能。
⭐⭐⭐⭐⭐ ⭐ 想让 agent ⭐ 做到它自己做不到的事 → 用 MCP。"
```

| | ⭐ 技能 | ⭐ MCP |
|---|---|---|
| 层 | ⭐⭐⭐ 行为 / 推理 | ⭐⭐⭐ 协议 / 连接 |
| 给 agent 什么 | ⭐⭐⭐ 知识、工作流、判断 | ⭐⭐⭐ 外部能力（API、查询） |
| 需要跑服务 | ⭐⭐⭐⭐ 否 | ⭐⭐⭐ 是 |
| 装的是什么 | ⭐⭐⭐ 一个文件 | ⭐⭐⭐ 一个可调用函数的服务 |
| 设置复杂度 | ⭐⭐⭐⭐⭐ 丢个文件 | ⭐⭐⭐ 配置并运行服务 |
| 认证 | ⭐⭐⭐ 不需要 | ⭐⭐⭐ 每个服务都要凭据 |
| 延迟 | ⭐⭐⭐ 零（读文件） | ⭐⭐⭐ 每次调用一次网络往返 |

**一组可直接判的例子**：

```
"遵循我们的提交规范"          → ⭐ 技能
"在 #deployments 发条消息"     → ⭐ MCP
"按我们的编码标准审 PR"        → ⭐ 技能
"为这个 bug 建一张 Jira 单"    → ⭐ MCP
"跑一遍我们的发布清单"         → ⭐⭐⭐ 技能（并可能引用 MCP 工具）
"从 Datadog 查生产指标"       → ⭐ MCP
```

> ⭐⭐⭐⭐⭐ 决策检查表（最简版）：
> ```
> 需要⭐ 实时的当前数据 ⭐ 或⭐ 真实的外部动作吗？
>   是 → MCP
>   否 → ⭐ 是"一个流程 / 规则 / 上下文"吗？
>        是 → 技能
>        否 → ⭐ 重新想清楚你到底要什么
> ```
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这⭐ 与我们已有的⭐ `five-layer-choice.md` 那条
> "⭐ 指令里出现 query / fetch / look up / current state → ⭐⭐⭐⭐⭐ ⭐ 几乎肯定需要 MCP"
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 完全同源——⭐ 两个独立来源，⭐⭐⭐⭐⭐ ⭐ 同一判据。

## 2. ⭐⭐⭐⭐⭐ 失败方式的不对称

> ⭐⭐⭐⭐⭐ **"⭐ MCP 工具失败⭐ 是可见的：服务挂了你会拿到连接错误，
> ⭐⭐⭐⭐⭐ ⭐ 查询超时你会拿到超时，⭐ 认证过期你会拿到 401——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ ⭐ 标准的服务监控⭐ 会抓住所有这些。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 而⭐ 技能失败⭐ 是隐形的。"**

| | ⭐⭐⭐ 失败时发生什么 | ⭐⭐⭐⭐ 能否被发现 |
|---|---|---|
| ⭐ MCP | ⭐⭐⭐⭐⭐ 报错、超时、401 | ⭐⭐⭐⭐⭐ 现有基础设施监控已覆盖 |
| ⭐⭐⭐ 技能 | ⭐⭐⭐⭐⭐ **什么都没发生**——没有错误、没有日志 | ⭐⭐⭐⭐⭐ 默认没有任何监控 |

> ⭐⭐⭐⭐⭐ 那段描述⭐ 极其精准，⭐⭐⭐⭐⭐ ⭐⭐⭐ 值得⭐ 完整引用：
> ⭐⭐⭐⭐⭐ **"⭐ agent 只是⭐ 在没有该技能指令的情况下⭐ 继续跑，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 输出⭐ 微妙地错了——⭐ 或者⭐ 完全错了——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 而⭐ 这种错⭐ 很难被发现。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐ **没有错误。没有告警。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 用户⭐ 甚至可能⭐ 不知道⭐ 那个技能⭐ 本该触发。**"**
>
> ⭐⭐⭐⭐⭐ 一个具体的例子：
> ⭐⭐⭐⭐⭐ **"⭐ 你完全可以有一份⭐ 写得完美的发布技能，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 它⭐ 因为⭐ 用户说了'ship the new version'⭐ 而没有说'deploy to production'
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 就⭐ 静默地⭐ 没有触发。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ agent ⭐ 照常跑，⭐⭐⭐⭐⭐ ⭐ 只是⭐ 没按你的流程走。"**
>
> ⭐⭐⭐⭐⭐ 这条⭐ 把我们散落各处的⭐ 多条结论⭐ 一次性⭐ 收进了⭐ 一个框架：
> ```
> 静默失败          ←→ three-failure-modes
> 结构正确的废话    ←→ 监控全绿但内容错
> 遥测的盲区        ←→ ⭐⭐⭐⭐⭐ 平台记录"被调用了"，⭐ 不记录"干得好不好"
> ⭐⭐⭐⭐⭐ 本条            ←→ ⭐⭐⭐⭐⭐ ⭐ 而⭐ 它⭐ 给出了⭐ 原因：⭐⭐⭐⭐⭐ ⭐⭐⭐ 技能是文本，⭐⭐⭐⭐ ⭐ 没有健康检查这一说
> ```
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐⭐ 最锋利的一句：
> ⭐⭐⭐⭐⭐ **"⭐ 没有任何健康检查⭐ 能回答'这个流程现在是错的了'。"**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 推论：⭐⭐⭐⭐⭐ **技能需要的⭐ 不是"更多监控"，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 而是⭐ 一种⭐ 现有监控⭐ 天然⭐ 不提供的⭐ 东西——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 即⭐ "本该触发却没触发" 的⭐ 检出能力**
> （这也正是 `skill-observability.md` 里⭐ 决策日志⭐ 存在的理由）。

## 3. ⭐⭐⭐⭐ Token 的不对称

> ⭐⭐⭐⭐⭐ **"⭐ 技能⭐ 空闲时很便宜：⭐⭐⭐⭐⭐ ⭐ 只有它的 description ⭐ 留在上下文里，⭐⭐⭐⭐⭐ ⭐⭐⭐ 直到⭐ 需要时才加载。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ ⭐ 而 MCP 服务器⭐ 不是：
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ **每一个已连接的服务器，⭐ 它的工具定义⭐ 都会⭐ 加载进⭐ 每一次请求。**"**

```
⭐⭐⭐⭐⭐ 推论：⭐⭐⭐⭐⭐ ⭐ 十二个技能 ⭐ 比 ⭐ 十二个服务器 ⭐ 便宜得多
⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 所以：⭐⭐⭐⭐⭐ ⭐⭐⭐ 剪掉闲置的 MCP 服务器
              = ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 快速降低 token 占用的⭐ 最省事办法
```

> ⭐⭐⭐⭐⭐ 这⭐ 是⭐ 一条⭐ 此前完全没覆盖过的⭐ 成本维度：
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 我们此前⭐ 反复算过 ⭐ 技能的常驻成本（⭐ 30–50 tokens/个），
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 但⭐ 从没⭐ 把它⭐ 跟 MCP 的⭐ 常驻成本⭐ 放在⭐ 同一张表上比。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ **两者都是"常驻"，⭐⭐⭐⭐⭐ ⭐⭐⭐ 但量级不同、且性质不同：
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 技能常驻的是⭐ 一句话，⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 服务器常驻的是⭐ 一整套工具定义。**
>
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 顺带一条⭐ 设计提醒：
> ⭐⭐⭐⭐ **"MCP 工具的响应可能很冗长。⭐⭐⭐⭐⭐ ⭐ 设计输出时要简洁：
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐ 返回 agent 需要的，⭐ 而不是⭐ 你有的。"**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 这⭐ 与 `three-crash-scenes.md` 那起
> "⭐ 脚本输出 3 万字塞爆上下文"⭐ 是⭐ 同一个错误的⭐ 两个发生位置：
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ **输出侧的浪费，⭐⭐⭐⭐⭐ ⭐⭐⭐ 在脚本和 MCP 上⭐ 都同样致命。**

## 4. ⭐⭐⭐⭐ 两层架构：技能编排，MCP 执行

> ⭐⭐⭐⭐⭐ **"⭐ 最有效的配置⭐ 用⭐ 技能⭐ 作编排者、⭐⭐⭐⭐⭐ ⭐⭐⭐ ⭐ MCP 工具⭐ 作执行者。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 技能⭐ 定义⭐ 做什么 ⭐ 和 ⭐ 什么时候做；
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ MCP 工具⭐ 提供⭐ 怎么做。"**

```
一个生产部署工作流：
  技能触发："deploy to production" / "ship it" / "push to prod"
  技能定义的顺序：跑测试 → 查 CI → 建 release tag → 部署 → 健康检查 → 通知
  其中多步需要 MCP：GitHub 建 release、Cloudflare 触发部署、Slack 发通知

⭐⭐⭐⭐⭐ ⭐ 没有技能 → agent 不知道你的发布流程
⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 没有 MCP   → agent 无法与 GitHub/Cloudflare/Slack 交互
⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 两者都要
```

> ⭐⭐⭐⭐⭐ 一个⭐ 真实系统的⭐ 结构佐证（Brad Feld 的 CompanyOS）：
> ⭐⭐⭐⭐ **12 个技能文件（定义系统如何运作）+ 8 个 MCP 服务器（提供实时工具访问）**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 评语：⭐⭐⭐⭐⭐ "⭐ 技能⭐ 加载便宜⭐ 且⭐ 定义确定性行为；
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ MCP 服务器⭐ 处理⭐ 动态的、有副作用的 ⭐ 工作。"
>
> ⭐⭐⭐⭐⭐ 最锋利的⭐ 一句总结（两个来源各说了一次）：
> ```
> ⭐⭐⭐⭐⭐ "⭐ 没有流程的工具 → ⭐ 高效地做错事的 agent。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 没有工具的流程 → ⭐ 无用但正确地⭐ 描述事情的 agent。"
> ```
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这⭐ 与我们已有的⭐ 多条⭐ 严丝合缝：
> ```
> 技能内容会变成子代理提示词，⭐⭐⭐⭐⭐ 只写准则 = ⭐ 空输出（无用但正确）
> ⭐⭐⭐⭐⭐ 确定性边界：⭐⭐⭐⭐⭐ ⭐ Hooks 用于⭐ 不可信任模型遵守的事（执行侧）
> ```
>
> ⭐⭐⭐⭐⭐ 还有一个⭐ 此前没收过的⭐ 观察：
> ⭐⭐⭐⭐⭐ **"在 headless 和 CI 场景中——⭐⭐⭐⭐⭐ ⭐⭐⭐ 没人在旁边⭐ 纠正一次糟糕的即兴发挥——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 技能层⭐ 比人们预想的⭐ 更重要。"**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这⭐ 正好⭐ 补上了 `ci-skill-validation.md` 那条
> "⭐ CI 不能测行为"⭐ 的⭐ 另一半：⭐ **正因为 CI 里没人看着，⭐⭐⭐⭐⭐ ⭐⭐⭐ 技能才更要写好。**

## 5. ⭐⭐⭐ 四个常见错误

```
① ⭐⭐⭐⭐⭐ 为静态知识建 MCP 服务器
   ⭐⭐⭐⭐⭐ ⭐ 信息不会变 → ⭐ 不需要一个跑着的进程 → ⭐⭐⭐⭐⭐ ⭐⭐⭐ 放进技能文件

② ⭐⭐⭐⭐⭐ 为实时操作写技能文件
   ⭐⭐⭐⭐⭐ ⭐ "⭐ 描述'如何检查状态'的⭐ 技能文件，
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ ⭐ 不能替代 ⭐ 真正通过 MCP ⭐ 去检查它。"

③ ⭐⭐⭐⭐ 在每次会话里加载全部技能
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ 技能便宜，⭐ 但不是免费 → ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 按需加载，不是预加载

④ ⭐⭐⭐⭐ 设计 MCP 时忽略 token 成本
   ⭐⭐⭐⭐ ⭐⭐⭐ 响应要简洁：⭐⭐⭐⭐⭐ ⭐⭐⭐ 返回需要的，不是全部的
```

> ⭐⭐⭐⭐⭐ 第 ② 条⭐ 最值得展开，⭐⭐⭐⭐⭐ ⭐⭐⭐ 因为它是⭐ 一个⭐ 极易犯的⭐ 认知错误：
> ⭐⭐⭐⭐⭐ **"教它怎么查" ⭐ 被当成了 ⭐ "让它查到了"。**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 这⭐ 与我们已有的⭐ 一条⭐ 完全同构：
> ⭐⭐⭐⭐⭐ **"技能无法触及⭐ 上下文中⭐ 不存在的数据"**——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 换个说法就是：⭐ 技能⭐ 无法⭐ 凭描述⭐ 凭空产生⭐ 数据。
>
> ⭐⭐⭐⭐ 还有一条⭐ 关于⭐ 不确定时怎么办：
> ⭐⭐⭐⭐⭐ **"⭐ 不确定就从技能开始——⭐⭐⭐⭐⭐ ⭐⭐⭐ 它几分钟就能写出来。"**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 这⭐ 与 `orchestrator-timing.md` 的
> "⭐ 先做第一个技能、再做第二个，⭐⭐⭐⭐⭐ ⭐⭐⭐ 搬了三次才写编排器"⭐ 是⭐ 同一策略：
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ **从便宜的那一层起步，⭐⭐⭐⭐⭐ ⭐⭐⭐ 让证据⭐ 决定⭐ 要不要升级。**

## 速查

```
□ ⭐⭐⭐⭐⭐ 一句判据：⭐ 让 agent 表现不同→技能；⭐ 让它做到做不到的事→MCP
   决策表：需要"实时当前数据或真实外部动作"？是→MCP；否则"流程/规则/上下文"？是→技能
□ ⭐⭐⭐⭐⭐ 失败不对称：⭐⭐⭐⭐⭐ MCP 报错(连接/超时/401)，现有监控全覆盖；
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 技能⭐ 什么都没发生——无错误、无日志、无告警
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 用户甚至可能不知道它本该触发
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 没有任何健康检查能回答"这个流程现在是错的了"
□ ⭐⭐⭐⭐ Token 不对称：⭐ 技能空闲时只有 description 在上下文；
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ ⭐ 每个已连接 MCP 服务器的⭐ 工具定义⭐ 加载进⭐ 每一次请求
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 十二个技能 << 十二个服务器 → ⭐ 剪闲置服务器是最省事的降本
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ MCP 响应同样要简洁：⭐ 返回 agent 需要的，不是你有的
□ ⭐⭐⭐⭐ 两层架构：⭐ 技能编排（做什么/何时做）+ ⭐ MCP 执行（怎么做）
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ "没有流程的工具→高效地做错事；没有工具的流程→无用但正确地描述"
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ headless/CI 场景没人纠正即兴发挥 → ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 技能层比预想更重要
□ ⭐⭐⭐ 四错：为静态知识建 MCP · ⭐⭐⭐⭐⭐ ⭐ 为实时操作写技能（"教它怎么查"≠"让它查到了"）
   ⭐⭐⭐⭐ 每次会话加载全部技能 · ⭐⭐⭐⭐ 忽略 MCP token 成本
□ ⭐⭐⭐⭐⭐ 不确定就从技能开始——⭐⭐⭐⭐⭐ ⭐⭐⭐ 它几分钟就能写出来（从便宜那层起步）
```

**一句话**：

> ⭐⭐⭐⭐ **技能与 MCP 的失败方式完全相反——MCP 挂了会报错且被现有监控抓住，技能失效则"什么都没发生"、没有错误也没有告警，用户甚至不知道它本该触发；所以两层要分工：技能编排（做什么、何时做），MCP 执行（怎么做），而没有流程的工具会高效地做错事、没有工具的流程只会无用但正确地描述事情。**
