## 1. ⭐⭐⭐⭐⭐ 绕过路径是为紧急情况设计的，而紧急情况最不该绕过

每个绕过机制都有正当的诞生理由：

```
--no-verify     → 修一个线上事故，来不及跑全套
紧急发布通道     → 半夜修故障
admin 覆盖开关   → 配置写错了，先恢复服务
```

> ⭐⭐⭐⭐⭐ 这些理由**全都是真的**。问题是绕过的**代价分布**恰好是反的。

考虑一下绕过发生时的状态：

```
平时：        时间充裕 · 上下文完整 · 有人能 review
⭐⭐⭐⭐⭐ 紧急时：时间压力 · 上下文残缺 · 只有一个人 · 疲劳
```

> ⭐⭐⭐⭐⭐ **而技能失效恰恰在紧急时最危险**——
> 因为那时人最依赖自动化替他兜住，也最没有能力自己复核。

于是绕过的真实含义不是"跳过一次检查"，是：

> ⭐⭐⭐⭐⭐ **在最没有能力人工复核的时刻，取消唯一一道自动复核。**

这和《`skill-evaluating/references/permission-set-split-criteria.md`》里那句
"Skill 里写'只读'不会把一个可写 Token 变成只读"是同一类错误——
⭐⭐⭐⭐⭐ **把保护设计成"在需要它的时候最容易被关掉"。**

三条约束，按有效性排序：

**① ⭐⭐⭐⭐⭐ 绕过必须产生一个工作项，不是产生一条日志**

```
绕过 → 自动开 issue，指派给绕过者，24h 内必须补跑并关闭
```

日志会被写、被归档、被遗忘；工作项有状态、有 owner、有到期提醒。

**② ⭐⭐⭐⭐ 绕过要有配额，且配额可见**

"本月已用 2/3 次紧急发布"这个数字出现在界面上，
⭐⭐⭐⭐ 它把"紧急"从一种**感受**变成一个**可计量的资源**。

**③ ⭐⭐⭐ 绕过的人不能是自己批准自己**

两个人（哪怕只是"在群里说一声"）的价值不在第二个人更懂，
在于⭐⭐⭐⭐⭐ **"有人知道这件事发生了"**——这和下一条的留痕是同一件事。

## 2. ⭐⭐⭐⭐⭐ 调阈值是最容易的"修"，于是每次都是调阈值

告警响了，可选的应对有三个：

```
① 修被监控的东西（贵、慢、可能不知道怎么修）
② ⭐⭐⭐⭐⭐ 调阈值（一行配置、立刻生效、告警马上安静）
③ 关掉这条告警（明显是错的，很少有人做）
```

> ⭐⭐⭐⭐⭐ **② 是唯一一个"立刻看到效果"的选项，于是它几乎总是被选中。**
> 而③因为看起来太极端，反而很少发生——②就是③的分期付款。

过程：

```
告警响 → 阈值 5% → 8%（"最近量大，正常波动"）
       → 12%（"这个指标本来就不准"）
       → 20%（"别再报了，我们每周看一次报表"）
```

> ⭐⭐⭐⭐⭐ **每一次上调都有具体理由，且理由当时都成立。**
> 而阈值在 20% 时，"告警"这个功能实际上已经不存在了——
> 只是配置文件里还写着它，监控面板上还画着那条线。

它与 flaky 门禁的失效链条完全同构，差别在于：

| | flaky 门禁 | ⭐⭐⭐⭐⭐ 阈值上浮 |
|---|---|---|
| 手段 | 重跑 / quarantine | 调数字 |
| ⭐⭐⭐⭐⭐ 每次都合理吗 | 是 | ⭐⭐⭐⭐⭐ 是 |
| 终点 | 红灯被忽略 | ⭐⭐⭐⭐⭐ **指标失去意义** |
| 看得出吗 | ❌ | ❌ |

## 3. ⭐⭐⭐⭐ 绕过必须留痕，而痕要落在能被看到的地方

留痕的位置决定它有没有用：

| 位置 | 有人看吗 |
|---|---|
| 日志文件 | ⭐ 只有排查时会翻 |
| ⭐⭐⭐ PR/issue 评论区 | ⭐⭐⭐⭐ 参与这件事的人会看到 |
| ⭐⭐⭐⭐⭐ 变更记录（changelog） | ⭐⭐⭐⭐⭐ 后来接手的人会看到 |
| ⭐⭐⭐⭐⭐ 指标面板上的标注线 | ⭐⭐⭐⭐⭐ 看报表的人会看到 |

最有价值的是最后一条：⭐⭐⭐⭐⭐ **在指标曲线上把"绕过发生的时刻"标出来**。

```
触发率 ────────────╲
                    ╲___╱────
                     ↑
                  绕过上线
```

> ⭐⭐⭐⭐⭐ 它让"这次下降"和"那次绕过"在空间上相邻。
> 否则三个月后看报表的人只会看到"触发率一直在掉"，
> 而他没有任何办法知道那次绕过是起点——**因为日志里的那条记录早就不在视野里**。

这与《`skill-versioning/references/adr-lightweight.md`》里
"记在哪比记什么重要"是同一条结论：**它必须在你会看到它的地方**。

## 4. ⭐⭐⭐⭐⭐ 阈值调到 100% 时，告警消失但问题还在

这条是第 2 节的终点，值得单独拿出来，因为它有一种特别干净的表现形式：

```yaml
alert:
  threshold: 0.05   # 5% 失败率告警
# ↓ 三个月后
alert:
  threshold: 1.0    # 100% —— 永远不会触发
```

> ⭐⭐⭐⭐⭐ **这是"删除告警"的唯一一种看起来不像删除的形式。**

删掉一条告警会有人问"为什么删了"；
把阈值改成 1.0 的 diff 是一行数字，review 时看到的判断是"放宽一点"。

判据很简单，且可以自动检查：

```bash
# 阈值 >= 物理上界 或 >= 1.0 的告警 = 已失效的保护
grep -rn "threshold" config/ | awk -F: '$2+0 >= 1.0'
```

> ⭐⭐⭐⭐⭐ 加进 CI。和"名字含 deploy 就强制 disable-model-invocation"是同一手法：
> **把反复强调的纪律变成一条可 grep 的机械检查**——
> 因为靠人记住的东西，在第三次紧急情况下一定会被忘掉。

还有一个更隐蔽的变体：⭐⭐⭐⭐ **阈值没变，但指标的定义变了**。

```
原：失败率 = 失败次数 / 总次数
改：失败率 = 失败次数 / 成功次数      ← 分母变了
```

第二条分母更大，于是同一个阈值下告警更少。
⭐⭐⭐⭐⭐ 它和"改语义必须改字段名"是同一个错误，只是发生在指标层——
而指标层的语义变更比字段层更难发现，因为**没有人会去 review 一个数字的定义**。

## 5. 三种"看起来在修实际在关"的动作

汇总成一个表，便于在 review 时识别：

| 动作 | 看起来 | ⭐⭐⭐⭐⭐ 实际 |
|---|---|---|
| `continue-on-error: true` | 让流水线不阻塞 | ⭐⭐⭐⭐⭐ 取消阻断 |
| 阈值上调 | 减少误报 | ⭐⭐⭐⭐⭐ 分期关闭告警 |
| ⭐⭐⭐⭐⭐ 加白名单例外 | 处理特殊情况 | ⭐⭐⭐⭐⭐ 为最常见的那种情况关掉检查 |

第三条最值得说，因为它通常是**从一条真实的例外开始的**：

```
"这个技能历史遗留，先加白名单" → 白名单里有 1 个
"这个也是" → 3 个
"这几个都是同一批" → ⭐⭐⭐⭐⭐ 12 个（占总数 30%）
```

> ⭐⭐⭐⭐⭐ 而检查仍然在跑、仍然显示通过——它只是不再检查那 30%。

三条约束：白名单**必须有理由字段**、**必须有到期时间**、
⭐⭐⭐⭐⭐ **超过总数 10% 就必须停下来查根因**（而不是继续加）。
最后一条与"flaky 标记超过 10% 该查系统性原因"、"红线膨胀"完全一致——
⭐⭐⭐⭐⭐ **三个不同领域的豁免机制，都在这同一个数字上开始失去意义。**

## 6. 自检

- [ ] ⭐⭐⭐⭐⭐ 每个绕过机制的存在理由还成立吗？（理由是真的，但它是为紧急设计的）
- [ ] ⭐⭐⭐⭐⭐ 绕过产生的是工作项还是日志？（日志 = 没人跟进）
- [ ] ⭐⭐⭐⭐ 绕过配额可见吗？（不可见的配额等于无限）
- [ ] ⭐⭐⭐⭐⭐ 有阈值 ≥ 1.0 的告警吗？（= 已失效的保护）
- [ ] ⭐⭐⭐⭐⭐ 这条告警的阈值，过去半年被上调过几次？每次的理由还成立吗？
- [ ] ⭐⭐⭐ 指标的定义变过吗？（分母变了 = 同阈值下告警更少，且没人 review）
- [ ] ⭐⭐⭐⭐⭐ 白名单占总数多少？每条有理由和到期时间吗？
- [ ] ⭐⭐⭐⭐⭐ 曲线上能看出"绕过发生的时刻"吗？（三个月后没人会对得上）
