## 1. ⭐ 触发策略：增量精准，不全量跑

```
按代码变更目录、服务模块，自动映射对应业务域的技能集合
只跑相关回归，控制执行时长
```

**分级触发**：

| 场景 | 触发范围 |
|---|---|
| 普通提交 | ⭐ 核心 P0 级技能 |
| 合并请求 | ⭐ P0 + P1 级全量 |
| 发布前 | 完整业务域全量 |

---

## 2. 流水线编排要点

```
① ⭐ 环境前置校验
   执行前先校验测试环境可用性、依赖服务状态
   ⭐ 环境异常直接终止，避免无效执行

② 数据准备
   自动构造测试数据，或从基准数据环境克隆
   ⭐ 保证每次执行数据一致

③ ⭐ 技能并行执行
   无依赖的技能并行跑，大幅缩短整体回归时长

④ 结果聚合
   统一收集所有技能执行结果，生成结构化报告
   包含：通过率 · 失败明细 · 耗时 · 日志链接

⑤ 门禁判定（见下）

⑥ 数据清理
   执行完成后自动清理测试数据，不污染环境
```

---

## 3. ⭐ 门禁判定

```
⭐ P0 级技能通过率必须 100%，不通过直接阻断合并
⭐ P1 级通过率低于阈值（如 95%）触发告警，需人工确认
```

> ⭐ 分级的关键：**P0 和 P1 的后果必须不同**。
> 这与 `code-review-skill-instance.md` 那条
> "FAIL 阻断 / WARN 不阻断必须有不同后果，否则分级没意义"是同一条原则。

---

## 4. ⭐ 幂等与环境隔离

```
幂等性保障  ⭐ 同一流水线多次重跑，不产生重复数据、不重复计费
环境隔离    每个 CI 任务运行在独立沙箱，互不干扰
失败重试    ⭐ 瞬时失败自动重试 1 次，减少环境波动导致的误拦截
结果回传    ⭐ 测试结果直接评论到合并请求页面，研发不用跳转平台查看
```

> ⭐ "重试 1 次"这个数字很克制——
> 对应 `error-handling.md` 的"任何重试都必须声明最大次数"。
> **重试多次会把环境波动放大成噪音**。

## 5. 核心要解决的问题

> ⭐ **技能本身会持续迭代（优化逻辑、新增参数、升级依赖），
> 很容易出现"改了新功能，坏了老能力"的退化问题。**

这正是 `version-strategy.md` 那条"没有版本和 CHANGELOG，
就无法把一次失败归因于'这次改坏了'"在 CI 层的解法——
**自动化回归校验框架**。

**MCP 协议层在这一架构里的三个作用**（不是简单 API 转发）：

```
① 自动发现与匹配
   流水线无需硬编码每个测试接口，根据代码变更范围自动匹配技能

② 标准化契约交互
   ⭐ 所有技能统一入参出参格式，流水线不用为每个测试能力写适配代码

③ 流式状态回传
   ⭐ 实时回传执行进度、日志、中间结果
   ⭐ CI 侧可以实时展示测试过程，而不是等最终结果
```

## 速查

```
触发：
□ ⭐ 增量精准（按变更模块映射技能集）
□ 普通提交 → P0
□ 合并请求 → P0+P1
□ 发布前 → 全量

编排：
□ ⭐ 环境前置校验（异常直接终止）
□ 数据一致（构造或从基准克隆）
□ ⭐ 无依赖技能并行
□ 结构化报告：通过率/失败明细/耗时/日志链接
□ 数据清理不污染环境

门禁：
□ ⭐ P0 100% 否则阻断
□ ⭐ P1 <阈值 告警 + 人工确认
□ ⭐ P0 与 P1 后果必须不同

□ ⭐ 幂等：重跑不产生重复数据/不重复计费
□ 独立沙箱
□ ⭐ 瞬时失败重试 1 次（有最大次数）
□ ⭐ 结果评论到 MR 页面
□ ⭐ 核心目的：防"改新功能坏老能力"
```

**一句话**：

> ⭐ **门禁的意义不在"卡住"，而在让"改了新功能、坏了老能力"这件事当场暴露。**
