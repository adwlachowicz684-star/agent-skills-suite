## 1. ⭐⭐⭐⭐⭐ 两种边界，只有一种有人看

| | 能力边界 | ⭐⭐⭐⭐⭐ 配置边界 |
|---|---|---|
| 由什么决定 | 工具本身能做什么 | ⭐ 你写了哪些检查 |
| 谁都知道 | ⭐ 文档可查、社区共识 | ⭐⭐⭐⭐⭐ **只有写配置的人知道** |
| 会变吗 | 工具升级时才变 | ⭐⭐⭐⭐⭐ 每次仓库变化都该变 |
| 有人审视吗 | 有（选型时讨论） | ⭐⭐⭐⭐⭐ **从来没有** |

举个例子。能力边界是"CI 不能验技能是否真的被触发"——这句话被反复提及，大家都知道。
配置边界是"我们仓库的 CI 里**没有**检查 description 长度"——
⭐⭐⭐⭐⭐ 这件事没有任何环节会提出来，因为它不是一个错误，是一个**缺省**。

> ⭐⭐⭐⭐⭐ **缺省不报错。它甚至不显示为"未配置"，它只是不存在。**

这是整套库里反复出现的那个不对称的又一个实例：
**"没写"在运行时不产生信号**，无论是技能正文里的省略、输入侧的省略，还是 CI 配置里的省略。

## 2. 三类盲区

### ① ⭐⭐⭐⭐⭐ 从来没配过（最常见）

新技能加了新检查项，而 CI 配置是三个月前写的：

```
仓库里有 38 个技能
CI 里有 6 条检查
```

那 6 条检查大多是**最初那批技能关心的问题**（YAML、name 格式、引用存在）。
后来发现的更重要的问题——描述与正文一致性、示例与契约一致性、语义变更——
⭐⭐⭐⭐⭐ **它们存在于文档里，不存在于 CI 里**。

> 它们被写进了《CI 能验什么》的清单，于是所有人都以为它被执行了。
> **"被写进文档"和"被写进配置"在人的记忆里是同一件事。**

### ② ⭐⭐⭐⭐ 配了但被跳过

```yaml
- name: skill-eval
  if: github.event_name == 'push' && github.ref == 'refs/heads/main'
```

条件是在某个具体需求下加的（"PR 上不跑太慢"），需求消失了条件还在。
⭐⭐⭐⭐ 于是这个检查在 PR 上永远显示"跳过"，而"跳过"在 UI 上是**灰色的、不引人注意的**。

或者更隐蔽的：

```yaml
continue-on-error: true   # 当时为了不阻塞迁移
```

> ⭐⭐⭐⭐⭐ `continue-on-error: true` 的检查，其唯一功能是**显示一个不影响结果的图标**。
> 它和没配的区别是：它让人以为配了。

### ③ ⭐⭐⭐⭐⭐ 配了但作用在错的集合上

```yaml
- run: validate_skill.py skills/*/      # 只验一层
```

而技能实际分布在 `packages/*/.claude/skills/`、`~/.claude/skills/`、插件里。

> ⭐⭐⭐⭐⭐ **检查通过了，因为它检查的是另一个集合。**
> 这是"嵌套的 `.claude/skills/` 目录只在子目录内才被发现"的镜像——
> 那份讲技能发现受作用域限制，这份讲**检查的覆盖面也受路径限制**，
> 而它同样是静默的：glob 匹配到 12 个，实际有 38 个，没有任何输出会说"还有 26 个没检查"。

## 3. ⭐⭐⭐⭐⭐ 差集检查：担心的 vs 检查的

不需要工具，一次会议就能做完：

```
左列：过去半年，我们这个库实际出过/担心的问题（按发生次数排序）
右列：CI 配置里的每一条检查
```

然后取**左列里右列没有的**。

| 我们担心的 | CI 有吗 |
|---|---|
| YAML 格式错 | ✅ |
| 引用文件不存在 | ✅ |
| ⭐⭐⭐⭐⭐ description 与正文不一致 | ❌ |
| ⭐⭐⭐⭐⭐ 示例不符合输出契约 | ❌ |
| ⭐⭐⭐⭐ 语义变更（改单位/改口径） | ❌ |
| ⭐⭐⭐⭐⭐ 副作用技能没设 disable-model-invocation | ❌（文档里有，配置里没） |

> ⭐⭐⭐⭐⭐ 最后一行最典型：它在 `ci-skill-validation` 里被标成 ⭐⭐⭐⭐⭐ 强制项，
> 而它在配置里的状态取决于**有没有人读完之后顺手加进去**。

关键在排序：⭐⭐⭐⭐⭐ **左列按"实际发生过"排序，不要按"理论上重要"排序**。
理论上重要的清单会包含所有东西，于是无法指导"这次补哪一条"；
而实际发生过的清单通常前三条就覆盖了 80% 的痛苦。

一个更省力的变体：**每次事故后，问一句"CI 能不能抓住它"**。
答不能 → 这就是下一条要加的检查。
⭐⭐⭐⭐⭐ 它把"补配置"从一项需要主动规划的工作，变成事故的副产品——
这与"每次事故产生一条 eval"完全同构，只是那份加的是用例，这份加的是检查项。

## 4. ⭐⭐⭐⭐ 配置只在被写的时候被审视一次

配置文件的生命周期和代码不一样：

```
代码：写完 → review → 每次改动再 review
配置：⭐⭐⭐⭐⭐ 写完 → 再也不看
```

原因是结构性的：**配置文件没有"业务逻辑"可读，它只有一串开关**。
review 一次 CI 配置需要把它展开成"这些开关合起来意味着什么"，
⭐⭐⭐⭐ 而这个展开过程很贵，于是 reviewer 的默认动作是"看着合理就过"。

两个能用的对策：

**① 让配置自述覆盖面**

```yaml
- run: validate_skill.py --report-coverage
# 输出：已检查 12 个技能；仓库内共发现 38 个技能目录
```

> ⭐⭐⭐⭐⭐ 把"我检查了多少"变成输出的一部分。
> 它不能自动修复盲区，但它让 12/38 这个数字出现在每一次运行的日志里。

**② ⭐⭐⭐⭐⭐ 给检查项写"它防的是什么"**

```yaml
- name: check-description-length
  # 防：description 超长导致加载失败（2026-07 事故 #88）
```

这一行注释的价值不在文档，在于⭐⭐⭐⭐⭐ **下次有人想删这条检查时，
他必须面对"我是在删掉对 #88 的防护"这个具体判断**，而不是"这条好像没用"。

## 5. ⭐⭐⭐⭐⭐ "有 CI"和"有覆盖"是两件事

这是本份的结论，也是最容易在汇报中被混淆的一处：

```
"我们接入了 CI"     → ⭐ 有一套流水线在跑
"我们有 6 条检查"   → ⭐⭐ 有 6 条检查在跑
"我们覆盖了主要风险" → ⭐⭐⭐⭐⭐ 需要差集检查才能说
```

> ⭐⭐⭐⭐⭐ 前两句都是可验证的事实，第三句是一个需要证明的结论，
> 而它在汇报里通常被当成前两句的推论。

三条最常用的"看起来在覆盖实际没覆盖"：

| 说法 | 实际 |
|---|---|
| "有 CI 门禁" | ⭐⭐⭐⭐ 可能只有 2 条结构检查 |
| "评测覆盖了 40 个用例" | ⭐⭐⭐⭐⭐ 可能其中 35 个恒过（baseline 也会通过） |
| "每次提交都跑" | ⭐⭐⭐⭐ 可能 `continue-on-error: true` |

第二条值得单独说：**用例数不等于覆盖**。
《`skill-judging/references/benchmark-assertions-delta.md`》讲的是"断言打在哪"，
本份讲的是"断言有没有打"——两者结合才是覆盖：
⭐⭐⭐⭐⭐ **40 个恒过的用例，提供的信息量和 0 个一样，而它在报表上看起来是 40。**

## 6. 自检

- [ ] ⭐⭐⭐⭐⭐ CI 里现在有几条检查？能把它们逐条说出来吗？（说不出 = 无人审视）
- [ ] ⭐⭐⭐⭐⭐ 过去半年实际出过的问题，有几条在 CI 里有对应检查？
- [ ] ⭐⭐⭐⭐ 有没有 `continue-on-error: true` / 条件跳过？为什么还在？
- [ ] ⭐⭐⭐⭐⭐ 检查的 glob 匹配到几个？仓库里实际有几个？（12/38 是静默的）
- [ ] ⭐⭐⭐⭐⭐ 每次事故后问过"CI 能不能抓住它"吗？
- [ ] ⭐⭐⭐ 每条检查有写"它防的是什么"吗？
- [ ] ⭐⭐⭐⭐ 运行日志里能看到"已检查 N / 共 M"吗？
- [ ] ⭐⭐⭐⭐⭐ 40 个用例里，有几个是 baseline 也会通过的？（恒过 = 没在测）
