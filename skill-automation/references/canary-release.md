> 都可能改变工具使用、拒答行为、详略、延迟和成本。**

## 为什么需要金丝雀

技能不是文档，是**可执行配置**。改它等于改代码，
但团队常常把它当成"改一段文案"——不版本化、不评估、直接全量。

> ⭐ 金丝雀的意义**不是消除不确定性**，
> 而是**把不确定性暴露在一小块可观测、可回滚的区域**，
> 在所有人依赖它之前。

## 先定义发布单元

提示词很少单独运行——它的行为依赖：

```
模型快照 · 工具 schema · 检索设置 · temperature · 响应格式 · 周边代码
```

把这些依赖**打包成一个发布清单**：

```json
{
  "release": "support-agent-2026-08-15.1",
  "prompt": "sha256:...",
  "model": "pinned-model-version",
  "tools": "toolset-v17",
  "retriever": "kb-2026-08-14",
  "sampling": { "temperature": 0.2 }
}
```

> ⭐ **没有清单，金丝雀对比就是含糊的**——
> 质量变化可能来自新索引，而不是提示词。

能 pin 的都 pin，不能 pin 的记录下来，**把 release ID 附到每条 trace 上**。

## 上线前：回归套件是闸门

覆盖四类：

```
□ 代表性请求
□ ⭐ 硬性边界情况
□ 策略测试
□ 输出契约
```

⚠️ 但要清醒：**套件是闸门，不是证明**。
离线样例无法复现用户的完整分布，
也复现不了检索、工具和会话历史之间的相互作用。

## 路由一小撮可比较的流量

```
① 从低百分比开始，且 ⭐ 一致分配（sticky routing）
   ——防止一次会话中途切换版本

② 在候选证明基本稳定之前，⭐ 排除高风险操作

③ 对照组与金丝雀组必须可比
   随机分配通常强于按地域/客户等级路由
   请求差异大时，⭐ 按任务类型分层
   （否则一组可能全是简单题）

④ ⭐ 影子模式先行：在复制的输入上跑候选，
   不展示答案、不允许副作用，离线比对输出与工具计划
   ——多花推理成本、测不到用户满意度，但能安全捕获明显回归
```

## 测什么：不止是点赞

用户评分稀疏且有偏。要配上任务特定信号：

```
正确解决 / 工作流成功完成
升级率 · 放弃率 · 重复联系率
结构化输出与引用的有效性
工具错误率 · 不必要工具调用率 · 禁用工具调用率
⭐ 安全策略违规与敏感数据泄露
延迟 · token 用量 · 单任务成本
```

⭐ **上线前就设好护栏**：
一个候选可能提升了回答质量，却让延迟翻倍或让危险工具调用变多。
先决定**哪些指标可以互相权衡、哪些触发自动停止**。

主观质量：抽样**盲评成对**给人工看，评审者不知道哪个是候选。
用**绑定到产品任务**的 rubric，而不是"你更喜欢哪个"。
LLM 评委可以帮忙筛量，但要**校准到人工标签**并监控位置/冗长偏差
（见 `judge-design.md`）。

## 前进或回滚要"刻意"

```
推进条件：最小样本量 + 观察窗口都满足后才升档
典型阶梯：内部 → 1% → 5% → 20% → 全量
具体数字不重要，⭐ 重要的是有明确的闸门

回滚应该是"改路由"，不是"紧急改代码"
→ 让上一个 manifest 保持可部署
→ ⭐ 让发布开关独立于应用二进制
```

一个容易漏的细节：

> 如果候选**能触发工具**，禁用它时**必须同时停掉排队的工作**，
> 或确保排队项保留正确的版本与策略。

发布成功后**不要删证据**——
评估结果、线上指标、已知弱点、决策记录都要随 release 存档。
这能让未来的回归更容易诊断，
也避免团队重新发现"为什么会有这条看起来很怪的指令"。

## 一个常见陷阱

> ⭐ **金丝雀指标看起来很好（新旧 token 数差不多），
> 但你没测对的那个指标。**

token 数不会告诉你新提示词是不是在幻觉、
是不是对 API 消费者太啰嗦、是不是语气变了。

结果：你放量到 50%，用户**安静地**抱怨（参与度下降、静默失败），
等你看仪表盘时损失已经造成。

修法：**开跑之前就定好假设并记下能验证它的指标**。

```
✅ "新提示词将减少 10% token，同时准确率 ≥ 95%"
   → 记录准确率（来自评委或人工），而不只是 token 数
```

另一条实操经验：

> **金丝雀权重要走离散台阶（5% / 10% / 25% / 50% / 100%），不要连续爬。**
> 从 15% 直接跳到 50% 没问题；
> 从 15% → 15.3% → 15.7% 是噪声，你会反复自我怀疑。

路由方式：登录用户用 hash（`user_id`）保证粘性；
匿名流量用随机（更噪）。
vLLM 场景下可以把路由放在 serving 层，让所有请求（含 gRPC）都遵守权重。

## 一个常被误解的价值

> ⭐ **金丝雀的真正价值不是"捕获回归"，而是"提高迭代速度"。**

有了它，改一次提示词、在真实用户身上量出影响，
只要 5 分钟，不需要一个 sprint 的 A/B。所以**应该大方地用**。

⚠️ 但陷阱是测量：**多数团队搭好了路由，却忘了埋点**，
最后得到一套完美的、什么也告诉不了他们的金丝雀基础设施。

> **先埋点（你要测什么），再路由。**

## 对技能的裁剪版

技能没有线上流量，但同样的思路可以缩小用：

```
① 发布单元：技能版本 + 依赖（脚本、模型、工具集）
   ——写在技能自己的 manifest 或 CHANGELOG 里

② 回归套件：20 条触发 + 输出用例（见 `regression-baseline.md`）

③ "影子模式" = ⭐ 双实例 A/B
   ——同一个任务，开技能 vs 不开，离线比对
   （见 `claude-ab-loop.md`）

④ "小流量" = ⭐ 先给 1–2 个同事用，而不是全团队
   ——技能没有百分比路由，"给人用"就是你的金丝雀

⑤ 回滚 = 恢复上一版文件 + 重启/重载
   ⭐ 前提是你保留了上一版（git tag 或备份）
```

最后一条是最容易被忽略的：
**没有保留上一版的回滚，是紧急重写，不是回滚。**
