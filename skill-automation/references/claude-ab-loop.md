## A/B 双实例模型

```
Claude A —— 专家：帮你设计和改进指令
Claude B —— 用户：带着技能去跑真实任务
```

> **为什么有效**：Claude 模型既理解"怎么写有效的 agent 指令"，
> 也理解"agent 需要什么信息"。

> ⚠️ 关键约束：**Claude B 必须是全新实例**（技能刚加载，无残留上下文）。
> 用同一个会话测，残留上下文会掩盖指令缺口——
> 这正是 `skill-evaluating` 强调"基线对比必须在新会话里跑"的原因。

## 先建评估，再写文档

> ⭐ **在写大量文档之前创建评估。**
> 这确保技能解决**真实问题**，而不是记录**想象的问题**。

**评估驱动开发五步**：

```
1. 识别差距：在"没有技能"的情况下，对代表性任务跑 Claude，
   记录具体的失败或缺失的上下文
2. 创建评估：构建三个场景来测这些差距
3. 建立基线：测量没有技能时的表现
4. 编写最少说明：只写足够解决差距并通过评估的内容
5. 迭代：执行评估 → 与基线比较 → 改进
```

> 官方原话：**"目前没有内置的运行这些评估的方式，用户可以自建评估系统。
> 评估是衡量技能有效性的真实来源。"**

**评估结构示例**：

```json
{
  "skills": ["pdf-processing"],
  "query": "从此 PDF 中提取所有文本并保存到 output.txt",
  "files": ["test-files/document.pdf"],
  "expected_behavior": [
    "使用适当的 PDF 处理库成功读取 PDF 文件",
    "从所有页面提取文本，不遗漏任何页面",
    "将文本保存到 output.txt，格式清晰可读"
  ]
}
```

> 注意 `expected_behavior` 是**可观察的行为**，不是"做得好"这种感觉。

## 五步创建流程

| # | 步骤 | 要点 |
|---|---|---|
| **1** | **不带技能先做一遍** | 用常规提示跟 Claude A 解决问题。**注意你反复提供了哪些信息**——那就是技能素材 |
| **2** | **识别可复用模式** | 例：做 BigQuery 分析时，你提供了表名、字段定义、过滤规则（"始终排除测试账户"）、常见查询模式 |
| **3** | **让 Claude A 建技能** | *"创建一个技能，捕获我们刚用的 BigQuery 分析模式。包含表结构、命名约定和过滤测试账户的规则。"*<br>**Claude 原生理解技能格式，不需要特殊 system prompt** |
| **4** | **审查简洁性** | *"删掉关于胜率是什么的解释——Claude 已经知道。"*<br>检查它有没有加不必要的解释 |
| **5** | **改善信息架构** | *"把表结构放进单独的参考文件，以后可能加更多表。"* |

**然后用 Claude B 测**：

```
□ 它能找到正确的信息吗？
□ 它正确应用规则了吗？
□ 它成功完成任务了吗？
```

## 迭代循环

> **观察 → 带回 → 改进**，在 A 和 B 之间来回：

```
用 Claude B 跑真实任务（不是测试场景）
    ↓
观察：它在哪里挣扎 / 成功 / 做出意外选择
    ↓
回到 Claude A：分享当前 SKILL.md + 你观察到的具体现象
    ↓
改完，回到 Claude B 再测
```

**反馈要说具体**：

```
❌ "它用得不太好"
✅ "当我让 Claude B 出区域销售报告时，它写了查询但忘了过滤测试账户，
    尽管技能里提到了这条规则。"
```

> ⭐ **你要发现的是"Claude 真正需要什么上下文"，
> 而不是试图提前预判它。**

## 验收标准要写成 API 行为

> 在改任何技能文本**之前**，先把期望行为写成严格形式：

```
□ 输入形状
□ 输出 schema
□ 必须做的规则
□ 禁止做的规则
□ 失败行为（上下文缺失时怎么办）
```

> **如果验收标准模糊，你的测试就会模糊。**

**黄金提示集**（从真实事故/工单里取，含四类）：

```
1. 正常案例
2. 噪声 / 歧义案例
3. 缺失上下文案例
4. 超出范围案例
```

**改进时的纪律**：

```
□ 每次迭代只改 1–2 个变量——否则无法归因
□ 只在全套通过率提升、失败模式减少（而非转移）、
  输出格式在边界案例下仍稳定时才发布
```

> ⚠️ **"失败模式减少，而不是转移"**——
> 这条很关键：改完 A 类失败少了、B 类失败多了，等于没改。

**团队常卡在这三处**：

```
□ 一个 mega-skill 想同时做摘要、规划、分类、策略解读 → 快速退化
□ 黄金提示集没有版本化 → 趋势线不可信
□ 没定义"数据不足或超范围时该拒答" → agent 会硬编
```

## 官方最近加的三件事

> 2026 年 Skill Creator 更新，把技能从"一次性提示"变成**版本化工件**：

| 能力 | 说明 |
|---|---|
| **Golden prompts 先行** | 实现之前先写代表真实任务的具体提示，作为基线用例 |
| **test-creator** | 从你的需求**自动生成测试**，不用手写每个用例 |
| **集成评估器** | 反馈会指出**指令冲突、重叠、薄弱区**，便于收紧规格 |

> 一句话：**这本质上是给提示词做 CI。**

**同时可用的官方内建能力**（部分客户端）：

- `claude plugin eval` —— 对插件跑测试套件、打分，**并与"无插件基线"对比**
- `claude plugin eval init` —— 自动起草用例与评分器
- `/skill-doctor` —— **显示每个技能占多少上下文、被调用多频繁**
- `/doctor` —— 完整设置体检，能诊断并修复

> ⭐ `/skill-doctor` 是清库的第一工具：
> **先看"哪个技能从没被用过、却一直占着上下文"。**

## 自查

```
□ 是否在写文档之前就建了评估（而非事后补）？
□ Claude B 是否是不带残留上下文的全新实例？
□ 是否测了不带技能的基线？
□ 反馈是否具体到"哪个任务、忘了什么"？
□ 每次迭代是否只改 1–2 个变量？
□ 是否确认失败模式是"减少"而非"转移"？
□ 黄金提示集是否版本化了？
□ 是否定义了"数据不足/超范围时拒答"？
□ 是否跑过 /skill-doctor 或等价工具清库？
```
