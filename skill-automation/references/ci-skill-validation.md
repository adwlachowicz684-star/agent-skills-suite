## 1. ⭐⭐⭐⭐⭐ CI 不能测技能行为

> ⭐⭐⭐⭐⭐ **"⭐ Claude Code 是一个⭐ 交互式工具，⭐ 不是 CI runner。
> ⭐⭐⭐⭐⭐ ⭐ 你⭐ 无法 ⭐ 在 GitHub Actions 流水线里⭐ 调起 Claude Code ⭐ 去测技能行为。"**

```
⭐⭐⭐⭐⭐ CI 能验证：
   · ⭐ YAML frontmatter 语法（能否解析）
   · ⭐⭐ 字段值（name 格式、description 长度、字段名是否合法）
   · ⭐⭐ 文件结构（SKILL.md 存在、引用的支撑文件存在）
   · ⭐⭐⭐ 脚本语法（bash 用 shellcheck、python 用 py_compile）

⭐⭐⭐⭐⭐ CI 不能验证：
   · ⭐⭐⭐⭐⭐ 技能是否真的被触发
   · ⭐⭐⭐⭐⭐ 触发后输出是否达标
```

> ⭐⭐⭐⭐⭐ 这条边界⭐ 极其重要，⭐⭐⭐⭐ ⭐⭐⭐ 因为它⭐ 解释了⭐ 一个常见误判：
> ⭐⭐⭐⭐⭐ **"我们的 CI 是绿的，为什么技能还是坏了？"**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ **绿只代表⭐ 结构合法，⭐⭐⭐⭐⭐ ⭐⭐⭐ 不代表⭐ 行为正确——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 而⭐ 技能恰恰⭐ 大量失败在⭐ 行为层。**
>
> ⭐⭐⭐⭐⭐ 这⭐ 与我们已有的⭐ 多条结论⭐ 精确对齐：
> ```
> "YAML 通过但技能仍失败" ←→ ⭐⭐⭐⭐⭐ `yaml-frontmatter-errors.md` 的⭐ 半可用态
> "结构正确的废话"        ←→ ⭐⭐⭐⭐⭐ `three-failure-modes.md` 的⭐ 静默失败
> "断言打在环境状态上"    ←→ ⭐⭐⭐⭐ `assert-on-environment.md` 不能只检查它说了什么
> ```
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 三条⭐ 从不同角度⭐ 指向同一件事：
> ⭐⭐⭐⭐⭐ **结构层的通过⭐ 从来不是⭐ 行为层的证据。**
>
> ⭐⭐⭐⭐ 另外一条⭐ 官方补充：Claude Code 支持⭐ 定时例行任务（routines），
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 运行在 Anthropic 基础设施上，⭐⭐⭐⭐ ⭐ 能跑⭐ 技能驱动的自动化工作流——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 但它⭐ 与 CI/CD 流水线⭐ 是分开的，⭐⭐⭐⭐⭐ ⭐ 别混为一谈。

## 2. ⭐⭐⭐⭐ CI 能做的四类结构验证

一份可抄的检查清单（每项都对应一个我们已有的失败模式）：

```
① ⭐⭐⭐⭐⭐ YAML frontmatter 能否解析
   ←→ ⭐⭐⭐⭐⭐ 半可用态（手动能调、自动不能）

② ⭐⭐⭐⭐⭐ name 字段格式：小写、连字符、数字，≤64 字符
   ←→ ⭐⭐⭐⭐⭐ `naming-conventions.md`：kebab-case 是协议不是风格

③ ⭐⭐⭐⭐⭐ description 存在且 <1,536 字符
   ←→ ⭐⭐⭐⭐⭐ `imperative-style.md`：超出被截断，⭐ 主要用例必须前置

④ ⭐⭐⭐⭐⭐ 名字含 deploy / commit / send / delete / migrate / push 的
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 必须设 disable-model-invocation: true
   ←→ ⭐⭐⭐⭐⭐ `seven-contracts.md` 与 `forty-skills-lessons.md` 的⭐ 副作用红线
```

> ⭐⭐⭐⭐⭐ 第 ④ 条⭐ 是⭐ 本轮最值得抄的一条——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 它把⭐ 我们反复收集的⭐ "副作用技能必须手动触发"
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 从⭐ 一条⭐ 靠人记住的规则，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 变成了⭐ **一条⭐ 可按名字自动判定的⭐ 机械检查**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ （正是⭐ `golden-rules-failure-modes.md` 说的⭐ "规则升级为代码"）。
>
> ⭐⭐⭐⭐ 另外两项：
> ⭐⭐⭐⭐ **引用的文件是否存在**（scripts/ references/ templates/）——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这⭐ 直接命中 `three-failure-modes.md` 那条
> "⭐ 引用了不存在的模板 → 模型自己补内容 → ⭐⭐⭐⭐⭐ ⭐ 幻觉的来源之一"；
> ⭐⭐⭐⭐ 以及⭐ **脚本语法检查**（shellcheck / py_compile）。

## 3. ⭐⭐⭐⭐⭐ 行为评测也能进 CI，但要另一条路

官方教材给了⭐ 另一条路径——⭐⭐⭐⭐⭐ **用 `claude -p` 非交互式地跑 eval 套件**：

```yaml
# .github/workflows/agent-evals.yml
on:
  pull_request:
    paths: ['CLAUDE.md', '.claude/**']     ⭐⭐⭐⭐⭐ 配置变更即触发
  schedule:
    - cron: '0 2 * * *'                    ⭐⭐⭐⭐ 也按周期跑
jobs:
  evals:
    steps:
      - run: npm install -g @anthropic-ai/claude-code
      - name: Run eval suite
        run: |
          for eval in evals/*.json; do
            claude -p "$(jq -r '.prompt' $eval)" \
              --allowedTools "Read,Edit,Bash(make test)" \
              --output-format json > result.json
            ./evals/check.sh "$eval" result.json
          done
```

> ⭐⭐⭐⭐⭐ 关键设计⭐ 有四处，⭐⭐⭐⭐⭐ ⭐⭐⭐ 每一处都⭐ 值得单独记：
>
> **① 触发条件是 `paths: ['CLAUDE.md', '.claude/**']`**
> ⭐⭐⭐⭐⭐ **"⭐ 配置⭐ 引导着 agent，⭐⭐⭐⭐⭐ ⭐ 因此⭐ 它⭐ 值得⭐ 拿到⭐ 代码所享受的⭐ 回归测试。"**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 这句⭐ 是⭐ 整份文档⭐ 最有力的一句话——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 它⭐ 把"⭐ 配置不是代码，所以不用测"⭐ 这个默认前提⭐ 直接推翻了。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 我们此前⭐ 反复说过⭐ "改一个文件，没有 CI 报警"，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ **这里就是⭐ 那个缺失的⭐ 报警装置。**
>
> **② ⭐⭐⭐⭐⭐ eval 套件是"活的"**
> ⭐⭐⭐⭐⭐ **"⭐ 随着模型变强，⭐ 曾经⭐ 有区分度的用例⭐ 会⭐ 不再有区分度，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 必须⭐ 从持续的监控中⭐ 补充新的。"**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这⭐ 与 `skillsbench-vs-realworld.md` 那条
> "⭐ 模型升级后⭐ 部分技能⭐ 被追上（outgrowth）"⭐ 是⭐ 同一事实的⭐ 运维侧说法：
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ **评测集⭐ 会过期，⭐⭐⭐⭐⭐ ⭐⭐⭐ 因为它⭐ 测的是⭐ 模型与技能之间的⭐ 差值。**
>
> **③ ⭐⭐⭐⭐⭐ 每次生产事故都要留一条 eval**
> ⭐⭐⭐⭐⭐ **"⭐ 每一次生产事故⭐ 都产生一条 eval，⭐⭐⭐⭐⭐ ⭐ 由⭐  owning 该事故的团队⭐ 撰写，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 并⭐ 永久留在套件里⭐ 作为回归测试。"**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这⭐ 与我们⭐ 已有的⭐ 多条⭐ 完全同构：
> ```
> gotchas 的维护方式：每纠正模型一个错误就写进去
> ⭐⭐⭐⭐⭐ 被推翻的规则及其 eval 数据 = 团队最值钱的资产之一
> ⭐⭐⭐⭐⭐ 每次事故 → 一条 eval（本条）
> ```
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ **三条都在说：⭐ 错误是⭐ 最便宜的⭐ 测试数据来源，⭐⭐⭐⭐⭐ ⭐ 别浪费它。**
>
> **④ ⭐⭐⭐⭐ 门禁 + 度量**
> ```
> ⭐⭐⭐⭐ 通过率阈值作为合并检查强制执行
> ⭐⭐⭐ 运行被记录，结果可随时间比较
> ⭐⭐⭐⭐ 先行的：通过率随时间的变化 + ⭐⭐⭐⭐⭐ 一次生产事故⭐ 多久变成⭐ 一条永久 eval
> ⭐⭐⭐⭐ 滞后的：⭐⭐⭐⭐⭐ CI 抓到的回归数 vs ⭐ 生产发现的回归数
> ```
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 最后这个比值⭐ 特别好——⭐ **它直接测量⭐ 这套门禁⭐ 有没有真的⭐ 拦住东西**，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 而不是⭐ 只测"它跑了没有"。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 这与 `skill-health-metrics.md` 的"指标是问诊工具"⭐ 同源。

## 4. ⭐⭐⭐⭐ 三层循环：本地 / PR / 周期

```
① ⭐⭐⭐⭐ 提交前本地跑
② ⭐⭐⭐⭐⭐ PR 上跑 CI
③ ⭐⭐⭐⭐⭐ 每周定时全量扫描（cron）
```

> ⭐⭐⭐⭐⭐ 一组⭐ 实测分配：
> ⭐⭐⭐⭐⭐ **"pre-commit hook ⭐ 能在到达 CI 之前⭐ 抓到约 90% 的问题。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 剩下约 10% ⭐ 大多⭐ 是⭐ YAML 合并冲突——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 它在 diff 里⭐ 看起来没问题，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 但 git 解析完之后⭐ 产生了⭐ 无效语法。"**
>
> ⭐⭐⭐⭐⭐ 最后半句⭐ 是⭐ 一个⭐ 此前完全没覆盖过的⭐ 失败来源：
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ **合并冲突解决后的产物⭐ 可能⭐ 语法无效，⭐⭐⭐⭐⭐ ⭐⭐⭐ 而⭐ diff 看起来是干净的。**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这⭐ 也让⭐ 第 ③ 层（周期扫描）⭐ 有了⭐ 独立存在的理由：
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ **PR 上跑的是"这次改动"，⭐⭐⭐⭐⭐ ⭐⭐⭐ 周期扫描跑的是"仓库当前状态"——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 两者⭐ 不等价。**
>
> ⭐⭐⭐⭐ 反馈速度也给了具体数字：**从 push 到 CI 结果 ⭐ 不到 30 秒**。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这与 `skill-test-pyramid-four.md` 的"⭐ 瞬时失败自动重试 1 次"
> ⭐⭐⭐ ⭐ 是⭐ 同一个立场：⭐ **门禁要快，⭐⭐⭐⭐⭐ ⭐⭐⭐ 否则⭐ 会被绕开。**

## 5. ⭐⭐⭐⭐⭐ 一组前后对比数字

| 指标 | 加 CI 前 | 加 CI 后 |
|---|---|---|
| ⭐⭐⭐⭐⭐ 坏技能流入 main | ⭐⭐⭐ 约 3 次/月 | ⭐⭐⭐⭐⭐ 6 周内 0 次 |
| ⭐⭐⭐⭐⭐ 发现坏技能的时间 | ⭐⭐⭐⭐ 1–7 天 | ⭐⭐⭐⭐⭐ < 30 秒 |
| ⭐⭐⭐⭐ 技能评审信心 | ⭐⭐⭐⭐⭐ "我看挺好" | ⭐⭐⭐⭐⭐ 有具体项的通过/失败 |
| ⭐⭐⭐ 新作者上手 | ⭐⭐⭐ 试错 | ⭐⭐⭐⭐ CI 直接纠正 |

> ⭐⭐⭐⭐⭐ 还有一句⭐ 极其诚实的⭐ 反思，⭐⭐⭐⭐⭐ ⭐⭐⭐ 值得⭐ 原样记下：
> ⭐⭐⭐⭐⭐ **"⭐ 给 40 个已存在的技能⭐ 补装 lint ⭐ 花了⭐ 一整个下午。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 我们是⭐ 花了三个月⭐ 才攒出那些技能的。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 如果⭐ 第一天就装上，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ ⭐ 每个坏技能⭐ 都会是⭐ PR 时的⭐ 2 分钟修复，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 而不是⭐ 一个批量整改项目。"**
>
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这⭐ 是"⭐ 三过早"⭐ 那一族的⭐ 又一个成员：
> ```
> 过早编排 · 过早分目录 · 过早通用化 · ⭐⭐⭐⭐⭐ 过晚装 lint
> ```
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 共同点是：⭐ **它们⭐ 都由⭐ "看起来还不用做"⭐ 开始，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 然后⭐ 在⭐ 规模变大后⭐ 变成⭐ 一笔⭐ 一次性大额支出。**

## 6. ⭐⭐⭐ 两条容易被忽略的坑

**① 描述质量打分需要上下文**

> ⭐⭐⭐⭐ **"⭐ 当前的打分器⭐ 会标记⭐ 过短或过泛的描述，⭐⭐⭐ 这通常是对的。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 但它⭐ 偶尔也会⭐ 标记⭐ 那些⭐ 恰好写得简洁的、⭐ 完全够用的描述。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐ 我在考虑⭐ 用技能正文内容⭐ 来校准
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ '⭐ 相对于该技能的范围，⭐ 多具体才算够具体'——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 一个⭐ 窄技能⭐ 可以比⭐ 宽技能⭐ 用更短的 description。"**

> ⭐⭐⭐⭐⭐ 后半句⭐ 是⭐ 一条⭐ 此前没有的⭐ 判据：
> ⭐⭐⭐⭐⭐ **"多具体才算够具体"⭐ 取决于⭐ 技能的范围宽度，⭐ 不是绝对值。**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 这⭐ 与我们已有的⭐ `description-by-collision-risk.md`
> （⭐ 长度由碰撞风险决定）⭐ 是⭐ 同一思路的⭐ 另一个维度：
> ```
> 碰撞风险 → 决定⭐ 要不要写 NOT 段
> ⭐⭐⭐⭐⭐ 范围宽度 → 决定⭐ "够具体"的⭐ 门槛在哪
> ```
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 两者⭐ 都在说：⭐ **description 的⭐ 合格线⭐ 不是⭐ 一个固定数字，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 而是⭐ 由⭐ 它所处的⭐ 环境决定的。**
>
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 而⭐ 前半句⭐ 是⭐ 一条⭐ 关于"自动化评分"本身的⭐ 提醒：
> ⭐⭐⭐⭐⭐ **打分器会误报，⭐⭐⭐⭐⭐ ⭐⭐⭐ 所以⭐ 它的输出⭐ 应该是⭐ "提示你去看一眼"，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 而不是⭐ 直接阻断。**
> ⭐⭐⭐⭐ 这与⭐ 我们已有的⭐ "P0 阻断 / P1 告警 + 人工确认"⭐ 分级⭐ 完全吻合。

**② 退出码要分级**

```
0 = 全部通过
1 = 一项或多项检查失败（⭐ 你的技能有问题）
2 = 配置或运行时错误（⭐⭐⭐ 工具本身跑不起来）
```

> ⭐⭐⭐⭐⭐ 这与 `script-cli-contract.md` 的⭐ 退出码分级⭐ 是⭐ 同一个原则：
> ⭐⭐⭐⭐⭐ **1 和 2 ⭐ 对应的⭐ 处置完全不同（改技能 vs 修工具），
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 而⭐ 它们⭐ 都是"非 0"。**

## 速查

```
□ ⭐⭐⭐⭐⭐ CI 不能测行为：Claude Code 是交互式工具，⭐ 不能在流水线里调起来测触发与输出
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ "CI 是绿的" ≠ 行为正确 → ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 技能恰恰大量失败在行为层
   ⭐⭐⭐⭐ 唯一例外：claude -p 非交互式跑 eval 套件（另见第 3 节）
□ ⭐⭐⭐⭐ CI 能验四类：YAML 可解析 · name 格式(小写连字符≤64) · description 存在且<1536
   ⭐⭐⭐⭐⭐ ⭐ 引用的 scripts/references/templates 存在（← 不存在→模型自补→幻觉）
   ⭐⭐⭐⭐ 脚本语法（shellcheck / py_compile）
□ ⭐⭐⭐⭐⭐ 名字含 deploy/commit/send/delete/migrate/push → 自动强制 disable-model-invocation
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 这是"规则升级为代码"的实例：⭐ 不再靠人记住
□ ⭐⭐⭐⭐⭐ 行为评测进 CI：paths 含 CLAUDE.md 与 .claude/** → ⭐ 配置值得拿到代码享有的回归测试
   ⭐⭐⭐⭐⭐ ⭐ eval 集是活的（模型变强→用例失去区分度→从监控补新的）
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ 每次生产事故→一条 eval→永久留在套件（错误是最便宜的测试数据来源）
   ⭐⭐⭐⭐⭐ ⭐ 度量：CI 抓到的回归 vs 生产发现的回归（测门禁有没有真拦住东西）
□ ⭐⭐⭐⭐ 三层循环：本地(pre-commit 抓~90%) · PR(CI) · ⭐⭐⭐⭐⭐ 每周 cron(跑"当前状态"≠"本次改动")
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ 剩下 10% 多是 YAML 合并冲突：diff 看着干净，解析后语法无效
   ⭐⭐⭐⭐ push→结果 <30 秒（门禁要快，否则会被绕开）
□ ⭐⭐⭐⭐⭐ 数字：坏技能 3次/月→0（6周）· 发现时间 1–7天→<30秒 · "我看挺好"→有具体项
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 反思：40 个技能补装 lint 花一整下午 = ⭐ 第四种"过早/过晚"债
□ ⭐⭐⭐ "够具体"的门槛由⭐ 技能范围宽度决定（窄技能可以更短），不是绝对值
   ⭐⭐⭐⭐⭐ ⭐ 自动化评分会误报 → 输出应是"提示去看一眼"，不是直接阻断
□ ⭐⭐⭐⭐ 退出码：0 通过 · 1 技能有问题 · 2 工具跑不起来（处置完全不同却都是非 0）
```

**一句话**：

> ⭐⭐⭐⭐ **"CI 是绿的"只代表结构合法、不代表行为正确——Claude Code 不能在流水线里被调起来测触发与输出；所以 CI 负责四类结构验证（尤其"名字含 deploy/commit/send/delete/migrate/push 就强制 disable-model-invocation"这种可机械判定的规则），而行为评测要走 `claude -p` 那条路，并把每次生产事故固化成一条永久 eval。**
