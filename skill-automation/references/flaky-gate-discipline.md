## 1. ⭐⭐⭐⭐⭐ 门禁失效的方式不是变绿，是被忽略

设计门禁时的隐含假设是：它会一直拦住坏东西，直到有人修好。
实际观察到的失效链条是另一种：

```
第 1 次红 → 认真看，是真问题，修
第 2 次红 → 看一眼，好像是 flaky，重跑
第 3 次红 → 直接重跑
第 6 次红 → ⭐⭐⭐⭐⭐ 不看内容就重跑
第 N 次红 → ⭐⭐⭐⭐⭐ 加 --no-verify / 点"跳过检查"
```

> ⭐⭐⭐⭐⭐ **门禁不是被"修好"或"关掉"的，它是被**逐步忽略**的。**

这一步一步之间没有明显的分界线——每一步看起来都是合理的节省。
而终点的可怕之处在于：**门禁的 UI 仍然是绿的**（最后一次重跑过了），
于是所有人——包括后来接手的人——都以为有一道门禁在工作。

对比一下三种状态：

| 状态 | 有没有在拦 | 看得出吗 |
|---|---|---|
| 没有门禁 | ❌ | ⭐ 看得出（一眼） |
| 门禁红着 | ✅ | ⭐ 看得出 |
| ⭐⭐⭐⭐⭐ 门禁被忽略 | ❌ | ⭐⭐⭐⭐⭐ **看不出** |

> ⭐⭐⭐⭐⭐ 第三种和第一种的**实际效果完全一样**，
> 而第三种在架构图、在流程文档、在合规检查里都算"有门禁"。

这正是"结构正确的废话"在流水线上的版本：**它具备门禁的全部形式，不具备门禁的功能。**

## 2. 判定：同一 commit 跑三次

不需要分析原因，判定 flaky 的成本和判定"技能不稳定"一样低：

```bash
for i in 1 2 3; do
  run_eval --commit $SHA --out "run_$i.json"
done
diff3 run_1.json run_2.json run_3.json
```

| 结果 | 判定 |
|---|---|
| 三次全红且失败项相同 | ⭐ 真实失败（系统性） |
| ⭐⭐⭐⭐⭐ 三次结果不一致 | ⭐⭐⭐⭐⭐ **flaky** |
| 三次全绿 | 稳定通过 |

关键在第一行和第二行的区别——**"三次全红"不是 flaky，哪怕它同样是"红"**。
这与 `failure-quadrant-diagnosis` 的 3 次判定完全同构，只是被测对象换成了门禁本身。

> ⭐⭐⭐⭐⭐ **而我们几乎从不怀疑门禁。** 红灯出现时排查方向是"技能坏了"，
> 从来不是"门禁坏了"——因为门禁是用来判断别人的东西，它不在被怀疑的集合里。

一个便宜到没有理由不做的做法：**在 PR 上自动标注本次是否首次通过**。

```
✓ skill-eval (通过，第 1 次)
⚠ skill-eval (通过，第 3 次重试)   ← 可见的 flaky 证据
```

> ⭐⭐⭐⭐⭐ 绿灯掩盖 flaky，而"第 3 次"这个数字把 flaky 变成可见的事实。
> 它不需要改评测、不需要改门禁，只需要把已有的重试次数显示出来。

## 3. 三类 flaky 源，修法完全不同

### ① 被测物本身不稳定（技能侧）

技能输出有随机性（采样、并行顺序、未固定 seed）。

- 判定：同一输入跑 N 次，输出不同
- ⭐⭐⭐⭐⭐ 修法：**降温度 / 固定 seed / 消除顺序依赖**
  （《`skill-aggregation/references/aggregation-order-dependence.md`》）
- ❌ 错误修法：加断言容差、放宽阈值 → 把"不稳定"改成"测不出来"

### ② 环境不稳定（测试侧）

```
依赖外部服务超时 · 共享数据库被别的测试改了 · 磁盘满 · 时间跨了午夜
```

- 判定：**清空环境跑两次应完全一致**
  （《`skill-evaluating/references/test-doubles-fixtures.md`》）
- ⭐⭐⭐⭐⭐ 修法：替身 / 固定时钟 / 独立命名空间

### ③ ⭐⭐⭐⭐⭐ 断言本身不稳定（最容易被误判为①）

```python
assert "大概" in output or "大约" in output   # 意图是"要带不确定标记"
```

模型这次输出"约"，下次输出"大约"，再下次输出"估计"。断言随机命中。

> ⭐⭐⭐⭐⭐ **它的表现和①一模一样——红灯随机出现——于是排查方向是"技能不稳定"，
> 团队去给技能加约束、降温度，而问题在断言。**

判定方法：**红灯出现时，失败的具体断言是不是同一个？**

```
每次红灯，失败项都不同 → ① 被测物不稳定
⭐⭐⭐⭐⭐ 每次红灯，失败的断言随机在几个等价断言间跳 → ③ 断言不稳定
```

| | ① 被测物 | ② 环境 | ⭐⭐⭐ ③ 断言 |
|---|---|---|---|
| 症状 | 输出不同 | 有时直接报错 | 输出相同却随机红 |
| 排查方向 | 技能 | 基础设施 | ⭐⭐⭐⭐⭐ **几乎总是查错方向** |
| 修法 | 固定 seed | 隔离 | ⭐ 改断言（不是改技能） |

## 4. ⭐⭐⭐⭐⭐ "重跑一次就绿了"在训练团队忽略红灯

这是本份最重要的一条。重跑这个动作本身是**中性**的——它确实能区分 flaky 和真失败。
问题在于它被执行的**方式**：

```
正确用法：先判定是不是 flaky（跑 3 次比对），再决定
常见用法：⭐⭐⭐⭐⭐ 不看内容，直接重跑，绿了就走
```

> ⭐⭐⭐⭐⭐ **第二种用法下，"重跑"不是诊断手段，是**绕过手段**。**
> 而它和 `--no-verify` 的唯一区别是：它留了一条绿灯记录，看起来更干净。

它的自我强化很隐蔽：

```
重跑成功 → PR 合并 → 没有事故 → 证明重跑是对的 → 下次更早重跑
```

> ⭐⭐⭐⭐⭐ **而没有事故不能证明什么**——因为 flaky 门禁本来就有 2/3 概率自己变绿，
> 你无法从"这次没事"里得到任何关于真失败的证据。

两条硬规则：

1. ⭐⭐⭐⭐⭐ **重跑之前必须记录第一次的失败项**（一行日志即可）。
   没有记录的重跑 = 那次失败从未发生过，于是 flaky 率永远是 0。
2. ⭐⭐⭐⭐ **同一 PR 上同一检查最多重试 1 次**。第二次还红就是真失败。
   理由不是严格，是⭐⭐⭐ **第三次重跑时已经没人看内容了**。

## 5. Quarantine 必须有时限

标记 flaky、移出关键路径（quarantine）是标准做法，也是**本份唯一一个会静默删除保护的机制**：

```
标记为 flaky → 不再阻断 → ⭐⭐⭐⭐⭐ 没有任何环节会提醒它还在那儿
```

> ⭐⭐⭐⭐⭐ **Quarantine 和"删除这条检查"在运行效果上完全相同，
> 唯一区别是配置文件里还留着它——而那正是它看起来还在工作的原因。**

三条约束：

| 约束 | 没有它会怎样 |
|---|---|
| ⭐⭐⭐⭐⭐ **必须有到期时间**（如 14 天） | 变成永久豁免 |
| ⭐⭐⭐⭐⭐ **到期自动恢复阻断**，不是自动续期 | 需要有人主动决定才能继续豁免 |
| ⭐⭐⭐⭐ 必须有 owner，且不是"团队" | 没人会收到提醒 |

第二条的方向尤其重要：**默认动作应该是"恢复保护"，不是"继续豁免"**。

> ⭐⭐⭐⭐⭐ 这跟"失败全量记录、成功采样"是同一取向——
> 让"需要关注的"自动浮出来，让"省事的"需要主动选择。

还有一条配额：**flaky 标记超过总数的 10% 就该停下来查系统性原因**。
它和《`skill-crafting/references/critical-rules-inflation.md`》的"红线膨胀"同构——
⭐⭐⭐⭐⭐ **flaky 标签的价值来自对比。当它标记了 30% 的检查，"flaky"就成了"红灯"的同义词。**

## 6. 自检

- [ ] ⭐⭐⭐⭐⭐ 同一 commit 跑 3 次，结果一致吗？（判定 flaky 的唯一方法）
- [ ] ⭐⭐⭐⭐⭐ PR 上能看到"第几次通过"吗？看不到 = flaky 不可见
- [ ] ⭐⭐⭐⭐⭐ 红灯时，失败的具体断言是不是同一个？（区分①和③）
- [ ] ⭐⭐⭐ 重跑之前记录第一次的失败项了吗？
- [ ] ⭐⭐⭐⭐⭐ 所有 quarantine 项都有到期时间和具名 owner 吗？
- [ ] ⭐⭐⭐⭐ 到期后默认恢复阻断，还是默认续期？
- [ ] ⭐⭐⭐ flaky 标记超过总数 10% 了吗？
- [ ] ⭐⭐⭐⭐⭐ 有没有人在不看内容的情况下重跑？——**这一条只能靠问，日志上看不出来**
