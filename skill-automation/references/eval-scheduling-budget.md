## 1. ⭐⭐⭐⭐⭐ 全量评测跑得太慢，于是没人等

行为评测（真跑 `claude -p`）的成本和单元评测不是一个量级：

```
结构检查（YAML / 引用 / 长度）  → 秒级，几乎免费
行为评测（真跑一次技能）        → ⭐⭐⭐⭐ 分钟级，每次要真跑模型
```

于是一个 40 用例 × 3 次的评测套件，耗时是"提交后等 20 分钟"。

然后发生的事不是"团队接受了 20 分钟"，而是：

```
第 1 周：等 20 分钟
第 2 周：⭐⭐⭐⭐⭐ 改成"只跑 10 个关键用例"，3 分钟
第 3 周：⭐⭐⭐⭐⭐ 改成 5 个
第 4 周：⭐⭐⭐⭐⭐ 改成 1 个"冒烟用例"
```

> ⭐⭐⭐⭐⭐ **每一步都是合理的妥协，而终点的评测套件只覆盖了 2.5% 的用例，
> 且它仍然显示"通过"。**

这跟 flaky 门禁的失效是同一种形状——**不是被关掉的，是被逐步稀释的**。
差别在于：flaky 是"红灯被忽略"，这里是"覆盖范围被悄悄缩小"。

> ⭐⭐⭐⭐⭐ 而两者都留下了一个看起来正常的绿灯。

关键的不对称：

| | 缩小覆盖范围 | 减少判定次数 |
|---|---|---|
| 省下 | 时间 | 时间 |
| ⭐⭐⭐⭐⭐ 代价 | ⭐⭐⭐⭐⭐ **回归发生在没跑的那部分** | 稳定性判断失效 |
| 可见吗 | ❌ | ⭐ 有时可见 |

而"回归发生在没跑的那部分"恰恰是最常见的——**因为你改的正是那部分**。

## 2. 三层调度：什么在什么时机跑

按反馈速度要求分层，不是按重要性分层（重要性大家都一样重要，排不出队）：

| 层 | 时机 | 内容 | 目标耗时 |
|---|---|---|---|
| ⭐ L1 提交前 | 每次 commit / PR | 结构 + 冒烟（1–3 用例） | < 60s |
| ⭐⭐⭐⭐ L2 合并后 | 每次合入主干 | 关键路径（10–20 用例） | < 10min |
| ⭐⭐⭐⭐⭐ L3 周期 | 每日 / 每周 | **全量**（套件 × 3 次） | 不限 |

三层各自的关键点：

**L1 必须能在本地跑，且和 CI 跑的是同一套**
否则本地绿了 CI 红，团队的结论是"CI 环境有问题"。
⭐⭐⭐⭐ 判据：同一份脚本，`--local` 和 `--ci` 只差一个参数。

**L2 是唯一能真正拦住回归的那一层**
L1 太浅抓不到，L3 太晚（已经合入了）。
⭐⭐⭐⭐⭐ 所以它必须是**阻断的**，不能是"报告"。

**L3 的价值不在拦截，在发现缓慢漂移**

> ⭐⭐⭐⭐⭐ **它跑得慢没关系，但它必须有固定的运行时间。**
> 一个"想起来才跑"的全量评测，其价值趋近于零——因为你无法区分
> "这次下降"和"上次跑的时候本来就低"。

这与 `production-drift-signals` 的分工很清楚：
那份是**每次调用都有的廉价信号**（不需要跑评测），
这份的 L3 是**周期性但完整的判定**（需要跑评测，但能给出对错）。

## 3. ⭐⭐⭐⭐⭐ 子集通过就合入 = 门禁形同虚设

最常见的妥协是这句：

> "L3 太慢了，我们改成 L3 失败了再去看，不阻断。"

听起来很务实。实际效果：

```
L3 不阻断 → L3 红了 → 没人立刻看（因为在忙别的）
         → 第二天又红了 → 已经是"常态"
         → ⭐⭐⭐⭐⭐ 从此 L3 的输出不再被任何人读取
```

> ⭐⭐⭐⭐⭐ **一个不阻断的检查，其输出会在大约两周内变成无人读取的背景噪音。**
> 这不是纪律问题——人的注意力会自然地从"不打断我的东西"上移开。

正确做法不是"让它阻断"，是**让它晚一点阻断**：

| 方案 | 效果 |
|---|---|
| ⭐⭐⭐⭐⭐ **L3 失败 → 自动开一个 issue，指派给最后改动该技能的人** | 变成有 owner 的工作项 |
| ⭐⭐⭐⭐ L3 连续失败 2 次 → 该技能标记为"待修"，触发时降级（改用上一版） | 有后果 |
| ⭐⭐⭐⭐⭐ L3 失败但 L2 通过 → 允许合入，**但允许合入的次数要有限** | 有额度，不是无限 |

第三条最值得抄：⭐⭐⭐⭐⭐ **给"带债合入"一个配额**（比如每月 2 次），
用完就必须先修。它承认了紧急情况是真实的，同时让"紧急"不再是无限量的。

## 4. 预算：一次评测的成本构成

行为评测的成本不只是"调用模型的钱"：

```
直接成本 = 用例数 × 重复次数 × 单次 token × 单价
间接成本 = ⭐⭐⭐⭐⭐ 等待时间内人的注意力切换
```

> ⭐⭐⭐⭐⭐ 第二项通常被完全忽略，而在小团队里它是主要成本——
> 一个人等 20 分钟不是 20 分钟的空闲，是**一次上下文切换**。

三个降本方向，按"先动哪个"排序：

**① 减少重复次数，而不是减少用例数**

```
3 次 → 2 次：省 33%，仍能发现不稳定（两次不一致 = 有 flaky）
2 次 → 1 次：省 50%，⭐⭐⭐⭐⭐ 但从此无法区分"不稳定"和"错"
```

> ⭐⭐⭐⭐⭐ **1 次是质变，不是量变**——它让整个第④格（对但不稳）从视野里消失。
> 所以最低是 2 次，不要为了省钱掉到 1 次。

**② ⭐⭐⭐⭐ 分层：稳定性用例只跑 1 次，判定性用例跑 3 次**

不是所有用例都需要重复。已经连续 20 次稳定的用例，它的价值在于"有没有回归"，
一次就够；新加的、历史上 flaky 的用例才需要重复。

**③ ⭐⭐⭐⭐⭐ 用便宜模型跑回归，用目标模型跑定版**

回归检测只需要"和上次不一样"，不需要"这次有多好"。
⭐⭐⭐⭐⭐ 但这一条有个硬前提：**便宜模型的判定结果不能用来做发布决策**——
它只能告诉你"去看一眼"，不能告诉你"可以发"。

## 5. ⭐⭐⭐⭐ 跑得慢的评测要变成异步的，不是变成可选的

上面所有问题的根因是同一个：**把"慢"翻译成了"可选"**。

```
慢 → 等不起 → 改成子集 / 改成不阻断 / 改成手动触发
```

> ⭐⭐⭐⭐⭐ 这三个翻译都把"慢"变成了"不保证执行"。
> 正确的翻译只有一个：**慢 → 移出同步路径，但保持必然执行。**

三种形态：

| 形态 | 什么时候用 | 关键约束 |
|---|---|---|
| ⭐⭐⭐⭐ 合并后队列 | L2、L3 | ⭐⭐⭐⭐⭐ 必须有结果回写（PR 上能看到） |
| 定时全量 | L3 | 固定时间 + 固定基线 |
| ⭐⭐⭐⭐ 事故触发 | 任何层 | 事故 → 加用例 → **永久留在套件里** |

回写那条最关键：⭐⭐⭐⭐⭐ **异步执行 + 结果不回写到开发者眼前 = 等于没跑。**
因为它唯一能起作用的方式是"有人看到它红了"。

最后一条（事故触发）已在 `ci-skill-validation` 里强调过，这里补上它的调度含义：

> ⭐⭐⭐⭐⭐ **事故产生的用例应该进 L1 还是 L3？**
> 答案几乎总是 **L1**——因为它测的是"这个具体的事故会不会再发生"，
> 而它必须每次都被检查。放进 L3 等于接受它每月才被验证一次。

## 6. 自检

- [ ] ⭐⭐⭐⭐⭐ L1 能在本地跑吗？本地和 CI 是同一套脚本吗？
- [ ] ⭐⭐⭐⭐⭐ 用例重复次数 ≥ 2 吗？（1 次会让"不稳定"彻底不可见）
- [ ] ⭐⭐⭐⭐ L2 是阻断的吗？（它是唯一能真正拦住回归的一层）
- [ ] ⭐⭐⭐⭐⭐ L3 有固定运行时间吗？（没有则无法区分"这次下降"和"本来就低"）
- [ ] ⭐⭐⭐⭐ 不阻断的检查，其输出有人读吗？（两周内会变成背景噪音）
- [ ] ⭐⭐⭐⭐⭐ 套件规模相比一个月前缩小了吗？（缩小的过程每一步都合理）
- [ ] ⭐⭐⭐⭐⭐ 带债合入有配额吗？（没有配额的"紧急"是无限量的）
- [ ] ⭐⭐⭐ 事故产生的用例进 L1 了吗？
