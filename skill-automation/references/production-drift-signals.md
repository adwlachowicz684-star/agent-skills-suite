## 1. ⭐⭐⭐⭐⭐ 正确性指标要评估，漂移指标不要

已有体系里的指标几乎都是**正确性指标**：

```
通过率 · delta · 触发命中率 · 覆盖率
```

它们都需要三样东西才能算：一份测试集、一个判定器、一次运行。
所以它们天然是**周期性**的——周更、发版前跑、事故后补。

> ⭐⭐⭐⭐⭐ **而技能的失效大多数不发生在评估节点上，发生在两次评估之间。**

漂移指标的特性相反：

| | 正确性指标 | ⭐ 漂移指标 |
|---|---|---|
| 需要判定对错吗 | ⭐ 需要 | ⭐⭐⭐⭐⭐ **不需要** |
| 成本 | 一次评估 | ⭐⭐⭐⭐⭐ 一条日志字段 |
| 频率 | 周期 | ⭐⭐⭐⭐⭐ 每次调用 |
| 能发现什么 | 现在好不好 | ⭐⭐⭐⭐⭐ **什么时候变的** |

> ⭐⭐⭐⭐⭐ 核心洞察：**要发现"变了"，不需要知道"哪个更好"。**
> 分布变了就是变了，判定是之后的事。

这补上了 `outgrowth-regression-detection.md` 缺的执行手段——那份给了三种模式和判据，
但没给"怎么在不跑评估的情况下知道回归发生了"。

## 2. 六个免费信号

按采集成本排序，全部来自已有的调用日志字段：

**① 触发率**（最便宜，也最先变）

```
本周 12 次 → 本周 3 次
```

不意味着坏了，但意味着⭐⭐⭐⭐⭐ **它与输入流的关系变了**——
可能是用户改了说法，也可能是另一个技能开始抢。

**② 输出长度分布**

> ⭐⭐⭐⭐⭐ **长度膨胀是最容易被忽略的退化。**
> 输出越来越啰嗦但没人报 bug，因为内容还是对的。
> （与 `skill-output/references/output-stability-contract.md` 的"上限 ≤ 基线 × 1.5"同一信号，
> 那份用在快照测试里，这份用在生产监控里。）

**③ 工具调用序列**

```
老：Read(3) → Grep(1) → Write(1)
新：Read(3) → Grep(1) → Edit(2) → Edit(1) → Edit(1)
```

⭐⭐⭐⭐⭐ **序列变化几乎总是行为变化**——而且它能发现输出看不出的变化：
结果一样，但走了一条更慢/更危险的路（例如从"一次写入"变成"反复修改"）。

**④ attempts（重试次数）**

```
attempts 均值 1.02 → 1.35
```

> ⭐⭐⭐⭐⭐ 与 `skill-chain-failure/references/retry-amplification.md` 呼应：**重试成功会抹掉失败记录**，
> 于是"成功率"仍然 100%，而 attempts 是唯一留下来的痕迹。

**⑤ coverage / 处理单元数**

```
处理 47 个 → 处理 20 个（并发上限）
```

截断类失败的唯一可见信号（见 `skill-aggregation/references/fan-out-fan-in.md`）。

**⑥ 用户否定率**（最贵，但信息量最大）

```
"不对"、"重来"、"不是这个"、"换个方式"
```

> ⭐⭐⭐⭐⭐ **这是唯一一个"来自用户的、不需要评估的"正确性代理指标。**
> 它不需要你知道输出对不对，只需要记一句用户有没有推翻它。

## 3. ⭐⭐⭐⭐⭐ 基线是"它自己"，不是"别的技能"

最容易做错的一步：拿全库平均值当基线。

```
技能 A 触发率 3 次/周，全库平均 8 次/周 → A 是不是要归档？
```

> ⭐⭐⭐⭐⭐ **不对。低频高价值的专家型技能本来就该是 3 次/周**
> （见 `skill-portfolio-audit.md`）。跟平均值比，会把最该留的那批先删掉。

正确的基线是**它自己的历史**，三种取法：

| 基线 | 适合 | 风险 |
|---|---|---|
| 上周同口径 | 高频技能 | 周内噪声 |
| ⭐⭐⭐⭐⭐ 自身近 4 周中位数 | 中低频 | 慢变漂移会被吸收 |
| 发版前的窗口 | 刚改过 | 需要人工圈定 |

> ⭐⭐⭐⭐⭐ **"自身中位数"是最通用的**——它不假设任何绝对阈值，
> 而"这个技能该被用几次"这个问题根本没有绝对答案。

一个必须记住的例外：

> ⭐⭐⭐⭐⭐ **改了 description 之后，旧基线立即失效。**
> 触发率的变化是预期的（那正是改 description 的目的），
> 但输出长度、工具序列的基线仍然有效——**只有被改的那个维度要重置基线。**

## 4. 三类变化各自意味着什么

| 变化形状 | 含义 | 先看哪份 |
|---|---|---|
| ⭐ 阶跃（一天内跳变） | 有具体事件：改了技能 / 模型更新 / 上游变了 | `skill-versioning/references/version-diff-behavior-compare.md` |
| ⭐⭐⭐⭐ 缓坡（数周单向漂移） | 输入流在变，或技能在被追上 | `outgrowth-regression-detection.md` |
| ⭐⭐⭐⭐⭐ 方差变大（均值不变） | 技能不稳定，或环境有随机性 | `failure-quadrant-diagnosis.md` 第④格 |

> ⭐⭐⭐⭐⭐ 第三类最值钱也最常被漏：
> **只看均值的话，它看起来完全正常**——而它正是"某一天会突然出错"的前兆。

而"均值不变、方差变大"这个形状，恰好对上了 `failure-quadrant-diagnosis.md` 里
"对但不稳"那一格——那个格子此前只能靠"同一输入跑 3 次"来发现，
⭐⭐⭐⭐⭐ 现在生产日志里就能看到，不需要专门跑。

## 5. 告警怎么设才不会麻木

```
❌ 六个信号全告警 → 每天几十条 → 全部被忽略
```

三条纪律：

**① 只告警方差和阶跃，不告警缓坡**

> ⭐⭐⭐⭐⭐ 缓坡要看，但不能告警——它没有"今天该做什么"的答案。
> 缓坡的正确载体是月度审计，不是告警。

**② 一个技能同时只有一条告警在飞**

> ⭐⭐⭐⭐⭐ 六个信号高度相关（工具序列变了，输出长度通常也变）。
> 全报 = 同一件事报六遍。做法：按优先级只发最高那条，其余附在详情里。

**③ 告警必须带"上次正常是何时"**

> ⭐⭐⭐⭐⭐ **"触发率下降"是没法行动的，"触发率自 09-12 起下降"是可以行动的。**
> 差别在于后者能让你去查那天改了什么——而大多数漂移确实对应一次具体改动。

与 `canary-release.md` 的分工：那份管**新版本**的灰度指标，
这份管**已全量**的技能——灰度结束后，监控不能一起结束。

## 6. 自检

```
□ ⭐⭐⭐⭐⭐ 六个信号里，你采集了几个？少于 3 个 → 只能靠评估发现漂移
□ ⭐⭐⭐⭐⭐ 基线是"它自己的历史"吗？用了全库均值 → 会误杀低频高价值
□ ⭐⭐⭐⭐⭐ 改了 description 之后，重置了对应维度的基线吗？
□ ⭐⭐⭐⭐ 有没有看方差？只看均值 → "对但不稳"那一格永远不可见
□ ⭐⭐⭐⭐ 告警带"上次正常是何时"吗？不带 → 收到也没法行动
□ ⭐⭐⭐⭐ 缓坡进了月度审计而不是告警流吗？
```

一分钟验证法：

> ⭐⭐⭐⭐⭐ **挑一个你最熟的技能，问："上一次有人抱怨它，和上一次有人改它，
> 哪个更早？"** 如果抱怨更早——说明漂移已经发生了一段时间而没人知道，
> 那六个信号里至少有一个本可以提前告诉你。
