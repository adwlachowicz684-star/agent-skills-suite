## 1. ⭐⭐⭐⭐⭐ 示例同时教输出和适用范围

写示例时的注意力分配：

```
输出侧：反复改，对齐契约，检查格式、长度、字段     ← 得到全部注意力
输入侧：一行"输入：Q4 销售数据.xlsx"              ← ⭐⭐⭐⭐⭐ 随手写的
```

而模型从示例里学的是**两端**：

| 侧 | 学到的 | 有没有人设计 |
|---|---|---|
| 输出 | 长什么样 | ⭐⭐⭐⭐⭐ 有（契约、模板、长度预算全在为它服务） |
| ⭐⭐⭐⭐⭐ 输入 | **什么样的输入会走到这里** | ⭐⭐⭐⭐⭐ **没有** |

> ⭐⭐⭐⭐⭐ **于是适用范围被一行随手写的输入决定了。**

机制上它和"示例的详尽度锚定输出长度"完全同构：
示例是已发生的事实，模型从中提取**一切可提取的规律**，
包括作者从未打算当规律的那些属性——格式、规模、语言、完整度、数量。

## 2. description 管任务类型，示例管输入形态

触发匹配通常被理解成只看 description。实际是两道匹配：

```
① description  → 任务类型匹配（"分析销售数据"）
② ⭐⭐⭐⭐⭐ 示例输入 → 形态匹配（"长这样的数据才是我管的"）
```

两道都要过。而⭐⭐⭐⭐⭐ **第②道从没被显式设计过**，于是它呈现为
"description 明明写了，但就是不触发"——排查方向指向 description，越改越偏。

一个典型现场：

```
description：分析销售数据，输出同比环比与异常提示
示例输入：   sales_2026Q1.xlsx（字段齐全、单文件、中文表头）

用户输入：  这两个 PDF 里的销售数据，帮我看看
实际：      不触发
```

> ⭐⭐⭐⭐⭐ **三个属性同时不匹配（格式、数量、字段来源），
> 而这三个属性没有任何一处写着——它们只存在于那一行示例输入里。**

## 3. ⭐⭐⭐⭐⭐ 三个被示例偷偷定义的边界

| # | 边界 | 示例里的体现 | 不匹配的后果 |
|---|---|---|---|
| ① | ⭐⭐⭐⭐⭐ **格式/载体** | 全是 `.xlsx` | CSV、PDF、数据库结果被当成"不是这类" |
| ② | ⭐⭐⭐⭐⭐ **数量** | 全是 1 个文件 | 12 个文件时不触发（或触发后只处理 1 个） |
| ③ | ⭐⭐⭐⭐ **完整度** | 字段齐全、无缺失 | 脏数据时认为"这不属于我"，用户于是自己手工处理 |

**② 最隐蔽，因为它和《`skill-input/references/input-cardinality.md`》那条完全接得上**：

> 技能的默认基数是 1，而示例输入是基数唯一的锚点。
> 示例里是一个文件 → 输出里呈现一个 → ⭐⭐⭐⭐⭐ **用户以为一共就一个**。

**① 最常命中的是跨格式**：作者采集示例时，手上恰好全是同一种格式，
于是"格式"这个维度在示例集里**方差为零**——
⭐⭐⭐⭐⭐ **方差为零的维度，模型无法知道它是变量还是常量**，默认按常量处理。

## 4. ⭐⭐⭐⭐⭐ 这是唯一"写在正文里却不在任何 checklist 上"的假设

已有《`skill-input/references/assumption-registry.md`》要求把假设显式登记成章节。
但示例输入携带的假设不在那个章节里，也不在任何检查表里：

```
假设章节里：  ✅ 已写"数据为 UTF-8 编码"
示例输入里：  ⭐⭐⭐⭐⭐ 全是 .xlsx（隐含"载体是表格文件"）
```

两条假设性质完全相同，⭐⭐⭐⭐⭐ **但只有第一条会被 review**——
因为第二条不长成"假设的样子"，它长成"一个例子"。

这正好解释了那个反复出现的现象：

```
按假设清单逐条核对，全都覆盖了，可线上还是有不该发生的不触发
```

> ⭐⭐⭐⭐⭐ **因为清单管的是写下来的假设，
> 而示例携带的假设从未进入清单。**

## 5. 设计示例的输入侧

把输入侧当成一层需要设计的信号，而不是一行说明。

**① 让关键维度在示例集里有方差**

| 维度 | 至少出现两种取值 |
|---|---|
| ⭐⭐⭐⭐⭐ 格式/载体 | `.xlsx` + 另一种（CSV / PDF / 接口返回） |
| ⭐⭐⭐⭐⭐ 数量 | 1 个 + 多个 |
| ⭐⭐⭐⭐ 完整度 | 齐全 + 缺字段（示范"缺了怎么办"，不是"这不归我管"） |

> ⭐⭐⭐⭐⭐ **有方差的维度才是变量。方差为零的维度，模型会当成常量。**

**② 覆盖不到的边界，用一句显式说明**

```
输入形态：表格文件（.xlsx/.csv）；PDF 与图片需先经 <转换步骤> 处理
```

这句的代价约 20 token，⭐⭐⭐⭐⭐ 而它把"静默不触发"变成"按已知路径处理"。

**③ 不希望被示例锚定的属性，显式反锚定**

```
示例输入为单个文件；⭐⭐⭐⭐⭐ 多个文件时对每个分别执行，不得只处理第一个
```

这与"示例值用假值（复制到会暴露自己的东西）"是同一手法的另一处应用：
⭐⭐⭐⭐⭐ **没法阻止它提取规律，就把规律显式写成它该是的值。**

**④ 示例输入不要"比真实更干净"**

《`skill-examples/references/example-mining-from-traces.md`》已确立"输入要带杂讯"。
这里补上理由的另一半：

> ⭐⭐⭐⭐⭐ 干净的输入不只是"教不了脏数据怎么处理"，
> **它还把"脏数据"划到了适用范围之外**——前者只是没教，后者是排除了。

## 6. 自检

```
□ ⭐⭐⭐⭐⭐ 示例集里，格式/载体这个维度有几种取值？只有一种 → 它被当成了常量
□ ⭐⭐⭐⭐⭐ 示例输入都是 1 个文件/1 条记录吗？是 → 默认基数被锚定为 1
□ ⭐⭐⭐⭐⭐ 把示例输入换成另一种格式（xlsx → PDF），描述还匹配吗？
     不确定 → 边界由示例偷偷定义，而它不在任何 checklist 上
□ ⭐⭐⭐⭐ 示例输入都是字段齐全的吗？是 → 脏数据被划在范围外
□ ⭐⭐⭐⭐ 有没有一句显式的"输入形态"说明？没有 → 加（约 20 token）
□ ⭐⭐⭐⭐ 示例里被锚定的属性（数量、规模），有没有显式反锚定？
□ ⭐⭐⭐ 上次"该触发没触发"的排查，有没有检查过示例输入？
     ⭐⭐⭐⭐⭐ 大概率没有——而它是第二道匹配
```
