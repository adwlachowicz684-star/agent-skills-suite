## 1. ⭐⭐⭐⭐⭐ 编出来的示例为什么不灵

坐下来写示例时，你脑子里出现的是**你希望它长什么样**：

```
输入：一份干净的、字段齐全的订单数据
输出：格式完美、字段齐全的分析报告
```

> ⭐⭐⭐⭐⭐ **这个示例教会模型的是"在一切顺利时输出什么"——
> 而模型早就知道。**

三个具体的失效：

**① ⭐⭐⭐⭐ 编的示例没有杂讯，而真实输入全是杂讯**

```
你编的："分析这批订单"
真实的："boss 发来 Q4 sales final FINAL v2.xlsx，利润=收入(C列)-成本(D列)"
```

> ⭐⭐⭐⭐⭐ 后者才需要示例——因为⭐⭐⭐ **模型不知道"FINAL v2"意味着要用这一版**，
> 也不知道利润要自己算。这些是编不出来的。

**② ⭐⭐⭐⭐⭐ 编的示例只覆盖"顺利路径"**

> ⭐⭐⭐⭐ 与失败路径的规律完全一致：
> 顺利路径你开发时早跑过几十遍了，**不需要示例**。

**③ ⭐⭐⭐⭐ 编的时候你会无意识地"更正确"**

```
编的示例里，分类是干净的、边界是清楚的
真实的输入里，⭐⭐⭐⭐⭐ 边界恰恰是模糊的——而那正是模型需要示例的地方
```

## 2. ⭐⭐⭐⭐⭐ 五个矿脉

按信息密度排序：

| # | 矿脉 | ⭐ 密度 |
|---|---|---|
| 1 | ⭐⭐⭐⭐⭐ **真实运行记录**（日志、trace、历史输出） | 最高 |
| 2 | ⭐⭐⭐⭐⭐ **你改好的那次**（bad → good 对照） | 最高 |
| 3 | ⭐⭐⭐⭐ 真实的用户原话（含错字、简称、口语） | 高 |
| 4 | ⭐⭐⭐⭐ 线上事故与边界 bug | 高 |
| 5 | ⭐⭐⭐ 现有文档里的好例子（复用，不重编） | 中 |

> ⭐⭐⭐⭐⭐ 第 1 和第 2 条是同一件事的两面：
> **第 1 条给"真实长什么样"，第 2 条给"好的标准是什么"。**

## 3. ⭐⭐⭐⭐⭐ 第一矿脉：真实运行记录

三类可直接用的记录：

**① ⭐⭐⭐⭐⭐ 已经被采纳的输出**

```
用户拿去用了、没改就用了 → ⭐⭐⭐⭐⭐ 这就是正例，且是已验证的
```

> ⭐⭐⭐⭐⭐ 判据很简单：**不是"你觉得好"，是"用户没改就用"**——
> 这是唯一有外部验证的示例来源。

**② ⭐⭐⭐⭐⭐ 被退回来重做的输出**

```
"这个不行，要按 X 来" → ⭐⭐⭐⭐⭐ 这是最好的素材：
                        它同时给了反例（被退回的）和正例（改好的）
```

> ⭐⭐⭐⭐ 与 `gotchas-mining.md` 的第一矿脉（你自己的纠错记录）是同一批材料——
> ⭐⭐⭐⭐⭐ 所以一次采集可以同时产出 Gotchas 和示例，
> 而且它们天然互相印证。

**③ ⭐⭐⭐⭐ 日志里的边界输入**

```
空输入 · 超长 · 缺字段 · 编码异常
```

> ⭐⭐⭐⭐ 这些在 `eval-case-design.md` 里是必测用例，
> ⭐⭐⭐⭐⭐ 而如果它们没进示例，模型第一次遇到时只能靠猜。

采集动作（很便宜）：

```
回头翻最近 20 次这个任务的运行记录
→ 标出：3 个被采纳的、2 个被退回的、2 个边界输入
→ 7 条示例，够用了
```

> ⭐⭐⭐⭐⭐ **7 条就够了**——这与少样本收益递减一致，
> 而且示例占上下文，多了反而有害。

## 4. ⭐⭐⭐⭐ 从"改好的那次"里捞

一个具体的采集格式，比单条示例有用得多：

```markdown
### 示例：利润口径

输入：Q4 sales final FINAL v2.xlsx（含 C 列收入、D 列成本）
❌ 错误输出：直接读"利润"列
   → 为什么错：该文件没有利润列，需按 收入−成本 计算
✅ 正确输出：先计算利润，再分析
⭐ 依据：用户原话"利润=收入(C列)-成本(D列)"
```

> ⭐⭐⭐⭐⭐ **成对写（❌/✅）比只写 ✅ 值钱得多**——
> 这与 `bad-skill-anatomy.md` 里"差评反例比再多正向示例都更能让模型理解什么算合格"
> 完全一致。

而⭐⭐⭐⭐ **"为什么错"和"依据"两行是采集时的天然产物**
（因为这就是你当时纠正它时说的话）——
⭐⭐⭐⭐⭐ 所以它们不是额外工作量，只是别丢掉。

> ⭐⭐⭐⭐ 这也解释了为什么示例要带 Rationale 字段
> （`examples-three-branches.md`）：
> **编的示例写不出 Rationale，采集的示例天然就有。**

## 5. ⭐⭐⭐⭐⭐ 采集纪律

| 纪律 | ⭐ 说明 |
|---|---|
| ⭐⭐⭐⭐⭐ **保持原样** | ⭐⭐⭐⭐⭐ 别把真实输入"整理干净"——杂讯就是价值 |
| ⭐⭐⭐⭐ 标明来源 | 便于日后判断是否过期 |
| ⭐⭐⭐⭐⭐ **7 条上限** | 多了占上下文，收益递减 |
| ⭐⭐⭐⭐ 至少 1 条模糊输入 | ⭐⭐⭐⭐⭐ 唯一教"判断"的那一档 |
| ⭐⭐⭐⭐ 至少 1 条失败/边界 | 否则失败路径没示例 |
| ⭐⭐⭐ 定期替换 | ⭐⭐⭐ 真实输入会变，示例也会腐烂 |

> ⭐⭐⭐⭐⭐ 第一行最重要，也最常被违反：
> **采集完你会忍不住顺手改一下措辞——那一改，价值就没了。**

一个检验方法：

> ⭐⭐⭐⭐⭐ **如果你的示例读起来像教科书，说明你编了。**
> 真实输入的标志是：⭐⭐⭐⭐ 有冗余、有口语、有不完整的地方。

## 6. ⭐⭐⭐ 什么时候编是合理的

三种情况，编是唯一选择（承认它，别硬采集）：

```
① ⭐⭐⭐⭐ 技能还没上线，没有运行记录
   → 先编 2–3 条最小示例上线，⭐⭐⭐⭐ 上线后立刻用真实的替换
② ⭐⭐⭐⭐ 需要一条"规范形态"的示例来定义格式
   → ⭐⭐⭐⭐⭐ 这一条就该是编的、干净的（它的作用是定格式，不是教判断）
③ ⭐⭐⭐ 覆盖一个已知但尚未发生的边界
   → 编，但⭐⭐⭐⭐ 标注"(构造)"，避免日后被当成真实案例
```

> ⭐⭐⭐⭐⭐ 第 ② 条是关键区分：
> **示例有两种作用——定格式、教判断。**
> ⭐⭐⭐⭐⭐ **定格式的示例该编（干净、规范）；
> 教判断的示例必须采集（带杂讯、带 Rationale）。**
>
> 把所有示例都编成"干净规范"的样子，
> 就是为什么很多技能的示例看起来很专业却不起作用。

---

## 一句可贴在墙上

> ⭐⭐⭐ **定格式的示例该编，教判断的示例必须采集。
> 而如果你的示例读起来像教科书——说明你编了。**
