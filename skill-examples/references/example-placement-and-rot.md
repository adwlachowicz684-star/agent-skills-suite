## 1. ⭐⭐⭐⭐⭐ 示例同时是最有效和最贵的

两个已知事实摆在一起会产生一个此前没人明说的冲突：

```
① ⭐⭐⭐⭐⭐ 模型对示例的信任度高于对指令的信任度（最强上下文信号）
② 示例是正文里单位 token 最高的内容（一段输入+一段输出+Rationale）
```

> ⭐⭐⭐⭐⭐ **最有说服力的东西恰好是最贵的。** 于是"多给示例"和"惜字如金"
> 在同一个位置直接冲突，而多数技能是靠感觉在这两者之间取一个值。

真正该算的不是"示例占多少"，是比例：

```
示例占比 = 示例 token / 正文 token
```

健康区间**不超过 1/3**。超过之后发生的事不是"更贵"，是⭐⭐⭐⭐⭐ **正文被稀释**——
模型的注意力落在示例上（`example-overrides-instruction.md`），
而正文里那些没有示例对应的规则，实际上失去了效力。

> ⭐⭐⭐⭐⭐ **示例给得越多，没被示例覆盖的规则越弱。**
> 这不是"边际收益递减"，是"边际成本转嫁给了正文"。

## 2. 放正文还是下沉：判据是"没有它会错吗"

渐进披露给了第三个选项（下沉到 `examples/` 参考文档按需加载），
但 `reference-discoverability.md` 已经指出：⭐⭐⭐⭐⭐ **"需要时读"这一步不保证发生。**

于是三选一的判据不是"重不重要"：

| 放哪 | 判据 | 代价 |
|---|---|---|
| ⭐⭐⭐⭐⭐ 正文 | **没有这个示例，模型会做错** | 每次触发都付费 |
| 下沉 | 没有它模型会做得差一点，但不会错 | ⭐⭐⭐⭐⭐ 可能永远不被读 |
| ⭐⭐⭐⭐⭐ 不放 | 有了它模型也不会更对 | 无 |

> ⭐⭐⭐⭐⭐ **中间那档最尴尬：它既付不起正文的位置，又常被漏读。**
> 所以下沉的示例必须在正文留一句"什么时候读它"（路由行），
> 否则它就是一份写了但不存在的内容。

第三行是常被忽略的：**有些示例是纯装饰**——它让技能看起来完整、专业、好评审，
但不改变模型行为。判据：

> ⭐⭐⭐⭐⭐ **遮住这个示例再跑一次，输出有区别吗？**
> 没有 → 它是给评审者看的，不是给模型看的。

## 3. 正文只放一个：最小判别示例

如果正文只能留一个，留哪个？

```
❌ 最典型的那个（它演示的是模型本来就会做的事）
✅ ⭐⭐⭐⭐⭐ 最容易做错的那个
```

> ⭐⭐⭐⭐⭐ **典型示例证明的是"这个技能能被使用"，
> 判别示例证明的是"这个技能和通用做法不一样"。**
> 只有后者值得占正文的位置。

最小判别示例的三要素：

```
输入：一个处在边界上的真实输入（带杂讯）
输出：正确的处理
⭐⭐⭐⭐⭐ Rationale：为什么这里不能按常规做法做
```

第三条不能省——没有它，模型学到的是"这种输入长这样"，不是"这种输入要那样处理"。
（与 `few-shot-example-quality.md` 的 Rationale 要求同源，但这里的理由不同：
⭐⭐⭐⭐ 正文位置的示例必须用 Rationale 换取它占的空间。）

数量上：**正文 1 个，下沉 3–5 个，总计不超过 5**。
上限 5 与少样本收益递减点一致（超过之后新增示例主要增加的是长度，不是判别力）。

## 4. ⭐⭐⭐⭐⭐ 示例比正文烂得快

已有文档反复讲"技能里的事实会腐烂"（`memory-layering-and-skills.md` 的程序记忆层没有时间维度）。
但腐烂速度不是均匀的：

| 内容 | 烂的速度 | 为什么 |
|---|---|---|
| 原则、判据 | 慢 | 抽象，不指向具体东西 |
| 流程步骤 | 中 | 依赖工具存在 |
| ⭐⭐⭐⭐⭐ 示例 | ⭐⭐⭐⭐⭐ **最快** | ⭐⭐⭐⭐⭐ 它由具体标识符构成 |

> ⭐⭐⭐⭐⭐ **原则说"校验输入"，永远不会错；
> 示例说"调用 `validate_user()`"，函数改名那天它就错了。**

而它错的方式最糟——结合 `example-overrides-instruction.md`：

```
正文：调用校验函数（已更新为新名）
示例：validate_user(...)  ← 旧名，没改

→ ⭐⭐⭐⭐⭐ 模型跟示例，调用旧名
→ 报错，或更糟：旧名仍然存在但已废弃，静默走老路径
```

> ⭐⭐⭐⭐⭐ **一次改名，在正文里是一次正确的更新，在示例里是一次反向教学。**

而且它没有时间戳：⭐⭐⭐⭐⭐ **示例不携带"我是什么时候的真实输出"，
于是它没有过期这个概念——它看起来永远是新鲜的。**

## 5. 腐烂不可见，但可 grep

腐烂的示例在评审时不可见（读起来通顺、格式规范、像真的），但它是**唯一可以用机械手段检测的腐烂**：

```bash
# 抽出示例里所有看起来像标识符的东西
grep -oE '\b[a-z_]+\(\)|\b[A-Z_]{3,}\b|`[a-zA-Z_/]+\.(md|py|json)`' SKILL.md \
  | sort -u
```

> ⭐⭐⭐⭐⭐ **示例里的每一个具体标识符，都应该能在代码库里被找到。**
> 找不到的，要么已经腐烂，要么是编的——而这两者后果相同。

三条维护规则：

```
□ ⭐⭐⭐⭐⭐ 改正文里的函数名/字段名/路径时，grep 一遍示例（它们不在同一次改动里）
□ ⭐⭐⭐⭐⭐ 示例里的外部引用要带"截至"——
      "字段 list（截至 v2.3）"比"字段 list"多 4 个字，省一次排查
□ ⭐⭐⭐⭐ 示例腐烂优先修，而不是优先加新示例（旧的还在反向教）
```

第二条值得单独强调，因为它和"参考文档给链接+摘要而不是全文复制"是同一手法：
⭐⭐⭐⭐⭐ **把"可能已经变了"这件事显式写在内容里，而不是依赖读者记得去怀疑。**

## 6. 自检

```
□ ⭐⭐⭐⭐⭐ 示例占正文的比例超过 1/3 吗？超过 → 正文规则正在被稀释
□ ⭐⭐⭐⭐⭐ 正文里那个示例，是"最典型的"还是"最容易做错的"？
□ ⭐⭐⭐⭐ 它带 Rationale 吗？没有 → 它占的位置白付了
□ ⭐⭐⭐⭐⭐ 遮住全部示例跑一次，输出有变化吗？没有 → 它们是装饰
□ ⭐⭐⭐⭐⭐ 下沉的示例，正文里有"什么时候读它"这一行吗？
□ ⭐⭐⭐⭐⭐ 示例里的标识符，grep 得出来吗？
□ ⭐⭐⭐⭐ 上次改函数名时，有没有同步 grep 示例？
```

一分钟验证法：

> ⭐⭐⭐⭐⭐ **把示例里的每个具体名字圈出来，问："它上个月叫什么？下个月会叫什么？"**
> 只要有任何一个你不确定，那份示例就已经在腐烂了——只是还没发作。
