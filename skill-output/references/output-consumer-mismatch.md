# 同一份输出要喂三类读者

> 前置：`skill-output/references/output-contract.md`（输出契约基础）
> 分工：那份定**字段与类型**；本份讲一个常被忽略的事实——
> ⭐⭐⭐⭐⭐ 同一份内容同时给人读、给机器解析、给审计留痕，而这三套要求互相冲突。

---

## 1. ⭐⭐⭐⭐⭐ 三个读者，需求是冲突的

| | 人（看回复） | 机器（下游/脚本） | ⭐ 审计（留痕） |
|---|---|---|---|
| 叙述 | ✅ 要 | ❌ 不要 | ✅ 要 |
| 结构（可解析） | ❌ 无所谓 | ✅ 必须 | ✅ 必须 |
| 完整度 | ⭐⭐⭐⭐ 精简（读不完） | ✅ 全量 | ✅ 全量 |
| 不确定性 | ✅ 要表达（"可能"） | ❌ 要枚举值 | ✅ 要 |
| 冗余说明 | ✅ 帮助理解 | ⭐⭐⭐⭐⭐ 干扰解析 | ✅ 要 |

> ⭐⭐⭐⭐⭐ 冲突集中在两行：**"完整度"和"冗余说明"**。
> 人要短、机器要全；人要解释、机器要干净。

---

## 2. ⭐⭐⭐⭐⭐ 技能通常按"给人看"写，而它在链上主要被机器读

```
作者写输出模板时，眼前是"用户会看到什么"
而实际运行时，70% 的消费是下游技能或脚本
```

后果不是"格式不够机器友好"这么轻微，是：

> ⭐⭐⭐⭐⭐ **合成一份 = 三边都妥协，且每一边的失败都是静默的。**

| 妥协方向 | 静默失败 |
|---|---|
| 为了人读而精简 | ⭐⭐⭐⭐⭐ 机器拿到的数据不完整，且不报错 |
| 为了人读而加解释 | 解析器把解释当成值 / 或跳过而丢掉口径 |
| 为了机器而堆字段 | 人读到第 12 行就停了（关键句在第 47 行） |
| 为了机器而用枚举 | ⭐⭐⭐⭐⭐ 人读不到"为什么" |

---

## 3. ⭐⭐⭐⭐⭐ 解法是分离，不是折中

```
产物文件（机器读）：紧凑、全量、带 schema、带 status
回复（人读）      ：简短、以结论开头、指向产物路径
日志（审计）      ：不可变、带时间戳、带输入摘要
```

判据一句话：

> ⭐⭐⭐⭐⭐ **把回复删掉，产物还完整吗？**
> 完整 → 分离正确；不完整 → 你把信息只写在了人读的那份里。

---

## 4. ⭐⭐⭐⭐⭐ 分离之后的新问题：三份会漂移

分离解决了冲突，代价是引入三个事实来源。

> ⭐⭐⭐⭐⭐ **而"复制导致副本漂移"是已知的失败模式——
> 分离如果不指定单一来源，就是把一个冲突换成三个漂移。**

唯一的正确形状：

```
⭐⭐⭐⭐⭐ 机器产物是 canonical
人读的回复 —— 从产物生成
审计日志   —— 从产物生成

❌ 模型先写产物，再"顺便"给人写一段
```

> ⭐⭐⭐⭐⭐ **"顺便写一段"是最常见的做法，也是两个事实来源的起点。**
> 它看起来省事，而它意味着：同一个数字有两处，且没有任何机制保证它们一致。

判据：

```
把产物里的某个值改掉，回复里的数字会跟着变吗？
不会 → ⭐⭐⭐⭐⭐ 回复是独立生成的，它是第二个事实来源
```

---

## 5. ⭐⭐⭐⭐⭐ 两个最常见的内容错位

### ① 产物里写人话

```json
{"quality": "看起来没问题", "notes": "数据比较干净"}
```

> ⭐⭐⭐⭐⭐ 下游无法解析"看起来没问题"，而它不会报错——
> 它会把这句话当成一个字符串值继续传下去。

### ② 回复里堆机器数据

回复里贴一张 40 行的表，用户读到第 8 行就停了，
而真正的结论（"3 个来源中 2 个失败"）在第 31 行。

> ⭐⭐⭐⭐⭐ 这直接违反 `skill-output/references/output-ordering-priority.md`：
> 覆盖率与例外必须在前 5 行。

两处的修法是同一个：**把该给机器的还给产物，把该给人的留在回复。**

---

## 6. ⭐⭐⭐⭐⭐ 审计读者的三条特殊要求

审计常被省，因为"没人会看"。而它的价值恰恰在没人会看的时候——出事之后。

```
① 不可变：失败后不得清理（成功才清理，失败保留并报告路径）
② 带时间戳与输入摘要：事后能回答"当时是基于什么得出的"
③ ⭐⭐⭐⭐⭐ 带 attempts 与 duration：能回答"它跑了几次"
```

第三条最常被省，而它正是唯一能发现"重试放大"的痕迹——
参见 `skill-chain-failure/references/retry-amplification.md`：
**重试成功会抹掉失败记录**，日志是唯一能还原它的地方。

> ⭐⭐⭐⭐⭐ **失败时清理临时目录 = 删掉了唯一能回答"它到底跑了什么"的东西。**
> （与 `skill-execution/references/intermediate-artifacts.md` 的结论一致）

---

## 7. ⭐⭐⭐⭐⭐ 自检清单

```
□ 三类读者都点名了吗？（人 / 机器 / 审计）—— 只想到人是最常见的漏
□ ⭐⭐⭐⭐⭐ 把回复删掉，产物还完整吗？
□ ⭐⭐⭐⭐⭐ 改产物里的值，回复会跟着变吗？—— 不会 = 第二个事实来源
□ 产物里有没有人话（"看起来没问题"）？
□ 回复里有没有长表（结论被挤到后面）？
□ ⭐⭐⭐⭐⭐ 失败时产物保留了吗？—— 清理了就等于没发生过
□ 日志里有 attempts 吗？—— 没有就无法发现重试放大
```

---

## 8. Critical Rules

```
MUST NOT 把三种读者合成一份输出 —— 三边妥协，且全部静默
MUST NOT 让人读的回复独立生成数据 —— 产物是 canonical，回复从产物生成
MUST NOT 在产物里写人话 —— 下游当字符串传下去，不报错
MUST NOT 在回复里堆长表 —— 覆盖率与例外必须在前 5 行
MUST NOT 失败后清理产物 —— 那是唯一能还原现场的证据
MUST 日志带 attempts / duration / 输入摘要 —— 否则重试放大不可发现
```
