## 1. ⭐⭐⭐⭐⭐ "详尽"不是长度规格

```
"产出一份详尽的报告"
"尽可能完整地说明"
"详细列出所有发现"
```

> ⭐⭐⭐⭐⭐ 这些词既没有上限也没有下限——
> ⭐⭐⭐⭐⭐ **而模型会把它们解读为"越长越好"。**

机制很直接：

> ⭐⭐⭐⭐⭐ 在缺少长度规格时，模型会用"多写"来降低"漏掉"的风险。
> 这是理性的——⭐⭐⭐⭐ 因为"漏掉"是可被指责的，
> ⭐⭐⭐⭐⭐ 而"啰嗦"几乎从不被指责。

后果是一个稳定的单向漂移：

```
第一版：800 字，合适
几轮迭代后：3000 字，没人要求过
```

> ⭐⭐⭐⭐⭐ 没有人做过"加长"这个决定，它自己发生了。
> 这就是⭐⭐⭐⭐⭐ **长度膨胀不需要任何人同意**。

## 2. ⭐⭐⭐⭐⭐ 长度是可判定的，内容不是

一个很划算的观察：

```
"内容要准确"  → ⭐ 不可判定（要跑 eval）
"每段不超过 5 行" → ⭐⭐⭐⭐⭐ 可判定（数一下）
```

> ⭐⭐⭐⭐⭐ **在所有输出要求里，长度是唯一不需要 eval 就能验证的一条。**
> 而它恰恰是最常被省略的一条。

所以作为第一道约束，它的性价比最高：

```
成本：约 20 token
覆盖：⭐⭐⭐⭐⭐ 每一次输出
验证：⭐⭐⭐⭐⭐ 行数统计，无需模型、无需人工判断
```

写法（可直接抄）：

```markdown
## 输出规格
- 全文 ≤ 40 行
- 每段 ≤ 5 行
- ⭐⭐⭐⭐⭐ 单项说明 ≤ 2 句（超过则拆条，不展开段落）
- 表格 ≤ 8 行（超出只保留前 8 行，并注明"共 N 项"）
```

> ⭐⭐⭐⭐⭐ 最后一句是关键：**超限时的动作必须写明。**
> 只写"≤ 8 行"不写超了怎么办，
> ⭐⭐⭐⭐ 模型会为了不超限而丢信息——
> ⭐⭐⭐⭐⭐ 而"丢掉但注明总数"和"悄悄丢掉"是两回事。

## 3. ⭐⭐⭐⭐⭐ 每段给上限，不给下限

一个反直觉但重要的取舍：

```
✅ 给上限：防止膨胀（膨胀是大概率事件）
❌ 别给下限：⭐⭐⭐⭐⭐ 下限会诱发填充
```

> ⭐⭐⭐⭐⭐ "每个部分至少 3 句"→ 当某个部分真的没什么可说时，
> 模型会⭐⭐⭐⭐⭐ **编出第 3 句**。
> 而那句话通常是最不可靠的一句——因为它是为了满足格式而生成的。

⭐⭐⭐⭐⭐ 这与"给'我不知道'留一个合法选项"是同一条原则：
**所有要求"必须有内容"的规格，都在制造编造的压力。**

配套写法：

```markdown
- 各段按需长短，不要求均衡
- ⭐⭐⭐⭐⭐ 某项无内容时写"无"或省略该节，不要为了完整而填充
```

## 4. ⭐⭐⭐⭐⭐ 长度膨胀是最安静的退化

`skill-evaluating/references/skill-snapshot-testing.md` 里那条判据值得单列出来：

> ⭐⭐⭐⭐⭐ **长度上限 ≤ 基线 × 1.5** ——
> ⭐⭐⭐⭐⭐ **长度膨胀是最容易被忽略的退化：
> 输出越来越啰嗦，但没人会报 bug，因为内容还是对的。**

它为什么安静：

```
内容错   → 用户会报
格式错   → 一眼可见
⭐⭐⭐⭐⭐ 变长了 → ⭐⭐⭐⭐⭐ 没人抱怨，甚至被视为"更详细了"
```

> ⭐⭐⭐⭐⭐ 而它同时在吃掉三样东西（见下节），
> ⭐⭐⭐⭐ 且这三样都不会出现在任何报错里。

监控方式（零成本）：

> ⭐⭐⭐⭐⭐ 把输出行数记进 trace，画一条时间序列。
> ⭐⭐⭐⭐ 不需要设阈值——⭐⭐⭐⭐⭐ 缓慢上升的曲线本身就是信号。

## 5. ⭐⭐⭐⭐ 长输出的三个真实代价

**① ⭐⭐⭐⭐⭐ 它挤掉了后续指令的上下文**

```
3 万字输出进上下文 → 模型中途丢掉关键任务指令
→ 对用户说"你在等什么，请告诉我你的具体需求"
```

> ⭐⭐⭐⭐⭐ 这是真实事故（three-crash-scenes）：
> 根因不在模型，⭐⭐⭐⭐⭐ 而在"工具执行"和"上下文管理"被混为一谈。
> 修复后 ⭐⭐⭐⭐ **3 万字 → 不到 2000 字符，且回复质量反而更高**。

**② ⭐⭐⭐⭐⭐ 噪音本身损害质量**

这与"压缩后质量反升 2.8%"是同一现象：

> ⭐⭐⭐⭐⭐ **多余的内容不只是浪费，它是负资产**——
> 因为它稀释了关键信息的密度。

**③ ⭐⭐⭐⭐ 下游解析成本**

```
输出每多一段无关说明，下游的解析脚本就要多处理一种情况
```

> ⭐⭐⭐⭐ 已有真实教训：格式不锁死，下游解析脚本**被折磨得改了三版**。

## 6. ⭐⭐⭐⭐⭐ 与"结构正确的废话"的关系

长度失控是那类失败的主要成因之一：

```
没有长度上限
→ 模型用"多写"降低"漏掉"的风险
→ 每一句都可能是正确的
→ ⭐⭐⭐⭐⭐ 但真正关键的那句被淹没在 3000 字里
```

> ⭐⭐⭐⭐⭐ 关键的那句没有消失——它还在，
> ⭐⭐⭐⭐⭐ **但它在第 47 行，而用户读到第 12 行就停止了。**

所以长度预算的本质不是省 token：

> ⭐⭐⭐⭐⭐ **长度预算是"关键信息可见性"的保障机制。**
> 节省成本只是它的副作用。

判据收口（一句话，可贴在墙上）：

> ⭐⭐⭐⭐⭐ **一份没人读完的输出，等于一份没有关键信息的输出。**
