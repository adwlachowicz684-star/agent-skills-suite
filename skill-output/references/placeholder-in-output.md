## 1. ⭐⭐⭐⭐⭐ 一份带着 TBD 的成品

```markdown
## 结论
- 主要风险：<待分析>
- 建议：TBD
```

> ⭐⭐⭐⭐⭐ 结构完整、格式规范、标题齐全。
> ⭐⭐⭐⭐⭐ 而它没有内容——⭐⭐⭐⭐⭐ **但它是作为"已完成"交付的。**

> ⭐⭐⭐⭐⭐ 占位符的危险不在于"没写完"，
> ⭐⭐⭐⭐⭐ 而在于**它让没写完的状态看起来像写完的格式**。

## 2. ⭐⭐⭐⭐⭐ 占位符的三种来源

**① ⭐⭐⭐⭐⭐ 模板里的空位被原样输出**

```
模板：  - 负责人：___
输出：  - 负责人：___        ← 空位被当成内容填回去了
```

> ⭐⭐⭐⭐⭐ 这是本份认为最主要、也最应该被修掉的一种——
> ⭐⭐⭐⭐⭐ 因为它是**技能自己造成的**（见第 6 节）。

**② ⭐⭐⭐⭐⭐ 示例值被复制到输出**

```
示例：  "客户：示例客户A"
输出：  "客户：示例客户A"
```

> ⭐⭐⭐⭐⭐ 这与《skill-examples》的 `examples-three-branches.md` 同源：
> ⭐⭐⭐⭐⭐ 少样本示例是最强的上下文信号，模型对示例的信任度高于对指令的信任度。
> 那份讲的是"值被当成默认值"，这份讲的是**那些值现在出现在成品里**。

**③ ⭐⭐⭐⭐⭐ 模型自造的"待办"标记**

```
[此处需要补充] · （略） · ... · N/A · 同上
```

> ⭐⭐⭐⭐⭐ 这类最杂，也最难管——⭐⭐⭐⭐ 因为它看起来像是有意的省略。
> ⭐⭐⭐⭐⭐ 而"（略）"在多数语境下是合法的（列表太长时确实会略）。

## 3. ⭐⭐⭐⭐⭐ 为什么它不会被拦下

三条，缺一不可，而它们通常同时成立：

**① ⭐⭐⭐⭐⭐ 结构检查全绿**

```
JSON 可解析 ✅ · schema 通过 ✅ · 字段齐全 ✅
⭐⭐⭐⭐⭐ 占位符是一个合法的字符串值
```

**② ⭐⭐⭐⭐⭐ 人类的阅读习惯是扫结构**

```
看到"## 结论" → 认为有结论
⭐⭐⭐⭐⭐ 读到"<待分析>"时，注意力已经在下一节了
```

> ⭐⭐⭐⭐⭐ 这与"长度预算"那条相反相成：
> 关键句在第 47 行没人读；⭐⭐⭐⭐⭐ **占位符在显眼位置也没人读**——
> 因为扫描时眼睛找的是标题，不是空值。

**③ ⭐⭐⭐⭐⭐ 没有一步在等它**

> ⭐⭐⭐⭐⭐ 与"缺失的部分不会报错，因为没有任何环节在等它"完全同构：
> ⭐⭐⭐⭐⭐ **没有任何下游在读取"负责人"这个字段，
> 于是它是空的对谁都没有影响——直到有人真的需要找负责人。**

## 4. ⭐⭐⭐⭐⭐ 三种占位符，危险度不同

| 形态 | 例子 | ⭐⭐⭐⭐⭐ 危险度 | 说明 |
|---|---|---|---|
| ⭐⭐⭐⭐⭐ **沉默型** | `___`、`""`、`[]`、`0` | 最高 | 看起来是"空"，也可能被读成"无" |
| ⭐⭐⭐⭐⭐ **伪装型** | `N/A`、`无`、`同上`、`略` | 最高 | ⭐⭐⭐⭐⭐ 看起来是一个**合法答案** |
| ⭐⭐⭐⭐ **直白型** | `<待补充>`、`TBD`、`TODO` | 高 | 至少能被 grep 到 |

> ⭐⭐⭐⭐⭐ 最危险的不是 `TBD`，而是 **`N/A` 和 `无`**——
> ⭐⭐⭐⭐⭐ 它们是一个完整的、语法正确的、语义错误的回答。

而《skill-output》的 `numbers-in-output.md` 已经命中过其中一半：

> ⭐⭐⭐⭐⭐ "新增问题 0" 可能是真的没有，也可能是没查到
> → ⭐⭐⭐⭐⭐ **`0` 和 `无` 是最危险的占位符，因为它们看起来像结果。**

所以判据是：

> ⭐⭐⭐⭐⭐ **这个"空"，是"确认过没有"，还是"没有确认"？**
> 两者在输出里长得一模一样，必须由技能区分。

## 5. ⭐⭐⭐⭐⭐ 修法：禁止 + 出口

单独写禁令会反噬（模型不知道该填什么），必须成对：

```markdown
- ⭐⭐⭐⭐⭐ 输出中不得出现占位符（___、TBD、<待补充>、示例值）
- ⭐⭐⭐⭐⭐ 某项确实无法获取时，写"未获取：<原因>"，不得写 N/A、无、0
```

> ⭐⭐⭐⭐⭐ 第二句是出口，也是判据：
> ⭐⭐⭐⭐⭐ **"未获取"这三个字把"空"从一个值变成一个状态**，
> 于是它可以在下游被识别、被统计、被追问。

三条配套：

```
① ⭐⭐⭐⭐⭐ 必填字段缺失时，整体状态标为 partial（不要标 ok）
② ⭐⭐⭐⭐⭐ 占位符不得出现在输出首屏（首屏是最容易被当成结论的地方）
③ ⭐⭐⭐⭐ 模板里的空位用显眼标记，且要求"未获取"填充
```

> ⭐⭐⭐⭐⭐ 第 ① 条与《skill-interfaces》的 `status: partial` 咬合：
> ⭐⭐⭐⭐⭐ **带着占位符的产物，其正确状态是 partial，不是 ok**——
> 而多数技能默认输出 ok，因为它"跑完了"。

再加一条成本极低的：**输出末尾一行自检**。

```markdown
输出末尾附一行：`占位符自检：无`（若有，改为列出位置）
```

> ⭐⭐⭐⭐⭐ 它把 grep 动作交给了模型自己，
> ⭐⭐⭐⭐⭐ 而"要写这一行"本身就会让它回去再看一遍。

## 6. ⭐⭐⭐⭐⭐ 模板里的空位是最常见来源

这是本份最值得单独记住的一条，因为它**完全是技能作者造成的**：

```markdown
## 输出模板
- 负责人：___
- 截止：___
```

> ⭐⭐⭐⭐⭐ 下划线在模板里表示"这里要填"，
> ⭐⭐⭐⭐⭐ 而模型看到的是一个**已经存在的字符串**——
> 它的默认动作不是"填"，是"照着模板输出"。

三个改进，按强度：

**① ⭐⭐⭐⭐⭐ 空位用不可能被误当值的标记**

```
- 负责人：{{FILL:负责人}}
```

**② ⭐⭐⭐⭐⭐ 模板里直接写"未获取"作为默认**

```
- 负责人：未获取（若上下文中确有，则填实际值）
```

> ⭐⭐⭐⭐⭐ 这是最有效的一条：⭐⭐⭐⭐⭐ **把默认值设成"可见的空"，
> 而不是"看起来填了的空"**。与 `inference-vs-asking.md` 的 L2 完全同构。

**③ ⭐⭐⭐⭐⭐ 给模板配一个字段说明表**（`description` 缺失等于省略一半提示）

```
| 负责人 | ⭐⭐⭐⭐⭐ 本次任务的直接负责人；上下文中没有则写"未获取" |
```

> ⭐⭐⭐⭐⭐ 三条合起来成本约 30 token，
> ⭐⭐⭐⭐⭐ 覆盖的是"输出里出现无法分辨的空值"这个高频问题。

## 7. ⭐⭐⭐⭐⭐ 自检与 grep

对输出：

```bash
grep -nE "___|TBD|TODO|待补充|待填|<.*>|N/A|同上|（略）|\(略\)|示例" output.md
```

对技能模板：

```bash
grep -nE "___|：:? *$" SKILL.md
```

> ⭐⭐⭐⭐⭐ 后者更重要：⭐⭐⭐⭐ **修掉模板里的裸空位，
> 比在输出里 grep 更早一步**——前者是根因，后者是症状。

三条判据：

```
① ⭐⭐⭐⭐⭐ 模板里的空位有默认值吗？（应该写"未获取"）
② ⭐⭐⭐⭐⭐ 每个字段都有说明吗？（包括"没有时写什么"）
③ ⭐⭐⭐⭐⭐ 输出里出现"无/0/N/A"时，能区分是"确认没有"还是"没查"吗？
```

一个十秒判断：

> ⭐⭐⭐⭐⭐ **随便挑一份输出，把所有"无"和"0"替换成"未获取"再读一遍。
> 如果读起来突然觉得"这份报告其实什么都没查到"——
> 那说明原版一直在用答案的形状掩盖空白。**
