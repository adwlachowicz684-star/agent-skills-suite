# 输出契约：Schema-First

> ⭐ **在生产系统里，每一个技能的输出都会成为下游的输入。**
> **输出格式的不确定性，是系统集成中最昂贵的隐性成本。**

## Schema 先行，不是事后适配

> **在写技能指令之前，先把输出 schema 写出来。**
> **Schema 是技能设计的起点，不是收尾。**

```json
{
  "type": "object",
  "required": ["summary", "action", "confidence"],
  "properties": {
    "summary":    {"type": "string", "maxLength": 200},
    "action":     {"type": "string", "enum": ["approve", "reject", "review"]},
    "confidence": {"type": "number", "minimum": 0, "maximum": 1}
  }
}
```

**为什么先行**：一旦抽取的东西比扁平列表更复杂，
**写 schema 就成了主要设计任务，而提示词几乎成了附带的**。

> ⚠️ **多个技能串联时尤其致命**：
> 转录 → 意图识别 → 回复生成 → 语音合成。
> **每一环的输出格式都是下游的输入格式。任意一环不确定，整条管道就崩。**

## Schema 要写到什么程度

> 一个 schema 一次性指定三件事：**对象结构 · 每个字段的类型 · 嵌套关系**。

```json
{
  "customer": {"name": "string", "email": "string", "phone": "string"},
  "order": {
    "order_id": "integer",
    "total_amount": "number with 2 decimals",
    "items": [{"name": "string", "quantity": "integer", "price": "number"}]
  }
}
```

> 注意 `items` 被明确为**对象数组**（而非单个对象），
> `total_amount` 被钉住**精度**。

**约束可以直接写进 schema**：

```
"email 必须是合法邮箱格式"
"phone 必须是 10 位数字"
"price 必须大于 0"
```

> ⭐ 这有两个好处：**直接改善输出**，以及
> **迫使你在数据到达之前就决定规则是什么**，
> 而不是等下游拒绝某一行时才发现问题。

**字段级约束**（更强）：

| 手段 | 作用 |
|---|---|
| `required` | 必填 |
| `enum` | 取值封闭 |
| `maxLength` / `minimum` / `maximum` | 边界 |
| `pattern`（如 `^U[0-9]{8}$`） | **可自动校验** |
| `format`（如 `date-time`） | 同上 |
| `additionalProperties: false` | **禁止返回契约外字段** |
| `minProperties` | **防空响应** |

> `pattern` 和 `format` 是关键——
> 它们让契约具备**可自动化校验**能力，而不只是参考。

## 四道防线

> 四种技术**会叠加**，所以在无人值守的管道上要**一起用**。

**① 给出合法输出的明确示例**

> 展示正确结果长什么样；数据有变体就给多个示例。
> 让模型有**可匹配的模式**，而不是只有一段要解读的描述。

**② 加校验指令**

```
"发送前先检查 JSON 是否合法"
"确认所有必需字段都存在且格式正确"
```

> 这促使模型**在产出答案之前**先检查，而不是你消费完才发现。

**③ 加错误恢复指令**

> ⭐ **这是生产提示词里最有价值的一行**：

```
"如果你无法生成合法输出，请说明原因，
 而不是生成不合法的输出。"
```

> **它把静默的垃圾转换成可读的消息**，
> 防止畸形数据破坏下游系统。

**④ 部署前实测**

> 结构化输出上线时，**逐字段校验前几个输出**，
> 而不是假设"第一次看起来对，管道就没问题"。

**顺序很重要**：

```
示例 + 精确 schema  → 拦住大多数错误
校验指令            → 拦住一部分剩余
错误恢复            → 兜住漏网的
实测                → 告诉你到底在哪一类
```

## 错误也要结构化

> ⭐ **错误情况的输出，同样要有 schema。不要让错误信息成为自由文本。**

```json
{
  "error": "string, 错误信息",
  "code": "string, 错误码",
  "recoverable": "boolean, 是否可恢复"
}
```

**解析失败的处理**：

```
1. 记录原始输出与解析错误
2. 用澄清提示重试（最多 2 次）
3. 2 次仍失败 → 返回结构化错误，而不是崩溃
```

**还要做语义校验**（超出 schema 之外）：

```
□ 置信度与动作一致吗？
□ 引用的 ID 在数据库里存在吗？
□ 日期在合法范围内吗？
```

> **"几乎合法"比明显错误更糟——它能骗过肉眼，却过不了解析器。**
> 尾随逗号、缺字段、数字成了字符串，都属于这一类。

## 输出之后的净化

> **永远不要像信任自己的代码那样信任 AI 输出——它是用户生成内容。**

| 目的地 | 净化动作 |
|---|---|
| 渲染成 HTML | 防 XSS |
| 作为代码执行 | 沙箱 + 执行前评审 |
| 存入数据库 | 防注入 |

---

## 监控

```
□ 记录 schema 校验的通过/失败率
□ 定期抽样审查输出的语义正确性
□ 校验失败率 >5% 时告警
```

**四条红旗**（看到就说明设计有洞）：

```
□ AI 输出未过 schema 校验就直接使用
□ JSON.parse() 没有 try/catch
□ AI 生成的 SQL / 代码未经评审就执行
□ 校验失败没有日志
```

## 常见借口

| 说 | 回应 |
|---|---|
| "模型 99% 的时间都输出合法 JSON" | 那 1% 会造成生产事故。**永远校验。** |
| "我们只是展示给用户，不解析" | 用户会**照着它行动**。错的输出导致错的行动。 |
| "结构化输出增加延迟" | 校验是**微秒级**；调试未校验的输出是**小时级**。 |
| "模型已经足够确定性了" | 没有任何 LLM 确定到可以跳过校验。 |

## 自查

```
□ 是否在写指令之前就定好了输出 schema？
□ 是否给出了合法输出的明确示例？
□ 是否有"发送前检查 JSON 合法性"的指令？
□ 是否有"无法生成合法输出时说明原因"的兜底？
□ 错误输出是否也有 schema？
□ 是否有解析失败重试（≤2 次）与结构化错误返回？
□ 是否做了超出 schema 的语义校验？
□ 是否按目的地做了净化（XSS / 注入 / 沙箱）？
□ 是否记录并告警校验失败率（>5%）？
□ 部署前是否逐字段实测过？
```
