## 1. ⭐⭐⭐⭐⭐ 模板是在"典型规模"下设计的，而典型是作者心里的一个数

写模板时的真实过程：

```
脑子里想着上次那次任务（大概 8 条结果）
→ 写了一个"每条 3 行 + 表头 + 小结"的模板
→ 觉得挺好
```

> ⭐⭐⭐⭐⭐ **"8 条"从来没有出现在文档里。它是模板的隐含前提，
> 而隐含前提在规模变成 200 条时不会报错。**

这也是为什么这类问题几乎不可能在自测时被发现：

```
自测用的就是上次那个任务 → 8 条 → 模板完美
→ ⭐⭐⭐⭐ 上线后第一次遇到 200 条 → 模板仍然完美地被执行
```

---

## 2. ⭐⭐⭐⭐⭐ 规模变化时，模型的默认动作是"保持格式"

遇到不适配的规模，模型有两个选项：

```
A 保持模板（产出 200 × 5 行 = 1000 行）
B 改变格式（改成汇总 + 异常项）
```

> ⭐⭐⭐⭐⭐ **它几乎总是选 A，因为模板是写下来的，而"这样更好读"不是。**

机制与"省略不是留白"完全一致：

> ⭐⭐⭐⭐⭐ **没写的地方由模型补，而它补的依据是它手上唯一的明确信息——模板。**

最反直觉的后果：

> ⭐⭐⭐⭐⭐ **模板被严格遵守，恰恰是这份输出不可用的原因。**
> 且它比"没遵守模板"难发现得多——格式检查全过，而格式检查是多数技能唯一的检查。

## 3. 三种规模失配

| 失配 | 规模 | 表现 |
|---|---|---|
| ⭐⭐⭐⭐⭐ 过多 | 200 条 | 1000 行输出；关键那条在第 47 条，用户读到第 12 条就停了 |
| ⭐⭐⭐⭐⭐ 过少 | 0–1 条 | 模板被"无 / 0 / —"填满，输出看起来完整 |
| ⭐⭐⭐⭐ 极端分布 | 一条占 90% | 每条等长 → 主要的被压缩、次要的被展开 |

第二种与 `placeholder-in-output.md` 的关系要说清：

> ⭐⭐⭐⭐ **那份讲的是"占位符本身危险"，这份讲的是"为什么会出现那么多占位符"——
> 因为模板要求了 8 个字段，而实际只有 1 条数据。**

第三种常出现在聚合类技能：⭐⭐⭐⭐ **"每条一段"在长尾分布下必然失衡**，
而失衡的方向恰好是反的——占 90% 的那条最需要空间，得到的和其他条一样多。

## 4. ⭐⭐⭐⭐⭐ 0 条时最危险：模板被填成一份看起来完整的空

```
## 风险项
- 高风险：无
- 中风险：无
- 低风险：无

## 汇总
- 总计：0
- 占比：0%
```

这份输出：

```
✅ 字段齐全  ✅ 格式正确  ✅ 每个空都有内容  ✅ 看起来是一份完成的报告
⭐⭐⭐⭐⭐ ❌ 它真正想说的是"我没查到"，而它写的是"没有风险"
```

> ⭐⭐⭐⭐⭐ **"无"和"0"是完整的、语法正确的、语义错误的回答。**
> 而模板是它们最大的制造机——模板要求每个字段都要有值，
> 于是"没数据"被表达成了"数据是零"。

修法不是删模板，是**给 0 条单开一档**（见第 5 节），
并且⭐⭐⭐⭐⭐ **模板里的默认值要写成"可见的空"**：

```
❌ - 高风险：___
✅ - 高风险：（未获取到数据时写"未获取"，不要写"无"）
```

## 5. 修法一：规模分档

不要写"一个模板"，写三档。成本约 30 token，覆盖全部规模：

```markdown
## 输出

- **0 条**：只输出一行结论——"未获取到 X（原因：…）"，⛔ 不要输出空模板。
- **1–10 条**：逐条列出，每条 ≤ 3 行，末尾附一句汇总。
- **>10 条**：⭐ 先给分布与异常项（≤ 10 行），再附完整清单（可折叠/写入文件）。
```

三档的边界不需要精确（5 或 10 都行），
⭐⭐⭐⭐ **但必须存在——它的作用是让"规模"这个隐含前提变成显式分支。**

> ⭐⭐⭐⭐⭐ **只有一档模板 = 默认所有规模都长一样。
> 而"所有规模都长一样"这个假设，只在作者想过的那个规模上成立。**

与"条件分支写法"的关系：这是典型的"if 没有 else"——
模板定义了典型规模的 if，**没有为其他规模写 else，于是 else 由模型定义**。

## 6. ⭐⭐⭐⭐⭐ 修法二：超出时怎么办，必须写明

即使分了档，仍然会出现"具体多少条不可控"的情况。这时必须写明丢弃策略：

```markdown
若结果 > 50 条：
  - 输出前 20 条（按严重度降序）
  - 末尾必须写："共 213 条，此处列出前 20 条，完整结果见 .tmp/full.json"
```

> ⭐⭐⭐⭐⭐ **不写明，模型就会自己决定丢弃策略；而它决定丢弃时通常不告诉用户。**

三条硬要求：

| 要求 | 为什么 |
|---|---|
| ⭐⭐⭐⭐⭐ 必须报总数 | 没有分母就没有完成（"列出前 20 条"里的 20 和 213 完全不是一回事） |
| ⭐⭐⭐⭐ 必须说排序依据 | "前 20 条"是哪 20 条——不说就等于随机 |
| ⭐⭐⭐⭐ 完整结果要落盘 | 否则被丢掉的那部分就真的消失了 |

三条里第一条最关键，也最常被省：

> ⭐⭐⭐⭐⭐ **"列出前 20 条"不写总数，用户会以为一共就 20 条。**
> 这与"摘要没有 coverage 字段"是同一条：**截断不可怕，静默截断才可怕。**

---

## 7. ⭐⭐⭐⭐ 修法三：规模大时切汇总，不切穷举

规模越大，"逐条列出"的价值越低：

```
8 条   逐条列出 → 用户全看
80 条  逐条列出 → 用户看前 10 条（⭐ 后 70 条只贡献了长度和噪音）
800 条 逐条列出 → ⭐⭐⭐⭐⭐ 用户只想知道"分布 + 有哪些异常"
```

> ⭐⭐⭐⭐⭐ **规模大到一定程度，"全面"就不再是优点——
> 它变成了"把关键那条埋起来的机制"。**

切换的形态：

```
≤10 条  逐条
>10 条  ⭐ 分布（按类别计数）+ 异常项逐条 + 完整清单落盘
```

> ⭐⭐⭐⭐ **这与"长度预算是可见性保障"是同一个结论的两面：
> 那份说"关键那句不能消失在第 47 行"，
> 这份说"规模一大，就一定会有第 47 行"。**

## 8. 检查清单

- [ ] 输出模板**分了档**（0 / 少量 / 大量），不是只有一个模板
- [ ] 0 条时明确写"不要输出空模板"，只输出一行结论
- [ ] 模板里的空位默认写"未获取"，不是 `___` / 无 / 0
- [ ] ⭐⭐⭐⭐⭐ 有"超出 N 条时"的丢弃策略，且**必须报总数**
- [ ] 丢弃时写明了排序依据（不是"前 N 条"）
- [ ] 被截断的完整结果落盘，并在输出里给路径
- [ ] 大规模档位用的是"分布 + 异常项"，不是逐条
- [ ] ⭐⭐⭐⭐ 长尾分布下，主要条目没有被"每条等长"压缩

## 一句话

> ⭐⭐⭐⭐⭐ **模板是一份针对某个规模的隐式承诺，而那个规模从来没被写下来。
> 于是规模变了，模型仍然完美地执行模板——
> 它遵守了你能检查的那一半（格式），牺牲了你没写下来的那一半（可用）。**
