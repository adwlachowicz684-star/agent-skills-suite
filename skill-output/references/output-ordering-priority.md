## 1. ⭐⭐⭐⭐⭐ 顺序不是排版，是主张

```
"3 个文件有问题，其中 1 个是安全问题；另外本次分析覆盖了 82% 的文件"
```

vs 同一份内容换个顺序：

```
"本次分析覆盖了 82% 的文件；3 个文件有问题，其中 1 个是安全问题"
```

> ⭐⭐⭐⭐⭐ 信息完全相同。⭐⭐⭐⭐⭐ 而读到第一句就停的人，
> 在第一版里知道"有安全问题"，在第二版里只知道"覆盖 82%"。

> ⭐⭐⭐⭐⭐ **输出顺序是模型对你没明说的那部分优先级的实现。**

## 2. ⭐⭐⭐⭐⭐ 模型的默认顺序：生成顺序

没有规定顺序时，模型按什么排？三股力量：

**① ⭐⭐⭐⭐⭐ 生成顺序**（最强）

```
先想到的先写。而"先想到"取决于技能里步骤的排列、
输入文件的顺序、以及它自己推理的先后顺序
```

**② ⭐⭐⭐⭐ 模板顺序**

```
技能给了模板 → 按模板填。这是唯一可控的一股
```

**③ ⭐⭐⭐ 语义惯性**

```
"结论在后""先背景后结论"这类写作习惯
⭐⭐⭐⭐⭐ 于是正文里没规定的部分，会按"通用互联网文本"的常见顺序排
```

> ⭐⭐⭐⭐⭐ 第 ① 条意味着：⭐⭐⭐⭐⭐ **技能里步骤的排列，会在输出里复现**
> ——而步骤按"执行先后"排，⭐⭐⭐⭐⭐ 用户需要的顺序通常是"重要程度"，
> 这两个顺序几乎从不相同。

## 3. ⭐⭐⭐⭐⭐ 三条代价，第一条最贵

**① ⭐⭐⭐⭐⭐ 用户提前停止阅读**

```
关键那句没消失，它在第 47 行
⭐⭐⭐⭐⭐ 而用户读到第 12 行就停了（见 `skill-output/references/output-length-budget.md`）
```

> ⭐⭐⭐⭐⭐ 长度预算解决的是"它会不会被埋在很后面"，
> ⭐⭐⭐⭐⭐ 顺序解决的是"**在有限长度里，前面放的是什么**"——
> 两者必须一起做，**只做长度预算，前面仍然可能全是背景。**

**② ⭐⭐⭐⭐⭐ 未声明的降级被当成完整结果**

```
"部分成功"写在最后 → 前面读起来像全量
→ ⭐⭐⭐⭐⭐ 用户拿前面的数字去决策
```

> ⭐⭐⭐⭐⭐ 与 `skill-output/references/placeholder-in-output.md` 同源：⭐⭐⭐⭐ 那个是"无/0"被当成答案，
> ⭐⭐⭐⭐⭐ 这个是"覆盖率/未达标"被放在没人读的位置，效果一样。

**③ ⭐⭐⭐⭐ 排序不稳定导致输出看起来"每次都不一样"**

```
同一输入两次运行 → 顺序不同 → 用户以为结论变了
⭐⭐⭐⭐ 而实际上内容完全一致
```

## 4. ⭐⭐⭐⭐⭐ 四类信息的位置规则

| 信息类型 | ⭐⭐⭐⭐⭐ 位置 | 理由 |
|---|---|---|
| ⭐⭐⭐⭐⭐ 结论 / 是否达标 | **首行** | 用户可能只读一行 |
| ⭐⭐⭐⭐⭐ 影响决策的例外（安全问题、阻断项） | **结论之后、细节之前** | 它会改变用户对结论的用法 |
| ⭐⭐⭐⭐⭐ 覆盖率 / 部分成功 / 未获取 | **首屏内，且不得在末尾** | 埋在末尾 = 等于没写 |
| ⭐⭐⭐⭐ 背景、方法、过程 | **最后** | 读了结论的人才需要它 |

三条硬性规则：

```
① ⭐⭐⭐⭐⭐ 输出首行必须是"结论或状态"，不得是背景或过程
② ⭐⭐⭐⭐⭐ 任何会让用户改变用法的限定条件，必须在首屏（前 5 行内）
③ ⭐⭐⭐⭐⭐ "验证之后不要再放任何东西"（已有结论：近因区要给验证）
```

> ⭐⭐⭐⭐⭐ 第 ① 条最常被违反，因为⭐⭐⭐⭐ "先交代背景再给结论"
> 是通用文本里最常见、也最受好评的写法——⭐⭐⭐⭐⭐ **而技能输出不是文章，
> 它是要被"扫一眼就用"的东西。**

一个例外要写清楚：**如果用户明确要求"先说原因再说结论"（如复盘、汇报），
按用户要求排**。所以规则应该是"默认首行结论，除非用户另行要求"。

## 5. ⭐⭐⭐⭐⭐ 排序判据：用户会不会因为没读到后面而做错决定

一句可执行的判据：

> ⭐⭐⭐⭐⭐ **假设用户只读前 5 行。他会做出和读完全文不同的决定吗？**

```
会 → ⭐⭐⭐⭐⭐ 那部分信息必须在前 5 行
不会 → 可以放后面
```

三类必在前 5 行的信息（判据的具体化）：

```
① ⭐⭐⭐⭐⭐ 改变结论适用范围的（覆盖率、未达标、部分成功）
② ⭐⭐⭐⭐⭐ 需要用户立即行动的（阻断项、不可逆动作已完成）
③ ⭐⭐⭐⭐⭐ 用户没预料到的（原以为是 A，实际是 B）
```

> ⭐⭐⭐⭐⭐ 第 ③ 条最容易被漏：⭐⭐⭐⭐ 技能按"用户期望的顺序"组织输出，
> ⭐⭐⭐⭐⭐ 而真正要紧的恰恰是**与用户期望不符的那一条**——
> 它通常被排在"其他"里。

## 6. ⭐⭐⭐⭐⭐ 列表内部的顺序

列表内部同样有优先级，而默认也是生成顺序。三种排序必须显式指定：

```
① ⭐⭐⭐⭐⭐ 按严重度（阻断 → 警告 → 建议）
② ⭐⭐⭐⭐ 按确定性（已确认 → 待确认 → 猜测）
③ ⭐⭐⭐⭐ 按影响范围（全局 → 模块 → 单点）
```

> ⭐⭐⭐⭐⭐ 不指定的后果：⭐⭐⭐⭐⭐ **一个阻断项排在三条建议之后**——
> 它没有被省略，但它在列表第 4 位，而列表通常只有前 2–3 项被读。

两条配套：

```
① ⭐⭐⭐⭐⭐ 混合严重度的列表必须标注（"[阻断]""[建议]"），
   标注比排序更可靠——排序会被"先想到"冲淡，标注不会
② ⭐⭐⭐⭐ 长度超限时，截断规则要写明"保留高严重度"
   —— 否则模型会从头截，把最不重要的留下
```

> ⭐⭐⭐⭐⭐ 第 ② 条与长度预算咬合：⭐⭐⭐⭐⭐ **"超限时的动作必须写明"，
> 而这里要额外写明的是"截哪一部分"**——不写就默认截尾部，
> 而尾部常常是最后才生成的、也可能是最重要的补充。

## 7. ⭐⭐⭐⭐⭐ 写法与自检

最小写法（约 40 token，加在输出契约里）：

```markdown
## 输出顺序
1. 首行：结论（通过 / 未通过 / partial）
2. 第 2–5 行：覆盖率、例外、需立即行动项
3. 之后：明细（按严重度降序）
4. 最后：方法与过程
```

> ⭐⭐⭐⭐⭐ 它比"输出要清晰"这种要求有效得多，
> ⭐⭐⭐⭐⭐ 因为它是**可判定的**：⭕ 看第一行就知道有没有遵守。

自检四条：

```
① ⭐⭐⭐⭐⭐ 首行是结论吗？（是背景 → 违反）
② ⭐⭐⭐⭐⭐ 覆盖率/未达标在前 5 行吗？
③ ⭐⭐⭐⭐⭐ 列表按严重度排了吗？混合严重度有标注吗？
④ ⭐⭐⭐⭐⭐ 超限时截的是哪一部分？（没写 → 默认截尾）
```

一个十秒判断：

> ⭐⭐⭐⭐⭐ **只看输出的前 5 行，遮住其余部分。
> 如果据此做出的决定会和看完全文不同 → 排序是错的，
> 而内容可能完全正确。**

## 一句可贴在墙上

> ⭐⭐⭐ **内容一样、顺序不同，用户读到的是两个不同的结论。
> 而默认顺序是生成顺序，不是重要程度。**
