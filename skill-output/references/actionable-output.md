> `decision-rationale-output.md` 要求输出写⭐ **依据**——回答"为什么信它"；

> 两者都要，且⭐⭐⭐⭐⭐ **缺动作比缺依据更常见**：
> 依据写不出来时输出会显得可疑，而动作写不出来时输出仍然完整、专业、像一份成果。

## 1. ⭐⭐⭐⭐⭐ 四类不可行动的输出

### a) 观察型：陈述了一个事实，没有指向任何动作

```
"订单量在 3 月出现明显下滑。"
```

真的、有数据、可能是报告里最重要的一句话——⭐⭐⭐⭐⭐ **而它没有说该做什么。**
读者会自己补一个动作，而每个人补的不一样。

### b) 方向型：指出了方向，没给判据

```
"建议优化首屏加载性能。"
```

> ⭐⭐⭐⭐⭐ 它把一个需要判断的问题，包装成了一个已经完成的结论。

### c) 条件型：把判断推回给用户

```
"是否需要进一步分析，取决于业务优先级。"
```

⭐⭐⭐⭐ **表面上是尊重用户，实际是输出没有完成自己的部分**——
用户不知道"进一步分析"会产生什么，所以无法决定。

### d) 复述型：把输入换了一种说法

```
"本报告对 3 月订单数据进行了多维度分析，涵盖渠道、品类、地区……"
```

⭐⭐⭐⭐ 常见于被要求"写摘要"时。它描述的是报告做了什么，不是读者该做什么。

## 2. ⭐⭐⭐⭐⭐ "建议"是一个免责词

```
"建议关注库存周转率。"
```

> ⭐⭐⭐⭐⭐ **"建议"让这句话在形式上是完整的，在责任上是空的**——
> 它描述了一个方向，但不承诺这个方向有任何价值。

同一个句子，去掉"建议"后就会露出来：

```
"关注库存周转率。"
→ 关注到什么程度算关注了？
→ 关注之后呢？
```

> ⭐⭐⭐⭐⭐ **"建议/关注/考虑/视情况"是一组让句子成立的助词，
> 它们的作用是把一个不完整的判断补成一个完整的句子。**

判据很直接：**删掉这些词，句子还成立吗？**
不成立 → 它本来就不成立，是助词在替它承担语法责任。

## 3. ⭐⭐⭐⭐⭐ 可行动的三要素

| 要素 | 缺了会怎样 |
|---|---|
| 动作 | ⭐⭐⭐⭐⭐ 不知道做什么 |
| 对象 | ⭐⭐⭐⭐ 做对了动作，做错了地方 |
| ⭐⭐⭐⭐⭐ 条件/阈值 | 不知道什么时候做、做到什么程度 |

```
❌ "建议优化首屏加载性能"
✅ "首屏加载 P75 为 4.2s，超过 3s 阈值 → 优先移除首屏未使用的 3 个 JS bundle（预计降到 2.8s）"
```

第三条最常被省，而它决定了前两条有没有用：

> ⭐⭐⭐⭐⭐ **没有阈值的动作，等于"永远可以做"——
> 于是它既紧急又不紧急，实际结果是永远不做。**

配套一条：**动作要有执行者**。
"需要确认数据口径"——谁确认？⭐⭐⭐⭐ 模型自己能确认的，不该出现在输出里（它应该已经确认了）；
它需要用户确认的，必须写明"等待确认"，否则这条会被读成"已经确认过了"。

## 4. ⭐⭐⭐⭐ 为什么它不会被报成 bug

| 缺陷 | 会被报吗 |
|---|---|
| 数字错了 | ✅ 会被抓 |
| 格式乱了 | ✅ 一眼看到 |
| ⭐⭐⭐⭐⭐ 读了不知道做什么 | ❌⭐⭐⭐⭐⭐ **不会——它看起来像"分析得很全面"** |

三个原因叠加，让它成为最难通过反馈发现的一类问题：

1. ⭐⭐⭐⭐⭐ **它用了正确的术语、提到了正确的对象**，只是没说要做什么——
   而"专业"的观感来自术语，不来自动作
2. ⭐⭐⭐⭐ 读者会自己补一个动作，于是"没读懂"被当成"我理解得不够"
3. ⭐⭐⭐⭐⭐ **没有可对照的失败事件**——它不产生错误，只产生"没人行动"

> ⭐⭐⭐⭐⭐ 所以它不是被修掉的，而是以"这报告挺好但好像没什么用"的名义被停用。

## 5. ⭐⭐⭐⭐⭐ 四类产出各自的可行动性要求

按 `output-kind-three.md` 的三类（判定/变更/产物）加一类"分析"：

| 产出 | 可行动意味着 |
|---|---|
| 判定型 | ⭐⭐⭐⭐⭐ 判定结果必须指向一个明确的后续（放行 / 拦截 / 转人工），不能停在"中等风险" |
| 变更型 | ⭐⭐⭐⭐⭐ 报告改了什么 + 是否需要人复核，不能停在"已完成" |
| 产物型 | ⭐⭐⭐⭐ 产物怎么用、给谁看 |
| ⭐⭐⭐⭐⭐ 分析型 | 每条结论对应一个动作；这是四者里最容易全部落空的 |

判定型那条值得单独强调：

```
"风险等级：中"
```

> ⭐⭐⭐⭐⭐ **等级不是动作。** 输出了等级，等于把"中等该怎么办"留给了读者，
> 而这个技能存在的意义恰恰是回答这件事。

## 6. ⭐⭐⭐⭐ 什么时候"没有动作"才是正确答案

不是所有输出都要给动作。三种情况下，明确写"无需动作"比编一个动作好：

| 情况 | 正确输出 |
|---|---|
| 检查通过，无异常 | ⭐⭐⭐⭐⭐ "已检查 43 项，0 项异常"——**这是动作已完成，不是没有动作** |
| 结论需要人做业务判断 | ⭐⭐⭐⭐ "两个方案成本相当（A 3 人日 / B 2.5 人日），取舍取决于是否接受新增依赖——需你决定" |
| ⭐⭐⭐⭐⭐ 数据不足以给出动作 | "未获取到 4 月数据，无法判断趋势" |

> 第三种最该写也最常被跳过——⭐⭐⭐⭐⭐ **缺数据时模型的默认动作是补一个结论**，
> 而"没有动作"看起来像技能没做完，于是它被填上了。

关键区分：⭐⭐⭐⭐⭐ **"无需动作"是结论，"没有说动作"是缺失。**
前者能被验证（有分母、有判定过程），后者不能。

## 7. ⭐⭐⭐⭐⭐ 自检

```
□ 逐条结论问：读完这条，下一步做什么？答不上来 = 不可行动
□ grep "建议|关注|考虑|视情况|需要进一步" ——每一处都是候选
□ 删掉"建议"之后句子还成立吗？不成立 = 是助词在承担语法责任
□ 每条动作有没有阈值？没有阈值 = 永远可以做 = 永远不做
□ 每条动作有没有执行者？
□ "已完成"之外有没有说"改了什么/需不需要复核"？
```

最便宜的一条：**把输出里所有"建议"替换成"必须"，再读一遍**。
如果读起来觉得"这也太武断了"——说明它本来就没有判据支撑；
如果读起来觉得"确实该做"——说明"建议"这个词只是在替它免责。
