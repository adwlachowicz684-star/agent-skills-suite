## 1. ⭐⭐⭐⭐⭐ 一个不可判定的指令

```
"检查所有文件，确保没有遗漏"
"分析全部记录"
"产出一份全面的报告"
```

> ⭐⭐⭐⭐⭐ **"所有"在技能里不是一个可执行的指令——
> 因为模型没有独立的清单可以核对。**

它实际做的是：

```
⭐⭐⭐⭐⭐ 遍历它能看到的样本 → 停下来 → 报告"完成"
```

> ⭐⭐⭐⭐⭐ 它停在哪里，取决于⭐⭐⭐⭐⭐ **它恰好看到了多少**，
> 而不是实际有多少。
>
> 这就是"只定义怎么开始的技能会停在一个任意的地方"的机制——
> 那份讲的是⭐⭐⭐⭐ 现象，这份给出⭐⭐⭐⭐⭐ 根因：
> **没有分母，就没有完成。**

一个自检：

> ⭐⭐⭐⭐⭐ **跑完后能不能回答"一共处理了多少个"？**
> 不能 → 它停在一个任意的地方，而你和它都不知道。

## 2. ⭐⭐⭐⭐⭐ 可枚举化的三步

**① ⭐⭐⭐⭐⭐ 先列出，再处理**

```markdown
1. 先枚举：列出所有待处理项，输出计数 N
2. 逐项处理
3. ⭐⭐⭐⭐⭐ 收尾核对：处理数 == N？不等则报告差异
```

> ⭐⭐⭐⭐⭐ 第 1 步的价值不在"列出来"，
> 在于⭐⭐⭐⭐⭐ **它把分母变成了显式可见的数字**，
> 于是第 3 步的核对才可能发生。

**② ⭐⭐⭐⭐ 枚举本身要有方法，不能靠遍历**

```
不要："遍历目录下的所有文件"
要：  "用 [具体命令] 列出，记录总数"
```

> ⭐⭐⭐⭐ 差别在于：遍历会受上下文窗口限制，
> ⭐⭐⭐⭐⭐ 而一条命令的计数是准确的。

**③ ⭐⭐⭐⭐⭐ 上限与分批**

```
若 N > 阈值：分批，并报告批次进度（3/12 批）
```

> ⭐⭐⭐⭐⭐ 这条同时解决了"规模假设"那个坑——
> 不写死"约 100 条"，而是先数、再按实际数量分批。

## 3. ⭐⭐⭐⭐⭐ 覆盖率必须出现在输出里

```
❌ "分析完成，共 12,480 行"
✅ ⭐⭐⭐⭐⭐ "分析完成：覆盖 8/12 个来源（67%）；
            source_b 因 401 未取到；结论不适用于该来源"
```

> ⭐⭐⭐⭐⭐ **"12,480 行"是真实的，同时是误导的**——
> 它省略了分母，于是下游会当成全量。

三种必须报覆盖率的情况：

| 情况 | ⭐⭐⭐⭐⭐ 报告什么 |
|---|---|
| ⭐⭐⭐⭐⭐ 部分来源失败 | `8/12（67%）` + 哪个失败 |
| ⭐⭐⭐⭐ 超出上限被截断 | `处理了前 500 条，共 2,341 条` |
| ⭐⭐⭐⭐ 超时提前结束 | `已完成 6/9 步，停在 [步骤名]` |

> ⭐⭐⭐⭐⭐ 三类的共同点：**它们都是"成功了"**——
> 没有任何一个会触发错误路径。
> ⭐⭐⭐⭐⭐ 所以覆盖率是唯一能让它们变可见的字段。

这与 `skill-execution/references/parallel-and-concurrency.md` 的
"部分成功必须报覆盖率"是同一条，
那份讲的是⭐⭐⭐⭐ 并行的场景，这份讲的是⭐⭐⭐⭐⭐ **所有场景**。

## 4. ⭐⭐⭐⭐ "全面"是个无上限的词

含糊词黑名单里没有专门收这一类，但它值得单列：

```
"全面分析" "详细检查" "深入调研" "彻底排查"
```

> ⭐⭐⭐⭐⭐ 这些词的问题不是含糊，是⭐⭐⭐⭐⭐ **无上限**——
> 含糊词（"适当""相关"）至少有个大致范围，
> 而"全面"在任何完成度下都可以被声称达成。

判据（可 grep）：

> ⭐⭐⭐⭐⭐ **这句话能对应一个可数的产出吗？**
> "全面分析"→ 不能；"覆盖 12 个来源中的 12 个"→ 能。

替换表：

| ❌ | ⭐⭐⭐⭐⭐ ✅ |
|---|---|
| 全面分析 | 覆盖 [N] 个 [具体项] |
| 详细检查 | 逐项执行 [检查表] 中的 [N] 项 |
| 深入调研 | 回答以下 [N] 个问题 |
| 彻底排查 | 遍历 [枚举命令] 的结果，报告计数 |

## 5. ⭐⭐⭐⭐ 枚举失败的三种静默形态

即使写了"先列出再处理"，仍会静默失败的三种：

**① ⭐⭐⭐⭐⭐ 枚举本身就漏了**

```
用 glob `**/*.ts` 漏掉了 `.tsx`
```

> ⭐⭐⭐⭐⭐ 枚举是准确的，但枚举的口径是错的。
> ⭐⭐⭐⭐ 特征：**计数看起来很合理**（没人知道应该是多少）。

**② ⭐⭐⭐⭐⭐ 枚举之后新增了项**

```
列出 12 个 → 处理过程中变成 14 个 → 处理了 12 个 → 报告 12/12 ✅
```

> ⭐⭐⭐⭐⭐ 自洽，且完全错误。
> 这是"分数是标尺和被测物的比值"那条的一个实例：
> ⭐⭐⭐⭐ **分母和分子同时变了，比值看着没问题。**

**③ ⭐⭐⭐⭐ 某项处理失败但没从计数里扣除**

```
12 项中第 7 项失败 → 仍报告"12/12"
```

> ⭐⭐⭐⭐⭐ 这是"错误被改写成功"在计数层面的版本。

> ⭐⭐⭐⭐⭐ 三种的共同点：**都不会报错，都会产出"完成"**。
> ⭐⭐⭐⭐ 而且三种都只能靠"分子分母分别独立验证"来发现——
> 只看比值永远看不出来。

## 6. ⭐⭐⭐⭐⭐ 与停止条件的分工

| | 管什么 |
|---|---|
| ⭐⭐⭐⭐ `skill-recovery/references/exit-conditions-when-to-stop.md` | ⭐⭐⭐⭐ **能不能结束**（跑不动/该转人/该放弃） |
| ⭐⭐⭐⭐⭐ 本份 | ⭐⭐⭐⭐⭐ **结束了意味着做完了多少**（分母与覆盖率） |

> ⭐⭐⭐⭐⭐ 顺序不能反：**先定义分母，再定义停止。**
> 因为⭐⭐⭐⭐⭐ "跑不动"这件事本身就需要分母才能判定——
> 你怎么知道是"跑不动"还是"已经全跑完了"？

一个反例能说明这个依赖：

```
没有分母时：
  "处理了 40 个，没报错" → 它停了 → 是做完了还是跑不动了？⭐ 无法判断
有分母时：
  "处理了 40/120 个"     → 它停了 → ⭐⭐⭐⭐⭐ 明确是没做完
```

> ⭐⭐⭐⭐⭐ 前一种情况下，模型会报告"完成"——
> 因为从它的视角看，它确实做完了它看到的全部。
> ⭐⭐⭐⭐⭐ **它没撒谎，它只是没有分母。**
