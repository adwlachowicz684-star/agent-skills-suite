## 1. ⭐⭐⭐⭐⭐ 三个数字，三种错法

```
"平均响应时间 230ms"
"覆盖率 67%"
"共 12,480 行"
```

> ⭐⭐⭐⭐⭐ 这三个数字看起来一样可靠，
> ⭐⭐⭐⭐⭐ 而它们的失效方式完全不同：

| 数字 | ⭐⭐⭐⭐⭐ 主要风险 |
|---|---|
| 测量值（230ms） | ⭐⭐⭐⭐ 单位与口径（P50 还是 P99？含不含网络？） |
| 比率（67%） | ⭐⭐⭐⭐⭐ **分母没说**（且分母常常是错的那个） |
| 计数（12,480） | ⭐⭐⭐⭐⭐ **残缺被当成全量**（部分成功时代价最大） |

## 2. ⭐⭐⭐⭐⭐ 没有单位的数字不是数字

```
❌ "耗时 230"
❌ "大小 4.2"
❌ "增长了 15"
```

> ⭐⭐⭐⭐⭐ 模型会补一个它认为最可能的单位，
> ⭐⭐⭐⭐⭐ **而用户会按自己的场景去理解——两者常常不是同一个。**

高频歧义（这几组最该显式写）：

```
⭐⭐⭐⭐⭐ 时间：ms / s / min（差 1000 倍）
⭐⭐⭐⭐⭐ 字节：KB / MB / 字符数（差 1024 倍，且中英文差 3 倍）
⭐⭐⭐⭐⭐ 比率：百分点 / 百分比（"提高了 15" vs "提高了 15%"）
⭐⭐⭐⭐ 计数：行 / 条 / 个 / 文件
```

> ⭐⭐⭐⭐⭐ "百分点 vs 百分比"这一条尤其危险：
> ⭐⭐⭐⭐⭐ 它不涉及量纲，只涉及一个词的差别，
> 而⭐⭐⭐⭐⭐ **结果可能差一个数量级（3% → 5%，是 +2pp 还是 +66%）。**

写法（一行就够）：

```markdown
## 输出
- ⭐⭐⭐⭐⭐ 所有数值必须带单位；比率必须说明是"百分点"还是"百分比"
```

## 3. ⭐⭐⭐⭐⭐ 精度是承诺，不是修饰

```
"留存率 41.2837%"
```

> ⭐⭐⭐⭐⭐ 这个数字承诺了五位有效数字的准确度，
> ⭐⭐⭐⭐⭐ 而它通常来自 12 条样本。

两条规则：

**① ⭐⭐⭐⭐⭐ 精度不能超过样本支撑的精度**

```
样本 < 100 → 保留到整数或一位小数
⭐⭐⭐⭐⭐ 样本 < 20 → 直接说"约 X"，并给出样本量
```

> ⭐⭐⭐⭐⭐ 反过来看：⭐⭐⭐⭐ 虚假精度是一种⭐⭐⭐⭐⭐ **廉价的权威感**——
> 它不提高正确性，只提高可信度。这正是"错得自信"的一种形态。

**② ⭐⭐⭐⭐⭐ 样本量必须和比率一起出现**

```
❌ "覆盖率 67%"
✅ ⭐⭐⭐⭐⭐ "覆盖率 67%（3 项中 2 项成功）"
```

> ⭐⭐⭐⭐⭐ 这与 `skill-output/references/enumeration-and-completeness.md` 的"没有分母就没有完成"同源：
> ⭐⭐⭐⭐⭐ **分母既是完成度的定义，也是数字可信度的唯一线索。**

还有一个常被忽略的点：

> ⭐⭐⭐⭐ **浮点相等判断不要用（0.1+0.2 ≠ 0.3）**——
> 涉及金额时尤其，用整数分或定点。

## 4. ⭐⭐⭐⭐⭐ 口径：分子和分母都要说

比率是最容易出错的一类，因为它有两个自由度：

```
"缺失率 5%"
```

> ⭐⭐⭐⭐⭐ 分子是什么（缺字段的行？缺的字段数？）
> ⭐⭐⭐⭐⭐ 分母是什么（全部行？参与本次分析的行？）

最容易犯的具体错误：

```
⭐⭐⭐⭐⭐ 分母用了"总数"，而分子只来自"成功读取的部分"
→ 缺失率被低估
```

> ⭐⭐⭐⭐⭐ 这就是为什么部分成功时，分母必须跟着变：
> ⭐⭐⭐⭐ 覆盖率 67% 而缺失率按 100% 算 → 两个数字互相矛盾，
> ⭐⭐⭐⭐⭐ 而用户看不出来，因为它们出现在报告的不同段落。

写法：

```markdown
- ⭐⭐⭐⭐⭐ 报比率时必须写明分子口径与分母口径
- ⭐⭐⭐⭐⭐ 部分成功时，分母 = 实际处理的数量，不是总数
```

## 5. ⭐⭐⭐⭐⭐ 派生数字要标明算法

```
"留存中位数 41%"
"加权得分 8.7"
```

> ⭐⭐⭐⭐⭐ 这些不是测量值，是算出来的——
> ⭐⭐⭐⭐⭐ **而"怎么算的"决定了它能不能被比较。**

最典型的坑是中位数 vs 平均数：

```
⭐⭐⭐⭐⭐ 两者在长尾分布上可以差几倍，
⭐⭐⭐⭐⭐ 而用户默认按"平均数"理解一个没标明的"平均"
```

三条要求：

```
① ⭐⭐⭐⭐⭐ 是 mean / median / P90 / 众数？必须写明
② ⭐⭐⭐⭐⭐ 加权的话，权重是什么？
③ ⭐⭐⭐⭐⭐ 排除了异常值吗？按什么规则？
```

> ⭐⭐⭐⭐⭐ 第 ③ 条最常被省，而它⭐⭐⭐⭐⭐ 往往是两个数字对不上的唯一原因：
> 两个部门都算"平均响应时间"，一个剔除了超时，一个没有。

一个低成本写法：**在数字后面用括号带一句**

```
"响应时间中位数 230ms（P50，含网络，未剔除超时）"
```

> ⭐⭐⭐⭐⭐ 这一句的作用与 `skill-input/references/relative-time-resolution.md` 的
> "把解析结果写进输出首行"完全一致：
> ⭐⭐⭐⭐⭐ 不是为了这次更正确，是为了**下次不用重跑就能看出差别**。

## 6. ⭐⭐⭐⭐⭐ 零和"无数据"是两件事

```
"新增问题 0"
```

> ⭐⭐⭐⭐⭐ 这可能是"真的没有"，也可能是"没查到"。

> ⭐⭐⭐⭐⭐ 而模型几乎总是写成前者——
> ⭐⭐⭐⭐⭐ 因为"0"看起来是一个结果，而"未获取"看起来是失败。

这是最危险的一类，因为它恰好落在模型最想避免的地方：

```
模型有强烈的完成倾向
→ 遇到缺数据时默认填一个（按《skill-content》的 `skill-content/references/default-actions.md`）
→ ⭐⭐⭐⭐⭐ 填 0 是最常见的填法，因为它"看起来中性"
```

三种必须区分的状态要显式分开：

```
0         = 查了，确实没有
null / N/A = ⭐⭐⭐⭐⭐ 没查到（失败或跳过）
未统计     = 本次口径不包含
```

写法：

```markdown
- ⭐⭐⭐⭐⭐ 无数据必须写"未获取"，不得写 0
- ⭐⭐⭐⭐⭐ 输出中若存在未获取项，必须在开头说明，不得只在脚注提及
```

> ⭐⭐⭐⭐⭐ 第二条尤其重要：⭐⭐⭐⭐⭐ **放在脚注的"未获取"等于没有——
> 用户读到的是正文里的那个 0。**

## 7. ⭐⭐⭐⭐⭐ 自检

写完输出契约后逐条问：

```
① ⭐⭐⭐⭐⭐ 每个数字都有单位吗？比率写清是百分点还是百分比了吗？
② ⭐⭐⭐⭐⭐ 每个比率都给了分母/样本量吗？
③ ⭐⭐⭐⭐⭐ 精度超过样本能支撑的吗？
④ ⭐⭐⭐⭐⭐ 派生数字标了算法（mean/median/P90、权重、剔除规则）吗？
⑤ ⭐⭐⭐⭐⭐ "无数据"会和 0 混淆吗？
```

> ⭐⭐⭐⭐⭐ 第 ⑤ 条命中率最高，⭐⭐⭐⭐ 第 ② 条最容易一次改好。

一个十秒判断：

> ⭐⭐⭐⭐⭐ **随手挑一个输出里的数字，
> 问"如果用户拿它去做决策，他还缺什么信息"。
> 答得出来的那些缺项，就是该写进输出契约的内容。**

---

## 一句可贴在墙上

> ⭐⭐⭐ **虚假精度是一种廉价的权威感——它不提高正确性，只提高可信度。
> 而"0"和"未获取"的区别，是唯一一个错了会导致错误决策、却永远不会报错的差别。**
