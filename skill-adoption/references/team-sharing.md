## 三种共享方式怎么选

| 方式 | 适用 | 优点 | 缺点 |
|---|---|---|---|
| **放进项目仓库** `.claude/skills/` | 小团队、项目专属 | ⭐ clone 即用 · 无需配置 · 随项目变更同步 · **技能也被 code review** | 只能项目级；跨项目要另想办法 |
| **独立技能仓库** | 多项目共用 | 团队级统一管理 | 需要额外同步机制 |
| **Git submodule** | 严格管理 | 版本锁定 | 复杂度高 |

> ⭐ **项目级的最大隐藏好处**：
> **技能跟着代码一起被 review**——它不再是"某个人的配置"，而是工程资产。

## 三个作用域：global / project / team

```
global/          全员全项目共用    基础工作流（品牌语气、标准研究流程）
projects/<name>/ 单个项目专属      某客户的语气、某产品的框架
team-specific/   按职能划分        销售/市场/工程各自一套
scripts/         安装与同步自动化
```

```bash
mkdir -p global/{claude,cursor,opencode}
mkdir -p projects
mkdir -p team-specific/{sales,marketing,engineering}
mkdir -p scripts
```

> ⭐ **治理规则随作用域收窄而放松**：
> global 需完整评审 · project 需项目负责人批准 · team-specific 需职能负责人批准。

**README 就是治理文档**，必须回答五件事：

```
□ 有哪些技能，各自做什么
□ 怎么申请新技能
□ 怎么更新已有技能
□ ⭐ 谁评审技能 PR
□ 安全审查清单包含什么
```

## 治理：三个必须回答的问题

```
① 谁能添加技能？
   ⭐ 定义一个角色（团队负责人 / 技术负责人 / 指定技能 owner）拥有合并权限
   其他人通过 PR 提议，未经评审不能合并

② 评审包含什么？
   ⭐ 每个技能 PR 必须通过四项（见下）

③ 更新怎么传播？
   建分支 → 提交 PR（说明改了什么、为什么）→ 评审合并
   → 成员跑 scripts/sync.sh
```

**四项 PR 评审**（这是最有价值的一份清单）：

```
□ ⭐ 安全评审
  通读整个技能文件
  查提示注入模式、外部 URL 引用、⭐ "修改其他文件"的指令

□ ⭐ 质量评审
  确认技能有五个组成部分：
  输入定义 · 处理规则 · 输出格式 · 质量关卡 · 交接规则

□ 兼容性评审
  在团队用的所有工具上验证（如同时测多个客户端）

□ 品牌评审
  面向客户的技能（外联/内容/支持），确认输出符合品牌规范
```

> ⭐ **质量评审那五项是可以直接抄的判断标准**——
> 缺任何一项，这个技能就是"半成品"。

## PR 流程与版本

```bash
git checkout -b update-code-review-skill
# 编辑 SKILL.md
git commit -m "feat: add a11y check to code-review skill"
git push origin update-code-review-skill
# 开 PR，团队评审触发效果与措辞后合并
```

**在 frontmatter 里加版本**（排查时能省大量时间）：

```yaml
---
name: code-review
description: Review PR code
version: 1.2.0
---
```

**SemVer 对技能的具体含义**：

```
1.0.1  patch   修处理规则里的 bug
1.1.0  minor   新增一种输出格式
⭐ 2.0.0  major   改变了输入契约
```

```
□ 维护 CHANGELOG.md
□ 保护 main 分支，要求 PR 评审
□ ⭐ 状态检查要验证技能在多个工具上都能工作
□ ⭐ 更新搞坏了工作流 → git revert + 重跑 sync 脚本即可回滚
```

**入职文档**（新人第一件事）：

```bash
git clone git@github.com:your-org/team-skills.git ~/.claude/skills/team
# 验证：执行 /skills，确认 team/code-review 等出现在列表里
```

## 四个常见挑战与解法

**① 团队成员版本不一致**

```
□ 建立定期 git pull 的规则
□ 技能更新在群里通知
□ ⭐ CI 检查技能版本（进阶）
```

**② 技能太多管不过来**

```
□ 定期审计未使用的技能
□ ⭐ 按分类目录组织
□ ⭐ 区分"必需"与"可选"
```

**③ 技能质量参差不齐**

```
□ 制定技能编写指南
□ ⭐ 强制 PR 评审
□ 提供模板
```

**④ ⭐ 安全：技能本身就是攻击面**

> ⭐ **这一点必须单独强调**：

```
□ 技能里有 scripts/、有命令、有时还有凭据读取逻辑
□ ⭐ 一个被污染的技能 = 让 agent 在你机器上跑了一段你没仔细看的脚本
□ ⭐ 团队共享放大了这个风险——
   一个人引入恶意或粗心的技能，影响全队
```

```
□ ⭐ 脚本绝不硬编码密钥，走 bootstrap / 环境变量
□ ⭐ 安全要求不能靠"感觉没问题"
□ 把私有技能当作"发布内部包"对待，而不是"在文档里分享提示词"
```

## 一条最省力的起步建议

> ⭐ **从一个技能开始，按团队反馈扩展。**

**写技能的四个步骤**（这条经验最实在）：

```
Step 1  不要一上来建体系——先解决一个真实痛点

Step 2 ⭐ 一条规则对应一个坑
  每写一条规则，问自己"这条规则是被哪个真实的坑逼出来的"
  ⭐ 答不上来，删掉
  ⭐ 预防性规则是技能膨胀的第一大原因

Step 3  给技能写清晰的触发条件
  ❌ "加载所有 C 相关技能"
  ✅ "写 C 代码时加载编码规范" · "做 CR 时加载 CR 规范"
  越精确越好

Step 4 ⭐ 用一次、改一次
  写完就交给 agent 做真实任务
  观察哪一步出了问题——规则不够具体？规则冲突了？
  ⭐ 每次发现问题，改一条。不要一次加十条
```

> ⭐ **核心原则：技能不是写出来的，是用出来的。**
> 你写了一百条规则但一条没用过——等于没写。

**ROI 的账**：

```
□ ⭐ 写好一条规则可能五分钟
□ 但这条规则 ⭐ 每次 agent 执行任务都会生效
□ ROI 远超写文档
```

**两个常见错误**：

```
❌ 把 System Prompt 全搬进技能
   ⭐ 技能不该定义"你是谁"，应定义"遇到什么场景怎么做"

❌ 技能写得像教科书
   追求注释完整度，而不是可执行性
```

**最后一句值得记**：

> **技能的本质不是"让 agent 更聪明"，是让你的经验可复制。**
> 你花三个月调教出一个懂你项目规范、懂你工作流的 agent——
> **不需要同事也花三个月，把技能给他，他立刻拥有你三个月的积累。**

## 自查

```
□ 是否选对了共享方式（项目仓库 / 独立仓库 / submodule）？
□ 技能是否跟着代码一起被 code review？
□ 是否分了 global / project / team 三个作用域？
□ README 是否回答了五个治理问题？
□ ⭐ 是否定义了"谁能合并"？
□ ⭐ PR 评审是否含四项（安全/质量/兼容/品牌）？
□ 质量评审是否检查了五个组成部分（输入/规则/输出/关卡/交接）？
□ 是否声明了新版技能的依赖前提（需要 shell？需要网络？）？
□ frontmatter 是否有 version？
□ SemVer 的含义是否明确（major = 改输入契约）？
□ 是否有 CHANGELOG 与分支保护？
□ 是否有回滚路径（revert + 重跑 sync）？
□ 是否有新人入职文档（第一件事是拉技能仓库）？
□ ⭐ 是否有"脚本不硬编码密钥"的硬要求？
□ 是否意识到"团队共享放大了技能作为攻击面的风险"？
□ ⭐ 是否做到了"一条规则对应一个坑"（答不上来就删）？
□ 是否避免了"把 System Prompt 全搬进技能"？
□ 是否遵循"用一次、改一次"（而非一次加十条）？
```
