## 1. ⭐⭐⭐⭐⭐ 最贵的不是决策，是重复决策

一个典型循环：

```
3 月：讨论"要不要把 A、B 合成一个技能" → 决定不合
6 月：新人问"为什么 A 和 B 是分开的" → 没人记得
      → 重新讨论一遍 → 又决定不合（或改主意合了）
9 月：又有人问……
```

> ⭐⭐⭐⭐⭐ **同一个决策被做了三次，其中两次是纯浪费。**

而更糟的是第二次：

> ⭐⭐⭐⭐⭐ **不知道当初为什么不合，就可能改主意——
> 而改的那个主意往往正是一开始被否决的那个。**
> 因为否决它的理由已经不在场了。

> ⭐⭐⭐⭐ 这与"真的有歧义时记 --decision 日志，
> 没记下来的仲裁等于下次重新吵"是同一条原则，
> 只是那份讲的是**运行时**的仲裁，这份讲的是**设计期**的决策。

## 2. ⭐⭐⭐⭐⭐ 哪些决策值得记

> ⭐⭐⭐⭐⭐ **判据：这个决定，三个月后被问"为什么"时，
> 你能凭记忆回答吗？**

值得记的四类：

**① ⭐⭐⭐⭐⭐ 拆分与合并**

```
为什么 A、B 是两个技能（或两个是一个）
```

> ⭐⭐⭐⭐⭐ 最高频被重新讨论的一类。
> ⭐⭐⭐⭐⭐ 因为我们既有 4 个拆分判据又有 5 个合并信号——
> **两边都有理由，所以每次讨论都能得出相反的结论。**

**② ⭐⭐⭐⭐⭐ 与直觉相反的选择**

```
"这里没有用表格，因为要被逐条执行"
"这里保留了冗余，因为压缩会丢开头"
```

> ⭐⭐⭐⭐⭐ **这种最该记**——因为下一个人（或下一次你）
> 会本能地"修正"它，而那个修正正是错的。

**③ ⭐⭐⭐⭐ 被否决的方案**

```
"考虑过做成脚本，因为 X 放弃了"
```

> ⭐⭐⭐⭐⭐ 记录被否决的方案比记录采纳的方案更值钱：
> ⭐⭐⭐⭐ 采纳的方案在产物里看得见（所以有迹可循），
> **被否决的什么痕迹都没有**——于是它会被反复重新提出。

**④ ⭐⭐⭐⭐ 依赖某个外部事实的决定**

```
"因为平台 X 不支持 aliases，所以用描述里写旧名的方式"
```

> ⭐⭐⭐⭐⭐ **外部事实会变**——变了之后这个决定就该重审。
> ⭐⭐⭐⭐ 记下"因为 X"就是为了在 X 变化时能找到所有受影响决定。

## 3. ⭐⭐⭐⭐ 六段式格式

```markdown
## ADR-003: A 与 B 保持两个独立技能

- 日期：2026-06-14
- ⭐ 状态：生效（/ 已被 ADR-007 取代）
- ⭐⭐⭐⭐⭐ 决策：不合
- ⭐⭐⭐⭐⭐ 理由：两者权限集合不同（A 只读、B 需写）
- ⭐⭐⭐⭐ 被否决的方案：合并为 A-with-B（省一次调用）
- ⭐⭐⭐⭐⭐ 重审条件：当 B 不再需要写权限时
```

六段的分工：

| 段 | ⭐ 作用 |
|---|---|
| 日期 | ⭐⭐⭐ 判断信息新鲜度 |
| ⭐⭐⭐⭐⭐ 状态 | ⭐⭐⭐⭐⭐ **唯一区分"现行"和"历史"的字段** |
| 决策 | 结论 |
| ⭐⭐⭐⭐⭐ 理由 | ⭐⭐⭐⭐⭐ 必须指向可查的东西（权限集合、硬数据） |
| ⭐⭐⭐⭐ 被否决的方案 | ⭐⭐⭐⭐⭐ 防重复提出 |
| ⭐⭐⭐⭐⭐ 重审条件 | ⭐⭐⭐⭐⭐ **让它有终点，也让它能被自动触发** |

> ⭐⭐⭐⭐⭐ 最后一段最常被省，也最有价值：
> ⭐⭐⭐⭐ **没有重审条件的 ADR 会变成永久约束**——
> 即使它依赖的前提早就消失了。

> ⭐⭐⭐⭐⭐ 理由那段要注意：
> **"因为这样更清晰"不是理由**（不可查），
> ⭐⭐⭐⭐⭐ **"因为权限集合不同"才是**（可查）。
> 这与"决策依据 vs 解释"是同一条判据。

## 4. ⭐⭐⭐⭐⭐ 记在哪：不是单独文件

三种选择：

| 位置 | ⭐ 评价 |
|---|---|
| ⭐⭐⭐⭐⭐ **技能目录内的 `DECISIONS.md`** | ⭐⭐⭐⭐⭐ 随技能搬迁，改技能时就在手边 |
| 仓库级 `docs/adr/` | 集中，但⭐⭐⭐ 改技能时不会想起去看 |
| ⭐⭐⭐ wiki / 文档站 | ⭐⭐⭐⭐ **等于没记**——需要时根本想不起去查 |

> ⭐⭐⭐⭐⭐ **第一条最重要**：
> ⭐⭐⭐⭐⭐ **ADR 必须在"你会看到它"的地方，
> 而不是"它应该待"的地方。**
>
> 放在 wiki 里的 ADR，和没写的区别很小——
> 因为重新讨论发生时，没人会先去翻 wiki。

这也是"目录契约"那条原则的应用：
⭐⭐⭐⭐ **决策记录跟着技能走，才能随技能一起分发**。

## 5. ⭐⭐⭐⭐⭐ ADR 的三种失效

| 失效 | ⭐ 症状 |
|---|---|
| ⭐⭐⭐⭐⭐ 从不重审 | ⭐⭐⭐⭐⭐ 前提变了，决定还在（与"腐烂"同构） |
| ⭐⭐⭐⭐ 只记采纳不记否决 | ⭐⭐⭐⭐⭐ 被否决方案被反复重新提出 |
| ⭐⭐⭐⭐ ADR 越写越长 | ⭐⭐⭐⭐ 变成设计文档 → 没人读 → 等于没写 |

> ⭐⭐⭐⭐⭐ 第一条的解药就是"重审条件"那一段：
> ⭐⭐⭐⭐ **把"要不要重审"从需要人记得想，变成有触发条件的机制**
> （与 `review_after`、错误预算、夹具 TTL 同一套路）。

第三条很实在：**一条 ADR 超过 20 行就没人读了**。
⭐⭐⭐⭐⭐ **ADR 是决策的索引，不是决策的论证**——
论证过程留在 PR 里（那里有完整的讨论）。

## 6. ⭐⭐⭐⭐ 与 changelog 的分工

| | ⭐⭐⭐⭐⭐ ADR | ⭐⭐⭐⭐ changelog |
|---|---|---|
| 记什么 | ⭐⭐⭐⭐⭐ 为什么这么定（含被否决的） | 改了什么 |
| 读者 | ⭐⭐⭐⭐ 三个月后的自己 / 新人 | 下游维护者 / 使用者 |
| 时间 | ⭐⭐⭐⭐⭐ 写一次，长期有效 | 每次改动都追加 |
| 会失效吗 | ⭐⭐⭐⭐⭐ 会（需要重审条件） | 不会（是历史） |

> ⭐⭐⭐⭐⭐ **changelog 是时间序列，ADR 是状态。**
> 一个"现在为什么是这样"的问题，changelog 回答不了——
> 因为它散落在十次改动里。
>
> 反过来，ADR 也回答不了"什么时候变成这样的"。

两者都要，且⭐⭐⭐⭐ **changelog 里可以写"见 ADR-003"**
——这是唯一把它们连起来的方式，成本一行。
