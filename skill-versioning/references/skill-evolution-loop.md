## 1. ⭐ 前提：技能是代码，不是文档

```
文档写完归档
⭐ 代码写完要跑测试、要 review、要迭代
⭐ Skill 应该是后者
```

> ⭐ 这句话是整个进化方法论的地基——**如果你把它当文档，就不会有迭代，
> 而它就会一直停在"第一版"的水平。**

配套一条来自 `skill-anatomy-antipatterns.md` / `weekend-lessons.md` 的实证：
**技能是从几行字加一条踩坑记录开始的**——所以"第一版很小"不是缺陷，是常态。

## 2. ⭐⭐ 什么算实践反馈：三档信号

> ⭐ **不是所有使用中的不顺畅都值得改技能。**

**强信号——必须改**：

```
· ⭐ 执行失败率高于 20%，且失败原因可归类
· ⭐ 同一个步骤在多次执行中都需要人工介入修正
· 生成的输出被用户反复要求重写
```

**中信号——应该改**：

```
· 某个步骤在特定场景下是多余的
  （例：技能写了"先检查权限"，但实际所有调用场景都已预检过权限）
· 某个参数的默认值在实践中几乎总是需要覆盖
· ⭐ 引用的外部资源（API、文档链接）已经变更
```

**弱信号——可以改**：

```
· 表述不够清晰，导致 agent 偶尔走偏
· 某些步骤的顺序在实际执行中不够自然
· 缺少一些边界 case 的处理指引
```

> ⭐⭐ **关键是要有一个机制来捕获这些信号，而不是靠感觉。**
> ⭐ **区别在于：技能的"bug"不是代码层面的，而是流程设计层面的。**

> ⭐ 中信号里那条"多余的预检步骤"特别值得记——
> 它是**技能里最常见的"看起来正确但实际浪费"的内容**，
> 也正是 `skill-reducer-study.md` 说"拿掉之后质量反而上升"的那类东西。

## 3. ⭐ 迭代节奏：周 / 月 / 季

**不需要每天改。**

```
周度回顾（15 分钟）
   翻一遍本周的技能使用记录
   看有没有"中信号以上"的问题
   ⭐ 有就记到 CHANGELOG

月度修订
   ⭐ 每月选 1–2 个使用频率最高的技能做一次正式修订
   ⭐⭐ 修订不是微调，是⭐ 重新审视整个 SKILL.md 的结构是否还合理

季度大改
   全面扫描，重点看：
   · 有没有技能已经完全不用了（该删）
   · ⭐ 有没有技能之间职责重叠（该合并）
   · 有没有新出现的场景缺技能（该建）
```

> ⭐ 月度那条里的"修订 ≠ 微调"很重要：
> **微调解决不了结构性问题**，而结构问题只有重新看一遍才发现。

## 4. ⭐⭐ 修订的四种操作

```
删   ⭐ 最容易忽略的一种
     ⭐⭐ 一个步骤如果连续 5 次使用中都没有产生实际作用，删掉它

合并
下沉（把内容移到 references/，主文件只留指针）
补充（补边界 case、补失败分支）
```

> ⭐⭐ **"删"排第一且被明确标注为最容易被忽略**，
> 这与人类写作直觉相反——**我们天然更愿意加东西而不是减东西**。

"连续 5 次没有产生实际作用"这个判据很实用：**它是可数的、可观察的**，
比"感觉没用"强得多（又一次印证 `write-reasons-not-rules.md` 的
"把形容词换成规格"）。

## 5. ⭐ compaction：把多条规则压成一条标准

技能迭代会逐渐变详细，**所以需要定期压缩重构**。

**一个具体例子**（旅行规划技能）：

```
压缩前（主文件里堆了很多条规则）：
  - 不要把距离很远的景点放在同一天
  - 每天要控制景点数量
  - 轻松旅行要留休息时间
  - 餐厅要靠近当天路线
  - 亲子旅行要减少换乘

⭐ 压缩后（合并成一条更稳定的质量标准）：
  "Prioritize route coherence and pace fit:
   keep each day geographically coherent, limit major stops
   according to pace, place meals and breaks near the route,
   and reduce transfers for family trips."
```

> ⭐⭐ 这个例子最有价值的地方在于：
> **五条具体规则 → 一条原则，不是信息的丢失，而是⭐ 抽象层级的提升**。
>
> 具体规则只能覆盖列举到的情况，原则能覆盖没列举到的情况
> ——这正是 `write-reasons-not-rules.md` 说的"写原因而非堆规则"：
> **给了原则，模型碰到你没预料的场景也知道怎么办。**

**规则的生命周期路径**（完整的四步）：

```
积累 → ⭐ 压缩 → 合并 → 下沉 → 删除
```

目标是让技能保持**清晰、轻量、可维护**。

## 6. ⭐ 用验证决定能否发布

```
候选技能生成后，进入验证环节：
   ⭐ 如果新版本表现更好 → 发布为 v1.1
   ⭐ 如果它过度保守（例：行程内容太少）→ ⭐ 这次修改被拒绝
      ⭐⭐ 并记录为下一轮优化的"负反馈"
```

**完整闭环**（值得抄的是它的顺序）：

```
用户反馈 → 成为证据 → 抽象成规则 → 写入合适的技能层级
        → 通过验证决定是否进入新版本
        → 随着规则积累，再做压缩/合并/下沉/删除
```

> ⭐⭐ **"被拒绝的修改要记录为负反馈"这一条是整套闭环里最关键的**：
> 没有它，下一次迭代很可能会**把同一个错误的改法再提一遍**。

## 速查

```
□ ⭐ 前提是"技能是代码不是文档"——文档写完归档，技能要迭代

⭐⭐ 三档信号：
□ 强（必须改）：失败率>20% 且可归类 / 同一步骤反复需人工介入 / 输出被反复重写
□ 中（应该改）：步骤多余（如已预检的权限）/ 默认值总被覆盖 / ⭐ 外部资源已变更
□ 弱（可以改）：表述不清 / 顺序不自然 / 缺边界 case
□ ⭐⭐ 要有机制捕获信号，不能靠感觉
□ ⭐ 技能的 bug 在流程设计层面，不在代码层面

⭐ 节奏：
□ 周度 15 分钟回顾（记录中信号以上）
□ ⭐ 月度：选 1–2 个最高频技能⭐ 重新审视结构（不是微调）
□ 季度：该删 / ⭐ 该合并（职责重叠）/ 该建

⭐⭐ 四操作：
□ ⭐ 删（最易忽略）：⭐ 连续 5 次没产生实际作用就删
□ 合并 / 下沉 / 补充

⭐ compaction：
□ ⭐⭐ 五条具体规则 → 一条原则 = 抽象层级提升，不是信息丢失
□ 原则能覆盖没列举到的情况
□ 路径：积累 → 压缩 → 合并 → 下沉 → 删除

□ ⭐⭐ 被拒绝的修改要记录为负反馈，否则下次会重提
□ 反馈→证据→规则→写入合适层级→验证→发布
```

**一句话**：

> ⭐⭐ **"删"是最容易被忽略的操作，而它有一条可数的判据：
> 连续 5 次使用中都没产生实际作用的步骤，删掉。**
