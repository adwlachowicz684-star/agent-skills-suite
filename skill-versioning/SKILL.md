# 技能的演进与版本

## 边界

- 用于：**技能改了之后**——版本、影响面、回归、回滚、迁移
- 不用于：瘦身/拆分决策 → 《skill-refining》
- 不用于：安全审计 → 《skill-security》
- 不用于：打包上架 → 《skill-distribution》

## 核心原则

> ⭐⭐⭐⭐ **改技能的成本与改动大小几乎无关，与影响面成正比。**
> 改一个字段名（1 行）风险远高于重写整个流程（300 行、无下游）。

```
□ ⭐⭐⭐⭐⭐ 版本可回滚 > 评估集 > 性能调优
     顺序反了，团队会在第 3 个月陷入"不知道哪个版本是对的"
□ ⭐⭐⭐⭐⭐ 歧义时默认回滚，不是保留
□ ⭐⭐⭐⭐ 有历史才能回滚，能回滚才敢改
```

## Critical Rules

- ⭐⭐⭐⭐⭐ **歧义时默认回滚**——模型越强，人工审核这道关越不能放松
- ⭐⭐⭐⭐⭐ **70% 的技能线上事故来自"未经评估的微调"**——不是大改，是看起来最无害的小改
- ⭐⭐⭐⭐⭐ **运营/非作者改描述 = 事故源头**——不要把技能当普通文本对待
- ⭐⭐⭐⭐ 每次改动都要能回答"影响谁"
- ⭐⭐⭐⭐ 被推翻的规则及其 eval 数据，是团队最值钱的资产之一
- ⭐⭐⭐⭐ 升级模型时移除沿袭的验证指令，否则过度验证

## 常见借口

| Agent 说 | 回应 |
|---|---|
| "只是改个描述，不用测" | ⭐⭐⭐⭐⭐ 描述是触发集，改了就有一批输入行为变了 |
| "改动很小" | ⭐⭐⭐⭐⭐ 风险与改动大小无关，与影响面成正比 |
| "回滚太麻烦，先往前修" | ⭐⭐⭐⭐⭐ 歧义时默认回滚。往前修会让你再也说不清哪个版本是对的 |
| "新模型更强，不用改技能" | ⭐⭐⭐⭐⭐ 升级要做减法，且提示跨模型只弱相关 |
