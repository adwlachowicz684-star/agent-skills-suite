## 1. ⭐⭐⭐ 两个机制，不是一个

> ⭐⭐⭐ **两个独立的机制在同时工作**：

```
① ⭐ "技能在哪里生效"  ⭐ 行为像 ⭐ CSS 选择器
   ⭐⭐ 从⭐ 宽到窄运行：
      home 目录 = 这台机器上每个会话
      repository = 一个项目
      嵌套目录   = 项目里的一个包

② ⭐ "两个技能同名时谁赢"  ⭐ 行为像 ⭐ 源与重要性（origin & importance）
   ⭐⭐⭐ ⭐ 它⭐ 不是从窄到宽运行的
   ⭐⭐⭐ ⭐⭐ 越⭐ 宽泛的放置位置越赢
```

**顺序**（与已有文档一致，这里给完整版）：

```
⭐⭐⭐ enterprise 覆盖 personal
      personal  覆盖 project
      以上三者   覆盖 bundled（内置）
```

> ⭐⭐⭐ 为什么值得用 CSS 这个比喻：
> 因为它⭐ 精确区分了"选择器"（生效范围，窄的更适用）
> 和"源/重要性"（冲突裁决，宽的更赢）——
> ⭐⭐ 而多数人的错误正是⭐ 把这两件事当成了一件。

## 2. ⭐⭐⭐ 常见错误：把"近"当成"强"

> ⭐⭐⭐ **人们很容易以为⭐ 离工作目录最近的技能最强
> （就像样式表里嵌套更深的规则通常更强）。**
>
> ⭐⭐⭐ **对"生效范围"这个直觉是对的；
> ⭐⭐⭐ ⭐ 对"同名冲突"它⭐ 完全相反。**

```
~home/.claude/skills/react-best-practices   → ⭐ 生效
my-app/.claude/skills/react-best-practices  → ⭐ 被覆盖

⭐⭐⭐ 越宽的放置位置每次都赢
```

**最省事的应对**（一句话）：

> ⭐⭐⭐ **给技能起⭐ 唯一的名字，这样的冲突⭐ 根本不必被裁决。**
> `frontend-pr-review`，而不是 `review`。

> ⭐ 这与 `naming-conventions.md` 的
> "绝不遮蔽官方技能名（用 `pdf-internal` / `commit-team`）"
> 是同一条，但这里补上了⭐ **为什么**：
> 因为一旦同名，赢的⭐ 不是你以为的那一个。

**还有一条小规则**：

```
⭐ 技能与命令同名 → ⭐ 技能优先
```

## 3. ⭐⭐⭐ 插件不在梯子上

> ⭐⭐⭐ **插件技能⭐ 不参与这个级联。**
>
> 它们带 `plugin-name:skill-name` 命名空间，
> ⭐⭐ 所以⭐ 根本不可能与其他层级冲突。

```
my-app/.claude/skills/code-review              → 解析为 code-review
plugins/pr-tools/skills/code-review            → 解析为 pr-tools:code-review

⭐⭐⭐ 不同的名字，所以插件技能永远不会与上面几层撞车
```

> ⭐⭐⭐ **"插件不是梯子的最底一级，⭐⭐⭐ 它们在梯子之外。"**
>
> ⭐⭐ 这条纠正了一个常见的错误表述——
> 很多资料把插件画成最低优先级，
> ⭐ 但正确理解是⭐ **它们有独立命名空间，压根不在同一条轴上**。

## 4. ⭐⭐⭐ 嵌套不覆盖，是共存

```
仓库根有 deploy
apps/web/.claude/skills/ 也有 deploy

⭐⭐⭐ 两个都保留
   根那个叫 deploy
   ⭐⭐ 嵌套那个⭐ 以目录限定名出现：apps/web:deploy
   它的 description 会说明⭐ 适用于哪个目录
```

**调用时会发生什么**（这个机制设计得很聪明）：

```
⭐ 输入 /deploy                → 运行根级技能
⭐ 输入 /apps/web:deploy       → 运行嵌套那个
⭐⭐⭐ 当⭐ 未限定名被调用时：
   根技能加载，⭐⭐ 并⭐ 附上一份限定变体列表
   ⭐⭐⭐ + 一条指令：⭐ 同时调用那些"目录包含当前正在处理的文件"的变体
```

> ⭐⭐⭐ **嵌套技能因此⭐ 即使没人输入它的限定名，
> ⭐ 仍然会应用于它自己目录里的工作。**
>
> ⭐⭐ 这是⭐ 唯一一处"更窄确实意味着更适用"的地方——
> 其余所有地方，冲突都由⭐ 源（origin）决定。

## 5. ⭐⭐ 放置位置同时决定两件事

| 位置 | 影响范围 | 备注 |
|---|---|---|
| ⭐ Personal | 你机器上每个项目 | ⭐ 私有的，⭐ 永远不进 git |
| ⭐ Project | 一个仓库 | ⭐⭐ 会传播给每个 clone 它的人 |
| ⭐ Plugin | 同时多个仓库 | ⭐ 有版本、有命名空间 |
| ⭐⭐ Enterprise | 整个组织 | ⭐⭐ 赢下每一场冲突 |

> ⭐⭐⭐ **你把技能放在哪里，⭐ 同时定了两件事：
> ⭐⭐ 它能影响多远，以及⭐⭐ 它被允许多大地做事。**

> ⭐⭐ 第二句容易被忽略——"被允许多大地做事"
> 正是指 `skill-invocation-control.md` 讲的权限边界：
> ⭐ **Enterprise 层不只是优先级最高，也是⭐ 最该被严格审查的一层**，
> 因为它影响所有人且你无法回避。

## 6. ⭐⭐ 编辑实时生效的唯一例外

```
⭐ 在⭐ 已被监视的目录下增删改技能 → ⭐ 当前会话内实时生效

⭐⭐⭐ 唯一例外：
   ⭐⭐⭐ ⭐ 会话开始时不存在的顶层 skills 目录，
        ⭐ 创建它需要重启——因为⭐ 之前那里没有东西可监视
```

> ⭐⭐⭐ 这条终于把我们此前那个矛盾的精确边界说清楚了：
>
> ```
> "改了技能要重启"（four-layer-diagnosis-flow）
>   ⭐ 只对"顶层目录本身是会话中新建的"这一种情况成立
> "改了不用重启"（trigger-fix-nine-causes）
>   ⭐⭐⭐ 对⭐ 已存在目录下的编辑成立——实时生效
> ```
>
> ⭐⭐ 补充一条：`--add-dir` 授予的是文件访问，不是配置发现，
> ⭐ 但⭐ 被添加目录里的 `.claude/skills/` ⭐ 也会被一并加载
> （这是一个⭐ 刻意的例外）。

## 速查

```
□ ⭐⭐⭐ 两个机制：① 生效范围 = 选择器（⭐ 窄的更适用）
                ② 同名冲突 = 源/重要性（⭐⭐⭐ 宽的更赢）
□ ⭐⭐⭐ ⭐ 别把"离工作目录近"当成"强"——对冲突它恰好相反
   enterprise > personal > project > bundled
□ ⭐⭐⭐ 起唯一名字（frontend-pr-review），冲突就不必被裁决
□ ⭐ 技能与命令同名 → 技能优先

□ ⭐⭐⭐ ⭐ 插件⭐ 不在梯子上（有 plugin-name 命名空间，压根不冲突）
□ ⭐⭐⭐ ⭐ 嵌套技能⭐ 共存不覆盖：apps/web:deploy
   ⭐⭐⭐ 未限定调用时，根技能会带上变体列表 + "也调用适用目录的变体"

□ ⭐⭐ 位置定两件事：影响多远 + ⭐⭐ 被允许多大地做事
   Personal(私有不进git) · Project(跟着 clone 走) · Plugin(跨仓) · ⭐ Enterprise(全组织)
□ ⭐⭐⭐ 重启的唯一正当理由：⭐ 顶层 skills 目录在会话中新建
   已有目录下的编辑 → ⭐ 实时生效
```

**一句话**：

> ⭐⭐⭐ **用 CSS 理解技能放置：生效范围是选择器（窄的更适用），同名冲突是源与重要性（宽的更赢，enterprise > personal > project > bundled）——
> 把"离工作目录近"当成"强"是最常见的错误；
> 而插件根本不在梯子上（有命名空间），嵌套技能是共存不是覆盖。**
