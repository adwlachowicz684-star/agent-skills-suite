## 1. ⭐⭐⭐⭐⭐ 三类问题收敛框架

> ⭐⭐⭐⭐⭐ **"⭐ 几乎每一个 Claude Code 的失败，
> ⭐⭐⭐⭐⭐ ⭐ 都是⭐ 一个⭐ 上下文加载问题、⭐ 一个⭐ 优先级问题、
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 或者⭐ 一个⭐ 描述匹配问题。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 一旦你能⭐ 说出你正在看的是哪一类，⭐⭐⭐⭐⭐ ⭐ 具体修法就显而易见了。"**

| 类型 | ⭐ 典型症状 | ⭐⭐ 修法方向 |
|---|---|---|
| ⭐⭐⭐ **上下文加载** | 东西根本没进上下文 | 查文件位置、YAML、作用域 |
| ⭐⭐⭐⭐ **优先级** | 加载了但被别人盖掉 | 查谁的作用域更高 |
| ⭐⭐⭐⭐ **描述匹配** | 加载了、也没被盖，但就是没触发 | 改 description |

> ⭐⭐⭐⭐⭐ 这个框架⭐ 与 `skill-loading/references/four-layer-diagnosis-flow.md` 的四层⭐ 高度吻合，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 但⭐ 它更值钱的地方在于⭐ **它是一次收敛，不是一次清单**：
> ```
> 清单：17 种失败模式，逐个试（⭐ 你会忘了第 9 个）
> ⭐⭐⭐⭐⭐ 框架：⭐ 先判断是三类中的哪一类 → ⭐⭐⭐⭐⭐ ⭐ 修法自动浮现
> ```
>
> ⭐⭐⭐⭐⭐ 而⭐ 那句"⭐ 你不会记住 17 种失败模式，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 你会记得⭐ 有一份目录存在、⭐ 然后去查你撞上的那一个"
> ⭐⭐⭐⭐ ⭐⭐⭐⭐ ——这与⭐ 我们自己的⭐ 整套库⭐ 是同一个立场：
> ⭐⭐⭐⭐⭐ **参考文档是⭐ 供查阅的，⭐⭐⭐⭐⭐ ⭐⭐⭐ 不是⭐ 供背诵的；
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐ 而⭐ 判断"该查哪一档"⭐ 才是⭐ 需要⭐ 被内化的能力。**

## 2. ⭐⭐⭐⭐ 诊断命令表

| 命令 | ⭐ 显示什么 |
|---|---|
| ⭐⭐⭐⭐⭐ `/context` | ⭐ 当前会话占用上下文的**全部内容**，按类别分解：系统提示、系统工具、MCP 工具、自定义子代理及其加载源、内存文件、**skills**、对话消息 |
| `/skills` | ⭐ 来自项目/用户/插件源的可用技能 |
| `/memory` | 内存文件位置 + 打开选项 + 自动内存开关 |
| `/hooks` | 活跃的 hook 配置 |
| `/mcp` | 已连接的 MCP 服务器及状态 |
| `/permissions` | ⭐⭐⭐ 当前生效的**已解析**允许/拒绝规则 |
| ⭐⭐⭐⭐ `/doctor` | 配置检查：安装健康、无效设置文件、未使用扩展、⭐ 同目录重复子代理名 + **建议的修复**（按 f 可应用） |
| ⭐⭐⭐⭐ `/debug [issue]` | 启用调试日志，并提示 Claude ⭐ 用日志输出和设置路径做诊断 |
| ⭐⭐⭐ `/status` | ⭐ 活跃的设置源，包括托管设置是否启用 |

**几个此前没收过的细节**：

> ⭐⭐⭐⭐⭐ **`/context` 的 skills 部分⭐ 还包含⭐ 捆绑技能（bundled），
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 而 `/skills` ⭐ 不会列出它们。**

```
⭐⭐⭐⭐⭐ 推论：⭐ 想看"到底占了上下文什么"，用 /context；
         ⭐⭐⭐⭐⭐ ⭐ 想看"我能调哪些"，用 /skills。
         ⭐⭐⭐⭐⭐ ⭐⭐⭐ 两者⭐ 不一样，⭐⭐⭐⭐ 别互相印证。
```

> ⭐⭐⭐⭐⭐ **首先运行 `/context` ⭐ 来确认你的 CLAUDE.md、规则或技能描述⭐ 是否存在。**

```
⭐⭐⭐⭐ 这是⭐ 官方给的⭐ 第一步——⭐⭐⭐⭐⭐ ⭐ 而不是先改描述、也不是重启。
⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ "存在吗"先于"写得好吗"。
```

## 3. ⭐⭐⭐⭐⭐ 作用域优先级（与技能覆盖顺序不同）

```
配置作用域（高者胜）：
  1. ⭐⭐⭐⭐⭐ Managed settings — 组织策略，⭐ 不可被覆盖
  2. Local    — .claude/settings.local.json（本机）
  3. Project  — .claude/settings.json（提交进仓库，团队）
  4. User     — ~/.claude/settings.json（你的默认）
```

> ⭐⭐⭐⭐⭐ 这与⭐ 技能的同名覆盖顺序⭐ **不是一回事，别记混**：
> ```
> 技能：enterprise > personal > project（越全局越赢）
> 配置：managed > local > project > user
> ```
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 两者⭐ 都有"⭐ 越全局越赢"的影子，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ ⭐ 但⭐ 技能的⭐ 第二三级顺序（personal > project）
> ⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 跟配置的（local > project）⭐ 名字不同、层级也不同。
>
> ⭐⭐⭐⭐⭐ 一句最能记住的后果：
> ⭐⭐⭐⭐⭐ **"一个⭐ 托管的组织策略，⭐ 会⭐ 静默覆盖⭐ 你昨天写的⭐ 项目规则。"**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 而 `/status` ⭐ 就是⭐ 告诉你⭐ 这件事正在发生的⭐ 那个命令。

## 4. ⭐⭐⭐⭐ 推荐的诊断顺序

```
① ⭐⭐⭐⭐⭐ /doctor     → 安装、设置、MCP
② ⭐⭐⭐⭐⭐ /context    → 确认什么真的加载了
③ ⭐⭐⭐⭐ 钻进子系统    → /skills /agents /hooks /mcp /permissions
④ ⭐⭐⭐⭐ /status      → 哪些设置源是活跃的
⑤ ⭐ /debug 或 claude --debug → Claude Code 本身的问题
```

> ⭐⭐⭐⭐⭐ 如果⭐ 以上都没查出原因，⭐ 官方给的答案⭐ 只有两句：
> ```
> ⭐⭐⭐⭐⭐ ① 某个东西⭐ 从⭐ 你预期之外的位置⭐ 加载了
> ⭐⭐⭐⭐⭐ ② ⭐ 更高的作用域⭐ 赢了
> ```
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这⭐ 恰好就是⭐ 三类问题里的⭐ 前两类——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ **兜底答案落在"加载"和"优先级"上，⭐ 而不是"描述"上。**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这⭐ 反过来印证了⭐ `skill-loading/references/four-layer-diagnosis-flow.md` 的 80/15/5：
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ **描述层只占 5%，⭐⭐⭐⭐⭐ ⭐⭐⭐ 别一上来就改它。**

**另外两条具体坑**（非技能但同源）：

```
· ⭐⭐⭐ hook 不触发：matcher 是⭐ 大小写敏感的——"edit" 不会命中 Edit
  ⭐⭐⭐⭐ hook 失败几乎总是四者之一：⭐ 文件没加载 / matcher 错 /
  ⭐⭐⭐ 脚本不可执行 / ⭐⭐⭐ 脚本有 bug
· ⭐⭐⭐⭐⭐ SessionEnd 清理不跑：⭐⭐⭐⭐⭐ ⭐ Claude ⭐ 不会自动跑清理，
  ⭐⭐⭐⭐⭐ ⭐⭐⭐ 必须⭐ 注册 SessionEnd hook；⭐⭐⭐ 想每轮跑就用 Stop hook
```

## 5. ⭐⭐⭐ 三条习惯

```
① ⭐⭐⭐⭐⭐  bookmark 这份目录——⭐⭐⭐⭐⭐ ⭐ 正确用法是"查"，不是"背"
② ⭐⭐⭐⭐⭐  ⭐ 主动跑 /doctor，⭐⭐⭐⭐⭐ ⭐⭐⭐ 而不是只在坏了才跑（一周一次足够）
   ⭐⭐⭐⭐ 理由：⭐⭐⭐⭐⭐ 在配置漂移⭐ 咬你之前⭐ 抓住它——小习惯，⭐ 不成比例的回报
③ ⭐⭐⭐⭐⭐  ⭐⭐⭐⭐⭐ 下次出问题，⭐ 先敲 /debug ——
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 在看日志之前、在搜文档之前、在开新终端之前
```

> ⭐⭐⭐⭐⭐ 第 ② 条⭐ 值得⭐ 单独强调：⭐ **"/doctor 是预防性的，不是治疗性的"**
> ⭐⭐⭐⭐ ——这跟 `skill-governance/references/skill-decay-governance.md` 的 `review_after`、
> `skill-governance/references/retirement-pipeline.md` 的定期审计⭐ 是⭐ 同一条纪律的⭐ 最短版本：
> ⭐⭐⭐⭐⭐ **对⭐ 静默失败的东西，⭐⭐⭐⭐⭐ ⭐ 唯一有效的对策是⭐ 定时去看它，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 因为⭐ 它不会自己报警。**

## 速查

```
□ ⭐⭐⭐⭐⭐ 三类收敛：⭐ 上下文加载 / ⭐ 优先级 / ⭐ 描述匹配 → ⭐ 说出哪一类，修法自现
   ⭐⭐⭐⭐⭐ ⭐ 兜底答案总落在前两类 → ⭐⭐⭐⭐⭐ ⭐⭐⭐ 别一上来改描述（描述层仅占约 5%）
□ ⭐⭐⭐⭐⭐ /context = ⭐ 占上下文的"全部"（含捆绑技能）；/skills = ⭐ 你能调哪些
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 两者不同，别互相印证
   ⭐⭐⭐⭐⭐ ⭐ 第一步永远是 /context：先确认"存在吗"，再谈"写得好吗"
□ ⭐⭐⭐⭐ 其余：/memory /hooks /mcp /permissions /status(哪些源活跃)
   ⭐⭐⭐⭐ /doctor(含建议修复，按 f 应用) · /debug(启用日志并让 Claude 自诊)
□ ⭐⭐⭐⭐⭐ 配置作用域：managed > local > project > user
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⚠️ 与技能覆盖顺序⭐ 不是一回事（技能：enterprise>personal>project）
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 托管组织策略会⭐ 静默覆盖⭐ 你昨天写的项目规则 → /status 能看见
□ ⭐⭐⭐⭐ 顺序：/doctor → /context → 钻子系统 → /status → /debug
□ ⭐⭐⭐ hook 不触发：matcher ⭐ 大小写敏感；失败四因 = 没加载/matcher错/不可执行/有bug
   ⭐⭐⭐⭐⭐ SessionEnd 清理必须自己注册 hook；想每轮跑用 Stop hook
□ ⭐⭐⭐⭐⭐ 习惯：⭐ 主动跑 /doctor（预防性，一周一次）；⭐⭐⭐⭐⭐ 出问题先敲 /debug
```

**一句话**：

> ⭐⭐⭐⭐ **几乎每个失败都归三类——上下文加载、优先级、描述匹配——说出是哪一类，修法就显而易见；而官方的兜底答案总落在前两类，所以诊断第一步永远是 `/context` 确认"它到底加载了没有"，而不是去改描述。**
