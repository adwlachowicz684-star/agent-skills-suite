## 1. ⭐⭐⭐⭐⭐ 精确边界：唯一需要重启的情况

先给结论：

> ⭐⭐⭐⭐⭐ **需要重启的只有一种：会话启动之后，顶层 skills 目录被新建。**

```
t0  会话启动（此时 ~/.claude/skills/ 不存在）
t1  你创建了 ~/.claude/skills/my-skill/SKILL.md
t2  当前会话看不到它 → ⭐ 需要重启
```

> ⭐⭐⭐⭐⭐ 这是⭐⭐⭐⭐ **目录级的发现**，不是文件级的加载。
> 扫描发生在会话启动时。

反过来，所有"改文件"的情况都实时生效：

```
✅ 已存在目录下新增一个技能目录      → 实时
✅ 修改 SKILL.md                     → 实时
✅ 修改 references/*.md              → 实时
✅ 增删 scripts/                     → 实时
```

> ⭐⭐⭐⭐⭐ 判据一句话：
> **"目录已存在" 是分界线。已存在的目录里改任何东西都实时生效；
> 会话启动后才新建的顶层目录需要重启。**

这也解释了为什么"改了要重启"这个说法会流传——
⭐⭐⭐⭐⭐ **第一次创建技能时确实要重启，而那是每个人都会遇到的一次。**
于是"第一次的经验"被泛化成了"每次都要"。

## 2. ⭐⭐⭐⭐⭐ 三种改动 × 三种生效时机

| 改动 | ⭐ 生效时机 | 判据 |
|---|---|---|
| ⭐⭐⭐⭐⭐ 改 SKILL.md / references | 下一次调用该技能时 | 正文是按需加载的 |
| ⭐⭐⭐⭐⭐ 改 description / name | ⭐⭐⭐⭐⭐ **下一次判断时** | 元数据常驻，但会被重新读取 |
| ⭐⭐⭐⭐ 新建顶层 skills 目录 | ⭐ 重启会话 | 目录扫描在启动时 |

三种混在一起，是"改了不生效"这个说法长期含糊的原因：

> ⭐⭐⭐⭐⭐ **同一个"改了"，三种时机完全不同。**
> 说"改了要重启"和说"改了不用重启"的人，
> ⭐⭐⭐⭐⭐ **改的可能根本不是同一类东西。**

一个推论（很实用）：

> ⭐⭐⭐⭐⭐ **改 description 的验证成本最低**——
> 不用重启、不用跑完整流程，
> ⭐⭐⭐⭐⭐ **直接问它"When would you use the X skill?"就能看到新版本。**

## 3. ⭐⭐⭐⭐⭐ 为什么"改了没生效"多是误判

按发生频率排，真正属于"没生效"的排在很后面：

**① ⭐⭐⭐⭐⭐ 你改的是另一个文件**

```
同名技能在两个层级都存在 → 你改了项目级，生效的是全局级
```

> ⭐⭐⭐⭐⭐ 这是最常见的一种，而它看起来完全像"改了没生效"——
> 因为文件确实改了，只是那份不是被加载的那份。
>
> ⭐⭐⭐⭐⭐ 关键：**覆盖顺序是"越宽泛越赢"，与"离得近更强"的直觉相反。**

**② ⭐⭐⭐⭐⭐ 嵌套目录作用域**

```
packages/frontend/.claude/skills/lint/
只在处理 frontend 下文件时可见
```

> ⭐⭐⭐⭐⭐ 你会以为是文件名/YAML 错了，查半天。
> 排障顺序应是：文件层检查通过 → **cd 到子目录再看** → 才轮到改 description。

**③ ⭐⭐⭐⭐⭐ YAML 静默失败**

```
格式错误 → 带空元数据加载正文
→ 手动 /skill-name 能用，自动调用永远不发生
```

> ⭐⭐⭐⭐⭐ 这一种是真正的"没生效"，但它表现为"能调用只是不自动触发"——
> 于是被当成描述问题。

**④ ⭐⭐⭐⭐ 触发了但走了别的路径**

```
（这是"假失灵"——内容已生效，是模型选了别的方法）
```

> ⭐⭐⭐⭐⭐ 区分方法：**重新显式调用一次。**
> 回来了 → 是真失忆/假失灵；没回来 → 才是加载问题。

**⑤ ⭐ 真的需要重启**

```
只有第 1 节那一种情况
```

> ⭐⭐⭐⭐⭐ 频率最低，但因为它"重启总有效"，
> 于是成了所有人的第一反应——
> 而⭐⭐⭐⭐⭐ 前四种重启都没用。

## 4. ⭐⭐⭐⭐⭐ 零成本的确认手段

按成本从低到高：

**① ⭐⭐⭐⭐⭐ 问它（最快）**

```
"When would you use the [skill name] skill?"
```

- 复述的根本不是你写的 → ⭐⭐⭐⭐⭐ **加载的不是这个文件**（覆盖/嵌套/缓存）
- 复述对但太笼统 → 描述不够具体
- 复述对 → ⭐⭐⭐⭐⭐ **已经生效了**，问题在触发竞争

> ⭐⭐⭐⭐⭐ 这一步同时回答了"生效了吗"和"为什么没触发"，
> 而重启只回答第一个，且更慢。

**② ⭐⭐⭐⭐ 让它列清单**

```
"What skills are available?"
```

> ⭐⭐⭐⭐⭐ 这是⭐⭐⭐⭐⭐ **读取实际生效列表**，
> 比读配置文件可靠——配置只说明"应该有什么"。

**③ ⭐⭐⭐⭐ 检查覆盖**

```
同名技能存在于几个层级？→ 宽泛的那个赢
```

> ⭐⭐⭐⭐ 这一步是第 3 节 ① 的直接检查，
> ⭐⭐⭐⭐⭐ 成本只有一次 `find`，却排除了最常见的一种。

## 5. ⭐⭐⭐⭐ 缓存与前缀：另一个"没生效"的来源

一个此前没和这个问题放在一起的机制：

> ⭐⭐⭐⭐ **提示缓存是一次前缀匹配。**
> 前缀里任何位置的改动，都会让它之后的所有内容失效。

反过来看——这也意味着：

```
⭐⭐⭐⭐ 你改了技能，但缓存里仍是旧前缀的一段
→ 表现：改了没生效（在长会话里更明显）
```

> ⭐⭐⭐⭐⭐ 与第 1 节的区别：
> 那是⭐⭐⭐ **发现**（目录扫不扫描），这是⭐⭐⭐⭐ **缓存**（内容刷不刷新）。

判据：

> ⭐⭐⭐⭐ **短会话里改了立刻生效、长会话里不生效** → 大概率是缓存，不是加载。
> ⭐⭐⭐⭐⭐ 而这时重启确实有效——
> **这解释了为什么"重启有效"这个经验如此顽固：它在这一类上真的有效。**

一个实践推论：

> ⭐⭐⭐⭐⭐ **验证改动效果时，用新会话。**
> 不是因为"改了要重启"，
> 而是⭐⭐⭐⭐⭐ **只有新会话才能保证你看到的是改动后的表现，
> 而不是缓存加改动的混合态。**

---

## 6. ⭐⭐⭐⭐⭐ 一句话结论

```
⭐⭐⭐⭐⭐ 改文件（正文/描述/参考/脚本）→ 实时生效，不需要重启
⭐⭐⭐⭐⭐ 会话中新建顶层 skills 目录     → 需要重启
⭐⭐⭐⭐⭐ 验证改动效果                   → 用新会话（为排除缓存，不是为生效）
```

> ⭐⭐⭐⭐⭐ 关键区分：**"让它生效"和"看清它的效果"是两件事。**
> 前者通常不需要重启，后者通常需要。
>
> ⭐⭐⭐⭐⭐ 而多数人说"改了要重启"的时候，
> 想表达的其实是⭐⭐⭐⭐⭐ **"我需要在干净环境里确认它真的变了"**——
> 这个需求是真实的，只是它被描述成了一个错误的机制。

---

## 一句可贴在墙上

> ⭐⭐⭐ **"让它生效"和"看清它的效果"是两件事。
> 前者通常不需要重启，后者通常需要。**
