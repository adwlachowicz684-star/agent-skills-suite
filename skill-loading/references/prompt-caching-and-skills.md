## 1. ⭐⭐⭐⭐⭐ 缓存是前缀匹配

> ⭐⭐⭐⭐⭐ **"⭐ 提示缓存⭐ 是一次⭐ 前缀匹配。
> ⭐⭐⭐⭐⭐ ⭐ 前缀里⭐ ⭐ 任何位置的⭐ 任何改动，⭐⭐⭐⭐⭐ ⭐⭐⭐ 都会让它⭐ 之后的所有内容⭐ 失效。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 围绕这个约束⭐ 设计你的整个系统。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ ⭐ 把顺序搞对，⭐⭐⭐⭐⭐ ⭐⭐⭐ 大部分缓存⭐ 就是免费的。"**

```
缓存命中的前提：⭐ 请求的前缀 ⭐ 与 ⭐ 已缓存的 ⭐ ⭐ 从第一个字节起 ⭐ 完全一致
```

> ⭐⭐⭐⭐⭐ 这条⭐ 之所以⭐ 此前⭐ 没人⭐ 把它⭐ 和技能⭐ 联系起来，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 是因为⭐ 我们⭐ 一直在⭐ 算 ⭐ "技能占多少 token"——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐ **而缓存破坏的代价⭐ 不是 ⭐ 技能本身的大小，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 而是 ⭐ 它⭐ 之后⭐ 所有内容的⭐ 重算成本。**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 一次⭐ 技能触发⭐ 如果⭐ 破坏了前缀，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 代价⭐ 是 ⭐ 整段对话历史 ⭐ 按 ⭐ 非缓存价 ⭐ 重新计费。

## 2. ⭐⭐⭐⭐⭐ 会话中途增删工具是最常见的破坏方式

> ⭐⭐⭐⭐⭐ **"⭐ 在对话中途⭐ 改变工具集 ⭐ 是⭐ 人们⭐ 破坏提示缓存⭐ 最常见的⭐ 方式之一。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 它⭐ 看起来⭐ 很直觉——⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 你⭐ 应该⭐ 只给模型⭐ 它此刻⭐ 需要的工具。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐ **但⭐ 因为⭐ 工具⭐ 属于⭐ 已缓存的前缀，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ ⭐⭐⭐⭐ 中途⭐ 增加或移除⭐ 一个工具，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐ 会让⭐ 整段对话的⭐ 缓存失效。**"**

**这与技能的直接关系**（本轮最重要的一条推论）：

```
⭐⭐⭐⭐⭐ 技能可以声明 allowed-tools / disallowed-tools
⭐⭐⭐⭐⭐ ⭐ 官方文档明确：
   "⭐⭐⭐⭐⭐ ⭐ 只要⭐ 你 ⭐ 或 Claude ⭐ 调用了该技能，
    ⭐⭐⭐⭐⭐ ⭐⭐⭐ Claude Code ⭐ 就会⭐ 应用⭐ 该技能的 allowed-tools"
⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐⭐ → ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ **触发技能 = 中途改变工具集 = 缓存失效**
```

> ⭐⭐⭐⭐⭐ 这条⭐ 解释了一个⭐ 此前⭐ 无法解释的⭐ 现象：
> ⭐⭐⭐⭐⭐ **为什么⭐ 有人⭐ 观察到⭐ "装了很多带 allowed-tools 的技能之后，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 长会话的⭐ 成本⭐ 出现了⭐ 不合比例的⭐ 上升"。**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 我们此前⭐ 记的⭐ 解释⭐ 是"⭐ 技能内容常驻"（`three-tier-token-math`），
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 但⭐ 那⭐ 只是⭐ 线性成本；
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ **缓存失效⭐ 是⭐ 阶跃的——⭐⭐⭐⭐⭐ ⭐⭐⭐ 一次触发，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐ 整段历史⭐ 重新计费。**
>
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ **这就是"技能加载⭐ 不是⭐ 一次性开销"的⭐ 真正机制**
> （此前 `context-budget-math.md` 只观察到现象，⭐⭐⭐⭐⭐ ⭐⭐⭐ 这里⭐ 给出了⭐ 原因）。

**顺带一条安全提示**（官方原话）：

> ⭐⭐⭐⭐ **"⭐ 一个技能⭐ 可以⭐ 给自己⭐ 授予⭐ 很宽的工具权限，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 所以⭐ 在⭐ 你⭐ 从未信任过的⭐ 文件夹里⭐ 运行之前，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 先⭐ 审查⭐ 签入该仓库的⭐ 技能的 allowed-tools。"**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 并且⭐ 官方特意⭐ 强调：⭐⭐⭐⭐⭐ **工作区信任⭐ 不 gate 这个字段**
> （`allowed-tools` ⭐ 不受⭐ 工作区信任⭐ 约束）——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这⭐ 与 `allowed-tools-least-privilege.md` 的
> "⭐ 声明摄入→权限强制→运行时隔离"⭐ 三层⭐ 完全吻合。

## 3. ⭐⭐⭐⭐⭐ 用工具建模状态转换，而不是改工具集

官方举的例子本身就是这条原则的完美演示：

```
⭐ 直觉做法（错）：⭐⭐⭐⭐⭐ 用户进入 Plan Mode 时，⭐ 把工具集换成只读工具
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ → ⭐⭐⭐⭐⭐ ⭐⭐⭐ 破坏缓存

⭐⭐⭐⭐⭐ 实际做法（对）：⭐⭐⭐⭐⭐ ⭐ 始终⭐ 在请求里⭐ 保留⭐ 全部工具，
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 用 ⭐ EnterPlanMode / ExitPlanMode ⭐ 这两个⭐ 工具本身 ⭐ 来表示状态
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 用户切换时，⭐⭐⭐⭐⭐ ⭐⭐⭐ agent ⭐ 收到一条⭐ 系统消息，
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 告诉它现在处于 Plan Mode 及规则
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐⭐ → ⭐⭐⭐⭐⭐ ⭐⭐⭐ **工具定义从未改变**
```

> ⭐⭐⭐⭐⭐ 额外收益（官方点出）很妙：
> ⭐⭐⭐⭐ **"⭐ 因为 EnterPlanMode ⭐ 是⭐ 模型⭐ 可以自己调用的⭐ 工具，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 它⭐ 可以在⭐ 检测到⭐ 难题时⭐ 自主进入 plan mode，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐⭐ 且⭐ 完全不破坏缓存。"**
>
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 抽象出来就是：
> ⭐⭐⭐⭐⭐ **"⭐ 用工具⭐ 建模状态转换，⭐⭐⭐⭐⭐ ⭐⭐⭐ 而不是⭐ 通过⭐ 改变工具集。"**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐⭐ 这⭐ 与⭐ 我们已有的⭐ `determinism-boundary.md`
> "⭐ Hooks 用于⭐ 模型⭐ 不可被信任⭐ 去遵守的事"⭐ 是⭐ 同一族：
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ **状态⭐ 应该用⭐ 有强制力的⭐ 机制承载，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 而不是⭐ 靠⭐ 改配置 / 靠模型自觉。**

## 4. ⭐⭐⭐⭐⭐ 延迟加载，而不是移除

```
问题：⭐⭐⭐ 几十个 MCP 工具 ⭐ 全部 ⭐ 放进每次请求 ⭐ 太贵；
      ⭐⭐⭐⭐⭐ ⭐ 但 ⭐ 中途移除 ⭐ 会破坏缓存

⭐⭐⭐⭐⭐ 解法：defer_loading
   ⭐⭐⭐⭐⭐ ⭐ 发送⭐ 轻量桩（只有工具名 + defer_loading: true）
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ 模型⭐ 需要时⭐ 通过⭐ 工具搜索⭐ "发现"它们
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 完整 schema ⭐ 只在⭐ 模型选中时⭐ 才加载
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ **缓存前缀保持稳定，⭐⭐⭐⭐⭐ ⭐⭐⭐ 因为⭐ 同样的桩⭐ 总是
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 以同样的顺序⭐ 出现**
```

> ⭐⭐⭐⭐⭐ 这⭐ 与 `skill-vs-mcp-two-layers.md` 那条
> "⭐ 每个已连接 MCP 服务器的工具定义⭐ 加载进每一次请求"⭐ 是⭐ 同一个⭐ 问题的⭐ 两面：
> ```
> 问题：MCP 工具定义常驻 → 贵
> ⭐⭐⭐⭐⭐ 解法：⭐⭐⭐⭐⭐ ⭐⭐⭐ 桩 + 按需搜索（不是移除）
> ```
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 而且⭐ 它⭐ 与 ⭐ 技能的⭐ 三级加载⭐ 是⭐ **完全同构的设计**：
> ```
> 技能：⭐⭐⭐⭐⭐ 常驻 description（桩）→ ⭐ 触发时加载正文（完整 schema）
> MCP ：⭐⭐⭐⭐⭐ 常驻工具名桩       → ⭐ 选中时加载完整定义
> ```
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ ⭐⭐⭐⭐⭐ **两个标准⭐ 各自独立地⭐ 收敛到了⭐ 同一个答案
> （渐进式披露），⭐⭐⭐⭐⭐ ⭐⭐⭐ 而且⭐ 都⭐ 是为了⭐ 同一个原因：⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 保住前缀。**

## 5. ⭐⭐⭐⭐⭐ Fork 必须共享父前缀

这一段是本份文档⭐ 技术含量⭐ 最高、⭐⭐⭐⭐⭐ ⭐⭐⭐ 也最⭐ 反直觉的⭐ 部分。

```
⭐⭐⭐⭐⭐ 朴素做法（错）：
   压缩时 ⭐ 另起一次 API 调用，⭐⭐⭐⭐ ⭐ 用 ⭐ 自己的 system prompt（如"总结这段对话"）
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ ⭐⭐⭐ 且 ⭐ 不附带工具
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ → ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ **前缀从第一个 token 起就分叉，
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐⭐ 一点缓存都用不上**

⭐⭐⭐⭐⭐ 正确做法（cache-safe forking）：
   ⭐⭐⭐⭐⭐ ⭐ 使用 ⭐ 与父会话 ⭐ 完全相同的
      ⭐ system prompt · ⭐ user context · ⭐ system context · ⭐ 工具定义
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ 前置 ⭐ 父会话的消息，⭐⭐⭐⭐⭐ ⭐⭐⭐ 末尾 ⭐ 追加 ⭐ 压缩提示 ⭐ 作为新的用户消息
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ → ⭐⭐⭐⭐⭐ ⭐⭐⭐ **从 API 看，⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 这次请求
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 与父会话的最后一次请求⭐ 几乎完全相同
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 唯一的新 token ⭐ 就是⭐ 压缩提示本身**
```

> ⭐⭐⭐⭐⭐ 官方那句⭐ 点出了⭐ 这个陷阱的⭐ 残酷之处：
> ⭐⭐⭐⭐⭐ **"⭐ 对话⭐ 越长，⭐⭐⭐⭐⭐ ⭐⭐⭐ 那一次调用⭐ 就越贵——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐⭐ 而⭐ 对话长⭐ 恰恰⭐ 正是⭐ 你需要压缩的⭐ 原因。"**
>
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 对技能的推论（一条⭐ 此前完全没写过的⭐ 设计约束）：
> ⭐⭐⭐⭐⭐ **"⭐ 如果你⭐ 需要跑⭐ 一个旁路计算
> （压缩、摘要、⭐⭐⭐⭐⭐ ⭐⭐⭐ 技能执行），
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 就⭐ 用⭐ 完全一致的⭐ cache-safe 参数，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 这样⭐ 才能⭐ 命中⭐ 父前缀的缓存。"**
>
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 注意⭐ 官方⭐ 把 ⭐ **"技能执行"**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 与 ⭐ 压缩、摘要 ⭐ 并列，⭐⭐⭐⭐⭐ ⭐⭐⭐ 都归为
> ⭐⭐⭐⭐⭐ **"旁路计算（side computation）"**——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 这⭐ 说明 ⭐ `context: fork` 的技能
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 在⭐ 官方模型里⭐ 就是⭐ 一次 fork 调用，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 因此⭐ 同样适用⭐ 这条缓存规则。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 这⭐ 与 `fork-token-economics.md` 那份
> （⭐ 主上下文成本零、fork 内仍加载完整正文）⭐ 是⭐ 互补的：
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ **那份算 token，⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 这份算缓存。**

**还有一个工程细节**：⭐⭐⭐ 需要预留"压缩缓冲区"，
⭐⭐⭐⭐ 保证上下文窗口里有足够空间⭐ 放下压缩消息 + 摘要输出 token。

## 速查

```
□ ⭐⭐⭐⭐⭐ 缓存是前缀匹配：⭐ 前缀任何位置的任何改动 → ⭐ 之后全部失效
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ 技能触发若改变工具集 = ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 整段对话历史按非缓存价重算（阶跃，非线性）
□ ⭐⭐⭐⭐⭐ allowed-tools 是缓存事件，不只是权限边界
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 官方：⭐ 只要调用了技能就应用其 allowed-tools；⭐⭐⭐⭐⭐ ⭐⭐⭐ 工作区信任不 gate 此字段
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ → ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这解释了"技能加载不是一次性开销"的真正机制
□ ⭐⭐⭐⭐⭐ 用工具建模状态转换（EnterPlanMode/ExitPlanMode），不是改工具集
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ 附加收益：⭐ 模型可自主进入该状态且不破坏缓存
□ ⭐⭐⭐⭐⭐ 延迟加载而非移除：⭐ 常驻轻量桩 + ⭐ 按需搜索加载完整 schema
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 与技能三级加载完全同构——⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 两个标准独立收敛到渐进式披露，⭐⭐⭐⭐⭐ ⭐⭐⭐ 都是为了保住前缀
□ ⭐⭐⭐⭐⭐ Fork 要共享父前缀：⭐ 同 system prompt/context/工具定义 + ⭐ 前置父消息 + ⭐ 末尾追加提示
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐ 陷阱：⭐⭐⭐⭐⭐ ⭐ 朴素压缩(自己的system prompt+无工具)⭐ 一点缓存都用不上，⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 且对话越长越贵
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 官方把"技能执行"与压缩、摘要并列为旁路计算 → ⭐⭐⭐⭐⭐ ⭐⭐⭐ 同样适用
□ ⭐⭐⭐⭐⭐ 像监控可用性一样监控缓存命中率，⭐ 缓存破坏设告警并当事故处理
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 几个百分点差异就能极大影响成本与延迟
□ ⭐⭐⭐⭐ 四条推论：谨慎声明 allowed-tools · ⭐⭐⭐⭐⭐ ⭐⭐⭐ 用消息承载变化而非改 system prompt
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ 不要中途换模型（⚠️ 与"简单步用小模型"冲突：⭐ 只在 fork 旁路里换）· ⭐⭐⭐⭐⭐ ⭐⭐⭐ 顺序对了缓存就基本免费
```

**一句话**：

> ⭐⭐⭐⭐ **提示缓存是前缀匹配——技能一旦带 `allowed-tools`，触发它就是在会话中途改变工具集，会让整段对话历史的缓存失效并按非缓存价重算；所以 allowed-tools 不只是权限边界，它还是一次缓存事件，而缓存命中率要像可用性一样设告警。**
