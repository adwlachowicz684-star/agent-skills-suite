## 1. ⭐⭐⭐ 先分诊：误触发 vs 漏触发

**两种病，症状相反，修法相反**：

```
⭐⭐ 误触发（false trigger）
   你说 "clean up this code"
   ⭐ PR review 技能触发了，而不是 refactor 技能
   ⭐ 两个 description 都写了 "Use when improving code quality"
   → ⭐ 模型读到两个都像，选错了

⭐⭐ 漏触发（misfire）
   你说 "set up cron scheduling"，什么都没触发
   ⭐ 你的 Tokio cron 技能 description 写的是
      "Use when implementing async scheduling with Tokio timers"
   ⭐⭐ 你没说 Tokio → ⭐ description 太具体
   → ⭐ 模型觉得不匹配
```

| | 症状 | 根因 | 修法 |
|---|---|---|---|
| 误触发 | 错的技能被调用 | ⭐ 语义重叠 / 太宽 | 加反触发、点名排除 |
| 漏触发 | 没有技能被调用 | ⭐⭐ 太具体 / 缺用户实际用词 | 补同义说法、降具体度 |

> ⭐⭐⭐ 这个分叉必须先做——**修法方向相反**，
> 如果没分清就开始改 description，很可能把误触发越改越宽，或把漏触发越改越窄。

**三个具体症状对应的修法**（来自另一处实践总结）：

```
输出错但触发对  → 指令要更紧，或反触发要⭐ 显式点出漂移方向
触发对但形状错  → ⭐ 正文里的示例要更具体
```

## 2. ⭐⭐ 10 个技能之后，误触发是主要维护负担

> ⭐⭐ **一旦你有超过 10 个技能，⭐⭐⭐ 误触发和漏触发⭐ 不再是边缘情况，
> ⭐ 它们就是⭐ 主要的维护负担。**

```
⭐⭐ 两个 description 语义重叠就会冲突：
   错的那个触发，或者请求稍微不常见时两个都不触发
```

> ⭐⭐⭐ 这条给了"什么时候该开始治理"一个具体门槛：**10 个技能**。
> 此前我们收集过"50 个技能上 embedding 两步路由"、
> "库规模导致遮蔽"——
> 现在这条补上了最早的那一档：**10 个就开始疼了，别等到 50 个。**

## 3. ⭐⭐ 调优循环四步

```
① ⭐ 生成带标签的查询
   分析当前 description，生成 20 条：
   ⭐ 10 条应该触发 + 10 条不应该触发
   ⭐⭐ 这些查询是用来⭐ 测试 description 的语义边界的

② ⭐⭐ 在 HTML UI 里人工审阅
   20 条以表格呈现，你逐条审阅并⭐ 纠正标错的
   ⭐⭐⭐ 领域知识就是在这里进入的：
        你知道哪些查询应该触发、哪些不该

③ ⭐ 迭代改写 description
   run_loop 脚本最多跑 ⭐ 5 轮
   每轮重写 description 并对这批标签查询测试

④ ⭐ 测准确率
```

> ⭐⭐ 第 ② 步是整套流程里**唯一无法自动化的一步**，也正因如此最关键：
> **"应该触发"这件事只有你知道。**
> 让模型自己生成又自己判断，就退化成了
> `eval-roles.md` 警告过的"让模型给自己作业打分"。

## 4. ⭐⭐⭐ 生成的查询首先是诊断

> ⭐⭐⭐ **生成的查询首先是诊断工具。**
> ⭐⭐ 如果你看"应该触发"那批，觉得有些条目不对——
> ⭐⭐⭐ **那就是一个信号：你的 description 要么太宽，
> 要么⭐ 把技能的用途描述错了。**

> ⭐⭐⭐ 这是这份材料里最反直觉的一条：
> **通常我们认为"生成的测试集"是用来评估技能的，
> 但这里它首先是在评估⭐ 你对技能的定义**。
>
> ⭐ 换句话说：**如果你不同意这批测试，先别急着改测试——
> 先想想是不是 description 写歪了。**
>
> 这与 `description-scope-shape.md` 那条
> "写不出三条反触发条件，说明我对范围理解得还不够"
> 是同一个思想的另一个出口：
> ⭐ **写不出/看不中，都说明定义还没想清楚。**

## 5. ⭐⭐ 迭代到第十轮说明什么

```
⭐⭐ 3–5 轮迭代是正常水平（一个打磨好的技能）
⭐⭐⭐ 如果你在第 10 轮还在追边缘情况
   → ⭐⭐ 范围多半太宽了 → ⭐ 回到"要不要拆"那个问题
```

> ⭐⭐⭐ 又一条"迭代次数暴露了上游问题"的经验法则。
> 与此前收集到的同类判据排队：
>
> ```
> · 修改超过 10 次，或连续 3 次增量改动没解决 → 重构
> · 提示词复制 2 次以上 → 升为技能
> · 技能输出手动搬运 3 次以上 → 升为编排器
> · ⭐⭐ 触发调优超过 5 轮 → ⭐ 范围太宽，该拆
> ```
>
> ⭐ 共同模式：**迭代次数不是努力的度量，是⭐ 结构问题的探测器。**

## 速查

```
□ ⭐⭐⭐ 先分诊：
   误触发 = 错的技能被调用 → 语义重叠/太宽 → 加反触发、点名排除
   漏触发 = 没技能被调用 → ⭐ 太具体/缺用户实际用词 → 补同义说法
□ 输出错触发对 → 指令更紧/反触发点出漂移方向
   触发对形状错 → ⭐ 正文示例更具体

□ ⭐⭐⭐ ⭐ 超过 10 个技能，误触发就是主要维护负担（别等 50 个）

□ ⭐⭐ 循环：生成 20 条（10 应触发/10 不应）→ ⭐⭐ 人工审阅纠正
   → 最多 5 轮改写 → 测准确率
□ ⭐⭐⭐ ⭐ 领域知识在审阅那步进入（"应该触发"只有你知道）
□ ⭐⭐⭐ ⭐ 生成的查询首先是诊断：
   你不同意"应触发"那批 → ⭐ description 太宽或写歪了
□ ⭐⭐ 3–5 轮正常；⭐⭐⭐ 第 10 轮还在追边缘 → ⭐ 范围太宽该拆

□ ⭐ 迭代次数是结构问题的探测器，不是努力的度量
```

**一句话**：

> ⭐⭐⭐ **误触发（太宽）和漏触发（太具体）修法方向相反，必须先分诊；
> 而调优时生成的那批查询首先是诊断——
> 如果你看"应该触发"的条目觉得不对，那是 description 写歪了的信号，
> 不是测试集的问题。**
