## 1. ⭐⭐⭐ 四类问题诊断表

收集 10–20 条真实说法后，按四类归类：

| 症状 | ⭐ 根因 | ⭐ 改哪里 |
|---|---|---|
| ⭐⭐⭐ 应触发但没触发 | ⭐⭐ description ⭐ 缺少意图词或场景词 | description |
| ⭐⭐⭐ 不应触发但触发了 | ⭐⭐ description ⭐ 太宽或⭐ 缺少边界 | description |
| ⭐⭐ 触发了但没帮助 | ⭐⭐⭐ ⭐ 正文质量不足 | ⭐ 正文 |
| ⭐⭐⭐ 触发后反而变差 | ⭐⭐⭐ 技能⭐ 与当前上下文冲突 · ⭐ 过时 · ⭐⭐ 过度规定 | ⭐⭐ 可能是**不该用技能** |

> ⭐⭐⭐ 这张表的价值在于⭐ **第四类**——它把"触发了但更差"
> 从"技能质量问题"重新归类为⭐ **"也许这里不该用技能"**。
>
> ⭐⭐ 这与 `worth-skillifying.md` 的"不该封装的被封装 → 制造伪稳定"、
> `outgrowth-regression-detection.md` 的"被追上 → 归档"是同一件事的
> ⭐⭐⭐ 第三个说法，但这里⭐ **给了一个可观察的入口症状**：
> ⭐⭐⭐ **"触发后反而变差" = 该检查这个技能是否还该存在。**
>
> ⭐ 三类改法完全不同：前两类改描述，第三类改正文，
> ⭐⭐⭐ 第四类⭐ 改的可能是"要不要留着它"。
> **不分清就动手，最常见的结果是改描述改了半天，问题是第四类。**

## 2. ⭐⭐ 改 description 的正确问法

> ⭐⭐⭐ **不要只加关键词。**

正确问法是三个：

```
① ⭐⭐ 哪些⭐ 用户意图应该命中
② ⭐⭐⭐ 哪些⭐ 近似场景不应该命中
③ ⭐⭐⭐ 哪些⭐ 隐式表达也要命中（同义说法、口语、错别字）
```

> ⭐⭐⭐ 第 ③ 条"隐式表达"对应 `trigger-tuning-loop.md` 的
> "漏触发根因 = 缺⭐ 用户实际用词"——
> ⭐⭐ 关键词是你以为他会说的，⭐ 隐式表达是他真的会说的。

## 3. ⭐⭐ 六步迭代

```
① ⭐⭐ 收集真实任务（10–20 条用户可能说的话）
② ⭐⭐⭐ ⭐ 按四类问题归类（见上表）
③ 定位根因
④ ⭐⭐ 修改 description（三个问法）
⑤ ⭐⭐⭐ 测试⭐ 输出质量（不只是命中）
⑥ ⭐⭐⭐ ⭐ 版本化
```

**第 ⑥ 步"把技能当代码管理"的四件事**：

```
· ⭐⭐ 修改原因写入 commit
· ⭐⭐⭐ ⭐ 保留评估样本
· ⭐⭐⭐ 记录命中率和误触发率
· ⭐⭐⭐ ⭐ 重要变更做回归测试
```

> ⭐⭐⭐ "保留评估样本"这条最容易被漏——
> 你改了一版描述，三个月后想比较，
> ⭐ 却发现当初那 20 条查询找不到了。
> ⭐⭐ 于是"命中率"变成一个⭐ 没有基准的数字。

## 4. ⭐⭐⭐ 五类技能各自的重点

**高风险命令类**（GitHub PR 处理 · Jira 工单更新 · 云平台部署）

```
⭐⭐⭐ ⭐ 加确认规则
```

**领域知识类**（公司业务 · 金融指标 · 医学流程 · 行业术语）

```
⭐⭐⭐ ⭐ 避免百科化——⭐⭐⭐ 只放 agent ⭐ 容易不知道或⭐ 容易误解的领域规则
⭐⭐ 把大知识库拆成 references
⭐⭐ 增加引用与来源要求
```

> ⭐⭐⭐ "只放容易误解的"精炼了我们一直说的
> "不要写模型已经知道的信息"——
> ⭐⭐⭐ **判据更准了：不是"它知不知道"，而是⭐ "它会不会搞错"。**
> 模型"知道"但经常搞错的东西，恰恰最该写进去。

**⭐⭐⭐ 纪律约束类**（TDD · 验证后再宣称完成 · 安全审批 · 调试流程）

```
⭐⭐ 明确硬门槛
⭐⭐⭐ ⭐ 写⭐ 红旗信号
⭐⭐⭐ ⭐ 写⭐ 常见借口和反驳
⭐⭐⭐ ⭐ 用⭐ 压力场景测试是否还会遵守
```

> ⭐⭐⭐⭐ **"这种技能⭐ 最容易被 agent '理性化绕过'，
> ⭐⭐⭐ ⭐ 所以要比普通技能⭐ 更强硬。"**
>
> ⭐⭐⭐ 这是本份最有价值的一条，且给出了⭐ 具体对策——
> **写"常见借口和反驳"**（即 anti-rationalizations 表），
> 以及⭐⭐ **"用压力场景测试是否还会遵守"**
> （对应 `skill-type-testing.md` 的"Discipline 类要在时间压力下再审一次"）。

## 5. ⭐⭐ 测什么：不只是命中

> ⭐⭐⭐ **命中只是第一步。**

七项比较维度：

```
有技能 vs 无技能
新版本 vs 旧版本
⭐ 成功率
⭐⭐ token 成本
⭐⭐ 执行时长
⭐⭐⭐ 工具调用是否更准确
⭐⭐⭐ ⭐ 人工修改量是否减少
```

> ⭐⭐⭐ 最后一项"⭐ 人工修改量"值得单独记——
> 它是⭐ 唯一一个直接衡量"人是否省事了"的指标，
> ⭐⭐ 其余六项都是过程指标。
>
> ⭐⭐ 与我们已有的 `roi-breakeven.md`（B / S×N）、
> `adoption-metrics.md`（先行/滞后指标）互补：
> 那两份是⭐ 组织级，这七项是⭐ 单次迭代级。

## 速查

```
□ ⭐⭐⭐ 四类诊断：应触发没触发→缺意图词 · 不该触发触发了→太宽/缺边界
   ⭐⭐ 触发了没帮助→⭐ 正文质量 · ⭐⭐⭐ 触发后反而变差→⭐ 可能"不该用技能"
   ⭐⭐⭐ ⭐ 第四类常被误当成"描述没写好"，改半天无效

□ ⭐⭐ 改描述三问：该命中哪些意图 · ⭐⭐⭐ 哪些近似场景不该命中 · 哪些隐式表达也要命中
□ ⭐⭐⭐ 六步：收集 → 归类 → 定位 → 改描述 → ⭐ 测输出质量 → ⭐ 版本化
   ⭐⭐⭐ 版本化四件事：commit 写原因 · ⭐⭐⭐ 保留评估样本 · 记录命中率/误触发率 · 回归测试

□ ⭐⭐⭐ 五类重点：高风险加确认 · ⭐ 领域知识避免百科化（⭐⭐⭐ 只放"容易搞错"的）
   ⭐⭐⭐⭐ 纪律约束类⭐ 最容易被"理性化绕过"→ ⭐ 写红旗信号 + ⭐ 常见借口和反驳
            + ⭐⭐ 用压力场景测是否还遵守

□ ⭐⭐ 七项比较，⭐⭐⭐ 最后一项"人工修改量是否减少"是唯一直接衡量人省事与否
```

**一句话**：

> ⭐⭐⭐ **先分清四类问题再动手——"触发后反而变差"往往意味着这个技能不该存在，常被误当成描述没写好而白改半天；
> 而纪律约束型技能最容易被"理性化绕过"，对策是写红旗信号与常见借口反驳，并用压力场景测试它是否还遵守。**
