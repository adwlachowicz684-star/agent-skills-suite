## 1. ⭐⭐⭐⭐⭐ 一个越测越好的死循环

```
1. 写完技能 → 让 Claude 生成 20 条评测查询
2. 调整描述直到 20 条全过
3. 上线，实际触发率 40%
```

> ⭐⭐⭐⭐⭐ 第 2 步的 100% 是真的——⭐⭐⭐⭐⭐ 但它描述的是
> **"技能与一组由它自己参与生成的查询之间的契合度"**，不是泛化能力。

这是本份的起点：**评测集不是中立的尺子，它也是被造出来的东西。**

---

## 2. ⭐⭐⭐⭐⭐ 四种污染，按隐蔽度排

**① ⭐⭐⭐⭐ 用同一个模型生成查询和跑测试**（最常见）

```
生成查询时，模型用的是"它认为这个技能会被怎么叫"的直觉
跑测试时，同一个模型用同一套直觉去匹配
→ ⭐⭐⭐⭐⭐ 两边同源，匹配率天然偏高
```

**② ⭐⭐⭐⭐⭐ 看着技能写查询**（更隐蔽）

```
"读一下这个技能，帮我写 20 条应该触发它的 query"
→ ⭐⭐⭐⭐⭐ 生成的查询会**复述描述里的用词**
→ 而触发匹配正是基于用词 → 测的是"描述能不能匹配它自己的措辞"
```

> ⭐⭐⭐⭐⭐ 这条与《skill-examples》的 `example-values-become-defaults.md`
> 是同一个机制的两面：⭐⭐⭐⭐ 那份讲示例值被复制成默认值，
> ⭐⭐⭐⭐⭐ 这份讲**描述里的措辞被复制成查询里的措辞**——
> 于是匹配必然成功。

**③ ⭐⭐⭐⭐⭐ 用技能的输出反推期望结果**

```
跑一次 → 看输出不错 → 把它存成 golden
→ ⭐⭐⭐⭐⭐ 从此这个用例永远通过（除非输出变了）
→ ⭐⭐⭐⭐⭐ 而"输出变了"包括"变好了"
```

> ⭐⭐⭐⭐⭐ 这条最致命：⭐⭐⭐⭐⭐ **golden 从"期望"退化成"现状"**，
> 于是任何改进都表现为"回归"。

**④ ⭐⭐⭐⭐ 只保留通过的用例**

```
跑 20 条 → 15 条过 → 留下这 15 条，说"通过率 75%"
（或更糟：删掉失败的 5 条，说"通过率 100%"）
```

## 3. ⭐⭐⭐⭐⭐ 为什么分数只会涨不会跌

三种污染共同产生一个方向性偏差：

```
⭐⭐⭐⭐⭐ 污染让分数**系统性偏高**，且偏高程度随迭代次数增加
```

机制：

```
每次按评测结果改技能 → 技能更贴合评测集
→ 评测集（由旧版技能参与生成）与新版技能更契合
→ ⭐⭐⭐⭐⭐ 分数上升，而真实触发率不变甚至下降
```

> ⭐⭐⭐⭐⭐ 这解释了一个常见困惑：⭐⭐⭐⭐ "触发率从 60% 调到 95%，
> 为什么线上还是不触发？"
> ⭐⭐⭐⭐⭐ 因为那 35% 的增益全部来自"评测集与技能的同源性"。

与已有结论的连接：

```
· "一份长期 100% 通过的测试集不是好消息"（已有）
  → ⭐⭐⭐⭐⭐ 本份给出成因之一：它可能是被污染的
· "定期把技能改坏一次，测试集不报警说明坏的是测试集"（已有）
  → ⭐⭐⭐⭐⭐ 本份补充：改坏还不报警，通常就是同源污染
```

## 4. ⭐⭐⭐⭐⭐ 判据：这份查询是"捞来的"还是"想出来的"

一句可执行的判据：

> ⭐⭐⭐⭐⭐ **每条查询能不能指出它来自哪一次真实使用？**

```
能（"这是 3 月 12 日小李在群里问的"）→ ⭐⭐⭐⭐⭐ 干净
不能（"我觉得用户可能会这么说"）      → ⭐⭐⭐⭐⭐ 污染
```

三类来源，按可信度排：

```
① ⭐⭐⭐⭐⭐ 真实记录：聊天记录、工单、搜索框、支持邮箱
② ⭐⭐⭐⭐ 真实记录的**变体**：改了术语、加了错字、换了说法
③ ⭐⭐⭐ 模型生成的近命中（用于补负例，⭐⭐⭐⭐⭐ 不能用于正例主体）
```

> ⭐⭐⭐⭐⭐ 第 ③ 条要写清楚：⭐⭐⭐⭐ 负例用"近命中"是官方推荐做法，
> ⭐⭐⭐⭐⭐ 但**正例用模型生成就是污染**——
> 因为负例的目的是测"会不会误触发"（模型生成偏难也可以接受），
> 而正例的目的是测"真实用户能不能触发"（必须由真实分布决定）。

一个可操作的中间态（没有真实记录时）：

> ⭐⭐⭐⭐⭐ **让模型生成，然后人必须改掉里面的术语**
> ——把"生成变更日志"改成"这次上线又出问题了"。
> ⭐⭐⭐⭐⭐ 判据：⭐⭐⭐⭐ **查询里不应该出现技能描述里的原词。**

## 5. ⭐⭐⭐⭐⭐ 修法一：来源标注

成本极低，收益是把污染变成**可见的状态**：

```yaml
- query: "这次上线又出问题了"
  expect: trigger
  source: real          # real | variant | generated
  origin: "2026-03-12 支持群"
```

三条要求：

```
① ⭐⭐⭐⭐⭐ 每条用例必须有 `source` 字段
② ⭐⭐⭐⭐⭐ 报告分数时**按 source 分组**，不报总分
③ ⭐⭐⭐⭐⭐ `generated` 占比 > 30% 时，该分数不足以支撑发布决策
```

> ⭐⭐⭐⭐⭐ 第 ② 条是关键：⭐⭐⭐⭐ 混在一起报，污染就继续隐形；
> ⭐⭐⭐⭐⭐ 分开报，"real 上 62%、generated 上 98%"会立刻说明问题。

顺带解决一个已有痛点：

```
"用反映你真实使用的脏输入，不是干净样例"（已有）
→ ⭐⭐⭐⭐⭐ `source: real` 就是这条的**可执行形式**
```

## 6. ⭐⭐⭐⭐⭐ 修法二：留置集

这是本份最结构性的一条：

```
切出 20% 用例 → 调优期间**完全不许看** → 只在最终决策时跑一次
```

> ⭐⭐⭐⭐⭐ 它与训练/测试切分同源，但技能场景有个额外理由：
> ⭐⭐⭐⭐⭐ **人会不自觉地按评测结果改描述，于是"测试集"在迭代中
> 事实上变成了训练集**——留置集是唯一没有被改过的尺子。

三条纪律：

```
① ⭐⭐⭐⭐⭐ 留置集在切分时就固定，之后不得增删改
② ⭐⭐⭐⭐⭐ 调优期间只报训练集分数（并标注）
③ ⭐⭐⭐⭐⭐ 最终按留置集分数决策——按训练集分数选就是过拟合
```

> ⭐⭐⭐⭐⭐ 第 ③ 条正是官方调优循环的那句（按测试集选而非训练集），
> 这里补上了**为什么在技能场景特别容易违反**：
> ⭐⭐⭐⭐⭐ 因为技能只有 1024 字符的描述，它比 prompt 更容易
> 被"针对这 20 条查询"精确调过。

一个廉价替代（没有留置集时）：

> ⭐⭐⭐⭐⭐ **每轮迭代都补 5 条新写的真实查询。
> 如果每轮都在涨 → 你在过拟合；
> ⭐⭐⭐⭐⭐ 如果新查询上的分数显著低于旧查询 → 你已经过拟合了。**

## 7. ⭐⭐⭐⭐⭐ 修法三：换模型生成

如果必须生成（初期没有真实记录）：

```
⭐⭐⭐⭐⭐ 用 A 模型生成查询，用 B 模型（被测者）跑测试
```

> ⭐⭐⭐⭐⭐ 至少打破同源性。⭐⭐⭐⭐ 不能做到完全干净，
> ⭐⭐⭐⭐⭐ 但把"同一个模型的同一套直觉"换成"两个模型的两套直觉"，
> 高估幅度会明显下降。

两条配套：

```
① ⭐⭐⭐⭐⭐ 生成时**不给技能正文**，只给一句话用途说明
   （给正文 → 复述用词 → 第 ② 类污染）
② ⭐⭐⭐⭐ 生成后人工过一遍，删掉"不像人话"的
   ⭐⭐⭐⭐⭐ 判据：真实输入有冗余、有口语、不完整；
               生成的输入通常语法完整、术语准确
```

> ⭐⭐⭐⭐⭐ 第 ② 条的判据与 `example-values-become-defaults.md`
> 完全一致：⭐⭐⭐⭐⭐ **"如果你的查询读起来像教科书，说明你编了。"**

## 8. ⭐⭐⭐⭐⭐ 自检

```
① ⭐⭐⭐⭐⭐ 每条用例标了 source 吗？（没标 → 污染程度未知）
② ⭐⭐⭐⭐⭐ 报总分还是分组报？（报总分 → 污染隐形）
③ ⭐⭐⭐⭐⭐ 正例的主体来自真实记录吗？（generated 占比 >30% → 不足以决策）
④ ⭐⭐⭐⭐⭐ 有留置集吗？最终按哪一份决策？
⑤ ⭐⭐⭐⭐⭐ golden 是"期望"还是"上次的输出"？
```

一个十秒判断：

> ⭐⭐⭐⭐⭐ **随便挑 3 条正例，盖住技能描述，问自己：
> "一个不知道这个技能怎么写的用户，会打出这句话吗？"
> ⭐⭐⭐⭐⭐ 有 2 条以上不会 → 你的触发率测的是描述与它自己措辞的契合度。**
