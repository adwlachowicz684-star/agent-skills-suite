## 1. ⭐ 为什么必须分层

> ⭐⭐ **没有第 2 层触发 eval，你永远不知道技能为什么不响应；
> 没有第 4 层 benchmark，你永远不知道改完到底是好是坏。**

这两句话是整套分层的理由——**上下两层缺口的性质完全不同**：
下层缺了不知道"为什么不动"，上层缺了不知道"改动有没有用"。

---

## 2. L1 结构 lint

**检查什么**：

```
· YAML 字段是否合法
· description 长度
· ⭐ 引用的文件是否真实存在
```

**工具**：pulser / 自写脚本

> ⭐ 第三条最值钱：**引用不存在的文件会导致模型读失败后自己补内容**
> ——这是幻觉的来源之一（见 `three-failure-modes.md`）。
> 而它 100% 可以在这一层被静态拦住。

---

## 3. ⭐ L2 触发 eval

**测什么**：

```
正样本：该触发的
⭐ 负样本：不该触发的（⭐ 这批比正样本值钱）

看两个指标：precision + recall
```

> ⭐⭐ "负样本比正样本值钱"这条值得单独记住：
> **正样本证明它能用，负样本证明它不会在别人该上场时抢戏。**

## 4. L3 行为 eval

**怎么跑**：

```
Claude Code -p --bare
Codex exec --json
输出 JSON / JSONL
```

**三种断言**：

```
结果断言  —— 做对了吗
路径断言  —— 用了正确的路径吗
⭐ 代价断言 —— 花了多少（token / 轮次 / 时间）
```

> ⭐ "代价断言"这一层常被漏掉。
> 但 `skillsbench-vs-realworld.md` 已经证明**无关技能会因消耗资源而有害**——
> 所以代价不是次要指标，是正确性的一部分。

**可集成 pytest**。

## 5. ⭐ L4 回归 / benchmark

**四个角色**（这个分工很清晰）：

```
Executor   并行跑
Grader     判分
Comparator 盲评 A/B
⭐ Analyzer 找规律
```

> ⭐ **"Analyzer 找规律"这一环是多数评测缺失的**——
> 大家只产出通过率数字，不做归因。
> 而这正是 `trace-debugging.md` "失败点 ≠ 出错点"要解决的问题。

**必跑时机**：⭐ **模型升级时**。

---

## 6. ⭐ 先手跑再加 CI

这个方法论步骤很实用：

```
① ⭐ 先用 CLI 手动跑一遍
   ——立刻抓出明显问题，并校准你对"好/坏输出"的预期
② ⭐ 预期校准之后，自动断言才真正有用
③ 然后才加 CI
```

> ⭐⭐ 第 ② 步是关键洞察：**断言的质量取决于你是否已经看过真实输出。**
> 跳过手跑直接写自动断言，写出来的往往是"恒过的断言"——
> 而 `assert-on-environment.md` 说过：**恒过的断言比没有断言更危险。**

**CI 的形态**：

```
GitHub Actions：对 skills/ 目录的 PR 触发
⭐ 一旦装上，它就隐形——直到它抓到东西。而它一定会抓到东西。
```

## 7. ⭐ 灵魂文档与 eval 的关系

（"灵魂文档"指 AGENTS.md / CLAUDE.md / SKILL.md 这类定义行为的文件）

> ⭐⭐ **Eval 不替代灵魂文档，它验证灵魂文档是否正在生效。**

```
灵魂文档定义 agent 应该做什么
eval     验证 agent 是否真的做了
```

**为什么两者都要**（这段论证很漂亮）：

```
⭐ 没有 eval 的灵魂文档 = 一份未测试的规格。
   你"相信" agent 会这样表现，因为指令是你写的。
   eval 告诉你这个信念是否准确。

⭐⭐ 当底层模型变了，指令没变，但行为可能变了
   ——⭐ 只有 eval 能告诉你这件事发生了。
```

**配对原则**：

```
⭐ 灵魂文档和 eval 应当由同一个人写，并以同样的严格度评审。

"always offer a specific resolution path"（文档）
+ "response contains resolution"（断言）
= 一对匹配的检查

⭐ 文档含糊 → 断言含糊 → 两者都没在干活
```

**复合价值**（这段解释了为什么值得投入）：

```
时间久了，eval 套件会变成"这个技能应该做什么"的规格本身。

客户问"能正确处理 X 吗" → 不再是"我们觉得可以"，而是"这是测试结果"
模型升级    → 定时 eval 告诉你有没有变化
技能被修改  → CI 告诉你这次改动是否安全
生产出事了  → eval 套件告诉你预期行为是什么、实际偏到哪里
```

> ⭐ 最后一句是投入的理由：
> **"否则就是盲飞，指望一切不变。考虑到 2026 年模型行为变化的速度，那不是策略。"**

## 速查

```
L1 结构 lint：
□ YAML 字段 / description 长度 / ⭐ 引用文件是否存在
□ 工具：pulser、自写脚本

⭐ L2 触发 eval：
□ 正样本（该触发）+ ⭐ 负样本（不该触发，⭐ 更值钱）
□ 指标：precision + recall

L3 行为 eval：
□ Claude Code -p --bare / Codex exec --json
□ ⭐ 三类断言：结果 / 路径 / ⭐ 代价
□ 集成 pytest

⭐ L4 回归 benchmark：
□ Executor 并行 / Grader 判分 / Comparator 盲评 / ⭐ Analyzer 找规律
□ ⭐ 模型升级时必跑

流程：
□ ⭐⭐ 先手跑一遍校准预期 → 再写自动断言 → 最后加 CI
□ CI 装上就隐形，直到它抓到东西

⭐ 灵魂文档 vs eval：
□ eval 不替代文档，它验证文档是否生效
□ ⭐ 模型变了指令没变，只有 eval 能告诉你
□ ⭐ 两者同一人写、同样严格评审；文档含糊则断言必然含糊
□ eval 套件最终会成为"这个技能该做什么"的规格本身
```

**一句话**：

> ⭐ **跳过手跑直接写自动断言，写出来往往是恒过的断言——
> 而恒过的断言比没有断言更危险。**
