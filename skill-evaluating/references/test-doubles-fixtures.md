## 1. ⭐⭐⭐⭐⭐ 为什么测不准

一个典型的"测试不稳定"现场：

```
同一份技能、同一批用例：
  周一跑：11/12 通过
  周三跑：8/12  通过
  没有改过任何东西
```

> ⭐⭐⭐⭐⭐ **这不是四象限里的"不稳定"，是测试本身带了外部状态。**

三种最常见的污染源：

| 污染源 | ⭐ 症状 |
|---|---|
| ⭐⭐⭐⭐⭐ 真实外部服务 | 限流、超时、数据被别人改了 |
| ⭐⭐⭐⭐⭐ 真实时间 | "最近 7 天"在不同日期返回不同集合 |
| ⭐⭐⭐ 真实文件系统状态 | 上次跑留下的产物被当成本次输入 |

> ⭐⭐⭐⭐⭐ **判定方法：清空环境重跑两次，结果应该完全一致。**
> 不一致 → 你测的不是技能，是技能 + 世界。

这个判定值得单独强调，因为它**便宜且决定性**：
不需要分析，跑两次就知道。

## 2. ⭐⭐⭐⭐ 四种测试替身

按保真度从低到高：

**① ⭐⭐⭐⭐ 固定夹具（fixture）**

```
预存一份响应/文件，技能读它
```

> ⭐⭐⭐⭐ 优点：完全确定、零成本。
> ⭐⭐⭐ 缺点：不会发现"真实格式变了"。

**② ⭐⭐⭐⭐⭐ 录制的真实响应（cassette）**

```
第一次连真实系统并录下来，之后回放
```

> ⭐⭐⭐⭐⭐ **这是性价比最高的一种**——
> 保真度接近真实，成本接近夹具。
> 适合：API 响应、数据库查询结果。

**③ ⭐⭐⭐⭐ 桩（stub）：只返回最小可用结构**

```
不返回真实数据，只返回"符合 schema 的一坨"
```

> ⭐⭐⭐⭐ 适合测**流程**而非**内容**：
> 你想验证"技能会按正确顺序调用 3 个步骤"，
> 那么每个步骤返回什么都不重要。

**④ ⭐⭐⭐ 沙箱环境**

```
独立的测试库 / 测试目录 / 临时 bucket
```

> ⭐⭐⭐ 保真度最高、成本最高。
> ⭐⭐⭐ 只在**写入类**技能上值得（因为写入的正确性离不开真实约束）。

## 3. ⭐⭐⭐⭐⭐ 边界在哪：替身不该替什么

> ⭐⭐⭐⭐⭐ **替错了东西，测试会一直绿，而线上一直红。**

**可以替**：

```
外部服务响应 · 数据库内容 · 文件系统输入 · 时间 · 随机数
```

**不该替**：

| 不该替 | ⭐ 为什么 |
|---|---|
| ⭐⭐⭐⭐⭐ **写入动作的副作用** | 替身后测的是"流程走完"，不是"真的改对了" |
| ⭐⭐⭐⭐⭐ **错误路径** | 替身通常只替成功响应 → ⭐⭐⭐⭐ **于是失败路径永远没被测** |
| ⭐⭐⭐⭐ **鉴权与权限边界** | 替身后一律放行 → 权限 bug 测不出来 |
| ⭐⭐⭐ 数据规模 | 夹具通常很小 → ⭐⭐⭐⭐ 规模假设类 bug 只在生产出现 |

> ⭐⭐⭐⭐⭐ 第二行最该记：
> **替身通常只替成功响应**——而失败路径恰恰是最容易漏、
> 线上最常出现的那一类（这是 `test-validation-three.md` 的结论）。
> ⭐⭐⭐⭐ **所以录制时，要专门录一份失败响应。**

第三行也常被忽略：技能里声明的 `allowed-tools`
在测试里往往被绕过（因为测试直接调函数），
于是权限约束从未被验证——而它正是反复强调的安全边界。

## 4. ⭐⭐⭐⭐ 替身本身也要测

> ⭐⭐⭐ **夹具会腐烂，而且它腐烂时测试的反应是"依然通过"。**

三种腐烂方式：

```
① ⭐⭐⭐⭐ 格式过期：真实 API 加了字段，夹具还是旧的
   → 测试绿，线上对不上
② ⭐⭐⭐ 内容失真：夹具被手工简化过，边界情形没了
③ ⭐⭐⭐⭐⭐ 永不刷新：录一次用三年
```

对策三条：

**① ⭐⭐⭐⭐ 夹具要有来源标记**

```yaml
# fixtures/api_response.json
_recorded: 2026-03-11
_source: GET /v1/reports
_ttl_days: 90
```

**② ⭐⭐⭐⭐ TTL 到期强制重录**

> ⭐⭐⭐⭐ 把"会不会过期"从需要人记得想，变成有日期的机制
> （与 `review_after`、错误预算同一套路）。

**③ ⭐⭐⭐⭐⭐ 定期对照真实系统跑一次**

```
CI 里：用替身（快、确定）
每周一次：用真实系统（慢、但能发现夹具腐烂）
```

> ⭐⭐⭐⭐⭐ **两者不一致时，不一致本身就是最有价值的信号**——
> 它说明"真实世界变了"，而这正是需要人看一眼的时刻。

## 5. ⭐⭐⭐⭐ 一个最小落地方案

不需要框架，四步：

```
1. ⭐⭐⭐⭐ 先做一个"清空环境跑两次"的检查
   → 不一致就说明有外部状态，先定位
2. ⭐⭐⭐⭐ 把外部依赖列出来（就是 data-dependency-declaration 那张表）
3. ⭐⭐⭐⭐ 每个依赖选一种替身（优先 cassette）
4. ⭐⭐⭐⭐ 专门录 1 份失败响应，作为失败路径用例
```

> ⭐⭐⭐⭐ 第 1 步几乎零成本且能立刻定性：
> **它区分了"技能不稳定"和"测试不稳定"**——
> 而这正是四象限诊断的前提（跑 3 次看一致性）。

一个可选的第 5 步：**把替身目录放进 `references/` 还是 `assets/`？**
判据见目录决策矩阵——⭐ **测试用的夹具不进上下文 → `assets/`**。

## 6. ⭐⭐⭐ 常见借口

| Agent 说 | 回应 |
|---|---|
| "连真实系统更真实" | ⭐⭐⭐⭐⭐ 真实但不可复现。清空跑两次结果不同，这个测试就没有信号。 |
| "夹具会过期" | ⭐⭐⭐⭐ 会，所以要有 `_recorded` 和 TTL。真实系统也会变，且变得悄无声息。 |
| "失败响应不用录，反正会报错" | ⭐⭐⭐⭐⭐ 失败路径正是最常漏、线上最常出现的。必须录。 |
| "写入用替身测就够了" | ⭐⭐⭐⭐ 写入用替身只测了流程，没测"真的改对了"。写入要用沙箱。 |
| "规模不用管，先测通" | ⭐⭐⭐⭐ 规模假设类 bug 只在数据量变大时崩，而那往往在生产。 |
