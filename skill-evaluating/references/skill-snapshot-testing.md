## 1. ⭐⭐⭐⭐⭐ 脚本有快照，技能没有

脚本侧的快照测试已经很成熟（golden 文件 + diff）。但技能输出侧几乎是空白：

| | 脚本 | 技能 |
|---|---|---|
| 快照 | ✅ 标准做法 | ⭐ 几乎没人做 |
| 变更可见化 | ✅ diff 一目了然 | ⭐ 改完技能，输出变了什么，靠感觉 |

后果就是那个熟悉的困境：

```
"改完感觉差不多，但线上有人说变差了"
→ 你无法证明变没变，因为没留基线
```

> ⭐⭐⭐ **没有快照，技能改动就是不可回退的**
> ——你连"回到改之前的行为"都做不到，因为不知道之前是什么行为。

---

## 2. ⭐⭐⭐⭐ 难在哪：输出是自然语言

脚本快照能成功，是因为脚本输出是**确定性的**：

```
同输入 → 同输出（字节级）
```

技能输出不是：

```
同输入 → 措辞不同、顺序可能不同、长度不同
```

> ⭐⭐⭐ 所以**直接对技能输出做字节 diff，必然全是噪音**
> ——每次都"变了"，于是没人看，于是它变成了又一个恒过的检查。

这就是为什么技能侧快照没人做：**第一版尝试几乎必然失败**，
因为它是个噪音生成器。

---

## 3. ⭐⭐⭐⭐ 三种可比粒度

按"抗噪能力"从强到弱：

| 粒度 | 做法 | ⭐ 适用 |
|---|---|---|
| **结构** | 提取 JSON/字段后比 key 集合与类型 | ⭐⭐⭐ 有输出契约的技能（首选） |
| **要素** | 检查必需元素是否出现（正则/列表） | ⭐⭐ 报告类技能 |
| **全文** | 字节或 token 级 diff | ⭐ 只适合极短、极固定的输出 |

> ⭐⭐⭐⭐ **第一条是为什么"输出契约"值得先做的原因之一**：
> 有了 schema，快照就退化成了简单的结构比对，
> 而快照又反过来让 schema 的每次变更都可见——**两者互相强化**。

第二条的要素清单要写成**可判定的**：

```
❌ "包含必要的背景说明"
✅ "包含：产品名、版本、复现步骤（≥1 条）、预期与实际"
```

---

## 4. ⭐⭐⭐⭐⭐ 快照必须"三选二"

单次输出不可比（有随机性），所以要靠**多次采样**构造稳定量：

```
同一用例跑 N 次（N ≥ 3），记录：
  ① 结构签名：所有 N 次都必须通过 schema
  ② 要素覆盖率：N 次中该要素出现的比例
  ③ 长度区间：[min, max]
```

> ⭐⭐⭐⭐ **判据是"三选二"：三项里有两项在阈值内即通过。**
> 要求三项全稳会让它变成不可达标准，于是又变成恒过（没人看）。

配套两个具体阈值建议：

```
⭐ 要素覆盖率 ≥ 80%（不是 100%——100% 会让它变成脆弱测试）
⭐ 长度上限 ≤ 基线 × 1.5（防"话痨化"）
```

第二条特别有价值：**长度膨胀是最容易被忽略的退化**——
输出越来越啰嗦，但没人会报 bug，因为内容还是对的。

## 5. ⭐⭐⭐ diff 的判读：谁来决定

```
CI 算出 diff → ⭐ 谁判断"这个变化是改进还是退化"？
```

三种做法：

| 方式 | 适用 | 风险 |
|---|---|---|
| ⭐ 人工判 | 低频高价值技能 | 会变成走过场 |
| LLM-as-Judge | 大规模 | ⭐ 需要防偏差（见 `judge-design.md`） |
| ⭐⭐ 分层：结构自动判、措辞人判 | ⭐ 推荐 | — |

> ⭐⭐⭐ 推荐第三种的理由很实际：
> **结构变化是客观的（字段没了就是没了），措辞变化是主观的。**
> 把它们分开，客观的自动化、主观的留给人——
> 这与"确定性判断要用确定性机制承载"是同一原则。

## 6. ⭐⭐⭐ 与恒过断言的区别

我们反复说过"恒过的断言比没有断言更危险"。快照测试天然有这个风险，
所以要有**自检机制**：

> ⭐⭐⭐ 每月一次：**故意把技能改差一点**（删掉一个必需要素的要求），
> 看快照会不会红。不红 → 快照失效。

> ⭐⭐⭐⭐ 这和 `eval-set-rot.md` 的"定期把技能改坏一次"是同一手法，
> 只是对象不同：那个测的是**评测集**，这个测的是**快照**。
> **两个都要做，因为它们是两套独立的检查。**

还有一个更便宜的自检：**快照的通过率不应该是 100%**。
长期 100% 说明阈值太松或者根本没在比对。

---

## 7. ⭐⭐ 更新纪律

快照必须能更新（否则会锁死一切改进），但更新要有纪律：

```
✅ 改进导致的 diff → 更新快照 + 在 PR 里贴出 diff
❌ "跑不过就更新"      → ⭐⭐ 那就等于没有快照
```

> ⭐⭐⭐ **关键要求是"在 PR 里贴出 diff"。**
> 因为快照的价值不在通过与否，**在于强迫你回答"这次改动改变了什么输出"**
> ——这和脚本 golden 文件的定位完全一致，只是载体从字节变成了结构。

配一条来自 `change-impact-analysis.md` 的要求：
**下游消费方要在 PR 评审者列表里**——输出形状变了，他们是唯一能判断影响的人。
