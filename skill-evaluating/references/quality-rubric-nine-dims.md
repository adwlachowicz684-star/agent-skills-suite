## 1. ⭐ 九维权重表

| 维度 | 权重 | 评什么 |
|---|---|---|
| Frontmatter 质量 | 7 | 描述规不规范？触发词全不全？ |
| 工作流清晰度 | 12 | 步骤能照着做吗？有输入输出吗？ |
| ⭐ 失败模式编码 | 12 | 写了"如果 X 失败 → Y"吗？还是只有正向流程？ |
| 检查点设计 | 6 | 关键决策前有确认环节吗？ |
| ⭐⭐ 可执行具体性 | 17 | ⭐ 有"建议/可以考虑"这种废话吗？ |
| 资源整合度 | 4 | 引用的文件能加载吗？ |
| 整体架构 | 12 | 结构不乱吧？有禁用套话吗？ |
| ⭐⭐⭐ 实测表现 | 23 | ⭐ 跑一下，输出质量行不行？ |
| 反例黑名单 | 6 | 有"不要做什么"吗？还是只有正向指令？ |

满分 100。

## 2. ⭐⭐ 权重最高的三项

```
实测表现       23   ⭐⭐⭐ 跑一下，输出质量行不行
可执行具体性   17   ⭐ 有没有"建议/可以考虑"这类废话
失败模式编码   12   写了"如果 X 失败 → Y"吗
```

> ⭐⭐ 三项加起来 52%——**超过一半的权重压在"能不能真跑、够不够具体、失败怎么办"**。
>
> 而"Frontmatter 质量"只占 7、"资源整合度"只占 4。

**这个分布本身就是一条方法论**：

```
⭐ 一个描述写得漂亮但跑不通的技能，得分会很低
⭐ 一个描述粗糙但每次都能稳定跑对的技能，得分不低
```

> ⭐ 这与 `quality-rubric.md` 的"Accuracy 30% 且有一票否决"
> 是同一个价值观的两个表达：**正确性 > 美观度**。

**三条具体判据**（可直接当检查表）：

```
· ⭐ "可执行具体性"扣分点：出现"建议""可以考虑""尽量""适当的"
  → ⭐ 这些是无效指令（与 `write-reasons-not-rules.md` 的
     "全是原则没有动作"同源）

· ⭐ "失败模式编码"扣分点：只有正向流程
  → 与《crafting》的 `preflight-gate.md`、`error-handling.md` 配套

· ⭐ "反例黑名单"扣分点：只有正向指令
  → ⭐ 但注意：禁令必须带替代方案（见 `guidance-forms.md`）
     ⭐ 只写"不要做 X"而不写"改做什么"，在这一维也不该满分
```

## 3. 一个真实打分案例

拿一个刚写完的技能跑一轮：

```
Frontmatter 质量   9×7/10  = 6.3   ✅
工作流清晰度       9×12/10 = 10.8  ✅
⭐ 失败模式编码     4×12/10 = 4.8   🔴 最大短板
⭐ 检查点设计       4×6/10  = 2.4   🔴
可执行具体性       8×17/10 = 13.6  ✅
资源整合度         9×4/10  = 3.6   ✅
整体架构           8×12/10 = 9.6   ✅
实测表现           7×23/10 = 16.1  ✅
⭐ 反例黑名单       2×6/10  = 1.2   🔴
─────────────────────────
总分 68.4 / 100
```

**三个短板**：反例黑名单（1.2）、检查点设计（2.4）、失败模式编码（4.8）。

> ⭐⭐ 注意这个案例最值得学的地方：
> **"实测表现"拿了 16.1/23（不错），但总分只有 68.4**
> ——说明**"能跑"和"设计得好"是两件事**，
> 而这套体系能把你"能跑但设计粗糙"的地方暴露出来。

> ⭐ 而且三个短板**正好落在"失败时会怎样"这一类**——
> 这不是巧合：**多数技能的短板都在异常路径上。**

## 4. ⭐⭐ 这把尺子量不到什么

这段话我认为是整份材料里最有价值的，因为它主动声明了边界：

> ⭐⭐ **这套框架主要评估技能的"文档工程质量"和"设计质量"，
> 不等于完整的运行时性能评估。**

它**不能**直接回答：

```
· 实际调用工具的成功率是多少
· 不同用户输入下是否稳定
· 长期运行成本是否合理
· 外部 API 抖动时是否真的能恢复
· ⭐ 真实用户是否愿意持续使用
```

**这些需要结合**：执行日志、测试集、失败样本、用户反馈。

> ⭐⭐ **知道一套评估框架"能量什么、不能量什么"，
> 才不会把分数当成真相本身。**

## 5. 与四维体系怎么选

| | 四维（quality-rubric） | 九维（本份） |
|---|---|---|
| 维度 | Clarity / Completeness / Accuracy / Usefulness | 九项加权，满分 100 |
| 特点 | ⭐ Accuracy 有**一票否决**（≥3.0） | ⭐ 实测表现权重大（23） |
| 更适合 | 判断"能不能上线" | 判断"哪里该改" |

> ⭐ **互补用法**：
> 先用四维做**准入门槛**（Accuracy 否决），
> 再用九维做**改进清单**（哪项低改哪项）。

**共同的关键纪律**（两边都强调）：

```
⭐ 每个分数都要引用具体证据
   ——"第 45 行 SQL 有注入风险"，而不是"有安全问题"

不要：
❌ 按个人风格偏好扣分
❌ 标记了废弃模式却不给替代方案
❌ 因缺少"可选章节"就判不合格
❌ ⭐ 不管安全问题，只看其他维度得分高就放行
❌ 为复杂技能赶时间评审
```

## 速查

```
九维权重：
□ ⭐⭐⭐ 实测表现 23
□ ⭐⭐ 可执行具体性 17（扣分点："建议/可以考虑/尽量"）
□ ⭐ 失败模式编码 12（只有正向流程就扣分）
□ 工作流清晰度 12 · 整体架构 12
□ Frontmatter 7 · 检查点 6 · 反例黑名单 6 · 资源整合 4

□ ⭐⭐ 正确性 > 美观度（描述漂亮但跑不通 = 低分）
□ ⭐ "能跑"≠"设计得好"（案例：实测 16.1/23，总分仅 68.4）
□ ⭐ 短板往往集中在异常路径上

⭐⭐ 边界（量不到什么）：
□ 工具调用成功率 / 跨输入稳定性 / 长期成本
□ API 抖动恢复能力 / ⭐ 用户是否愿意持续使用
□ 需结合：执行日志 + 测试集 + 失败样本 + 用户反馈
□ ⭐⭐ 别把分数当成真相本身

□ ⭐ 四维做准入门槛，九维做改进清单
□ ⭐ 每个分数都要引用具体证据
```

**一句话**：

> ⭐⭐ **一个技能"实测表现"拿了 16.1/23，总分却只有 68.4——
> 因为"能跑"和"设计得好"是两件事，而三个短板全在异常路径上。**
