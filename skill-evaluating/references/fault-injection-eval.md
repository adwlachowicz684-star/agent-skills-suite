## 1. ⭐ 先写恢复契约

> ⭐ **在注入故障之前写出不变量。**
> ⭐ 一份有用的契约要指明"哪些状态必须存活"和"哪些副作用不得重复"。

模板：

```
恢复后：
  · 从最新的持久化检查点恢复
  · 保留任务标识与安全策略
  · 消耗不超过剩余的重试/截止时间预算
  · ⭐ 每个对外可见的副作用最多提交一次
```

**用显式状态建模工作流**：

```
created → running → checkpointed → waiting_for_tool
                        │               │
                        ▼               ▼
                     failed         resumed → completed
```

> ⭐ **每个转移都要定义：负责人、持久化字段、允许的重试次数、终态行为。**
>
> ⭐ **内存里的值不算检查点，除非 harness 能证明它在模拟重启后存活。**

## 2. ⭐ 故障矩阵

> ⭐ **选能覆盖新恢复逻辑的最小故障集。
> ⭐ 在确定性计划通过之前，不要随机化计划。**

| 注入点 | 必须观察 | 预期遏制 |
|---|---|---|
| **工具启动前沙箱拒绝** | 无不安全副作用；原因被保留 | 仅当策略允许时重试 |
| **MCP/工具超时**（请求 id 已分配） | 超时归属于该请求 | ⭐ 带同一幂等键的有界重试 |
| **worker 在检查点写入后重启** | worker 重新加载同一任务版本 | 从最新检查点恢复 |
| ⭐ **恢复前检查点缺失/过期** | 过期数据被拒绝或标记 | ⭐ 安全停止；**绝不编造进度** |
| **并行分支失败**（fan-out 后一个分支） | 兄弟分支状态被保留 | join 策略决定重试/降级/停止 |
| ⭐ **记忆丢失** | 清空临时上下文 | 持久事实被重建；必需事实缺失时**询问或停止** |
| ⭐ **最后一次尝试时重试/截止耗尽** | 不再安排额外调用 | 终态 failed 或 timed_out |

## 3. ⭐ 确定性注入计划

> ⭐ **用事件序号，而不是挂钟随机。**

```json
{
  "seed": "harness-fixture-07",
  "faults": [
    {"event": "tool.call",   "ordinal": 2, "kind": "timeout", "tool": "search"},
    {"event": "worker.start","ordinal": 2, "kind": "restart"},
    {"event": "branch.join", "ordinal": 1, "kind": "partial_failure", "branch": "summarize"}
  ]
}
```

三条硬规则：

```
① ⭐ harness 应该输出计划本身，不只是 seed
② ⭐ 故障身份要与观测到的错误分开
   ——否则包装器可能把 timeout 意外变成通用失败
③ ⭐ 同一计划跑两次，比较归一化后的时间线，再换计划
```

## 4. 四种判定

```
recovered       已恢复
contained       已遏制
unrecoverable   不可恢复
inconclusive    不确定
```

> ⭐ **"不确定"这一档非常重要**——
> 它诚实地表示"这次没测出结论"，
> ⭐ 而多数评测会把 inconclusive 强行算成 pass 或 fail。

**导致 inconclusive 的典型原因**：

```
⭐ 缺少范围、夹具或恢复契约 → 判定不确定
```

**降级规则**：

```
⭐ 如果无法证明 exactly-once，就降级判定并要求对账
```

## 5. 安全前提

**冻结这些变量**：

```
工作流修订版 · 模型/提示配置 · 工具 schema
seed · 输入夹具 · 超时 · 重试预算 · 截止时间 · 预期终态
```

**运行条件**：

```
· 一次性沙箱 + 合成输入 + 打桩工具
· 除非测试明确需要本地测试服务器，否则禁用网络
· ⭐ 每个注入的故障都是内存内或夹具控制的事件
```

> ⭐ **绝不为了制造故障而去：删除真实数据、吊销真实凭据、
> 杀掉无关进程、改动一个线上服务。**

**不要用本技能的场景**：

```
❌ 生产目标 · 真实用户数据 · 活凭据 · 无界外部服务
✅ 转成 ⭐ 本地模拟器或经授权的 staging harness
```

## 速查

```
□ ⭐ 先写恢复契约（存活状态 + 不得重复的副作用）
□ 每个转移：负责人/持久字段/重试次数/终态
□ ⭐ 内存值不算检查点（除非证明能活过重启）
□ ⭐ 确定性计划通过前不随机化
□ ⭐ 用事件序号，harness 输出计划本身
□ ⭐ 故障身份与观测错误分开
□ ⭐ 同计划跑两次比时间线
□ 四判定：recovered/contained/unrecoverable/inconclusive
□ ⭐ 不能证明 exactly-once → 降级 + 要求对账
□ ⭐ 冻结全部变量；一次性沙箱；禁网
□ ⭐ 绝不靠破坏真实环境来制造故障
□ 检查点缺失 → 安全停止，⭐ 绝不编造进度
```

**一句话**：

> ⭐ **在注入故障之前写出不变量——
> 不知道"什么必须存活"，就无法判定恢复是否成功。**
