## 1. ⭐ 为什么必须第一天就建

```
⭐ 演示阶段只关心"能不能跑通"
⭐ 工程系统必须关心"为什么失败、哪里慢、哪个技能常出错"
```

> ⭐ **没有日志、监控和评估，Agent 系统就是黑盒。**

一个具体的现实压力：

```
很多 Agent 在演示阶段表现正常，
⭐ 进入真实流量后会出现难以复现的问题。

一次回答变慢：可能来自模型调用，也可能来自工具执行
一次结果出错：可能是提示词、上下文、权限或外部服务导致

⭐⭐ 没有调用链和日志，排障只能靠猜。
```

## 2. ⭐ 一次调用要记录什么

```
request_id · session_id · user_id
skill_name · ⭐ skill_version
input · output_status · error_type
latency_ms · retry_count · timestamp
```

> ⭐ **`skill_version` 是最常被漏的一个**——
> 没有它，你看到"这个技能最近变差了"却无法定位是哪次改动引起的。

```
⭐ 敏感信息要脱敏或不记录明文
```

## 3. ⭐⭐ 调用日志 vs 决策日志

这两类日志的区分是这份文档最重要的部分：

```
调用日志 —— 记录技能执行情况
  技能名、参数、开始/结束时间、成功/失败、错误信息

⭐ 决策日志 —— 记录⭐ 为什么选择这个技能
  { "selected_skill": "web_search", "reason": "用户询问最新信息" }
```

> ⭐⭐ **很多问题不是执行失败，而是选错技能，所以决策日志很重要。**

**决策日志要记录的三类信息**：

```
① ⭐ 路由层召回的候选技能 ID 列表
② ⭐ 模型决定调 A 而不是 B 的那条决策，连同它的"理由"（如果输出了 reasoning）
③ ⭐ 整个链路中每个"决策点"都要做快照，不能只记一次
```

> ⭐ 第 ③ 条是 trace 的精髓：**trace 信息不能只记一次**。
> 这样你才能像查快递一样查一次 Agent 行动的完整旅程。

**一个真实场景**：

```
用户反馈："刚才自动退款流程走到一半卡住了"
→ 拿 trace ID 一查
→ ⭐ 立刻看到卡在哪一步、那一步调了哪个技能、技能返回了什么异常

⭐ 没有这套能力，你可能连问题到底出在模型决策还是技能执行都分不清。
```

## 4. ⭐ 入参快照要记两份

```
⭐ 实际传入技能的参数 JSON，要注意记⭐ 两份：
   · 模型传入的
   · ⭐ Schema 校验后的
```

> ⭐ 因为可能经历了默认值填充或格式修正——
> ⭐ **只看"校验后"的那份，你会以为是模型主动填了这些值。**
> 这正是"技能不按我预期工作"的一类隐蔽成因。

**耗时也要拆三段**：

```
⭐ 排队时间 / 执行时间 / 返回序列化时间
```

> 不拆的话，"慢"只能归到"技能慢"，定位不到瓶颈在哪一段。

## 5. 监控指标清单

```
调用次数 · 调用成功率 · 失败率
平均耗时 · ⭐ P95 耗时 · 超时率
⭐ 空结果率 · ⭐ 错误类型分布
重试次数 · 调用成本
```

> ⭐ 三个容易被忽略的：
> **空结果率**——调用成功了但什么都没返回，纯看成功率是看不出来的；
> **错误类型分布**——"失败率 5%"和"失败率 5% 且全是超时"是完全两回事；
> **重试次数**——它的上升往往是漂移的前兆。

**配套的健康度机制**（一个真实做法）：

```
综合评分每周算一次
⭐ 低于阈值的技能被标记为"待优化"
⭐ 并从自动路由的候选列表里暂时摘除
```

> ⭐ 这个设计很妙：**不健康的技能不是被删，而是先退出路由。**
> 与 `retirement-pipeline.md` 的"归档 ≠ 删除"是同一思路。

## 6. ⭐ 评估 ≠ 监控

```
⭐ 监控关注系统运行是否稳定
⭐ 评估关注能力效果是否好
```

**举例**：搜索技能

```
监控看：成功率、耗时
⭐ 评估看：⭐ 结果相关性、来源可信度、结果新鲜度、空结果率
```

> ⭐ **一个技能可以监控全绿而评估不及格**——
> 每次都成功返回，但返回的东西没用。

**不同技能的评估指标**（四类样本）：

| 技能 | 评估指标 |
|---|---|
| 搜索 | 结果相关性、来源可信度、新鲜度、空结果率 |
| RAG | 召回率、top-k 相关性、引用准确性、⭐ 幻觉率 |
| 文件解析 | 解析成功率、文本完整性、表格识别准确率 |
| 邮件 | 草稿成功率、收件人识别准确率、⭐ 误发送率 |

**任务级评估**（比技能级更高一层）：

```
⭐ 技能调用成功 ≠ 用户任务成功
```

还要看：

```
最终任务是否完成 · 答案是否准确 · 用户是否满意
是否需要人工修改 · 是否多次重试
```

> ⭐ **Agent 系统应同时评估技能层和任务层。**

## 速查

```
□ ⭐ 第一天就建可观测性，否则排障只能靠猜
□ ⭐ 字段要含 skill_version（否则定位不到是哪次改动引起）
□ 敏感信息脱敏或不记明文

□ ⭐⭐ 调用日志（执行情况）+ 决策日志（为什么选它）
□ ⭐ 决策日志要记：候选列表 / 决策理由 / ⭐每个决策点都快照
□ ⭐ 入参快照记两份：模型传入的 + Schema 校验后的
□ ⭐ 耗时拆三段：排队 / 执行 / 序列化

指标：
□ 调用次数、成功率、失败率、平均耗时、P95、超时率
□ ⭐ 空结果率、⭐ 错误类型分布、重试次数、成本
□ ⭐ 低分技能先退出路由候选，而不是直接删

评估 ≠ 监控：
□ 监控看稳定性，评估看效果
□ ⭐ 同时评估技能层与任务层
□ ⭐ 技能调用成功 ≠ 用户任务成功
```

**一句话**：

> ⭐ **很多问题不是执行失败，而是选错技能——
> 所以没有决策日志，你连错在哪一层都不知道。**
