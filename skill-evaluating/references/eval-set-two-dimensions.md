## 1. ⭐⭐ 为什么必须有评测集

> ⭐⭐ **技能库没有评测⭐ 就等于没有回归测试。**
> ⭐⭐⭐ **改一个描述，可能悄悄弄坏另一个技能的触发。**

> ⭐⭐⭐ 这条给出了"为什么技能库尤其需要评测集"的理由——
> 不是"测试总归是好的"，而是⭐ **技能之间存在非局部耦合**：
> 你改 A 的 description，坏的可能是 B 的触发。
>
> 这与 `library-size-effect.md` 的遮蔽、
> `capability-offset-net-gain.md` 的 59% 抵消是同一事实的三个侧面：
> **技能不是独立 deploy 的单元，它们共享一个触发预算和一个上下文。**

## 2. ⭐⭐⭐ 维度一：触发评测

**测什么**：

```
⭐ 给一组⭐ 真实用户表达，看⭐ 编排层选中的技能是否正确
```

**样本怎么造**（三条，都很具体）：

```
① ⭐⭐⭐ 这批样本要⭐ 刻意包含容易混淆的表达
   例：同一句话既可能触发 scan-directory，也可能触发 grep-content

② ⭐ 样本量不用大——⭐⭐ 三五十条覆盖主要混淆对就够

③ ⭐⭐⭐ 必须包含⭐ 反例——⭐ 也就是"这句话⭐ 不该触发任何技能"的情况
```

> ⭐⭐⭐ 第 ③ 条与 `trigger-tuning-loop.md` 的
> "10 条应该触发 + 10 条不应该触发"完全一致——
> ⭐ 两个独立来源都把**负样本列为必需项而不是可选项**。
> 也呼应 `eval-case-design.md` 的
> "负向用例检查的是'它没做什么'"。
>
> ⭐⭐ 第 ① 条也很实用：**不要随机造样本，要专门造"混淆对"**——
> 因为随机样本大部分是 trivial 的，测不出边界。

## 3. ⭐⭐⭐ 维度二：执行评测

**测什么**：

```
⭐ 给固定输入，看⭐ 输出是否符合契约
```

**重点测三类**：

```
① 正常路径
② ⭐ 边界输入（空数组、极深目录、零字节文件）
③ ⭐⭐⭐ 失败路径（路径不存在、权限不足）
```

**测试用例的写法**（可直接照抄的格式）：

```markdown
## Test Cases
### TC-1: Basic Operation
- Input: `/code-review src/index.ts`
- Expected: Review results in JSON format
### TC-2: No File Specified
- Input: `/code-review`
- Expected: Error "Please specify a file"
### TC-3: Nonexistent File
- Input: `/code-review nonexistent.ts`
- Expected: Error "File not found"
```

> ⭐⭐ 这个格式的价值在于⭐ **Expected 那一栏强制你写下预期**——
> 包括⭐ 错误情况下的预期。
> 多数人只写"正常会怎样"，于是"报错时报得对不对"永远没被测。

## 4. ⭐⭐⭐ 失败路径最容易漏，却是线上最常见

> ⭐⭐⭐ **"失败路径最容易漏，但它恰恰是线上最常出现的。"**

> ⭐⭐⭐ 这是本份最值得记住的一句，而且它给出了一个⭐ 反常识的解释：
>
> ```
> 直觉：线上大部分请求是正常的，所以应该重点测正常路径
> ⭐⭐⭐ 实际：⭐ 正常路径你开发时已经跑了几十遍，早就不出问题了；
>       ⭐ 线上出问题的恰恰是⭐ 你没测过的那些情况
> ```
>
> ⭐⭐ 这也解释了 `fault-injection-eval.md` 为什么值得做——
> 那整份文档就是专门造失败路径的。
> 以及 `three-failure-modes.md` 的"引用了不存在的模板文件"——
> 那也是一个失败路径。

**回归测试**（配套）：

```
⭐ 更新技能后，⭐ 重新测一遍之前能过的用例
```

## 5. ⭐⭐ 五步渐进式测试

```
① ⭐⭐ 先用最小配置验证技能被识别
   --- name: test-skill / description: Test skill ---
   ## Instructions → "Test successful"
   /test-skill 能用 → ⭐ 基础配置是对的

② ⭐⭐ 逐步加功能
   Step 1 验证最小配置 ✓
   Step 2 加基本指令
   Step 3 定义输出格式
   Step 4 加 references/
   Step 5 加 scripts/（如需要）
   ⭐⭐⭐ 每步都验证 → ⭐ 能快速定位问题

③ 用不同输入测
④ 用日志
⑤ 把测试用例文档化
```

> ⭐⭐⭐ 这条与 `incremental-debug-procedure.md` 的增量调试、
> 以及"一次只改一组"是同一个原理在测试阶段的应用：
> **一次加一层，坏了就知道是哪一层。**
>
> ⭐⭐ 第 ① 步尤其有用：一个 10 行的"Test successful"技能
> 能⭐ 一次性排除掉文件层的所有问题
> （路径、大小写、YAML、编码），
> 这正是 `troubleshooting-manual.md` 说的"80% 的问题在第一步"。

## 速查

```
□ ⭐⭐⭐ 没有评测集 = 没有回归测试
   ⭐⭐⭐ 改一个描述可能悄悄弄坏另一个技能的触发（⭐ 非局部耦合）

□ ⭐⭐⭐ 维度一 触发评测：真实用户表达 → 看选中是否正确
   ⭐⭐⭐ ① 刻意造"混淆对" ② 三五十条够 ③ ⭐ 必须含"不该触发任何技能"的反例
□ ⭐⭐⭐ 维度二 执行评测：固定输入 → 输出符不符合契约
   三类：正常 · ⭐ 边界（空数组/极深目录/零字节）· ⭐⭐ 失败（路径不存在/权限不足）

□ ⭐⭐⭐ ⭐ 失败路径最容易漏，却是线上最常见
   （正常的你早跑过几十遍；线上出问题的正是你没测的）
□ ⭐⭐⭐ 用例格式：Input / ⭐ Expected（⭐ 含错误预期）——逼你写全

□ ⭐⭐ 五步渐进：最小配置 → 逐步加（每步验证）→ 不同输入 → 日志 → 文档化
□ ⭐⭐ "Test successful" 10 行技能能一次排除文件层所有问题
```

**一句话**：

> ⭐⭐⭐ **评测集要分两个维度——触发评测看"选对了没"（必须含"不该触发任何技能"的反例），
> 执行评测看"输出符合契约没"；
> 而失败路径最容易漏，却恰恰是线上最常出现的。**
