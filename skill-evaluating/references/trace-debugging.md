## 1. ⭐ 先拿完整 transcript

```
system prompt · 已加载的技能内容 ·
⭐ 每一次工具调用及其参数 · 每一次工具结果
```

> ⭐ **不要做摘要。读字面 token 流。**
> ⭐ **因为 bug 就藏在某句具体说过或返回过的话里，而摘要会把它藏起来。**

Claude Code 里可直接查看；用 Agent SDK 就记录原始 message list。

## 2. ⭐ 找第一个错的 turn（不是失败那一 turn）

> ⭐ **一个在第 12 轮才变得明显的循环，
> ⭐ 通常是从第 3 轮开始的——
> ⭐ 那时模型形成了一个错误信念，并且此后从未得到反驳它的证据。**

这是整份文档最重要的一句：**失败点 ≠ 出错点**。

---

## 3. ⭐ 诊断问题：当时那个动作合理吗

```
⭐ 在每个可疑 turn 问：
   ⭐ "给定 Claude 此时能看到的一切，它这个动作合理吗？"

合理   → ⭐ bug 在上游——修它拿到的上下文或工具结果
不合理 → ⭐ bug 是局部的——修 SKILL.md 里那条本该引导它的指令
```

**流程**：

```
运行失败/停滞 → 抓完整 transcript
  → 找第一个错的 turn
  → 那个动作合理吗？
      ├─ 是 → 修上下文或工具结果
      └─ 否 → 修 SKILL.md 指令
  → ⭐ 改完，重放同一条 transcript
  → 失败消失了吗？没有就回到上一步
  → ⭐ 消失了 → ⭐ 用一条回归 eval 锁住它
```

> ⭐ 最后两步常被漏：**重放同一条 transcript**（不是重新跑个新case）
> 和**用回归 eval 锁住**（否则下次还会犯）。

**三类具体故障**：

| 症状 | 判读 | 修法 |
|---|---|---|
| **选错工具** | 看响应里的 `tool_calls` 数组 | ⭐ 问题在技能配置或 system prompt，不在日志层 |
| **参数幻觉** | 调了一个不存在的 flag | 指令里给出精确参数名与示例 |
| **重试不止** | 同一调用反复 | ⭐ 技能定义里加显式重试上限，或改进工具返回的错误信息让模型能自适应 |

**"中途停止"两种**：

```
最后一条是 LLM 请求但无响应  → 模型提供方超时（默认 60s）
最后一条是工具调用          → ⭐ 工具本身挂了
                              （检查它是否发起了可能超时的外部 HTTP）
```

## 4. ⭐ 循环的唯一根因，三种伪装

> ⭐ **循环有一个根因，三种伪装：
> ⭐ agent 没有一个无歧义的"已完成"信号。**

```
① ⭐ 没有明确的成功判据 → 它一直在打磨
② ⭐ 有重试指令但没有重试预算 → 一个失败的工具被永久调用
③ ⭐ 两个步骤互相撤销 → 来回震荡
```

**三条的修法都是同一个：让终止显式化。**

```markdown
## Stopping rules
- You are DONE when: tests pass AND the diff touches only files listed in scope.md.
- If a tool call fails, retry at most twice. On the 3rd failure,
  stop and report the exact error plus the command you ran.
  ⭐ Do NOT try alternative tools.
- ⭐ Never run the same shell command twice in a row with identical arguments.
  ⭐ If you would, you are looping — stop and explain what you are missing.
```

> ⭐ **最后那条规则"骗人地强大"**：
> ⭐ **通过给循环模式命名、并指示模型把重复当作信号，
> ⭐ 你把无限循环转换成了一条有用的错误信息。**
>
> ⭐ 模型很擅长注意到"我快要重复自己了"——⭐ 只要你先告诉它重复是有意义的。

## 5. 四阶段排错与恢复启发式

**四阶段**：

```
① 失败捕获（在盲目重试之前，精确记录失败）
② 分类（agent 是否丢了真实目标、去优化错误的子任务了？
        失败是确定性的还是瞬时的？
        ⭐ 能验证这个诊断的最小可逆动作是什么？）
③ ⭐ 遏制式恢复（用能改变诊断面的最小动作）
④ 内省报告
```

**安全的恢复动作**：

```
· 停止重复重试，重述假设
· ⭐ 修剪低信号上下文，只留当前目标、阻塞项与证据
· 重新检查真实的文件系统/分支/进程状态
· ⭐ 把任务收窄到一个失败的命令、一个文件、一个测试
· 从推测性推理切换到直接观察
· ⭐ 高风险或外部阻塞时升级给人
```

> ⭐ **不要声称自己做了没做的自愈动作**（"重置 agent 状态""更新 harness 配置"），
> 除非你真的通过当前环境里的真实工具在做。

**恢复启发式（按此顺序）**：

```
① 一句话重述真实目标
② ⭐ 核验世界状态，而不是相信记忆
③ 收窄失败范围
④ 跑一个有区分度的检查
⑤ ⭐ 只有到这一步，才重试

❌ 坏模式：换几种措辞把同一动作重试三遍
✅ 好模式：捕获失败 → 分类模式 → 跑一个直接检查
          → ⭐ 只有检查支持时才改计划
```

**内省报告该含**：

```
会话/任务 · 失败现象 · 根因 · 恢复动作 ·
结果（success | partial | blocked）·
token/时间燃烧风险 · 需要的后续 · ⭐ 以后该编码进去的预防性改动
```

> ⭐ 最后一项最有价值：**"以后该编码进去的预防性改动"**
> ——这正是 `feedback-loop-design.md` 那条"规则升级为代码"的输入。

**一个"幽灵超时"的实战**：

```
现象：某查询技能高峰期随机超时，但手动调外部 API 很快
排查：从日志找到超时的 request_id：req_abc123
     ⭐ 用这个 id 在日志系统里搜出该请求的全部相关日志
```

> ⭐ **用 request_id 串联**是这类"时好时坏"问题的唯一有效手段——
> 靠时间戳对不上，靠肉眼找不出来。

## 速查

```
□ ⭐ 拿完整 transcript，读字面 token 流，不做摘要
□ ⭐ 找第一个错的 turn（不是失败那一 turn）
□ ⭐ 问："给定它当时能看到的，这个动作合理吗？"
    合理 → 修上下文/工具结果；不合理 → 修 SKILL.md
□ ⭐ 改完重放同一条 transcript
□ ⭐ 用回归 eval 锁住

循环：
□ ⭐ 唯一根因 = 没有无歧义的"已完成"信号
□ 三种伪装：无成功判据 / 无重试预算 / 两步互撤
□ ⭐ 修法都是：让终止显式化
□ ⭐ "不要用完全相同的参数连跑同一条命令两次"
    ——命名循环 = 把死循环变成有用的错误信息

□ ⭐ 遏制式恢复：最小可逆动作
□ ⭐ 核验世界状态，而不是相信记忆
□ ⭐ 收窄到一个命令/文件/测试
□ ⭐ 只有跑过有区分度的检查后才重试
□ ❌ 换措辞重试三遍
□ ⭐ request_id 串联（时好时坏问题唯一有效手段）
□ ⭐ 报告含：以后该编码进去的预防性改动
□ ⭐ 不声称没做的自愈动作
```

**一句话**：

> ⭐ **模型很擅长注意到"我快要重复自己了"——
> 只要你先告诉它重复是有意义的。**
