# 四层测试金字塔

> ⭐ **别想着用一种工具把所有事都干了——把测试拆成金字塔，每层用最合适的工具。**
> **这四层失败的原因完全不同，混在一起测，调试时就只能两眼一抹黑。**

## 四层

| 层 | 类比 | 测什么 | 一次跑多久 | 工具 |
|---|---|---|---|---|
| **第 1 层** | 编译期检查 | YAML frontmatter、字段格式、文件存在性 | **毫秒级** | `validate_skill.py`、自写脚本 |
| **第 2 层** | 路由 / dispatch | 该用的时候触发了吗？不该用的时候没乱触发吗？ | **秒级** | LLM 当判官，跑 description |
| **第 3 层** | 集成测试 | 真拉起 agent 跑一遍，看步骤、工具、产出 | **分钟级** | headless 模式（如 `claude -p`） |
| **第 4 层** | 回归 / benchmark | 改完是变好了还是变差了 | **小时级** | A/B comparator，多次跑取均值 |

**各层的关键点**：

**第 1 层最便宜也最容易被忽视。**
> 它把低级错误挡在"编译期"——YAML 格式、name 与目录名一致、
> description 长度、引用文件是否存在。**这一层不该用 LLM 判。**

**第 2 层是触发测试**，见 `triggering.md`。
> 正例 + 负例 + near-miss，跑 3 次取均值。

**第 3 层是行为测试**：
> 真的跑一遍完整任务，检查它是否走了该走的步骤、
> 用了该用的工具、产出了符合契约的结果。

**第 4 层是回归**：
> ⭐ **目的是防止"修了一个 Bug，引入两个新 Bug"。**
> 用历史 badcase + 黄金数据集，每次上线前跑一遍。

## 为什么必须分层

> **一个真实的诊断经验**：

> 现象："技能不工作"。
> 直觉：去第 3 层（行为）反复跑任务调试。
> 实际原因：**在第 2 层——description 根本没匹配上。**
> 如果有第 2 层的测试，**5 分钟就能定位**。

**判断口诀**：

```
技能完全没反应        → 第 1 层（可能加载就失败了）
该触发时没触发        → 第 2 层
触发了但跑偏          → 第 3 层
之前好好的现在变差    → 第 4 层
```

## 倒金字塔：数量分布

> ⭐ **数量上呈倒金字塔——底层的单元测试最多、最快、最稳定。**

```
        ┌──────────────────────┐
        │  回归 / benchmark 10% │  历史 badcase + 黄金数据集
        ├──────────────────────┤
        │  集成测试        30% │  多技能协作、agent 编排
        ├──────────────────────┤
        │  单元测试        60% │  单个技能的输入输出
        └──────────────────────┘
```

**评测体系横向贯穿**，作为对"模型输出质量"的专项保障，
用**规则打分 + LLM-as-judge 双重判定**。

**每层的手段**：

```
单元测试  Pytest/Vitest + 纯函数断言，覆盖技能、工具函数、状态转换
集成测试  用 stub 替换 LLM provider，用 mock server 替换渠道，
          验证 agent 编排链路
E2E      Playwright 驱动真实渠道，连真实模型，做冒烟验证
评测体系  对话结果送进评估器，规则打分 + LLM-as-judge
```

> ⚠️ **反模式：冰淇淋筒（很多 E2E、很少单元测试）→ 倒过来。**
> 也别走另一个极端：**90%+ 都是单元测试会缺集成覆盖与用户工作流验证**。

## 可测试性先于测试

> ⭐ **很多技能不好测，是因为逻辑全写在一个巨大的 prompt 里，
> 或者全写在一个 process 方法中。**

**设计阶段就要把"纯逻辑"和"模型调用"分开**：

```
scripts/     —— 确定性逻辑，可单元测试，不消耗 token、不依赖模型
SKILL.md     —— 指令，靠第 2/3 层测
```

> ⭐ **把技能中的确定性逻辑单独抽出来测试，
> 可以在不消耗 Token、不依赖模型的情况下快速发现问题。**
> **这是所有技能测试方案中最便宜、最稳定的一层。**

这也正是"确定性逻辑进 `scripts/`"这条设计原则的**第二个理由**——
第一理由是省 token，**第二理由是可测试**。

**测试分层判定**（避免错层）：

```
□ "什么都算单元测试"
  → 测流水线执行的不算单元，应归入集成（涉及组件交互）
□ "新功能都加冒烟测试"
  → 冒烟只留给关键路径与部署验证
□ "给确定性逻辑用 GenAI 测试"
  → 2 + 2 == 4 用 assert，不要用 LLM 判官
□ "集成测试里 mock 掉一切"
  → 要么用真实 DB（集成），要么移入单元测试（隔离）
```

## Mock 策略

> 按被测对象选择 mock 层次：

```
□ 技能内部函数 / 纯逻辑    → 不 mock，直接断言
□ 工具调用参数             → mock 工具返回值
□ agent 的决策链路         → ⭐ Mock LLM：把模型换成可编程的 stub
                              验证提示词组装、tool schema、路由逻辑
□ 消息渠道                 → 集成测试：本地 mock server 模拟 Webhook 回调
□ 真实模型的行为           → ⭐ 不用传统断言硬卡，交给评测体系用评估器打分
```

> ⭐ **关键区分**：
> **确定性部分用 assert；模型行为用评估器。**
> 用断言去卡模型输出，得到的是脆弱且昂贵的测试。

**测试代码本身的规范**：

```
□ AAA 模式：Arrange / Act / Assert
□ FIRST 原则：Fast · Isolated · Repeatable · Self-validating · Timely
□ 覆盖率是手段不是目的——高覆盖 ≠ 好测试
□ 没有有意义断言的测试会虚高覆盖率却抓不到 bug
□ flaky 测试立即隔离到单独套件，修根因（时序/顺序依赖/外部状态）后再归队
```

## 自查

```
□ 是否四层都有覆盖（而不是只跑第 3 层）？
□ 第 1 层是否用脚本而非 LLM 判（便宜且确定）？
□ 第 2 层是否有负例与 near-miss？
□ 第 4 层是否维护了历史 badcase 与黄金数据集？
□ 数量分布是否呈倒金字塔（单元最多）？
□ 确定性逻辑是否已抽到 scripts/ 以便单测？
□ 是否避免了"用 LLM 判官测确定性逻辑"？
□ mock 层次是否与被测对象匹配？
□ 是否有 flaky 测试的隔离与根因修复机制？
□ 改完后是否跑了第 4 层确认没引入新问题？
```
