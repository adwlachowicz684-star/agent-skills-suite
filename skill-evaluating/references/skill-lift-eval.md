# Skill Lift：用 A/B 对照证明技能有用

> ⭐ **NVIDIA 实测 300+ 技能的核心方法**：
> **让 agent 在启用技能和不启用技能的两种情况下，分别完成同一个任务。**

## SkillEvaluator 的三层评估

```
第一层  静态检查
        格式、安全、代码质量

第二层  ⭐ 重复检测
        ⭐ 用向量相似度检查技能内部是否存在重复指导
        ⭐ 比较整个技能目录，识别跨技能的内容重叠
        理由：当环境里有几十上百个技能时，
             重复内容会额外占上下文，
             ⭐ 也可能让多个能力相近的技能同时进入选择范围

第三层  ⭐ 真实任务评测
        基于开源评测框架，把用例交给 agent 实际执行
        agent 分别在启用与不启用技能下完成同一任务
        ⭐ 对比两组结果，计算 Skill Lift
        ⭐ 两组测试放在各自独立环境里跑，避免互相影响
```

> ⭐ **第二层"重复检测"是个很好的补充**——
> 呼应 `skill-orchestration` 的 `skill-composition-patterns.md` 的重叠合并与
> `skill-distribution` 的 `library-ops.md` 的健康诊断。

## 五维度与实测数据

> **数据快照 2026-08-12，覆盖 300+ NVIDIA Verified Skills、
> 30+ 产品，在 Claude Code 与 OpenAI Codex 上执行。**

| 维度 | 不启用 | 启用 | Skill Lift |
|---|---|---|---|
| **正确性** | 46 | 87 | **+41** |
| **可发现性** | 42 | 82 | **+40** |
| **有效性** | 39 | 78 | **+39** |
| **效率** | 43 | 78 | **+35** |
| 安全性 | 97 | 98 | +1 |

```
□ ⭐ 所有维度平均 Skill Lift = +31 分
□ ⭐ 排除基线已达 97 分的安全性后，平均 = +39 分
```

> ⭐ **"安全性只 +1"是个重要的观察**：
> 基线已经 97 分，说明**在没有技能时 agent 也不会主动写危险代码**——
> 所以安全类技能的边际收益要看具体场景，不能指望平均数字。

**五个维度的含义**：

```
正确性    任务结果是否正确
可发现性  ⭐ 加入技能后，agent 能不能在合适的时候找到它
有效性    能否合理使用
效率      ⭐ 过程是否更高效
安全性    是否引入安全问题
```

```
⚠️ 注意：不启用技能时 agent 没有对应技能可调用，
   ⭐ 因此正确性/有效性的基线不能看作 agent 的原生能力分数
   ⭐ 可发现性和效率适合用来观察"加进去之后能不能找到并用好"
```

## 必须自问的代价

> ⭐ **技能不一定更省 token**：

```
Token 消耗   25,227 → 55,582   ⭐ 增加 120.3%
执行时间     34 秒  → 41.1 秒
```

```
□ 有些技能让 agent 少查资料、少走弯路
□ ⭐ 另一些技能增加了步骤和上下文
   ——在提高任务表现的同时，也带来更多 token 与耗时
□ ⭐ 即便技能能帮助完成任务，
   也必须单独检查它带来的执行成本
```

> ⭐ 呼应 `skill-governance` 的 `cost-control.md` 的三个 token 桶与
> `failure-modes.md` 的"过度验证是最大成本源"：
> **提升与代价必须一起看**。

## 数据的正确读法

> ⭐ **NVIDIA 自己也提醒了三点，这三点比数据本身更重要**：

```
① ⭐ 85% 的技能每个任务只运行了 1 次，15% 运行 2 次
   agent 真实任务评测本身有随机性——同一任务这次顺，
   下次可能走不同执行路径

② ⭐ 当前公布的是大量实验汇总后的"整个目录平均结果"，
   ⭐ 并没有提供置信区间

③ ⭐ 不同产品之间的 Skill Lift 差异，
   比两套 agent 框架之间的差异更明显
   Claude Code 与 Codex 平均相差约 5 分
   ⭐ 而不同产品之间的 Lift 分布在 +2 到 +46
```

```
结论：
□ 这组基准适合观察⭐ 整体趋势
□ ⭐ 要判断某个技能是否稳定有效，需要增加重复运行次数，
   观察多次运行之间的波动
□ ⭐ 单一平均分只能反映整体趋势，
   无法判断一个技能在所有 agent 和所有任务中的实际效果
```

> ⭐ 呼应 `metrics.md` 的边际效应与 `eval-tooling.md` 的 pass@k：
> **跑一次不算证据**。

## 四类评测用例

> ⭐ **完整模式下，评测数据要覆盖四类**：

```
① 显式用例   任务明确需要使用该技能提供的能力
② ⭐ 隐式用例  用户没有点名技能，但任务本身需要其中的知识或操作指导
③ ⭐ 上下文用例 是否需要使用技能，要结合具体任务上下文判断
④ ⭐ 负例     任务与该技能无关，agent 应避免错误加载或使用
```

```
每个用例包含：提示词 · 预期输出 · 可选的断言
```

> ⭐ 这四类正对应 `metrics.md` 的"负例 > 边界 > 正例"优先级，
> 也呼应 `test-pyramid.md` 的触发/行为分层。

## 自查

```
□ 是否做了"启用 vs 不启用"的配对对照？
□ ⭐ 两组是否跑在各自独立的环境里？
□ 是否检查了技能内部与跨技能的重复内容？
□ 是否用向量相似度做过重复检测？
□ ⭐ 是否同时统计了 token 与执行时间的代价？
□ ⭐ 是否知道"技能不一定更省 token"（可能 +120%）？
□ 是否跑了多次以避免随机性（而非只跑 1 次）？
□ ⭐ 是否知道"跨产品的差异 > 跨框架的差异"？
□ 是否理解"单一平均分只能反映趋势"？
□ 评测用例是否覆盖四类（显式/隐式/上下文/负例）？
□ ⭐ 是否有负例（不该加载时要能不加载）？
□ 是否知道"不启用时的基线 ≠ agent 原生能力分数"？
□ 安全性维度是否注意到基线已很高（边际收益有限）？
□ 是否把提升与代价放在一起判断？
```
