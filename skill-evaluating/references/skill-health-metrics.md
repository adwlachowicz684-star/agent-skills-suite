## 1. ⭐⭐⭐⭐ 六个维度

```
① ⭐⭐⭐⭐ 复用率
② ⭐⭐⭐⭐⭐ 调用成功率（⭐ 分三层）
③ ⭐⭐⭐⭐⭐ Token 收益
④ ⭐⭐⭐⭐⭐ 选择冲突率
⑤ ⭐⭐⭐⭐ 变体密度
⑥ ⭐⭐⭐⭐ 边界清晰度
```

**② 调用成功率要分三层**（这是本轮最实用的一条分层）：

```
技术成功：⭐ 流程跑通了
任务成功：⭐ 问题真的被解决了
结果成功：⭐⭐⭐⭐⭐ ⭐ 用户不需要再大改
```

> ⭐⭐⭐⭐⭐ 这三层⭐ 与我们已有的⭐ 多条结论⭐ 精确对应：
> ```
> 技术成功 ←→ "别把 HTTP 200 当成功"（200 = 请求被接受）
> 任务成功 ←→ "断言打在环境状态上"（不能只检查它说了正确的话）
> ⭐⭐⭐⭐⭐ 结果成功 ←→ ⭐⭐⭐⭐⭐ "⭐ schema 合规不保证值是对的"
> ```
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ **三层是⭐ 逐步收紧的，⭐⭐⭐⭐⭐ ⭐⭐⭐ 而⭐ 绝大多数监控⭐ 只测了第一层。**

**③ Token 收益**（一个此前没有的经济学视角）：

> ⭐⭐⭐⭐⭐ **"⭐ 使用技能后，⭐ 相比⭐ 直接通用推理，⭐ token 消耗⭐ 是否更低。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 技能的⭐ 存在⭐ 必须有⭐ 经济学意义。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 如果它⭐ 更长、更贵，⭐ 还没有⭐ 明显压缩推理成本，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 那它⭐ 只是把⭐ '抽象'⭐ 伪装成了⭐ '复杂'。"**

> ⭐⭐⭐⭐⭐ 最后半句⭐ 是本轮最锋利的一句，⭐⭐⭐⭐⭐ ⭐⭐⭐ 它⭐ 直接命中了
> `token-cost-optimization.md` 的"⭐ 伪技能陷阱"——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 而这里⭐ 给了⭐ 一个⭐ 可测量的判据：
> **带技能跑一次 vs 不带跑一次，总 token 谁多。**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐ 若⭐ 带技能更贵，⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 那它⭐ 大概率就是⭐ 伪技能。
> ⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 注意这⭐ 与 `roi-breakeven.md` ⭐ 互补：
> 那份算的是⭐ 人的时间，这份算的是⭐ 机器成本，⭐⭐⭐⭐⭐ ⭐ 两者都要为正才算真的值。

**⑤ 变体密度**：

```
⭐⭐⭐⭐ 一个技能簇里，存在多少"⭐ 本质相同、表面不同"的技能
⭐⭐⭐⭐⭐ ⭐ 如果只是 quick / deep / auto 这类⭐ 变体复制，
⭐⭐⭐⭐⭐ ⭐⭐⭐ 说明⭐ 系统⭐ 不会抽象，⭐⭐⭐ 只会复制
```

> ⭐⭐⭐⭐⭐ "不会抽象，只会复制"⭐ 这句⭐ 说得极准，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 而⭐ 它⭐ 与我们已有的⭐ 一条判据⭐ 恰好配对：
> ```
> 反转测试 / 空转测试 → 判断⭐ 一句话⭐ 有没有信息量
> ⭐⭐⭐⭐⭐ 变体密度       → 判断⭐ 一整份技能⭐ 有没有信息量
> ```
> ⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 同一个问题的⭐ 两个粒度。

**⑥ 边界清晰度**——一个技能能否明确回答四个问题：

```
我解决什么问题 · 我不解决什么问题
什么时候该调用我 · 什么时候不该调用我
```

> ⭐⭐⭐⭐⭐ 这四问⭐ 与 `description-scope-shape.md` 的
> "⭐ 写不出三条反触发条件就不该发布"⭐ 是⭐ 同一件事的⭐ 两个说法，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 而⭐ 这里⭐ 把它⭐ 变成了⭐ 一个⭐ 可对库里每个技能⭐ 逐条打的⭐ 分。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 那句后果描述也很准：
> ⭐⭐⭐⭐⭐ **"边界不清的技能，⭐ 短期看起来万能，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 长期会变成⭐ '什么都能沾一点，但什么都不够稳'。"**

## 2. ⭐⭐⭐⭐⭐ 只保留三个的话

```
① ⭐⭐⭐⭐⭐ 复用率      → ⭐⭐⭐⭐⭐ 它⭐ 最直接反映⭐ 技能是否真的⭐ 进入了系统主循环
② ⭐⭐⭐⭐⭐ 调用成功率  → ⭐⭐⭐⭐⭐ 它决定⭐ 这个技能⭐ 到底是资产还是风险
③ ⭐⭐⭐⭐⭐ 选择冲突率  → ⭐⭐⭐⭐⭐ 它⭐ 最快暴露⭐ 技能蔓延（sprawl）和⭐ 边界重叠
```

> ⭐⭐⭐⭐⭐ 三个放在一起⭐ 恰好回答三个问题：
> ```
> ⭐ 有没有人在用？（复用率）
> ⭐ 用了好不好用？（成功率）
> ⭐ 用的时候会不会打架？（冲突率）
> ```
>
> ⭐⭐⭐⭐⭐ 这套⭐ 与我们已有的⭐ 度量⭐ 是⭐ 互补而非重复：
> `adoption-metrics.md` 的四个组织级指标⭐ 看的是⭐ 人（采纳率、返工率），
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 而⭐ 这三个⭐ 看的是⭐ 技能本身在系统里的运行状态。
> ⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 一个⭐ 从组织视角，⭐ 一个⭐ 从系统视角——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 都做才完整，⭐⭐⭐⭐⭐ ⭐⭐⭐ 只做一个⭐ 会误判
> （例如：采纳率高但冲突率也高 = ⭐ 大家都在用一个⭐ 其实不该存在的技能）。

## 3. ⭐⭐⭐⭐⭐ 指标是问诊工具，不是淘汰表

> ⭐⭐⭐⭐⭐ **"⭐ 体检指标的⭐ 对象，⭐ 不只是技能本身，⭐⭐⭐⭐⭐ ⭐ 而是⭐ 系统的抽象质量。"**

| ⭐ 症状 | ⭐⭐⭐⭐⭐ 真正的病灶可能是 |
|---|---|
| 复用率低 | ⭐⭐⭐⭐⭐ 不是技能无用，而是⭐ **命名不对** |
| 成功率低 | ⭐⭐⭐⭐ 不是技能没价值，而是⭐ **边界太宽** |
| 选择冲突高 | ⭐⭐⭐⭐⭐ 不是调用器太笨，而是⭐ **技能树结构有问题** |
| 变体密度高 | ⭐⭐⭐⭐ 不是团队太懒，而是⭐⭐⭐ **没有合并制度** |

> ⭐⭐⭐⭐⭐ 这张表⭐ 是本轮最值钱的东西——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 因为⭐ 它把⭐ 每一个指标⭐ 都映射到了⭐ 一个不同的⭐ 修法上：
> ```
> 复用率低   → ⭐ 改名字（不是删技能）
> 成功率低   → ⭐ 收窄范围（不是重写）
> 冲突率高   → ⭐ 重构技能树（不是调路由参数）
> 变体密度高 → ⭐ 建立合并制度（不是责备团队）
> ```
>
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 而⭐ 那句总结⭐ 值得⭐ 单独记：
> ⭐⭐⭐⭐⭐ **"所以⭐ 体检指标⭐ 不是⭐ 一张冷冰冰的淘汰表，⭐⭐⭐⭐⭐ ⭐⭐⭐ 而是⭐ 一个问诊工具。"**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 这与 `skill-portfolio-audit.md` 的
> "⭐ 不删除，只调整作用域"⭐ 是⭐ 完全一致的立场：
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ **指标的用途是⭐ 告诉你该做什么手术，⭐ 不是⭐ 判死刑。**

## 4. ⭐⭐⭐⭐ 一个可对照的达标线

另一份来源给了⭐ 更硬的⭐ 阈值（工程化视角）：

```
⭐⭐⭐⭐ 技能复用率 ≥ 70%
   目标：⭐⭐⭐⭐ 80% 的新业务需求 ⭐ 能通过⭐ 组合现有技能⭐ 实现，⭐ 而非开发新技能

   达标：上线"会员等级自动升降"，
        ⭐⭐⭐⭐⭐ ⭐ 仅用 get_user_orders + calculate_total_spent + update_user_level
        ⭐⭐⭐⭐⭐ ⭐⭐⭐ ⭐ 三个已有技能⭐ 编排完成
   不达标：⭐ 每个新需求都写新技能，复用率 < 30%

⭐⭐⭐⭐ 平均故障恢复时间 MTTR ≤ 5 分钟
   达标：第三方限流 → ⭐⭐⭐ 自动降级返回缓存 → ⭐ 5 分钟内人工解除
   不达标：⭐⭐⭐ 重启服务 + 查日志 + 改代码 + 重新部署，耗时 2 小时
   实操：⭐⭐⭐⭐⭐ ⭐ 每个技能必须内置熔断器
        failure_threshold=3 · reset_timeout=300000（5 分钟），超阈值自动降级
```

> ⭐⭐⭐⭐⭐ "80% 的新需求靠组合实现"⭐ 这个目标⭐ 非常具体，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 而且⭐ 它⭐ 把"复用率"⭐ 从⭐ 一个统计数字⭐ 变成了⭐ 一个设计目标：
> ⭐⭐⭐⭐⭐ **如果每个新需求都要写新技能，⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 说明你的技能库⭐ 在结构上⭐ 没有被设计成⭐ 可组合的。**
>
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这与 `composition-patterns-types.md` 的"⭐ 显式依赖声明"
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 直接相关：⭐ **不声明依赖，⭐⭐⭐⭐⭐ ⭐⭐⭐ 就没法组合，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 于是只能每个需求⭐ 重新造一个。**
>
> ⭐⭐⭐⭐⫘ 熔断器的数字也值得抄：**failure_threshold=3**——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 又一次出现了"三次"这个⭐ 反复出现的停止阈值
> （systematic-debugging 的三次修复规则、无限循环的重试上限、
> 代理冲突的三次失败回 L2 重估）。

## 5. ⭐⭐⭐ 三条黄金原则

```
设计时：⭐⭐⭐ 一个技能只做一件事，且做好一件事
实现时：⭐⭐⭐⭐ 资源加载要"用时必有，不用不载"
运行时：⭐⭐⭐⭐⭐ 执行过程要"可观测、可中断、可回滚"
```

> ⭐⭐⭐⭐ 第二条⭐ 就是⭐ 渐进式披露的⭐ 中文最精炼表述；
> ⭐⭐⭐⭐⭐ 第三条⭐ 则⭐ 把我们散落各处的⭐ 多条要求⭐ 收成了六个字：
> ```
> 可观测 ←→ 决策日志 + 调用日志 + 埋点（skill-observability）
> 可中断 ←→ 前置门禁快速失败 + 重试预算（preflight-gate / trace-debugging）
> 可回滚 ←→ 版本化 + 灰度 + 歧义时默认回滚（gray-release / rot-rollback）
> ```
>
> ⭐⭐⭐⭐ 配套的⭐ 效果数据（同一来源）：
> ⭐⭐⭐ **"性能提升 3 倍，同时维护成本降低 50%"**。

## 速查

```
□ ⭐⭐⭐⭐⭐ 调用成功率分三层：技术成功(流程跑通) · 任务成功(问题真解决)
   ⭐⭐⭐⭐⭐ 结果成功(⭐ 用户不需要再大改) ← ⭐⭐⭐⭐⭐ 绝大多数监控只测第一层
□ ⭐⭐⭐⭐⭐ Token 收益：⭐ 带技能 vs 不带，总 token 谁多？
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 更长更贵却没压缩推理成本 = ⭐ 把"抽象"伪装成了"复杂"（伪技能陷阱）
   ⭐⭐⭐⭐ ⭐ 与 ROI 互补：那份算⭐ 人的时间，这份算⭐ 机器成本，⭐⭐ 两者都要为正
□ ⭐⭐⭐⭐ 变体密度：quick/deep/auto 这类复制 = ⭐⭐⭐⭐⭐ ⭐ 系统不会抽象，只会复制
□ ⭐⭐⭐⭐ 边界清晰度四问：解决什么/不解决什么/何时该调/何时不该调
   ⭐⭐⭐⭐⭐ ⭐ 边界不清 → ⭐⭐⭐⭐⭐ "什么都能沾一点，但什么都不够稳"
□ ⭐⭐⭐⭐⭐ 只留三个：复用率(有没有人用) · 成功率(资产还是风险) · 冲突率(会不会打架)
□ ⭐⭐⭐⭐⭐ 指标是问诊工具不是淘汰表：
   复用率低→⭐改名字 · 成功率低→⭐收窄范围 · 冲突高→⭐重构技能树 · 变体密度高→⭐建合并制度
□ ⭐⭐⭐⭐ 达标线：复用率≥70%（80% 新需求靠组合实现）· MTTR≤5min（内置熔断器，阈值=3）
□ ⭐⭐⭐ 三原则：一技能一件事 · ⭐⭐⭐⭐ 用时必有不用不载 · ⭐⭐⭐⭐⭐ 可观测/可中断/可回滚
```

**一句话**：

> ⭐⭐⭐⭐ **"体检指标不是一张冷冰冰的淘汰表，而是一个问诊工具"——复用率低可能是命名不对而非技能无用、成功率低可能是边界太宽而非没价值、冲突高可能是技能树结构有问题而非调用器太笨；而最容易被忽略的一维是 Token 收益：带技能跑比不带还贵，那它只是把"抽象"伪装成了"复杂"。**
