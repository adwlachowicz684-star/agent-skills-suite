## 触发 ≠ 能用

> **看到技能首次被触发会让人以为确认了。并没有。**
> 触发只说明：Claude 找到了它、把你的提示匹配上了 description、拉进了正文。
> **至于它随后产出的是不是你要的东西，一个字都没说。**

**这是两种独立的失败模式**，混为一谈正是"演示时看着能用、
别人一上手就不可靠"的最常见原因。

所以测试必须**分开做两件事**：

```
① 发现（Discovery）：该触发的触发，不该触发的不触发
② 输出（Output）：触发了之后，产出符合预期
```

## 三层起步法

**① 先用最小配置验证被识别**

```yaml
---
name: test-skill
description: Test skill
---
## Instructions
输出 "Test successful"
```

能跑通就说明基础设置（目录、文件名、frontmatter）是对的。

**② 增量加功能，每步验证**

```
Step 1: 最小配置能跑 ✓
Step 2: 加基础指令        → 验证
Step 3: 定义输出格式      → 验证
Step 4: 加 references/    → 验证
Step 5: 加 scripts/       → 验证
```

> 一次性写完整的复杂技能，**出问题时无法定位是哪一层坏了**。

**③ 用不同的输入测**

```
正常用例：/code-review src/index.ts
边界用例：/code-review（不指定文件）
错误用例：/code-review nonexistent.ts
```

## 三类输入

写测试用例时，**用真实用户会打的字，不是你知道技能怎么工作后会用的措辞**。

| 类型 | 例子 |
|---|---|
| **正常** | "审查这个 PR 的安全问题" |
| **自然变体** | "检查一下这个 diff 有没有风险"、"这次改动会引入漏洞吗" |
| **近失样本** | "给我的 React 应用加 Tailwind 样式"（像但不该触发 demo-app 技能） |

> **至少包含一个刻意的近失样本**——它抓的是"description 太宽"，
> 而不是"太窄"。

OpenAI 官方的四类提示集设计：

| 类型 | 测什么 |
|---|---|
| **显式调用**（test-01） | 直接点名技能，确保名字/description 改动不破坏直接调用 |
| **隐式调用**（test-02） | 描述场景但不提技能名——测 description 够不够强 |
| **上下文调用**（test-03） | 加领域上下文/噪声，仍应触发 |
| **负面对照**（test-04） | 相邻但不该触发的请求 |

> 规模：**10–20 条就够发现回归**，不需要大基准集。
> 从小的 CSV 开始，遇到真实失败就加一行——它会长成"这个技能必须持续做对什么"的活记录。

## 基线对比

> **这是所有测试方法背后的核心技术**：同一个提示跑两次——
> **一次启用技能，一次禁用**，**两次都用全新会话**，然后比较输出。

> ⚠️ **全新会话比听起来更重要。** 写作/编辑技能时残留的上下文会悄悄掩盖指令本身的缺口
> ——你已经知道技能应该做什么，agent 可以依赖这个共享上下文，
> 而不是依赖技能正文足够清晰能独立成立。

**不改动 SKILL.md 就禁用技能**：

```json
{ "skillOverrides": { "your-skill-name": "off" } }
```

四种状态：

| 状态 | 含义 |
|---|---|
| `on` | 完全列出且可调用 |
| `name-only` | 只列名字无描述，仍可调用 |
| `user-invocable-only` | 对 Claude 隐藏，你仍可直接跑 |
| `off` | 完全隐藏（包括 `/` 菜单） |

## 断言行为不变量

> **技能测试真正要抓的不是全文输出，而是行为不变量。**
> 不管 agent 怎么组织语言，**该触发哪个技能、该调哪个工具、
> 该生成哪些文件、哪些安全边界不能越过**——这些必须稳定。

**最小回归框架四件套**：

```
cases.yaml    测试用例（先定义契约，再写 runner）
runner        执行任务
assertions    断言行为
trace report  记录轨迹
```

> ⚠️ **先定义 case，不是先写脚本。** 用例定义的是"这个技能到底承诺什么"，
> runner 只是执行契约的工具。**如果你连 case 都写不出来，说明边界还没想清楚。**

**断言写在"它留下了什么"上，而不是"它说了什么"**：

```javascript
expect(result).costUSD.toBeLessThanOrEqual(2)
expect(result).skills.activated.toInclude("refactor-code")
expect(result).toolsUsed.toInclude("read", "edit").not.toInclude("web")
expect(result).toolCalls.not.toIncludeInOrder([
  { name: "shell", args: { command: /rm -rf/ }, exitCode: 0 },
])
expect(result, workspace).file("src/foo.ts")
  .toHaveBeenModified().toContain(/function Foo/)
```

> 技能不会两次做完全相同的事——**所以测试断言的是它留下的东西**。
> 不放心就跑 N 次取通过率。

**可断言的四类不变量**：

| 类别 | 断言 |
|---|---|
| **成本** | token / 费用上限 |
| **技能** | 激活了哪个 |
| **工具** | 用了哪些、**没用**哪些 |
| **文件** | 哪些被修改、包含什么 |
| **顺序** | 工具调用序列 |

## 调试清单

### 技能不被识别

```
□ ls -la ~/.claude/skills/my-skill/      —— SKILL.md 存在吗
□ 文件名是否恰好 SKILL.md（大写）—— 不是 skill.md / Skill.md
□ frontmatter 冒号后是否有空格：name: my-skill ✓ / name:my-skill ✗
□ file ~/.claude/skills/.../SKILL.md     —— 是否 UTF-8（无 BOM）
□ /skills 命令里能看到吗 —— 看不到就是放置或格式问题
```

### 技能不自动触发

```
□ description 够具体吗（"审查 TypeScript PR 的安全与性能" vs "检查代码"）
□ 是否有 description 相近的其他技能在抢
□ 显式调用 /my-skill 能跑通吗（能 → 是触发问题；不能 → 是格式问题）
```

### 输出不符预期

| 症状 | 修法 |
|---|---|
| 输出随意 | 加输出模板/示例 |
| 步骤跳了 | 用 Step 1/2/3 编号，关键步骤标"必须" |
| 命令不对 | 补具体命令、工具名、参数 |
| 遇到异常就停 | 每步加"如果 X 则 Y"的兜底 |
| 自作主张加步骤 | 加"不要做 X"的明确禁止 |
| 只看结果不看过程 | **对照 body 逐项检查每一步是否执行** |

> ⭐ **改技能不改 AI**——行为不对，问题在 description 或 body，**不在 AI**。

## 缓存问题

> **改了技能但行为没变** —— 当前会话缓存了旧版本。

```
□ /reload-skills 刷新，或开新会话
□ name / description 在启动时读取，必须重启客户端
□ 参考文件改动通常立即生效，但 frontmatter 不会
```

## 自查

```
□ 是否分开测了"发现"和"输出"？
□ 最小配置阶段验证过吗？
□ 是否有至少一条近失负例？
□ 基线对比是否用了全新会话？
□ 断言是否写在"留下了什么"上（文件/工具/成本），而非"说了什么"？
□ 每次改完是否重跑了回归用例？
□ 改完是否刷新了缓存/重启？
```
