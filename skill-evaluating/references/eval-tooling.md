## 为什么必须跑 k 次

> ⭐ **测 agent 代码和测确定性代码根本不同：
> 一个技能跑通一次，可能有 40% 的时间会失败。**

**一次成功说明不了任何事。** 要的是分布，不是单点。

```
caliper run my-skill.eval.yaml --k 10 --baseline

ID      Task                          k(5)  pass@k
task-1  Extracts action items as JSON  5/5   100%  PASS

With skill 100%   No skill 60%   Delta +40%
```

---

## pass@k 与 pass^k

| 指标 | 含义 | 用途 |
|---|---|---|
| **pass@1** | 首次尝试成功率 | 基线体验 |
| **pass@3** | 3 次内至少成功一次 | **常用目标 >90%** |
| **pass^k** | **k 次全部成功** | **更高标准**，用于关键路径 |

> ⭐ **关键区分**：
> **能力评测**看 pass@k（低通过率，是改进目标）；
> **回归评测**看 pass^k（接近 100%，是保护目标）。
> **混在一起会导致错误的优先级判断。**

## --baseline 是杀手级功能

> ⭐ **它把一切都重跑一遍——不带你的技能——让你看到增量。**

| Delta | 含义 |
|---|---|
| **+40%** | 技能真的有用 |
| **0%** | 技能**什么也没做** |
| **−100%** | 技能**在帮倒忙** |

> 一个发人深省的实例：
> 连"JSON 抽取"这种**两年前的模型就能解决的任务**，
> 都能测出 **40% 的 delta**。
> **这证明了技能的真实价值，也证明不测基线就永远不知道。**

**评测量级建议**：

```
□ --k 5  快速信号
□ --k 10 发布前的可信度
□ 支持多后端：可用便宜模型（如 GPT-4o-mini）做评审，
  被测技能跑在另一个模型上
```

## 能力评测 vs 回归评测

**能力评测**（测"能做到以前做不到的事吗"）：

```markdown
[CAPABILITY EVAL: feature-name]
Task: 描述 Claude 应完成什么
Success Criteria:
  - 标准 1
  - 标准 2
Expected Output: 期望结果的描述
```

**回归评测**（确保改动没弄坏已有的）：

```markdown
[REGRESSION EVAL: feature-name]
Baseline: <SHA 或检查点>
Tests:
  existing-test-1: PASS/FAIL
  existing-test-2: PASS/FAIL
Result: X/Y passed (previously Y/Y)
```

**判据**：

```
能力评测 pass@3 > 90%
回归评测 pass^3 = 100%
```

## 三类评分器

| 类型 | 适用 | 例子 |
|---|---|---|
| **代码评分器** | 确定性检查（**优先**） | `grep -q "export function handleAuth" src/auth.ts` · `npm test` · `npm run build` |
| **模型评分器** | 开放式输出 | 打 1–5 分 + 给出理由 |
| **人工评分器** | 需要判断 | 标注风险等级 LOW/MEDIUM/HIGH |

> ⭐ **硬检查交给代码，rubric 交给评审者。**
> 能用 `grep` 判断的，绝不要花 token 让模型判断。

**退出码约定**（便于接 CI）：

```
0 全部通过 · 1 用例/技能失败 · 2 输入错误 · 3 provider 故障
```

**测试粒度建议三层**：单步 → trace → 多轮会话。

## 工具生态

| 工具 | 定位 | 适用 |
|---|---|---|
| **skill-creator** | 创建 + 验证 + 改进 | 三模式：Eval（查触发是否误触发）/ Benchmark（A/B 不同 description）/ Improve（按失败案例自动改进） |
| **Caliper** | 轻量 harness，跑 k 次打分 | **pass@k + baseline 对比** |
| **skilltest** | 多平台跑技能 + 自然语言断言 | **同一套测试跨 claude-code / cursor / 多模型对比** |
| **Promptfoo** | 提示/技能评测框架 | 批量跑用例、A/B |
| **gstack** | 开发者向 harness | **diff 驱动的测试选择**（只跑相关的高价测试） |
| **LangSmith / LangFuse** | 全链路追踪 / 可观测 | 生产监控与调试 |
| **Semgrep / SonarQube** | 静态扫描 | 敏感信息检测、代码质量交叉验证 |
| **WireMock / MockServer** | API Mock | 模拟外部依赖 |
| **Playwright + MCP** | UI 自动化 | 涉及 Web 交互的技能 |

**几个值得抄的设计**：

- **forward-testing**：启动一个**不知情的 subagent 当测试员**，给它任务让它用技能完成，再检查输出质量——**它不知道在测技能**，结果更真实
- **diff 驱动的测试选择**：按 git diff 自动选择要跑的测试，只跑相关的高价测试，而不是每次全跑
- **持久化评测产物**，与基线自动对比

## 分层原则

> ⭐ **只在能显著降低风险的地方，才加昂贵的 LLM-as-judge。**

```
层 1（便宜、免费、每次提交都跑）
  技能解析 · 文档生成 · 类单元测试的确定性检查

层 2（付费、按需跑）
  LLM 评审 · 端到端测试
```

> **这是"不让评测成本压垮 CI"的关键。**

**其他实测提示**：

```
□ 评测模型的能力很重要——
  某案例中 llama-3-3-70b 抓出了全部已知失败，小模型漏了 4–5 个
□ 成本量级：$0.64/run 的自建评测是可行的参考点
□ 二进制 pass/fail 对非确定性流程几乎无用——
  行为指纹能检出 86% 的回归，二进制测试是 0%
□ trace-first 离线模式：拿生产 trace 跑回归检查，零额外推理成本
```

## 自查

```
□ 是否跑了 k 次（而非只测一次就发布）？
□ 是否用了 --baseline 得到 delta（而非只看绝对通过率）？
□ 能力评测与回归评测是否分开（前者 pass@3，后者 pass^3）？
□ 硬检查是否交给了代码评分器（而非都让模型判）？
□ 是否有确定性检查优先的分层（便宜的每次跑、贵的按需跑）？
□ 退出码是否能接 CI？
□ 测试是否覆盖三层粒度（单步 / trace / 多轮）？
□ 是否用了"不知情测试员"（forward-testing）避免测试污染？
□ 是否按 diff 选择高价测试（而非每次全跑）？
□ 评测产物是否持久化并与基线自动对比？
```
