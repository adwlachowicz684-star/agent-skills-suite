## 1. ⭐⭐⭐ 三个是门槛

```
SkillsBench 数据：
  手工撰写的技能 → ⭐ 任务成功率⭐ 显著拉高
  模型自动生成的 → ⭐⭐ 反而⭐ 下降
  ⭐⭐⭐ ⭐ 每个任务挂载⭐ 超过 3 个技能之后，⭐⭐⭐ 成功率⭐ 还会进一步下滑
```

> ⭐⭐⭐ **"3"这个数字比"50 个技能该上两步路由"要严苛得多。**
> 后者说的是⭐ 路由效率（超过 50 个会选不准），
> ⭐⭐⭐ 前者说的是⭐ **同时挂载**——
> 哪怕你只有 20 个技能、路由很准，
> ⭐⭐⭐ **只要一个任务同时挂了 3 个以上，成功率就会掉。**

> ⭐⭐ 这与 `capability-offset-net-gain.md` 的机制解释完全一致：
> ⭐⭐⭐ 常驻的技能描述⭐ 即使没触发也会渗入判断，
> 后果之一是⭐ **验证环节被挤占**。
> **挂 3 个 = 3 份指令同时挤占验证余量。**

**另两条同源数据**（同一份来源）：

```
· 上下文装不下
· ⭐⭐ 模型自由发挥过头
· ⭐⭐⭐ 成功率随版本漂移
```

> ⭐⭐⭐ "成功率随版本漂移"是一个⭐ 独立命名的问题——
> 它与 `model-migration-audit.md`（提示跨模型只弱相关）、
> `skill-rot-rollback-discipline.md`（歧义时默认回滚）同源，
> ⭐⭐ 但这里把它列为⭐ **三类典型问题之一**，
> 说明它在实践中足够常见。

## 2. ⭐⭐ 一个实践者的独立佐证

```
"我之前一股脑装了 ⭐ 二十几个社区技能包，
 ⭐⭐ 结果 agent ⭐ 每次随机加载好几个，⭐ 上下文消耗巨大，⭐⭐ 任务质量反而下降。
 ⭐⭐⭐ 后来我把技能⭐ 精简到不到十个，每个都精挑细选，⭐⭐⭐ 效果立刻好转。"
```

> ⭐⭐⭐ **"技能不是越多越好，而是越精准越好。"**

> ⭐⭐⭐ 注意这里的机制与 SkillsBench 那条⭐ 不同但互补：
> ```
> SkillsBench：⭐ 单任务同时挂载 >3 → 成功率下滑（⭐ 并发挤占）
> 本份：      ⭐⭐ 库存 >20 → ⭐⭐ 随机加载好几个 → 质量下降（⭐ 选择噪声）
> ```
> ⭐⭐⭐ 两个独立来源，两个不同的量：
> **一个是"同时挂几个"，一个是"库里有多少"。**
> 合起来的建议很明确：**库要小（<10–20），单任务挂载要少（≤3）。**

**另一个小习惯值得抄**：

> ⭐⭐ **"目录名、name、description 里的⭐ 核心触发词⭐ 全部统一，减少干扰。"**

> ⭐⭐ 与 `naming-conventions.md` 的"一致性 > 形态"同源，
> ⭐⭐⭐ 但这里给了一个⭐ 更具体的做法：
> **三处（目录名 / name / 触发词）用同一个词**，
> 而不是"命名用一套、描述里用另一套同义词"。

## 3. ⭐⭐⭐ 三条工程化原则

**原则一：渐进披露的体量表**（第二个独立来源给的同一组数字）

| 层级 | 加载时机 | ⭐ 体量建议 |
|---|---|---|
| 1. 元数据（description） | ⭐ 始终 | ⭐⭐ ≈100 token |
| 2. SKILL.md 主体 | 命中触发后 | ⭐⭐⭐ ≤5000 token / ≤500 行 |
| 3. 引用脚本与文档 | 步骤中按需 | 无硬上限，但需分割到 references/ 与 scripts/ |

> ⭐⭐⭐ **"元数据是模型判断是否加载技能的⭐ 唯一依据，
> ⭐⭐⭐ ⭐ 写得模糊等于这个技能⭐ 不存在。"**
>
> ⭐⭐ 这是我们已有的"description 是唯一发现机制"的⭐ 第四个说法。

**原则二：把确定性锁进脚本**

```
凡是"⭐ 无论谁跑结果都必须一致"的逻辑——
  命名规则 · SQL 模板 · 检查清单 · 命令拼接
⭐⭐⭐ → ⭐ 全部编码到 scripts/ 下的可执行文件
⭐⭐ ⭐ 模型只负责⭐ 解释失败原因与下一步
```

| 场景 | ❌ 错误做法 | ✅ 正确做法 |
|---|---|---|
| 校验 CSV 头 | 让模型"读一下表头" | ⭐ `scripts/check_header.py` 返回 0/非 0 |
| 命名生成 | 模型自由拼接 | ⭐ `scripts/next_name.py` 输入前缀输出合规名 |
| 提交前检查 | 提示词里"请运行 lint" | ⭐ `scripts/pre_commit.sh` 强制串联 lint + test |

> ⭐⭐⭐ 第三行最值得记：**"提示词里写'请运行 lint'"是错误做法**——
> 因为那是一句⭐ 请愿，不是一次执行。
> ⭐⭐ 这与 `determinism-boundary.md` 的"Hooks 用于模型不可被信任去遵守的事"、
> `feedback-loop-design.md` 的"规则升级为代码"是⭐ 同一条原则的
> ⭐⭐⭐ **第四个独立来源**。

**原则三：写 "How" 不写 "What"**

```
❌ "Python 是一种编程语言"
✅ "用 pandas.read_csv() 加载 CSV，分三步完成"
⭐⭐⭐ 给出⭐ 前后对比 · Few-shot 示例 · ⭐⭐⭐ 踩坑点
      ⭐⭐ 比⭐ 抽象原则⭐ 有效得多
```

> ⭐⭐ 与 `knowledge-delta-checklist.md` 的
> "该有的是模型不知道的"、`eight-practical-lessons.md` 的"写指令不写论文"
> 同源。⭐⭐⭐ **"How 不 What"是最精炼的表述。**

## 4. ⭐⭐⭐ 与已有证据拼起来

把所有关于"技能数量与规模"的门槛排成一条曲线：

```
单任务同时挂载 ⭐⭐⭐ ≤3      （SkillsBench：超过 3 个成功率下滑）
库存           ⭐⭐ 10–20     （实践者：20 多个时随机加载、质量下降）
路由需要两步   ⭐⭐ 50        （routing-tiers：>50 上模型决策+两步路由）
注册中心       ⭐ >50         （skill-decay-governance）
```

> ⭐⭐⭐ 这条曲线以前是零散的，现在第一次⭐ 完整了。
> 其中⭐ **"≤3"是最容易被违反的**——
> 因为它不是关于库的管理，而是关于⭐ **单个任务的设计**：
> 你很容易让一个复杂任务同时挂上四五个技能，而不觉得有什么问题。

## 5. ⭐⭐ 该怎么做

```
① ⭐⭐⭐ 设计任务时，⭐ 显式数一数会同时挂几个技能（目标 ≤3）
② ⭐⭐ 库存精简到 10–20，⭐⭐ 每个精挑细选
③ ⭐⭐ 目录名 / name / 核心触发词⭐ 三处统一
④ ⭐⭐⭐ 凡是"无论谁跑结果都必须一致"的 → ⭐ 立刻搬进 scripts/
   ⭐⭐⭐ 特别检查：⭐ 正文里有没有"请运行 X"这种请愿句式
⑤ ⭐⭐⭐ 写 How 不写 What；⭐ 给前后对比 + 踩坑点
⑥ ⭐⭐ 定期跑⭐ 不带技能的评测（判断是否该退役）
```

## 速查

```
□ ⭐⭐⭐⭐ SkillsBench：⭐⭐ 每个任务⭐ 挂载超过 3 个技能，⭐⭐⭐ 成功率进一步下滑
   ⭐⭐ ⭐ 这是"同时挂载"而非"库存量"，比 50 那条严苛得多
□ ⭐⭐ 模型自动生成的技能⭐ 反而下降（第二个来源印证）
□ ⭐⭐ 独立佐证：库存 20+ → ⭐ 随机加载好几个 → 质量下降
   ⭐⭐⭐ 精简到 <10 后⭐ 效果立刻好转；"不是越多越好，是越精准越好"
   ⭐⭐⭐ 两个量不同：⭐ 同时挂几个(≤3) vs ⭐ 库里有多少(10–20)
□ ⭐⭐ 目录名 / name / 核心触发词⭐ 三处统一

□ ⭐⭐⭐ 体量：元数据 ≈100 token · 主体 ≤5000 token/≤500 行 · 引用按需无上限
   ⭐⭐⭐ "元数据是唯一依据，写得模糊等于不存在"（第四个说法）
□ ⭐⭐⭐ 确定性锁进脚本：⭐⭐⭐ ⭐ 提示词里写"请运行 lint"是错误做法（是请愿不是执行）
   ⭐⭐⭐ 模型只负责⭐ 解释失败原因与下一步（第四个独立来源）
□ ⭐⭐⭐ 写 How 不写 What；⭐ 给前后对比 + 踩坑点

□ ⭐⭐⭐ 门槛曲线：同时挂载 ≤3 · 库存 10–20 · 两步路由 50 · 注册中心 >50
   ⭐⭐⭐ ⭐ "≤3"最易违反——它是关于⭐ 单个任务的设计，不是库的管理
```

**一句话**：

> ⭐⭐⭐ **SkillsBench 的硬数字是：每个任务同时挂载超过 3 个技能，成功率就会进一步下滑——这比"库里超过 50 个才需要两步路由"严苛得多，因为它约束的是单个任务的设计而非库的规模；
> 配套的三条工程化原则里最实用的是"凡是无论谁跑结果都必须一致的逻辑都锁进 scripts"，所以正文里出现"请运行 lint"这种请愿句式就是错误。**
