## 1. ⭐⭐⭐⭐⭐ 标尺本身会变形

我们花大力气建了测试集，然后把它当成**固定的标尺**：

```
技能改了 → 跑测试集 → 看分数
```

> ⭐⭐⭐⭐⭐ **但标尺本身也在变。**
> 而分数是"被测物"和"标尺"的比值——
> ⭐⭐ 你无法从分数判断是哪一边变了。

这解释了那个常见困惑：

```
"分数一直很稳，为什么线上还是出问题？"
→ ⭐⭐⭐ 因为标尺和被测物一起烂掉了，
   比值没变，绝对值变了。
```

## 2. ⭐⭐⭐⭐ 四种腐烂

**① ⭐⭐⭐⭐⭐ 过拟合（最常见）**

```
测试集建好后，你照着它调技能
→ 技能越来越贴合这 20 条
→ ⭐ 分数越来越高，泛化越来越差
```

判据（`description-tuning-official-loop.md` 同源）：
**每一轮都在涨，就是过拟合的典型曲线。**

**② ⭐⭐⭐⭐ 陈旧**

```
测试用的是六个月前的数据格式 / 接口版本 / 业务规则
技能已经按新规则改了，但测试还在考旧规则
→ ⭐ 分数看起来在掉，其实掉的是标尺
```

**③ ⭐⭐⭐ 覆盖空洞**

```
测试集覆盖了 A、B、C 三个分支
后来技能加了 D 分支
→ 测试集全绿，因为 D 根本没被测
```

> ⭐⭐⭐ 这一类和"结构正确的废话"是同一形状：
> **所有检查都过，因为该检查的东西不在检查范围内。**

**④ ⭐⭐⭐ 答案漂移**

```
当初标注的"正确答案"，现在看是错的
（业务规则变了 / 当初标错了）
```

最容易发生在**主观标注**上（质量分、是否充分）。

## 3. ⭐⭐⭐⭐⭐ 第一个信号：全绿

> ⭐⭐⭐⭐⭐ **一份长期 100% 通过的测试集，不是一个好消息。**
> **它说明这份测试集已经不再提供信息了。**

这与我们已有的两条完全同源：

```
· 一份从未抓到过任何问题的清单，说明检查得还不够硬
· ⭐ 恒过的断言比没有断言更危险
```

> ⭐⭐⭐⭐ **三条是同一句话的三种说法**：
> **一个永远通过的检查，价值为零，而且它还在给你虚假的信心。**

具体的诊断三问：

| 问 | 全绿意味着 |
|---|---|
| 最近一次改动，它抓到了吗？ | 没抓到 → 覆盖空洞或过拟合 |
| 换模型跑，分数变了吗？ | 没变 → ⭐ 测的是模型本来就有的知识 |
| 故意注入一个错，它抓到了吗？ | ⭐⭐ 没抓到 → 断言失效 |

> ⭐⭐⭐⭐ 第三问是最强的检查，且成本极低。
> **定期给技能注入一个已知错误，看测试集会不会红。**
> 不红，就是标尺坏了。

## 4. ⭐⭐⭐ 三类维护动作

| 动作 | 做什么 | 频率 |
|---|---|---|
| ⭐ **注入测试** | ⭐⭐ 故意改坏技能，看测试集是否报警 | 每月 / 每次大改 |
| **补充覆盖** | 技能新增分支 → 同步加用例 | ⭐ 随 PR（写进 checklist） |
| **陈旧复查** | 检查标注答案是否仍然成立 | 每季度 |

> ⭐⭐⭐ **第一类最重要，也最没人做。**
> 因为它测的不是技能，是测试集——
> 而我们默认标尺不需要被检验。

第二类的落地方式很关键：**不能靠"记得加"**，
要变成 PR 模板里的一条勾选项：

```
- [ ] 本次改动是否新增了分支/场景？新增的用例在哪个文件？
```

⭐ 这和"把 P0/P1 后果写进门禁"是同一手法——**把建议变成结构**。

## 5. ⭐⭐⭐⭐ 维护的触发条件

不要定时维护（会变成走过场），按事件触发：

| 事件 | ⭐ 动作 |
|---|---|
| ⭐ 线上事故 | ⭐⭐ **必须补一条用例，永久留下**（`ci-skill-validation.md`） |
| 模型版本升级 | ⭐ 全部重跑，分数同变则说明标尺与被测物分离得还行 |
| 技能新增分支 | 补用例 |
| ⭐ 连续 N 次全绿 | ⭐⭐ 立即做一次注入测试 |
| 业务规则变更 | 陈旧复查 |

> ⭐⭐⭐ 第一条和第四条是两条**必须**的动作，其余是**应该**。
> 这样分档才能让"必须"的真的被执行。

## 6. ⭐⭐ 两个反直觉的做法

**① 保留一部分"永远不该通过"的用例**

```
用例集里刻意放几条"技能不该响应"的查询
如果哪天它们通过了 → ⭐⭐⭐ 边界被放宽了，且没人知道
```

> ⭐⭐⭐ 这是防"答案漂移"最便宜的手段：
> **它让你的标尺自带一个报警装置。**

**② 测试集也要有版本**

```
evals/v1/  ← 历史可比
evals/v2/  ← 改了口径就升版
```

⭐ 只保留最新版会导致：**你无法回答"我们比三个月前好了还是差了"**。
而这个问题恰恰是评估存在的根本理由。

代价是维护两套，所以折中：**只在口径变化时升版，补充用例不升版**。

> ⭐⭐⭐ **定期把技能改坏一次。测试集不报警，说明坏的是测试集。**
