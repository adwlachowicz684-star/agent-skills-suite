## 1. ⭐ 模型说"已预订"，不等于真的有预订

Anthropic 讲 agent eval 时强调的关键点：

> ⭐ **断言要打在环境状态上，而不是模型输出上。**

```python
# ❌ 反例：只检查模型说了什么
assert "已放量" in 最终输出

# ✅ 正例：检查环境的真实状态
assert 查询部署("payments-api").版本号 == "1.42.0"
assert 查询SLO("payments-api").错误预算百分比 > 50
```

> ⭐ 这个区别决定了你的 eval **能不能真的抓到失败**。
> 前者只要模型"说了正确的话"就过——**它可能什么都没做**。

## 2. 优质断言的三个特征

```
① 可程序验证   输出是合法 JSON、文件存在且维度正确
② 具体可观测   图表坐标轴有标签、报告包含 ≥3 条建议
③ ⭐ 非脆弱     ⭐ 不绑定固定句式，允许合理表述差异
```

> ⭐ 第 ③ 条容易被忽略：
> 断言写得太死（"必须包含'综上所述'"）会误报，
> 把合格输出判成失败，然后你会开始怀疑整套 eval。

**评分方式**：

```
脚本校验  格式、计数、文件存在性 —— ⭐ 稳定可复用，优先
LLM 评分  内容完整性、逻辑合理性 —— 语义层，选择性用
```

**评分原则**（两条很硬）：

```
· ⭐ PASS 必须有 concrete 证据，不"疑罪从无"
· ⭐ 同步校验断言本身——剔除恒过/恒失败的无效断言
```

> ⭐ 第二条极少有人做，但极其重要：
> **一个永远通过的断言跟没有断言一样，而且更危险**——
> 它给你虚假的安全感。这与 `golden-rules-failure-modes.md`
> "从未抓到问题的清单说明检查得不够硬"是同一条。

## 3. ⭐ 分层执行：确定性 → Rubric → 稳定性

**第一步：确定性断言**（先跑完再说）

```
能用代码判的绝不用模型判：
  输出的 JSON 能不能 parse
  HTML 里有没有混进 <script>
  该生成的文件在不在
  字数落没落在区间内

⭐ 零成本、零方差
⭐ 能在两秒内筛掉一半的失败样本
```

**第二步：Rubric**

```
把"好"拆成 4–6 个维度
每个维度 0–3 分
⭐ 每一档写死锚点
⭐ 写不出锚点的维度 → 说明不够具体，删掉或拆开
```

锚点示例：

```
结构完整性
  3 分  包含全部要求章节且顺序正确
  2 分  章节齐全但顺序错乱
  1 分  缺 1 个章节
  0 分  缺 2 个及以上
```

> ⭐ **打分可以交给 LLM-as-judge，⭐ 但判分标准必须人手写。**
> 每轮抽 10% 做人工复核，算一致性（Cohen's kappa），
> 低于阈值就回去改 rubric，**而不是改模型**。

**第三步：稳定性**

```
⭐ 同一条用例跑 5 次，5 次全过才算过
⭐ 单次通过率会把偶然误当成能力
```

---

## 4. ⭐ pass^k：跑 5 次全过才算过

```
Sierra 2024 年发布 τ-bench 时用的 pass^k，就是这个思路
⭐ 单次跑通只能证明运气；跑五次都通，才叫可交付
```

**更宽的通用口径**：

```
agent 非确定，⭐ 每个用例跑 3–5 次看分布，不看单次
⭐ 每个用例用干净环境，防止上下文串味掩盖真实失败
```

## 5. ⭐ 最小可用路由测试集（20 条）

路由**最容易测、也最该先测**。建议每个技能维护 20 条样本：

| 类型 | 数量 | 目的 |
|---|---|---|
| 典型正例 | 5 | 验证核心任务能触发 |
| 近义改写 | 5 | ⭐ 验证自然表达漂移下的鲁棒性 |
| ⭐ 强负例 | 5 | ⭐ 验证排除条款生效 |
| 相邻技能边界 | 5 | 验证候选之间的区分度 |

> ⭐ **"强负例"这组特别有价值**——
> 它测的就是你在"不适用于"里写的那些东西到底有没有生效。

**另一份 20 条配比**（可作为交叉参考）：

```
6 典型正例 · 4 近义正例 · 4 强负例
2 碰撞 · 2 有状态失败 · 2 对抗
```

**一条有用的 trace 至少应包含**：

```
· 技能 id 与版本号
· ⭐ 触发时的全部候选及选中理由
· 正文加载范围
· 脚本调用、参数、输出
· 检查点结果
· 回滚事件
```

**调试流程**（四步）：

```
① 复现      固定 prompt、模型、工具状态、环境变量
② 分层重放  先 mock 工具验证步骤逻辑，再接真实环境验证副作用
③ 差异对比  ⭐ 并排看成功与失败的 trace，定位差异出在
            路由 / 参数 / 分支 / 检查点
④ ⭐ 最小化修复 ⭐ 每次只改一类（description、正文、脚本、数据）
               然后重跑同一份评测集
```

> ⭐ 第 ④ 步的理由很实在：
> **一次改四样，效果好了不知道是哪样的功劳；效果差了更惨，得再改回来。**

## 速查

```
□ ⭐ 断言打在环境状态，不是模型输出
□ 断言三特征：可程序验证 / 具体可观测 / 非脆弱
□ ⭐ PASS 要有 concrete 证据
□ ⭐ 剔除恒过/恒失败的无效断言
□ ⭐ 顺序：确定性断言 → Rubric → 稳定性
□ ⭐ Rubric 每档写死锚点；标准人手写，判分可交给 LLM
□ ⭐ pass^5：跑 5 次全过才算过
□ ⭐ 20 条路由集：5 正 / 5 改写 / 5 强负 / 5 边界
□ 每次只改一类，然后重跑同一份评测集
□ ⭐ 10% 人工复核算 kappa，低了改 rubric 不是改模型
```

**一句话**：

> ⭐ **模型说"已预订"，不等于环境里真的存在预订记录。**
