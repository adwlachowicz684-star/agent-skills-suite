## 基线是什么

> ⭐ **基线不是"上一次的结果"，
> 是一组固定用例在两个版本上的对比。**

```
基线 = 固定用例集 × 固定判定标准 × 可重跑
```

**三种基线**（用途不同）：

| 类型 | 对比对象 | 回答什么 |
|---|---|---|
| **无技能基线** | 启用 vs 不启用 | ⭐ 这个技能到底有没有用 |
| **版本基线** | 新版 vs 旧版 | 这次改动是改进还是退化 |
| **跨模型基线** | 模型 A vs 模型 B | 换个模型还能用吗 |

呼应 `skill-lift-eval.md`：
**唯一有意义的问题是"有这个技能比没有好多少"**。

## 套件的构成

**规模建议**：

```
□ 起步：20 条（10 正 / 10 负）
□ ⭐ 正式：40–60 条，含边界与冲突
□ 形态：固定 prompt + 期望结果（断言）
```

**用例类型分布**（呼应 `metrics.md` 的 20 条起始组合）：

```
□ 正向：该触发的
□ 改述：同一意图的不同说法
□ ⭐ 硬负例：明确不该触发的
□ ⭐ 冲突：与另一个技能边界模糊的
□ 状态：依赖前置条件的
□ 对抗：试图绕过护栏的
```

**优先级**：⭐ **负例 > 边界 > 正例**。

## 跑法

```
1. 固定用例集，不打乱
2. ⭐ 每个用例跑 3 次（模型行为非确定性）
3. 记录：是否触发、输出是否通过断言、token、耗时
4. 与基线版本对比
```

**为什么跑 3 次**：

> ⭐ **单次结果不能区分"真的变好了"和"这次运气好"**。
>
> 呼应 `skill-lift-eval.md` 的诚实提醒：
> 85% 的公开评测只跑 1 次，**没有置信区间**。

**分离记录触发与输出**：

```
□ 触发率（该触发的 / 不该触发的）
□ ⭐ 输出通过率（触发之后做对了吗）
□ 两者分开统计——混在一起看不出该修哪里
```

呼应 `test-pyramid.md` 的核心论点：
**四层失败原因完全不同，混着测等于两眼一抹黑**。

## 判定：改进还是转移

> ⭐ **确认失败模式是"减少"而非"转移"。**

```
A 类失败减少，B 类失败也减少  → 真改进
A 类减少，B 类增多且量相当    → ⭐ 转移了，等于没改
总数减少但新增一类失败         → ⭐ 需要判断新失败是否更可接受
```

**记录格式**：

```
改动：description 加入"批量转换"触发词

       改前      改后
漏触发   7         2      ⭐ 减少 5
误触发   1         3      ⭐ 增加 2
输出错   4         4      不变

判定：⭐ 净改善（漏触发是主要问题，误触发代价更低）
     但需观察误触发是否继续上升
```

> ⭐ 最后那句"需观察"很重要——
> 一次对比只说明当下，趋势要看多次。

## 基线要能重跑

```
□ ⭐ 用例集进版本控制
□ ⭐ 判定标准写死（不要每次靠人判断）
□ ⭐ 环境固定（模型版本、技能版本、温度）
□ 结果可导出对比
```

**一条硬要求**：

```
□ 能判定的断言进脚本（exit code / JSON 字段）
□ 需要判断的才交给 LLM judge
□ ⭐ 混在一起会让基线每次跑出不同结果
```

呼应 `test-pyramid.md` 第 1 层：
**结构 lint 不用 LLM 判**——确定性检查必须确定性。

## 常见错误

| 错误 | 后果 | 修法 |
|---|---|---|
| 只跑一次 | 把运气当改进 | ⭐ 跑 3 次取趋势 |
| 用例每次不同 | 无法对比 | ⭐ 固定用例集进版本控制 |
| 只测正向 | 看不到误触发 | ⭐ 负例优先 |
| 判定标准靠人 | 基线漂移 | ⭐ 可判定的进脚本 |
| 触发与输出混统 | 不知道修哪里 | 分开记录 |
| 只看总数 | 漏掉"转移" | ⭐ 按失败类型分类统计 |
