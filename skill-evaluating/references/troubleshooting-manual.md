## 万能四步法

> ⭐ **遇到技能失效，严格按这个顺序，不要跳**：

```
第一步  校验文件加载（文件层）
        核对路径、文件名、编码、YAML 格式，重启客户端，
        看技能列表是否加载成功
        ⭐ 失败就停在这一层排查，不要往下测

第二步  手动强制调用（触发层）
        指名调用技能
        ⭐ 能执行 = description 触发规则的问题
        ⭐ 不能执行 = 文件加载失败

第三步  隔离冲突测试（优先级层）
        关掉其他所有技能、临时屏蔽全局 Rule，单独测当前技能
        排除规则覆盖与边界冲突

第四步  校验运行环境（环境层）
        切换 Agent 模式、检查依赖工具、跨平台复现
```

> ⭐ 呼应 `reload-debug.md`：
> **重启客户端往往没用**——要执行 `/reload-skills`。
> 技能系统有自己的缓存与注册表。

## 症状 → 原因 → 修法

| 症状 | 可能原因 | 修法 |
|---|---|---|
| **从不触发** | description 不匹配用户语言 | ⭐ 用用户的真实说法重写 description |
| **对错误查询触发** | description 太宽、无负向触发 | 收窄范围，加显式排除 |
| **间歇性触发** | 与另一技能重叠冲突 | 检查可组合性，消除歧义 |
| **触发了但输出错** | 指令含糊 | 加具体示例与预期输出格式 |
| **测试通过、生产不灵** | ⭐ **测试措辞是作者的词汇，不是用户的** | 用非作者的说法测 |
| **无法判断是否触发** | 无可观测性 | 加埋点 / 日志 |

**加载失败的四类结构原因**：

```
□ YAML frontmatter 缺失或畸形（引号未闭合、混用 tab 与空格）
□ description 超出平台字符上限
□ 标题层级不符合预期结构（H1 标题，H2 章节）
□ ⭐ 字段名含 Unicode 字符导致解析器出错
□ description 为空（模型没有任何可匹配的东西）
```

**加载不上的结构要求**：

```
□ ⭐ SKILL.md 必须在具名目录里，不能在 skills 根目录
□ ⭐ 文件名必须恰好是 SKILL.md（SKILL 全大写，md 小写）
□ 用 claude --debug 看加载错误，搜你的技能名
```

**优先级冲突**：

```
企业 > 个人 > 项目 > 插件

⭐ 如果有个企业版 "code-review"，你的个人 "code-review"
   每次都会被它赢——即使你改了个人版
修法：⭐ 改名（通常更省事），或找管理员
```

**插件技能不出现**：清缓存 → 重启 → 重装。还不行就是插件结构错了。

**运行时错误**：

```
□ 缺依赖——外部包必须已安装
□ 权限——脚本要 chmod +x
□ ⭐ 路径分隔符——统一用正斜杠，Windows 上也是
```

## 五步调试法（含一个很实用的技巧）

> ⭐ **核心是"看模型到底在想什么"**：

```
1. 开 debug 模式，看模型是否识别了技能、读了哪些文件
   ⭐ debug 日志里能看到技能描述是否被注入 prompt

2. 识别了但不执行
   → 问题在 description 的触发条件，去调 "Use when..." 部分

3. 执行了但顺序不对
   → 问题在正文流程表述
   → ⭐ 改成编号步骤，并加"必须"这类约束词

4. 顺序对但结果不对
   → 问题在 references 或脚本
   → ⭐ 单独测脚本，确认输出格式能被模型理解

5. 反复验证误触发
   ⭐ 每次改完 description，用一个"不该触发"的请求测试
```

> ⭐ **最实用的那个技巧**：
>
> **在 SKILL.md 正文开头临时加一段 Debug 节**：
> "运行步骤时，输出当前步骤名称和关键变量"
>
> 相当于给 agent 加日志，**对定位"模型在哪一步跑偏了"特别有用**，
> 改完再删掉即可。

**最小测试法**：

```
□ 不要用复杂场景测
□ ⭐ 造一个最简单的输入，把干扰因素降到最低
□ 先直白地指名调用（"请查看 X 技能并严格执行"），
  排除是不是描述匹配的问题，再回来调 description
```

**一个真实案例**（说明为什么要看日志）：

> 某个技能一直不生效，开日志才发现
> **agent 每次读取 SKILL.md 都超时**——
> 最后定位到技能目录里放了一个**几十 MB 的图片**，把上下文撑爆了。
> 压缩图片后立刻解决。

> ⭐ 呼应 `skill-distribution` 的 `packaging.md` 的孤儿资产检测与 `skill-refining` 的 `context-budget.md`：
> **技能目录里不要放大文件。**

## 六个高频具体故障

```
① Skill 没有触发
   查 description 触发关键词是否清晰
   是否有其他技能优先级更高、抢占了场景
   ⭐ 技能名是否符合命名规范（小写、横杠、不要中文）

② ⭐ 忘记读取 references 文件
   → SKILL.md 的步骤里⭐ 必须显式写"读取某文件"这个动作
   → 确认相对路径正确、区分大小写
   → 不要一次性强制读取大量参考文档

③ assets 模板渲染失败，占位符残留 {{xxx}}
   → 检查占位符写法前后一致
   → ⭐ 确认所有占位变量都收集到了用户输入
   → 模板内不要混入复杂判断逻辑

④ scripts 脚本调用报错
   → 检查路径与执行权限
   → 入参格式是否符合脚本要求
   → ⭐ 优先本地单独测脚本，确认能跑，再交给 agent 调用

⑤ 上下文超限、响应慢
   → ⭐ 按需读取，不要一次加载全部 references
   → 拆分大文档为多个小文件
   → 精简 SKILL.md 正文

⑥ 改了文件但 agent 没读到最新版
   → 多数工具只在启动时扫描技能目录
   → ⭐ 装完/改完必须重启（或 reload）
```

**环境层的三类问题**（本机正常、换环境就失效）：

```
□ ⭐ 运行模式不支持——某些平台的高级技能自动触发
   只在 SOLO / Agent 模式生效，普通聊天窗口不行
□ 依赖工具缺失——Python/Node/外部 API/本地脚本
□ ⭐ 平台兼容差异——各平台对字段支持度不同
   → 跨平台开发建议：⭐ 只保留 name、description 等通用字段
```

## 两个"看不见"的元问题

> ⭐ **这两个问题不会报错，只会让你一直用着一个坏技能。**

### 元问题 1：描述太宽或太窄（都不行）

```
❌ 太宽  "helps with coding tasks"
   → 和所有编码技能竞争，一个都赢不了
   → ⭐ agent 会降低它的优先级，因为它对任何具体查询都不是最佳匹配

❌ 太窄  "generates TypeScript interfaces from OpenAPI 3.1 YAML specifications"
   → 只对这一句话触发
   → 用户说"make types from my API spec"或
     "convert this swagger file to TypeScript" 就完全错过

✅ 中间地带  2–5 句，覆盖三层：
   显式触发    这个技能做什么
   隐式触发    它解决什么问题
   上下文触发  什么情境说明它相关
   ⭐ 目标：能匹配上用户描述该功能的 80% 种说法
```

### 元问题 2：没有反馈闭环（看不见就没法修）

> ⭐ **这是元问题中的元问题**：

```
□ 手动测试用的是你写 description 时的那套措辞——当然会匹配
□ ⭐ 真正的问题是：换别人用别的说法，它还匹配吗？
□ 没有可观测性，你就是在盲调
   修完 description、部署上去、然后祈祷
```

```
□ ⭐ 多数用户不会报告"agent 没用我以为它会用的技能"
   他们只是得到一个次优回答，然后继续干活
□ 手动调试是点状的——今天修的，明天又会冒出新失败模式
□ ⭐ 手动调试不适用于 10+ 技能的workspace，
   也不适用于已发布、用户词汇无法预测的技能
```

**该做什么**：

```
□ ⭐ 请同事描述他想要什么，然后用他的原话测
□ 记录"本该触发但没触发"的查询及其确切措辞——这就是词汇缺口
□ 加可观测性：真实触发率，而不是假定的触发率
□ ⭐ 监控"应该触发但没触发"（missed trigger）
```

## 自查

```
□ 是否按四层顺序排查（而非跳着试）？
□ 是否先跑 validator（结构问题先排除）？
□ ⭐ 是否知道"指名调用能执行 = description 问题"这个判据？
□ 是否检查了优先级冲突（企业 > 个人 > 项目 > 插件）？
□ 是否知道 SKILL.md 必须在具名目录、文件名恰好 SKILL.md？
□ 运行时错误是否查了依赖/权限(chmod +x)/路径分隔符？
□ ⭐ 是否用过"临时 Debug 节输出步骤名"这个技巧？
□ 是否用了最小测试法？
□ ⭐ 是否检查过技能目录里有没有大文件（撑爆上下文）？
□ 是否显式写了"读取 references 文件"这个动作？
□ 是否本地单独测过脚本再交给 agent？
□ ⭐ 是否考虑过环境层（运行模式 / 依赖 / 平台字段兼容）？
□ description 是否既不宽到竞争失败、也不窄到只匹配一句话？
□ ⭐ 是否请同事用他自己的话测过？
□ 是否有 missed trigger 的可观测手段？
```
