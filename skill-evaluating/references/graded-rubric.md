## 1. 官方为什么反对全有或全无

> ⭐ **官方明确说：不要用全有或全无的 rubric。**

原因很具体：

```
改一个措辞可能连带影响其他维度
→ 全有或全无会把这些连带影响掩盖成"整体不通过"
→ ⭐ 你就看不到真实的回归发生在哪一维
```

举例：一次改动让"格式"变好但"完整性"变差，
全有或全无只会告诉你"失败"，
**你不知道是哪一维退步了，也无法判断净收益**。

---

## 2. 正确做法：每维独立 0–1

```json
{
  "completeness": 1,
  "format": 0,
  "accuracy": 1
}
```

> ⭐ **每个维度独立给 0–1 分**，这样：
> - 能看出哪一维退步
> - 能算加权总分
> - 改动的效果可归因

## 3. 与"避免全有或全无评分"的关系

这与 `metrics.md` / `judge-design.md` 里反复出现的原则一致：
**评分必须机器可读、可分解**，
不能是"通过/不通过"一个比特。

配套要求（与 `four-dimension-eval.md` 一致）：

```
⭐ 用 --output-schema 约束返回固定格式 JSON
⭐ 否则跨版本的分数无法量化对比
```

## 4. 行为锚点的写法

每个维度给出**具体行为**作为锚点，而不是抽象形容词：

```json
{
  "code_style": {
    "description": "代码是否符合 ESLint 规范",
    "scale": "1-5",
    "anchors": {
      "1": "完全不符合规范",
      "3": "部分符合，有小问题",
      "5": "完全符合规范"
    }
  }
}
```

> ⭐ 锚点必须是**可观察到的行为**，
> 不是"好/较好/一般"这类需要主观判断的标签。

这与 `quality-rubric.md` 的"1-5 行为锚点"是同一套方法的简化版。

## 速查

| 要做 | 不要做 |
|---|---|
| ✅ 每维独立 0–1 | ❌ 单一通过/不通过 |
| ✅ 固定 JSON schema | ❌ 自然语言评分 |
| ✅ 锚点是具体行为 | ❌ 抽象形容词 |
| ✅ 能归因到维度 | ❌ 只知道"失败了" |
