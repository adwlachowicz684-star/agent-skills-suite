## 1. SkillsBench：受控条件下的乐观结论

86 项任务、11 个领域、7,308 条轨迹、7 种模型-框架配置，三个条件对照：

```
无技能基线        24.3%
人工筛选技能      40.6%   ⭐ +16.2 pp
自生成技能        21.0%   ⭐ −1.3 pp
```

**领域差异极大**（这是最该记住的一张表）：

```
医疗健康      +51.9 pp
制造业        +41.9 pp
网络安全      +23.2 pp
自然科学      +21.9 pp
能源          +17.9 pp
办公/白领     +17.8 pp
金融          +15.1 pp
媒体内容      +13.9 pp
机器人        +7.0 pp
数学          +6.0 pp
⭐ 软件工程    +4.5 pp   ← 最低
```

> ⭐ 规律：**技能在"基础模型预训练覆盖不足"的领域帮助最大。**
> 临床数据协调、制造缺陷代码本、SEC 文件分析——这些模型没见过足够多；
> 而 git 工作流和标准编码模式，模型早就熟了。

**体量也是反直觉的**：

```
2–3 个模块的聚焦技能   +18.6 pp
4 个以上技能           +5.9 pp    ⭐ 收益递减
"详细"型（中等长度、聚焦）  +18.8 pp
⭐ "全面"型（详尽文档）     −2.9 pp   ⭐⭐ 有害
```

**技能是算力均衡器**（这条很有战略价值）：

```
⭐ Claude Haiku 4.5 带技能  27.7%
⭐ 胜过 Claude Opus 4.5 不带技能  22.0%
```

**自生成技能无效**（这条对"让 AI 自己写技能"泼冷水）：

```
⭐ 模型还不能可靠地写出它所受益的那种程序性知识。
失败模式不是"拒绝写"，而是写出来不精确/不完整：
   "用 pandas 处理数据"（没有具体 API 模式）
   或者只是把任务复述一遍的通用脚手架
```

**以及一个诚实的保留**：84 项可比任务中 **16 项出现负增益**。

## 2. ⭐⭐ 34,198 个真实技能：优势被压缩到 3pp

UCSB / MIT CSAIL / MIT-IBM Watson 的后续研究，把技能从"精心递到手上"
换成"自己在大而嘈杂的库里找"，结果急剧变化：

```
Claude Opus 4.6 + Claude Code：
   精心策划并强制加载      55.4%
   独立检索                40.1%
   ⭐ 真实场景（池里没有量身定制的技能）  38.4%
   ⭐ 无技能基线            35.4%
```

> ⭐⭐ **优势从 20 个百分点压缩到 3 个百分点。**

**为什么差距这么大**（研究者的原话最有说服力）：

```
基准测试是把"量身定制"的技能直接递到 agent 手上。
一个例子：识别 USGS 水文站洪水日的任务，
直接给了三个技能，里面包含下载水文数据的确切 API、
洪水阈值的具体 URL、以及现成的代码片段。

⭐⭐ "这些技能加起来几乎直接拼出了该任务的精确解题指南。"
```

而真实条件是：**必须在大而嘈杂的技能集合里搜索、辨认哪些适用、
并把通用技能适配到具体问题——且不保证存在合适的技能。**

## 3. ⭐⭐⭐ 三个瓶颈

**① 技能选择失败**（最致命）

```
即使精选技能就在手边：
   Claude 只加载了        49% 的情况
   加入干扰技能后降到     31%
   ⭐ 最难场景下只有       16% 的运行加载了技能
```

> ⭐⭐ 这条与 `activation-rate.md` 那组"基础描述 20%"的数据**互相印证**：
> **技能最大的失效点不在内容质量，而在"根本没被选中"。**

**② 检索能力弱**

```
最好的检索方法（agentic 混合检索）  Recall@5 仅 65.5%
更简单的语义检索                    Recall@3 再差 18.7 pp
```

**③ 适配能力差**

```
⭐ 当没有量身定制的技能时，agent 无法把通用技能有效适配到具体任务。
```

**一个更早的独立佐证**（2024 Vercel）：

```
⭐ agent 在 56% 的测试案例中未能检索到已有的可用技能
   ——表现与"没有任何文档"的基线持平。
⭐ 一个被动加载的 Markdown 文件：100% 通过率
   而技能系统：79%
```

> ⭐ 这个对照极其锋利：**同样的内容，主动检索 79%、被动加载 100%。**
> 差距全部来自"检索"这一个环节。

---

## 4. ⭐ 弱模型：技能反而有害

```
Kimi K2.5      有技能 19.8%  vs  无技能基线 21.8%   ⭐ 更差
Qwen3.5-397B   有技能 19.7%  vs  无技能基线 20.5%   ⭐ 更差
```

> ⭐ **无关技能会主动伤害弱模型**——
> 它们消耗 token 和算力去加载、去遵循那些没用的指令。

> ⭐ 这是"装得越多越好"这一直觉的**直接反证**，
> 与 `library-size-effect.md` 的"遮蔽占 68%"是同一现象的两个测面。

## 5. ⭐ 精炼是乘数，不是解药

```
任务特定的精炼（agent 探索任务、评估检索到的技能、构建新技能）：
   Claude 从 40.1% → 48.2%（在 SKILLSBENCH 上）

⭐ 但研究者的判断很关键：
   ⭐ 精炼主要是"已有技能质量的乘数"，而不是新知识的来源。
   ⭐ 只有当最初检索到的技能里包含相关信息时，它才有用。
   任务无关的离线精炼：结果不一致。
```

> ⭐ 一句翻译：**精炼放大的是检索质量，不能替代检索质量。**
> 检索到垃圾 → 精炼出更好的垃圾。

## 6. 该怎么读这两个数

**两个研究都成立，测的不是同一件事**：

| | SkillsBench | 34,198 真实技能 |
|---|---|---|
| 技能来源 | 人工精心筛选、量身定制 | 开源仓库真实存量 |
| 是否需检索 | ⭐ 直接递到手上 | ⭐ 自己在大库里找 |
| 结论 | +16.2 pp | ⭐ 压缩到 +3 pp |

> ⭐⭐ **所以 SkillsBench 测的是"技能内容的上限收益"，
> 真实场景研究测的是"检索 + 内容"的联合收益。**
>
> **差掉的那一大截，全部发生在"有没有被选中"这一步。**

**对做技能的人，三条直接含义**：

```
① ⭐ 把精力从"把内容写得更好"分一部分到"让它更容易被选中"
   ——瓶颈在检索，不在内容（49% → 16% 的加载率才是真问题）

② ⭐ 少装。无关技能对弱模型是净负债，对强模型也是干扰源

③ ⭐ 别指望自生成。模型写不出它自己最需要的那类程序性知识
   ——这条也解释了为什么"元技能"必须内嵌规范与范例，
     而不是让模型凭记忆写（见 `skill-` 元技能相关文档）
```

**研究者提出的三个必要改进**（供参考方向）：
技能选择、检索质量、泛化适配——**三项全在"内容之外"**。

## 速查

```
SkillsBench（受控）：
□ 无技能 24.3% → 精选 40.6%（+16.2pp）→ 自生成 21.0%（−1.3pp）
□ ⭐ 领域差异：医疗 +51.9pp，软件工程仅 +4.5pp
□ ⭐ 2–3 个模块 +18.6pp；4+ 技能 +5.9pp
□ ⭐⭐ "全面"型文档 −2.9pp（有害）；"详细"型 +18.8pp
□ ⭐ Haiku 带技能 27.7% > Opus 不带技能 22.0%
□ 16/84 任务负增益

真实场景（34,198 个技能）：
□ ⭐⭐ 优势从 20pp 压缩到 3pp
□ ⭐⭐⭐ 选择失败：加载率 49% → 加干扰 31% → 最难场景 16%
□ 检索弱：最好方法 Recall@5 仅 65.5%
□ ⭐ 无量身技能时无法有效适配
□ ⭐ 弱模型有技能反而更差（19.8% vs 21.8%）
□ Vercel 2024：56% 案例检索失败；被动加载 100% vs 技能系统 79%

⭐ 精炼：
□ 是已有质量的⭐ 乘数，不是新知识来源
□ 检索到垃圾 → 精炼出更好的垃圾

□ ⭐⭐ 瓶颈在"有没有被选中"，不在"内容写得好不好"
```

**一句话**：

> ⭐⭐ **同一个内容，被动加载 100% 通过、主动检索 79%——
> 差的那一截不在内容里，在检索里。**
