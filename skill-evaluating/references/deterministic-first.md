## 1. 一条贯穿多处的原则

> ⭐ **能用代码判的，绝不交给模型。**

这条原则在本套文档的多个位置反复出现，
值得单独拎出来。

---

## 2. 它在四个地方的体现

| 位置 | 体现 |
|---|---|
| **技能结构** | 确定性逻辑进 `scripts/`，不进正文 |
| **测试** | ⭐ 第 1 层（结构 lint）不用 LLM 判 |
| **评估** | ⭐ 先做确定性检查（产物/事件），再做 rubric 评分 |
| **追踪** | ⭐ grep 断言代替人工读 trace |

```
确定性检查回答："它做对基础事情了吗？"
rubric 评分回答："它按你想要的方式做了吗？"
```

> ⭐ **保持第一层轻量**，在加入模型评分之前
> 先有快速、可解释的基础保障。

---

## 3. 为什么不只是为了省钱

三个理由，省钱只是最次要的：

```
① ⭐ 可重复——同样输入必得同样结果（模型评分有波动）
② ⭐ 可解释——失败时能指出哪一条断言没过
③ 快——毫秒级，能进 CI 每次 PR 都跑
```

第 ① 条最关键：模型评分**天然有波动**，
所以阈值要设"基线均值 − 3σ"（见 `four-dimension-eval.md`）。
确定性检查没有这个问题。

## 4. 判据

写检查前问一句：

```
这个判据能用一条命令/断言表达吗？
```

```
✅ 文件 X 存在
✅ 工具序列包含 [backup, edit, verify]
✅ 同工具连续调用 ≤ 3
✅ 输出 JSON 能被 schema 校验通过
❌ "输出是否有帮助"
❌ "代码是否优雅"
```

前者进脚本；后者才交给模型评委，且要给 rubric 与锚点。

---

## 速查

| 判据类型 | 交给 |
|---|---|
| 存在性、顺序、计数、schema | ⭐ 代码 |
| 质量、风格、有用性 | 模型（带 rubric + 锚点 + 固定 JSON） |
| 两者都要 | ⭐ 先代码后模型，分层 |
