## 1. ⭐⭐⭐⭐⭐ 两端日志的盲区

典型的可观测性记录只有两端：

```
输入：用户说了什么、技能是否被触发
输出：最终结果、耗时、token
```

> ⭐⭐⭐⭐⭐ **中间是黑的。**

后果是一个熟悉的困境：

```
"这个技能昨天还好好的，今天输出就不对了"
→ 你只能看到输入没变、输出变差
→ ⭐⭐⭐ 于是你开始猜：是描述？是正文？是模型更新？是数据？
```

> ⭐⭐⭐⭐ 而这正是"反复修反复出现"的温床——
> 因为每次猜的答案都被下一次失败推翻。

对照已有的那条结论：⭐⭐⭐ **"失败点 ≠ 出错点"**（trace 那份）。
两端日志连失败点都给不准，更别说出错点。

## 2. ⭐⭐⭐⭐ 三种粒度

| 粒度 | 记什么 | ⭐ 成本 | 能回答什么 |
|---|---|---|---|
| **两端** | 输入 + 输出 | 极低 | 成功了吗 |
| ⭐ **步骤** | 每个步骤的开始/结束/关键值 | 低 | ⭐⭐⭐ 卡在哪一步 |
| ⭐⭐ **决策** | 每个分支为什么这么选 | 中 | ⭐⭐⭐⭐ 为什么选这条路 |

> ⭐⭐⭐⭐⭐ **第二档是性价比的分水岭**：
> 从第一档到第二档，成本增加很少，
> 但能回答的问题从"成功了吗"跳到"卡在哪一步"。

第三档最贵，也最有用——但只在**分支多的技能**上值得：
⭐ 一个只有三步线性流程的技能，决策日志几乎全是噪音。

## 3. ⭐⭐⭐⭐⭐ 技能内的轻量 span

不需要接入什么系统，**一份技能自己就能产出结构化的过程记录**：

```markdown
## 执行记录（每次运行结束前输出）

```json
{"skill":"cohort-analysis","steps":[
  {"n":"read","ok":true,"rows":12480},
  {"n":"validate","ok":false,"reason":"missing field: user_id"}
],"stopped_at":"validate","outcome":"failed"}
```
```

四块字段，缺一不可：

```
steps[]   每步名字 + 成功与否 + 一个关键数值
stopped_at 在哪一步停的（成功时填 "completed"）
outcome   completed / failed / partial
⭐ reason  失败原因（成功时省略）
```

> ⭐⭐⭐⭐⭐ **`stopped_at` 是最值钱的字段**：
> 它把"失败了"变成"在 validate 失败了"——
> ⭐⭐⭐ 从"要排查整个技能"缩小到"要看一个步骤"。

而 `outcome` 三档里的 **`partial` 最容易被漏**——
它正是我们反复说的"局部成功、整体失败"的可观测形态。

## 4. ⭐⭐⭐⭐ 记什么、不记什么

| 记 | ⭐ 不记 |
|---|---|
| 步骤名、成功与否 | 大段输出内容 |
| ⭐ 关键数值（行数、条数、大小） | 完整输入数据 |
| ⭐⭐ 分支选择的依据 | ⭐⭐⭐ 密钥、token、完整 URL |
| 耗时（分步） | 每一步的中间推理 |

> ⭐⭐⭐⭐ **第二行是关键**：
> 记"12480 行"而不是"前 100 行内容"——
> ⭐⭐⭐ **数值既能定位问题，又不占上下文**。

第三行的"依据"可以很短：

```
{"branch":"fallback","because":"source_a returned 401"}
```

> ⭐⭐⭐⭐ 这一条尤其重要，因为 **fallback 是最需要被看见的分支**：
> 技能"成功"了，但走的是降级路径——
> ⭐⭐⭐⭐ 而如果没记，你永远不知道它降级过。

## 5. ⭐⭐⭐ 成本与采样

三条务实做法：

```
① ⭐ 记录本身也占上下文 → 放最后，且压缩到几行 JSON
② ⭐⭐ 高频技能采样（如 10%），低频全量
③ ⭐⭐⭐ 失败全量记录，成功采样
```

> ⭐⭐⭐⭐⭐ **第三条最该做**：
> **失败样本的信息量远高于成功样本，而失败本来就少。**
> 所以"失败全量"几乎不增加成本，却覆盖了所有有价值的样本。

这也和"每次生产事故产生一条 eval"配套：
⭐ **事故进 eval，失败记录进日志**——两者是同一批样本的两种用途。

## 6. ⭐⭐⭐⭐ 三种用法

**① 排错**：从"输出不对"直接定位到步骤

```
readonly-vs-writing-skills.md 那条"断言打在环境状态上"的实现前提
就是你知道它执行到了哪一步
```

**② ⭐⭐⭐⭐ 发现隐式降级**

```
统计 outcome=partial 的比例
⭐⭐⭐ 一个长期"成功"但 partial 比例上升的技能，正在悄悄退化
——这正是"平均通过率看不出换血"的过程版
```

**③ ⭐⭐⭐⭐⭐ 触发改进**

```
某个步骤 ok=false 反复出现 → ⭐ 那一步就该被写进 Gotchas
```

> ⭐⭐⭐⭐⭐ 第三条是闭环：
> **观测直接产出内容**。
> 它把"Gotchas 是采集的不是写的"从人工回忆变成了自动信号——
> 而且这个信号比回忆可靠得多，因为它不依赖有人记得记下来。

---

## 一句可贴在墙上

> ⭐⭐⭐ **只有两端的日志能告诉你"失败了"，
> 只有 `stopped_at` 能告诉你"在哪一步"。**
