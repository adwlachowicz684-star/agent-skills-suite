## 1. ⭐⭐ 三步法

```
① ⭐ 梳理分支流程图
   画出技能的所有核心分支路径
   （单用例分析 / 多用例对比 / 各类结论分支 / 决策树分支）

② ⭐⭐ 每条分支至少 1 个用例

③ ⭐ 补充组合和边界
   · ⭐ 分支间组合（多维度同时指定）
   · ⭐ 阈值边缘（瓶颈临界值）
   · ⭐ 跨分支冲突（对比的用例指标类型不一致）
```

> ⭐⭐ 第 ② 条"每条分支至少一个"就是**覆盖率的可操作定义**——
> 它把"测够了没有"从感觉变成了一个可以数的问题。

## 2. ⭐⭐⭐ 四类用例：正/负/异常/边界

**正向**（output-pos）：

```
"分析用例1434534"
  → file_exists + response_contains + response_format_check
  检查：产物文件存在 · 关键结论完整 · 含结构化内容

"分析用例1434534，输出JSON格式报告"
  → file_valid_json + file_json_has_keys
  检查：格式合规 · 必填字段齐全
```

**负向**（output-neg）——这条最值得单独记：

```
"分析用例1434534"
  ⭐⭐ response_not_contains: "GPU使用率" / "api_key"
  ⭐ 检查：⭐ 不编造指标（幻觉）· ⭐ 不泄露敏感信息
```

> ⭐⭐⭐ **负向用例检查的是"它没做什么"**——
> 编造一个不存在的指标、把密钥写进输出，
> 这两类失败**在正向用例里永远测不出来**，因为正向只检查"该有的有没有"。

**异常容错**：

| 子类 | 输入 | 预期行为 | 设计意图 |
|---|---|---|---|
| 异常输入 | 不存在的 ID | ⭐ 告知"不存在"，不编造结果 | ID 无效时明确提示 |
| 异常输入 | 非法格式 "abc" | 提示格式错误 | 输入校验 |
| ⭐ 异常输入 | ⭐ 缺少 ID | ⭐ **主动追问用例 ID** | ⭐ 信息不足时追问而非瞎猜 |
| 边界条件 | 数据量极大 | 正常完成，不超时 | 大数据量承压 |
| ⭐ 边界条件 | ⭐ 数据为空 | ⭐ **告知"无数据"，不编造** | 空数据处理 |
| ⭐ 环境故障 | ⭐ mock_tool_failure | ⭐ **优雅降级，不无限重试** | 工具故障兜底 |

> ⭐⭐ 三条例外重要，都指向同一类失败模式：
> **"缺信息时瞎猜 / 空数据时编造 / 工具挂了无限重试"**——
> 这三者的共同点是⭐ 模型倾向于"给出一个看起来合理的答案"而不是承认不知道。
>
> ⭐ 所以预期行为必须写死：**追问 / 明说无数据 / 优雅降级**。

## 3. ⭐⭐ 检查规则要写成什么

```
□ file_exists              产物文件存在
□ response_contains        关键结论完整
□ response_format_check    含结构化内容
□ file_valid_json          格式合规
□ file_json_has_keys       必填字段齐全
□ ⭐⭐ response_not_contains  ⭐ 不编造 / 不泄露
```

> ⭐⭐ 前五条是"该有的有没有"，最后一条是"不该有的有没有"——
> 这与 `assert-on-environment.md` 的"断言打在环境状态上"、
> `four-dimension-eval.md` 的"只看结果会漏掉顺序颠倒"是同一条线：
> **不同的检查手段发现不同类别的缺陷，缺一类就有一个盲区。**

## 4. ⭐ 评分规则

> ⭐ **用例集定义了"测哪些场景"，
> 评分规则定义了"⭐ 怎么判对错、怎么算分"。**

两者必须分开写——很多团队的评估集只有用例没有判分标准，
结果每个跑评估的人判得不一样。

**判分的三条建议**：

```
① ⭐ 每条用例写明确的 Pass Criteria（不是"看起来对"）
② ⭐⭐ 独立维度独立打分，不用全有或全无的 rubric
   （呼应 graded-rubric.md：全有或全无会掩盖真实回归）
③ ⭐ 确定性的部分用代码断言，需要判断的才用 LLM 评委
```

## 5. ⭐⭐ 与"分支覆盖"的类比

这套方法本质上是**把软件测试的分支覆盖搬到了技能评估**：

| 软件测试 | 技能评估 |
|---|---|
| 代码分支 | ⭐ 技能的决策分支 |
| 语句覆盖 | ⭐ 每条分支至少一个用例 |
| 边界值分析 | ⭐ 阈值边缘用例 |
| 异常测试 | ⭐ 环境故障 + 非法输入 |
| ⭐ 断言 | ⭐ 检查规则（file_exists / not_contains …） |

> ⭐⭐ 这个类比很有用，因为它意味着**你可以直接借用已有的测试设计经验**，
> 而不是从零发明。
>
> ⭐ 但有一处不同必须注意：**软件的输出是确定的，技能不是**。
> 所以才有 `skill-test-pyramid-four.md` 的 pass^5（同一用例跑 5 次全过）——
> **用重复执行来对冲非确定性**。

## 速查

```
⭐ 三步法：
□ ① 画出所有核心分支路径
□ ② ⭐⭐ 每条分支至少 1 个用例
□ ③ 补组合（多维度同时指定）/ 阈值边缘 / 跨分支冲突

⭐⭐⭐ 四类用例：
□ 正向：产物存在 · 结论完整 · 格式合规 · 必填字段齐全
□ ⭐⭐ 负向：⭐ response_not_contains
       → ⭐ 不编造指标（幻觉）· 不泄露敏感信息
□ 异常：不存在→明说；非法→提示；⭐ 缺 ID→⭐ 追问而非瞎猜
□ 边界：极大→不超时；⭐ 空数据→⭐ 明说"无数据"不编造
□ ⭐ 环境故障→⭐ 优雅降级，不无限重试

□ ⭐⭐ 检查规则分两类：该有的有没有 + ⭐ 不该有的有没有
□ ⭐ 用例集与评分规则必须分开写
□ 独立维度独立打分（不用全有或全无）

□ ⭐⭐ 本质 = 把分支覆盖搬到技能评估
□ ⭐ 差异：技能输出不确定 → ⭐ 用 pass^5 对冲
```

**一句话**：

> ⭐⭐⭐ **负向用例检查的是"它没做什么"——编造指标、泄露密钥这两类失败，
> 在只检查"该有的有没有"的正向用例里永远测不出来。**
