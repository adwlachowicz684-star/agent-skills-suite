## 三个角色

| 角色 | 职责 | 关键设计 |
|---|---|---|
| **Grader** | 评估断言是否通过 | ⭐ **自我批评**——同时指出断言本身的问题 |
| **Comparator** | 盲比较两个版本的输出 | ⭐ **双盲实验设计**，去偏见化 |
| **Analyzer** | 事后分析为什么赢家赢了 | 产出**按优先级排序**的改进建议 |

> 三者顺序执行：**先判定，再比较，最后归因**。
> 跳过 Grader 直接比较，你会拿两个都不合格的版本互相比。

## Grader：PASS 的真标准

**PASS 的双重要求**：

```
1. 有证据
2. ⭐ 证据反映的是"真正的任务完成"，而非"表面合规"
```

**FAIL 里有一种最易漏**：

> ⭐ **"巧合通过"（accidental pass）**
> ——断言技术上满足了，但底层任务结果是错的。

例子：断言"输出包含 JSON"，agent 输出了一段符合 JSON 语法
但数据全错的文本——断言过了，任务没完成。

官方原话，值得原样记住：

> **"对一个薄弱断言给出'通过'的评级，其危害比毫无用处还要糟糕
> ——它会制造出虚假的信心。"**

> 这与 `grounding-verification.md`（**`skill-crafting`**）同源：
> 表面合规是 agent 的默认失败模式。

**Grader 的自我批评职责**：

```
□ 不只判"过没过"
□ ⭐ 还要判"这个断言本身合不合理"
□ 发现薄弱断言要指出，而不是照着它判
```

## Comparator：为什么要盲

> ⭐ **知道哪个是新版本就会带入偏见**——
>  evaluator 会不自觉地给"看起来更努力的那个"高分。

**双盲设计**：

```
□ 两个版本去掉标识（版本号、日期、作者）
□ 随机标记为 A / B
□ 判定完成后才揭晓对应关系
```

**判定什么**：

```
不是"哪个更好"这种笼统问题，而是逐维度：
  □ 正确性
  □ 完整性
  □ 遵循指令程度
  □ 输出格式稳定性
```

## Analyzer：事后归因

> **不止判谁赢，要回答"为什么赢"。**

产出必须是**按优先级排序**的改进建议——不是一份平等的清单。

```
✅ 改进建议（按预期收益排序）
   1. description 加入"批量转换"触发词 → 预计修掉 3/7 漏触发
   2. 步骤 4 增加 schema 校验         → 预计修掉 2/7 输出错
   3. Gotchas 补充 UTF-16 文件处理     → 预计修掉 1/7

❌ 改进建议
   - description 可以再优化
   - 步骤 4 说明不够清楚
   - 补充一些边界情况
```

## 对抗测试

> ⭐ **让另一个 LLM 问：「什么边界情况会打破这个技能？」**

这是阶段三之后、发布之前的一道工序。做法是：

```
1. 把 SKILL.md 交给一个独立模型实例
2. 提示：你是一个想搞坏它的测试者。
   列出会让它失败的输入、环境、顺序、前提条件。
3. 对每一条补防护或明确声明不支持
```

**常见的对抗角度**：

```
□ 输入为空 / 超大 / 含特殊字符
□ 依赖的工具没装 / 版本不对
□ 网络不可用
□ 用户中途改需求
□ 部分失败（前 3 步成功，第 4 步失败）
□ 并发调用同一技能
□ 技能被另一个技能抢先触发
```

呼应 `metrics.md` 里那 20 条起始用例的组合：
**负例 > 边界 > 正例**。

## 泛化而非过拟合

> ⭐ **技能要被使用无数次、面对无数种 prompt。**

```
❌ 只为特定测试用例做针对性修改 → 技能失去通用性
✅ 遇到顽固问题，换个隐喻或推荐不同的工作模式
✅ ⭐ 解释"为什么"而非堆砌"必须"——LLM 有良好的推理能力
```

**检测过拟合的方法**：

```
□ 训练集/测试集分割
   ——用一组 prompt 调，用另一组验
□ 如果测试集效果远低于训练集 → 过拟合了
□ ⭐ 新写的规则能不能解释成一条通用原则？
   不能，说明它是为某个 case 打的补丁
```
