## 饱和：套件最常见的死法

```
初始：      套件能抓住真实失败
几次迭代后：技能学会了这套用例
现在：      100% 通过
⭐ 含义：   套件不再能告诉你"改动有没有让它变差"
```

诊断：

```
□ 通过率 100% 持续多轮？
□ ⭐ 新加的改动从来没有让分数下降过？
□ 用例里的措辞是不是和 description 越来越像？
```

第三个是最隐蔽的原因：
**随着你根据失败调整 description，
用例的措辞会不知不觉变成 description 的措辞**——
于是路由测试退化成字符串匹配。

> ⭐ 修法：**每隔一段时间，请一个没读过 description 的人
> 重写几条例句的措辞。**

## 三类要持续补充的用例

**① 真实失败**

```
每次生产环境或日常使用中出现"它没做对"
→ ⭐ 立刻加一条用例
```

这是最有价值的来源，因为它是**真实分布**，不是你想象的分布。

**② 边界与对抗**

```
□ 输入为空 / 超大 / 格式不对
□ ⭐ 请求听起来相关但其实不该触发
□ 请求听起来不相关但其实该触发
□ 指令里埋了冲突的要求
```

**③ 新功能或新技能引入后**

```
□ 加了新技能 → 加共存用例
□ ⭐ 改了 description → 重新检查所有触发用例的措辞
```

## 定期清理

套件也会积累垃圾：

```
□ 重复的用例（同一件事测两次）
□ ⭐ 失效的用例（技能职责已变，此例不再适用）
□ 永远通过且永远会通过的基础用例（可以保留少量作为烟雾测试）
□ ⭐ 措辞与 description 重合的用例（见上）
```

> ⭐ 清理标准和清理技能一样：
> **删掉后不改变套件区分力的，就删。**

但注意：**保留少量基础用例作为烟雾测试**是合理的——
它们确认"基本功能没崩"，即使它们总是通过。

## 版本化

三套版本历史必须**各自独立**：

```
① 数据集（用例）版本
② 系统（技能）版本
③ ⭐ 判分器（含评委配置与 rubric）版本
```

为什么必须分开：

```
分数变了
→ 是技能变差了？
→ 还是判分器换了？
→ 还是用例变了？
⭐ 三者不分开记录，就无法归因
```

配套：**结果要连同三个版本号一起存档**。

## 配套纪律

**① ⭐ 每次改动都跑，不是一次性闸门**

```
❌ "上线前跑一次"
✅ "eval-driven development"——每次改动都跑
```

**② ⭐ 生产环境 pin 住技能与提示词版本**

```
不 pin → 你测的和跑的不是同一个东西
```

**③ 保留原始输出与判分标签**

```
聚合数字会掩盖：
  · 判分器绿但 transcript 错（奖励黑客）
  · ⭐ 通过但过程是错的（巧合通过）
```

**④ ⭐ 不允许"为了让候选通过"改 rubric**

改判分标准来提高分数，是这套体系最严重的腐败。

> 判据：**如果改了 rubric 之后分数上升，
> 那次上升不算数。**

## 自查

```
[ ] 通过率是 100% 吗？（是 → 加更难的用例）
[ ] ⭐ 用例措辞是否已经和 description 重合？
[ ] 最近一次真实失败被加进套件了吗？
[ ] 有边界与对抗用例吗？
[ ] 数据集/系统/判分器三个版本号分开记录了吗？
[ ] ⭐ 每次改动都跑（不是一次性）？
[ ] 保留了原始输出供抽查？
[ ] ⭐ 有没有为了通过而改 rubric？
[ ] 生产环境 pin 了版本吗？
```

## 一条提醒

> ⭐ **eval 套件的敌人是"它看起来在工作"。**

一个每周都跑、每周都全绿的套件，
给人"一切正常"的错觉，
而它可能已经半年没有真正区分过任何东西了。

**定期问一句：上一次这个套件让我发现问题是多久以前？**
