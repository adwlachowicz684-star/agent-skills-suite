## 1. ⭐⭐⭐ 三种失败模式

```
① ⭐⭐ Outgrowth（被追上）
   基线（无技能）已经达到 88%，你的技能 89%
   ⭐⭐⭐ delta 小到不值得这份开销 → ⭐ 模型追上了 → ⭐ 归档这个技能

② ⭐⭐ Regression（回归）
   模型更新后，你的技能通过率从 92% 掉到 71%
   ⭐⭐ 模型改变了对 description 的解读方式
   ⭐ 没有 eval，你不会发现，直到生产里出来一条错的 commit message

③ ⭐ Underperformance（本来就不行）
   技能从来没有达到过预期效果
```

> ⭐⭐⭐ **三种都是"没有测量就看不见"的。**
> 区别在处置：**回归要修，被追上要删，本来不行要重做或放弃。**

---

## 2. ⭐⭐ 只有评估能告诉你的两件事

**① 抓到回归**

```
commit-message 技能：92% → 71%（模型更新后）
⭐⭐ 原因是模型对 description 的解读变了
⭐⭐⭐ 没有 eval 你不会注意到——直到生产里出一条错的
```

> ⭐⭐⭐ "直到生产里出一条错的"这句话很关键：
> **回归的代价不是分数下降，是你在错误的地方信任了它**
> （呼应 `skill-rot-rollback-discipline.md` 的"自信的漂移"）。

**② ⭐⭐ 发现"被追上"**

```
基线 88%，技能 89%
⭐⭐ delta 太小，不足以支撑这份开销 → ⭐ 归档
```

> ⭐⭐⭐ **"发现被追上"是评估在维护成本上回本的地方。**
>
> ⭐⭐ 一句必须记住的话：
> **⭐⭐⭐ "一个你从不修剪的库会⭐ 长成负债。"**
>
> ```
> ⭐ 不再增值的技能⭐ 仍然会触发、仍然消耗上下文、
> ⭐⭐ 仍然会干扰触发匹配
> ```
>
> 第三条尤其重要——它与 `library-size-effect.md` 的遮蔽、
> `capability-offset-net-gain.md` 的 59% 抵消
> 构成了同一个结论的三个机制：
> ⭐⭐⭐ **留着无用的技能不是"放着而已"，它在主动损害其他技能。**

## 3. ⭐⭐ 基准的三指标与 delta

基准（benchmark）在评估之上加了三个指标，每个都含**均值、标准差、相对基线的 delta**：

| 指标 | 测什么 | 什么时候重要 |
|---|---|---|
| `pass_rate` | ⭐ 通过断言的百分比 | ⭐ **永远重要**——这是质量信号 |
| `duration_ms` | 每次运行耗时 | 你在意工作流延迟时 |
| `total_tokens` | 每次运行 token | 成本或速率限制要紧时 |

> ⭐⭐ **delta 那一列才是你要看的数。**
>
> ```
> A：pass_rate +15 个百分点，但 token 翻倍
> B：pass_rate +3 个百分点，token 无增加
> ⭐⭐ 这是两种完全不同的取舍，不能只看 pass_rate
> ```
>
> ⭐⭐⭐ 这与 `capability-offset-net-gain.md` 的"净增益"是同一思路的延伸：
> **技能不是白来的，要看它换来什么、付出什么。**

## 4. ⭐⭐⭐ 标准差比你想的更重要

> ⭐⭐ **一个 pass_rate 均值 85% 但标准差高的技能，是不可靠的。**
> ⭐⭐⭐ **你要的是一致的表现，而不是一个有时 100% 有时 60% 的技能。**

**配套机制**：

```
⭐ 基准 schema 里有 runs_per_configuration 字段（⭐ 通常设为 3）
⭐⭐ 专门为"多次运行"而设——因为 LLM 输出不确定
⭐⭐ 单次运行告诉你"这一次发生了什么"，不是"通常会发生什么"
```

> ⭐⭐⭐ 这与 `assert-on-environment.md` 的 `pass^5`（跑 5 次全过才算过）
> 是同一个原理，只是官方给的默认值是 3。
> ⭐ 仲裁：**关键断言用 5，常规基准用 3**——
> 因为 `pass^5` 针对的是"这条断言是否稳定"，
> 而 `runs_per_configuration=3` 针对的是"这批用例的整体均值是否可信"。

## 5. ⭐⭐ 什么时候该跑一次基准

**四个具体时刻**（不是"有空就跑"）：

```
① ⭐⭐ 刚创建技能时（这就是你的基线）
② ⭐⭐ 更新技能时（这是你的 before/after 证据）
③ ⭐⭐ Claude 模型版本变化时
④ ⭐⭐ 怀疑某个"能力提升型"技能⭐ 已经被追上时
```

> ⭐⭐⭐ "基准结果就是你要做的那个决定的证据。没有它，你是在猜。"
>
> ⭐⭐ 第 ③ 条与 `model-migration-audit.md` 完全一致——
> 那份从"指令要重校准"的角度，这份从"测量要给证据"的角度，
> **两边都把模型更新列为必须重跑的时刻**。

**一个很实用的提醒**（关于输入选择）：

```
⭐⭐⭐ 用⭐ 反映你真实使用的输入，不是理想化的干净样例。

一个 commit-message 技能在完美输入上拿 95%，
⭐ 在你实际打出的那些凌乱、半成品的 message 上可能只有 70%。
```

> ⭐⭐⭐ 这条解释了"为什么本地测得好、实际用起来差"。
> 它和 `eval-case-design.md` 的"按分支铺用例"是互补的：
> ⭐ **分支保证覆盖面，脏输入保证真实性**——两者都要。

## 6. ⭐⭐ 没有区分度的断言是噪音

> ⭐⭐ **分析环节专门去找"在两种配置下都 100% 通过"的断言。**

```
例："输出是合法 JSON"
⭐ 无论有没有技能都会通过
⭐⭐ 它测的是⭐ 模型的基线能力，不是⭐ 技能的贡献
```

> ⭐⭐⭐ **这些断言是噪音，要换成真正有区分度的。**
>
> 这与 `eval-loop-official.md` 那条
> "两组都通过的断言没有区分度，要换掉"是⭐ 同一条规则的独立佐证。
> 也呼应"恒过的断言比没有断言更危险"——
> **它给你一种"我在测"的错觉。**

## 速查

```
□ ⭐⭐⭐ 三失败模式：
   ⭐⭐ Outgrowth（基线追上）→ ⭐ 归档
   ⭐⭐ Regression（模型更新打破）→ 修
   ⭐ Underperformance（本来不行）→ 重做或放弃
□ ⭐⭐⭐ 三种都"没有测量就看不见"

□ ⭐⭐ 回归代价不是分数下降，是⭐ 你在错误的地方信任了它
□ ⭐⭐⭐ ⭐ 一个从不修剪的库会长成负债
   ⭐⭐ 不再增值的技能仍在触发、耗上下文、⭐⭐ 干扰触发匹配

□ ⭐⭐ 基准三指标：pass_rate（永远）· duration_ms · total_tokens
   ⭐⭐ ⭐ delta 列才是要看的数
□ ⭐⭐⭐ ⭐ 高标准差 = 不可靠（均值 85% 但有时 60%）
   ⭐ runs_per_configuration 通常 3
   ⭐ 仲裁：关键断言 pass^5，常规基准 3 次

□ ⭐⭐ 跑基准四时刻：创建 · 更新 · ⭐ 模型版本变化 · 怀疑被追上
□ ⭐⭐⭐ ⭐ 用反映真实使用的脏输入，不是理想化干净样例

□ ⭐⭐ 两种配置都 100% 通过 = ⭐ 测的是模型基线不是技能 → 换掉
```

**一句话**：

> ⭐⭐⭐ **评估能告诉你三件别的东西都告诉不了的事——
> 模型更新打破了它（要修）、模型追上了它（要归档）、它本来就不行（要重做）；
> 而"被追上"这一条最值钱：一个从不修剪的库会长成负债，
> 因为不再增值的技能仍在触发、仍消耗上下文、仍干扰触发匹配。**
