## 5. ⭐⭐⭐⭐⭐ 权限集合不同就该拆

一个真实的⭐ 拆分案例，⭐⭐⭐⭐⭐ ⭐⭐⭐ 理由⭐ 特别⭐ 有说服力：

```
❌ 我把"客户邮件草拟"和"合同审查"塞进同一个 Skill
   理由都是"跟客户打交道"
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ 结果：description 越写越长，⭐⭐⭐⭐⭐ ⭐⭐⭐ 权限也拧巴
   ⭐⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 写邮件只需要读客户记录，⭐⭐⭐⭐⭐ ⭐⭐⭐ 审合同却要碰一堆敏感字段
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ → ⭐⭐⭐⭐⭐ ⭐⭐⭐ 拆开之后两个都顺了
```

> ⭐⭐⭐⭐⭐⭐ **这⭐ 给了⭐ "一职责一技能"⭐ 一个⭐ 全新的⭐ 判据：
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ **两个场景⭐ 需要的⭐ 权限集合⭐ 不一样 → ⭐⭐⭐⭐⭐ ⭐⭐⭐ 就该拆。**
>
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 我们⭐ 此前⭐ 有⭐ 三个⭐ 拆分判据：
> ```
> ① ⭐⭐⭐⭐⭐ 重启测试（失败后人类从哪重启 → 从中间产物则拆）
> ② ⭐⭐⭐⭐⭐ 双向无知（互相需要知道对方领域细节 → 其实是一个技能）
> ③ ⭐⭐⭐⭐⭐ 能独立完成一个有意义的业务动作（防拆过头）
> ```
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 现在⭐ 有⭐ 第四个：⭐⭐⭐⭐⭐ **权限集合**。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 而⭐ 它⭐ 比⭐ 前三个⭐ 都更⭐ 硬——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 因为⭐ 前三个⭐ 是⭐ 质量⭐ 判断（⭐ 拆错了⭐ 效果差），
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ **这一个⭐ 是⭐ 安全⭐ 判断
> （⭐⭐⭐⭐⭐ ⭐⭐⭐ 不拆 = ⭐⭐⭐⭐⭐ ⭐⭐⭐ 低权限场景⭐ 被授予了⭐ 高权限）。**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 这⭐ 与 `allowed-tools-least-privilege.md` 的
> "⭐ 最小权限"⭐ 完全同源，⭐⭐⭐⭐⭐ ⭐⭐⭐ 只是⭐ 应用到了⭐ 拆分粒度上。

## 6. ⭐⭐⭐⭐⭐ "只读"不会把可写 Token 变成只读

> ⭐⭐⭐⭐⭐ **"⭐ 权限⭐ 不能⭐ 只写在⭐ 提示词里——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ Skill 里写'只读'，⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐ 不会⭐ 把⭐ 一个可写 Token
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 变成只读。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐⭐ 真正⭐ 决定 Agent ⭐ 能碰什么的，是：
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 用户身份 · ⭐⭐⭐⭐⭐ ⭐⭐⭐ 源系统 ACL ·
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ MCP 或 App 权限 · ⭐⭐⭐⭐⭐ ⭐⭐⭐ 沙箱与网络策略。"**

```
⭐⭐⭐⭐⭐⭐ "Skill 里写'只读'，不会把一个可写 Token 变成只读"
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ —— ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这是⭐ "声明不是强制"⭐ 这条⭐ 结论
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 我见过⭐ 表述⭐ 最锋利的⭐ 一次
```

> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这⭐ 已是⭐ 该结论的⭐ **第六个**⭐ 独立来源
> （⭐⭐⭐⭐⭐ ⭐⭐⭐ 前五个：⭐⭐⭐⭐⭐ ⭐⭐⭐ 破坏性拦截写进技能是表演、
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ Markdown 指令不是访问控制、
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ Hooks 用于模型不可被信任去遵守的事、
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 权限声明不是安全边界、
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 安全说明只写给人看=不存在）。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 而⭐ 这份⭐ 额外⭐ 列出了⭐ **真正⭐ 起作用的⭐ 那四层**——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这⭐ 是⭐ 前五次⭐ 都没有⭐ 具体⭐ 给出的⭐ 清单，⭐⭐⭐⭐⭐ ⭐⭐⭐ 很实用。
>
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 顺带一条⭐ 安全分级⭐ 判据：
> ⭐⭐⭐⭐ **只读资料、生成草稿 → ⭐⭐⭐⭐⭐ ⭐⭐⭐ 风险低；
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 会发消息、改系统、部署代码、删数据 → ⭐⭐⭐⭐⭐ ⭐⭐⭐ 得严审。**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这⭐ 与⭐ 我们⭐ 那条
> "⭐ 名字含 deploy/commit/send/delete/migrate/push ⭐ 就强制
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ disable-model-invocation: true"⭐ 是⭐ 同一条⭐ 判据的⭐ 文字版与机器版。

## 8. ⭐⭐⭐⭐ 核心规则与个人配置分离

一个解决⭐ 多人协作冲突的⭐ 结构⭐ 设计：

```
症状：⭐⭐⭐⭐⭐ ⭐⭐⭐ 团队成员各自改了同一个 Skill，合并时冲突
原因：⭐⭐⭐⭐⭐ ⭐⭐⭐ Skill 文件没有模块化，所有规则写在一个文件里

⭐⭐⭐⭐⭐ 解法：⭐⭐⭐⭐⭐ ⭐⭐⭐ 把 Skill 拆成
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 核心规则（只读，团队共享）
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 个人配置（可覆盖，各自维护）
```

> ⭐⭐⭐⭐⭐ 这⭐ 是⭐ 一个⭐ 我们⭐ 此前⭐ 没有的⭐ 拆分维度——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 我们⭐ 记过⭐ 按⭐ 认知动作拆、⭐⭐⭐⭐ ⭐⭐⭐ 按⭐ 重启点拆、⭐⭐⭐⭐⭐ ⭐⭐⭐ 按权限拆，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 但⭐ 没有⭐ 按⭐ **可变性**⭐ 拆。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 而⭐ 这个⭐ 维度⭐ 在⭐ 团队场景⭐ 下⭐ 特别⭐ 有用，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 因为⭐ 它⭐ 把⭐ "冲突"⭐ 从⭐ 一个⭐ 需要协商的⭐ 社会问题，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐ 变成了⭐ 一个⭐ 文件布局问题。
>
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 它⭐ 也⭐ 与⭐ 我们⭐ 已有的⭐ 一条⭐ 精确对应：
> ⭐⭐⭐⭐⭐ **"⭐ 想改共享技能⭐ 就在仓库里 fork 并发新版本，⭐⭐⭐⭐⭐ ⭐⭐⭐ 别改本地副本"**
> （`iteration-three-levels.md`）——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 那份⭐ 说的是⭐ 流程，⭐⭐⭐⭐⭐ ⭐⭐⭐ 这份⭐ 说的是⭐ 结构：
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ **把⭐ 允许个人改的⭐ 那部分⭐ 显式隔离出来，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 于是⭐ "别改本地副本"⭐ 就不再⭐ 需要⭐ 靠⭐ 纪律维持。**

**同批还有几条经验**（简短但实用）：

```
⭐⭐⭐⭐ 坑 4：⭐⭐⭐⭐⭐ ⭐⭐⭐ 技能里的代码示例会过时
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ 解法：定期检查；⭐⭐⭐⭐ ⭐⭐⭐ 或者不在技能里写死代码，只写规则和约束
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ → ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这解释了"技能里该不该放代码块"的一个具体风险

⭐⭐⭐⭐ 坑 5：⭐⭐⭐⭐⭐ ⭐⭐⭐ "输出要简洁"是主观的
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ 解法：⭐⭐⭐⭐⭐ ⭐⭐⭐ 给正例与反例的对比，而不只说规则
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ → ⭐⭐⭐⭐⭐ ⭐⭐⭐ 与"把每个形容词换成一条规格"同源
```

## 速查

```
□ ⭐⭐⭐⭐⭐ 大部分问题不在正文里，而在触发与连接这两头
   ⭐⭐⭐⭐⭐⭐ ⭐⭐⭐ "一看到不对就疯狂补字，越补越乱"——⭐⭐⭐⭐⭐ ⭐⭐⭐ 错误排错不只是浪费时间，⭐⭐⭐⭐⭐ ⭐⭐⭐ 是主动把技能改差
□ ⭐⭐⭐⭐⭐ 五步顺序（按最常见→最罕见，不是按最容易改→最难改）：
   ① 没触发→改名称与 description    ② 触发漏步骤→改正文与文件导航
   ③ 读到规则还做错→补真实示例 / 或把确定规则交给脚本
   ④ 工具失败→查连接·参数·凭证·权限  ⑤ 多个 Skill 抢任务→收窄描述或重新分组
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ③的先后：⭐⭐⭐⭐⭐ ⭐⭐⭐ 先确认是"不懂"(给示例) 还是"做不到"(给脚本)
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⑤的根治是改分组，不是加仲裁
□ ⭐⭐⭐⭐⭐ 五类测试用例：⭐ 该触发的正常 · ⭐ 不该触发的相似 · ⭐ 说法模糊的边界
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 缺输入或工具挂掉 · ⭐⭐⭐⭐⭐⭐ ⭐⭐⭐ 跟别的 Skill 并存时还选不选得对（本轮新增的一档）
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ ①⑤ 测入口（选得对不对），②③④ 测出口（干得对不对）
□ ⭐⭐⭐⭐⭐ 负例要"够近"：❌"今天天气怎么样" ✅"修改 Jira 状态"/"给客户发进度"/"写项目复盘"
