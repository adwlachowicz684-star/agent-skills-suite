## 什么时候能用 judge

**✅ 适合**：

```
□ 输出质量、语气、完整性这类难以用规则判的
□ ⭐ 有明确 rubric 的开放式判断
□ 大规模初筛（人工只复核边界案例）
```

**❌ 不适合**：

```
□ ⭐ 能用代码判定的（exit code、JSON 字段、字符串包含）
□ ⭐ 需要领域事实的（模型会编）
□ 安全相关的一票否决项
```

呼应 `test-pyramid.md`：
**第 1 层结构 lint 不用 LLM 判**——确定性检查必须确定性。

## 提示词四要素

**① 明确的评分维度**

```
□ ⭐ 一次只判一个维度
   ——"这个输出好不好"会让 judge 自己加权
□ 每个维度配 1–5 的行为锚点（不是形容词）
```

呼应 `quality-rubric.md` 的**行为锚点**——同一条要求。

**② 输出格式固定**

```
□ ⭐ 要求返回结构化（JSON）：分数 + 理由 + 引用证据
□ ⭐ 要求"引用具体证据"——否则会分数通胀
```

呼应 `quality-rubric.md` 的三个评分陷阱：
**每个分数都要引用具体证据**。

**③ 给反例**

```
□ ⭐ 明确列出"什么算巧合通过"
   ——断言技术上满足但任务没完成
```

呼应 `eval-roles.md`（**`skill-evaluating`**）。

**④ 要求自评置信度**

```
□ 低置信度的判定标出来交人工
□ ⭐ 不要让它硬判
```

## 四种评判形式

| 形式 | 适用 | 注意 |
|---|---|---|
| **分类** | rubric 描述的是**可观察条件** | 输出 `pass / fail / needs_review`，别给自由文本 |
| **多维打分** | 要区分 groundedness / completeness / clarity | ⭐ **硬失败项不能进平均分** |
| **成对比较** | 绝对分数难定义时 | ⭐ **顺序会污染结果**，必须换序复测 |
| **参照式** | 事实类、领域类任务 | ✅ 给评委**已核准的事实/摘录**，比凭记忆强得多 |

成对比较常比绝对打分更容易定义，但
**"换个顺序结论就变"的那一对，应标记为分歧，而不是硬选一个赢家。**

## 三种偏差

| 偏差 | 表现 | 修法 |
|---|---|---|
| **位置偏差** | 偏爱第一个/更长的答案 | ⭐ 随机化顺序、双盲 |
| **自我偏好** | 偏爱自己风格的表达 | ⭐ 用不同的模型当 judge |
| **宽松偏差** | 普遍给高分 | ⭐ 校准：与人类打分对齐 |
| **冗长/风格偏差** | 奖励更长、更自信、排版更好 | ⭐ 显式写"除非 rubric 要求，不得因长度/格式/语气加分" |
| **提示敏感与方差** | 换个说法结论就变 | ⭐ **固定评委配置并随每次运行记录**；换模型或 rubric 版本 = 换测量系统，必须重校准 |

⚠️ 一个常见误解：**换个模型家族并不自动 unbiased，同一个家族也不自动 invalid**。
别按品牌下结论，**在人工复核过的用例上实测**。

**双盲**呼应 `eval-roles.md` 的 Comparator 设计：
**知道哪个是新版本就会带入偏见**。

## 校准：跟人类对齐

> ⭐ **judge 的分数没有绝对意义，只有与人类判断的一致性。**

```
1. 抽 30–50 个样本，人工打分
2. 跑 judge
3. ⭐ 算一致率（agreement rate）
4. 一致率低 → 改 rubric，不是改模型
```

**一个容易忽略的点**：

```
□ ⭐ 校准要定期重做——模型更新后 judge 行为会变
□ 呼应 cross-model：提示词是模型相关的
```

## 能不用的就不用

**替代方案优先级**：

```
1. ⭐ 代码断言（exit code、schema、正则）
   ——最便宜、最稳定、可重复

2. ⭐ 确定性度量（覆盖率、token 数、耗时）

3. ⭐ 人工抽样复核
   ——样本小但可信

4. LLM judge
   ——⭐ 只在上面都不行时用
```

> ⭐ 呼应 `eval-tooling.md`（**`skill-evaluating`**）：
> **硬检查交给代码，rubric 交给评审者**。

## 一个反直觉的提醒

> ⭐ **不要用同一个模型既当执行者又当判官。**

```
□ 建造者不能当审计员（见 grounding-verification.md，
  **`skill-crafting`**）
□ ⭐ 用不同模型，或至少独立实例 + 只读上下文
```

呼应 `security-pipeline.md`（**`skill-orchestration`**）的
**独立审查子 agent**——同一条原则。

## 机器可读的判据

rubric 该写：产品任务与目标用户 · 评委可用哪些证据 ·
⭐ **一个判据只对应一个决策** · 通过/失败样例各一份 ·
不确定时怎么办 · 输出标签的机器可读定义 · 哪些必须升级给人。

❌ 最坏的 rubric：**"请给质量打 1–5 分"**——
评委无法执行一个团队自己都没定义过的标准。

✅ 好的判据：

```json
{
  "label": "unsupported_claim",
  "definition": "答案包含所给来源不支持的事实性断言",
  "allowed": ["基于来源的复述", "明确表达不确定"],
  "fail":   ["无来源的新数字", "与来源矛盾的自信断言"]
}
```

## 绝不能只靠评委的场合

```
❌ 没有提供证据时的精确事实正确性
❌ 可执行代码的正确性
❌ 法律 / 医疗 / 财务决策
❌ 合规判定
```

这些场合评委只能做**优先级排序**，不能做终审。

## 人机结合的工作流

```
① 确定性判分  → 拒绝契约与安全违规
② 模型评委    → 给剩余主观维度打分
③ 人工复核    → 高风险用例 + 评委分歧 + 随机抽样
④ 确认的错误  → 沉淀为校准集 / 回归用例
⑤ 评委与 rubric 版本 → 与结果一同存档
```

两条纪律：

- ⭐ **用评委排优先级，不是用来取消问责**
- **人工推翻必须留理由**——那是改进 rubric 或发现需求本身有歧义的唯一来源

用于回归时：基线与候选**必须用同一套评委配置**；
比较分布与具名切片，不要只比平均分；
⚠️ **不允许实验者为了让候选通过而改 rubric**；
数据集、系统、判分器三者要**各自独立的版本历史**。

## 成本与隐私

评委调用耗时耗 token，最宽的套件放在**受保护的合并节点或定时任务**，
不要每次按键都跑。

⚠️ 隐私那条容易被忽略：**评委收到的是模型输出，通常还含原始输入或参照上下文**。
把它当应用数据处理——最小化、保护凭据、确认供应商的存储与区域控制。
**不要因为"评估是内部行为"就把生产 trace 发出去。**
