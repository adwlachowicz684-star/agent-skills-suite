## 1. 两类技能

| 类型 | 做什么 | 例子 |
|---|---|---|
| **能力型** | ⭐ 完成一件具体工作 | 审查代码、生成测试、写 commit message、搭文档骨架 |
| **偏好型** | ⭐ 强制某种风格或流程 | "一律用 conventional commits"、"按我们的命名规范"、"组件按这个结构写" |

---

## 2. 评估方式完全不同

```
能力型 → ⭐ 测"工作是否被正确完成"
         按输出质量定义清晰的通过/失败判据

偏好型 → ⭐ 测"流程是否被遵循"
         ⭐ 检查输出是否符合规定格式，而不是"总体好不好"
```

> ⭐ 关键差别：**偏好型不看"好不好"，只看"符不符合"。**
> 一套 rubric 同时评两类，必然有一类被误判。

---

## 3. ⭐ 为什么这个区分重要

> ⭐ **模型更新对能力型的影响远大于偏好型。**

```
能力型：更聪明的模型可能改变它做代码审查的方式
       → ⭐ 打乱你精心排序的步骤
偏好型："文件名用 kebab-case" 不太会坏
       → ⭐ 因为指令没有歧义
```

所以：

| 事件 | 该做什么 |
|---|---|
| 模型升级 | ⭐ **优先重跑能力型技能的基准** |
| 流程/规范变更 | 重跑偏好型 |

> 这与 `versioning-compat.md` 那条呼应：
> **破坏性变更不只是代码层面的，模型升级也是。**

---

## 4. 发布前与更新后

**发布前**：

```
至少 5 条测试提示覆盖主要用例
⭐ 2–3 条负向提示
目标通过率 90%+
⭐ 跑 3–5 次基准确认一致性
```

**模型更新后**：

```
⭐ 任何 Claude 模型发布后一周内重跑基准
与你的基线对比
⭐ 通过率下降超过 10 个百分点 → 调查并修复
```

> ⭐ **"保存今天的基线数字"这一步看似简单，
> 但它是唯一能让你在模型更新后发现回归的办法。**

**迭代时**：

```
改之前先跑 improve 模式（盲评 A/B）
```

## 速查

| 技能类型 | 评估重点 | 主要风险 |
|---|---|---|
| ⭐ 能力型 | 工作是否被正确完成 | ⭐ 模型升级会打乱步骤 |
| ⭐ 偏好型 | 流程是否被遵循 | 规范本身变了 |

| 时机 | 动作 |
|---|---|
| 发布前 | 5 正 + 2–3 负，90%+，跑 3–5 次 |
| ⭐ 模型升级后一周 | ⭐ 重跑基准，掉 >10pp 就修 |
| 迭代前 | 盲评 A/B |
