# 共享状态的所有权

> 共享只读文件的影响面是单向的；共享可写状态的影响面是双向的，而且会留下痕迹。

## 一、与共享只读文件的差别

跨技能共享一份只读 reference 时，影响面是单向的；
改它，N 个技能行为同时变。那个问题是"影响面不可见"。

可写状态多出两样东西：

| | 只读共享 | ⭐ 可写共享 |
|---|---|---|
| 方向 | 单向（写者 → 读者） | ⭐⭐⭐⭐⭐ 双向 |
| 后果持续 | 到下次读取为止 | ⭐⭐⭐⭐⭐ 跨会话留存 |
| 谁能破坏 | 只有作者 | ⭐⭐⭐⭐⭐ 任何一个写者 |

> ⭐⭐⭐⭐⭐ **只读文件被改坏，改的人看得见；
> 可写状态被写坏，写的人不知道有人在读。**

## 二、最常见的形状：两个技能，一份文件，两种语义

```
skill-A 写：{"last_run": 1735689600}     ← 时间戳
skill-B 写：{"last_run": "2026-01-01"}   ← 字符串
```

JSON 都合法、写入都成功、没有一个报错。
读者拿到的是"取决于谁最后写"的类型。

> ⭐⭐⭐⭐⭐ **类型不一致在两个写者各自的世界里都不存在——
> 它只存在于共享的那一个文件里，而没有任何环节在检查它。**

这正是"改语义必须改字段名"（《skill-interfaces》的 `skill-interfaces/references/contract-evolution.md`）的同一条规则，
只是那份讲的是版本之间，这份讲的是**同一时刻的两个写者之间**——
⭐⭐⭐⭐⭐ 后者更难发现，因为不存在"改了什么"可供比对。

规则：

- ⭐⭐⭐⭐⭐ 共享状态必须有**单一拥有者**，其余技能只能读或通过拥有者提供的接口写
- ⭐⭐⭐⭐⭐ 字段名必须带类型或单位后缀（`last_run_ts` / `duration_ms`）
- ⭐⭐⭐⭐ 写者必须在状态里留下 `writer` 字段——否则坏的时候无法归因

## 三、"单一拥有者"怎么落地

不是靠约定，是靠这三件事：

| 机制 | 作用 |
|---|---|
| ⭐⭐⭐⭐⭐ schema 由拥有者定义并校验 | 非法写入当场失败，而不是污染文件 |
| ⭐⭐⭐⭐⭐ 写入路径只有一处 | 绕开它需要显式调用别的技能 |
| ⭐⭐⭐⭐ 文件头部注明拥有者 | ⭐⭐⭐⭐ 后来者知道该问谁 |

第三条最便宜也最常被省：

```json
{
  "_owner": "skill-standup",
  "_schema_version": 2,
  ...
}
```

> ⭐⭐⭐⭐⭐ `_owner` 的价值不在运行时，在**下一个想改这个文件的技能作者**——
> 他看到这一行，就知道这不是他的文件。

这和"被借的 reference 文件头部写'被 skill-A 引用'"是同一手法：
⭐⭐⭐⭐⭐ **把单向的隐式依赖变成双向的可见事实。**

## 四、隐式耦合：读别人的状态

比"两个写者"更常见的是"一个写、另一个偷偷读"：

```
skill-A 维护 state/progress.json（自己的）
skill-B 为了省事，直接读 skill-A 的文件判断进度
```

此时 A 是唯一写者、B 是唯一读者，看起来很干净。问题在：

> ⭐⭐⭐⭐⭐ **A 不知道 B 在读，所以 A 改格式时不会通知任何人——
> 而 A 的 changelog 里也确实"没有影响面"。**

B 那侧的失败形状：

| A 的改动 | B 的表现 |
|---|---|
| 加字段 | B 正常（读不到新字段无所谓） |
| ⭐⭐⭐⭐⭐ 改字段名 | B 读到 undefined → 静默走默认分支 |
| ⭐⭐⭐⭐⭐ 改语义 | B 正常，判断错了 |
| 改成 append-only | B 读到数组而不是对象 |

> ⭐⭐⭐⭐⭐ 四种里只有第一种是安全的，而它是唯一一个"什么都没变"的情况。

规则：

- ⭐⭐⭐⭐⭐ **跨技能读取状态必须声明为依赖**，与代码依赖同等对待
- ⭐⭐⭐⭐⭐ 读者必须校验 schema 版本（见《skill-state》的 `skill-state/references/state-schema-versioning.md`），不兼容就报错，不得猜
- ⭐⭐⭐⭐ 优先让拥有者提供"查询接口"，而不是直接读文件

## 五、共享状态与并发叠加

《state-file-concurrency》讲的是同一个技能被并发调用。
两个技能写同一份文件时，那份文档的所有结论**都成立且更严重**：

| 单技能并发 | ⭐ 跨技能共享 |
|---|---|
| 写者行为一致 | ⭐⭐⭐⭐⭐ 写者行为不一致 |
| 丢失更新可预测 | ⭐⭐⭐⭐⭐ 结果取决于调用顺序 |
| 可以加锁约定 | ⭐⭐⭐⭐⭐ 两个技能不会用同一把锁 |

> ⭐⭐⭐⭐⭐ **单写者假设在两个技能之间彻底失效**——
> 每个技能都以为自己是单一写者，而它们都是对的（各自视角下）。

唯一可靠的解法不是加锁，是**取消共享写入**：

- 各写各的文件，需要合并时由编排层归约
- 或者：一个技能写，其余通过调用它来间接写

> ⭐⭐⭐⭐⭐ "通过调用它来间接写"通常比"直接写共享文件"慢，
> 而它换来的不是性能，是**错误可归因**。

## 六、什么时候该共享

判据不是"它们需要同一份数据"（这几乎总成立），是：

> ⭐⭐⭐⭐⭐ **这份状态的一致性，需要跨技能强制保证吗？**

| 情况 | 结论 |
|---|---|
| 一个技能写、其余只读，且格式稳定 | ⭐⭐⭐⭐ 可以共享（但要标 `_owner`） |
| 两个技能都要写 | ⭐⭐⭐⭐⭐ 不该共享——拆成两份 + 归约 |
| 只是"顺便用一下对方的数据" | ⭐⭐⭐⭐⭐ 不该共享——复制一份自己的 |
| 状态本身是编排层的（如"整条链做到哪"） | ⭐⭐⭐⭐⭐ 属于编排层，不属于任何技能 |

最后一行是关键区分：⭐⭐⭐⭐⭐ **"整条链的进度"不是任何一个技能的状态**——
让某个技能拥有它，等于让一个环节拥有整条链。

## Critical Rules

- ⭐⭐⭐⭐⭐ 共享可写状态必须有单一拥有者；其余技能只能读或经其接口写
- ⭐⭐⭐⭐⭐ 字段名带类型/单位后缀，防止两个写者语义不一致
- ⭐⭐⭐⭐⭐ 状态文件必须写 `_owner` 与 `_schema_version`
- ⭐⭐⭐⭐⭐ 跨技能读状态 = 声明依赖；不得"顺便读一下"
- ⭐⭐⭐⭐⭐ 两个技能都要写 → 拆成两份 + 归约，禁止共享写入
- ⭐⭐⭐⭐⭐ 链级进度属于编排层，不属于任何单个技能
- ⭐⭐⭐⭐ 读者校验版本不兼容必须报错，不得猜测旧格式

## 自检

| 检查 | 方法 |
|---|---|
| 有几个写者 | `grep -rn "progress.json" skill-*/`——超过一处写 = 共享写入 |
| 谁拥有 | 文件里有 `_owner` 吗？没有 → 出事时无法归因 |
| 有读者吗 | ⭐⭐⭐⭐⭐ 把文件改名跑全库——有几个技能坏了？（答案通常比预期多） |
| 语义一致吗 | ⭐⭐⭐⭐⭐ 两个写者各自写一遍，读到的类型一样吗？ |
| 该拆吗 | 两个技能都要写 → 能不能各写一份再由编排层归约？ |
