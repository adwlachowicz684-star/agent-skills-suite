# 记忆写入纪律

> 状态文件带时间戳，记忆不带。而记忆是唯一跨会话留存的东西。

## 一、记忆与状态的根本差别

| | 状态文件 | ⭐ 记忆 |
|---|---|---|
| 生命周期 | 可被删除、可被重算 | ⭐⭐⭐⭐⭐ 长期留存 |
| 来源 | 有 run-id、有时间戳 | ⭐⭐⭐⭐⭐ 通常只有结论 |
| 出错后 | 删掉即可 | ⭐⭐⭐⭐⭐ 无法追溯它从哪来 |
| 谁读 | 写它的那个技能 | ⭐⭐⭐⭐⭐ 任何技能、任何会话 |

> ⭐⭐⭐⭐⭐ **写入记忆是这套体系里唯一一个不可逆的错误。**
> 正文写错了可以改，状态写错了可以删，
> 记忆写错了——它会在三个月后以"已知事实"的形式出现在另一个会话里。

## 二、记忆中毒的形状

```
会话 1：模型推断"库存阈值为 30"（其实没有依据）
       → 写进记忆："项目库存阈值 30"
会话 2：读到"库存阈值 30" → 不再推断，直接使用
       → 输出里出现 30，且这次它是"有据可查"的
会话 3：有人问"30 从哪来" → 答"记忆里记着"
```

> ⭐⭐⭐⭐⭐ **三次会话之后，一个猜测变成了事实，而没有任何一步在说谎。**

这与"输出会变成事实"（《skill-output》）是同一机制，但更严重：

| | 输出变事实 | ⭐ 记忆中毒 |
|---|---|---|
| 存续 | 单次会话 | ⭐⭐⭐⭐⭐ 永久 |
| 可追溯 | 上下文里找得到那句话 | ⭐⭐⭐⭐⭐ 上下文早已消失 |
| 可纠正 | 用户当场能指出 | ⭐⭐⭐⭐⭐ 没人知道该纠正什么 |

第二条最绝望：⭐⭐⭐⭐⭐ **会话 1 的上下文消失时，
"这是推断"这个唯一重要的属性也跟着消失了，留下的只有结论本身。**

## 三、写入前的三问

不是"要不要记"，是这三个具体问题：

| 问 | 否 → |
|---|---|
| ⭐⭐⭐⭐⭐ 这条的来源能写进记忆吗？ | 不写 |
| ⭐⭐⭐⭐⭐ 它会被验证吗？（下次运行会重查吗） | 不写 |
| ⭐⭐⭐⭐ 它错了对结果影响大吗？ | 可写，但要标置信度 |

> ⭐⭐⭐⭐⭐ **第一问是硬门槛**：写不出来源的结论，不该进记忆。
> 因为记忆里没有来源字段时，"来源"这一维在存储时就丢失了——
> 而它就是三个月后唯一能救命的东西。

记忆条目的最小集：

```
值：      库存阈值 30
来源：    用户 2026-03-11 在 standup 中说  ← ⭐⭐⭐⭐⭐ 必须有
置信度：  用户口述，未实测
失效条件：用户在后续会话中给出不同数字
```

> ⭐⭐⭐⭐⭐ **"失效条件"是最常被省的一项，而它是唯一能让记忆自我淘汰的机制。**
> 没有它，一条记忆永远不会过期——这才是记忆腐烂的真正原因，
> 不是"时间久了"，是**没有任何东西会去检查它是否还成立**。

## 四、什么不该写进记忆

| 类型 | 为什么 |
|---|---|
| ⭐⭐⭐⭐⭐ 模型的推断结论 | 它就是记忆中毒的来源 |
| ⭐⭐⭐⭐⭐ 会腐烂的事实（谁负责什么、当前配置） | 程序记忆层没有时间维度 |
| ⭐⭐⭐⭐ 一次性的任务细节 | 抬高读取成本，零复用 |
| ⭐⭐⭐⭐ 与正文重复的流程 | 两处维护，必然分叉 |
| ⭐⭐⭐⭐⭐ 未经用户确认的偏好 | ⭐⭐⭐⭐⭐ "用户喜欢简洁"可能只是一次上下文的产物 |

最后一条最隐蔽：⭐⭐⭐⭐⭐ **偏好是最容易被误记的一类**——
用户这次说"简短点"，是因为这次他在赶时间，
而记忆会把"赶时间"记成"用户是喜欢简短的人"。

规则：

- ⭐⭐⭐⭐⭐ 偏好类记忆必须**观察到至少两次**才写，一次不写
- ⭐⭐⭐⭐⭐ 记"用户说过什么"，不记"用户是什么样的人"——前者可核对，后者是推断

## 五、反思层：写什么

记忆四层里的"反思"层（《memory-tiers.md》）是最容易被写坏的一层，
因为它要求的是**从运行中提炼**，而提炼正是模型最容易编造的动作。

合格的反思条目：

```
❌ "处理这类请求时应该先检查权限"   ← 无法验证，且像通用建议
✅ "2026-09-11：因未检查权限导致误改生产配置；
    此后所有写操作前置权限检查"      ← ⭐⭐⭐⭐⭐ 有事件、有因果、有日期
```

> ⭐⭐⭐⭐⭐ **差别在"因为发生了 X"——
> 没有具体事件的反思条目，本质上是一条通用建议伪装成经验。**

判据：⭐⭐⭐⭐⭐ **能不能指出触发这条反思的那一次运行？**
指不出 → 它是被"想"出来的，不是被"提炼"出来的——
而《skill-content》的 `skill-content/references/gotchas-mining.md` 已经说明：坐下来写产不出 Gotchas，反思同理。

## 六、写入时机

> ⭐⭐⭐⭐⭐ **不要在成功的运行结尾顺手写记忆。**

理由不是成本，是：⭐⭐⭐⭐⭐ **成功时你不知道哪一步真正有用**——
于是写进去的是"这次做了什么"，而不是"这次学到了什么"。

| 时机 | 写什么 |
|---|---|
| ⭐⭐⭐⭐⭐ 用户纠正之后 | 纠正本身（最高信号） |
| ⭐⭐⭐⭐⭐ 失败之后 | 失败原因 + 正确做法 |
| ⭐⭐⭐⭐ 用户确认某个推断成立 | 该推断 + 来源 |
| ⭐⭐⭐ 成功结尾 | ⭐⭐⭐ 只写会被下次复用的事实（产物路径等），不写结论 |

> ⭐⭐⭐⭐⭐ 与 Gotchas 的采集规律完全一致：
> **高信号记忆来自纠错与失败，不是来自成功。**

## 七、记忆的读取纪律

写入错了还能删，读错了会扩散：

- ⭐⭐⭐⭐⭐ **不得把记忆里的事实当作已验证**——它是"上次有人这么说过"
- ⭐⭐⭐⭐⭐ 记忆里的值必须能与当前运行交叉验证；冲突时以当前为准并**更新记忆**
- ⭐⭐⭐⭐ 读取记忆时把来源一起读出来；来源缺失的条目按"低置信度"处理

> ⭐⭐⭐⭐⭐ 第三条是唯一能自动淘汰坏记忆的机制：
> **每次读取都是一次验证机会**，而多数实现读的是值、丢的是来源。

## Critical Rules

- ⭐⭐⭐⭐⭐ **写不出来源的结论禁止写入记忆**
- ⭐⭐⭐⭐⭐ 记忆条目必须带来源、置信度、失效条件
- ⭐⭐⭐⭐⭐ 模型的推断结论禁止写入记忆
- ⭐⭐⭐⭐⭐ 偏好类记忆需观察两次以上；记"用户说过什么"，不记"用户是什么样的人"
- ⭐⭐⭐⭐⭐ 反思条目必须能指出触发它的那次运行
- ⭐⭐⭐⭐ 不得在成功运行结尾顺手写结论类记忆
- ⭐⭐⭐⭐ 读记忆必须连来源一起读；来源缺失 = 低置信度

## 自检

| 检查 | 方法 |
|---|---|
| 有来源吗 | ⭐⭐⭐⭐⭐ 随机抽 5 条记忆，几条能说出来源？ |
| 会过期吗 | 每条都有失效条件吗？没有 → 它永远不会被淘汰 |
| 中毒了吗 | ⭐⭐⭐⭐⭐ 把记忆全部删掉跑一次，结果差多少？差很多 = 记忆在承担它不该承担的角色 |
| 反思是真的吗 | ⭐⭐⭐⭐⭐ 每条反思能指出那次运行吗？指不出 = 编的 |
| 偏好可靠吗 | 每条偏好是观察到几次？一次 = 可能是上下文产物 |
