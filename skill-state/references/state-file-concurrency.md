## 1. ⭐⭐⭐⭐⭐ 写者从来不止一个

作者写状态文件时，心里跑的是一次运行：

```
一次运行 = 一个进程 = 一个写者 → 顺序写 → 安全
```

实际写者至少有六个：

| 写者 | 何时出现 |
|---|---|
| 第二个会话 | ⭐⭐⭐⭐⭐ 用户开了两个终端（很常见） |
| ⭐⭐⭐⭐⭐ 重试 | 上一次没退出干净，或超时后重跑 |
| 子代理 / fork | ⭐⭐⭐⭐ 并行分支同时完成各自的部分 |
| 并行扇出 | `skill-aggregation` 的多路并发 |
| 调度器 | 定时任务在人工会话还在跑时触发 |
| 你自己 | 手动改了那个文件调试 |

> ⭐⭐⭐⭐⭐ **"同时开两个会话"不需要任何特殊配置，
> 而它足以让任何单写者设计失效。**

最容易被忽略的是**重试**：重试看起来是"再来一次"，而第一次往往并没有结束——
超时只是调用方放弃了，写入方还在跑。

## 2. 读-改-写：不报错的丢失更新

状态文件最常见的形态是"一个 JSON 快照"：

```
progress.json = {"done": ["a", "b"], "failed": []}
```

更新它的动作是三步：

```
1. 读 progress.json
2. 在内存里 append "c"
3. 写回 progress.json
```

两个写者交错：

```
A 读 {done:[a,b]}
B 读 {done:[a,b]}
A 写 {done:[a,b,c]}   ← 被覆盖
B 写 {done:[a,b,d]}
最终：{done:[a,b,d]}   ⭐⭐⭐⭐⭐ c 消失了
```

> ⭐⭐⭐⭐⭐ **没有任何组件报错。文件合法、格式正确、写入成功。**
> 唯一的症状是"少了一条"，而没人知道该有几条。

它的不可见性来自：**丢失的是"别人写的东西"，而读的人从来没见过那份东西。**

> ⭐⭐⭐⭐⭐ 对比一下：单写者场景下同样的代码 100% 正确。
> 所以它不是 bug，是⭐⭐⭐⭐⭐ **一个未被写下来的前提被违反了**。

## 3. ⭐⭐⭐⭐⭐ 追加天生并发安全，覆盖不是

```
覆盖写（write）  → 后写者赢，先写者的数据静默消失
追加写（append） → ⭐⭐⭐⭐⭐ 两条都在（顺序不定，但都在）
```

差别不在"哪个更好"，在**失败形状**：

| | 覆盖 | ⭐ 追加 |
|---|---|---|
| 冲突时 | ⭐⭐⭐⭐⭐ 丢数据，不可见 | 重复条目，可见 |
| 事后能发现吗 | 不能 | ⭐⭐⭐⭐ 能（数一下就知道多了） |

> ⭐⭐⭐⭐⭐ **追加把"丢失"换成了"重复"，而重复是可见的。**
> 这与"示例值用 2099-01-01"是同一手法：
> **没法阻止它发生，就让它发生成会暴露自己的样子。**

推论（也是本份最实用的一条）：

> ⭐⭐⭐⭐⭐ **进度写日志（append），不写快照（overwrite）。**
> 需要"当前状态"时，从日志重放——重放是确定性操作，而覆盖不是。

代价是日志会增长——那是 `state-file-lifecycle.md` 的问题，
而且**增长是可见的、可处理的，丢失不是**。

## 4. 五种修法，按代价排序

```
① ⭐⭐⭐⭐⭐ 每 run 独立文件（路径带 run-id）——零成本，且顺带解决"旧状态"
② ⭐⭐⭐⭐⭐ 改为追加日志 —— 改一次，永久安全
③ ⭐⭐⭐⭐   原子写（写 .tmp + rename）—— 解决半写状态，不解决丢失更新
④ ⭐⭐⭐     写者标识 + 冲突检测（读时发现别人的 writer_id 变了就中止）
⑤ ⭐⭐       文件锁 —— 能解决，但引入死锁与僵尸锁
```

**③ 常被误当成解药**：原子写保证的是"不会读到写了一半的文件"，
⭐⭐⭐⭐ **它完全不解决丢失更新**——两次完整写入，第二次覆盖第一次，
每一次都是原子的。

**⑤ 通常不值得**：锁要解决"锁的持有者崩了怎么办"，
而那会引入超时、僵尸锁检测、锁的锁……⭐⭐⭐ **引入一个有状态的机制来保护状态，
状态的总量反而增加了。**

**④ 的性价比常被低估**：它不需要锁，只需要写的时候带上自己的 id，
读的时候比对。冲突时不猜、不合并、直接中止并报告——
⭐⭐⭐⭐⭐ **中止是可接受的，因为"有人同时在跑"是用户需要知道的事。**

## 5. 单写者假设必须写下来

> ⭐⭐⭐⭐⭐ **"这个状态文件同时只会有一个写者"是一句设计决策，
> 而它从来没被写成一句话。**

于是后来者（包括三个月后的你自己）看到的是"一个普通的 JSON 文件"，
会自然地给它加第二个写者——比如加一个并行分支。

最小成本的做法，写进技能正文两行：

```markdown
状态文件：progress.jsonl
- 追加写，不覆盖
- ⭐ 允许多个写者并发；条目重复是可接受的，由读取侧去重
```

> ⭐⭐⭐⭐⭐ 这两行的价值不在"实现"，在于**把假设从作者脑子里搬到文件里**。
> 没有它，这个假设会在第一次有人加并行分支时静默失效。

## 6. 自检

| 检查 | 方法 |
|---|---|
| ⭐⭐⭐⭐⭐ 有没有并发写者 | 两个终端同时跑同一个技能，看状态文件 |
| ⭐⭐⭐⭐⭐ 会不会丢 | A 写一条、B 写一条、比对最终有几条 |
| 单写者假设写下来了吗 | 正文里能找到"并发"两个字吗 |

最低成本的一条只有十秒：**打开状态文件，看它是 `{}` 还是一行一行**。

> ⭐⭐⭐⭐⭐ 如果是 `{}`，它是快照，它会丢数据；
> 如果是一行一行，它是日志，它最多重复。
