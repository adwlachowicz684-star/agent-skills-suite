# 状态文件的生命周期：每写一份状态，就增加一份义务

> ⭐⭐⭐⭐⭐ 状态不是越多越好。**每写一份状态，都在给以后的每一次运行增加义务。**

## 1. ⭐⭐⭐⭐⭐ 状态的成本不在写入，在后续每一次运行

写一次状态的代价你看得见：一次文件写入。

之后的代价你看不见，但每次运行都要付：

```
① 存在性检查       — 每次运行都要判断"有没有上次的状态"
② ⭐⭐⭐⭐ 新鲜度校验 — 不校验就会被旧状态误导（见 state-schema-versioning）
③ 版本兼容         — 不兼容要迁移或重算
④ 读取成本         — 读进上下文的部分要付费
⑤ ⭐⭐⭐⭐⭐ 认知负担 — 每次排查都要问"这次的结果是不是受上次状态影响"
```

> ⭐⭐⭐⭐⭐ **⑤ 是最大的一项，而且它不出现在任何账本上。**

它解释了那个常见现象：**一个技能加了状态之后，变得难以调试**——
不是因为它更复杂了，而是因为⭐⭐⭐⭐⭐ **同一个输入现在可能产生不同的输出**，
取决于一个你没看过的文件。

判据（与 `skill-execution/references/repeat-invocation-same-session.md` 同源）：

> ⭐⭐⭐⭐⭐ **清空状态文件跑一遍，结果一样吗？**
> 不一样 → 状态在影响结果 → 每次排查都要先考虑它。

## 2. 三种不该写状态的情况

```
① ⭐⭐⭐⭐⭐ 能确定性重算的
② ⭐⭐⭐⭐⭐ 只会用一次的
③ ⭐⭐⭐⭐   事实（会腐烂）
```

**① 最常见**：把"已处理的文件列表"存起来，而它 `ls` 一下就有。

> ⭐⭐⭐⭐⭐ 判据：**重算的成本 < 校验状态是否仍然正确的成本 → 重算。**
> 这与"重跑常常比接续可靠"是同一条，只是那条针对跨会话，这条针对任何缓存。

**② 最浪费**：为了"以后可能用"而写。⭐⭐⭐⭐⭐ 状态文件的成本是按"运行次数"摊的，
而收益是按"被用到的次数"算的——**用一次的状态，收益是 1，成本是 N。**

**③ 最隐蔽**：见第 4 节。

## 3. append-only 一定会长到不可用

`state-file-concurrency.md` 推荐追加写。追加的代价是增长：

```
第 1 周   200 行   读起来没问题
第 8 周   4000 行  ⭐⭐⭐⭐ 读全量 = 一次上下文污染
第 半年   50000 行 ⭐⭐⭐⭐⭐ 读不进来，技能静默只读到截断部分
```

> ⭐⭐⭐⭐⭐ **截断是静默的**——读到一半不会报错，
> 于是"最近的状态"变成了"文件开头那部分状态"。

这是"列表越长越像穷举"（`skill-precision/references/enumeration-closed-vs-open.md`）
的读取侧版本：**内容在增长，读取方式没变，于是读取方式先失效。**

三个应对，按代价：

```
① ⭐⭐⭐⭐⭐ 倒序读 + 取尾部 N 条（最新状态在尾部）
② ⭐⭐⭐⭐   分片（按月/按 run），读的时候只打开相关分片
③ ⭐⭐⭐⭐   定期压实（compaction）：把日志折叠成一份快照 + 之后的日志
```

③ 是唯一治本的，但它引入了⭐⭐⭐⭐ **两份状态**（快照 + 增量），
于是又回到"哪个是 canonical"的问题。
⭐⭐⭐⭐⭐ **如果做了压实，快照必须是 canonical，日志只是重建用的备份**——
反过来就会在两者不一致时无法决定信谁。

## 4. ⭐⭐⭐⭐⭐ 状态里的事实也会腐烂，而且更隐蔽

正文里的事实会腐烂（`skill-versioning/references/skill-rot-rollback-discipline.md`），
这条人人知道。状态文件里的事实**一样会腐烂，但没人会去检查**：

```
正文：    在仓库里 → 走 PR → 有人 review → 过期可能被发现
⭐⭐⭐⭐⭐ 状态文件：在 .progress/ 里 → 不在 git 里（通常被 .gitignore）
          → 没有 PR → 没有人读 → ⭐⭐⭐⭐⭐ 永远不会被质疑
```

> ⭐⭐⭐⭐⭐ **状态文件的腐烂概率更高，被发现的概率更低——两个方向都更坏。**

典型内容：

| 写进状态的事实 | 什么时候变成错的 |
|---|---|
| "项目用 pnpm" | 迁移到 npm 之后 |
| "数据源是 A 表" | 表下线之后 |
| "负责人是张三" | 换人之后 |
| ⭐⭐⭐⭐⭐ "上次跑到 offset=1200" | 上游数据被重写之后 |

最后一行最危险：⭐⭐⭐⭐⭐ **它是一个看起来纯技术的数字，
而它的有效性依赖于"上游没变过"这个没有任何地方记录的前提。**

判据（与 `assumption-registry.md` 同源）：

> ⭐⭐⭐⭐⭐ **这条状态，在什么条件下会变成错的？**
> 答不出 → 它不是状态，是一个你没意识到的假设。

修法只有一条：**条目的有效范围必须和条目存在一起**。

```json
{"offset": 1200, "valid_for": "source_rev=abc123", "written_at": "..."}
```

> ⭐⭐⭐⭐⭐ 有了 `valid_for`，读取时可以比对；没有它，
> 你连"这条还能不能用"这个问题都提不出来。

## 5. 清理策略

三条，按优先级：

```
① ⭐⭐⭐⭐⭐ 状态目录默认进 .gitignore 之前，先想清楚它要不要留
② ⭐⭐⭐⭐⭐ 条目带时间戳是清理的前提（没有时间戳无法按年龄删）
③ ⭐⭐⭐   到期视为"不存在"，而不是删除
```

**① 常被做反**：随手加进 `.gitignore`，于是状态文件变成
⭐⭐⭐⭐⭐ **既不可审计、也不可回滚、还会在换机器时静默丢失**的一类东西。

> 判据：**这个文件丢了，技能还能跑吗？**
> 能 → 进 .gitignore；不能 → 它是数据，不是缓存，该进版本控制。

**③ 值得解释**：到期不删除而是"视为不存在"，
好处是⭐⭐⭐⭐ 排查时还能看到"上次是什么时候跑的"，
而删除之后这个问题永久无法回答。

## 6. 一份状态该活多久

| 状态类型 | ⭐ 合理寿命 | 依据 |
|---|---|---|
| 本次运行的中间产物 | ⭐⭐⭐⭐⭐ 运行结束（失败时保留） | 跨运行复用 = 用旧数据 |
| 增量游标（offset / 时间戳） | ⭐⭐⭐⭐ 到上游重写为止 | 依赖 `valid_for` |
| 进度快照 | ⭐⭐⭐⭐ 任务完成 | 完成后它就是历史 |
| ⭐⭐⭐⭐⭐ 记忆（学到的偏好、gotchas） | 直到被证伪 | ⭐⭐⭐⭐⭐ 没有 TTL，必须有被推翻的机制 |
| 事实（项目用 pnpm） | ⭐⭐⭐⭐⭐ 不该进状态 | 会腐烂且无人审 |

最后一行是本份的结论：
⭐⭐⭐⭐⭐ **记忆层可以有事实，状态文件不该有事实**——
因为记忆层有检索与重写机制，状态文件只有"读"这一个动作。
