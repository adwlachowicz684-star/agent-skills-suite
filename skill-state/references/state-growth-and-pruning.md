# 状态的增长与裁剪

> append-only 解决了并发安全，代价是把"什么时候清理"变成了一个没人负责的问题。

## 一、写入时被忽略的成本，在读取时被支付

```
第 1 次运行：追加 1 条 → 文件 1KB
第 200 次运行：追加 200 条 → 文件 200KB
```

写入侧每一行代码看起来都是常数成本——**追加一行**。
读取侧不是：

```
读取成本 = f(历史总条数)，不是 f(本次需要几条)
```

> ⭐⭐⭐⭐⭐ **追加型状态的成本曲线是"今天便宜、以后贵"，
> 而写它的那天永远在曲线的便宜端。**

三处支付点：

| 环节 | 表现 |
|---|---|
| 读进上下文 | ⭐⭐⭐⭐⭐ 200 条历史全进上下文，其中 199 条与本次无关 |
| 解析时间 | JSON 全量反序列化；大文件还会触发截断 |
| ⭐⭐⭐⭐⭐ 判断质量 | 历史越长，模型越难判断"哪条是当前的" |

第三点最贵且最不被注意：⭐⭐⭐⭐⭐ **它不报错、不慢、只是判断更差**——
于是被归类为"这技能越用越不准"，而没人归因到状态长度。

## 二、"只追加"与"要读全部"是矛盾的

append-only 的正确用法是**重放出当前状态**：

```
日志：+A, +B, -A        → 当前：{B}
```

但最常见的实现是：

```
读取全部历史 → 交给模型 → "你看现在做到哪了"
```

> ⭐⭐⭐⭐⭐ **把重放这个确定性操作，交给了模型去做。**
> 它能做对，但它做的是"理解一段历史"，不是"执行一次重放"。

差别的后果：

| | 重放（脚本） | ⭐ 交给模型 |
|---|---|---|
| 长历史 | 成本在脚本 | ⭐⭐⭐⭐⭐ 成本在上下文 |
| 矛盾条目 | 按规则冲突处理 | ⭐⭐⭐⭐⭐ 自己选一个，不告诉你 |
| 结果 | 确定 | 每次可能不同 |

规则一句话：

> ⭐⭐⭐⭐⭐ **状态文件要么小到可以整份读，要么必须有脚本负责归约。**
> 中间状态（几 KB、靠模型读）是最差的一档——它同时承担了两边的成本。

## 三、裁剪不是删除，是归约

直接删历史会丢信息。正确形状是：

```
热文件（最近 N 条 / 当前状态）  ← 每次读这个
冷文件（归档历史）              ← 只在需要追溯时读
```

> ⭐⭐⭐⭐⭐ **关键在"归约后的热文件必须由脚本生成"**——
> 让模型写摘要，等于把状态的正确性交给了每一次运行。

三种归约策略：

| 策略 | 适用 | 产物 |
|---|---|---|
| ⭐⭐⭐⭐⭐ 快照 | 状态可完全由最新值表示 | 只保留最后一条 |
| 窗口 | 只需要最近一段时间的 | 最近 N 条 |
| ⭐⭐⭐⭐ 聚合 | 需要统计而非明细 | 计数 / 汇总值 |

聚合那条要小心：⭐⭐⭐⭐ **聚合是不可逆的**——
聚合之后"某次具体发生了什么"就查不到了，而它恰恰是排查时唯一有用的东西。
所以聚合必须保留明细归档。

## 四、增长上限必须显式写下来

> ⭐⭐⭐⭐⭐ **没有上限的 append-only 文件，是一个正在等待发生的事故。**

它不会在某一天突然出问题，它只是让每一次运行都稍微贵一点、稍微不准一点——
⭐⭐⭐⭐⭐ 而"缓慢变差"是最难被发现的一类问题，因为它每一天的对比基线都是昨天。

上限的形式不重要，重要的是它存在且被检查：

```
条数上限：超过 500 条触发归档
体积上限：超过 50KB 触发归档
时间上限：超过 30 天的条目移入归档
```

三个常见错误：

| 错误 | 后果 |
|---|---|
| ⭐⭐⭐⭐⭐ 只设体积不设条数 | 单条很长时体积先到，明细被截断 |
| 归档与热文件同目录 | ⭐⭐⭐⭐ 归档又被读进来了 |
| 归档后不验证 | ⭐⭐⭐⭐⭐ 归约脚本有 bug → 热文件少了东西，且不报错 |

第三条最贵：**归约是唯一一个会把"正确但有 bug"写进热文件的环节**——
它每次都成功、每次都产生一个更小的文件，而内容可能已经丢了东西。

## 五、什么时候该删掉整个状态

不是"不用了就删"，有明确的触发条件：

| 条件 | 动作 |
|---|---|
| ⭐⭐⭐⭐⭐ 工作对象变了（换项目 / 换目标） | 删——旧状态对新对象毫无意义 |
| 技能语义变了（输出结构改版） | ⭐⭐⭐⭐⭐ 删，不要迁移 |
| 状态版本不兼容 | 删并重算（见《state-schema-versioning》） |
| 只是很久没用 | ⭐⭐⭐⭐ **不要删**——低频高价值的状态最珍贵 |

> ⭐⭐⭐⭐⭐ **"很久没用"是最常被误用为删除理由的一条。**
> 状态的价值不在使用频率，在**重建成本**。

判据：

```
重建这份状态的成本 vs 保留它的成本
```

重建很贵（跑了三天爬来的）→ 多久没用都该留；
重建很便宜（一次 API 调用）→ 立刻删。

## 六、膨胀的可 grep 信号

状态膨胀和正文膨胀不同，它有明确的机械信号：

| 信号 | 含义 |
|---|---|
| ⭐⭐⭐⭐⭐ 状态文件行数 > 200 | 早已该归档 |
| ⭐⭐⭐⭐⭐ 读取状态后没有任何过滤 | 全量进上下文 |
| ⭐⭐⭐⭐ 没有归档目录 | 从来没归约过 |
| ⭐⭐⭐⭐ 状态里出现"历史""之前""上次" | ⭐⭐⭐⭐⭐ 在用自然语言存历史——模型在读一段叙事，不是读一份状态 |

最后一条最值得记：⭐⭐⭐⭐⭐ **状态是给机器读的结构，
一旦它变成一段叙事，就同时失去了可归约性和可验证性。**

## Critical Rules

- ⭐⭐⭐⭐⭐ 追加型状态必须有显式增长上限与归档触发条件
- ⭐⭐⭐⭐⭐ 状态要么小到可整份读，要么由脚本归约；禁止"几 KB 靠模型读"
- ⭐⭐⭐⭐⭐ 归约必须由脚本完成，不得让模型写摘要当状态
- ⭐⭐⭐⭐⭐ 归档必须与热文件物理分离（不同目录，且归档不被默认读取）
- ⭐⭐⭐⭐⭐ 不得把"很久没用"当作删除理由；判据是重建成本
- ⭐⭐⭐⭐ 聚合不可逆 → 聚合必须同时保留明细归档
- ⭐⭐⭐⭐ 归约后必须验证条数/字段完整，不得只验证"文件变小了"

## 自检

| 检查 | 方法 |
|---|---|
| 成本在哪 | ⭐⭐⭐⭐⭐ 跑 50 次后测一次读取 token——它涨了吗？ |
| 谁在归约 | 归约逻辑在脚本里还是在提示词里？在提示词里 → 迟早出错 |
| 有上限吗 | 能不能一句话说清"到什么规模会触发归档" |
| 归档被读了吗 | ⭐⭐⭐⭐ 把归档目录改名，技能还能跑吗？不能 → 它在读归档 |
| 能重建吗 | 删掉整个状态，重跑一次能得到等价状态吗？ |
