# 跨会话持久化：把记忆写进仓库

> "agent 没有记忆" 是个架构问题，不是模型问题。
> ⭐ **解法不是更大的上下文，是让技能往仓库里写文件。**

## 为什么这是架构问题

会话结束，上下文就没了。靠"下次再解释一遍"解决，
等于把成本永久转移给使用者。

> ⭐ 正确做法：**让技能产出仓库级文件，
> 未来的会话去读这些文件。**

这不是 workaround，是**架构层面的正解**——
它把"记忆"从易失的上下文，搬到了持久的版本化存储。

## 该写哪些文件

按用途分三类：

```
CONTEXT.md        当前状态：在做什么、做到哪、卡在哪
ADR / 决策日志    为什么这么定（⭐ 比"定了什么"重要得多）
进展日志          完成了什么、验证了什么、还剩什么
```

**决策日志尤其值钱**：
一个没有理由的结论，下次会话会**重新讨论一遍**；
有理由的结论，下次会话直接接受并往下走。

## 写入的四条纪律

**① 写明时间戳与前置条件**

```
❌ "已重构 auth 模块"
✅ "2026-09-23 重构 auth 模块完成
     前提：假设 session 存储仍用 Redis
     验证：跑了 47 个测试全绿"
```

**② 区分"事实"与"推断"**

```
✅ "实测：构建耗时 4.2s"
✅ "推测：瓶颈可能在依赖解析（未验证）"
```

> 不区分的话，下个会话会把推断当事实，越走越歪。

**③ 记"为什么"，不只是"是什么"**

```
❌ "使用了 X 方案"
✅ "选择 X 而非 Y，因为 Y 在并发 >100 时锁竞争严重（实测 3 次）"
```

**④ 写入要能被机器校验**

```
✅ 写清"验证方式"，让下个会话能重跑
❌ 只写结论
```

配套一条：**写入动作本身要幂等**——
重复执行不应该产生重复条目。

## 读取侧：怎么让下个会话找到

写入了但没人读，等于没写。三种挂载方式：

```
① 在 CLAUDE.md 里点名：
   "开始工作前先读 CONTEXT.md 与 docs/decisions/"

② ⭐ 写进技能的强制步骤：
   "步骤 1：读 CONTEXT.md，确认当前状态"

③ 用 Hook 在会话开始时注入
```

> 第 ② 条最可靠——它把"读"变成了**流程的一部分**，
> 而不是依赖模型记得去读。

## 与技能自身记忆的关系

有个容易混淆的点：

| | 存在哪 | 谁写 | 生命周期 |
|---|---|---|---|
| **会话上下文** | 内存 | — | 会话内 |
| **产物文件** | 仓库 | agent（按技能） | ⭐ 跟随版本 |
| **技能内容** | 磁盘 | 人 | 跟随技能版本 |

关键区分：**产物文件会被后续会话更新**，
所以它必须有**明确的写入规则**（否则会互相覆盖）。
技能内容则是相对静态的。

⚠️ 一个真实风险：**两个并行的 agent 同时写 CONTEXT.md**。
如果用了并行编排，写入必须串行化，或各写各的文件再合并。

## 什么时候不该用

```
❌ 短暂的一次性任务——写文件 overhead 大于收益
❌ 内容高频变化且无需追溯——反而制造噪声
❌ ⭐ 敏感信息——写进仓库就跟随 git 历史了
```

最后一条要特别注意：
**产物文件会被 commit**，
所以密钥、内部 URL、个人信息不能写进去。

## 一条验收判据

写完之后，做个简单测试：

```
新开一个会话，只告诉它"继续上次的工作"
不给任何额外解释

能接上  → 产物文件写对了
接不上  → 缺关键信息，补
```

> ⭐ 这个测试比"文件是否生成"有意义得多——
> 它测的是**信息是否足够重建上下文**，而不是文件是否存在。
