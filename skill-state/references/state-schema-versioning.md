## 1. ⭐⭐⭐⭐⭐ 状态文件跨的是时间，不是空间

技能间交接发生在**同一秒**：两个版本都在磁盘上，改了能立刻对上。

状态文件跨的是**几周**：

```
v1 技能 写了 progress.json
        …… 两周、三次技能更新、两个人改过正文 ……
v4 技能 读 progress.json
```

> ⭐⭐⭐⭐⭐ **交接的两端至少都还活着，可以一起改；
> 状态文件的写入端已经不存在了——它是两周前的那个技能。**

所以交接契约里那些"改了就一起改"的做法，在这里全部失效：
你没法通知两周前的自己。

还有一个更长的尾巴：

> ⭐⭐⭐⭐ **状态文件的生命周期通常长于技能版本。**
> 用户不会因为你发了 v4 就删掉 `.progress/`——
> 而那正是"这次的结果和上次不一样"最常见的来源，且没人会往这儿想。

## 2. 三种错配：改名、改语义、改默认

| 类型 | 例子 | 症状 |
|---|---|---|
| ① 字段改名 | `items` → `entries` | ⭐⭐⭐⭐ 新字段读不到 → 当成"空"→ 重跑一遍 |
| ⭐⭐⭐⭐⭐ ② 改语义 | `duration` 毫秒 → 秒 | ⭐⭐⭐⭐⭐ 值在、类型对、判断全错 |
| ⭐⭐⭐⭐ ③ 改默认 | 缺省从 100 变 20 | 旧文件里没写的字段，含义变了 |

**① 是最好的一种**：它表现为"数据没了"，会被注意到。

**② 最坏**，理由和 `contract-evolution.md` 一致，但在状态文件上更严重——
⭐⭐⭐⭐⭐ 交接包里的语义错误至少能被下游的异常值触发一次怀疑，
而状态文件里的值**一直在那儿，从来没人怀疑过**。

```
progress.json: {"last_offset": 1200}     ← v1 写的是"字节偏移"
v4 读作"条目偏移"，从 1200 条开始读
→ 跳过 1200 条真实数据
→ ⭐⭐⭐⭐⭐ 输出完整、格式正确、覆盖率看起来还挺高
```

**③ 最难归因**：症状是"这次跑出来的比上次少"，
而排查方向几乎总是"数据源变了"，不会是"默认值变了"。

## 3. 为什么完全没有校验

技能间契约至少有 schema 和版本协商（参见 `skill-interfaces`）。
状态文件什么都没有，原因是结构性的：

> ⭐⭐⭐⭐⭐ **状态文件被当成"自己的私有文件"，
> 于是它享受了内部的信任等级，却承担了跨版本的外部风险。**

三个后果：

1. ⭐⭐⭐⭐⭐ **没有 schema**——因为"我自己写的我知道格式"
2. ⭐⭐⭐⭐⭐ **没有版本字段**——因为当时只有一个版本
3. ⭐⭐⭐⭐ **没有来源标记**——读的时候不知道是谁写的、什么时候写的

第 2 条最要命：**版本字段只有在第二次修改时才第一次被需要，
而那时文件里已经有一批没带版本的历史数据了。**

> ⭐⭐⭐⭐⭐ 所以版本字段必须在第一次写文件时就带上——
> 它是那种"现在不写就永远补不回来"的东西。

## 4. ⭐⭐⭐⭐⭐ 读不懂就重算，不要猜

读取旧状态时的两个选项：

```
A. 猜：字段不认识 → 按名字猜个大概 → 继续
B. 重算：字段不认识 → 判定为不可用 → 从头跑
```

> ⭐⭐⭐⭐⭐ **A 看起来是"兼容"，实际是把一个明确的失败换成了一个不明确的错误。**

这条与 `skill-output/references/output-becomes-fact.md` 那条
"技能不得假设上下文里的既有结论是真的"完全同源：
⭐⭐⭐⭐⭐ **无来源就重算，不得引用**——状态文件和上下文里的结论，
在这一点上是同一种东西。

判据：

```python
if state.get("state_version") != CURRENT:
    # ⭐⭐⭐⭐⭐ 不猜、不迁移、不部分使用
    state = {}          # 视为无状态
    log("状态版本不匹配，已重算")
```

> ⭐⭐⭐⭐ 副作用是"重跑了一遍"（成本），
> 换来的是"不会静默错"（正确性）。
> 状态存在的意义是省时间，⭐⭐⭐⭐⭐ **当它省下的时间换来的是不确定性，它就不该被用。**

## 5. 状态文件的最小字段集

```json
{
  "state_version": 3,
  "written_by": "skill-name@1.4.0",
  "written_at": "2026-10-01T10:12:33+08:00",
  "run_id": "20261001-101233-a7f2",
  "data": { }
}
```

五个字段，每个都有独立用途：

| 字段 | 没有它会怎样 |
|---|---|
| ⭐⭐⭐⭐⭐ `state_version` | 无法判定兼容 → 只能猜 |
| ⭐⭐⭐⭐ `written_by` | 无法区分是技能写的还是人手改的 |
| ⭐⭐⭐⭐⭐ `written_at` | 无法判定新鲜度 → "旧状态"被当成"已完成" |
| ⭐⭐⭐⭐ `run_id` | 无法区分两次运行 → 并发时无法归因 |
| ⭐⭐⭐ `data` 单独一层 | 元数据与业务数据混在一起，schema 无法演进 |

> ⭐⭐⭐⭐⭐ **`data` 单独包一层是最容易被省、也最难后补的一个**
> ——没有它，将来每加一个元字段都和业务字段平级，无法区分。

## 6. 迁移函数的写法

三条规则，按顺序：

```
① ⭐⭐⭐⭐⭐ 迁移是显式的函数，不是读取时的 if 拼凑
② ⭐⭐⭐⭐  只迁移向前（旧 → 新），不写反向迁移
③ ⭐⭐⭐⭐⭐ 迁移失败 = 视为无状态，不是抛异常
```

③ 最反直觉，也最该遵守：**抛异常会让技能挂掉，而"没状态"它还能跑**。

```python
MIGRATIONS = {1: migrate_1_to_2, 2: migrate_2_to_3}

def load_state(path):
    raw = json.load(open(path))
    v = raw.get("state_version")
    if v is None or v > CURRENT:      # ⭐ 未来版本同样视为不兼容
        return {}
    while v < CURRENT:
        fn = MIGRATIONS.get(v)
        if fn is None:                # ⭐⭐⭐⭐⭐ 没有迁移路径 → 重算
            return {}
        raw = fn(raw); v += 1
    return raw.get("data", {})
```

> ⭐⭐⭐⭐⭐ `v > CURRENT` 那一支常被漏：状态文件比技能还新
> （用户从新版本回退了技能，或多台机器版本不一致），
> 而它和"版本太旧"一样不可用。
