# 状态的作用域与位置

> 状态文件放哪，是一个比"写什么"更早的决定，而且它几乎从来没被显式做过。

## 一、两个作用域是分开的

技能有作用域（enterprise / personal / project，见《skill-loading》），状态文件也有作用域。
**这两套作用域互不知道对方的存在。**

```
技能在 project 级   → 只有这个项目能看到它
状态写在 ~/.cache/  → 所有项目共用一份
```

> ⭐⭐⭐⭐⭐ **技能是按作用域加载的，状态是按路径读写的——
> 没有任何机制保证两者指向同一个范围。**

后果不是报错，是"技能生效了、状态串了"：

| 组合 | 症状 |
|---|---|
| 技能 project 级 + 状态全局 | ⭐⭐⭐⭐⭐ A 项目的进度被 B 项目读到，两边互相污染 |
| 技能 personal 级 + 状态项目内 | ⭐⭐⭐⭐ 换个项目就"失忆"，而状态文件明明还在 |
| 技能 project 级 + 状态在 /tmp | ⭐⭐⭐⭐ 机器重启后静默从零开始，看起来像"第一次跑" |

> ⭐⭐⭐⭐⭐ 三者都不报错。状态读不到时技能的默认动作不是"报告无状态"，
> 而是**当成首次运行**——而首次运行的输出是完全合法的。

## 二、"读不到"和"没有"是同一个动作

```
state = read(path)
if not state:  # 不存在 / 权限 / 路径错 / 被清理
    state = {}   # ← 首次运行
```

> ⭐⭐⭐⭐⭐ **这个 `if` 把四种完全不同的情况合并成了一种。**

其中只有"真的第一次跑"是无害的。另外三种：

| 真实情况 | 被当成 | 代价 |
|---|---|---|
| 路径权限变了 | 首次运行 | ⭐⭐⭐⭐ 重复做已做的事（写入类技能 = 重复副作用） |
| 换了一台机器 | 首次运行 | ⭐⭐⭐⭐ 同上，且发生在最不被注意的时候 |
| 状态被别的技能覆盖 | 首次运行 | ⭐⭐⭐⭐⭐ 原状态丢失，且没有任何记录 |

修法只要一行：**区分"不存在"和"读失败"**。

```
不存在  → 首次运行（正常）
读失败  → 报错，不得当成首次运行
```

> ⭐⭐⭐⭐⭐ 在写入类技能里，这个区分的价值不在正确性，在**副作用次数**。

## 三、位置的选择顺序

不是"放哪都行然后记住它"，是有明确的优先级：

| 优先级 | 位置 | 适用 |
|---|---|---|
| 1 | ⭐⭐⭐⭐⭐ 项目内（`.claude/state/` 或产物目录） | 状态只对本项目成立 |
| 2 | 用户级目录 | 状态跨项目通用（个人偏好、全局计数） |
| 3 | ⭐ 临时目录 | 只在单次运行内有效 |

判据一句话：**这份状态，换到另一个项目还成立吗？**
成立 → 用户级；不成立 → 项目内。

最容易做错的一类是⭐⭐⭐⭐ **"看起来跨项目通用、其实不是"**：
进度、覆盖率、已处理清单——它们都只在同一个工作对象上成立，
而"换个项目"恰恰意味着工作对象换了。

> ⭐⭐⭐⭐⭐ 反过来放（项目状态放用户级）的失败是**双向**的：
> 不只是读到错的状态，还会**污染另一个项目**——
> 于是两个项目各自都"有时对有时不对"，而排查时没人会想到对方项目。

## 四、相对路径的陷阱

```
state_path = "state/progress.json"
```

> ⭐⭐⭐⭐⭐ **相对路径解析的基准是进程的当前工作目录，不是技能文件所在目录。**

同一个技能，从不同目录被触发时读写的是不同文件——
而"从不同目录触发"是常态，不是异常。

| 触发方式 | cwd |
|---|---|
| 在项目根目录 | 项目根 |
| ⭐ 在子目录处理文件 | 子目录 |
| 被另一个技能调用 | ⭐⭐⭐⭐ 调用者的 cwd |

第三种最隐蔽：⭐⭐⭐⭐⭐ **被链式调用时，状态位置由上游决定，而上游不知道下游有状态。**

规则：

- ⭐⭐⭐⭐⭐ **状态路径必须由技能自己解析到绝对路径**，不得依赖 cwd
- ⭐⭐⭐⭐ 解析基准优先用**工作对象的位置**（仓库根、目标文件所在目录），不是技能文件位置
- ⭐⭐⭐⭐ 解析失败要报错，不得静默回落到当前目录

## 五、状态与产物必须分开

```
工作目录/
  report.md        ← 产物（给人看，会被提交、被读、被发送）
  progress.json    ← 状态（给机器看，不该被提交）
```

混在一起的三种后果：

| 混淆 | 后果 |
|---|---|
| 状态进产物目录 | ⭐⭐⭐⭐ 被提交、被别人拉到、被当成产物读 |
| 产物当状态 | ⭐⭐⭐⭐⭐ 产物被下游改了之后，状态就错了（而它是"看起来还在"的） |
| 两者同名 | ⭐⭐⭐⭐⭐ 覆盖：一次运行同时毁掉产物和进度 |

> ⭐⭐⭐⭐⭐ **"产物当状态"是最贵的一种**：读产物文件（如报告）判断"做到哪了"，
> 而 report 被人手改过——于是进度判断基于一份已经不是自己写的内容。

规则：

- ⭐⭐⭐⭐⭐ 状态文件加前缀或放独立目录（`state/`），与产物物理分离
- ⭐⭐⭐⭐⭐ 状态文件必须在 `.gitignore` 里——它不该进版本库
- ⭐⭐⭐⭐ 判断进度只看状态文件，**不得解析产物内容推断进度**

## 六、清理的作用域

删除状态文件是一个"重置"动作，而⭐⭐⭐⭐⭐ **它的作用域常常比作者以为的大**：

```
rm ~/.claude/state/*.json    # 以为是重置当前项目
                             # 实际是重置了所有项目
```

反过来也一样：⭐⭐⭐⭐ 只删项目内的状态，全局状态还在，于是"重置了但没完全重置"——
这种半重置状态比不重置更难排查，因为⭐⭐⭐⭐⭐ **部分状态存在时，技能的行为看起来是"有记忆的"，只是记的是错的。**

规则：

- ⭐⭐⭐⭐⭐ 清理动作必须写明作用域（删的是哪一级）
- ⭐⭐⭐⭐⭐ **清理前必须能回答"这份状态属于哪个作用域"**——答不上来说明位置选错了
- ⭐⭐⭐⭐ 提供"重建"路径：删完之后，从产物重放还是从头跑？

## Critical Rules

- ⭐⭐⭐⭐⭐ **状态的作用域必须与技能的作用域一致**，否则会静默串或静默失忆
- ⭐⭐⭐⭐⭐ **"读不到状态"不得默认当成首次运行**——必须区分"不存在"与"读失败"
- ⭐⭐⭐⭐⭐ 状态路径由技能自己解析为绝对路径，不得依赖 cwd
- ⭐⭐⭐⭐⭐ 状态与产物物理分离（独立目录 + `.gitignore`）
- ⭐⭐⭐⭐⭐ 不得通过解析产物内容来推断进度
- ⭐⭐⭐⭐ 换项目即换工作对象 → 状态必须是项目级
- ⭐⭐⭐⭐ 清理动作必须显式声明作用域

## 自检

| 检查 | 方法 |
|---|---|
| 作用域一致吗 | ⭐⭐⭐⭐⭐ 技能装到另一个项目，状态会串吗？会 → 位置错了 |
| 路径稳吗 | 从子目录、从另一个技能调用，读写的是同一个文件吗？ |
| 读失败会怎样 | ⭐⭐⭐⭐⭐ 手动 `chmod 000` 状态文件后跑一次——它报"首次运行"还是报错？报首次运行 → 有 bug |
| 会污染吗 | 在两个项目交替跑，看进度是否互相影响 |
| 能重置吗 | 能不能一句话说清"删哪些文件 = 完全重置" |
