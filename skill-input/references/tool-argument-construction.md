## 1. ⭐⭐⭐⭐⭐ 一句"用 X 工具"漏掉了什么

```markdown
3. 用 Jira API 创建工单
```

这句话交代了**做什么**和**用什么**，漏掉的是：

```
⭐⭐⭐⭐⭐ 怎么调：端点 / 方法 / 认证方式
⭐⭐⭐⭐⭐ 传什么：必填字段 / 字段名 / 取值来源
⭐⭐⭐⭐⭐ 算成功：什么响应算成功 / HTTP 200 不等于成功
⭐⭐⭐⭐⭐ 失败了：重试 / 报告 / 禁止什么
```

> ⭐⭐⭐⭐⭐ 这四项里，模型能自己推的只有第 1 项的粗粒度，
> 而⭐⭐⭐⭐⭐ **第 2 项它推不出来——因为字段名是任意的**。

而它的默认动作是：

> ⭐⭐⭐⭐⭐ **猜一个看起来合理的参数，调用，然后按"成功"继续往下走。**

这与默认动作那份完全同构，但后果更重：
⭐⭐⭐⭐⭐ **猜错参数会真的发出一次请求**——这是写入动作，不是推理。

## 2. ⭐⭐⭐⭐⭐ 猜参数名是幻觉的高发区

为什么工具参数特别容易猜错：

```
字段名是任意命名的：
  ticket_title / title / summary / subject
  assignee / assignee_id / owner / responsible
```

> ⭐⭐⭐⭐⭐ **语义上都说得通，实际只有一个是对的。**
> 模型没有偏好可以依据，于是它选最常见的那个。

三种具体的失败形状：

**① ⭐⭐⭐⭐⭐ 参数名错 → 400，但模型可能改写**

```
返回 400 "unknown field: title"
→ ⭐⭐⭐⭐⭐ 模型把它当成"需要调整"，改一个字段名再试
→ 三次之后可能创建了一个字段残缺的工单
```

**② ⭐⭐⭐⭐⭐ 参数名错但被静默忽略**

```
很多 API 忽略未知字段而不报错
→ 工单创建成功，但标题是空的
→ ⭐⭐⭐⭐⭐ 完全静默：200 + 成功 + 缺内容
```

> ⭐⭐⭐⭐⭐ 第二种是最危险的，而且⭐⭐⭐⭐⭐ **它比第一种更常见**——
> 因为宽松解析比严格解析普遍。

**③ ⭐⭐⭐⭐ 值取错了来源**

```
"assignee": 填了当前用户而不是报告人
```

> ⭐⭐⭐⭐ 字段名对了，值错了。⭐⭐⭐⭐⭐ 这一类连报错都没有，
> 而且需要领域知识才能发现（谁该被指派，模型不知道）。

## 3. ⭐⭐⭐⭐⭐ 参数模板：能抄的写法

不要写：

```markdown
3. 用 Jira API 创建工单，填入标题、描述和负责人
```

要写：

````markdown
3. 创建工单（POST /rest/api/3/issue）
   ```json
   {
     "fields": {
       "project":   { "key": "<项目 KEY：取自输入，不得猜测>" },
       "summary":   "<标题：取自输入的 [标题] 字段>",
       "issuetype": { "name": "Bug" }
     }
   }
   ```
   ⭐⭐⭐⭐⭐ 未知字段：先用 [查 schema 的命令] 确认，不得猜测字段名
````

> ⭐⭐⭐⭐⭐ 三个关键改动：
> ① **给出确切的字段名**（不是"标题"而是 `summary`）
> ② **给出每个值的来源**（取自输入的哪一字段）
> ③ ⭐⭐⭐⭐⭐ **显式标注"不得猜测"**

第 ③ 条最容易省，而它⭐⭐⭐⭐⭐ **正是唯一能阻止"试到成功为止"的那一条**。
（与错误协议里的第④段"明确禁止什么"是同一条规则。）

成本对比很划算：

```
一段 JSON 模板 ≈ 60 token
覆盖的失败：⭐⭐⭐⭐⭐ 一次猜错 = 一次错误的真实写入
```

## 4. ⭐⭐⭐⭐⭐ 未知字段先查 schema，不要猜

写进正文的一句话（对所有外部工具通用）：

```markdown
⭐⭐⭐⭐⭐ 遇到不确定的字段名：先查询该工具的 schema/文档，
         确认后再调用。不得基于语义猜测字段名，也不得试错式重试。
```

> ⭐⭐⭐⭐⭐ 这是"先探测，不先写"的第七个同构场景
> （环境、端口、规模、字段结构、上游产物、分支判据、工具 schema）。
>
> ⭐⭐⭐⭐⭐ 而这里它比别处更关键：**前六个猜错只是结果错，
> 这个猜错是真的发出一次外部请求。**

配套两条：

**① ⭐⭐⭐⭐ 禁止试错式重试**

```
❌ 用 title 失败 → 改用 summary → 再试
✅ ⭐⭐⭐⭐⭐ 第一次就查 schema，一次调对
```

> ⭐⭐⭐⭐⭐ 试错式重试在只读场景是效率问题，在写入场景是数据问题——
> ⭐⭐⭐⭐ 中途某一次可能成功了，而你以为是最后一次那个。

**② ⭐⭐⭐⭐⭐ 写入类调用前必须有确认点**

```
创建/发送/删除类调用 → ⭐⭐⭐⭐⭐ 先展示将要提交的内容，确认后再发
```

> ⭐⭐⭐⭐⭐ 这是唯一能接住"字段名猜错但被静默忽略"的机制——
> ⭐⭐⭐⭐ 因为那种失败在调用之后完全不可见。

## 5. ⭐⭐⭐⭐⭐ 失败时不要换工具，先换参数

模型面对工具调用失败的默认动作是：

```
⭐⭐⭐⭐⭐ "这个工具走不通，换一个办法"
```

而多数真实的失败其实是：

```
参数错 / 认证过期 / 权限不足 / 上游限流
```

> ⭐⭐⭐⭐⭐ 这四种都不是"工具不对"，换工具是错的方向。

写进正文的分诊表（一张表就能挡住）：

| 响应 | ⭐ 判定 | ⭐⭐⭐⭐⭐ 动作 |
|---|---|---|
| 400 unknown field | 参数名错 | 查 schema，不要换工具 |
| 401 / 403 | ⭐⭐⭐⭐⭐ 认证或权限 | 停止并报告，**不要重试**（重试不会改变权限） |
| 429 | 限流 | 按 Retry-After 等待 |
| ⭐⭐⭐⭐⭐ 200 但内容为空 | ⭐⭐⭐⭐⭐ 字段被忽略 | ⭐⭐⭐⭐⭐ 校验必填字段是否真的写入，视为失败 |

> ⭐⭐⭐⭐⭐ 最后一行最重要：**200 不等于成功**（已反复强调），
> 而这一行给出了⭐⭐⭐⭐⭐ 具体的校验动作——不只是"别把 200 当成功"这句口号。

## 6. ⭐⭐⭐⭐ 一个自检

写完后逐条问：

```
① ⭐⭐⭐⭐⭐ 每个外部工具调用，字段名都写全了吗？（不是"标题"而是 summary）
② ⭐⭐⭐⭐⭐ 每个值的来源都标了吗？（取自输入的哪一字段）
③ ⭐⭐⭐⭐⭐ 写了"不得猜测字段名"吗？
④ ⭐⭐⭐⭐⭐ 写入类调用前有确认点吗？
⑤ ⭐⭐⭐⭐ 有失败分诊表吗？（区分参数错 / 权限 / 限流 / 200 但空）
```

> ⭐⭐⭐⭐ 第 ⑤ 条常被省，而它是⭐⭐⭐⭐⭐ 唯一能防止"换个办法继续"的一条。
> 没有它，模型会把一次参数错误，演化成一串你没预期的操作。
