## 1. ⭐⭐⭐⭐⭐ "除了 A"被处理成"包括 A"

用户说：

```
"把所有服务的日志都汇总一遍，除了 gateway 那个"
```

输出里 gateway 的日志在，而且它通常是最大的一份——
于是它在汇总里占比最显眼。

> ⭐⭐⭐⭐⭐ **这不是"理解错了"，是"没有处理"。**
> 模型读到了整句，提取出了动作（汇总）和对象（所有服务的日志），
> ⭐⭐⭐⭐⭐ **而"除了 gateway"是一个修饰语，不是这两者之一。**

失败的形状值得单独记：

```
输出里有 gateway    → 用户看到，会说"我说了不要 gateway"
输出里没有 gateway  → 用户什么都不会说
```

> ⭐⭐⭐⭐⭐ 所以这类错误**只在"用户恰好记得自己说过"的时候才被发现**。
> 在长会话里，用户常常自己也不记得第三轮时提过一个例外。

## 2. ⭐⭐⭐⭐⭐ 为什么否定这么容易被漏

不是模型能力问题，是**提取结构**的问题。模型从输入里提取的是：

```
动作（动词）· 对象（名词短语）· 修饰（形容词/数量）
```

而"除了 X"不属于这三类的任何一类——⭐⭐⭐⭐⭐ **它是一个对集合的运算符，
不是集合的元素**。

于是它需要一个额外的动作才能被保留下来：**把它应用到已经提取出的集合上**。

```
提取：{所有服务的日志}
应用：− {gateway}      ← ⭐⭐⭐⭐⭐ 这一步是"额外的一步"
```

> ⭐⭐⭐⭐⭐ **而"额外的一步"在没有被显式要求时，依赖模型自己去想到要做。**
> 它在短输入里通常做了，在长输入里通常没做——
> ⭐⭐⭐⭐⭐ 因为长输入里要做的"额外步骤"不止这一个，它们互相竞争。

中文额外吃亏的地方：否定词常出现在**句尾**（"……，测试数据不算"），
而⭐⭐⭐⭐ 句尾信息在近因区，注意力反而应该更高——
⭐⭐⭐⭐⭐ 但它被读成了"补充说明"，不是"约束"。

## 3. ⭐⭐⭐⭐⭐ 三种否定，三种漏法

### ① 排除型（"除了 / 不含 / 跳过"）

```
"统计所有接口的耗时，不含健康检查"
```

漏法：**被当成举例**（"健康检查这种的就不用管了"，然后照样统计了）。

> ⭐⭐⭐⭐⭐ 判据：排除项通常是**数量大或形态特殊的那一批**——
> 正因为它们显眼才被单独点名，也正因如此，漏掉它们对结果影响最大。

### ② 边界型（"只 / 仅限 / 只要"）

```
"只看最近一周"
```

漏法：被当成**强调**（"最近一周最重要"），于是其余部分以"补充"的名义进了输出。

> ⭐⭐⭐⭐⭐ 与排除型的差别在于：排除型漏了是"多了东西"（可见），
> ⭐⭐⭐⭐⭐ 边界型漏了通常是"多了东西但看起来更全"——
> 而"更全"在多数评审语境里被当成优点。

### ③ 条件否定（"如果……就不 / 除非"）

```
"如果某个文件超过 1MB 就跳过它"
```

漏法最严重，因为它**同时需要"读否定"和"执行判断"两步**：

```
❌ 跳过整个条件句 → 全量处理（没有任何东西报错）
❌ 读了条件但没判断 → 全量处理（同上，且看起来执行了指令）
❌ 判断了但动作反了 → 只处理超过 1MB 的（输出存在但内容完全相反）
```

> ⭐⭐⭐⭐⭐ 第三种最贵：它**不是漏做，是做反了**，
> 而输出里没有任何东西能说明"筛选条件被取反了"。

## 4. ⭐⭐⭐⭐⭐ 否定与分母：例外改变了 N

`input-cardinality.md` 说"批量必须先枚举出 N"。这份补上后半句：

> ⭐⭐⭐⭐⭐ **N 是应用例外之后的数字，不是应用之前的。**

```
目录里 47 个文件
"除了 tests/ 下的"  → tests/ 有 12 个
N = 35，不是 47
```

而实际发生的通常是：

```
枚举得到 47 → 处理 47 → 输出"共 47 个"
```

> ⭐⭐⭐⭐⭐ 输出里那句"共 47 个"是真实的，
> ⭐⭐⭐⭐⭐ **它只是把一个"例外被漏掉"的事实，包装成了一个看起来经过核对的数字。**

修法不是"记得减"，是**顺序**：

```
❌ 枚举 → 处理 → 报数
✅ ⭐⭐⭐⭐⭐ 枚举 → 应用例外 → 再数一次 → 处理 → 报数
```

⭐⭐⭐⭐⭐ 关键在"再数一次"——它把一个心算变成了两次可核对的动作，
而且第二次的数字会暴露第一次的例外有没有生效。

## 5. ⭐⭐⭐⭐⭐ 否定的位置决定它有没有被读到

同一句例外，放在三个位置，结果完全不同：

| 位置 | 效果 |
|---|---|
| 句首（"除了 gateway，汇总所有服务日志"） | ⭐⭐⭐⭐⭐ 最好：在集合形成之前就约束了它 |
| 句中（"汇总所有服务日志，除了 gateway，按天分组"） | ⭐⭐⭐ 容易被"按天分组"挤掉 |
| 句尾（"汇总所有服务日志，按天分组。gateway 不用管"） | ⭐⭐⭐⭐ 取决于它是否另起一句 |

> ⭐⭐⭐⭐⭐ 这是作者**能控制**的，但它几乎从不被控制——
> 因为写输入的是用户，不是作者。

所以技能侧能做的只有一件事：**在读输入时先扫一遍否定词**。

```
扫：除了 / 不含 / 不包括 / 跳过 / 忽略 / 不用管 / 不算 / 去掉
    只 / 仅限 / 只要 / 仅
    除非 / 如果……就不 / ……时跳过
```

> ⭐⭐⭐⭐⭐ 这份词表约 60 token，而它守住的是"整个任务的范围"。
> 这是输入侧性价比最高的一段正文。

呼应：《skill-crafting》的 `vague-word-blacklist` 是 grep 正文的含糊词；
⭐⭐⭐⭐⭐ 这份是 grep **用户输入**的否定词——同一个手法，作用在另一端。

## 6. ⭐⭐⭐⭐⭐ 写法：把否定变成枚举

否定之所以难处理，是因为它要求"对集合做减法"，
而⭐⭐⭐⭐⭐ **集合本身在进入模型时常常还没形成**（用户说的是"所有服务"，
模型得先去列目录才知道有哪些）。

两种写法都能消掉这一步：

### ① 让例外先落地成一个列表

```
1. 列出所有服务目录 → services[]
2. 读到任何排除条件时，从 services[] 中移除，并记录移除了哪些
3. 输出首行写"范围：services[] 共 N 个（已排除：gateway）"
```

⭐⭐⭐⭐⭐ 第三步是核心：**排除项必须出现在输出里**。
因为⭐⭐⭐⭐ "没排除"和"没有例外"在输出上是同一个样子，
只有写出"已排除：X"才能区分。

### ② 把"只/仅限"改写成显式的枚举

```
❌ "只看最近一周"
✅ "时间范围 = [今天−7, 今天]；范围外的数据不进入任何统计"
```

第二句的后半句是必要的——⭐⭐⭐⭐⭐ "只看"定义的是应该看什么，
而没有定义范围外的东西该**怎么办**（不看？还是看了但不计入？）。
而⭐⭐⭐⭐⭐ 不定义时，模型默认"看了，且顺手放进去了"——
因为它的完成倾向是让输出更完整。

## 7. ⭐⭐⭐⭐⭐ 自检

| 检查 | 方法 |
|---|---|
| 输入里有否定词吗 | 扫上面那张 60 token 的词表 |
| ⭐⭐⭐⭐⭐ 例外生效了吗 | 把排除项单独放进输入跑一次，它应该**不出现** |
| 排除项出现在输出里吗 | grep "已排除 / 未纳入 / 跳过" |
| ⭐⭐⭐⭐⭐ N 是减法之后的吗 | 数一遍剩下的，和报的数对一下 |
| "只/仅限"定义了范围外怎么办吗 | 看有没有"范围外不进入统计"这类句子 |

最便宜的一条：

> ⭐⭐⭐⭐⭐ **给技能输入一句"除了 X"，看输出里 X 在不在。**
> 在 → 否定没被处理，而技能的其他部分看起来一切正常。

## 一条边界

⭐⭐⭐ 否定处理不需要写成一节正文，通常一句就够：

```
读到排除/限定条件时：先形成完整集合，再应用条件，
并在输出首行写明"范围：N 个（已排除：……）"。
```

⭐⭐⭐⭐⭐ 超过三行的否定处理规则，通常说明该用的不是规则而是枚举步骤。
