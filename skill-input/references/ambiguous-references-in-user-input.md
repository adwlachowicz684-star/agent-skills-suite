## 1. ⭐⭐⭐⭐⭐ 一句"也这样处理"

```
用户：把 A 模块的日志改成 JSON 格式
（模型做完了）
用户：B 也这样
```

> ⭐⭐⭐⭐⭐ 这句话不缺主语、不缺动词、语法完整。
> ⭐⭐⭐⭐⭐ 它缺的是**"这样"指向什么**——而那个东西在上一轮的输出里。

这是本份的核心形状：**输入在语法上完整，在语义上依赖上下文。**

## 2. ⭐⭐⭐⭐⭐ 五类指代，按危险度排

**① ⭐⭐⭐⭐⭐ 代词与指示词**（"也这样""同样处理""那个文件"）

```
⭐⭐⭐⭐⭐ 危险度最高：它看起来完整，且绑定失败完全静默
```

**② ⭐⭐⭐⭐⭐ 省略主语/宾语**（"再跑一次""继续""改回去"）

```
⭐⭐⭐⭐⭐ "改回去"——回到哪个版本？改动前？上一次成功时？某个提交？
```

**③ ⭐⭐⭐⭐⭐ 相对范围**（"剩下的""其他的""全部"）

```
⭐⭐⭐⭐⭐ "剩下的"依赖一个**技能自己算出来的**集合——
而那个集合模型和用户可能算得不一样
```

**④ ⭐⭐⭐⭐ 相对时间**（"上次""最近""跟之前一样"）

```
已由《skill-input》的 `relative-time-resolution.md` 覆盖，
⭐⭐⭐⭐⭐ 但那里讲的是"窗口边界"，这里是"参照物"——
"上次"是上次运行，还是上次用户说话？
```

**⑤ ⭐⭐⭐⭐ 比较级与程度**（"更简洁一点""详细一些""差不多"）

```
⭐⭐⭐⭐⭐ 它依赖一个**未说出的基线**。
"更简洁"是比刚才那版简洁？比默认输出简洁？
```

## 3. ⭐⭐⭐⭐⭐ 为什么它不会被分诊拦下

已有的输入分诊判的是三类：残缺、矛盾、超范围。

```
残缺？  ❌ 不缺——每个句子成分都在
矛盾？  ❌ 不矛盾
超范围？❌ 完全在范围内
```

> ⭐⭐⭐⭐⭐ 三类判据全部通过，而输入仍然指向不明。
> ⭐⭐⭐⭐⭐ **分诊检查的是"句子是不是完整的"，不是"它指的是不是唯一的"。**

这是个缺口，而且是高频缺口——⭐⭐⭐⭐⭐ **多轮对话里，
后续轮次的输入天然大量使用指代**（因为人不会重复说过的话）。

## 4. ⭐⭐⭐⭐⭐ 模型的默认动作：就近绑定

```
遇到指代，模型不追问，它绑定到一个候选。
而它选哪个？→ ⭐⭐⭐⭐⭐ 就近 + 最显著
```

```
就近  = 上下文中最近一次提到的同类对象
最显著 = 刚刚花最多篇幅处理的那个
```

> ⭐⭐⭐⭐⭐ 这个默认在多数时候是对的——**这正是它危险的原因**：
> ⭐⭐⭐⭐⭐ 它对到不需要纠正，错到也不会被发现（因为结果看起来合理）。

最坏的一种错法：

```
⭐⭐⭐⭐⭐ 就近绑定成功，但用户指的是另一个
→ 技能照常执行、输出完整、格式正确
→ ⭐⭐⭐⭐⭐ 而它处理的是错的对象
```

> ⭐⭐⭐⭐⭐ 与《skill-crafting》的 `positional-references.md` 完全同构：
> 那份讲技能**内部**的"上一步/第 3 步"会因插入而错位，
> 这份讲**用户侧**的"也这样/那个"会因上下文而错位。
> 共同解法也一致：**给中间对象起名**。

## 5. ⭐⭐⭐⭐⭐ 判据：有没有第二个候选

一句可执行的判据：

> ⭐⭐⭐⭐⭐ **在上下文中，这个指代有几个可能的绑定对象？**

```
1 个  → ⭐⭐⭐⭐ 直接绑定，并在输出里写明绑定结果（可见即可查）
≥2 个 → ⭐⭐⭐⭐⭐ 必须处理，不得自行选一个
```

> ⭐⭐⭐⭐⭐ 关键在"≥2 个时不得自行选"：
> ⭐⭐⭐⭐⭐ 不是"要问"，而是"不得静默决定"——问和标注都是合法处置。

三种常见多候选来源：

```
① ⭐⭐⭐⭐⭐ 上一轮处理了多个同类对象（A、B 都改过 → "也这样"指谁？）
② ⭐⭐⭐⭐⭐ 对话里出现过多个同名/同类事物（两个"配置文件"）
③ ⭐⭐⭐⭐⭐ 指代依赖一个隐含集合（"剩下的" = 全集 - 已处理，而全集未定义）
```

> ⭐⭐⭐⭐⭐ 第 ③ 条最隐蔽：⭐⭐⭐⭐ 它看起来有一个确定的计算方式，
> ⭐⭐⭐⭐⭐ 但"全集"通常是技能自己算出来的——⭐⭐⭐⭐⭐ **于是"剩下的"
> 依赖一个用户从没见过、也从没确认过的集合。**

---

## 6. ⭐⭐⭐⭐⭐ 三种处置，第二种最常用也最常被省

| | 何时 | 动作 |
|---|---|---|
| ⭐⭐⭐⭐ 唯一候选 | 只有 1 个绑定对象 | 执行，并在输出首行写明绑定结果 |
| ⭐⭐⭐⭐⭐ **绑定并标注** | 有明显首选但存在次选 | ⭐⭐⭐⭐⭐ 按首选执行，输出中显式声明"按 X 理解；若指 Y 请说明" |
| ⭐⭐⭐⭐⭐ 必须问 | 无首选 / 选错代价不可逆 | 停止并列出候选 |

> ⭐⭐⭐⭐⭐ 第二行是本份最值得抄的一条：
> ⭐⭐⭐⭐⭐ **它同时满足"不打断"和"不静默"**——
> 而人们通常只在"执行"和"追问"之间二选一，于是要么静默要么啰嗦。

它与 `inference-vs-asking.md` 的 L2（推断并标注）是同一原则，
但那里的判据是"错了能不能看出来"，这里是"**有没有第二个候选**"：

```
⭐⭐⭐⭐⭐ 两个判据要一起用：
  有第二个候选 → 必须标注（本份）
  错了看不出来 → 必须问（那份）
  ⭐⭐⭐⭐⭐ 两条都命中 → 必须问，不能只标注
```

第三条（必须问）的触发条件要写死，否则模型会把它读成"尽量别问"：

```
⭐⭐⭐⭐⭐ 涉及不可逆动作（删除/发送/发布）时必须问，无论候选是否明显
⭐⭐⭐⭐⭐ "改回去""撤销"类请求必须问（回到哪个状态）
```

## 7. ⭐⭐⭐⭐⭐ 写法

最小写法（约 40 token，加在输入处理里）：

```markdown
## 输入含指代时
- ⭐⭐⭐⭐⭐ "也这样""同样""那个""剩下的""改回去"等含指代时，
  先列出可能的绑定对象
- ⭐⭐⭐⭐⭐ 存在 ≥2 个候选时，不得自行选一个：
  有明显首选则执行并在输出首行声明绑定结果；无首选则列出候选并询问
- ⭐⭐⭐⭐⭐ 涉及不可逆动作时，无论候选是否明显都必须确认
```

三条配套写法：

```
① ⭐⭐⭐⭐⭐ 给中间产物/处理对象起名（"→ 记为 target_modules"），
   让后续指代有唯一绑定的锚点（与 `positional-references.md` 同手法）
② ⭐⭐⭐⭐⭐ 输出首行写"本次处理的对象：<显式列表>"——
   成本一行，让绑定错误在**第一屏**就可见
③ ⭐⭐⭐⭐ 多轮任务里，每轮开头复述一次当前作用域
   （"当前处理范围：A、B 两个模块"）
```

> ⭐⭐⭐⭐⭐ 第 ② 条与《skill-output》的 `output-ordering-priority.md` 咬合：
> ⭐⭐⭐⭐⭐ "本次处理的对象"是"会让用户改变用法的信息"，属于前 5 行内容。

一个便宜的额外收益：

> ⭐⭐⭐⭐⭐ 写了这一行之后，"处理错了对象"这类问题的排查时间接近于零——
> 因为第一屏就写着它以为在处理什么。

## 8. ⭐⭐⭐⭐⭐ 自检

```
① ⭐⭐⭐⭐⭐ 技能有没有处理"用户输入含指代"的情况？（多半没有）
② ⭐⭐⭐⭐⭐ 有没有"存在 ≥2 候选时不得自行选"的硬规则？
③ ⭐⭐⭐⭐⭐ 输出首行写了"本次处理的对象"吗？
④ ⭐⭐⭐⭐⭐ 不可逆动作是不是无条件确认？
⑤ ⭐⭐⭐⭐⭐ "剩下的/其他的"这类词，全集定义了吗？
```

一个十秒判断：

> ⭐⭐⭐⭐⭐ **拿上一个任务，说一句"另一个也这样处理"。
> 它是问你了、还是直接做了？
> 直接做了 → 它绑定了一个候选，而你不知道是哪一个，
> 直到某次它绑错——而绑错时输出依然完整。**

## 一句可贴在墙上

> ⭐⭐⭐ **"也这样"不缺主语、不缺动词，它缺的是指向——
> 于是分诊三类判据全过，而模型就近绑定了一个候选。**
