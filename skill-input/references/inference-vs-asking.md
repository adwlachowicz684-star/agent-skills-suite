## 1. ⭐⭐⭐⭐⭐ 两种默认值，一种会问一种不会

同一个"缺"，两种反应：

```
缺输出格式 → 模型不问，自己选一个
缺业务口径 → 模型也不问，自己选一个
```

> ⭐⭐⭐⭐⭐ 差别只在于：**人会不会发现它在猜。**

> ⭐⭐⭐⭐⭐ 格式猜错了，用户一眼看到；
> ⭐⭐⭐⭐⭐ 口径猜错了，输出完全合理——只是算的是另一件事。

所以本份的出发点不是"该不该问"这个笼统问题，而是：

> ⭐⭐⭐⭐⭐ **哪些"猜"是可见的。可见的可以猜，不可见的必须问或标注。**

---

## 2. ⭐⭐⭐⭐⭐ 判据：错了的代价，不是缺的程度

常见但错的判据：

```
❌ "这条信息重不重要？重要就问"
```

> ⭐⭐⭐⭐⭐ 问题在于几乎所有被写进技能的信息都"重要"——
> ⭐⭐⭐⭐ 于是按这个判据，技能会变成一个问卷。

正确的判据只有一条：

> ⭐⭐⭐⭐⭐ **如果它猜错了，用户能从输出里看出来吗？**

```
能看出来 → 可以猜（错了会被立刻纠正，成本 = 一次返工）
⭐⭐⭐⭐⭐ 看不出来 → ⭐⭐⭐⭐⭐ 必须问，或推断但强制标注
```

---

## 3. ⭐⭐⭐⭐⭐ 三级决策表

| 级别 | 判据 | 动作 | 例子 |
|---|---|---|---|
| ⭐⭐⭐⭐⭐ **L1 推断即可** | 错了可见、可逆、不影响输出主体 | 直接填，不说明 | 输出用表格还是列表 |
| ⭐⭐⭐⭐⭐ **L2 推断并标注** | 错了不可见，但不改变结果性质 | ⭐⭐⭐⭐⭐ 填了并在输出里写明 | "未提供币种，按 CNY 计算" |
| ⭐⭐⭐⭐⭐ **L3 必须问** | 错了会改变结果本身 | ⭐⭐⭐⭐⭐ 停下来问，不得继续 | "留存"按注册口径还是活跃口径 |

> ⭐⭐⭐⭐⭐ 三级里最容易被跳过的是 **L2**——
> ⭐⭐⭐⭐ 因为 L1 和 L3 都有明确的动作（做 / 停），
> ⭐⭐⭐⭐⭐ 而 L2 是"照做，但留痕"，它看起来像多此一举。

而它恰恰是最常用的那一档：**大多数缺失既不至于要打断用户，也不该被静默地替他决定。**

## 4. ⭐⭐⭐⭐⭐ 该问的时候不问：推断被写成了事实

这是 L3 被当成 L1 时的后果：

```
用户："算一下留存率"
技能（没问口径）→ 按注册口径算 → 输出"留存率 41%"
```

> ⭐⭐⭐⭐⭐ 用户拿这个 41% 去汇报。
> ⭐⭐⭐⭐⭐ 而活跃口径下是 23%。

三个特征让它难以被发现：

```
① ⭐⭐⭐⭐⭐ 输出里没有任何"这是猜的"的痕迹
② ⭐⭐⭐⭐⭐ 数字本身是自洽的（分子分母都对）
③ ⭐⭐⭐⭐ 用户只有在和另一个数字对不上时才会怀疑
```

> ⭐⭐⭐⭐⭐ 这与《skill-output》的 `numbers-in-output.md` 完全咬合：
> ⭐⭐⭐⭐⭐ **数字的可信度来源不是精度，是口径；而口径恰恰是最容易被默选的东西。**

另一种变形更隐蔽：**默认值来自模型先验而非领域常识**。

```
按《skill-content》的 `default-actions.md`：
省略 = 授权模型按"通用互联网文本里的常见做法"决定
```

> ⭐⭐⭐⭐⭐ 所以对 L3 项，⭐⭐⭐⭐⭐ **"没写"不是中性动作，是一次默认授权**——
> 而这次授权的对象，是一个不知道你们公司口径的模型。

## 5. ⭐⭐⭐⭐⭐ 该推断的时候问了：确认疲劳

反向错误同样有代价，而且代价是**长期的**：

```
每次都问"输出用中文还是英文？"
→ 用户第 3 次开始不看内容直接回车
→ ⭐⭐⭐⭐⭐ 第 7 次，一条真正的 L3 问题被顺手回车了
```

> ⭐⭐⭐⭐⭐ **廉价确认会摧毁确认机制本身。**
> 这与 `human-checkpoint-design.md` 的"无脑确认会摧毁检查点的全部价值"是同一条。

三个信号说明你已经问太多：

```
① ⭐⭐⭐⭐ 问题的答案在上下文里已经出现过
② ⭐⭐⭐⭐⭐ 问的是"格式/措辞/顺序"这类错了可见的东西
③ ⭐⭐⭐⭐ 同一个问题在同一个任务里出现了第二次
```

> ⭐⭐⭐⭐⭐ 第 ② 条最该记：⭐⭐⭐⭐ **格式类问题永远不该问**——
> 它错了会被看见，而问它要花掉一次注意力预算。

## 6. ⭐⭐⭐⭐⭐ 第三种选择：推断并标注

L2 的标准写法只有一句：

```markdown
- 未提供币种时，按 CNY 计算，并在输出首行注明"币种未指定，按 CNY 计算"
```

> ⭐⭐⭐⭐⭐ 成本约 15 token，收益是⭐⭐⭐⭐⭐ **把一次静默的假设变成可见的事实**。

三种标注位置，效果差很多：

| 位置 | 效果 |
|---|---|
| ⭐⭐⭐⭐⭐ 输出首行 | 一定被读到 |
| 涉及的数字旁边 | ⭐⭐⭐⭐ 只在有人细看那个数字时被读到 |
| ⭐⭐ 脚注 / 结尾 | ⭐⭐⭐⭐⭐ 等于没写（用户读到正文就停了） |

> ⭐⭐⭐⭐⭐ 这与 `relative-time-resolution.md` 的"把解析结果写进输出首行"、
> `numbers-in-output.md` 的"未获取不得写在脚注"是同一条规则的第三次出现：
> ⭐⭐⭐⭐⭐ **静默失败的唯一解药是可见性，而可见性取决于位置。**

还有一个额外收益，和 `decision-rationale-output.md` 一样：

> ⭐⭐⭐⭐ **写了假设的输出，事后排查不需要重跑**——
> 一眼就能看出差异来自口径，而不是数据或逻辑。

## 7. ⭐⭐⭐⭐⭐ 自检与写法

对技能里每一处"用户可能不提供"的信息：

```
① ⭐⭐⭐⭐⭐ 猜错了，用户能从输出里看出来吗？
   能 → L1（不问不标）
⭐⭐⭐⭐⭐ 不能 → 继续问 ②③
② ⭐⭐⭐⭐⭐ 猜错了会改变结果本身吗？
   会 → L3（必须问，硬上限 1 次）
   不会 → L2（推断并标注在首行）
③ ⭐⭐⭐⭐⭐ 标注写在首行了吗？
```

> ⭐⭐⭐⭐⭐ 三条里第 ① 条的命中率最高：
> ⭐⭐⭐⭐ 多数技能把所有缺失一律按 L1 处理，
> ⭐⭐⭐⭐⭐ 而实际 scan 一遍通常会发现 2–3 项其实是 L3。

一个十秒判断：

> ⭐⭐⭐⭐⭐ **挑一个技能没写、用户也没说的信息，
> 问"如果两个不同的人各猜一个，会得出两份不同的报告吗"。
> 会 → 它是 L3，必须问。**

---

## 一句可贴在墙上

> ⭐⭐⭐ **格式猜错了会被看见，口径猜错了不会。
> 所以判据不是"重不重要"，而是"错了能不能被看出来"。**
