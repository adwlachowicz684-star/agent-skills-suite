## 1. ⭐⭐⭐⭐⭐ 两种省略不是一回事

已有文档大量处理**技能侧的省略**（作者没写 → 模型补）。输入侧有一类完全不同的省略：

```
技能侧省略：作者没写"失败怎么办" → 模型补一个默认动作
⭐⭐⭐⭐⭐ 输入侧省略：用户没说"不要改文件" → 模型补一个默认动作
```

两者都"由模型补"，但补的依据不同，这决定了修法不同：

| | 技能侧省略 | ⭐ 输入侧省略 |
|---|---|---|
| 补的依据 | 技能的完成倾向 | ⭐⭐⭐⭐⭐ 训练分布里的"常规做法" |
| 改谁能修 | 改技能（写默认动作） | ⭐⭐⭐⭐⭐ **改技能也有效**——写明"未言明项"的默认 |
| 失败形态 | 继续跑 | 继续跑，且跑得更像样 |

> ⭐⭐⭐⭐⭐ 关键差别在第一行：**技能侧补的是"怎么完成"，输入侧补的是"要什么"。**
> 后者补错了，输出仍然完整、仍然专业——只是它是另一个任务的答案。

一个典型：

```
用户："帮我看看这个月的留存"
未言明：口径（新增/活跃）· 维度（总体/分渠道）· 是否要归因 · 要不要落文件

⭐⭐⭐⭐⭐ 用户没说的这四项，模型一项都不会问——
       因为每一项它都有一个"看起来很合理"的默认值。
```

## 2. 补的东西来自训练分布，不是这个项目

> ⭐⭐⭐⭐⭐ **"常规做法"存在于模型的先验里，而它指的是互联网上的常规，
> 不是你所在项目的常规——这两者在多数时候不是同一个东西。**

这正是 `skill-quality/references/skill-replaces-not-adds.md` 那条的镜像：

```
技能覆盖范围内   → 行为由技能定义（替换了模型的默认）
⭐⭐⭐⭐⭐ 技能没覆盖的维度 → 行为由模型的先验定义（没有东西替换它）
```

而"用户没说的维度"几乎必然落在技能没覆盖的一档——因为**技能写的是流程，不会穷举意图边界**。

三个具体偏差：

| 未言明项 | 模型的默认 | 你的项目实际 |
|---|---|---|
| 留存口径 | 新增用户留存 | ⭐ 活跃用户留存 |
| "处理"的含义 | 分析并给出结论 | ⭐ 只整理不判断 |
| "看看"的深度 | 全面检查 | ⭐ 只看有没有明显异常 |

> ⭐⭐⭐⭐⭐ 三个默认单独看都合理。而它们合起来产出的是"一份专业的、关于另一个问题的报告"。

## 3. 五类最贵的未言明项

按"错了能不能被看出来"排序（沿用 `inference-vs-asking.md` 的 L1/L2/L3 判据）：

**① 改不改（只读 vs 写入）** —— ⭐⭐⭐⭐⭐ 最贵

```
"帮我看看这个文件" → 隐含"不要改它"
"优化一下这个函数" → 隐含"可以改"
```

> ⭐⭐⭐⭐⭐ **模型默认按"任务需要什么"来定，而不是按"用户是否授权"。**
> 而"看看"和"优化"在它的理解里都需要先读，差别只在最后一步——
> 于是最保守的措辞也拦不住一次写入。

**② 范不范围（单文件 vs 全库）** —— ⭐⭐⭐⭐

```
"这个函数有问题" → 修这一个，还是修所有同类调用点？
```

模型的默认通常是**只改提到的那个**（局部性偏好），而用户想的常常是"举一反三"。
反向也会发生：它顺手改了同文件里的另外两处，因为它判断"这是同一个问题"。

**③ 要不要落盘** —— ⭐⭐⭐⭐

```
"总结一下" → 输出在对话里，还是写成一个文件？
```

两者都是"完成"，而落盘会留下不需要的产物、不落盘会丢掉需要的记录。

**④ 严格到什么程度** —— ⭐⭐⭐

```
"检查一下" → 是合规审计级别，还是扫一眼？
```

> ⭐⭐⭐⭐⭐ 这一项没有正确答案，但有代价：严了慢且啰嗦，松了漏。
> 而它的默认值会随模型版本漂移。

**⑤ 说给谁听** —— ⭐⭐⭐

```
"整理一下" → 给自己看的笔记，还是要发出去的周报？
```

决定了语气、粒度、要不要写依据——而输出长度和措辞的差异会被误读为"技能不稳定"。

## 4. ⭐⭐⭐⭐⭐ 确认会把"没说"变成"说了"

最容易踩的坑：

```
模型：你是想看新增用户留存还是活跃用户留存？
用户：活跃
```

看起来解决了。但：

> ⭐⭐⭐⭐⭐ **这一问一答，把"用户没说"变成了"用户指定了活跃留存"。**
> 而用户真实的想法可能只是"你看着办，差不多就行"。

后果是**输出的责任转移**：此后口径不对不再是模型的判断问题，而是"按你说的做的"——
⭐⭐⭐⭐⭐ 而用户并不知道自己刚刚承担了这个责任，他只是回了一个他觉得最合理的词。

更常见的是批量确认：

```
模型：口径用活跃的？维度按渠道拆？要不要归因？结果写文件吗？
用户：都行
```

> ⭐⭐⭐⭐⭐ **"都行"是用户把判断权交回来了，但模型会把它当成四项都选了默认值。**
> 于是确认做了，责任没转移，而输出里多了四句"按您的要求"。

规则：

```
□ ⭐⭐⭐⭐⭐ 确认只用于：错了会改变结果本身（L3）
□ ⭐⭐⭐⭐⭐ 非 L3 的一律"推断 + 标注"，不要问
□ ⭐⭐⭐⭐⭐ 确认时必须给出推荐项 + 理由，不能是开放式选择
□ ⭐⭐⭐⭐ 得到"都行/你决定"时，回到推断 + 标注，不要当成已确认
```

第三条最关键：**"你想看哪种？"和"默认按活跃口径（因为你上次用的是这个），可以吗？"
是两种不同的确认**——前者转移责任，后者提供推荐。

## 5. 三种处理，按代价排序

**① 推断 + 标注**（默认，覆盖大多数）

> ⭐⭐⭐⭐⭐ 照做，但在输出首行写明取了哪个默认值。
> 与"相对时间解析结果写进首行"完全同构：**它不能防止选错，但把错从不可见变成一眼可见。**

成本约 10–20 token，且它同时解决了"用户不知道自己没说"这件事——
⭐⭐⭐⭐⭐ **用户看到"口径：活跃（默认）"才会意识到自己其实有偏好。**

**② 在技能里声明"未言明项"的默认** —— 项目级才做

```markdown
## 未言明时的默认
- 未指定口径 → 活跃用户（本项目统一口径）
- "看看/检查" → 只读，不修改任何文件
- "整理/总结" → 输出到对话，不落盘
```

> ⭐⭐⭐⭐⭐ 这三条的价值不在"省一次询问"，在**把项目惯例从人的脑子里搬进技能**——
> 而它恰好是模型先验填补的那个位置。

**③ 询问**（仅 L3，且必须带推荐项）

## 6. 自检

```
□ ⭐⭐⭐⭐⭐ 拿一条真实输入，列出它没说的维度——列不满 3 项说明你没在找
□ ⭐⭐⭐⭐⭐ 这些维度的默认值，是"互联网常规"还是"本项目常规"？
□ ⭐⭐⭐⭐⭐ 输出首行能不能看出取了哪些默认值？看不出 → 用户无法纠正
□ ⭐⭐⭐⭐ 有没有把非 L3 的项拿去问了？问了 → 责任被错误转移
□ ⭐⭐⭐⭐ 得到"都行"之后，是回到标注了，还是当成已确认？
□ ⭐⭐⭐⭐ "看看""检查""处理"这类词，技能里有没有写明默认动作？
```

一分钟验证法：

> ⭐⭐⭐⭐⭐ **把一句两分钟前刚说过的真实指令写下来，问自己：
> "我当时心里默认的那些东西，哪一条我说出口了？"**
> 通常一条都没有——而模型面对的正是同样一句话。
