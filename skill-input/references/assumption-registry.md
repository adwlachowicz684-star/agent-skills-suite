## 1. ⭐⭐⭐⭐⭐ 假设 ≠ 依赖

两者都是"没写出来的前提"，但有一个关键差别：

| | 依赖 | ⭐ 假设 |
|---|---|---|
| 缺失时 | ⭐⭐⭐ **会失败**（文件不存在、变量没设） | ⭐⭐⭐⭐⭐ **不失败，只是结果错** |
| 可检测 | ✅（`test -f`、`env`） | ⭐⭐⭐ 通常不可检测 |
| 典型 | `.eslintrc`、`ANTHROPIC_API_KEY` | "表名是单数" |

> ⭐⭐⭐⭐⭐ **差别在第一行的第二列**：
> **依赖缺失会让你停下来，假设不成立会让你继续错下去。**

举例：

```
依赖：需要 .eslintrc        → 没有就报错
⭐ 假设：项目用 ESLint 而非 Biome → 没有 .eslintrc 它就去读 Biome 配置，
                                   ⭐⭐⭐ 然后"成功"地给出基于错误工具的结论
```

## 2. ⭐⭐⭐⭐⭐ 为什么不成立时不报错

> ⭐⭐⭐⭐⭐ **因为技能里的每条指令，都是"在某套假设下正确"的——
> 模型不知道那套假设是什么，⭐⭐⭐⭐ 所以它会自动补一套最可能的。**

机制链条：

```
技能写"读配置文件" 
→ 模型找项目里"看起来像配置文件"的那个
→ ⭐⭐⭐ 找到了（可能不是你指的）
→ 执行成功 → 输出"成功"
```

> ⭐⭐⭐⭐ **每一步都是成功的。只有最后的结果错了，
> 而结果错不属于任何一步的失败判据。**

这就是为什么它比依赖缺失危险：
⭐⭐⭐⭐⭐ **依赖缺失是"响的失败"，假设不成立是"静的成功"。**
（这是"静默失败"这条结论的又一个场景。）

## 3. ⭐⭐⭐⭐ 五类常见假设

| # | 假设类型 | 例子 | ⭐ 不成立时 |
|---|---|---|---|
| 1 | ⭐⭐⭐ **工具/版本** | "用 pnpm"、"Node 18+" | 用了 npm，锁文件格式不对 |
| 2 | ⭐⭐⭐⭐ **数据形状** | "字段名是 snake_case" | 找不到就猜一个映射 |
| 3 | ⭐⭐⭐⭐ **规模** | "数据量在几千行内" | 100 万行 → 全读进上下文 |
| 4 | ⭐⭐⭐⭐⭐ **顺序/时序** | "先跑过 A" | 直接跑 B，读不到产物就自己造 |
| 5 | ⭐⭐⭐ **环境** | "有网络"、"是 Git 仓库" | 静默降级 |

> ⭐⭐⭐⭐⭐ **第 3 类是隐藏最深、代价最高的一类**——
> 因为它在小样本上完全正确，只在规模变大时崩，
> ⭐⭐⭐⭐ 而"规模变大"往往发生在生产环境，不是开发时。

典型症状：

```
"这个技能测试的时候好好的，上线就炸了"
→ ⭐⭐⭐⭐ 十有八九是第 3 类假设（规模）
```

第 4 类就是数据依赖那份的"前置产物"——
⭐⭐⭐ 两份文档的关系是：**前置产物是假设的一种，
只是它恰好可以被检测**（因为你能 `test -f`）。

## 4. ⭐⭐⭐⭐⭐ 写法：假定 + 不成立时

关键不在"列出假定"，在**每条必须配一个"不成立时怎么办"**：

```markdown
## 假定
| 假定 | ⭐ 不成立时 |
|---|---|
| 包管理器为 pnpm | 停止并说明；不得改用 npm |
| 表名/字段为 snake_case | 停止；⭐ 不得猜测映射 |
| 数据量 < 50,000 行 | ⭐ 改用 `scripts/aggregate.py`，不得整表读入 |
| 已有 `analysis.json` | 停止；先运行 `analyze` |
```

> ⭐⭐⭐⭐⭐ **第二列几乎总是"停止"——这是对的。**
> ⭐⭐⭐ 因为**假设不成立意味着模型已经不在作者设计的场景里了，
> 它做的任何"适配"都是猜测。**

对比一下坏写法：

```
❌ "本技能假定项目使用 pnpm。"
   → 没有第二列 → 模型遇到 npm 项目会"贴心地"改用 npm
   → ⭐⭐⭐ 于是它去读 package-lock.json 并按 npm 的语义解释
   → 输出正常，结论错误
```

> ⭐⭐⭐⭐⭐ **只写假定不写后果，比不写更糟**——
> 因为它给了模型一个信号"作者知道这里有前提"，
> 于是它更自信地自行适配。
> ⭐⭐⭐ 这正是禁令要带正面对应物那条原则的又一次应用。

## 5. ⭐⭐⭐⭐ 从哪找自己没意识到的假设

三个方法，按效果排序：

**① ⭐⭐⭐⭐⭐ 看量词和名词**

```
读一遍 SKILL.md，圈出所有：
  "配置文件"（哪个？）· "表"（哪张？）· "先"（在什么之后？）
  "数据"（多大？）· "用户"（哪个角色？）
```

> ⭐⭐⭐⭐ **每一个没有限定词的名词，都是一处未声明的假设。**

**② ⭐⭐⭐⭐ 换一个环境想一遍**

```
这个技能在一个：
  新项目 / 不同技术栈 / 数据量大 100 倍 / 空仓库 的环境里
  会做什么？
```

**③ ⭐⭐⭐ 让不了解背景的 agent 跑，看它问什么**

> ⭐⭐⭐⭐⭐ 这一条已经在 `skill-scoping/references/second-reader-test.md` 里说过了，
> 但这里值得重复：**它同时产出依赖清单和假设清单**，
> ⭐⭐⭐ 一份功夫两份产出，是最划算的检查。

> ⭐⭐⭐ 补充一个特别有效的变体：
> **故意给一个不满足假设的输入**，看它是停下来还是自行适配。
> 如果它适配了 → 那条假设没有"不成立时"的处置 → 补上。

## 6. ⭐⭐⭐ 与默认动作的分工

两份文档都在补"没写出来的东西"，但补的对象不同：

| | 默认动作 | ⭐ 本份（假定） |
|---|---|---|
| 补的是 | ⭐ 行为边界（出错/不确定时怎么办） | ⭐⭐ 世界模型（我以为世界是什么样的） |
| 触发条件 | 执行中遇到阻碍 | ⭐ 一开始就可能不成立 |
| 时机 | 事后 | ⭐⭐⭐ **事前** |

> ⭐⭐⭐⭐ **顺序是：先写假定（前置门禁检查它），再写默认动作（执行中兜底）。**
> 假定不成立应该⭐ **快速失败**；默认动作管的是⭐ **运行时失败**（与前置门禁那条决策规则一致）。

两者合起来覆盖了两类"沉默"：

```
假定缺失   → 静静地按错误的世界模型跑完
默认动作缺 → 跑不动时静静地绕过去
```

> ⭐⭐⭐⭐⭐ **一个是"跑错了但不知道"，一个是"绕路了但不知道"。
> 两套清单都写上，才把这两条沉默路径堵住。**

## 一句可贴在墙上

> ⭐⭐⭐ **依赖缺失会报错，假设不成立不报错——
> 它只是让你在错误的世界里，成功地跑完。**
