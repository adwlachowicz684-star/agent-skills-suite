> 这份管⭐⭐⭐⭐⭐ **歧义成立之后，那条选择规则该怎么写**——

## 1. ⭐⭐⭐⭐⭐ 第四类输入问题：不是缺失，是歧义

已有的分诊处理三类：

```
残缺    少了一样东西        → 推断或问
矛盾    两个需求互斥        → 标注并选一个
超范围  领域都不对          → 直接说不做
```

但还有第四类，它不触发上面任何一种检查：

> ⭐⭐⭐⭐⭐ **什么都不缺，每一个候选都合法，而它们不是同一个东西。**

```
"帮我看看这个月的报表"
→ 目录里有 report_jan.xlsx / report_feb.xlsx / report_final.xlsx
```

三个文件都在、都能打开、都是报表。
⭐⭐⭐⭐ **校验全部通过。而"这个月"指的是哪一个，没有任何一处写着。**

## 2. 五类歧义

| 类型 | 例子 | ⭐ 为什么模型选不对 |
|---|---|---|
| ⭐⭐⭐⭐⭐ 多个文件 | "处理这个文件" | 上下文里通常有 3–20 个"文件" |
| ⭐⭐⭐⭐ 多个时间段 | "看看这个月的" | 数据跨度与"月"的定义都可能不同 |
| ⭐⭐⭐⭐ 多个环境 | "查一下线上数据" | staging / prod / 灰度 都是"线上" |
| ⭐⭐⭐⭐⭐ 多个同名实体 | "给张伟发" | 同名是真同名，不是拼写问题 |
| ⭐⭐⭐ 多种解释 | "最近的几次" | "最近"的基准可以有三四种 |

第四类最硬，因为⭐⭐⭐⭐⭐ **它不是信息不足导致的——再多的上下文也消不掉同名**，
唯一能消掉它的是一条明确的消歧规则（工号 / 部门 / ID）。

## 3. ⭐⭐⭐⭐⭐ 缺规则时按相似度选，而相似度不等于意图

没有规则时，模型不会报错也不会问，它会选一个。选的依据是**相似度**，而相似度有三个系统性的偏差：

| 偏差 | 表现 | ⭐ 为什么和用户想的不同 |
|---|---|---|
| ⭐⭐⭐⭐⭐ 近因 | 选最后被提及的那个 | 用户指的通常是**正在编辑的**或**报错的那个** |
| ⭐⭐⭐⭐ 频次 | 选在训练分布里最常见的那个 | 用户的项目里最常见的可能是另一个 |
| ⭐⭐⭐⭐ 名称匹配 | 选名字最像查询的那个 | `report_final.xlsx` 最像"报表"，但它通常是旧的 |

`report_final.xlsx` 那行尤其典型：

> ⭐⭐⭐⭐⭐ **"final" 在文件名里出现得越多，它越不可能是最新的——
> 而它恰恰是相似度最高的那个。**

第三条也解释了为什么"看起来选得很合理"：

> ⭐⭐⭐⭐ **模型的选法在语义上完全站得住脚。
> 它错的不是推理，是它用的信号（名称、近因）与用户用的信号（我正在做什么）不是同一组。**

## 4. ⭐⭐⭐⭐⭐ 选错不会报错，因为每个候选都合法

把它和另外两类输入失败放在一起看：

| 失败 | 有没有信号 |
|---|---|
| 缺少输入 | ⭐ 有——技能会卡住或填默认值 |
| 输入矛盾 | ⭐ 有——两个需求不可能同时满足 |
| ⭐⭐⭐⭐⭐ 选中了错误的候选 | ⭐⭐⭐⭐⭐ **完全没有** |

> ⭐⭐⭐⭐⭐ **它甚至比"填默认值"更危险：
> 填默认值时输出里有个可疑的空，而这里输出是满的、格式是对的、数字是真的——
> 只是它是另一个文件的数字。**

用户的体验路径也最差：

```
拿到一份完整、专业、格式完美的报告
→ 用了它
→ ⭐⭐⭐⭐⭐ 几天后才发现看的是错的那个对象
→ 而那时已经无法归因到"当初选错了文件"
```

这与"错得自信而正确"是同一族的第五个场景，
但它的可排查性最差——因为**输出里没有任何一处暴露"我选的是 A 不是 B"**。

## 5. 修法：选择规则三要素

一份能消歧的输入声明要写三件事，缺一件就不完整：

```markdown
## 输入：目标文件

1. ⭐ 默认规则：取当前 git 分支上最近一次修改的 .xlsx；
2. ⭐ 不确定时的动作：按默认规则选，并在输出首行回显所选文件；
3. ⭐⭐⭐⭐⭐ 例外：若用户明确点名，以点名为准，不做二次推断。
```

第三条最常被省，也最不能省：

> ⭐⭐⭐⭐⭐ **用户一旦点名，任何"更合理的"推断都是在覆盖一个明确的指令。**
> 而模型的默认动作恰恰是"综合判断"——它没意识到"用户说了"是一票终局的。

**默认规则要写成可执行的排序，不是描述**：

```
❌ "选最合适的那个文件"                          ← 又是一次相似度判断
✅ "① 正在编辑的 → ② 最近修改的 → ③ 名称含月份的"  ← 可复现
```

> ⭐⭐⭐⭐ **判据：两个人照这条规则选，会选出同一个吗？**
> 不会 → 它没消除歧义，只是把歧义写成了规则的样子。

## 6. ⭐⭐⭐⭐⭐ 把选中的对象回显在输出首行

这是整份里性价比最高的一条，成本约 10 个 token：

```
统计对象：report_feb.xlsx（修改于 2026-09-28，分支 main）
统计区间：2026-09-01 ~ 2026-09-30
```

> ⭐⭐⭐⭐⭐ **它不能防止选错，但能把"错"从不可见变成一眼可见。**

机制与"相对时间解析结果写进输出首行"完全相同：

```
对静默失败，⭐⭐⭐⭐⭐ 可见性比正确性更值得优先投入
——正确性要改模型，可见性只要加一行。
```

配套两条：

- ⭐⭐⭐⭐ 回显的是**判定依据**，不只是结果（"最近修改"比只写文件名有用）
- ⭐⭐⭐⭐ 回显要放在**输出首行**，不是末尾——用户读到末尾时已经信任了前面的内容

## 7. 三类必须问

与"推断 vs 询问"的判据一致（错了能不能被看出来），但有三类无论代价都要问：

| 情况 | 为什么必须问 |
|---|---|
| ⭐⭐⭐⭐⭐ 候选不可枚举 | 连"有几个"都不知道，就没有默认规则可用 |
| ⭐⭐⭐⭐⭐ 后果不可逆 | 发错人 / 删错库 / 发错环境——回显救不回来 |
| ⭐⭐⭐⭐ 同名且都活跃 | 相似度相等，默认规则也分不出 |

问法也有讲究：

```
❌ "你要哪个？"              ← 把候选列表的生成成本推给用户
✅ "目录下有 A / B / C（均为 .xlsx），按'最近修改'取 B。
    若你要的是 A 或 C，告诉我；否则我继续。"   ⭐⭐⭐⭐⭐ 给默认 + 给退出
```

> ⭐⭐⭐⭐⭐ **给默认 + 给退出，才是一次有效的确认；
> 只给选项是"把判断成本推给了一个没有信息的人"。**

以及纪律：⭐⭐⭐⭐ **同一任务内同一类歧义最多问一次**
（第二次问暗示用户刚才的回答可能被推翻）。

## 8. 检查清单

- [ ] 技能的"输入"章节写明了**选择规则**，不只是"输入是什么"
- [ ] 默认规则是**可执行的排序**，两个人照做会选出同一个
- [ ] 有"不确定时的动作"（不是留白）
- [ ] ⭐ 有"用户点名时以点名为准"这条例外
- [ ] ⭐⭐⭐⭐⭐ 输出首行回显被选中的对象及其判定依据
- [ ] 候选不可枚举 / 后果不可逆 / 同名且都活跃 —— 这三类写成必问
- [ ] 必问的话术是"给默认 + 给退出"，不是"你要哪个"
- [ ] 同名实体有稳定的消歧键（工号 / ID / 部门），且写进了技能

## 一句话

> ⭐⭐⭐⭐⭐ **输入校验能拦住"缺"和"错"，拦不住"不只一个"。
> 而没有选择规则时，模型会按相似度选一个——
> 相似度最高的是"最像的那个"，不是"用户正在弄的那个"，
> 而这类错误不会留下任何痕迹，直到有人用了那份看起来完全正确的输出。**
