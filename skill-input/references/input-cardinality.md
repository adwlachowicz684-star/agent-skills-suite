## 1. ⭐⭐⭐⭐⭐ 技能的默认基数是 1

正文写"读取文件并提取其中的字段"——这句话里没有基数，于是：

> ⭐⭐⭐⭐⭐ **没有写基数时，默认值是 1。**

而用户的请求常常不是 1：

```
"把这些文件都处理一下"
"检查一下这几个模块"
"把客户列表里的都过一遍"
```

模型读到的不是一个数量，是一个"任务"。于是它开始处理，处理完一个，输出一份完整的产物——⭐⭐⭐⭐⭐ **而"完整"是指这一份产物本身完整，不包含"还有 N−1 个没做"这个信息**。

中文里尤其容易出问题：

> ⭐⭐⭐⭐⭐ **"这个文件"和"这些文件"在模型眼里差别极小**——
> 中文的量词与复数不像英文那样改变词形，于是基数信号很弱，容易被当成修饰语略过。

## 2. 三种基数错误

| 类型 | 表现 | 工作做了多少 |
|---|---|---|
| ⭐⭐⭐ 只处理第一个 | 取了最早提到的那个 | 1/N |
| ⭐⭐⭐⭐ 只处理最后一个 | 取了上下文里最显眼的那个 | 1/N |
| ⭐⭐⭐⭐⭐ 全处理了，只报一个 | 输出呈现一份 | N/N（成果不可见） |

前两种是"少做了"，第三种是⭐⭐⭐⭐⭐ **做全了但成果丢了**——而且它最常被误判为前两种：用户看到输出里只有一个对象，以为只处理了一个，于是**重复要求再做一遍**。

---

## 3. ⭐⭐⭐⭐⭐ 最危险的是"全处理了但只报一个"

```
处理了 12 个模块
输出里呈现 1 个（模板限制 / 长度预算 / "举一个例子说明"）
```

> ⭐⭐⭐⭐⭐ **输出里出现的那一个，用户会当成"全部"。**

而它是"全部"还是"其中一个"，输出里没有任何字段写着。于是两种方向都会出错：

```
方向 A：其实是 1/12，用户以为完成了 → 11 个没做且没人知道
方向 B：其实是 12/12，用户以为只做了 1 个 → 要求重做，且怀疑技能能力
```

> ⭐⭐⭐⭐⭐ **方向 B 尤其冤枉：工作全做了，而它获得的评价是"这技能不好用"。**
> 这类"不好用"的反馈不会被归因到基数，于是技能常被弃用而作者一直不知道原因。

修法只要半句：输出里写"共 12 个，已处理 12 个，以下展示 1 个（其余见产物文件）"。

## 4. ⭐⭐⭐⭐⭐ N 是模型从上下文里数出来的

批量输入时，N 从哪来？通常不是从文件系统或数据库来的，而是：

```
模型数了数上下文里被提到的对象
```

> ⭐⭐⭐⭐⭐ **它数的是"被提及的"，不是"实际存在的"。**

于是三个偏差全部指向"少算"：

| 偏差 | 例子 |
|---|---|
| ⭐⭐⭐⭐ 只数被提到的 | "上面那三个文件"——实际目录里 12 个 |
| ⭐⭐⭐⭐ 数重复项 | 同一对象被提两次，算成两个或算错 |
| ⭐⭐⭐⭐⭐ 由示例决定 | 正文示例里写了 2 个，于是 N 的默认锚点是 2 |

> ⭐⭐⭐⭐ 第三条与"示例的具体值会被当成默认值"是同一机制：
> 示例里的数量也会成为基数锚点，而它从来没被当成一条规则写过。

## 5. 批量下部分成功是必然，不是异常

```
单个成功率 p = 0.95
批量 N = 20 → 全部成功的概率 = 0.36
```

> ⭐⭐⭐⭐⭐ **批量越大，"至少一个失败"越接近必然。**

所以批量场景下 `status` 二值（ok/fail）是有害的：⭐⭐⭐⭐⭐ 它把"20 个里成了 19 个"和"20 个全成"都表示成 ok，把"成了 1 个"表示成 fail——**两个方向都在说谎**。

批量技能的输出必须有三段，而不是一个 status：

```
共 N 个 · 成功 M 个 · 失败 K 个（列出失败项）
```

> ⭐⭐⭐⭐⭐ "列出失败项"不能省——只给计数时，用户知道少了但不知道少了哪几个，
> 于是唯一的补救方式是全部重做。

## 6. 一个失败：整批回滚还是静默跳过

两种策略的默认值与后果：

| 策略 | 默认采用吗 | 后果 |
|---|---|---|
| ⭐ 跳过继续 | ✅ 是（完成倾向） | ⭐⭐⭐⭐⭐ 少了一个，输出照常完整 |
| 整批失败 | ❌ 否 | 可见但浪费已完成的部分 |

> ⭐⭐⭐⭐⭐ 默认是"跳过继续"，因为模型的默认动作是绕开阻碍继续完成。

于是第 5 节的三段输出在这里是**唯一防线**：N 与 M 对不上时，用户至少能发现少了。

判据：

```
可恢复、可单独重做 → 跳过 + 记录 + 报 N/M/K
⭐⭐⭐⭐⭐ 有副作用（已写入/已发送）→ 不得"跳过"，必须停下报告已完成的部分
```

> 第二条与写入型技能的规则一致：**已发生的副作用必须被报告，不因后续失败而被省略。**

## 7. 修法：先枚举、报 N、列失败

**① 先枚举再处理**

```
"用户给的如果是复数，先列出全部对象，再逐个处理"
```

> ⭐⭐⭐⭐⭐ 枚举这一步的价值不在"更完整"，在⭐⭐⭐⭐ **它把 N 变成了一个被写下来的数**——
> 于是后面 M 对不上时是可发现的。

**② 超出阈值时确认一次**

```
N > 20 → "共 32 个，确认全部处理？"
```

⭐⭐⭐⭐ 这是一条 L3（必须问，错了会改变结果本身）——但它受"同一任务内只问一次"约束，不要每个对象问一次。

**③ 输出报 N/M/K 三段，并列失败项**（见第 5 节）

**④ 展示受限时说明**

```
"以下展示前 5 个（共 32 个，完整结果见 artifacts/xxx.json）"
```

> ⭐⭐⭐⭐⭐ 与输出长度预算里的"超出时必须报总数"是同一条：
> ⭐⭐⭐ **"列出前 20 条"不写总数，用户会以为一共就 20 条。**

## 8. 与输出侧分母的分工

`enumeration-and-completeness.md` 讲输出侧：**没有分母就没有完成**——"检查所有文件确保没有遗漏"会停在任意位置。

这份讲的是⭐⭐⭐⭐⭐ **分母从哪来**：

```
输出侧：已处理 M 个 / 应处理 N 个
              ↑
输入侧：⭐⭐⭐⭐⭐ N 必须先被枚举出来，否则 M 再准也没有意义
```

> ⭐⭐⭐⭐⭐ **M 是执行结果，N 是输入侧的声明。**
> 只有 M 没有 N 时，覆盖率永远"接近 100%"——这正是 `partial-aggregation.md` 里那条
> "分母必须由编排层给出"的输入侧版本。

## 9. 自检

**① 给 3 个对象跑一次，数输出里提到了几个。**
提到 1 个 → 基数默认是 1，而它从来没被写成一条规则。

**② 把请求改成"所有这些文件"，看输出里有没有"共 N 个"。**
没有 → ⭐⭐⭐⭐⭐ 基数没有被声明，于是 1/N 与 N/N 在输出里长得一模一样。

**③ 让其中一个对象失败，看输出。**
如果输出仍是 `status: ok` → 第 5 节的三段输出没生效；如果失败项没被列出 → 用户唯一的补救是全部重做。

**④ 检查正文示例里写了几个对象。**
如果示例里是 1 个 → ⭐⭐⭐⭐ 那个"1"正在作为基数锚点被复制，而它不是一条规则。
