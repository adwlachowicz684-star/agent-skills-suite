## 1. ⭐⭐⭐⭐⭐ 三种"看起来通过了"的输入

```
① 错误响应体     HTTP 200，body 是 {"error": "quota exceeded"}
② 空壳数据       JSON 合法，字段齐全，值全是 null / 0 / ""
③ 旧数据         格式对、内容真、时段错
```

三者有一个共同点：

> ⭐⭐⭐⭐⭐ **它们能让技能完整地跑完，且每一步都成功。**

而它们的危险程度不同，排序反直觉：

| | 输出 | 用户会不会发现 |
|---|---|---|
| ① 错误响应体 | 空或极少 | ⭐⭐⭐ 会（"怎么什么都没有"） |
| ② 空壳数据 | 结构完整、值可疑 | ⭐⭐ 不一定 |
| ⭐⭐⭐⭐⭐ ③ 旧数据 | ⭐⭐⭐⭐⭐ 完整、真实、有趋势 | ⭐⭐⭐⭐⭐ **不会** |

> ⭐⭐⭐⭐⭐ 最危险的是唯一"看起来完全正常"的那一类。
> 这也正是 `intermediate-artifacts.md` 里"存在但旧"最难发现的原因——
> 那份讲的是产物，这份讲的是输入，机制相同。

## 2. ⭐⭐⭐⭐⭐ 错误响应体是最典型的一种

```
fetch(url) → 200 OK
body: {"error": {"code": 429, "message": "quota exceeded"}}
```

技能的处理通常是：

```python
data = json.loads(resp.text)     # ✅ 解析成功
validate(data)                   # ✅ 是合法 JSON
items = data.get("items", [])    # ✅ 没有 items 字段 → 默认 []
process(items)                   # ✅ 处理了 0 条，没报错
```

> ⭐⭐⭐⭐⭐ 四步全部成功。
> ⭐⭐⭐⭐⭐ **而"限额超了"这个唯一重要的信息，被 `get("items", [])` 这一步吃掉了。**

可怕的地方在于这个 `get` 的写法完全正确、完全标准、完全推荐——
⭐⭐⭐⭐⭐ **防御性编程在这里制造了静默失败**。

修法不是不用 `get`，是：

```python
if "error" in data:              # ⭐⭐⭐⭐⭐ 先看它是不是一个错误
    raise UpstreamError(data["error"])
if "items" not in data:          # ⭐⭐⭐⭐⭐ 再看关键字段是不是真存在
    raise SchemaError("missing items")
```

> ⭐⭐⭐⭐⭐ 两个 `if` 约 4 行，它们区分了"没有数据"和"取数失败"——
> 而这两者在输出上是同一个样子（0 条）。

呼应 `failure-definition-missing.md` 里那张表：
⭐⭐⭐⭐⭐ "200 但内容为空"在模型的默认判定里属于**成功**——
因为它是"系统没说失败"的那一类。这里给出的是代码侧的对应修法。

## 3. ⭐⭐⭐⭐⭐ 校验只检查容器，不检查内容

常见的输入校验长这样：

```
□ 文件存在吗？      ✅
□ 能解析成 JSON 吗？✅
□ 有必需字段吗？    ✅
```

三关全过。而实际内容可能是：

```json
{"items": [], "total": 0, "generated_at": null}
```

> ⭐⭐⭐⭐⭐ **三关检查的都是"容器"，没有一关看"里面装了什么"。**

这是输入侧版本的"结构化 ≠ 正确"，但后果更远一层：

```
输出侧：schema 合规但值错 → 至少有一个值，可以被核对
⭐⭐⭐⭐⭐ 输入侧：容器合规但内容错 → 后续全部步骤都在处理"0 条"
          → ⭐⭐⭐⭐⭐ 没有值可供核对，整条链路失去被校验的机会
```

所以：

> ⭐⭐⭐⭐⭐ **输入侧的校验失败，会让后面的所有校验失去意义——
> 因为它们在校验一个空集。**

## 4. ⭐⭐⭐⭐⭐ 为什么没人发现：校验通过之后就没有下一步了

```
校验通过 → 处理 → 输出
```

这条链路上没有任何一个环节会**回头看**输入。

```
输出是 0 条 → 没人问"是因为没有，还是因为没取到"
              因为 0 是一个合法结果
```

> ⭐⭐⭐⭐⭐ 这正是 `empty-output-silent-success.md` 讲的那件事，
> 只不过那份发生在输出侧（"好的"），这份发生在输入侧（"0 条"）。
> ⭐⭐⭐⭐⭐ **两者合起来构成完整的一条静默链：
> 输入静默地空了 → 输出静默地成功。**

而排查时人们看的是输出——输出是对的（0 条就是 0 条），
于是排查方向永远是"是不是查询条件写错了"，
⭐⭐⭐⭐⭐ 而查询条件写得完全正确，是数据从来没进来。

## 5. ⭐⭐⭐⭐⭐ 三类检查，只有第三类在查内容

| 类型 | 查什么 | 例子 | 能抓到①吗 | 能抓到②吗 |
|---|---|---|---|---|
| ① 存在性 | 有没有 | `os.path.exists` | ❌ | ❌ |
| ② 结构性 | 格式对不对 | `json.loads` / schema | ❌ | ❌ |
| ⭐⭐⭐⭐⭐ ③ 内容性 | 值像不像真的 | `total > 0`、`generated_at` 非 null | ⭐⭐⭐⭐ 部分 | ⭐⭐⭐⭐⭐ 能 |

> ⭐⭐⭐⭐⭐ 第三类是唯一能抓到问题的，
> ⭐⭐⭐⭐⭐ 而它几乎从不被写——因为它看起来像"业务逻辑"，
> 不像"校验"。

内容性断言的判据不是"值合不合理"（那需要领域知识），是：

> ⭐⭐⭐⭐⭐ **这个值有没有可能是一个默认值。**

```
null / 0 / "" / [] / {} / 1970-01-01 / -1
```

> ⭐⭐⭐⭐⭐ 这七个值同时是"真实结果"和"缺失的默认"，
> ⭐⭐⭐⭐⭐ **所以它们不能作为"通过"的依据，只能作为"需要第二信号"的触发。**

第二信号是廉价的：

```
total == 0 时，检查 generated_at 是否为 null
             → 都不是 → 真的没有（可信）
             → 都是   → 取数失败（不可信）
```

## 6. ⭐⭐⭐⭐⭐ 写法：内容断言

写入技能的一段正文（约 60 token）：

```markdown
## 输入校验

取到数据后，按顺序检查：

1. 响应体是否含 error/error_code 字段 → 有则视为取数失败，≠"0 条"
2. 关键字段是否真的存在（不是 get(..., []) 兜出来的）
3. 关键值是否为默认值集合 {null, 0, "", [], 1970-01-01}
4. ⭐⭐⭐⭐⭐ 3 命中时，用第二个字段交叉确认：
   全为默认 → 报"未获取到"；否则 → 报实际值
5. "未获取到"不得写成 0 / 无 / N/A
```

第 5 条是收口，呼应 `placeholder-in-output.md`：
⭐⭐⭐⭐⭐ "无"和 0 是最危险的占位符，因为它们看起来是答案。

⚠️ 一条边界：内容断言**只能标记可疑，不能直接判定失败**。

```
total == 0 可能真的是 0
```

> ⭐⭐⭐⭐⭐ 所以断言的输出是"可疑 + 需要交叉确认"，
> 不是"报错退出"。⭐⭐⭐⭐ 把可疑当失败会造成误报，
> 而误报的代价是所有人开始绕过这道检查——
> 与 `flaky-gate-discipline.md` 里 flaky 门禁的结局相同。

## 7. ⭐⭐⭐⭐⭐ 自检

| 检查 | 方法 |
|---|---|
| ⭐⭐⭐⭐⭐ 有 error 字段检查吗 | 让上游返回一个错误响应体，看是否报失败 |
| 用了 `get(k, [])` 兜底吗 | grep `get(` / `or []` / `or {}` |
| 有默认值集合检查吗 | grep `null` / `1970` / `total > 0` |
| ⭐⭐⭐⭐⭐ 0 条时会说"未获取"吗 | 造一个空响应，看输出是"0"还是"未获取" |
| 校验失败会中断吗 | 还是只记一行 log 继续跑 |

最便宜也最决定性的一条：

> ⭐⭐⭐⭐⭐ **把上游改成返回一个错误响应体，跑一次。**
> 技能报失败 = 有检查；输出 0 条并"完成" = 没有。
> 这个测试 30 秒，而它测的是输入侧唯一会导致整条链路失去意义的那一类失败。
