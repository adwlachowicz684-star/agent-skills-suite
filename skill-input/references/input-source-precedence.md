## 1. ⭐⭐⭐⭐⭐ 三个来源，没有优先级

技能执行时能拿到同一信息的三个版本：

```
① 用户这次说的话      "用 2025 年的数据"
② 项目里的配置文件    analysis.yaml: year: 2024
③ 上一次运行留下的状态 last_run.json: year: 2025
```

> ⭐⭐⭐⭐⭐ 三个都是"输入"。技能读到了全部三个，
> ⭐⭐⭐⭐⭐ **而没有任何一个地方写着"冲突时听谁的"。**

于是模型自己定了一个。问题不在于它定得对不对，而在于：

> ⭐⭐⭐⭐⭐ **它不会说它定了。** 输出里只有一个 2024 或 2025，
> 没有任何地方能看出"这里曾经有过分歧"。

对比一下三种失败：

| | 用户能不能发现 |
|---|---|
| 输入残缺 | 能（输出少一块） |
| 多个合法候选 | ⭐⭐⭐⭐ 不能（每个候选都合法） |
| ⭐⭐⭐⭐⭐ 来源冲突 | ⭐⭐⭐⭐⭐ **不能，而且用户往往会以为是自己记错了** |

最后一行是最贵的：用户看到输出是 2024，会想"我说了 2025 啊"——
然后怀疑自己。⭐⭐⭐⭐⭐ 而实际上三个来源都在上下文里，只是没人在仲裁。

## 2. ⭐⭐⭐⭐⭐ 默认优先级是"最近的"，而它几乎总是错的

模型的默认不是随机的，是稳定的：**取最近被提及的**。

```
用户第 1 轮说 2025
配置文件里是 2024
用户第 5 轮（在别的上下文里）提了一句"今年的"
→ 取第 5 轮的
```

> ⭐⭐⭐⭐⭐ 近因在别处是一种偏好（首因/近因），
> ⭐⭐⭐⭐⭐ **在这里它是一个 bug 的生成器**——
> 因为它把"用户最新的话"当成了"用户最新的决定"，
> 而多数时候那只是"用户最近提到的一个相关词"。

反直觉的地方在于：**用户这次说的话，权重应该最高，但它排在最容易被挤掉的位置**——

```
用户的话在开头（会话早期）
配置文件在中间（被读取时进入）
状态在最后（刚读进来）
```

> ⭐⭐⭐⭐⭐ 于是"最重要的那个"恰好在近因区的最远端。

## 3. ⭐⭐⭐⭐⭐ 四类冲突与判据

| 冲突 | ⭐ 判据 | 谁赢 |
|---|---|---|
| 本次指令 vs 配置 | ⭐⭐⭐⭐⭐ 显式指令覆盖配置 | 用户 |
| 本次指令 vs 状态 | ⭐⭐⭐⭐⭐ 同上，且状态要被改写 | 用户 |
| 配置 vs 状态 | ⭐⭐⭐⭐ 看哪个更新（用时间戳，不是用读取顺序） | 较新者 |
| 上下文结论 vs 任何来源 | ⭐⭐⭐⭐⭐ **不算来源，不得参与** | —— |

第四行需要解释，见第 5 节。

第三行的括号是关键：⭐⭐⭐⭐⭐ **"用时间戳判断新旧"，不是"用读取顺序"**。
读取顺序取决于代码怎么写的，而它每次都一样——
⭐⭐⭐⭐⭐ 于是"用读取顺序"会让冲突**永远以同一种方式解决**，
看起来像有规则，实际是把一次偶然固化成了规则。

> ⭐⭐⭐⭐⭐ 这也是"配置 vs 状态"必须各自带 `updated_at` 的原因：
> 没有时间戳时，"谁更新"这个判断无法被做出，只能被猜。

## 4. ⭐⭐⭐⭐⭐ 配置文件是最容易被静默越过的一层

三种来源里，配置文件的处境最差：

```
用户的话：⭐⭐⭐⭐⭐ 有"用户说了算"的天然权威
状态：    ⭐⭐⭐⭐ 有 run-id 和时间戳
配置文件：⭐⭐⭐⭐⭐ 什么都没有——它只是一段被读进来的文本
```

> ⭐⭐⭐⭐⭐ 配置文件承载的是"团队的长期决定"，
> ⭐⭐⭐⭐⭐ **而它在上下文里的地位等同于一段背景资料。**

典型事故：

```
团队在 analysis.yaml 里定了"金额一律以分为单位"
某次用户说"按元显示"
技能照做 → 后续所有输出都用元
analysis.yaml 还在，没人动过，也没人再读它
```

> ⭐⭐⭐⭐⭐ 这里真正的问题不是那一次输出——
> 是⭐⭐⭐⭐⭐ **"用户的一句话"永久性地覆盖了一份配置文件，
> 而这个覆盖没有任何记录**。
> 三个月后没人知道"按元显示"来自哪一次对话。

修法不是"禁止覆盖"（那会让技能很难用），而是：

> ⭐⭐⭐⭐⭐ **覆盖配置时必须输出一句"本次覆盖了 <配置项>（默认 <值>）"。**

一句 20 token，它把一次静默的覆盖变成一次可见的覆盖。

## 5. ⭐⭐⭐⭐⭐ 上下文里的"事实"不算来源

`output-becomes-fact.md` 说：输出一进入对话，就获得了和用户输入同等的地位。
这份给出输入侧的处理规则：

> ⭐⭐⭐⭐⭐ **来源清单里只有三种东西：用户本次输入 · 项目文件 · 状态文件。
> 上下文里"看起来是事实"的内容，不算来源。**

理由不是"它可能错"（它可能是对的），而是：

```
用户本次输入：⭐⭐⭐⭐⭐ 用户刚说的，用户会负责
项目文件：    ⭐⭐⭐⭐⭐ 有路径、可打开、可 review
状态文件：    ⭐⭐⭐⭐ 有 run-id、时间戳
上下文结论：  ⭐⭐⭐⭐⭐ 三者皆无——它不指向任何可核对的东西
```

> ⭐⭐⭐⭐⭐ 所以"上下文中已确认 year=2025"这句话，
> ⭐⭐⭐⭐⭐ 在任何一次新的运行里都不构成依据——**除非它能指出是哪一次运行写的**。

这条在实践中会显得很啰嗦（明明刚算过），但它防的是那个特定的病：

```
第一次运行：推断 year=2025（因为"最近"）
第二次运行：把上一次的 2025 当来源 → 于是它从"推断"变成了"事实"
第三次运行：有人问 2025 从哪来 → "之前一直是这么算的"
```

呼应《skill-state》的 `memory-write-discipline.md`：
⭐⭐⭐⭐⭐ 那份说"写不出的来源的结论禁止写入记忆"——
这份是同一个规则在读取侧的形式：**读到的东西说不出来源，就不算来源。**

## 6. ⭐⭐⭐⭐⭐ 优先级链怎么写

一段约 80 token 的正文，覆盖上面全部四类：

```markdown
## 输入来源优先级

同一信息在多个来源冲突时，按以下顺序取值：

1. 用户本次明确指定的值   ← 最高
2. 项目配置文件
3. 上次运行状态

规则：
- 用 1 覆盖 2 时，输出中写明"本次覆盖了 <配置项>（默认 <值>）"
- 2 与 3 冲突时，按各自 updated_at 取较新者；无时间戳时取 2
- 上下文中的既有结论不是来源；无法指出来源的值视为未指定
- ⭐⭐⭐⭐⭐ 三者都无此信息时，按 inference-vs-asking.md 的三级表处理，
  不得从上下文推断
```

最后一条最容易被省，而它是整段的收口：
⭐⭐⭐⭐⭐ 没有它，"优先级链"会被读成"总能找到一个值"，
于是链的终点变成了"用最近的"。

## 7. ⭐⭐⭐⭐⭐ 自检

| 检查 | 方法 |
|---|---|
| 有优先级链吗 | grep "优先级 / 覆盖 / 冲突时" |
| ⭐⭐⭐⭐⭐ 覆盖配置会报吗 | 造一个"用户输入与配置相反"的用例，看输出有没有"覆盖了" |
| 2/3 冲突用时间戳吗 | 把状态改成更旧的，看结果是否回到配置值 |
| ⭐⭐⭐⭐⭐ 上下文结论被当来源了吗 | 清空会话重跑，结果应该不变 |
| 三者都没有时会问吗 | 删掉全部三个来源，看是"未获取"还是"猜了一个" |

最后一条是判定的分水岭：

> ⭐⭐⭐⭐⭐ **三者都没有时输出"未指定"而不是猜一个，
> 才说明这条优先级链是真的；否则它只是一段看起来有规则的正文。**

## 一条边界

⭐⭐⭐ 优先级链只在技能**真的有多个来源**时才需要。
只有一个来源的技能写了它，反而会引入一个不存在的问题——
⭐⭐⭐⭐⭐ 判据：列出你的技能实际会读的每一处输入，少于两处就不写。
