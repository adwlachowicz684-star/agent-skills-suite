## 1. ⭐⭐⭐⭐⭐ 第一条消息就是一个完整任务

用户实际操作是这样的：

```
消息1：「帮我分析一下这个月的销售数据」
消息2：「按区域分组」
消息3：「对了，排除测试数据」
```

而技能在消息 1 到达时就已经触发并开始跑了。

> ⭐⭐⭐⭐⭐ **消息 2 和消息 3 到达时，它们不是"补充"，
> 它们是对一个已经在运行的流程的修改。**

但用户不这么认为。在用户心里这三句话是**一次**输入——
他分三条发只是因为打字习惯。

> ⭐⭐⭐⭐⭐ 这个错位是这一类问题的全部来源：
> **技能把"分批到达"当成了"三次输入"，用户认为那是"一次输入的三行"。**

于是出现那个经典的对话：

```
用户：帮我分析这个月的销售数据
助手：（跑完 40 行输出）
用户：按区域分组          ← 用户以为这是同一句话的继续
助手：（重新跑一遍）
用户：排除测试数据        ← 又一次
助手：（再跑一遍）
```

三次运行、三份输出、⭐⭐⭐⭐⭐ 而用户只想要一份。

## 2. ⭐⭐⭐⭐⭐ 三种"输入还没说完"

### ① 追加式（最常见）

```
「分析销售数据」+「按区域分组」
```

第一条本身是一个**可以独立完成的任务**——这是问题所在。

> ⭐⭐⭐⭐⭐ 如果第一条不能独立完成，模型会问；
> ⭐⭐⭐⭐⭐ **正因为它能独立完成，模型不问，直接做了。**

### ② 修正式

```
「分析销售数据」+「哦不对，是上个月的」
```

与第一类的差别：⭐⭐⭐⭐ **第一条的结果被完全作废**。
而模型常常保留第一份输出的部分内容（因为"看起来还能用"）。

### ③ 前置式（最容易出错）

```
「帮我看下这个文件」+「（粘贴一大段内容）」
```

> ⭐⭐⭐⭐⭐ "这个文件"在消息 2 到达前**没有指代对象**。
> 模型的默认动作不是等，是⭐⭐⭐⭐⭐ **从上下文里找一个最像"这个文件"的东西**。

呼应 `ambiguous-input-selection.md`：那份讲"多个合法候选时选哪个"，
这里更糟——⭐⭐⭐⭐⭐ **候选根本不存在，模型造了一个。**

## 3. ⭐⭐⭐⭐⭐ 为什么它不等：触发发生在语义完整之前

机制上的原因很直接：

```
触发匹配：在每条用户消息到达时进行
完整性判断：⭐⭐⭐⭐⭐ 没有任何环节负责
```

> ⭐⭐⭐⭐⭐ 触发问的是"这条消息像不像这个技能的事"，
> 它从来不问"用户说完没有"。

而"说完没有"这件事**不可判定**——模型无法知道用户后面还有没有话。
所以正确的结论不是"学会判断"，而是：

> ⭐⭐⭐⭐⭐ **既然不可判定，就要在技能里显式声明"什么时候算说完"，
> 而不是让模型去猜。**

顺带解释一个常见困惑：为什么有时它会等、有时不等？

```
用户输入以冒号结尾 / 明显是半句  → 有时会等（这是语言模型的续写倾向，不是判断）
用户输入是一个完整句            → ⭐⭐⭐⭐⭐ 一定不等
```

> ⭐⭐⭐⭐⭐ "有时会等"是运气，不是机制。依赖它的技能会表现得时好时坏。

## 4. ⭐⭐⭐⭐⭐ 与"中途变更"的差别：用户不知道自己在改

`change-questions.md` 的四问假设了一个前提：**用户意识到自己改了主意**。

这份的场景里，前提不成立：

```
用户视角：我在补充我的需求
技能视角：用户在修改一个已完成的任务
```

> ⭐⭐⭐⭐⭐ 后果是：四问里的判据全部失效——
> 因为四问依赖"用户能回答'你是补充还是改主意'"，
> ⭐⭐⭐⭐⭐ 而在这个场景里，用户会说"我在补充"，
> 于是技能按"缩小范围"处理，实际上整份输出都要重做。

最浪费的一种结果：

```
用户补了一个分组维度 → 按"缩小范围"处理 → 保留已算出的总数
                    → ⭐⭐⭐⭐⭐ 而分组之后总数可能要重算（口径变了）
```

> ⭐⭐⭐⭐⭐ "保留已完成部分"在真正的补充场景下是对的，
> 在这个场景下是错的，而⭐⭐⭐⭐ 两者在输入文本上完全无法区分。

区分的唯一信号是**时间**：

```
技能还没开始跑 / 刚跑 → 当成"输入未说完"，合并后重新规划
技能已经跑完并输出    → 当成"中途变更"，走四问
```

> ⭐⭐⭐⭐⭐ 这条不需要模型理解用户意图，只需要看自己在哪一步。
> 这是唯一可靠的判据。

## 5. ⭐⭐⭐⭐⭐ 三种等待策略，以及各自的代价

| 策略 | 做法 | 代价 |
|---|---|---|
| ① 不等（默认） | 立即开始 | ⭐⭐⭐⭐⭐ 三次运行、三份输出 |
| ② 总是等 | 收到后问"还有吗" | ⭐⭐⭐⭐ 每条消息都多一轮，确认疲劳 |
| ⭐⭐⭐⭐⭐ ③ 声明必需槽位 | 缺槽位才问，且一次性问完 | 需要作者列出槽位 |

② 的代价常被低估：⭐⭐⭐⭐⭐ **"还有要补充的吗"问第三次时，
用户会回答"没了"，而这是他第一次真正考虑这个问题**——
于是这个问题不是在收集信息，是在制造信息。

③ 是唯一正确的，而它要求的东西很轻：

```
这个技能的必需槽位：对象 · 时间范围 · 分组维度
```

> ⭐⭐⭐⭐⭐ 三个词。有了它，"消息 1 到达"就从"可以开始"
> 变成了"缺两个槽位，问一次"。

与 `inference-vs-asking.md` 的衔接：
那份给出"该推断还是该问"的三级表，
⭐⭐⭐⭐⭐ 这份补上"**问的时候一次问完**"——
因为这里的场景是"用户正准备一口气说完"，
问一句他就答三句；分三次问，他就觉得这个技能很烦。

## 6. ⭐⭐⭐⭐⭐ 写法：显式声明"输入完整性"

约 80 token 的一段正文：

```markdown
## 输入完整性

本技能需要三个槽位才能开始：对象 · 时间范围 · 分组维度。

- 首条消息到达时先检查槽位，缺则一次性问完（一次对话，不逐条问）
- ⭐⭐⭐⭐⭐ 已开始执行后收到的新消息，按 change-questions.md 的四问处理
- ⭐⭐⭐⭐⭐ 尚未开始执行时收到的新消息，视为同一批输入，合并后重新规划，
  不保留任何中间结论
- 不得依赖"用户应该说完"；句号不表示说完
```

第三行是核心，而且它有个反直觉的推论：

> ⭐⭐⭐⭐⭐ **"尚未开始执行"时的补充，要丢弃已经做的任何推理。**
> 因为那时的推理是基于不完整输入做的，
> ⭐⭐⭐⭐⭐ 保留它 = 把一次猜测带进了正式运行——
> 而它一旦进入上下文，就会获得事实的地位（见 `output-becomes-fact.md`）。

⚠️ 边界：**只有"需要多个槽位"的技能才需要这一节**。
单一槽位的技能（如"把这个文件转成 PDF"）写了它，
会把一次简单操作变成一次对话。

## 7. ⭐⭐⭐⭐⭐ 自检

| 检查 | 方法 |
|---|---|
| 槽位列出来了吗 | 看正文有没有"本技能需要……才能开始" |
| ⭐⭐⭐⭐⭐ 会一次性问完吗 | 造一个三个槽位全缺的输入，看是问一次还是问三次 |
| 补充会合并吗 | 消息1 发一半、消息2 发一半，看是一次运行还是两次 |
| ⭐⭐⭐⭐⭐ 合并时丢弃中间结论了吗 | 消息1 后让它说出推断，消息2 后看那个推断还在不在 |
| 已跑完后的补充走四问吗 | 跑完再补一句，看它有没有问"是补充还是改主意" |

最便宜的一条：

> ⭐⭐⭐⭐⭐ **把需求分两条消息发给技能，数一下它运行了几次。**
> 一次 = 有输入完整性处理；两次及以上 = 没有。
> 这个测试 20 秒，不需要任何工具。

## 一条与既有文档的边界

`repeat-invocation-same-session.md` 讲"同一会话内第二次调用会带上第一次的输出"。
这份看起来像同一件事，但触发方式不同：

| | 那份 | ⭐⭐⭐⭐⭐ 本份 |
|---|---|---|
| 第二次怎么来的 | 用户明确要求"再跑一次" | ⭐⭐⭐⭐⭐ 用户以为自己在说同一句话 |
| 用户知情吗 | 知情 | ⭐⭐⭐⭐⭐ **不知情** |
| 修法 | 声明读哪份输入 | 声明输入完整性 + 槽位 |

> ⭐⭐⭐⭐⭐ 差别在第二行：用户不知情时，
> 他不会去检查"这次是不是带了上一次的东西"——
> 于是那份文档里的自检也做不出来。
