## 1. ⭐⭐⭐⭐⭐ 最贵的属性：出错的地方 ≠ 报错的地方

```
A → B → C 中 B 出错 → ⭐⭐⭐⭐⭐ C 的失败报告里根本不会提到 B
```

> ⭐⭐⭐⭐⭐ **链式结构最贵的属性不是"更容易失败"，是"失败的位置和报错的位置不在同一处"。**

所以链路 ID 不是工程洁癖：⭐⭐⭐⭐⭐ **没有它，定位就退化成"逐级重跑"，而重跑会改变状态——
于是定位动作本身可能就改变了结果。**

---

## 2. ⭐⭐⭐⭐⭐ 链式失败的三种形状

| 类型 | 表现 | ⭐ 关键点 |
|---|---|---|
| ⭐⭐⭐⭐⭐ 中间产物缺失 | 下游拿到空/旧文件 | 用"文件存在"判断"做过"是错的 |
| ⭐⭐⭐⭐⭐ 部分成功被当全成功 | 上游 2/3 成功，下游按全量处理 | `status: partial` 必须传递 |
| ⭐⭐⭐⭐⭐ 错误被逐级改写 | A 返回错误，B 当输入，C 输出"成功" | 每级都要显式检查上游状态 |

> ⭐⭐⭐⭐⭐ **第三种最危险：每一级都在正常完成自己的工作，合起来把一个错误加工成了一份看起来成功的报告。**

与单技能内"错误被改写成功"的区别：那份的改写发生在⭐ **模型这一层**（技能返回错误码，模型写成成功）；
⭐⭐⭐⭐⭐ 这份的改写发生在⭐ **数据这一层**——A 的错误成为 B 的合法输入，C 真的完成了工作。
后者更难发现，因为**没有任何一级在说谎**。

唯一的结构性对策：**每级显式检查上游状态**——不能靠"下游自然会发现问题"，
因为下游拿到的仍然是格式正确的输入。

## 3. ⭐⭐⭐⭐⭐ 定位：从后往前二分

```
① 拿到最终产物，逐级往前问：这一级的输入对吗？
② ⭐⭐⭐⭐⭐ 输入对、输出错 → 错在这一级
③ 输入就错了 → 继续往前
```

二分的价值不是快，是⭐⭐⭐⭐ **它不需要重跑**——用记录好的输入输出快照比对即可。
两个前提：⭐⭐⭐⭐⭐ **每级记录输入摘要与输出摘要**（没记录就只能重跑）；⭐⭐⭐⭐ **每级有稳定 ID 能跨级关联**。

最常见的失效是**只记录了输出**：能看到"每一级产出了什么"，看不到"它拿到的是什么"——
而链式失败的判据恰恰是"输入对不对"。

## 4. ⭐⭐⭐⭐⭐ 扇出扇入：N 个半成品

| | 串行 | ⭐ 并行 |
|---|---|---|
| 失败时状态 | 卡在某步 | ⭐⭐⭐⭐⭐ N 个半成品 |
| 报错 | 一个 | ⭐⭐⭐⭐⭐ 可能 0 个 |

> ⭐⭐⭐⭐⭐ **N 个半成品：每个单独看都是成功的，合起来是错的，没有任何组件会报错。**

三条硬规则：

```
① ⭐⭐⭐⭐⭐ 汇总必须报覆盖率（"3 个来源中 2 个成功，覆盖率 67%"）
② ⭐⭐⭐⭐⭐ 部分成功必须传 partial，下游不得按全量处理
③ ⭐⭐⭐⭐ 顺序敏感性测试：A→B 与 B→A 结果不同 → 禁止并行
```

第③条的价值：**不需要你事先知道依赖在哪**——它把"证明无依赖"变成了两次运行。

---

## 5. ⭐⭐⭐⭐⭐ 覆盖率与 partial 传递

> ⭐⭐⭐⭐⭐ **汇总把"部分成功"加工成了"完整报告"——而这一步没有任何组件报错。**

`partial-aggregation.md` 的核心是分母：⭐⭐⭐⭐⭐ **覆盖率的分母必须由编排层给出**——
若由"成功返回的那几路"自己报，覆盖率永远接近 100%。

> ⭐⭐⭐⭐⭐ 编排器是链条上唯一"知道全局"的组件，所以覆盖率、partial 传递、失败定位只能由它负责——
> 单个技能报的"成功"是⭐ **对自己而言的成功**。

## 6. ⭐⭐⭐⭐⭐ 重试放大

```
每层失败重试 3 次 → 三层链最坏 27 次调用
```

但比成本更危险的是：⭐⭐⭐⭐⭐ **重试成功之后，"失败"这件事在输出里完全消失了。**
> A 第 1 次失败、第 2 次成功 → 交接包 `status: ok` → 下游完全不知道有过失败。

它比"27 次调用"更值钱：前者是成本，后者是正确性。而且它比第 5 节更前置——
⭐⭐⭐⭐⭐ 汇总根本没机会看到 partial，因为重试已经把 partial 变成了 ok。

反向那半同样重要：**`attempts` 恒为 1 不是好消息**，很可能只是没有失败检测。

---

## 7. ⭐⭐⭐⭐⭐ 依赖环路：超时是最没有信息量的失败

环不会报错，唯一症状是"跑很久然后超时"。

> ⭐⭐⭐⭐⭐ **超时只告诉你"超过了某个时间"，不告诉你卡在哪、第几轮。**

更糟的是它不稳定——同一输入可能 2 秒完成也可能超时，于是被归类为"偶发问题"，而偶发问题通常被重试绕过，不被修。

三种环里最危险的是**等待环**（A 等 B 完成、B 等 A 完成）：⭐⭐⭐⭐⭐ 它不在任何依赖声明里，
环只存在于两个技能对"什么时候算完成"的定义的交叉处。

最实用的一条是代次计数：⭐⭐⭐⭐⭐ 没有 generation，无进展检测只能比较输出内容，而输出每次都在变——
**而"输出每次都在变"恰恰是环的特征，不是收敛的证据。**
