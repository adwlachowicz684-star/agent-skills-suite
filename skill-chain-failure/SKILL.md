# 链式失败：串起来之后，坏在哪里、怎么定位

> 前置：《skill-composition》（该不该串、串成什么形状）·《skill-execution》（单个技能怎么跑）·
> 《skill-interfaces》（技能间传什么）

## 1. ⭐⭐⭐⭐⭐ 最贵的属性：出错的地方 ≠ 报错的地方

```
A → B → C 中 B 出错 → ⭐⭐⭐⭐⭐ C 的失败报告里根本不会提到 B
```

> ⭐⭐⭐⭐⭐ **链式结构最贵的属性不是"更容易失败"，是"失败的位置和报错的位置不在同一处"。**

所以链路 ID 不是工程洁癖：⭐⭐⭐⭐⭐ 没有它，定位就退化成"逐级重跑"，**而重跑会改变状态**。

---

## 2. ⭐⭐⭐⭐⭐ 链式失败的三种形状

| 类型 | 表现 | ⭐ 关键点 |
|---|---|---|
| ⭐⭐⭐⭐⭐ 中间产物缺失 | 下游拿到空/旧文件 | 用"文件存在"判断"做过"是错的 |
| ⭐⭐⭐⭐⭐ 部分成功被当全成功 | 上游 2/3 成功，下游按全量处理 | `status: partial` 必须传递 |
| ⭐⭐⭐⭐⭐ 错误被逐级改写 | A 返回错误，B 当输入，C 输出"成功" | 每级都要显式检查上游状态 |

> ⭐⭐⭐⭐⭐ **第三种最危险：每一级都在正常完成自己的工作，合起来把一个错误加工成了一份看起来成功的报告。**
> 与单技能内"错误被改写成功"的区别：那份改写发生在**模型层**，这份发生在⭐ **数据层**——
> 后者更难发现，因为**没有任何一级在说谎**。

详见 `skill-chain-failure/references/chain-failure-shapes.md`。

## 3. ⭐⭐⭐⭐⭐ 定位：从后往前二分

```
① 逐级往前问：这一级的输入对吗？
② ⭐⭐⭐⭐⭐ 输入对、输出错 → 错在这一级
③ 输入就错了 → 继续往前
```

二分的价值不是快，是⭐⭐⭐⭐ **它不需要重跑**——用记录好的输入输出快照比对即可。
两个前提：⭐⭐⭐⭐⭐ **每级记录输入摘要与输出摘要**；⭐⭐⭐⭐ **每级有稳定 ID 能跨级关联**。

最常见的失效是**只记录了输出**：能看到"每一级产出了什么"，看不到"它拿到的是什么"——
而链式失败的判据恰恰是"输入对不对"。

---

## 4. ⭐⭐⭐⭐⭐ 重试放大

```
每层失败重试 3 次 → 三层链最坏 27 次调用
```

但比成本更危险的是：⭐⭐⭐⭐⭐ **重试成功之后，"失败"这件事在输出里完全消失了**
（A 第 1 次失败、第 2 次成功 → `status: ok` → 下游完全不知道有过失败）。

而且它比"覆盖率"更前置——⭐⭐⭐⭐⭐ 汇总根本没机会看到 partial，因为重试已经把 partial 变成了 ok。
反向那半同样重要：**`attempts` 恒为 1 不是好消息**，很可能只是没有失败检测。

---

## 5. ⭐⭐⭐⭐⭐ 依赖环路：超时是最没有信息量的失败

环不会报错，唯一症状是"跑很久然后超时"。

> ⭐⭐⭐⭐⭐ **超时只告诉你"超过了某个时间"，不告诉你卡在哪、第几轮。**

它不稳定——同一输入可能 2 秒完成也可能超时，于是被归类为"偶发问题"，而偶发问题通常被重试绕过，不被修。

三种环里最危险的是**等待环**（A 等 B 完成、B 等 A 完成）：⭐⭐⭐⭐⭐ 它不在任何依赖声明里，
环只存在于两个技能对"什么时候算完成"的定义的交叉处。

最实用的是代次计数：⭐⭐⭐⭐⭐ 没有 generation，无进展检测只能比较输出内容，
而输出每次都在变——**而"输出每次都在变"恰恰是环的特征，不是收敛的证据。**
