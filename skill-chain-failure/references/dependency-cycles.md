## 1. 环是从两次编辑里长出来的

> ⭐⭐⭐⭐⭐ **没有人会一次写出一个环。**

真实过程永远是两次独立的、各自合理的编辑：

```
编辑 1：给 A 加一句"若发现格式问题，调用 lint-fixer"
编辑 2：给 lint-fixer 加一句"修完重新校验，不合格则回到来源技能重来"
```

两次 review 都会通过——因为它们看的是两个不同的文件，
⭐⭐⭐⭐⭐ 而依赖图是这两个文件的**乘积**，不在任何一个文件里。

这和 `positional-references.md` 是同一个病，只是层次不同：
那份是"插入一步导致编号指代失效"，
⭐⭐⭐⭐⭐ 这份是"插入一步导致依赖成环"——**两者都坏在第二次编辑，而不是第一次写作。**

推论很实际：

> ⭐⭐⭐⭐ **环的检测不能在写的时候做（那时还没有环），只能在改的时候做。**
> 所以它是 CI 该干的事，不是 review  checklist 能干的事。

## 2. 三种环

| 类型 | 形态 | 能画出来吗 |
|---|---|---|
| ⭐⭐⭐ 显式环 | A 调 B，B 调 A | ⭐⭐⭐⭐ 能（依赖图里有） |
| ⭐⭐⭐⭐⭐ 状态环 | A 写 state.x，B 监听 x 并触发 A | ⭐⭐ **勉强** |
| ⭐⭐⭐⭐⭐ 等待环 | A 等"B 完成"，B 等"A 完成" | ⭐⭐⭐⭐⭐ 不能（写在各自的完成条件里） |

> ⭐⭐⭐⭐⭐ 第三种最危险，因为它**根本不在依赖声明里**——
> 两个技能的依赖图都是干净的，环只存在于它们对"什么时候算完成"的定义的交叉处。

第二种的表现最具迷惑性：它看起来是"事件驱动"，很现代、很解耦，
⭐⭐⭐⭐⭐ 而解耦恰恰是它成环的原因——**A 和 B 都不认为自己调用了对方**，
它们只是在读写一块共享状态。这与"上下文是所有人都在涂改的黑板"是同一现象，
只是那块黑板换成了 state 文件或消息总线。

## 3. ⭐⭐⭐⭐⭐ 表现：超时，而超时什么都不告诉你

环不会报错。它的唯一 Symptoms 是"跑了很久，然后超时"。

> ⭐⭐⭐⭐⭐ **超时是所有失败里信息量最低的一种**——
> 它只告诉你"超过了某个时间"，不告诉你卡在哪、为什么、第几轮。

更糟的是它不稳定：

```
第 1 次跑：恰好在第 2 轮满足条件 → 2 秒完成 ✅
第 2 次跑：条件始终差一点 → 跑到超时 ❌
```

> ⭐⭐⭐⭐⭐ **于是它会被归类为"偶发问题"，而偶发问题通常会被重试绕过，
> 而不是被修。** 这与 `failure-quadrant-diagnosis.md` 的第 ④ 格（对但不稳）完全同构：
> 它现在能跑通所以没人管，而它不稳定，随时会变成稳定地超时。

识别信号（都不需要额外工具）：

```
① ⭐⭐⭐⭐⭐ 同一个输入，耗时差异超过 10 倍 → 循环次数不同，不是性能问题
② ⭐⭐⭐⭐⭐ 日志里同一批技能反复出现，每次参数略有不同 → 每次都在"改进"，但没有收敛
③ ⭐⭐⭐⭐ 超时前的最后几条动作看起来都很合理 → 这就是"无进展"的形态
```

## 4. 为什么隐式环检测不到

依赖图是能画出来的，但图画不出来的是：

> ⭐⭐⭐⭐⭐ **技能的依赖声明写的是"我要调谁"，而环常常通过"我被谁触发"形成。**

两者不是同一张图：

```
A 声明：调用 B        （出边）
A 未声明：被 C 触发   （入边，通常由路由/事件决定，不在 A 的文件里）
```

⭐⭐⭐⭐⭐ 显式环能检测到，是因为它只用出边；状态环和等待环都要用到入边，
**而入边分散在路由表、事件配置、以及别人的完成条件里——没有任何一处能看到全貌。**

所以能做的只有两条：

```
① ⭐⭐⭐⭐ 把入边也写进声明（"我可能被谁触发"）——把图补全
② ⭐⭐⭐⭐⭐ 运行时兜底：任何编排都必须有迭代上限，不管你相不相信它有环
```

> ⭐⭐⭐⭐⭐ 第 ② 条是必需的，因为它同时兜住了"图没补全"的情况。
> 依赖图永远不可能完整——这正是需要运行时上限的理由，而不是偷懒的借口。

## 5. ⭐⭐⭐⭐⭐ 代次计数：区分"第一次"和"第 N 次"

环里最难的一点不是"停下来"，是：

> ⭐⭐⭐⭐⭐ **停下来之后，你不知道它是第几轮停的，也就不知道它有没有取得进展。**

所以每次进入链路都必须带一个代次：

```yaml
run_id: r-7f3a
generation: 3          # 这是第 3 次进入这条链
entered_via: lint-fixer
```

三条用法：

```
① ⭐⭐⭐⭐⭐ generation > N → 硬停并报告"未收敛"（而不是重试）
② ⭐⭐⭐⭐⭐ 每一轮的交接包都带 generation → 日志里能看出有没有收敛
③ ⭐⭐⭐⭐ 同一 run_id 下重复收到同一 generation 的产物 → 说明有分支在重跑
```

> ⭐⭐⭐⭐⭐ 第 ② 条的价值不在于"能停"，在于⭐⭐⭐⭐ **让"有没有进展"变成可观察的**——
> 这正是无进展检测器需要的输入。没有 generation，无进展检测只能比较输出内容，
> 而输出内容每次都在变（否则就是死循环，反而好发现）。

## 6. 三档处理

| 档 | 做法 | 何时用 |
|---|---|---|
| ⭐⭐⭐ 报错误并停 | 检测到环直接失败 | 显式环，且确认是错误 |
| ⭐⭐⭐⭐ 打破环 | 指定入口技能，禁止回边 | ⭐⭐⭐⭐⭐ 环是"有意的迭代"（如生成→评审→修改） |
| ⭐⭐⭐⭐⭐ 迭代上限 | 不管有没有环，都设 generation 上限 | ⭐⭐⭐⭐⭐ **任何时候都要有** |

> ⭐⭐⭐⭐⭐ 中间那档最重要：**不是所有环都是 bug。** "生成 → 评审 → 修改"就是一个环，
> 它是我们想要的。⭐⭐⭐⭐⭐ 区分有意迭代和意外环的判据不是"有没有环"，
> 是⭐⭐⭐⭐⭐ **"它有没有收敛条件"，以及"收敛条件是否被显式写出来了"。**

一个有意迭代必须同时满足：

```
① ⭐⭐⭐⭐⭐ 有明确的收敛判据（什么情况下不再进入下一轮）
② ⭐⭐⭐⭐⭐ 有上限（即使判据永远不满足）
③ ⭐⭐⭐⭐ 每一轮都记录"这一轮改变了什么" → 没改变就是无进展
```

> ⭐⭐⭐⭐⭐ 只有①没有②，收敛判据不满足时就是无限循环；
> ⭐⭐⭐⭐⭐ 只有②没有①，它会在上限处停下来，而你不知道它是"到了上限"还是"收敛了"——
> 这两者在输出里长得一模一样。
