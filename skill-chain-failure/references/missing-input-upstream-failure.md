## 1. 一个真实的现场

```
A（抓取）→ 超时失败 → 但报告了"完成"
B（分析）→ 读 raw_data → 读不到 → 报告"缺少输入 raw_data"
```

> ⭐⭐⭐⭐⭐ **B 的报错是对的，而它的报错没有任何用。**

用户看到的是「B 说缺 raw_data」，于是去检查 B 的输入声明、B 的参数、B 的前置条件——
⭐⭐⭐⭐⭐ **全都是对的**。真正出错的是 A，而 A 已经成功退出了。

---

## 2. 为什么这是唯一一种"责任分离"的失败

把三类链上失败放在一起看：

| 失败 | 报错的技能 | 出错的技能 | 一致吗 |
|---|---|---|---|
| A 传错字段 | B | A | ⭐⭐⭐ 基本能定位（B 会说"字段不对"） |
| A 传了 partial | B | A | ⭐⭐ 能定位（B 会说"缺一半"） |
| ⭐⭐⭐⭐⭐ **A 没跑却说跑了** | B | A | ❌ **B 报的是"没数据"，没人知道是"没跑"** |

> ⭐⭐⭐⭐⭐ **这是"谁该负责"和"问题在哪"分离的唯一一种失败。**

前两类里，B 至少能说出"上游给我的东西不对"；
第三类里，B 只能说出"我没有拿到东西"——
⭐⭐⭐⭐⭐ **而"没有拿到"同时是三种上游状态的共同表现**：没跑、跑了但没写、写了但路径变了。

## 3. "存在"不等于"成功"

```
A 失败 → 但 raw_data.json 存在（上一次运行留下的）
B 读到 → 数据完整、格式正确、schema 校验通过
输出 → ⭐⭐⭐⭐⭐ 一份基于上周数据的"本周分析"
```

三种"存在但不可用"，全部能通过存在性检查：

| 状态 | 通过 `os.path.exists` | 后果 |
|---|---|---|
| 存在但为空 | ✅ | B 拿到 0 条，输出"无" |
| ⭐⭐⭐⭐⭐ 存在但是旧的 | ✅ | ⭐⭐⭐⭐⭐ **输出完整、数字真实、时段错误** |
| 存在但 partial | ✅ | 覆盖率 <100%，但不报 |

> ⭐⭐⭐⭐⭐ 第二种最贵：**它不产生任何异常信号**，
> 而且它和正确输出的区别只有一点——数据是哪个时段的，而这一点不在输出里。

这与 `skill-execution/references/intermediate-artifacts.md` 那条
「不要用存在判断做过」是同一机制，只是那份讲**同一技能内的重跑**，
这份讲**跨技能的陈旧**——后者连"上一次"这个概念都没有，因为 A 和 B 不共享状态。

## 4. 修法在 A 侧，不在 B 侧

```
❌ 改进 B 的报错措辞        → B 说得更清楚，问题依然存在
❌ 在 B 里加"自动重跑 A"    → ⭐⭐⭐⭐⭐ B 开始承担 A 的职责，顺序耦合（见 merge-signals）
✅ ⭐⭐⭐⭐⭐ A 失败时必须留下空产物并写原因
```

> ⭐⭐⭐⭐⭐ **空产物不是"没写"，是"写了一份写着失败的文件"。**

```json
{
  "run_id": "r-20261001-01",
  "skill": "fetch",
  "status": "failed",
  "reason": "timeout after 30s",
  "produced_at": "2026-10-01T10:04:12Z"
}
```

差别在哪：B 读到文件时，它现在能回答"为什么没数据"。

> ⭐⭐⭐⭐⭐ **没有 reason 字段时，B 只能猜，而它猜的方向是"格式不对"**——
> 于是它会尝试清洗、尝试兼容、尝试跳过，每一步都合理，每一步都离真相更远。

顺带一条：⭐⭐⭐⭐ **A 的成功产物也必须带 run_id 与 produced_at**，
否则"存在但是旧的"这一种依然测不出来。

## 5. 为什么"检查前置产物"本身不够

很多链会在 B 的开头加一句：

```
"开始前确认 raw_data.json 存在，不存在则中止并报告"
```

它拦得住"完全不存在"，拦不住第 3 节那三行。要拦住它们，检查必须升级为三项：

```
① 存在
② ⭐⭐⭐⭐⭐ status == ok（读产物里的状态字段，不是读文件在不在）
③ ⭐⭐⭐⭐ run_id 与本次运行的 run_id 一致
```

> ⭐⭐⭐⭐⭐ 第③条最常被省，而它是唯一能拦住"存在但是旧的"的一条——
> 参见 `skill-chain-failure/references/retry-amplification.md` 里"重试成功会抹掉失败记录"：
> 那份讲记录层，这份讲产物层，两者合起来才闭合。

一条便宜的兜底：**读不到就报"未获取"，不报"无"**——
`skill-output/references/placeholder-in-output.md` 里"无"和 0 是最危险的占位符，
在这里的后果是：用户以为分析过了，其实没跑。

## 6. 自检

| 检查 | 不通过的信号 |
|---|---|
| ⭐⭐⭐⭐⭐ A 失败时会不会留下产物文件？ | 不会（只在成功时写文件） |
| ⭐⭐⭐⭐⭐ 产物里有没有 status / reason 字段？ | 只有数据，没有状态 |
| ⭐⭐⭐⭐⭐ B 能不能回答"为什么缺"？ | 它只能说"没拿到" |
| ⭐⭐⭐⭐ B 的前置检查是存在性还是状态+run_id？ | 只有存在性 |
| ⭐⭐⭐⭐ 把 A 手动改成失败，B 报什么？ | 报"格式错误"（它在猜） |
| ⭐⭐⭐⭐⭐ 删掉 raw_data.json 再跑，B 报什么？ | ⭐⭐⭐ 报"无数据"而不是"上游未产出" |
