## 1. 三种形状

| 类型 | 表现 | ⭐ 关键点 |
|---|---|---|
| ⭐⭐⭐⭐⭐ 中间产物缺失 | 下游拿到空/旧文件 | 用"文件存在"判断"做过"是错的 |
| ⭐⭐⭐⭐⭐ 部分成功被当全成功 | 上游 2/3 成功，下游按全量处理 | `status: partial` 必须传递 |
| ⭐⭐⭐⭐⭐ 错误被逐级改写 | A 返回错误，B 当输入，C 输出"成功" | 每级都要显式检查上游状态 |

三条的共同点：**都不是"某一级报错了"，而是"某一级拿到了不该拿到的东西，然后正常地完成了工作"。**

> ⭐⭐⭐⭐⭐ 所以链级失败的排查单位不是"哪一步错了"，而是 **"哪一步的输入错了"**——
> 而输入错，通常不是因为上一步报错，恰恰是因为上一步**没有报错**。

## 2. 形状一：中间产物缺失

```python
# B 的开头
data = json.load(open("analysis.json"))   # 文件存在 → 成功
```

三种"存在但不是你要的"：

| 情况 | 症状 |
|---|---|
| 空文件（A 写了头就崩了） | 解析出空结构，后续全空 |
| ⭐⭐⭐⭐⭐ 旧文件（固定名，上一次运行留下的） | 数据是旧的，格式完全正确 |
| 别人的文件（同名不同源） | 字段对不上，可能被静默忽略 |

> ⭐⭐⭐⭐⭐ **最贵的是第二种**：文件内容真实、格式正确、来源正确——只是它是上一次的。
> 而"文件存在"这个判据在三种情况下都返回 True。

判据一句话：**"存在"证明的是"有人写过"，不是"这一次写过了"。**

修法两条，缺一不可：

```
① ⭐⭐⭐⭐⭐ 路径带 run-id（换环境也不会撞车）
② ⭐⭐⭐⭐⭐ 读取前校验新鲜度（mtime / 内含 run-id / 内含时间戳）
```

只做①不够：脚本里写"存在就复用"仍会命中缓存。只做②不够：撞名的旧文件会被判为不新鲜，但真实原因不明。

## 3. 形状二：部分成功被当全成功

```
A 处理 3 个来源，2 个成功 1 个超时
→ 交接包 status: ok（它自己确实完成了）
→ B 按 3 个来源的全量做汇总
```

> ⭐⭐⭐⭐⭐ **"成功"是⭐ 对自己而言的成功**——
> A 没有说谎，它确实把自己能做的做完了。

关键区分：

| | 含义 |
|---|---|
| 原子的成功 | 全部完成才算成功 |
| ⭐⭐⭐⭐⭐ 部分的成功 | 完成了一部分，且**没有声明是哪一部分** |

第二种才是链的隐患。它比失败更难处理，**因为失败至少会被传递**（错误协议会让它显式中断），
而 partial 会顺着"成功"这条通道一路流下去。

三条硬规则：

```
① ⭐⭐⭐⭐⭐ partial 必须传递，下游不得按全量处理
② ⭐⭐⭐⭐⭐ 覆盖率的分母必须由编排层给出（否则永远接近 100%）
③ ⭐⭐⭐⭐⭐ 汇总输出里必须出现"X 个中 Y 个成功"这句话本身
```

第③条最常被省，而它最便宜——**没有它，输出是一份完整的报告，而它是 2/3 的报告**。

## 4. 形状三：错误被逐级改写

```
A：{"status": "error", "message": "配额不足"}
B：把上面当输入，提取字段，缺的就按默认填 → 输出一份结构完整的中间结果
C：读 B 的结果，正常完成 → 最终输出"分析完成"
```

> ⭐⭐⭐⭐⭐ 每一级都在正常完成自己的工作，
> 合起来把一个错误加工成了一份看起来成功的报告。

它和单技能内"错误被改写成功"的区别：

| | 改写发生在哪一层 | 谁在改写 |
|---|---|---|
| 单技能内 | ⭐ **模型层**（技能返回错误码，模型写成成功） | 模型 |
| ⭐⭐⭐⭐⭐ 链级 | ⭐ **数据层**（A 的错误成为 B 的合法输入） | 没有任何人 |

> ⭐⭐⭐⭐⭐ 后者更难发现，因为**没有任何一级在说谎**——
> 每一级的输出都是它自己输入的忠实加工结果。

机制上它是"结构化 ≠ 正确"的链级版本：A 的错误对象完全符合 B 期望的 schema，
schema 校验通过，B 没有任何理由怀疑它。

## 5. 为什么第三种最贵

```
形状一：下游拿到空/旧 → 结果通常明显不对 → 会被发现
形状二：结果比预期少 → ⭐⭐⭐⭐ 需要有人知道"应该有多少"才能发现
形状三：结果完整、格式正确、有数字有结论 → ⭐⭐⭐⭐⭐ 没有任何可发现的入口
```

> ⭐⭐⭐⭐⭐ 三种形状按"可发现性"排序，第三种的发现成本是无穷大——
> 因为**它不产生任何异常信号**，只有拿到外部事实去比对才能察觉。

一个具体的放大器：**错误信息本身会被当成数据加工**。

```
A 返回："无法获取 2026-09 的数据"
B 提取"2026-09" → 当作时间标签写入结果
C 输出："2026-09：0 条"
```

> ⭐⭐⭐⭐⭐ 错误文本里的数字、日期、名称，在下游眼里和正常数据没有区别。
> 于是"获取失败"被加工成了"确实为 0"——这正是"无"和 0 最危险的那种形态。

## 6. 唯一的结构性对策

> ⭐⭐⭐⭐⭐ **每级显式检查上游状态**——不能靠"下游自然会发现问题"，
> 因为下游拿到的仍然是格式正确的输入。

具体三条，按成本排序：

```
① ⭐⭐⭐⭐⭐ 读取上游产物时先读 status 字段，非 ok 立即中断并原样上报
② ⭐⭐⭐⭐⭐ 错误对象不得进入正常数据通道（schema 上区分 error 与 result）
③ ⭐⭐⭐⭐ 每级输出里带上"我读的是哪一份产物"（run-id / 路径 / 时间戳）
```

第②条是结构性的：**只要 error 和 result 共用同一个 schema，
"错误被当数据"就不是 bug，而是设计**。

第③条的价值在于定位：⭐⭐⭐⭐ 看到"2026-09：0 条"时，
如果能看到它是从哪一份产物算出来的，二分就只需要一次。

## 7. 自检

| 检查 | 不通过的信号 |
|---|---|
| ⭐⭐⭐⭐⭐ 每一级是否读取并检查了上游 `status`？ | 只有最后一级有输出检查 |
| ⭐⭐⭐⭐⭐ 中间产物路径是否带 run-id？ | 固定文件名 `analysis.json` |
| ⭐⭐⭐⭐⭐ partial 是否有字段、是否被下游读取？ | 只有 `status: ok/error` 两态 |
| ⭐⭐⭐⭐ 错误对象是否与正常结果共用 schema？ | `result` 字段可空 |
| ⭐⭐⭐⭐ 覆盖率分母由谁给出？ | 由各路自己报 |
| ⭐⭐⭐⭐⭐ 把某一级的产物换成 error 对象跑一次，链是中断还是照常出报告？ | ⭐ 照常出报告 = 三种形状全中 |
