## 先写数据契约，别先写代码

> ⭐ **在任何代码之前，为每个数据源写清契约**：

```
□ Schema（列、类型、可空性）
□ 量级预期（每批/每天多少行）
□ ⭐ 新鲜度 SLA（数据可以有多旧？）
□ ⭐ 质量不变量（X 列恒为正，Y 列恒为合法邮箱）
```

> ⭐ **契约就是你的测试套件规格说明。**

**数据工程的心智模式**：

```
□ 把数据当作有自己生命周期、质量与契约的产品
□ ⭐ 永远要问的六个问题：
   1. 真源在哪？数据从哪来？
   2. 上游数据迟到、缺失或畸形时怎么办？
   3. Schema 是什么？将如何演进？
   4. 怎么知道数据是对的？有哪些质量检查？
   5. 延迟要求是什么？批还是流？
   6. 谁消费这份数据？他们的契约是什么？
```

## 七条必须挑战的假设

> ⭐ **这类"假设 → 反驳"清单是数据工程技能最有价值的部分**
> ——呼应 `skill-crafting` 的 `anti-rationalizations.md` 的形态。

| 常见假设 | 反驳 |
|---|---|
| "数据是干净的" | **它不是。验证一切。** |
| "Schema 不会变" | **它会变。为演进而设计。** |
| "我们处理全部数据" | 迟到数据呢？重复呢？乱序呢？ |
| "这只是个简单转换" | **转换会累积。记录血缘。** |
| "数据质量以后再修" | **垃圾进，垃圾出。尽早验证。** |
| "批处理够用了" | 真的吗？实际延迟要求是多少？ |
| "上游很可靠" | ⭐ **每个源迟早会发坏数据。问题只是你抓不抓得住。** |

> ⭐ 最后一条尤其值得单独记——
> 它把"要不要做校验"这个争论变成了**确定会发生 vs 何时发现**。

## 失败模式 → 处理策略

> ⭐ **每种失败都要有显式策略，而不是笼统的"报错重试"**：

| 失败模式 | 处理 |
|---|---|
| 源不可用 | ⭐ 退避重试，连续 N 次失败后告警 |
| 源 Schema 变更 | ⭐ **响亮失败 + 告警，绝不静默丢弃** |
| 质量关卡失败 | ⭐ **响亮失败 + 隔离坏数据 + 告警** |
| 转换错误 | 带上下文记日志 → 死信队列 → 告警 |

**四条工程原则**：

```
□ 在摄入时验证
□ ⭐ 隔离坏数据，绝不让它传播
□ ⭐ 幂等——多次运行产生相同输出
     用确定性逻辑，显式处理重复
     ⭐ 不要假设 exactly-once 投递
□ ⭐ 用 event time，不用 processing time
     显式定义迟到数据的处理（窗口内接受 / 丢弃 / 旁路）
```

**存储层要点**：

```
Delta Lake  ACID（append/overwrite/merge）· 基于谓词的 upsert
            time travel · ⭐ 小文件压缩与 Z-order · vacuum 清理
Iceberg     分区与排序优化 · MERGE INTO upsert
            快照隔离与 time travel · binpack 压缩 · 快照过期
```

**成本优化**（具体数字很有用）：

```
□ 分区：按日期/实体，⭐ 避免过度分区（保持 >1GB）
□ 文件大小：Parquet ⭐ 512MB–1GB
□ 生命周期：热（Standard）→ 温（IA）→ 冷（Glacier）
□ 计算：批用 spot，流用 on-demand，临时用 serverless
□ 查询：分区裁剪 · clustering · 谓词下推
```

**可观测性**（要跟踪的具体指标）：

```
□ 记录数：进 / 出 / 失败
□ 处理延迟 · ⭐ 源新鲜度 · 运行时长
□ ⭐ 任一项超出正常范围即告警
□ 流式额外：消费延迟、schema 漂移、吞吐、死信队列速率
```

## 词汇精确化

> ⭐ **这张表是"形容词 → 可观察谓词"的范本，值得照抄到其他领域**：

| ❌ 别说 | ✅ 要说 |
|---|---|
| "实时" | "流式，延迟 <1s" / "每 5 分钟微批" |
| "数据质量" | "空值率 <1%" / "X 上有唯一约束" / "范围 [0,100]" |
| "schema" | "Avro schema v2" / "向后兼容" |
| "管道" | "批 DAG" / "流式拓扑" / "ELT 作业" |
| "数据源" | "真源" / "派生自 X" / "来自 Y 的 CDC" |
| "延迟" | "event time lag" / "处理延迟" / "watermark" |

> ⭐ 呼应 `skill-authoring` 的 `writing-style.md`：形容词对模型等于没有约束。

## 验证清单与反理性化

**交付前必须全部满足**：

```
□ 所有数据源都定义了契约
□ ⭐ 契约校验在摄入时执行
□ 管道幂等
□ 数据血缘已追踪
□ ⭐ 质量关卡在写入目标之前就已实现
□ 迟到数据策略已定义
□ ⭐ 错误处理路由到死信队列并告警
□ 可观测性指标已跟踪
□ 有针对转换与质量关卡的测试
□ ⭐ Runbook 已写好
  ——值班工程师必须能在没有原作者的情况下排障
```

**测试该覆盖什么**：

```
□ 转换（已知输入 → 已知输出）
□ 边界（null、空、畸形）
□ schema 兼容性
□ 失败与恢复
□ ⭐ 质量关卡本身（它真能抓到坏数据吗？）
□ 负载（能扛 10x 吗？）
□ ⭐ 回填与恢复——在你需要之前就测过
```

**两条值得单独强调的反理性化**：

```
❌ "源很可靠，不需要契约校验"
✅ 每个源迟早会发坏数据。问题只是你抓不抓得住。

❌ "数据血缘是锦上添花"
✅ ⭐ 血缘在你第一次需要回答下面两个问题时就成了刚需：
   "这个 bug 影响了哪些记录？"
   "我们需要删除哪些用户的数据？"
```

> ⭐ **第二条尤其锋利**——
> 血缘看起来是治理开销，实际是**合规刚需**（呼应 `skill-governance` 的 `compliance-audit.md` 的删除权）。

## 自查

```
□ 是否要求"先写契约，再写代码"？
□ 契约是否含新鲜度 SLA 与质量不变量？
□ 是否有"假设 → 反驳"清单（七条）？
□ ⭐ 每种失败模式是否都有显式策略（而非笼统重试）？
□ 是否强调"绝不静默丢弃/传播"？
□ 是否要求幂等（且不假设 exactly-once）？
□ 是否要求用 event time 而非 processing time？
□ 是否有具体数字（分区 >1GB、Parquet 512MB–1GB）？
□ ⭐ 是否有词汇精确化对照表（把形容词换成可测量表述）？
□ 验证清单是否含"质量关卡在写入目标前"？
□ 是否有针对质量关卡本身的测试？
□ ⭐ 是否要求 Runbook（无原作者也能排障）？
□ 是否要求在需要之前就测过恢复流程？
□ 血缘是否被定位为合规刚需而非可选治理？
```
