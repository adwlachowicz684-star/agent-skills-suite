## 1. 一个"不是提示词夹"的技能

> ⭐ **它不是一夹子提示词，而是一条资产工作流：
> agent 决定方案 → 图像生成产出原始视觉 →
> ⭐ 确定性脚本把视觉变成可复用的游戏资产。**

这个定位非常清楚地把两种工作切开了。

---

## 2. 三段式流水线

```
① 计划    agent 用自然语言理解需求，规划资产管线
② 生成    内置图像生成产出原始视觉
③ ⭐ 处理  本地处理器做清理、切分、校验、导出
```

覆盖三类产出：

| 产出 | 内容 |
|---|---|
| **Sprite sheets** | 角色、怪物、道具、攻击、法术、投射物、命中效果、idle/walk、参考引导变体 |
| **分层地图** | 仅地面底图 → 装饰参考 → 道具包 → 透明道具 → y-sort 摆放 → 碰撞 → 区域 → 预览 |
| ⭐ **引擎交接** | Godot 场景、可编辑 TileMap 层、分离的道具、遇敌草地、碰撞体、出口、调试玩家 |

## 3. 产出物

以 Godot 塔防为例，一次跑完产出：

```
scenes/ForestPass.tscn        底图、分离道具、敌人路径、塔位、HUD 节点
六个塔族                       生成塔美术与升级阶段
动画敌人表                     地面单位、飞行单位、Boss
元数据                         波次、难度、塔目录、碰撞、路径、塔位
运行时行为                     建造、升级、出售、投射物、索敌
```

> ⭐ 注意最后一行——**不只是资产，连运行时行为都接好了**。
> 这说明技能编排可以做得很深。

## 4. ⭐ 为什么它值得研究

三条可迁移的经验：

### ① ⭐ 分工切得极干净

```
模型做：理解需求、规划、生成视觉
脚本做：抠像、抽帧、对齐、透明 PNG/GIF 导出、
        道具包切片、QA 元数据
```

> 与 `scripts-as-production.md` 那句
> "脚本产生事实与结构，模型产生语言与选择"完全同构——
> **只是这里的"结构"是像素级数据**。

### ② 中间产物落盘，可断点续跑

三段之间靠**文件**传递，不是靠上下文。
这与 `composition.md` 的"中间产物落文件"一致，
且在多模态场景下更关键——**图片进不了上下文的性价比区间**。

### ③ 引擎交接是显式的一步

> ⭐ **"生成资产"和"能被引擎用"是两件事。**

很多生成类技能死在这里：产出了漂亮图，
但格式、分层、碰撞体、元数据全不对，引擎里用不了。

## 速查

| 阶段 | 谁做 |
|---|---|
| 理解需求、规划 | 模型 |
| 生成视觉 | 图像生成 |
| ⭐ 抠像/抽帧/对齐/切片/校验 | ⭐ 脚本 |
| ⭐ 引擎交接（场景、碰撞、元数据） | ⭐ 显式一步，别漏 |
| 阶段间传递 | ⭐ 落文件，不落上下文 |
