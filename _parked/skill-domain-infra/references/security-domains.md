## 按成熟度分层

从规模分布（见 `domain-taxonomy.md`，**`skill-selection`**）能看出成熟度分层：

```
成熟（30+）：云安全 60 · 威胁狩猎 55 · 威胁情报 50
             Web 应用 42 · 网络 40 · 恶意软件 39
             取证 37 · 安全运营 36 · IAM 35 · SOC 33

中等（12–30）：容器 30 · OT/ICS 28 · API 28 · 漏洞管理 25
              事件响应 25 · 红队 24 · 渗透 23 · 终端 17
              DevSecOps 17 · 钓鱼 16 · 密码学 14 · 零信任 13
              移动 12

长尾（<10）：  勒索软件 7 · 合规 5 · 欺骗技术 2
```

> ⭐ **分层直接决定技能粒度**：
> 成熟域要细分（云安全按 AWS/Azure/GCP 再拆），
> 长尾域该合并（欺骗技术的 2 个不值得独立成域）。

## 各类技能的形态差异

不同安全域的技能**长得完全不一样**——这点常被忽略：

| 类型 | 形态 | 例子 |
|---|---|---|
| **流程型** | 分阶段手册 | 红队：界定范围 → 攻击路径 → 凭证 → 提权 → 横向 → OPSEC → 清理 → 报告 |
| **分析型** | 假设驱动的调查法 | 威胁狩猎：先有假设，再找证据 |
| **工具型** | 工具用法 + 规则写法 | semgrep、nuclei 模板、sqlmap |
| **检测型** | 模式匹配规则 | 变体分析：发现一个漏洞后在全库找同类 |
| **参考型** | ⭐ 长文档 | Android 安全指南 850 行：IPC、WebView、密码学、deeplink、Frida |
| **产出型** | 报告模板 | 标准化漏洞报告 + CVSS + PoC |

> ⭐ **不要用同一套模板套所有域**。
> 呼应 `skill-types.md`（**`skill-authoring`**）：
> **先判断它属于哪一类，再决定结构。**

## 安全类技能的六条红线

**① 授权边界必须显式**

```
□ ⭐ 只针对明确授权范围内的目标
□ ⭐ 破坏性操作（提权、横向移动、数据修改）必须单独确认
□ ⭐ 每个阶段结束要有清理流程（清理日志、后门、植入物）
```

**② 反幻觉验证是硬约束**

```
□ ⭐ 每条发现必须有可复现证据（file:line / 命令 / 请求响应）
□ ⭐ 无法举证的降级为"需人工确认"，不能写成确定结论
□ ⭐ 可利用性验证独立成步——"看起来像漏洞"和"真的能利用"是两件事
```

呼应 `security-pipeline.md`（**`skill-orchestration`**）。

**③ OPSEC 与副作用**

```
□ ⭐ 测试行为本身会留下痕迹，要记录并按需清理
□ ⭐ 不要对生产环境做未授权的探测
□ ⭐ 凭证处理：不写进日志、不写进报告、用完即弃
```

**④ 双重用途的边界**

```
□ ⭐ 技能可以教防御方法，不应帮助对未授权目标实施攻击
□ ⭐ 明确的适用范围声明（授权渗透 / CTF / 自有资产）
```

**⑤ 标准映射不能编造**

```
□ ⭐ ATT&CK / D3FEND / NIST 的编号必须来自真实映射
□ ⭐ 不确定就标"未验证——需人工复核"，绝不补全
```

呼应 `legal-contract-skills.md`（**`skill-domain-biz`**）同一条铁律。

**⑥ 报告要能被第三方复核**

```
□ ⭐ 严重度打分要有依据（CVSS 向量串，不只是一个数字）
□ ⭐ PoC 要可复现（完整步骤，不是"理论上可行"）
□ ⭐ 修复建议要具体（改哪个配置/哪行代码）
```

## 标准映射的价值

frontmatter 里带标准映射字段：

```yaml
atlas_techniques: [AML.T0047]
d3fend_techniques: [D3-MA, D3-PSMD]
nist_ai_rmf: [MEASURE-2.6]
nist_csf: [DE.CM-01, RS.AN-03]
```

**三个作用**：

```
1. ⭐ 让 agent 能跨技能关联（同技术的多个技能互相引用）
2. ⭐ 让报告能对接企业已有的合规框架
3. ⭐ 让检索多一个维度（按攻击技术找技能，而不只是按名字）
```

> ⭐ 呼应 `domain-taxonomy.md` 的 `tags` 价值：
> **一个技能可以有多个归属维度，用户从不同角度都能找到它。**

## 报告规范

`security-findings` 类技能通常独立存在——**报告的产出规范与发现的过程规范分离**。

**必须包含的字段**：

```
□ 标题与类别
□ ⭐ 严重度（CVSS 向量串 + 分值）
□ ⭐ 受影响位置（file:line / 端点 / 配置项）
□ ⭐ 复现步骤（完整可执行）
□ ⭐ 影响分析（能导致什么）
□ ⭐ 修复建议（具体到配置或代码）
□ ⭐ 证据附件（请求响应、截图、日志片段）
□ 参考（CWE / ATT&CK 编号）
```

**排序规则要写清**：

```
❌ "按严重度排序"
✅ "按 (可利用性 × 影响范围) 排序；不可利用的高危排在可验证的中危之后"
```

> 后者避免了"一堆 CVSS 9.8 但都利用不了"的报告淹没真正的问题。
>
> 呼应 `security-testing-skills.md` 的 CVSS/EPSS/KEV 排序思路：
> **EPSS（被实际利用的概率）和 KEV（已知被利用）比 CVSS 分值更能指导优先级**。
