## 1. ⭐ 先有数字，再谈优化

优化前必须确立**可量化的目标线**，否则无法判断"优化好了没有"。

**渲染目标**：

```
主线程 < 8ms
GPU    < 12ms
DrawCall < 2000
Overdraw < 2.5x
```

**内存警戒线**：

```
低端 < 512MB
中端 < 1GB
高端 < 1.5GB
```

> ⭐ **超出极易被系统强杀或闪退**——
> 移动端超出内存限制是**静默崩溃，没有错误日志**。

一个必须先做的判断：

> ⭐ **始终在你要支持的最低规格设备上 profile。**
> 在 iPhone 15 Pro 上 60fps 却在三年前的安卓机上崩溃的游戏
> —— 那不叫已优化，叫未测试。

**区分两类帧率问题**（诊断第一步）：

```
平滑 30fps 但周期性 200ms 尖峰  → ⭐ GC 或昂贵的一次性操作
持续 20fps                      → 整体负载过高
```

> ⭐ 这个区分决定了完全不同的处置方向。

## 2. 四种合批怎么选

| 手段 | 适用 | 注意 |
|---|---|---|
| **静态合批** | 确定不会动、不会隐藏、不会销毁的物体 | ⭐ 见下节 |
| **动态合批** | 同材质、同 Shader、小模型（顶点 <300） | ⭐ 有 CPU 开销，⭐ 要 profile 确认真的有帮助 |
| **GPU Instancing** | 大量重复对象（树、石头、草、子弹） | 1 个批次渲染成百上千 |
| **SRP Batcher** | URP/HDRP | 减少 shader 属性上传的 CPU 成本；⭐ shader 要兼容 |

另加 **Sprite Atlas**（2D）：每张独立精灵贴图都是潜在的 draw call 断点。

## 3. ⭐ 静态合批不是越多越好（真实教训）

> ⭐ 静态合批会创建一张合并后的网格，
> **内存和磁盘上都会多一份数据**；
> 且被合批的物体若美术要改，重新烘焙代价不小。

**建议**：

```
⭐ 只对"确定不会动、不会隐藏、不会销毁"的物体做静态合批
⭐ 合批前用 Profiler 对比内存增量
```

**真实案例**：

```
某项目为压 Draw Call，把整条街所有路灯、长椅全部静态合批
→ 一个场景内存直接多 200MB
→ 触发系统级回收
→ ⭐ 帧率反而更不稳定
```

> ⭐ 这是"优化一项指标导致另一项恶化"的教科书案例。
> 与 `performance-optimization.md` 的"改进 <5% 就回滚"、
> `four-dimension-eval.md` 的多维度思路完全一致。

**对照的正向案例**（塔防游戏）：

```
初始 Draw Call 400+，低端机 CPU 渲染线程耗时 ~14ms，帧率 35–40
合并材质与贴图 + 相同模型开 GPU Instancing
→ Draw Call 降到 ~80
→ CPU 渲染耗时降到 4ms
→ ⭐ 帧率稳定 60
```

## 4. Overdraw 与纹理

**降 Overdraw**：

```
分层渲染：UI / 场景 / 特效 / 角色分 Layer，
          透明层与不透明层严格分离
特效裁剪：粒子、流光、光晕等透明特效 ⭐ 不超过 2 层叠加，
          远距离直接关闭或降分辨率
遮挡剔除：实测可减少 30–50% Draw Call
```

> ⭐ 用 Scene View 的 overdraw 可视化模式定位问题区域——
> **移动端 GPU 填充率有限，Overdraw 是严重的性能消耗**。

**纹理清单**：

```
⭐ ASTC 压缩（iOS 与 Android 都用它，质量/比特优于 ETC2、PVRTC）
   Max Size 按实际需要设（512/1024 常常肉眼无差，省 75% 内存）
   不需要 CPU 访问的纹理 ⭐ 关闭 Read/Write（否则 CPU 与 GPU 各一份，翻倍）
   3D 纹理用 mipmap（内存 +33%，但渲染性能与远处画质显著提升）
   UI 纹理与精灵 ⭐ 关闭 mipmap
   用 2 的幂（NPOT 在许多移动 GPU 上无法压缩）
   ⭐ 用 Memory Profiler 审计，按大小排序质疑最大者
```

## 5. ⭐ GC 尖峰

> ⭐ **GC 尖峰是移动端卡顿最常见的原因。**
> 托管堆满时运行时暂停游戏来清理，
> 移动硬件上这些暂停更长也更明显。

**消除每帧分配**——用 Profiler 的 GC Alloc 列定位。常见来源：

```
字符串拼接
LINQ 查询
⭐ 某些集合类型上的 foreach
值类型装箱
GetComponent() 调用
```

**三条对策**：

```
① ⭐ 缓存组件引用（Awake/Start 取一次，Update 里绝不调用）
② ⭐ 对象池（子弹、粒子、敌人）——同时消除实例化成本与 GC 压力
③ 预分配集合
```

## 6. 画质动态降级

建立**性能—画质自适应机制**，按 CPU/GPU 分数自动调节：

| 档位 | 机型 | 设置 |
|---|---|---|
| 高端 | 骁龙 8 Gen3 / 天玑 9300+ | 60 帧、全特效、软阴影、4X MSAA |
| 中端 | 骁龙 7 Gen2 / 天玑 8200 | 60 帧、中特效、硬阴影、2X MSAA |
| 低端 | 骁龙 695 / 天玑 700 | ⭐ 30 帧、低特效、关闭阴影、关闭抗锯齿 |

**LOD**（3–4 级）：

```
0–50m     高清模型（1000–2000 面）
50–150m   中等模型（300–500 面）
150m+     低模（50–100 面）或 2D 标记
```

**光照与特效**：

```
静态场景（主城、副本）光照烘焙为贴图，禁用实时光照
中低端机关闭软阴影，阴影分辨率降至 512x512
粒子降级：大场景 1000 → 200；复杂粒子替换为简单光效/面片
```

## 速查

| 症状 | 优先查 |
|---|---|
| 周期性尖峰 | ⭐ GC / 一次性昂贵操作 |
| 持续低帧 | 整体负载（DrawCall / Overdraw / GPU） |
| 静默闪退 | ⭐ 内存超限 |
| 合批后更卡 | ⭐ 静态合批的内存增量 |
| 掉帧但 DrawCall 不高 | ⭐ Overdraw |

```
□ 目标线是否先定（主线程 8ms / GPU 12ms / DC 2000 / Overdraw 2.5x）
□ ⭐ 是否在最低规格设备上 profile
□ 静态合批是否核过内存增量
□ 动态合批是否确认真的有帮助
□ GC Alloc 列是否为零（热路径）
□ ⭐ 是否有画质降级档位
```

**核心原则**（一句话）：

> ⭐ **能不渲染就不渲染，能简化就简化。**
