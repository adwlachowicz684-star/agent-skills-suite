## 为什么数据团队尤其需要技能

**没有技能的三个反复出现的问题**：

```
□ 指标口径在不同域之间不一致
□ ⭐ 业务团队不信任——换个问法答案就变
□ 迭代慢——每个修复都是全局的，而不是按域的
```

> ⭐ **"换个问法答案就变"是信任崩塌的根源。**
> 技能让口径显式化，也**让用户在查询时就能指定业务域**，
> 从而**在早期减少歧义**。

## 七步构建法

**1. 从反复出现的失败模式出发**

```
□ 拉出最近 20–50 次失败的分析型 agent 交互
□ 按失败类型分组：
  · 指标定义错
  · ⭐ 表粒度错（grain）
  · 漏了业务规则
  · 输出格式不适合交接给业务方
□ 每个反复出现的模式 → 映射到一个技能目标
```

> 呼应 `skill-authoring` 的 `workflow.md` 的 RED 阶段：**从真实失败出发，而不是从想象出发。**

**2. 一个技能只做一条工作流**

```
❌ "更擅长 SQL"        —— 太泛
✅ 营销效果分析 / 财务 KPI 分析 / 产品漏斗分析 / 销售管道分析
```

> **窄技能更好测，也更容易被信任。**

**3. 编码上下文工程的优先级**

> ⭐ **这步定义了"先信谁"，是随机检索与应用式上下文工程的区别**：

```
1. 指标与语义定义
2. dbt 文档与血缘
3. 数仓元数据
4. ⭐ 宁可先问澄清问题，也不要猜
```

**4. 加严格的 SQL 与分析护栏**

```
□ ⭐ 聚合前先定义粒度（grain）
□ 校验时间窗口与时区假设
□ ⭐ 优先用已文档的 marts，而不是原始层
□ 每个答案都要附上假设与校验
□ 用 dbt 的话，把模型层期望直接写进技能
```

**5. 为业务用户定输出契约**

```
1. 决策摘要
2. SQL 与指标逻辑
3. 校验说明
4. 下一步行动
```

> ⭐ **这个顺序让答案同时可用给技术和非技术受众。**
> 呼应 `skill-crafting` 的 `output-contract.md`。

**6. 按数据域建技能（子代理式模式）**

```
营销分析技能 / 财务分析技能 / 产品分析技能 / 销售分析技能
——每个域技能像一个专注的子代理，有自己的定义、KPI 和规则

在 RULES.md 里声明哪些域技能可用、何时用哪个
→ 相当于轻量编排：agent 路由到正确的域行为，
  而不是套用一套全局指令
```

**7. 每次改动都版本化并测试**

```
□ Git 版本化
□ PR 评审
□ ⭐ 保留 before/after 的基准 diff
□ 每个域技能有明确的 owner
```

## 目录结构参考

```
natural_language_query/
├── SKILL.md              # 元信息 + 执行流程
├── docs/
│   ├── sql-style.md      # SQL 规范
│   ├── finance-metrics.md
│   └── ab-experiment-metrics.md
├── resources/
│   ├── datasets.yaml     # 可用数据集
│   └── metric-map.yaml   # 指标映射
└── scripts/
    ├── hive.py
    ├── doris.py
    └── validate_sql.py
```

**SKILL.md 示例**：

```yaml
---
name: natural_language_query
description: 将用户的自然语言问题转换为 SQL，并基于业务元数据选择 Hive 或 Doris 查询。适用于财务查数、A/B 实验指标查询、订单和用户相关数据查询。
---
```

**执行流程写法**（每步都是可执行的、指向具体文件）：

```
1. 识别用户要查询的业务主题（财务 / A/B 实验 / 订单 / 用户）
2. 读 resources/datasets.yaml，确认可用数据集
3. 读对应领域文档，获取指标口径、字段含义、过滤条件
4. 按 docs/sql-style.md 生成符合规范的 SQL
5. 调用 scripts/validate_sql.py 校验 SQL
```

> ⭐ **"读哪个文件拿什么"写清楚**——这正是 `skill-crafting` 的 `directory-contract.md`
> 讲的"告诉 Claude 里面有什么，它会在合适时自己读"。

## 模型 vs 脚本的分工

> 这张表值得直接抄进任何分析类技能：

| 工作 | 适合 LLM | 适合代码 |
|---|---|---|
| 理解用户意图 | ✅ | ❌ |
| 选择分析路径 | ✅ | 部分适合 |
| 生成 SQL 草稿 | ✅ | 部分适合 |
| **执行 SQL** | ❌ | ✅ |
| **计算同比/环比/贡献度** | ❌ | ✅ |
| 判断异常原因 | ✅ | 需要结合代码结果 |
| 生成自然语言解释 | ✅ | ❌ |

> ⭐ **模型负责"判断做什么"，脚本负责"把明确的事做准"。**
> 这直接呼应 `skill-crafting` 的 `script-engineering.md`：确定性计算绝不交给模型即兴发挥。

## SQL 与输出契约

**常用模式**（放进技能里能显著减少废话与错误）：

```sql
-- 环比（用窗口函数，别在 Python 里算完写死）
SELECT month, revenue,
       LAG(revenue) OVER (ORDER BY month) AS prev_revenue
FROM monthly;
```

**图表选择矩阵**（给 agent 明确的路由规则，而不是让它自由发挥）：

| 数据问题 | 最佳图 | 备选 |
|---|---|---|
| 时间趋势 | 折线 | 面积 |
| 部分与整体 | 环形 | 堆叠柱 |
| 比较 | 柱状 | 条形 |
| 分布 | 直方图 | 箱线图 |
| 相关性 | 散点 | 热力图 |
| 地理 |  choropleth | 气泡地图 |

**设计规则**（这类"硬性审美约束"最值得写进技能）：

```
□ 柱状图 Y 轴从 0 开始
□ 饼图不超过 5 块
□ 仪表盘布局：KPI 卡片 → 趋势 → 拆解 → 对比 → 明细表
```

**统计方法**（放进 `scripts/` 而不是让模型现推）：

```python
# 假设检验：返回 t 值、p 值、Cohen's d 与显著性判定
stat, p = stats.ttest_ind(a, b)
d = (a.mean() - b.mean()) / np.sqrt((a.std()**2 + b.std()**2) / 2)
```

## 三个真实踩坑

**① 索引列上套函数导致全表扫描**

```
症状：有索引的表上查询跑几分钟
原因：WHERE UPPER(name) = ... ——对索引列用了函数
解法：把函数作用在比较值上，或建表达式索引
     ⭐ 并可让 scripts/ 里的检查脚本自动检测这个模式
```

**② 空值率的告警不等于有问题**

```
症状：检查脚本对"业务上本就可选"的字段报 HIGH_NULL_RATE
原因：脚本按统一阈值（如 >50%）标记，不考虑业务意图
解法：⭐ 让阈值可按字段配置，并在技能里写明
     "哪些字段的高空值是预期的"
```

> ⭐ **这条特别值得记住**：
> **通用校验规则遇到业务语义时会产生误报，
> 技能的价值恰恰在于把业务语义补进去。**

**③ 指标口径随问法漂移**

```
症状：同一个问题换个说法，答案不同
原因：口径没有显式化，模型每次重新推断
解法：resources/metric-map.yaml 集中定义，
     技能强制"先查映射表再写 SQL"
```

## 自查

```
□ 是否从 20–50 次真实失败出发（而非凭空设计）？
□ 是否按业务域拆分（而非一个泛泛的"数据分析"技能）？
□ 是否编码了上下文优先级（先信谁）？
□ 是否有 SQL 护栏（粒度 / 时区 / 优先 marts / 附假设）？
□ 是否有输出契约（摘要→SQL→校验→行动）？
□ 是否写了"读哪个文件拿什么"？
□ 确定性计算是否都进了 scripts/？
□ 是否有图表选择矩阵与设计规则？
□ 每个域技能是否有 owner？
□ 改动是否保留 before/after 基准 diff？
□ 通用校验的阈值是否可按业务字段配置（防误报）？
```
