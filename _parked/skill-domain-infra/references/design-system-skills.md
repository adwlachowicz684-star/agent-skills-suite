## 设计系统技能该装什么

> 与其让每个开发者记住间距刻度、变体命名、图标规则，
> **不如让技能在生成或审查代码时直接应用这些标准。**

**五类必装内容**：

```
1. 组件清单
   规范组件 · 可接受的变体 · 已废弃模式 · 推荐组合方式

2. 设计 Token
   颜色 · 间距 · 字体 · 圆角 · 阴影 · 动效 · 断点规则
   ⭐ 包括哪些 token 不该硬编码

3. 代码约定
   文件命名 · prop 命名 · 导入路径 · 目录结构
   · 样式方案 · TypeScript 要求

4. 交互模式
   加载态 · 禁用态 · 校验错误 · 焦点处理
   · 键盘行为 · 响应式布局

5. 内容模式
   标签格式 · 辅助文本 · 空状态文案
   · 错误语言 · 微文案约束
```

**一个实际请求的样子**：

```
输入："创建一个带校验和响应式布局的账单地址表单"

产出：用现有表单组件 · token 化的间距
     · 已批准的错误文案 · 可访问的字段关联
     · ⭐ 框架特定的实现
```

## Token 三层架构

> ⭐ **这是设计系统技能的核心结构，值得直接搬**：

```
Primitive（原子层）  → Semantic（角色层） → Alias（组件层）
     基础值                 UI 概念              组件专属
```

```
Primitive  基础色（hex/rgb）· 间距刻度 · 字号字族
           · 圆角 · z-index · 动效时长/缓动对
           ⭐ 必须平台无关——token 名里不要带 px，单位在适配层解析

Semantic   把原子映射到 UI 概念
           color.background.primary · color.text.heading
           spacing.padding.container · radius.rounded.small
           ⭐ 每个语义 token 必须解析到唯一一条原子路径
           ⭐ 这一层不许出现直接 hex 值

Alias      组件专属，alias 到语义层
           button.background.primary · card.border.radius
           ⭐ 这是唯一允许组件刻意偏离语义默认值的地方
              ——且必须在 token 元数据里写明原因
```

**映射到运行时**：

```
Web        → CSS 自定义属性，注入 :root 与主题选择器
React Native → JS 常量对象
Electron/Tauri → 同 Web（IPC 或内嵌样式表）

⭐ 检查点：token schema 必须可序列化为 JSON
        所有平台都从同一份真源派生
```

> ⭐ 呼应 `skill-crafting` 的 `fact-boundary.md` 与 `skill-distribution` 的 `team-workflow.md`：
> **"单一真源 + 平台适配层"和"技能里不放死数字"是同一个原则。**

## 可检查的验收清单

> ⭐ **这类清单是技能价值最高的部分**——
> 全是可自动检查的谓词，不是形容词。

```
□ 无裸 hex 颜色
□ ⭐ 无超出刻度的自定义间距
□ 无未经批准的按钮变体
□ 无缺失的标签
□ 所有颜色对满足 WCAG 2.2 AA（正文 4.5:1，大文本 3:1）
□ ⭐ 每个组件都含 focus-visible 样式与 skip-nav 模式
□ 支持 prefers-reduced-motion 与 reduced-transparency
□ Token 全部用 TypeScript 接口定型——⭐ 绝不发布未定型的设计值
□ 语义 token 映射到 CSS 自定义属性（支持运行时换主题）
□ 单一 token 源 + 平台专属适配器
□ ⭐ 组件文档含 prop 表、使用指南、显式 do/don't 示例
```

**为什么这类清单有效**：

```
□ 减少一次性 CSS
□ 减少不一致的组件 API
□ ⭐ 减少跨产品表面的"设计漂移"
□ 让初级开发者更快上手，让资深开发者少改风格问题
```

## 重构：技能省时间最多的地方

> ⭐ **重构比新建更能体现技能价值**——
> 因为前端代码库会积累重复标记、不一致样式、过时的组件 API。

**一个重构技能该做的**：

```
入口：一个用自定义 CSS、遗留类名、临时标记的旧组件

□ 把旧模式映射到新模式
□ ⭐ 用 token 替换固定值
□ 把过大的组件拆小
□ ⭐ 在改善一致性的同时保留原有行为
□ 改进 prop 类型
□ 命名对齐设计系统
```

**特别适合这些时机**：

```
□ 设计系统迁移
□ 品牌刷新
□ 从"页面专属样式"转向共享组件
```

**常见组件工作流**（值得各自封装成技能分支）：

```
新组件脚手架   目录 · index · 样式 · 测试 · story · 文档桩
变体扩展       尺寸 / 状态 / 主题 / 布局变体，且不破坏现有 API
表单构建       可访问字段 · 校验态 · 辅助文本 · 错误文案 · 提交行为
状态处理       加载 / 空 / 错误 / 禁用 / 乐观更新
设计交接转换   把设计稿翻译成引用 token 与可复用原语的实现任务
```

## 技能的层次顺序

> ⭐ **一个很实用的经验：安装顺序有意义，后面的建立在前面的之上。**

```
1. 设计资料库（风格 / 配色 / 字体搭配 / UX 规则 / 可视化类型）
   ——先让 agent "有设计感"
2. 官方前端设计模式（布局 / 组件结构 / 响应式）
   ——让它用规范方式落地
3. 现代组件库（如 shadcn/ui）
   ——给它一套可直接用的组件
4. 无障碍检查（WCAG）
   ——上线前自检
5. ⭐ 设计规范检查（"设计版 Linter"）
   ——输出标到 file:line，跟代码 Linter 一样
6. Figma → 代码
```

> ⭐ **第 5 项"设计版 Linter"值得特别注意**：
> 它把设计审查变成了**可自动执行的检查**，输出格式与代码 linter 一致。
> 这正是 `skill-evaluating` 的 `test-pyramid.md` 第 1 层（结构 lint）在设计领域的对应物。

**一个进阶技巧**（多页面项目）：

```
□ 不要每一页都重新生成设计系统
□ ⭐ 持久化成：design-system/MASTER.md（全局规则）
              design-system/pages/checkout.md（页面级覆盖）
□ 之后只说"用 checkout.md 做页面，没写到的按 MASTER.md"
```

> ⭐ 呼应 `skill-crafting` 的 `instruction-layering.md`：
> **全局规则 + 局部覆盖的两层结构**，在这里是具体实例。

**技能是活的**：

```
□ token 变了要更新
□ 组件废弃了要更新
□ 无障碍指南演进要更新
□ ⭐ 引入新框架封装要更新
□ ⭐ 配上代码库里的真实例子——包括"推荐实现"与"要避免的模式"
   ——素材越具体，技能引导越可靠
```

## 自查

```
□ 是否装了五类内容（组件清单 / token / 代码约定 / 交互模式 / 内容模式）？
□ ⭐ Token 是否分了 Primitive / Semantic / Alias 三层？
□ 语义层是否禁止直接 hex 值？
□ 是否平台无关（token 名里不带 px）？
□ 是否有可自动检查的验收清单（无裸 hex、无越界间距等）？
□ 是否含 WCAG 2.2 AA 对比度与 focus-visible 要求？
□ Token 是否用 TypeScript 接口定型？
□ 是否支持运行时换主题（CSS 自定义属性）？
□ ⭐ 重构部分是否要求"保留原有行为"？
□ 是否区分了新建 / 变体扩展 / 表单 / 状态处理等工作流？
□ 是否考虑到技能的安装层次顺序？
□ 多页面项目是否用了 MASTER + 页面级覆盖两层？
□ ⭐ 是否配了代码库真实例子（含"要避免的模式"）？
□ 是否声明了"token 变了就要更新技能"？
```
