## 五支柱

一份成熟的数据管道技能通常覆盖这五个决策域：

```
1. 摄入模式   ETL vs ELT
2. 编排       Airflow / Dagster / Prefect
3. 转换       dbt
4. 大规模处理  Spark
5. 架构选择   流 vs 批
```

**关键定位**：技能是**资深数据工程师的决策框架**，
不是 API 文档。重点在**每个模式的取舍**，不在用法。

> 呼应 `skill-anatomy.md`（**`skill-authoring`**）的"程序优于声明"：
> **教怎么选，不教怎么写。**

## 四条铁律

**① 从第一天就设计成可安全重跑**

```
□ ⭐ 用日期分区、merge key 或 upsert 逻辑
□ ⭐ 让重试永远不会污染数据
□ 这是数据管道技能里最重要的一条
```

**② 现代栈优先 ELT 而非 ETL**

```
ELT：先加载原始数据，在数仓里转换
  □ 保留原始真相
  □ 支持 schema-on-read
  □ ⭐ 让分析师能迭代转换逻辑而无需重新摄入

ETL 仍然胜出的场景：
  ⭐ 需要在数据落库前过滤敏感数据（PII）
```

**③ 分区与增量，永不全量重载**

```
□ ⭐ 每次全表扫描不可扩展
□ 用增量模型（dbt）、按日期分区加载、水印
□ ⭐ 只有小参照表或灾难恢复才回退到全量
```

**④ 编排，不要脚本化**

```
□ ⭐ "cron 调一个 Python 脚本"不是管道
□ 用正式编排器拿重试、依赖管理、回填、可观测性
□ ⭐ 编排器拥有调度和状态，不是你的应用代码
```

外加一条常被漏的：

**⑤ 像测代码一样测数据**

```
□ ⭐ schema 测试、行数检查、唯一性约束、新鲜度 SLA
   不是可选项
□ dbt tests / Great Expectations / 自定义断言
   应该 gate 住每个管道阶段
□ ⭐ 坏数据流入下游，比管道失败更贵
```

## ETL vs ELT 的判定

这是这类技能最核心的决策表：

```
需要在落库前过滤 PII？          → ETL（先转换后加载）
想让分析师自己迭代转换逻辑？      → ELT（先加载后转换）
单次加载量 > 1TB？              → 需要分区与增量策略
源系统 schema 经常变？           → ELT（schema-on-read 更抗变）
有合规要求"敏感字段不得入湖"？    → ⭐ ETL（硬约束，不是偏好）
```

> ⭐ 注意最后一条的分量不同：
> 前四条是**权衡**，第五条是**合规硬约束**。
> 技能里要把这两类分开写——混在一起会让 agent 在合规问题上做权衡。

呼应 `guidance-forms.md`（**`skill-crafting`**）：
**硬约束写禁令（带理由），偏好写配方**。

## 流 vs 批

> ⭐ **这是架构决策，不是工具选择。**

```
批：按时间窗口处理（每小时、每天）
流：事件到达即处理

多数组织两者都要：
  批 → 历史聚合
  流 → 实时看板与告警

Lambda：两套并行
Kappa：  单一流层处理一切
```

## 什么样的技能算合格

对照这份实例，一个数据管道技能应该：

**有**：

```
□ ⭐ 决策表（什么时候用哪个模式），不是教程
□ ⭐ 不可协商的硬规则（可重跑、增量、数据测试）
□ ⭐ 明确的反模式（cron + 脚本、"全量重载就行"）
□ 各阶段的工具对应（Fivetran/Airbyte 摄入，
   Airflow/Dagster 编排，dbt 转换，数仓服务）
□ ⭐ CDC（变更数据捕获）与 schema 演进这类进阶主题
```

**不应该有**：

```
□ Airflow 的完整 API 文档（→ 交给 --help 或文档检索）
□ 大段示例代码（→ scripts/ 或 references/）
□ "选择合适的编排工具"这类无判据的建议
```
