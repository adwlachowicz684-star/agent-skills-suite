# 可观测/运维类技能（云厂商实践）

> ⭐ **这类技能的价值**：
> 把原本需要**多人协作、跨平台操作**的链路
> ——告警 → 定位 → 修复 → 发布——
> 在同一个 agent 对话界面里端到端完成。

## 被封装成技能的运维动作

```
云监控 Skills
□ ⭐ 把告警配置、数据接入等高频运维动作
   封装为 agent 可直接调用的标准指令

STAROps Skills
□ 查询各类观测数据（日志、指标、链路、事件）
□ ⭐ 异常发现、根因定位
```

**平滑过渡的路径**（这点很重要）：

```
□ ⭐ 既支持在现有工作流中嵌入 AI 提效
□ ⭐ 也支持为关键业务构建 agent 原生的诊断模式
□ 不必推翻存量监控体系
```

**全栈数据覆盖**：

```
云产品 · 移动端 · 小程序 · 多语言应用 · 大模型 · agent
——指标、链路、日志、事件数据
```

## 全链路闭环

```
① 编码     开发者在 agent 客户端写代码
② 发布     通过 MCP 触发代码提交、流水线构建、镜像产出
           镜像推送至镜像服务，由容器服务拉起应用
③ ⭐ 告警    监控技能为应用/容器/镜像配置数据接入与告警规则
④ ⭐ 诊断    告警触发后调用诊断技能，
            ⭐ 从指标异动 → Deployment 变更 → 具体代码发布与提交人
            ⭐ 给出"可追溯到代码变更"的结构化根因
⑤ ⭐ 修复    直接生成修复代码，通过 MCP 发起 Pull Request
            ⭐ 自动附带问题背景与根因分析，进入 Review
```

> ⭐ **"可追溯到代码变更的根因"是这里的关键能力**——
> 呼应 `skill-crafting` 的 `grounding-verification.md`：**落地 = 锚定到现实**。
> 运维诊断如果只说"CPU 高了"，就不是根因。

**运维数字孪生**（UModel）：

```
□ 对采集到的数据做语义化建模
□ ⭐ 对各类 IT 资源、业务资源进行本体化建模
□ ⭐ 打通跨域对象
```

> ⭐ 这解决了运维的老问题：
> **研发域与运维域的数据本来是割裂的**，
> 指标异动关联不到代码发布。

## 一个完整实战

**告警配置**（一条自然语言指令）：

```
"为这个集群配置 CPU 告警"

→ agent 基于技能自动拆解为：
  告警规则配置 · Webhook 通知设置
→ ⭐ 由技能内置的 Schema 与校验逻辑保障字段配置合法性
```

**告警诊断**（可追问）：

```
开发者把告警信息输入 agent，结合诊断技能完成根因诊断

⭐ 可继续追问："这次问题由哪次发布引起"
   ⭐ 因为接入了 DevOps 数据，agent 能诊断出：
     具体哪次发布引入了问题
     关联的流水线执行情况
     ⭐ 发布时间与监控指标变化的关联性
   → 给出综合性根因结论
```

**代码修复**：

```
现象与根因明确后，直接修复代码
通过 MCP 发起 Pull Request
⭐ 自动附带问题背景、根因分析与修复说明
```

> ⭐ **PR 里自动附带根因分析**是个很好的实践——
> 呼应 `git-pr-workflow.md` 的 PR 正文格式固定，
> 也呼应 `skill-crafting` 的 `grounding-verification.md` 的证据文化。

## Agent 友好意味着什么

> ⭐ **这是把云能力封装成技能时的四条设计约束**：

```
1. ⭐ 提供适合大模型调用的 API 与 CLI

2. ⭐ Skills 内置参数 Schema 与多重校验逻辑
   ——确保 agent 生成的配置项字段合理，⭐ 避免误配

3. ⭐ 支持自然语言拆解成子任务
   （"配 CPU 告警" → 规则配置 + Webhook 通知）

4. ⭐ 结果可追溯、可追问
   （"哪次发布引起的"能回答，而不是只给一个数值）
```

> ⭐ 第 2 条呼应 `skill-crafting` 的 `output-contract.md` 的 Schema-First 与
> `api-design-skills.md` 的契约优先：
> **agent 生成的配置必须有 schema 校验**，不能靠模型自觉。

## 自查

```
□ 高频运维动作是否被封装成标准指令？
□ ⭐ 是否支持"在现有工作流嵌入"与"agent 原生"两条路径？
□ 是否覆盖了全栈数据（含大模型与 agent 自身）？
□ ⭐ 根因是否可追溯到代码变更与提交人？
□ 是否打通了研发域与运维域的数据？
□ ⭐ 是否形成"告警→定位→修复→发布"闭环？
□ ⭐ 是否内置参数 Schema 与多重校验（防误配）？
□ 是否支持自然语言拆解为子任务？
□ ⭐ 结果是否可追问（而非只给一个数值）？
□ PR 是否自动附带问题背景与根因分析？
□ 是否提供了适合大模型调用的 API 与 CLI？
□ ⭐ 是否避免了"推翻存量监控体系"的迁移成本？
□ 告警配置是否有 webhook/通知的完整子任务？
□ 是否给出了恢复建议（不只给诊断）？
```
