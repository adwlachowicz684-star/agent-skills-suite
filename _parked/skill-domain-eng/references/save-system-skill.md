## 1. ⭐ 头号反模式

> ⭐ **新手最常见的存档设计反模式是：把游戏逻辑直接写进存档对象。**

后果三条：

```
① ⭐ 存档与游戏逻辑紧耦合——任何逻辑修改都影响存档兼容性
② 存档数据格式混乱，可读性差
③ ⭐ 难以实现"多存档槽位"或"云存档"
```

---

## 2. ⭐ 双层架构

```
SaveData   纯数据层，⭐ 只含可序列化的字段
GameState  运行时状态，含方法、引用、状态机

存档时：从 GameState 提取数据 → SaveData
读档时：从 SaveData  恢复数据 → GameState
```

> ⭐ **这种分离让存档与逻辑互不污染。**

Godot 4 推荐用 `Resource` 子类封装 `SaveData`：

```
① 编辑器内可创建 SaveData 模板，可视化配置
② ⭐ ResourceSaver 自动处理序列化，无需手写 JSON 转换
③ ⭐ 类型安全，编译期即可发现字段拼写错误
```

> 第 ③ 条很关键——手写 JSON 的字段拼写错误
> **要到运行时才炸**，而 Resource 在编译期就抓到。

## 3. 迁移三规则

```
① ⭐ 永远不修改旧版本的迁移逻辑
   —— v1_to_v2 的代码永久保留，即使 v1 玩家已不存在
② ⭐ 每个迁移函数只做一件事
   —— v1_to_v2 加字段、v2_to_v3 删字段，避免大爆炸式重构
③ ⭐ 迁移前后写入日志
   —— 便于排查玩家"存档异常"问题
```

> ⭐ 第 ① 条最反直觉也最重要：
> 删掉"已经没人用"的旧迁移代码，
> 会让某个老存档**从可用变成损坏**。

这与 `versioning-compat.md` 的语义版本规则同构——
**兼容性代码不是死代码，不能按死代码处理**。

## 4. 状态机数据与全局状态整合

> ⭐ **状态机的数据绝不是孤立的**——
> 它必须与全局游戏状态一同序列化和反序列化，并确保一致性。

**统一存档管理器**模式：

```
SaveGameManager（中央协调）
  ① 注册可存档系统
     每个子系统（PlayerManager / InventorySystem /
     WorldStateManager / CharacterFSM）注册一个 Serialize()
     或实现 ISerializable
  ② 组织存档结构
     定义最终文件整体结构，各子系统数据分区
  ③ ⭐ 按正确顺序填充
     例：世界状态先于实体状态
```

> ⭐ 第 ③ 条是实操中最容易漏的——
> **加载顺序错了，状态机恢复出来的行为会和保存前不一致**。

**恢复的验收标准**（两条都很具体）：

```
① 一致性：生命值加载为 50 → UI 血条和内部属性都必须反映这个值
② ⭐ 行为正确性：加载后状态机的行为应与保存前完全一致
   —— AI 应继续之前的决策流程，玩家输入应得到预期响应
```

> 这两条可以直接作为 eval 的断言——
> **具体、可观察**，符合 `eval-loop-official.md` 的要求。

## 5. 云存档与冲突策略

```
Steam    GodotSteam 插件的 ISteamRemoteStorage 接口
iOS      iCloud（需原生插件）
Android  Google Play
```

**必须设置冲突解决策略**：

```
本地优先 / 云端优先 / 时间戳优先
```

> ⭐ 不设策略 = 最后一次写入随机获胜，
> 玩家会丢失进度且无从排查。

## 6. 时机与加载顺序

**存档时机**（不是每帧）：

```
关卡完成 · 离开关卡 · 玩家退出
```

> 一个 Unity 场景的坑：
> `Time.timeScale = 0` 暂停后，移动和动画停了，
> **但动画回调、协程、UI 动画可能还在跑**
> （部分 Tween 插件用 `unscaledDeltaTime`，不会自动暂停）。
>
> ⭐ **暂停不能只靠 timeScale**，还要在 UIManager 统一处理；
> 且暂停时调用 Rigidbody 操作可能导致物理穿透。

**资源管理**：

```
小项目：Resources.Load 够用
关卡多/模型精度高 → ⭐ Addressable Asset System
   —— 资源分组、远程更新、按需加载、降低启动内存
```

## 速查

```
□ 数据/逻辑是否分离（SaveData vs GameState）
□ ⭐ 旧迁移代码是否保留
□ 每个迁移函数是否只做一件事
□ 迁移是否有日志
□ ⭐ 加载顺序是否正确（世界先于实体）
□ 状态机数据是否纳入统一存档
□ ⭐ 云存档冲突策略是否设定
□ 存档时机是否在关键节点而非每帧
□ 暂停是否只靠 timeScale（这是个坑）
```

**一个反例值得记**：简易 RPG 用 JSON/ini "杀鸡用牛刀"——
自定义结构体按固定顺序读写，**任何一步失败就判定存档损坏**。
**简单场景下，可调试的二进制结构反而更合适。**
