# UX 文案与微文案

> 界面上的字是产品的一部分。
> 这类技能的价值：**把"说人话"变成可检查的规则**。

## 四条基本规则

```
1. ⭐ 说用户能懂的话，不说系统内部的话
2. ⭐ 说结果，不说过程
3. ⭐ 具体，给下一步
4. 简短，但不牺牲清晰
```

## 错误信息三段式

> ⭐ **发生了什么 → 为什么 → 现在该做什么**

```
❌ "错误 500"
❌ "操作失败，请重试"

✅ "无法保存这份报告
    服务器暂时没有响应。
    已自动重试 2 次。你可以稍后再试，或导出为本地文件。"
```

**三条附加规则**：

```
□ ⭐ 不把技术细节（错误码、堆栈、字段名）直接给用户看
□ ⭐ 但要在别处可见（日志、详情折叠区）——供支持排查
□ ⭐ 不责怪用户（"你输错了" → "这个格式我们还不认"）
```

## 按钮与标签

```
□ ⭐ 用动词短语，不用"确定/取消"这类通用词
   "保存草稿" / "删除这 3 项"——用户不看上下文也知道会发生什么

□ ⭐ 破坏性按钮要能看出后果
   "删除" → "删除项目（含 12 个文件）"

□ 长度：按钮 2–4 字（中文）或 1–3 词（英文）
□ ⭐ 同一动作在全产品用同一个词（不要"移除/删除/清空"混用）
```

> ⭐ **一致性这条是技能最容易产生价值的地方**——
> 模型的默认行为是"换个说法显得不重复"，
> 而产品需要的是**笨拙的一致**。

呼应 `customer-success-playbook.md`（**`skill-domain-biz`**）的同一条思路：
**产品用量权重最高，因为它客观**——
文案一致性也是靠"不许变化"来保证的。

## 空状态

> ⭐ **空状态是最容易被忽略、也最该写好的地方。**

三段结构：

```
1. 这里本该有什么（说明这块是干嘛的）
2. ⭐ 为什么现在是空的
3. ⭐ 一个明确的下一步动作
```

```
❌ "暂无数据"

✅ "还没有创建任何报表
    创建后可以在这里统一管理并共享给团队。
    [创建第一个报表]"
```

## 语气与禁词

**语气基准**（技能里要写死，不能让模型自由发挥）：

```
□ 称呼：用"你"还是"您"（写死一种）
□ 句末：用不用句号（写死一种）
□ ⭐ 人称：不说"我们很抱歉"——说"你可以…"
```

**禁用词清单**（这类清单是技能的核心资产）：

```
❌ 术语表里的禁用词
   例：不用"赋能/抓手/闭环"（内部黑话）
❌ ⭐ 吓唬用户的词
   "警告！""严重错误！"——除非真的严重
❌ ⭐ 推卸责任的表达
   "你操作有误""用户错误"
❌ 空泛安抚
   "请稍后再试"（不给任何信息）
```

呼应 `methodology-skills.md` 的品牌规范四件套：
**语气基准 · 术语表 · 禁用词 · 示例库**。

## 可检查的验收清单

```
□ 每条错误信息都含三段（什么/为什么/怎么办）
□ 没有直接暴露技术细节给终端用户
□ 按钮是动词短语且标出后果
□ 破坏性操作说明了影响范围
□ 空状态含"为什么"和"下一步"
□ 全产品同一动作用同一个词
□ 不在禁用词清单里
□ ⭐ 长度符合（按钮 2–4 字）
```
