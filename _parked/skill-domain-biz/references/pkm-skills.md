## 为什么笔记不够

> **三个摩擦点，每个都是失败点**：

```
① 你得在正确的时刻想起它存在
② 你得在成千上万条笔记里找到它
③ 你得想清楚怎么把它应用到当前情境
```

> ⭐ **多数被捕获的知识从未被复用**——
> 不是因为质量低，而是因为在"需要的那一刻"，
> 检索与应用的成本太高。

**一个衡量第二大脑价值的公式**：

```
第二大脑价值 = 记录覆盖度 × 自动整理度 × ⭐ Agent 可调用度
```

> ⭐ **三项相乘，任何一项为零，整体价值归零。**
>
> 传统笔记软件前两项能打六七十分，
> 但 **Agent 可调用度几乎为零**——
> 沉淀的知识无法被 AI 调用，相当于第二大脑一直处于离线状态。

## 转化管线

```
被动笔记 → 互联笔记 → ⭐ AI 技能 → 可组合的 agent 能力
```

**四步具体操作**：

```
1. 阅读与捕获
   从非虚构书里做笔记：框架、心智模型、决策标准、可操作原则
   ⭐ 用自己的话写

2. 原子化
   拆成原子笔记，每条一个清晰的想法

3. 生成技能
   让 AI 从你的笔记创建一个技能
   例："读我关于《原子习惯》的笔记，
        创建一个帮我高效养成新习惯的技能"

4. 组合与应用
   ⭐ 来自不同书的技能可以组合使用
```

**具体映射例子**：

| 来源 | 变成的技能 |
|---|---|
| 谈判书 | 准备清单 + BATNA 分析技能 |
| 写作书 | 按作者原则审草稿的技能 |
| 决策书 | 决策框架应用技能 |
| 商业战略书 | 按战略模式审计计划的技能 |

## 捕获与原子化的硬指标

> ⭐ **这些数字本身就是"可观察谓词"，可以直接写进技能**：

**捕获阶段**：

```
□ ⭐ 捕获动作必须 ≤5 秒
  超过就说明你的捕获机制太复杂
□ ⭐ 立刻加一行上下文：这解决了什么问题？什么语言/框架？
  ——防止"这笔记是干嘛的"问题把笔记变成坟场
□ 检查点：每条 inbox 笔记至少有
  标题 + 原始内容/代码 + 一行上下文
```

**处理阶段**：

```
□ 每天结束时清空 inbox
□ ⭐ 不留超过 48 小时的陈旧条目
□ 删除不再相关的（错误已修、API 已过时）
□ ⭐ 原子化：一条笔记 = 一个想法/模式/方案
  超过约 20 行有意义内容就该拆分
□ 检查点：每条已处理笔记主题单一，能独立作为参考
```

## PARA 与链接

**四类分类**：

```
Projects   有截止日期的活跃工作（如 auth-migration-api）
Areas      需要持续维护的责任（如 security、performance-tuning）
Resources  未来会用到的参考资料（如 database-indexing-strategies）
Archives   已完成项目或不活跃领域的条目
```

```
□ 检查点：每条笔记恰好属于一个 PARA 类别
  若同时适合多个，选时间敏感度最高的那个
```

**链接构建**（这是"笔记集合"变成"知识图谱"的那一步）：

```
□ 每条永久笔记找出 1–3 条概念相关的已有笔记，建立双向引用
□ ⭐ 检查点：每条新永久笔记至少有一条出链（引用别人）
                          和一条入链（被别人引用）
```

**每周回顾**：

```
□ 零碎先扔临时箱，周末集中归类、排雷、覆盖旧知
□ 维护一份按问题类型索引的可复用模式"菜谱"
```

## 组合性：真正的乘数

> ⭐ **来自不同来源的技能可以协同工作——这是能力层面的复利，不只是信息层面的。**

```
写作技能 + 说服框架 + 结构化思考模型
→ 组合出比任何单一来源都强的东西
```

**三条设计原则**（值得直接搬进你自己的技能库规范）：

```
范围      ⭐ 一个技能做好一件事
          太宽 → 产出于篇一律的通用结果
          太窄 → 很少被触发
          合适范围 = 映射到一条具体工作流或一类决策

可移植性  ⭐ 纯 Markdown 存在标准目录里
          跨机器、跨工具、跨 AI 供应商，无厂商锁定

可测试性  ⭐ 范围良好的技能可以被测试：
          给一个已知输入，验证输出是否符合预期
```

> ⭐ **"可移植性"这条与 `skill-crafting` 的 `directory-contract.md` 直接呼应**——
> 技能是纯文本，这是它相对微调最大的结构性优势。

## 不该用的场景

```
❌ 团队级文档        → 用写作技能或专门文档平台
❌ 存敏感凭据或密钥   → ⭐ 用密钥管理器，不是笔记
❌ 长篇技术写作      → PKM 是原子的、可检索的知识，不是文章
❌ 用完即弃的临时草稿 → 不值得进库
```

> ⭐ **"不存密钥"这条要特别强调**——
> 呼应 security：笔记库通常是最容易被忽视的泄露面，
> 且它往往被整体授权给 agent 读取。

## 自查

```
□ 是否知道"Agent 可调用度"是相乘项（为零则整体归零）？
□ 捕获动作是否 ≤5 秒？
□ 每条笔记是否都有一行上下文（解决什么问题）？
□ inbox 是否 48 小时内清空？
□ 原子笔记是否 ≤20 行有意义内容？
□ 每条永久笔记是否既有出链又有入链？
□ 是否有每周回顾（归类、排雷、覆盖旧知）？
□ 是否维护了按问题类型索引的模式"菜谱"？
□ ⭐ 是否在笔记库里存了密钥（应明确禁止）？
□ 从笔记生成的技能是否做到了"一个技能一件事"？
□ 是否利用了跨来源技能的组合性？
```
