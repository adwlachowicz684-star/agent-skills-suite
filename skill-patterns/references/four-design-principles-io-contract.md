## 1. ⭐⭐⭐ 四项原则

| 原则 | 含义 |
|---|---|
| ⭐ 单一职责（SRP） | ⭐ 一个技能只做一件事 |
| ⭐⭐ 输入输出稳定 | ⭐⭐⭐ 输入可预测，⭐⭐⭐ **输出可解析** |
| ⭐⭐⭐⭐ 无状态 | ⭐⭐⭐⭐ **不依赖上下文记忆，每次调用独立** |
| ⭐⭐⭐ 可组合 | ⭐⭐ 可被工作流调用，作为更大任务链的一环 |

> ⭐⭐⭐ **"这些原则直接决定了技能的⭐ 可维护性、可复用性和⭐ 可组合性。"**

> ⭐⭐⭐⭐ **"输出可解析"这个措辞比"输出格式稳定"更精准**——
> 它把判据从"看起来一样"前移到了⭐ **下游能不能机械处理**。
>
> ⭐⭐⭐ 对照 `output-stability-contract.md` 的验收条件
> （文件是否生成 · JSON 是否可解析 · 列表是否包含必要字段）：
> ⭐⭐⭐ **"可解析"是唯一能被机器立即判定的一条**，
> 所以它是四项里⭐ 最该先保证的。

## 2. ⭐⭐⭐⭐ 无状态：最容易被违反的一条

```
⭐⭐⭐⭐ Skill ⭐ 不依赖上下文记忆，⭐⭐ 每次调用独立
```

> ⭐⭐⭐⭐ 这条⭐ 此前从未被明确列为原则，但它的⭐ 违反方式我们见过很多次：
> ```
> · three-crash-scenes.md：技能 B ⭐ 复用了技能 A 的中间状态 → 产出体系全错
> · three-stages-...md：激活后指令⭐ 常驻，被后续轮次反复看到
> · context-budget-math.md：激活不是一次性开销
> ```
> ⭐⭐⭐⭐ **"常驻"是机制，"无状态"是你该据此采取的设计纪律**——
> 正因为机制上做不到真正无状态，⭐⭐ 你才必须在⭐ 设计上显式隔离。
>
> ⭐⭐⭐ 具体做法（三条）：
> ```
> ① ⭐⭐⭐ 中间产物⭐ 显式命名/加前缀，让它⭐ 自带归属标记
> ② ⭐⭐⭐ 跨技能交接时显式收尾（ANNOUNCE→SUMMARIZE→LOAD→PASS）
> ③ ⭐⭐⭐ 步骤措辞要能承受⭐ 被反复看到（不要写"第一步做 X"）
> ```
> ⭐⭐⭐ 第 ③ 条与 `context-budget-math.md` 完全一致——
> **"第一步"这种措辞在第 20 轮仍然会被读到，而 agent 不知道那是一次性的。**

## 3. ⭐⭐⭐ 数据契约 schema.yaml

```
⭐⭐⭐ `schema.yaml` 是技能的"⭐ 数据契约"
⭐⭐⭐ 它用⭐ 结构化语言⭐ 定义了技能的⭐ 输入参数和输出格式
⭐⭐⭐⭐ 这种契约化定义确保了⭐ 下游系统（工作流引擎、API 调用方）
       ⭐⭐⭐ 能够⭐ 可靠地解析技能的输出结果
```

**它解决了什么问题**：

```
自然语言写的输入输出说明 → ⭐⭐⭐ 解析器读不了
   （正是 dependency-lockfile 里 36.6% 隐藏依赖的成因）

schema.yaml → ⭐⭐⭐ 机器可读 → ⭐⭐⭐ 下游能可靠解析
```

> ⭐⭐⭐⭐ 这与我们已有的一条完全同构：
> ```
> dependency-resolution-conflicts.md：
>   "需要 Python 环境"不是声明，`python: ">=3.11"` 才是
> 本份：
>   "输出一个 JSON"不是契约，⭐ `schema.yaml` ⭐ 才是
> ```
> ⭐⭐⭐⭐ **同一个原则在两个层面各出现一次：依赖要结构化，I/O 也要结构化。**
> 自然语言描述的东西，⭐ 机器读不了，⭐⭐ 于是也没法被自动校验。

**与已有文档的分工**：

| 场景 | 用什么 |
|---|---|
| 脚本的输入输出 | ⭐ `script-cli-contract.md`（退出码 + stdout） |
| 技能对外的 I/O | ⭐⭐⭐ `schema.yaml`（给工作流/API 用） |
| 给模型看的输出格式 | ⭐ `output-stability-contract.md`（模板 + 示例） |

> ⭐⭐ 三者的⭐ 读者不同：
> **脚本契约给模型看，schema.yaml 给下游系统看，输出模板给模型看。**
> ⭐⭐⭐ 只有"技能要被工作流/其他程序调用"时才需要 schema.yaml——
> 纯人机交互的技能不必引入这层复杂度（避免"过早工程化"）。

## 4. ⭐⭐ 与已有原则的关系

```
单一职责 ←→ 已有四条独立来源（scope-multiplication 的笛卡尔积、
             双向无知、重启测试、一技能一动词）
输入输出稳定 ←→ output-stability-contract.md（跑两遍测试法）
无状态     ←→ ⭐⭐⭐ 本份新增（机制上无法完全做到，但设计上必须显式隔离）
可组合     ←→ skill-chaining-composition.md（叠加不覆盖、交接四步）
```

> ⭐⭐⭐ 四项原则的价值在于⭐ 提供了一个验收清单：
> 写完之后逐条问——
> ```
> □ 它能用一句话说清只做哪一件事吗
> □ 它的输出能被机械解析吗
> □ 换一个会话、不带上文，它还能跑出同样结果吗
> □ 它能被别的工作流当成一个环节调用吗
> ```
> ⭐⭐⭐ 第 ③ 问最实用——**换一个干净会话跑一次**（正是跑两遍测试法）。

## 速查

```
□ ⭐⭐ 单一职责：一个技能一件事
□ ⭐⭐⭐ 输入输出稳定：⭐⭐⭐ 判据是⭐ 输出"可解析"而非"看起来一样"
   ⭐⭐⭐ "可解析"是四项里唯一能被机器立即判定的 → 最该先保证
□ ⭐⭐⭐⭐ 无状态：⭐⭐⭐⭐ 不依赖上下文记忆，每次调用独立
   ⭐⭐⭐⭐ 机制上做不到（指令常驻），所以⭐ 设计上必须显式隔离：
      ① 中间产物加归属标记 ② 交接显式收尾 ③ ⭐ 步骤措辞要能承受被反复看到
□ ⭐⭐⭐ 可组合：能作为更大任务链的一环

□ ⭐⭐⭐ schema.yaml = 数据契约：⭐ 结构化定义 I/O，让⭐ 下游能可靠解析
   ⭐⭐⭐⭐ 同构："输出一个 JSON"不是契约，schema.yaml 才是
           （正如"需要 Python"不是声明，`python: ">=3.11"` 才是）
   ⭐⭐ 读者不同：脚本契约给模型 · schema.yaml 给下游系统 · 输出模板给模型
   ⭐⭐⭐ 只有要被工作流/程序调用时才需要，别过早引入

□ ⭐⭐⭐ 验收四问：一句话职责？输出可解析？⭐ 换干净会话还能跑？能被当环节调用？
   ⭐⭐⭐ 第 3 问最实用 = 跑两遍测试法
```

**一句话**：

> ⭐⭐⭐⭐ **四项原则里此前最缺的是"无状态"——机制上技能指令会常驻、做不到真正无状态，所以设计上必须显式隔离（中间产物加归属标记、交接显式收尾、步骤措辞要能承受被反复看到）；而"输入输出稳定"的判据应是"输出可解析"而非"看起来一样"，因为可解析是四项里唯一能被机器立即判定的。**
