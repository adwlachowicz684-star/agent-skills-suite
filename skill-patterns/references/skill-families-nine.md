## 1. 九类

Anthropic 把内部跑过的几百个技能归成九类：

| 类型 | 教什么 | 典型内容 |
|---|---|---|
| **库 / SDK 类** | 正确使用某个内部库或 CLI | 参考代码片段文件夹 + 踩坑清单 |
| ⭐ **验证类** | 测试并验证代码是否正常工作 | 搭配 Playwright / tmux；程序化断言 |
| **数据 / 监控类** | 连数据库、看板，按预设 query 拉数据 | 带凭证的获取库、仪表盘 ID、常见工作流 |
| **业务流程自动化** | 把重复操作打包成一条命令 | standup-post、weekly-recap；依赖其他技能或 MCP |
| **脚手架类** | 生成框架代码、新服务模板 | 预配置认证/日志/部署 |
| **代码质量 / 审查** | 强制执行质量标准、辅助审查 | 确定性脚本；可挂 hooks 或 GitHub Action |
| **CI/CD 与部署** | 获取、推送、部署 | 看护 PR（重试不稳定 CI、解冲突）；渐进切流 + 回归回滚 |
| **运维手册（Runbook）** | 从症状出发走完多工具调查 | 收 Slack 消息/告警 → 结构化报告 |
| **基础设施运维** | 日常维护，部分含破坏性操作 | 查孤儿 Pod、查账单异常；⭐ 需要护栏 |

**库 / SDK 类的一条细节**：

```
⭐ 尤其适用于"内部库"或"Claude 容易出错的常见库"
   ⭐ 通常包含：参考代码片段文件夹 + ⭐ 一份踩坑清单
```

> ⭐ "内部库"这一点很关键——**模型训练数据里没有你的内部库**，
> 这正是 `knowledge-delta-checklist.md` 说的"模型不知道的东西"。

## 2. ⭐⭐ 跨类最难用好

> ⭐⭐ **跨多个类的技能通常最难用好。**

```
例：写一个"客服助手"
  又想做查询（数据类）
  又想做推送（业务流程类）
  又想做归档（基础设施类）
→ ⭐ 结果哪件事都做不利索
```

> ⭐⭐ **最好的技能都是"一类做到底"。**

> ⭐ 这与 `description-scope-shape.md` 的"一技能一动词一范围"、
> `granularity-atomic-workflow.md` 的"重启测试"是同一条原则的三种表述——
> **单一职责这件事，在这套体系里被反复验证。** --
实际上三条来自完全不同的来源（Anthropic 内部经验 / 独立博客 / 拆分方法论），
互相独立地得出同一结论。

## 3. ⭐⭐ 验证类值得花一整周

> ⭐⭐ **验证类技能对确保输出质量极其重要，
> ⭐ 值得让一个工程师花一整周时间专门打磨。**

**两个高级技巧**：

```
① ⭐ 让 Claude 录制输出视频以便回看测试过程
② ⭐ 在每个步骤强制执行程序化断言
```

> ⭐ 第 ② 条与 `deterministic-scripts.md` 的"该脚本化的就脚本化"、
> `assert-on-environment.md` 的"断言打在环境状态上"完全同源：
> **验证不能靠模型自己说"通过了"，必须有程序化断言。**

这也解释了为什么 `skill-evaluating` 里的测试金字塔把 L1（结构/契约）
放在最底层且要求 100% 通过——**它是最便宜且最可靠的那一层**。

## 4. ⭐ 对抗性审查

代码质量类里有个很有意思的做法：

```
⭐ "对抗性审查"：
   生成一个⭐ 全新视角的子代理来批评代码
   → 然后修复问题
   → ⭐ 反复迭代，⭐ 直到只剩下吹毛求疵级别的意见
```

> ⭐⭐ 两条值得抄的设计：
>
> ① **停止条件是"只剩吹毛求疵级别"**——这是个可观察的判据，
>    比"迭代 3 次"或"直到满意"都好
> ② **"全新视角"** 对应 `multi-agent-review.md` 的 `challenge_agent`
>    是必需角色——专家专注自己的领域，会漏掉横切关注点

这类技能还可以**挂在 hooks 或 GitHub Action 里自动运行**
（呼应 `determinism-boundary.md` 的"确定性约束放 hook"）。

## 5. ⭐ 好技能是被使用筛选出来的

Anthropic 内部的分发机制很特别（这段描述值得原样记住）：

```
⭐⭐ 技能不是被指派的：
   有人写出来 → 扔到 GitHub 的沙箱文件夹 → 在 Slack 里推广
   → ⭐ 等获得足够关注后，才正式进入市场
```

> ⭐⭐ **这个机制很像开源社区——
> ⭐ 好的技能是被"使用"筛选出来的，不是被"规划"出来的。**

配套一条警告：

> ⭐ **创建糟糕或冗余的技能非常容易，
> 所以⭐ 正式发布前一定要有某种筛选机制。**

**关于"技能即组织记忆"**（这个视角我认为最有价值）：

```
⭐ 你团队里最懂 PR 流程的人、最熟悉数据看板的人、
  最会处理线上事故的人——
  ⭐ 他们脑子里的隐性知识，过去靠口口相传，现在可以沉淀成技能。
```

> ⭐⭐ **这是一种新的"组织记忆"。**
> 这与 `reproduction.md` 的"技能作为可传递的专业知识"、
> `methodology-skills.md` 的"把成熟方法论编码成技能"是同一条主线——
> **技能的真正价值不在自动化，在⭐ 把隐性知识变成可执行资产。**

**起步心态**（收尾那句很打动人，也最实用）：

```
⭐ "我们大多数技能一开始就是几行字加一条踩坑记录，
   然后随着 Claude 撞上新的边界 case，被一点点喂大。"
```

→ ⭐ **别想着一次写完美。先写最小版本，让它跑起来，
然后用每一次失败去喂养它。**

## 速查

```
九类：
□ 库/SDK（⭐ 内部库 + 踩坑清单）
□ ⭐ 验证类（⭐ 值得花一整周打磨）
□ 数据/监控 · 业务流程自动化 · 脚手架
□ 代码质量审查（可挂 hooks/GitHub Action）
□ CI/CD 部署 · ⭐ Runbook（症状→多工具调查→报告）
□ 基础设施运维（⭐ 需护栏）

□ ⭐⭐ 跨多个类的技能通常最难用好 → ⭐ "一类做到底"
□ ⭐ 单一职责原则被三个独立来源反复验证

⭐⭐ 验证类：
□ ⭐ 值得一个工程师花一整周
□ 技巧① 录制输出视频以便回看
□ ⭐ 技巧② ⭐ 每步强制程序化断言（不能靠模型自述"通过"）

⭐ 对抗性审查：
□ 全新视角子代理批评 → 修复 → ⭐ 迭代到"只剩吹毛求疵级别"
□ ⭐ 停止条件可观察，比"迭代3次"好

□ ⭐⭐ 好技能是被"使用"筛选出来的，不是被规划出来的
□ ⭐ 发布前必须有筛选机制（创建糟糕技能太容易）
□ ⭐⭐ 技能 = 新的"组织记忆"（隐性知识 → 可执行资产）
□ ⭐ 起步：几行字 + 一条踩坑记录，用失败喂养它
```

**一句话**：

> ⭐⭐ **跨多个类的技能通常最难用好——最好的技能都是"一类做到底"。**
