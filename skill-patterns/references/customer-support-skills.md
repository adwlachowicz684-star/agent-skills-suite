## 为什么不能只靠提示词

```
□ ⭐ 普通提示词一次能跑，但长期不稳定
□ ⭐ 一个人会用，团队难复用
□ 技能把流程写进 SKILL.md，把模板放进 templates/，
  把边界放进 references/
  → ⭐ 让 agent 每次按同一套路径执行
```

**五条核心机制**：

```
1. ⭐ 用 SKILL.md 规定回复结构，而不是让 agent 自由发挥
2. ⭐ 先判断客户问题类型，再决定查哪些知识片段
   ——避免一次性加载全部资料
3. ⭐ 每条回复都带来源、适用条件和"不可承诺项"
4. ⭐ 把"需要人工确认"的问题单独列出
   ——形成客服与销售/售后的协作闭环
5. 边界与升级规则进 references/，可独立更新
```

> ⭐ 第 2 条是渐进式披露在业务场景的落地：
> **按需加载不只是省 token，更是避免把不适用的规则混进来**。

## 五步工作流

```
① 收集输入   消息、文档、表格、历史记录
② 判断场景   识别类型、优先级、适用边界
③ 按需加载   ⭐ 只读取相关的模板和规则
④ 生成结果   摘要、清单、回复、待确认项
⑤ ⭐ 复核闭环 人工确认、记录反馈、沉淀样本
```

**两个真实案例的对比**（这类技能最该写进去的东西）：

| | 没有技能 | 有技能 |
|---|---|---|
| **SaaS 价格/功能咨询** | 凭记忆回复，再翻价格表和合同模板；新人把试用规则、发票规则、折扣规则混在一起 | 识别场景 + 补充字段 + 结构化输出 + ⭐ 列出需人工确认项 |
| **硬件售后保修** | 直接让客户寄回 → 本可远程解决的问题进入维修流程，增加物流成本 | ⭐ 先给排查路径 → 判断服务边界（12 个月内、排除人为损坏）→ 标准回复 + 工单字段 + 升级规则 |

> ⭐ 第二个案例特别有说服力：
> **技能的价值不只是"回答得更准"，而是改变了动作顺序**——
> 先远程排查，再决定是否寄修。

## 输出要拆成四块

> ⭐ **不要把输出写成一整段回复**：

```
1. 客户回复    可直接发出去的文本
2. ⭐ 内部动作   转销售跟进 / 建工单 / 补字段 / 24 小时未回复自动提醒
3. ⭐ 风险提示   不得承诺固定折扣、不得越过合同审批承诺特殊条款
4. 复盘字段    设备型号、购买渠道、故障现象、已尝试操作
```

**工单字段示例**（硬件售后）：

```
设备型号 · 购买渠道 · 故障现象 · 已尝试操作 · 是否需要寄修
```

**升级规则**（写成可判定的条件）：

```
□ ⭐ 三次远程排查失败 → 转二线工程师
□ ⭐ 出现硬件异常码 → 转二线工程师
□ 复杂投诉 → ⭐ 技能先整理事实，再交负责人（不自动回复）
```

> 呼应 `skill-crafting` 的 `guidance-forms.md`：**升级条件必须是可观察谓词**，
> 不能写"视情况而定"。

## 必守的四条红线

```
1. ⭐ 不要把过期价格表混进知识库
   ——否则 agent 会生成"看似专业但实际错误"的回复

2. ⭐ 不要让技能直接承诺退款、赔偿、折扣
   ——这些必须进入人工复核

3. ⭐ 知识库字段要稳定
   至少包含：问题类型 · 适用产品 · 规则原文 · ⭐ 生效时间

4. ⭐ 复杂投诉不要只靠自动回复
   ——技能应先整理事实，再交给负责人
```

> ⭐ 第 3 条的"生效时间"字段是关键——
> 呼应 `legal-contract-skills.md` 的依据日志：
> **没有时间信息的规则，无法判断它现在还成不成立**。

## 知识库字段规范

> ⭐ **最小字段集**（写在 `references/知识库字段规范.md`）：

```
□ 问题类型
□ 适用产品
□ ⭐ 规则原文（逐字，便于追溯）
□ ⭐ 生效时间
```

**目录结构**（一个完整的业务技能包长什么样）：

```
SKILL.md                        定义执行流程
templates/客服回复模板.md         模板
references/知识库字段规范.md        字段规范
references/升级规则清单.md         边界与升级条件
scripts/知识片段整理脚本.py        确定性整理
assets/示例输入说明.md             示例
```

**落地建议**：

```
□ ⭐ 先用小范围真实数据试跑三次，
   确认输出结构稳定后，再接入日常工作流
□ 把反馈与样本沉淀回 references/，形成闭环
```

## 自查

```
□ 是否规定了回复结构（而非让 agent 自由发挥）？
□ ⭐ 是否先判问题类型再决定加载哪些知识片段？
□ ⭐ 每条回复是否带来源、适用条件、不可承诺项？
□ ⭐ 是否把"需人工确认"的问题单独列出？
□ 输出是否拆成四块（客户回复/内部动作/风险提示/复盘字段）？
□ ⭐ 升级规则是否是可判定条件（三次失败/异常码）？
□ 是否禁止直接承诺退款/赔偿/折扣？
□ ⭐ 知识库字段是否含"生效时间"？
□ 是否警告"过期价格表混进知识库"的风险？
□ 复杂投诉是否要求先整理事实再交人？
□ 是否有试跑三次再接入的建议？
□ 目录结构是否用齐了 templates/ references/ scripts/ assets/？
□ 是否有沉淀反馈回 references 的闭环？
```
