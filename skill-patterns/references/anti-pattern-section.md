# 反模式章节：怎么把它写得有用

> 多数技能里的 "Anti-Patterns" 一节是**装饰**——
> 列了几条常识，对行为没有任何影响。

## 一个反模式的四要素

```markdown
### ❌ [Pattern Name]

[agent 做错了什么]

[为什么这很糟 —— ⭐ 带具体代价]

[该怎么做]
```

四条缺一不可。**缺第三条（具体成本）是最常见的失败**。

## 什么是"有名字"

> ⭐ **命名是为了能在对话里被引用。**

```
❌ "一种不好的做法"
✅ "静默失败链" / "先翻日志综合征" / "大 diff 直灌"
```

命名之后，人和 agent 都能说"你又犯了 X"——
**一个没有名字的错误模式无法被指认，也就无法被纠正**。

## 什么是"成本具体"

```
❌ "这会导致问题"
❌ "这样不好"
✅ "浪费 6,200 次请求"
✅ "会导致 15 分钟的调试"
✅ "会让下游静默接收一个空数组，三步之后才暴露"
```

> ⭐ **具体成本的作用不是吓唬模型，
> 是让它能在"要不要走捷径"时做出正确的权衡。**

模型没有代价直觉——你说"这样不好"，
它不知道"不好"是 10 秒还是 10 小时。

## 坏例子 vs 好例子

**坏的**

```markdown
### ❌ 不好的测试写法
写测试时不认真。
这会导致测试质量下降。
应该认真写测试。
```

问题：没名字（"不好的写法"不算名字）、
成本抽象（"质量下降"）、替代方案是废话（"认真写"）。

**好的**

```markdown
### ❌ 快照测试泛滥

改动任何代码后，直接用 `--updateSnapshot` 更新快照，
不去读 diff。

为什么糟：⭐ 快照更新等于"把当前行为定义为正确"，
          掩盖了真实回归。我们曾因此漏掉一个
          让金额少算一位的 bug，上线三周后才发现。

该怎么做：⭐ 只在纯展示组件上用快照。
          涉及数值、状态、业务逻辑的，写显式断言。
```

四要素齐了，而且**"我们曾因此……"** 这种真实经历
比任何抽象警告都有说服力。

## 去哪里找反模式

> ⭐ **反模式不能靠想象，必须来自真实经历。**

三个来源：

```
① 你自己在真实任务里看到 agent 犯的错
   ⭐ ——价值最高，因为你知道代价

② 让第二个 agent 只用这份技能做任务，看它在哪跑偏

③ 团队 code review / 事故复盘里反复出现的模式
```

判据和 Gotchas 一样：**这一条是"猜的"还是"见过的"？**

> ⭐ 这也是为什么反模式和 Gotchas 一样
> **几乎不可能通过 no-op 测试**——
> 修剪时永远别动它们。

## 与禁令的区别

反模式章节**不是禁令清单**：

```
禁令      "不要做 X"                    ——没说该做什么
反模式    "不要做 X（因为代价是 Y），
           应该做 Z"                    ⭐ ——同时给了替代方案
```

回顾 `guidance-forms.md`：
**禁令单独使用可能反噬，而"配方"形态更硬。**
反模式章节因为带了"该怎么做"，实际上更接近**配方**。

> 所以如果你要在两者间选一个保留，**保留反模式章节**。

## 自查

```
[ ] 每条都有名字（能在对话里被引用）？
[ ] ⭐ 每条的成本都是具体的数字或具体后果？
[ ] 每条都给了"该怎么做"？
[ ] ⭐ 每条都来自真实经历，不是理论推测？
[ ] 有"我们曾因此……"这类具象证据吗？
[ ] 数量适中（3–8 条；太多说明该拆技能）？
```

最后一条：**如果一个技能的反模式超过 8 条，
通常说明它承担了太多职责**——该拆了（见 `splitting.md`）。

## 一条提醒

反模式章节**不要写成"常见错误汇总"**——
那是给人看的教程。

> ⭐ **技能里的每一节都要对 agent 的行为产生影响。**
> 如果一条反模式不会改变 agent 下一步做什么，它就是装饰。
