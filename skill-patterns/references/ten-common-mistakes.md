## 1. 太长

```
SKILL.md 超过 1000 行 → 拆开
⭐ Claude 的上下文有限
```

修法：保持在 500 行以内，参考资料拆出去。

---

## 2. ⭐ 太抽象

```
❌ "Write good code"  —— 毫无用处
✅ "函数不超过 50 行；每个函数最多 3 个参数；
   变量不用缩写（customerName 而非 custNm）；
   每个公开函数需要 JSDoc"
```

> ⭐ 判据：**能不能机械检查**。
> "不超过 50 行"能；"易于阅读"不能。

---

## 3. ⭐ 指令自相矛盾

```
❌ "Always add comments"
   "Don't add unnecessary comments"
```

> ⭐ 这类矛盾不会报错，只会让模型随机选一边。
> **写完必须通读一遍找矛盾**——
> 尤其是技能经过多人多次修改之后。

---

## 4. 缺上下文

```
❌ "Use the standard testing pattern"
✅ "Use Jest with React Testing Library. Structure tests as:
   describe('ComponentName', () => { it('should render correctly', ...); });"
```

> ⭐ **别假设模型知道你的技术栈。**

---

## 5. 描述写内容而非触发

```
❌ 描述技能"是什么"
✅ 描述"何时用"
```

> 与 `nine-anti-patterns.md` 第 6 条（隐身技能）同源。

---

## 6. 太宽

```
触发一切 → 对任何事都没用
```

修法：收窄到具体动作与产物。

---

## 7. 缺约束

```
agent 会理性化地跳过步骤
```

修法：加 "Do NOT" 规则与 HARD-GATE 标记。

> 与《skill-crafting》的 `anti-rationalizations.md` 互补。

---

## 8. ⭐ 未对真实提示测试

```
未经真实提示测试的技能，到生产环境会误触发
```

> ⭐ **修法很特别：在写技能之前先写测试提示。**
> 这与 `eval-loop-official.md` 的"先跑一遍再加断言"略有张力——
> 但两者其实说的是不同阶段：
> **先写触发用的提示（决定 description），
> 跑完再加输出断言。**

---

## 9. 外部文件依赖

```
脆弱——文件可能不存在
```

修法：**自包含，或先检查文件是否存在。**

---

## 10. ⭐ 该用表格却用散文

```
更难扫描，且更费 token
```

修法：结构化对比一律用表格。

---

## 速查

| 错误 | 判据 |
|---|---|
| 太长 | >500 行就拆 |
| ⭐ 太抽象 | ⭐ 能否机械检查 |
| ⭐ 自相矛盾 | 通读一遍 |
| 缺上下文 | 别假设知道技术栈 |
| 描述写内容 | 改成写触发 |
| 太宽 | 收窄到具体动作 |
| 缺约束 | 加 Do NOT / HARD-GATE |
| ⭐ 未测真实提示 | ⭐ 先写测试提示 |
| 外部依赖 | 自包含或先检查存在 |
| ⭐ 该用表格用散文 | 结构化对比用表格 |

**四条最该记住的**：

```
① ⭐ 每条规则要能机械检查
② ⭐ 写完通读找矛盾（尤其多人改过之后）
③ ⭐ 先写测试提示，再写技能
④ ⭐ 结构化信息用表格
```
