## 1. ⭐⭐⭐ 四层优先级

```
1. ⭐⭐ Platform Schema          （最高）
   └── ⭐ 硬限制：permissions · tools · model
2. ⭐⭐ Project Facts
   └── ⭐⭐ 约束——它们⭐ 过滤选项
3. ⭐⭐⭐ Meta Skills
   └── ⭐⭐ 推理框架——它们⭐ 引导方法
4. ⭐ Core Skills                （最低）
   └── ⭐ 程序——在约束内执行
```

**规则**：

> ⭐⭐⭐ **高层约束低层。⭐⭐⭐ 低层⭐ 不能覆盖高层。**

> ⭐⭐⭐ 这个层级比我们已有的"用户 > 技能 > 全局 Rule"更完整的地方，
> 在于它区分了⭐ **事实和技能**：
>
> ```
> "用模式 X"   ← 技能（guidance，指导）
> "X 被禁止"   ← 事实（constraint，约束）
> ```
>
> ⭐⭐ **指导可以被更具体的指导取代；⭐⭐⭐ 约束不能被任何指导取代。**
> 这是一个此前没收过的区分。

## 2. ⭐⭐ 类型一：事实 vs 技能

```
场景：技能说"用模式 X"，事实说"X 被禁止"
⭐⭐⭐ 裁决：⭐⭐⭐ 事实赢
```

**具体例子**：

```
Skill (coding-standard)：  "不可能的情况用 error"
Fact  (project/constraints)："绝不用 error，一律 Maybe/Either"
→ ⭐ 用 Maybe/Either（事实赢）
```

**一个边界情形很有意思**：

```
⭐⭐ 有些知识⭐ 同时是事实和技能
   例："Nix is truth"
      = 事实（约束）+ 技能（总是跑 `nix build`）

⭐⭐⭐ 裁决：⭐⭐ 事实那一面（约束）优先；
       ⭐ 技能那一面（程序）是⭐ 满足该约束的方式
```

> ⭐⭐ 这个拆解很漂亮——**同一句话有两个成分，
> 冲突时取约束成分，程序成分降级为"怎么满足它"**。

## 3. ⭐⭐⭐ 类型二：技能 vs 技能

**三步裁决**：

```
① ⭐⭐ 是否有一个更具体？（⭐ 具体的赢）
② ⭐⭐ 任务在哪一层？（⭐ 用那一层的技能）
③ ⭐ 仍模糊 → ⭐⭐ 走不确定性处理：⭐ 提问
```

**例子**：

```
Skill A (coding-standard)："函数保持在 20 行以内"
Skill B (hakyll-patterns)："这个编译器模式通常是 30 行"
→ ⭐⭐ Skill B 赢（⭐ 对当前上下文更具体）
```

> ⭐⭐⭐ 这与 `routing-tiers-and-arbitration.md` 的
> "特异优先于通用"是⭐ 同一条规则的独立来源，
> 但这里多了⭐ 第 ② 步"看任务在哪一层"——
> **这是一个新维度：不是比谁更具体，而是比谁管这一层。**
>
> ⭐ 也与 `collision-arbitration.md` 的"更具体的赢"一致，
> ⭐⭐⭐ 三个来源同一结论：**specificity 是仲裁的第一原则。**

## 4. ⭐⭐ 类型三：代理 vs 代理

```
场景：tech-lead 的设计 与 coder 的实现顾虑 冲突
```

**裁决**：

```
① ⭐ tech-lead ⭐ 拥有 L2 决策（设计层）
② ⭐ coder ⭐ 带证据上报 L1 顾虑
③ ⭐⭐⭐ ⭐ 如果设计被证明不可行（⭐ 三次尝试失败）→ ⭐ 回到 L2 重估
```

**例子**：

```
Tech-lead："用多态函数"
Coder："类型系统不允许，试了 3 次"
→ ⭐⭐ 带证据升级回 tech-lead，⭐ 重估设计
```

> ⭐⭐⭐ 那个"三次"与我们已有的两条⭐ 完全同构：
> ```
> · systematic-debugging：三次独立修复都暴露新问题 → 这是架构问题，停下谈架构
> · infinite-loop-timeout：重试三次失败 → 停止并说明缺什么
> ```
> ⭐⭐⭐ **"三次"是一个反复出现的停止阈值**——
> 三次足够排除偶然，又不至于浪费太多。

## 5. ⭐⭐⭐ 类型四：元 vs 核心

```
场景：元技能说"去问"，而核心技能有一个默认答案
⭐⭐⭐ 裁决：⭐⭐⭐ 元技能赢
```

**例子**：

```
Meta (uncertainty)："低置信度 + 不可逆 → 提问"
Core (coding-standard)："默认用 Text 而非 String"
任务：为一个新的公开 API 选类型

→ ⭐⭐ 提问（⭐⭐⭐ 元认知 ⭐ 覆盖默认）
```

> ⭐⭐⭐ **"元认知统治何时应用核心技能"**——
> 这条很重要，因为它确立了⭐ **"何时停下"优先于"怎么做"**。
>
> ⭐⭐ 与我们已有内容对照：
> `preflight-gate.md` 的"前置条件失败 → 快速失败"、
> `skill-ownership-changeflow.md` 的"歧义时默认回滚"——
> ⭐⭐⭐ 三条都在说：**停止/提问的判断，优先级高于执行判断。**

**还有一条上下文的补充说明**（避免误解）：

```
⭐⭐ 上下文会改变⭐ 规则被执行的严格程度，⭐ 但不改变层级
   例：dev 上下文 速度 > 完美；review 上下文 正确性 > 速度
   ⭐⭐⭐ → 这只改变"多严格"，⭐⭐⭐ 不改变"谁赢"
```

## 6. ⭐⭐ 解析流程与记录格式

**四步**：

```
① 识别冲突类型
② 查优先级层级
③ 应用该类型专属规则
④ ⭐ 仍模糊则：a 收集更多上下文  b 走不确定性处理  c ⭐⭐ 记录决策与理由
```

**记录格式**（可直接抄）：

```markdown
## Conflict Resolution
**Conflict**: [描述]
**Sources**:
- [来源 A]: [它说什么]
- [来源 B]: [它说什么]
**Type**: Fact vs Skill / Skill vs Skill / ...
**Resolution**: [决定了什么]
**Rationale**: [为什么，引用哪条优先级规则]
```

> ⭐⭐ 这个格式的价值在于⭐ **强制写出 Rationale**——
> 与 `skill-chaining-composition.md` 的"真的有歧义时记 --decision 日志"
> 是同一条：⭐⭐⭐ **没记下来的仲裁 = 下次重新吵一遍**。

**还有一条新信息处理的规则**：

```
⭐⭐⭐ 如果执行中发现某个"事实"是错的：
   ① ⭐⭐ 不要静默覆盖
   ② ⭐⭐ 标记出来："发现 X，当前事实说是 Y，要更新吗？"
   ③ ⭐ 用新信息继续，⭐ 并记下这个出入
```

## 7. ⭐⭐⭐ 反模式表

| ⭐ 不要 | 为什么 | ⭐ 改成 |
|---|---|---|
| ⭐⭐ 静默忽略冲突 | 隐藏问题 | ⭐ 显式解决 |
| ⭐⭐ 总是提问 | 浪费时间 | ⭐⭐ 先用优先级，真模糊才问 |
| ⭐⭐⭐ 让低层覆盖高层 | ⭐⭐⭐ 破坏整个系统 | ⭐ 强制层级 |
| ⭐⭐ 改事实而不标记 | ⭐⭐ 丢失知识 | ⭐ 记录更新 |

> ⭐⭐⭐ 第二条"总是提问浪费时间"与我们已有的一条形成⭐ 漂亮的互补：
> ```
> routing-tiers：候选得分都低 → ⭐ 提问（因为猜错代价大）
> 本份：⭐⭐ 有冲突先查优先级，⭐ 别一有冲突就问
> ```
> ⭐⭐⭐ 合起来是完整的判断链：
> **优先级能裁的就别问；优先级裁不了且代价不对称时才问。**

## 速查

```
□ ⭐⭐⭐ 四层：Platform Schema > Project Facts > ⭐ Meta Skills > Core Skills
   ⭐⭐⭐ 高层约束低层，⭐ 低层不能覆盖高层
□ ⭐⭐⭐ ⭐ 事实是约束，技能是指导——⭐⭐⭐ 指导可换，约束不可换

□ ①事实vs技能 → ⭐⭐⭐ 事实赢（"X被禁止"压过"用模式X"）
   同时是事实+技能 → ⭐ 取约束面，程序面降级为"怎么满足它"
□ ②技能vs技能 → ① 更具体的赢 ② ⭐ 看任务在哪一层 ③ ⭐ 仍模糊就问
□ ③代理vs代理 → tech-lead 拥 L2；coder 带证据上报 L1；⭐⭐⭐ 三次失败回 L2 重估
□ ④元vs核心  → ⭐⭐⭐ 元赢（⭐ "何时停下"优先于"怎么做"）
□ ⭐⭐ 上下文只改变"多严格"，⭐⭐⭐ 不改变"谁赢"

□ ⭐⭐ 记录格式：Conflict / Sources / Type / Resolution / ⭐ Rationale
□ ⭐⭐⭐ 发现事实错了：⭐⭐ 不静默覆盖，⭐ 标记 + 用新信息继续 + 记出入
□ ⭐⭐⭐ ⭐ 优先级能裁就别问；裁不了且代价不对称才问
```

**一句话**：

> ⭐⭐⭐ **冲突层级是 Platform Schema > Project Facts > Meta Skills > Core Skills（高层约束低层），
> 其中"事实是约束、技能是指导——指导可换、约束不可换"是关键区分；
> 而"元 vs 核心"确立了"何时停下"优先于"怎么做"。**
