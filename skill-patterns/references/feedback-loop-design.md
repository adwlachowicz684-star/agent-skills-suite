## 1. ⭐ 没有验证步骤的技能只是建议

> ⭐ **A skill without a verification step is a suggestion.**
> （没有验证步骤的技能只是一个建议）
>
> ⭐ **Every skill must have at least one feedback loop: do → check → fix.**
> （每个技能必须至少一个反馈环：做 → 检查 → 修）

这两句是 harness 工程的核心。
它们把"技能"和"提示词"区分开——
**技能自带闭环，提示词没有**。

## 2. 三类反馈环

| 类型 | 形态 | 例子 |
|---|---|---|
| **自审查清单** | ⭐ 完成后逐项勾选客观条件 | 见下节 |
| **脚本校验** | 跑脚本，看退出码 | `validate.py` 返回 0 才继续 |
| **外部验证** | 真实运行/真实数据 | 跑测试、build、真实 API 调用 |

> ⭐ 优先级：**脚本校验 > 自审查清单 > 主观判断**。
> 因为脚本不会自欺，清单可能敷衍，主观等于没有。

这与 `test-pyramid.md` 第 1 层"不用 LLM 判"同源。

## 3. ⭐ 清单项怎么写才有效

**有效清单项的特征**：

```
✅ 具体、二值（能明确判定通过/不通过）
- [ ] SKILL.md 正文少于 100 行（不含 frontmatter）
- [ ] 全部 5 类测试通过：init、moves、win、negative、visual
- [ ] 完整跑一遍没有 console 错误

❌ 主观（无法通过"检查"这个动作判定失败）
- [ ] 代码干净
- [ ] 测试通过
- [ ] 输出看起来不错
```

**规模与松紧**：

```
⭐ 目标 6–12 项
⭐ ⭐ 规模要让"真实运行偶尔会挂掉其中一项"
⭐ 一份从未抓到过任何问题的清单，说明检查得还不够硬
```

> ⭐ 最后一条是最重要的判据：
> **永远全绿的清单 = 没在检查**。
> 好的清单应该让你偶尔看到红色。

## 4. ⭐ 规则升级为代码

> ⭐ **当某条书面指令反复被违反时，
> 把它编码成校验函数或 linter——
> ⭐ 而不是把段落写得更严厉。**
>
> **可执行的规则会自我执行。**

这是全文最实用的一条。

```
"不要在 SKILL.md 里写代码块"      → 段落，反复被违反
"SKILL.md 超过 500 行就报错"      → ⭐ 校验器，自动生效
```

实证就在我们自己这套东西里：
`skill_rules.py` 里的扫描规则，
比在文档里写一百遍"不要硬编码路径"有效得多。

> ⭐ 这也解释了 `failure-modes.md` 里"禁令反噬"的现象——
> **禁令是段落，它依赖模型遵守；
> 校验器是代码，它不依赖。**

## 5. 反馈环放哪一层

```
L1 description  —— 触发是否正确（靠 5+5 测试）
L2 正文         —— ⭐ 每步后的 STOP 检查点
L3 脚本         —— ⭐ 校验器，确定性判定
```

> ⭐ 三个层次都要有，但**优先级不同**：
> **L3 最可靠且最便宜**，能进脚本的都进脚本。

**正文里的 STOP 标记**：

```
## Phase 1: Discovery
[Ask about: runtime, ports, volumes, env vars, multi-stage needs]
⭐ STOP — confirm requirements.

## Phase 2: Generate Configuration
⭐ STOP — present for review.
```

> ⭐ 没有 STOP 标记，agent 会一气呵成跳过所有验证步骤——
> 与 `five-design-patterns.md` 的 Pipeline 门控同理。

---

## 速查

```
□ 是否至少一个 做→检查→修 循环
□ ⭐ 能脚本化的校验是否都进了 scripts
□ 清单项是否二值可判定（不是"看起来不错"）
□ ⭐ 清单是否 6–12 项
□ ⭐ 清单是否"偶尔会红"
□ 正文每阶段是否有 STOP 标记
□ ⭐ 反复被违反的指令是否已升级为校验器（而非写更严厉）
```

**一句话**：

> ⭐ **可执行的规则会自我执行。**
