## 1. ⭐ 作用域即信任边界

> ⭐ **把作用域当作信任边界。
> 用户级 = 本地偏好；项目级 = 共享行为。
> 从前者跨到后者，应该感觉像一次"发布事件"，而不是随手拷贝。**

这个心智模型很关键——
它把"我把文件复制到项目里"重新定义成**一次需要被治理的动作**。

## 2. ⭐ 安装清单（manifest）

```
skills:
  - name: code-review
    source: acme/agent-skills
    pin: v1.2.0
    scope: project
    agents: [codex, claude-code]
    owner: platform-security

  - name: incident-summary
    source: acme/agent-skills
    pin: 7b6c9fd
    scope: project
    agents: [codex]
    owner: sre
```

> ⭐ 六个字段各有分工：
> `source` 从哪来 · `pin` 哪个版本 · `scope` 作用范围 ·
> `agents` 哪些客户端 · **`owner` 谁负责**。

> ⭐ `owner` 字段最容易被漏，也最要命——
> **没有 owner 的技能，出问题没人认领。**

**定制的正确方式**：

```
⭐ 想改共享技能 → 在技能仓库里 fork 并发新版本
⭐ ❌ 不要直接改已安装的副本
```

理由很硬：**update 命令强制时会覆盖本地修改过的技能文件**。

> ⭐ 一句话总结：
> **如果一个技能值得你去定制，它就值得被正当地版本化。**

## 3. ⭐ 三条最常见的错

| 错误 | 后果 |
|---|---|
| ⭐ **以为只有模型需要治理** | ⭐ **告诉模型该做什么的那一层，更易改动、更易被忽视** |
| ⭐ **默认用浮动安装** | ⭐ 一个看似微小的技能更新，可能改变 agent 处理密钥、工具调用或仓库写入的方式 |
| 混用个人与共享行为 | 一旦成为团队规范，就需要来源、评审和发布标签 |

> ⭐ 第二条最危险：
> "版本管理太麻烦" 这个权衡，
> **在你意识到技能能改 agent 的写入行为之前，看起来都无害。**

## 4. Hub-and-Spoke：谁拥有什么

```
中心平台团队（hub）  拥有并维护共享基座：
                      共享技能库 · 审查过的 MCP 连接器 · 通用护栏与审计
产品团队（spoke）    从基座组装自己的 agent，拥有领域专属行为
```

两条边界：

```
hub 不替所有人建 agent  → 否则成为瓶颈
spoke 不重造安全与连接器 → 否则混乱
```

**共享技能的样子**（带 owner 和 version）：

```yaml
name: company-data-access
version: 2.1.0
description: Safe, audited access to the company data warehouse.
owner: platform-team
```

> ⭐ **因为技能有版本、有归属，
> 一个安全修复或脱敏规则发布一次，就传播到所有依赖它的 agent。**
>
> **这就是"规模化"与"蔓延"的区别：改进在中心复利，而不是要追着十几个 fork 改。**

**四个常见坑**：

```
① 每个团队自建一切        → 必然分歧，安全不一致
② 过度集中                → 平台团队成为瓶颈，影子 agent 照样出现
③ ⭐ 没有组合视图          → ⭐ 列不出每个 agent 的 owner/成本/权限 = 失控
④ 每个团队各写一套治理策略 → 十二个团队写十二套 = 十二个缺口
```

## 5. 别过度

> ⭐ **这不意味着每个技能都需要变更顾问委员会。**

轻量但有效的组合：

```
① 两人评审规则
② 明确的 owner
③ ⭐ 安装前先预览（preview-before-install）
④ ⭐ 锁定版本
```

> ⭐ **控制手段要与风险匹配**：
> 本地记笔记的技能 ≠ 生产调试的技能。
> 但**两者都受益于"知道它从哪来、什么时候改过"**。

**最简单也最健康的一条规则**：

> ⭐ **如果一个技能能影响共享工作，
> 它就应该有一个来源仓库、一个锁定版本、和一个会对下次更新负责的人。**

## 速查

```
□ manifest 是否含 owner / pin / source / scope
□ ⭐ 是否锁定版本（不用浮动安装）
□ ⭐ 定制是否走 fork + 发版（而非改本地副本）
□ 安装前是否预览
□ ⭐ 是否有组合视图（列出所有 agent 的 owner/成本/权限）
□ hub 拥有基座，spoke 拥有领域行为
□ ⭐ 控制力度匹配风险，别上 CAB
```

**一句话**：

> ⭐ **团队要的不是更聪明的 Prompt，而是更稳定的治理。**
