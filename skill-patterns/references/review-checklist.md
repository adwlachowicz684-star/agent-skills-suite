## 1. 十项检查清单

| 检查项 | 判断标准 |
|---|---|
| ⭐ 触发条件是否在 description 中 | ⭐ 不依赖正文里的 "When to use" |
| name 是否规范 | 小写、数字、连字符，语义明确 |
| 职责是否单一 | 一个技能只解决一个核心任务 |
| 输入输出是否结构化 | 明确需要什么、返回什么 |
| ⭐ 步骤是否可执行 | ⭐ 指令式语言，不是抽象原则 |
| ⭐ 失败策略是否完整 | ⭐ 明确停止、重试、报错、降级逻辑 |
| 资源是否分层 | 细节放 references，确定性逻辑放 scripts |
| 是否避免重复 | ⭐ 同一信息不要同时出现在 SKILL.md 和 references |
| ⭐ 是否有评测用例 | ⭐ 至少覆盖黄金路径和误触发场景 |
| 是否去掉无关文档 | 不放 README、安装指南、更新日志等噪音 |

> ⭐ 第 5 条和第 1 条**同一信息不要重复**特别容易违反——
> 写 references 时习惯性把正文的要点再抄一遍，
> 结果是两处都要维护，必然漂移。

## 2. 九条反模式

| 反模式 | 问题 | 更好的做法 |
|---|---|---|
| 写大量背景故事 | 消耗上下文，执行无帮助 | 只保留任务必要信息 |
| ⭐ 使用模糊形容词 | ⭐ AI 执行不稳定 | 改成可检查的行为约束 |
| ⭐ 把触发条件放正文 | ⭐ 触发前 AI 看不到 | 放进 frontmatter description |
| 把参考资料塞进正文 | SKILL.md 膨胀 | 拆到 references/ |
| ⭐ 手写确定性格式 | ⭐ 容易出错 | 用脚本生成和校验 |
| 混用术语 | 增加理解成本 | 统一命名 |
| ⭐ 提供太多选项 | ⭐ 增加决策成本 | ⭐ 给默认路径和例外条件 |
| 包含时效性规则 | 容易过期 | 放 deprecated 或版本化参考文件 |

> ⭐ 第 7 条值得单独说：
> **给一堆选项不是"灵活"，是把决策成本转嫁给模型。**
> 正确做法是**给默认路径 + 明确的例外条件**。

## 3. ⭐ 反转测试

> ⭐ **一个很有用的技巧是"反转测试"。**

含义：**把技能里的每条规则反过来读一遍**——
如果反过来也说得通，那这条规则就是空话。

```
"确保代码质量"      → 反过来"不确保代码质量"荒谬 → 但这是废话，无操作指引
"函数不超过 50 行"  → 反过来明确错误                → ⭐ 有效，可检查
```

> 与 `pruning.md` 的 no-op 测试同源，
> 但更轻量——**不需要跑，读一遍就能筛**。

## 4. 如果只记三条

```
① ⭐ 触发条件写进 description
② ⭐ 脆弱操作交给 scripts
③ ⭐ 每条规则都要能对应一个失败场景
```

> 第 ③ 条是这条清单里最锋利的一句：
> **任何一条规则，如果你说不出"它防止了哪次失败"，就删掉。**
> 这与 `skill-structuring` 的 `what-not-to-ship.md` 的"一条规则对应一个坑"完全一致。

## 速查

```
□ description 含触发条件（不靠正文）
□ name 规范
□ 单一职责
□ 输入输出结构化
□ 步骤可执行（非原则）
□ 失败策略完整（停止/重试/报错/降级）
□ 资源分层
□ ⭐ 正文与 references 不重复
□ ⭐ 有用例（黄金路径 + 误触发）
□ 无 README/安装指南等噪音
□ ⭐ 每条规则都对应一个失败场景
□ 给默认路径，别给一堆选项
□ ⭐ 确定性格式交给脚本生成
```

**定位**（一句话）：

> ⭐ **好的技能，是在 AI 的不确定性和工程系统的确定性之间搭桥。**
