# 调试与错误恢复：五步分诊

> ⭐ **为什么值得做成技能**：
> 调试最容易漂移成"到处读文件"。**两条护栏**能防止这件事。

## 五步分诊

```
reproduce → localize → reduce → fix → guard
```

**Step 1 复现**：

```
□ 一旦拿到足以定位来源的信息，就往前走
□ ⭐ 不要为了"收集齐全"而无限期停留在这一步
```

**Step 2 定位来源**：

```
□ ⭐ 目标不是读完所有相关文件，而是快速形成一个可用假设
□ ⭐ 读出错点周围 10–20 行
   ——比只读那一行给的信息有用得多
□ ⭐ 检查这段代码最近是否改动过
   git log -10 --oneline <file>
   git diff HEAD~3 -- <file>
□ 找明显的候选：
  空指针解引用 · 对异步顺序的错误假设 · 缺失的环境变量
  · 变更的接口契约 · 差一错误
□ ⭐ 进入第 3 步之前先把假设写下来
```

**Step 3 收集证据**（见下表）

**Step 4 分析**：

```
□ 把结构化上下文交给调试子 agent：
  error: / logs: / context: / history: / environment:
□ agent 返回：
  ⭐ 带置信度排序的根因假设
  错误模式分类
  ⭐ 三阶段修复计划（立即改动 → 验证 → 部署）
  具体代码补丁
□ ⭐ 选置信度最高的假设与修复计划
□ ⭐ 若两个假设置信度接近，记下两个，先走更可能的那个
  ——第一个修复不奏效时再回来
```

**Step 5 应用与验证**：

```
□ 应用修复
□ ⭐ 跑相关测试，或复现原始触发条件
□ 错误消失 → 向用户总结：
   ️根因（大白话）
   ️改了什么、为什么这样能修
  ⭐ 后续（加回归测试、更新文档、监控某个指标）
□ ⭐ 错误仍在或出现了新错误 → 把新状态当作更新后的输入，
   回到第 2 步
   ⭐ "什么失败了"是关于真正根因在哪的有用信息
```

## 两条护栏

> ⭐ **这两条是这套方法的灵魂**：

**① 一次只验证一个假设**

```
□ 挑最可能的原因，应用修复，验证
□ ⭐ 只有验证失败才换下一个假设
□ ⭐ 同时修多个假设会把信号搅浑
```

**② ⭐ 区分代码 bug 与环境问题**

```
□ 如果根因是：
  缺失的环境变量 · 错误的 Node/Python 版本
  · 损坏的缓存 · 下游服务挂了
□ ⭐ 就明说——修复在代码之外，打代码补丁没用
```

> ⭐ 第 ② 条呼应 `skill-evaluating` 的 `troubleshooting-manual.md` 的"环境层排查"与
> `performance-optimization.md` 的"瓶颈在哪必须测量"：
> **很多"代码问题"其实是环境问题**，但 agent 默认会去改代码。

> ⭐ 第 ① 条呼应 `skill-evaluating` 的 `eval-tooling.md` 的"每次只改 1–2 个变量"：
> **无法归因的修改等于没改**。

## 要收集哪些证据

| 证据 | 从哪找 |
|---|---|
| 完整错误与堆栈 | 用户输入、测试输出或 CI 日志 |
| 出错代码 | 读来源文件；若属调用链，记下周边函数 |
| ⭐ 最近改动 | 对 package.json / go.mod / requirements.txt 或受影响模块跑 `git log --oneline -5` |
| 配置 / 环境变量 | 相关 .env、配置对象、框架初始化 |
| 日志 | logs/ 目录、stdout 捕获，或问用户 |

```
□ ⭐ 如果已有证据强力支持假设，可以立刻委派
□ ⭐ 已经理解问题时，没必要把什么都收集一遍
```

## 假设的写法

> ⭐ **把假设写下来这一步不能省**：

```
示例："我认为这里失败，是因为登出时调用 getUser()
     时 userId 是 undefined。"
```

```
□ ⭐ 一个陈述出来的假设能防止调查漂移成无焦点的读文件
□ ⭐ 呼应 grounding-verification.md：
   写下来的假设是可证伪的——这正是它比"继续看看"强的地方
□ 呼应 context-engineering.md 的 scratchpad：
   假设就是调试任务的 scratchpad
```

## 自查

```
□ 是否是五步分诊（复现/定位/归约/修复/防护）？
□ ⭐ 是否强调"读出错点周围 10–20 行"而非只读一行？
□ ⭐ 是否要求进第 3 步前先写下假设？
□ 假设是否具体（含具体变量与条件）？
□ ⭐ 是否要求"一次只验证一个假设"？
□ ⭐ 是否要求区分代码 bug 与环境问题？
□ 环境问题是否明确列出（env/版本/缓存/下游）？
□ ⭐ 失败后是否回到第 2 步（把新状态当输入）？
□ 证据表是否列出了五类及各自来源？
□ ⭐ 是否允许"证据足够就立刻委派"（不机械收集）？
□ 根因假设是否带置信度排序？
□ ⭐ 置信度接近时是否记下两个并说明可回退？
□ 修复计划是否三阶段（改动/验证/部署）？
□ ⭐ 验证后是否要求总结根因 + 改了什么 + 后续？
□ 是否提到加回归测试作为后续？
□ 是否检查了最近改动（git log / diff）？
```
