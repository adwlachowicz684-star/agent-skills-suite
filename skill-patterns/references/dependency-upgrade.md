# 依赖升级类技能

> 一个"看起来简单、实际坑极深"的领域。
> ⭐ 关键不是改版本号，是**证明没弄坏东西**。

## 真正的难点

```
改 package.json 里的版本号     —— 30 秒
证明这次升级没有破坏任何东西   —— ⭐ 这才是工作量的 95%
```

而且第二件事**不能靠"看起来没问题"**：

```
❌ "构建通过了，应该没事"
⭐ 构建通过 ≠ 行为没变
   ——尤其依赖的行为变更常常只在特定输入下触发
```

## 四步流程

**① 盘点**

```
□ 当前版本与目标版本
□ ⭐ 中间跨越了几个版本（跨越多，风险越大）
□ 这个依赖被哪些模块使用
□ 有没有被间接依赖（另一个包也依赖它）
```

> ⭐ 第三条常被跳过：
> **不知道谁在用，就无法评估影响范围。**

**② 查变更**

```
□ ⭐ CHANGELOG 里的 Breaking Changes
□ 废弃与移除的 API
□ 默认值的改变（⭐ 最危险——不报错）
□ 行为变化（返回值、边界处理）
```

**③ 改并验证**

```
□ 改版本号
□ ⭐ 跑完整测试套件（不是只跑构建）
□ ⭐ 跑依赖这个模块的所有下游测试
□ 检查类型错误
```

**④ 观察**

```
□ 灰度/预发环境跑一段时间
□ ⭐ 关注只在运行时才暴露的变化（性能、内存、日志量）
```

## 破坏性变更的判定

版本号的语义（SemVer）只是**声明**，不是保证：

```
MAJOR  可能有破坏性变更
MINOR  新增功能，向后兼容
PATCH  修复
```

⚠️ 但现实里：

```
□ ⭐ 很多包不严格遵守 SemVer
□ ⭐ "向后兼容"的 MINOR 也可能改变边界行为
□ 传递依赖的变化不在你的版本号里体现
```

所以判定的可靠方式不是看版本号，而是：

```
① 读 CHANGELOG 的 Breaking 段（即使 MINOR）
② ⭐ 看类型签名是否变化
③ ⭐ 跑测试（这是唯一真正可靠的）
```

## 不应该自动做的事

```
❌ ⭐ 自动升级 MAJOR 版本
❌ 自动升级并直接合并到主分支
❌ 跳过测试直接提交
❌ ⭐ 自动修改 lockfile 而不验证安装结果
❌ 忽略 peer dependency 冲突
```

> ⭐ 第一条最该强调：
> **MAJOR 升级需要人读变更说明并决策**，
> 它不是可以自动化的事。

## 输出格式

```
## 升级摘要
依赖：xxx  1.2.3 → 2.0.0（跨 1 个 MAJOR）

## ⭐ 破坏性变更
- `foo(a, b)` → `foo({a, b})`
  影响：src/api.ts:42、src/util.ts:17
- 移除 `bar()`，替代为 `baz()`

## 已做的修改
- [file:line] [改了什么]

## ⭐ 验证
- 单元测试：147 passed / 0 failed
- 类型检查：通过
- ⭐ 下游模块测试：全部通过

## ⭐ 需人确认
- 无法自动验证的行为变化（列出）
- 是否需要灰度观察期
```

> ⭐ 最后一节"需人确认"不能省——
> **自动化测试覆盖不到的地方，必须显式交给人**。

## 自查

```
[ ] ⭐ 盘点过"谁在用这个依赖"？
[ ] 读过 CHANGELOG（含 MINOR 的 Breaking 段）？
[ ] ⭐ 检查了默认值变化？
[ ] 跑的是完整测试套件，不是只跑构建？
[ ] ⭐ 下游模块的测试也跑了吗？
[ ] MAJOR 升级有人参与决策？
[ ] ⭐ 输出列出了"无法自动验证的行为变化"？
[ ] ⭐ 建议了灰度观察期？
```

## 一条通用原则

依赖升级适用于所有"改动外部依赖"的场景：
库升级、API 版本切换、基础设施变更、schema 迁移。

```
可自动化：盘点、查变更、改、跑测试、生成报告
必须留人：MAJOR 决策、无法验证的行为、上线时机
```

> ⭐ 而且**"证明了没弄坏"这件事，
> 必须有具体的证据清单**——
> 呼应 `grounding-verification.md`：
> **"我跑了测试"要写明跑了什么、结果是什么。**
