## 1. ⭐⭐⭐⭐ 三层骨架

```
① ⭐⭐⭐⭐⭐ 注册与发现层      —— ⭐ 解决"Agent 怎么找到你"
② ⭐⭐⭐⭐⭐ 能力抽象层        —— ⭐ 输入 Schema / 输出 Schema
③ ⭐⭐⭐⭐⭐ 执行与副作用管理层 —— ⭐ MCP 工具 / 外部系统 / 回滚与清理
```

```
Agent 任务规划层
      ↓
Skill 注册与发现层          ← 元描述：意图 + 前置 + 后置
      ↓
Skill 能力抽象层            ← 输入 Schema / 输出 Schema / 依赖声明
      ↓
Skill 执行与副作用管理层     ← MCP 工具 / 外部系统
```

> ⭐⭐⭐⭐⭐ 这套⭐ 骨架的⭐ 价值⭐ 在于⭐ 它⭐ 把⭐ 我们⭐ 此前⭐ 散落记录的⭐ 一堆事实
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 放进了⭐ 三个⭐ 明确的⭐ 位置。⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 对照一下：
> ```
> 我们已有的                        对应层
> ─────────────────────────────────────────
> description / 触发词 / 标签        → ① 注册与发现层
> ⭐ 输入契约 / 输出契约 / schema       → ② 能力抽象层
> ⭐⭐⭐ 依赖声明 / lockfile            → ②（并跨越到③）
> ⭐⭐⭐⭐⭐ 副作用 / 回滚 / 幂等 / 清理   → ③ 执行与副作用管理层
> ```
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ **这⭐ 说明⭐ 我们⭐ 此前⭐ 收集的内容⭐ 是完整的，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 但⭐ 缺少⭐ 一个⭐ 把它们⭐ 组织起来的⭐ 结构——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐ 而⭐ "结构"⭐ 恰恰是⭐ 规模化的⭐ 前提。**
>
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 这也⭐ 呼应了 `skill-refining/references/skill-scope-tiering.md` 里⭐ 那条
> "⭐ 无 category 拒绝注册"——⭐⭐⭐⭐⭐ ⭐⭐⭐ 那个⭐ "category"
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐ 正是⭐ 第 ① 层的⭐ 准入字段。

## 2. ⭐⭐⭐⭐⭐ 注册与发现层：三层筛选

> ⭐⭐⭐⭐⭐ **"⭐ 不是⭐ 写一段 description ⭐ 就完了。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ Agent ⭐ 做任务规划时，⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 是靠
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ **语义匹配 + ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 能力标签** ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐ 来筛选 Skill 的。"**

```
① ⭐⭐⭐⭐⭐ 领域标签
   ⭐⭐⭐⭐⭐ ⭐ 每个技能⭐ 至少：⭐⭐⭐⭐⭐ ⭐⭐⭐ 一个主标签 + ⭐⭐⭐⭐ ⭐⭐⭐ 两个辅助标签
   例：接口测试 · UI 验证 · 数据校验 · 性能压测

② ⭐⭐⭐⭐⭐ 意图描述（四段式）
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 是什么 + ⭐ 解决什么问题 + ⭐ 适用场景 + ⭐⭐⭐⭐⭐ ⭐⭐⭐ 不适用场景
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ **尤其"不适用场景"这一项，
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐ 直接决定 Agent 会不会滥用你的 Skill**

③ ⭐⭐⭐⭐⭐ 前置指纹
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ 声明执行这个技能需要哪些前置条件
   例："需要目标接口的 OpenAPI 文档已加载" · "需要登录态 Token 已缓存"
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ **Agent 在规划阶段就会检查前置是否满足，不满足就不调用**
```

> ⭐⭐⭐⭐⭐ 第 ③ 条⭐ 是⭐ 本轮⭐ 最值钱的⭐ 一条，⭐⭐⭐⭐⭐ ⭐⭐⭐ 因为⭐ 它⭐ 与⭐ 我们
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 已有的⭐ `skill-execution/references/preflight-gate.md`（STEP 0 前置门禁）⭐ 形成了⭐ 一个⭐ 漂亮的⭐ 分工：
> ```
> preflight-gate：⭐⭐⭐⭐⭐ ⭐⭐⭐ 技能⭐ 内部 ⭐ 检查前置（⭐ 已进入执行，失败则快速失败）
> ⭐⭐⭐⭐⭐ 前置指纹  ：⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ Agent 在 ⭐ 规划阶段 ⭐ 就排除（⭐⭐⭐⭐⭐ ⭐⭐⭐ 根本不调用）
> ```
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ **后者⭐ 更省——⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 它⭐ 避免了
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ "加载了、开始了、然后才发现缺东西"⭐ 这种
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐ 最差的⭐ 情况。**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 这⭐ 也⭐ 是"⭐ 把判断⭐ 前移"⭐ 的⭐ 又一个⭐ 实例
> （同族：⭐ 声明期预防 ⭐ 优于 ⭐ 运行时仲裁 —— `skill-orchestration/references/collision-arbitration.md`）。
>
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 而⭐ 第 ② 条⭐ 的⭐ 四段式⭐ 与⭐ 我们已有的
> ⭐⭐⭐⭐⭐ **"description 的 WHAT / WHEN / HOW / NOT / ALSO"**
> （`skill-triggering/references/description-by-collision-risk.md`）⭐ 高度重合，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐ 但⭐ 这里⭐ 多出了⭐ 一整块：⭐ **"是什么"**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐⭐ —— 即⭐ 一个⭐ 明确的⭐ 领域类别声明，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 而⭐ 那⭐ 正是⭐ 第 ① 层⭐ 标签的⭐ 文字形式。

## 3. ⭐⭐⭐⭐⭐ 元描述 = 意图 + 前置 + 后置

```
⭐⭐⭐⭐⭐ 元描述 = ⭐⭐⭐⭐⭐ ⭐ 意图 + ⭐⭐⭐⭐⭐ ⭐⭐⭐ 前置 + ⭐⭐⭐⭐⭐ ⭐⭐⭐ 后置
```

> ⭐⭐⭐⭐⭐ 这个⭐ 三段式⭐ 比⭐ 我们⭐ 常用的⭐ "WHAT/WHEN/HOW/NOT" ⭐ 更⭐ 结构化，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 因为⭐ 它⭐ 显式⭐ 包含了⭐ 两个⭐ 状态边界：
> ```
> 前置 → ⭐⭐⭐⭐⭐ ⭐⭐⭐ 调用前 ⭐ 世界必须是什么样（否则别调）
> ⭐⭐⭐⭐⭐ ⭐ 后置 → ⭐⭐⭐⭐⭐ ⭐⭐⭐ 调用后 ⭐ 世界会变成什么样（⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 副作用）
> ```
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ **"后置"⭐ 这一项⭐ 我们⭐ 此前⭐ 没有⭐ 单独⭐ 命名过**——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 它⭐ 散落在
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ "副作用技能必须 disable-model-invocation"
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐⭐ 与
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ "输出契约 / 产物可定位" ⭐ 这几条里，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐ 而⭐ 这里⭐ 给⭐ 它⭐ 一个⭐ 明确的⭐ 位置。
>
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 推论：⭐⭐⭐⭐⭐ **"前置 + 后置"⭐ 合起来
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 就是⭐ 一个⭐ 技能的⭐ 完整⭐ 副作用契约**——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这⭐ 与 `skill-execution/references/seven-contracts.md` 的
> "⭐ 从说明书到责任契约"⭐ 是⭐ 同一个⭐ 目标，⭐⭐⭐⭐⭐ ⭐⭐⭐ 只是⭐ 切分方式不同。

## 4. ⭐⭐⭐⭐ 能力抽象层

```
⭐⭐⭐⭐ 输入 Schema  ：JSON Schema
⭐⭐⭐⭐ 输出 Schema  ：结构化状态 + ⭐⭐⭐⭐⭐ ⭐⭐⭐ （产物定位信息）
⭐⭐⭐⭐⭐ 依赖声明    ：所需 MCP 工具 / ⭐⭐⭐⭐⭐ ⭐⭐⭐ 依赖哪些其他 Skill

> ⭐⭐⭐⭐⭐ 依赖声明那句⭐ 理由⭐ 说得⭐ 很硬：
> ⭐⭐⭐⭐⭐ **"⭐ 这是⭐ 编排的⭐ 基础。⭐⭐⭐⭐⭐ ⭐⭐⭐ 没有这个声明，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ Agent ⭐ 只能⭐ 盲目尝试，⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 效率和准确性⭐ 直接腰斩。"**
>
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这⭐ 与⭐ 我们已有的⭐ 两条⭐ 精确对应：
> ```
> `skill-orchestration/references/composition-patterns-types.md`：⭐⭐⭐⭐⭐ ⭐ 隐式依赖最隐蔽
>                                ⭐⭐⭐⭐⭐ ⭐⭐⭐ 单独测试看不出，⭐⭐⭐⭐⭐ ⭐⭐⭐ 只在生产"被单独调用"时暴露

> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ **三个来源⭐ 同一结论，⭐⭐⭐⭐⭐ ⭐⭐⭐ 而⭐ 这里⭐ 补上了
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐ 代价的⭐ 量化：⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ "直接腰斩"。**
>
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 还有一条⭐ 值得⭐ 单独⭐ 记：

## 5. ⭐⭐⭐⭐⭐ 执行与副作用管理层

```
测试 Skill 执行
    ↓
执行成功？——是——→ ⭐ 记录产生的数据
            ⭐⭐⭐⭐⭐ ⭐⭐⭐ 否——→ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 回滚 Skill
    ↓（两者都汇合到"任务结束时"）
⭐⭐⭐⭐⭐ ⭐⭐⭐ 调度清理 Skill
    ↓
⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 验证环境干净
```

> ⭐⭐⭐⭐⭐ 这张图⭐ 有⭐ 三个⭐ 我们⭐ 此前⭐ 没有⭐ 显式⭐ 画出来的⭐ 设计点：
>
> **① ⭐⭐⭐⭐⭐ 成功路径也要"记录产生的数据"**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 不是只记日志，⭐⭐⭐⭐⭐ ⭐⭐⭐ 而是⭐ 记录
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ "这次执行⭐ 产生了什么"——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 这是⭐ 清理的⭐ 依据。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 对照 `skill-execution/references/seven-contracts.md` 的
> "⭐ 产物不可定位 → ⭐⭐⭐⭐⭐ ⭐⭐⭐ 完成不可验证"：
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ **这里⭐ 更进一步——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 产物不可定位 → ⭐ 连清理都没法做。**
>
> **② ⭐⭐⭐⭐⭐ 失败路径是"回滚 Skill"，不是"报告错误"**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 把回滚⭐ 也建模成⭐ 一个技能
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ （⭐ 可组合、可测试、可被单独审查）
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这⭐ 与 `skill-execution/references/seven-contracts.md` 那条
> "⭐ 重试要区分'没写入' vs '已写入但回应丢失'，⭐⭐⭐⭐⭐ ⭐⭐⭐ 否则创建重复对象"
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐ 是⭐ 同一件事的⭐ 正向解法。
>
> **③ ⭐⭐⭐⭐⭐ 两条路径汇合后都要"验证环境干净"**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这是⭐ 一个⭐ 独立的⭐ 收尾步骤，⭐⭐⭐⭐⭐ ⭐⭐⭐ 且⭐ 有⭐ 验证——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐ **不是"清理了"就算，⭐⭐⭐⭐⭐ ⭐⭐⭐ 是"验证干净了"才算。**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 这⭐ 与 `skill-examples/references/judgment-branches-acceptance.md` 的
> "⭐ 少了验收，⭐⭐⭐⭐⭐ ⭐⭐⭐ agent 很容易用一句'已完成'糊过去"⭐ 同源。

## 6. ⭐⭐⭐⭐ 两个踩过的坑

**① ⭐⭐⭐⭐⭐ 不要拿测试用例标题当技能名**

```
❌ "验证用户登录接口返回 200"
✅ "接口测试"（主标签）+ 领域化的意图描述
```

> ⭐⭐⭐⭐⭐ 这条⭐ 与⭐ 我们已有的⭐ `skill-structuring/references/naming-conventions.md` 完全同源，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 但⭐ 这里⭐ 给出的是⭐ 一个⭐ 具体的⭐ 高频错误形态：
> ⭐⭐⭐⭐ **把"一次具体执行的标题"当成"一类能力的名字"。**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 判据可以是⭐ 我们那条⭐ 现成的：
> ⭐⭐⭐⭐⭐ **"能被两个以上场景复用才拆成技能，否则只是普通函数"**
> （`skill-interfaces/references/skill-data-passing.md`）——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 一个⭐ 名字里⭐ 带了⭐ 具体用例的⭐ 技能，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐ 多半⭐ 通不过⭐ 这条检验。

**② ⭐⭐⭐⭐⭐ 依赖声明缺失 → Agent 只能盲目尝试**

见第 4 节。⭐⭐⭐⭐⭐ ⭐⭐⭐ 一句话：⭐ **"效率和准确性直接腰斩"**。

## 速查

```
□ ⭐⭐⭐⭐ 三层骨架：① 注册与发现层（怎么找到你）② 能力抽象层（输入/输出 Schema）
   ③ 执行与副作用管理层（MCP/外部系统/回滚清理）
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这套骨架把散落的知识归位：description→① 契约→② 依赖→②③ 副作用→③
□ ⭐⭐⭐⭐⭐ 发现层三层筛选：⭐⭐⭐⭐⭐ ⭐⭐⭐ 领域标签（1 主 + 2 辅）·
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 意图描述四段式（是什么/解决什么/适用场景/⭐⭐⭐⭐⭐ ⭐⭐⭐ 不适用场景）
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 前置指纹（⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 规划阶段就检查，不满足就不调用）
□ ⭐⭐⭐⭐⭐ 前置指纹 vs preflight-gate：⭐ 前者在规划阶段排除（更省，根本不加载），
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ 后者在进入执行后快速失败 → ⭐⭐⭐⭐⭐ ⭐⭐⭐ 判断前移的又一实例
□ ⭐⭐⭐⭐⭐ 元描述 = 意图 + 前置 + 后置
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ "后置"此前没有单独命名 → ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 前置+后置 = 完整的副作用契约
□ ⭐⭐⭐⭐ 能力抽象层：⭐ 输入 Schema · ⭐⭐⭐⭐⭐ ⭐⭐⭐ 输出 Schema（含产物定位）·
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ 依赖声明（MCP 工具 + ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 依赖哪些其他 Skill）
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ 缺依赖声明 → Agent 盲目尝试 → "效率与准确性直接腰斩"
□ ⭐⭐⭐⭐⭐ 执行层三步：⭐⭐⭐⭐⭐ ⭐⭐⭐ 成功也要"记录产生的数据"（清理的依据）
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 失败走"回滚 Skill"（建模成技能=可组合可测试可单独审查）
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 两条路径汇合后"验证环境干净"（不是清理了算，是验证干净了才算）
□ ⭐⭐⭐⭐⭐ 两坑：⭐⭐⭐⭐⭐ ⭐⭐⭐ 别拿测试用例标题当技能名（判据：能被 2+ 场景复用吗）· 依赖声明缺失
```

**一句话**：

> ⭐⭐⭐⭐ **企业级技能库要分三层——注册与发现层（领域标签 + 四段式意图 + 前置指纹，让 Agent 在规划阶段就排除不满足前置的技能，而不是加载后再快速失败）、能力抽象层（输入输出 Schema + 依赖声明，缺了声明 Agent 只能盲目尝试、效率与准确性直接腰斩）、执行与副作用管理层（成功要记录产生的数据、失败走回滚技能、最后必须验证环境干净）。**
