## 1. ⭐⭐⭐⭐⭐ 三招

从"一大坨 system prompt"迁移到模块化技能库，实操顺序是固定的三步：

### 招一：依赖审计

> **列出每一条指令，问：它引用了自身之外的任何东西吗？**
> 有 → 它是耦合的。**先给这个耦合命名，再试图解决它。**

```
"按我们的规范处理"          → 耦合：规范在哪？
"参考上一轮的判断"          → 耦合：上一轮不一定存在
"用之前那个脚本"            → 耦合：哪个脚本？
```

> ⭐ **先命名再解决**——这一步常被跳过，于是你以为是"技能写不好"，
> 其实是依赖没拆干净。

这与 `dependency-resolution-conflicts.md` 那条
"隐藏依赖的特征症状是**时好时坏**"是同一件事的两个面：
一个讲检测信号，一个讲处理动作。

### 招二：自包含重写

> ⭐⭐ **把每项能力重写成"假设加载进一个冷上下文、没有任何会话历史"的规格。**
> 它必须自己说清：**做什么 · 期望什么输入 · 它负责哪些决定 · 什么算完成。**

```
❌ "按上次的方式处理"（依赖历史）
✅ "输入：一个 .xlsx 路径。输出：三张汇总表。
    你负责决定：缺失值填 0 还是剔除（见决策表）。
    完成标志：三张表都写到 <输入名>_summary.xlsx。"
```

## 2. ⭐⭐⭐⭐⭐ 拆分判据：重写需要几份文档

> ⭐⭐⭐ **如果重写需要超过一份文档，那很可能是两个技能在假装成一个——拆开。**

这是我们收到的**第四个拆分判据**，也是唯一一个从"重写产物"倒推的：

| 判据 | 问法 | 出处 |
|---|---|---|
| 重启测试 | 跑到一半失败，人从哪重启？ | `granularity-atomic-workflow.md` |
| 双向无知 | 两个技能都需要知道对方细节吗？ | `skill-dependency-injection.md` |
| 业务动作 | 能独立完成一个有意义的业务动作吗？ | `four-pitfalls-practice.md` |
| ⭐ **重写体积** | **自包含重写需要几份文档？** | 本份 |

四条互补：前三条从"运行时行为"判断，这一条从"写下来有多大"判断——
而后者**在你还没跑过一次时就能用**。

## 3. ⭐⭐⭐⭐ 调用契约

> ⭐⭐ **没有清晰触发条件的技能，要么从不加载（能力缺失），
> 要么总是加载（延迟加载彻底失效）。**
> **契约让调用变成确定性的。**

契约三件套与我们的 `seven-contracts.md` 完全对应，这里给最小版本：

```
触发条件：用户说出 X / 命中 Y 类文件
输入：    什么格式，缺了怎么办
完成：    什么算做完（可验证，不是"已完成"）
```

> ⭐⭐ 第二条特别容易漏：**"缺了怎么办"**。
> 没写的后果是模型即兴发挥一条回退路径
> （`preflight-gate.md` 的 MUST NOT ③）。

## 4. ⭐⭐⭐⭐⭐ 诊断法：抽一个出来试试

这是本份最值钱的一条：

> ⭐⭐⭐ **从你当前 agent 的 system prompt 里挑一个工具/能力，
> 试着把它重写成一个自包含的、有调用边界的技能。
> 如果它不能被干净地隔离出来——你找到了真正的架构问题。**

它的价值在于**诊断不需要改任何东西**：

| 结果 | 说明 |
|---|---|
| 干净地抽出来了 | 这项能力本来就该是技能 |
| ⭐ 抽的过程中不断要引用别的段落 | ⭐ 依赖关系本身就是病灶 |
| 抽出来后触发条件写不出来 | 它不是"按需能力"，是常驻规则 |

> ⭐⭐ **第三种结果最容易被误判**——
> 你会以为是自己描述写得不好，其实它压根不该做成技能
> （`worth-skillifying.md` / `when-not-to-use-skill.md`）。

## 5. ⭐⭐⭐ RAG 与技能不是替代关系

一句话分清：

```
RAG     回答：⭐ "关于这个，我知道些什么？"
Skills  回答：⭐⭐⭐ "此刻，我该怎么精确执行这个任务？"
```

| | RAG | 技能 |
|---|---|---|
| 单位 | 文本块 | ⭐ 完整能力规格 |
| 时机 | 每次查询 | ⭐ 能力被调用时 |
| 风险 | 检索到的块拼不起来 | 触发不准 |

> ⭐⭐⭐ **上下文工程不是"把更多东西塞进窗口"，
> 而是"对什么留在外面保持自觉"。**

顺带一个可直接引用的数字对比（同来源的会话启动预算表）：

```
全量预加载：20000 / 20000 已用（窗口占满）
渐进式：     3500 / 20000 已用（剩 16500）
```

这与我们已有的三个数字（50 技能省 96%、启动 8K 占 4%、L1 30–50 token）
是**第四个独立来源**——四个口径都落在同一个数量级结论上。

## 6. ⭐⭐⭐ 最不舒服的发现

> ⭐⭐⭐ **多数团队最终会发现的那个不舒服的事实是：
> 他们的问题从来不是检索质量。**
> **他们的指令是当成散文写的，不是当成规格写的。**

这句可以直接当作整套库的题眼：

| 散文 | 规格 |
|---|---|
| "先大致看看结构" | "读 src/ 下所有 *.ts，输出文件数与总行数" |
| "注意性能问题" | "标出 N+1 查询、循环内的 I/O、未加索引的 WHERE" |
| "尽量保持一致" | "字段名一律 snake_case" |

⭐ **反转测试**（反过来读也说得通 → 空话）在这里有了一个更硬的替代问法：
**这条指令能被机器判定通过/失败吗？**
