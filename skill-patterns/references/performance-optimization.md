## 四阶段：测量 → 诊断 → 优化 → 验证

```
scientist（测量） → architect（诊断） → executor（优化） → scientist（验证）
```

**执行策略**：

```
模式        顺序执行（不可跳步）
证据门槛    ⭐ 每次优化必须给出可度量的改进（前后数字）
范围        ⭐ 只修头号瓶颈——不要一次优化所有东西
安全        ⭐ 优化前后都要跑基准
```

**阶段 1 基线测量**：

```
□ 确定测什么（运行时 / 内存 / I/O / 网络）
□ ⭐ 跑 3 次取中位数
□ 用合适的工具 profil
  Python   cProfile · py-spy · memory_profiler
  Node.js  --prof · clinic.js · 0x
  Shell    time · strace -c · hyperfine
□ 找出累计时间/内存的前三个热点
```

**基线输出格式**（固定字段，便于对比）：

```
操作：[测了什么]
中位耗时：X ms（n=3，stddev=Y）
热点：[函数/文件:行] — X% 总耗时
     [函数/文件:行] — Y%
     [函数/文件:行] — Z%
内存峰值：X MB
```

**阶段 4 验证**（最关键的一步）：

```
□ ⭐ 跑与阶段 1 完全相同的基准
□ 对比：耗时改进（百分比与绝对值）· 内存影响 · ⭐ 正确性
□ ⭐ 改进 <5% → 回滚（不值得这点复杂度）
□ 改进 ≥5% → 保留并报告
```

## 瓶颈分类法

> ⭐ **诊断阶段要给瓶颈归类**，因为不同类的解法完全不同：

| 类型 | 特征 |
|---|---|
| **算法** | 本可 O(n) 却是 O(n²) |
| **I/O 密集** | 阻塞读、缺缓存、本可并行却串行 |
| **内存** | 大分配、缺清理、数据结构选错 |
| **网络** | ⭐ N+1 查询、缺批处理、同步调用 |
| **并发** | 锁竞争、GIL、线程饥饿 |

> ⭐ 呼应 `skill-crafting` 的 `guidance-forms.md`：这是 `if <可观察谓词> then` 的典型用法——
> 先归类，再选对应的解法，而不是笼统地"优化一下"。

**常见优化手段**（按类对应）：

```
□ 向量化操作替代循环
□ 缓存重复计算结果
□ 预编译正则表达式
□ ⭐ 模型单例化，避免重复加载
□ 异步调用 + 超时与重试
□ 上下文管理器确保资源释放
□ 避免全局变量存大量数据
```

## 五个常见陷阱

> ⭐ **这份清单是整章最实用的部分**：

| ❌ 错 | ✅ 对 |
|---|---|
| 只 profile 一层（如只查数据库，假定它是瓶颈） | ⭐ **profile 整条管线**（下载→解压→解析→写入） |
| 串行派 agent（跑完一个再跑下一个） | ⭐ **一条消息里并行 spawn 所有 agent** |
| 不 profile 就优化（"先调数据库配置"） | ⭐ **先 profile**——可能数据库只占 4% |
| 只做 P0（最高收益也最高成本） | ⭐ **顺手把 P2 快赢做了**（1.3x 只花 4–8 小时） |
| 改完不重新 profile，假定有效 | ⭐ **重跑验证**，确认达到预期改进 |

**三个操作细节**：

```
□ ⭐ 测量前跑 3–5 次预热，否则结果波动
□ 内存 profile 要加 tracemalloc
□ ⭐ 重测前清缓存、重启服务——否则看到的是缓存效果
```

## 回滚规则：低于 5% 就撤

> ⭐ **这条规则把"要不要保留这次改动"从争论变成计算**：

```
改进 <5%  → 回滚（复杂度不值）
改进 ≥5%  → 保留并报告
```

**保留/回滚的输出格式**：

```
优化前：X ms 中位
优化后：Y ms 中位
改进：Z%（节省 X-Y ms）
内存影响：[相同/更好/更差]
正确性：[已验证/发现回归]
判决：KEEP / REVERT
```

**停止条件**：

```
□ 已验证有可度量改进 → 保留并报告
□ 无改进 → 回滚并报告发现
□ ⭐ 头号热点在外部代码（库、系统调用）→ 报告并给绕行建议
□ 用户取消
```

**好与坏的对照**（放进技能当示例非常有效）：

```
✅ 好（数据驱动）
   基线：/leads 端点中位 2.3s
   热点：models/lead.py:47 的数据库查询，占 89%（循环里的 N+1）
   优化：批量查询 SELECT ... WHERE id IN (...)
   之后：中位 180ms，改进 92% → KEEP

❌ 坏（过早优化）
   "把所有 import 改成懒加载"
   → ⭐ 没有基线测量，没有证据表明 import 是瓶颈 → REJECT
```

## 一个反直觉的真实案例

> ⭐ **这个案例值得整段记住，它演示了"假设驱动"的代价**：

```
场景：管线 47K rows/sec，目标 100K（低 53%）

优化前的假设：
  "QuestDB ILP 写入是瓶颈"
  → 准备调数据库配置、优化 Sender API

5 个 agent 并行调查后的实际发现：
  Profiling Agent    ⭐ CloudFront 下载占 90%（857ms）
                     ILP 写入只占 4%（40ms）
  Config Agent       数据库已是最优，调参 <5% 提升
  Client Agent       Sender API 已是最优
  Batch Size Agent   44K 批大小已在最优区间

结论：
  ⭐ 优化下载，而不是数据库
  P0 并发多标的下载（10–20x）
  P1 多月管线并行（2x）
  P2 流式 ZIP 解压（1.3x）

⭐ 结果：避免了在数据库上浪费 2–3 周——
        而数据库实际能以 1.1M rows/sec 写入（比目标快 11 倍）
```

> ⭐ **教训**：
> **"瓶颈在哪"是一个必须测量的问题，不是一个可以讨论的问题。**
> 呼应 `skill-crafting` 的 `grounding-verification.md` 与 `data-engineering-skills.md` 的
> "先写契约/先测量，别先动手"。

