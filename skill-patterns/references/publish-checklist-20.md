## 1. 评分方法

```
每条按 0–2 分打分：
  0 = 完全没做
  1 = 做了一部分
  2 = 做得很到位

⭐ 总分 28 分以上（满分 40）才建议发布
⭐ 低于 22 分就得回炉
```

## 2. ⭐ 二十项

| # | 检查项 | 说明 |
|---|---|---|
| 1 | 名称唯一且具体 | ⭐ 不是"日志处理"，而是 `nginx-error-log-analyzer` |
| 2 | description 写了触发场景 | 含"当用户提供…并要求…"句式 |
| 3 | description 未写功能堆砌 | 没有"用于处理数据"这类空话 |
| 4 | ⭐ **有明确的 when not to use** | ⭐ 至少 2 条不该使用的情形 |
| 5 | 输入信息有明确来源 | 告诉模型从哪获取：路径、对话还是命令输出 |
| 6 | 输入格式有说明 | 支持的文件类型、编码、格式要求 |
| 7 | 步骤按执行顺序排列 | ⭐ 编号清晰，跨步骤依赖要标注 |
| 8 | ⭐ **每个步骤有可检查的产出** | 每步末尾有明确的中间产物描述 |
| 9 | ⭐ **确定性操作已脚本化** | ⭐ 解析、统计、格式化没让模型自由发挥 |
| 10 | 各步骤有回退兜底 | 文件缺失、命令失败时有明确提示或备选路径 |
| 11 | 关键约束集中列出 | 输出格式、命名规范、禁止事项有单独小节 |
| 12 | 模板和样例已放 resources | 有完整范例，不是口头描述 |
| 13 | 资源文件大小可控 | ⭐ 单文件不超过几十 KB，避免上下文膨胀 |
| 14 | 脚本有参数校验 | 不传参、传错参时给出清晰错误 |
| 15 | 脚本异常有兜底 | 文件不存在、权限不足、空输入不崩溃 |
| 16 | 脚本输出格式稳定 | ⭐ CSV/JSON 等结构化格式，字段固定 |
| 17 | ⭐ **allowed-tools 已收紧** | 没有给模型多余权限 |
| 18 | 版本号已更新 | 有 version 字段，迭代时递增 |
| 19 | 有最小自测用例 | tests 目录下至少一条可执行输入样例 |
| 20 | ⭐ **已经用真实场景回放过** | ⭐ 至少用 1 份真实输入跑通过整个流程 |

## 3. ⭐ 两条最容易被忽略的

> ⭐ **第 4 条（when not to use）和第 9 条（确定性操作脚本化）。**

理由非常实在：

```
没有"不做什么"清单 → ⭐ 技能会变成到处乱插手的刺头
确定性操作不脚本化 → ⭐ 跑一次一个样，根本没法持续使用
```

> 前者对应 `scope-section.md` 的边界章节；
> 后者对应 《skill-scripting》`scripts-as-production.md` 的核心论点。
> **这两条恰好也是我们自己校验器会报错的项**。

## 4. 另一份精简版（九项）

适合快速过一遍：

```
[ ] 目录名与 SKILL.md 中的 name 一致
[ ] ⭐ description 描述触发场景，并列出排除场景
[ ] 正文步骤可被模型执行，不依赖看不见的外部状态
[ ] 关键输出格式已有示例
[ ] 脚本依赖写入 requirements.txt / package.json
[ ] ⭐ 所有文件使用相对路径，或通过配置注入根目录
[ ] ⭐ 敏感信息不写入技能文件，API Key 一律走环境变量
[ ] ⭐ 已用一个正面请求和一个负面请求测试
[ ] ⭐ 修改后重启 Agent，并确认加载成功
```

> ⭐ 最后一条很关键：
> **改完不重启就测试，测的是缓存里的旧版本**
> （与 `skill-structuring` 的 `frontmatter-pitfalls.md` 的平台缓存问题一致）。

## 速查

```
□ 总分 ≥28 才发，<22 回炉
□ ⭐ 第 4 条 when not to use（≥2 条）
□ ⭐ 第 9 条 确定性操作脚本化
□ 每步有可检查产出
□ ⭐ allowed-tools 收紧
□ ⭐ 用真实输入回放过全流程
□ 改完重启再测
□ 密钥走环境变量，不写进文件
```

**一句话**：

> ⭐ **没有"不做什么"清单，技能就会变成到处乱插手的刺头。**
