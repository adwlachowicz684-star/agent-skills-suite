## 1. ⭐ 六步创建法

```
① 明确场景     —— 收集具体使用示例
② 选择模式     —— ⭐ 根据任务特点选结构（见 structure-modes-abcde）
③ 写 Description —— ⭐ 最关键，决定触发
④ 写核心流程   —— SKILL.md 正文
⑤ 补充资源     —— references / scripts / assets
⑥ 测试迭代     —— ⭐ 实际使用并优化
```

> ⭐ 第 ② 步排在第 ③ 步之前很重要：
> **先决定文件怎么组织，再写 description**——
> 否则容易写出一个"什么都往 SKILL.md 里塞"的技能。

---

## 2. ⭐ 每一步的检查点

| 步 | 检查点 |
|---|---|
| ① 场景 | ⭐ 能举出 3 个真实使用例子吗？举不出说明还不值得做 |
| ② 模式 | 属于 A–E 哪一种？目录结构定了吗？ |
| ③ Description | ⭐ 含 WHAT + WHEN + 关键词？有"不用于 X"吗？ |
| ④ 流程 | 每步有可检查的产出吗？有回退吗？ |
| ⑤ 资源 | 确定性操作脚本化了吗？references 有加载触发吗？ |
| ⑥ 测试 | ⭐ 用真实输入跑过吗？正例+负例都测了吗？ |

## 3. ⭐ 五阶段学习路径

这是一条很实在的进阶路线，每阶段都有明确的练习：

| 阶段 | 练习 | 学到的 |
|---|---|---|
| ① | ⭐ 写一个只有一个 Markdown 文件的知识型技能 | 技能的骨架 |
| ② | ⭐ 把团队的"部署规范"或"安全审查规范"整理成技能目录 | ⭐ **技能不一定要有脚本** |
| ③ | 封装工具型技能：把每月要做的日志检查写成技能，加脚本和验证用例 | 脚本 + 验证 |
| ④ | ⭐ 尝试多个技能路由 | ⭐ 观察描述相近时会不会选错，学会用边界规则和关键词区分 |
| ⑤ | 引入动态检索和评测体系 | ⭐ 此时你已知道哪些高频、哪些偶发，优化才有依据 |

> ⭐ 第 ② 阶段的练习特别好：
> 它直接破除"技能必须有脚本"的误解——
> **把规范文档整理成技能目录，本身就是一个完整有效的技能**。

> ⭐ 第 ④ 阶段对应 `namespace-collision.md` 的遮蔽问题——
> **只有真的装了多个相近技能，才会体会到它**。

---

## 4. 两条最实用的建议

**① 从最小文件开始**

> ⭐ **对初学者最有价值的练习不是照抄一份复杂技能，
> 而是把日常工作里最常被询问的一次排查过程，
> 整理成一个只有一个 Markdown 文件的知识型技能。**

**② 难点不在语法**

> ⭐ **Agent Skills 的难点从来不是语法，
> 而是如何把业务经验写得清晰、可执行、可验证。**

## 速查

```
□ 六步：场景 → 模式 → description → 流程 → 资源 → 测试
□ ⭐ 模式在 description 之前定
□ ⭐ 场景阶段能举出 3 个真实例子
□ ⭐ 学习从"单文件知识型技能"起步
□ ⭐ 规范文档本身就能成为一个技能（不需要脚本）
□ ⭐ 多技能路由要实测（遮蔽问题）
□ ⭐ 难点是把经验写清楚，不是语法
```

**最小可跑的模板**（5 行就能跑）：

```yaml
---
name: commit-writer
description: 根据 git 暂存区生成符合 Conventional Commits 规范的提交信息。
  当用户说"写 commit"、"提交信息"或在 git commit 前自动调用。
---
```

```
1. 跑 git diff --staged 看暂存改动
2. 判断主类型：feat / fix / refactor / docs / chore / test
3. 输出格式：type(scope): description（祈使句）
4. 复杂改动加一段正文说明 why（不写 what）
5. 破坏性变更加 BREAKING CHANGE: 脚注
```

> ⭐ 注意第 4 条：**body 写 why 不写 what**——
> what 从 diff 就能看出来，why 才是需要说明的。
