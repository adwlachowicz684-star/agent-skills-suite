# 代码评审的信任层

> ⭐ **评审意见的价值 ≈ 发现问题的能力 × 你相信它的程度。**
> 多数自动化评审死在第二个因子上。

## 信任是怎么丢的

自动化评审失去信任，几乎总是同一个过程：

```
① 报了一个明显错误的问题（误报）
② 开发者花了时间确认它是错的
③ ⭐ 第二次、第三次
④ 之后所有评审意见都被自动忽略
```

> ⭐ **信任是乘法关系**：
> 几次误报之后，**真问题也会被一并忽略**。
> 这比"没有评审"更糟——它消耗了注意力却没产生价值。

## 三层信任

```
① 可验证    每条意见都能被独立确认
② 可操作    说清"改成什么"，不只说"这不好"
③ ⭐ 可解释 说清"为什么这是问题"
```

三层都做到，开发者才会认真看。

## 让意见可验证

**① ⭐ 必须带 file:line**

```
❌ "认证部分有问题"
✅ "auth/session.ts:42 未校验 token 过期时间"
```

> 没有位置的意见无法被验证，只能被相信或忽略。

**② 引用具体证据**

```
❌ "这里可能有竞态"
✅ "handler 在第 12 行读取 state，第 20 行才写回，
    期间没有其他同步；并发调用会互相覆盖"
```

**③ ⭐ 给出"如何确认"**

```
✅ "把并发数设为 10 重跑这个用例，会看到计数少于 10"
```

> 这一条是信任的核心：
> **让开发者能自己复现，而不是必须相信你。**

## 分级：别把 NOTE 当 BLOCK

标准三级：

```
BLOCK   ⭐ 合并前必须修
WARN    应该修
NOTE    可以考虑
```

> ⭐ **分级错误的代价不对称**：

```
把 NOTE 报成 BLOCK  → 阻塞流程，消耗信任
把 BLOCK 报成 NOTE  → ⭐ 真问题被忽略
```

后者更危险，但**前者更常见**——
因为"报得多"看起来像"审得仔细"。

两条硬规则：

```
□ ⭐ 每条 BLOCK 必须附带具体的修复建议
□ ⭐ 存在任何安全问题 → 一律 BLOCK，不允许 APPROVE
```

第二条是安全评审的底线：**不能有"有安全问题但总体通过"这种结论**。

## 不该自动做的事

```
❌ 自动应用修复（评审应该是分析，不是行动）
❌ 自动 approve
❌ ⭐ 对没跑过的验证做"应该没问题"的推断
```

第三条呼应 `grounding-verification.md`：
**"我看了代码，应该能过"不是验证。**

配套的一条：

```
✅ 没发现问题时，明确说"APPROVE，已检查：X / Y / Z"
```

> ⭐ **"没发现问题"要说明检查了什么**——
> 否则读者不知道它是"查过没有"还是"没查"。

## 一个完整输出格式

```
PR Review: [title]

Summary
[2–3 句概述改动]

Findings
BLOCK  [file:line] [描述]
       Fix: [具体建议]
WARN   [file:line] [描述]
       Fix: [具体建议]
NOTE   [file:line] [描述]

Verdict: APPROVE / CHANGES_REQUESTED / BLOCK
[一句话理由]
```

这个格式的关键：

```
□ ⭐ Summary 限定 2–3 句——防止用概述代替判断
□ Findings 按严重度分组，不是按文件顺序
□ ⭐ 每条 BLOCK/WARN 都有 Fix
□ Verdict 一句话，不带含糊
```

## 信任的修复

如果评审已经失去信任，怎么恢复：

```
① ⭐ 短期：把所有 NOTE 降为"评论"，不再出现在阻塞列表
② 中期：统计误报率，把高频误报的规则删掉
③ ⭐ 长期：每条意见都带"如何确认"，让信任可重建
```

第 ② 条值得强调：
**删掉一条会误报的规则，比让它继续报更划算**——
即使它偶尔抓到真问题。

## 自查

```
[ ] 每条意见都带 file:line？
[ ] ⭐ 每条都说了"如何确认"？
[ ] 每条 BLOCK 都有具体修复建议？
[ ] ⭐ 分级准确吗（宁可 WARN 也不要 BLOCK 泛滥）？
[ ] 有安全问题就一律 BLOCK？
[ ] ⭐ 没发现问题时说明了检查了什么？
[ ] 没有对未执行的验证做推断？
[ ] 输出是结构化的（不是一整段散文）？
```
