## 三条核心纪律

**① 命名与幂等**

```
□ ⭐ 强制带时间戳的迁移文件名
□ ⭐ 幂等的 UP/DOWN SQL——可以安全地多次应用
```

**② 零停机 Expand-Contract**

```
□ ⭐ 重命名和破坏性变更必须走
   Expand → Migrate → Transition → Contract
□ 避免锁表与停机
```

**③ 关注点分离与回滚**

```
□ ⭐ DDL 与 DML 必须分成不同文件
□ ⭐ 每个迁移都要有显式的 rollback / downgrade 实现
□ ⭐ 禁止在 main 分支上直接做破坏性操作
```

## Expand-Contract 四阶段

```
1. Expand（扩展）
   加新结构，不改旧的
   例：加一个可为 NULL 的新列

2. Migrate（迁移）
   ⭐ 单独的 DML 回填数据
   例：把旧列的值分批回填到新列

3. Transition（切换）
   应用改为写新结构
   例：应用同时写旧列和新列 / 只写新列

4. Contract（收缩）
   ⭐ 移除旧结构
   例：删掉旧列
```

> ⭐ **为什么重名列要用这四步**：
> 直接 `ALTER TABLE ... RENAME` 会让正在运行的应用
> 在切换瞬间找不到列——而四阶段让新旧结构**共存一段时间**。

呼应 `database-sql-skills.md` 的安全迁移四步法与
**大表直接 ALTER 会锁表**的警告。

## 完整用例

```
目标：给表加一个列并切换过去

1. 加一个可为 NULL 的列        ← DDL 迁移
2. 写独立的 DML 回填            ← ⭐ 单独的数据迁移
3. 应用切换到写新列             ← 应用改动
4. 在 contract 阶段移除旧列     ← DDL 迁移
```

**要点**：

```
□ 第 1 步和第 2 步是不同文件
□ ⭐ 回填要分批，不要一个事务吃掉整表
□ 第 4 步必须等确认应用已完全不读旧列
```

## 已合并迁移不可改

> ⭐ **已合并的迁移文件是不可变的；
> 修改它们会破坏幂等与回滚的一致性。**

```
❌ 直接编辑 main 分支上已合并的迁移
❌ 不走 expand-contract 就做破坏性操作

✅ ⭐ 永远向前加新的迁移，不回头改旧的
```

**为什么**：

```
□ 别人已经跑过这个迁移了
□ 改了文件 = 他们的数据库状态与文件不再对应
□ ⭐ 这正是幂等被破坏的典型方式
```

**FAQ 式的判定**（这类技能很适合用问答形式写）：

```
Q：如何在生产关系库上做零停机迁移？
A：用 expand-contract 分阶段应用 schema 变更，避免锁表。
   加可为 NULL 的列、单独回填、切换应用写入、
   在 contract 阶段移除旧列。

Q：为什么 DDL 和 DML 要分成不同文件？
A：⭐ 防止锁冲突，并确保安全的回滚路径。
   两者独立执行，让 expand 和 migrate 阶段可靠且可逆。

Q：修改已合并迁移文件的限制是什么？
A：⭐ 已合并的迁移不可变；直接编辑会破坏幂等与回滚一致性。
```

## 为什么这类技能要写死流程

对照自由度校准（**`skill-crafting`** 的 `guidance-forms.md`）：

```
任务脆弱性：⭐ 极高（错了就是生产事故）
→ 该给：精确脚本 + 严格步骤清单
→ 不该给：松散的自然语言启发式
```

**这类技能的三个特征**：

```
1. ⭐ 步骤顺序不可交换（先 expand 再 contract）
2. ⭐ 每一步都有独立的失败模式（锁表、数据不一致、应用报错）
3. ⭐ 回滚不是"撤销"，是另一个显式流程
```
