## 1. ⭐⭐⭐⭐⭐ 一个能直接推翻做法的实验

fanout 实验给了个很干净的对照：

```
同一组字段、同一个 API，两种写法：

A ⭐⭐⭐ 过度具体：把字段名硬编码进技能
B ⭐⭐⭐⭐⭐ 只写通用方法：读 schema、数行数、按结构遍历

结果：迁移到另一个数据集时
  A ⭐⭐⭐ 效果"明显变差"
  B ⭐⭐⭐⭐⭐ 表现不变
```

> ⭐⭐⭐⭐⭐ **过度具体化的代价不在当前任务，在迁移时——
> 而迁移前你完全看不到它。**

> ⭐⭐⭐⭐⭐ 这才是最关键的一点：
> **A 在第一次跑的时候看起来更好**（更精确、更确定），
> ⭐⭐⭐⭐⭐ 只有等到数据集变了才暴露——
> 而那时你不会归因于"当初写得太具体"。

官方团队的另一句直接给出了原则：

> ⭐⭐⭐⭐⭐ **避免 railroading：给目标和约束，不是每一步。**
> ⭐⭐⭐⭐ 理由很硬：**技能可复用性越高，过度具体化的代价越大。**

## 2. ⭐⭐⭐⭐⭐ 先探测，不先写

跟"不要写约束"表面冲突，其实是同一层次的两半：

```
❌ 不要写"数据长什么样"（会过期）
✅ ⭐⭐⭐⭐⭐ 要写"怎么查出数据长什么样"（不会过期）
```

> ⭐⭐⭐⭐⭐ 这是整套库里反复出现的同一手法：
> **把静态事实换成获取该事实的方法。**

已出现五次，全部同构：

| 场景 | 不要写 | ⭐⭐⭐⭐⭐ 要写 |
|---|---|---|
| 环境细节 | `/Users/me/proj/...` | 运行时探测 |
| 端口 | `8080` | 从配置读 |
| 数据规模 | "约 100 条" | 先数行数 |
| ⭐⭐⭐⭐⭐ 字段结构 | "用 `user_id` 字段" | 先读 schema |
| 上游产物 | "读 `analysis.json`" | 先检查是否存在 + 校验 |

> ⭐⭐⭐⭐⭐ 统一判据：**这句话会在什么条件下变成错的？**
> 如果能想到任何一个 → 它应该是一个探测动作，而不是一句声明。

## 3. ⭐⭐⭐⭐ 四条反具体化规则

**① ⭐⭐⭐⭐⭐ 先跑一次看数据，再决定怎么写**

```
不要："表有 user_id、created_at、amount 三列"
要：  "先读表头，确认列名与类型，再决定取哪些"
```

> ⭐⭐⭐⭐⭐ 这条最该抄，因为它同时解决了三个问题：
> 字段名变化、字段缺失、字段含义漂移。
> 而写死字段名，这三个全都会静默失败。

**② ⭐⭐⭐⭐⭐ 用结构，不用名字**

```
不要："取第 3 列"
不要："取 amount 列"   ← 只是换了种死法
要：  "取数值型列中名称为金额语义的那列"
```

> ⭐⭐⭐⭐ 中间那行值得注意：**"取第 3 列"和"取 amount 列"
> 是同一种错误**——一个依赖位置，一个依赖命名，都会变。

**③ ⭐⭐⭐⭐ 数量用探测，不用常量**

```
不要："处理 100 条记录"
要：  "先数总数，按实际数量分批处理"
```

> ⭐⭐⭐⭐ 这条与"规模假设"那条是同一个坑的两种表述：
> **写死数量在样本小的时候完全正确，只在变大时崩——
> 而那往往发生在生产。**

**④ ⭐⭐⭐⭐ 输出格式用契约，不用样例**

```
不要："输出像这样的表格：[具体样例]"
要：  "输出符合 schema.yaml 的结构"
```

## 4. ⭐⭐⭐⭐⭐ 三层拆分：通用 / 领域 / 项目

一个真实对照很有说服力：

```
❌ "从我最近的提交生成变更日志"
   → 每个项目的日期范围、格式规范都不同 → 每次都要重写

✅ 拆成三个技能：
   ① recent-commits     —— 查什么（通用）
   ② changelog-format   —— 怎么格式化（通用）
   ③ repo-onboarding    —— ⭐⭐⭐⭐⭐ 项目特定的日期范围与规范
```

> ⭐⭐⭐⭐⭐ **关键是第三条**：
> 项目特定的知识不是"污染"，
> 但⭐⭐⭐⭐⭐ **它必须是独立的一层**，这样通用部分才能真的通用。

这与 `portability-across-projects.md` 那条
"组织耦合集中到一个标记为'本项目特有'的章节"是同一结论，
只是那份是**章节粒度**，这份是**技能粒度**——
⭐⭐⭐⭐ **两层都要做**：先在一个技能内分区，规模大了再拆成技能。

一个判据能决定什么时候该从"分区"升级到"分技能"：

> ⭐⭐⭐⭐⭐ **如果"项目特有"那一节占了全文 30% 以上，就该拆出去。**

## 5. ⭐⭐⭐⭐⭐ 可迁移性自检

零成本方法：

```
⭐⭐⭐⭐⭐ 改一个词测试：
把技能里的项目名 / 工具名 / 系统名全部替换成 "X"，
再读一遍——还通顺吗？
```

三种结果：

| 结果 | ⭐ 判断 |
|---|---|
| 完全通顺，意思不变 | ⭐⭐⭐⭐⭐ 通用部分，可迁移 |
| 出现"X 系统的特殊规则" | ⭐⭐⭐⭐⭐ 项目特有部分——应集中到第 4 节那一层 |
| ⭐⭐⭐⭐⭐ 读不通 | ⭐⭐⭐⭐⭐ **它依赖的东西没有被写出来**（隐式耦合） |

> ⭐⭐⭐⭐⭐ 第三行是这份最有价值的产出：
> **读不通，说明有一处依赖你脑子里知道、但技能里没写。**
>
> 这与 `assumption-registry.md` 里"假设不写'不成立时'比不写更糟"
> 是同一类问题——只是那个是显式的，这个是连作者都没意识到的。

## 6. ⭐⭐⭐⭐ 例外：什么时候该写死

不是所有具体化都错。三条例外：

**① ⭐⭐⭐⭐⭐ 已知的、会变化的坑（Gotchas）**

```
"这个接口在月结期间会静默返回上个月的数据"
```

> ⭐⭐⭐⭐⭐ 必须写死——因为⭐⭐⭐⭐⭐ **它不可推理**，
> 探测不出來。这正是 Gotchas 章节存在的原因。

**② ⭐⭐⭐⭐ 有明确约定的项目规范**

```
"提交信息必须用 conventional commits"
```

> ⭐⭐⭐⭐ 这是"约定"不是"事实"——它不会因为环境变了而错，
> 只会因为人改主意而变。所以写死是对的（但要标 `review_after`）。

**③ ⭐⭐⭐⭐⭐ 安全红线**

```
"禁止读取 ~/.ssh/id_rsa"
```

> ⭐⭐⭐⭐⭐ 必须绝对写死，不能"探测"。
> ⭐⭐⭐⭐ 因为探测意味着"可能不存在禁止"——
> 而安全边界不能依赖运行时发现。

> ⭐⭐⭐⭐⭐ 判据一句话：
> **会变的东西不要写死，不会变的东西不要探测。**
> 而⭐⭐⭐⭐ 判断"会不会变"的根据是——
> 它是**事实**（会变）还是**约定**（人定的，只有人改才变）。
