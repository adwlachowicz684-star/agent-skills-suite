## 为什么文案方法论是绝佳范例

> 文案领域有**几十年沉淀的、命名明确的框架**（AIDA、PAS、BAB、4Ps、4Us、FAB、ACCA…）。
> 这类"已有成熟方法论"的领域，正是技能最该发挥的地方：

```
□ 方法论本身是稳定的（不随版本变）
□ ⭐ 但模型不会"默认知道该用哪个框架"
□ 而且"用好框架"和"知道框架"是两回事
```

> 呼应 `skill-selection` 的 `skill-vs-rag.md`：**程序性知识（How-to）走技能**。
> 文案公式正是典型的 How-to，不是 What。

**技能的完整形态**：

```
□ 公式清单（每个含：是什么 / 何时用 / 示例）
□ ⭐ 公式选择表（给 agent 的路由规则）
□ 反模式清单（含"为什么"与"改用什么"）
□ 工作流（人 / AI 各做什么）
```

## 公式选择表 = 决策树

> ⭐ **这是整份技能里最有价值的部分**——
> 它把"模型自己猜"变成"按可观察条件路由"。
> 呼应 `skill-crafting` 的 `guidance-forms.md` 的 `if <可观察谓词> then`。

| 情境 | 最佳公式 |
|---|---|
| 冷受众 | AIDA、ACCA |
| 已意识到问题 | PAS |
| 推荐语 / 案例 | BAB |
| 产品功能 | FAB |
| 标题 | 4Us |
| 销售页 | 4Ps |
| 快速钩子 | 1-2-3-4 |

**四个常用公式的展开**：

```
AIDA     注意 → 兴趣 → 欲望 → 行动
         适用：从广告到落地页的任何转化型文案

PAS      问题 → 放大 → 解决
         适用：受众已意识到问题

BAB      之前 → 之后 → 桥梁
         适用： testimonials、案例、转型故事

4Ps      承诺 → 描绘 → 证明 → 催促
         适用：长销售页、 webinar 推介

4Us      紧迫 + 独特 + 有用 + 极具体
         适用：标题、主题行、钩子

FAB      特性 → 优势 → 利益
         适用：产品描述、功能发布

ACCA     认知 → 理解 → 确信 → 行动
         适用：教育型内容、复杂产品
```

## 每个公式的写法

> ⭐ **统一的四段结构**——这本身就是 `skill-authoring` 的 `patterns.md`
> 讲的"决策树 + 按需加载"里每个分支的写法：

```
#### Name        <公式名>
#### Description <一句话：做什么>
#### When        <⭐ 何时用——可观察条件>
#### Example     <完整示例>
```

**实例**（注意 `When` 是可观察的，不是形容词）：

```
Name        Feature-Advantage-Benefit
Description 从特性出发，讲清优势，落到利益
When        写产品描述或功能文案时
Example     F: 256 位加密
            A: 你的数据受与银行同级的保护
            B: 所以你可以放心分享敏感文件，不必担心泄露
```

**4Us 的示例写法特别值得学**——它用**递进的弱→强对照**：

```
弱：           "How to Improve Your Marketing"
+有用：        "How to Get More Customers"
+紧迫：        "How to Get More Customers This Week"
+独特：        "The Counterintuitive Way to Get More Customers"
+极具体（最佳）："How I Got 247 Customers in 7 Days Using Only Twitter"
```

> ⭐ **这种"逐级变好"的示例，比单个完美示例教得多。**
> 呼应 `skill-authoring` 的 `examples.md`：**示例是 agent 理解"你要什么形状"的最快通道。**

**另一条基础原则也该编码进去**：

```
One Reader, One Message
描述：写给一个具体的人，讲一件具体的事
何时：永远——这是所有好文案的地基

❌ "我们的平台帮助团队更好地协作"
✅ "你受够了 Slack 消息石沉大海。用 Threads，
    每段对话都有自己的位置，你再也不用问'那条在哪来着？'"

秘诀：写给一个人（疲惫的 PM），
     讲一个问题（消息丢失），
     给一个方案（会话线程）
```

## 反模式该怎么编码

> ⭐ **这里是本文与 `skill-crafting` 的 `guidance-forms.md` 直接对接的地方。**

一个成熟实现里的反模式写法是三段式：

```
Name         特性倾倒
Description  罗列特性而不翻译成利益
Why          客户不在乎它"做什么"，在乎"对他们意味着什么"
Instead      ⭐ 每个特性都要接一句 "所以你可以…" 或 "这意味着…"
```

> ⭐ **必须有 `Why` 和 `Instead`**——
> 只写"不要倾倒特性"是禁令，模型不知道该做什么；
> 给出 `Instead` 才是配方。
> 这正是 `skill-crafting` 的 `guidance-forms.md` 那张"失败形态 → 该用什么"表的实证。

**另外两条**：

```
Name         企业套话
Why          "利用协同效应的革命性方案"——等于什么都没说
Instead      ⭐ 用小学六年级的词汇。你奶奶听不懂就重写。

Name         试图显得聪明
Why          复杂的文案制造摩擦
Instead      短句、具体的词
```

> ⭐ 注意 `Instead` 里那句判据——**"你奶奶听不懂就重写"**——
> 它是一个**可执行的操作性判据**，而不是"要简洁"这种形容词。
> 呼应 `skill-authoring` 的 `writing-style.md`：形容词对模型等于没有约束。

**人机协作流程**（也值得编码）：

```
阶段 1 人类策略  定义价值主张、目标受众痛点、语气与约束（仅人类）
阶段 2 AI 生成   5–10 个标题变体、正文草稿、CTA 变体
阶段 3 人类筛选  挑最好的元素、组合、补品牌细节、核对事实
阶段 4 AI 打磨   语法与清晰度、可读性、SEO 关键词
阶段 5 人类终审  最终批准、法务合规、品牌一致性

比例：30% 人类思考 · 40% AI 生成 · 30% 人类打磨
```

> ⭐ **把"哪些步骤只能人做"显式写出来**——
> 这是很多技能漏掉的关键边界（法务合规、事实核对）。

## 可迁移的六条

不管你的领域是不是文案，这套编码方式都可以直接搬：

**① 找到领域里"已命名的方法论"**

```
□ 有名字的框架比无名经验更容易被模型检索与对齐
□ ⭐ 引用公认来源（TDD、DDD、红绿重构、AIDA）
  ——给 agent 一个连贯的心智模型，也给用户一个验证设计的途径
```

**② 为每个方法论写"何时用"**

> ⭐ **没有 `When` 的方法论清单等于没写**——
> agent 不知道该选哪个，就会随机选或全用一遍。

**③ 做成选择表，而不是罗列**

```
□ 情境 → 该用哪个
□ ⭐ 这是把"模型判断"变成"查表"
```

**④ 示例用"弱→强递进"**

```
□ 单个完美示例不如一组递进示例
□ ⭐ 递进示例展示了"好"的梯度，模型才知道边界在哪
```

**⑤ 反模式必须带 `Why` + `Instead`**

```
□ Why     ——让模型理解约束的理由（禁令要带理由）
□ Instead ——给出正面配方（否则禁令会反噬）
```

**⑥ 显式标出"只能人做"的步骤**

```
□ 法务合规、事实核对、最终批准
□ ⭐ 漏掉这条，技能会越权完成本该人做的判断
```

## 自查

```
□ 领域里是否已有命名的方法论（有则直接编码，不要自己发明）？
□ 每个方法论是否都写了 When（可观察条件）？
□ 是否做成了"情境 → 选哪个"的选择表？
□ 是否用了弱→强递进的示例？
□ 反模式是否都有 Why + Instead？
□ ⭐ 是否显式标出了"只能人做"的步骤？
□ 是否给出了人机协作的阶段划分？
□ 是否避免了形容词式约束（"要简洁"）而改用了操作性判据？
□ 是否引用了方法论的公认来源？
□ 每个公式的示例是否完整（而非只给骨架）？
```
