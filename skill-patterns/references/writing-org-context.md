## 六类最适合的高价值场景

> ⭐ **判断一个场景值不值得做成技能，看它是否落在以下六类**：

### ① 周报 / 月报 / 项目汇报生成

```
痛点
□ 汇报频率高但信息密度低
□ ⭐ 结构固定却每次重写
□ ⭐ 多数据源拼装成本高（项目系统 / 代码仓库 / 会议纪要）
□ 不同人输出风格差异大，管理者阅读成本高

技能的价值
□ 固化检查顺序与判断标准
□ 降低人为疏漏概率
```

### ② 固定结构写作与文档模板

```
常见文档类型
□ 产品需求文档（PRD）
□ 技术方案 / RFC
□ ⭐ 事故复盘与复盘报告
□ 内部技术分享材料

技能的价值
□ 统一结构与逻辑顺序
□ ⭐ 明确"每一部分该回答什么问题"
□ 提升文档的决策支持能力
```

### ③ 强组织语境与内部知识依赖类

```
场景特征
□ 强依赖公司内部的定义、规则与共识
□ ⭐ 脱离组织语境，通用模型输出失真
□ ⭐ 一致性比创造性更重要
```

> ⭐ **第三类是判断标准**：
> 如果一致性比创造性重要 → 做成技能；
> 如果要的是创意 → 别做，会束缚它。

### ④ 品牌调性与内容规范

```
痛点：对外表达风格割裂 · 术语口径不统一
     · ⭐ 禁用表达靠口口相传 · 新人学习成本高

技能包含
□ 语气与风格基准
□ ⭐ 统一术语表
□ ⭐ 禁用词与风险表达
□ 标准示例库
```

> ⭐ **"禁用表达靠口口相传"这个痛点点得很准**——
> 这正是隐性知识显性化的典型场景。

### ⑤ 团队工程与协作规范

```
覆盖范围
□ Commit 信息规范
□ PR 描述模板
□ 工程目录与命名规范
□ 代码风格与最佳实践
```

### ⑥ 业务口径与指标定义

```
痛点：同一指标多种解释 · 报表对不上结论
     · 新人理解成本高 · 数据决策缺乏可信基础

技能的优势
□ ⭐ 固化指标定义
□ ⭐ 明确计算逻辑与边界条件
□ 统一数据解释方式
```

## 固定结构写作

> ⭐ **技能要写的是"每一部分该回答什么问题"，不只是"有哪些章节"**：

```
□ 统一结构与逻辑顺序
□ ⭐ 明确每一部分回答什么问题
□ 提升文档的决策支持能力（而非格式好看）
```

**以 PRD 为例**（详见 `pm-skills.md`）：

```
问题陈述 → 目标与成功指标 → 用户故事 → 需求 → 技术考量
→ 设计要点 → ⭐ 风险与缓解 → 发布计划 → ⭐ 待决问题
```

---

## 品牌调性与内容规范

**四件必须写清的事**：

```
1. 语气与风格基准
   ⭐ 要给出"好的输出"与"不好的输出"对比
   ——呼应 what-not-to-do.md 的坑 5：
     "输出要简洁"是主观的，agent 会理解成"只写一句话"

2. ⭐ 统一术语表
   同一个东西只能有一个叫法

3. ⭐ 禁用词与风险表达
   例如：不用"最""第一"等绝对化表述（视行业与法域）

4. 标准示例库
   ⭐ 一两份干净范例远胜几十个杂乱例子
```

## 业务口径与指标定义

> ⭐ **这类技能解决的是"报表对不上结论"这个高频痛点**：

```
每条指标定义必须含
□ 指标名（唯一）
□ ⭐ 计算逻辑（可执行的公式或 SQL 片段）
□ ⭐ 边界条件（什么算、什么不算）
□ 数据来源（哪张表 / 哪个系统）
□ ⭐ 常见误读（这条最有价值）
```

```
□ 固化指标定义
□ 明确计算逻辑与边界条件
□ 统一数据解释方式
```

> ⭐ 呼应 （领域实例库·已归档） 的 `data-analytics.md` 的"换个问法答案就变"——
> 业务口径不固化，同一个问题每次答案都不同，信任就崩了。

## 多资源协同的复杂生产任务

> ⭐ **这一类技能更接近"轻量自动化系统"**：

```
场景特征
□ 仅靠提示词不稳定
□ ⭐ 需要脚本、模板、示例协同
□ 输出质量要求高且可复用
```

```
典型形态
  SKILL.md        编排逻辑
  scripts/        确定性处理（提取、校验、渲染）
  assets/         模板
  references/     术语表、口径、示例库
```

## 一句话总结本质

> ⭐ **Skills 的本质不是"工具升级"**：
> **把个人经验转化为组织可复用的生产力资产。**

**判断要不要做的三个问题**：

```
□ 这个任务结构是否固定？（固定 → 适合）
□ ⭐ 一致性是否比创造性重要？（是 → 适合）
□ 是否依赖只有你们组织知道的语境？（是 → 尤其适合）
```

## 自查

```
□ 是否落在六类高价值场景之一？
□ ⭐ 是否判断过"一致性 vs 创造性"这个分水岭？
□ 固定结构写作是否说明了"每部分回答什么问题"？
□ 品牌规范是否含四件事（语气/术语表/禁用词/示例库）？
□ ⭐ 禁用词是否写死了具体词（而非"注意措辞"）？
□ ⭐ 是否有"好输出 vs 坏输出"的正反例对比？
□ 指标定义是否含计算逻辑与边界条件？
□ ⭐ 是否列出了"常见误读"？
□ 多资源任务是否用齐了 scripts/ + assets/ + references/？
□ 是否明确了数据源拼装的来源清单？
□ 是否避免了把"要创意"的任务也做成技能？
□ 示例是否克制（一两份干净范例，而非几十个）？
```
