> 采购类技能的核心难题：**不同供应商的回答无法直接比较**

## 0/3/5 打分制

> ⭐ **每问只打三个值，按证据强度而非满意度。**

```
0 = 缺失、含糊，或是营销话术
3 = 部分证据，有文档但不完整
5 = ⭐ 强证据、具名客户、可衡量的承诺
```

**强/弱回答的对照**（这是这类技能最有价值的部分）：

以"审计留痕"为例：

```
✅ 强回答：
   具名格式（如不可变 JSONL、一次写入存储），
   明确时长（受监管行业 ≥7 年），
   客户可按需导出

❌ 弱回答：
   "审计轨迹可按需提供"
```

以"透明度报告"为例：

```
✅ 强：是，且公开链接了最近 3 年的报告
❌ 弱：否（⭐ 不必然淘汰，但是一个区分项）
```

> ⭐ **"弱回答不必然淘汰但要记录"这个判定很关键**——
> 否则打分会退化成一票否决清单。

## 期望分布

```
10 问 × 5 分 = 单维度满分 50
各维度按权重加权 → 0–100 总分

⭐ 老实打分的话，多数供应商首轮落在 35–55
⭐ 70 以上在当前这代 agentic AI 供应商里很罕见
```

> ⭐ **"35–55 是正常区间"这句话本身很重要**：
> 没有它，评分者会把 45 分误判成"这家不行"。

```
45 分在某些品类里可能仍是最好的选择
⭐ 在签约前知道差距在哪，才能去谈缓释承诺
```

呼应 `ab-testing-growth.md`（**（领域实例库·已归档）**）那条：
**指标要配解读规则**，否则会被反向误读。

## 红旗清单

> ⭐ **以下任一命中即默认淘汰——但应触发"记录在案的例外"，
> 而不是机械拒绝。**

```
🚩 "从未有客户从我们平台迁移走"
   供应商成立超过 3 年 → 统计上不可能，
   ⭐ 说明它不追踪或不披露流失

🚩 拒绝披露其所依赖基础模型的训练数据来源
   （不是客户自己的微调数据，那是合理受限的）

🚩 没有公开的漏洞披露 SLA
   说明没有成熟的披露流程

🚩 "我们的 ROI 案例是专有的，无法外部验证"
   ⭐ 供应商在主张它不愿让买方验证的生产力提升

🚩 调价通知期 <30 天
   说明它保留在合同期内实质性重新定价的权利，
   ⭐ 与多年期企业协议不相容
```

> ⭐ **"红旗 ≠ 自动拒绝，而是默认淘汰 + 需记录的例外"**
> ——这个双段设计比一票否决更实用，也比"酌情考虑"更严格。

呼应 `hr-recruiting-skills.md` 与 `legal-contract-skills.md` 的同一条风格：
**红线要可判定，且要有例外路径**。

## 委员会流程：先冷评分

```
阶段 1  发给入围供应商，固定答复窗口（通常 3–4 周）
        ⭐ 窗口短反而有利——偏向那些有预写答案的供应商，
           而"有预写答案"本身就是运营成熟度的信号

阶段 2  ⭐ 在任何供应商电话会议之前完成内部评分
        ⭐ 电话会引入偏见——先冷评分
        每个维度两名评审，分歧在评审会上解决

阶段 3  对 top 2–3 做技术/安全审查
        书面证据与客户推荐、安全问卷交叉核对

阶段 4  ⭐ 针对低于 3 分的每个维度，要求合同承诺
        （SLA、路线图条目、退出条款）在签约前补上缺口
        ⭐ 愿意在这里谈判的供应商，通常能活过 18 个月的治理周期
```

> ⭐ **"先冷评分再开会"** 呼应 `eval-roles.md`（**`skill-evaluating`**）
> 的 Comparator 双盲设计——**同一条防偏见原则**。

## 两条方法论

**① 能力矩阵选型会得出错误的采购结论**

```
❌ 按功能勾选表比较 → 选出功能最多但部署形态不匹配的
✅ ⭐ 先定部署形态：
    工程主导 / SaaS 优先 / LangChain 栈原生 / 研究级（评测用）
   再在该形态内比较
```

**② 这份 RFP 不替代通用 SaaS RFP**

```
□ 通用 RFP：uptime、席位定价、SSO、支持
□ 本 RFP：⭐ 六个 agent 特有的治理维度
□ ⭐ 两者并行跑，分别打分，综合决策
```

**结构规则**：

```
60 问分六个维度，每维 10 问
维度 1 治理成熟度（含评测工具问题）
维度 5 供应商锁定（含可观测性问题）
```

## 可迁移的做法

不管评估什么（供应商、工具、框架），这四点都能用：

```
1. ⭐ 打分用 0/3/5，按证据强度而非主观满意度
2. ⭐ 给出强/弱回答的具体对照样例
    ——"弱"的标准比"强"更能帮评审者对齐
3. ⭐ 给出期望分布，防止把正常区间误判为不合格
4. ⭐ 红旗是"默认淘汰 + 需记录的例外"，不是一票否决
```
