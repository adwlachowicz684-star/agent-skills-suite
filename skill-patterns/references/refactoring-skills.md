## 1. 定位与边界

**做什么**：在不改变外部行为的前提下改善代码质量与结构。
专精设计模式、SOLID、防腐层（ACL）。

**该用**：

```
提升可读性与可维护性
消除重复与复杂度
拆分过大的类/函数
引入合适的抽象层
为新功能做准备
遗留代码迁到现代模式
```

⭐ **Do NOT invoke when**（这条边界很值得抄）：

```
添加新功能          → 先重构，再加；用对应的领域技能
调试运行时错误      → 用 debugger
审查安全            → 用 security-auditor
优化性能瓶颈        → 用 performance-engineer
```

> ⭐ 这条"不做什么"清单的价值在于**防止技能被误用于它不擅长的场景**，
> 且每个都指向了正确的替代——这正是 `guidance-forms.md` 说的
> "NOT for X → 用 Y 代替"是最强的路由提示。

## 2. 代码味道 → 重构手法对照表

| 味道 | 症状 | 重构 |
|---|---|---|
| 重复代码 | 同样逻辑重复 | 提取方法/类、模板方法模式 |
| 过长函数 | >20 行 | 提取方法、分解条件 |
| 过大的类 | >200 行 | 提取类、单一职责 |
| 依恋情结 | 用别类的数据多 | 移动方法到合适的类 |
| 基本类型偏执 | 什么都用字符串 | 引入值对象 |
| 霰弹式修改 | 改一处要动多处 | 把相关变更聚到一起 |
| 发散式变化 | 一个类因多种原因改 | 按职责拆分 |
| 过长参数列 | >3 个参数 | 用对象/builder |

> ⭐ **这类"味道 → 手法"表是重构类技能的核心资产**——
> 它把"模型自己猜"变成查表，与 `methodology-skills.md` 的公式选择表同理。

## 3. 三个核心工作流

### ① 安全重构循环（最基础）

```
确保有充分的测试覆盖
确定要解决的具体味道
应用最小可能的重构步骤
跑测试验证行为未变
提交
重复直到味道消除
```

> ⭐ **每一步都要提交**——保持可回退。

### ② 引入模式

```
识别重复出现的结构性问题
选合适的设计模式
⭐ 在既有代码旁边创建新结构（不是替换）
增量迁移调用方
移除旧实现
记录模式的使用原因
```

第三条是关键——**并行存在再迁移**，不是原地改。

### ③ 防腐层（ACL）实现

```
识别系统/领域之间的边界
为内部领域定义干净接口
创建适配/转换层
⭐ 所有跨边界调用都走 ACL
内部模型独立演进
```

## 4. 质量指标线

| 指标 | 阈值 |
|---|---|
| 圈复杂度 | 每函数 < 10 |
| 嵌套深度 | 最多 3 层 |
| 函数长度 | 建议 < 20 行 |
| 文件长度 | 建议 < 300 行 |

> ⭐ **这些数字让"质量"变成可自动检查的谓词**，
> 与设计系统技能的"无裸 hex"是同一手法。

**成功判据**：

```
✅ 所有测试通过（无行为变化）
✅ 代码更可读
✅ 复杂度降低（行数更少、逻辑更简单）
✅ 重复被消除（DRY）
✅ 测试覆盖率维持或提升
✅ 性能不变或更好
✅ 无回归
```

## 5. 反模式

| 反模式 | 正解 |
|---|---|
| ⭐ 大爆炸式重构 | 增量 + 绞杀者模式 |
| ⭐ 无测试就重构 | ⭐ **先补特征化测试** |
| 过度设计 | 模式只在需要时用 |
| 边加功能边重构 | ⭐ **重构提交与功能提交分开** |
| 忽略团队约定 | 对齐既有代码风格 |

第二条和第四条最常犯：
**没有安全网就动手**，以及**重构和功能混在一个提交里**（无法回退）。

## 6. 何时停手

```
测试开始频繁失败（太激进）
代码"够好了"（完美是完成的敌人）
截止日期临近（先提交已有的）
没有可衡量的收益（边际递减）
只是在调风格（没有改善结构）
```

> ⭐ **"你只是在调风格，而不是改善结构"**——
> 这条自我检查非常实用，能防止无意义的 churn。

## 速查

| 场景 | 处置 |
|---|---|
| 函数太长 | 提取方法，每步提交 |
| 重复 | 提取共享工具，更新调用点 |
| 无测试 | ⭐ 先补特征化测试 |
| 要加新功能 | 先重构提交，再功能提交 |
| 跨系统集成 | 防腐层 + 干净内部接口 |
| 改不动了 | 检查是否只是在调风格 |
