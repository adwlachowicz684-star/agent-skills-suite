## 1. ⭐ 两个基本类比

```
⭐ 技能 ≈ 纯函数
⭐ 智能体 ≈ 微服务
```

> ⭐ 整个系统构成一个**依赖图**，
> 受制于那些让软件可维护的同一批原则。

> ⭐ 一句收口：
> **"技能是函数，智能体是服务。
> 把软件从单体推向微服务的那批力量，正在把 AI 从单体提示词
> 推向组合式的技能-智能体系统。"**

## 2. ⭐ 十三条原则映射

| 软件原则 | 软件含义 | ⭐ 技能/智能体等价物 |
|---|---|---|
| 原子性 / SRP | 一个类一个职责 | ⭐ **一个技能一个用途** |
| 开闭原则 | 扩展不改原有 | ⭐ **渐进式披露：reference 文件扩展而不动 SKILL.md** |
| 里氏替换 | 实现可安全互换 | ⭐ 任何 "search" 技能可在另一个 search 技能的位置工作 |
| 接口隔离 | 不强制依赖 | ⭐ `DEPENDENCIES.md`；Always/OnTrigger/Never 分层 |
| 依赖倒置 | 依赖抽象而非具体 | ⭐ **"搜索知识库" 而非 "用这些 flag 调 qmd"** |
| 组合优于继承 | 由部件构建 | ⭐ **串联/分层技能；智能体团队由专家组成** |
| 松耦合 | 相互依赖最小 | ⭐ 技能显式声明依赖；智能体边界清晰 |
| 高内聚 | 相关逻辑在一起 | ⭐ 所有知识库搜索逻辑在一个技能里，不散落 |
| DRY | 不重复 | ⭐ **Barrel 模式元技能消除重复的上下文加载** |
| 幂等 | 可安全运行两次 | ⭐ 同样输入产出同样结构 |
| 契约式设计 | 显式接口 | ⭐ **技能声明输入预期与输出形状** |
| 快速失败 | 尽早发现错误 | ⭐ **技能在工作前检查前置条件** |
| 约定优于配置 | 合理默认值 | ⭐ 一致的技能/智能体目录结构，减少样板 |

**几个特别值得单说的**：

**开闭原则 → 渐进式披露**：

```
⭐⭐ 这是整个技能机制最优雅的对应：
   想扩展技能的能力，加一个 reference 文件即可，
   ⭐ 不用改 SKILL.md 一个字。
```

**依赖倒置 → 说意图不说工具**：

```
❌ "用 --flags 这些参数调用 qmd"
✅ ⭐ "搜索知识库"
```

> ⭐ 与 `protocol-layering.md` 的"技能是协议无关的纯 Markdown"同源：
> **绑定到具体工具会让技能随工具变化而失效。**

**快速失败 → STEP 0 前置门禁**：

> 与 `preflight-gate.md` 完全对应：**在工作前检查前置条件**，
> 而不是跑到一半才发现缺东西。

**结构类比**（帮助记忆）：

```
npm 包/模块          → 带 SKILL.md 的技能目录
Barrel 文件(index.ts) → ⭐ 元技能：一次加载一簇依赖
TypeScript interface → 技能的输入/输出契约
微服务                → 带配置文件的智能体
服务网格 + 服务发现   → 智能体注册表 + 路由
```

## 3. ⭐⭐ 两张图

这是这份文档最有用的部分——**两个图是不同的东西**：

```
⭐ 技能依赖图：
   ⭐ 有向无环图（DAG），技能依赖 0..n 个其他技能
   ⭐ 共享依赖的技能形成"簇"
   ⭐ 簇用 barrel 元技能来加载共享上下文

⭐ 智能体协作图：
   有向图，智能体之间委派、审查、交接
   ⭐⭐ 与技能不同：技能通过"依赖"组合，
        ⭐ 智能体通过"协作"组合
   ⭐ 协作的智能体簇形成"团队"
```

> ⭐⭐ **关键区别一句话**：
> **"技能靠依赖组合，智能体靠协作组合。"**
>
> 这解释了为什么技能依赖要防环（DAG），
> 而智能体之间的委派/审查可以是双向的（有向图允许环）。

## 4. ⭐ 组合的四种模式

```
① 技能串联（chaining）
   一个技能的输出喂给下一个
   "搜索笔记" → "总结结果" → "写草稿"

② 技能选择（selection）
   智能体根据任务选哪个技能（技能级路由）

③ 技能分层（layering）
   ⭐ 高层技能编排若干底层技能
   例："发布 newsletter"技能编排多个子技能

④ ⭐ 桶模式（Barrel）
   元技能隐藏一簇依赖的复杂度
```

**组合的四个收益**（这是为什么要做组合）：

```
复用   —— "读取笔记"可被代笔、研究、维护三个智能体共用
可维护 —— ⭐ 更新一个技能，改善所有用到它的智能体
可测试 —— ⭐ 小技能比大单体提示词更容易验证
灵活   —— ⭐ 用现有技能以新方式组合出新的智能体，不必从零写
```

## 5. ⭐⭐ 组合带来的四个新问题

> ⭐ 这是"组合不是免费的"那一面，也是多数文档不写的部分。

```
① ⭐ 依赖冲突
   两个技能可能假设了不兼容的上下文或约定

② ⭐ Token 爆炸
   组合多个技能会超出上下文预算

③ ⭐⭐ 顺序敏感
   ⭐ 技能加载顺序会影响行为

④ 版本兼容
   更新一个技能可能破坏那些把它和其他技能组合使用的智能体
```

**各自的应对**：

| 问题 | 应对 |
|---|---|
| 依赖冲突 | ⭐ 显式声明输入/输出契约（契约式设计） |
| Token 爆炸 | `context-budget-math.md` 的预算算术 + 桶模式 |
| ⭐ 顺序敏感 | ⭐ 显式写交接协议（`skill-chaining-composition.md` 的四步） |
| 版本兼容 | 语义化版本 + `dependency-lockfile.md` 的 pin |

> ⭐ 第 ③ 项最容易被忽略：**同一个技能集，加载顺序不同结果就不同**。
> 这与 `scale-effects.md` 的"遮蔽"是同一族问题——
> **组合让每件事都变成多体的**。

**可组合性的五个前置条件**（缺一个就组合不起来）：

```
□ 清晰接口：技能声明需要什么输入、产出什么输出
□ ⭐ 最小耦合：技能能独立工作，⭐ 不假设其他技能已加载
□ 渐进式披露：先摘要，需要时才加载细节
□ 一致的目录结构（约定优于配置）
□ 幂等：同样输入产出同样结构
```

> ⭐ 第二条是硬约束：**技能不假设其他技能已加载**——
> 否则它就无法被单独复用，也就失去了组合的意义。

## 速查

```
□ ⭐ 技能 ≈ 纯函数；智能体 ≈ 微服务
□ ⭐ 开闭原则 → 加 reference 扩展，不动 SKILL.md
□ ⭐ 依赖倒置 → 说意图（"搜索知识库"）不说工具（"调 qmd"）
□ ⭐ 快速失败 → STEP 0 前置门禁
□ Barrel 元技能 = index.ts，消除重复加载
□ ⭐ 技能声明输入预期 + 输出形状（契约式设计）

两张图：
□ ⭐ 技能依赖图 = DAG（要防环）
□ ⭐ 智能体协作图 = 有向图（允许环）
□ ⭐⭐ 技能靠依赖组合，智能体靠协作组合

四模式：串联 / 选择 / 分层 / 桶模式
四收益：复用 / ⭐改一处改善全部 / 可测试 / 灵活

⭐ 组合的代价：
□ 依赖冲突 → 显式契约
□ Token 爆炸 → 预算算术 + 桶模式
□ ⭐⭐ 顺序敏感 → 显式交接协议
□ 版本兼容 → semver + pin

□ ⭐ 可组合的前提：技能不假设其他技能已加载
```

**一句话**：

> ⭐⭐ **更新一个技能，改善所有用到它的智能体——
> 这是组合最大的收益，也是组合最大的风险来源。**
