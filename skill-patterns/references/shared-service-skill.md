## 1. ⭐⭐ 两种受众，两套规则

| | 给用户的技能 | ⭐ 共享服务技能 |
|---|---|---|
| 调用者 | 人 / 主 agent | ⭐ 另一个技能 |
| description 写给谁 | ⭐ 用户会输入的话 | ⭐⭐ "被其他技能调用时" |
| 输入 | 自然语言也可以 | ⭐ 必须结构化 |
| 输出 | 可以给报告 | ⭐⭐ 必须机器可解析 |
| 失败 | 可以说"没找到" | ⭐⭐ 必须返回明确错误，不能沉默 |

> ⭐⭐ 最关键的一行是 description：**共享服务技能的 description
> 不该写"当用户想格式化 JSON 时"，
> 而该写"当被其他技能调用来格式化 JSON 时"。**
>
> 这不是措辞讲究——⭐ **它决定了这个技能会不会在用户直接提问时被误触发**。
> 一个 utility 技能被用户直接触发通常不是你想要的结果
> （它只会做一半的事）。

## 2. ⭐⭐⭐ 三条硬规则

**① ⭐⭐ 总是返回有效输出或明确的错误信息**

```
❌ 找到就输出，找不到什么都不说
✅ ⭐⭐ "Always return valid JSON output or clear error messages."
```

> ⭐⭐⭐ 为什么这条是硬的：**共享服务技能位于链条中间**。
> 它沉默一次，整条链就在中间断掉，
> 而上游看到的只是"下游没给我东西"——⭐ **极难定位**。
>
> 这与 `script-cli-contract.md` 的"失败必须诚实（非 0 退出）"是同一条原则，
> 只是载体从脚本换成了技能。

**② ⭐ 输入输出契约必须钉死**

```
输入：接受原始 JSON 或 JSON 字符串
输出：2 空格缩进美化 / 校验并报告错误 / 可选压缩
```

**③ ⭐⭐ 只做一件事，且不含业务语义**

```
✅ json-formatter：格式化并校验 JSON
❌ invoice-json-formatter：格式化发票 JSON（并把发票规则写进去）
```

> ⭐⭐ 第二条尤其重要：**一旦掺入业务语义，它就只能被那一条链用**。
> 这跟 `gamedev-skill-routing.md` 的
> "学科技能拥有可移植概念，代码部分让给引擎技能"是同一种切法。

## 3. ⭐ 什么时候该造一个

```
□ ⭐ 同一个确定性操作在⭐ 两条以上链里重复出现
□ ⭐ 它的输出会被上游继续解析（不是给人看的）
□ ⭐ 你希望它⭐ 可以被替换（换实现不影响上下游）
```

**反例**（不该造）：

```
❌ 只在一处使用——直接内联或写成脚本
❌ 需要判断力——判断交给主技能，共享服务只做机械操作
```

> ⭐ 第二条呼应 `seven-anti-patterns-scale.md` 的"过度脚本化"：
> ⭐ **判断步骤留在 markdown，机械步骤才下沉**。
> 共享服务技能也适用——**它是机械的那部分**。

## 4. ⭐ 常见的漏项

```
① ⭐ 忘了写"被其他技能调用时"——结果被用户直接触发
② ⭐ 没有错误输出——链条静默断裂
③ ⭐ 掺入业务语义——复用性归零
④ ⭐ 输出里混了说明文字——上游解析失败
   （呼应 script-cli-contract.md 的"stdout 只放结果"）
⑤ ⭐⭐ 版本变了没通知依赖方——⭐ 与 `deprecation-compat-strategy.md`
   的"跨版本循环依赖"同源
```

> ⭐⭐ 第 ④ 条是技能形态特有的坑：
> 脚本有 stdout/stderr 分离的物理约束，
> **技能没有——它只有一段输出**，所以必须在正文里写明
> "只输出 X，不要附加解释"。

## 5. ⭐ 与"脚本"的分工

一个容易混的问题：**共享服务技能 vs scripts/ 里的脚本，什么时候用哪个？**

```
✅ 脚本：⭐ 纯确定性、每次结果必须一模一样
   （JSON 语法校验、格式转换、哈希计算）

✅ 共享服务技能：⭐ 需要一点语言理解，但又是可复用的机械步骤
   （"把这段自然语言提取成 JSON 字段"）

❌ 别把确定性操作做成技能——脚本更省 token 且可测试
```

> ⭐⭐ 判据与 `deterministic-scripts.md` 一致：
> **"从 Y 算出 X，X 是数字、Y 是结构化数据" → 脚本；
> "用自然语言解释 X" → LLM。**
> 共享服务技能处在中间地带：**有语言成分，但输出是结构化的、可复用的**。

## 速查

```
□ ⭐⭐ 受众不同则规则不同：description 写"被其他技能调用时"
   ⭐ 否则会被用户直接误触发

⭐⭐⭐ 三硬规则：
□ ⭐⭐ 总是返回有效输出或明确错误（⭐ 沉默会让链在中间断裂且难定位）
□ ⭐ 输入输出契约钉死
□ ⭐⭐ 只做一件事，⭐ 不含业务语义（掺了就只能被一条链用）

□ 该造：两条以上链重复 · 输出被上游解析 · ⭐ 希望可替换
□ 不该造：只用一处 · ⭐ 需要判断力（判断留主技能）

□ 常见漏项：忘了写受众 · 无错误输出 · 掺业务语义
   ⭐ 输出混说明文字（⭐ 技能没有 stdout/stderr 分离，必须正文写明）
   ⭐ 版本变更未通知依赖方

□ ⭐ 与脚本分工：纯确定性→脚本；有语言成分但输出结构化→共享服务技能
```

**一句话**：

> ⭐⭐⭐ **共享服务技能必须"总是返回有效输出或明确的错误信息"——
> 它位于链条中间，沉默一次整条链就断了，而上游只知道"下游没给我东西"，极难定位。**
