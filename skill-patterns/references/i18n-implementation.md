## 五阶段工作流

| 阶段 | 时长 | 内容 |
|---|---|---|
| **1 项目分析** | 5–10 min | 识别框架、构建工具、组件结构；检查是否已有 i18n；建组件清单；设计命名空间 |
| **2 字符串提取** | 30–60 min | ⭐ 逐个组件读取，提取**全部**面向用户的字符串；按命名空间与组件组织；建主翻译清单 |
| **3 基础设施** | 15–20 min | 装 i18next（或框架对应库）；建配置；为**所有**语言建完整翻译文件；加类型定义 |
| **4 组件迁移** | 40–80 min | 改用 hook；替换全部硬编码字符串；处理插值、复数、复杂模式；确保零残留 |
| **5 验证** | 10–15 min | ⭐ 验证无硬编码残留；校验翻译文件语法与一致性；测语言切换；验翻译质量 |

**总时长**：典型应用（50–100 组件）1.5–3 小时。

> ⭐ **阶段 2 占了总时长的三分之一以上**——
> 这是最容易低估、也最容易漏的阶段。

## 一个关键陷阱：只查源码

> ⭐ **检查是否已有 i18n 时，只在源码目录里查。**

```bash
# ✅ 正确——只查源码目录
Grep: "i18n|i18next|vue-i18n|useTranslation" in src/
Glob: "src/**/locales/**"
Glob: "src/**/i18n/**"

# ❌ 错误——不要查文档
# 不要在 docs/、README*.md、任何 .md 文件里搜
```

**为什么**：文档里提到 i18next 不代表代码里接了。
在文档里搜会让 agent **误判"已有 i18n 基础设施"**，
从而跳过阶段 3，整个流程从一开始就错了。

> 呼应 `grounding-verification.md`（**`skill-crafting`**）：
> **行动前先查状态**（`skill-principles.md` 原则 7）——
> 但**查错地方比不查更糟**。

## 字符串提取范围

**必须提取的**：

```
□ 文本内容：<div>Hello World</div>
□ 标签：     <label>Email</label>
□ ⭐ 占位符： placeholder="请输入..."
□ 按钮文字： <button>Submit</button>
□ 标题：     <h1>Dashboard</h1>
□ 消息：     <p>Error occurred</p>
□ ⭐ 属性：   title、aria-label、alt
□ 选项：     <option>English</option>
```

> ⭐ **`placeholder`、`aria-label`、`alt`、`title` 是最常漏的四类**。
> 它们不在标签之间，肉眼看不出来，但对可访问性是必需的。

呼应 `a11y-skills.md`（**（领域实例库·已归档）**）：
**自动化工具只能抓到 30–57% 的无障碍问题**——
`aria-label` 这类正是漏掉的那部分。

## 命名约定

按组件路径生成 key：

```
组件：src/components/chat/ChatView.tsx

"Chat"              → chat.chatView.title
"New Conversation"  → chat.chatView.newConversation
"Type a message..." → chat.chatView.inputPlaceholder
"Send"              → chat.chatView.sendButton
```

**约定要点**：

```
□ 命名空间 + 组件名 + 用途
□ ⭐ 用途用语义（sendButton）而非位置（button1）
□ 大小写约定要写进技能（这里是小驼峰）
```

## 完成标准

> ⭐ **这套标准的可判定性极高——这是它适合做成技能的核心原因。**

```
✅ 100% 面向用户的文本走 i18n
✅ ⭐ UI 组件里零硬编码字符串
✅ 所有语言的翻译文件完整
✅ 应用在所有支持的语言下都能正常工作
✅ 无 console 报错或警告
```

**验证手段**（阶段 5）：

```
□ ⭐ 搜索模式验证无残留（不是"看起来没有"）
□ 校验翻译文件语法与一致性
□ 测试语言切换
□ 验证翻译质量
```

> ⭐ "搜索模式验证"这四个字是关键——
> 呼应 `grounding-verification.md`：
> **给具体命令，不靠 agent 自己扫一眼**。

## 为什么这个场景适合做成技能

对照通用判据：

```
□ ⭐ 流程长且有明确阶段 → 容易漏步骤
□ ⭐ 完成标准可判定（零硬编码、翻译文件完整）
□ ⭐ 有具体的易漏点（placeholder/aria-label/alt/title）
□ ⭐ 有会导致全盘皆错的陷阱（在文档里搜 i18n）
□ 一次投入可复用到多个项目
```

**技能形态**：

```
□ 五阶段 + 各阶段时长预估（帮 agent 判断进度）
□ ⭐ 明确的 ✅/❌ 命令示例（查源码 vs 查文档）
□ ⭐ 易漏清单（四类属性）
□ ⭐ 可判定的完成标准
```

## 与多语言技能的关系

呼应 `i18n.md`（**`skill-refining`**）：

```
i18n.md            → ⭐ 技能本身怎么做多语言
                     （name 不翻译、description 必须翻译）
本篇               → ⭐ 用技能帮别人做产品国际化
```

两者是不同层面——别混淆 target。
