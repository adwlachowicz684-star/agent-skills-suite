# 日志分析与排障

> 日志分析是"模型擅长、但容易编造"的典型场景。
> 技能要做的是**强制证据链**。

## 先定时间窗与范围

```
□ ⭐ 明确起止时间（含时区）
□ ⭐ 明确范围：哪个服务/实例/租户
□ ⭐ 明确基线：正常时这个指标是多少
```

> ⭐ **没有基线的"异常"判断都是猜测**。
> "错误率 3%"是高是低，取决于平时是 0.1% 还是 5%。

呼应 `performance-optimization.md`（**（领域实例库·已归档）**）：
**先测量再优化**——同一条纪律。

## 四类信号

**① 错误与异常**

```
□ 错误码分布（按 count 排序，不是按出现顺序）
□ ⭐ 新增错误码（基线里没有的）
□ 错误率随时间的变化（是突增还是缓慢上升）
```

**② 延迟**

```
□ ⭐ 看 p50/p95/p99，不看平均值
□ ⭐ 平均延迟会掩盖长尾——p99 坏掉时平均值可能毫无变化
```

**③ 流量与饱和**

```
□ QPS / 连接数 / 队列深度
□ ⭐ 饱和信号（线程池满、连接池耗尽）
```

**④ ⭐ 相关性**

```
□ 错误与哪个维度相关：版本？地域？租户？接口？
□ ⭐ 单看总数看不出——必须分群
```

呼应 `event-driven-architecture.md`（**（领域实例库·已归档）**）：
**它隐藏的失败模式是"lag 无声增长"**——
只看总数就会错过。

## 证据链要求

> ⭐ **每条结论必须挂在一个可独立验证的锚点上。**

```
❌ "可能是数据库连接问题"
✅ "10:23–10:31 期间 db.pool.timeout 出现 412 次
    （基线 <5 次/小时），集中在 us-east-1 的 api-3/4/7
    ——证据：logs/api/*.log:10482-11093"
```

**锚点三要素**：

```
□ ⭐ 时间窗
□ ⭐ 位置（文件:行、实例、服务）
□ ⭐ 计数与基线对比
```

呼应 `grounding-verification.md`（**`skill-crafting`**）与
`security-pipeline.md`（**`skill-orchestration`**）的
**反幻觉验证**——同一条规则在排障场景的应用。

## 不要做的事

```
❌ ⭐ 不编造日志片段
   ——"看起来像这样的日志"是致命的

❌ ⭐ 不用 grep 计数代替聚合查询
   ——大文件上 grep -c 会漏掉多行堆栈的上下文

❌ ⭐ 不把完整日志倒进上下文
   ——先聚合、先采样、先摘关键片段

❌ ⭐ 不下超出证据支持的结论
   ——"可能是 X 导致"要标为假设，并写明如何验证
```

第三条呼应 `runtime-failures.md`（**`skill-refining`**）：
**10,000 token 的查询结果通常能压成 200 token 的相关数据**。

## 输出格式

```
## 结论
[1–3 条，每条带锚点]

## 证据
[时间窗 · 位置 · 计数 · 基线]

## 待验证假设
[假设 + 下一步该查什么]

## ⭐ 未找到的部分
[明确列出查了但没找到的]
```

> ⭐ **最后一节最容易被省**——
> agent 默认会输出一个"完整"的分析，
> 把没查到的部分悄悄用推断填上。
>
> 呼应 `vertical-compliance.md`（**（领域实例库·已归档）**）：
> **要求 agent 说明"哪些它没有验证"**。
