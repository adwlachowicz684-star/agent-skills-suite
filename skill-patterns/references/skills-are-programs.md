## 1. ⭐⭐⭐⭐⭐ 类比：文档 vs 程序

> ⭐⭐⭐ **技能不是文档。它们是程序。运行时是 LLM。**

这个替换不是修辞，它直接改变三件事：

| 当成文档 | ⭐ 当成程序 |
|---|---|
| 越详尽越好 | ⭐ 每条都要证明自己值这个 token |
| 读一遍大概懂就行 | ⭐ 要能被"执行"并产出确定形状的结果 |
| 目录只是整理 | ⭐ 目录是模块划分，决定加载什么 |
| 附录可有可无 | ⭐ 未被引用的文件就是死代码 |

> ⭐⭐⭐ **"死代码"这个类比最有用**：
> 一个没人 import 的模块不会拖慢程序，但一个没被引用的技能文件会——
> 因为它仍可能被检索到，仍会稀释判断。

## 2. ⭐⭐⭐⭐⭐ 1024 字符决定它存不存在

> ⭐⭐⭐ **agent 在决定加不加载你的技能之前，只看到两样东西：name 和 description。**
> **就是这 1024 个字符，决定你的技能存在还是不存在。**

```
❌ "React skills."
✅ "Creates and builds React components using Tailwind CSS.
    Use when the user wants to update component styles or UI logic.
    Don't use it for Vue, Svelte, or vanilla CSS projects."
```

注意最后一句**反触发**：

> ⭐⭐ **没有它，你的 Angular 迁移技能会在 React 项目上触发，
> 你的 Python 测试技能会在 Go 代码上触发。**

`name` 的硬规则（与 `naming-conventions.md` 一致，这里给完整版）：

```
1–64 字符 · 小写字母+数字+连字符 · 无连续连字符 · 必须与父目录名一致
```

## 3. ⭐⭐⭐⭐ 目录即模块划分

```
skill-name/
  SKILL.md      # ⭐ 大脑。程序入口。<500 行
  scripts/      # ⭐ 确定性任务的已测代码
  references/   # ⭐ JIT 上下文，一层深
  assets/       # 模板与静态文件
```

| 目录 | 类比 | 判据 |
|---|---|---|
| `scripts/` | 编译好的二进制 | ⭐ 变化即 bug → 固化 |
| `references/` | 按需 import 的模块 | ⭐ 每次要有新见解 → 读进上下文，付 token |
| `assets/` | 资源文件 | ⭐ 被 copy+fill 消费，零成本 |

**一层深**的理由不是审美：

> ⭐ **SKILL.md 链到 A、A 再链到 B，agent 可能只读到 B 的一部分。**
> 全部从 SKILL.md 直接链。

## 4. ⭐⭐⭐⭐ 不该存在的四类文件

> ⭐⭐ **目录里的每个文件都在消耗上下文。对自己狠一点。**

| 类别 | 具体 | 为什么删 |
|---|---|---|
| 文档文件 | README.md · CHANGELOG.md · INSTALLATION_GUIDE.md | ⭐ agent 运行时不需要，且 README 不在加载链里——**写在 README 里的安全约束根本读不到**（`unicode-injection-defense.md` 同源） |
| 冗余逻辑 | agent 本来就做得好的指令 | 零增量 |
| 库代码 | 长生命周期的通用库 | ⭐ 技能里只放"小而单一"的脚本 |
| 时敏信息 | 版本、价格、截止日期 | ⭐ 程序记忆层没有时间维度 |

## 5. ⭐⭐⭐⭐ 写给人看 vs 写给机器看

三条直接改变写法的规则：

**① 编号步骤，而不是段落**

```
❌ "先分析结构，再看看有没有问题，最后给建议"
✅ "Step 2: 如果需要 source maps，跑 ng build --source-map；
    否则跳到 Step 3。"
```

⭐ 明确画决策树，不留"创造性诠释"的空间。

**② 模板优先于散文**

> ⭐ **agent 擅长模式匹配。assets/ 里的一个 JSON 模板，
> 胜过描述输出长什么样的三段文字。别描述——展示。**

**③ 第三人称祈使句**

```
✅ "Extract the text…"
❌ "You should extract…" / "I will extract…"
```

与我们已有的 `imperative-style.md` 一致，但这里给了理由：
**第一/第二人称会制造"谁在说话"的歧义**——
当这段指令被注入另一个 agent 的上下文时尤其明显。

## 6. ⭐⭐⭐ 术语一致性：一个概念一个词

> ⭐⭐ **用领域原生词汇，并全程只用这一个。**

```
Angular 里说 "template"，
就不要在别处说 "html" / "markup" / "view"
```

理由是具体的：**不一致会增加 agent 把相似概念混为一谈的概率。**
这与 `terminology.md` 一致，但这里的机制解释值得记——
**不是"更专业"，是"减少混淆的机会"。**

## 7. ⭐⭐ 自检

| # | 检查 | 不合格信号 |
|---|---|---|
| 1 | ⭐ 每条内容都证明自己值 token | 有"以防万一"的段落 |
| 2 | description 有反触发 | 只写了正向场景 |
| 3 | ⭐ 目录里没有 README/CHANGELOG | 有 |
| 4 | 引用链只有一层 | 有 A→B→C |
| 5 | 输出给了模板而非描述 | 用散文描述输出 |
| 6 | ⭐ 第三人称祈使句 | 出现 "you" / "I" |
| 7 | 一个概念一个词 | 同义反复出现 |

## 一句可贴在墙上的话

> ⭐⭐⭐ **"如果 agent 换一条路走，你介意吗？"**
> 不介意 → 给约束和目标（程序里的"接口"）
> 介意 → 写脚本或工作流（程序里的"实现"）

这与 `eight-practical-lessons.md` 的"给约束不给流程"、
`anthropic-team-lessons.md` 的"避免 railroading"是同一判据的三次出现。
