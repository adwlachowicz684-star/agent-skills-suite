## 1. ⭐⭐ 七反模式一览

| # | 反模式 | 后果 | 修法 |
|---|---|---|---|
| 1 | 模糊 description | ⭐ 永不触发 | 改成 "Use when…" 触发句 |
| 2 | ⭐ **巨型技能** | ⭐ 加载晚、触发不可靠、章节冲突时混乱 | 一职责一技能 |
| 3 | ⭐ 长流程写进 CLAUDE.md | ⭐ 每轮都付 token | 移到技能 |
| 4 | ⭐ **过度脚本化** | 复杂脚本维护成本高 | 判断步骤留在 markdown |
| 5 | ⭐ **放错作用域文件夹** | ⭐⭐ **静默失败，无报错** | 个人 vs 项目 vs 插件分级 |
| 6 | ⭐⭐ 危险技能没设调用控制 | ⭐ 灾难性 | `disable-model-invocation: true` |
| 7 | ⭐ 超出 token 预算 | 部分技能更难被发现 | 查诊断、精简 description |

## 2. ⭐⭐ monorepo 的作用域：靠文件夹，不靠配置

```
apps/marketing-site/.claude/skills/   只在营销站相关时加载
packages/ui/.claude/skills/           只在共享 UI 包相关时加载
.claude/skills/（仓库根）              全局可用
```

> ⭐⭐ **No configuration. No setup.**
> **把技能放进正确的文件夹，正确的技能就会在正确的地方加载。**

> ⭐ 这条与 `frontmatter-full-reference.md` 的 `paths:` 字段是互补的两种手段：
> `paths:` 是⭐ 显式声明文件 glob；文件夹位置是⭐ 隐式的作用域。
> 前者更精确，后者零配置。

## 3. ⭐⭐⭐ Markdown 指令不是访问控制

> ⭐⭐⭐ **一个 Markdown 指令本身不是访问控制。**

```
⭐⭐ "/deploy 技能没有 disable-model-invocation: true
     = Claude 可以因为'代码看起来就绪了'就决定部署。
     ⭐ 灾难性。"
```

> ⭐⭐ **任何有副作用的技能都必须设成用户专属调用。**
> deploy / send / commit / write to production —— 一个不漏。

> ⭐⭐⭐ 这是本份最重要的一条，也是⭐ 第四个独立来源说同一件事：
>
> ```
> · 把破坏性命令拦截写进技能 = 表演（模型三轮后就忽略）
> · 技能里的权限声明不是安全边界
> · Hooks 用于模型不可被信任去遵守的事
> · ⭐⭐⭐ Markdown 指令不是访问控制
> ```
>
> 四者共同指向一条：**需要保证的事，必须交给有强制力的层**。

**一个可维护团队库的三个特征**（正好对应治理）：

```
① 把可复用团队约定、技术特定流程、项目特定指令⭐ 分开
② ⭐ owner、版本、评审日期保持清晰
③ ⭐⭐ 有副作用的技能需要⭐ 显式的权限边界
```

**起步建议**（与 `team-landing-seven.md` 一致）：

```
⭐ 从一个重复的工作流开始
⭐⭐ 同时测两件事：
    ⭐ 该运行时它运行了吗
    ⭐⭐ 该让路时它让路了吗
```

> ⭐⭐ 后半句常被漏——**只测"该触发时触发"会得到一个到处乱触发的技能**。
> 这正是 `description-by-collision-risk.md` 的负样本比正样本值钱。

## 4. ⭐ 长流程放 CLAUDE.md 的代价

```
❌ 200 行部署清单写在 CLAUDE.md
   ⭐⭐ 每一轮都要为它付 token
✅ 移进技能；CLAUDE.md 保持精简
```

**两者的正确分工**（这个表述最清楚）：

```
CLAUDE.md = ⭐ 常驻事实（架构决策、技术栈、代码风格）
技能      = ⭐ 触发式程序（只在 description 匹配时加载）
```

> ⭐ 与 `context-file-selection.md` 的结论一致，但这里给了更好的记忆法：
> **CLAUDE.md 是"每轮都为真"的东西；技能是"当做 X 时"的东西。**

**技能 vs 自定义命令**（一条历史事实）：

```
自定义命令 .claude/commands/foo.md = ⭐ 旧格式，现在是技能的子集
⭐ 同名时技能优先
⭐ 新工作一律用技能
```

## 5. ⭐ 过度脚本化

> ⭐ **不要把判断步骤也写成脚本。**

```
❌ 为了"看起来工程化"把整个流程写成复杂 shell/python
✅ ⭐ 判断步骤留在清晰的指令里
✅ ⭐ 只有⭐ 固定计算、校验、可重复的数据处理才用小的、测过的脚本
```

> ⭐ 这条是对 `deterministic-scripts.md` 的必要补充——
> 那份讲"该脚本化什么"，这份补**"不该脚本化什么"**：
> **需要判断力的部分留在 markdown，因为脚本无法表达判断**。

## 速查

```
□ ① 模糊 description → "Use when…" 触发句
□ ② ⭐ 巨型技能 → 一职责一技能
□ ③ ⭐ 长流程进 CLAUDE.md → 每轮付费，移到技能
□ ④ ⭐ 过度脚本化 → ⭐ 判断步骤留在 markdown
□ ⑤ ⭐⭐ 放错作用域文件夹 → ⭐⭐ 静默失败无报错
□ ⑥ ⭐⭐ 危险技能未设调用控制 → ⭐ 灾难性
□ ⑦ 超 token 预算 → 精简 description

□ ⭐⭐ monorepo：靠文件夹位置定作用域，零配置
□ ⭐⭐⭐ ⭐ Markdown 指令不是访问控制
   → deploy/send/commit/写生产 ⭐⭐ 一律 disable-model-invocation
□ ⭐⭐⭐ 四个独立来源同一结论：要保证的事交给有强制力的层

□ ⭐ CLAUDE.md = 每轮为真的常驻事实；技能 = 当做X时的程序
□ ⭐ 同名时技能优先于旧自定义命令

□ ⭐⭐ 同时测"该运行时运行"和⭐⭐ "该让路时让路"
```

**一句话**：

> ⭐⭐⭐ **一个 Markdown 指令本身不是访问控制——
> 任何有副作用的技能（deploy / send / commit / 写生产）都必须设成用户专属调用。**
