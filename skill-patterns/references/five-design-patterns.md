## 1. 五种模式

> ⭐ 前提：**SKILL.md 的格式已经标准化了，真正的挑战是内容设计。**
> 这五种模式来自对 Anthropic 仓库、Vercel 实践、Google 内部规范的研究。

---

## 2. 模式一：Tool Wrapper（工具包装器）

**痛点**：希望 agent 遵循某个库的最佳实践时，传统做法是把规则硬塞进系统提示词——臃肿，且无法按需加载。

**解法**：把库的上下文打包成独立技能，检测到关键词才加载 `references/`。

```yaml
name: api-expert
description: FastAPI 开发最佳实践与约定
metadata:
  pattern: tool-wrapper
  domain: fastapi
```

行为：

```
审查代码时：加载约定 → 逐条检查违规 → 引用具体规则给建议
编写代码时：加载约定 → 严格遵循 → 加类型注解 → 用 Annotated 依赖注入
```

**适用**：团队编码规范分发、第三方库使用指南、安全审查规则。

> ⭐ 这是**起步模式**——最简单，覆盖面最广。

---

## 3. 模式二：Generator（生成器）

**痛点**：每次生成技术方案，输出结构都不一样——有时表格，有时列表，段落顺序飘忽。

**解法**：模板强制输出结构一致，agent 像填空一样生成。

`assets/template.md`：

```markdown
# 项目名称
- 背景:
- 目标:
## 方案对比
| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| A    |      |      |      |
## 推荐方案
- 技术选型:
```

**行为**：加载模板 → 读风格指南 → 询问缺失变量 → 填充

**适用**：周报、架构设计文档、需求规格、变更日志。

> ⭐ 模板放 **`assets/`** 而非 `references/`——
> 它是被填充的骨架，不是被阅读的知识
> （对应 `skill-structuring` 的 `references-vs-assets.md` 的分界）。

## 4. 模式三：Reviewer（评审者）

**痛点**：几十条规范写进提示词，一更新所有技能都要改。

**解法**：**把"检查什么"与"怎么检查"分离**——清单放 `references/review-checklist.md`。

```markdown
- [ ] 所有函数都有类型注解        (严重:高)
- [ ] 异常处理覆盖了文件操作      (严重:中)
- [ ] 没有硬编码的敏感信息        (严重:高)
- [ ] 日志记录使用结构化方式      (严重:低)
```

输出按严重度分组：

```
❌ 严重: config.py 第15行硬编码密码 → 建议从环境变量读取
⚠️ 中: file_handler.py 未捕获异常   → 建议加 try/except
✅ 低: 所有函数均包含类型注解
```

**适用**：代码审查、合规检查、设计文档评审。

> ⭐ **关键收益：指令（怎么审）保持稳定，
> 检查标准（查什么）可独立迭代。**

## 5. 模式四：Inversion（反转）

**痛点**：agent 接到任务就开干，需求理解偏差导致返工。

**解法**：**翻转交互方向——agent 变成采访者**，结构化提问收集完上下文才行动。

```markdown
### 阶段1: 需求澄清（你必须回答完所有问题才能进入下一阶段）
1. 这个 API 的主要资源是什么?
2. 需要支持哪些 HTTP 方法?
3. 是否需要身份验证?
### 阶段2: 模型设计
### 阶段3: 代码生成
```

**门控指令**（不可协商）：

```
"DO NOT start building until all phases are complete."
```

**适用**：复杂需求拆解、项目脚手架、用户画像分析、架构设计。

> ⭐ 这个模式与 `guidance-forms.md` 的关系值得注意：
> 它用的是**禁令**（DO NOT start building），
> 但**同时给出了完整的替代路径**（先完成这些阶段）——
> 所以是有效禁令。

## 6. 模式五：Pipeline（管道）

**痛点**：多步骤有依赖，agent 经常跳过中间步骤或打乱顺序。

**解法**：显式定义步骤顺序和检查点，**每步输出是下一步的输入**。

```markdown
### 步骤1: 提取原文
  输出: artifacts/source.txt
### 步骤2: 翻译
  读取 artifacts/source.txt → 输出 artifacts/translated.txt
### 步骤3: 本地化适配
  读取 artifacts/translated.txt → 输出 artifacts/localized.txt
### 步骤4: 生成报告
  输出 artifacts/report.md
```

**菱形门控**：每步完成都要确认产出物存在且符合要求才进入下一步。

```
步骤1 研究 → ◇ 检查点: 研究报告是否完整?
步骤2 起草 → ◇ 检查点: 草稿是否覆盖所有要点?
步骤3 审查 → ◇ 检查点: 所有问题是否已修复?
步骤4 输出
```

**适用**：数据处理流水线、CI/CD 编排、多步骤内容生产。

> ⭐ 注意"每步输出落文件"——
> 与 `composition.md` 的"中间产物落文件"完全一致。

## 7. ⭐ 选型决策树

```
输出是否需要遵循固定模板/结构?
├─ 是 → 输出之前需要先向用户提问收集信息?
│        ├─ 是 → Inversion（先采访后填模板）
│        └─ 否 → Generator（直接按模板生成）
└─ 否 → 任务包含需要顺序执行、且有验证点的多个步骤?
         ├─ 是 → Pipeline（多步骤 + 门控）
         └─ 否 → 需要对提交的内容做评审/评分?
                  ├─ 是 → Reviewer（对照清单评审）
                  └─ 否 → Tool Wrapper（专家知识包装）
```

> ⭐ **实践建议：从 Tool Wrapper 起步。**
> 当你发现 agent 输出结构乱、跳步骤、急于行动时，
> **再升级到对应更复杂的模式**——不要一上来就 Pipeline。

## 8. 速查对比表

| 模式 | 使用场景 | 目录使用 | ⭐ 核心约束维度 | 复杂度 |
|---|---|---|---|---|
| **Tool Wrapper** | 需要某个库/工具的专家知识 | `references/` | 知识来源 | ⭐ 低 |
| **Generator** | 输出必须每次符合固定结构 | `assets/` + `references/` | 输出结构 | 中 |
| **Reviewer** | 对照标准评审打分 | `references/`（清单） | 评估标准 | 中 |
| **Inversion** | 必须先收集上下文才能行动 | `assets/`（综合模板） | 信息收集顺序 | 中（多轮） |
| **Pipeline** | 有依赖步骤 + 需要验证门控 | `references/` + `assets/` + `scripts/` | ⭐ 执行顺序 + 验证点 | 高 |

**组合使用**：

> 生产环境中每个技能的**中位数组合模式数为 2 种**。
> 常见组合：**Pipeline + Reviewer**（在流水线某一步嵌入评审清单）。

## 速查

```
□ 输出要固定结构 → Generator
□ 但先要问用户 → Inversion
□ 多步骤 + 验证点 → Pipeline
□ 对照清单评审 → Reviewer
□ 都不符合 → Tool Wrapper（默认起步）
□ ⭐ 别一上来就 Pipeline
□ 组合是常态（中位数 2 种）
□ 门控要有可判定的检查点
