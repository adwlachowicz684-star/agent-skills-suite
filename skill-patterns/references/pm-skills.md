## 模式路由：先选对分支

> ⭐ **选错分支会导致产出无效**——这是 PM 类技能最该前置的一步。

```
需要定义新功能？   → PRD 模式（背景 · 目标 · 范围 · 验收标准）
需要竞品分析？     → ANALYSIS 模式（四维：功能/体验/技术/商业模式）
需要规划路线图？   → ROADMAP 模式（基于 OKR 的 NOW-NEXT-LATER）
需要用户研究？     → RESEARCH 模式（访谈 · 问卷 · 行为数据分析）
```

```
□ ⭐ 任务模糊时，优先选 PRD 模式，并在文档顶部说明假设
□ 一条链式工作流的例子：
   /discover → /user-research → /competitive-analysis
   → /strategy → /north-star → /write-prd
```

> ⭐ 呼应 `skill-refining` 的 `architecture-layering.md` 的 Router 模式：
> **先路由到子模式，再执行**，避免一个技能什么都做。

## PRD 该含什么

```
1. 问题陈述        解决什么用户痛点或业务需求
2. ⭐ 目标与成功指标  成功长什么样——⭐ 定量的
3. 用户故事与用例   谁用、怎么用（As a... I want... so that...）
4. 需求            功能与非功能需求，⭐ 排好优先级
5. 技术考量        架构影响、依赖、约束
6. 设计与 UX 要点  关键交互模式或设计要求
7. ⭐ 风险与缓解    什么可能出错，怎么应对
8. 发布计划        灰度策略、feature flag、监控
9. ⭐ 待决问题      还有什么需要决定或调研
```

> ⭐ **第 9 项"待决问题"最容易被漏**，
> 但它恰恰是 PRD 与"假装很确定"的分界线——
> 呼应 （领域实例库·已归档） 的 `research-skills.md` 的"说明哪些没有验证"。

**产出格式**（分层，便于不同读者）：

```
执行摘要     业务目标 · 用户价值 · 技术可行性 · 优先级 · 预计工期
详细规格     功能描述 · 用户故事 · 验收标准 · 技术要求 · 边界情况
实施路线图   阶段计划（需求确认→设计评审→开发实现→测试验收）
```

## 优先级框架

> ⭐ **用结构化框架，而不是拍脑袋**：

```
RICE    Reach × Impact × Confidence / Effort
ICE     Impact × Confidence / Ease
价值 vs 成本   2×2 矩阵
Kano    基本型 · 期望型 · 兴奋型
```

```
优先级排序依据 = 业务影响 + 用户影响 + 技术可行性
```

**路线图要点**（这五条比框架本身更值钱）：

```
□ ⭐ 主题化——按战略主题分组，而不只是功能清单
□ 有时间段——NOW / NEXT / LATER 或按季度
□ ⭐ 结果导向——强调目标与结果，不只是产出
□ 留有余地——给学习和调整留空间
□ 沟通清晰——不同受众给不同视图
```

## 明确的不适用范围

> ⭐ **一份成熟的 PM 技能会显式列出这些**：

```
❌ 做最终产品决策       —— 这是 PM 的活，技能只协助
❌ 管理利益相关者关系与政治
❌ 详细的 UI/UX 设计工作 —— 用设计工具并与设计师协作
❌ 项目管理与迭代排期    —— 用项目管理工具

⭐ 另外不建议用于：
   战略产品愿景（需要深度客户共情）
   定价决策（需要市场与财务专长）
   面对面的客户发现（此时深度比速度更有价值）
```

> ⭐ **"不替 PM 做决策"这条必须写进技能**——
> 呼应 `methodology-skills.md` 的第⑥条：
> **显式标出"只能人做"的步骤**。

## 常见坑与最佳实践

**⚠️ 坑（Don't）**：

```
□ 不核实就发布竞品分析——⭐ 分享前必须核实事实
□ 不经工程团队参与就定稿用户故事
□ ⭐ 过度依赖框架而忽视定性判断
□ 不按公司文化与沟通风格定制产出
□ ⭐ 跳过利益相关者对生成需求的验证
□ 仅凭 AI 打分做优先级决策
□ 忽略公司特有的上下文与文化
```

**✅ 最佳实践（Do）**：

```
□ 用真实数据验证研究与竞品分析
□ 生成技术需求时与工程团队协作
□ ⭐ 按公司语境定制框架与模板
□ ⭐ 用技能产出初稿，再用利益相关者输入打磨
□ 沉淀有效的提示模式供团队复用
□ 结合 AI 效率与人的判断直觉
□ ⭐ 提供上下文（公司目标、约束、客户反馈）
□ ⭐ 要求给备选（"展示 3 种排这个路线图的方式"）
□ 按受众要求格式（"执行摘要 vs 工程规格"）
□ ⭐ 70% 生成 + 30% 定制——这个配比值得抄
```

**用户研究综合的要点**：

```
□ 识别模式——跨受访者浮现了什么主题
□ ⭐ 逐字引用——用真实用户原话说明观点
□ ⭐ 能量化就量化——"10 位里有 7 位说…"
□ 分段——不同用户类型可能有不同需求
□ ⭐ 连接到指标——定性发现如何解释定量数据
```

**进阶路径**（可作为技能的学习曲线）：

```
1 基础  用户故事 · 功能规格 · 状态更新
2 中级  竞品分析 · 优先级框架 · PRD
3 高级  产品策略 · GTM 规划 · OKR 设定
4 专家  产品愿景 · 市场定位 · 商业模式创新
```

## 自查

```
□ 是否有模式路由（PRD / ANALYSIS / ROADMAP / RESEARCH）？
□ ⭐ 是否声明"选错分支导致产出无效"？
□ 模糊任务是否默认 PRD 模式并要求声明假设？
□ PRD 是否含"定量成功指标"与"待决问题"？
□ 是否提供了优先级框架（RICE / ICE / Kano）？
□ 路线图是否强调主题化与结果导向（而非功能清单）？
□ ⭐ 是否显式列出不适用范围（不做最终决策等）？
□ 是否强调"70% 生成 + 30% 定制"？
□ ⭐ 是否有常见坑清单（不核实就发布、跳过相关方验证等）？
□ 用户研究是否要求逐字引用与量化？
□ 是否要求"连接到指标"（定性解释定量）？
□ 是否提供了进阶路径（让使用者知道技能边界在哪）？
□ 是否要求按受众调整格式（执行摘要 vs 工程规格）？
```
