## 1. ⭐ 什么是黄金规则

> ⭐ **黄金规则是特定于技能领域的硬性机械规则。
> 对设计阶段识别出的每一种失败模式，写一条规则来防止它。**

这句话有两层意思：

```
① 规则不是凭空想的——⭐ 它必须对应一个具体的失败模式
② 规则是机械的——能判定，不是形容词
```

---

## 2. ⭐ 失败模式 → 黄金规则对照表

| 失败模式 | 黄金规则 |
|---|---|
| agent 把所有内容都塞进 SKILL.md | ⭐ **"SKILL.md 是地图。如果你在 SKILL.md 里写代码块，它就该进 reference 文件。"** |
| agent 写出含糊的 description | ⭐ **"Description 就是发现机制。如果 description 不含用户会说的关键词，技能就不会触发。"** |
| agent 跳过测试 | ⭐ **"每个技能必须至少一个反馈环：做 → 检查 → 修。"** |
| 每次运行输出都不一样 | ⭐ **"把每个形容词换成一条规格。"** |

> ⭐ 这四条可以直接抄进任何技能。
> 它们的共同形态：**一句话，机械，可判定**。

第二条尤其锋利——它把"description 要写好"这句正确的废话，
变成了"不含用户会说的关键词就不会触发"这个**可检查的事实**。

## 3. ⭐ 自查清单：可验证 vs 主观

```
✅ 正确——可客观验证
- [ ] SKILL.md 正文少于 100 行（不含 frontmatter）
- [ ] 全部 5 类测试通过：init、moves、win、negative、visual
- [ ] 完整跑一遍没有 console 错误

❌ 错误——主观
- [ ] 代码干净
- [ ] 测试通过
- [ ] 输出看起来不错
```

> ⭐ 后三条的问题：**它们永远无法通过"检查"这个动作被判定为失败**。
> "代码干净"谁说了算？agent 自己说了算——那就等于没检查。

**设计目标**：

```
⭐ 一份从未抓到过任何问题的清单，说明检查得还不够硬
⭐ 目标 6–12 项
⭐ ⭐ 规模要让"真实运行偶尔会挂掉其中一项"
```

> ⭐ 最后一条是最精妙的设计：
> **如果清单永远全绿，它要么是废话，要么检查得太松。**
> 好的清单应该"偶尔会红"——这说明它在真检查。
>
> 这与 `quality-rubric.md` 的"每个分数要引用具体证据"、
> `eval-loop-official.md` 的"两组都通过的断言没有区分度"
> 是同一条原理的三种表述。

## 4. 五条 harness 工程原则

> **harness engineering**：把约束、约定、反馈环编码进技能文件，
> 而不是依赖 agent 的通用判断力。

| 原则 | 含义 |
|---|---|
| ⭐ **地图，不是手册** | SKILL.md 是目录。细节在 reference 文件里。agent 按需导航 |
| ⭐ **具体胜过抽象** | ⭐ 每条质量标准是一条规格，不是一个形容词。"函数 30 行内"是标准，"代码整洁"不是 |
| ⭐ **反馈环就是产品** | ⭐ 没有验证步骤的技能只是建议。每个技能至少编码一个 做→检查→修 循环 |
| ⭐ **规则升级为代码** | ⭐ 某条书面指令反复被违反时，⭐ 把它编码成校验函数或 linter，⭐ 而不是把段落写得更严厉 |
| ⭐ **不在文件里就等于不存在** | ⭐ agent 只能看到技能目录里的东西。每条约束、约定、模式都必须写下来，否则会被忽略 |

> ⭐ 第四条值得单独体会：
> **写得更严厉没有用**——这正是 `failure-modes.md` 里
> "禁令反噬"和"验证置换"的根源。
> 真正有效的是**把规则变成可执行的代码**。

> 第五条也常被忽略：
> agent 看不到你脑子里的约定，也看不到别的技能里的内容。
> **没写进目录的东西，对它不存在。**

## 速查

```
□ 每条规则是否对应一个失败模式
□ 规则是否机械可判定
□ ⭐ 自查清单项是否可客观验证（不是"看起来不错"）
□ ⭐ 清单是否 6–12 项
□ ⭐ 清单是否"偶尔会红"（永远全绿 = 没在检查）
□ 是否有一个 做→检查→修 循环
□ ⭐ 反复被违反的规则是否已升级为脚本/linter
□ ⭐ 所有约定是否都写进了文件
```

**一句话**：

> ⭐ **"函数 30 行内" 是标准，"代码整洁" 不是。**
