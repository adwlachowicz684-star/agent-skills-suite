## 1. ⭐⭐⭐⭐⭐ 问题不是"没日志"，是日志指向错的地方

```
A → B → C，B 出错
⭐⭐⭐⭐⭐ C 的失败报告里根本不会提到 B
```

> ⭐⭐⭐⭐⭐ **出错的地方 ≠ 报错的地方。**
> 这是链式结构最贵的属性。

多数团队的第一反应是"加日志"。但⭕ **通用 span 日志解决不了这个问题**——它记录的是"每个技能各自跑得怎么样"，而链式失败的信息恰恰在**技能之间**，不在任何一个技能内部。

> ⭐⭐⭐⭐ 判据：⭐⭐⭐⭐⭐ **你的日志能回答"A 交给 B 的东西是什么"吗？**
> 不能 → 链断掉时你只能逐个技能重跑。

---

## 2. ⭐⭐⭐⭐⭐ 链路 ID：一条链，一个标识

最低成本的一步，也是最有用的一步：

```
每次链运行生成一个 chain_id
每一级把它写进自己的输出与日志
⭐⭐⭐⭐⭐ 于是"这次运行的全部痕迹"可以用一条 grep 取出
```

没有它，日志是**按技能**聚合的，你无法把一次运行的多级记录拼起来。

三个必须随 chain_id 一起传递的字段：

| 字段 | ⭐ 为什么 |
|---|---|
| `stage` | 第几级（A=1, B=2...） |
| `upstream_status` | ⭐⭐⭐⭐⭐ 上游给我的状态是什么 |
| `coverage` | ⭐⭐⭐⭐ 我处理了多少 / 应该处理多少 |

> ⭐⭐⭐⭐ 第二个字段是关键：⭐⭐⭐⭐⭐ **它把"我失败了"和"我拿到了坏输入"区分开**，
> 而这正是链式失败里最常混淆的一对。

## 3. ⭐⭐⭐⭐⭐ 定位法：从后往前二分

链很长时不要从头查：

```
① 取最后一级的输入文件（它在磁盘上，会话结束也还在）
② ⭐⭐⭐⭐⭐ 这个输入是错的吗？
   是 → 问题在更前面，往前一级，重复
   否 → 问题就在这一级
```

> ⭐⭐⭐⭐⭐ **每一步都只需要看一个文件**，不需要重跑任何东西。
> 这依赖一个前提：**每一级都把产物写到磁盘**（`skill-execution/references/intermediate-artifacts.md`）。

> ⭐⭐⭐ 反面：如果中间产物只存在于上下文里，链一断你就只能整条重跑——
> ⭐⭐⭐⭐ 而重跑会引入新变量，于是"偶发"问题永远定位不到。

二分变体（链很长时）：跳到中间一级，判断它之前还是之后出问题，然后递归。⭐⭐⭐⭐ 三级链用线性、八级以上用二分。

## 4. ⭐⭐⭐⭐⭐ 每级显式检查上游状态

```
⭐⭐⭐⭐⭐ 每级开头：
  读上游 status
  status != ok  → 停止并向上报告，不要"尽力继续"
```

> ⭐⭐⭐⭐⭐ 唯一的结构性对策。不能靠"下游自然会发现问题"——
> ⭐⭐⭐⭐ 下游拿到的是格式正确的输入，它会正常跑完并输出成功。

三个必须检查、不能跳的项：

```
① upstream_status 是否 ok
② ⭐⭐⭐⭐⭐ 上游 status 是否 partial（不是错误，但也不是全量）
③ ⭐⭐⭐⭐ 上游产物是否本次运行生成（不是上一次的缓存）
```

第 ② 条最常被漏，因为⭐⭐⭐⭐ **partial 不是错误，很多实现只检查"是不是错误"**。第 ③ 条对应"用文件存在判断做过"那个陷阱。

---

## 5. 三种"看起来是下游的错"

| 表象 | ⭐ 真因 | 判据 |
|---|---|---|
| 汇总结果比预期少 | ⭐⭐⭐⭐⭐ 上游 partial 被当全量 | 查 `coverage`，不看总数 |
| 下游报"字段缺失" | 上游换版改了字段名 | ⭐⭐⭐⭐ 比对上游 schema 版本 |
| 下游输出"成功"但内容空 | ⭐⭐⭐⭐⭐ 上游错误被当成空输入，下游照常跑完 | 查 `upstream_status` |

> ⭐⭐⭐⭐⭐ 第三种最贵：⭐⭐⭐⭐ 每一级都在正常完成自己的工作，
> 合起来把一个错误加工成了一份看起来成功的报告——**没有任何一级会报错**。
