# Fan-out / Fan-in：并行后的汇聚

> 并行不难，难的是**汇聚**。
> 多数并行编排的失败发生在收口处。

## 两个阶段

```
Fan-out（发散）
  把任务拆成 N 个独立子任务，并行执行

Fan-in（汇聚）
  ⭐ 把 N 份结果合并成一份可用输出
```

> ⭐ **技能文档常常只写 fan-out，不写 fan-in**——
> 而后者才是失败的集中地。

## Fan-out 的三条前提

呼应 `composition.md` 与 `parallel-subagents.md`：

```
1. ⭐ 子任务输出互不依赖
2. ⭐ 有统一的输出契约（否则无法合并）
3. ⭐ 超时与重试策略已知
```

补充两条：

```
4. ⭐ 文件所有权排他（多个子任务不能写同一文件）
5. ⭐ 指令窄且带可度量成功标准
```

## Fan-in 的三个动作

**① 收集**

```
□ ⭐ 等所有子任务返回，或超时后按已返回的继续
□ ⭐ 记录哪些超时/失败了——不能静默丢弃
```

**② 归一化**

```
□ ⭐ 各子任务的输出格式必须一致（靠输出契约）
□ ⭐ 不一致时先转换，不要直接拼接
```

**③ 合并与去冲突**

```
□ 去重（不同子任务可能报告同一问题）
□ ⭐ 冲突消解（见下）
□ 排序（按严重度/置信度，规则要写死）
```

呼应 `security-pipeline.md`（**`skill-orchestration`**）的
**结果汇聚：去重、按严重度排序**。

## 四种汇聚失败

| 失败 | 症状 | 修法 |
|---|---|---|
| **静默丢弃** | 超时的子任务结果没了，没人知道 | ⭐ 记录并报告 |
| **格式不统一** | 拼接后一塌糊涂 | ⭐ 输出契约 + 归一化步骤 |
| **重复计数** | 同一问题被报三次 | 去重（要有去重键） |
| ⭐ **顺序不确定** | 每次跑出来顺序不同 | ⭐ 排序规则写死 |

> ⭐ **"去重键"值得单独设计**：
> 三个子任务报同一个漏洞时，靠什么判定是同一个？
> 通常是 `file:line + 类别`——这个键要写进技能。

**排序规则要写死**这条呼应 `ab-testing-growth.md`
（**`skill-domain-biz`**）的"指标要配解读规则"：
**没有规则的排序会随模型心情变化**。

## 汇总规则比分工更重要

> ⭐ **没有汇总规则，主任务只会收到几份互相独立的长报告。**

呼应 `multi-agent-review.md` 的同名原则。

**汇总规则该写什么**：

```
□ ⭐ 输出的固定结构（不是"把大家的发现汇总一下"）
□ 严重度/优先级的排序规则
□ 冲突时的裁决依据
□ ⭐ 哪些要原样保留，哪些要压缩
```

**一个具体做法**：

```
子任务返回：结构化 JSON（固定 schema）
汇总：      按 schema 字段归并，不读自然语言报告
```

> ⭐ **让子任务返回结构化而非散文**，
> 汇聚就从"理解"变成了"归并"——可靠得多。

呼应 `output-contract.md`（**`skill-crafting`**）的 Schema-First。

## 与交接的关系

呼应 `handoff-protocol.md`：

```
□ 子任务返回前先摘要
□ ⭐ 结论带锚点（file:line / ID）
□ ⭐ 未解决项显式列出
□ 大数据走文件，不进上下文
```
