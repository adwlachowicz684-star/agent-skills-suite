## 1. ⭐⭐⭐⭐⭐ 一个不会报错的汇总

```
扇出：3 个数据源
结果：A 成功（120 条）· B 401 失败 · C 成功（80 条）
汇总："共 200 条数据，主要趋势是……"
```

> ⭐⭐⭐⭐⭐ 这句话技术上**完全真实且完全误导**。
> ⭐⭐⭐⭐⭐ 它省略了 `source_b 401 → 覆盖率 67%`。

> ⭐⭐⭐⭐⭐ 没有一方在撒谎——是交接协议里没有这个字段。

---

## 2. ⭐⭐⭐⭐⭐ 汇总天然倾向于"当作全量"

三条机制：

**① ⭐⭐⭐⭐⭐ 汇总的输入是"有的那些"，不是"应有的那些"**

```
拿到的：A 的 120 条 + C 的 80 条
⭐⭐⭐⭐⭐ B 不在输入里 → 它在汇总的视野里也不存在
```

> ⭐⭐⭐⭐⭐ **缺失的东西不产生矛盾，于是不会被发现**——
> 与"一致性检查发现不了整体缺失"完全同源。

**② ⭐⭐⭐⭐⭐ 汇总的输出模板里没有"缺失"这一栏**

```
## 结论
## 趋势
## 建议
```

> ⭐⭐⭐⭐⭐ 没有"未纳入"这一节，⭐⭐⭐⭐ 于是缺失没有位置可以出现。

**③ ⭐⭐⭐⭐⭐ "汇总"这个动作本身的语义是"把它们合起来"**

> ⭐⭐⭐⭐⭐ 它不包含"检查有没有少"——
> ⭐⭐⭐⭐⭐ 而作者通常会默认"汇总"隐含了完整性。

---

## 3. ⭐⭐⭐⭐⭐ 三种静默，第二种最常见

**① ⭐⭐⭐⭐⭐ 数字静默**：报总数不报覆盖率

```
"共 200 条"  ← 没说应该是 300 条
```

**② ⭐⭐⭐⭐⭐ 趋势静默**（最常见，也最难发现）

```
B 数据源的区间恰好是增长最快的一段
→ 汇总显示"平稳上升"
→ ⭐⭐⭐⭐⭐ 而真实趋势可能完全不同
```

> ⭐⭐⭐⭐⭐ 关键：**缺失通常不是随机的**。
> 401 的是某个系统、超时的是某段时间、格式错的是某类文件——
> ⭐⭐⭐⭐⭐ 于是缺失会系统性地扭曲趋势方向，而不只是让数字变小。

**③ ⭐⭐⭐⭐⭐ 结论静默**

```
"建议关注 X"  ← 而 X 之所以排第一，是因为缺少了本会反驳它的那个源
```

> ⭐⭐⭐⭐⭐ 三种里它最贵：⭐⭐⭐⭐ 前两种影响的是描述，
> ⭐⭐⭐⭐⭐ 第三种影响的是行动——而行动错了不会有人回来查数据。

## 4. ⭐⭐⭐⭐⭐ 为什么覆盖率被省掉

三个原因，第二个最根本：

**① ⭐⭐⭐⭐⭐ 上游没传 `status: partial`**

```
B 失败了 → 但它的失败没有变成下游可见的状态
→ 下游只看到"两个结果"，以为就该是两个
```

> ⭐⭐⭐⭐⭐ **静默是从上游开始的**：⭐⭐⭐⭐ 上游不标 partial，
> ⭐⭐⭐⭐⭐ 下游就没有理由怀疑完整性——这是《skill-interfaces》的字段问题，
> 但在汇总这一侧才暴露后果。

**② ⭐⭐⭐⭐⭐ 汇总技能不知道"应该有几个"**

```
它拿到 N 个结果 → 只能报 N
⭐⭐⭐⭐⭐ 它不知道 N 应该是多少 —— 除非扇出清单是显式的
```

> ⭐⭐⭐⭐⭐ **没有分母就没有完成**（《skill-output》的
> `enumeration-and-completeness.md`）在汇总层完全适用，
> ⭐⭐⭐⭐⭐ 而多数汇总技能的分母是"我收到了几个"——这是自指的分母。

**③ ⭐⭐⭐⭐⭐ 报缺失会显得"没做完"**

> ⭐⭐⭐⭐⭐ 完成倾向：⭐⭐⭐⭐ 模型倾向于呈现一个完整的结果，
> ⭐⭐⭐⭐⭐ 而"3 个中 2 个"看起来是缺陷——于是它被省略。

---

## 5. ⭐⭐⭐⭐⭐ 修法：汇总必须输出分母

三条，成本都极低：

**① ⭐⭐⭐⭐⭐ 分母来自扇出清单，不是来自收到的结果**

```
扇出前：记下 `expected = [A, B, C]`（写进中间文件）
汇总时：覆盖率 = len(received) / len(expected)
```

> ⭐⭐⭐⭐⭐ 这是唯一能打破自指的办法：
> ⭐⭐⭐⭐⭐ **分母必须在扇出之前就存在**，而不是从收到的东西里数出来。

**② ⭐⭐⭐⭐⭐ 汇总首行必须是覆盖率，不是结论**

```markdown
覆盖率：2/3（67%）· 缺失：source_b（401）
```

> ⭐⭐⭐⭐⭐ 与"把解析后的时间窗口写进输出首行"是同一手法：
> ⭐⭐⭐⭐⭐ 对静默失败，可见性比正确性更值得优先投入。

**③ ⭐⭐⭐⭐⭐ 覆盖率 < 100% 时，输出状态是 partial，不是 ok**

```
⭐⭐⭐⭐⭐ 带着缺口的产物，其正确状态是 partial
```

这与 `placeholder-in-output.md` 咬合：⭐⭐⭐⭐⭐ **"少了一个源"和"有占位符"
是同一类缺陷，都应该让整个产物降级**——而不是让它以 ok 的形态交付。

---

## 6. ⭐⭐⭐⭐⭐ 缺失必须在汇总里占位

只报覆盖率还不够，因为**缺失的那一块在报告里仍然是空白**：

```markdown
## 各来源明细
| 来源 | 记录数 | 状态 |
|---|---|---|
| source_a | 120 | ok |
| ⭐⭐⭐⭐⭐ source_b | — | ⭐⭐⭐⭐⭐ 未获取（401） |
| source_c | 80 | ok |
```

> ⭐⭐⭐⭐⭐ 关键是 source_b **必须占一行**，且写"未获取"而不是省略或写 0。

理由与"0 与未获取"完全一致：

```
❌ 省略 source_b  → 读者以为只有两个源
❌ 写 0          → ⭐⭐⭐⭐⭐ 读者以为那个源真的没有数据
✅ 写"未获取（401）" → 读者知道有这个源、没拿到、为什么
```

三条配套：

```
① ⭐⭐⭐⭐⭐ 趋势段的措辞要带限定："基于 2/3 来源（缺 source_b）"
② ⭐⭐⭐⭐⭐ 缺失源若与结论相关，必须在结论里明示"本结论缺少 X 的交叉验证"
③ ⭐⭐⭐⭐⭐ 不得以"其他来源一致"为由省略缺失——一致性不等于完整性
```

> ⭐⭐⭐⭐⭐ 第 ③ 条最常被违反：⭐⭐⭐⭐ "A 和 C 都这么说"看起来是交叉验证，
> ⭐⭐⭐⭐⭐ 而它们可能恰好是同一类数据源（见第 3 节"缺失不是随机的"）。

## 7. ⭐⭐⭐⭐⭐ 自检

对每一个会汇总多个来源的技能：

```
① ⭐⭐⭐⭐⭐ 分母从哪来？（从收到的结果里数 → 自指，无效）
② ⭐⭐⭐⭐⭐ 覆盖率出现在输出首行吗？
③ ⭐⭐⭐⭐⭐ 缺失的源在明细里占一行吗？写的是"未获取"还是 0？
④ ⭐⭐⭐⭐⭐ 覆盖率 < 100% 时状态标 partial 了吗？
⑤ ⭐⭐⭐⭐⭐ 结论段有没有声明"缺少 X 的交叉验证"？
```

一个十秒判断：

> ⭐⭐⭐⭐⭐ **把汇总输出里的所有总数都加上一句"（共 N 个中的 M 个）"再读一遍。
> 如果读起来突然觉得"这份结论其实很脆弱"——
> 那说明原版一直在用完整的形态掩盖不完整的依据。**
