# 共享参考文档：真的只有一份，所以不漂移——但影响面没人知道

> 相关：《skill-refining》的 `skill-refining/references/shared-thresholds-single-source.md`
> （同一个值被复制 → 副本漂移；解法是立 canonical + 引用）·
> 《skill-structuring》的 `skill-structuring/references/reference-discoverability.md`
> （那一行描述决定 reference 存不存在）·
> `skill-structuring/references/rename-alias-deprecation.md`（改名不会报错，而是静默降级）
> 前置：那份解决⭐⭐⭐⭐ **"复制导致的漂移"**（副本各自演化）；
> 这份解决⭐⭐⭐⭐⭐ **"共享导致的爆炸"**——只有一份、不会漂移，但改它影响 N 个技能，而 N 没写在任何地方。

## 1. 两种"同一个东西出现在多处"

| | 副本 | ⭐ 共享 |
|---|---|---|
| 物理份数 | N 份 | ⭐⭐⭐⭐⭐ 1 份 |
| 会漂移吗 | ⭐⭐⭐⭐⭐ 会（改了 A 没改 B） | 不会 |
| 改一处的影响面 | 1 个技能 | ⭐⭐⭐⭐⭐ N 个技能，且 N 不可见 |

> ⭐⭐⭐⭐⭐ **共享解决了漂移，代价是把"影响面"变成了不可见的东西。**

这不是说共享是错的——恰恰相反，`shared-thresholds-single-source.md` 推荐的就是共享。
问题是共享之后**没有配套任何记录"谁在用"的机制**，于是它被当成了"一个普通文件"来对待。

## 2. ⭐⭐⭐⭐⭐ 你以为改的是一个文件，实际改的是 N 个技能的行为

```
改 references/output-format.md 里的一行
→ 引用它的 5 个技能的输出格式同时变了
→ ⭐⭐⭐⭐⭐ 而这 5 个技能各自的 changelog 里一条都没有
```

最贵的属性：

> ⭐⭐⭐⭐⭐ **技能的变更记录是按技能组织的，而这次变更的载体是一个不属于任何技能的文件。**
> 于是从任何一个技能的版本历史里，都看不到发生过这次变更。

与"运营改了描述导致当天准确率掉一截"是同一类问题，但更难定位：
那个改动至少在某个技能里，这个改动在技能之外。

⭐⭐⭐⭐ 有意思的是：**检测本身很便宜**——`grep -rn "文件名" skill-*/` 一次就出来。
所以瓶颈不是检测手段，是⭐⭐⭐⭐⭐ **"改之前先查"这个动作没有绑定在任何流程里**。

## 3. 三种共享

| 类型 | 怎么形成的 | ⭐ 风险 |
|---|---|---|
| ⭐⭐⭐ 有意共享 | 明确的公共约定文件，大家都引用 | 低（有共识） |
| ⭐⭐⭐⭐ 无意共享 | 名字太通用（output-format.md），两个技能各自引用了同一个 | 中（双方都不知道对方） |
| ⭐⭐⭐⭐⭐ 跨技能借用 | A 直接引用 `skill-B/references/x.md` | 高（见第 4 节） |

第二种的成因很具体：**通用文件名**。两个作者各自写技能时都觉得 output-format.md 是自然的名字，
而目录结构决定了它们会撞在一起（同名文件在不同技能下是不同文件，但若都指向一个公共位置就是同一个）。

---

## 4. ⭐⭐⭐⭐⭐ 第三种最危险：借用方存在，但被借方不知道

A 的正文里写着"格式见 `skill-B/references/x.md`"。

```
B 的作者重构 B → 删掉或改名 x.md
→ ⭐⭐⭐⭐⭐ A 的引用悬空，而 B 的作者不知道 A 存在
```

> ⭐⭐⭐⭐⭐ 关键在于**引用是单向的**：A 里有一条指向 B 的记录，B 里没有任何指向 A 的记录。
> 所以 B 的任何检查（grep B 自己的目录、看 B 的 changelog）都不会发现。

而悬空的后果与"僵尸 reference"一致，且更难发现：

```
模型要读 x.md → 读不到
→ ⭐⭐⭐⭐⭐ 它不会报错，它会按正文剩下的部分继续（参考文档是"需要时读"，读不到不是错误）
```

> ⭐⭐⭐⭐⭐ 删除一个文件在结构上是合法的（不像删除一个被引用的函数会编译失败），
> 所以没有任何机制会阻止这件事。

---

## 5. 删除一个 reference 不会报错

把三种"静默移除"放在一起看才完整：

| 移除 | 症状 | 报错吗 |
|---|---|---|
| 删除 reference 文件 | 模型读不到，按剩余正文继续 | ❌ |
| ⭐⭐⭐⭐ 改名技能 | 旧名调用 → 不存在 → 模型自己想办法 | ❌ |
| ⭐⭐⭐⭐⭐ 改共享文件 | N 个技能行为同时变 | ❌ |

> ⭐⭐⭐⭐⭐ 三者的共同点：**移除的是"运行时才被读取的东西"，而没有任何静态检查覆盖运行时读取。**

## 6. 修法

三条，成本都很低，关键是绑定在流程里而不是靠记得：

```
① ⭐⭐⭐⭐⭐ 借用必须留反向记录：在被借文件头部写一行
   "被 skill-A 引用；改名或删除前必须通知 A"
② ⭐⭐⭐⭐ 共享文件显式标注 owner 与影响面，不放进任何人"自己的"目录
③ ⭐⭐⭐⭐⭐ 删除/重命名任何 reference 之前，硬门槛：
   grep -rn "<文件名>" skill-*/  → 有命中就必须先处理引用方
```

> ⭐⭐⭐⭐⭐ 第①条的价值不在提醒，在⭐⭐⭐⭐ **它把单向引用变成双向可见**——
> 这正是第 4 节那个缺失的东西。

第③条要写成 CI 能跑的形式才有意义（与"规则升级为代码"同源）：
⭐⭐⭐⭐ 只写在规范里等于没写，因为删除文件时没人会去读规范。

另外一条反直觉的：**共享不总是要做成"提取公共文件"**。
若两个技能只是碰巧名字相同而语义不同（A 的"输出格式"是表格、B 的是 JSON），
⭐⭐⭐⭐⭐ **强行共享会把两个不同的约定粘成一个，之后任何一方调整都直接影响另一方**——
这比复制更糟，因为复制至少还能各自演化。

---

## 7. 检查清单

- [ ] ⭐⭐⭐⭐⭐ 凡被其他技能引用的 reference，文件头部写明"被谁引用"
- [ ] ⭐⭐⭐⭐⭐ 删除/重命名 reference 前必须 grep 全库，有命中先处理引用方
- [ ] ⭐⭐⭐⭐ 共享文件放在公共位置并标注 owner，不放进单个技能目录
- [ ] ⭐⭐⭐⭐ 通用文件名（output-format.md 等）先确认语义是否真的一致再共享
- [ ] ⭐⭐⭐ 上述 grep 写成 CI 检查，不只写在规范里
