## 1. ⭐⭐ 字段约束表

| 字段 | 必填 | 约束 |
|---|---|---|
| `name` | ✅ | ⭐ **最多 64 字符**；仅小写字母、数字、连字符；**不能以连字符开头/结尾，不能含连续连字符**；⭐ **必须与父目录名一致** |
| `description` | ✅ | ⭐ **最多 1024 字符**；说明做什么与何时用；应含帮助识别任务的关键词 |
| `license` | — | 许可证名或打包的许可证文件引用 |
| `compatibility` | — | ⭐ 最多 500 字符；环境要求（目标产品、系统包、网络访问） |
| `metadata` | — | 任意键值映射（作者、版本等） |
| `allowed-tools` | — | ⭐ 空格分隔的预批准工具列表；**实验性——各实现支持不一** |

> ⭐⭐ `name` 的"必须与父目录名一致"这一条容易漏，
> 而且⭐ **不一致会导致加载失败**（见下节）。
> 这与 `naming-conventions.md` 的 kebab-case 要求是一致的，
> 但那份没提"必须与目录名相同"这个⭐ 硬性对应关系。

**大小写与重复**：

```
⭐ 识别的顶层字段名必须用⭐ 小写拼写，且只能出现一次
（Python 文件型与 MCP 打包型加载器把 metadata 的键当⭐ 区分大小写的字符串）
```

## 2. ⭐⭐⭐ 会让技能加载失败的硬条件

> ⭐⭐⭐ 以下任何一条都会**阻止技能加载**（不是警告，是加载不了）：

```
① ⭐ 无效 YAML
② ⭐ 重复的已识别字段
③ ⭐ 字段大小写错误
④ ⭐⭐ 期望标量处给了集合（collection where a scalar is expected）
```

**不会阻止加载的**（对比记忆）：

```
✅ ⭐ 未知的顶层字段 → ⭐ 为向前兼容而忽略
✅ ⭐ metadata 里无效的条目（含嵌套集合）→ ⭐ 跳过并警告
   （完全重复的键保留第一个有效值并记警告）
```

> ⭐⭐⭐ 这个区分很实用：**top-level 字段错了 = 加载失败；
> metadata 里的东西错了 = 只警告**。
> 这解释了 `frontmatter-pitfalls.md` 里那个困惑——
> "为什么有的错是静默失败、有的只是警告"。
>
> ⭐⭐ 而"期望标量处给了集合"正是最常见的踩法：
> `tools: [a, b]` 在多数系统要求⭐ 块序列（多行 `- a`），
> 或者⭐ 单值也要写成数组——取决于实现。

## 3. ⭐⭐ 四阶段渐进式披露

```
① Advertise（~100 tokens/技能）
   ⭐ 名称与描述在⭐ 每次运行开始时注入 system prompt
② Load
   触发后加载 SKILL.md 正文
③ ⭐ 按需加载引用的文件（references/）
④ ⭐⭐ 脚本在⭐ 上下文窗口之外执行
```

> ⭐⭐ 第 ④ 条是常被漏掉的一层，也是最省的一层：
> **脚本执行不占上下文**（呼应 `scripts-as-production.md`）。
>
> ⭐⭐⭐ 但要注意它带来的约束：
> **脚本的输出会占上下文**——
> 所以 `script-cli-contract.md` 的"stdout 只放结果、stderr 放调试"
> 才那么重要：⭐ 脚本本身不占上下文，但它的输出会。

**正文长度要求**：

```
⭐ "SKILL.md 保持在 500 行以内，详细参考材料移到单独文件"
```

> ⭐⭐ 这与 `budget-truncation.md` 的"压缩后每个技能只留前 5,000 tokens"
> 对上了——**500 行 × 4 字符 ≈ 20,000 字符 ≈ 5,000 tokens，
> 所以 500 行这个数字不是拍的，是⭐ 由物理边界倒推出来的。**
> 之前我们是从 token 推出来的，这里从行数给了交叉验证。

## 4. ⭐⭐ 正文风格：Markdown，不是 XML

> ⭐⭐ **SKILL.md 正文用⭐ 纯 Markdown——标题、粗体标签、项目符号列表，
> ⭐⭐⭐ 不要用 XML 标签骨架（不要 `<instructions>` / `<rules>` 等）。**

**理由**（跨厂商验证，2026-07-11）：

```
· ⭐ 符合 Anthropic 自己的 SKILL.md 编写示例
· ⭐ 符合 OpenAI 当前（GPT-5.5/5.6）的模型指引格式
· ⭐⭐ 只有 Gemini 的文档把 XML 和 Markdown 视为等价
  → ⭐⭐⭐ 所以 Markdown 是⭐ 更安全的跨平台默认值
```

**XML 仍然正确的窄场景**：

```
⭐ 运行时提示词（runtime prompts）——⭐ 指令与嵌入数据混合的地方
   ⭐ 典型：子代理提示词（subagent prompts）
⭐⭐ 不适用于 SKILL.md 正文——正文不用标签
```

> ⭐⭐⭐ 这个区分很关键：**很多人把所有地方都写成 XML，或全部写成 Markdown。
> 正确的切法是⭐ 看有没有"指令与数据混合"**——
> 子代理提示词里要塞进动态数据，才需要标签做边界；
> SKILL.md 是静态指令，不需要。

**标题层级**：

```
⭐ 层级一致（不跳级 H2 → H4）
H1 = 仅文件标题 · H2 = 主要章节 · H3 = 子章节
⭐ 避免 H4+（意味着过度嵌套）
```

## 5. ⭐⭐⭐ 用项目符号，不用表格

> ⭐⭐ **指令和参考数据⭐ 都用项目符号列表，不用表格。**
> ⭐ 嵌套列表不超过 2 层。

**给的正例**：

```markdown
- Always use `uv` for Python packages
- Type hints on all public functions
- Run tests before committing

**Context thresholds:**
- Claude Code: 50% warning, 60% critical
- Cursor: 70% warning, 80% critical
```

> ⭐⭐⭐ **这条与我们这套库的习惯相反**——
> 我们的 references 大量使用表格。
>
> ⭐ 诚实的判断：**两种写法各有适用场景，不能盲从**：
>
> ```
> 表格适合：⭐ 多维度对照、需要横向比较、⭐ 给人快速扫读
> 列表适合：⭐ 指令序列、⭐ 需要被逐条执行、⭐ 嵌套结构
> ```
>
> ⭐⭐ 但有个⭐ 可操作的折中判据值得采纳：
> **⭐ "要被执行的"用列表，"要被比较的"用表格。**
>
> ```
> Critical Rules / 检查清单 / 步骤 → ⭐ 列表（可逐条打勾）
> 维度对照 / 参数表 / 前后对比   → 表格（需要横向看）
> ```
>
> ⭐ 我们库里"速查清单"用的是列表、对照用的是表格，
> 恰好符合这个判据——所以这条劝告⭐ 对我们是印证而非推翻。
> 值得改的是：⭐ 把表格里那类"其实要被逐条执行"的内容改成列表。

**Good / Avoid 对照的写法**：

```
⭐⭐ 放进单独的 ### Good / ### Avoid 子标题
⭐⭐ 绝不混在同一个块里
```

## 6. ⭐⭐ 肯定句优先 + Hard Limits 章节

> ⭐⭐ **优先告诉 agent 该做什么，而不是不该做什么。**

```
❌ "Never commit unless asked"
✅ ⭐ "Only commit when the user explicitly asks"
```

> ⭐⭐⭐ 注意这条与我们已有的⭐ 两条结论的张力：
>
> ```
> A. guidance-forms.md：禁令可能反噬（正文里"不要做X"因没给替代而更差）
> B. activation-rate.md：⭐⭐ description 里⭐ 祈使句+否定约束 = 100% 激活
> ```
>
> ⭐⭐ 本条与 A ⭐ 完全一致（都是"给替代方案而不是纯禁令"）；
> ⭐⭐ 与 B 的张力可以这样仲裁：
> **B 的否定约束形式是 "NOT for X → 用 Y 代替"——
> ⭐ 它自带替代方案，所以不是纯禁令。**
> 三条其实指向同一条：⭐⭐⭐ **禁令必须配替代方案，否则无效或有害。**

**Hard Limits 章节**：

```
⭐⭐ 为⭐ 没有自然肯定表述的残余禁令⭐ 保留一个 ## Hard Limits 章节
   （密钥、force-push、不可逆删除）
⭐⭐ 保持简短——⭐⭐⭐ 如果那里的条目一直在累积，
   ⭐ 说明其中一些其实存在⭐ 还没被找到的肯定式改写
```

> ⭐⭐⭐ 最后半句是个很好的自检信号：
> **Hard Limits 越长，说明你偷懒没去找肯定式写法。**
> 这与 `write-reasons-not-rules.md` 的
> "数一数'必须/禁止'的个数，一屏好几个就该改"是同一个思想。

## 7. ⭐ Token 预算

```
AGENTS.md 入口        < 500 tokens
单个标准文件          < 2000 tokens
SKILL.md 文件         < 500 行（~5000 tokens 上限）
⭐ 会话总计           < 5000 tokens（索引 + 1–2 个活跃技能）
```

> ⭐⭐ "会话总计 < 5000（索引 + 1–2 个活跃技能）"这条很有意思：
> ⭐⭐ 它默认你一次只有⭐ **1–2 个技能活跃**。
> 所以⭐ 如果你的工作流同时需要 5 个技能，就已经超出设计假设了——
> 这与 `skill-chaining-composition.md` 的组合成本、
> `library-size-effect.md` 的遮蔽是同一件事的不同侧面。

**结构建议**（可直接照做）：

```
· ⭐ 加一行 metadata 声明 Load if 条件
· ⭐ 关键规则放靠近顶部
· ⭐ 检查清单/行动项放靠近底部
· ⭐ 加 Related 章节做交叉引用
```

> ⭐ 后两条与 `budget-truncation.md` 的
> "压缩只保留前 5000 tokens → 关键指令必须在顶部"完全对上：
> ⭐⭐ **关键规则靠顶，是因为截尾会先砍掉底部。**

## 速查

```
□ ⭐ name ≤64 字符、kebab-case、⭐⭐ 必须与父目录名一致
□ ⭐ description ≤1024 字符
□ ⭐ compatibility ≤500 字符
□ ⭐ allowed-tools 空格分隔 · ⭐ 实验性，各实现支持不一

□ ⭐⭐⭐ 加载失败（硬）：无效 YAML · ⭐ 重复已识别字段
   ⭐ 字段大小写错 · ⭐⭐ 期望标量处给了集合
□ ✅ 只警告：未知顶层字段（忽略）· metadata 无效条目（跳过）
   ⭐⭐ 区分记忆：top-level 错=加载失败；metadata 错=只警告

□ ⭐⭐ 四阶段：Advertise(~100/技能) → Load → 按需加载文件
   → ⭐⭐ 脚本在上下文外执行（⭐ 但其输出会占上下文）
□ ⭐⭐ SKILL.md <500 行（⭐ 由 5000 tokens 物理边界倒推）

□ ⭐⭐ Markdown 不用 XML（Anthropic/OpenAI 一致；Gemini 两者等价）
   ⭐ 例外：⭐ 运行时提示词/子代理提示词（指令与数据混合）才用 XML 标签
□ 标题不跳级，避免 H4+

□ ⭐⭐⭐ 列表还是表格：⭐⭐ "要被执行"用列表，"要被比较"用表格
   ⭐ 嵌套 ≤2 层 · ⭐⭐ Good/Avoid 放单独子标题，绝不混一块
□ ⭐⭐ 肯定句优先；⭐⭐⭐ Hard Limits 越长=越偷懒
□ ⭐ 预算：AGENTS.md<500 · 单文件<2000 · SKILL.md<500行
   ⭐⭐ 会话<5000（⭐ 隐含假设：一次只有 1–2 个活跃技能）
□ ⭐⭐ 关键规则靠顶（截尾先砍底部），检查清单靠底
```

**一句话**：

> ⭐⭐⭐ **top-level 字段写错（无效 YAML / 重复 / 大小写错 / 该给标量却给了集合）
> 会让技能直接加载不了，而 metadata 里的错误只警告——
> 这个区分是排查"为什么我的技能根本不出现"的第一道分诊。**
