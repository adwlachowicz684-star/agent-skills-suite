## 1. ⭐⭐ 四层与 specificity

指令从四个来源到达 agent，⭐ 每层在会话生命周期的不同时刻加载：

```
① System prompt      （最外层，工具/平台设定）
② Project instructions（AGENTS.md / CLAUDE.md / copilot-instructions.md）
③ Skill content      （SKILL.md，技能运行时加载）
④ ⭐ User message    （最内层，当下任务）
```

> ⭐⭐ **每层都比它上面那层更具体。
> ⭐⭐ 冲突时⭐ 具体性通常决定优先级。**
>
> ⭐⭐⭐ **但注意：⭐ 这是⭐ 行为倾向，不是模型强制执行的正式规则。**
> ⭐⭐⭐ **层与层之间的矛盾会产生⭐ 不可预测的输出。**

> ⭐⭐ 这条"是倾向不是规则"的声明很重要——
> 它解释了为什么"优先级链"能解决大多数问题但不是全部，
> ⭐⭐⭐ 以及为什么⭐ **避免跨层矛盾比记住优先级顺序更根本**。

## 2. ⭐⭐⭐ 每层该放什么

| 层 | 该放 | ⭐ 不该放 |
|---|---|---|
| System | 角色、权限、基线约束 | — |
| ⭐ Project | ⭐⭐ 对⭐ 每个任务都成立的约定/约束/工具偏好 | ⭐⭐⭐ 任务特定的规则 |
| ⭐ Skill | ⭐⭐ 只适用于⭐ 这类任务的知识 | ⭐⭐⭐ 重复项目层已有的约定 |
| ⭐ User message | ⭐ 当下的具体任务 | 长期约定 |

**两条最值得记住的**：

```
⭐⭐⭐ ① Project 层：⭐ "这条规则对每个任务都成立吗？"
       不是 → ⭐ 它不属于这里

⭐⭐⭐ ② Skill 层：⭐⭐ "在项目层重复约定 = ⭐ 制造第二个真相来源，它会漂移"
       ⭐⭐ 技能应当⭐ 扩展或细化项目指令，⭐⭐⭐ 不重复它们
```

> ⭐⭐⭐ 第 ② 条与"不要在技能里写模型已知信息"、
> "参考文档给链接+摘要不全文复制"是同一条：
> ⭐⭐ **同一件事只应在一个地方被定义。**

**一个说明分层价值的好例子**：

```
项目层 CLAUDE.md："新函数必须写测试"
用户消息："生成这个 helper——先跳过测试，我稍后加"
→ ⭐ 用户消息赢（更具体），函数无测试生成

⭐⭐ 然后加一个代码评审技能，规则是"标记任何没有对应测试的函数"
→ ⭐⭐⭐ 它在同一函数上运行时⭐ 依然会标记
   ⭐⭐⭐ 因为"标记"不冲突——先前那条用户消息是关于⭐ 生成，不是关于⭐ 评审
```

> ⭐⭐⭐ **这个 gap 是刻意的**：
> **项目层定策略，技能层按场景执行，用户消息限定当下动作。**
> ⭐⭐ 分开放，技能才⭐ 不会被一条本不适用于它的用户消息噤声。

## 3. ⭐⭐⭐ 位置偏差：埋在中间的指令会被忽略

> ⭐⭐⭐ **指令遵循率⭐ 随约束在提示中的⭐ 位置⭐ 显著变化，
> ⭐⭐ 存在可测量的⭐ 首因效应与近因效应（Purpura et al., 2026）。**
>
> ⭐⭐⭐ **靠近开头的约束⭐ 比埋在中间的⭐ 被遵循得更可靠。**

**因此的操作建议**：

> ⭐⭐⭐ **对关键规则，⭐ 在两端都重复一遍。**

> ⭐⭐⭐ 这条是全新的、且立刻可用的——
> 它给了一个此前没出现过的⭐ 排版层面的干预手段：
> 不是"写得更严厉"，而是⭐ **放在开头和结尾**。
>
> ⭐⭐ 而且它与我们已有的两条完全咬合：
> ```
> · 压缩只保留前 5000 tokens → 关键指令在顶部
> · 模型会用 head -100 预览长文件 → 顶部放目录
> ```
> ⭐⭐⭐ 三条独立证据指向同一结论：**开头是黄金位置，结尾是次优，中间是黑洞。**

## 4. ⭐⭐⭐ 子代理打破整个层叠

> ⭐⭐⭐ **子代理⭐ 不继承父代理的上下文。**
>
> 它从⭐ 自己的 system prompt 全新开始（通常是调用时注入的那个），
> ⭐⭐⭐ **父级的项目指令、已加载的技能、会话历史⭐ 都不存在，
> ⭐⭐ 除非显式传入。**

**后果**：

```
⭐⭐⭐ 子代理⭐ 可能违反父代理一直在遵守的项目约定
   ⭐⭐ ——除非父级⭐ 显式把相关约束传下去
```

**调试要点**（这句很关键）：

> ⭐⭐⭐ **调试要查的是⭐ 子代理在调用那一刻收到了什么，
> ⭐⭐ 而不是父代理当时拥有什么。**

> ⭐ 这与 `subagent-skill-inheritance.md` 的
> "子代理不继承技能，必须显式列 skills:"完全一致，
> ⭐⭐ 但这里把它放进了⭐ 四层模型里：
> **委派时，② ③ 两层默认都不存在，只有①④。**

## 5. ⭐⭐ 按层诊断

**当 agent 忽略一条指令时，按层问**：

```
① ⭐ 这条指令来自哪一层？
   ⭐⭐ 埋在长 AGENTS.md 中间的指令⭐ 在与位置偏差竞争

② ⭐⭐ 有没有更接近任务的冲突指令？
   例：一句"先跳过测试"就压过了项目层"总是写测试"

③ ⭐⭐⭐ 是子代理吗？
   如果是，⭐ 项目层指令可能⭐ 根本不在它的上下文里

④ ⭐⭐ 是不是超过了合规上限？（见下）
```

---

## 6. ⭐⭐ 合规上限

```
⭐⭐⭐ 栈里的规则越多，⭐⭐ 优先级低的规则⭐ 越可能被忽略
```

> ⭐⭐⭐ 这给了"惜字如金"一个⭐ 更精确的机制解释：
> 不只是省 token，
> ⭐⭐ **每多一条规则，都在稀释其他所有规则的被遵守概率**。
>
> ⭐ 与 `library-size-effect.md` 的遮蔽、
> `capability-offset-net-gain.md` 的 59% 抵消同源——
> ⭐⭐⭐ **注意力是稀缺资源，规则之间在竞争它。**

## 速查

```
□ ⭐⭐ 四层：System → Project(AGENTS.md/CLAUDE.md) → Skill → ⭐ User message
   ⭐⭐⭐ ⭐ 具体性决定优先级 = ⭐ 行为倾向，⭐ 不是模型强制的规则
   ⭐⭐⭐ 层间矛盾 → ⭐ 不可预测的输出

□ ⭐⭐⭐ Project 层只放"对每个任务都成立"的；否则属于 Skill 层
□ ⭐⭐⭐ ⭐ Skill 层不重复项目约定 = ⭐ 避免第二个真相来源漂移
□ ⭐⭐⭐ 分层让技能不会被一条本不适用它的用户消息噤声

□ ⭐⭐⭐ ⭐ 位置偏差：⭐ 开头 > 结尾 > 中间（首因/近因效应，Purpura 2026）
   ⭐⭐⭐ ⭐ 关键规则在两端都写一遍
   （与"压缩留前 5000 token""head -100 预览"三条证据同源）
□ ⭐⭐⭐ ⭐ 子代理打破层叠：②③ 两层默认不存在
   ⭐⭐ 调试要查"子代理收到了什么"，不是"父代理有什么"
□ ⭐⭐⭐ 规则越多，低优先级规则越可能被忽略 = 惜字如金的机制解释
```

**一句话**：

> ⭐⭐⭐ **指令分四层（System / Project / Skill / User），具体性决定优先级但那只是行为倾向不是强制规则——所以避免跨层矛盾比记住优先级更根本；
> 而位置偏差实证指出：靠近开头的约束比埋在中间的被遵循得更可靠，关键规则要在两端都写一遍。**
