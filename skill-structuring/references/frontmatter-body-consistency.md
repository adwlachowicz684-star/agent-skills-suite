## 1. ⭐⭐⭐⭐⭐ 一个能正常工作的坏技能

```
description: 分析销售数据，识别趋势，并输出可执行的改进建议
```

正文：

```markdown
## 流程
1. 读取数据
2. 识别趋势
3. 输出趋势摘要
```

> ⭐⭐⭐⭐⭐ "可执行的改进建议"在正文里**一个字都没有**。

而它的表现：

```
✅ YAML 合法
✅ name 合规
✅ 触发正常（description 写得很好）
✅ 输出了趋势摘要，格式正确
❌ ⭐⭐⭐⭐⭐ 承诺的第三项从未出现，且没人注意到
```

---

## 2. ⭐⭐⭐⭐⭐ 为什么它比字段写错更危险

对比两类问题：

| | 症状 | 谁会发现 |
|---|---|---|
| ⭐⭐⭐⭐ frontmatter 写错 | 技能不出现 / 手动能用自动不能 | ⭐⭐⭐⭐ 立刻（看不见就是坏了） |
| ⭐⭐⭐⭐⭐ 正文没跟上 | ⭐⭐⭐⭐⭐ 一切正常，只是少了一部分 | ⭐⭐⭐⭐⭐ **没人** |

> ⭐⭐⭐⭐⭐ 关键差别：⭐⭐⭐⭐⭐ **缺失的部分不会报错，因为没有任何环节在等它。**

而它的后果是双向的：

```
① ⭐⭐⭐⭐ 用户按 description 的承诺期待一个东西，没等到
② ⭐⭐⭐⭐⭐ 更糟：description 承诺越宽，触发越多，
   于是"少做一点"这件事发生的次数越多
```

> ⭐⭐⭐⭐⭐ 第 ② 条是本份最该记住的：
> ⭐⭐⭐⭐⭐ **我们花了很多力气让 description 更容易命中，
> 而它每多命中一次，正文的缺口就被兑现一次。**

## 3. ⭐⭐⭐⭐⭐ 四类不一致

**① ⭐⭐⭐⭐⭐ 承诺了能力，正文没实现**（第 1 节的例子）

**② ⭐⭐⭐⭐⭐ 正文实现了，description 没说**

```
正文里有"支持多种输出格式"
description 只说"生成报告"
```

> ⭐⭐⭐⭐⭐ 后果是**永不触发的分支**——
> 它占着上下文，但永远没机会被用到。
> 这与"死代码"完全同构，只是**死代码不占运行开销，死分支占**。

**③ ⭐⭐⭐⭐⭐ description 里写了正文没有的限制**

```
description: 仅适用于 Python 项目
正文：完全没有做语言检查
```

> ⭐⭐⭐⭐⭐ 于是"仅适用于"这句只在**触发阶段**起作用
> （不该触发的输入被拦住了），⭐⭐⭐⭐ 而真正该拦的地方（执行时）没拦。
> 这正是⭐⭐⭐⭐⭐ "声明不是强制"的又一个变体。

**④ ⭐⭐⭐⭐⭐ 示例与正文规则冲突**

```
正文：不要编造数据
示例：输出里出现了一个正文规则禁止的东西
```

> ⭐⭐⭐⭐⭐ 按《skill-examples》的结论，示例的优先级高于指令——
> ⭐⭐⭐⭐⭐ **所以冲突时赢的是示例，而评审者读的是正文。**

## 4. ⭐⭐⭐⭐⭐ 单向一致性检查

检查方向很重要：

```
❌ 从正文出发，问"description 说到了吗" → 会漏掉第①类
✅ ⭐⭐⭐⭐⭐ 从 description 出发，问"正文里有吗" → 四类全覆盖
```

> ⭐⭐⭐⭐⭐ 理由：⭐⭐⭐⭐⭐ **正文更长，从长的一侧出发会天然觉得"都写了"；
> 从短的一侧出发，每一项都必须被指认到正文的具体位置。**

操作（人工，一分钟）：

```
把 description 按逗号/顿号拆成 N 个承诺
逐个在正文里找对应章节
找不到 → ⭐⭐⭐⭐⭐ 记下来，这就是缺口
```

> ⭐⭐⭐⭐⭐ 这个拆法还顺带解决了另一件事：
> ⭐⭐⭐⭐ 拆出来的项数 N 本身就是范围检查——
> N 过大说明一个 description 里塞了太多承诺（与"一技能一职责"呼应）。

## 5. ⭐⭐⭐⭐⭐ 修哪一边

发现不一致后有两个方向，而默认方向常常是错的：

```
默认反应：把 description 改窄（让它只承诺正文有的）
⭐⭐⭐⭐⭐ 常常错的：因为那个承诺可能正是用户真正需要的
```

判据三条：

**① ⭐⭐⭐⭐⭐ 这个承诺是"用户需要"还是"为了好触发"？**

```
为触发而写 → 删（这是⭐⭐⭐⭐⭐ 关键词堆砌的隐蔽形态）
用户真的需要 → 补正文
```

**② ⭐⭐⭐⭐⭐ 补正文的成本 vs 触发损失**

```
description 是杠杆最大的地方（改它能带来 50% 效果变化）
→ ⭐⭐⭐⭐ 所以轻易改窄它，代价可能远大于补几行正文
```

**③ ⭐⭐⭐⭐⭐ 有正文没 description（第②类）→ 优先改 description**

> ⭐⭐⭐⭐⭐ 这一条几乎总是该改 description：
> ⭐⭐⭐⭐ 功能是现成的，只需要让它有机会被用到，成本最低。

## 6. ⭐⭐⭐⭐⭐ 让它变成可检查的

三条机械化手段，按成本递增：

**① ⭐⭐⭐⭐⭐ 正文里显式列出"本技能交付什么"**

```markdown
## 交付物
本技能承诺交付且必须出现在输出中的三项：
1. 趋势识别
2. 改进建议
3. 数据覆盖说明
```

> ⭐⭐⭐⭐⭐ 有了这一节，"承诺 vs 实现"变成**同一份文件内的对照**，
> ⭐⭐⭐⭐⭐ 而不是跨文件（frontmatter vs 正文）的对照——
> 后者没人会做，前者写完就在眼前。

**② ⭐⭐⭐⭐ 用验收条件把承诺变成断言**

```markdown
## 验收
输出必须包含：趋势（≥1 条）、建议（≥1 条且含动作与期限）
```

**③ ⭐⭐⭐⭐ grep 检查**

```bash
# 提取 description，人工拆项后逐项 grep 正文
grep -oP '(?<=^description: ).*' SKILL.md
```

> ⭐⭐⭐⭐⭐ 与含糊词、无出处数字那两份一样：
> ⭐⭐⭐⭐⭐ **只有能变成一条命令的检查才会真的被执行。**
> 而这一条尤其适合放进 CI，因为它是纯文本对照，不需要运行模型。

## 7. ⭐⭐⭐⭐ 例外

两种"不一致"是合理的，不要修：

**① ⭐⭐⭐⭐⭐ description 里的反触发条件**

```
"NOT for 简单的单文件改动"
```

> ⭐⭐⭐⭐⭐ 它本来就不该在正文里有对应实现——
> ⭐⭐⭐⭐ 它的作用是**不触发**，正文是触发后才加载的。
> 这与《skill-patterns》的 `skill-patterns/references/skill-anatomy-antipatterns.md` 那条
> "正文里不要有 When to Use 章节"是同一个道理。

**② ⭐⭐⭐⭐⭐ 平台约定的标准能力**

```
"支持 --help" 之类由框架提供的能力
```

> ⭐⭐⭐⭐ 不属于技能自己实现的部分，不需要正文对应。

判据收口：

> ⭐⭐⭐⭐⭐ **需要技能自己"做"出来才算数的承诺，必须有正文对应；
> 用来"拦"或不由技能实现的，不必。**
