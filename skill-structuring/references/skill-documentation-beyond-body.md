## 1. ⭐⭐⭐⭐⭐ 正文不是文档

> ⭐⭐⭐⭐⭐ **SKILL.md 是给模型读的执行指令，不是给人读的说明。**

两者需求相反：

| | 给模型（SKILL.md） | ⭐⭐⭐⭐⭐ 给人（README） |
|---|---|---|
| 长度 | ⭐⭐⭐⭐ 越短越好 | 可以长 |
| 冗余 | ⭐⭐⭐⭐ 删（同义复述是干扰） | ⭐⭐⭐⭐ 需要（人靠冗余定位） |
| 结构 | ⭐⭐⭐⭐ 开头是黄金位置 | 可以随时跳转 |
| 语气 | ⭐⭐⭐⭐⭐ 命令式、无解释 | 需要解释与背景 |

> ⭐⭐⭐⭐⭐ 这就解释了一个常见困境：
> **你为了让同事看懂而往正文里加的背景说明，正在降低技能的效果。**
> 而为了让模型跑得准而删掉的那些解释，正是同事最需要的。

结论：**两者必须分开**。而因为 README 不在渐进式披露的加载链里，
⭐⭐⭐⭐⭐ **所以 README 里写再多也不会产生 token 成本**——
它是"免费"的文档空间，被严重低估了。

## 2. ⭐⭐⭐⭐ README 该写什么

五块，按人读的顺序：

**① ⭐⭐⭐⭐⭐ 这个技能解决什么问题（含"什么时候不该用"）**

```markdown
## 用途
把散落的会议记录整理成结构化周报。

⭐ 不适用：
- 需要对外发送的正式报告（用 report-external）
- 只有一条记录时（直接写即可，不值得跑）
```

> ⭐⭐⭐⭐⭐ "不适用"那部分比"用途"更值钱：
> 人最容易犯的错不是不会用，是**在错的场景用了**。
> 这与正文里的反触发是同一件事的两面（一个给模型，一个给人）。

**② ⭐⭐⭐⭐⭐ 前置条件**

```
需要什么权限 · 需要哪些文件存在 · 需要什么外部服务可用
```

> ⭐⭐⭐⭐⭐ **这是 README 里唯一必须和正文严格一致的部分**——
> 不一致会导致"文档说能跑、实际跑不了"。
> 判据：**能直接对应 `data-dependency-declaration.md` 那张表。**

**③ ⭐⭐⭐⭐ 使用示例（真实的，含输入长什么样）**

```
输入：一份 40 条的会议记录
输出：按议题分组的周报（约 800 字）
耗时：约 30 秒
```

**④ ⭐⭐⭐⭐ 已知限制**

```
- 不支持超过 200 条的输入（会截断）
- 中文文件名在某些平台上会匹配失败
```

**⑤ ⭐⭐⭐⭐ 维护信息**

```
Owner · 最后更新时间 · 上游来源（若是 fork）
```

## 3. ⭐⭐⭐⭐⭐ 不该写进 README 的

三条：

**① ⭐⭐⭐⭐⭐ 安装步骤**

> ⭐⭐⭐⭐⭐ **"把目录复制到 ~/.claude/skills/" 这句话在技能被安装之后是废话。**
> 人是在已经装上之后才读 README 的。
> 安装说明属于分发渠道（市场页面/仓库首页），不属于技能自身。

**② ⭐⭐⭐⭐⭐ 安全约束**

> ⭐⭐⭐⭐⭐ **写在 README 里的安全约束，agent 根本读不到**
> ——README 不在加载链里。
> ⭐⭐⭐⭐ 要写必须写进正文流程（默认 dry-run、禁止生产写）。

> ⭐⭐⭐⭐⭐ 这条最危险，因为它看起来"已经写过了"：
> 评审者看到 README 里有安全说明就签字了，
> 而实际运行的那份指令里什么都没有。

**③ ⭐⭐⭐⭐ 与正文重复的流程描述**

> ⭐⭐⭐⭐ 重复 = 两份都会腐烂，且你会改一个忘另一个。
> README 应该**指向正文**（"流程见 SKILL.md"），不是复述它。

## 4. ⭐⭐⭐⭐ 三个常被漏的字段

**① ⭐⭐⭐⭐⭐ 变更记录（CHANGELOG）**

```
不是给模型的，是给"这次行为怎么变了"的人看的
```

> ⭐⭐⭐⭐⭐ 与 `version-changelog-practice.md` 的差别在读者：
> 那份的读者是**下游维护者**（他们要知道会不会断），
> 这份的读者是**使用者**（他们要知道现在会怎样）。
> ⭐⭐⭐⭐ 所以 README 里的变更记录要写"对你有什么影响"，
> 不是"改了哪个文件"。

**② ⭐⭐⭐⭐⭐ 失败案例**

```
"输入超过 200 条时会静默截断（2026-05 修复中）"
```

> ⭐⭐⭐⭐⭐ **正例人人写，失败案例没人写，
> 而后者才是用户真正会遇到的。**
> 这与"评测集要含失败路径"是同一条原则——
> ⭐⭐⭐⭐ 顺利路径你早跑过几十遍了。

**③ ⭐⭐⭐⭐ 与其它技能的关系**

```
本技能是 X 的上游；若同时需要 Y，先跑本技能
```

> ⭐⭐⭐⭐ 这一块在只有几个技能时没必要，
> ⭐⭐⭐⭐⭐ 但超过 10 个之后它是唯一能回答"该用哪个"的东西
> （与"超过 10 个技能，误触发就从边缘情况变成主要维护负担"对上）。

## 5. ⭐⭐⭐⭐ 文档也会腐烂

三种腐烂，按隐蔽程度：

| 种类 | ⭐ 症状 |
|---|---|
| ⭐⭐⭐⭐ 前置条件变了 | 文档说要 A，实际要 B → 跑不了，且报错指向别处 |
| ⭐⭐⭐⭐⭐ 限制被修复了但没更新 | ⭐⭐⭐⭐⭐ **用户绕开了一个不存在的限制**（最隐蔽） |
| ⭐⭐⭐⭐ 示例过期 | 输出格式已变，文档还是旧样 |

> ⭐⭐⭐⭐⭐ 第二种最值得记：
> **过时的限制比没有限制更有害**——
> 它会让人做无谓的规避动作，而且永远不会有人来报 bug
> （因为"按文档绕开了"看起来是正常的）。

对策（与 `review_after` 同思路）：
⭐⭐⭐⭐ **README 里写"最后验证时间"**，且
⭐⭐⭐⭐⭐ **每次改正文时强制问一句"README 要不要改"**——
把它做成 PR 模板的一行，而不是靠记得。

## 6. ⭐⭐⭐⭐ 最小可用文档集

```
README.md
  用途 + ⭐⭐⭐⭐⭐ 不适用
  ⭐⭐⭐⭐⭐ 前置条件（与正文严格一致）
  一个真实示例
  已知限制 + ⭐⭐⭐⭐⭐ 失败案例
  最后验证时间 / Owner
```

> ⭐⭐⭐⭐⭐ 不到 40 行，但对"别人能不能用起来"的影响，
> ⭐⭐⭐⭐⭐ 大于正文里任何一段措辞的打磨。

一个自检：

> ⭐⭐⭐⭐⭐ **让一个没见过这个技能的人，只看 README，
> 说出"我该在什么情况下用它"。**
> 说不出来 → README 缺的是第 ① 块的"不适用"部分。
