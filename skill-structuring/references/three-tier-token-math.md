## 1. ⭐⭐⭐⭐ 三级加载模型

| 层级 | 内容 | ⭐ 何时加载 | ⭐⭐ 成本 |
|---|---|---|---|
| **L1 元数据** | YAML frontmatter 的 name + description | ⭐⭐⭐ 始终，启动时 | ⭐⭐⭐⭐ **每技能约 30–50 tokens** |
| **L2 正文** | SKILL.md 主体 | ⭐⭐⭐ Claude 判断相关时 | ⭐⭐⭐ 200–500 行 ≈ **2K–5K tokens**，触发时整份加载 |
| **L3 参考/脚本** | `references/*.md`、可执行脚本 | ⭐⭐⭐⭐ 按需——仅在 SKILL.md 链过去且 Claude 读了 | ⭐⭐⭐ **未读取前为零** |

> ⭐⭐⭐⭐⭐ 官方给出的⭐ 规模论证：
> ⭐⭐⭐⭐⭐ **"30–50 tokens × 100 个技能 ≈ 5K tokens 的⭐ 前置开销。
> ⭐⭐⭐⭐⭐ ⭐ 这就是为什么一个 Claude Code 安装⭐ 可以有 100+ 个技能⭐ 而不在启动时卡死。"**
>
> ⭐⭐⭐⭐⭐ 这个数字⭐ 直接回答了一个⭐ 反复出现的担忧：
> ⭐⭐⭐⭐ **"装多少技能算多？"→ ⭐⭐⭐ 100 个也才 5K，⭐⭐ 问题不在数量本身。**
> ⭐⭐⭐⭐ 与 `skill-portfolio-audit.md` 的"库存 20+ 时 agent 每次随机加载好几个"
> ⭐⭐⭐ 并不矛盾——⭐⭐⭐⭐ **那说的是⭐ 候选集太大导致⭐ 选择质量下降，
> ⭐⭐⭐⭐⭐ ⭐ 而这里说的是⭐ 元数据本身的⭐ 静态开销很小。**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ **两个成本来源不同：一个是常驻的、一个是每次判断时的**——
> ⭐⭐⭐⭐ 后者才是⭐ 真正的瓶颈（这也解释了为什么⭐ ≤3 挂载那条⭐ 比数量更重要）。

## 2. ⭐⭐⭐⭐⭐ 8K 与 4%：健康基线

> ⭐⭐⭐⭐⭐ **一个典型的 200K token Claude Code 会话，
> ⭐⭐⭐⭐⭐ ⭐ 启动时加载约 ⭐ 8K 开销
> ⭐⭐⭐⭐⭐ ⭐（系统提示 + 记忆 + 技能元数据 + CLAUDE.md）
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ = ⭐ 窗口的 4%，⭐⭐⭐⭐ ⭐ 剩下 96% 留给⭐ 真正的对话。**

> ⭐⭐⭐⭐⭐ 这是整个收藏里⭐ 第一个⭐ "健康基线"数字——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ **你可以用它⭐ 自查**：
> ```
> ⭐ 启动开销 ≈ 8K（健康）
> ⭐ 明显超过 → ⭐⭐⭐ 去查是⭐ 技能元数据太多、⭐ CLAUDE.md 太长、
>               ⭐ 还是系统提示被别的东西占了
> ```
> ⭐⭐⭐⭐⭐ 而 ⭐ **4% 这个比例本身就是⭐ 设计意图的证据**：
> ⭐⭐⭐ **渐进式披露的目的，就是让"装了很多东西"⭐ 几乎不占用窗口。**

## 3. ⭐⭐⭐ 破坏它会怎样

```
⭐⭐⭐⭐ 如果破坏渐进式披露（例如⭐ 启动时就加载所有 SKILL.md 正文）：
   30 个技能 × 3K tokens = ⭐⭐⭐ 90K
   ⭐⭐⭐⭐⭐ ⭐ = ⭐ 在用户说出第一句话之前，⭐ 一半窗口就没了
```

> ⭐⭐⭐⭐ 与 `context-budget-math.md` 的⭐ 96% 那个数字⭐ 相互印证
> （那份算的是⭐ 全量预加载 250K vs 渐进式 10K），
> ⭐⭐⭐⭐⭐ 但⭐ 这里给的是⭐ "反过来做会怎样"的⭐ 绝对值对照：
> **90K / 200K = 45%**。
>
> ⭐⭐⭐⭐⭐ 一句话总结这个机制的价值：
> ⭐⭐⭐⭐⭐ **"⭐ 上下文窗口是一种⭐ 公共资源。"**
> ⭐⭐⭐⭐ 这是⭐ 该原则⭐ 第三次出现，⭐⭐⭐⭐ ⭐ 而这次⭐ 带了具体数字。

## 4. ⭐⭐⭐ 同一机制的三个其他应用

> ⭐⭐⭐⭐ **渐进式披露不只用在技能上**——同一个模式还出现在：

```
① ⭐⭐⭐ MCP 工具：⭐⭐ 启动时只加载⭐ 工具名，⭐⭐⭐ 完整 schema 延后
② ⭐⭐⭐⭐ 路径限定的 CLAUDE.md 规则：.claude/rules/*.md 带 paths frontmatter
   ⭐⭐⭐⭐⭐ ⭐ 只在⭐ 读取匹配文件时⭐ 加载
③ ⭐⭐⭐ 子目录 CLAUDE.md：⭐ 只在 Claude ⭐ 在该目录工作时加载
```

> ⭐⭐⭐⭐⭐ 认识到"这是⭐ 同一个模式"很有用——
> ⭐⭐⭐⭐⭐ **它意味着⭐ 你在技能上学会的那套"按需"直觉，
> ⭐⭐⭐⭐ ⭐ 可以直接迁移到⭐ rules 和 MCP 上**：
> ⭐⭐⭐⭐ ⭐⭐⭐ **凡是"可能用不到"的东西，
> ⭐⭐⭐⭐⭐ ⭐ 都应该有⭐ 一个"什么时候才付这个钱"的⭐ 触发条件。**
>
> ⭐⭐⭐⭐ 反过来说，⭐⭐⭐ **一个⭐ 没有触发条件的常驻内容，
> ⭐⭐⭐⭐ 就是⭐ 在每一次对话里⭐ 无条件收费**——
> ⭐⭐⭐⭐ 这正是 `skill-portfolio-audit.md` 的"认知切换成本"、
> `capability-offset-net-gain.md` 的"常驻描述渗入判断"
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ ⭐ 的⭐ 统一解释。

## 5. ⭐⭐ 硬约束与失败模式

| 字段 | 限制 | ⭐⭐⭐⭐ 超限后果 |
|---|---|---|
| `name` | ⭐ 64 字符；仅小写字母/数字/连字符；无 XML 标签；⭐⭐⭐⭐ 无保留字（anthropic、claude） | ⭐⭐⭐⭐⭐ **加载时被拒绝** |
| `description` | ⭐ 1,024 字符；非空；无 XML 标签 | ⭐⭐⭐⭐⭐ **加载时被拒绝** |

**其余失败模式**（这一组很实用，因为⭐ 每种症状不同）：

```
· ⭐⭐⭐ 含保留字           → 加载时拒绝
· ⭐⭐⭐⭐ 第一人称描述      → ⭐⭐⭐ 技能能用，但⭐⭐⭐⭐ Claude 更不容易正确调用它
· ⭐⭐⭐⭐⭐ description 写成多段 YAML 折叠标量 → ⭐⭐⭐⭐⭐ 超过 1,024 → ⭐ 加载时拒绝
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ "这就是用户写多段描述时⭐ 会撞上的那个错误"
```

> ⭐⭐⭐⭐ 注意⭐ 第二条的⭐ 失败性质完全不同：
> ⭐⭐⭐⭐⭐ **它不报错，⭐⭐⭐⭐⭐ ⭐ 只是⭐ 效果悄悄变差**。
> ⭐⭐⭐⭐ 这与 `naming-conventions.md` 里 camelCase 的例子⭐ 同类——
> ⭐⭐⭐⭐⭐ **"不报错的失败"比"报错的失败"⭐ 危险得多，
> ⭐⭐⭐⭐⭐ ⭐ 因为你⭐ 没有信号去发现它。**

**其余硬规则（速查）**：

```
正文：<500 行 · ⭐⭐⭐⭐ 避免内联时间敏感信息（"After August 2025…"）
     ⭐⭐⭐ 老模式用⭐ 可折叠块 · ⭐⭐⭐ 路径一律用正斜杠（含 Windows）
     ⭐⭐⭐⭐ MCP 工具名完全限定 ServerName:tool_name
     ⭐⭐⭐⭐⭐ 魔法数字旁必须有 # why 注释
     ⭐⭐⭐⭐ 术语统一（选定"API endpoint"就用到底）
     ⭐⭐⭐ 脚本里⭐ 不要把错误丢给 Claude 处理——⭐⭐ 显式处理
reference：⭐⭐⭐⭐⭐ ⭐ 保持⭐ 距 SKILL.md 一层深（⭐⭐⭐⭐⭐ 这是最常被违反的一条）
          ⭐⭐⭐ >100 行需顶部 TOC · ⭐⭐ 按领域组织（references/finance.md、sales.md）
```

## 速查

```
□ ⭐⭐⭐⭐ 三级：L1 元数据 30–50 tokens/技能（100 个≈5K）
   L2 正文 200–500 行≈2K–5K（触发时整份）· L3 参考/脚本 未读取前为零
□ ⭐⭐⭐⭐⭐ 健康基线：⭐ 200K 会话启动开销≈8K = ⭐ 4%，留 96% 给对话
   ⭐⭐⭐⭐⭐ ⭐ 明显超过 8K → 去查元数据/CLAUDE.md/系统提示
□ ⭐⭐⭐⭐ 破坏代价：30 技能 × 3K = 90K = ⭐ 第一句话之前没了一半窗口
□ ⭐⭐⭐⭐⭐ 同一模式另三处：MCP（只加载工具名）· rules（按 paths）
   ⭐ 子目录 CLAUDE.md（按目录）
   ⭐⭐⭐⭐⭐ ⭐ 推论：⭐ 没有触发条件的常驻内容 = ⭐ 每次对话无条件收费
□ ⭐⭐⭐⭐⭐ name>64 / description>1024 → ⭐ 加载时拒绝
   ⭐⭐⭐⭐⭐ ⭐ 第一人称描述 → ⭐ 不报错，⭐⭐⭐⭐⭐ 只是⭐ 更不容易被正确调用
   ⭐⭐⭐⭐⭐ "不报错的失败" 比 "报错的失败" 危险——⭐ 你没有任何信号
```

**一句话**：

> ⭐⭐⭐⭐ **官方数字：L1 元数据每技能 30–50 tokens（100 个技能也才 5K）、L2 正文触发时整份加载 2K–5K、L3 未读取前为零，一个健康会话的启动开销约 8K 即窗口的 4%——而破坏这个模式（全量预加载）会在用户说出第一句话之前就用掉 90K、即一半窗口。**
