## 1. ⭐⭐⭐⭐⭐ 一个技能 = 一个可搬迁的目录

> ⭐⭐⭐⭐⭐ **判据：把整个目录复制到另一台机器的
> `~/.claude/skills/` 下，它应该立刻能用。**
> 不能 → 契约被破坏了。

这条判据的力量在于它**不需要你懂技能机制**——
复制一下就知道。而它检验的是三件事：

```
① ⭐⭐⭐⭐⭐ 没有外部绝对路径
② ⭐⭐⭐⭐⭐ 自带依赖（或声明清楚）
③ ⭐⭐⭐⭐ 没有隐含的"还要装另一个技能"
```

> ⭐⭐⭐⭐⭐ 第 ③ 条最常被违反，也最难发现：
> 它在本机永远能跑（因为另一个技能就在旁边），
> ⭐⭐⭐⭐⭐ **只在别人装了单个技能时失败**——
> 这正是"隐式依赖在生产才暴露"的另一种形态。

---

## 2. ⭐⭐⭐⭐ 三条硬约束

**① ⭐⭐⭐⭐⭐ 自包含**

```
references/ 里的每个被引用文件都必须存在
scripts/ 里每个被提到的脚本都必须可执行
```

> ⭐⭐⭐⭐⭐ **引用了不存在的模板文件 → 模型读取失败 → 自己补内容 → 幻觉**
> （这是 `three-failure-modes.md` 里已确认的一条因果）。
> 所以⭐⭐⭐⭐ **悬空引用不是"小瑕疵"，是幻觉的直接来源**，
> 必须是硬错误而不是警告。

**② ⭐⭐⭐⭐⭐ 无状态残留**

```
目录下不应有：输出文件 · 日志 · 临时文件 · .progress.json
```

> ⭐⭐⭐⭐⭐ 这些会在分发时一起被打包出去，
> 于是别人装上就带着"上次跑到第 8 个"的假状态
> （与 `cross-session-continuity.md` 里"残留状态是假失灵来源"一致）。

**③ ⭐⭐⭐⭐ 命名不冲突**

```
⭐⭐⭐⭐⭐ 绝不遮蔽官方技能名
   pdf-internal / commit-team，而不是 pdf / commit
```

> ⭐⭐⭐⭐⭐ **通用名会造成静默冲突**：错的那一个被调起，而你毫无察觉。
> 这条在 `team-naming-collisions.md` 里已强调，这里补一句：
> ⭐⭐⭐⭐ **在分发场景下，"可能冲突"几乎等于"一定冲突"**——
> 因为你不知道用户已经装了什么。

## 3. ⭐⭐⭐⭐⭐ 不该出现在技能目录里的东西

| 不该有 | ⭐ 为什么 |
|---|---|
| ⭐⭐⭐⭐⭐ `.env` / 真实密钥 | ⭐⭐⭐⭐⭐ 会被打包、会被提交。`KEY=actual_value` 就是泄露 |
| ⭐⭐⭐⭐⭐ 任何输出产物 | 会随分发扩散；且让目录看起来"已经跑过" |
| ⭐⭐⭐⭐ 与技能无关的说明文档 | ⭐⭐⭐⭐ 会被检索到、稀释判断（死代码的技能版） |
| ⭐⭐⭐⭐ 大体积二进制 | 分发体积爆炸；⭐⭐⭐ 且多数是误放 |
| ⭐⭐⭐⭐ `.DS_Store` / `__pycache__` | 噪声，且会污染 diff |
| ⭐⭐⭐⭐ 空目录 | ⭐⭐⭐⭐ "见过十几个子文件夹大多为空"——过早分目录的产物 |

> ⭐⭐⭐⭐⭐ 第一行值得单独说：
> 判据不是"有没有 .env 文件"，是⭐⭐⭐⭐⭐ **等号右边是真值而不是占位符**。
> 很多人把密钥写在 `references/config-example.md` 里，
> 因为"不在 .env 里就不算泄露"——**它照样会被打包和提交。**

## 4. ⭐⭐⭐⭐ 打包与分发

三种形态，按保真度：

```
① ⭐⭐⭐⭐ 目录（zip / tar）
   最通用，任何平台都能装
② ⭐⭐⭐⭐ 插件（plugin）
   ⭐⭐⭐⭐⭐ 能带 hooks 和 MCP——而技能本身只是指令
③ ⭐⭐⭐ 市场 / 注册中心
   最方便，但⭐⭐⭐⭐⭐ 引入了供应链风险（13.4% 严重问题率）
```

> ⭐⭐⭐⭐⭐ 第 ② 条的分界最值得记：
> **技能承载知识（可移植），插件承载 Claude Code 专属自动化。**
> 换工具时你只丢掉外壳——
> ⭐⭐⭐⭐ 所以"这个技能必须做成插件"往往意味着
> 你把不该放进技能的东西放进去了。

打包前检查（可 grep 的三条）：

```bash
grep -rnE "(https?://[^ ]*@|AKIA[0-9A-Z]{16}|sk-[A-Za-z0-9]{20})" .   # 凭据
find . -name "*.env*" -o -name "*output*" -o -name "*.log"             # 残留
find . -type d -empty                                                  # 空目录
```

> ⭐⭐⭐⭐ 三条都很便宜，且⭐⭐⭐⭐⭐ 第一条能挡住最常见的泄露——
> 而"我审阅过这个文件"对隐藏 Unicode 注入是完全失效的，
> ⭐⭐⭐⭐ 所以机器检查不是可选项。

## 5. ⭐⭐⭐⭐⭐ 目录契约自检

七条，发布前过一遍：

```
□ ⭐⭐⭐⭐⭐ 复制到新机器能直接用（可搬迁性）
□ ⭐⭐⭐⭐⭐ 无任何悬空引用（防幻觉）
□ ⭐⭐⭐⭐⭐ 无真实密钥（含 config-example 里的）
□ ⭐⭐⭐⭐ 无输出产物 / 日志 / 进度文件残留
□ ⭐⭐⭐⭐ name 不遮蔽官方技能名
□ ⭐⭐⭐⭐ 无空目录
□ ⭐⭐⭐⭐ README 与正文的前置条件一致
```

> ⭐⭐⭐⭐⭐ 最后一条最容易被漏，且后果最不对称：
> ⭐⭐⭐⭐⭐ **文档说能跑、实际跑不了**——
> 用户会花很长时间怀疑是自己环境的问题，
> 而不是怀疑文档。

与相邻文档的分工：

```
directory-decision-matrix   单个文件放哪个子目录（进不进上下文）
⭐⭐⭐⭐⭐ 本份                 整个目录要满足什么（可搬迁、无残留、不冲突）
skill-documentation         README 写什么
```
