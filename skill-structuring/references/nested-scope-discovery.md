## 1. ⭐⭐⭐⭐ 嵌套技能只在相关子目录工作时才出现

```
monorepo 中：
  ⭐⭐⭐ `packages/frontend/.claude/skills/lint/`
  ⭐⭐⭐⭐ ⭐ 只有⭐ 在编辑 frontend 代码时⭐ 才会出现
```

> ⭐⭐⭐⭐ **"嵌套的 `.claude/skills/` 目录，⭐⭐⭐ 只有在 Claude
> ⭐⭐⭐ ⭐ 处理该子目录下的文件时⭐ 才会被发现。"**

> ⭐⭐⭐⭐ 这条极易被误诊：
> ```
> 你装了一个子包技能 → 在主目录工作时"技能不存在"
> → 你以为是⭐ 目录名/文件名/YAML 错了 → ⭐⭐⭐⭐ 查了半天
> → ⭐⭐⭐⭐ ⭐ 其实它只是⭐ 不在当前作用域
> ```
> ⭐⭐⭐ 这是 `four-layer-diagnosis-flow.md` 的"环境层"里
> ⭐⭐⭐ **此前完全没覆盖的一项**。
> ⭐⭐⭐ 那份清单里"换个项目/平台能复现吗"已经接近了，
> ⭐⭐⭐⭐ 但没说⭐ **"换个目录试试"**——而 monorepo 下这正是第一嫌疑。

**排障顺序建议**（在文件层通过之后、改 description 之前）：

```
① ⭐⭐⭐ 确认文件层没问题（目录名/文件名/YAML）
② ⭐⭐⭐⭐ ⭐ cd 到那个子目录 / 打开该目录下的文件，再看技能在不在
③ 才轮到改 description
```

## 2. ⭐⭐⭐ 与 `paths` 字段的对比

两者都能做"按路径限定可用性"，但机制不同：

| | ⭐ 机制 | ⭐⭐ 谁来判定 |
|---|---|---|
| ⭐⭐ 嵌套目录 | ⭐⭐⭐ 物理位置决定发现 | ⭐⭐⭐ 系统（自动） |
| ⭐⭐⭐ `paths:` frontmatter | ⭐⭐⭐ glob 模式匹配 | ⭐⭐⭐ 声明在技能里 |

```
paths:
  - src/api/**
  - server/routes/**
```

> ⭐⭐⭐ 关键区别：
> ```
> 嵌套目录 = ⭐⭐⭐ 系统按"你正在处理哪个文件"自动发现
> paths    = ⭐⭐⭐⭐ ⭐ 作者⭐ 显式声明⭐ "我只在涉及这些文件时才该被考虑"
> ```
> ⭐⭐⭐⭐ **`paths` 更强**：它还能用于⭐ 非 monorepo 场景
> （同一个仓库里按模块限定），且⭐ 是⭐ 唯一能直接减少候选集的字段
> ——这点在 `frontmatter-full-reference.md` 里记过。
>
> ⭐⭐⭐ 两者可以叠加：既放在子目录、又写 `paths`，双保险。
> ⭐⭐ 但注意⭐ **别过度**：多一层机制就多一处"为什么它没触发"的排查点。

## 3. ⭐⭐⭐ 三个由此而来的排障结论

```
① ⭐⭐⭐⭐ "技能在这个包里有、在那个包里没有"
   → ⭐⭐⭐⭐ ⭐ 多半不是配置错误，是⭐ 嵌套作用域（设计如此）

② ⭐⭐⭐ "同一个技能在不同开发者机器上行为不同"
   → ⭐⭐⭐⭐ ⭐ 先查⭐ 个人目录（~/.claude/skills/）
      ⭐⭐⭐ 不同开发者可能有⭐ 同名的不同个人技能
      （与 skill-overrides-audit.md 一致：个人 > 项目）

③ ⭐⭐⭐ "新技能不出现"
   → ⭐⭐⭐⭐ ⭐ 唯一需要重启的情况是
      ⭐⭐⭐⭐⭐ `.claude/skills/` ⭐ 这个目录本身⭐ 是会话中首次创建的；
      ⭐⭐⭐ 已存在目录下的新增是⭐ 实时检测到的
```

> ⭐⭐⭐ 第 ③ 条是我们那个长期矛盾的⭐ 第三个来源，
> ⭐⭐⭐ 且措辞最精确：**不是"改了技能要不要重启"，而是"目录是否是新建的"。**
> ⭐⭐⭐ 与 `skill-cascade-css.md` 的结论完全一致。

## 4. ⭐⭐⭐ 技能审计：一个能直接用的样本思路

冲突是静默的（更高优先级者⭐ 无声胜出，落选者⭐ 完全不可见），
所以⭐⭐⭐ **需要一个能列出"当前到底谁生效"的技能**。

一份审计技能的骨架（可直接照此写）：

```yaml
---
name: audit-skills
description: >
  Audit all discoverable skills and report conflicts, duplicates,
  and precedence issues. Use when the user says "check skills",
  "audit skills", or "skill conflicts".
disable-model-invocation: true
allowed-tools: Read Grep Glob Bash(ls *) Bash(find *)
---
```

**要点（这几处都是好设计，值得学）**：

```
① ⭐⭐⭐ `disable-model-invocation: true`
   ⭐⭐⭐⭐ ⭐ 审计是"你主动要它跑"的，⭐⭐ 不该自动触发
   （与"deploy 类技能应禁止自动触发"同源）

② ⭐⭐⭐ `allowed-tools: Bash(ls *) Bash(find *)`
   ⭐⭐⭐⭐ ⭐ 把 Bash ⭐ 收窄到 ls/find，⭐⭐⭐ 而不是给裸 Bash
   （allowed-tools 是少数⭐ 真正在执行侧生效的声明）

③ ⭐⭐⭐ 输出格式⭐ 显式区分 CONFLICTS / NO CONFLICTS 两节
   ⭐⭐⭐ ⭐ 冲突项要⭐ 同时列出两个版本的 description
   ⭐⭐⭐⭐ ——这样你才知道⭐ 哪一个是跳测试的
```

**它该报告什么**：

```
· 个人技能数 / 项目技能数
· ⭐⭐⭐⭐ 同名冲突项 + ⭐ 哪个赢 + ⭐⭐ 两个版本的描述对比
· 无冲突项（也列出来，便于确认"它确实存在"）
· ⭐⭐⭐ 嵌套作用域：哪些技能只在特定子目录可用（本份第 1 节）
```

> ⭐⭐⭐ 最后一项是本份的贡献：多数审计脚本只查⭐ 同名冲突，
> ⭐⭐⭐⭐ ⭐ 不查⭐ 作用域导致的"时有时无"——而那正是 monorepo 的主要困惑来源。

## 5. ⭐⭐ 一条确认手段

> ⭐⭐⭐ **"无法判断当前生效的是哪个版本的技能时——直接问 Claude：
> ⭐⭐⭐⭐ 'What skills are available?'"**

> ⭐⭐⭐ 这条简单到容易被忽略，但它是⭐ 唯一的⭐ 权威确认方式：
> 你读配置文件是在⭐ 推测，⭐⭐ 而问它是在⭐ 读取实际生效的列表。
>
> ⭐⭐⭐⭐ 适用场景：部署行为异常、怀疑被个人技能覆盖、
> 改了技能不确定是否生效——**先问这一句，再动手排查。**

## 速查

```
□ ⭐⭐⭐⭐ 嵌套 .claude/skills/ ⭐ 只在⭐ 处理该子目录文件时⭐ 才被发现
   ⭐⭐⭐⭐ ⭐ 极易误诊为"技能坏了"——⭐⭐⭐ 先 cd 到子目录再看，别急着改 description
□ ⭐⭐⭐ 嵌套目录（系统按位置自动）vs ⭐⭐⭐ paths 字段（作者显式声明 glob）
   ⭐⭐⭐⭐ paths 更强：非 monorepo 也能用，⭐⭐⭐ 且是⭐ 唯一能直接减少候选集的字段
□ ⭐⭐⭐ "这个包有那个包没有" → 多半是⭐ 嵌套作用域（设计如此，不是 bug）
   ⭐⭐⭐ "不同人机器行为不同" → ⭐ 先查个人目录
   ⭐⭐⭐ "新技能不出现" → ⭐⭐⭐⭐ 只有⭐ 目录本身是会话中新建⭐ 才需重启

□ ⭐⭐⭐ 审计技能三要点：
   ⭐⭐⭐ disable-model-invocation: true（不该自动触发）
   ⭐⭐⭐⭐ allowed-tools: Bash(ls *)（⭐ 收窄而非裸 Bash，⭐ 执行侧真生效）
   ⭐⭐⭐⭐ 冲突项⭐ 必须同时列出两个版本的 description（才知道哪个跳测试）
   ⭐⭐⭐ 别忘了报告⭐ 嵌套作用域导致的"时有时无"
□ ⭐⭐⭐⭐ 无法判断哪个版本生效 → ⭐ 直接问 "What skills are available?"
```

**一句话**：

> ⭐⭐⭐⭐ **嵌套的 `.claude/skills/` 目录只在处理该子目录文件时才被发现——这极易被误诊为"技能坏了"（其实只是不在当前作用域），排障时应在文件层检查通过后、改 description 之前先 cd 到那个子目录再确认；
> 而"无法判断哪个版本生效"时唯一权威的确认方式是直接问 Claude 有哪些技能可用。**
