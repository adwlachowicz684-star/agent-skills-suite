## 1. ⭐⭐⭐ 三道关卡

| 关卡 | 进入条件 | ⭐ 上下文成本 | ⭐⭐ 失败形态 |
|---|---|---|---|
| ⭐ ① Discovery 发现 | `name` + `description` ⭐ 常驻 | ⭐ 每个都付（共享预算） | ⭐⭐ 没触发 / 误触发 |
| ⭐ ② Activation 激活 | SKILL.md 全文进入上下文 | ⭐⭐ 会话内⭐ 持续占位 | ⭐⭐⭐ 压缩 · 遗忘 · 被挤出 |
| ⭐ ③ Execution 执行 | ⭐ 无额外加载关卡、无第二道匹配 | ⭐⭐ 按需 | ⭐⭐⭐ 脚本 · 知识 · 指令漂移 |

> ⭐⭐⭐⭐ **"进入条件简单"不等于"执行过程简单"。**
>
> 第 ③ 关的要点：**一旦激活，模型就开始逐条遵循指令——
> ⭐⭐⭐ 没有额外的加载关卡，也没有第二道匹配。**
> 所以⭐ **激活之后发生的一切问题，都不能指望"再匹配一次"来纠正。**

**三个阶段的上下文哲学不同**：

```
①② ⭐⭐ 预加载、常驻、共享预算
③  ⭐⭐⭐ 按需，且⭐⭐ 只按需
```

## 2. ⭐⭐⭐⭐ 真失忆 vs 假失灵

长会话后期你感觉某个技能失效了——**只有两种可能，且修法完全不同**：

```
⭐⭐⭐ 真失忆：⭐⭐⭐ 它排在⭐ 压缩队列末尾，⭐⭐ 被预算挤出去了
        ⭐⭐⭐ ⭐ 重新调用一次，内容就回来了

⭐⭐⭐⭐ 假失灵（⭐⭐⭐ 更常见）：⭐⭐⭐⭐ ⭐ 内容其实⭐ 还在上下文里，
        ⭐⭐⭐ ⭐ 是模型⭐ 选择了别的工具和路径
```

| | 去查什么 | ⭐ 修法 |
|---|---|---|
| 真失忆 | ⭐ 压缩预算、挂载顺序 | 重新调用 / 减小体积 |
| ⭐⭐⭐ 假失灵 | ⭐⭐⭐ description 与指令的写法 | ⭐⭐⭐ 改描述，⭐⭐⭐ 或用 hooks 把关键行为定死 |

> ⭐⭐⭐⭐ **"两类失灵，两种修法，⭐⭐⭐⭐ 没区分清楚就动手，只会白费功夫。"**
>
> ⭐⭐⭐⭐ 这条与我们已有的 `context-budget-math.md`
> （"技能中途失效——指令不一定消失了，可能模型只是改用了别的方法"）
> ⭐⭐⭐ 是⭐ 第二个来源，
> ⭐⭐⭐⭐ 但这里⭐ **给了分辨方法**：**重新调用一次**——
> 回来了就是真失忆，没回来（还是不用它）就是假失灵。
> ⭐⭐⭐⭐ **这是一个零成本的二分诊断，值得立刻用。**

## 3. ⭐⭐⭐ 压缩带回的是"开头 5000"

```
⭐⭐⭐⭐ 带回来的是⭐ "开头 5000"，⭐⭐⭐⭐ 不是⭐ "最重要的 5000"
```

> ⭐⭐⭐⭐ **"你把关键约束写在 SKILL.md 的前半部分还是后半部分，
> ⭐⭐⭐ ⭐ 在压缩发生的这一刻可能产生⭐⭐⭐ 截然不同的效果。"**

> ⭐⭐⭐⭐ 这是"开头是黄金位置"的⭐⭐⭐ **第四个独立来源**，
> 且是最强的一个——因为它给出了⭐ **精确的作用时刻**：
> ```
> · prompt-layering：存在首因/近因效应（实证）
> · 压缩保留前 5000 token（官方）
> · 模型用 head -100 预览长文件（行为观察）
> · ⭐⭐⭐⭐ 本份：压缩带回的是"开头 5000"不是"最重要的 5000"
> ```
> ⭐⭐⭐ 四条从不同角度指向同一结论，
> ⭐⭐⭐ **且这条说明了它不是偏好而是机制**——
> 系统⭐ 没有能力判断哪 5000 重要，它只能取开头。

## 4. ⭐⭐⭐ 脚本源码不进上下文，输出进

| 资源 | ⭐ 是否自动进入上下文 | 用途 |
|---|---|---|
| ⭐⭐⭐ script **源码** | ⭐⭐⭐⭐ **默认不进入**（除非被显式读取） | 执行确定性任务 |
| ⭐⭐⭐ script **输出** | ⭐⭐⭐ **会进入**（供模型判断下一步） | — |
| reference 内容 | 根据 SKILL.md 指引⭐ 按需读取 | 规则、模板、样例 |
| 中间产物 | 按需进入 | 支持回溯与阶段交接 |

> ⭐⭐⭐ 这一条⭐ 修正了一个常见误解：
> 很多人以为"技能里挂了脚本 = 脚本内容占了上下文"。
> ⭐⭐⭐ **恰恰相反——脚本可以只被执行而不被读入，这正是它便宜的原因。**
>
> ⭐⭐⭐ 但要注意第二行：⭐ **脚本的输出会进上下文**。
> 所以 `three-crash-scenes.md` 那起 3 万字事故的机制在这里得到解释：
> ⭐⭐⭐⭐ **脚本源码便宜（不进上下文），脚本输出昂贵（进上下文）**
> ——所以"把体积控制放在脚本层"是对的（源码长没关系），
> 而"输出不压缩"是致命的。

**核心原则**（可直接作为设计准则）：

> ⭐⭐⭐ **不全量读入，不盲目进入；⭐⭐ 按需调用，
> ⭐⭐⭐ 最小化上下文，最大化清晰度与可控性。**

## 5. ⭐⭐⭐ 执行期的三条可控杠杆

**分工判据**（一句很干净的话）：

> ⭐⭐⭐⭐ **语义留给模型，校验交给代码。**
> ⭐⭐⭐ **有标准答案的判断 → 交给代码；
> ⭐⭐⭐ 需要语义理解的判断 → 留给模型，⭐⭐⭐⭐ 但要⭐ 安排检查点。**

```
LLM 侧：读懂源文件 · 提取候选条目 · ⭐ 判断两条信息是否同一件事
        生成简报文本 · ⭐ 判断论证是否成立
脚本侧：命名规则 · SQL 模板 · 检查清单 · 命令拼接 · 编码探测
```

> ⭐⭐⭐ 一个具体实例（值得抄）：
> **"Agent 不允许自己 open 原始文件，必须通过 `parse_property_table` 技能读取，
> 而我在技能内部写死了编码探测和异常处理逻辑。"**
>
> ⭐⭐⭐⭐ 作者的评价很到位：
> "表面上看只是多了一层封装，⭐⭐⭐⭐ 实际上是把⭐ '不确定性'
> ⭐⭐⭐ 从 Agent 的⭐ 自由决策中拿掉了。"
>
> ⭐⭐⭐ 这起事故的原始症状：⭐ 模型用 UTF-8 读失败 → ⭐⭐ 自己猜 GBK →
> ⭐⭐⭐ 读出一堆乱码 → ⭐⭐⭐⭐ **后面所有步骤全部建立在垃圾数据上**
> （正是"错得自信而正确"）。

**另一条执行期纪律**（对应无限重试）：

```
⭐⭐⭐ 同一个技能、同一个参数组合，⭐⭐⭐ 最多重试两次
⭐⭐⭐ 两次都失败 → ⭐⭐⭐ 跳到"向人类请求帮助"状态
```

> ⭐⭐⭐ "这条规则很简陋，但非常有效，能挡住绝大多数死循环问题。"
> ⭐⭐⭐⭐ 根因表述值得记：⭐ **"你给了 Agent 执行能力，
> 却没有给足'反思能力'。"**
>
> ⭐⭐⭐ 与我们已有的 `trace-debugging.md` 停止规则
> （"连续两次相同参数命令 = 你在循环"）是⭐ 同一条的第二个来源，
> ⭐⭐ 但这里⭐ **给了一个明确的数字：2 次**，并指定了失败后的去向（转人工）。

**还有一条**（数值处理）：

> ⭐⭐⭐ **"大模型对数值的感知能力极弱"**——
> 让它从表格里找"数值最高的一行"，它给出了错的（第 37 行才是最大）。
> ⭐⭐⭐⭐ **原因：模型处理文本 token，⭐⭐ 对长数字的大小比较不稳定。**
>
> ⭐⭐⭐ 这是⭐ **"什么该交给代码"的一个此前没覆盖的具体类别**：
> 不只是"确定性逻辑"，⭐⭐⭐ **数值比较本身也该交给代码**。

## 6. ⭐⭐ 一句成本观

> ⭐⭐⭐ **"你为 SKILL.md 的⭐ 每一行字，⭐⭐⭐⭐ 支付的是⭐ 整个会话的持续开销。"**

> ⭐⭐⭐ 这句话比"惜字如金"更有力，因为它⭐ 点明了计价单位：
> 不是"一次加载"，是⭐ **整个会话 × 每一次激活**。
> 而 `context-budget-math.md` 的"激活后指令留在对话里持续消耗"
> 是它的机制版本——⭐⭐⭐ 两份合起来就是完整的成本模型。

## 速查

```
□ ⭐⭐⭐ 三关：① 发现(name+description常驻) ② 激活(全文常驻) ③ 执行(按需)
   ⭐⭐⭐⭐ 激活后⭐ 没有第二道匹配 → ⭐⭐ 激活后的错误不会被"重新匹配"纠正

□ ⭐⭐⭐⭐ 真失忆 vs 假失灵：
   ⭐⭐⭐⭐ ⭐ 诊断：重新调用一次——回来=真失忆(被压缩挤出)；不回来=假失灵(模型选了别的路)
   ⭐⭐⭐⭐ 假失灵⭐ 更常见 → 改描述，⭐⭐⭐ 或用 hooks 把关键行为定死

□ ⭐⭐⭐⭐ 压缩带回的是⭐ "开头 5000"不是"最重要的 5000"
   ⭐⭐⭐⭐ → 关键约束放前半部分（第四个来源，且是机制而非偏好）

□ ⭐⭐⭐ 脚本源码⭐ 默认不进上下文（便宜）；⭐⭐⭐⭐ 脚本⭐ 输出⭐ 必进上下文（昂贵）
   → 脚本长没关系，⭐⭐⭐ 输出不压缩是致命的
   准则：不全量读入、不盲目进入；按需调用，最小化上下文

□ ⭐⭐⭐⭐ 语义留给模型，校验交给代码；⭐⭐⭐ 留给模型的要⭐ 安排检查点
   ⭐⭐⭐ 实例：不让 agent 自己 open 文件（它会猜编码 → 垃圾数据 → 后面全错）
        = 把不确定性从自由决策中拿掉
   ⭐⭐⭐ 数值比较也该交给代码（模型对长数字大小比较不稳定）
   ⭐⭐⭐ 同技能同参数⭐ 最多重试 2 次，失败转人工（挡住绝大多数死循环）
□ ⭐⭐⭐ 成本观：⭐ 每一行字 = ⭐ 整个会话 × 每次激活 的持续开销
```

**一句话**：

> ⭐⭐⭐⭐ **长会话后期技能"失效"有两种：真失忆（被压缩挤出，重新调用一次就回来）和假失灵（内容还在，但模型选了别的路径，更常见）——零成本的二分诊断就是重新调用一次；
> 而脚本源码默认不进上下文、输出必进上下文，所以脚本写得长没关系，输出不压缩才致命。**
