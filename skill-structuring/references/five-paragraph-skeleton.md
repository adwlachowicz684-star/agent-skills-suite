## 1. ⭐⭐⭐⭐⭐ 五段与它们的存在理由

| 段 | 内容 | ⭐ 为什么在这个位置 |
|---|---|---|
| ① 身份 | 一句话：这是什么、什么时候用 | ⭐⭐⭐⭐ 最先被读到，决定要不要继续 |
| ② 红线 | 绝不能做的事 | ⭐⭐⭐⭐⭐ **压缩必保留** |
| ③ 流程 | 怎么做 | 中段，允许被截断 |
| ④ 失败处理 | 出错怎么办 | ⭐⭐⭐⭐ 异常路径，常被省 |
| ⑤ 验收 | 什么叫完成 | ⭐⭐⭐⭐⭐ **近因区，执行完立刻要做** |

> ⭐⭐⭐⭐⭐ ② 和 ⑤ 的位置不是建议，是两条独立机制逼出来的：
> ⭐⭐⭐⭐ **压缩带回的是"开头"（②必须靠前）**；
> ⭐⭐⭐⭐ **近因效应让结尾的指令更容易被执行（⑤必须靠后）**。

---

## 2. ⭐⭐⭐⭐⭐ 红线在首、验证在尾，两端重复

```
首因区 ← ② 红线
       ③ 流程
       ④ 失败处理
近因区 ← ⑤ 验收
```

> ⭐⭐⭐⭐⭐ **关键规则在两端都写一遍。**
> 指令遵循率随约束位置显著变化，存在可测量的首因与近因效应——
> ⭐⭐⭐⭐ 靠近开头的约束比埋在中间的被遵循得更可靠。

重复不是冗余：⭐⭐⭐⭐ 首部的红线防"根本没读到"，尾部的验收防"读到了但没执行"。**两者防的是不同时刻的丢失**。

## 3. 中间段放什么

中间是黑洞，所以⭐⭐⭐⭐ **中间只放"丢了也不会出事"的东西**：

```
✅ 流程细节（模型自己能推）
✅ 格式示例
❌ ⭐⭐⭐⭐⭐ 红线、禁令、失败处理、验收
```

> ⭐⭐⭐⭐⭐ 判断方法：⭐⭐⭐⭐ **这段如果被截断，输出会变成错的还是只是变丑？**
> 变错 → 必须移到首或尾；只是变丑 → 留在中间。

一个具体陷阱：⭐⭐⭐⭐ **把约束写在具体步骤旁边，等于默认它只在那一步生效**。约束要么进红线段，要么在步骤里重复一次并标明"全局"。

---

## 4. ⭐⭐⭐⭐ 验证之后不要再放任何东西

```
⑤ 验收
❌ 附录 / 补充说明 / 作者备注
```

> ⭐⭐⭐⭐ 近因区是最贵的位置。验证恰好是执行完立刻要做的动作——
> ⭐⭐⭐⭐ **把附录放在验收之后，等于用最贵的位置装了最不重要的内容。**

附录、背景、参考链接一律放 references，或放在 ④ 之后、⑤ 之前。

---

## 5. 一个骨架样本

```markdown
# 一句话身份：做什么、什么时候用          ← ①

## 红线                                   ← ②
- MUST NOT 编造未查到的数据，填 unknown
- MUST NOT 在未经确认时写入

## 流程                                   ← ③
1. ...
2. ...

## 失败处理                               ← ④
| 情况 | 动作 |
|---|---|
| 数据缺失 | 停止并报告，不填 0 |

## 验收                                   ← ⑤
- [ ] 每条结论都有来源
- [ ] failures 字段已填（空也要 []）
```

约 100–150 行。⭐⭐⭐⭐ 超过 300 行就该拆——**不是因为读不完，是因为尾部会丢**。
