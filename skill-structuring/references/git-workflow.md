## 1. 版本管理：一个技能一个仓库

技能本质是**文本文件夹**，用 Git 管最合适：

| 做法 | 说明 |
|---|---|
| 一个技能一个仓库 | 便于独立版本化和分享 |
| 语义化版本号 | `v1.0.0`，大改升主版本 |
| 写 CHANGELOG | 记录每个版本改了什么 |
| 打 tag | 方便回溯到某个稳定版本 |

> ⚠️ **含敏感信息（API key、内部数据）的技能只做本地 git，不要 push 到公开仓库**；
> 用 `.gitignore` 挡掉 key/db 文件。

## 2. ⭐ Changelog 就写在 SKILL.md 末尾

一个轻量但有效的做法——**在 SKILL.md 末尾加 Changelog 区块，每次改完追加一行**：

```markdown
## Changelog
- v0.3.2: 修复标题为空时 digest 缺失的问题
- v0.3.1: 新增封面图自动裁切 (2.35:1)
- v0.3.0: 重构排版组件，支持 tip_box/success_box
- v0.2.0: 新增代码块高亮样式
- v0.1.0: 初始版本
```

> ⭐ **关键约定：倒序排列——最新的在最上面。**
> 别人打开文件第一眼就看到最近改了什么，不用翻到底部。

⚠️ 但注意 `skill-structuring` 的 `what-not-to-ship.md` 那条：
**独立的 `CHANGELOG.md` 文件不该出现在技能目录里**。
这里的做法是**作为 SKILL.md 末尾的一个区块**，两者不冲突。

## 3. 三条命令的协作流

不需要复杂工作流，就三条：

```bash
# 1. 改之前先拉最新
git pull origin main

# 2. 改完提交，commit 信息写清楚改了什么
git add .
git commit -m "v0.3.2: 修复 digest 为空的问题"

# 3. 推送
git push origin main
```

> ⭐ **commit 信息规范：`版本号: 改了什么`**。
> 不要写 "fix bug" 这种废话——**一个月后你自己都不知道改了啥**。

push 遇到冲突（remote 有新提交）：

```
❌ 不要强推
✅ 先 pull 合并，解决冲突再 push（git 会提示哪些行冲突）
```

## 4. ⭐ 分工比流程更重要

> 多人写技能最怕的不是改代码，而是**两个人改了同一个区块**。
> ⭐ **解决方法不是技术层面的，是分工层面的。**

推荐分工：

| 角色 | 负责 |
|---|---|
| A | ⭐ **指令**——SKILL.md 正文（"做什么""不做什么"） |
| B | **模板**——HTML 模板、prompt 模板、参考文件 |
| C | **测试**——写测试用例，验证输出质量 |
| D | **发布**——版本管理、Marketplace 发布 |

> **两个人都改 SKILL.md 正文？那必然冲突。**

这与 `enterprise-registry.md` 的 RBAC 四角色是同一思路在小组的轻量版。

## 5. 两个翻车现场

### 翻车 1：⭐ 改了触发词没通知

> 同事还在用旧触发词测试，结果全部不触发。

> ⭐ **触发词变更属于破坏性更新，必须通知所有人。**

这正好对应 `versioning-compat.md` 那条：
**不是每次 description 改进都是安全的**——它会改变触发边界。

### 翻车 2：靠聊天工具传文件

```
❌ Slack 里说"把这个 SKILL.md 复制到你的 skills 目录"
```

> ⭐ **drift 就是这么开始的。**
> 走 catalog 或共享仓库 + README 里的安装步骤。

## 速查

| 事 | 做法 |
|---|---|
| 版本 | 语义化 + tag |
| 变更记录 | ⭐ SKILL.md 末尾 Changelog 区块，倒序 |
| commit 信息 | `版本号: 改了什么` |
| 冲突 | 先 pull 再解决，不强推 |
| 多人协作 | ⭐ 按指令/模板/测试/发布分工 |
| 触发词变更 | ⭐ 属破坏性更新，必须通知 |
| 含敏感信息 | 只本地 git + .gitignore |
