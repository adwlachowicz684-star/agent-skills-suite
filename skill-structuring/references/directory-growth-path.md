## 1. ⭐⭐⭐ 最小可用：一个文件就能跑

```
python-agent-debugger/
└── SKILL.md
```

> ⭐⭐ **最小可用结构只有一个文件。**
> ⭐⭐⭐ **不要一上来就搞 `scripts/`、`templates/`、`references/`——
> 等你真正需要的时候再加。**

**见过什么**（值得当反面教材）：

```
⭐ "我见过一个技能目录里有十几个子文件夹，
   ⭐ 结果大部分是空的或者只有一两个文件。"
⭐⭐ 这种过度设计除了增加认知负担之外没有任何好处
```

> ⭐⭐⭐ 这与 `first-skill-minimal.md` 的"第一个技能可以只有 10 行"
> 是同一条原则在目录层面的延伸。
> 也和 `orchestrator-timing.md` 的
> "过早编排 = 过早抽象"同源——
> ⭐⭐⭐ **技能开发的三个"过早"：过早编排、过早分目录、过早通用化。**

## 2. ⭐⭐ 各目录的职责（不是为了让结构显完整）

| 位置 | 职责 | 适合放什么 |
|---|---|---|
| `SKILL.md` | ⭐ **路由后的主流程编排** | 目标、边界、步骤、输入、输出、验证 |
| `scripts/` | ⭐ 确定性执行 | 环境检查、数据转换、格式校验、重复命令 |
| `references/` | ⭐ 按需补充上下文 | API 文档、错误目录、团队规范、长篇背景 |
| `assets/` | ⭐ 提供可复用材料 | 报告模板、配置模板、示例文件、图片资源 |
| `agents/openai.yaml` | ⭐⭐ Codex 展示与依赖元数据 | 显示名称、图标、调用策略、MCP 工具依赖 |

> ⭐⭐ 那句"这些目录⭐ 不是为了让结构显得完整，
> 而是⭐ 解决不同性质的问题"是本份的核心。
> 它与 `directory-decision-matrix.md` 的判据
> （"问它进不进上下文"）是同一个问题的两种表述：
>
> ```
> 进上下文 → references/
> 按路径引用零成本 → assets/
> 执行 → scripts/
> ```

**另一种常见的最小三件套**（不同来源，略有出入，如实记录）：

```
my-skill/
├── SKILL.md        # 核心
├── README.md       # ⭐ 给人看
└── examples/       # 示例
```

> ⭐ 两种最小结构都合理，差异在⭐ 是否把"给人看的说明"和"示例"独立出来。
> ⭐⭐ 仲裁判据：**是否要分发给他人**——
> 自用：一个 SKILL.md 足够；
> 要给人用：加 README（人读）与 examples（模型参考）。

## 3. ⭐⭐ 什么时候该拆

一条具体的、可判定的阈值：

```
⭐⭐ SKILL.md 超过 500 行，或者 examples 超过 5 个 → ⭐ 就该拆了
```

> ⭐⭐ 500 行这个数字我们已经从两个独立来源验证过了
> （`official-spec-and-style.md`：由 5000 tokens 物理边界倒推）。
> ⭐ **"examples 超过 5 个"是这里新增的一档**——
> 正好与 `few-shot-examples.md` 的"数量黄金比例（中等 4–6，>5 收益递减）"对上：
> ⭐⭐ **超过 5 个示例不划算，就该把示例移出正文进独立文件。**

**另外两档**（来自我们已有的判据，排队对照）：

```
· 正文写不出一句话的"一件事陈述" → 该拆
· description 里"或"出现超过一次 → 多半是两个技能
· 人类会从中间产物重启 → 该拆
```

## 4. ⭐⭐ 三种拆法

```
① ⭐ 按功能拆
   "数据准备" 与 "模型训练" 分成两个子目录

② ⭐ 按资源类型拆
   templates/ 放模板 · references/ 放参考 · scripts/ 放脚本

③ ⭐ 按场景拆
   scenarios/basic/ 与 scenarios/advanced/
```

**拆分原则**（一句话）：

> ⭐⭐ **每个子目录都应该有⭐ 明确的职责，且⭐⭐ 能被独立理解。**

**三条细节**（容易漏但很实用）：

```
· ⭐ 模板文件里用 {{variable}} 占位符——agent 一看就知道哪里要替换
· ⭐ 示例文件要用⭐ 真实的、完整的案例，这样 agent 能直接参考
· ⭐⭐ 参考文档⭐ 不要全文复制进来，而是⭐ 给链接和摘要，避免体积过大
```

> ⭐⭐⭐ 第三条值得强调，因为它与
> `reference-file-practices.md` 的"每次引用就会读一次"、
> `token-bloat-audit.md` 的静态开销是同一件事：
> ⭐ **塞进库里的每个字都要反复付费。**
> 而且这里给了具体做法：**摘要 + 链接，而不是全文**。

**还有一条**：

```
⭐ 文件命名要有规律
```

## 5. ⭐ 生产级：发布到生态的额外要求

```
skill-name/
├── SKILL.md          # 唯一必需
├── scripts/
├── references/
├── assets/
├── ⭐⭐ tests/        # ⭐ 发布官方生态强制：⭐ 单元测试，覆盖率需 ≥80%
└── ⭐⭐ README.md     # ⭐ 发布官方生态强制：面向用户的使用说明、安装配置指南
```

> ⭐⭐ 两条"强制"值得注意：**要进官方生态，得有 tests/ 且覆盖率 ≥80%，
> 以及面向人的 README。**
>
> ⭐⭐⭐ 一个有意思的对照：我们此前记过
> "技能正文里不要放安装/贡献/隐私章节"——
> 那些是⭐ 给人看的、该进 README，不进 SKILL.md。
> 这里正好给出了归位的地方：**README 是强制的，它就是用来装这些的。**

**命名硬性规范**（再次验证，与前两轮一致）：

```
⭐ 文件夹名必须与 SKILL.md 的 name 字段⭐ 完全一致
⭐ 仅小写字母、数字、连字符；不可中文、大写、下划线、特殊符号
```

## 6. ⭐ 一个平台特有的目录

```
agents/openai.yaml   # ⭐⭐ Codex 专用
```

> ⭐⭐ Codex 会从仓库和用户范围的 `.agents/skills` 等位置发现本地技能。
>
> ```
> ⭐ 项目专属流程 → ⭐ 跟随仓库维护
> ⭐ 跨项目都要用的个人能力 → ⭐ 放在用户范围
> ```
>
> ⭐⭐⭐ 一句很重要的方法论提醒（原文）：
> **"具体位置和调用方式可能继续演进，
> ⭐ 安装前应以官方文档为准，⭐⭐ 而不是照搬其他 Agent 工具的路径。"**
>
> 这与 `cross-agent-portability.md` 的中性目录 `.agents/skills/` 呼应，
> 但也提醒我们：**路径是会变的，别把某篇文章里的路径当标准。**

## 速查

```
□ ⭐⭐⭐ 最小可用 = 一个 SKILL.md；⭐ 不要一上来搭大而全骨架
   ⭐⭐ "十几个子文件夹大多为空" = 过度设计，只增加认知负担
□ ⭐⭐⭐ 三"过早"：过早编排 · ⭐ 过早分目录 · 过早通用化

□ ⭐⭐ 职责：SKILL.md 编排 · scripts 确定性 · references 按需
   assets 可复用材料 · agents/openai.yaml Codex 元数据
□ ⭐ 另一种最小三件套：SKILL.md + README（人读）+ examples（模型参考）
   ⭐ 仲裁：是否分发给他人

□ ⭐⭐ 拆的阈值：⭐ SKILL.md>500行 或 ⭐ examples>5个
   （5 个正好对上少样本收益递减点）
□ ⭐⭐ 三种拆法：按功能 / 按资源类型 / 按场景
□ ⭐⭐ 原则：⭐ 每个子目录职责明确且⭐⭐ 能被独立理解
□ ⭐⭐⭐ ⭐ 参考文档给"链接+摘要"，不要全文复制（每个字都要反复付费）
□ ⭐ {{variable}} 占位符 · ⭐ 示例要真实完整 · ⭐ 命名有规律

□ ⭐⭐ 发布生态强制：tests/（⭐ 覆盖率≥80%）+ README.md
   ⭐⭐⭐ README 就是"安装/贡献/隐私"那些⭐ 不该进 SKILL.md 的内容的归位处
□ ⭐ 文件夹名必须与 name 完全一致
□ ⭐⭐ Codex 从 .agents/skills 发现；⭐ 项目专属跟随仓库，个人能力放用户范围
   ⭐⭐⭐ 路径会演进，以官方文档为准，别照搬文章里的路径
```

**一句话**：

> ⭐⭐⭐ **目录不是为了让结构显得完整，而是为了解决不同性质的问题——
> 所以从 1 个文件起步，SKILL.md 超 500 行或示例超 5 个时才拆，
> 而"参考文档给链接+摘要不要全文复制"这一条，
> 是因为塞进库里的每个字都要被反复付费。**
