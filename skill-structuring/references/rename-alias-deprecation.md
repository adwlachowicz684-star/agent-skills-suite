## 1. ⭐⭐⭐⭐⭐ 改名是破坏性的

代码里改函数名，编译期就报错；技能改名，**不会有任何东西报错**：

```
旧名字被调用 → 技能不存在
→ ⭐⭐⭐⭐⭐ 模型不会说"这个技能没了"
→ ⭐⭐⭐⭐⭐ 它会自己想办法完成这个任务
→ 于是：静默降级到你不知道的路径
```

> ⭐⭐⭐⭐⭐ **这是"技能失效没有错误、没有日志、没有告警"这条结论的又一场景。**

三处会断的地方：

| 断裂点 | ⭐ 症状 |
|---|---|
| ⭐⭐⭐⭐⭐ 触发匹配 | 用户说法没变，但描述里的名字变了 → 不再触发 |
| ⭐⭐⭐⭐ 文档与引用 | 全库 `《skill-x》的 y.md` 指向旧名 |
| ⭐⭐⭐⭐ 编排链 | 上游写死 `/old-name` → 调不动 |

> ⭐⭐⭐⭐⭐ 第一行最关键：**名字是触发词的一部分**。
> 改名字等于改触发集——所以按 `version-diff-behavior-compare.md` 的判据，
> ⭐⭐⭐⭐ **改名必须走行为对比，不能只走文本评审。**

## 2. ⭐⭐⭐⭐ 别名的三种形态

**① ⭐⭐⭐⭐⭐ 描述里保留旧名（最实用）**

```yaml
description: ...
  旧名 `old-name`（已弃用，等同本技能）
```

> ⭐⭐⭐⭐⭐ **这是唯一一种不需要运行时支持的别名**——
> 因为触发匹配发生在描述文本上，把旧名写进描述就等于它还能被匹配到。
> ⭐⭐⭐ 多数改名用这一条就够了。

**② ⭐⭐⭐⭐ 旧技能转发到新技能**

```markdown
# old-name（已弃用）
本技能已更名为 new-name。请改用《skill-x》的 new-name。
```

> ⭐⭐⭐⭐ 优点：显式调用 `/old-name` 也会得到指引。
> ⭐⭐⭐⭐ 代价：⭐ **它在库存里多占一个候选位**（常驻成本，见成本归账）。

**③ ⭐⭐⭐⭐ frontmatter 别名字段（若平台支持）**

```yaml
metadata:
  aliases: [old-name, legacy-name]
```

> ⭐⭐⭐ 最干净，但依赖平台支持——
> **开放标准只定义 6 个字段**，`aliases` 属于扩展，
> ⭐⭐⭐ 换平台会被忽略（见 `frontmatter-full-reference.md`）。

## 3. ⭐⭐⭐⭐⭐ 弃用的四段式

只写"已弃用"三个字，等于什么都没说。四段缺一不可：

```markdown
## 弃用说明

- ⭐ 状态：已弃用（自 2026-08-01）
- ⭐⭐⭐⭐⭐ 替代：用《skill-x》的 `new-name`
- ⭐⭐⭐⭐ 差异：新技能默认 dry-run，旧技能默认直接写入
- ⭐⭐⭐⭐ 移除时间：2026-11-01 后不再维护
```

> ⭐⭐⭐⭐⭐ **第三行最常被省，也最危险**：
> 如果新旧行为有差异，"改用新技能"这个建议本身就会引入 bug。
> 这正是 `skill-scope-tiering.md` 那条原则——
> ⭐⭐⭐⭐⭐ **没有恢复路径的空壳，就是没人承认的删除。**

> ⭐⭐⭐⭐ **第四行让弃用有终点。**
> 没有日期的弃用 = 永久保留 = 库存只增不减。

三条记录纪律：

```
① ⭐⭐⭐⭐ 写替代，不只写"已弃用"
② ⭐⭐⭐⭐⭐ 写新旧差异（行为层面的，不是"改了个名"）
③ ⭐⭐⭐⭐ 写移除日期
```

## 4. ⭐⭐⭐⭐ 迁移动作：谁去改调用方

> ⭐⭐⭐⭐ **别名只是缓冲，不是迁移。**

三个必须做的迁移动作：

**① ⭐⭐⭐⭐⭐ 全库引用替换（可 grep）**

```bash
grep -rn "old-name" --include="*.md" .
```

> ⭐⭐⭐⭐ 我们自己在多次拆分里反复踩这个：
> 移动文件后引用还指向旧路径。
> ⭐⭐⭐⭐⭐ **自动化这一步是唯一可靠的方式**——手工找必漏。

**② ⭐⭐⭐⭐⭐ 触发词补录**

```
旧名写进新技能的描述（见 §2 ①）
并确认用户会不会用旧名来叫它
```

> ⭐⭐⭐⭐ 判据：**用户实际会说的词，是捞的不是想的**（`trigger-word-mining.md`）。
> 旧名恰好是一个"已被证实会被说到"的词——⭐⭐⭐⭐ 所以它必留。

**③ ⭐⭐⭐⭐ 编排链里的写死引用**

```
上游技能正文里的 `/old-name` 必须同步改
```

> ⭐⭐⭐⭐ 这一处最容易漏，因为它不报任何错——
> 且属于 `change-impact-analysis.md` 里的第②类（编排下游会级联）。

## 5. ⭐⭐⭐⭐⭐ 别名不是免费的

| 代价 | ⭐ 说明 |
|---|---|
| ⭐⭐⭐⭐⭐ 常驻成本 | 旧技能仍在候选集里，⭐ **每次判断都收费**（成本归账） |
| ⭐⭐⭐⭐⭐ 触发干扰 | 两个语义相同的候选 → ⭐⭐⭐⭐ 选择质量下降 |
| ⭐⭐⭐⭐ 维护分叉 | 有人改了新的忘了旧的 |
| ⭐⭐⭐⭐⭐ "留着备用"变成永久 | 没有移除日期就不会有人移除 |

> ⭐⭐⭐⭐⭐ 第二行是我们已有结论的直接推论：
> **库存里每多一个语义重叠的候选，判断成本就上升一分**
> （这与"中间地带是技能死去的地方"不冲突——
> 那条说低频高价值该留，这条说⭐⭐⭐ **语义重复的别名不该留**）。

所以：⭐⭐⭐⭐⭐ **别名要有过期时间，且要写进弃用说明**（§3 第四行）。

## 6. ⭐⭐⭐ 什么时候不该改名

三种情况，改名的代价大于收益：

```
① ⭐⭐⭐⭐ 名字已经在用户需求里被反复使用
   → 改了就要长期维护旧名触发，反而更复杂
② ⭐⭐⭐⭐ 只是想让它"更准确"
   → ⭐⭐⭐⭐⭐ 改描述就够了，不必改 name
③ ⭐⭐⭐ 改名是因为技能被拆分了
   → ⭐⭐⭐⭐ 更该做的是让两个新技能各自有清晰名字，
     而不是给旧的留一个别名指向其中某一个
```

> ⭐⭐⭐⭐⭐ 第 ② 条最实用：**`name` 是标识，`description` 是触发面**。
> 想改变"什么情况下会被用到"，改 description；
> ⭐⭐⭐⭐ **改 name 只在"这个名字本身是错的"时才必要。**

第 ③ 条也是 `merge-signals-five.md` 的镜像：
拆分后旧名指向谁都不对——因为它现在对应两件事了。
⭐⭐⭐ 这种情况应该让旧名**彻底失效**（给出明确错误），
而不是悄悄指向其中一个。

## 一句可贴在墙上

> ⭐⭐⭐ **改名不会报错——它会静默地把调用方引向一条你不知道的路径。
> 所以：旧名写进描述、新旧差异写明、移除日期写死。**
