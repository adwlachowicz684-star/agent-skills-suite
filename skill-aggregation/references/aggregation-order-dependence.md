## 1. ⭐⭐⭐⭐⭐ 汇总常常不是一个可交换的函数

数学上可交换意味着 `f(A,B) = f(B,A)`。多数汇总实现不满足：

```
dedupe(保留第一个)   → 顺序改变结果
merge(后者覆盖前者)  → 顺序改变结果
"保留最新的一条"     → ⭐⭐⭐⭐⭐ 取决于"最新"怎么定义
```

> ⭐⭐⭐⭐⭐ **汇总看起来是一个纯函数，于是所有人都默认它与顺序无关。**

这个默认假设从不出现在文档里——因为它不是一个决定，是一个没人意识到自己做了的假设。

---

## 2. 三种顺序依赖

| 类型 | 例子 | 顺序改变什么 |
|---|---|---|
| ⭐⭐⭐ 去重 | 同 key 两条，保留哪条 | 保留下来的字段值不同 |
| ⭐⭐⭐⭐ 覆盖 | 两个 dict 合并，后者胜 | 最终字段值不同 |
| ⭐⭐⭐⭐⭐ 时间语义 | "取最新" / "取第一条" | 取到的那条完全不同 |

第三种最贵，因为它看起来是**有明确规则的**（"保留最新的"），而规则里的那个词在并行下没有定义。

---

## 3. ⭐⭐⭐⭐⭐ 并行下"顺序"由完成时间决定

串行时顺序是代码里的顺序，确定、可见、可复现。

并行时：

```
三路同时跑 → 谁先返回，谁就是"第一个"
→ ⭐⭐⭐⭐⭐ 顺序由完成时间决定，而完成时间受网络、数据量、重试影响
→ 每次运行都可能不同
```

于是症状是：

```
"跑两遍结果不一样"
```

> ⭐⭐⭐⭐⭐ 它会被归类为"模型不稳定"（failure-quadrant 的第 ④ 格：对但不稳），
> 而根因是一个⭐ **确定性的顺序依赖**——它每次都严格遵守规则，只是规则依赖了一个不确定的量。

这个误判的代价是：⭐⭐⭐⭐ 按"不稳定"去修（加示例、加约束、降低温度），**方向完全错了**，而且会让上下文更贵。

---

## 4. ⭐⭐⭐⭐⭐ "保留最新的"里的"最新"是谁的时间

最常见的一条汇总规则。作者写它时心里的"最新"通常是：

```
数据时间：created_at 最大的那条
```

而实现出来（尤其在并行汇总里）通常是：

```
到达时间：⭐⭐⭐⭐⭐ 最后返回的那条
```

> ⭐⭐⭐⭐⭐ **并行下，到达顺序与数据顺序无关。**
> 于是"保留最新"实际保留了"最慢返回的那个"——而最慢的通常是数据量最大或重试过的那个，
> 与"最新"没有任何关系。

可怕之处在于：⭐⭐⭐⭐⭐ **输出里没有任何东西能暴露这一点**——它给出一条记录，那条记录是真实存在的、字段是完整的、看起来完全合理。

修法只要半句：把"最新"写全。

```
❌ "保留最新的一条"
✅ "按 created_at 降序，取第一条（不得按返回顺序取）"
```

---

## 5. 去重：保留第一个还是最后一个

同 key 的两条记录，字段往往不同（一个来自缓存、一个来自实时接口）。保留规则不同 → 输出不同。

> ⭐⭐⭐⭐ **两条都合法，于是没有矛盾可报**——`merge-conflict-resolution` 的差值阈值在这里完全不适用。

所以去重规则必须显式写，且⭐⭐⭐⭐⭐ **必须绑定到数据字段，不能绑定到"顺序"**：

```
✅ "同 key 时取 updated_at 较大的一条"
❌ "同 key 时保留第一条"
```

---

## 6. 覆盖：后者盖前者，而"后者"不确定

字段级合并（`{**a, **b}`）几乎是所有汇总实现的默认写法：后者覆盖前者。

串行时"后者"是代码里的第二个；并行时⭐⭐⭐⭐⭐ **"后者"是最后返回的那一路**。

于是同一组输入、跑两次、两次结果不同，而两次都"严格遵守了合并规则"。

> ⭐⭐⭐⭐⭐ 这类 bug 的特征是：**它只在并行下出现，而在单路测试里永远无法复现**——
> 因为单路测试只有一条，"后者"总是那一条。

---

## 7. ⭐⭐⭐⭐⭐ 判据：把输入倒过来跑一遍

```
输入顺序 A,B,C → 输出 R1
输入顺序 C,B,A → 输出 R2
R1 ≠ R2 → 汇总存在隐藏的顺序依赖
```

成本是两次运行，不需要事先知道依赖在哪。

> ⭐⭐⭐⭐⭐ 它和 `fan-out-fan-in.md` 的顺序敏感性测试是同一个动作，但用途不同：
> 那份用它判 **"能不能并行"**；
> 这份用它判 **"不能并行的话，是哪一处顺序依赖在作祟"**——
> 判出来之后往下走到第 8 节修，而不是简单地"那就串行吧"。

---

## 8. 修法三档

**① 改成可交换（首选）**

```
"取 created_at 最大/最小的一条"   → 与顺序无关
"取数量最大/计数之和"              → 与顺序无关
```

> ⭐⭐⭐⭐⭐ **把顺序依赖换成数据依赖**——排序键改成数据字段，顺序就不再是变量。

**② 显式排序键**

```
"合并前先按 created_at 升序排序，再逐条合并"
```

注意排序键必须是⭐⭐⭐⭐⭐ **数据字段，不是到达顺序**——写"按到达顺序"等于没写。

**③ 报顺序**

```
输出首行："按 created_at 降序合并，共 3 路"
```

最弱的一档，但它是⭐⭐⭐⭐ **唯一能让顺序依赖可见的手段**：当下一次结果不同时，至少能看出"排序键变了"还是"到达顺序变了"。

---

## 9. 与顺序敏感性测试的关系

两份合起来才是完整闭环：

| | 那份（能否并行） | ⭐ 这份（怎么修） |
|---|---|---|
| 动作 | A→B 与 B→A 各跑一次 | 同样两次 |
| 结论 | 不同 → 禁止并行 | 不同 → 定位是哪一处顺序依赖 |
| 后续 | ⭐ 串行（代价：延迟） | ⭐⭐⭐⭐⭐ 改成可交换（代价：约 20 token，保留并行） |

> ⭐⭐⭐⭐⭐ 此前只有判据没有修法，于是"测出不同"的默认结论是放弃并行。
> 而多数顺序依赖只要换个排序键就能消除——**放弃并行是一笔不必要的交易**。

---

## 10. 自检

**① 把多路输入顺序倒过来跑一次。**
输出变了吗？变了 → 存在隐藏的顺序依赖，按第 8 节修。这个测试两分钟，能抓出并行汇总里最难发现的一类 bug。

**② 全文搜"最新/第一条/最后一个/后者/覆盖"。**
每命中一处，问：**这个词的基准是数据字段还是返回顺序？** 答不上来 → 它就是那条隐藏依赖。

**③ 把最慢的那一路人为延迟 10 秒，看输出是否变化。**
变了 → 你的汇总规则依赖到达时间，而到达时间在生产里由负载决定。

**④ 输出里有没有写"按什么排序合并"？**
没写 → ⭐⭐⭐⭐ 顺序依赖不可见，于是它永远不会被怀疑，只会被当成"偶发不一致"。
