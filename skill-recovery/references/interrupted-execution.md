## 1. ⭐⭐⭐⭐⭐ 中断不是失败，所以失败处理根本不会被触发

技能的失败处理是为"调用失败"设计的：脚本返回非零、API 报错、文件读不到。
而中断时**没有任何一步失败**——每一步都成功了，只是没有跑到最后。

```
三步写入流程：改 A → 改 B → 改 C
在改 B 之后被打断

A ✅ 已改   B ✅ 已改   C ⬜ 没轮到
```

> ⭐⭐⭐⭐⭐ **没有任何组件报错，因为没有组件失败。**
> 于是错误处理路径、重试逻辑、错误协议**全部不适用**——它们等的是一个不会到来的错误。

这就是为什么这类问题几乎从不被归因正确：

```
用户看到：技能"没做完"，但也没报错
诊断方向：❌ "是不是写错了" · ❌ "是不是触发有问题"
真因：    ⭐⭐⭐⭐⭐ 它做完了它做到的部分，然后被要求停下了
```

## 2. 三种中断

| 类型 | 触发者 | ⭐ 特征 |
|---|---|---|
| ⭐⭐⭐⭐⭐ 用户主动打断 | 用户（ESC / 发新消息） | 用户接下来多半会改需求，而世界已经变了 |
| ⭐⭐⭐⭐ 预算/超时耗尽 | 系统 | 与"跑不动"难区分——它看起来就是慢 |
| ⭐⭐⭐⭐ 被门禁拦截 | Hook / 权限（exit 2） | 有明确消息，但**只拦住当前那一步** |

第三种容易被误认为"安全地停下了"：

> ⭐⭐⭐⭐ **门禁拦住的是"这一步"，不是"这个技能"。**
> 之前已经完成的写入不会回滚，之后的步骤只是没发生——于是它等同于在第 N 步被打断，
> 只是多了一行看起来像错误的提示（而那行提示会被模型当成"这一步失败了"，不是"整体中止了"）。

## 3. ⭐⭐⭐⭐⭐ 中断留下的世界是"部分修改"的，而没有东西记录这一点

```
第一轮：改 A ✅ 改 B ✅ 打断
第二轮：重新运行
   → 看到 A 已改、B 已改
   → ⭐⭐⭐⭐⭐ "看起来做过了" → 跳过 → C 永远不会被改
```

> ⭐⭐⭐⭐⭐ 这是"不要用文件存在判断做过"的中断版本，而且更狠：
> 那份的问题是**拿到旧数据**（内容错），这份的问题是**跳过剩余步骤**（范围错），
> 而范围错不会产生任何错误数据可供比对。

三种后续走向，全部静默：

```
① 跳过已完成的部分 → 剩余部分被漏掉（用户以为全做了）
② 全部重做         → 幂等才有救；不幂等就是重复写入
③ 部分重做         → ⭐⭐⭐⭐⭐ 混合状态，且没有任何标记说明哪部分是哪一轮的
```

第③种最常发生，因为"看起来做过了"只对 A、B 成立，模型于是只做 C——
而 A、B 是第一轮的参数下改的，C 是第二轮的参数下改的。

> ⭐⭐⭐⭐⭐ **用户改了需求之后重新运行，是第③种的最高发场景**：
> 一半按旧目标、一半按新目标，而输出报告里完全看不出来。

## 4. ⭐⭐⭐⭐⭐ 最贵的推论：记录必须在开始之前写，不能在中断之后补

本能的修法是"中断时写一个 status: interrupted"。它不可靠，原因不是实现难：

> ⭐⭐⭐⭐⭐ **中断的定义就是"收尾动作不会发生"。**
> 任何依赖"中断之后执行某段代码"的方案，都在依赖一件被定义成不会保证发生的事。

所以规则反过来：

```
❌ 中断后记录
✅ ⭐⭐⭐⭐⭐ 开始之前先写 intent 文件（我要改 A / B / C，run-id=X，时间=T）
   → 启动时检查：存在未完成的 intent → 说明上次没跑完
   → 恢复（接着做 C）或回滚（按 intent 还原 A、B）
```

> ⭐⭐⭐⭐⭐ 这份文件的价值不在"记录进度"，在⭐⭐⭐⭐ **让"这次没跑完"这件事在进入正文之前就可见**——
> 而正文一旦开始执行，它面对的就是一个无法分辨"做过/没做过"的世界。

判据很干净：**如果现在断电，下次启动能不能判断出上次没跑完？** 不能 → 缺 intent。

## 5. 三种修法

| 修法 | 做法 | ⭐ 适用 |
|---|---|---|
| ⭐⭐⭐⭐⭐ 意图先行 | 开始前写 intent（含目标、受影响对象、run-id） | 所有写入型技能 |
| ⭐⭐⭐⭐ 原子化 | 写临时文件 → 全部成功 → 一次性替换 | 单文件/单目录改写 |
| ⭐⭐⭐ 分段可重跑 | 每段自带完成标记，重跑只做未标记的段 | 长流程、可幂等 |

第二条成本最低但适用范围窄：⭐⭐⭐⭐ **它只解决"改到一半的文件"，不解决"改了三个文件里的两个"**。

第三条要注意一个坑：**完成标记必须包含 run-id**。

```
❌ A.done（下一轮看到 A.done 就跳过——但它可能是上一轮参数下做的）
✅ ⭐⭐⭐⭐⭐ A.done.run-X（run-id 不匹配 → 重做）
```

## 6. ⭐⭐⭐⭐ 与"询问用户"的冲突

被打断后用户说"算了，改成 X"——

```
模型面对：A、B 已按旧目标改完，新目标是 X
默认动作：从当前状态继续做 X
```

> ⭐⭐⭐⭐⭐ **"从当前状态继续"在中断场景下几乎总是错的**，
> 因为当前状态是旧目标的产物，而它看起来和"正常的工作进度"一模一样。

正文要写的不是"如果用户改变主意"，是更具体的一条：

> ⭐⭐⭐⭐⭐ **已被中断过的运行，不得从当前状态继续——必须先确认已完成部分在新目标下是否仍然有效。**

与 `skill-execution/references/change-questions.md` 的分工：那份的四问用于**同一轮内**的目标变更；
这份用于**跨运行**的目标变更，此时已写入的副作用仍然存在（进度不持久，副作用持久）。

## 7. 检查清单

- [ ] ⭐⭐⭐⭐⭐ 写入型技能在开始前写 intent 文件（目标 + 受影响对象 + run-id）
- [ ] ⭐⭐⭐⭐⭐ 启动时检查是否存在未完成的 intent —— 有则恢复或回滚，不静默继续
- [ ] ⭐⭐⭐⭐ 完成标记带 run-id，不写裸 `.done`
- [ ] ⭐⭐⭐⭐ 多对象写入不用"文件存在"判断做过
- [ ] ⭐⭐⭐⭐ 正文写明：被门禁拦截 = 整体中止，不是这一步失败
- [ ] ⭐⭐⭐⭐ 打断后改需求：先核对已完成部分在新目标下是否仍有效
- [ ] ⭐⭐⭐ 长流程优先做成"分段可重跑"，而不是"整体原子"
