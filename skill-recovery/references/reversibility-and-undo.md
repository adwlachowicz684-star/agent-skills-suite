## 1. ⭐⭐⭐⭐⭐ "完成了"之后没有下一步

一个典型场景：

```
技能：批量重命名 47 个文件
输出：✅ 完成，已重命名 47 个文件
用户：等等，我给错规则了
```

> ⭐⭐⭐⭐⭐ **技能没有下一步了。它的输出是终点。**

为什么这是设计缺陷：

```
⭐⭐⭐⭐⭐ 技能定义了"怎么做"，也定义了"什么算完成"
⭐⭐⭐⭐⭐ 但几乎从不定义"做完了但错了，怎么办"
```

> ⭐⭐⭐⭐⭐ 于是用户的唯一选择是**手动逆操作 47 次**，
> ⭐⭐⭐⭐⭐ 而技能恰恰是刚刚证明自己能批量做这件事的那个东西——
> **它能做，但不能反做。**

## 2. ⭐⭐⭐⭐⭐ 三类可撤销性

按代价排（这个分类决定了后面所有动作）：

| | ⭐ 可撤销 | 例子 |
|---|---|---|
| **A ⭐⭐⭐⭐⭐ 天然可逆** | 是 | 生成文件（删掉即可）、分析、查询 |
| **B ⭐⭐⭐⭐⭐ 可逆但需记录** | 有条件 | 改名、改字段——**需要记得原值** |
| **C ⭐⭐⭐⭐⭐ 不可撤销** | 否 | 已发送、已发布、已删除（无回收站） |

> ⭐⭐⭐⭐⭐ 关键在 B：**它在物理上是可逆的，
> 但只有在"记住了原值"这个条件下才可逆。**
> ⭐⭐⭐⭐⭐ 而技能恰恰不负责记住任何东西（无状态）——
> **这个错位就是 B 类动作真正的风险来源。**

判据一句话：

> ⭐⭐⭐⭐⭐ **可逆性不取决于动作本身，取决于"逆操作所需的信息还在不在"。**

## 3. ⭐⭐⭐⭐⭐ 技能应留下 undo 信息

对 B 类动作，最低成本的做法：

````markdown
## 输出
完成后必须输出变更清单（机器可解析）：
```json
{"changes":[{"from":"old_name.md","to":"new_name.md"}],"undo_file":"<路径>"}
```
````

以及一条硬规则：

> ⭐⭐⭐⭐⭐ **写一个 undo 文件（或输出可反解的变更清单），
> 而不是只写"完成"。**

> ⭐⭐⭐⭐⭐ 为什么是文件而不是输出：
> ⭐⭐⭐⭐ **输出会随会话消失，文件不会**——
> 这跟"副作用持久，进度不持久"是同一个不对称，只是这次我们要利用它。

三个具体要求：

**① ⭐⭐⭐⭐⭐ 清单必须包含原值**

```
❌ "已重命名 47 个文件"
✅ ⭐⭐⭐⭐⭐ 每条记录含 before / after
```

> ⭐⭐⭐⭐⭐ 只记 after 的清单无法反解——
> 你不知道第 23 个文件原来叫什么。

**② ⭐⭐⭐⭐⭐ 清单本身是幂等的**

```
重复执行 undo 不应产生二次变更
```

**③ ⭐⭐⭐⭐ 报告 undo 手段，而不是等用户问**

```
✅ "已重命名 47 个；撤销：见 .undo/2026-09-29-rename.json"
```

> ⭐⭐⭐⭐ 这一条与错误协议里 `safe_reply` 那条同源：
> ⭐⭐⭐⭐⭐ **你不说"下一步能做什么"，用户就得自己想办法——
> 而他想的办法通常是手动重做 47 次。**

## 4. ⭐⭐⭐⭐⭐ 不可撤销动作的补偿，不是回滚

C 类（已发送、已发布）——

> ⭐⭐⭐⭐⭐ **不要假装能撤销。补偿和回滚是两件事。**

正确的做法是三条，按发生顺序：

**① ⭐⭐⭐⭐⭐ 发送前必须有确认点**

```
展示将要发送的内容 + 收件方，确认后再发
```

> ⭐⭐⭐⭐⭐ 这是唯一真正的防线（与写入边界那份一致）。
> ⭐⭐⭐⭐ 注意：确认点要在**内容已生成但尚未发送**时，
> 不能只是"要不要发送？"——那没有信息。

**② ⭐⭐⭐⭐⭐ 幂等键防重复**

```
同一意图重复执行只应产生一次副作用
```

> ⭐⭐⭐⭐⭐ 不可撤销动作的**重复**比"做错"更常见，
> 且⭐⭐⭐⭐⭐ 重复往往来自重试——
> 而重试是模型面对失败时的默认动作。

**③ ⭐⭐⭐⭐⭐ 输出里提供补偿动作，不是撤销动作**

```
❌ "可通过 X 撤销"
✅ ⭐⭐⭐⭐⭐ "已发送，不可撤销。如需更正：发送一条更正说明（模板见下）"
```

> ⭐⭐⭐⭐⭐ 差别很实在：前者让用户去找一个不存在的按钮，
> 后者给出了⭐⭐⭐⭐⭐ **一个实际存在的下一步**。

## 5. ⭐⭐⭐⭐ 部分成功时的撤销

最难的一种，也是最容易出错的一种：

```
47 个文件中，前 31 个成功，第 32 个失败
```

> ⭐⭐⭐⭐⭐ 此时"撤销"的语义本身有歧义：
> 撤销全部？还是只回滚失败的？还是保留成功的继续？

三条规则：

**① ⭐⭐⭐⭐⭐ 默认不自动回滚**

```
⭐⭐⭐⭐⭐ 部分成功时停下来报告，不要自动回滚已成功部分
```

> ⭐⭐⭐⭐⭐ 理由：自动回滚是一种⭐⭐⭐⭐ **模型替用户做的判断**，
> 而它通常猜不对——有时用户要的就是那 31 个。

**② ⭐⭐⭐⭐⭐ 报告必须区分"已变更"和"未变更"**

```
❌ "处理了 47 个，其中 16 个失败"
✅ ⭐⭐⭐⭐⭐ "已变更 31 个（清单见 X），未变更 16 个（清单见 Y）"
```

> ⭐⭐⭐⭐⭐ 前者让用户无法判断现在的状态是什么——
> 而"现在是什么状态"恰恰是撤销所需的全部信息。

**③ ⭐⭐⭐⭐ 提供两种撤销粒度**

```
回滚全部（用 undo 清单）/ 仅继续未完成部分（用未变更清单）
```

## 6. ⭐⭐⭐⭐⭐ 自检

对任何会改变外部状态的技能：

```
① ⭐⭐⭐⭐⭐ 这个动作属于 A / B / C 哪一类？
② ⭐⭐⭐⭐⭐ 若是 B：输出里有原值清单吗？清单落盘了吗？
③ ⭐⭐⭐⭐⭐ 若是 C：发送前有确认点吗？有幂等键吗？输出里有补偿动作吗？
④ ⭐⭐⭐⭐⭐ 部分成功时：会停下来报告吗？报告区分已变更/未变更吗？
```

> ⭐⭐⭐⭐⭐ 第 ① 问必须先答——
> **没分类就讨论"怎么撤销"，等于在讨论一个可能不存在的能力。**

一个十秒的判断：

> ⭐⭐⭐⭐⭐ **跑完之后，用户说"我搞错了"，
> 你要花多少时间恢复？答不出 → 可撤销性没设计。**

---

## 一句可贴在墙上

> ⭐⭐⭐ **可逆性不取决于动作本身，取决于逆操作所需的信息还在不在。
> 而无状态的技能恰恰不负责记住任何东西——所以你必须让它写出来。**
