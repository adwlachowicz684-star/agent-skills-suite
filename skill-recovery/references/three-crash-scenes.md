## 1. ⭐⭐⭐ 计算器被调用去"计算情绪"

**现场**：

```
用户问："我最近心情很糟糕怎么办"
⭐⭐⭐ agent ⭐ 优先调用了⭐ 计算器技能，试图去"⭐ 计算"用户的情绪状态
```

**根因**（这句是本份最该记住的）：

> ⭐⭐⭐⭐ **"LLM 在技能选择上会做⭐ 语义匹配，
> ⭐⭐⭐⭐ 而⭐ 语义匹配的边界⭐ 需要你⭐ 主动收紧。
> ⭐⭐⭐ 不要指望模型'理解'你技能的真实意图，
> ⭐⭐⭐ ⭐ 你必须在⭐ 文本层面逼它理解。"**

> ⭐⭐⭐ **"必须在文本层面逼它理解"**——
> 这句精确解释了为什么"反触发"有效：
> 它的作用不是"告诉模型别用"，
> ⭐⭐⭐ 而是⭐ **在文本上制造一段距离**，
> 让语义匹配在那一段距离上失败。
>
> ⭐⭐⭐ 所以我们已有的 `NOT for X → 用 Y 代替` 句式
> 在这里得到了⭐ 机制层面的解释——**"用 Y 代替"那半句之所以关键，
> 正是因为它把语义距离拉开了**（指向另一个明确的东西），
> 而不是只在原地加一个"不"。
>
> **修复后：误调用率几乎降到零。**

## 2. ⭐⭐⭐⭐ 脚本原始输出把主对话塞成炸药包

**现场**：

```
跑"爬虫技能"时，脚本把⭐ 原始网页全文⭐ 直接返回作为中间输出
这个输出⭐ 又被原样传给了模型继续处理
结果：⭐⭐⭐ 上下文里塞了 ⭐⭐⭐ 3 万多字的网页垃圾信息
      ⭐⭐⭐ ⭐ 模型在中途⭐ 丢掉了之前的关键任务指令
      ⭐⭐⭐ 对用户说"你在等什么，请告诉我你的具体需求"
```

> ⭐⭐⭐⭐ **这个症状极具迷惑性**：看起来是"模型变笨了/忘了任务"，
> ⭐⭐⭐ 但根因⭐ 完全不在模型，而在于⭐ **脚本输出没做压缩**。

**根因一句话**：

> ⭐⭐⭐⭐ **"本质上是把⭐ '工具执行' 和⭐ '上下文管理' ⭐⭐ 两件事混为了一谈。"**

**修复分两步**（这个两步结构值得照抄）：

```
① ⭐⭐⭐ 脚本层：过滤掉非正文内容
   ⭐⭐ 只保留⭐ 标题 · 正文段落 · 关键时间
② ⭐⭐⭐ 接入层：增加一个⭐ 摘要压缩节点
   ⭐⭐ 让脚本⭐ 先输出⭐ 结构化摘要⭐ 再传给 agent 主上下文
```

**效果**：

```
同样任务：⭐⭐⭐ 3 万字 → ⭐⭐⭐ 不到 2000 字符
⭐⭐⭐⭐ 而且⭐ 回复质量反而更高了
```

> ⭐⭐⭐ **"回复质量反而更高"** 是本份最反直觉、也最有说服力的部分——
> 它不是"以质量换成本"，而是⭐ **噪音本身就在损害质量**。
> 这与 `skill-reducer-study.md` 的"压缩后质量反升 2.8%"
> 是⭐ 完全同一现象的⭐ 第二个独立来源（一个在技能文本，一个在脚本输出）。

**已沉淀为团队规范的一句话**（可直接抄）：

> ⭐⭐⭐⭐ **任何脚本输出在进入上下文前，⭐⭐⭐ 必须先过一道⭐ 压缩或截断。**

> ⭐⭐⭐ 这条与 `token-bloat-audit.md` 的 Fix 6
> （"一个 dump 500 行日志的 Bash 命令会拖慢之后每一个响应"）同源，
> ⭐⭐⭐ 但这里把它提升成了⭐ **脚本契约的一部分**——
> 不是"少打点字"，而是⭐ **脚本必须负责自己输出的体积**。

## 3. ⭐⭐⭐ 第二个技能复用了第一个的中间状态

**现场**：

```
用户在⭐ 一次会话中⭐ 同时触发了两个技能链：
  "产品反馈标签提取" + "竞品价格对比"
两个技能内部⭐ 各自带着大量中间步骤

⭐⭐⭐ 执行第二个技能时，agent ⭐ 把它当成了第一个技能的延续
⭐⭐⭐ ⭐ 开始⭐ 复用第一个技能的中间状态
→ ⭐⭐ 第二个技能输出的⭐ 标签体系完全不符合预期
```

> ⭐⭐⭐ 这个失败模式此前⭐ 完全没覆盖过：
> 我们讲过"技能常驻"（激活后指令留在对话里），
> ⭐⭐⭐ 但没讲过⭐ **常驻的中间产物也会被复用**。
>
> ⭐⭐⭐⭐ **"技能 A 的中间状态" 在模型看来只是"上下文里的一段内容"——
> 它不知道那段东西属于 A 而不属于 B。**

**两条推论**：

```
① ⭐⭐⭐ 中间产物要⭐ 显式命名/加前缀，让它⭐ 自带归属标记
② ⭐⭐⭐ 跨技能交接时，⭐ 上一个技能应⭐ 明确收尾
   （对应 skill-chaining-composition.md 的 ANNOUNCE → SUMMARIZE → LOAD → PASS）
```

> ⭐⭐⭐ 这也解释了为什么"交接失败是最常见的组合坑"——
> 不交接的话，遗留的中间状态⭐ 会静默污染下一个技能。

## 4. ⭐⭐ 三个共同点

```
① ⭐⭐⭐ 三起事故⭐ 表面症状都不在根因所在层
   · 看起来是"模型乱调用" → 根因在⭐ 描述边界
   · 看起来是"模型变笨了" → 根因在⭐ 脚本输出
   · 看起来是"技能写错了" → 根因在⭐ 会话状态串扰

② ⭐⭐⭐ 三起都是⭐ 静默的——没有报错、没有异常，产出"看起来正常"

③ ⭐⭐⭐ 修复都不在"把指令写得更严厉"，
   ⭐⭐⭐⭐ 而是⭐⭐ 在⭐ 边界/体积/归属⭐ 这三个⭐ 结构层面
```

> ⭐⭐⭐ 第 ③ 条与 `feedback-loop-design.md` 的
> "规则升级为代码，而不是把段落写得更严厉"完全一致：
> **这三个修法都是结构性的，没有一个是"多说一句"。**

## 速查

```
□ ⭐⭐⭐⭐ 计算器算情绪 → ⭐⭐⭐⭐ 语义匹配的边界必须⭐ 主动收紧
   ⭐⭐⭐⭐ ⭐ 不要指望模型"理解"你的真实意图，⭐⭐⭐ 要在⭐ 文本层面逼它理解
   ⭐⭐⭐ 这解释了为什么 "NOT for X → 用 Y 代替" 有效：⭐ 它拉开了语义距离
   修复后误调用率⭐ 几乎降到零

□ ⭐⭐⭐⭐ 脚本原始输出 → ⭐⭐ 3万字 → ⭐⭐⭐⭐ 模型丢掉关键指令
   ⭐⭐⭐⭐ 根因：把"工具执行"和"上下文管理"混为一谈
   两步修复：⭐ 脚本层只留标题/正文/时间 + ⭐⭐⭐ 接入层加摘要压缩节点
   效果 3万字→<2000字符，⭐⭐⭐⭐ 且⭐ 回复质量反而更高
   ⭐⭐⭐⭐ 规范：⭐ 任何脚本输出进入上下文前⭐ 必须先过一道⭐ 压缩或截断

□ ⭐⭐⭐ 技能 B 复用了技能 A 的中间状态 → 产出体系全错
   ⭐⭐⭐⭐ 模型不知道那段内容属于 A 不属于 B
   → ⭐⭐ 中间产物显式命名/加前缀；⭐⭐⭐ 跨技能交接必须显式收尾

□ ⭐⭐⭐ 三起共同点：⭐⭐⭐ 表面症状都不在根因层 · 都静默 · ⭐⭐ 修复都在结构层
```

**一句话**：

> ⭐⭐⭐⭐ **三起事故最有价值的一条是"脚本原始输出把主对话塞成炸药包"——3 万字网页垃圾让模型中途丢掉关键指令并对用户说"你在等什么"，而根因不在模型在于把"工具执行"和"上下文管理"混为一谈；
> 修复后 3 万字降到 2000 字符且回复质量反而更高，因为噪音本身就在损害质量。**
