## 1. ⭐⭐⭐⭐⭐ 三种"结束"

技能通常只写了第一种：

| | 含义 | ⭐ 典型缺失 |
|---|---|---|
| **完成** | 做完了，交付 | ⭐⭐⭐⭐ 定义了"做什么"但没定义"做到什么程度算完" |
| **转人** | 需要人来定夺 | ⭐⭐⭐⭐⭐ **几乎从不写** |
| **放弃** | 做不到，停止 | ⭐⭐⭐⭐⭐ **几乎从不写** |

> ⭐⭐⭐⭐⭐ **只定义"完成"意味着：所有不能完成的情况，
> 都被默认归入"继续尝试"。**

而"继续尝试"的默认终点就是我们反复记录的那些事故：
静默编造 · 绕路 · 循环 · N 个半成品。

## 2. ⭐⭐⭐⭐⭐ 完成的定义必须是可判定的

典型的、不可判定的完成条件：

```
❌ "分析代码并修复发现的问题"
❌ "产出一份全面的报告"
❌ "确保没有遗漏"
```

> ⭐⭐⭐⭐⭐ **"全面""确保""没有遗漏"没有终止条件**——
> 它们只会导致两件事：要么永远不算完，要么模型自己宣布完成。

可判定的写法：

```
✅ "遍历 src/ 下所有 .ts 文件（数量以 `find` 结果为准），
    对每个文件输出 ≤3 条问题；全部文件处理完即结束"
```

三个要素，缺一不可：

```
① ⭐⭐⭐⭐⭐ 范围可枚举（能数出来）
② ⭐⭐⭐⭐ 每个单元有产出上限（≤3 条）
③ ⭐⭐⭐⭐ 有明确的"全部处理完"信号
```

> ⭐⭐⭐⭐⭐ 第 ① 条最关键：**"范围可枚举"是唯一能对抗"确保没有遗漏"的东西。**
> 如果你数不出总数，模型也数不出——
> 于是它只能"感觉差不多了就停"。

一个可直接用的自检：

```
问：这个技能跑完后，能不能回答"一共处理了多少个？"
   能 → 完成条件可判定
   不能 → ⭐⭐⭐⭐⭐ 它会停在一个任意的地方，而你无法判断是不是漏了
```

## 3. ⭐⭐⭐⭐⭐ 转人：三种必须交给人类的情况

> ⭐⭐⭐⭐⭐ **模型不知道自己不知道什么。
> 所以"该不该问人"这个判断，只能由技能预先写死。**

三种必须转人的情况（写成硬规则，不留给模型判断）：

**① ⭐⭐⭐⭐⭐ 不可逆动作前的确认**

```
发外部通知 · 删除 · 部署 · 提交 · 发邮件
```

> ⭐⭐⭐⭐ 这类已经反复提过，但这里要补一句：
> ⭐⭐⭐⭐⭐ **"确认"必须是显式的、带内容的**——
> "确认要继续吗？"不够，要显示"将要发给谁、内容摘要是什么"。

**② ⭐⭐⭐⭐⭐ 多个合理方案且后果不同**

```
"发现两种修法：A 改动小但有副作用，B 改动大但干净"
```

> ⭐⭐⭐⭐ 判据：**如果选错了需要回滚，就该问。**
> 模型的默认动作是挑一个继续（见 `default-actions.md`），
> ⭐⭐⭐⭐⭐ 而这个默认动作在"后果不同"的场景里是错的。

**③ ⭐⭐⭐⭐⭐ 信息缺失且无法推断**

```
"不知道目标是 staging 还是 production"
```

> ⭐⭐⭐⭐⭐ **这一条最该写、也最常缺**——
> 因为"缺失"时模型的默认动作是⭐⭐⭐⭐ **猜一个继续**（填默认值）。
> 而 ⭐⭐⭐⭐⭐ **默认值是作者的世界观，不是用户的。**

三条共同的写法要求：**问什么、给哪些选项、以及"如果用户不回答怎么办"**。
第三项常被忘，于是人没回答时它又回到"猜一个"。

## 4. ⭐⭐⭐⭐ 放弃：什么时候不该继续

> ⭐⭐⭐⭐ **不是所有失败都该重试，也不是所有缺失都能补。**

三种应该直接放弃（而非继续尝试）的情况：

| 情况 | ⭐ 为什么不该继续 |
|---|---|
| ⭐⭐⭐⭐ **缺少必要输入** | 继续 = 用猜测填补（见前置门禁） |
| ⭐⭐⭐⭐⭐ **前提不成立** | 继续 = 在错误的世界里成功跑完（见 `assumption-registry.md`） |
| ⭐⭐⭐⭐ **已尝试 N 次仍无进展** | 继续 = 循环（见 `budget-caps-no-progress.md`） |

> ⭐⭐⭐⭐⭐ 三者共同的判定：
> **"再试一次"改变的是运气，不是条件。**
> 如果条件没变，重试用处为零——这是与"重试预算"那份的分工：
> ⭐⭐⭐ 那份管"还能试几次"，这份管"根本不该试"。

放弃时的输出要求（容易被写成"失败了"三个字）：

```
1. 停止在哪一步（stopped_at）
2. ⭐⭐⭐⭐ 缺什么 / 什么前提不成立
3. ⭐⭐⭐⭐⭐ 用户下一步该做什么（具体动作，不是"请补充信息"）
4. ⭐⭐⭐⭐ 已经做了什么、是否需要回滚
```

> ⭐⭐⭐⭐⭐ 第 3 条决定这次失败是"有用的停止"还是"又一个死胡同"：
> ⭐⭐⭐⭐⭐ **"请提供更多信息"是零信息量的**——
> 要说"需要 `ANTHROPIC_API_KEY`，在 `.env` 里设置后重跑"。

## 5. ⭐⭐⭐⭐ 出口的三种写法

按可靠性排序：

**① ⭐⭐⭐⭐⭐ 条件式（最可靠）**

```markdown
如果遇到 <具体条件>，停止并 <具体动作>。
```

> 条件必须可判定。"如果觉得不确定"不可靠，
> "如果字段 X 缺失"可靠。

**② ⭐⭐⭐⭐ 清单式**

```markdown
完成前必须全部为真：
- [ ] 每个文件都已处理（总数 = find 结果）
- [ ] 每条问题都带了文件名和行号
- [ ] ⭐ 失败项已列入 failures 字段
```

**③ ⭐⭐⭐ 预算式（兜底）**

```markdown
最多 3 轮；超过则停止并报告当前状态。
```

> ⭐⭐⭐⭐ **第二种常被忽略的价值：它同时是完成条件和验收条件。**
> 一份清单既是"跑到哪算完"，也是"怎么检查跑完了"——
> 这省掉了单独写验收章节的成本。

## 6. ⭐⭐⭐⭐⭐ 没有出口的技能会怎样

三种结局，都不是"完成"：

```
① ⭐⭐⭐⭐ 无限细化：不断发现"还有一个问题"，永不结束
② ⭐⭐⭐⭐⭐ 自行宣布完成：跑了一段就"已完成"，实际漏了一半
③ ⭐⭐⭐⭐ 悄悄绕过：遇到阻碍换条路走，最后交付了另一个东西
```

> ⭐⭐⭐⭐⭐ **这三种在日志里都看不出异常**——
> ① 有大量成功步骤，② 输出格式完整，③ 每一步都成功。

这正是"局部成功、整体失败、且静默"这条结论的又一场景。
而修法很便宜：**补一节"什么时候结束/转人/放弃"，不到 100 token。**

> ⭐⭐⭐⭐⭐ 对照我们已有的结论：
> **模型有强烈的完成倾向，遇到阻碍的默认动作不是停下报告，而是想办法绕过去。**
> 所以"出口"不是可选优化，⭐⭐⭐⭐⭐ **是抵消这个默认倾向的唯一手段。**

## 一句可贴在墙上

> ⭐⭐⭐ **只定义"怎么开始"的技能，会把所有"不能完成"的情况
> 默认归入"继续尝试"——而继续尝试的终点，是静默编造。**
