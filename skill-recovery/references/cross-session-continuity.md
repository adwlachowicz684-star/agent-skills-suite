## 1. ⭐⭐⭐⭐⭐ 会话一断，什么都没了

一个典型现场：

```
第 1 天：技能跑了 12 个文件中的 8 个，会话结束
第 2 天：新会话，"继续昨天的"
→ ⭐⭐⭐⭐⭐ 模型不知道昨天跑到第 8 个
→ ⭐⭐⭐⭐ 它有两个选择：从头跑（重复），或从第 8 个之后猜着跑（漏）
```

> ⭐⭐⭐⭐⭐ **两个选择都是错的，而技能没写第三个选项。**

更隐蔽的一点：

```
⭐⭐⭐⭐⭐ 会话切换会重置"已完成"的记忆，但不会重置文件系统
```

> ⭐⭐⭐⭐⭐ 也就是说：**副作用是持久的，进度是不持久的。**
> 这个不对称是接续问题的根源——
> 已经写入的东西还在，而"写到哪了"丢了。

## 2. ⭐⭐⭐⭐⭐ 可接续的最小状态

不记全部，只记五件事。判据：**缺了它就无法安全继续**：

```
① ⭐⭐⭐⭐⭐ 已完成哪些（可枚举的清单，不是"大部分"）
② ⭐⭐⭐⭐⭐ 当前进度指针（下一个要处理的是谁）
③ ⭐⭐⭐⭐ 已发生的副作用（改了哪些文件 / 已发出什么）
④ ⭐⭐⭐⭐ 失败项及其原因
⑤ ⭐⭐⭐ 开始时间与输入版本（用于判断状态是否还新鲜）
```

> ⭐⭐⭐⭐⭐ 第 ① 条必须是可枚举的——
> 这与"完成条件必须可枚举"是同一条原则在新场景的应用：
> ⭐⭐⭐⭐ **"大部分完成了"无法接续，因为它没说哪部分没完成。**

第 ③ 条最容易被省，也最危险：

```
⭐⭐⭐⭐⭐ 不知道已经改过什么 → 继续跑会重复修改
→ 这正是幂等那份的核心：⭐⭐⭐ 先查状态，再决定跳过还是重做
```

## 3. ⭐⭐⭐⭐ 三种接续模式

**① ⭐⭐⭐⭐⭐ 外部进度文件（最可靠）**

```json
{"done":["a.ts","b.ts"],"next":"c.ts","failed":{"d.ts":"401"}}
```

> ⭐⭐⭐⭐⭐ 优点：跨会话、跨模型、可被人检查。
> ⭐⭐⭐⭐ 这是唯一一种"重启后仍然成立"的接续方式。

**② ⭐⭐⭐⭐ 从副作用反推**

```
扫描输出目录，看哪些产物已存在 → 推断已完成
```

> ⭐⭐⭐⭐ 优点：不需要额外状态文件（零维护）。
> ⭐⭐⭐⭐⭐ 缺点：**"产物存在"不等于"产物正确"**——
> 一个写了一半的文件也会存在。
> 所以⭐⭐⭐⭐ 需要配套的完整性标记（如 `.done` 后缀或校验和）。

**③ ⭐⭐⭐⭐ 重新开始（最被低估）**

```
不接续，整个重跑
```

> ⭐⭐⭐⭐⭐ **当任务是幂等且成本可接受时，重跑比接续可靠得多**——
> 因为它消除了"状态是否还新鲜"这个整类问题。
>
> 判据：⭐⭐⭐⭐⭐ **如果重跑一次的成本 < 排查状态不一致的成本，就重跑。**

> ⭐⭐⭐⭐ 这条与"确定性优于聪明"是同一取向：
> ⭐⭐⭐⭐⭐ **接续是一种优化，只有当它明显更便宜时才值得引入状态。**

## 4. ⭐⭐⭐⭐⭐ 为什么"让它自己看"行不通

最常见的做法是正文写一句：

```
❌ "如果上次未完成，先检查已完成的部分再继续"
```

三个问题：

**① ⭐⭐⭐⭐⭐ "已完成的部分"在哪里？没说**

> ⭐⭐⭐⭐⭐ 模型不知道该看哪个目录、哪个文件、什么格式。
> 于是它去看——**而它看到什么取决于它先打开哪个文件**。

**② ⭐⭐⭐⭐⭐ 它不知道"完成"的判据**

```
一个文件被创建了 = 完成？还是内容正确 = 完成？
```

> ⭐⭐⭐⭐⭐ 这正是"局部成功、整体失败"的又一场景：
> 每个文件都存在（局部成功），但有一半是半成品（整体失败）。

**③ ⭐⭐⭐⭐⭐ 它没有"上次"这个概念**

> ⭐⭐⭐⭐⭐ 新会话里"上次"指向什么，完全取决于你写了什么。
> 不写就是让它自己定义——⭐⭐⭐⭐ 而它定义的"上次"和你以为的不是同一个。

> ⭐⭐⭐⭐⭐ 三者的共同点：**"让它自己看"是把一个需要契约的问题，
> 交给了一个没有契约的推断过程。**

## 5. ⭐⭐⭐⭐ 写入位置与腐烂

进度状态写在哪里？

| 位置 | ⭐ 评价 |
|---|---|
| ⭐⭐⭐⭐⭐ 产物目录下的 `.progress.json` | 与产物同生命周期，好清理 |
| ⭐⭐⭐⭐ 独立的 `.claude/state/` | 集中，但⭐⭐⭐ 容易积累垃圾 |
| ⭐⭐⭐ 写在产物文件里（元数据） | 分散，但不会与产物脱节 |
| ⭐⭐⭐⭐⭐ **上下文里（不落盘）** | ⭐⭐⭐⭐⭐ **会话一断就没了——这不是接续，是假装接续** |

> ⭐⭐⭐⭐⭐ 最后一行是本份最想说的一句：
> **"我在上下文里记着进度"不是接续方案**，
> 因为上下文正是那个会消失的东西。

腐烂与清理：

```
⭐⭐⭐⭐ 进度文件要有时间戳 + 输入版本
   → 超过 N 天或输入已变 → ⭐⭐⭐⭐ 判定为陈旧，重新开始而非续跑
⭐⭐⭐⭐ 任务完成后删除进度文件
   → ⭐⭐⭐⭐⭐ 残留的 .progress.json 会让下次误以为"上次没做完"
```

> ⭐⭐⭐⭐⭐ 第二条很实在：**残留状态是"假失灵"的一个来源**——
> 它看起来像"上次中断了"，其实上次早就成功结束了。

## 6. ⭐⭐⭐⭐ 一个可抄的章节

```markdown
## 跨会话接续

进度写入 `<产物目录>/.progress.json`：
  done[] · next · failed{} · started_at · input_version

接续时：
1. ⭐⭐⭐⭐ 读进度文件；不存在 → 从头开始
2. ⭐⭐⭐⭐⭐ 校验 input_version 与当前一致；不一致 → 重新开始并说明原因
3. ⭐⭐⭐⭐ 校验 done[] 里的产物确实完整；不完整 → 移出 done，重做
4. ⭐⭐⭐⭐ 从 next 继续
5. ⭐⭐⭐⭐ 完成后删除进度文件

⭐⭐⭐⭐ 若重跑成本 < 校验成本 → 直接重跑，不接续
⭐⭐⭐⭐⭐ 不得依赖上下文中的"上次进度"——会话结束即消失
```

> ⭐⭐⭐⭐⭐ 第 2 条（版本校验）和第 3 条（完整性校验）
> 是最常被省的两步，**而它们正是"接续"和"盲接"的分界线**。

与相邻文档的分工：

```
idempotency-resume   同一会话内：中断后怎么继续（先查状态）
⭐⭐⭐⭐⭐ 本份           跨会话：上下文没了之后怎么继续（需要落盘状态）
memory-layering      技能=程序记忆；⭐ 指令层无状态，数据层可有状态
```

> ⭐⭐⭐⭐⭐ 最后一行点出了合法性：
> **"技能是无状态的"指的是指令层，不禁止数据层落盘。**
> 官方样例里的 `standups.log` 正是这个模式。
