# 行动前先查状态

> 一大类失败的根因是**假设环境已就绪**。
> 这条原则的修法很具体。

## 问题

```
技能：运行 npm run deploy
agent：直接跑 → 失败（依赖没装 / 没登录 / 分支不对）
用户：为什么它不问一声？
```

> 根因不是 agent 笨，是**技能没写"先检查"**。

## 模式

> ⭐ **不要假设环境已配好。让 agent 先验证状态，再分支。**

```markdown
先检查 X 是否已配置：
  [命令]
如果没配，引导用户完成设置：
  [步骤]
```

**完整形式**：

```
1. 检查（具体命令）
2. ⭐ 分支（配了 → 走主线；没配 → 引导设置或报错退出）
3. 主线
```

**关键在第 2 步的"或报错退出"**：

```
□ ⭐ 不能只有"引导设置"——有些情况不该自动配置
□ 例：生产环境缺凭据 → 停下来报给人，不要自己找
```

呼应 `approval-gates.md`（**`skill-governance`**）：
**门该拦不可逆操作**——自动配置基础设施也算。

## 三种该查的状态

**① 依赖与工具**

```
□ 需要的 CLI/库是否已安装、版本是否符合
□ ⭐ 版本检查：要有明确的最低版本
```

**② 凭据与环境**

```
□ 是否已登录、token 是否有效
□ ⭐ 环境变量是否存在（不打印其值）
```

**③ 前置产物**

```
□ 上一步的产物是否存在
□ ⭐ 不要重新生成已存在的东西（幂等）
□ ⭐ 也不要假设它存在
```

呼应 `idempotency-resume.md` 的状态文件检查。

## 查错地方比不查更糟

> ⭐ **一个真实案例**：
> 检查项目是否已有 i18n 时，如果在**文档目录**里搜，
> 会误判"已有 i18n 基础设施"，
> 从而跳过整个配置阶段，**整个流程从一开始就错了**。

```bash
# ✅ 只查源码目录
Grep: "i18next|useTranslation" in src/

# ❌ 不要在 docs/、README、.md 里搜
```

呼应 `i18n-implementation.md`（**`skill-domain-eng`**）。

**技能里要写清"在哪里查"**，不能只写"检查 X 是否存在"。

## 与幂等的关系

```
状态检查 = 幂等的前置条件

□ ⭐ 每个单元前检查状态 → 跳过已完成的 → 幂等
□ ⭐ 状态检查本身不能修改状态（除非明确是初始化）
```

> 最后一条容易犯：
> "检查一下配置文件是否存在，没有就创建一个"
> ——这已经不是检查了，是初始化，要走批准。
