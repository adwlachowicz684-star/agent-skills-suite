## 1. ⭐⭐⭐⭐⭐ 两个方向

```
     判断 ←─────────────────────→ 机制
      │                            │
  模型（读上下文、权衡）        脚本（计算、IO、解析）
      │                            │
      └──── 漂移发生在边界上 ──────┘
```

| 方向 | 表现 | 信号 |
|---|---|---|
| ⭐⭐⭐⭐⭐ 向外（膨胀） | 判断逻辑写进了脚本 | 脚本里出现业务规则、阈值枚举 |
| ⭐⭐⭐⭐ 向内（回归） | 模型不用脚本，自己重算 | 输出里的数字和脚本输出对不上 |

> ⭐⭐⭐⭐⭐ **膨胀是"脚本替模型做了决定"，回归是"模型替脚本做了计算"。**
> 两者都是越界，而越界的那次提交看起来都是一次正常的改进。

## 2. 方向一：脚本膨胀（判断进了代码）

演化的第一步总是合理的：

```
v1  scan(dir) -> files[]                    ← 纯机制
v2  scan(dir) -> files[] + 过滤测试文件      ← ⭐ 还是机制，因为规则明确
v3  + 排除 legacy/、vendor/、*.min.js       ← ⭐⭐ 开始是约定
v4  + "如果项目用了 monorepo 就跳过 packages/*/dist"
v5  + 按文件修改时间排序，优先最近改的
```

> ⭐⭐⭐⭐⭐ **从 v3 到 v5 的每一步，都是在把"作者当时的判断"固化成代码。**
> 而 v5 里那些判断在写下来的那一刻就已经开始过期了。

三个可识别的信号：

| 信号 | 例子 |
|---|---|
| ⭐⭐⭐⭐⭐ 脚本里出现"视情况"的等价物 | `if is_monorepo:` / `if len(files) > 50:` |
| ⭐⭐⭐⭐ 硬编码的业务枚举 | `SKIP_DIRS = ["legacy", "vendor", "tmp", ...]` |
| ⭐⭐⭐⭐ 脚本需要读参考文档才能理解 | 脚本里出现 `see references/xxx.md` |

> ⭐⭐⭐⭐ 第三条最准：**脚本本来是不需要上下文就能读懂的东西**，
> 一旦它开始需要文档，它就已经不是脚本了。

## 3. ⭐⭐⭐⭐⭐ 膨胀的代价不是复杂，是"确定的错误"

脚本最大的优点是确定性。膨胀之后，这个优点变成了缺点：

```
机制性判断（文件是不是 .ts）   → 一万次都对，且永远对
业务性判断（该不该跳过这个目录）→ ⭐⭐⭐⭐⭐ 一万次都一样地错
```

> ⭐⭐⭐⭐⭐ **确定性保证的是"每次一样"，不保证"每次都对"。**
> 而判断一旦进代码，纠正它的成本从"改一行正文"变成"改脚本 + 发版本 + 重新分发"。

配套的一个更隐蔽的问题：

> ⭐⭐⭐⭐ **膨胀后的脚本，其规则不再参与任何评审。**
> 正文的改动会经过 PR、会被人读到；
> 而 `SKIP_DIRS` 数组里加一个元素，在 diff 里就是一行字符串，
> ⭐⭐⭐⭐⭐ **它看起来像配置，实际是一条规则。**

这与《skill-precision》的
`skill-precision/references/constraint-carrier-ladder.md` 是同一个结构的两端：
那份讲"约束该放哪一层"，这份讲"**判断不该在脚本这一层**"——
脚本是最硬的一层，所以**判断放进去之后最难改**。

## 4. 方向二：模型回归（绕过脚本自己算）

反方向的漂移更不容易被发现，因为它不产生任何代码变更：

```
脚本输出：{"total": 1247, "anomalies": 3}
模型输出："共发现 5 处异常。"
```

> ⭐⭐⭐⭐⭐ **多出来的 2 处，是模型自己"看出来"的。**

三种触发，第二种最常发生：

| 触发 | 说明 |
|---|---|
| 脚本输出看起来太少 | 模型觉得"不止这些"，于是补充 |
| ⭐⭐⭐⭐⭐ 脚本输出格式不直观 | 模型读不出结构，于是自己重新算一遍 |
| 脚本失败过一次 | 模型记住了"它不太行"，下次自己来 |

> ⭐⭐⭐⭐ 第二种是纯设计问题，而且它指向一个反直觉的结论：
> **脚本输出越"可读"，模型越不会自己算。**
> 输出设计（见 `tool-output-design.md`）不只是效率问题，在这里是正确性问题。

代价：

```
模型重算 → 用了和脚本不同的口径 → 输出里两个数字不一致
        → ⭐⭐⭐⭐ 而用户只会看到最后那个（模型的）
```

> ⭐⭐⭐⭐⭐ 于是脚本的确定性被完全抵消：
> 一万次一致的计算，经过一次模型的"修正"，变成了不一致。

判据：**输出里的每个数字，都能在脚本输出里找到吗？**
找不到 → 它来自模型，而模型不掌握脚本的口径。

## 5. ⭐⭐⭐⭐ 判据：这一行的规则来自哪里

对脚本里每一行（尤其是每个 `if` 和每个常量）问三个问题：

```
① 这条规则的来源是什么？（代码库约定 / 团队决定 / 作者当时的判断）
② 它会变吗？
③ ⭐⭐⭐⭐⭐ 它变了之后，谁能发现？
```

| 回答 | 归属 |
|---|---|
| 来自代码库（扩展名、schema） | ✅ 脚本，且**应该运行时探测而非硬编码** |
| ⭐⭐⭐⭐⭐ 来自团队决定，会变，改了没人发现 | ❌ 应外置为数据文件 |
| 来自作者判断 | ❌ 应回到正文，让模型决定 |

> ⭐⭐⭐⭐⭐ 判据的简化版：**这一行的值，会在什么条件下变成错的？**
> 答"项目重构时" → 外置；
> 答"团队改主意时" → 回正文；
> 答"不会" → 留在脚本。

注意与《skill-patterns》的
`skill-patterns/references/reusability-over-specification.md`（先探测不先写）
是同一条原则在脚本层的版本：
**能探测的就不要写死，写死的就不是脚本该管的东西。**

## 6. 修法：规则外置，脚本只留机制

```python
# ❌ 规则在代码里
SKIP_DIRS = ["legacy", "vendor", "node_modules", "dist"]

# ✅ 规则在数据里，脚本只做"读规则并应用"
rules = json.load(open(os.path.join(HERE, "scan-rules.json")))
skip = rules["skip_dirs"]
```

差别不在优雅，在三件事：

| | 规则在代码 | ⭐ 规则在数据 |
|---|---|---|
| 改规则的 diff | 一行代码，看起来像重构 | 一行 JSON，看起来像配置变更 |
| ⭐⭐⭐⭐ 谁能改 | 要动脚本、要测试 | 直接改 |
| ⭐⭐⭐⭐⭐ 能否被模型读取 | 不能（脚本源码不进上下文） | 能（按需读） |

> ⭐⭐⭐⭐⭐ 第三行是关键：**脚本源码默认不进上下文，只有它的输出进。**
> 所以写在脚本里的规则，对模型是不可见的——
> 它无法核对、无法解释、无法在规则不适用时做出例外。

而规则的最终归属其实有三档，不该只有"脚本 vs 正文"：

```
① 永不变化的机制       → 脚本内硬编码
② 会变但需要一致执行的  → ⭐⭐⭐⭐⭐ 数据文件（脚本读，模型也能读）
③ 需要权衡的判断       → 正文（模型决定，脚本提供事实）
```

> ⭐⭐⭐⭐ 第 ② 档最常被跳过，于是它要么被当成 ① 写死，要么被当成 ③ 交给模型——
> **前者变成确定的错误，后者变成不确定的结果。**

## 7. ⭐⭐⭐ 第三种漂移：脚本成了唯一的事实来源

```python
def is_valid(x):
    return x > 0      # ⭐⭐⭐⭐⭐ "有效"的定义，只存在于这里
```

正文里写着"过滤掉无效项"，而"无效"的定义在脚本的一个函数里。

> ⭐⭐⭐⭐⭐ **定义的唯一副本在一个模型读不到的地方。**
> 于是模型永远无法回答"为什么这条被排除了"——
> 它只能复述脚本返回的结果。

修法是把定义抬到能被读到的层：

```json
{"valid_rule": "value > 0", "excluded": 12, "reason_counts": {"<=0": 12}}
```

> ⭐⭐⭐⭐ **脚本不必让模型理解规则，但必须让模型能引用规则。**
> 一行 `valid_rule` 字符串的成本，换来的是模型能解释自己的输出。

## 自检

| 检查 | 做法 |
|---|---|
| ⭐⭐⭐⭐⭐ 常量清点 | `grep -nE "^[A-Z_]+ *=" scripts/*.py`，逐个问"它会变吗" |
| ⭐⭐⭐⭐ 输出核对 | 跑一次，把模型输出里的每个数字与脚本输出对照 |
| ⭐⭐⭐⭐ 脚本是否需文档 | 新同事读脚本能否不看 references/ 就懂？不能 → 已膨胀 |
| ⭐⭐⭐ 规则副本 | 正文里提到的每个概念，其定义是否只在脚本里存在 |

> ⭐⭐⭐⭐⭐ 最省的一条：**把脚本里所有 `if` 的条件抄出来，**
> 逐个问"这个条件是谁定的"。
> 答"我定的"的那些，就是将来会咬人的那些。
