## 1. ⭐⭐ 技能脚本与 CI 脚本的差别

```
CI 脚本的读者      = 人（看日志判断成败）
⭐ 技能脚本的读者    = ⭐ 模型（看退出码与 stdout 判断成败）
```

> ⭐⭐ 这个差别决定了测试重点完全不同：
> **CI 脚本测试"有没有打出正确的日志"；
> 技能脚本测试"⭐ 模型能不能从退出码和 stdout 得出正确结论"。**

所以技能脚本的测试必须包含一类 CI 脚本不需要的断言：
**"失败时，模型会知道这是哪一类失败吗？"**

---

## 2. ⭐ 三层测试

```
L1 契约测试   ⭐ 退出码分级是否正确、stdout/stderr 是否分离
L2 行为测试   ⭐ 给定输入 → 输出（golden 文件对比）
L3 属性测试   ⭐ 确定性（跑两次 diff）、幂等（跑三次结果一致）
```

> ⭐ L1 最容易被跳过，但它恰恰是技能脚本特有的那一层。
> 一个输出完全正确、但所有失败都返回 `exit(1)` 的脚本，
> **L2/L3 全绿，而在真实使用中会让模型误判失败类型**
> （这正是 `script-cli-contract.md` 里"接口不通被误判成测试未通过"的场景）。

## 3. ⭐⭐ golden 文件法

**做法**：

```
① 准备一组有代表性的输入，放在 tests/fixtures/
② 跑一遍，把输出存为 tests/golden/*.expected
③ 之后每次改动，跑一遍并 diff
④ ⭐ diff 有差异时，必须人工确认是"预期变更"还是"回归"
   是预期变更 → 更新 golden 文件（并在 PR 里说明为什么）
   是回归     → 修脚本
```

> ⭐⭐ 第 ④ 步是这个方法的灵魂：
> **golden 文件不是"让测试变绿"的开关，它是⭐ 变更的可见化机制。**
> 你被迫回答"这次改动到底改变了什么输出"。

配套两条纪律：

```
· ⭐ golden 文件要进版本控制，并且 PR 里单独可见
· ⭐ 输入 fixture 要含边界情形（空输入、超长输入、异常字符），
  不能只有 happy path
```

## 4. ⭐ 退出码断言：测行为而不是测文本

```
❌ assert "error" in stdout          ← 测的是文本，措辞一改就假失败
✅ assert proc.returncode == 20      ← 测的是分类，与措辞无关
```

**按退出码分级分别断言**（承接 `script-cli-contract.md` 的 10/20/30）：

| 场景 | 期望退出码 | 断言重点 |
|---|---|---|
| 输入合法、正常完成 | 0 | ⭐ stdout 能被下游解析 |
| 输入不合法 | VALIDATION_FAILED | ⭐ stderr 有可执行的原因说明 |
| 找不到模板/资源 | TEMPLATE_NOT_FOUND | ⭐ 模型能据此换路径，而不是猜 |
| 数据量超限 | DATA_TOO_LARGE | ⭐ 模型能据此分批处理 |

> ⭐⭐ 关键断言是最后一条：**"模型能据此换路径"**。
> 一个笼统的 `exit(1)` 让模型只能重试或放弃；
> 一个 `exit(20)` 让它知道"找不到模板"→ 去找别的模板或问用户。

**还要断言 stderr 的"可行动性"**：

```
❌ stderr: "失败"
✅ stderr: "找不到模板 X：已搜索 scripts/templates/ 与 assets/，
          均未匹配。可用模板：A、B、C"
```

> ⭐ 后者直接给出了替代选项——这正是 `guidance-forms.md` 的
> "禁令/失败必须带替代方案"在脚本输出上的体现。

## 5. ⭐ 幂等性测试：跑三次

```
run1 = run(input)
run2 = run(input)
run3 = run(run(input))   ← ⭐ 对"已处理过的结果"再跑一次

assert run1 == run2      ⭐ 确定性
assert run2 == run3      ⭐ 幂等性
```

> ⭐⭐ 第三次的写法是关键：**喂给它上一次的输出**。
> 这能抓出最常见的技能脚本缺陷——**重复执行会重复追加**
> （日志追加两次、记录插入两条、文件被二次包裹）。

**确定性测试**（承接 `deterministic-scripts.md`）：

```
python3 x.py --time-range last_1h > /tmp/run1.json
python3 x.py --time-range last_1h > /tmp/run2.json
diff /tmp/run1.json /tmp/run2.json
⭐ 任何 diff 都意味着没达成纯函数保证
```

> ⭐ 排查顺序：**随机数 → 当前时间依赖 → 全局状态 → 字典遍历顺序**。

## 6. ⭐ 一个常被漏的点

> ⭐ **技能脚本的测试要覆盖"它被装在不同位置"的情况。**

```
· 用 `${CLAUDE_SKILL_DIR}` 引用自带资源 → 换位置仍可用
· 用相对路径 → 换目录就断
```

**测法**（很便宜）：

```
把技能目录复制到一个完全不同的路径再跑一遍测试
⭐ 这条能一次性抓出所有硬编码路径
```

> 这与 `cross-agent-portability.md` 的"用其他成员账号跑一遍"是同一思路：
> **在你的环境里能跑 ≠ 在别人的环境里能跑。**

## 速查

```
□ ⭐⭐ 技能脚本的读者是模型，不是人
   → 测试重点是"⭐ 模型能否从退出码得出正确结论"

三层测试：
□ ⭐ L1 契约（退出码分级、stdout/stderr 分离）——⭐ 最常被跳过
□ ⭐ L2 行为（golden 文件对比）
□ ⭐ L3 属性（确定性、幂等）

⭐⭐ golden 文件：
□ fixtures 含边界情形（空/超长/异常字符），不能只有 happy path
□ ⭐⭐ diff 有差异时必须人工确认"预期变更 vs 回归"
□ ⭐ golden 文件是⭐ 变更的可见化机制，不是让测试变绿的开关
□ golden 进版本控制，PR 里单独可见

⭐ 退出码断言：
□ ❌ 测文本（"error" in stdout）→ 措辞一改就假失败
□ ✅ 测分类（returncode == 20）→ 与措辞无关
□ ⭐⭐ 关键断言："模型能据此换路径吗？"
□ stderr 要给替代选项，不只是"失败"

⭐ 幂等：
□ run1 == run2（确定性）
□ ⭐ run2 == run(run1)（⭐ 喂上一次的输出，抓"重复追加"）
□ 排查顺序：随机数 → 当前时间 → 全局状态 → 遍历顺序

□ ⭐ 复制到完全不同路径再跑一遍 → 一次性抓出所有硬编码路径
```

**一句话**：

> ⭐⭐ **golden 文件不是让测试变绿的开关，它是变更的可见化机制——
> 每次 diff 都强迫你回答"这次改动到底改变了什么输出"。**
