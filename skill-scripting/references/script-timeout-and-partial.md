## 1. ⭐⭐⭐⭐⭐ 超时是最没信息量的失败

脚本的失败大致分两类：

| | 信息量 |
|---|---|
| 崩溃（异常 / 非 0 退出） | ⭐⭐⭐⭐ 有堆栈、有行号、有错误消息 |
| ⭐⭐⭐⭐⭐ 超时 | ❌ 只有"超过了某个时间" |

> ⭐⭐⭐⭐⭐ **超时不告诉你在哪一步、处理了多少、还剩多少。**
> 它甚至不区分"快跑完了"和"第一步就卡住了"。

而且它是**不稳定的**：同样的输入，可能 8 秒完成，也可能超时。
于是它被归类为"偶发问题"，而偶发问题的标准处理是重试——

> ⭐⭐⭐⭐⭐ **重试把超时从"一个需要修的问题"降级成了"一次需要绕过的卡顿"。**
> 这是它长期不被修复的机制性原因。

## 2. ⭐⭐⭐⭐ 中间那段时间是完全黑的

```
t=0     调用脚本
t=0~90s ⭐⭐⭐⭐⭐ 什么都没有
t=90s   超时 / 或者成功返回一大堆
```

与模型侧不同：**模型在思考时会输出进度**，而脚本在跑的时候不输出任何东西——
除非你显式写了。

三个后果：

| 后果 | 说明 |
|---|---|
| ⭐⭐⭐⭐ 用户以为卡死了 | 中断 → 又多一种半途状态 |
| ⭐⭐⭐⭐⭐ 无法判断"要不要等" | 模型不知道还剩 5 秒还是 5 分钟 |
| ⭐⭐⭐⭐ 超时后无法续跑 | 不知道已完成多少，只能从头 |

> ⭐⭐⭐⭐⭐ 中间那条最贵：**"要不要继续等"这个决定，模型没有任何依据可以做。**
> 于是它要么过早放弃（重跑，产生副作用叠加），要么一直等到超时（浪费整段时间）。

## 3. ⭐⭐⭐⭐⭐ 半途状态：最贵的产物

脚本跑到一半被中断时，文件系统里的东西处于三种状态之一：

| 状态 | 后续重跑 | 危险吗 |
|---|---|---|
| 没有写入任何东西 | 安全 | 低 |
| ⭐⭐⭐⭐ 写了完整的一部分 | 需要知道从哪里继续 | 中 |
| ⭐⭐⭐⭐⭐ 文件写了一半（截断） | ⭐⭐⭐⭐⭐ **存在但不可用** | 高 |

> ⭐⭐⭐⭐⭐ 第三种正是 `missing-input-upstream-failure.md` 里
> "存在 ≠ 成功"的三种形态之一：
> **存在性检查通过、格式检查可能也通过（前半段是合法的）、而内容不完整。**

典型场景：

```python
with open(out, "w") as f:        # ⭐⭐⭐⭐⭐ 先清空，再慢慢写
    for item in items:
        f.write(process(item))
```

中断发生在第 800 条时，`out` 里是 800 条——⭐⭐⭐⭐⭐ **它是一个看起来正常的产物**。

修法是原子写（写入临时文件 + rename）：
它保证的是"要么完整，要么不存在"，⭐⭐⭐⭐ **而不是"不会丢失"**——
两次完整写入、第二次覆盖第一次，每一次都是原子的（见
《skill-state》的 `skill-state/references/state-file-concurrency.md`）。

> 所以原子写解决的是"截断"，不解决"半途"。
> **半途需要的是状态记录，不是原子性。**

## 4. 修法一：进度走 stderr

```python
for i, item in enumerate(items, 1):
    if i % 100 == 0:
        print(f"[进度] {i}/{len(items)}", file=sys.stderr)
```

三条纪律：

| | 说明 |
|---|---|
| ⭐⭐⭐⭐⭐ 必须走 stderr | 走 stdout 会污染结果（`script-cli-contract.md` 已有） |
| ⭐⭐⭐⭐ 必须带分母 | "第 300 条"没有信息量，"300/1200" 才有 |
| ⭐⭐⭐⭐ 用固定前缀 | `[进度]` 让模型能识别这是进度而不是错误 |

> ⭐⭐⭐⭐⭐ 第二条的收益不止于可读性：
> **分母出现后，超时时模型能说出"已完成 300/1200"**，
> 于是"要不要重跑"第一次有了依据。

频率上：每 N 条一次，**不要每条一次**——
进度本身也是上下文成本（见
《skill-context》的 `skill-context/references/runtime-context-growth.md`）。

## 5. ⭐⭐⭐⭐⭐ 修法二：分块 + 断点续跑

把一个长脚本改成可续跑，只需要三个要素：

```
① 输出按块写（chunk_000.json, chunk_001.json, ...）
② 每写完一块，更新进度文件
③ 启动时先读进度文件，跳过已完成的块
```

```python
done = read_progress()          # {"completed_chunks": [0, 1, 2]}
for idx, chunk in enumerate(chunks):
    if idx in done["completed_chunks"]:
        continue                # ⭐⭐⭐⭐ 幂等重入
    write_chunk(idx, chunk)
    done["completed_chunks"].append(idx)
    write_progress(done)
```

> ⭐⭐⭐⭐⭐ **这让"超时"从一次失败变成一次暂停。**
> 第二次调用不是重跑，是继续——成本从 100% 降到剩余部分。

注意与幂等的关系（见 `duplicate-execution-hazards.md`）：

```
可续跑 ≠ 幂等
可续跑：重复调用不会重做已完成的部分
幂等  ：重复调用不会产生额外副作用
```

> ⭐⭐⭐⭐ **两个都要。** 只有可续跑时，块粒度之外的副作用（如最终汇总、发通知）仍会重复。

## 6. ⭐⭐⭐⭐ 修法三：超时前自己写状态

脚本无法知道自己什么时候会被杀掉，但可以**主动设置自己的上限**：

```python
DEADLINE = time.time() + 60      # ⭐⭐⭐⭐ 比外部超时早一点
for item in items:
    if time.time() > DEADLINE:
        write_state({"status": "partial", "done": n, "total": len(items)})
        print(json.dumps({"ok": False, "reason": "self_timeout",
                          "done": n, "total": len(items),
                          "resume": "再次调用本脚本会跳过已完成部分"}))
        sys.exit(30)
    ...
```

> ⭐⭐⭐⭐⭐ **自己超时返回 30，和被外部杀掉，对模型来说是完全不同的两件事：**
> 前者有结构化的状态、有分母、有续跑说明；
> 后者什么都没有。

差别值得强调：

| | 模型能做什么 |
|---|---|
| 被杀（外部超时） | ⭐⭐⭐⭐⭐ 只能重跑，且不知道要重跑多少 |
| 自超时（exit 30） | 可以决定继续、可以报 partial、可以只跑剩余部分 |

> ⭐⭐⭐⭐ 把"能不能优雅退出"从依赖外部机制，变成脚本自己能控制的事——
> 这是脚本层唯一能对抗超时的手段。

## 7. ⭐⭐⭐⭐ 与"重跑"的关系

超时之后的标准动作是重跑。这里有个容易算错的账：

```
重跑的成本 = 已完成部分 + 剩余部分
可续跑的成本 = 剩余部分 + 一次状态读取
```

看似可续跑总是更优，但有一条反例：

> ⭐⭐⭐⭐⭐ **如果重跑一次的成本 < 排查状态不一致的成本，就重跑。**
> （同《skill-recovery》的 `skill-recovery/references/cross-session-continuity.md` 的判据）

所以正确的顺序是：

```
① 脚本是否幂等？      → 否 → 先修幂等，再谈续跑
② 是否有半途产物风险？ → 是 → 原子写（不是续跑）
③ 单次耗时是否值得续跑？→ 只在超过某个阈值时才做断点续跑
```

> ⭐⭐⭐⭐ 第三步常被跳过：**给一个 8 秒的脚本做断点续跑，
> 引入的状态管理复杂度远超它省下的时间**，
> 而状态文件本身又带上了它那一整套问题（版本、并发、清理）。

## 8. 自检

| 检查 | 做法 |
|---|---|
| ⭐⭐⭐⭐⭐ 进度可见性 | 长循环里有没有 stderr 进度？带分母吗？ |
| ⭐⭐⭐⭐⭐ 半途产物 | 中途 Ctrl-C，输出文件是完整的、不存在的，还是截断的？ |
| ⭐⭐⭐⭐ 自超时 | 有没有内部 deadline？超时时能输出结构化状态吗？ |
| ⭐⭐⭐⭐ 重跑安全 | 连跑两次，副作用是 1 次还是 2 次？ |
| ⭐⭐⭐ 原子写 | 输出是否先写临时文件再 rename？ |

> ⭐⭐⭐⭐⭐ 最省的一条：**Ctrl-C 一次。**
> 它能在 10 秒内回答"半途状态"和"重跑安全"两个问题，
> 而这两个问题的每一种坏答案，在生产里都表现为"偶发的错误结果"。
