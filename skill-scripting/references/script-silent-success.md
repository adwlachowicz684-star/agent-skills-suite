## 1. ⭐⭐⭐⭐⭐ 四种"成功"

| | 退出码 | 输出 | 实际做了什么 |
|---|---|---|---|
| 真成功 | 0 | 有结果 | ✅ 做了该做的 |
| ⭐⭐⭐⭐⭐ **空集合成功** | 0 | `{"items": []}` | ❌ 一个都没处理（因为根本没找到） |
| ⭐⭐⭐⭐ **全过滤成功** | 0 | `{"kept": 0}` | ❌ 处理了，但过滤条件把全部排除了 |
| ⭐⭐⭐⭐ **降级成功** | 0 | 有结果 | ❌ 用了另一条精度更低的路径 |
| ⭐⭐⭐ **短路成功** | 0 | `{"skipped": true}` | ❌ 前置判断成立就直接返回 |

> **四类的共同点：脚本没有说谎。**
> 它精确地报告了它做的事——问题是它做的事不是你以为的那件。

## 2. ⭐⭐⭐⭐⭐ 为什么脚本尤其容易

脚本与模型的分工里有一条隐含假设：

```
脚本  → 产生事实
模型  → 产生语言
```

> ⭐⭐⭐⭐⭐ **"事实"这个定位让脚本获得了默认信任**——
> 它是确定性的、可复现的、跑一万次一个样的，
> 于是模型不会去核对脚本的输出，就像它不会去核对 `1 + 1 = 2`。

而这个信任在下面这个情况下是错的：

```
脚本确实跑了一万次都一样
⭐⭐⭐⭐⭐ 它只是每次都在确定性地处理一个空集合
```

> ⭐⭐⭐⭐ **确定性的名声被"成功"继承了，而"成功"这件事本身没有被确定性保证。**

第二个原因是结构性的：

> ⭐⭐⭐⭐⭐ **脚本处理集合，而集合的大小不由脚本决定。**
> glob 匹配多少文件、查询返回多少行、过滤后剩几条——
> 全部来自外部，脚本只是照着处理。

于是同一个脚本，在仓库 A 处理 47 个，在仓库 B 处理 0 个，**两次都是 exit 0**。

## 3. 形态一：空集合（0 匹配）

```python
files = glob.glob("src/**/*.ts", recursive=True)
for f in files:
    process(f)
print(json.dumps({"processed": len(files)}))
# → {"processed": 0}
```

三种成因，都静默：

| 成因 | 症状 | 为什么没人发现 |
|---|---|---|
| 模式写错 | `*.ts` 而项目是 `.tsx` | ⭐⭐⭐⭐ 0 是一个看起来合理的结果 |
| ⭐⭐⭐⭐⭐ `recursive` 漏了 | 只匹配一层 | 顶层确实有文件 → 有输出，只是少 |
| cwd 不对 | 从别处被调用 | ⭐⭐⭐⭐⭐ 见 `script-environment-assumptions.md` |

> ⭐⭐⭐⭐⭐ 第二种最贵：它不是 0，是 47 中的 12。
> **输出里有内容、有数字、格式正确，只是分母是错的。**

## 4. 形态二：全部被过滤

```python
items = load_all()                       # 1200 条
items = [i for i in items if i["status"] == "active"]
# → 0 条，因为字段实际叫 state，值是 "ACTIVE"
```

> ⭐⭐⭐⭐⭐ **过滤是"减少"，所以 0 是一个合法的减少结果。**
> 没有任何一个环节会认为"减到 0"是异常。

而且它比空集合更难发现：**脚本读到了数据、解析了字段、执行了比较**——
每一步都真的做了，只是比较永远为假。

判据很便宜：

```python
if not filtered and raw:
    print(f"⚠ 过滤后为空：原始 {len(raw)} 条，条件 {cond}", file=sys.stderr)
    # ⭐⭐⭐⭐ 关键：不是报错，是告警 + 保留分母
```

## 5. 形态三：降级路径

```python
try:
    import yaml
    cfg = yaml.safe_load(open(p))
except ImportError:
    cfg = parse_with_regex(open(p))   # ⭐⭐⭐⭐⭐ "贴心"地继续
```

> ⭐⭐⭐⭐⭐ **降级是脚本里唯一一种"作者以为在帮忙、实际在制造两种正确答案"的设计。**

它比直接崩溃危险，因为：
- 直接崩溃 → 有退出码、有 stderr、模型会报告
- 降级 → 输出结构相同、退出码相同，**只是值少了一部分或精度低了一档**

而且降级路径的测试覆盖率几乎总是 0——
因为它只在"缺依赖的机器"上执行，**而开发机上永远走主路径**。

规则：

> ⭐⭐⭐⭐ **是否降级是调用方的决定，不是脚本的。**
> 缺依赖就该非 0 退出并说明装什么；
> 只有调用方明确传 `--allow-fallback` 时才走备选路径。

## 6. 形态四：提前返回

```python
if not os.path.exists(path):
    print(json.dumps({"ok": True, "processed": 0}))
    return          # ⭐⭐⭐⭐ 一次"防御性"的早退
```

这个写法看起来是好的——它处理了文件不存在的情况，没有崩溃。
但它把三种完全不同的情况合并成了一个返回值：

| 情况 | 应该 |
|---|---|
| 真的没有这个文件 | ✅ 可以早退 |
| 路径算错了 | ❌ 应该报错 |
| ⭐⭐⭐⭐⭐ 上游技能没跑成功 | ❌⭐⭐⭐⭐⭐ **应该报错并说明** |

> ⭐⭐⭐⭐⭐ 第三种正是《skill-chain-failure》的
> `skill-chain-failure/references/missing-input-upstream-failure.md` 讲的失败：
> **B 报告"缺输入"，它是对的，而这个报错没有任何用**——
> 出错的是 A，而 A 已经成功退出了。

修法不是把早退改成崩溃，是让它带得动信息：

```python
if not os.path.exists(path):
    print(json.dumps({
        "ok": False,
        "reason": "missing_input",
        "expected": path,
        # ⭐⭐⭐⭐⭐ 让模型能说清"缺什么、为什么缺"
        "hint": "检查上游步骤是否已成功运行；文件应由此步骤生成"
    }))
    sys.exit(20)
```

## 7. ⭐⭐⭐⭐ 修法：让脚本报分母

> ⭐⭐⭐⭐⭐ **"处理了 0 个"和"没处理"是同一句话的两种写法，
> 除非输出里同时有分母。**

脚本的最小输出契约应该多两个字段：

```json
{
  "ok": true,
  "total": 47,        ← ⭐⭐⭐⭐⭐ 分母：本来应该有多少
  "processed": 47,    ← 分子：实际处理了多少
  "skipped": 0,       ← ⭐⭐⭐⭐ 跳过了多少（含跳过原因分类）
  "items": [...]
}
```

三个数一起出现时，静默成功无处藏身：

```
total=0     → 输入的集合就是空的（上游/路径问题）
total=47, processed=0  → 全被过滤或全被跳过
total=47, processed=12 → ⭐⭐⭐⭐⭐ 漏了 35 个（最贵的一种）
```

> ⭐⭐⭐⭐ 只报 `processed` 时，第三种和完全正常没有区别。

而 `skipped` 不分类就等于没报：

```json
"skipped": {"already_exists": 30, "filtered_out": 5}
```

> ⭐⭐⭐⭐⭐ 因为"跳过 35 个"里，
> **`already_exists`（重跑，无害）和 `filtered_out`（条件不匹配，可能是 bug）需要完全不同的反应。**

## 8. ⭐⭐⭐⭐ 与模型侧的分工

```
脚本侧（这份）：集合是空的 / 被过滤空了 / 走了降级 / 早退了
模型侧（empty-output-silent-success）：脚本成功返回后，模型没有输出
```

两者叠加时形成一个完整的静默链：

```
glob 0 匹配 → exit 0 → 模型认为"没有异常" → 回复"好的。"
```

> ⭐⭐⭐⭐⭐ **三个环节没有一个在说谎，而用户得到的是一次彻底的空转。**

所以两边的修法必须都做，只做一边没用：
- 只改脚本（报分母）→ 模型可能不读分母
- ⭐⭐⭐⭐⭐ 只改模型侧（要求"必须输出"）→ 模型会输出"已处理 0 个"，
  **这比沉默更糟，因为它现在有一个看起来经过核对的数字**

正确顺序是**先脚本后模型**：分母先存在，模型才有的可报。

## 9. 自检

| 检查 | 做法 |
|---|---|
| ⭐⭐⭐⭐⭐ 空输入测试 | 造一个空目录/空文件跑一次，看输出是报错还是 `{"processed": 0}` |
| ⭐⭐⭐⭐ 分母存在性 | 输出里有没有 `total`？没有 → 静默成功随时可能发生 |
| ⭐⭐⭐⭐ 降级路径 | `grep -n "except ImportError\|except Exception" scripts/*.py` 每处都要问：这是在降级吗 |
| ⭐⭐⭐ 过滤后为空 | 有没有"原始 N 条、过滤后 0 条"的告警分支 |
| ⭐⭐⭐ 早退点 | 每个 `return` / `sys.exit(0)` 是否携带可区分的 reason |

> ⭐⭐⭐⭐⭐ 最快的一条：**把输入目录改名再跑一次。**
> 如果脚本还是 exit 0 并且输出结构完全一样，
> 那么它区分不了"没有"和"没找到"——而这两种情况需要完全不同的处理。
