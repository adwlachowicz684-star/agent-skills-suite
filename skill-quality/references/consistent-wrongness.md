# 一致性错误比随机错误更危险

> 前置：`skill-triggering/references/failure-quadrant-diagnosis.md`（稳定地错 vs 偶尔错）
> 分工：那份讲**怎么把失败分到四象限**；本份讲一个更刺眼的结论——
> ⭐⭐⭐⭐⭐ 象限 ①（稳定地错）不是"好修"，是**最难被发现**，因为一致性看起来像正确性。

---

## 1. ⭐⭐⭐⭐⭐ 装了技能之后，bug 变少了——这可能是坏消息

```
装技能前：错误随机分布     → 用户注意到波动 → 提出质疑
装技能后：错误一致         → ⭐⭐⭐⭐⭐ 看起来像"规范" → 被接受
```

> ⭐⭐⭐⭐⭐ **一致性是正确性的伪装。**

用户的判断依据不是"对不对"（他往往不知道正确答案），
而是"这次和上次一样吗"。

> ⭐⭐⭐⭐⭐ 而"一样"恰恰是技能保证的——它不是技能的副作用，是技能的目的。

于是形成一个闭环：

```
技能让输出一致
→ 一致被读成"可靠"
→ 可靠导致不再核对
→ ⭐⭐⭐⭐⭐ 错误获得永久豁免
```

---

## 2. ⭐⭐⭐⭐⭐ 与四象限的关系：那份说"①好修"，本份说"①更难发现"

`failure-quadrant-diagnosis.md` 的判定：同一输入跑 3 次，全错 = ①系统性。

那份的处理建议是"改一次就好"——**在你知道它错的前提下**，这没错。
但它没说的是：

> ⭐⭐⭐⭐⭐ **"稳定"这个属性本身，会让你更晚知道它错。**

| | 稳定地错 ① | 偶尔错 ② |
|---|---|---|
| 用户感知 | ⭐⭐⭐⭐⭐ 无波动，看起来正常 | 有波动，会被质疑 |
| 报 bug 概率 | ⭐⭐⭐⭐⭐ 低 | 高 |
| 发现途径 | ⭐⭐⭐⭐⭐ 只能靠外部基准 | 多跑几次就能碰到 |
| 修复难度 | 低 | 高 |

> ⭐⭐⭐⭐⭐ **发现难度和修复难度是反的。**
> 而"能不能被发现"才是决定这个错误存在多久的变量。

---

## 3. ⭐⭐⭐⭐⭐ 与稳定性测试的张力（需要仲裁）

`skill-output/references/output-stability-contract.md` 教的做法：

```
/clear 后跑两遍，比较结构与主题
一致 → 判定"稳定"（作为优点）
```

本份要说的：

```
一致 → 只能证明稳定，⭐⭐⭐⭐⭐ 不能证明正确
```

仲裁结果——**两者都对，但一致性只是必要条件**：

```
✅ 一致性检查（内部）——证明"可复现"
✅ 基准对照（外部）  ——证明"是对的"
⭐⭐⭐⭐⭐ 只有前者，会把"稳定的错"判成"稳定得好"
```

> ⭐⭐⭐⭐⭐ **这也是"长期 100% 通过的测试集不是好消息"的第二条独立理由**——
> 第一条是测试集本身失效，这条是：被测物稳定地错，而测试集在确认它稳定。

---

## 4. 三种外部基准，任选其一即可打破闭环

| 基准 | 成本 | 适用 |
|---|---|---|
| ⭐⭐⭐⭐⭐ 无技能基线 | 低（跑一次不带技能） | 判断是否"装了反而更差" |
| 手工答案 5 条 | ⭐⭐⭐⭐ 中，但最可靠 | 判定型输出 |
| ⭐⭐⭐⭐ 另一模型 / 另一版本 | 低 | 快速发现口径分歧 |

> ⭐⭐⭐⭐⭐ 关键在于**基准必须独立于被测技能**。
> 用同一套规则生成的"期望输出"不是基准——它和被测物共享同一个错误源。

最容易被误当成基准的：

```
❌ 上一次的输出      —— 它可能是错的，而一致性会确认它
❌ 同一个技能的另一版 —— 两版可能犯了同一个错
❌ ⭐⭐⭐⭐⭐ 模型自己写的"标准答案" —— 同源，无法证伪
```

---

## 5. ⭐⭐⭐⭐⭐ 二次效应：一致的错误会变成规范

这是本份最远的后果，也是最难逆转的一步：

```
① 技能稳定地错
② 输出被人接受
③ ⭐⭐⭐⭐⭐ 这些输出被采集成"示例"（因为它们是真实被采纳的输出）
④ 示例反向教模型（见 `skill-examples/references/example-overrides-instruction.md`）
⑤ ⭐⭐⭐⭐⭐ 错误进入示例后，获得了比正文更高的优先级
```

> ⭐⭐⭐⭐⭐ **到这一步，错误已经不是"技能的问题"，而是"这个库的规范"。**

而采集示例是我们推荐的做法（"示例是采集的，不是编的"）——
本份给出这条建议的**前提条件**：

> ⭐⭐⭐⭐⭐ **采集被采纳的输出时，"被采纳"不等于"正确"。**
> 用户没有改就用，可能只是因为它每次都一样。

---

## 6. ⭐⭐⭐⭐⭐ 一条几乎零成本的检测

```
把输入改成一个你知道答案的变体，跑一次

输出跟着变 → 至少它在响应输入
输出不变   → ⭐⭐⭐⭐⭐ 它在输出一个固定的东西，而那个东西被当成了结果
```

与 `skill-aggregation/references/merge-conflict-resolution.md` 的自检同构：
把来源 A 改成 1,500，输出没变 → 它一直在取 B，从未比较。

这里的版本更通用：

> ⭐⭐⭐⭐⭐ **对输入不敏感的输出，不是"稳定"，是"固定"。**
> 两者在日志里长得一模一样。

---

## 7. Critical Rules

```
MUST NOT 把"输出一致"当作"输出正确"的证据 —— 一致是可复现性，不是正确性
MUST NOT 用上一次的输出当基准 —— 它可能就是那个稳定的错
MUST NOT 用模型自己生成的"标准答案"当基准 —— 同源，无法证伪
MUST NOT 因为"没人报 bug"判定技能健康 —— ⭐⭐⭐⭐⭐ 一致性错误恰恰不产生 bug 报告
MUST 至少一个独立于技能的外部基准 —— 无技能基线 / 手工答案 / 另一模型
MUST 采集示例前先确认输出是对的 —— "被采纳"不等于"正确"
```

---

## 8. 自检清单

```
□ 有没有一个独立于技能的基准？（不是上一次输出、不是模型自生成）
□ 最近一次"确认正确"是什么时候？依据是什么？
□ ⭐⭐⭐⭐⭐ 改一个已知答案的输入，输出会跟着变吗？
□ 示例里有没有从"稳定但错误"的输出里采集来的？
□ ⭐⭐⭐⭐⭐ 装了技能后 bug 变少 —— 是错误变少了，还是错误变一致了？
```

最后一条是本份的总纲：**这两个状态在监控面板上无法区分。**

---

## 9. 何时不用

```
Do NOT 用于：
❌ 怎么把失败分到四象限 —— `skill-triggering/references/failure-quadrant-diagnosis.md`
❌ 稳定性测试怎么跑 —— `skill-output/references/output-stability-contract.md`
❌ 多路结果矛盾 —— `skill-aggregation/references/merge-conflict-resolution.md`
❌ ⭐⭐⭐⭐⭐ 输出随机波动 —— 那是象限 ②，问题在歧义/依赖，不在于"一致性伪装"
```
