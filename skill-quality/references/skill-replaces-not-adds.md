# 技能是替换，不是叠加

> 前置：`skill-quality/references/capability-vs-preference.md`（能力问题 vs 偏好问题）
> 分工：那份讲**两类问题修法不同**；本份讲一个更在先的机制——
> ⭐⭐⭐⭐⭐ 技能一旦触发，模型的默认行为就被**替换**了，包括那些比技能更好的默认行为。

---

## 1. ⭐⭐⭐⭐⭐ 一个错误的心理模型

普遍直觉：

```
技能 = 给模型补充知识
水平 = max(模型自带能力, 技能描述的做法)
```

实际机制：

```
技能一旦触发 → 该范围内的行为由技能定义
水平 = 技能的水平（不是两者的最大值）
```

> ⭐⭐⭐⭐⭐ **技能不是"加上"一层能力，是"替换"一段行为。**

原因很直接：**指令的优先级高于先验。** 模型会抑制自己更优的默认解来遵守指令——
这不是缺陷，是"遵循指令"的定义。

---

## 2. ⭐⭐⭐⭐⭐ 推论：技能写什么，等于把什么从模型手里拿走

这是本份最值钱的一句：

> ⭐⭐⭐⭐⭐ **技能里写的每一条，都是在用"你的版本"替换"模型的版本"。**
> 如果你的版本不比它更好，这次替换就是净损失。

于是有了第一条可操作判据：

```
写每一条时问：模型不用这个技能，会怎么做？

一样  → ⭐⭐⭐⭐⭐ 删掉（它在替换一个等价行为，只增加偏离风险）
不一样 → 留下，并写清"为什么不用模型的默认做法"
```

> ⭐⭐⭐⭐⭐ 第二条里的"写清为什么"不是形式主义——
> 它让后来者（以及模型升级之后）能判断这条替换是否还成立。

---

## 3. 该替换什么、不该替换什么

| 内容类型 | 模型默认 | ⭐ 该不该写进技能 |
|---|---|---|
| ⭐⭐⭐⭐⭐ Gotchas（不可推理的坑） | 会踩 | ✅ 必写（这是替换收益最大的地方） |
| 项目/组织约定 | ⭐⭐⭐⭐⭐ 不可能知道 | ✅ 必写（训练数据里没有） |
| 输出格式与验收 | 每次不同 | ✅ 必写（任意性，价值在统一） |
| ⭐ 纪律约束（别猜、别跳过） | 倾向相反 | ✅ 必写（替换的对象正是默认倾向） |
| ❌ 通用最佳实践 | ⭐⭐⭐⭐⭐ 本来就会，且会随模型升级变好 | ⭐⭐⭐⭐⭐ **不写** |

> ⭐⭐⭐⭐⭐ 最后一行是本份的核心。
> "通用最佳实践"是最常写进技能的内容，也是唯一一类**会随时间自动变差**的内容——
> 因为模型在变好，而你的文字不变。

---

## 4. 与已有结论的衔接

本份不是新发现，是把三个已有结论统一到一个机制下：

| 已有结论 | 本份给出的机制 |
|---|---|
| ⭐⭐⭐⭐⭐ 59% 抵消（新增 553 次成功，带来 324 次失败） | 新增能力的同时替换掉了原有做法 |
| ⭐⭐⭐⭐ Outgrowth（基线 88% vs 技能 89%） | 技能的水平固定在写作时，模型在进步 |
| ⭐⭐⭐⭐ 能力问题 vs 偏好问题 | 能力问题是"替换有效"，偏好问题是"替换了但没换对" |

> ⭐⭐⭐⭐⭐ **"被追上"不是偶发事件，是替换机制的必然结果。**
> 只要技能写的是模型能学会的东西，它就一定会被追上。

与 `skill-triggering/references/outgrowth-regression-detection.md` 的分工：

```
那份：怎么测量"被追上了"（基线对照法）
本份：为什么会被追上 + 怎么写才能延后这一刻
```

---

## 5. ⭐⭐⭐⭐⭐ 反直觉推论：技能越"全"，衰减越快

```
大而全的技能（覆盖 20 个最佳实践）
  → 替换的面积大
  → 其中通用类占多数
  → ⭐⭐⭐⭐⭐ 模型每进步一次，就有一批替换变成净损失
```

> ⭐⭐⭐⭐⭐ **所以"大而全"不只是 token 成本高，它的半衰期也最短。**

这给了"惜字如金"一个机制性理由——此前我们只说"省 token"：

```
① 省上下文（已知）
② ⭐⭐⭐⭐⭐ 减少被替换掉的默认行为的面积（本份）
```

第二条更根本：**它解释了为什么删掉某段文字有时会让效果变好**——
不是因为省了 token，是因为把那段行为还给了模型。

---

## 6. ⭐⭐⭐⭐⭐ 纪律型技能是例外，也是替换最有价值的地方

```
约束型技能（"没有数据就写'未获取'，不得填 0"）
```

模型的默认倾向是"填一个看起来合理的值继续"。
技能要替换的**正是这个倾向**。

> ⭐⭐⭐⭐⭐ 这类替换不会随模型进步失效——因为模型的完成倾向不会消失。
> 所以它是最值得写、也最抗衰减的一类。

判据可以合并成一句：

> ⭐⭐⭐⭐⭐ **写"模型做不到"的（能力/知识/格式），别写"模型做得到但你可能忘了提醒"的。**

（与 `skill-crafting` 里"每条规则都要能对应一个失败场景"是同一判据的另一面：
对应不出失败场景的规则，往往就是"模型本来就会"的那类。）

---

## 7. 升级模型时该删什么

`skill-versioning/references/model-migration-audit.md` 说"升级模型默认做减法"。
本份给出**该减哪些**：

```
优先删（按此顺序）：
① 通用最佳实践      ← 模型已经会了，且更好
② 冗长的流程步骤    ← 模型能自己推（"给约束不给流程"）
③ ⭐⭐⭐⭐⭐ 验证指令  ← 新模型自带验证，沿袭的验证会导致过度验证

保留：
✅ Gotchas（不可推理，模型不会自己知道）
✅ 项目/组织约定
✅ 输出契约与验收
✅ 纪律约束
```

> ⭐⭐⭐⭐⭐ **判断方法：把这条删掉，用新模型跑一次。
> 结果不变或变好 → 它已经在做无用替换，该删。**

---

## 8. ⭐⭐⭐⭐⭐ 自检清单

```
□ 每一条都能回答"模型不装这个技能会怎么做"——答不上来就没法判断它在替换什么
□ 通用最佳实践类内容是否已标为"可移除"
□ ⭐⭐⭐⭐⭐ Gotchas / 约定 / 输出契约 / 纪律 四类是否齐了（这四类抗衰减）
□ 升级模型后是否按 §7 顺序做过减法
□ ⭐⭐⭐⭐⭐ 有没有"模型本来就会"的段落 —— 它们是未来被追上的主要来源
```
