# 官方有效性清单（逐项对照）

> 官方发布前的检查表，分四组。
> 带 ⭐ 的是最容易漏、且漏了会真出问题的项。

## 目录

- [核心质量](#核心质量)
- [代码与脚本](#代码与脚本)
- [测试](#测试)
- [几条常被忽略的细节](#几条常被忽略的细节)

## 核心质量

```
□ description 具体，且含关键词
□ ⭐ description 同时说清"做什么"和"什么时候用"
□ SKILL.md 正文 < 500 行
□ 需要时，额外细节拆到独立文件
□ ⭐ 不含时效信息（若有，放进 "old patterns" 章节）
□ 全文术语一致
□ 示例具体，不抽象
□ ⭐ 文件引用只有一层深
□ 恰当使用了渐进式披露
□ 工作流步骤清晰
```

## 代码与脚本

```
□ ⭐ 脚本自己解决问题，而不是把问题丢回给模型
□ 错误处理明确且有帮助
□ ⭐ 无"巫术常量"（每个取值都要有理由）
□ 指令中列出了依赖包，且已验证可用
□ 脚本有清晰文档
□ ⭐ 无 Windows 风格路径（一律正斜杠）
□ 关键操作有校验/验证步骤
□ 质量关键型任务包含反馈回路
```

**"巫术常量"** 这条值得单独说：
技能里出现 `timeout=30`、`max_retries=3`、`chunk_size=512` 这类数字时，
要么在注释里写清为什么是这个值，要么改成可配置参数。
模型会照抄这些数字到别处，而它们在那儿未必合适。

## 测试

```
□ ⭐ 至少建了三个评估
□ ⭐ 在 Haiku / Sonnet / Opus 上都测过
□ 用真实使用场景测过
□ 团队反馈已纳入（若适用）
```

⭐ **跨模型测试是最常被跳过、也最能暴露问题的一条。**
小模型对模糊指令的容忍度低得多——
一个只在 Opus 上跑得通的技能，换个模型可能连触发都对不上。

做法：同一个任务集，三档模型各跑一遍，
记录"触发率 / 步骤执行率 / 输出合格率"。
差异最大的那一项，就是你的指令最含糊的地方。

## 几条常被忽略的细节

**① MCP 工具要用完全限定名**

```
❌ bigquery_schema
✅ BigQuery:bigquery_schema
```

不加 server 前缀时，多个 MCP server 并存会让模型找不到工具。

**② 不要假设包已安装**

```
❌ "用 pdf 库处理这个文件"
✅ "先安装依赖：pip install pypdf
     然后：from pypdf import PdfReader"
```

**③ 执行意图要写清**

```
执行：  "运行 analyze_form.py 提取字段"
当作参考读：  "参考 analyze_form.py 了解提取算法"
```

这一句之差决定脚本是被跑还是被读进上下文——
**读进上下文就变成 token 成本了**。

**④ 按领域组织目录，便于发现**

```
✅ reference/finance.md   reference/sales.md
❌ docs/file1.md          docs/file2.md
```

**⑤ 打包完整资源不吃上下文**
完整 API 文档、大量示例、大体积数据集都可以放，
**在被访问之前不产生任何上下文成本**——这是渐进式披露的物理基础。

**⑥ 测试文件访问路径**
用真实请求验证模型能 navigating 你的目录结构。
写完了但模型找不到文件，等于没写。

## 一条反面对照

官方给的坏例子/好例子，差别在**触发条件**：

```
❌ "一个处理文档的有用技能"

✅ "填写 PDF 表单字段、提取表单数据、扁平化已完成的 PDF。
     当用户提到 PDF 表单、可填写表单或程序化字段填充时使用。"
```

第二条里有**具体的动作**和**具体的触发词**，
第一条两个都没有——模型无法据此路由。
