## 四维度与权重

| 维度 | 权重 | 关注 |
|---|---|---|
| **Clarity 清晰** | 25% | 结构、可读性、渐进式披露 |
| **Completeness 完整** | 25% | 覆盖面、示例、边界情况、反模式 |
| ⭐ **Accuracy 准确** | **30%** | ⭐ 正确性、最佳实践、安全 |
| **Usefulness 有用** | 20% | 真实适用性、生产就绪度 |

> ⭐ **Accuracy 权重最高，且是唯一有单项否决的维度**——
> 一个写得漂亮但给出危险建议的技能，比丑陋的安全技能更糟。

**另一套常见的四维度**（可作交叉参考）：

```
Clarity 25% · Completeness 25% · ⭐ Examples 25% · Focus 25%
总分 /20
```

> 差异在于后者单独把"示例"和"聚焦"列为维度。
> **如果你的技能库常见问题就是"例子不够""范围太宽"，用这套更对症。**

## 1–5 分量表

```
1  不可接受    根本性损坏、危险或不可用
2  需要大改    有重大问题，需要显著修订
3  可接受     ⭐ 达到最低标准，能用
4  良好        高质量，只有小改进空间
5  优秀        典范级，生产就绪，同类最佳
```

**以"示例"维度为例的具体锚点**（这种锚点比抽象描述有用得多）：

```
5  多个具体示例（3+）· 展示输入与输出
   · 覆盖常见场景与边界 · 示例真实可实践
4  2+ 具体示例 · 展示预期产出 · 覆盖主要用例
3  ⭐ 1–2 个示例 · 有些帮助 · 场景覆盖有限
2  只有 1 个示例或示例含糊 · 未展示输出 · 过于抽象
1  无示例，或示例令人困惑
```

**"聚焦"维度的锚点**：

```
5  单一清晰目的 · 范围明确 · 一句话能说清用途
3  主目的可辨 · 有些不必要的宽度 · 可以更紧凑
2  ⭐ 试图做太多 · ⭐ 应该拆成多个技能 · 职责混杂
1  无明确目的 · 单体式 · 不清楚它是干什么的
```

> ⭐ 判据很直接：**你能用一句话说清这个技能的用途吗？**
> 说不清，就是聚焦维度不合格。

## 通过线

```
最低      3.0 加权平均（可接受）
目标      4.0 加权平均（良好）
卓越      4.5+ 加权平均（优秀）

⭐ 单项否决：Accuracy 必须 ≥3.0（不能有危险建议）
```

**另一套阈值**（/20 制）：

```
18–20  优秀    生产就绪，典范
15–17  良好    建议小改进，可部署
12–14  及格    需要打磨，有显著改进空间
 9–11  弱      部署前需要大幅改进
 1–8   差      需要重做，未就绪

⭐ 最低部署要求：任何维度不得低于 3
⭐ 最佳实践：所有维度 ≥4
```

**总分解释要带上评级名**，别只给数字：

```
X/20（优秀 / 良好 / 及格 / 弱 / 差）
```

## 四种评审模式

| 模式 | 耗时 | 做什么 |
|---|---|---|
| **快速检查** | 秒级 | frontmatter 合法？必需章节在？代码块有语言标签？有无 TODO/FIXME？token 数合理？ |
| **完整评审** | 15–30 分钟 | 跑自动检查 → 人工通读 → 测试代码示例 → 逐维度打分 → 记录问题与建议 → 出报告 |
| **对比评审** | 中 | 与参考实现（如模板技能）逐项对照 |
| **批量评审** | 长 | ⭐ 按类别批量审，或筛出低于阈值的技能 |

> ⭐ **批量评审的实用用法**：
> `--below-score 3.5` 直接列出所有不合格的技能——
> 这是清库时的第一工具（呼应 `skill-distribution` 的 `library-ops.md` 的五维健康诊断）。

## 评审四要四不要

**✅ 要做**：

```
□ ⭐ 具体
  ❌ "有安全问题"
  ✅ "第 45 行：SQL 查询存在注入风险"

□ ⭐ 可行动——每个问题都附上怎么修

□ ⭐ 公平——用同一套标准

□ ⭐ 记录证据——每个分数都要引用具体内容

□ ⭐ 排序——关键问题在前，建议在后
```

**❌ 不要**：

```
□ 按个人风格偏好打分
□ ⭐ 标记废弃模式却不给替代方案
□ 因为缺"可选章节"就判不及格
□ ⭐ 无论其他维度多好，都忽略安全问题
□ 对复杂技能赶工评审
```

**报告模板**（固定结构，便于积累对比）：

```markdown
# 技能评审报告
**技能名**：  **评审人**：  **日期**：  **版本**：

## 执行摘要
总分 X/20（评级）——一段话总评

## 维度得分
### Clarity: X/5
观察：· 证据（引用技能原文）：
### Completeness: X/5
### Examples: X/5
### Focus: X/5
```

## 三个评分陷阱

> ⭐ **这三个陷阱会让整套评分体系失效**：

**① 橡皮图章（Rubber Stamp）**

```
现象  未充分评审就通过
危害  ⭐ 低质量技能会侵蚀对整个技能库的信任
修法  用完整评审清单，测试代码示例
```

**② 完美主义阻塞（Perfectionist Block）**

```
现象  因为小问题就判不及格
危害  ⭐ 让有用的技能无法被使用
修法  ⭐ 区分"阻断性问题"与"建议"
```

**③ 分数通胀（Score Inflation）**

```
现象  无理由给高分
危害  ⭐ 让分数变得没有意义
修法  ⭐ 每个分数都要有具体证据
```

> ⭐ 呼应 `skill-crafting` 的 `grounding-verification.md` 的"别让 AI 给自己的作业打分"：
> **评分必须由独立评审者给出，且要引用证据。**

**进阶：先验证证据再评分**：

```
□ 若为 AI 生成的代码，应用"验证缺口协议"
  ——用批评 agent、可验证目标、关键路径人工监督
□ ⭐ 若证据不完整（如资源注册表缺失），
   ⭐ 整体评分上限应被压到 6/10
□ 审核失败后必须重新审核，不能直接推进
□ ⭐ 无卓越证据不给满分——大多数质量工具应在 6–7 分区间
```

**接入 CI**：

```
□ 把快速检查放进 CI（结构性问题自动阻断）
□ ⭐ 安全扫描只警告不阻断（误报率高，自动阻断会侵蚀信任）
   ——呼应 CI/CD 流水线的那条决策
□ 低于阈值的技能自动列出，供批量清理
```

## 自查

```
□ 是否用了带权重的四维度（Accuracy 权重最高）？
□ ⭐ Accuracy 是否有单项否决（≥3.0）？
□ 1–5 分是否有具体的行为锚点（而非抽象描述）？
□ ⭐ "聚焦"是否用"能否一句话说清用途"来判？
□ 通过线是否明确（最低 / 目标 / 卓越）？
□ ⭐ 是否有"任何维度不低于 3"的部署底线？
□ 是否区分了四种评审模式（尤其批量评审用于清库）？
□ ⭐ 每条问题是否都具体（到第几行）+ 可行动（怎么修）？
□ ⭐ 每个分数是否都引用了证据？
□ ⭐ 是否区分了"阻断性问题"与"建议"？
□ 是否避免了三个陷阱（橡皮图章 / 完美主义 / 分数通胀）？
□ 是否知道"证据不完整时评分上限要压低"？
□ ⭐ 是否有独立评审者（不让 AI 给自己作业打分）？
□ CI 接入是否遵循"结构阻断、安全只警告"？
□ 报告是否有固定模板（便于跨技能对比）？
```
