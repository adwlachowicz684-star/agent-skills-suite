## 1. ⭐⭐⭐⭐⭐ 四类失败

按两个轴切：**结果对不对** × **是否稳定**。

|  | ⭐ **稳定**（每次都一样） | ⭐ **不稳定**（时好时坏） |
|---|---|---|
| **结果错** | ① 系统性错误 | ② 概率性错误 |
| **结果对** | ③ 健康 | ④ ⭐⭐⭐ 隐患（对但不稳） |

> ⭐⭐⭐⭐⭐ **第 ④ 格是最危险的一格**：
> 它现在是对的，所以没人管它；
> 而它不稳定，所以 ⭐⭐⭐⭐ **它随时会变成第 ② 格，且没人知道为什么**。

---

## 2. ⭐⭐⭐⭐⭐ 为什么这个二分最重要

> ⭐⭐⭐⭐⭐ **"稳定地错"和"不稳定地错"是两种完全不同的病，
> 但绝大多数排错流程对它们用同一套动作。**

具体后果：

```
把 ② 当成 ① 修：你改了指令，跑一次，对了 → 发布
                 ⭐⭐⭐ 但它下次还会错，因为根因没动
把 ① 当成 ② 修：你以为是模型随机性 → 加了更多示例、更多约束
                 ⭐⭐⭐ 它照样错，而且上下文更贵了
```

> ⭐⭐⭐⭐ 第二种浪费尤其常见，而且 ⭐⭐⭐⭐ **它主动让技能变差**——
> 这正是"一看到表现不对就疯狂补正文，越补越乱"的机制。

判定的代价极低：**同一个输入跑 3 次**（`three-skill-ceiling.md` 的触发稳定性测试）
就能分清。⭐ ⭐ **三次全错 = ①，三次不一样 = ②**。

---

## 3. ⭐⭐⭐⭐ 各类对应什么根因

**① 系统性错误（稳定 + 错）**

```
根因几乎都在⭐ 规格层：
  指令写错了 · 缺了一步 · 输出契约不对 · 依赖了错误的事实
```

> ⭐⭐⭐⭐ 好消息：**这一类最好修**，因为它可复现，
> 你改一次就能验证。坏消息：⭐⭐⭐ 它往往是"从没测过"——
> 因为作者测的是自己心里那个流程，不是文件里写的那个。

**② 概率性错误（不稳定 + 错）**

```
根因几乎都在⭐⭐⭐ 歧义层或环境层：
  指令有歧义（每次补的方式不同）
  ⭐⭐⭐ 依赖了没声明的东西（数据依赖/前置产物）
  ⭐⭐⭐ 依赖了顺序（并行或顺序不同结果不同）
  外部服务时好时坏
```

> ⭐⭐⭐⭐⭐ **这一类的第一嫌疑人是"没声明的依赖"**——
> 它的特征症状就是 ⭐⭐⭐⭐ **"时好时坏"**，
> 而这正是 `data-dependency-declaration.md` 里第四类（前置产物）的表现。

**③ 健康** —— 不用管。

**④ 隐患（对 + 不稳）**

```
⭐⭐⭐⭐⭐ 输出每次不同，但每次都能过关
```

> ⭐⭐⭐⭐⭐ **这是最该处理、也最没人处理的一格。**
> 它包含：风格漂移、长度波动、要素顺序不同、有时多给建议有时不给。

为什么危险：⭐⭐⭐⭐ **一旦输入稍微变化，它就掉进 ②**
——因为它本来就没有任何机制保证稳定。
而且 ⭐⭐⭐ 用户会注意到的：同一个技能，昨天和今天给的东西不一样。

## 4. ⭐⭐⭐⭐⭐ 诊断：先定象限，再动手

四步，每步都很便宜：

```
1. 取一个已知失败（或可疑）的输入
2. ⭐ 跑 3 次（清会话，见 output-stability-contract.md）
3. 看三次结果：
   全错且错法一样 → ①
   有错有对       → ②
   全对但长得不一样 → ④
4. ⭐⭐⭐⭐⭐ 再跑一个"应该成功"的输入 3 次
   → 这一步能抓出"只在某类输入上不稳"的情况
```

> ⭐⭐⭐⭐⭐ **第 4 步不能省**：
> 很多人只测失败输入，于是 ④ 永远进不了视野——
> 因为它在成功输入上"看起来是好的"。

修法对照：

| 象限 | ⭐ 修法 |
|---|---|
| ① | 改规格（指令、契约、事实） |
| ② | ⭐⭐⭐⭐ 消除歧义 / 声明依赖 / 固定顺序 —— **不是加示例** |
| ④ | ⭐⭐⭐⭐ 收紧输出契约（字段、顺序、长度区间、必需要素） |

> ⭐⭐⭐⭐ ② 那条最反直觉：**不稳定时，加示例是错的做法**。
> 示例教的是判断，而 ⭐⭐⭐ 不稳定的根因不是"不会判断"，
> 是"每次看到的世界不一样"（依赖缺失）或"有多个合理答案"（歧义）。

## 5. ⭐⭐⭐⭐ 一个常见误判

```
"分数从 95% 掉到 88%"
```

> ⭐⭐⭐⭐ 这个描述丢失了全部信息——**它没说是 ① 还是 ②**。

两种真相，完全不同的处置：

| | 真相 | 含义 |
|---|---|---|
| A | 12% 的输入**稳定地**错 | ⭐ 新增了一类情况没覆盖（可能是输入分布变了）→ 补规格 |
| B | 原来对的那些**现在时好时坏** | ⭐⭐⭐⭐ 技能在退化（模型更新/依赖漂移）→ 查漂移 |

> ⭐⭐⭐⭐⭐ **分辨方法**：看失败的那些是不是同一批。
> **同一批 = A；每批不一样 = B。**

这正好接上"回归 vs 被追上"那份：
⭐⭐⭐ B 就是 Regression，A 往往是 Outgrowth（出现了它本来就没打算覆盖的新输入）。

## 6. ⭐⭐⭐ 与阶段分类的合作

两套分类不冲突，是**两个维度**：

```
阶段分类（触发前 / 触发后）→ 回答"在哪出问题"
⭐ 本份（稳定 / 不稳定）   → 回答"是什么性质的问题"
```

> ⭐⭐⭐⭐⭐ **触发层的问题几乎全是 ① 或 ② 中的"稳定"侧**
> ——因为触发是匹配，匹配要么匹配上要么没匹配上。
> ⭐⭐⭐⭐ **执行层才大量出现 ② 和 ④**——因为生成有随机性。

所以一个高效的排错顺序是：

```
先按阶段定位（触发 or 执行）→ 再按象限定性 → 才动手
```

> ⭐⭐⭐ 还有一个交叉点值得记住：
> **复合失效（compound-failure）常常伪装成 ②**——
> 因为它"有时好有时坏"（取决于那个隐藏故障有没有机会表现）。
> ⭐⭐⭐⭐ **所以：如果按 ② 修了却没改善，回头怀疑复合失效。**

## 一句可贴在墙上

> ⭐⭐⭐ **先分清"稳定地错"还是"偶尔错"——
> 它们的根因不同，而你只有一次机会改对。**
