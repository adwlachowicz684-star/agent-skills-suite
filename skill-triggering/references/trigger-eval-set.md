## 最小可用形态

`evals/trigger-evals.json`：

```json
{ "id": "<skill>-pos", "skill": "<skill>",
  "prompt": "...", "should_trigger": true }
```

每个技能**一条正例 + 一条 near-miss 负例**。

> ⭐ **near-miss 负例是承重的那一半**——
> 只有它能发现"description 已经变得太宽"。

## 让这套真的起作用的三条规则

**① ⭐ 负例要针对"会和它混淆的那个兄弟技能"写，不是针对无关话题**

```
❌ 对一个 eval 技能，用"数据库"做负例
   ——什么也证明不了
✅ 用"调超参数"做负例
   ——它证明了 fine-tuning 的边界还在
```

判据：**这条负例能区分开哪两个技能？**
答不出来就是无效负例。

**② ⭐ 绝不在 prompt 里复用 description 的措辞**

```
❌ 用描述里的原词 → 变成字符串匹配测试，不是路由测试
✅ ⭐ 用自己的话写触发测试
```

这条最容易被违反，也最致命——
它让整套 eval 变成"證明我的描述包含这个词"，
而真问题是"用户用别的说法时它还认得出来吗"。

**③ 绝不让两个用例共用同一个 prompt**

```
重复的 prompt 会虚增用例数，且测的是同一件事两次
```

**④ 配套纪律**

```
□ 每新增或重命名一个技能，就加一组用例
□ ⭐ 跑 lint 脚本抓"缺配对"和"重复 prompt"
```

## 四类触发场景

一个最小 CSV（10–20 行）就该覆盖这四类：

| 类型 | 测什么 | 例子 |
|---|---|---|
| **显式调用** | 点名时能调起 | "用 $setup-demo-app 技能创建项目" |
| **隐式调用** | ⭐ 不点名也能选中 | "搭一个最小的 React + Tailwind demo" |
| **情境调用** | ⭐ 有噪声的真实提示也能触发 | "做一个展示 Responses API 的小 demo" |
| **负向对照** | ⭐ 不该触发时不触发 | "给现有的 React 应用加 Tailwind" |

最后一条的价值：它抓的是**假阳性**——
技能过于急切地触发，在用户只想增量改动时脚手架了一个新项目。

> ⭐ **这个 mix 是有意的**：
> 有些 eval 确认显式调用时的行为，
> 有些确认"用户完全没提到技能名"的真实场景。

## 可疑结果诊断表

| 症状 | 最可能的原因 | 修法 |
|---|---|---|
| **100% 通过** | 饱和——套件已不具区分力 | ⭐ 加更难的边界与对抗用例 |
| **某个任务 0% pass@100** | ⭐ 任务规格有问题或含糊，**不是模型不行** | 审规格；请第二个人给 transcript 打分 |
| **未改动但重跑分数就变** | 评委非确定性，或 trial 间共享状态 | ⭐ 固定 judge temperature、隔离环境、多次平均 |
| **评委高分但人不同意** | 评委未校准；长度偏差 | ⭐ 用示例输出重新锚定 rubric；验证与人工标签的一致率 |
| **过 eval 但生产失败** | 测试分布与真实流量不匹配 | ⭐ 从生产数据与 bug 报告重建用例 |
| **改进无法泛化** | 对迭代集过拟合 | ⭐ 在留出切片上打分 |
| **判分器绿但 transcript 错** | ⭐ 奖励黑客 / 代理指标 | 读原始 transcript；堵住漏洞；**断言最终状态** |

最后一行值得单独记：**判分器绿 ≠ 事情做对了**。
唯一可靠的是**读 transcript**并对最终状态断言。

## 召回随技能数退化

```
⭐ API 请求最多支持 8 个技能
⭐ 每多一个技能，它的 name+description 都在争夺注意力
```

两条操作含义：

```
① ⭐ 用 eval 套件量化"加了新技能之后召回有没有掉"
   掉了就停止添加

② 合并窄技能前，必须先用 eval 证明
   合并后的技能 ⭐ 与被它取代的那些表现相当
```

> 第 ② 条是个很好的闸门——
> **"合并看起来更整洁"不等于"合并后仍然好用"。**

## 循环：先跑基线

官方给的循环：

```
① ⭐ 先不开技能，在代表性任务上跑，记录具体失败
② 至少建三个针对这些缺口的 eval 场景
③ 测量基线
④ 写能通过的最小指令集
⑤ 迭代
```

> ⭐ **第一步不能省**：
> 你不知道它在哪里失败，就不知道 eval 该测什么。

## 五个维度（上线前都要过）

```
① 触发准确率
② ⭐ 隔离行为（单独用时能工作）
③ ⭐ 共存（不偷别人的触发词、不拖累兄弟技能）
④ 指令遵循
⑤ 输出质量
```

> ⭐ **永远既要单独测，也要在"当前启用的整套技能"旁边测。**
> **"描述太宽偷了兄弟技能的触发词"只在共存测试里才会暴露。**

以及那句反复出现的要求：

> ⭐ **Haiku / Sonnet / Opus 都要测——
> 对 Opus 足够的指令，对 Haiku 常常欠规格。**

## 一条关于 harness 的提醒

```
没有内置 eval runner → 你得自己搭
但 harness 可以很轻：
  跑 agent 时开 --json，把 JSONL trace 存盘，
  ⭐ 然后写确定性检查（有没有跑 npm install？
     有没有创建 package.json？命令顺序对吗？）
```

> ⭐ **先上轻量确定性判分，再考虑模型判分。**
> 这些检查快、可解释，是加任何模型评分之前该有的第一层。
