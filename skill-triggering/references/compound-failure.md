## 1. ⭐⭐⭐⭐⭐ 单因假设

几乎所有排错流程都隐含一个假设：

```
症状 → 一个根因 → 修它 → 好了
```

我们自己的五步排错顺序也是这么写的。这在多数时候成立，
但有一个前提：**同一时刻只有一个故障**。

> ⭐⭐⭐⭐ **而技能的实际失效，经常是复合的**——
> 因为技能的三个环节（发现 / 触发 / 执行）**由不同机制负责，
> 它们可以独立地各自坏掉。**

对照一下：一个程序要么编译不过、要么跑错，很少两者同时（编译不过就跑不了）。
**技能不一样——它可以在"根本没被发现"的同时"描述也写得不好"。**

---

## 2. ⭐⭐⭐⭐⭐ 互相当不在场证明

这是复合失效最毒的地方：

```
故障 A：技能从未被触发（文件层问题）
故障 B：description 写得过宽（会误触发）

你观察：没有误触发
你推断：description 没问题 ← ⭐⭐⭐ 错
真因：  它根本没被加载，所以 B 没有机会表现出来
```

> ⭐⭐⭐⭐⭐ **A 给了 B 一个不在场证明。**
> 你看到的"这个方面没问题"，可能只是"这个问题还没机会发生"。

反过来也成立：

```
故障 A：触发率很低
故障 B：触发后执行很差

你观察：跑 eval 分数很低
你推断：执行有问题，改正文
真因：  ⭐ 低分里混着"没触发导致的 0 分"和"触发了但做错的低分"
       → ⭐⭐ 你改正文，而正文根本没被读到
```

> ⭐⭐⭐ 第二种尤其常见：
> **触发率 40% 时，你的 eval 分数里 60% 是"没触发"贡献的，
> 而你把它当成了"执行不好"的证据。**

## 3. ⭐⭐⭐⭐ 三种典型复合

**① 未加载 × 描述差**

```
表现：技能形同虚设，但看不出哪里错
⭐ 陷阱：所有基于"观察行为"的诊断都失效——因为没有行为可观
```

**② 触发不良 × 执行不良**

```
表现：分数低，且怎么改都只改善一点点
⭐⭐ 陷阱：⭐ 改善"只有一点点"正是复合的信号
       ——单因故障修好了应该有阶跃，不是爬坡
```

**③ 描述宽 × 竞争者强**

```
表现：该触发时偶尔触发，不该触发时也偶尔触发
⭐ 陷阱：你会以为是两个独立问题，其实是同一个
       ——"它不够特异，所以既抓不住该抓的，也挡不住不该抓的"
```

## 4. ⭐⭐⭐⭐ 识别信号

四个信号，任一出现就怀疑复合：

| 信号 | 含义 |
|---|---|
| ⭐⭐ 改了有效但**只改善一点点** | ⭐⭐⭐ 有第二个故障在垫底 |
| ⭐⭐ 两个症状**互相矛盾** | 不可能同时成立 → 至少一个是假象 |
| ⭐⭐⭐ 修好 A 后**立刻冒出 B** | ⭐⭐⭐ A 一直在给 B 打掩护 |
| 同一个问题**反复修反复出现** | ⭐ 你在修症状，根因不止一个 |

第二个信号的例子：

```
"它从不触发" + "它老是乱触发"
→ ⭐ 不可能同时。其中一个是错的观察
   （多半是：在两个不同环境/不同人那里各观察到一半）
```

> ⭐⭐⭐ 这类矛盾信号最有价值，因为它**直接证明你的观察集不完整**。

## 5. ⭐⭐⭐⭐⭐ 解法：逐层清空

不要"找到根因就停"，要**逐层确认干净**：

```
第 1 层 文件/加载   → 确认技能真的在候选集里（/skills 或让模型复述）
   ⭐ 不干净就清干净，然后重新观察——不要往下走

第 2 层 触发       → 跑触发 eval（正例 10 / 近命中负例 10）
   ⭐ 触发率不达标就修到这里为止，先别碰正文

第 3 层 执行       → 才能开始改正文
   ⭐⭐⭐ 前两层没清干净就改正文 = 在噪音上调优
```

> ⭐⭐⭐⭐⭐ **核心纪律：每层清干净后重新观察一次，再决定去下一层。**
> 这正是 `troubleshooting-order-five-cases.md` 说的"找到问题就停"
> 的加强版——**不仅要停，还要停完重新看**。

配套一条硬要求：**每一层的结论要能被独立验证**。

```
❌ "应该加载了吧"
✅ "让模型复述流程，对得上"
✅ "`/skills` 里有它"
```

## 6. ⭐⭐⭐ 修好一个另一个显形，是好事

```
修好 A → B 立刻暴露 → ⭐ 你的第一反应通常是"怎么又坏了"
```

> ⭐⭐⭐⭐ **这不是又坏了，是诊断进度。**
> **B 一直存在，只是 A 挡着你看不见。**

判断方法很简单：

| 修好后 | 说明 |
|---|---|
| 出现的是**全新症状** | ⭐ 可能是你引入的回归，要警惕 |
| 出现的是**之前被抱怨过但查不到原因的症状** | ⭐⭐⭐ 是复合失效，继续修 |

> ⭐⭐ 区分这两条的关键：**新症状是不是有人早就提过？**
> 提过 → 复合；没人提过 → 你引入的。

## 7. ⭐⭐ 预防措施

三条，按成本排序：

**① 分层埋点**（最根本）

```
触发率 · 加载成功率 · 执行合格率 分开记
⭐ 三个数字一起看，复合失效无处藏身
```

**② 每次只改一层**

```
⭐⭐⭐ 一次 PR 只改一层的东西
   改了描述就别同时改正文
```

否则你无法归因——而这恰恰是复合失效的温床。

**③ 修之前写一句"我预期会看到什么"**

```
"我把 name 改对之后，预期 `/skills` 里会出现它，触发率从 0 变成 >50%"
```

> ⭐⭐⭐ **预期不匹配就是复合的信号。**
> 改对了但没达到预期 → 一定还有第二个故障。
> 这条几乎零成本，但能拦住大多数"我以为修好了"。

## 一句可贴在墙上

> ⭐⭐⭐ **改对了却没达到预期——那不是没改对，是还有第二个故障。**
