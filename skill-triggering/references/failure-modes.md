## 回归税

> ⭐ **最好的技能之所以胜出，主要是因为它们"让人变差得更少"，
> 而不是"让人变得更好得更多"。**

一项近 6,000 次运行的研究（两个办公自动化基准 × 三种模型框架）发现：

| 概念 | 定义 |
|---|---|
| **回归（regression）** | 不加技能能做对，**加了技能反而做错** |
| **残余失败（residual failure）** | 加与不加都做错 |

关键结论：**回归量大到足以主导排序**。所以：

> **不要把净效果只拆成"平均提升"——必须拆成 gain 和 regression 两部分看。**

另一项研究（SkillsBench + SWE-Skills-Bench）用差异分析法确认了 **307 次技能诱发的失败**：

```
125 次功能性失败 + 182 次效率退化
```

## 三种回归模式

| 模式 | 含义 | 为什么危险 |
|---|---|---|
| **① 描述渗透（description osmosis）** | **技能仅仅因为在上下文里存在就改变行为——即使从未被调用** | 你写的 description 本身就是指令 |
| **② 落地置换（grounding displacement）** | 技能规定的流程**覆盖了 agent 对自己输入的理解** | 流程压过了对实际材料的解读 |
| **③ 验证置换（verification displacement）** | 流程**压制了 agent 本来会对输出做的检查** | 走完流程就交付，不再自检 |

> ③ 尤其反直觉：你写了一份详细流程，
> agent 就**把"走完流程"当成了"任务完成"**——
> 它不再做那些本来会做的验证。

## 技能诱发失败的分类

### 功能性失败（125 例）

| 类型 | 占比 | 说明 |
|---|---|---|
| **任务实现错误（Task-Implementation Fault）** | **82/125** | 看似相关的技能让 agent **填错**（46）或**漏掉**（36）必需元素 |
| 环境错配（Environment Mismatch） | — | 技能假设的环境不成立 |
| 产物错位（Artifact Misplacement） | — | 输出放错位置 |
| **适用性错配（Applicability Mismatch）** | **仅 2/125** | 明显不相关的技能 |

> ⭐ **最重要的发现**：技能造成伤害**主要不是因为不相关**——
> 恰恰相反，**"看起来相关"的技能才是主要风险源**。
>
> 在功能性失败里，真正"不适用"的只有 2 例。
> 危险来自**被过度信任的正确相关性**。

### 效率退化（182 例）

| 类型 | 占比 | 说明 |
|---|---|---|
| **过度流程（Excessive Procedure）** | **114/182** | 把**可选的**探索、构建、验证变成了**强制工作** |
| └ 其中"过度验证" | **67** | 单独就占了一大块 |
| 上下文膨胀（Context Bloat） | — | — |
| 依赖解析（Dependency Resolution） | — | — |

> ⭐ **"过度验证"是最大的单一成本源（67 例）**。
> 这非常反直觉——我们以为多加校验更安全，
> 但**强制性的验证步骤会把可选工作变成必做工作**。

**推论**：

```
□ 校验步骤要分"必做"和"按需"，不要一律强制
□ 流程里写"如果 X 则检查 Y"，而不是"总是检查 Y"
□ 技能不该让简单任务变复杂——规模适配
```

## 检索是独立的瓶颈

> **更好的技能内容，不保证对的技能会被选中。**

| 候选池大小 | 实际使用精确率 |
|---|---|
| **5** | **29.6%** |
| **100** | **3.3%** |

> 候选池从 5 涨到 100，**精确率从 29.6% 掉到 3.3%**。

这就是为什么技能系统需要**命名、索引、过滤、上下文匹配**——
而不仅仅是"把技能写得更好"。

**另一个关键发现**：

> **调用到"完全正确的那个技能"既非充分也非必要条件。**
>
> 易混淆的干扰项会损害离线识别，但**下游成功率保持稳定**——
> agent 可能会适配、部分使用、或重建相关流程。

**推论**：别把"是否命中 ground-truth 技能"当成主要指标。
真正要看的是**下游任务是否成功**（见 `metrics.md` 第 5 层）。

## 技能真正的作用机制

> **技能主要是"流程锚点"，不是"知识注入"。**

| 机制 | 占比 |
|---|---|
| **流程锚定（procedural anchoring）** | **65.7%** |
| 显性知识注入（explicit knowledge injection） | **4.5%** |

> 技能**稳定的是 agent 的行动方式**，
> 而不是**提供它本来拿不到的事实**。

**为什么会这样**：agent 可能理解任务目标，
但仍因**工具顺序混乱、状态跟踪薄弱、错误恢复不一致**而失败。
一个结构良好的技能把**充满噪声的成功轨迹**变成**可复用的行动模式**。

匹配比较中，技能比 Workflow Memory 高 **6.06 分**。

### 由此推出的关键判断

> **技能擅长稳定流程，不擅长教知识。**

| 你想解决的问题 | 技能合适吗 |
|---|---|
| 工具调用顺序混乱、状态跟踪差、恢复不一致 | ✅ **这正是技能的主场** |
| agent 缺少某个领域事实 | ⚠️ 效果有限（仅 4.5%），考虑 RAG / references 检索 |
| 环境/工具/任务假设会变 | ❌ 脆弱假设是主要失败源 |

## 由此推出的写法

### ① 防描述渗透

> description 不只是路由元数据——**它在上下文里就是一条指令**。

```
□ description 里不要写行为规范（"总是……"）
□ 不要用"本技能会彻底重构你的代码库"这类暗示性措辞
□ description 只回答：做什么、何时用、不用于什么
```

### ② 防落地置换

> 流程不得压过对实际输入的理解。

```markdown
✅ 先读实际输入，再套流程：
1. 读取目标文件，记录实际结构
2. **若实际结构与以下模板不符，以实际结构为准并在输出中指出**
3. 套用流程……

❌ 直接开流程：
1. 按以下模板改写文件……
```

### ③ 防验证置换

> 加了流程之后，agent 反而**不再做本来会做的检查**。

```markdown
✅ 显式保留自检：
## 交付前
不论流程是否走完，都必须：
- [ ] 跑一次 <验证命令>
- [ ] 确认产出符合 <验收标准>
```

### ④ 防过度流程

> **67/182 的退化来自"过度验证"。**

| ❌ 强制 | ✅ 条件化 |
|---|---|
| "总是运行完整测试套件" | "若改动涉及核心逻辑则跑完整套件；否则只跑相关测试" |
| "每一步都要生成检查点文件" | "仅在中间产物需人工干预时落文件" |

**规模适配**：小任务不该触发完整仪式。

```markdown
若任务小于 <阈值>，跳过步骤 3–5 直接产出。
```

### ⑤ 减少检索压力

```
□ 技能总数控制在可控范围（候选池 5 → 100 会让精确率掉 10 倍）
□ name 与 description 用可区分的措辞，避免互相混淆
□ 定期用 /skill-doctor 清掉从不调用的（见 runtime-controls.md）
```

## 自查

```
□ 是否做了"无技能 / 有技能"配对对照来测 regression？
□ description 里有没有写成行为规范（会造成描述渗透）？
□ 流程是否允许"实际输入与模板不符时以实际为准"？
□ 是否显式保留了交付前自检（防验证置换）？
□ 校验步骤是否区分了必做/按需（防过度验证）？
□ 简单任务能否跳过部分仪式（规模适配）？
□ 是否存在脆弱假设（环境/工具/路径写死）？
□ 技能总数是否已膨胀到需要清理？
```
