# 触发调试实战

> ⭐ **核心洞察**：
> **手动测试用的是"你写 description 时的那套措辞"——当然会匹配。**
> 真正的问题是：**换别人用别的说法，它还匹配吗？**

## 五步排查法

**Step 1：先查结构与语法**

```
□ YAML frontmatter（引号未闭合、tab/空格混用）
□ description 是否超出平台字符上限
□ 标题层级是否符合预期（H1 标题、H2 章节）
□ 字段名里的 Unicode 字符会让解析器崩
□ ⭐ 空的 description —— agent 没有任何东西可匹配
```

> ⭐ **文件解析不了，后面什么都不用谈。**
> 先用校验器，再花时间debug别的。

**Step 2：用 10 种不同说法测试**

> ⭐ **不要用你写 description 时的那句措辞。**

```
□ 用一个"从没读过你的 description"的人会用的说法
□ ⭐ 请同事描述他想要什么，然后用他的原话
□ 覆盖 80% 的人可能描述这个功能的方式
```

> 呼应 `gen_eval_set.py` 与 `metrics.md` 的 near-miss 负样本。

**Step 3：查技能冲突**

```
□ 列出所有已装技能，找出领域重叠的
□ 用歧义 query 测试，看哪个赢
□ 错的那个赢了 → 收窄触发条件，或加显式排除
```

**Step 4：查会话日志**

```
□ 找"本该触发却没触发"的 query
□ ⭐ 记下确切措辞——那就是你要补的词汇缺口
```

**Step 5：持续监测真实触发率**

```
手动调试是"时间点"的：你今天修好了今天发现的，
⭐ 但明天会出现新的失败模式。
```

## 症状诊断表

| 症状 | 可能原因 | 修法 |
|---|---|---|
| **从不触发** | description 不匹配用户的语言 | 用真实用户措辞重写 |
| **错误 query 也触发** | 太宽泛、没有否定触发 | 收窄范围，加显式排除 |
| **时灵时不灵** | 与重叠技能冲突 | 检查可组合性，消歧 |
| **触发了但输出不对** | 指令含糊 | 加具体示例与期望输出格式 |
| ⭐ **测试通过、生产不灵** | **测试措辞是作者的词汇，不是用户的** | 用非作者的多样说法测 |
| **无法判断有没有触发** | 没有可观测性 | 加触发监测 |

> ⭐ 倒数第二行最值得记住——
> 这是"我以为它好了"最常见的来源。

**描述宽窄的两端**：

```
❌ 太宽："helps with coding tasks"
   ——与每个编程技能竞争，一个都赢不了
   ——agent 会降低它的优先级，因为对任何具体 query 都不是最佳匹配

❌ 太窄："generates TypeScript interfaces from OpenAPI 3.1 YAML specs"
   ——只有这个精确说法才触发
   ——"make types from my API spec""把 swagger 转成 TypeScript"全部漏掉

✅ 中间地带：2–5 句，覆盖三类触发
   · 显式触发：技能做什么
   · 隐式触发：解决什么问题
   · 上下文触发：什么情况说明它相关
```

## 为什么必须隔离重放

> ⭐ **链式工作流里，最难的 bug 是"看起来不像 bug"的**：
>
> 一个技能跑了、返回了东西、管道继续。
> **三步之后你才发现输出是错的**——少了个字段、截断得莫名其妙、
> 或者格式不是下一个技能期望的。
> **什么都没抛错。它只是安静地生产了垃圾，然后交给了下游。**

**为什么难抓**：

```
① 模型不抛异常
   让模型提取结构化列表，它返回了一段话——技能不崩，
   只是把一段话交给了下一步。
   ⭐ 如果下一步能宽松地解析这段话，错误就静默传播，
      直到有人看最终输出。

② 上下文跨步骤累积
   第 4 步的输入是第 1–3 步的输出
   ⭐ 等你看到坏输出，根因可能在两步之前，
      而模型早已把自己的行为合理化完了

③ 子代理异步运行
   ⭐ 一个遇到"软失败"的子代理，仍能返回格式良好的完成消息——
      只是内容不对

④ 静默截断很常见
   期望长结构化输入的技能，可能收到的是被裁剪过的
   ⭐ 裁剪从不被标记，技能只是拿得到的那部分继续干活
```

**正确做法**：

```
❌ 不要重跑整条链——浪费 token，且让失败更难观察
✅ 捕获失败技能收到的确切输入，单独重放它
```

**在边界校验，而不是在模型调用内部**：

```python
def run_skill(input_data):
    raw = call_model(input_data)
    validated = validate_output(raw)      # ⭐ 在返回前校验
    if not validated.ok:
        raise SkillOutputError(
            f"unexpected format: {validated.error}\n"
            f"expected: {validated.expected_schema}\n"
            f"got: {raw[:500]}")
    return validated.data
```

> ⭐ **关键是让 `SkillOutputError` 响亮**——
> 它打断管道，并明确告诉你哪个 schema 被违反了。
> 这比让畸形输出继续静默传播好得多。

**可观测性加在技能边界，不在模型调用内部**：

| ✅ 记 | ❌ 别记 |
|---|---|
| 调用前的输入 hash 与大小 | prompt 包装 |
| 返回后的校验结果（pass/fail + schema diff） | 每个中间想法 |
| 耗时（异常长常意味着截断或模型困惑） | 每次 token 计数 |
| **技能名与版本** | |

> ⭐ **记"技能名与版本"**——否则你不知道是哪个版本产出的。
> 呼应 `skill-governance` 的 `telemetry-schema.md`。

## 官方排查清单

```
不触发      → 改进 description，加用户真会说的触发短语
不加载      → 查路径、文件名（必须恰好是 SKILL.md）、YAML 语法
用错技能    → 让各 description 更彼此区分
被遮蔽      → ⭐ 查优先级层级，改名通常更简单
插件技能不见 → 清缓存 + 重启 + 重装
运行时失败  → 查依赖、权限（chmod +x）、路径分隔符（一律正斜杠）
```

**几个官方细节**：

```
□ SKILL.md 必须在具名目录里，不能直接在 skills 根下
□ 文件名必须恰好是 SKILL.md（SKILL 全大写，md 小写）
□ ⭐ 用 claude --debug 看加载错误，搜你的技能名
□ ⭐ 优先级冲突：企业版与个人版同名 → 企业版永远赢
   （解法通常是改名，比找管理员改企业版容易）
□ 运行时：依赖要装、脚本要 chmod +x、路径一律 /
```

> 呼应 `reload-debug.md`：**先跑验证器，再确认真的加载了**。

## 从手动调试到持续监测

> ⭐ **手动调试是反应式的**：
> 你注意到问题 → 调查 → 修复 → 希望修复能hold住。
> **这对你自己维护的单个技能有效。**
> **对 10+ 技能的工作区无效，对已发布的、用户词汇你无法预测的技能更无效。**

**为什么需要持续监测**：

```
□ 你可能因为"手动测试时触发正确了一次"就认为它好了
□ ⭐ 但多数用户不会报告"agent 没用我期望的技能"
□ 他们只是拿到一个次优的回答，然后继续干活
□ ⭐ 如果它仍漏掉 60% 的相关 query，你不会知道——
    直到有用户抱怨，而他们可能永远不会抱怨
```

**需要监测的四类信号**：

```
□ 真实触发率（不是假设的）
□ ⭐ 本该触发却没触发的 query（含确切措辞）
□ 触发了但输出不符合 schema 的比例
□ 冲突胜出情况（哪个技能抢走了本该属于别人的 query）
```

## 自查

```
□ 是否用"非作者的措辞"测过（而不是自己写 description 的那句）？
□ 是否请同事用他们的原话描述过需求？
□ 是否列了重叠技能并测过歧义 query？
□ ⭐ 是否有"本该触发却没触发"的监测（而非只看成功案例）？
□ 链式工作流里，是否在技能边界做了 schema 校验？
□ 校验失败是否"响亮"（打断管道）而非静默继续？
□ 日志是否记了技能名与版本？
□ 是否知道"子代理软失败仍会返回格式良好的完成消息"？
□ 是否考虑过长输入被静默截断的可能？
□ 是否知道优先级冲突时"改名"通常比"改上层"容易？
□ 是否跑过 claude --debug 搜自己的技能名？
```
