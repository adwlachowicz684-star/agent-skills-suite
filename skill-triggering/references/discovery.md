## 三层结构的官方口径

| Tier | 加载什么 | 何时 | 成本 |
|---|---|---|---|
| **1. 目录** | name + description | 会话启动 | **~50–100 tokens/技能** |
| **2. 指令** | 完整 SKILL.md 正文 | 技能被激活时 | <5000 tokens |
| **3. 资源** | scripts / references / assets | 指令引用时 | 因文件而异 |

> ⭐ **规范只定义了"目录里放什么"，不强制"目录放哪"**。
> 路径是各客户端自己的事——这也是碎片化的根源。

## 扫描规则

**扫什么**：在每个技能目录里找**含名为 `SKILL.md` 的子目录**。

```
~/.agents/skills/
├── pdf-processing/
│   ├── SKILL.md      ← 被发现
│   └── scripts/
├── data-analysis/
│   └── SKILL.md      ← 被发现
└── README.md         ← 被忽略（不是技能目录）
```

**实用规则**：

```
□ 跳过不可能含技能的目录：.git/ · node_modules/
□ （可选）尊重 .gitignore，避免扫构建产物
□ 设边界：深度 4–6 层、最多 2000 个目录，防止大规模目录树失控
□ 启动时扫一次；新会话重新扫（不重启可用 /reload）
```

**路径约定**：

| 层级 | 跨客户端 | 客户端原生 |
|---|---|---|
| 项目 | `.agents/skills/` | `.claude/skills/` 等 |
| 用户 | `~/.agents/skills/` | `~/.claude/skills/` 等 |

> 有些实现**也扫 `.claude/skills/`**（务实兼容，因为存量技能都在那）。
> 另外还有：向上到 git root 的祖先目录（monorepo 有用）、XDG 配置目录、用户自定义路径。

## 命名冲突

> ⭐ **通用约定：项目级覆盖用户级。**

同一作用域内（如同时在 `.agents/skills/` 和 `.claude/skills/` 发现同名），
**先找到或后找到都行——选一个并保持一致**。

> ⚠️ **冲突时要打日志**，让用户知道有个技能被**遮蔽（shadowed）**了。
> 否则用户会困惑"我明明装了它，怎么不生效"。

**一个实现细节**：有些运行时用**目录基名**作为规范标识符（而非 `name` 字段）
来做去重与冲突裁决——**所以目录名和 name 务必一致**。

## 信任门控

> ⭐ **项目级技能来自你正在处理的仓库，而那个仓库可能是不可信的**
> （比如刚 clone 的开源项目）。

**建议**：把项目级技能的加载**门控在信任检查之后**——
只有用户把该目录标记为可信时才加载。

**一个更精细的实现**（值得抄）：

> `!command` 这类**嵌入式 shell 命令只在可信位置的技能里执行**：
> 全局技能（`~/.agents/skills/`、`~/.claude/skills/`）、内置技能、
> 全局配置里声明的绝对路径。
>
> **项目级技能（`.kilo/skills/`）和从远程 URL 拉取的技能永不执行命令**——
> 它们的占位符被替换成一个标记，注明"该技能不可信"。

> 这条设计很聪明：**不是一刀切禁止，而是按来源分级**。
> 呼应 `skill-orchestration` 的 `prompt-injection.md` 的"按信任级别分类每项输入"。

## 模式专属技能

> 部分实现支持**只在特定模式下激活**的技能：

```
~/.roo/skills-code/          # 仅 Code 模式
.roo/skills-architect/       # 仅 Architect 模式（项目级）
.agents/skills-{modeSlug}/   # 跨客户端的模式专属
```

**优先级**（高→低）：

```
1. 项目 .roo/ 模式专属
2. 项目 .roo/ 通用
3. 项目 .agents/ 模式专属
4. 项目 .agents/ 通用
5. 全局 .roo/ 模式专属
6. 全局 .roo/ 通用
7. 全局 .agents/ 模式专属
8. 全局 .agents/ 通用
```

> **项目技能永远覆盖同名全局技能；同项目层级内 `.roo/` 覆盖 `.agents/`。**

**什么时候用模式专属**：

| 场景 | 为什么 |
|---|---|
| 代码重构模式（仅 Code 模式） | Architect 模式下它是噪音 |
| 系统设计模板（仅 Architect 模式） | 反之亦然 |

> ⚠️ **一个真实故障**：技能放在 `skills-code/` 但你在 Architect 模式——**它不会加载**。
> 排查时先确认模式对不对。

## 符号链接共享

> **技能支持符号链接**——这是跨项目共享技能库的正确姿势：

```bash
ln -s /shared/company-skills ~/.roo/skills/company-standards
```

> ⚠️ **技能名取自符号链接名**（未链接时取目录名），
> **frontmatter 的 `name` 必须与之完全一致**——
> **不能用不同名字的别名指向同一个技能**。

## 增强匹配的额外字段

部分实现扩展了 frontmatter，把"何时用 / 何时不用"**拆成独立数组**：

```yaml
metadata:
  vellum:
    activation-hints:
      - "用户要处理 PDF 表单"
      - "提到文档抽取"
    avoid-when:
      - "只是问 PDF 是什么"
      - "要生成图片而非解析文档"
    category: documents
    display-name: PDF 处理
```

> ⭐ 这个思路值得借鉴：**把 Do NOT 从 description 散文里抽出来，变成结构化字段**。
> 在只支持标准字段的客户端上，退化为把 `avoid-when` 拼回 description 即可。

**其他可选标准字段**：

| 字段 | 说明 |
|---|---|
| `license` | 许可证名或指向 bundled license 文件 |
| `compatibility` | 环境要求（**≤500 字符**：目标产品、系统包、网络访问） |
| `metadata` | 任意键值（作者、版本等） |
| `allowed-tools` | 预批准工具列表（**实验性**，各实现支持不一） |

## 自查

```
□ 目录名与 name 字段是否完全一致？（不一致可能静默失败或被遮蔽）
□ 是否被更高优先级位置的同名技能遮蔽了？
□ 是否放在了模式专属目录里、而当前不在那个模式？
□ 项目级技能所在目录是否被标记为可信？
□ 若用符号链接，name 是否与链接名一致？
□ 是否在大型目录树里（扫描深度/数量可能被限）？
□ 是否有 .gitignore 把技能目录排除了？
□ 改了技能但没重启 / 没 /reload？
```
