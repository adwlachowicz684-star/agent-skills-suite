## 1. ⭐⭐⭐ 伪技能陷阱

> ⭐⭐⭐ **"伪技能"：只是把一个长提示词包进一个函数里，
> 没有做任何任务拆解和接口设计。**
>
> ⭐⭐ **除了增加代码复杂度，⭐ 没有带来任何 Token 或效率上的好处。**

> ⭐⭐⭐ 这是本份最重要的一条，因为⭐ **它让后续所有优化都失去意义**：
> 你优化加载、优化缓存、优化输出，
> 但如果那个东西本质上就是一段被包起来的提示词，
> **它每次还是要把整段内容读一遍**——只是多了层壳。

**判据**（怎么知道自己是不是在做伪技能）：

```
□ 有没有做任务拆解？（还是一整段）
□ 有没有接口设计？（输入/输出有没有被明确定义）
□ ⭐ 有没有⭐ 按需加载的部分？（还是每次都整段进上下文）
□ 有没有把确定性部分抽成脚本？
```

> ⭐ 四个"没有"里中两个以上，基本就是伪技能。
> 这与 `worth-skillifying.md` 的五维矩阵互补——
> 那个判断"该不该做"，这个判断"做出来了是不是真的技能"。

## 2. ⭐⭐ 找到真正的耗能大户

> ⭐ **不要只看总账单。**

**必须能回答的三个问题**：

```
① 哪个技能/工作流被⭐ 调用最频繁？
② 每次调用的⭐ 平均输入/输出 Token 是多少？
③ ⭐⭐ 有没有异常的"Token 泄漏"？
   （例：某个技能意外输出了大量无关文本）
```

> ⭐⭐ **"Token 泄漏"** 这个词很关键——
> 它不是"用得多"，是⭐ **在输出你根本不需要的东西**。
> 这类问题在总账单上完全看不出来，只能靠分技能埋点。

**埋点做法**：

```
在关键函数调用处记录：
   每次模型调用的 Token 数 · 模型类型 · 耗时
→ 发到监控系统（Prometheus + Grafana）
→ ⭐ 一眼看出"成本热点"
```

**一条最高 ROI 的经验**：

> ⭐⭐ **优化一个被高频调用的技能，
> 比优化十个低频技能效果更显著。**

> ⭐ 这与 `skill-evolution-loop.md` 的
> "每月选 1–2 个⭐ 使用频率最高的技能做正式修订"完全对上：
> **优化顺序按频率排，不按"看起来有多臃肿"排。**

## 3. ⭐ 上下文管理三件套

**① 压缩 / 摘要**

```
用一个小模型或专用技能，把之前的对话做摘要
例："对话摘要"技能把 20 轮聊天压成 5 句话背景摘要
→ 后续对话只带这个摘要
```

**② 向量检索（RAG）**

```
⭐ 不要每次把整个知识库塞进 Prompt
→ 切片存向量库，提问时召回最相关的几个片段
⭐⭐ 这是控制上下文长度的黄金法则
```

**③ 缓存**

```
对相同输入的重复请求缓存结果：
· 基于输入参数的缓存机制
· 合理的过期时间
· ⭐ 对频繁调用的基础技能优先缓存
```

> ⭐ 三条里第 ② 条对应 `skill-vs-rag.md`，
> 第 ① 条对应 `context-compression.md`——**这份的价值在于把三者放进同一张图**，
> 并指出它们是⭐ 不同层级的手（都不是改技能本身，是改上下文）。

## 4. ⭐⭐ 模型路由层

> ⭐ **不要所有任务都无脑上最强模型。**

```
简单分类 / 提取 / 格式化    → ⭐ 小模型完全够用
                             （成本只有顶级模型的几十分之一）
复杂推理 / 创造性写作 / 高准确 → 才上顶级模型
特定领域任务               → 考虑微调过的开源模型
```

**做法**：⭐ **构建一个"模型路由层"**——
根据技能的复杂度和质量要求，动态决定调用哪个模型。

```
例：analyze_article   → 路由到小模型
   generate_strategic_plan → 路由到顶级模型
```

> ⭐⭐ 这条常被忽略，因为大家默认"一个 agent 一个模型"。
> 但技能的粒度正好适合做路由决策——
> **每个技能天然带有"这件事有多难"的信息**。

> ⭐ 顺带：这与 `cross-model.md` 的"跨模型测试矩阵"是配套的——
> 你先按难度分层，再为每层测它在哪些模型上还成立。

## 5. 十个具体优化技巧

```
① ⭐ 精简技能描述文本（description 是主要消耗源之一）
② （去重与引用，见 `deduplication.md`）
③ （分层加载，见 `progressive-disclosure-patterns.md`）
④ ⭐ 缓存技能执行结果
⑤ ⭐ 精简技能返回结果：只返回用户真正需要的信息
   · 移除调试信息和内部状态
   · 采用结构化数据格式
   · ⭐ 根据用户需求动态调整返回字段
⑥ ⭐ 优化调用方式：批量调用、用引用代替重复定义、设优先级
⑦ 精简提示词：简洁指令、避免不必要的示例和解释、用标准模板
⑧ ⭐⭐ 减少技能嵌套调用（⭐ 嵌套会导致消耗呈指数级增长）
   · 扁平化调用结构
   · 合并功能相似的嵌套技能
   · 避免不必要的中间技能
⑨ ⭐ 优化依赖管理：仅加载当前所需、移除未用依赖、延迟加载
⑩ ⭐ 定期分析与监控（记录 token 使用、识别高消耗模式、定期重构）
```

> ⭐⭐ 第 ⑧ 条最反直觉也最重要：**嵌套是乘法的**。
> 这与 `reference-file-practices.md` 的
> "嵌套引用会让模型改用 head -100 预览"是两个独立来源指出嵌套的代价——
> **一个说它贵，一个说它会丢信息。**

## 速查

```
□ ⭐⭐⭐ 伪技能 = 长提示词包个函数，没拆解没接口
       → ⭐⭐ 后续所有优化都白费
       判据：没拆解？没接口？⭐ 没按需加载？没抽脚本？

□ ⭐⭐ 分技能埋点（token/模型/耗时）→ 找成本热点
□ ⭐⭐ 查"Token 泄漏"（输出了根本不需要的东西）
□ ⭐⭐ 优化一个高频技能 > 优化十个低频技能

□ 压缩摘要（20轮→5句）· ⭐ 向量检索（RAG 黄金法则）· 缓存
□ ⭐⭐ 模型路由层：按技能难度分层选模型
   （小模型够用就别上顶级，成本差几十分之一）

□ ⭐⭐ 减少嵌套调用（⭐ 消耗呈指数级增长）
□ ⭐ 精简返回：移除调试信息、结构化、动态调整字段
□ ⭐ 精简 description（主要消耗源之一）
□ 定期分析监控
```

**一句话**：

> ⭐⭐⭐ **"伪技能"——只是把长提示词包进函数、没做任务拆解和接口设计——
> 除了增加复杂度，没有带来任何 Token 或效率上的好处。**
