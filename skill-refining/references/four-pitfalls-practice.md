## 1. ⭐⭐⭐ 坑一：描述强，实现弱

```
早期花大力气写 SKILL.md，⭐⭐ 但⭐ 实现层只做了很简单的封装
结果：⭐⭐⭐ 模型总是调用一些"⭐ 听起来很强"的技能，
      ⭐⭐⭐ ⭐ 得到的输出却很鸡肋，⭐⭐⭐ ⭐ 信任度崩坏
```

**得到的教训**（这句值得单独记住）：

> ⭐⭐⭐⭐ **"夸奖一个 agent 的⭐ 入口能力之前，⭐⭐⭐ 先把⭐ 出口能力做扎实。"**

> ⭐⭐⭐ 这是本份最有价值的一条，因为它指出了一个⭐ 系统性偏差：
> 我们（包括这套库）大量内容都在讲⭐ **入口**——
> description 怎么写、触发率怎么提、激活机制是什么。
> ⭐⭐⭐ 而⭐ **出口**（技能被触发之后到底产出了什么）讲得少得多。
>
> ⭐⭐⭐ 更关键的是它指出了⭐ 后果的性质：不是"效果一般"，
> ⭐⭐⭐ 而是⭐ **信任度崩坏**——
> 一旦用户遇到过几次"听起来很强、结果很鸡肋"，
> ⭐⭐ 他会把⭐ 整个技能库一并弃用，包括那些真正好用的。
>
> ⭐⭐ 这与 `hit-rate-four-questions.md` 的第三类
> "触发了但没帮助 → 正文质量不足"是同一件事，
> ⭐⭐⭐ 但这里补上了⭐ **信任层面的连带损害**——
> 一个坏技能会污染整个库的声誉。

## 2. ⭐⭐⭐ 坑二：忽视版本管理

```
技能迭代多了之后，⭐⭐ 同名的新旧版本⭐ 行为差异可能很大
不做版本管理 → ⭐⭐⭐ 日志对不上 · ⭐⭐⭐ 效果对比混乱 · ⭐⭐ 排查问题时极其痛苦
```

**解法（三件事）**：

```
① ⭐⭐ 所有技能走 Git 仓库管理
② ⭐⭐ 每次发布生成版本号
③ ⭐⭐⭐ ⭐ 自动记录到⭐ 注册表里
```

> ⭐⭐⭐ 第 ③ 条"自动记录到注册表"是我们此前没写的一层：
> `version-changelog-practice.md` 讲的是⭐ 单技能内的版本号与 CHANGELOG，
> ⭐⭐ 这里讲的是⭐ **库级别的注册表**——
> 一个地方能查到"当前生效的是哪个版本"。
>
> ⭐⭐⭐ 两者缺一不可：单技能有版本号，你才知道改了什么；
> ⭐⭐⭐ 库级有注册表，你才知道⭐ **现在跑的是哪一版**
> （对应 `team-admission-criteria.md` 的"active 列表"概念）。

## 3. ⭐⭐⭐ 坑三：只建不评

```
技能库搭完就觉得万事大吉，⭐⭐ 不做测评、不回放日志
⭐⭐⭐ 结果：⭐⭐⭐ 上线三个月后才发现⭐ 一堆误用问题⭐ 已经累积了很久
```

**对比数据**：

```
有了⭐⭐ 日志回放 + ⭐⭐ 指标监控之后
⭐⭐⭐ 很多问题在⭐ 几天内就能被发现并修复，⭐⭐ 效率完全不同
```

> ⭐⭐⭐ **"三个月 vs 几天"** 是本份最有说服力的数字。
> 它说明⭐ **没有反馈回路的技能库，问题不是"没被发现"，
> 而是会以三个月的量级累积**——
> ⭐⭐⭐ 到那时你已经分不清哪些是当初的设计、哪些是后来腐坏的。
>
> ⭐⭐ 与 `skill-decay-governance.md` 的"库里最差的是你最早写的"、
> `adoption-metrics.md` 的"高调用次数但没有质量审查 = 负债"
> ⭐⭐⭐ 是⭐ 第三个独立来源。

## 4. ⭐⭐⭐ 坑四：做过细的粒度拆分

**一个具体到荒谬的例子**：

```
❌ 把"打开网页""读取标题""提取正文""清理 HTML 标签"⭐ 各做一个技能
   ⭐⭐⭐ 看似模块化很彻底，⭐⭐⭐ ⭐ 实则让模型在决策时⭐ 疲于奔命
```

**正确粒度**：

> ⭐⭐⭐ **"能独立完成一个⭐ 有意义的业务动作。"**

```
✅ "抓取网页并提取正文" = 一个技能
❌ "读取页面标题"      = 没必要单独成技
```

**另一句经验**：

> ⭐⭐ **"太短说不清，太长记不住。"**

> ⭐⭐⭐ 这条与我们已有的⭐ 三个拆分判据形成一个完整序列：
> ```
> · 重启测试（refining）：跑到一半失败，人从哪重启？从中间产物→拆
> · 双向无知（orchestration）：两个技能互相需要对方细节→其实是一个
> · ⭐⭐⭐ 本份：⭐⭐ 能不能⭐ 独立完成一个有意义的业务动作？不能→太细了
> ```
> ⭐⭐⭐ 三个判据方向不同，合起来才完整：
> **重启测试找"该拆没拆"，本份找"拆过头了"，双向无知找"拆错了地方"。**

> ⭐⭐ 还要注意它与"一技能一职责"的张力：
> 两者不矛盾——⭐⭐⭐ **"一个职责"不等于"一个动作"**。
> "抓取并提取正文"是一个职责（业务动作），
> 而"读取标题"只是一个动作（不是一个完整职责）。

## 5. ⭐⭐ 两个小技巧

**① 日志里记录触发理由**

```
⭐⭐⭐ 日志里把⭐ 每次技能调用的⭐ 触发理由记录下来
⭐⭐⭐ ⭐ "模型⭐ 为什么选了这个技能"，⭐⭐⭐ 这个信息对后续优化⭐ 价值极高
```

> ⭐⭐⭐ 这与 `skill-observability.md` 的"决策日志比调用日志更关键"
> 是⭐ 完全相同的第二条来源。两份独立来源都把⭐ **决策理由**
> 列为最重要的埋点，值得立刻做。

**② 预热技能**（我们此前没覆盖过的一个机制）

```
⭐⭐ 当用户⭐ 第一次提到某个领域话题时，agent 可以⭐ 主动"加载"相关技能到活跃列表
⭐⭐⭐ 后续调用时就⭐ 不再需要从上百个技能里重新检索
⭐⭐⭐ 这种⭐ 会话级别的"技能预热"机制，对⭐ 响应速度和准确率都有明显提升
```

> ⭐⭐⭐ 这个想法很妙，因为它⭐ 用"提前"解决了"检索失败"——
> 而我们此前所有关于触发的方案都是⭐ 事后优化（改描述、加触发词、两步路由）。
>
> ⭐⭐ 但要标一个⭐ 张力警告：
> 预热会⭐ **同时加载多个技能**，与 `capability-offset-net-gain.md` 的
> "常驻的技能描述即使没触发也会渗入判断、挤占验证环节"
> ⭐⭐⭐ 存在冲突。
> ⭐⭐⭐ 保守用法：**只预热 1–2 个、且预热后应观察是否挤占了验证**。

## 速查

```
□ ⭐⭐⭐⭐ 坑一 描述强实现弱 → ⭐⭐⭐ 先把出口能力做扎实，再谈入口
   ⭐⭐⭐ ⭐ 后果是⭐ 信任度崩坏（一个坏技能污染整个库的声誉）
□ ⭐⭐⭐ 坑二 忽视版本管理 → 日志对不上、效果对比混乱
   解法三层：Git + 版本号 + ⭐⭐⭐ ⭐ 库级注册表（知道现在跑的是哪一版）
□ ⭐⭐⭐ 坑三 只建不评 → ⭐⭐⭐ 三个月 vs ⭐ 几天的差距
□ ⭐⭐⭐ 坑四 过细拆分 → ⭐⭐⭐ 判据：⭐ 能独立完成一个有意义的业务动作？
   ⭐⭐ "太短说不清，太长记不住"
   ⭐⭐⭐ 三个拆分判据：重启测试(该拆没拆) · 本份(拆过头) · 双向无知(拆错地方)
   ⭐⭐⭐ "一个职责" ≠ "一个动作"

□ ⭐⭐⭐ 日志必须记⭐ 触发理由（第二个独立来源说它价值最高）
□ ⭐⭐ 预热技能：⭐ 首次提到领域话题时加载 → 后续不用重新检索
   ⭐⭐⭐ ⚠️ 与"常驻描述挤占验证环节"冲突 → ⭐ 保守用法：只预热 1–2 个并观察
```

**一句话**：

> ⭐⭐⭐ **四个坑里最关键的是"描述强、实现弱"——先把出口能力做扎实再谈入口，因为听起来很强却输出鸡肋会直接导致信任度崩坏，一个坏技能会污染整个库的声誉；
> 而粒度判据是"能独立完成一个有意义的业务动作"（"一个职责"不等于"一个动作"）。**
