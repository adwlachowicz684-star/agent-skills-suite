## 1. ⭐⭐⭐ 一个被误诊的现象

**真实经历**：

```
Claude Opus 5 / GPT-5.6 发布后，作者预期工作流会明显变好
⭐⭐ 结果有些工作流反而更差：
   agent 更急躁、更不可预测、偶尔"更笨"
⭐ 自然的反应：怪新模型
```

**正确的怀疑方向**：

> ⭐⭐ **当 agent 失败时，能力可能已经具备。
> ⭐⭐⭐ 问题可能出在⭐ 我们怎么指示它、给了什么记忆、怎么安排工作流。**

**于是问了一个此前一直忽略的问题**：

```
⭐⭐ "我的自定义技能，还跟新模型兼容吗？"
```

> ⭐⭐⭐ 这个转向很值得记住：
> **"模型变笨了"是最容易得出的结论，
> 但⭐ 它把不可控因素（模型）当成了解释，
> 从而⭐ 关掉了唯一你能控制的变量（指令）。**

**审计发现的问题**（四类，正是技能腐烂的形态）：

```
· ⭐ 围绕旧模型行为写的指令
· ⭐ 冗余的指令
· ⭐ 不再必要的指令
· ⭐⭐ 把新模型推得太狠、导致它⭐ 过度执行任务的指令
```

> ⭐⭐⭐ 第四类最反直觉：⭐ **为旧模型加的"加强"指令，
> 在新模型上会变成"过量"**。
> 清理后重测，结果明显变好。

## 2. ⭐⭐ 让 agent 审计自己的技能

**可以直接照抄的审计提示词**：

```
Can you audit our custom skills against the current models?
Flag stale prompts, conflicting instructions, outdated assumptions,
and anything that should be simplified or removed.
⭐ Then test each skill on a representative task
   and propose the smallest updates needed.
```

> ⭐⭐ 三个设计点值得学：
>
> ```
> ① ⭐⭐ "against the current models"——⭐ 明确审计基线是⭐ 当前模型，
>     不是"技能写得对不对"
> ② ⭐⭐ "should be simplified or removed"——⭐⭐ 主动问"什么该删"，
>     而不是只问"什么该加"
>     （呼应 skill-reducer-study.md：压缩后质量反升 2.8%）
> ③ ⭐⭐⭐ "propose the smallest updates needed"——⭐ 限制改动幅度
>     ⭐⭐ 这与 skill-rot 的"小编辑复利"直接对冲：
>     ⭐ 一次只改最小量，才能让回归可归因
> ```

> ⭐ 边界：这与 `skill-rot-rollback-discipline.md` 的
> "agent 可以提议，人审核"完全一致——**审计 + 提议可以自动，落地必须人批**。

## 3. ⭐⭐ 官方指引：升级时要做减法

**Anthropic（Claude Opus 5 文档）**：

```
⭐⭐ "模型现在⭐ 不需要被要求就会自行验证"
⭐⭐⭐ 明确建议⭐ 移除从早期模型沿袭下来的验证指令，
      ⭐ 因为它们会导致⭐ 过度验证（over-verification）
```

**OpenAI（GPT-5.6 指引）**：

```
· ⭐ 移除重复的指令
· ⭐ 简化工具描述
· ⭐⭐ 每次改动后⭐ 跑同一套评估
· ⭐⭐ 内部编码 agent 评估：
      ⭐ 更精简的 system prompt ⭐ 分数提升约 10–15%，同时 token 更少
      ⚠️ OpenAI 自己说这是⭐ 方向性数字，应在你自己的负载上验证
```

> ⭐⭐⭐ 两条官方指引方向一致：**升级模型时，技能的默认动作是"删"不是"加"。**
> 这与直觉相反——多数人升级后会⭐ 追加指令来"压住"新行为，
> 而官方建议的是⭐ 移除那些为旧模型打的补丁。

> ⭐⭐ 顺带印证了 `token-bloat-audit.md` 与 `skill-reducer-study.md`：
> **精简既有质量收益也有成本收益，两个收益方向一致。**

## 4. ⭐⭐⭐ 提示不能跨模型迁移

**ICLR 2024 的研究**：

```
⭐⭐ "提示性能⭐ 不能完美地在模型之间迁移"
⭐ 不同模型之间，提示格式的性能⭐ 只呈弱相关
```

> ⭐⭐⭐ 一句精准的总结：
> **⭐ "一个对昨天的模型有帮助的提示，可能让明天的模型困惑。"**

**推论**（对跨模型测试）：

```
· ⭐⭐⭐ 在一个模型上调优好的技能，换模型必须⭐ 重测，不能假设沿用
· ⭐⭐ 这解释了为什么 `official-checklist.md` 那条
      "Haiku/Sonnet/Opus 三档都测"是最常被漏的一条——
      ⭐⭐ 它不只是"多测几个"，而是⭐⭐⭐ 弱相关意味着
      单档调优的结果⭐ 不能外推到其他档
· ⭐⭐ 结合 `unicode-injection-defense.md` 的"越强越脆弱"：
      ⭐⭐⭐ 换模型要同时重测⭐ 表现和⭐ 安全
```

## 5. ⭐⭐ 模型更新检查清单

```
① ⭐ 用代表性任务跑一遍现有技能
② ⭐⭐ 找出⭐ 为绕开旧模型行为而写的指令（这是重点）
③ ⭐ 移除重复或冲突的规则
④ ⭐⭐ 删除新模型⭐ 自然会遵循的指令（否则导致过度执行）
⑤ ⭐⭐⭐ 一次只改一组指令
⑥ ⭐⭐ 改完跑⭐ 同一套测试
⑦ ⭐⭐ 只保留产生⭐ 可测量改进的改动
```

> ⭐⭐⭐ 第 ⑤ 条"一次只改一组"是整套清单的枢纽——
> 没有它，第 ⑦ 条"只保留有改进的"就无从判断是哪一条起了作用。
> 这与 `incremental-debug-procedure.md` 的增量调试、
> `skill-rot` 的"无法二分"是同一条原则。

**一个类比**（很贴切）：

```
⭐⭐ "这基本上就是依赖维护——
     只不过这个依赖是⭐ 自然语言行为。"
```

> ⭐⭐ 这个类比是对的，而且有实操含义：
> **把模型当成依赖，就该像依赖一样有"升级后回归测试"这个环节。**

**最后一句**：

> ⭐⭐⭐ **自定义技能不是永久文档。
> ⭐ 它们是 agent 系统的一部分，
> ⭐⭐ 而每当底层模型变化，这个系统就变了。**
>
> "你可能换了引擎，却还在用旧车主的手册。"
> 或开发者版本：**模型可能没问题，你的提示只是有了技术债。**

## 速查

```
□ ⭐⭐⭐ "新模型变笨了"通常是误诊——
   ⭐⭐ 把不可控的（模型）当解释，⭐ 关掉了唯一能控的变量（指令）

□ ⭐⭐ 审计提示词要点：⭐ 对标当前模型 · ⭐⭐ 问什么该删
   ⭐⭐⭐ 提议"最小改动"（一次少量，回归才可归因）
□ ⭐ 审计发现四类：围绕旧模型行为 · 冗余 · 不再必要 · ⭐⭐ 推得太狠

□ ⭐⭐⭐ 官方两条：⭐ 升级时默认做减法
   Anthropic：⭐⭐ 新模型自行验证 → ⭐ 移除验证指令，否则过度验证
   OpenAI：移除重复 · 简化工具描述 · ⭐ 每次改完跑同一套评估
      ⭐ 精简 system prompt +10~15% 分且更少 token（方向性数字）

□ ⭐⭐⭐ ICLR 2024：⭐ 提示性能跨模型只弱相关
   → ⭐⭐⭐ 单档调优结果不能外推；⭐ 换模型同时重测表现与安全
□ ⭐⭐⭐ "对昨天的模型有帮助的提示，可能让明天的模型困惑"

□ ⭐⭐ 检查清单七条，⭐⭐⭐ 枢纽是"一次只改一组"
□ ⭐⭐ 本质 = 依赖维护，依赖是自然语言行为
```

**一句话**：

> ⭐⭐⭐ **升级模型时技能的默认动作是"删"不是"加"——
> 那些为绕开旧模型行为而写的指令（尤其是验证指令）
> 在新模型上会变成过度执行；
> 而提示性能跨模型只弱相关，所以换模型必须重测，不能沿用。**
