## 1. 三级预算，只有前两级算数

| 层 | 内容 | 预算 | 何时加载 |
|---|---|---|---|
| **L1 元数据** | name + description | ~100 tokens/技能 | ⭐ 启动即全部加载 |
| **L2 指令** | SKILL.md 正文 | ⭐ **硬上限 5,000 tokens** | 触发后加载 |
| **L3+ 资源** | references / scripts | 按需，**实际不设限** | 显式需要才读 |

```
5,000 tokens ≈ 3,500–4,000 汉字 ≈ 400–600 行 Markdown
```

> ⚠️ 超出 5,000 tokens（例如 2,000 行 ≈ 12,000 tokens）**违反 API 校验**。
> 这也是 `validate_skill.py` 把 500 行设为硬上限的原因——
> **500 行 × 4 字符/token ≈ 20,000 字符 ≈ 5,000 tokens**，正好对上物理边界。

**只有 L1 和 L2 计入硬预算。L3 永远不读，除非显式需要。**

## 2. ⭐ description 预算是共享的

这是"技能装多了就失效"的直接机制：

```
总 description 预算 ≈ 8,000 字符（默认）

15 个技能  →  每个分到约 533 字符
```

> ⭐ **你精心写进 description 的触发词，可能根本没进上下文——被截掉了。**

这就是 `discovery-ux.md` 里那条"装太多技能描述会被压缩"的具体数字。
**它是共享预算，不是每个技能独立额度。**

## 3. ⭐ 压缩只留前 5,000 tokens

```
压缩后：每个技能只有前 5,000 tokens 存活
总上限：25,000 tokens
超出时：⭐ 最旧的先被丢掉
```

**直接推论**：

```
❌ 关键指令写在 10,000-token 文件的底部 → 压缩时被砍掉
✅ 把 Quick Reference（核心规则/命令/约束）放顶部，详细示例沉到底部
```

这与《skill-crafting》的 `skill-structuring` 的 `directory-contract.md` 里"承重指令必须放顶部"是同一条。
这里给出的是**精确的字数**：前 5,000 tokens 是安全区。

## 4. ⭐ 手动技能能把预算彻底归零

一个被低估的优化手段：

```yaml
disable-model-invocation: true
```

> ⭐ **它会把该技能的 description 从预算里完全移除。**

适用场景（本来就是手动调用的）：

```
deploy · release · 维护类任务 · 破坏性操作
```

> 这些技能**本来就不该让模型自动触发**，
> 设了这个开关**既更安全，又免费省下预算**——双重收益。

⚠️ 前提是你确实需要手动调用它。设了之后模型不会再自动路由，
用户必须指名。所以**只对该手动的技能用**。

## 5. 动态注入会阻塞加载

动态上下文注入（`` !`command` ``）在**技能加载之前**跑 shell 命令。

```
❌ 命令慢（API 调用、大文件解析）→ ⭐ 阻塞整个技能加载
```

**修法**：把输出压小，不要注入完整文件内容。

```bash
!`git log --oneline -5`              # ✅ 小
!`cat large-file.json`               # ❌ 阻塞
!`cat large-file.json | head -20`    # ✅ 管道截断
!`jq '.summary' data.json`           # ✅ 只取字段
!`wc -l data.csv`                    # ✅ 只要数量
```

验收线：**动态注入命令 2 秒内完成。**

## 6. reference 不跨轮持久

一个容易误判成本的行为：

> ⭐ **每次 Claude 遇到 "见 references/X.md" 就去读一次。**
> **内容不会在轮次之间保留**，除非它当时正在处理它。

所以高频使用的参考数据：

```
✅ 在主 SKILL.md 里放一份紧凑摘要
✅ 完整文件只在边缘场景才引用
```

否则你要为同一份内容反复付费。

## 7. 两个隐藏开关

| 开关 | 作用 | 代价 |
|---|---|---|
| `SLASH_COMMAND_TOOL_CHAR_BUDGET` | ⭐ 提高 description 预算上限 | ⭐ **它是在拿对话空间换技能发现**——描述占多了，实际对话能用的就少 |
| 正文里的 `ultrathink` | 为该技能执行启用扩展思考 | 复杂分析有用，但**增加延迟** |

> ⚠️ 两者都**不要默认开**。
> 尤其 `ultrathink`——写在技能内容里就生效，很容易被无意带上。

另外一条常被误解的：

> **预算是窗口总量的百分比，在启动时固定**——
> 它随窗口大小缩放，**不随会话已用量变化**。
>
> 所以当你确实超载时，**换更大的窗口是最便宜的解法**
> （1M 窗口比 200K 给约 5 倍元数据空间）。

⚠️ 但注意这**只解决元数据预算问题**——
前面 `scale-effects.md` 说过，**技能遮蔽才是主因**（占 68%），
换大窗口对遮蔽无效（两篇文章结论一致：换大窗口没用，只能减候选）。

## 8. 60 秒交付前检查

```
□ description 用第三人称，写了 what + when，关键词密集
□ ⭐ 关键触发词前置（截断时先活下来）
□ description 用引号或 >- 解析成一行（不用 |，避免多行问题）
□ name 小写连字符，≤64 字符，不含 claude / anthropic
□ description 远低于 1024 字符（技能库装满后还得再短）
□ ⭐ 正文 < 500 行，细节推到 references/
□ ⭐ 只启用本项目真正需要的技能
□ ⭐ 实测过触发率（用工具或几条真实 prompt），不是"应该没问题"
□ 纯手动技能设 disable-model-invocation: true
□ 动态注入命令 < 2 秒
□ 关键指令在正文前 5,000 tokens 内
```

## 速查

| 症状 | 先查 |
|---|---|
| 装多了触发词失效 | ⭐ description 共享预算被截（~533 字符/技能 @15 个） |
| 压缩后技能变了 | ⭐ 只留前 5,000 tokens，关键规则上移 |
| 技能加载很慢 | ⭐ 动态注入命令太慢（>2s） |
| 同一 reference 反复读 | 主文件加紧凑摘要 |
| 预算不够 | 换大窗口 + 手动技能设 `disable-model-invocation` |
| 触发不准（不是预算问题） | ⭐ 那是遮蔽，见 `scale-effects.md` |
