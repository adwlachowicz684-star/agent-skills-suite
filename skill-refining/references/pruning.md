## 五种失败模式

来自 writing-great-skills，可当 checklist 逐条对照。

### ① 过早完成（Premature Completion）

**症状**：步骤还没真正完成就跳到下一步。

**对策**：先把**完成标准磨到足够具体**。只有当标准本身无法更精确、且确实观察到 agent 赶工时，才拆分步骤。

> 不要一上来就拆步骤——**先质疑是不是标准写得不够清楚**。

### ② 重复（Duplication）

**症状**：同一含义出现在多处。

**对策**：**保持单一真相源**。一个规则只在一个地方定义，其他地方**引用**它。

> 检验：改一处能不能改变行为？不能，就是重复了。

### ③ 沉淀（Sediment）

**症状**：过时的层级沉淀下来——**因为添加感觉安全、删除感觉危险**。

**对策**：建立**修剪纪律**，定期删除。

> 这是技能库随时间变差的**最主要原因**。

### ④ 蔓延（Sprawl）

**症状**：技能太长，**即使每行都是活的、唯一的**。

**对策**：用信息层级。通过指针披露引用，按分支或序列拆分。

### ⑤ 空操作（No-op）

**症状**：**一行模型默认就会遵守的话——你付了负载却什么也没说。**

**对策**：对每个句子问一句"**它相比默认行为有改变吗**"。如果没有，删掉。

> 典型例子：**"请认真思考""仔细分析""要彻底"**——
> 模型本来就会这么做。写了等于没写，还白占 token。

## no-op 测试

> **对每个句子单独运行 no-op 测试：这个句子删了，Agent 的行为会有变化吗？**

```
Run the no-op test on each sentence in isolation,
and when one fails, delete the whole sentence rather than trim words from it.
```

**判断标准**：删除后模型行为**不变** → 这句话是空操作 → 删掉。

| 句子 | 判定 |
|---|---|
| "请仔细分析代码" | ❌ 空操作——删 |
| "每个函数超过 50 行就标记 WARNING" | ✅ 有改变——留 |
| "输出要专业" | ❌ 空操作——删 |
| "输出用 JSON，含 file/line/severity 三个字段" | ✅ 有改变——留 |
| "尽量遵循最佳实践" | ❌ 空操作且模糊——删 |

## 修剪方法

**激进，不是逐行改，是逐句判断**：

1. 对每个句子**单独**运行 no-op 测试
2. **一句没通过就删整句**，不要从中修剪词
3. **大部分失败的散文应该删掉，不是重写**

> 原文：*Be aggressive — most prose that fails should go, not be rewritten.*

**修剪顺序**：

```
□ 先删空操作句（零风险，纯收益）
□ 再删重复（合并到单一真相源）
□ 再删沉淀（过时的规则）
□ 最后处理蔓延（拆分）
```

## 拆分判据

> **能不拆就不拆，拆了就要值回 Token 成本。**

**按调用方式拆**：当有
- 一个独立的引导词应该自行触发，或
- 另一个技能需要访问它

→ 拆出一个 model-invoked 技能。**代价是增加上下文负载。**

**按顺序拆**：当**后续步骤会诱惑 Agent 赶工当前步骤**时，把步骤序列拆开。

> 把它们移出视野，鼓励 Agent 在当前任务上做更多挖掘。

## 七条写作原则

| # | 原则 | 说明 |
|---|---|---|
| 1 | **克制** | 主文件要求越少，agent 越聪明。**能解释为什么的，就别写死怎么做**——步骤写太死，遇到异常就卡住 |
| 2 | **事实和推断分开** | 技术事实是客观约束（API 格式、文件路径）；经验推断只是当前认知下的偏好（推荐用蓝色）。**只陈述事实，让 agent 自己权衡路径** |
| 3 | **给框架不给清单** | 传递**怎么思考**而不是怎么执行。简单任务可以写脚本固定，复杂任务给逻辑框架更灵活 |
| 4 | **渐进式披露** | 上下文是稀缺资源。详细内容拆到 `references/`，按需加载 |
| 5 | **一定要有踩坑章节** | **信噪比最高的部分**。把真实翻车经验写成 Gotchas / 易错点，持续更新 |
| 6 | **用词谨慎：目标导向而非操作导向** | 用"获取数据"而不是"抓取网页"，用"调研信息"而不是"搜索社区"。**把工具选择权留给 agent**，它可能发现更适合的替代方案 |
| 7 | **边界要写清楚** | 不只写怎么做，还要明确**哪些不做**。防止 agent 好心办坏事、越权操作 |

### 第 5 条展开：踩坑章节怎么写

**要具体到能直接执行**：

```
❌ "深色要用得克制"
✅ "偏深蓝必须用精确 hex #0A2E5C，不要用'深蓝'这种模糊描述"
```

**持续更新**：每次翻车就往里加一条。**稳定性会大幅提升。**

### 第 1 条与"低自由度"的关系

这两条看起来矛盾，其实不冲突：

| 场景 | 做法 |
|---|---|
| **脆弱易错、只有一种对法** | 写死步骤（低自由度） |
| **开放多变、依赖上下文** | 给目标与理由，让 agent 推导 |

> 判据：**这件事做错了有多严重？有多少种正确做法？** 见 `skill-authoring` 的 `patterns.md` 的自由度校准。

## 自查

```
□ 有没有"请认真思考"这类空操作句？
□ 每条规则是否只在一个地方定义？
□ 有没有已经过时但没删的层级？
□ 超过 300 行了吗（即使每行都活）？
□ 步骤是否写死了本该留灵活性的地方？
□ 是否在陈述"偏好"而不是"事实"？
□ 是否有 Gotchas / 踩坑章节？
□ 是否用了操作导向而非目标导向的措辞？
□ 边界（不做什么）写清楚了吗？
```
