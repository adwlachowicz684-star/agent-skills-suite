## 1. ⭐⭐ 技能为什么会腐烂

> ⭐⭐ **技能是⭐ 活在动态环境里的静态产物。**
> 模型在进步、代码库在变、任务在演化——固定的提示文件必然退化。

**三种具体的腐烂形态**（值得逐个对照自查）：

```
① ⭐ 错误的触发
   一个为 "deploy" 写的技能，在团队重命名工作流之后仍然触发，
   或者在说法变化之后不再匹配

② ⭐ 过期的条件
   指令引用了一个两个月前就被重构掉的目录布局或 API 形状

③ ⭐ 不匹配的输出格式
   技能输出的格式，下游消费者已经不再解析了
```

> ⭐⭐⭐ 重点：**这些失败⭐ 都不需要弱模型才会发生**。
> 模型能力不足会加剧它们，但⭐ 根因是"产物冻结了，而周围的一切在移动"。
>
> ⭐ 这与 `data-source-validation.md` 的"数据源验证"是同一类问题——
> 那份讲的是数据，这份讲的是⭐ 技能引用的结构本身。

## 2. ⭐⭐⭐ 天真的修法让它更糟

> ⭐⭐ **诱人的回应是：让 agent 一感觉到摩擦就自己改技能。**
> ⭐⭐⭐ **多数自改进方案就是在这里悄悄变成了不受控漂移。**

**无审计的自修改，有一个特定的失败特征**（三条，都很准）：

```
① ⭐⭐ 你无法回答"这个技能为什么这么说"
   ——因为⭐ 理由从未被记录

② ⭐⭐ 你无法对回归做二分查找
   ——因为⭐ 没有"改了什么、什么时候改的"的历史

③ ⭐⭐⭐ 看起来合理的小编辑会复利
   ——⭐ 每一次单独看都通过 vibe check，
      ⭐⭐ 加起来就是一个谁都不认识的技能
```

**更关键的那一句**：

> ⭐⭐⭐ **更强的模型本身不解决这件事。**
> 更强的模型也许能在提交前拦下一些自己的错误，
> ⭐⭐ 但⭐ 通过审查的那些编辑会⭐ 更流畅、更难发现——
> 这可以说让⭐ 存活下来的漂移更糟。
>
> ⭐⭐⭐ **"自信的漂移读起来就像改进，直到它失败为止。"**

> ⭐⭐⭐ 这句是本份最锋利的一句，也⭐ 直接修正了
> `self-evolution-three-levels.md` 里偏乐观的部分：
> **自进化不是"模型越强越安全"，恰恰相反——
> 模型越强，通过审查的漂移越难被人类发现。**
> 所以⭐⭐ 人工审核这道关⭐ 必须存在，且不能因为"输出看起来很专业"而放松。

## 3. ⭐⭐⭐ 一个让自修改变安全的循环

四步（O-I-A-E）：

```
① ⭐ Observe   在⭐ 真实使用中观察表现，不是在理论上
② ⭐ Inspect   表现不佳时，⭐ 在动手之前先看清为什么
③ ⭐ Amend     做出改动，⭐⭐ 并记录理由，且理由要有前两步的证据支撑
④ ⭐ Evaluate  对照⭐ 真实行为检查这次改动是不是真的有帮助
```

**把循环箍住的那一条约束**：

> ⭐⭐⭐ **自改进⭐ 绝不能在没有评估的情况下被信任。**
> ⭐⭐ **而评估只有在存在回滚路径时才有牙齿。**

```
⭐⭐ 歧义时的默认动作是 ⭐ 回滚，不是保留。
```

> ⭐⭐⭐ "默认回滚"这条与 `fault-injection-eval.md` 的
> "恢复前检查点缺失/过期 → 安全停止，绝不编造进度"是同一种保守取向。
> 也与 `retirement-pipeline.md` 的"归档 ≠ 删除"一致——
> **留着旧版本，成本极低；丢掉它，代价极高。**

**结论**（一句话版本）：

```
⭐⭐⭐ 同样的编辑、同样的模型，
      ⭐ 有 评估 + 回滚 + 追踪 → 风险画像完全不同
      没有 → 就是漂移
```

## 4. ⭐⭐ 最小可行纪律：四条

> ⭐⭐ **如果你的 agent 能编辑自己的技能，最小可行纪律其实很小。**

```
① ⭐⭐ 只追加的审计日志
   每次编辑记一行：改了什么 · 为什么 · 什么时候 · ⭐ 什么证据触发了这次改动
   ⭐ 一个扁平的 skill-audit.log 就够起步

② ⭐⭐ 写之前先快照
   应用改动前保存前一版
   ⭐ 如果技能在 git 仓库里，git 免费给了你这个

③ ⭐⭐⭐ 回归绊线
   如果改动后行为在你追踪的信号上变差，
   ⭐ 自动回滚或标记给人
   ⭐⭐ 歧义时默认回滚

④ ⭐ 周期性健康扫描
   定时审查，标出表现不佳或过期的技能
   ⭐⭐ 让漂移在⭐ 周期里被发现，而不是在事故中被发现
```

> ⭐⭐⭐ 第 ③ 条是四条里最"贵"也最值钱的：
> **没有它，①②只是让你知道了自己是怎么死的。**
>
> ⭐ 第 ④ 条与 `ops-iteration-sop.md` 的周期性运维、
> `skill-lifecycle.md` 的四阶段是同一件事的不同节奏。

**一个态度**（值得照抄）：

> ⭐⭐ **这些都不需要新研究——
> 就是软件团队已经用在生产代码上的同一套纪律，
> ⭐⭐ 只是现在要应用到⭐ 大多数团队还当成"没人审查的配置文件"的提示产物上。**

## 5. ⭐⭐⭐ 一个可以立刻自测的问题

> ⭐⭐⭐ **如果你的 agent 能编辑自己的指令，
> 而你回答不了"改了什么、为什么、怎么撤销"，
> ⭐⭐ 那你拥有的不是自改进系统，而是一个缓慢变异的系统。**
> ⭐⭐⭐ **而你会在最糟的时刻发现这两者的区别。**

**判据**（三问，任一答不出就是漂移状态）：

```
□ 这个技能为什么这么说？（理由是否可追溯）
□ 上次回归发生在哪次改动？（能否二分）
□ 撤销要多久？（是否有回滚路径）
```

## 速查

```
□ ⭐⭐ 腐烂三形态：⭐ 错误触发 · ⭐ 过期条件 · ⭐ 不匹配的输出格式
   ⭐⭐⭐ 都不需要弱模型才会发生——根因是产物冻结而环境在动

□ ⭐⭐⭐ 让 agent 自己改 = ⭐ 不受控漂移
   失败三特征：⭐ 无理由记录 · ⭐ 无法二分 · ⭐⭐ 小编辑复利
□ ⭐⭐⭐ ⭐ 更强的模型让漂移更危险
   （通过审查的编辑更流畅、更难发现）
   ⭐⭐⭐ "自信的漂移读起来就像改进，直到它失败为止"

□ ⭐⭐⭐ 循环：Observe → Inspect → Amend（⭐ 记理由）→ Evaluate
□ ⭐⭐⭐ ⭐ 自改进绝不能无评估被信任；⭐ 评估要有回滚路径才有牙齿
□ ⭐⭐ ⭐ 歧义时默认回滚，不是保留

□ ⭐⭐ 四条纪律：追加日志 · ⭐ 写前快照（git 免费）
   ⭐⭐⭐ 回归绊线（最值钱）· 周期健康扫描
□ ⭐⭐ 不需要新研究，是把生产代码纪律用到提示产物上

□ ⭐⭐⭐ 三问自测：为什么这么说？上次回归在哪次改动？撤销要多久？
```

**一句话**：

> ⭐⭐⭐ **自改进是版本控制问题，不是智能问题——
> 更强的模型只会让通过审查的漂移更流畅、更难发现；
> 所以"评估 + 回滚 + 追踪"才是那个真正的解锁，
> 而且歧义时的默认动作必须是回滚，不是保留。**
