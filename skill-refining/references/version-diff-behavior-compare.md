## 1. ⭐⭐⭐⭐⭐ 改了什么 ≠ 变了什么

```
Changelog：  "移除第 4 步的兜底逻辑"
实际行为变化：输入缺失时不再自动填充，改为报错退出
```

> ⭐⭐⭐⭐⭐ **同一件事的两种描述，而第二种才是下游需要的。**

更要命的是反过来——**有些改动会产生你没预料到的行为变化**：

```
改了描述的一个词 → 触发集变了 → 一批原本不触发的输入现在触发了
                 → ⭐⭐⭐⭐ 那些输入从没被这个技能处理过
                 → ⭐⭐⭐⭐⭐ 它们的行为"变了"，而你一行正文都没动
```

> ⭐⭐⭐⭐⭐ **描述是行为的一部分**——
> 这是为什么"只改描述的 PR"也必须走行为对比，不能只走文本评审。

已知的量化佐证：**只改描述就能带来 50% 的效果提升**，
同时 **70% 的线上事故来自"未经评估的微调"**。
⭐⭐⭐⭐⭐ **两者是同一个杠杆的两端**——所以改描述必须经过与其他改动同等的行为验证。

## 2. ⭐⭐⭐⭐ 对比要在行为层做

两种对比方式：

| | ⭐ 文本 diff | ⭐⭐⭐⭐⭐ 行为对比 |
|---|---|---|
| 看什么 | 两版 SKILL.md 差了几行 | 同一批输入，两版输出差在哪 |
| 能发现 | 你写了什么 | ⭐⭐⭐⭐ 它实际做了什么 |
| 漏掉 | ⭐⭐⭐ 所有"没写但变了"的 | 需要跑，成本高 |

> ⭐⭐⭐⭐ **正确顺序：先文本 diff（便宜，用来决定跑什么），
> 再行为对比（贵，但唯一可靠）。**

⭐⭐⭐ 一个实用判据，决定要不要跑行为对比：

```
改了描述 / 触发词      → ⭐⭐⭐⭐⭐ 必须跑（触发集变了）
改了输出契约           → ⭐⭐⭐⭐⭐ 必须跑（下游会断）
改了示例               → ⭐⭐⭐⭐ 跑（示例是最强信号）
⭐ 只改了错字/排版      → 可以不跑
```

## 3. ⭐⭐⭐⭐⭐ 最小对比集

不需要大测试集。三层，每层 3–5 个，共约 12 个输入：

| 层 | 取什么 | ⭐ 为什么 |
|---|---|---|
| **典型输入** | 你最常用那 3 个 | ⭐⭐⭐⭐ 抓"主力场景退化" |
| **边界输入** | 缺字段、超长、空输入 | ⭐⭐⭐⭐⭐ 抓"异常处理变化"——最常见的回归 |
| ⭐⭐⭐⭐⭐ **新增触发** | 因为改描述而新进来的输入 | ⭐⭐⭐⭐⭐ **这一层几乎没人做，而它恰恰是改描述后新增的风险** |

> ⭐⭐⭐⭐⭐ **第三层是本份的核心建议**：
> 改描述后，**先找出"现在会触发但以前不会"的输入，把它们加进对比集**。
> 这些输入从未被这个技能处理过，**它们的行为是未知的**。

跑法：两版各跑一次，逐条比。⭐ **不要只看"对不对"，要看"怎么对的"**
——这正是四象限里的第 ④ 格（对但不稳），只有对比才能发现。

## 4. ⭐⭐⭐⭐ 三类差异的判读

对比结果粗分三类，处理方式完全不同：

| 差异 | ⭐ 判读 | 动作 |
|---|---|---|
| **A. 只有目标项变了** | ⭐⭐⭐⭐ 干净 | 发布 |
| **B. 目标项没变，别的变了** | ⭐⭐⭐⭐⭐ 意外副作用 | ⭐ **查清原因**，不是"接受" |
| **C. 目标项变了，别的也变了** | ⭐⭐⭐⭐ 范围过大的改动 | ⭐⭐⭐ 拆成两个 PR |

> ⭐⭐⭐⭐⭐ **B 最危险，因为它常常被当成 A 放过去**——
> 对比者看到"我要的改对了"，就停止检查了。

一个真实形态的 B：

```
目标：修一处字段名拼写
实际：修了拼写，同时因为重写了那段话，顺带删掉了一个约束
      → 输出格式更干净了 → 评审时"看起来是改进"
```

> ⭐⭐⭐⭐ 这也是要写⭐⭐⭐ **"我预期会看到什么"**（`compound-failure.md` 里的习惯）
> 的第二个理由：**改对了但多改了东西，只有预先写了预期才能发现。**

## 5. ⭐⭐⭐⭐ 一个常被忘的对基线

版本对比通常只在 v1 vs v2 之间做。但至少两种情况下需要第三个基线：

**① ⭐⭐⭐⭐⭐ 无技能基线（baseline）**

```
v2 比 v1 好，但 v2 比"不用技能"还差 → 这个技能该归档
```

> ⭐⭐⭐⭐⭐ 这就是"被追上"（Outgrowth）：**基线无技能 88%，你的技能 89%**。
> ⭐⭐⭐ 只在 v1/v2 之间比，永远发现不了这件事。

**② ⭐⭐⭐ 上一版的已知失败输入**

```
v1 的 3 个失败输入，v2 是否修好了？
```

> ⭐⭐⭐ 这条看似显然，但常被跳过——
> 因为对比集是"重新挑的"，包含了新输入，却没包含旧失败。
> ⭐⭐⭐⭐ **每次生产事故产生一条 eval，永久留在套件里**（`ci-skill-validation.md`）——
> 这些就是必须进对比集的东西。

## 6. ⭐⭐⭐ 记录：把结论写进 Changelog

Changelog 常见写法只记改动：

```markdown
## [1.2.0]
- 移除第 4 步兜底逻辑
```

⭐⭐⭐⭐ 加上行为层结论后：

```markdown
## [1.2.0]
- 移除第 4 步兜底逻辑
  ⭐ 行为变化：输入缺失时不再填充，改为报错退出
  ⭐ 对比：12 个输入，11 个一致；1 个（缺字段）行为改变，符合预期
  ⭐ 未跑：无技能基线（已知 v1 为 89% vs 基线 88%，接近归档阈值）
```

> ⭐⭐⭐⭐ 最后一行最有价值：**它把"这次没验证什么"也记下来了**。
> 下次有人接手时，这些信息比版本号有用得多。

三条记录纪律：

```
① ⭐⭐⭐⭐ 写行为变化，不只写改动
② ⭐⭐⭐ 写"跑了多少输入、几处不一致"
③ ⭐⭐⭐⭐ 写"没验证什么"
```

> ⭐⭐⭐ 第三条呼应 evaluation 里那条原则：
> ⭐⭐⭐⭐⭐ **知道一套评估"能量什么、不能量什么"，才不会把结果当成真相。**
