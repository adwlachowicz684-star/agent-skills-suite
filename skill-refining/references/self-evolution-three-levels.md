## 1. 层次一：人在回路上的手工迭代

**做法**：

```
每次技能在真实场景翻车
  → 把失败日志找出来，对比技能文件里写的内容
  → 判断是"某一步指令不够明确"还是"分支条件覆盖不全"
  → 手动更新版本号
```

> ⭐ **这个层次虽然朴素但最稳，因为每一步都有人的判断兜底。**
> ⭐ **对个人开发者和小团队来说，这个阶段已经能解决 80% 的问题。**

> ⭐ 这两句很实在——**别因为层次二听起来更高级就跳过层次一**。
> 大部分收益来自最朴素的那一档。

## 2. 层次二：LLM 蒸馏与自动合并

**触发条件**：⭐ **轨迹样本足够多以后**。

**一种具体做法**：

```
把最近 50 条成功轨迹的关键片段发给一个大模型
  → 让它提取共性、生成新版本的技能内容
  → ⭐ 再由人工只做一次审核
```

> ⭐⭐ 作者搭过这个闭环之后的感受值得原样引用：
>
> **"自动进化仓库不是目的，
> ⭐ 让每一份执行数据都被有效地流回技能仓库，才是'自己变强'的真正含义。"**

> ⭐ 这把"自进化"的重点从"自动生成新版本"
> 转移到了**"数据流回得来吗"**——后者才是真正的瓶颈。

## 3. 层次三：运行时反馈闭环

系统化形态（见 `observability-trace-debug.md` 的可观测性三层）：
决策日志、调用日志、trace_id 贯穿，让每次执行都留下可复盘的信号。

**长期图景**（这段总结得很准）：

```
模型提供通用推理能力
工具连接外部系统
⭐ Skills 承载可复用的程序性知识

⭐ 真实任务中的反馈不断进入技能的⭐ 路由层、指令层、资源层
→ 最终形成一套⭐ 可版本管理、可评估、可回滚、可复用的能力体系
```

> ⭐ "路由层 / 指令层 / 资源层"这个三分法很好——
> **反馈不只是改指令，也可能是改 description（路由）或改 references（资源）。**

## 4. ⭐⭐ 一个可复制的落地样例

Warp 的 Loop Engineering（技能让 agent 自己改进技能）：

**PR 规则**（这几条可直接抄）：

```
① ⭐ 不直接提交到默认分支
   → 创建 skill-improvement/ 分支，再提 PR
② ⭐ PR 里必须包含：
   · 被审查的 Issue 摘要
   · ⭐ 观察到的反馈
   · ⭐ 判断结论
   · ⭐ 学到的规则
   · ⭐ 具体修改了哪些 guideline
③ ⭐⭐ 最后由人类 review 和 merge
```

**起步建议**（小到可以立刻做）：

```
① 先选一个边界清楚的任务（例：只处理新 Issue 分诊）
② 写一份初版技能，写清楚：
   任务目标 · 输入来源 · 操作步骤 · 分类标准 · 输出格式
   ⭐ 以及需要向维护者请求什么反馈
```

> ⭐ 第 ② 条里最后一项最容易被漏：**初版技能要写明"我需要什么反馈"**——
> 否则你收集不到信号，`skill-evolution-loop.md` 那三档信号就没有来源。

**为什么选 Issue 分诊起步**（两条理由都很实在）：

```
① 初版技能可以很朴素，只含基础分类规则
② ⭐⭐ Issue 分诊天然留下反馈记录：
   reaction、回复、label 变化、重复 Issue 判断是否被认可
   ⭐ 都能成为外循环读取的信号
```

> ⭐⭐ 第二条是关键：**选一个有天然反馈信号的任务做起点**，
> 你就不用额外造反馈机制。这比"先建一套反馈系统"现实得多。

**它没绕开人类判断**：

> ⭐⭐ **让维护者对项目背景、团队习惯和历史讨论的理解，
> 继续参与技能的演进。**
> ⭐ 外循环 agent 可以提议修改，但⭐ 不能直接改主分支。

这与 `skill-ownership-changeflow.md` 的"没跑 eval 的 PR 不接受"、
以及 `comparator-ab-eval.md` 的"AI 给自己打分不可靠"是同一条纪律：
**可以自动化提议，不能自动化放行。**

## 5. ⭐⭐⭐ 边界：什么时候"自进化"只是撞墙

> ⭐⭐⭐ **"Skill 能自己变强吗？我的答案是：能，
> 但⭐ 只能在反馈信号的约束下变强。"**

```
⭐⭐ 如果没有轨迹记录、没有成功的判定标准、没有回归测试，
⭐ 所谓"自进化"就只是⭐⭐ 一次又一次地用同样的错误方法生成新版本，
   然后⭐ 把墙撞得更响。
```

> ⭐⭐⭐ **"把墙撞得更响"** —— 这是对"无反馈自进化"最精准的描述。

**三个必要条件**（缺一不可）：

```
□ 轨迹记录
□ ⭐ 成功的判定标准
□ 回归测试
```

**作者的提醒**（值得原样记住）：

> ⭐⭐ **不要迷信"会自进化的 Skill"这种说法，
> ⭐ 要把注意力放在"⭐ 你让什么信号返回来指导进化"上。**

**三个层次与"能解决多少问题"的对应**：

```
层次一（手工迭代）     ⭐ 解决 80% 的问题（个人/小团队到此足够）
层次二（LLM 蒸馏）     需要轨迹样本足够多
层次三（运行时闭环）   需要完整可观测性
```

## 速查

```
层次一 手工迭代：
□ 失败日志 vs 技能文件 → 判断是指令不清还是分支不全 → 手动升版本
□ ⭐ 最稳，每一步有人兜底
□ ⭐⭐ 个人/小团队到此已能解决 80% 问题——别跳级

层次二 LLM 蒸馏：
□ ⭐ 前提：轨迹样本足够多
□ 50 条成功轨迹 → 提取共性 → 生成新版 → ⭐ 人工只审一次
□ ⭐⭐ 重点不是"自动生成"，是⭐ 执行数据能否流回技能仓库

层次三 运行时闭环：
□ 反馈可进入三层：⭐ 路由层 / 指令层 / 资源层
□ 目标：可版本管理、可评估、可回滚、可复用

⭐⭐ 落地样例（Warp）：
□ ⭐ 用 skill-improvement/ 分支提 PR，不直接改主分支
□ ⭐ PR 含：Issue 摘要 + 观察到的反馈 + 判断结论 + 学到的规则 + 改了什么
□ ⭐⭐ 最后必须人类 review + merge
□ ⭐⭐ 起步选"有天然反馈信号"的任务（如 Issue 分诊）
□ ⭐ 初版技能要写明"我需要什么反馈"

⭐⭐⭐ 边界：
□ ⭐⭐⭐ 只能在反馈信号的约束下变强
□ ⭐ 三个必要条件：轨迹记录 · ⭐ 成功判定标准 · 回归测试
□ ⭐⭐ 没有它们 = 用同样错误方法生成新版本，把墙撞得更响
□ ⭐⭐ 别关注"会不会自进化"，关注"什么信号返回来"
```

**一句话**：

> ⭐⭐⭐ **没有轨迹记录、没有成功判定标准、没有回归测试的自进化，
> 只是用同样的错误方法一遍遍生成新版本——然后把墙撞得更响。**
