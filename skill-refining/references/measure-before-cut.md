# 裁剪前先测量：别剪错了地方

> ⭐ **"技能太长"是症状，不是诊断。**

## 三笔账

```
① 目录税     ——所有 description，每轮都付
② 正文加载   ——触发时整篇注入，一次性
③ ⭐ 按需读取 ——references 被读时才付，且读了就在上下文里
```

> ⭐ **多数人只算第 ② 笔，以为"缩短正文"就是优化。
> 但如果你的技能库很大，第 ① 笔才是大头。**
> （见 `disclosure-math.md` 与 `library-size-effect.md`。）

而如果你的技能里 references 很大且常被读，
第 ③ 笔可能才是真凶。

## 先量，再剪

```
步骤 1  量目录税：所有 description 的字符数总和
步骤 2  量正文：SKILL.md 行/字符
步骤 3  ⭐ 量 references：每份多大、被读的频率
步骤 4  ⭐ 观察一次真实任务，看实际读了哪些文件
```

第 4 步最关键，也最常被跳过：

> ⭐ **你以为"很少用到"的 reference，
> 可能每次都被读**——因为你写了很强的 STOP 指令。

反过来，**你以为"核心"的正文段落，
可能在真实任务里从没影响过任何一步**。

## 常见的误剪

**① 剪掉了 Gotchas**

```
❌ "这段太啰嗦了"
⭐ Gotchas 是唯一几乎不可能通过 no-op 测试的内容
   剪掉 = 让技能重新踩已经踩过的坑
```

**② 剪掉了边界示例**

```
❌ "示例占太多行，移走"
⭐ 边界示例是对 description 契约的测试（见 examples-as-contract.md）
```

**③ 剪掉了失败模式**

```
❌ "失败情况很少发生"
⭐ 少见不等于不发生；而且发生时不写就是静默错误
```

**④ 为了行数好看而合并步骤**

```
❌ 把三个步骤合成一条 bullet
⭐ 一条 bullet 一个主张（见 body-writing-rules.md）
   合并会让模型只执行第一件
```

> ⭐ 四类误剪的共同点：
> **它们都是"看起来可以精简"的高价值内容。**

## 三类真正该剪的

**① 空操作句**

```
□ 模型默认就会做的事
□ 重复已说过的话
□ ⭐ 没有任何一条会被违反的规则
```

判据：**删掉它，行为会变吗？** 不会 → 删。

**② 重教模型已知的内容**

```
□ 语言语法、通用概念
□ ⭐ 你在"解释"而不是"规定"
```

**③ 与 references 重复的内联内容**

```
⭐ 内联清单与 reference 覆盖同样内容时，reference 赢
   内联应剪到 ≤3 条，标为 tripwire/gist
   （见 reference-routing.md）
```

## 一个对照流程

```
① 记录基线：跑一遍 eval，记结果
② 记录成本：跑一遍任务，记 token 消耗与读了哪些文件
③ ⭐ 只做一类改动（如"把所有内联清单剪到 3 条"）
④ 重跑 eval 与成本测量
⑤ ⭐ 结果没变差才算剪对了
   变差 → 撤回那类改动
```

> ⭐ 第 ③ 条的"只做一类"很重要：
> 一次做五种改动，就无法知道哪个是有效的、哪个是有害的。
> （呼应 `claude-ab-loop.md`：每次只改 1–2 个变量。）

## 自查

```
[ ] ⭐ 量过三笔账，知道成本到底在哪？
[ ] ⭐ 观察过真实任务里哪些文件被读了？
[ ] 没有剪掉 Gotchas？
[ ] ⭐ 没有剪掉边界示例？
[ ] 没有剪掉失败模式？
[ ] ⭐ 没有为了行数而合并步骤？
[ ] 剪之前有 eval 基线？
[ ] ⭐ 一次只做一类改动？
[ ] 剪完重测过（结果与成本）？
```

## 一条提醒

> ⭐ **"更短"不是目标，"每一段都配得上它的 token"才是。**

有些技能确实该 80 行，
有些技能 300 行也不算长——
取决于它的职责和信息密度。

> 判据永远是那句：
> **"这一段配得上它的 token 成本吗？"**
> 而不是"能不能再短一点"。
