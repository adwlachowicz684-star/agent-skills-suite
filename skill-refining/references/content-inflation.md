## 1. ⭐⭐⭐⭐⭐ 加法是默认动作，减法需要理由

```
出了一次问题 → 加一段
评审提了个意见 → 加一段
发现漏了个情况 → 加一段
```

> ⭐⭐⭐⭐⭐ **每一次"加"都有明确的触发事件和明确的作者动机，
> 而"删"从来没有触发事件——没有人会因为"没出事"而提议删掉一段。**

于是内容只增不减，且⭐⭐⭐⭐⭐ **每一段在加入的那一刻都是对的**——
这就是它无法通过 review 被发现的原因：单看任何一段，都找不出删除的理由。

判据应该反过来：

```
❌ "这一段有错吗？"（几乎总是没有）
✅ ⭐⭐⭐⭐⭐ "删掉这一段，会出什么事？"（答不上来 = 它已经不产生作用了）
```

这跟"每条规则都要能对应一个失败场景"是同一个判据——
⭐⭐⭐⭐⭐ 只是那个判据用于**写**的时候，这个用于**存**的时候。
一条规则在写的时候有失败场景，不代表三年后那个场景还存在。

## 2. ⭐⭐⭐⭐⭐ 膨胀不是变长，是价值密度下降

```
第 1 版：40 行，每行都在改变行为
第 12 版：210 行，其中 60 行仍在改变行为
```

行数涨了 5 倍，有效内容涨了 0 倍。而代价不止是"多读了 150 行"：

| 后果 | 机制 |
|---|---|
| ⭐⭐⭐⭐ 触发后加载成本 | 正文整份加载 |
| ⭐⭐⭐⭐⭐ 压缩截断风险 | ⭐⭐⭐⭐⭐ 压缩带回的是"开头 5000"，不是"最重要的 5000" |
| ⭐⭐⭐⭐⭐ 有效指令被稀释 | 60 行有效内容散在 210 行里，权重被摊薄 |
| ⭐⭐⭐⭐ 维护意愿下降 | 没人愿意通读 210 行，于是改动变成局部追加 |

> ⭐⭐⭐⭐⭐ **第三条最贵**：稀释不产生任何错误信号。
> 技能没有变错，它只是变得"没那么有效了"——而这种变化无法被测量。

## 3. ⭐⭐⭐⭐⭐ 恶性循环

```
正文变长
  → 有效指令权重下降 / 被截断
  → 行为偏差变多
  → 作者认为"没写清楚"，加一段说明
  → 正文更长
```

> ⭐⭐⭐⭐⭐ **这个循环的每一步都是合理的下一步，而它的终点是技能彻底失效。**

它解释了那个常见现象：⭐⭐⭐⭐ **改了 description 之后触发率上去了，效果却没变好**——
因为被多触发的每一次，都在兑现一个已经被稀释的正文。

打断循环的唯一办法是**在"加"之前先问"能不能删"**，而这不是自律问题——
⭐⭐⭐⭐⭐ 见第 6 节：膨胀有可 grep 的接缝。

## 4. ⭐⭐⭐⭐ 三种膨胀

| 类型 | 动因 | 特征 |
|---|---|---|
| ⭐⭐⭐⭐⭐ 防御性 | 怕出事 | 禁令、注意事项、红线 |
| ⭐⭐⭐⭐ 覆盖性 | 想覆盖所有情况 | 分支、例外、"如果……则……" |
| ⭐⭐⭐⭐⭐ 历史性 | 旧内容没删 | 与新增内容并存（即"沉积"） |

**防御性**最常见，特征是同一件事被写了正反两面：

```
"输出要全面，覆盖所有方面"
"输出要简洁，不要冗余"
```

> ⭐⭐⭐⭐⭐ 两句各自都是那次事故后加的，都对应一个真实场景，
> 放在一起则是⭐⭐⭐⭐⭐ **一个模型只能折中的冲突**（见 `skill-precision/references/conflicting-instructions.md`）。

**历史性**最难发现，因为⭐⭐⭐⭐⭐ **旧内容不是错的，它只是被取代了**——
取代它的新内容和它分别读都合理，只有放在一起才矛盾。

## 5. ⭐⭐⭐⭐⭐ 加内容之前的正确顺序

发现"技能没做到某件事"时，按这个顺序处理：

```
① ⭐⭐⭐⭐⭐ 能下沉吗？——改成脚本 / hook / CI
② ⭐⭐⭐⭐⭐ 能删掉什么来腾出权重？——加一段必须同时删一段
③ ⭐⭐⭐⭐ 能改现有的一段吗？——而不是新增
④ ⭐⭐⭐ 真的要新增一段吗？
```

第 ① 步的价值在 `constraint-carrier-ladder.md`：
⭐⭐⭐⭐⭐ **加正文是在用"更长"换"更可能被遵守"，而这两者是反的**；
下沉是在用"更窄"换"必然被遵守"，方向是对的。

第 ② 步是唯一能打断循环的Mechanical 手段。它不需要判断哪段没用——
⭐⭐⭐⭐⭐ **它只需要"必须选一段删掉"这个动作**，而选哪段会被认真考虑，
这在"只加不删"时永远不会发生。

## 6. ⭐⭐⭐⭐⭐ 膨胀的接缝词

膨胀不是一次性发生的，是一次次追加的。追加处有语言痕迹：

```bash
grep -nE "另外|此外|还要注意|特别注意|补充|顺便|同时也要注意" SKILL.md
```

| 接缝词 | 它接入了什么 |
|---|---|
| "另外 / 此外" | ⭐⭐⭐⭐⭐ 一段与前一段没有结构关系的新内容 |
| "还要注意" | ⭐⭐⭐⭐⭐ 第二条注意事项——说明第一节没被遵守 |
| "补充一点" | ⭐⭐⭐⭐ 写完才想起来的，通常没有位置归属 |
| "特别注意" | ⭐⭐⭐⭐⭐ 试图用措辞补偿权重，说明作者知道它在变弱 |

> ⭐⭐⭐⭐⭐ **"还要注意"是最强的一个信号**——
> 它意味着第一道注意事项没有起作用，而作者的应对是再加一道，不是去查为什么没起作用。

另外两个结构性信号：

```
⭐⭐⭐⭐⭐ 同一个词出现在三个以上章节 → 该合并
⭐⭐⭐⭐⭐ "注意事项"章节超过 5 条 → 它已经变成一个垃圾场
```

## 7. ⭐⭐⭐⭐ 膨胀会让描述失效

一个反直觉的因果：

```
正文膨胀 → 有效指令被稀释 → 实际能兑现的能力下降
但 description 没有变（它仍是按 v1 的能力写的）
→ ⭐⭐⭐⭐⭐ 描述承诺的，正文已经兑现不了了
```

> ⭐⭐⭐⭐⭐ **这与"description 承诺了正文没有"是同一个症状的两种成因**——
> 那份是描述改多了，这份是正文稀释了。两者在用户侧完全一样。

判据：**按 description 里写的每一个承诺，在正文里指认兑现它的位置。**
指认不出来 → 要么描述改多了，要么那段已经被稀释到不起作用了。

## 8. ⭐⭐⭐⭐⭐ 自检

```
□ 上次删除一段是什么时候？想不起来 = 只加不删
□ 每一段都能回答"删了会出什么事"吗？
□ grep 接缝词：另外/此外/还要注意/补充/特别注意
□ "注意事项"有超过 5 条吗？
□ 有没有同一件事的正反两面各写一遍？（防御性膨胀）
□ 有没有两个章节在讲同一件事？（历史性膨胀）
□ 触发率上去了但效果没变好？→ 检查是不是稀释，不是描述问题
□ 上次想加一段时，先问了"能下沉吗"吗？
```

一条能立刻执行的规则：**任何一次 PR，如果只加不删，要求作者在描述里写明"为什么这次不需要删"。**
它把"删"从一个需要主动想起来的动作，变成了一个需要解释其缺席的默认项。
