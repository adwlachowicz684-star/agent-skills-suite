## 1. 做对的三件

### ① ⭐ description 写"什么时候用"，不写"是什么"

```
❌ 第一版："一个用于 Flaky test 分诊和治理的 skill，
          包含分类、修复建议和归因分析。"
   跑了三次，全没触发

✅ 改后："当用户说 'flaky'、'测试不稳定'、'用例时好时坏'、
         '门禁被红了' 时触发。分诊 retry 类、环境类、断言类 flaky，
         输出修复优先级。"
   ⭐ 立刻命中，命中率 0 → 4/5
```

> 作者的总结：**这一条原则，比所有 prompt engineering 技巧都管用。**

### ② 主文件只放骨架，细节拆到 reference

```
❌ 第一版：所有判断规则塞进 SKILL.md，600 多行
   加载一次烧掉 4000+ token，"慢得像在拨号上网"

✅ 改后：SKILL.md 142 行（只写判断流程 + 何时去查哪份文件）
        references/flaky-categories.md   每种 flaky 的特征
        references/fix-playbook.md       每类的修复模板
```

> ⭐ 作者的比喻很准：
> **跟测试用例分层思路一样——冒烟用例放主链路，回归用例放扩展集。
> 别把所有逻辑堆在入口。**

### ③ ⭐ 用脚本兜底"AI 不擅长的事"

```
AI 擅长：判断和归类
AI 不擅长：精确读取一个 1000 行的日志文件
```

> ⭐ **分诊准确率从约 70% 提到 92%**（手动复核 25 条做的对比）。

> **AI + 脚本，分工得当，比纯 prompt 强很多。**

## 2. 做错的三件

### ① ⭐ 一开始就想做"通用 skill"

```
最初的野心：做一个"能处理所有测试场景"的 skill
```

> 这与 `cold-start.md` 那条完全对应：
> **别从最宽的开始。** 也与 `what-not-to-do.md` 的
> "反面教材：内容创作者技能想同时涵盖博客/社媒/邮件/技术文档"同源。

### ② 把所有规则堆进主文件（见上面第 ② 条的 ❌）

### ③ 触发词写得像文档而非像用户的话（见上面第 ① 条的 ❌）

## 3. 数据

| 指标 | 改前 | 改后 |
|---|---|---|
| 命中率 | 0 | **4/5** |
| 主文件行数 | 600+ | **142** |
| 单次加载 token | 4000+ | 显著下降 |
| ⭐ 分诊准确率 | ~70% | **92%** |

> ⚠️ 最后一项是作者手动复核 25 条的对比，**样本很小**，
> 方向可信，数字当参考。
