## 基线类

| 借口 | 反驳 |
|---|---|
| "先改完再补基线" | 没有基线就无法证明改动有效，**事后补的是假数字**。 |
| "这次改动很小，不用测" | 小改动最容易引入静默回归——尤其改 description。 |
| "我看得出它变好了" | 感觉不是证据。跑 3 次取均值，模型行为非确定性。 |
| "基线跑一次太慢" | 一次跑不完的成本，远低于改坏了再回退的成本。 |

## 拆分类

| 借口 | 反驳 |
|---|---|
| "再调一轮措辞应该就好了" | **迭代 10 次仍失败 = 架构问题，不是措辞问题**。 |
| "拆开太麻烦，先加个条件分支" | description 里出现长分支条件**正是**拆分信号。 |
| "拆细一点更好定位" | 子技能超过 7 个会抬升路由成本，维护者更难理解整体。 |
| "这两个能力放一起用户更方便" | 只有入口相同、执行过程完全不同就该拆。 |
| "拆分后 description 会变短影响触发" | 恰恰相反——**拆后每个描述能写得非常聚焦，触发准确率提升**。 |

## 修剪类

| 借口 | 反驳 |
|---|---|
| "这份以后可能用到" | 未被引用的资源是噪音，**会稀释检索**。 |
| "删了万一行为变了" | 这正是 no-op 测试要回答的——测过再删。 |
| "说明详细一点没坏处" | 有的：**每句话都在付 token**，且长了反而降低解析效率。 |
| "删 Gotchas 能省不少" | **绝对不行**——Gotchas 是最高信号的部分，删了行为必变。 |
| "这个示例挺有代表性" | 一两份干净范例远胜几十个杂乱例子，后者互相干扰。 |

## 发布与版本类

| 借口 | 反驳 |
|---|---|
| "先发布，tag 后补" | 插件系统拉的是 git tag，后补等于这段时间用户装不到。 |
| "改了点措辞，算 PATCH 吧" | **description 改动会移动触发边界**，按 MINOR 或 MAJOR 对待。 |
| "直接改旧技能比另起 v2 省事" | 彻底改造旧技能会**静默改变行为**，另起 v2 才能灰度迁移。 |
| "废弃就直接删掉" | 四阶段不可跳——尤其**改 description 让 agent 不再选它**。 |
| "翻译时顺便改下 name" | name 是标识符，改了就断链。路径和命令名同理。 |
| "输出结构微调没事" | 对解析它的下游就是破坏性变更——**加键可以，重构不行**。 |

## 停止类

| 借口 | 反驳 |
|---|---|
| "还能再压 20 行" | 靠合并路由行腾空间是**可发现性的损失**，连续做会伤害路由质量。 |
| "再拆细一点" | 到了 3–7 个的中位区间就该停，再拆是过度工程。 |
| "这个技能还能覆盖更多场景" | 想兼顾太多会**跨越多个类别**，把 agent 搞糊涂。 |
| "别人家的技能都更长" | 长度不是质量标准——**优化后的技能可以比不装技能还便宜**。 |

## 自查

```
□ 是否在改之前就跑完了基线？
□ 是否识别出了"迭代 10 次仍失败"的架构信号？
□ 是否保护了 Gotchas 不被修剪掉？
□ description 改动是否按破坏性变更对待了？
□ 是否到了该停止的信号还不肯停？
```
