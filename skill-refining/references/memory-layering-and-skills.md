## 1. ⭐⭐ 记忆四层

工业界普遍把 agent 记忆分为四层：

| 层 | 定义 | 特点 | 典型实现 |
|---|---|---|---|
| ⭐ 短期（工作记忆） | 当前对话轮次内的临时记忆 | ⭐ 读写最快、容量有限、⭐ 对话结束就消失 | 最近 N 轮对话、当前任务状态 |
| ⭐⭐ 长期（持久记忆） | 跨会话持久化 | ⭐ 容量近乎无限、⭐ 读取需检索 | 向量库 + 结构化库 |
| ⭐⭐⭐ 程序记忆 | ⭐⭐⭐ Agent 学会的⭐ 做事方法 | ⭐⭐ 一旦习得可重复执行，⭐ 不需要每次重新学习 | ⭐⭐⭐ **工具调用记录 · 成功任务链路 · ⭐ 技能** |
| ⭐⭐⭐ 反思记忆 | ⭐ 对自身历史行为的⭐ 复盘/总结/修正 | ⭐⭐ 从失败与成功中提炼，⭐ 高阶 agent 的标志 | 复盘总结 · 错误案例库 |

**长期记忆还分两类**（这个细分有用）：

```
语义记忆：⭐ 事实类/知识类
         "用户是 Java 后端开发" · "公司用阿里云"
情景记忆：⭐ 时间线类事件
         "上周三用户排查过 Redis 缓存击穿"
```

## 2. ⭐⭐⭐ 技能 = 程序记忆

> ⭐⭐⭐ **在四层框架里，⭐⭐ 技能占据的是⭐ "程序记忆"这一格。**
>
> ⭐⭐⭐ **类比很准：⭐ 骑车、打字——学会了就形成肌肉记忆。**

这个定位立刻推出三条判据（下一节），
其中第一条解释了我们一直反复强调却只靠经验支撑的那句话。

---

## 3. ⭐⭐⭐ 由此推出的三条内容判据

**判据一：技能不该装事实**

```
⭐⭐⭐ 事实属于⭐ 语义记忆（长期记忆），⭐⭐ 不属于程序记忆
⭐⭐⭐ → ⭐⭐ 技能里堆事实 = ⭐ 用错了一层
```

> ⭐⭐⭐ 这正是"不要写模型已经知道的信息"
> 和"领域知识型避免百科化"的⭐ 结构性解释：
> ⭐⭐⭐ **不是因为浪费 token（虽然确实浪费），
> ⭐⭐⭐ ⭐ 而是因为它⭐ 把本该由长期记忆/检索承担的东西，
>     ⭐⭐ 塞进了程序记忆的格子里——
>     ⭐⭐⭐ 于是它⭐ 过期了你也不知道，因为它没有"更新时间"这个概念。**
>
> ⭐⭐ 这直接呼应 `team-admission-criteria.md` 第 11 条
> "参考资料必须说明来源或更新时间"——
> **技能里的事实之所以会腐烂，正因为程序记忆层没有时间维度。**

**判据二：技能该装"怎么做"，且要能被重复执行**

```
⭐⭐⭐ 程序记忆的定义就是⭐ "一旦习得可重复执行，不需要每次重新学习"
→ ⭐⭐ 所以⭐⭐⭐ 一次性上下文不该进技能
```

> ⭐⭐ 这与 `prompt-vs-skill-failure-modes.md` 的第 ③ 步
> "把当前事实移出去"完全对上——
> ⭐⭐⭐ **"当前"和"重复"是互斥的：塞了当前的，就不能重复了。**

**判据三：短期记忆里的东西不需要写进技能**

```
⭐⭐ 短期记忆 = 上下文窗口里的内容 = ⭐ 已经在了
⭐⭐⭐ → ⭐⭐ 重复一遍 = ⭐⭐⭐ 第二个真相来源（会漂移）
```

> ⭐⭐⭐ 与 `prompt-layering-positional-bias.md` 的
> "技能层不重复项目层约定"是同一条。
> 三个来源一致：**技能只装"程序"这一层独有的东西。**

## 4. ⭐⭐⭐ 反思记忆 → 技能的持续改进

> ⭐⭐⭐ **反思记忆是⭐ "从失败和成功中提炼经验，指导后续行动"。**

映射到技能维护，就是⭐⭐⭐ 一个此前没被明确命名的机制：

```
⭐⭐⭐ 每次技能失败 → 写进 Gotchas
   每次纠正模型一个错误 → 写进 Gotchas
   （examples-three-branches.md 原话）
```

> ⭐⭐⭐ 这其实就是⭐ **在给技能接一根反思记忆的线**——
> 技能本身（程序记忆）不会自己复盘，
> ⭐⭐ 所以维护者必须⭐ **手工把反思结果固化回程序记忆**。
>
> ⭐⭐⭐ 由此得出一条具体的维护要求：
> **修一个技能时，只改正文是不够的——
> 要同时把"这次为什么会错"写成一条可检查的规则。**
> 否则下次同样的错会以另一种形式重现。
>
> ⭐⭐ 与 `skill-decay-governance.md` 的 `review_after`
> 和 `team-admission-criteria.md` 的 CHANGELOG 合起来：
> **反思记忆制度化的三个产物 = Gotchas + review_after + CHANGELOG。**

## 5. ⭐⭐ 读取侧的启示

记忆读取流程（每一轮对话前主动召回注入 prompt）：

```
召回触发 → ⭐ 多路召回（向量 / 精确 / 时序）→ ⭐⭐ 重排序(Rerank)
        → ⭐⭐⭐ 只保留最相关的前 N 条 → 上下文组装
```

**核心原则**（这句对技能同样成立）：

> ⭐⭐⭐ **"只把有用的记忆给模型，⭐⭐ 而不是把所有记忆都塞进去。"**

> ⭐⭐⭐ 这与技能的⭐ 渐进式披露是⭐ 完全相同的原则，
> 只是发生在不同的层：
> ```
> 记忆层：多路召回 → rerank → 只取 Top N
> 技能层：⭐ 目录层(name+description) → 激活层(SKILL.md) → 资源层(references/scripts)
> ```
> ⭐⭐⭐ 两者都是⭐ **"先粗筛、再精取"**——
> 而技能库规模过 50 个时我们建议的两步路由，
> ⭐⭐ 本质上就是⭐ **手工实现了一个 rerank 层**。

**还有一条写入侧的**：

```
⭐ 记忆写入不是把用户原话直接存进去，⭐ 而是⭐⭐⭐ 先加工再存储
   信息提取 → 向量化 → 结构化 → ⭐ 重要性打分 → ⭐⭐ 时间戳
```

> ⭐⭐⭐ "⭐ 重要性打分"和"⭐⭐ 时间戳"这两个字段
> 可以直接借鉴到技能的 references 管理：
> **给每份 reference 标上重要性与最后核验时间**
> ——前者决定它是否该留在目录层，后者决定它是否已腐烂。

## 速查

```
□ ⭐⭐ 记忆四层：短期(上下文窗口) · 长期(语义/情景) · ⭐⭐⭐ 程序(⭐ 技能) · ⭐⭐⭐ 反思(复盘)
□ ⭐⭐⭐ ⭐ 技能 = 程序记忆（骑车/打字，学会就不忘）

□ ⭐⭐⭐ 判据一：⭐ 技能不该装事实（事实属语义记忆）
   ⭐⭐⭐ ⭐ 技能里的事实会腐烂，因为⭐ 程序记忆层没有时间维度
□ ⭐⭐⭐ 判据二：技能装"怎么做"且可重复 → ⭐⭐⭐ "当前"与"重复"互斥
□ ⭐⭐⭐ 判据三：⭐ 不重复短期记忆里已有的（= 不重复项目层约定）
□ ⭐⭐⭐ 反思记忆要⭐ 手工固化回程序记忆：⭐ 修技能时同时把"为什么错"写成规则
   ⭐⭐ 制度化三产物：Gotchas + review_after + CHANGELOG

□ ⭐⭐⭐ "只把有用的记忆给模型" = 渐进式披露的同一原则（先粗筛再精取）
   ⭐⭐ 50+ 技能的两步路由 = ⭐ 手工实现 rerank 层
□ ⭐⭐ 借鉴：给每份 reference 标⭐ 重要性 + ⭐⭐ 最后核验时间
```

**一句话**：

> ⭐⭐⭐ **在记忆四层里技能占据"程序记忆"——所以技能不该装事实（事实属语义记忆，而程序记忆层没有时间维度，所以它过期了你也不知道），不该装一次性上下文（"当前"与"可重复"互斥），也不该重复上下文窗口里已有的东西。**
