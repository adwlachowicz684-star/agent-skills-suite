## 1. 两种口径

| 口径 | 格式 | 特点 |
|---|---|---|
| **两分制** | `MAJOR.MINOR` | ⭐ 没有 patch 分量，所有变更落在正好两个桶里 |
| **三分制** | `MAJOR.MINOR.PATCH` | 语义化版本，修补单独一档 |

---

## 2. ⭐ 判据：调用方会不会坏

> ⭐ **判据是现有调用方会不会坏掉，而不是改了多少文字。**
>
> ```
> 沿用旧版本仍能拿到正确结果 → MINOR
> ⭐ 无论改动了多少行
>
> ⭐ 让"按旧版本使用"变成错误结果 → MAJOR
> ```

**三分制的具体划分**：

| 变更类型 | 版本 | 例子 |
|---|---|---|
| 错字、措辞澄清 | Minor 1.0→1.1 | 修了第 3 步里一句不清楚的话 |
| 新增：新步骤、新坑、新表 | Minor 1.0→1.1 | 为边界情况加了第 7 步 |
| ⭐ **破坏性：重构流程、改输入** | **Major 1.0→2.0** | 从 5 步重组为 8 步 |

**MAJOR 的触发条件**（具体化）：

```
· 步骤被重新编号或删除
· ⭐ 必需输入被新增或改名
· ⭐ 预期结果被重新定义，导致沿用旧版本会产出错误结果
```

**另一份口径**（更贴近技能语境）：

```
MAJOR  触发条件或契约变化  → 移除自动放量、修改必填输入
MINOR  新增步骤或检查      → 增加 SLO 预算校验
PATCH  文案或示例修订      → 调整描述、补充示例
```

---

## 3. ⭐ 两分制版本（MAJOR.MINOR）

两分制的优势是**没有模糊地带**——不存在"这算 patch 还是 minor"的纠结。

```
⭐ 每次变更必须落在两个桶之一
⭐ 新变体从 "1.0" 起步
⭐ 升 MAJOR 时把 MINOR 归零
```

**既有版本不追溯**：

> ⭐ **已有的语料版本 grandfathered——
> 不要为了纠正历史上的错误标注而回过头去改版本号。**

## 4. 三分制（SemVer）

| 段 | 何时递增 | 示例 |
|---|---|---|
| MAJOR | 不兼容的重大改动 | 1.0.0 → 2.0.0 |
| MINOR | 新增功能，向下兼容 | 1.0.0 → 1.1.0 |
| PATCH | Bug 修复，不影响功能 | 1.0.0 → 1.0.1 |

**在 frontmatter 中声明**：

```yaml
name: csv-analyzer
version: 1.2.0
description: 分析 CSV 文件，输出统计摘要。
```

**提交信息前缀**：

```
feat:     新功能        feat: 新增 Excel 输出支持
fix:      Bug 修复      fix: 修复空文件时的崩溃问题
docs:     文档更新      docs: 补充参数说明
refactor: 重构（无功能变化）
perf:     性能优化      perf: 大文件处理速度提升 3 倍
```

## 5. 破坏性变更的处理

**CHANGELOG 里显式标注**：

```markdown
v2.0.0 - 2026-08-20
- ⭐ BREAKING: 移除自动放量，调用方必须显式审批
- description: 增加"临时排查调试"场景的排除条款
- checks: 放量前要求校验 SLO 预算
```

> ⭐ **没有版本号和 CHANGELOG，
> 就无法把一次失败归因于"这次改坏了"。**

**迁移指引**（不兼容变更必须给）：

```markdown
## 迁移指南：从 v1.x 升级到 v2.0
### 主要变化
输出文件名由 output.xlsx 改为 output_YYYYMMDD.xlsx
### 受影响场景
如果你的工作流依赖固定文件名，需要重命名或使用 --output 参数
### 迁移步骤
1. 更新到 v2.0
2. 检查是否有依赖固定文件名的脚本
3. 如有，添加 --output output.xlsx 保持旧行为
```

> ⭐ **使用者众多时，考虑保留旧参数并标记为"已废弃"，
> 给过渡时间，而不是直接删除。**

## 速查

```
□ ⭐ 判据是"调用方会不会坏"，不是"改了多少字"
□ 沿用旧版仍正确 → MINOR（无论多少行）
□ 步骤重编号/输入改名/结果重定义 → MAJOR
□ 新变体从 1.0 起步，升 MAJOR 时 MINOR 归零
□ ⭐ 不追溯修改历史版本号
□ ⭐ 破坏性变更在 CHANGELOG 显式标 BREAKING
□ ⭐ 给迁移指引；用户多时先标 deprecated 再删
□ ⭐ 忘记 bump → 下次演进无法区分新旧状态；提交前必须 bump
```

**一句话**：

> ⭐ **没有版本和 CHANGELOG，就无法把一次失败归因于"这次改坏了"。**
