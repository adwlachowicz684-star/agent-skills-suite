## 1. ⭐ 版本管理的三个层次

| 层 | 手段 | 体验 | 问题 |
|---|---|---|---|
| L1 | **frontmatter version** | 零门槛 | ⭐ 靠人的自觉 |
| L2 | **Git** | 功能完备 | 要自己记得 commit |
| L3 | **平台内置快照** | ⭐ 体验最好 | ⭐ 能做到的平台屈指可数 |

**L1**（手写版本号）：

```yaml
name: code-reviewer
version: 2.3.0
last_modified: 2025-06-15
```

**L2**（Git）：

```
git add SKILL.md
git commit -m "fix: 修复文件路径处理的空格问题"
git tag v1.0.1
```

**L3**（平台内置）：

```
skill-name/
├── SKILL.md          # 当前活跃版本
├── versions/
│   ├── 2025-06-01-001.md
│   └── 2025-06-03-002.md
└── curator.toml
```

> ⭐ L3 的巧妙处：**没有额外学习成本**——
> 不用学 Git、不用记命令，每次保存自动拍快照，需要时点一下回退。
> **版本间可 diff、可回退、甚至可 fork 出独立演化的分支。**

**三层不互斥**：

```
L1 做快速标识 + L2 做完整历史追溯 + L3 兜底
⭐ 如果三样都没有……结局就是"改完回不去"
```

## 2. ⭐ 层次一是靠自觉的

> ⭐ **L1 有个致命问题：它靠人的自觉。
> 忙起来就忘了改，或者改了但没记 changelog，
> ⭐ 久而久之版本号就变成了一个没人信的数字。**

**L2 也有盲区**：

```
⭐ 大部分 AI Agent 平台的 Web UI 不给你接触底层文件系统的机会——
   你在网页上编辑技能，背后改了啥，没有 Git 帮你记。
```

**现实状况**（说实话）：

```
· 大多数平台没有内置技能版本管理
· 有些把技能版本绑到 Agent 版本上（间接版本管理）
· 有些靠外部工具补救（让你自己放 Git）
· ⭐ 普通用户目前能依赖的，主要还是 Git + 自觉
```

> ⭐ **最低限度方案**：
> **先把技能放进 Git 仓库——这是投入产出比最高的方案。**
> 平台不支持内置版本管理的话，
> **至少改之前复制一份备份——老土，但管用。**

## 3. 增量 vs 重构

**增量迭代**：现有技能上小修小补（加指令、改一段、调参数）
```
· 改动范围小、风险可控，适合日常优化
⭐ 但积累到一定程度会变成"屎山"——
   每个指令单独看还行，合在一起互相矛盾
```

**重构迭代**：推倒重来
```
· 结构不合理、指令太乱、行为无法通过微调修正
⭐ 干净但代价大，且⭐ 重写的技能可能丢掉一些你没意识到的隐含行为
```

> ⭐ **经验法则：
> 如果一个技能的修改次数超过 10 次，
> 或连续 3 次增量改动都没解决问题，就考虑重构。**

## 4. ⭐ in-session patching 的陷阱

> ⭐ **有些平台允许你在对话中直接修改技能——
> 跟 agent 说"帮我把第三条指令改成 XXX"，它当场就改了。**
>
> ⭐ **这很方便，但也很危险：这种修改往往不留日志。**
> **你改了，AI 的行为变了，过两天回头看根本想不起来当时改了什么。**

**应对**：

```
① ⭐ in-session patch 只用于调试
② ⭐ 调试完毕，必须把改动同步回文件
③ ⭐ 写一条变更记录
④ ⭐ 如果平台支持，让 agent 改完自动生成一个版本快照
```

## 5. 更新时机与节奏

**何时该更新**：

```
· 工具/框架发布新版本
· 最佳实践演进
· ⭐ 发现了常见问题
· ⭐ 用户反馈暴露了缺口
· ⭐ 项目约定变化
```

**更新流程**：

```
① 识别变化     检查技能"年龄"、看官方更新、看框架变更
② 记录更新     改了什么（版本/特性/废弃）、影响哪些章节
③ 更新内容     改 SKILL.md、更新示例、加新实践、
               ⭐ 废弃旧模式但要解释为什么
④ 验证         ⭐ 测试更新后的代码示例、检查文档链接、
               ⭐ 检查自相矛盾、测试技能调用
```

**周期性节奏**：

```
定期：  收集用户反馈 · 考虑拆分过大的技能
年度：  需要时大重构 · 归档废弃内容 · ⭐ 合并重叠的技能
```

> ⭐ 最后一项很关键：**定期合并重叠技能**——
> 因为重叠正是 `library-size-effect.md` 里那个"遮蔽占 68%"的根源。

## 速查

```
□ L1 frontmatter 版本号（靠自觉）
□ ⭐ L2 Git（投入产出比最高，先做这个）
□ L3 平台内置快照（有就用，可 diff/回退/fork）
□ ⭐ 改之前至少复制一份备份
□ ⭐ 修改 >10 次 / 连续 3 次增量没解决 → 重构
□ ⭐ in-session 修改只用于调试，必须同步回文件 + 写变更记录
□ 废弃旧模式要解释为什么
□ 验证时检查"自相矛盾"
□ ⭐ 年度合并重叠技能
```

**一句话**：

> ⭐ **"改完回不去"是最常见的技能维护事故——
> 而它只需要一个 Git 仓库就能避免。**
