## 单体技能的问题

随着功能变复杂，技能通常会长成这样：

```
❌ 超过 500 行 —— 信息太多，无法有效解析
❌ 混合关注点 —— 处理多个不相关的职责
❌ 浪费上下文 —— 即使只有一小部分相关，也加载整个文件
❌ 难以维护   —— 改动需要仔细浏览大文件
```

> **解决方案**：拆分 → 路由 → 按需加载。
> 结果：在保持"每个技能 <500 行"的同时，构建复杂应用。

## 拆分信号

| 信号 | 说明 |
|---|---|
| **文件超过 300 行** | 或某个 Step 的规则超过 100 行 |
| **描述里要写很长的分支条件** | ⭐ 这是最实用的信号 |
| **迭代 10 次还修不好某个失败模式** | **问题在架构，不在措辞**——别再调提示词了 |

**一个真实案例**：

> 电商客服 Agent：团队第一反应是写一个大而全的客服技能，
> 80 多次迭代、3 周，凭感觉"挺好的"。
> 然后建了 100 个真实问题的评估集——**准确率 62%**。
> 继续死磕提示词调到 74% 就彻底卡住：
> **改好了退货场景，产品咨询就出错；修好了咨询，订单查询又崩了。**
> 典型的"打地鼠"。

**解法是拆**：

```
router-skill        → 判断意图，派给对应专家
order-status-skill  → 只管订单查询
return-skill        → 只管退货
product-qa-skill    → 只管产品咨询
```

> 每个技能的提示词都很简单，因为只需处理一类问题。
> **几天时间，准确率到了 90%。**

## 拆与不拆的判断

**粒度原则**：

> ⭐ **一个意图一个技能，不要贪多。**
> 当你在描述技能时发现需要写很长很长的分支条件，就是拆分的信号。

**但也别拆太细**——路由成本上升，模型要判断的分支变多，
维护者更难理解整体结构。目标：**最多 3–7 个子技能**。

**该合并的两种情况**：

| 情况 | 为什么 |
|---|---|
| **行为边界天然不可分割** | 如"创建退换货申请"和"校验是否在质保期内"——后者是前者的内部步骤，硬拆会让编排层很别扭 |
| **调用频率极低的辅助逻辑** | 如"查余额"和"查积分"都是低频，合并成"用户资产查询"反而清爽 |

**合并判据**：

> 如果拆开后，**agent 需要对同一个用户请求连续调用两次，
> 且第二次的参数依赖第一次的结果**——那不如合并，或交给编排层处理。

**另一个判据**：

> 如果两个能力**共享大量规则** → 放同一个技能；
> 如果它们**只有入口相同、执行过程完全不同** → 拆成子技能。

## 三层架构

```
基础能力层   原子能力，不含业务语义
             HTTP 请求、数据库读写、消息推送、文件上传
业务能力层   面向具体业务的技能
             订单查询、售后申请、优惠券核销
编排层       ❌ 不属于技能，属于 agent 的 prompt 与流程设计
             决定先调哪个业务技能、怎么合并多个结果
```

> ⭐ **最大好处：每一层都能独立扩展、独立测试。**
> 基础层换实现不影响上层；业务层新增技能不影响底层；
> 编排层改动不至于让你重写技能代码。

## Router 模式

**结构**：

```
tencent-ima/
├── SKILL.md              # 主入口，只保留模块决策表
├── ima_api.cjs           # 共享脚本
├── notes/
│   ├── SKILL.md
│   └── references/api.md
└── knowledge-base/
    ├── SKILL.md
    └── references/api.md
```

**主 SKILL.md 只放决策表**：

| 用户意图 | 路由到 | 读取 |
|---|---|---|
| 搜索笔记、创建笔记、整理笔记 | notes 模块 | `notes/SKILL.md` |
| 上传文件、搜索知识库、管理知识库 | knowledge-base 模块 | `knowledge-base/SKILL.md` |

> 用户说"帮我搜索知识库里关于 AI Agent 的资料"
> → 只加载主入口 + `knowledge-base/SKILL.md`。

**意图路由器的关键约束**（一个真实案例的细节）：

```yaml
name: intent-router
description: 当用户输入为中文客服对话时使用。负责识别意图并路由到
  对应处理技能。仅做意图分类，不直接回答用户问题。
```

> ⭐ **description 里明确写"不做回答"**——
> 这是路由器的关键约束，避免模型直接越权生成回复。

**模块级工具隔离**：

```
□ 白名单制——每个模块明确列出可用接口，白名单外一律禁止
□ 危险接口显式禁用——万能工具（如直接 HTTP 调用）全局禁止
□ 工具隔离——不同模块用不同接口集合，防误调用
```

## 分层路由

> 10+ 个子技能或多个逻辑子系统时，用**路由器的路由器**：

```
main_router.md (100 行)
├── user_subsystem_router.md    (150 行)
│   ├── user_auth.md            (400 行)
│   ├── user_profiles.md        (350 行)
│   └── user_permissions.md     (380 行)
├── product_subsystem_router.md (180 行)
│   └── ...
└── order_subsystem_router.md   (160 行)
    └── ...
```

**动态路由（上下文感知）**——路由器考虑对话上下文：

```
首次用户（无历史）        → 始终激活 getting_started
回访用户（有上下文）      → 分析最近主题，激活相关子技能，跳过介绍
错误状态（之前操作失败）  → 激活排障技能，并带上失败操作的上下文
```

**路由逻辑过长的修法**：

```
□ 简化路由逻辑——用关键字表而不是散文
□ 删除冗余描述
□ 减少子技能数量——合并密切相关的，目标 3–7 个
```

## 成本实测

> ⚠️ **数据来自不同来源、口径不一，请当方向性参考。**

| 场景 | 结果 |
|---|---|
| 任务轮次 | 无技能 11 轮 → 有技能 4 轮（**压缩 64%**） |
| Token（某项目优化） | 单任务 78K → 51K（**−35%**）；**成功率 82% → 88%** |
| 常驻开销（同一项目） | 系统提示+工具定义 5.2K → 1.8K（**−65%**） |
| **SkillsBench**（较严格） | 输入 token **+6~13%**，但性能 **+16.2pp**；每 trial 仅多 $0.03–0.22 |

> ⭐ **两个一致的结论**：
>
> 1. **上下文越干净，模型注意力越集中，出错概率越低——
>    臃肿不只是费钱，还费准确率。**
> 2. **省 token 的真正来源是减少返工轮次**，
>    而不是把指令写短。一次返工要重新生成整段输出，代价远高于多带 800 token 的技能。

> ⚠️ **别指望砍一半**：20% 是针对"已经比较克制"的架构说的；
> 基线本来就臃肿的才省得多。**稳住 20% 是现实的。**

## 自查

```
□ 单个文件是否超过 300 行（或某个 Step 超过 100 行）？
□ description 里是否出现了很长的分支条件（拆分信号）？
□ 是否迭代 10 次还修不好某个失败模式（该改架构而非措辞）？
□ 子技能数量是否在 3–7 之间（不过多）？
□ 是否误把"天然不可分割"或"低频辅助"的逻辑拆开了？
□ 是否存在"连续两次调用且第二次依赖第一次结果"（应合并）？
□ 是否分了基础/业务/编排三层（编排层不属于技能）？
□ Router 的 description 是否写了"仅做路由，不直接回答"？
□ 是否做了模块级工具白名单？
□ 路由逻辑是否用关键字表而非散文？
```
