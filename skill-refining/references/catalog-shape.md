## 1. 先判归属：是真技能还是被包装的段落

在写任何技能之前先问两个问题：

```
① 它有明确的触发条件吗？（一个可识别的、应当把它拉进来的情境）
② 正文值得超过 200 tokens 吗？
```

判据很干脆：

| 情况 | 结论 |
|---|---|
| 没有明确触发条件 | ⭐ **它属于 CLAUDE.md**，不是技能 |
| ⭐ **正文比 description 还短** | **这个技能只是伪装成段落**——提升为 CLAUDE.md 规则，去掉外壳 |
| 数据是动态的 | 走 MCP，不要写进技能 |

**反向提升同样有效**：

> CLAUDE.md 里一条**只在特定情境适用**的规则，应当**降级为技能**，
> 好让它不再挤占常驻的加载面。

## 2. 五个反模式

### ① 模糊的描述

```
❌ "Use this skill for thinking about complex problems."
   —— 模型永远判断不了什么叫"足够复杂"
```

⭐ **修法：写成 触发 + 范围 + 输出 三段式**

```
✅ "Use when reviewing a proposed system design before approval.
    Audits for conceptual integrity, scope creep, and constraint exploitation.
    Outputs a verdict and a remaining-risk list."
```

### ② 正文是一篇演讲

现象：正文先用 4,000 tokens 从第一性原理推导一遍，然后才说要做什么。
模型读完了却**难以提取出动作**——**这个技能的成本高于它的收益**。

```
❌ 先讲理论渊源、设计哲学、为什么这样更好……（三段之后才进入操作）
✅ 以程序开头，不讲理由
```

⭐ **修法**：把哲学/原理移到 Tier 3 的 reference 文件，正文链接过去。
正文要短到**像一份带说明文字的清单，而不是一篇论文**。

### ③ 本该是 CLAUDE.md 规则的技能

现象：一个"技能"只有三句话，而且对每个会话都适用。

⭐ **修法：提升为 CLAUDE.md。** 省下路由开销，还更可靠。

### ④ 没有分类学的目录

现象：技能不断堆积但没有形状，description 互相重叠，
模型选错——因为**两个技能都讲得通**。

> ⭐ 微软的渐进式披露研究给了一个反直觉发现：
> **当许多技能响应相似的触发词时，元数据层变得更嘈杂、路由更差，
> 即使没有任何单个技能发生变化。**

⭐ **修法**：每季度扫一遍目录，专门找 **description 碰撞**。
**如果两个 description 都讲得通能路由同一个任务——合并，或者把它们区分开。**

### ⑤ 没有审计节奏

现象：没人再读这个目录。过时的技能用过时的触发词路由，
description 不再反映正文，正文引用了已经改名的 API。

⭐ **修法**（见第 5 节）。

## 3. 子代理系统提示词不是技能

> ⭐ **子代理有自己的"宪法"。**
> 它可以像主代理一样加载技能，但**它的角色定义属于子代理定义本身，
> 不属于一个需要主代理去路由的技能。**

配套判断：

> **"什么时候派生子代理 vs 什么时候留在上下文里"这个决策，
> 在技能的上游，而不是与技能并列。**

也就是说——不要写一个"决定是否派生子代理"的技能。那是编排层的事。

## 4. 目录分类学

### 粒度：过宽与过窄同样失败

| | 例子 | 问题 |
|---|---|---|
| 过宽 ❌ | 一个 `general-research` 技能同时覆盖 web 搜索、arXiv、PubMed、数据集 | 太多工具和上下文，模型困惑 |
| 过窄 ❌ | 拆成 `arxiv-search-physics` 和 `arxiv-search-cs` | **技能膨胀**，反而更难找到对的 |
| 刚好 ✅ | 一个 `arxiv-search`，单一聚焦能力 | |

### 命名

```
✅ kebab-case：        csv-analyzer
✅ 描述性 + 动作导向：  api-client / data-fetcher
❌ 通用无信息：        skill1 / tool-a / general-helper
```

> 如果技能什么都做，那它实际上什么都没做好。

### 结构性反模式

| 反模式 | 说明 |
|---|---|
| ⭐ **循环依赖** | 技能互相要求对方先加载 → 初始化循环，调试噩梦 |
| **硬编码密钥** | 一律用环境变量，文档里写 `export XYZ_API_KEY="..."` |
| **过于通用** | `general-helper` 类，拆成单一职责 |

## 5. 30 天审计节奏

修法和 CLAUDE.md 一样：**30 天审计一次**。

打开每一个 SKILL.md，问三个问题：

```
① description 是否仍然匹配正文？
② 正文是否仍然匹配代码库？（有没有引用已改名的 API / 已废弃的路径）
③ 这个技能本身是否还配得上它占的位置？
```

**砍掉不合格的。**

> ⭐ 这五个失败的**形状是同一个**：
> **表面与教义发生了漂移**。
> 要么 description 相对正文承诺过多或说明不足，
> 要么正文相对工作解释过多，
> 要么目录在增长而没人管它的形状。

纪律是：**像读文档一样读目录——审查已有的东西，要和你写新东西一样频繁。**

## 6. 渐进复杂度：三个版本

不要在第一天就追求完美技能：

```
V1（指令）  只有一个 SKILL.md，说明模型如何用现有工具达成目标
V2（参考）  加 references/api.md 或 schema 文件，提供更深上下文
V3（脚本）  引入 scripts/ 下的 Python / Shell，自动化复杂逻辑
```

> 这与《skill-refining》的 `architecture-layering.md` 一致：
> **先让它能跑，再按测出来的缺口加层，不要预先设计。**

## 速查

| 信号 | 处置 |
|---|---|
| 正文比 description 还短 | 提升为 CLAUDE.md，去掉技能外壳 |
| 正文是长篇演讲 | 移原理到 references，正文以程序开头 |
| 两个 description 都讲得通同一任务 | 合并，或明确区分 |
| 技能互相要求先加载 | 拆掉循环依赖 |
| CLAUDE.md 中只在特定情境适用的规则 | 降级为技能 |
| 子代理的角色定义 | 放子代理定义，不要做成技能 |
