## 1. ⭐⭐⭐⭐⭐ 症状：你改了一个文件，全队行为都变了

```
"我不止一次对技能做了破坏性改动，
 静默地影响了整个团队。"
```

这句话的恐怖之处在于三个"没有"：

```
· 没有 CI 报警
· 没有构建失败
· ⭐ 没有一个人被告知
```

> ⭐⭐⭐ **技能改动的传播是静默的**，因为它的消费者不是代码，是人——
> 而人不会在自己不知道的情况下报 issue。

根因是一个结构性缺失：**我们有"技能依赖什么"，没有"谁依赖这个技能"。**

---

## 2. ⭐⭐⭐⭐ 四类下游

改一个技能，可能影响到的对象有四类，缺任何一类都会漏：

| 下游 | 例子 | ⭐ 为什么容易漏 |
|---|---|---|
| **① 人** | 直接调用 `/skill-name` 的同事 | ⭐ 他们不在代码里，grep 不到 |
| **② 编排链路** | 编排器把它的输出喂给下一个技能 | ⭐ 依赖写在编排器里，不在技能里 |
| **③ 子代理** | 子代理挂载了这个技能 | ⭐ 挂载关系在 fork 正文里 |
| **④ 文档/规范** | CLAUDE.md、团队 wiki 引用了它的输出格式 | ⭐ 文档引用不可 grep |

> ⭐⭐⭐ **第②类最危险**：因为它会**级联**。
> 你改了 A 的输出格式，B 解析失败，C 拿到空的 B 输出——
> 而 C 的失败报告里根本不会提到 A。

这正是 `skill-data-passing.md` 那句"出错的地方 ≠ 你改动的地方"的机制。

---

## 3. ⭐⭐⭐⭐⭐ 影响面清单（改之前跑一遍）

六问，答不上来的就不许改：

| # | 问题 | 查不到时 |
|---|---|---|
| 1 | ⭐ 谁会调用它？（人 + 编排 + 子代理） | 当成"可能有"，走完整流程 |
| 2 | ⭐ 有没有技能消费它的输出？ | ⭐⭐ **默认有**，先去找 |
| 3 | 这次改动会改变**输出形状**吗？ | 形状一变，下游全变 |
| 4 | 会改变**触发条件**吗？ | ⭐ 触发变了，调用它的场景就变了 |
| 5 | 会改变**权限要求**吗？ | ⭐ 少给权限 = 静默失败 |
| 6 | 有没有外部系统依赖变了？ | 见 `dependency-resolution-conflicts.md` |

> ⭐⭐⭐ **第 2 问的默认答案是"有"，不是"没有"。**
> 这是整份文档最重要的一条——因为查不到不等于不存在，
> 而"我以为没人用"正是所有静默破坏的起点。

## 4. ⭐⭐⭐ 反向依赖图：多数团队没有的东西

依赖声明（`depends_on`）记录的是**正向**关系：我需要谁。
而影响面分析需要的是**反向**：谁需要我。

```
正向（多数人有）：  A → B（A 依赖 B）
⭐ 反向（需要）：    B ← A（B 被 A 依赖）
```

**最低成本的实现**（不用上注册中心）：

```bash
# 在全库搜技能名，找出所有引用它的地方
grep -rn "skill-name" --include="*.md" .
```

> ⭐⭐⭐ 就这么一行，能把"静默影响全队"变成"改之前就知道影响谁"。
> 它不完美（漏掉口头约定），但把不可见变成了可见。

更好的做法是在 CI 里自动生成：

```
每次 PR → 扫出被改技能 → grep 反向引用 → ⭐ 把下游列在 PR 描述里
```

> ⭐⭐⭐ **关键不是精确，是出现在 PR 里。**
> 评审者看到"这个改动会影响 3 个下游"和看到"无下游"，
> 审查强度完全不同。

## 5. ⭐⭐⭐⭐ 按影响面决定流程强度

不是所有改动都值得全套流程——**按影响面分档才守得住**：

| 影响面 | 典型改动 | ⭐ 要求 |
|---|---|---|
| 无下游 | 错别字、内部注释 | 直接合 |
| 只有人 | 补充说明 | PR + 人工跑一遍 |
| ⭐ 有编排下游 | ⭐ 输出形状、步骤编号 | ⭐ PR + 下游技能一起跑回归 |
| ⭐⭐ 有外部依赖 | 权限、数据源 | ⭐⭐ PR + 灰度 + 回滚预案 |

> ⭐⭐⭐ 这张表和 `skill-as-business-rule.md` 的"四类改动危险等级"
> 是两个维度，要交叉看：
> **改动类型**（描述 vs 规则）× **影响面**（有没有下游）。
> 两者都高时，才需要最重的流程。

---

## 6. ⭐⭐⭐ 改完之后的验证顺序

顺序很重要——**先验证自己，再验证下游**：

```
1. 结构校验（validate_skill.py）
2. ⭐ 本技能的行为回归（eval 集）
3. ⭐⭐ 下游技能的回归——不是"跑一遍"，是"用真实输出跑"
4. 灰度 + 监控版本级指标
```

> ⭐⭐⭐ 第 3 步的坑：**很多人用"手工构造的输入"跑下游**，
> 那测的是下游能不能处理理想输入，不是能不能处理你的新输出。
> 必须**把上游的真实输出喂进去**。

配一条来自 `outgrowth-regression-detection.md` 的要求：
**eval 输入要脏**——用真实使用的半成品输入，不是干净样例。

---

## 7. ⭐⭐ 一个反直觉的结论

```
⭐ 改技能的"成本"和改动大小几乎无关，和影响面成正比。
```

对照一下：

| 改动 | 大小 | 影响面 | 实际风险 |
|---|---|---|---|
| 改一个字段名 | 1 行 | ⭐ 全下游 | ⭐⭐ 极高 |
| 重写整个流程 | 300 行 | 无下游 | 低 |

> ⭐⭐⭐ **这直接反驳了"大改动才需要谨慎"的直觉。**
> 也解释了为什么 `version-changelog-practice.md` 的 MAJOR 判据
> 不是"改了多少行"，而是"按旧版本使用会不会变成错误结果"——
> 那本质上就是一个影响面判据。
