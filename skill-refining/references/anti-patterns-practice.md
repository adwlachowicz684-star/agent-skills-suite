## 七个高频坑

| 坑 | 症状 | 原因 | 解法 |
|---|---|---|---|
| **1. 触发词太泛** | 误触发率高 | 用了太常见的词 | 改成精确短语："用户提到'写文章''出稿''写公众号'时" |
| **2. 规则冲突** | 同时加载两个技能，输出格式乱了 | 两者对同一件事要求矛盾 | **设优先级**，冲突时高优先级覆盖；或合并成一个 |
| **3. 代码示例过时** | AI 按旧方式写代码报错 | 技能创建时的示例没随依赖库更新 | 定期检查示例是否还能跑；**或只写规则不写死代码** |
| **4. 没有示例** | 写了"输出要简洁"，AI 理解成"只写一句话" | "简洁"是主观的 | ⭐ **给正例和反例的对比**，不只给形容词 |
| **5. 没有版本管理** | 改坏了想回退找不到旧版 | 直接改文件没备份 | Git 管理；或改前复制一份 |
| **6. 多人协作冲突** | 各改同一个技能，合并时冲突 | 所有规则挤在一个文件 | **拆成核心规则（只读）+ 个人配置（可覆盖）** |
| **7. 无超时控制** | 网络抖动时用户等 30s+ | I/O 没设 timeout | 所有 I/O 设 timeout（建议 8 秒），返回友好提示 |

> ⭐ **坑 3 的解法值得多想一层**：
> **"或不在技能里写死代码，只写规则和约束"**——
> 这正是"确定性逻辑进 `scripts/`"之外的一条补充思路：
> 会过时的具体示例，本身就是一种维护负债。

## 新手最容易写坏的地方

**① 把技能写成角色扮演**

```
❌ "你是世界级架构师"    —— 这不是技能，最多是语气设定
✅ 真正的架构评审技能应该写：
   先看边界 → 再看依赖 → 再看失败模式 → 再看迁移路径
   → 最后给出是否可上线的判断
```

**② 一个技能管太多事**

```
❌ "全能产品研发运营增长设计发布技能"
   —— 很难触发，也很难维护
   ⭐ 技能越大，越像一份没人愿意读的制度文件
✅ 按任务拆小，反而更容易复用
```

**③ 只写成功路径，不写失败路径**

> ⭐ **人类 SOP 最值钱的往往是异常处理**：
> 抓不到数据怎么办、字段缺失怎么办、权限不足怎么办、输出不合格怎么办。

```
❌ 只写"第一步、第二步、第三步"
✅ 每个可能失败的步骤都写明：失败长什么样 + 怎么办
   Happy-path-only 的技能在生产环境一定会崩
```

**④ 把脚本当装饰**

```
❌ scripts/ 里放了脚本，但 SKILL.md 没写什么时候运行、
   输入是什么、失败怎么处理 → agent 很可能不用
✅ 脚本不是摆设，要把调用条件写清楚
```

**⑤ 不做版本管理**

```
团队技能应该像代码一样进 Git。
⭐ 否则某天 agent 行为突然变了，你不知道是谁改了哪一行。
```

**⑥ 忽略错误路径**（工程侧）

```
所有外部调用 wrap in try-catch + 结构化 error
一次 API 故障不应导致整个对话崩溃
```

**⑦ 返回冗余数据**

```
用 schema 严格约束 output，只返必需字段
生产环境建议加 additionalProperties: false
——防止模型返回意外字段导致解析异常
```

## 优秀技能的四个特征

| 特征 | 说明 | 验收标准 |
|---|---|---|
| **Clear** | agent 100% 理解何时/如何用 | SKILL.md 通过"意图匹配测试" |
| **Robust** | 失败时优雅降级，不崩盘 | 错误场景 100% 返回结构化 error |
| **Focused** | 单一职责，拒绝功能膨胀 | 代码 review 时没人问"这为啥在这？" |
| **Documented** | 人与 AI 都能无障碍使用 | **新成员 30 分钟内可贡献新技能** |

> ⭐ **最后一条是最容易被忽略的验收标准**——
> 它检验的是技能的可维护性，而不是它当下能不能跑。

**还有一个平衡框架**值得记：

```
        🎯 精准性
          / \
🧠 智能体理解力 —— 🛠️ 工程可靠性
          \ /
        👥 用户体验
```

> **构建生产级技能，本质是在三个维度取得平衡。**
> 只追求精准而忽略工程可靠性，技能在真实环境会碎。

## 今天就能做的行动清单

```
□ 选一个简单场景，按四件套结构建第一个技能
□ ⭐ 为 SKILL.md 添加 3 个"禁用场景"，
    观察 agent 决策准确率的变化
□ 在 schema 中加入 required 和字段 description，
    对比参数填充成功率
□ 为所有外部调用添加 8 秒超时，模拟弱网测试体验
□ ⭐ 邀请同事"盲测"——不给文档，
    看 TA 能否通过 SKILL.md 理解技能用法
□ 跑一次"我有哪些技能"确认可发现性
□ 用 Git 管理技能目录
```

> ⭐ **"盲测"这条尤其值得做**——
> 它同时检验了可发现性、可读性与可维护性。
> 呼应 `discovery-ux.md`：**技能写得再好，用户不知道它存在就等于不存在。**

## 一个工程侧的安全附录

```
□ Schema 加固：output schema 建议加
  additionalProperties: false，防意外字段导致解析异常

□ 权限加固：技能涉及用户数据时，
  在 handler 入口加 userId 校验与权限中间件，实现技能级 RBAC

□ 审计：定义权限与审计规则——
  哪些角色有权触发，执行日志如何留存
```

> 呼应 `skill-governance` 的 `compliance-audit.md`：
> **"干什么有记录，结果能审计"** 是权限控制的核心，
> 不只是技术配置。

## 自查

```
□ 触发词是否足够精确（而非泛泛关键词）？
□ 是否与已有技能存在规则冲突（冲突时是否有优先级）？
□ 代码示例是否会过时（是否改成了只写规则）？
□ 是否给了正例与反例（而非只给形容词）？
□ 是否进了 Git 版本管理？
□ 多人协作是否拆了核心规则与个人配置？
□ 是否所有 I/O 都有超时？
□ 是否只写了成功路径（应补失败分支）？
□ scripts/ 是否写清了调用条件与失败处理？
□ 输出是否有 schema 约束（含 additionalProperties: false）？
□ 是否做了"同事盲测"？
□ 是否有权限校验与执行日志留存？
```
