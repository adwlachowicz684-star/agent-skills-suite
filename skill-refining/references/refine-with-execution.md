## 迭代循环

```
真实使用 → 观察偏差 → 归因 → 改一点 → 复测
    ↑                                    ↓
    └────────────────────────────────────┘
```

**关键约束**：

```
□ ⭐ 每次只改 1–2 个变量——否则无法归因
□ ⭐ 改完必须复测（validate + 触发测试 + A/B）
□ ⭐ 确认失败模式是"减少"而非"转移"
   ——A 类少了 B 类多了等于没改
```

呼应 `claude-ab-loop.md`：双实例迭代，A 写 B 测。

## 从 Claude 的视角观察

**三个观察点**：

```
1. ⭐ agent 如何在真实场景中使用你的技能
   ——有没有意料之外的执行路径

2. ⭐ 对某些上下文的过度依赖
   ——它是不是每次都要你补充同一件事？
   → 那件事就该写进技能

3. ⭐ 特别关注 name 和 description 的效果
   ——该触发时没触发？不该触发时触发了？
```

**一个具体的观察方法**：

```
让 agent 复述"你现在在用哪个技能、流程是什么"
  ⭐ 对得上 → 加载成功
  ⭐ 对不上 → 加载失败或读了旧版本
```

呼应 `reload-debug.md` 与 `troubleshooting-manual.md`。

## 让 agent 自我反思

**触发条件**：agent 使用技能偏离预期时。

**做法**：

```
1. 指出偏离点（具体到第几步、输出哪里不对）
2. ⭐ 让它自己分析：哪里出了问题？是技能没写清楚，还是你没读到？
3. 把结论写回技能
```

**为什么有效**：

> ⭐ **这个过程帮你发现 agent 实际需要什么上下文，
> 而非提前猜测。**

注意边界：

```
□ 让它反思"哪里出了问题"——有效
□ ⭐ 让它给自己的输出打分——无效
   （建造者不能当审计员，见 grounding-verification.md）
```

## 提取重复模式

> ⭐ **强信号**：如果多个测试里 agent 都独立写了类似的辅助脚本
> （如每次都创建 `create_docx.py`），
> **应该把这个脚本放进 `scripts/` 让技能直接调用。**

**识别方法**：

```
□ 翻看最近几次会话，agent 是不是每次都写了同一段代码？
□ 那段代码的差异是"每次都想不一样"还是"其实都一样"？
□ ⭐ 后者就是该提取的
```

**提取后**：

```
□ 脚本进 scripts/
□ SKILL.md 里写明调用方式
□ ⭐ 脚本要有 --help 和错误处理（见 《skill-scripting》`script-engineering.md`）
```

呼应 `skill-principles.md`（**`skill-crafting`**）：
**确定性推进代码——重复即脚本。**

## 泛化而非过拟合

> ⭐ **技能要被使用无数次、面对无数种 prompt。**

**过拟合的症状**：

```
□ 训练集效果好，测试集明显差
□ ⭐ 新加的规则说不出通用理由，只是"上次那个 case 需要"
□ 技能越来越长，但覆盖面越来越窄
```

**修法**：

```
1. ⭐ 遇到顽固问题，换个隐喻或推荐不同的工作模式
   ——而不是继续加规则

2. ⭐ 解释"为什么"而非堆砌"必须"
   ——LLM 有良好的推理能力，给 why 它就能泛化

3. ⭐ 训练/测试集分割
   ——用一组调，用另一组验
```

**一条自检问句**：

```
新写的这条规则，能不能说成一条通用原则？
  ⭐ 能 → 好的改进
  ⭐ 不能 → 它是为某个 case 打的补丁，会伤害泛化
```

呼应 `eval-roles.md`（**`skill-evaluating`**）的过拟合检测。

## 什么时候该重写而不是修补

**三个信号**：

```
1. ⭐ 补丁超过 5 处，且互相之间有张力
   ——（改 A 影响 B，改 B 又影响 A）

2. ⭐ 正文超过 150 行，路由表没有可合并项了
   ——（这是物理上限，不是"再挤挤"）

3. ⭐ 失败模式从"漏掉某步"变成"整体方向不对"
   ——说明结构错了，不是内容不够
```

**重写 vs 拆分**：

```
内容太多但结构还清晰 → 拆（见 architecture-layering.md）
结构本身不对         → 重写
```

呼应 `splitting.md`：**"该拆还是该重写"的判定**。

## 一条反面经验

**不要为了省行数合并路由表的异类条目**：

```
□ 前面几轮我们为了把正文压在 150 行内，合并了多组路由行
□ ⭐ 每次合并都是可发现性的损失
□ 到第七次时已经没有可合并项了——那时该拆，不是继续挤
```

> **合并同类项是可以的；合并异类项是透支。**
