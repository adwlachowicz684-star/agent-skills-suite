## 1. ⭐ 五个信号

| 信号 | 具体表现 | 为什么是信号 |
|---|---|---|
| ⭐ **Workflow 超过 7 步** | ⭐ agent 开始跳步或混淆步骤 | ⭐ 单次上下文能稳定执行的步骤有上限 |
| ⭐ **description 用"或"连接 4+ 场景** | 路由规则本身在冲突 | ⭐ 每多一个"或"，触发判断就多一个歧义 |
| ⭐ **Quality Bar 相互矛盾** | 同时要求"简洁"和"详尽" | ⭐ 矛盾的标准意味着承担了不同任务 |
| 测试场景相互覆盖 | ⭐ 正反向测试边界模糊 | ⭐ 无法写出清晰的测试用例 |
| 文件接近 500 行 | 维护成本急剧上升 | 官方建议控制在 500 行以内 |

**真实案例**：膨胀版 `article-review` 命中全部 5 个信号——
稳定版 6 步，膨胀版 15 步，同时在做审稿、风格分析、去 AI 味、排版建议、润色**五个不同认知动作**。

> ⭐ "不是某个步骤写错了，而是这个技能已经不再是'一个能力'。"

## 2. ⭐ 决策流程

```
检查 5 个信号
  ├─ 0–1 个  → 技能健康，维持现状
  ├─ ⭐ 2–3 个 → ⭐ 先试缩窄
  │              ├─ 缩窄后信号消失 → 维持单技能
  │              └─ ⭐ 缩窄后信号仍在 → 拆
  └─ 4–5 个  → 直接拆
```

> ⭐ **"先试缩窄"这一步最容易被跳过，也最有价值**：
> **拆分有成本**——拆完要协调多个技能间的路由、维护更多文件、管理更复杂的测试。

**三种缩窄方法**：

```
① 合并 Workflow 步骤（⭐ 7 步是上限，不是目标）
② 从 description 去掉次要触发词，只保留核心
③ 但去掉的功能需要另一个技能来承接
```

> ⭐ 诚实的观察：**缩窄可以缓解膨胀，但不能完全解决它。
> 当需要承担 5 种不同认知动作时，缩窄只是把问题推到了别处。**

## 3. ⭐ 按认知动作拆，不按功能清单切

```
❌ 按功能清单切：审稿 / 风格 / 排版 / 润色（四个并列项）
✅ ⭐ 按认知动作拆：每个技能回答一个独立问题
```

**判据**：

```
⭐ "这个技能能不能一个人、不叫别人，独立跑完？"
```

**按"能回答一个独立问题"切**（实例）：

```
玫瑰图回答方向  ← 可独立需要
演化图回答时序  ← 可独立需要
→ 所以值得单独存在
```

**拆分收益**（实测）：11 个技能拆完之后，**多数场景只需要读其中 1~2 个**。

## 4. 两个极端

**极端一：太粗的"巨无霸"**

```
一个 data-processor 既读库、又清洗、又画图、还发邮件

① ⭐ 边界模糊  —— 一个"清洗数据"的小请求，要加载涵盖四种任务的说明书
                   其中三分之三是噪声
② ⭐ 路由漂移  —— 用户只说"查这张表"，巨无霸和专门的查询技能同时进候选
③ 难测难改    —— 任何一段出错都难定位，加个参数牵一发动全身
```

> ⭐ **形象判断信号**：
> **如果技能名字里出现了"和 / and"，或者同一份正文里长出几条完全不相干的执行分支，它就太大了。**

**极端二：太碎的"碎片"**

```
把"开客厅灯""开卧室灯""开厨房灯"各做成一个技能
```

后果：

```
· 命名噪声让路由更难，相似技能彼此抢触发
· ⭐ 上下文里列几十个几乎同义的描述，反而稀释了真正的信号
· ⭐ 更隐蔽的：⭐ 过度拆分把本该在技能内部闭环的逻辑，
     强行推到了上层编排——⭐ agent 每做一步都要重新决策"下一步调哪个"
     链路更长、更易断
```

**黄金粒度**：

```
⭐ 单一职责 + 可组合 + 强契约

✅ 做"灯光控制"，用"房间 + 动作 + 亮度"三个输入覆盖所有房间
❌ 做"开客厅灯"
```

## 5. ⭐ 什么时候别拆

```
① ⭐ 一次性脚本别拆——只跑一次、不会再用的代码，写成技能纯属浪费
   ⭐ 技能的价值来自反复调用
② ⭐ 拆得比"一件事"还细就没意义
   ⭐ 如果两个技能永远同时出现、且中间没有独立价值，那它们本来就该是一个
③ ⭐ Agent 太多也会乱
   每个 Agent 都要维护一套路由表、一套纪律、一套汇总逻辑——有维护成本
```

**配套的三条反模式**（编排视角）：

```
① 把什么都塞进一个技能    → 上下文撑爆 + 规则互相干扰
② ⭐ 让 Agent 亲自下场干活 → 技能变摆设；同样逻辑写两遍，改一处漏一处
   ⭐ 正解：Agent 只做拆解、路由、排计划、守纪律
③ ⭐ 技能之间互相 import   → 改一处崩一片，没法单独测
   ⭐ 正解：走数据契约——约定好文件格式，谁都不依赖谁的代码
```

> ⭐ **分工判据**：
> **技能回答"这件事怎么做"，Agent 回答"这些事按什么顺序、什么规矩做"。**

## 速查

```
五信号：
□ ⭐ Workflow >7 步（开始跳步）
□ ⭐ description 用"或"连 4+ 场景
□ ⭐ Quality Bar 自相矛盾（既简洁又详尽）
□ 测试边界模糊
□ 接近 500 行

决策：
□ 0-1 → 维持
□ ⭐ 2-3 → 先缩窄（合并步骤 / 去掉次要触发词）
□ ⭐ 缩窄后信号仍在 → 拆
□ 4-5 → 直接拆

拆法：
□ ⭐ 按认知动作，不按功能清单
□ ⭐ 判据：能不叫别人独立跑完吗
□ ⭐ 按"能回答一个独立问题"切

两极端：
□ 名字含"和/and" = 太大
□ ⭐ 永远同时出现 = 本该是一个
□ 黄金粒度：单一职责 + 可组合 + 强契约

□ ⭐ 一次性脚本别拆
□ ⭐ 技能间不写代码依赖，走数据契约
□ ⭐ Agent 只拆解/路由/排计划/守纪律
□ 分工：技能="怎么做"，Agent="按什么顺序做"
```

**一句话**：

> ⭐ **名字里出现"和"，或者两条互不相干的执行分支——它就太大了。**
