# 优化工作流

> 本流程处理的是**技能已存在**之后的改动。
> 每一步都可跳过，但**第 2 步（基线）和第 6 步（复测）不可跳**。

## 六步流程

### 步骤 1：定位问题类型

```
□ 不触发 / 乱触发        → 路由问题，先去 skill-evaluating 测
□ 触发了但跑偏           → 可能是上下文污染，考虑隔离执行
□ 内容太长               → 结构拆分
□ 太耗 token             → 修剪 / 瘦身
□ 输出格式不稳           → 输出契约（见 skill-authoring 的 output-contract.md）
□ 要给别人用 / 换语言     → 翻译
□ 要发出去               → 打包发布
□ 要长期维护             → 版本演进
```

> ⚠️ **不确定的先测**。
> 优化一个"你以为是 A 其实是 B"的问题，是最常见的浪费。

### 步骤 2：跑基线（不可跳过）

```bash
python scripts/validate_skill.py ./my-skill      # 结构
python scripts/estimate_tokens.py ./my-skill     # 成本
```

**必须记录**：

```
□ SKILL.md 行数
□ description 字符数
□ 启动常驻 token
□ references 份数与按需总量
□ validate 的错误/警告数
□ 触发率（跑 3 次的均值——见 skill-evaluating 的 triggering.md）
```

> ⭐ **没有改动前的数字，就无法证明改动有效。事后补的是假数字。**

### 步骤 3：确认改动会生效

> ⚠️ 改完不生效是最常见的挫败——
> **90% 是因为加载阶段就失败了，但错误被静默吞掉。**

```
□ name / description 是启动时读的 → 改了必须重载
□ 纯正文改动 → 热重载即可
□ 涉及工具策略 / System Prompt 注入逻辑 → 必须开全新会话
□ 验证方法：改完让它复述"你那个技能现在的流程是什么"
```

详见 `skill-evaluating` 的 **`skill-evaluating` 的 `reload-debug.md`**。

### 步骤 4：定改动类型并只改一类

> ⭐ **一次只改一类变量**——
> 同时改结构和措辞，失败时无法归因，下次还得重来。

### 步骤 5：执行

按对应详解执行（见主文件路由表）。

### 步骤 6：复测与回归（不可跳过）

```
□ validate 必须 0 错误
□ token 数字必须下降或持平
□ 老问题没回来
□ ⭐ 也没有"转移"成新问题（A 类少了 B 类多了 = 等于没改）
```

## 四类改动的分工

| 改动类型 | 信号 | 详解 | 验证方式 |
|---|---|---|---|
| **结构拆分** | >300 行、description 出现长分支条件、**迭代 10 次仍修不好** | `architecture-layering.md` · `splitting.md` | 路由是否仍能命中每个子技能 |
| **内容修剪** | no-op 测试通过的句子（删了行为不变） | `pruning.md` | 删完行为是否真的没变 |
| **瘦身** | 启动常驻占比高、references 未按需加载 | `context-budget.md` | estimate_tokens 数字 |
| **路由调整** | 欠触发 / 过触发 / 技能偷窃 | `skill-evaluating` 的 `triggering.md` | 触发率（跑 3 次） |

> ⚠️ **"迭代 10 次还修不好某个失败模式"是架构信号，不是措辞信号。**
> 这时候改 prompt 是打地鼠——该拆了。

## 改动前 vs 改动后

**汇报模板**：

```
## 改动摘要
类型：结构拆分
依据：description 里出现了 3 层分支条件（拆分信号）

## 数字对比
| 指标 | 前 | 后 |
|---|---|---|
| SKILL.md 行数 | 412 | 128 |
| 启动常驻 token | 1,240 | 257 |
| references 份数 | 2 | 6 |
| validate | 0 错误 3 警告 | 0 错误 0 警告 |

## 回归结论
- 老问题（输出格式不稳）：已解决
- 新问题检查：路由命中率 3 次均值 92%，与拆分前持平 ✅

## 未改动部分
- Gotchas 章节：原样保留（最高信号，不可删）
```

## 什么时候该停止优化

> ⭐ **优化是有尽头的，过度优化会开始损害可发现性。**

**停止信号**：

```
□ no-op 测试全部通过（剩下的句子删了行为会变）
□ 启动常驻已降到 200–400 token 区间
□ 路由表再合并就会丢失可发现性
□ 拆到 3–7 个子技能的中位区间
□ ⭐ 继续改需要牺牲 Gotchas 或示例
```

> ⚠️ **一个具体的红线**：
> **SKILL.md 已经压缩到 150 行以内就别再靠合并路由行腾空间了**——
> 合并是可发现性的损失，连续做会真正伤害路由质量。
> 该做的是**再拆一个技能**，而不是继续挤。

## 自查

```
□ 是否记录了改动前的基线数字？
□ 是否一次只改了一类变量？
□ 改完是否验证了真的加载生效？
□ validate 是否 0 错误？
□ token 是否下降或持平？
□ 是否确认老问题没回来、也没转移？
□ 是否保留了 Gotchas？
□ 是否到了该停止的信号（而不是继续挤）？
```
