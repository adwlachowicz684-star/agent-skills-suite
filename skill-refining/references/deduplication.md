# 去重：同一件事为什么会有三份

> ⭐ **同一份内容出现在三个地方时，
> 改一次要改三处，而漏改的那处会静默产生错误结果。**

## 四种重复

**① 同一规则写在多份技能里**

```
❌ 三个技能都写了"不要提交 .env"
✅ 写进 CLAUDE.md 或一份共享的 references
```

**② 技能与 CLAUDE.md 重复**

```
❌ 命名约定在 CLAUDE.md 和技能里各一份
```

**③ 技能与 MCP 工具描述重复**

```
❌ 技能的指令复述了工具文档里已有的内容
```

**④ ⭐ 同一份常量散落多处**

```
❌ 品牌色值出现在 brand-ppt / brand-doc / brand-excel 三份技能里
```

> 第 ④ 条最危险，因为**它是静默的**：
> 改了其中两处，第三处继续产出不合规的结果，而且没人发现。

## 去重的判据

不是所有重复都要消除。问三个问题：

```
① ⭐ 这两处会一起改吗？
   会 → 应该合并
   不会 → 可以保持分开（它们只是现在看起来一样）

② 删掉其中一处，会有人受影响吗？

③ ⭐ 它们各自服务的场景不同吗？
```

> ⭐ **第 ① 条是核心**：
> **"看起来一样"不是重复，"必须一起改"才是重复。**

举例：

```
两个技能都要求"输出 JSON"
→ 这只是巧合一致，不需要合并
→ ⭐ 但如果你决定改成 YAML，两处都要改 → 那它就是重复
```

## 三种处理方式

**① 上移到共享层**

```
→ CLAUDE.md / AGENTS.md（每轮都需要的）
→ 一份共享的 references（按需的）
```

适用：**多个技能都需要，且内容稳定**。

**② 抽取为单一来源，其他引用**

```
brand-tokens.md   ← 唯一来源
brand-ppt.md      → 引用它
brand-doc.md      → 引用它
```

适用：**常量、术语表、阈值表**。

> ⭐ 注意引用要一层深（见 `skill-structuring` 的 `reference-routing.md`）——
> 引用链不能超过一层。

**③ 合并技能**

```
brand-ppt + brand-doc + brand-excel → brand-guidelines
```

适用：**它们本来就是同一件事的几个方面**。

⚠️ 但合并要有闸门：**合并后的 eval 必须与被取代的表现相当**
（见 `skill-count-limit.md`）。

## 怎么扫描

不需要靠记忆，几类可机械查：

```bash
# 常量：同一个 hex 色值出现在几个文件
grep -rn "#0066CC" skill-*/references/

# 规则：同一句话出现在几处
grep -rn "不要提交 .env" skill-*/ 

# 路径：同一路径被硬编码几处
grep -rn "scripts/" skill-*/SKILL.md
```

> ⭐ 更实用的做法：
> **把"共享常量"集中到一个文件，
> 然后用脚本检查是否有技能里出现了散落的常量值。**

（呼应 `brand-guidelines.md`：色值该有单一来源。）

## 一个警告

> ⚠️ **过度去重会造成"远距离依赖"。**

```
把所有常量抽到一个文件
→ 每个技能都要读它
→ ⭐ 它变成了一个所有人都依赖的单点
```

判据：

```
□ 这个常量被几个技能用？
  1–2 个 → 各自持有更简单
  3+ 个  → ⭐ 值得抽取
```

> **两份之间的"重复"成本，通常低于引入共享层的协调成本。**

## 自查

```
[ ] ⭐ 有没有常量散落在多个技能里？（grep 一下色值/阈值/路径）
[ ] 技能里有没有复述 CLAUDE.md 已有的规则？
[ ] ⭐ 技能里有没有复述工具文档已有的内容？
[ ] 共享内容有单一来源吗？
[ ] ⭐ 引用链没有超过一层？
[ ] 合并前跑过 eval 对照吗？
[ ] ⭐ 有没有"为了去重而去重"（引入不必要共享层）？
```

## 一条延伸

> ⭐ **去重的本质是"找出必须一起变化的东西"。**

这也是为什么 `team-workflow.md` 强调
**"SKILL.md 与数据文件分离"**——
how 变和 what 变的频率完全不同，
把它们放一起，就会被迫一起改。

**按变化频率分组，比按内容相似度分组更有用。**
