## 1. ⭐⭐⭐ 三种占位符形式

```
① ⭐⭐⭐ $ARGUMENTS        —— 全部参数（技能名后面的所有文字）
② ⭐⭐⭐ $ARGUMENTS[N]      —— 按位置取，从 0 开始
③ ⭐⭐⭐ $N                 —— ②的简写：$ARGUMENTS[0] ≡ $0
```

```
name: migrate-component
description: Migrate a component from one language to another

Migrate the $0 component from $1 to $2. Preserve all existing behavior and tests.

/ migrate-component SearchBar JavaScript TypeScript
→ "Migrate the SearchBar component from JavaScript to TypeScript."
```

> ⭐⭐⭐⭐⭐ 注意⭐ 一个⭐ 容易记错的⭐ 点：⭐ **`$0` 是第一个参数，不是 `$1`**
> （这⭐ 与⭐ shell 脚本的⭐ `$1` ⭐ 相反，⭐⭐⭐⭐ ⭐⭐⭐ 而⭐ 恰恰是⭐ shell 习惯⭐ 会让人写错）。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这一条⭐ 与 `argument-substitution.md` 里⭐ 那条⭐ 完全一致——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 那里⭐ 是从⭐ "shell 示例代码会被替换"⭐ 的角度说的，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 这里⭐ 是从⭐ "取第几个"⭐ 的角度说的。

## 2. ⭐⭐⭐⭐⭐ 没有占位符时也会收到参数

> ⭐⭐⭐⭐⭐ **"⭐ 如果你⭐ 带参数⭐ 调用了一个技能，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 但⭐ 技能正文里⭐ 没有任何占位符⭐ 接收到它，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ Claude Code ⭐ 会在⭐ 技能内容末尾⭐ 追加 ⭐ `ARGUMENTS:`，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 这样⭐ Claude ⭐ 仍然⭐ 能看到⭐ 你打了什么。"**

这意味着"忘了写占位符"不会静默丢参数——但内容会挂在末尾。

**三条细节差异**（这是本轮最值得记的一组）：

```
① ⭐⭐⭐⭐ 位置占位符 ⭐ 在其位置上 ⭐ 没有参数时 → ⭐⭐⭐⭐⭐ ⭐⭐⭐ 原样保留为字面文本
                                ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 且⭐ 不算作"接收到了参数"
                                ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ → ⭐⭐⭐⭐⭐ ⭐⭐⭐ 仍会触发末尾追加 ARGUMENTS:

② ⭐⭐⭐⭐⭐ 命名占位符 ⭐ 即使 ⭐ 该位置无参数 → ⭐⭐⭐⭐⭐ ⭐⭐⭐ 也算"接收到了"
                                ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 因为⭐ 它⭐ 展开为⭐ 空字符串

③ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 推论：⭐⭐⭐⭐⭐ ⭐⭐⭐ **想让"无参数时不触发末尾追加"，用命名占位符**
```

> ⭐⭐⭐⭐⭐ 第 ① 条⭐ 解释了⭐ 一个⭐ 常见的⭐ 诡异现象：
> ⭐⭐⭐⭐⭐ **技能正文里⭐ 出现了⭐ 字面量 `$1`**——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 那⭐ 不是替换失败，⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 而是⭐ "该位置没有参数"⭐ 的⭐ 设计行为。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 这⭐ 与 `argument-substitution.md` 那条"参数不足时 \$2 会原样留下，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 模型会去猜它是什么"⭐ 是⭐ 同一件事，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 而这里⭐ 补上了⭐ 精确的⭐ 判定规则。

## 3. ⭐⭐⭐⭐⭐ 多技能同载（stacking）

> ⭐⭐⭐⭐⭐ **"⭐ 你也可以在⭐ 一条消息的⭐ 开头 ⭐ 叠加⭐ 多个技能。"**

```
/ write-tests / fix-issue 123
→ ⭐⭐⭐⭐⭐ 两个技能都被加载
→ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 尾随文字 123 ⭐ 作为 $ARGUMENTS ⭐ 传给 ⭐ 每一个
```

**四条硬规则**（每一条都是此前没写过的）：

```
① ⭐⭐⭐⭐⭐ 最多展开 ⭐ 第一个 + ⭐⭐⭐⭐ 其后最多 5 个（共 6 个）
② ⭐⭐⭐⭐⭐ 遇到第一个"不是内联用户可调用技能"的 token 就停止展开
③ ⭐⭐⭐⭐⭐ 该 token 及其之后的所有内容 → ⭐⭐⭐⭐⭐ ⭐⭐⭐ 成为⭐ 每一个已展开技能的⭐ 参数文本
④ ⭐⭐⭐⭐⭐ 停止的具体情形：
   · ⭐⭐⭐⭐⭐ 以 fork 子代理运行的技能（如 ⭐ /code-review，v2.1.218 起）
   · ⭐⭐⭐⭐ 参数本身可能以斜杠命令开头的技能（如 ⭐ /loop）
```

> ⭐⭐⭐⭐⭐ 第 ④ 条⭐ 第一条⭐ 尤其⭐ 重要，⭐⭐⭐⭐⭐ ⭐⭐⭐ 因为它⭐ 与⭐ 我们已有的⭐ 一条⭐ 刚好接上：
> ⭐⭐⭐⭐⭐ **`context: fork` 的技能⭐ 在 v2.1.218 之前⭐ 是内联运行的、可以叠加；
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 之后⭐ 改为 fork 子代理，⭐⭐⭐⭐⭐ ⭐⭐⭐ 于是⭐ 会终止叠加。**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ **这是一条⭐ 版本相关的⭐ 行为变化——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 同一个技能，⭐⭐⭐⭐⭐ ⭐⭐⭐ 在不同版本上⭐ 组合能力不同。**
>
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 另外⭐ 还有一条⭐ 历史变更：
> ⭐⭐⭐⭐ **v2.1.199 之前，⭐ 只有第一个技能被加载，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 而 ⭐ `/fix-issue 123` ⭐ 会⭐ 作为字面文本⭐ 成为它的参数。**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 也就是说：⭐ **"叠加"⭐ 这个能力⭐ 本身⭐ 是较新的，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 老版本上⭐ 多写几个技能名⭐ 会⭐ 全部变成⭐ 一段奇怪的参数。**
>
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 与⭐ 已有知识的⭐ 对接：
> ⭐⭐⭐⭐⭐ **`skill-chaining-composition.md` 说"后加载的不覆盖先加载的，所有活跃技能的约束同时生效"**——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 本条⭐ 正是⭐ 那个"同时活跃"⭐ 状态的⭐ 具体产生方式之一，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 并且⭐ 给出了⭐ 一个硬上限（6 个）。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 顺带一提：⭐⭐⭐⭐⭐ **这个上限（6）比⭐ 我们建议的⭐ "单任务挂载 ≤3"
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐ 宽松得多——⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 能这么做 ≠ 该这么做。**

## 4. ⭐⭐⭐⭐⭐ \`!\` 动态上下文注入

```
name: pr-summary
description: Summarize changes in a pull request
context: fork
agent: Explore
allowed-tools: Bash(gh *)

Pull request context
PR diff:       !gh pr diff
PR comments:   !gh pr view --comments
Changed files: !gh pr diff --name-only

Your task: Summarize this pull request...
```

> ⭐⭐⭐⭐⭐ **"⭐ `!` 语法⭐ 在⭐ 技能内容⭐ 被发送给 Claude ⭐ 之前 ⭐ 运行 shell 命令。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 命令输出⭐ 替换该占位符，⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐ 所以 Claude 收到的是⭐ 真实数据，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 而不是那条命令本身。"**

**六条精确规则**（全部是硬知识）：

```
① ⭐⭐⭐⭐⭐ 替换⭐ 只 ⭐ 对原始文件 ⭐ 跑一遍（Substitution runs once over the original file）
② ⭐⭐⭐⭐⭐ 命令输出⭐ 作为纯文本插入，⭐⭐⭐⭐⭐ ⭐⭐⭐ 不会⭐ 被再次扫描⭐ 查找 `!` 占位符
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ → ⭐⭐⭐⭐⭐ ⭐⭐⭐ 一条命令⭐ 不可能⭐ 输出一个⭐ 供后续第二轮展开的⭐ 占位符
③ ⭐⭐⭐⭐⭐ 行内形式⭐ 仅在 ⭐ `!` 位于⭐ 行首 ⭐ 或 ⭐ 紧跟空白字符之后 ⭐ 时被识别
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 若 `!` 紧跟另一个字符（如 `KEY=!...`）→ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 不识别
④ ⭐⭐⭐⭐⭐ 版本要求：v2.1.228 或更高
⑤ ⭐⭐⭐⭐⭐ 从 claude.ai 账户同步的技能 → ⭐⭐⭐⭐ ⭐⭐⭐ **不会在你的机器上运行这些命令**
⑥ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 这条⭐ 与⭐ `$ARGUMENTS` ⭐ 是⭐ 两套⭐ 独立的机制
```

> ⭐⭐⭐⭐⭐ 第 ② 条⭐ 是⭐ 一条⭐ 典型的⭐ 安全设计：
> ⭐⭐⭐⭐⭐ **不允许⭐ 命令输出⭐ 再产生⭐ 新的占位符**——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐⭐ 否则⭐ 一个⭐ 被注入的⭐ 输出⭐ 就能⭐ 诱导⭐ 执行⭐ 另一条命令
> （⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 正是 `unicode-injection-defense.md` 那类⭐ 二次注入的⭐ 变体）。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这⭐ 与⭐ `argument-substitution.md` 的
> "⭐ 替换在加载时执行，⭐⭐⭐⭐⭐ ⭐⭐⭐ 模型读到之前⭐ 就已经替换完了"⭐ 是⭐ 同一族：
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ **替换发生在模型看见之前，⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 因此⭐ 是⭐ 不可被模型审查的。**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 推论：⭐⭐⭐⭐⭐ **这类"加载前执行"的机制
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 必须⭐ 在⭐ 信任边界内⭐ 谨慎使用**（尤其第 ⑤ 条指出，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 同步来的技能⭐ 不会在你机器上跑——⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 反过来说，⭐⭐⭐⭐⭐ ⭐⭐⭐ 本地技能会）。
>
> ⭐⭐⭐⭐⭐ 第 ③ 条⭐ 也⭐ 值得单独记：⭐ **`KEY=!value` 里的 `!` 不会被识别**——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这⭐ 是⭐ 一个⭐ 极窄的⭐ 语法细节，⭐⭐⭐⭐⭐ ⭐⭐⭐ 但⭐ 它⭐ 能解释
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ "为什么这一行没有被替换"⭐ 这类⭐ 排障问题。

## 速查

```
□ ⭐⭐⭐ 三种形式：$ARGUMENTS（全部）· $ARGUMENTS[N] · $N（≡$ARGUMENTS[N]，从 0 开始）
   ⭐⭐⭐⭐ ⭐⭐⭐ ⚠️ $0 是第一个参数，不是 $1（与 shell 习惯相反，最容易写错）
□ ⭐⭐⭐⭐⭐ 无占位符也会收到：末尾追加 `ARGUMENTS:`（不静默丢失）
   ⭐⭐⭐⭐⭐ 位置占位符无参数 → 原样留字面文本 + ⭐⭐⭐⭐⭐ ⭐⭐⭐ 仍算"没接收到"→仍追加 ARGUMENTS:
   ⭐⭐⭐⭐⭐ 命名占位符无参数 → 展开为空串 + ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 算"已接收"→不追加
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 推论：⭐⭐⭐⭐⭐ ⭐⭐⭐ 想避免末尾追加用命名占位符
□ ⭐⭐⭐⭐⭐ 叠加：/write-tests /fix-issue 123 → ⭐ 两个都加载，123 传给每一个
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ 最多 第一个+5（共6）· ⭐⭐⭐⭐⭐ ⭐⭐⭐ 遇非"内联用户可调用" token 停止
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 停止项：⭐⭐⭐⭐⭐ fork 子代理技能（/code-review，v2.1.218 起）· /loop 类
   ⭐⭐⭐⭐ 版本：v2.1.199 前只有第一个加载，其余变字面参数
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 能叠加 6 个 ≠ 该挂 6 个（建议单任务 ≤3）
□ ⭐⭐⭐⭐⭐ `!` 注入：发送前跑 shell，输出替换占位符，模型收到真实数据而非命令
```

**一句话**：

> ⭐⭐⭐⭐ **`$0` 才是第一个参数；位置占位符无参时会原样留字面文本并仍触发末尾追加 `ARGUMENTS:`，而命名占位符展开为空串就算"已接收"；多技能可在一条消息开头叠加（第一个 + 最多 5 个，遇到 fork 子代理类技能就停止），而 `!` 注入会在发送前跑 shell、输出不再二次扫描以防注入——两者共同的底层事实是：替换发生在模型看见之前，它看不见也审查不了。**
