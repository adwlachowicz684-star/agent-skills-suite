## 1. ⭐⭐⭐⭐ 让 Claude 把描述复述回来

> ⭐⭐⭐⭐⭐ **调试手法：⭐⭐⭐⭐ 问 Claude
> ⭐⭐⭐⭐⭐ ⭐ "When would you use the [skill name] skill?"
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ Claude 会⭐ 把描述原样复述回来。
> ⭐⭐⭐⭐⭐ ⭐⭐ ⭐ 根据⭐ 它复述出来的内容⭐ 缺什么，去改描述。**

> ⭐⭐⭐⭐⭐ 这是一条⭐⭐ ⭐ 零成本、⭐⭐⭐ ⭐ 极准、⭐⭐⭐⭐ ⭐ 且几乎没人用的技巧。
> 它的价值在于⭐⭐⭐⭐⭐ **把你看到的文件，换成⭐ 模型实际读到的东西**：
> ```
> 你以为你写的是："处理 PDF 法律合同"
> 模型复述出来是："Processes documents"
> → ⭐⭐⭐⭐⭐ ⭐ 你立刻知道它读的是⭐ 另一个文件（或旧版本）
> ```
>
> ⭐⭐⭐⭐⭐ 它能一次区分⭐ 三种完全不同的故障：
> ```
> ① 复述出的内容⭐ 根本不是你写的 → ⭐⭐⭐⭐ ⭐ 加载的不是这个文件（同名覆盖/缓存）
> ② 复述出的内容⭐ 对但太笼统     → ⭐⭐⭐ 描述本身不够具体
> ③ 复述正确但⭐ 仍然不触发       → ⭐⭐⭐⭐ ⭐ 有更强的竞争者在赢（见第 5 节）
> ```
>
> ⭐⭐⭐⭐ 与 `nested-scope-discovery.md` 的
> "无法判断哪个版本生效 → 直接问 What skills are available?"
> ⭐⭐⭐⭐ 是⭐ 同一手法的两个问法：
> ⭐⭐⭐ **一个问"有哪些"，一个问"你会在什么时候用这个"**——
> ⭐⭐⭐⭐ 后者更精准，因为它⭐ 直接暴露了⭐ 触发判据。

**同一来源给出的另一个排查角度**（也值得记）：

```
⭐⭐⭐ 两台机器上行为不同 → ⭐ 先 `claude --version` 对比（5 秒）
⭐⭐⭐ 版本一致但仍不同 → ⭐⭐ 怀疑⭐ 缓存状态（~/.claude/state/ 可能有陈旧条目），
                        ⭐⭐ 重启可清
```

> ⭐⭐⭐ 这与我们已有的"改了参数默认值，执行时用的还是旧值——平台缓存了技能描述"
> ⭐⭐⭐ 是⭐ 同一现象，⭐⭐⭐⭐ 但这里给了⭐ 具体路径和⭐ 处置（重启）。

## 2. ⭐⭐⭐⭐ 触发太频繁的三解法

```
① ⭐⭐⭐⭐ 加否定触发（⭐⭐⭐⭐⭐ 并⭐ 指向替代技能）
   "Advanced data analysis for CSV files. Use for statistical modeling,
    regression, clustering. ⭐⭐⭐⭐⭐ Do NOT use for simple data exploration
    (use data-viz skill instead)."

② ⭐⭐⭐⭐ 更具体
   ❌ "Processes documents"
   ✅ "Processes PDF legal documents for contract review"

③ ⭐⭐⭐ 澄清范围
   "PayFlow payment processing for e-commerce. ⭐⭐ Use specifically for
    online payment workflows, ⭐⭐⭐⭐ not for general financial queries."
```

> ⭐⭐⭐⭐⭐ 三解法与我们已有的 `trigger-tuning-loop.md`
> （误触发：加反触发、点名排除、收窄）⭐⭐ 完全一致，
> ⭐⭐⭐⭐ 但这里⭐ 每条都给了⭐ 可照抄的⭐ 完整句式——
> ⭐⭐⭐⭐⭐ 尤其第 ① 条那个⭐⭐⭐ `(use data-viz skill instead)`
> ⭐⭐⭐⭐⭐ 是⭐⭐⭐⭐⭐ "禁令必须带替代方案"的⭐ 又一次完美实例
> （这是该判据的⭐⭐⭐⭐ 第七个来源，且⭐ 句式最完整）。

## 3. ⭐⭐⭐⭐ 指令不被遵循的四个原因

```
① ⭐⭐⭐ 指令太啰嗦
   → ⭐ 保持简洁 · ⭐⭐ 用要点与编号列表 · ⭐⭐⭐ 把详细参考移出到单独文件

② ⭐⭐⭐⭐ 指令被埋没了
   → ⭐⭐⭐⭐ ⭐ 关键指令放⭐ 顶部 · ⭐⭐ 用 ## Important / ## Critical 标题
   → ⭐⭐⭐⭐ ⭐⭐⭐ ⭐ 必要时⭐ 重复关键点

③ ⭐⭐⭐⭐⭐ 措辞含糊
   ❌ "Make sure to validate things properly"
   ✅ "CRITICAL: Before calling create_project, verify:
       - Project name is non-empty
       - At least one team member assigned
       - Start date is not in the past"

④ ⭐⭐⭐⭐ "模型犯懒"
   → ⭐⭐⭐ 加显式鼓励："Take your time" / "Quality is more important than speed"
   ⭐⭐⭐⭐⭐ ⭐ 但注意：⭐⭐⭐⭐⭐ ⭐ 加在⭐ 用户提示里⭐ 比加在 SKILL.md 里⭐ 更有效
```

> ⭐⭐⭐⭐ 第 ② 条⭐ 是我们"开头是黄金位置"结论的⭐⭐⭐⭐ 第五个来源，
> ⭐⭐⭐⭐⭐ 且⭐ 第一次给出了⭐ 具体的落地手法：
> ⭐⭐⭐⭐ **用 `## Critical` 这样的⭐ 显式标题，⭐ 并在必要时⭐ 重复关键点。**
> ⭐⭐⭐⭐⭐ 与我们已有的"关键规则在两端都写一遍"⭐ 完全吻合。
>
> ⭐⭐⭐⭐⭐ 第 ③ 条那组对照⭐ 值得单独抄——
> ⭐⭐⭐⭐⭐ 它把"要具体"落成了⭐ 一个可检查的形式：
> ⭐⭐⭐⭐ **每条验证项都能被⭐ 机械判定**（非空 / ≥1 / 不在过去）。
> ⭐⭐⭐⭐⭐ 这与 `assert-on-environment.md` 的
> "断言要打在环境状态上（版本号 == 1.42.0）"
> ⭐⭐⭐⭐⭐ ⭐ 是⭐ 同一条原则在⭐ 提示措辞层面的应用。
>
> ⭐⭐⭐⭐⭐ 第 ④ 条那个限定⭐ 最容易被忽略：
> ⭐⭐⭐⭐ ⭐ "加在用户提示里比加在 SKILL.md 里更有效"。
> ⭐⭐⭐⭐⭐ 这说明⭐ **SKILL.md 的指令权重⭐ 低于⭐ 用户当轮输入**——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 与 `priority-override-layers.md` 的
> "临时 Prompt > 技能内置规则 > 全局 Rule" ⭐⭐⭐⭐⭐ ⭐ 完全同源，
> ⭐⭐⭐⭐ ⭐ 且⭐ 这是第二次独立确认。

**另一个更有力的做法**（同一来源推荐）：

> ⭐⭐⭐⭐⭐ **"对于⭐ 关键验证，⭐⭐⭐⭐⭐ ⭐ 考虑⭐ 打包一个脚本⭐ 用程序执行检查，
> ⭐⭐⭐⭐⭐ ⭐ 而不是⭐ 依赖语言指令。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 代码是确定的；语言的解释不是。"**

> ⭐⭐⭐⭐⭐⭐ 这是"确定性判断要用确定性机制承载"的
> ⭐⭐⭐⭐⭐⭐ ⭐⭐⭐ **第七个独立来源，且措辞最干净**
> （"Code is deterministic; language interpretation isn't."）。
> ⭐⭐⭐⭐⭐ ⭐ 官方还指明：⭐ Office 系列技能就是这个模式的⭐ 现成范例。

## 4. ⭐⭐⭐ 大上下文与"新鲜会话好用、中途失效"

```
症状：⭐⭐⭐ 技能在⭐ 新鲜会话里好用，⭐ 中途失效
原因：⭐⭐⭐⭐ ⭐ 几乎肯定是⭐ 正文长度导致的截断——
     ⭐⭐⭐⭐ 随着会话变长，⭐ 加载一份很长的 SKILL.md
     ⭐⭐⭐⭐ ⭐ 会把当前这轮⭐ 推过模型的上下文上限
修法：⭐⭐⭐ ⭐ 把正文削到 ⭐ 1,500 词以下，
     ⭐⭐⭐⭐ 或⭐ 把参考材料拆成⭐ 按需加载的兄弟文件
```

> ⭐⭐⭐ 这与 `three-stages-discovery-activation-execution.md` 的
> "真失忆 vs 假失灵"⭐⭐ 是⭐ 同一症状的⭐ 两种根因：
> ```
> · 那份讲的是：被压缩挤出去了（真失忆）／模型选了别的路径（假失灵）
> · ⭐⭐⭐⭐ 这里讲的是：⭐⭐⭐⭐⭐ ⭐ 根本没能完整加载进来（截断）
> ```
> ⭐⭐⭐⭐⭐ **三者诊断方式不同**：
> ```
> 重新调用一次 → 回来了 = 真失忆；没回来 = 假失灵
> ⭐⭐⭐⭐⭐ ⭐ 而"新鲜会话好用"这个⭐ 前兆本身，⭐⭐⭐ 就是⭐ 截断的⭐ 特征信号
> ```
> ⭐⭐⭐⭐ 所以⭐⭐⭐⭐ **"在开头几轮好用、后面不行"应⭐ 首先怀疑长度**，
> ⭐⭐⭐⭐ 而⭐ 不是⭐ 先去改描述。

## 5. ⭐⭐⭐ 两类排查的分工

| 症状 | ⭐ 首先怀疑 | 用什么文档 |
|---|---|---|
| **完全不出现** | ⭐⭐⭐ 文件层（目录/文件名/YAML/BOM）· ⭐⭐ 嵌套作用域 | `nine-checks-not-working.md` · `nested-scope-discovery.md` |
| **出现但不触发** | ⭐⭐⭐ 描述 · ⭐⭐⭐⭐ 竞争者更强 | 本份第 1、2 节 · `trigger-tuning-loop.md` |
| **触发但行为不对** | ⭐⭐⭐⭐ 指令被埋没/含糊 · ⭐⭐ 权限不足 · ⭐ 模型 pin | 本份第 3 节 |
| **开头好、后面不行** | ⭐⭐⭐⭐⭐ ⭐ 正文长度截断 | 本份第 4 节 |

> ⭐⭐⭐⭐ 这份文档补的是⭐ 后三类；
> ⭐⭐⭐ 第一类见 structuring。⭐⭐ 两者⭐ 不重叠。

## 速查

```
□ ⭐⭐⭐⭐⭐ 零成本神技：问 "When would you use the [skill name] skill?"
   ⭐⭐⭐⭐⭐ Claude 会把描述原样复述 → ⭐⭐ 根据缺什么去改
   ⭐⭐⭐⭐⭐ 一次区分三种故障：
     ① 复述的不是你写的 → ⭐ 加载的不是这个文件（同名覆盖/缓存）
     ② 复述对但太笼统   → 描述不够具体
     ③ 复述对却不触发   → ⭐ 有更强的竞争者在赢
□ ⭐⭐⭐ 两台机器行为不同 → ⭐ 先比 claude --version（5秒）→ ⭐ 再疑缓存 ~/.claude/state/（重启清）

□ ⭐⭐⭐⭐ 触发太频繁：① ⭐⭐⭐⭐⭐ 加否定触发 + ⭐ 点名替代技能
                  ② 更具体   ③ 澄清范围
□ ⭐⭐⭐⭐⭐ 指令不被遵循四因：
   ① 太啰嗦（移出详情） ② ⭐⭐⭐⭐ 被埋没（⭐ 置顶 + ## Critical + ⭐ 重复关键点）
   ③ ⭐⭐⭐⭐⭐ 含糊（⭐ 写成可机械判定的清单：非空/≥1/不在过去）
   ④ ⭐⭐⭐⭐⭐ 犯懒（鼓励⭐ 加在用户提示里比 SKILL.md 更有效
      → ⭐⭐⭐⭐⭐ 第二次独立确认"临时 Prompt > 技能规则"）
   ⭐⭐⭐⭐⭐⭐ 更强解法：⭐ 关键验证⭐ 打包成脚本
      "Code is deterministic; language interpretation isn't."（第七个来源）
□ ⭐⭐⭐⭐⭐ "新鲜会话好用、中途失效" = ⭐⭐⭐⭐⭐ ⭐ 正文长度截断的⭐ 特征信号
   → ⭐⭐⭐⭐ ⭐ 先削长度，⭐ 不是先改描述
```

**一句话**：

> ⭐⭐⭐⭐ **"问 Claude 你什么时候会用这个技能"是一个零成本且极准的调试技巧——它会把描述原样复述回来，一次就能区分"加载的不是这个文件""描述太笼统""有更强的竞争者在赢"三种故障；而"新鲜会话好用、中途失效"几乎肯定是正文长度截断，该先削长度而不是先改描述。**
