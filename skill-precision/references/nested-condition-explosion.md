## 1. ⭐⭐⭐⭐⭐ 一段看起来并不复杂的指令

```
如果文件存在：
    如果格式合法：
        如果大小 < 10MB：
            处理它
```

只有四行，读起来很清爽。它定义了 **8 条路径**。

> ⭐⭐⭐⭐⭐ 作者心里只有 1 条（存在 + 合法 + 小），
> 而⭐⭐⭐⭐ **剩下 7 条不是"未测试"，是"未定义"**。

---

## 2. ⭐⭐⭐⭐⭐ 路径数怎么算

```
n 层二分支      → 2ⁿ 条路径
分支数分别为 a,b,c → a × b × c 条
```

3 层 = 8 条；4 层 = 16 条。而典型的技能测试集是 **3–10 个用例**。

> ⭐⭐⭐⭐⭐ 这不是"覆盖不全"，是⭐⭐⭐⭐ **大部分的运行时行为由模型定义，
> 而作者以为自己定义了**。

---

## 3. ⭐⭐⭐⭐⭐ 三种形态：嵌套 / 分散 / 隐含

### ① 嵌套（显式 if 套 if）

最容易识别，也最容易在评审时被放过——因为每一层单独看都对。

### ② 分散（同一个条件在两个章节各判一次）

```
第 2 节：如果输入是表格，按行处理
第 5 节：表格输入需要先用 X 归一化
```

> ⭐⭐⭐⭐⭐ 两处结论可能不一致，而⭐⭐⭐⭐ **没有任何环节会把这两节放在一起读**。
> 这与 `skill-precision/references/conflicting-instructions.md` 同源，但那份按"被约束的维度"分组来发现，
> 这份按"同一个条件出现几次"来发现。

### ③ 隐含（"否则按常规处理"）

```
否则按常规处理 / 视情况而定 / 其余情况类似
```

> ⭐⭐⭐⭐⭐ **"常规"没有定义，而它覆盖的往往是占比最大的那一批输入。**

三种形态里 ③ 最危险：

```
①② 至少还有一个"写了的分支"可以对照
③  ⭐⭐⭐⭐⭐ 连对照都没有——它是一次彻底的授权
```

## 4. ⭐⭐⭐⭐⭐ 为什么作者发现不了

```
写的时候：作者沿 happy path 走一遍，通了 → 觉得写完了
读的时候（模型）：⭐⭐⭐⭐⭐ 只会看到它当前所处的那条路径，
                  其余 7 条它永远不会主动去查
```

> ⭐⭐⭐⭐⭐ **所以未定义分支的暴露条件是"那种输入真的出现了"——也就是生产。**

这解释了那个常见现象：技能在测试集上一直很好，上线后某天突然"行为变了"，
而 diff 显示无人改动。

## 5. ⭐⭐⭐⭐⭐ 修法一：决策表

把嵌套的条件正交化成表格：

| 文件存在 | 格式合法 | 大小 <10MB | 动作 |
|---|---|---|---|
| 否 | — | — | 报错：文件不存在（停止） |
| 是 | 否 | — | ⭐ 报错并给出前 3 行样例 |
| 是 | 是 | 否 | 分块处理，每块 10MB |
| 是 | 是 | 是 | 正常处理 |

三个收益：

```
① ⭐⭐⭐⭐⭐ 组合数从"隐含的 8"变成"表上写的 4"——你终于知道有几种
② ⭐⭐⭐⭐⭐ 不可能的组合被显式标成"—"，而不是留空
③ ⭐⭐⭐⭐ ⭐ 表格是可评审的：评审者能逐行问"这一行对吗"
```

> ⭐⭐⭐⭐⭐ 关键不是表格这个形式，是⭐⭐⭐⭐⭐ **把"乘积"摊平成"列表"**——
> 摊平之后，遗漏变成可见的空格。

## 6. ⭐⭐⭐⭐⭐ 修法二：前置规范化（消掉一整层）

```
如果格式是 A → 转成统一格式
如果格式是 B → 转成统一格式
如果格式是 C → 转成统一格式
（之后所有地方只处理统一格式）
```

> ⭐⭐⭐⭐⭐ **这一层的价值不是"处理了三种格式"，
> 是它之后的所有代码都少了一个维度。**

它和"先探测不先写"（`skill-patterns/references/reusability-over-specification.md`）同源：
把"有哪些可能"从静态声明改成运行时转换。

适用判据：**这一层的分支，后面每个步骤都要重新判断一次吗？**
是 → 前置规范化；否 → 保持嵌套。

## 7. ⭐⭐⭐⭐⭐ 修法三：两阶段（乘积变和）

```
阶段一 分类：输入 → 三类中之一（表驱动，一张表）
阶段二 处理：每一类一个独立块，块内无分支
```

```
路径数：从 3×2×2 = 12  →  3 + 3 = 6
可读性：每一类单独可读、单独可改、单独可测
```

> ⭐⭐⭐⭐⭐ 这是三种修法里最通用的一种：
> 决策表适合条件少的情况，规范化适合"可以转换"的情况，
> ⭐⭐⭐⭐ **而两阶段在任何情况下都能用，且不需要改语义。**

---

## 8. ⭐⭐⭐⭐⭐ 表行数 = 最少用例数

`skill-evaluating/references/eval-case-design.md` 说"每条分支至少一个用例"，但没说**有多少条分支**。

> ⭐⭐⭐⭐⭐ **决策表的行数，就是分支的数量。**
> 于是"测够了没有"第一次变成了一个可数的问题——
> 不是凭感觉说"应该够了吧"，是数表里的行数。

配套的反向检查：

```
⭐⭐⭐⭐ 表有 6 行、测试集只有 3 个用例 → 至少 3 条路径在生产里是首次执行
```

## 9. ⭐⭐⭐⭐ 自检

```bash
# 数嵌套层数
grep -cE "^\s{4,}(如果|if )" SKILL.md
# 找"常规"这类未定义兜底
grep -nE "按常规|视情况|其余情况|类似处理|以此类推" SKILL.md
```

| 检查 | 阈值 | 动作 |
|---|---|---|
| ⭐⭐⭐⭐⭐ 嵌套层数 | ≥2 层 | 改决策表或两阶段 |
| ⭐⭐⭐⭐⭐ "常规/视情况" | 出现即处理 | 定义它，或删掉这个分支 |
| ⭐⭐⭐⭐ 同一条件出现次数 | ≥2 次 | 合并到一处，或前置规范化 |
| ⭐⭐⭐⭐ 决策表行数 vs 用例数 | 行数 > 用例数 | 补用例 |

## 速查

```
□ ⭐⭐⭐⭐⭐ 四行三层嵌套 = 8 条路径，作者只定义了 1 条
□ ⭐⭐⭐⭐⭐ 未定义的组合由模型定义，而它只在生产里才被触发
□ ⭐⭐⭐⭐⭐ 三种形态：嵌套 / 分散（同条件判两次）/ 隐含（"按常规"）
□ ⭐⭐⭐⭐⭐ "按常规"覆盖的往往是占比最大的那批输入，且没有对照
□ ⭐⭐⭐⭐⭐ 决策表：把乘积摊平成列表，遗漏变成可见的空格
□ ⭐⭐⭐⭐⭐ 前置规范化：消掉一整层维度，后面全部少一个 if
□ ⭐⭐⭐⭐⭐ 两阶段（先分类再处理）：路径数从乘积变和，任何场景都能用
□ ⭐⭐⭐⭐⭐ 决策表行数 = 分支数 = 最少用例数（"测够没有"第一次可数）
```

**一句话**：

> ⭐⭐⭐⭐⭐ **三层嵌套只有四行、读起来很清爽，而它把 8 条路径中的 7 条留给了模型——作者写的时候沿一条路走通就以为写完了，模型读的时候只看它所在的那一条，于是那 7 条直到生产才第一次被执行。三种修法里最通用的是两阶段（先分类再处理）：路径数从乘积变成和，且不需要改语义。**
