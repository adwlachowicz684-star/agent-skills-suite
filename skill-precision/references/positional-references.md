## 1. ⭐⭐⭐⭐⭐ 一句完全通顺的话

```markdown
## 流程
1. 扫描所有源文件
2. 提取其中的导出符号
3. 对上一步的结果去重
4. 输出
```

> ⭐⭐⭐⭐⭐ "上一步的结果"指什么，写的人清楚，读的人也清楚。

问题不在当下这一刻，而在：

> ⭐⭐⭐⭐⭐ **它假设了第 2 步的输出一定在上下文里，且一定被认得出来。**

---

## 2. ⭐⭐⭐⭐⭐ 三种位置指代

| 类型 | 例子 | ⭐⭐⭐⭐⭐ 脆弱点 |
|---|---|---|
| ⭐⭐⭐⭐⭐ 向后指 | "上一步的结果"、"如上所述"、"前面提到的规则" | 前文可能不在上下文 |
| ⭐⭐⭐⭐⭐ 向前指 | "如下"、"下面的示例"、"见最后一节" | 后文可能被截断 |
| ⭐⭐⭐⭐⭐ 按编号指 | "第 3 步"、"步骤 2 的输出"、"规则 4" | 编号会变 |

> ⭐⭐⭐⭐⭐ 第三种最危险，因为⭐⭐⭐⭐⭐ **它看起来最精确**——
> 写"第 3 步"的人认为自己已经把指代写清楚了。

---

## 3. ⭐⭐⭐⭐⭐ 为什么它在技能里格外危险

在普通文档里，位置指代是安全的，因为读者拿着完整文档。技能有三条机制让它失效：

**① ⭐⭐⭐⭐⭐ 正文可能被部分加载**

```
按三级加载，正文是整份加载的；
但参考文件不是——模型常用 head -100 预览
→ ⭐⭐⭐⭐⭐ "见最后一节"指向的内容可能从未被读到
```

**② ⭐⭐⭐⭐⭐ 压缩截断**

```
⭐⭐⭐⭐⭐ 压缩带回的是"开头 5000"，不是"最重要的 5000"
→ ⭐⭐⭐⭐⭐ "如上所述的红线"在压缩后可能已不在上下文里，
   而"按上面的红线处理"这句话还在
```

> ⭐⭐⭐⭐⭐ 这是最坏的组合：**指令留下了，它引用的东西没了。**
> 模型不会报错，它会按自己的理解补一个"上面大概是说"。

**③ ⭐⭐⭐⭐⭐ 章节会被重新排序**

```
五段式骨架要求红线在首、验证在尾
→ 排序时步骤编号全变
→ ⭐⭐⭐⭐⭐ "第 3 步"指向了另一个动作
```

---

## 4. ⭐⭐⭐⭐⭐ 修改是最常见的触发方式

位置指代很少在"第一次写"时出错——那时它是准的。它坏在**第二次编辑**：

```
原：1 扫描 2 提取 3 去重 4 输出
改：在第 2 步后插入"过滤测试文件"
新：1 扫描 2 提取 3 过滤 4 去重 5 输出
```

> ⭐⭐⭐⭐⭐ 如果第 4 步写的是"对上一步的结果去重"，它仍然正确；
> ⭐⭐⭐⭐⭐ 如果写的是"对第 2 步的结果去重"，它现在错了——
> ⭐⭐⭐⭐⭐ **而且不会报错，它会去对"提取"的结果做去重，跳过过滤。**

这正是本份最该记住的一条：

> ⭐⭐⭐⭐⭐ **编号指代把"插入一步"这个最普通的编辑动作，
> 变成了一次静默的逻辑变更。**

而插入中间步骤恰恰是最常见的修改——比删除、比改措辞都常见。

## 5. ⭐⭐⭐⭐⭐ 修法：把指代换成名字

三种改法，按强度递增：

**① ⭐⭐⭐⭐⭐ 给中间产物起名（最推荐）**

```markdown
2. 提取导出符号 → 记为 `symbol_list`
4. 对 `symbol_list` 去重
```

> ⭐⭐⭐⭐⭐ 好处不只是抗重排：⭐⭐⭐⭐⭐ **名字本身就是一份隐式的数据契约**——
> 它顺带明确了第 4 步的输入是什么类型、什么结构。
> 这与《skill-interfaces》的"中间产物要有 schema"是同一手法，只是粒度更小。

**② ⭐⭐⭐⭐⭐ 用名字而不是编号指规则**

```
❌ "按规则 4 处理"
✅ ⭐⭐⭐⭐⭐ "按「红线：不得编造」处理"
```

> ⭐⭐⭐⭐⭐ 规则名还有第二个收益：⭐⭐⭐⭐ 它可以在别处被 grep 到，
> 于是"哪些地方依赖这条规则"变成可查的——
> 这正是影响面分析（《skill-versioning》的 change-impact-surface.md）需要的。

**③ ⭐⭐⭐⭐⭐ 向前指改成显式复述**

```markdown
❌ "输出格式见下面"
✅ ⭐⭐⭐⭐⭐ "输出必须是 JSON，字段见 `skill-output/references/output-schema.md`"
```

> ⭐⭐⭐⭐⭐ 判据：⭐⭐⭐⭐ **"如下"后面的东西，如果被截断，这句话还剩什么？**
> 什么都不剩 → 必须复述要点。

## 6. ⭐⭐⭐⭐⭐ 该保留的位置指代

不是所有位置指代都要改。两种可以留：

**① ⭐⭐⭐⭐ 紧邻指代**

```markdown
1. 扫描源文件
2. 对扫描结果去重      ← 相邻步骤，"扫描结果"无歧义
```

> ⭐⭐⭐⭐⭐ 判据：**指代与目标之间隔了几行？**
> ⭐⭐⭐⭐⭐ 隔了 0–1 行 → 安全；隔了一个章节 → 必须换成名字。

**② ⭐⭐⭐⭐⭐ 结构性指代**

```markdown
"本节的规则优先于后续章节"
```

> ⭐⭐⭐⭐⭐ 它指的是**结构关系**而不是具体内容，
> ⭐⭐⭐⭐⭐ 结构关系不会因插入内容而失效（插入后仍然"本节优先"）。

判据收口：

> ⭐⭐⭐⭐⭐ **改成名字会让这句变长多少？
> 多 3–5 个字 → 改；多一整段 → 说明该拆章节了，而不是纠结指代。**

## 7. ⭐⭐⭐⭐⭐ 自检与 grep

```bash
grep -nE "上一步|前一步|上面|上文|如上|前述|如下|下面|最后一步|第 ?[0-9]+ ?步|步骤 ?[0-9]+|规则 ?[0-9]+" SKILL.md
```

逐条问一句：

> ⭐⭐⭐⭐⭐ **如果中间被插入一个新步骤，这句还会指向同一个东西吗？**

不会 → 换成名字。

> ⭐⭐⭐⭐⭐ 与含糊词、无出处数字那两份一样的原则：
> ⭐⭐⭐⭐⭐ **只有能变成一条命令的检查，才会真的被执行。**
> 而这一条尤其值得放进 CI，因为它是纯文本匹配，零误报。

一个十秒判断：

> ⭐⭐⭐⭐⭐ **把技能的步骤顺序随机打乱，再读一遍。
> 读不通的地方，就是编号指代在替你承担"顺序不能变"这个隐性约束。**
