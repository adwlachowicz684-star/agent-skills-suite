## 1. ⭐⭐⭐⭐⭐ 六层载体

同一条约束——比如"不得删除用户上传的原件"——至少可以写在六个地方：

| 层 | 写在哪 | 谁来保证 | 生效时机 |
|---|---|---|---|
| ① | description | ⭐ 无人（它只影响"是否被触发"） | 每次判断 |
| ② | 正文（SKILL.md） | 模型遵守 | 触发后 |
| ③ | reference | 模型遵守 **且** 模型去读了 | ⭐ 需要时 |
| ④ | 脚本（scripts/） | 代码逻辑 | 脚本被调用时 |
| ⑤ | hook | 运行时拦截 | 工具调用前/后 |
| ⑥ | CI / 校验器 | 流水线 | 变更前 |

> ⭐⭐⭐⭐⭐ **① 不是约束层。** 写在 description 里的"不得……"不影响执行，
> 它只改变"这个技能会不会被叫起来"——而多数人把它当成已经声明过了。

## 2. ⭐⭐⭐⭐⭐ 核心规律：可靠性与覆盖面反向

```
② 正文   → 覆盖面⭐⭐⭐⭐⭐ 全部行为    · 可靠性⭐⭐ 依赖模型遵守
④ 脚本   → 覆盖面⭐⭐⭐  脚本内的路径  · 可靠性⭐⭐⭐⭐ 代码逻辑
⑤ hook   → 覆盖面⭐     特定工具调用   · 可靠性⭐⭐⭐⭐⭐ 无法绕过
⑥ CI     → 覆盖面⭐     入库那一刻     · 可靠性⭐⭐⭐⭐⭐ 但不在运行时
```

> ⭐⭐⭐⭐⭐ **越往下越硬，也越往下越窄。**

这条解释了为什么"全部下沉"不是答案：

> ⭐⭐⭐⭐⭐ 一条规则下沉到 hook 之后，它只在那个工具被调用时生效。
> 模型换一条路径完成同一件事（比如不调 `rm` 而调 `git clean`），约束就不存在了。
> **它没有违反约束——它走的是一条约束没有覆盖的路。**

所以下沉的实质是：**用覆盖面换可靠性**。这个交换在错误的路径集合已知时是划算的，未知时不划算。

## 3. ⭐⭐⭐⭐ 每一层各自的失效方式

| 层 | 失效方式 | 可见吗 |
|---|---|---|
| ① description | 根本不影响执行 | ❌ 看起来"写过了" |
| ② 正文 | 被压缩截断 / 被更具体的指令覆盖 / 三轮后开始忽略 | ❌ 静默 |
| ③ reference | ⭐⭐⭐⭐⭐ **没被读到**——它不是错误，只是没发生 | ❌ 完全静默 |
| ④ 脚本 | 模型没调用这个脚本，改用了别的方式 | ❌ 静默 |
| ⑤ hook | matcher 没匹配上（工具换了/参数形态不同） | ❌ 静默 |
| ⑥ CI | ⭐⭐⭐⭐⭐ **它不在运行时**——只保证入库时合规 | ✅ 至少会报错 |

> ⭐⭐⭐⭐⭐ **六层里有五层是静默失效的，而它们失效时都"看起来正常"。**

只有 ⑥ 会明确报错，而它是唯一一个不作用于运行时的层——这是这套机制最尴尬的地方。

## 4. ⭐⭐⭐⭐⭐ 怎么选：三个判据

### 判据一：这条约束能被一条确定性规则判定吗

```
"不得删除 uploads/ 下的文件"     → 能（路径可字符串匹配）→ ⭐ 下沉
"报告要写得专业"                  → 不能                → ⭐ 留在正文
```

能判定的却留在正文 = 靠模型自觉，而模型有完成倾向。
不能判定的却下沉 = 见第 5 节。

### 判据二：违反的代价是什么量级

| 代价 | 处理 |
|---|---|
| 输出不好看 / 啰嗦 | 正文即可 |
| ⭐ 结果错了但可重跑 | 正文 + 输出校验（脚本） |
| ⭐⭐⭐⭐⭐ 不可逆、不可发现 | ⭐ 必须到 ⑤ hook 或 ⑥ CI |

判据不是"重不重要"——几乎所有约束都重要。是⭐⭐⭐⭐⭐ **"错了能不能被发现"**：
可发现的错可以留在软层（会被发现然后修），不可发现的错必须进硬层。

### 判据三：这条约束在约束"谁"

```
约束模型的输出格式 → 正文 / 输出校验脚本
约束模型的工具调用 → ⭐⭐⭐⭐ hook（PreToolUse 有 modifyInput，可就地改写）
约束人的改动      → ⭐⭐⭐⭐⭐ CI（唯一能拦住人的一层）
```

> ⭐⭐⭐⭐⭐ 第三条最常被搞错：给模型写的东西放进 CI，CI 永远绿，
> 而作者以为它"已经被 CI 保护了"。

## 5. ⭐⭐⭐⭐⭐ 反向下沉：需要判断的规则硬编码

下沉不是无条件的好。最常见的反向错误：

```yaml
# hook: 禁止在生产库执行 DELETE
if "DELETE" in command and "prod" in command: exit 2
```

问题：

```
✅ 拦截  DELETE FROM users WHERE ...        （确实该拦）
❌ 拦截  一篇文档里写着 "DELETE FROM users"  （误伤）
❌ 放行  TRUNCATE / DROP / 分批删除          （漏）
```

> ⭐⭐⭐⭐⭐ **hook 没有上下文。它看到的是命令字符串，不是意图。**

所以：

> ⭐⭐⭐⭐⭐ 需要判断的约束硬编码之后，就变成了⭐ **一个错误的硬拦截**——
> 它比软约束更糟，因为软约束至少在应该放行的时候会放行。

判据：⭐⭐⭐⭐⭐ **这条规则有没有反例？有反例就不能硬编码。**
有反例的规则要留在正文 + 写清判据，或者做成**可协商的 hook**（exit 2 给出替代方案，让模型改输入后重试——这正是 `modifyInput` 的用途）。

另外一条很少被提到：**误伤的成本远高于漏过**。漏过是一次事故，误伤会让所有人开始绕开这道门禁——⭐⭐⭐⭐⭐ 而绕开的习惯一旦形成，这道门禁对所有情况都失效了。

## 6. ⭐⭐⭐⭐ 层间重复：下层兜底，上层给理由

一条约束同时写在正文和 hook 里，不是冗余：

```
正文：为什么不能删（删了无法恢复、用户上传的是唯一副本）
hook：拦住 rm
```

> ⭐⭐⭐⭐⭐ **上层给理由，下层给保证。** 两者缺一都不完整：
> 只有正文 → 没有保证；只有 hook → 模型不理解，于是它去找没被拦的路径。

反过来，⭐⭐⭐⭐⭐ **把同一句话在正文里写两遍不是冗余防护，是膨胀**
（见 `skill-crafting/references/critical-rules-inflation.md`）——重复只在**跨层**时才有意义，同层重复只增加稀释。

## 7. ⭐⭐⭐⭐⭐ 四种最常见的错配

| 错配 | 实际发生 | 后果 |
|---|---|---|
| ⭐⭐⭐⭐⭐ 安全约束写在正文 | "不得删除生产数据" | ⭐⭐⭐⭐⭐ 三轮后开始忽略，且没有任何信号 |
| ⭐⭐⭐⭐⭐ 安全约束写在 README | README 里有一整节 | ⭐⭐⭐⭐⭐ agent 根本读不到，而评审者以为签字过了 |
| ⭐⭐⭐⭐ 格式约束写在正文 | "输出必须是 JSON" | 靠模型自觉；应下沉到 schema 校验脚本 |
| ⭐⭐⭐⭐ 需要判断的规则硬编码 | hook 拦截含 "DROP" 的命令 | ⭐⭐⭐⭐⭐ 误伤 → 所有人绕开它 |

第三个值得多说一句：**"输出必须是合法 JSON"是 100% 可判定的**，
把它写在正文里，等于用一个语言模型去做一个 `json.loads()` 就能做的事。
而它失败时的形状恰恰是最糟的那种——⭐⭐⭐⭐⭐ **输出看起来像 JSON，只是少了个引号。**

## 8. ⭐⭐⭐⭐ 自检

```
□ 数一数：正文里有多少条约束是"可判定的"？每一条都是下沉的候选
□ description 里有没有写约束？有 → 它不影响执行，移到正文
□ 有没有约束只写在 README / 注释 / 提交信息里？→ agent 读不到
□ 每条硬约束（hook/CI）有没有反例？有 → 它会在反例上误伤
□ 每条需要判断的规则有没有被硬编码？有 → 检查误伤
□ 层间重复是不是"正文给理由 + 下层给保证"？还是同层重复了两遍
```

一个能立刻做的检查：**列出正文里所有"不得/禁止/必须"，逐条问"这条能被 grep 到吗"**。
能被 grep 到的，都是下沉候选——而通常会有 30%–50% 命中。
