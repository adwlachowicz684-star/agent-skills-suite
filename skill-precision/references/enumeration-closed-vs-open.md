## 1. ⭐⭐⭐⭐⭐ 一个看起来没有分支的分支

```markdown
支持的文件类型：PDF、Word、Excel
```

```
遇到 Markdown 文件 → ?
```

> ⭐⭐⭐⭐⭐ 这句话里没有 if，也没有"否则"，
> ⭐⭐⭐⭐⭐ 但它隐含了一个分支：**不在列表里的怎么办。**

而它从未被写出来。

---

## 2. ⭐⭐⭐⭐⭐ 模型的默认动作是归类，不是报告

关键不在于它会不会遇到 Markdown，而在于遇到时它做什么：

```
⭐⭐⭐⭐⭐ 报告"不支持的类型"  ← 需要技能明确要求
⭐⭐⭐⭐⭐ 归到最接近的一类继续 ← 模型的默认动作
```

> ⭐⭐⭐⭐⭐ 为什么默认是后者？因为它有强烈的完成倾向
> （《skill-content》的 `skill-content/references/default-actions.md`）：
> ⭐⭐⭐⭐⭐ **遇到阻碍时的默认动作不是停下报告，而是想办法绕过去。**

于是后果是：

```
Markdown 被当成纯文本处理 → 输出了、没报错、结构丢失
```

> ⭐⭐⭐⭐⭐ 这正是"局部成功、整体失败、且静默"的又一次出现：
> ⭐⭐⭐⭐ 每一个环节都做了它该做的事，只是对象错了。

---

## 3. ⭐⭐⭐⭐⭐ 封闭 vs 开放，写法完全不同

先决定它是哪一种，再决定怎么写。判据：

> ⭐⭐⭐⭐⭐ **列表之外还有别的合法值吗？**

**封闭（穷举）**

```markdown
## 支持的类型（穷举，共 3 种）
- PDF
- Word（.docx）
- Excel（.xlsx）

⭐⭐⭐⭐⭐ 遇到其他类型：报错并停止，不得尝试处理
```

**开放（举例）**

```markdown
## 常见类型（举例，非穷举）
- PDF
- Word（.docx）

⭐⭐⭐⭐⭐ 其他类型：按通用文本提取处理，并在输出中标注"未识别类型：<扩展名>"
```

> ⭐⭐⭐⭐⭐ 两种写法都合法，⭐⭐⭐⭐⭐ **唯一不可接受的是不说明是哪种**——
> 因为那等于让模型替你决定"这个列表是不是全部"。

---

## 4. ⭐⭐⭐⭐⭐ 半封闭是最常见也最错的形态

现实中最常见的写法是这种：

```markdown
支持：PDF、Word、Excel、PPT、图片、CSV、JSON、Markdown
```

> ⭐⭐⭐⭐⭐ 列了八项，看起来很全面，
> ⭐⭐⭐⭐⭐ 而这恰恰说明它是**开放列表**——
> 因为作者是在"想一个加一个"，不是在定义一个封闭集合。

> ⭐⭐⭐⭐⭐ **列表越长，它越可能是开放列表，却越看起来像穷举。**

这是本份最该记住的一条，因为它解释了为什么这类问题**系统性地**发生：

```
写封闭列表 → 短（能穷举的本来就少）
写开放列表 → 长（想尽可能覆盖）
⭐⭐⭐⭐⭐ 而长列表在视觉上"更完整"，于是被读成穷举
```

判据（很实用）：

> ⭐⭐⭐⭐⭐ **超过 5 项的枚举，默认按开放处理，并显式写"非穷举"。**

## 5. ⭐⭐⭐⭐⭐ "等"这个字决定了全部

```markdown
支持 PDF、Word 等格式
```

> ⭐⭐⭐⭐⭐ 一个"等"字，把封闭变成了开放——
> ⭐⭐⭐⭐⭐ 而它通常是随手加的（为了让句子读起来顺）。

两个方向都可能是作者没想清楚的：

**① ⭐⭐⭐⭐⭐ 原本是穷举，加了"等" → 边界消失**

```
"支持 PDF、Word、Excel 等" → 现在 Markdown 算不算？
⭐⭐⭐⭐ 没人知道，包括作者
```

**② ⭐⭐⭐⭐⭐ 原本是开放，没加"等" → 被当成穷举**

```
"支持 PDF、Word" （其实想说"主要是这两种"）
→ 模型遇到 Excel 时认为不支持
```

判据一句话：

> ⭐⭐⭐⭐⭐ **能不能把这个列表换成"共 N 种"或"例如"？
> 换不了 → 作者自己也不知道它是哪种。**

而含糊词黑名单里已经有"等等"这一项——
那份说的是"等等"没有终止条件，这份说的是它**同时破坏了枚举的封闭性**。

## 6. ⭐⭐⭐⭐⭐ 枚举值的写法：可判定优先于可读

即使明确了封闭，每一项的**判定方式**仍可能含糊：

```
❌ "Word"           → .doc 算吗？
❌ "图片"           → .svg 算吗？.webp 算吗？
⭐⭐⭐⭐⭐ "Word（.docx）" → 按扩展名判定，无歧义
```

> ⭐⭐⭐⭐⭐ 判据：⭐⭐⭐⭐ **两个人对同一个文件会不会得出不同结论？**
> 会 → 这项写得不够可判定。

三种给出判定的方式，按可靠性：

```
① ⭐⭐⭐⭐⭐ 扩展名（.docx）      — 最可靠，机器可判
② ⭐⭐⭐⭐ MIME / 魔数            — 可靠，但需要工具
③ ⭐⭐ 描述性（"Word 文档"）      — ⭐⭐⭐⭐⭐ 需要模型判断，会漂移
```

> ⭐⭐⭐⭐⭐ 第 ③ 种最常被写，因为它最自然；
> ⭐⭐⭐⭐⭐ 而它正是"遇到未知类型时静默归类"的入口——
> 因为描述性判定本来就没有明确边界。

还有一种反向错误值得单独提：**枚举项之间不互斥**。

```
"文本类（txt、md）" / "代码类（py、js）" / "配置文件（json、yaml）"
→ ⭐⭐⭐⭐⭐ .json 同时属于文本类和配置文件
→ 归到哪一类取决于模型，且两次可能不同
```

> ⭐⭐⭐⭐⭐ 这与失败四象限里的"概率性失败"直接相关：
> ⭐⭐⭐⭐⭐ **枚举不互斥，是"同一输入两次结果不同"最容易被忽略的成因之一。**

## 7. ⭐⭐⭐⭐⭐ 自检与 grep

```bash
grep -nE "支持[:：]|类型[:：]|格式[:：]|包括|等[格类形]" SKILL.md
```

对每一处枚举问三句：

```
① ⭐⭐⭐⭐⭐ 这是穷举还是举例？写明了没有？
② ⭐⭐⭐⭐⭐ 不在列表里时该做什么？写了吗？
③ ⭐⭐⭐⭐⭐ 每一项都能被唯一判定吗？项之间互斥吗？
```

> ⭐⭐⭐⭐⭐ 第 ② 条命中率最高——它从来没被写过，
> ⭐⭐⭐⭐⭐ 因为作者写列表时在想"有哪些"，不在想"没有的怎么办"。

一个十秒判断：

> ⭐⭐⭐⭐⭐ **随便挑一个不在这个列表里的东西，
> 问"技能遇到它会怎么做"。答不出来 → 枚举边界没写。**

---

## 一句可贴在墙上

> ⭐⭐⭐ **列表越长，它越可能是开放列表，却越看起来像穷举。
> 而遇到列表外的东西时，模型的默认动作是找一个最接近的归类，不是报告。**
