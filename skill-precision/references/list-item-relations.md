## 1. ⭐⭐⭐⭐⭐ "A、B、C"是且、或、还是顺序

```markdown
## 输出
- 列出受影响的文件
- 说明影响范围
- 给出修复建议
```

> ⭐⭐⭐⭐⭐ 这三条是**全部都要**（且），
> 还是**按情况选一条**（或），还是**按这个顺序**（顺序）？

作者写的时候通常想的是"且 + 顺序"，而写出来的是三个并列的短横。

> ⭐⭐⭐⭐⭐ 关键点：⭐⭐⭐⭐⭐ **Markdown 的列表语法只表达"这是一组"，
> 不表达组内关系。关系完全靠读者推断。**

## 2. ⭐⭐⭐⭐⭐ 三种关系，三种完全不同的失败

| 关系 | 作者意图 | 模型按别的解读时 |
|---|---|---|
| ⭐⭐⭐⭐ 且（AND） | 三条都要 | 只做一条 → 输出缺项 |
| ⭐⭐⭐⭐⭐ 或（OR） | 选一条 | ⭐⭐⭐⭐⭐ 全做 → 冗余、矛盾、上下文变贵 |
| ⭐⭐⭐⭐⭐ 顺序 | 先后有意义 | ⭐⭐⭐⭐⭐ 换个顺序 → 结果不同且不报错 |

第三种最危险，因为它和前两种不一样：

> ⭐⭐⭐⭐⭐ **"且"和"或"搞错，输出会明显不对（缺项或冗余）；
> "顺序"搞错，输出看起来完整、正确，只是结果是另一件事。**

这与 `skill-input/references/relative-time-resolution.md` 那条"时间窗口错会静默换一批数据"是同一类失败：**形式完整，内容错位**。

## 3. ⭐⭐⭐⭐⭐ 默认解读是"且"，而多数时候不是

> ⭐⭐⭐⭐⭐ 模型的默认解读是 **AND + 顺序执行**——
> 因为它见过最多的列表就是"步骤清单"。

问题在于这个默认值会对两类内容**系统地出错**：

**① ⭐⭐⭐⭐⭐ 备选方案列表被当成步骤**

```markdown
- 方案 A：全量重建
- 方案 B：增量更新
```

> ⭐⭐⭐⭐⭐ 按 AND 解读 → 两个都做 → 重建完再更新一遍。
> ⭐⭐⭐⭐ 而这在很多场景**不会报错**，只是多花一倍时间。

**② ⭐⭐⭐⭐⭐ 条件列表被当成必做**

```markdown
- 若文件已存在，追加
- 若文件不存在，创建
```

> ⭐⭐⭐⭐⭐ 这两条是互斥的，而按 AND 解读会**先追加再创建**（或反向），
> ⭐⭐⭐⭐⭐ 于是产生一个"创建后又被覆盖"的结果。
> 这正是 `skill-precision/references/conditional-branch-writing.md` 说的"没有 else 的 if"的列表版本。

## 4. ⭐⭐⭐⭐⭐ 写法：把关系写进引导句

最省力的修法——**不动列表，只改引导句**：

| 关系 | ⭐⭐⭐⭐⭐ 引导句写法 |
|---|---|
| 且 | "输出必须包含以下**全部**三项" |
| 或 | "**根据情况选择其一**" |
| 顺序 | "**按以下顺序**执行" |
| 优先级 | "**按优先级**排列，资源不足时从后往前舍弃" |
| 无顺序 | "以下各项**顺序不限**" |

> ⭐⭐⭐⭐⭐ 最后一行常被忽略，而它恰恰重要：
> ⭐⭐⭐⭐ **不写"顺序不限"，模型就会按它认为合理的顺序来**，
> 于是你失去了一次"让它并行"或"让它按你熟悉的顺序"的机会。

一个额外收益：

> ⭐⭐⭐⭐⭐ 引导句同时也是⭐⭐⭐⭐ 最容易 review 的地方——
> 评审者只要读一句就知道这个列表的语义，不必逐项推断。

## 5. ⭐⭐⭐⭐⭐ 混合列表是最隐蔽的一种

```markdown
## 输出
- 结论
- 依据
- 若数据不足，说明缺什么
```

> ⭐⭐⭐⭐⭐ 前两条是 AND，第三条是条件——
> ⭐⭐⭐⭐⭐ **同一个列表里混了两种关系，而引导句只能写一种。**

这就是本份最该记住的一条：

> ⭐⭐⭐⭐⭐ **引导句管不住混合列表。**

两种处理，按优先级：

**① ⭐⭐⭐⭐⭐ 拆成两个列表**

```markdown
## 输出（以下全部）
- 结论
- 依据

## 补充（条件）
- 数据不足时：说明缺什么
```

**② ⭐⭐⭐⭐ 至少把条件项显式标出**

```markdown
- 【条件】数据不足时：说明缺什么
```

> ⭐⭐⭐⭐⭐ 选 ① 还是 ② 的判据：⭐⭐⭐⭐ **条件项超过一个就拆**——
> 一个可以用标记，多个会让"哪些是必做"这件事本身变得需要推断。

## 6. ⭐⭐⭐⭐⭐ 顺序列表的两种歧义

即使是明确写了"按以下顺序"，仍有两种歧义：

**① ⭐⭐⭐⭐⭐ 前一步失败后，后面的还要不要跑**

```markdown
按以下顺序执行：
1. 拉取数据
2. 校验数据
3. 生成报告
```

> ⭐⭐⭐⭐⭐ 第 2 步失败 → 第 3 步跑不跑？
> 不写 → 模型的默认动作是⭐⭐⭐⭐ **想办法继续**，
> 于是它会基于未校验的数据生成报告，并且不说。

**② ⭐⭐⭐⭐⭐ "顺序"指依赖顺序还是输出顺序**

```markdown
按以下顺序输出：结论、依据、建议
```

> ⭐⭐⭐⭐⭐ 这说的是**输出的排列顺序**。
> 而模型有可能把它读成**执行的先后顺序**——
> 于是先想一个结论，再去找能支撑它的依据。

> ⭐⭐⭐⭐⭐ 第二种歧义很隐蔽，但后果严重：
> ⭐⭐⭐⭐⭐ **先有结论再找依据，正是编造的标准形态。**
> 修法只要一个词：写"**输出顺序**"而不是"顺序"。

## 7. ⭐⭐⭐⭐⭐ 自检与 grep

```bash
# 找出所有没有引导句、或引导句不含关系词的列表
grep -nE "^- " SKILL.md | head -50
```

逐条问三句：

```
① ⭐⭐⭐⭐⭐ 这几项是"都要"还是"选一个"？引导句写了吗？
② ⭐⭐⭐⭐⭐ 列表里有条件项吗？有 → 拆开或标记了吗？
③ ⭐⭐⭐⭐⭐ 顺序有意义吗？有意义 → 写了失败后怎么办吗？
```

> ⭐⭐⭐⭐⭐ 第 ② 条命中率最高，因为⭐⭐⭐⭐ 条件项在写作时
> 是"顺手加的"（写完了想起还有个情况），于是它自然落在列表末尾，
> ⭐⭐⭐⭐⭐ 而末尾正是"看起来像第四项"的位置。

一个十秒判断：

> ⭐⭐⭐⭐⭐ **读这个列表的第一句，能不能知道要满足几项？
> 不能 → 关系没写。**

---

## 一句可贴在墙上

> ⭐⭐⭐ **Markdown 的列表只表达"这是一组"，不表达组内关系。
> 而模型的默认解读是"且 + 顺序"——所以关系不写在引导句里，就由它替你决定。**
