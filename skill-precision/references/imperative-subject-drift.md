## 1. ⭐⭐⭐⭐⭐ 三类执行主体

```
① ⭐⭐⭐ 模型自己    —— 读文件、跑命令、生成文本、比对
② ⭐⭐⭐⭐⭐ 用户    —— 批准、提供凭证、做业务判断、看屏幕确认
③ ⭐⭐⭐⭐ 外部系统  —— 发邮件、创建工单、部署、写生产库
```

一份技能里的每一个祈使句，都有且只有一个真正的执行者。

> ⭐⭐⭐⭐⭐ 而绝大多数祈使句都没有写出它是谁。

---

## 2. ⭐⭐⭐⭐⭐ 默认规则：模型认领所有无主语动作

> ⭐⭐⭐⭐⭐ **模型读到一个祈使句，默认把它认领为自己的动作——
> 因为整份文档都在教它做事，这个默认在 99% 的情况下是对的。**

它是合理的默认，所以不该被全面纠正。问题只出在那 1%：

```
"确认用户已登录"
    ↑ 这件事模型做不到
```

## 3. ⭐⭐⭐⭐⭐ 三种失败形态

### a) 本该用户做的，被模型做了

```
技能：确认用户拥有该仓库的写权限后继续
模型：已确认用户拥有写权限。（继续）
      ↑ 它什么都没确认，它生成了一句确认
```

> ⭐⭐⭐⭐⭐ **这类失败是必然的，不是偶然的**：
> 模型没有能力执行这个动作，但⭐⭐⭐⭐⭐ **它有很强的能力生成"已执行"的陈述**。

这是"结构正确的废话"的执行主体版本——它不是在内容上编造，是在**动作归属**上编造，
而后者更难发现，因为输出里没有任何可被核对的实体。

### b) 本该模型做的，被读成既有状态

```
技能：确保索引是最新的
模型：（读成"索引应该已经是最新的"）→ 跳过
```

与"没有 else 的 if"的区别：

```
那份：分支没写 → 模型补一个 else
这份：⭐⭐⭐⭐ 动作被降级成了假设 → 模型干脆没有进分支
```

### c) 状态断言被当成动作（或反过来）

```
"配置已加载" —— 这是在陈述现状，还是在下达指令？
```

- 读成断言 → 为假时它不知道该报错，于是继续
- 读成指令 → 它每次都重新加载一遍

## 4. ⭐⭐⭐⭐⭐ "确保"是最危险的一个词

它把三件事压缩成一个词：

```
确保 X = 检查 X · 若不满足则修复 · 修复不了则 ?
            ↑ 主语没了          ↑ else 没了
```

```markdown
❌ 确保输出包含版本号

✅ 检查输出是否包含版本号；
   不包含则重新生成一次并在开头补上；
   补不上则写"未获取"，并登记到 failures
```

> ⭐⭐⭐⭐⭐ **判据：把"确保 X"展开后，如果出现了"若不满足则…"这个分支，
> 说明原句缺的不只是主语，还有 else——它同时犯了两个错。**

同类词：`确认` `保证` `验证一下` `记得` `注意`。

## 5. ⭐⭐⭐⭐ 三类动词的归属表

| 动词 | 真正执行者 | 写错时的表现 |
|---|---|---|
| 读 / 列出 / 统计 / 生成 / 比对 | 模型 | 写成给用户 → 模型等待一个不会到来的动作（卡住，或默默跳过） |
| ⭐⭐⭐⭐⭐ 批准 / 确认 / 提供 / 决定 | 用户 | ⭐⭐⭐⭐⭐ **模型自己"完成"了它，输出一句确认** |
| ⭐⭐⭐⭐ 发送 / 创建 / 部署 / 合并 | 外部系统 | ⭐⭐⭐⭐ 描述了动作但它没发生；或换了工具、换了参数 |

第三种里最需要单独记的一条：

> ⭐⭐⭐⭐⭐ **"通知负责人"看起来只是"告诉你结果"，
> 而它是唯一一个错误会跑到组织外部、且无法收回的动作。**
> （与 `skill-execution/references/readonly-vs-writing-skills.md` 同源）

## 6. ⭐⭐⭐⭐⭐ 写法：只给"非模型"那两类补主语

```
① 需要用户 → ⭐⭐⭐⭐⭐ 显式"要求用户 X" + ⭐⭐⭐⭐⭐ 停止点 + 不回复时的默认
② 需要外部系统 → 点名工具 + 失败语义 + ⭐⭐⭐⭐ 写入后回读校验
③ 需要模型 → 祈使句本身就够了，⭐⭐⭐⭐ 不要加主语
```

第三条常被做反：

> ⭐⭐⭐⭐ **给所有句子加"模型应该"，会让正文变长、稀释重点，
> 而且会引入第二人称/第三人称的文体问题**（见 `skill-crafting/references/imperative-style.md`）。

> ⭐⭐⭐⭐⭐ 所以规则是：**默认归属模型是对的，只有 ①② 两类必须写主语。**

停止点那半句最容易被省，而它决定了成败：

```markdown
要求用户提供目标环境（prod / staging）；
在收到回复前不要继续；
若两轮内未收到，按 staging 处理并在输出首行标注"环境未确认，按 staging 处理"。
```

## 7. ⭐⭐⭐⭐ 状态断言 vs 动作指令

| 原文 | 性质 | 问题 |
|---|---|---|
| 配置已加载 | 断言 | 为假时应该报错，而不是去加载 |
| 加载配置 | 动作 | 清晰 |
| 索引是最新的 | 断言 | ⭐⭐⭐⭐ 被读成"已经是最新的"，于是跳过刷新 |

修法：把断言改成可观察谓词。

```
❌ 确保索引是最新的
✅ if 索引文件的 mtime 早于最近一次提交时间: 重新构建索引
```

> ⭐⭐⭐⭐ 判据：**这句话能被证伪吗？** 不能被证伪的是断言，不是指令。

## 8. ⭐⭐⭐⭐ 自检与 grep

```bash
grep -nE "确保|确认|保证|验证一下|记得|注意要" SKILL.md
```

对每一条命中，补出主语：

| 命中 | 谁能真的执行 | 处理 |
|---|---|---|
| 能补出"模型" | 模型 | 保持祈使句，不动 |
| 能补出"用户" | 用户 | ⭐⭐⭐⭐⭐ 必须改写：要求用户 + 停止点 + 默认 |
| 能补出"工具" | 外部系统 | 点名工具 + 失败语义 |
| ⭐⭐⭐⭐⭐ 补不出任何人 | —— | 这条是空话，删掉或改成可观察检查 |

> ⭐⭐⭐⭐⭐ **最后一行是这份文档最有用的产出**：
> 补不出执行者的祈使句，就是一句看起来像指令的陈述。

## 速查

```
□ ⭐⭐⭐⭐⭐ 无主语祈使句 → 模型默认认领，包括它做不到的那些
□ ⭐⭐⭐⭐⭐ 模型没能力执行，但有很强的能力生成"已执行"的陈述
□ ⭐⭐⭐⭐⭐ "确保"= 检查+修复+兜底 三件事，主语和 else 一起没了
□ ⭐⭐⭐⭐ 只有"需要用户"和"需要外部系统"两类必须写主语
□ ⭐⭐⭐⭐⭐ 需要用户的动作必须带停止点：收到回复前不继续
□ ⭐⭐⭐⭐ ⭐ 需要外部系统的动作必须带写入后校验（回读）
□ ⭐⭐⭐⭐ 断言改可观察谓词；不能被证伪的不是指令
□ ⭐⭐⭐⭐⭐ grep 命中后补不出执行者的 → 是空话，删
```

**一句话**：

> ⭐⭐⭐⭐⭐ **无主语祈使句的默认执行者是模型，这个默认 99% 正确，所以剩下那 1% 从不被人检查——而恰恰是那 1%（"确认用户已登录""确保环境就绪"）模型做不到，却能生成一句完美的"已确认"。规则是：只给"需要用户"和"需要外部系统"两类补主语，且前者必须带停止点。**
