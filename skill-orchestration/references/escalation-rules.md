# 升级规则：什么时候交给人

> "有疑问就问人"不是升级规则。
> 这份讲怎么把它写成可判定的条件。

## 三种含糊写法

```
❌ "有疑问时交给人工"
   ——模型不会知道自己"有疑问"

❌ "复杂情况转人工"
   ——"复杂"没有判据

❌ "必要时升级"
   ——同上
```

> ⭐ **这类写法的效果等价于没写**——
> agent 的默认行为是继续做下去。
>
> 呼应 `what-not-to-do.md`（**`skill-authoring`**）：
> **"确保质量"对模型等于没有约束**——同一类问题。

## 四类可判定的触发条件

**① 阈值类**

```
✅ 置信度 <0.8 → 进人工队列
✅ 涉及金额 >X → 人工复核
✅ 影响行数 >N → 需批准
```

**② 类别类**

```
✅ 涉及跨境数据传输 → 转法务
✅ 触及受保护特征 → 停止，转 HR
✅ 需要承诺退款/赔偿/折扣 → 人工
```

**③ 状态类**

```
✅ champion 离职 → 48 小时内高管介入
✅ 任一健康分维度为 0 → 升级
✅ ⭐ 某个单元反复失败 → 停下来交人工
```

**④ 不可逆类**

```
✅ 删除 / force push / 生产部署 → 批准门
✅ 阻断生产流量 → 批准门
```

呼应 `approval-gates.md`（**`skill-governance`**）与
`customer-success-playbook.md`（**`skill-domain-biz`**）的
分级告警表。

## 升级包该带什么

```
□ ⭐ 当前已完成什么（产物路径）
□ ⭐ 触发升级的具体条件（哪一条、数值多少）
□ ⭐ 已尝试过什么、结果如何
□ ⭐ 建议的下一步（带负责人建议）
□ ⭐ 相关证据（file:line、日志片段、ID）
```

> ⭐ **第二条最关键**：
> 收到升级的人第一句是"为什么找 me"——
> 升级包要直接回答。

呼应 `handoff-protocol.md`：
交接包的五个字段在升级场景同样适用。

## 三条配套规则

**① 升级后不要继续自动推进**

```
□ ⭐ 交出去了就等——不要一边等人一边继续做
□ 否则人会收到一个"已经变了"的升级包
```

**② 升级次数要设上限**

```
□ ⭐ 反复升级会让人麻木
□ 设：同一任务最多升级 N 次，超出则整体转人工
```

呼应 `error-handling.md`（**`skill-crafting`**）的
**重试要有最大次数**——同一条纪律。

**③ 升级要有回执路径**

```
□ 人做了决定之后，agent 怎么知道？
□ ⭐ 写进状态文件（呼应 idempotency-resume.md 的批准持久化）
```

## 一个反直觉的提醒

> ⭐ **升级太少和太多都是问题。**

```
升级太少 → 该拦的没拦住
升级太多 → ⭐ 人开始闭眼点确认，门等于不存在
```

呼应 `approval-gates.md` 的**过犹不及**：
**护栏只拦不可逆操作，才能保住门的效力**。
