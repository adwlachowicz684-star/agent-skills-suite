# 自动化：Hooks / 定时 / 技能的分工

> 技能用熟之后，下一个追求就是**自动化**——
> 不用手动输入，让它在该跑的时候自己跑。

## 四种机制的抽象粒度

| 机制 | 解决什么 | 粒度 | 例子 |
|---|---|---|---|
| **Hooks** | **每次 X 事件发生就该做什么** | 工具调用 / turn / 会话级 | 每次写文件前做安全检查 |
| **Skills** | **完整流程该怎么走**（需模型判断） | 任务级 | 完整部署该怎么走 |
| **/loop** | **会话内的间隔轮询** | 会话内 | 等待部署完成时轮询 |
| **定时任务 / Routines** | **我不在场时也要跑** | 脱离会话 | 每天早 8 点生成日报 |

> ⭐ **各层把"抽象粒度"匹配到合适的任务上。**

**只用一层会怎样**：

| 只用 | 后果 |
|---|---|
| 只用 Hooks | **把太多逻辑塞进钩子**——脚本臃肿、不可维护 |
| 只用 Skills | **每个动作都要用户手动触发** |
| 只用 /loop + 会话 | **离开电脑就停摆** |

## 三问决策法

> 依次问自己，**通常 5 分钟内能定**。

```
Q1: 这件事该在哪个事件上发生？
    能定位到 PreToolUse / PostToolUse 等具体事件 → 优先 Hooks
    定位不到 → 它可能不是事件驱动的，转 Q2

Q2: 这是不是一套需要模型判断的步骤？
    是 → Skills 更合适
    （模型擅长按上下文决定是否调用，但不擅长保证每次都发生）

Q3: 这件事需要在我不在场时运行吗？
    需要 → 定时任务 / Routines
    "看着跑"就行 → /loop
```

**速查**：

```
纯确定性的事件反应      → Hooks
需模型按描述匹配的复杂流程 → Skills
会话内的间隔轮询        → /loop
脱离会话的计划/触发     → Routines / Cron
```

## 三层联动架构

| 层级 | 组件 | 职责 | 触发时机 |
|---|---|---|---|
| **L1** | **Hooks** | 实时事件监听 | `PreToolUse` / `PostToolUse` / `Stop` / `Notification` |
| **L2** | **定时任务** | 调度 | cron 表达式 / 固定间隔 |
| **L3** | **Skills** | **具体能力执行** | 被 Hooks / 定时任务调用 |

> **分工原则**：
> **Skill 负责"做什么"，Hook 负责"什么时候检查"。**
> **不要把检查逻辑写进 Skill——Hook 更适合做通用检查。**

**一个真实组合**（社区互动自动化，每天定时跑）：

```
Cron（每天）
  → 调用 Skills（列帖子 / 回复 / 搜文档 / 发帖）
  → Hook（监听任务完成，触发通知）
```

实测：完整一轮约 5 分钟，包含 1 次回复、2 次文档搜索、1 次发布。

> ⚠️ 一个实用细节：**会话级定时任务默认 7 天自动过期**。
> 需要长期运行要显式设持久化参数（如 `durable: true`）。

## 常见的错配

| ❌ 错配 | 症状 | ✅ 正确 |
|---|---|---|
| **把流程塞进钩子** | 脚本臃肿、不可维护 | 流程进技能，钩子只做事件反应 |
| **把钩子语义化进技能** | 技能想"保证每次都发生"，但它做不到 | 保证性交给 Hook |
| **把定时任务当 /loop 的替代** | 离开电脑就停摆，或反之过度工程 | 按 Q3 分 |
| 自动化跑起来就不管了 | **跑飞了** | 见下节护栏 |

> ⭐ **一条核心原则**：
> **模型擅长按上下文决定是否调用，但不擅长保证每次都发生。**
> 需要"保证"就别指望技能。

## 渐进式放权四阶段

> 别直接 Yolo——**逐步建立信任**。

| 阶段 | 配置 | 做法 |
|---|---|---|
| **1. 手动** | default 模式 | 每次操作都确认，观察行为 |
| **2. 半自动** | acceptEdits | 加 PostToolUse Hook 自动跑测试，**保留关键操作的确认** |
| **3. 高度自动** | dontAsk | 完善的 Hook 检查体系 + 限制工具范围（`--tools`） |
| **4. 完全自动** | **仅限沙箱** | devcontainer 或虚拟机，**绝不用于生产环境** |

## 护栏：自动化越久越需要

> **"先跑起来，再优化"是对的。
> 但"跑起来"之后第一件事就是加护栏。**

**三个值得加的 Hook**：

| Hook | 作用 |
|---|---|
| **PostToolUse** | 每次 MCP 调用后记日志——上游返回异常数据时**能追溯** |
| **Stop** | 主流程完成后兜底触发（如自动推送） |
| **PreToolUse** | **拦截异常调用**——如 agent 因故要连调 50 次 API，直接拦掉，避免额度耗尽 |

> 第三条最有价值：**它是成本与安全的双重护栏**。

**其他护栏**：

```
□ 事件去重——避免同一事件触发多次执行
□ 错误重试——定时任务失败时自动重试
□ 日志审计——记录每次执行的详细信息
□ 逃生通道——知道怎么快速停止，保留 git 回退手段
□ 测试 Hook 本身——避免 Hook 误拦截
```

> ⚠️ **Hook 本身也要测**。
> 一个误拦截的 Hook 会让整条流水线静默卡住。

**关于推送**：定时任务的结果通常要送到人能看到的地方（Slack / 飞书群等），
**"跑完了但没人看到"等于没跑**。

## 自查

```
□ 是否用三问决策法选对了机制（而非一律用技能）？
□ 检查逻辑是否错放进了技能（该在 Hook）？
□ 是否依赖技能去"保证每次都发生"（做不到）？
□ 长期任务是否设了持久化（默认 7 天过期）？
□ 是否加了 PreToolUse 拦截异常高频调用？
□ 是否有事件去重、错误重试、日志审计？
□ 是否有逃生通道（能快速停止 + git 回退）？
□ 是否测试过 Hook 本身不会误拦截？
□ 结果是否送到了人能看到的地方？
□ 是否按四阶段渐进放权（而非直接完全自动）？
```
