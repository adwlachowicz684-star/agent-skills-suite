## 1. ⭐⭐ 一条前置原则：工作流内优先

> ⭐⭐ **如果用户已经在某个流程中间了，⭐ 该流程内的技能⭐ 自动加权。**
> ⭐⭐⭐ **上下文连贯 ⭐ 比能力强弱更重要。**

```
比喻很贴切：
⭐⭐⭐ 你正在做手术，⭐ 不该因为"隔壁科室也会缝针"就把病人推过去
```

> ⭐⭐ 这条与我们已有的 `routing-tiers-and-arbitration.md` 的
> "显式指定 > 精确匹配 > 特异优于通用"不冲突——
> ⭐⭐ 它是一个⭐ 额外的加权维度：
> **同等条件下，已经在跑的那个流程里的技能优先。**
>
> ⭐⭐ 这解释了"为什么有时换了个更强的技能反而更差"——
> 因为⭐ 换过去要重新建立上下文。

## 2. ⭐⭐⭐ 排他型

```
两个技能的⭐ 任务方向根本不一样，⭐⭐⭐ 必须二选一
```

**例子**：

```
"代码审查" 和 "代码修改" 同时命中
→ ⭐⭐⭐ 你不能⭐ 一边审一边改，⭐ 得先定下来到底要干嘛
```

**解法**：

> ⭐⭐ `exclusive_group`——⭐⭐⭐ **同组只留优先级最高的。**

> ⭐⭐ 这与 `conflict-precedence-four-types.md` 的
> "技能 vs 技能 → 更具体的赢"是互补的：
> 那条是⭐ 运行时裁决，
> ⭐⭐⭐ 这里是⭐ 声明期预防——
> **作者事先声明"这两个不能同时生效"，就不需要运行时猜。**

---

## 3. ⭐⭐⭐ 组合型

```
⭐⭐ 多个技能⭐ 不是在抢活，而是⭐ 可以串起来
例：先"检索资料" → 再"提炼重点" → 最后"生成报告"
```

**关键警告**（这条最实用）：

> ⭐⭐⭐ **但⭐ 顺序不能乱——
> ⭐⭐⭐ ⭐ 如果没有⭐ 预定义的串联顺序，
>    ⭐⭐⭐ 三个技能⭐ 同时跑，输出互相覆盖，
>    ⭐⭐⭐ ⭐ 结果⭐ 比只跑一个还差。**

> ⭐⭐⭐ 这给了我们已有的"顺序敏感"一条⭐ 具体后果：
> `composition-patterns-types.md` 说"同一技能集，加载顺序不同结果就不同"，
> ⭐⭐ 这里说得更狠：**无序并行 = 比只用一个更糟**（不是持平，是更差）。
>
> ⭐⭐ 所以 ⭐ **给组合型冲突的解法不是"选一个"，而是"定顺序"**。

---

## 4. ⭐⭐⭐ 确认型

```
⭐⭐ 多个技能都说得通，但⭐⭐⭐ 系统自己判断不了
```

**例子**：

```
用户说"帮我处理这个文档"
→ ⭐⭐⭐ 这到底是要⭐ 总结、改写、还是⭐ 抽取结构化字段？
```

**解法**：

> ⭐⭐⭐ **最稳的做法不是硬猜，⭐⭐⭐⭐ 是⭐ 追问一句。**

**两类常见错误**（这段诊断很准）：

> ⭐⭐⭐ **很多系统的问题不是没有消解逻辑，
> ⭐⭐⭐ ⭐ 而是⭐ 把所有冲突都当排他型处理了：
>    ⭐⭐ 该组合的被硬选了一个
>    ⭐⭐⭐ 该确认的被硬猜了一个**

> ⭐⭐⭐ 这与 `conflict-precedence-four-types.md` 反模式表里的
> "总是提问 = 浪费时间"要合起来看，才完整：
> ```
> 优先级能裁 → 裁（别问）
> 能组合     → 定顺序（别选一个）
> 都裁不了   → ⭐⭐ 追问（别硬猜）
> ```
> ⭐⭐⭐ 三种冲突三种处理，⭐ 混用就出错。

## 5. ⭐⭐⭐ 降级层：三件事

> ⭐⭐⭐ **"这是⭐ 我见过最多 agent 缺的一层。"**

```
路由不清，硬选一个
多个候选差不多，随便挑一个
执行到一半发现信息不够，也硬往下做
```

**降级就三件事**：

```
① ⭐⭐⭐ 意图不清就追问
   ⭐⭐⭐ ⭐ 别猜——⭐⭐⭐ 猜错了比不做更糟

② ⭐⭐⭐ 前置条件不满足就回退
   例：某个技能依赖特定工作流状态，但用户根本没初始化
   ⭐⭐ 别硬跑，⭐⭐⭐ 回到基础能力处理就好
   具体例子：你装了 GSD 全家桶，但项目里没有 .planning/ 目录
        ⭐⭐⭐ gsd-progress 跑出来的东西⭐ 毫无意义

③ ⭐⭐ 风险高就加一层确认
   要删数据？要发通知？要执行不可逆操作？⭐⭐ 停一下让用户确认
```

**一句值得单独记住的话**：

> ⭐⭐⭐ **"真正毁掉一个 agent 口碑的，⭐⭐⭐ ⭐ 从来不是'它不会'，
> ⭐⭐⭐ 而是——⭐⭐⭐ '它明明不会，还特别自信地瞎做了'。"**

> ⭐⭐⭐ 这是⭐ 第五个独立来源在说同一件事：
> ```
> 1. priority-override-layers：结构正确的废话
> 2. skill-rot-rollback：自信的漂移读起来就像改进
> 3. prompt-vs-skill-failure-modes：错得自信而正确
> 4. seven-contracts：别把 HTTP 200 当成功
> 5. ⭐⭐⭐ 本份："它明明不会，还特别自信地瞎做了"
> ```
> ⭐⭐⭐ 五个来源、五种说法、同一件事。
> **这已经是整套库里被反复验证得最多的一条结论。**

## 6. ⭐⭐⭐ 用流水线解决"指令方向相反"

**一个典型冲突**：

```
Skill A (Creative)："尽可能发挥想象力，不受拘束"
Skill B (Legal)：   "严谨，字斟句酌，不要过度承诺"
```

> ⭐⭐⭐ 这两条⭐ 不是"谁更具体"的问题，⭐⭐ 是⭐ 方向相反。

**解法不是裁决，是排序**：

```
⭐⭐⭐ 流水线编排：
   Creative 先生成 → ⭐⭐ Legal/Security 再审核把关

⭐⭐⭐ ⭐ Legal/Security 通常充当⭐ "守门员"，放在⭐⭐⭐ 流水线末端
```

> ⭐⭐⭐ 这个模式很值得记住，因为它给出了一类冲突的⭐ 结构性解法：
> **方向相反的两个技能不是二选一，而是⭐ 分阶段。**
> 生成在前、约束在后——
> ⭐⭐ 这也正是 `code-review-trust.md` 的"生成者 ≠ 校验者"
> 与 `frontend-ui-skills.md` 的"生成完派框架专家校验"的通用形态。

**另一个相关模式（动态路由）**：

```
用户问"我的包裹丢了，怎么赔付？"  → Router 激活 Refund Policy Skill
用户接着问"那我账户里还有多少钱？" → ⭐ Router ⭐ 切换到 Account Info Skill
```

> ⭐⭐ 多轮对话里路由要⭐ 跟着意图走，而不是锁死在第一轮选的技能上。

## 速查

```
□ ⭐⭐ 工作流内优先：⭐⭐⭐ 上下文连贯 ⭐ 比能力强弱更重要（做手术别换科室）

□ ⭐⭐⭐ 三型：
   ① 排他型 → ⭐⭐ exclusive_group（⭐ 声明期预防，非运行时裁决）
   ② 组合型 → ⭐⭐⭐ ⭐ 定顺序（⭐⭐⭐ 无序并行 = 比只跑一个还差）
   ③ 确认型 → ⭐⭐⭐ ⭐ 追问（别硬猜）
   ⭐⭐⭐ ⭐ 常见错误：把三种都当排他型处理

□ ⭐⭐⭐ 降级三件事：意图不清就追问 · 前置不满足就回退 · 风险高就加确认
   ⭐⭐⭐ "猜错了比不做更糟"
□ ⭐⭐⭐⭐ "毁掉口碑的不是'它不会'，是'它明明不会还特别自信地瞎做了'"
   ⭐⭐⭐ ——第五个独立来源，整套库里被验证最多的一条

□ ⭐⭐⭐ 指令方向相反 → ⭐⭐ 不是裁决，是⭐ 流水线（生成在前、守门员在末端）
```

**一句话**：

> ⭐⭐⭐ **冲突有三种——排他型用 exclusive_group、组合型定顺序（无序并行比只跑一个还差）、确认型追问；
> 而最常见也最致命的错误是把三种都当排他型处理：该组合的被硬选一个、该确认的被硬猜一个。**
