## 1. 本质区别：多一本手册 vs 多一个人

```
Skill     = 多一本手册   → 知识注入，人还是那个人
SubAgent  = 多一个人     → 任务委托，对方有自己的上下文和决策空间
```

> ⭐ **判断问题**：这件事需要**另一个人来承担**，还是只需要**多一本手册**？

| | Skill | SubAgent |
|---|---|---|
| 解决 | 怎么做 | 谁来做 |
| 机制 | 注入上下文 + 指令 | 隔离执行 + 返回结果 |
| 增强 | 知识 | ⭐ 分工 |

## 2. 两个组合方向

### 方向 A：SubAgent 含 Skill（最常见）

在子代理定义的 frontmatter 里加 `skills` 字段预加载：

```yaml
skills: ["api-generating"]
```

> **SubAgent 是老板，Skill 是工具书。**
> 创建时自动加载，子代理按技能提供的步骤和模板执行。

### 方向 B：Skill 含 SubAgent

通过 `context: fork` 让技能自动派遣子代理执行。

> **Skill 是老板，SubAgent 是执行者。**
> SKILL.md 的正文内容就是它的任务指令。

## 3. 三种实战模式

### 模式一：预加载（方向 A 的单次应用）

```
子代理预加载 1 个或多个 skill
→ 像受过培训的专业技师，上岗即具备完整知识体系
```

配置就是 `skills: ["skill-a", "skill-b", "skill-c"]`。

### 模式二：⭐ 派遣执行（`context: fork`）

> ⭐ **主对话保持干净，不被中间过程污染。**

适合三种场景：

```
① 深度探索代码库（中间过程不需要用户看到）
② 批量生成文档（输出量很大）
③ ⭐ 安全隔离操作（不应影响主对话状态）
```

`agent` 字段决定子代理类型：

```
Explore  只读探索
Plan     规划
默认     通用类型
```

### 模式三：流水线编排

```
阶段1  路由扫描器子代理 + 路由检测 skill  → 扫描所有 API 端点
阶段2  文档生成器子代理 + 文档编写 skill  → 为每个端点生成文档
阶段3  质量检查器子代理 + 检查 skill      → 验证文档完整性
```

> ⭐ **每个阶段的输出作为下一阶段的输入**——
> 与 `composition.md` 的"中间产物落文件"一致。

## 4. ⭐ 终极价值

```
同一个 agent，注入不同 skill，变成不同专家：

  api-generating        → API 文档专家
  security-review       → 安全审查专家
  financial-analyzing   → 财务分析专家
```

> ⭐ **Skill 是可拆卸的知识模块，Agent 是通用的执行平台。**

所以：

```
Skill 提供知识（怎么做）
SubAgent 提供隔离（谁来做）
⭐ 组合起来得到的不是更多工具，而是一个可按需组装的专家团队
```

## 速查

| 需求 | 用 |
|---|---|
| 只需要知识 | Skill |
| 需要隔离/并行/独立上下文 | SubAgent |
| 子代理需要专业知识 | ⭐ SubAgent + `skills:` 字段 |
| 主对话要干净 | ⭐ `context: fork` |
| 多阶段 | 流水线，输出落文件 |
