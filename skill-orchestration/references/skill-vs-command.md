# 技能 vs 斜杠命令：100% 触发 vs 按需触发

> ⭐ **这是最容易被选错的二分之一。**
> 选错了会出现"关键流程时灵时不灵"。

## 根本差别

```
技能      模型根据 description 判断是否相关
          ⭐ 概率性触发

斜杠命令  用户显式输入 /command
          ⭐ 100% 触发
```

> 这个差别决定了它们的分工：
> **技能是"它该自己想到"，命令是"我要它做"。**

## 判据

> ⭐ **关键流程必须用命令，辅助能力才用技能。**

展开：

```
用命令：
  □ ⭐ 漏做会有后果的流程
  □ 需要在固定时刻执行（如发布前）
  □ ⭐ 用户明确知道自己要做什么

用技能：
  □ 用户可能没意识到有这个能力
  □ ⭐ 触发时机由上下文决定，不由用户决定
  □ 漏做不会有严重后果（下次还能补）
```

反过来说：**如果一个流程漏做会出事，
把它做成"靠模型想起来"的技能，就是在赌。**

## 对照表

| | 技能 | 斜杠命令 |
|---|---|---|
| 触发方 | 模型 | ⭐ 用户 |
| 触发可靠性 | 概率性 | ⭐ 100% |
| 适合 | 辅助能力、程序性知识 | ⭐ 关键流程 |
| 漏做的后果 | 通常可补 | ⭐ 可能出事 |
| 可发现性 | ⭐ 模型自动想到 | 用户要记得有它 |

## 一个混合用法

两者不是互斥的，一个常见且有效的组合：

```
命令   /review-pr      ——用户显式发起，100% 执行
技能   security-review ——模型在看到认证/输入处理代码时自动想到
```

> ⭐ 分工是：**命令保证"要做的做了"，技能保证"该想到的想到了"。**

另一个组合：

```
命令负责启动流程
流程内部调用技能
```

即：**入口确定性，过程智能化**。

## 常见错误

**① 把关键流程做成技能**

```
❌ "发布前检查"做成技能
   ⭐ 漏了一次就是一次事故
✅ 做成 /pre-release-check
```

**② 把辅助能力做成命令**

```
❌ /explain-this-error
   ⭐ 用户不会记得有它，也就永远不会用
✅ 做成技能，模型看到错误时自动用
```

> 判据：**用户会不会"想起"要输入这个命令？**
> 不会 → 应该是技能。

**③ 两者做重复了**

```
❌ /review-pr 命令 + pr-review 技能，内容一样
   ⭐ 两份会漂移，漂移的规则比没有规则更糟
```

（呼应 `instruction-layering.md`：同一份内容不要放三处。）

**④ 用技能承载"必须在此时执行"的约束**

```
❌ 技能里写"每次提交前必须跑 lint"
   ⭐ 模型可能不触发
✅ 用 PreToolUse hook 或 CI 闸门
```

> 这条最关键：**需要 100% 保证的规则，
> 既不能靠技能，也不能只靠命令，要靠 hook 或 CI。**
> （见 `hook-risk.md`。）

## 自查

```
[ ] 这个流程漏做会有后果吗？→ 用命令（或 hook/CI）
[ ] 用户会主动想起要调用它吗？
    不会 → 用技能
[ ] ⭐ 有没有两者内容重复的？
[ ] 需要"每次都必然执行"的约束，放在哪一层？
    技能 = 概率；命令 = 用户保证；hook/CI = 系统保证
[ ] ⭐ 命令入口 + 技能过程的组合，是否更合适？
```

## 一条补充

有些运行时还支持**禁用模型自动调用**
（如 `disable-model-invocation: true`），
让一个技能只能被显式调用。

> ⭐ 这实际上把"技能"变成了"命令"——
> **适合那些内容复杂、但必须显式触发的东西**。

用法示例见 `fork-context-skill.md`：
评审类技能通常这么配，因为它会消耗较多上下文，
不该被模型随手触发。
