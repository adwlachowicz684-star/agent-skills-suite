## 1. ⭐ 什么留下、什么返回

```
辅助工作——文件读取、搜索结果、中间草稿、多步工具链
   ⭐ 全部留在 fork 内部

主线程只看到：
   ⭐ 一次技能调用 + ⭐ 一个紧凑的结果
   ——不是产生它的那条轨迹
```

> 官方给的问题描述很精准：
> "当你用一个执行多步工具调用或拉取大量参考资料的技能时，
> ⭐ **那些辅助内容会挤占你的主聊天上下文，
> 并降低后续响应的质量**。"

**选择单位是"技能调用"，不是任务或轮次**——同一模型，隔离上下文。

---

## 2. ⭐ 三个条件全成立才 fork

```
① ⭐ 技能产生的辅助 token 远多于它的最终结果
    （搜索密集、规划、多步推理、长工具链）
② ⭐ 结果是自包含的
    ——用户通常不会引用中间状态来追问
③ ⭐ 技能正文包含明确的逐步指令，而不只是参考资料
```

> ⭐ **任何一条不成立，留在主上下文才是正确的默认值。**

配置：

```yaml
---
name: deep-research
description: Research a topic thoroughly across the codebase
context: fork
agent: Explore
---
```

内置 agent 类型：

```
Explore          Haiku，只读——快速代码库搜索
Plan             只读——规划前的研究
general-purpose  完整工具
```

> ⭐ **VS Code 1.118（2026-04-29）也以同样的 `context: fork` 提供了
> "Dedicated Context for Skills"**——这个机制不止一家。

## 3. ⭐ 六种别 fork 的情况

**① 纯参考型技能**

> ⭐ **`context: fork` + 一个由分类法/模板/知识构成的正文 = 空输出。**
> 子代理把正文当成它的任务；**没有指令，就无事可做**。

这与 `fork-official-details.md` 那条完全一致。

**② 追问敏感性**

```
用户经常对中间发现采取行动（"现在重构第三个调用方"）
⭐ fork 恰好丢弃了下一轮需要的状态
```

**③ 辅助足迹很小**

```
⭐ 子代理的框架开销（system prompt、工具定义、结果包装）
  ⭐ 可能超过 fork 省下的部分
```

**④ 需要确定性的输出**

```
安全审计、diff 审查等
⭐ 用户必须看到原始工作的场合，无法容忍被摘要化
```

**⑤ 调试迭代期**

> ⭐ **在编写技能的过程中，内部轨迹需要可见。
> ⭐ 等技能稳定后再 fork。**

**⑥ 自派发递归**（见下）

## 4. ⭐ 自派发递归（已知 bug）

> ⭐ **一个 `context: fork` 的正文，如果长得像技能规格
> （`# Name:` 加标语式标题、第三人称叙述、一个 `ARGUMENTS:` 块），
> ⭐ 会被 fork 出去的子代理模式匹配成"派发请求"，
> ⭐ 于是重新调用自己，而不是执行。**
> **没有重入保护就会循环到被杀掉。**

**修法**：

> ⭐ **把 fork 的正文写成直接的命令式步骤。**

> 这是个很隐蔽的坑——**你写得越"像一份规范"，越容易触发**。

## 5. 两种组合模式

| | 子代理预加载技能 | 技能授权子代理 |
|---|---|---|
| 配置 | 子代理 frontmatter 的 `skills:` | 技能 frontmatter 的 `context: fork` + `agent:` |
| 设计核心 | ⭐ **定义角色**（role-based） | ⭐ **定义任务**（task-based） |
| 知识关系 | 知识是代理的背景资产，启动即拥有 | 技能是执行指令，按需分叉 |
| 复用单元 | 代理是长期存在的执行主体 | ⭐ **技能是复用单元，fork 只提供环境** |
| 适用 | 固定角色：始终遵循某规范的审查代理 | 已有成熟技能库，想避免污染主窗口 |

```yaml
# 模式一：子代理预加载
---
name: api-developer
skills:
  - api-conventions
  - error-handling-patterns
  - auth-patterns
---

# 模式二：技能 fork
---
name: deep-research
context: fork
agent: Explore
---
```

**怎么选**：

```
· ⭐ 构建新功能 → 优先创建 Agent（最灵活）
· ⭐ 已有成熟技能库、只想隔离执行 → 用 context: fork
```

> ⭐ **两者底层编译到同一个机制：技能内容被注入 agent 上下文。**

**核心分工**：

```
⭐ 主会话 = 决策者
⭐ 子代理 = 执行沙盒，只回传摘要
```

以及一句好比喻：

```
Subagent 控制"用几个上下文"
Skill     控制"往上下文里放什么"
```

## 速查

```
□ ⭐ 辅助工作留在 fork 内；主线程只看紧凑结果
□ ⭐ 三条件全成立才 fork（辅助多 / 结果自包含 / 正文有明确指令）
□ ⭐ 任一不成立 → 留在主上下文是默认值

❌ 六种别 fork：
□ 纯参考型正文（→ 空输出）
□ 追问敏感（丢掉下轮要的状态）
□ 辅助足迹小（开销 > 省下的）
□ 需确定性输出（审计不能摘要化）
□ ⭐ 调试期（等稳定后再 fork）
□ 自派发递归风险

□ ⭐ fork 正文写成直接命令式步骤（别写得像技能规格）
□ 子代理预加载 = 定义角色；技能 fork = 定义任务
□ ⭐ 新功能 → 建 Agent；已有技能库 → fork
□ 主会话决策，子代理只回传摘要
```

**一句话**：

> ⭐ **fork 是把脏活关进另一个房间——
> 但如果你要的就是看到脏活的过程（审计、调试），就别关。**
