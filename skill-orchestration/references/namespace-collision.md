## 1. 三种典型表现

技能超过 5 个，冲突几乎必然发生：

```
① 触发了错的技能      —— 两个 description 语义重叠
② 同时触发多个        —— 行为不可预期
③ ⭐ 一个都没触发     —— 两个技能互相"稀释"了触发概率
```

> ⭐ 第三种最隐蔽：看起来是"技能没写好"，
> 实际上是**两个技能都在场，各自降低了对方的置信度**。

**根因统一**：description 语义重叠。

---

## 2. 三个解法

### ① 拆职责（最根本）

把"数据查询"和"报告生成"拆成两个独立技能，
用 description 明确边界：**什么场景用我，什么场景不用我**。

```
❌ 一个 data-skill 又查又渲染
✅ query-data（只查） + render-report（只渲染）
```

### ② 用 allowed-tools 做权限隔离

> ⭐ 即使 description 写得再好，模型也可能"跨界"。
> `allowed-tools` 是**第二层防护**。

```
查询技能   → 不给写权限
报告技能   → 不需要数据库直连
```

这不只防冲突，还顺带限制了爆炸半径（与 `least-privilege.md` 一致）。

### ③ 设计手动触发口令

对于**天然有歧义**的场景：

```
用户说 "查数据 [描述]"  → 一定走查询技能
```

> ⭐ **这比依赖模型自动判断可靠得多**——
> 歧义场景不是靠优化 description 能解决的，承认它、给它一个明确入口。

## 3. 命名空间设计三招

### 第一招：description 里写"专属信号"

每个技能除了写"什么时候触发"，还要写**哪些信号属于我**。

```
周报技能：    "用户提到'本周工作'时触发本技能"
会议纪要技能："用户提到'会议内容整理'时触发本技能"
```

> 两者都用触发场景字段把**专属信号词**写清楚，
> 模型就能根据话里的信号词精确分流。

### 第二招：⭐ 排除声明互相点名

场景确实相近时，**各自的"不适用"段落要互相点名**：

```
周报技能：    "本技能不处理会议纪要整理，那属于 meeting-notes 的职责"
会议纪要技能："本技能不处理周报生成，那属于 weekly-report 的职责"
```

> ⭐ **"你中有我、我中有你"的互斥声明，让模型在边界场景做出明确选择，
> 而不是随机触发一个。**

这与 `activation-rate.md` 那条"NOT for X → 用 Y 代替是最强路由提示"完全一致——
**一条同时治两个病**。

### 第三招：维护"技能地图"

在技能体系里维护一份索引（放常驻 reference 或笔记），列出：

```
每个技能的：名称 · 触发信号 · 擅长场景 · 不适用场景
```

两个作用：

- 给模型的**路由参考**
- ⭐ 给你自己的**记忆清单**——**新增技能时先查索引，避免重复**

这与 `skill-inventory.md`（治理的前提是知道有什么）是同一件事在个人/小团队的轻量版。

## 4. ⭐ 遮蔽而非移除

来自 Manus 的实践，这条对工具管理通用：

> ⭐ **动态 add/remove 工具会破坏 KV cache 和模型的"世界观"。**
> **遮蔽（masking）是在不改定义的前提下限制选择空间，保持状态一致性。**

正确做法：

```
✅ 工具定义始终存在，用 logit masking 在解码层限制可选
❌ 动态增删工具定义
```

配套的三层策略（工具爆炸时的通用解法）：

| 层 | 手段 | 作用 |
|---|---|---|
| 基础设施 | Agent Skills 模块化封装 | 命名空间隔离、按需加载 |
| 决策优化 | RAG + 意图识别 | ⭐ 把候选集缩到 **3–8** |
| 执行控制 | 遮蔽 + 上下文工程 | 限制选择空间而不改定义 |

> 冷启动阶段工具少时，**先用规则分组**（文档/数据/API），再逐步细化。
> 不要一上来就上向量检索。

## 5. 三个工程坑

### ① 参数命名冲突

真实案例：

```
技能 A 用 start_date
技能 B 用 begin_date
→ 编排层传参时经常搞混
```

**修法**：

```
✅ 所有技能入参统一 snake_case
✅ ⭐ 入参必须是扁平结构，不用嵌套对象
```

### ② 超时不能一刀切

```
数据量大 → 几分钟
简单报告 → 几秒钟
```

统一 timeout 的后果：**要么快技能等太久，要么慢技能被频繁掐断**。

**修法**：每个技能单独配 timeout，并在 description 里写明"这是长耗时技能"，
⭐ **让模型在执行前先告知用户需要等待**（与 `progress-reporting.md` 一致）。

### ③ 脚本里必须用相对路径

绝对路径换机器就断——这与 《skill-scripting》`script-engineering.md` 一致，
但在**多技能编排**时更容易踩：每个技能都自带路径假设，组合起来必冲突。

## 6. 正向模式：串联

冲突要防，但更常见的是**多个技能串起来完成复杂任务**：

```
用户："查上周销售数据，做分析报告，发到钉钉群"
        ↓
Skill A（数据查询）→ Skill B（报告生成）→ Skill C（通知）
```

编排原则（与 `composition.md` 一致）：

```
✅ 链式调用：前一个的输出就是后一个的输入
❌ 让模型自行决定调用顺序
```

复杂场景可以上轻量 DAG，⭐ **但前提是技能足够原子化、接口足够清晰**——
否则 DAG 会变得难以维护。

## 速查

| 症状 | 处置 |
|---|---|
| 触发了错的技能 | 拆职责 + 专属信号词 |
| 同时触发多个 | allowed-tools 权限隔离 + 互斥声明 |
| ⭐ 一个都没触发（互相稀释） | ⭐ description 重叠，加互斥点名 |
| 天然有歧义的场景 | 设计手动触发口令，别硬优化 |
| 参数传错 | 统一 snake_case + 扁平结构 |
| 长任务被掐断 | 每技能单独 timeout + description 里预告 |
| 工具太多拖垮性能 | ⭐ 遮蔽而非移除 + RAG 缩候选到 3–8 |
