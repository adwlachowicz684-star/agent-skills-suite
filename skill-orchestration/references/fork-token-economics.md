## 1. ⭐⭐⭐⭐ token 经济学表

| 模式 | ⭐ 主上下文成本 | ⭐⭐⭐ 压缩后 |
|---|---|---|
| 内联技能 | ⭐⭐ 正文全进主上下文 | ⭐⭐⭐ 5,000 tokens |
| fork 子代理 | ⭐⭐⭐ **零**（隔离运行） | ⭐⭐⭐ 仅摘要 |
| 组合（技能 + 子代理） | ⭐⭐⭐⭐ 主上下文零 + fork 内全量 | ⭐⭐⭐ 仅摘要 |
| 多个 fork | ⭐⭐⭐⭐ 每个 fork 各零 | ⭐⭐⭐ 每 fork 一份摘要 |

> ⭐⭐⭐⭐⭐ 这张表⭐ 第一次把四种模式的成本⭐ 放在同一张表里，
> ⭐⭐⭐⭐ 而⭐ 最关键的一格是⭐ **"组合"**：
> ⭐⭐⭐⭐⭐ ⭐ 它的主上下文成本是零，⭐ 但 fork 内部仍加载⭐ 完整技能正文。
>
> ⭐⭐⭐⭐⭐ 这解释了⭐ 一个此前含糊的问题：
> ⭐⭐⭐⭐⭐ **"派子代理 + 给它挂技能"为什么是⭐ 强模式**——
> ⭐⭐⭐⭐ 因为⭐ 你既拿到了⭐ 隔离（主上下文零成本），
> ⭐⭐⭐⭐ ⭐ 又拿到了⭐ 共享（技能正文在 fork 内生效）。
> ⭐⭐⭐⭐⭐ ⭐ 这正是"技能=共享、子代理=隔离"⭐ 两个收益⭐ 同时拿到。
>
> ⭐⭐⭐⭐ 而"多个 fork"那一行⭐ 意味着：
> ⭐⭐⭐⭐⭐ **并行 fork 的⭐ 上下文成本是⭐ 线性叠加在 fork 侧、主上下文仍是零**——
> ⭐⭐⭐⭐ 所以⭐ 并行探索是⭐ 少数"变多但不挤主上下文"的手段
> （与 `skill-chaining-composition.md` 的"叠加不覆盖"不矛盾：
> ⭐⭐ 叠加说的是⭐ 同一上下文内，fork 说的是⭐ 另起上下文）。

**压缩预算的补充数据**：

```
⭐⭐⭐ 每技能保留前 5,000 tokens，⭐ 总预算 25,000
⭐⭐⭐ 技能内容⭐ 在压缩后存活（survives compaction）—⭐ 但只剩前 5,000
```

## 2. ⭐⭐⭐⭐ 坑一：只有准则没有任务 → 空输出

> ⭐⭐⭐⭐⭐ **"⭐ 最常见的错误。一个 `context: fork` 的技能，
> ⭐⭐⭐⭐⭐ ⭐ 如果正文是⭐ '遵循这些编码规范' 这类⭐ 准则，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 子代理⭐ 拿不到任何⭐ 可执行的任务 → ⭐⭐⭐⭐⭐ ⭐ 输出为空。"**

```
❌ "follow these coding standards"
✅ "Read files in src/auth/, check for SQL injection vulnerabilities,
    return a list of findings."
```

> ⭐⭐⭐⭐⭐ 机制解释很关键，值得单独记住：
> ⭐⭐⭐⭐⭐ **"⭐ 技能内容⭐ 会变成⭐ 子代理的提示词。"**
>
> ⭐⭐⭐⭐⭐ 也就是说：⭐⭐⭐ **fork 不是"派个人去干活"，
> ⭐⭐⭐⭐⭐ 而是⭐ 把你的正文⭐ 当成一份⭐ 完整的任务说明⭐ 交给它。**
> ⭐⭐⭐⭐⭐ 所以⭐⭐⭐⭐ **fork 型技能的正文必须写成⭐ 一份独立可执行的工单**，
> ⭐⭐⭐ 而不是⭐ 一段"做事的原则"。
>
> ⭐⭐⭐⭐⭐ 这与 `context-isolation-fork.md` 那条"fork 正文要写成⭐ 直接的命令式步骤"
> ⭐⭐⭐⭐ ⭐ 是⭐ 同一结论——而这里⭐ 给出了⭐ 失败的样子（空输出）和⭐ 原因（正文=提示词）。

**agent 类型选错是同一类问题**：

```
Explore          ⭐ 只读（搜索、阅读、分析），⭐⭐ 不能改文件
Plan             ⭐ 创建结构化计划，能读，⭐ 不能改
general-purpose  ⭐ 全权限（读、写、执行）
自定义 agent     ⭐ 在 .claude/agents/ 里定义
```

## 3. ⭐⭐⭐ 坑二：fork 出来的写不了文件

```
症状：fork 的技能无法写文件
原因：用了 agent: Explore（只读）
修法：换 general-purpose 或自定义 agent
⭐⭐⭐⭐ ⭐ 但先想清楚：⭐⭐⭐⭐⭐ ⭐ "⭐ 文件修改⭐ 是否应该⭐ 留在主上下文，
   ⭐⭐⭐⭐⭐ ⭐ 只把⭐ 分析⭐ 委派出去？"
```

> ⭐⭐⭐⭐⭐ 最后那句反问⭐ 是本轮最实用的一条设计建议：
> ⭐⭐⭐⭐⭐ **委派分析、保留写入**——⭐⭐⭐ 因为⭐ 写入有副作用、
> ⭐⭐⭐ 且⭐ 需要主上下文的⭐ 完整判断力。
> ⭐⭐⭐⭐ 与 `seven-contracts.md` 的"⭐ 副作用要能被授权"、
> `allowed-tools-least-privilege.md` ⭐ 同源。

## 4. ⭐⭐⭐ 坑三：子代理"忽略" CLAUDE.md

> ⭐⭐⭐ **子代理⭐ 确实会加载项目的 CLAUDE.md。**
> ⭐⭐⭐⭐ 但如果 CLAUDE.md ⭐ 很大（接近 200 行），
> ⭐⭐⭐⭐ ⭐ 它会与⭐ 技能内容⭐ 争抢上下文空间。

```
修法：⭐⭐⭐ 两者都保持简洁
     ⭐⭐⭐⭐⭐ ⭐ 如果子代理⭐ 需要某些特定的 CLAUDE.md 规则，
     ⭐⭐⭐⭐⭐ ⭐⭐⭐ ⭐ 在⭐ 技能正文里⭐ 显式引用它们
```

> ⭐⭐⭐⭐⭐ 这修正了一个⭐ 常见误解——⭐ **不是"子代理读不到 CLAUDE.md"**
> （我们已有的 `subagent-skill-inheritance.md` 说"子代理不继承技能"，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 但⭐ CLAUDE.md 是⭐ 另一回事，⭐⭐⭐⭐⭐ ⭐ 它会被加载）。
> ⭐⭐⭐⭐ 真正的失败是⭐ **被挤掉**，不是⭐ 没加载。
> ⭐⭐⭐⭐ 不过⭐ 注意这个数字：⭐⭐⭐⭐⭐ **200 行**——
> 与 `context-file-selection.md` 里"300 行 CLAUDE.md 的代价"⭐ 量级一致，
> ⭐⭐⭐⭐ 而官方建议是⭐⭐⭐ **保持在 200 行以内**。

## 5. ⭐⭐⭐⭐ 内联技能挤出对话

```
⭐⭐⭐⭐ 一份 8,000 tokens 的技能正文，会⭐ 挤掉对话本身的可用上下文
⭐⭐⭐⭐⭐ ⭐ 症状：⭐⭐⭐⭐⭐ ⭐ 你注意到 Claude "忘了" 早期的消息
       → ⭐⭐⭐⭐⭐ ⭐ 这个技能⭐ 太大了，不适合内联使用
```

> ⭐⭐⭐⭐⭐ 这条给了⭐ 一个可观察的⭐ 诊断信号：
> ⭐⭐⭐⭐⭐ **"Claude 开始忘事" = ⭐ 你的内联技能太大了。**
> ⭐⭐⭐⭐⭐ 这是⭐ 此前没收过的——我们之前知道"技能大了会占上下文"，
> ⭐⭐⭐⭐ 但⭐ 没有把它⭐ 对应到一个⭐ 用户能直接观察到的症状上。
>
> ⭐⭐⭐⭐ 修法不是"删内容"，而是⭐ **换模式**：
> ⭐⭐⭐⭐ ⭐ 内联 → fork（主上下文成本归零）。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ **所以"技能太大"有两种解法，取决于⭐ 它到底需不需要主上下文**：
> ```
> · 需要共享 → ⭐ 拆分（拆成按需加载的 reference）
> · ⭐⭐⭐⭐⭐ 不需要 → ⭐⭐⭐ fork（压根不进主上下文）
> ```

## 速查

```
□ ⭐⭐⭐⭐ token 经济学：内联=全进主上下文(压缩后5,000) · fork=主上下文零(仅摘要)
   ⭐⭐⭐⭐⭐ 组合=主上下文零 + fork内全量 → ⭐⭐⭐⭐⭐ ⭐ 同时拿到隔离与共享（强模式）
□ ⭐⭐⭐⭐⭐ 坑一：⭐ 技能内容会变成子代理的提示词
   ⭐⭐⭐⭐⭐ ⭐ fork 正文只有准则没有任务 → ⭐⭐⭐⭐⭐ ⭐ 输出为空（最常见错误）
   ⭐⭐⭐⭐ ⭐ 必须写成⭐ 一份独立可执行的工单（读哪些文件、查什么、返回什么）
□ ⭐⭐⭐ 坑二：agent: Explore 只读 → 写不了文件
   ⭐⭐⭐⭐⭐ ⭐⭐ 先问：⭐⭐⭐⭐⭐ ⭐ 文件修改是否该留在主上下文，只委派分析？
□ ⭐⭐⭐⭐⭐ 坑三：⭐ 子代理会加载 CLAUDE.md（不是读不到！）
   ⭐⭐⭐⭐ 失败是⭐ 被挤掉（CLAUDE.md 近 200 行会与技能内容争抢）
   ⭐⭐⭐⭐⭐ 需要特定规则 → ⭐⭐⭐ 在技能正文里显式引用
□ ⭐⭐⭐⭐⭐ "Claude 开始忘事" = ⭐⭐⭐⭐⭐ ⭐ 内联技能太大
   ⭐⭐⭐⭐ 修法看⭐ 需不需要主上下文：需要→拆 reference；⭐⭐⭐⭐⭐ 不需要→fork
```

**一句话**：

> ⭐⭐⭐⭐ **"技能内容会变成子代理的提示词"——所以 fork 型技能的正文必须写成一份独立可执行的工单，只写"遵循这些规范"会导致空输出（最常见的错误）；而"派子代理并给它挂技能"之所以是强模式，是因为它主上下文成本为零、fork 内却仍加载完整技能正文，同时拿到了隔离与共享两个收益。**
