## 1. 五阶段

```
① 依赖分析    独立任务 → 并行批次；依赖任务 → 串行；关卡 → 同步点
② 团队指派    每个子任务选最优子代理配置
③ 并行派发    ⭐ 一条消息里发多个 Task 调用
④ 结果综合    只让紧凑摘要进入主上下文
⑤ 串行关卡    后续批次依赖前批结果时使用
```

## 2. 子任务 → 配置对照表

| 子任务类型 | `subagent_type` | Model | Tools |
|---|---|---|---|
| 代码库探索 | Explore | haiku | Read, Grep, Glob |
| 架构设计 | Plan | sonnet | 所有只读工具 |
| 多步实现 | general-purpose | sonnet/opus | 全部工具 |
| 简单文件搜索 | Explore | haiku | Glob, Grep |
| 代码审查 | Explore | sonnet | Read, Grep |
| 测试执行 | general-purpose | haiku | Bash, Read |

> ⭐ **按任务难度配模型**——探索用 haiku，实现用 sonnet/opus。
> 这是控制成本最直接的一档。

## 3. ⭐ 并行派发的正确写法

```
✅ 一条消息里包含多个 Task 工具调用（并行）
   Task 1: Explore 探索代码库
   Task 2: Explore 分析模式
   Task 3: general-purpose 执行测试

❌ 分多条消息顺序发（浪费时间）
   消息1 → 等结果 → 消息2 → 等结果
```

> ⭐ **并行与否取决于你写在哪一条消息里，不是取决于你发了几个。**

## 4. ⭐ 委派决策矩阵

| 条件 | 动作 |
|---|---|
| 任务有 3+ 个独立子任务 | 用 subagent-teams |
| ⭐ 上下文窗口已经很大 | ⭐ 委派**全部**探索 |
| 任务涉及多文件读取 | 委派给 Explore |
| 需要测试 + 实现 | ⭐ 分成不同 agent |
| ⭐ 单步且简单 | ⭐ **不要委派——开销不值** |
| 严格串行依赖 | 用串行关卡，不要并行 |
| 用户明确要求 | 总是用 |

> ⭐ 倒数第三条最容易违反：
> 简单任务委派的开销大于收益。

## 5. 子代理 prompt 该写什么

**必须包含**：

```
具体目标        到底要找什么/做什么
范围边界        聚焦哪些文件或区域
⭐ 输出格式      如何组织响应
上下文          前面步骤的相关信息
```

**必须不包含**：

```
不必要的背景（浪费子代理上下文）
一条 agent 里塞多个不相关任务（破坏专业化）
模糊指令（"看看代码库"）
```

**模板**：

```
[动作动词] [具体目标] in [范围]。Focus on [关键方面]。
Return: [结构化输出格式]。Context: [先前相关发现]。
```

## 速查

| 事 | 做法 |
|---|---|
| 并行 | ⭐ 同一条消息多个 Task 调用 |
| 模型选择 | 探索 haiku / 设计 sonnet / 实现 opus |
| 结果回传 | ⭐ 只让紧凑摘要进主上下文 |
| 简单任务 | ⭐ 不委派 |
| 上下文已满 | 全部探索都委派出去 |
| prompt | 目标 + 边界 + ⭐ 输出格式 + 上下文 |
