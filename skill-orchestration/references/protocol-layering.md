# 技能 / MCP / A2A：三层各管什么

> ⭐ **一句话记住三者**：
> **Skill 是 Agent 的"手"（完成单一任务）
> MCP 是"通用插座"（工具插在同一个接口上）
> A2A 是"电话线"（Agent 之间互相打电话）**

## 三者定位对照

| 技术 | 全称 | 核心定位 | 通信对象 | 典型场景 |
|---|---|---|---|---|
| **Skill** | 技能组件 | 单一功能的封装模块 | Agent ↔ 技能 | 代码生成、文件处理、邮件发送 |
| **MCP** | Model Context Protocol | 智能体与工具间的通用接口 | Agent ↔ 工具 | 统一工具调用、一次开发多端复用 |
| **A2A** | Agent-to-Agent | 智能体之间的通用通信协议 | Agent ↔ Agent | 多 Agent 协作、跨平台任务调度 |

**一个具体例子**（三者同时用到）：

```
让 AI 做一份市场分析报告
→ Skill 负责"生成图表""清洗数据"这些原子能力
→ MCP 让它连上数据库与 API
→ ⭐ A2A 让分析 agent 与检索 agent、写作 agent 互相交付任务
```

## MCP vs A2A：方向不同

> ⭐ **最清晰的记法**：

```
MCP  垂直——把 agent 向下连到它操作的系统
A2A  横向——把 agent 跨接到它的同伴
```

| 维度 | MCP | A2A |
|---|---|---|
| 主要关注 | 单个 agent 的工具与系统访问 | 多个 agent 间的协调与委派 |
| 方向 | **垂直**（agent → system） | **横向**（agent → agent） |
| 交互模式 | 请求-响应，**基本无状态** | ⭐ **会话式、有状态** |
| 核心单元 | 工具调用 | **委派的任务** |
| 层级 | 行动层 | **编排层** |
| 发起方 | Anthropic（2024-11） | Google（2025-04，捐给 Linux 基金会） |
| 架构 | 客户端-服务端（JSON-RPC 2.0） | ⭐ 对等 + Agent Card（任务生命周期、SSE/webhook） |
| 延迟 | 低（直接工具调用） | 较高（多跳委派），但为长任务优化 |

**A2A 的三个锚点组件**：

```
Agent Card    能力发现——每个 agent 发布机器可读的能力描述
Task Object   在 agent 间传递的工作单元（含请求与上下文）
能力协商      编排器在派任务前先找到对的 agent
```

**状态性的实际影响**：

```
□ MCP 请求-响应更简单，易于治理与推断延迟
□ ⭐ A2A 有状态——需要在工作流间管理共享任务状态
   随着交互量增长，⭐ 对可观测性与治理的要求更高
```

> 呼应 `skill-governance` 的 `telemetry-schema.md` 与 `compliance-audit.md`：
> **有状态的多 agent 交互，审计难度显著高于单次工具调用。**

## 一个根本假设的差异

> ⭐ **这是最值得记住的一条**：

```
MCP 假设"工具是你的"
→ host 连上 server 时能看到每个工具的完整输入 schema
  因为 server 是 host 自身能力的被动延伸

A2A 假设"agent 是别人的"
→ ⭐ 客户端连上远程 agent 时，⭐ 只能看到对方选择公开的技能
  因为那是个独立行为体——可能是竞对、付费第三方，
  或有自己的安全边界
```

> ⭐ **这一个假设级联出后面所有差异**：
> 状态性（对等方随时间协商）、流式与推送（长任务要进度更新）、
> 动态发现（运行时才得知对方能力，而非编译期）。

**安全模型也不同**：

```
MCP  服务端控制——每个 server 在执行前强制权限、认证、范围限制
     ⭐ 逻辑留在服务端，降低提示注入风险
A2A  通过签名 Agent Card、显式同意流、可观测的任务生命周期建立信任
     ⭐ agent 可以验证能力，并在任务中途撤销访问
```

## 参考架构：同一个 agent 说两种协议

> ⭐ **行业收敛出的参考模式**（一个"月末关账"的例子）：

```
用户请求：月末关账
    ↓ A2A
编排 agent
    ├── A2A → 对账 agent   （内部用 MCP 连账本 DB / ERP / 汇率工具）
    └── A2A → 报表 agent   （内部用 MCP 连电子表格工具）

⭐ 编排器从来看不到对账 agent 的工具与逻辑
   它只看到 Task 从 working 变成 completed
```

> ⭐ **最微妙的一点**：
> **同一个进程，在同一时刻，既是对上的 A2A server，又是对下的 MCP host。**
>
> 所以"MCP 还是 A2A"在系统层面是个**伪二选一**——
> **一个设计良好的 agent 两种都说：向下对工具，向上对同伴。**

**桥接适配器已经存在**：

```
□ 把 A2A agent 暴露成 MCP server（"agent-as-tool" 模式）
□ 把 MCP 流量路由到 A2A 端点
→ ⭐ 你永远不会被锁死在一种线格式里
```

**实践建议**：

> ⭐ **给 agent 设计一个干净的内部核心，
> 把两种协议当作可互换的边缘**：
> MCP 用于它消费的能力，A2A 用于它协作的同伴，
> 接缝处按需加适配器。
>
> 这样"选哪个协议"就从**架构决策**降级成**接线细节**——
> 这正是你想要的。

## 对技能设计的含义

**① 技能是最小单元，不属于任何协议层**

```
□ 技能是纯 Markdown 文件——不走网络、不需要协议
□ ⭐ 它可以在 MCP agent 里，也可以在 A2A agent 里
□ 这是技能相对 MCP server / A2A agent 的结构性优势：
  ⭐ 零依赖、零延迟、可版本化
```

**② 技能可以包装 MCP 工具的使用方式**

```
□ MCP 提供"能做什么"（能力）
□ ⭐ 技能提供"该怎么做"（程序性知识）
□ 两者是互补而非竞争——呼应 skill-vs-rag.md 与 mcp-composition.md
```

**③ 跨 agent 协作时，技能要声明"对外公开什么"**

```
□ A2A 里 agent 只公开它选择公开的技能
□ ⭐ 所以技能应当区分"内部用"与"对外 advertised"
□ 敏感技能不该出现在 Agent Card 的能力列表里
```

**④ 有状态协作需要更强的可观测性**

```
□ 任务跨 agent 传递时，每个环节都要能追溯
□ ⭐ 技能在 A2A 场景下要额外输出：
   任务状态、产出物（artifact）、验证证据
```

**⑤ 别为了"用上新协议"而改架构**

```
□ 多数团队其实两种都要，但它们解决不同问题
□ ⭐ "选一个"是错误提问——正确提问是"我什么时候需要哪个"
```

```
□ 是否能一句话说清 Skill / MCP / A2A 的分工？
□ 是否知道 MCP 是垂直（agent→工具）、A2A 是横向（agent→agent）？
□ ⭐ 是否理解"MCP 假设工具是你的，A2A 假设 agent 是别人的"？

□ 是否区分了技能的"内部用"与"对外公开"？
□ 跨 agent 场景下，技能是否输出任务状态与验证证据？
□ 是否避免了"选 MCP 还是 A2A"这个错误提问？
□ 是否为协议变化预留了适配器接缝？
```
