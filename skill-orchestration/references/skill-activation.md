# 技能的动态激活与停用

> 多数讨论假设技能"装上就在"。
> 生产级 agent 的一个关键能力是：**换阶段就换技能**。

## 为什么需要停用

> ⭐ **agent 换到不同工作阶段时，应该停用不再需要的技能，
> 激活新的。这让上下文始终聚焦在当前相关的事情上。**

对照静态方案的代价：

```
静态常驻：所有技能的 description 每轮都在上下文里
          ⭐ 每个加载的技能都在为每一轮付费，不管你有没有用过它

动态切换：只有当前阶段相关的技能在上下文里
```

呼应 `runtime-controls.md` 里 `/skill-doctor` 的定位：
**列表里每一个技能每一轮都在消耗上下文，不管有没有用过**。

## 三种激活策略

| 策略 | 什么时候用 | 优点 | 缺点 |
|---|---|---|---|
| **常驻** | 每次都要用的基础能力 | 零切换成本 | ⭐ 常驻税 |
| **按需自动** | 场景明确、触发词可靠 | 不用管 | ⭐ 依赖 description 写得好 |
| **显式激活/停用** | ⭐ 阶段式工作（侦察→利用→报告） | 上下文最省 | 需要编排逻辑 |

> ⭐ **第三类是被低估的**：
> 安全测试、迁移、审计这类"分阶段"的工作，
> 前一阶段的技能在后一阶段**不只是没用，还会干扰**
> （比如侦察阶段的技能会让 agent 在写报告阶段继续找漏洞）。

## 技能切换的执行方式

**显式切换**：

```
进入阶段 2（漏洞利用）
  → 停用 recon-and-enumeration
  → 激活 exploitation-workflow
```

**切换时要做的三件事**：

```
1. ⭐ 保存当前阶段的产物到文件（技能本身无状态）
2. 停用旧技能
3. 激活新技能，并在新技能的上下文里引用步骤 1 的产物路径
```

> 呼应 `memory-state.md` 的交接班协议——
> **切换技能本质是跨会话/跨阶段的记忆传递问题**。

**保留产物的原因**：

```
☐ 技能切换时上下文里的内容会被丢弃
☐ ⭐ 但前一阶段的发现是后一阶段的输入
☐ → 必须写盘，按路径引用
```

## 内置技能库的规模控制

一个真实的参考值：某安全 agent **内置 25 个技能**覆盖主要安全工作域。

**分布示例**：

```
redteam                    → 完整的对抗模拟框架
                              scoping · 攻击路径映射 · 凭证工作流
                              · 权限提升 · 横向移动 · OPSEC
                              · 清理流程 · 有证据支撑的报告
variant-analysis           → 发现一个漏洞后在代码库里找同类
nuclei-templates           → 从零写自定义检测模板
sqlmap-guide               → SQL 注入测试
semgrep                    → 自定义静态分析规则
libfuzzer                  → 模糊测试方法论
android-security-guide     → ⭐ 850 行：IPC 攻击、WebView 利用、
                              密码学问题、deeplink 滥用、Frida hook
ios-security-guide         → IPA 分析、二进制检查、keychain、
                              传输安全、URL scheme、密钥扫描
mobile-advanced-techniques → Frida 工作流、反 Frida 绕过、
                              原生库分析、白盒密码学、流量拦截
security-findings          → ⭐ 标准化漏洞报告模板 + CVSS + PoC
exploitability-verification→ 确认发现是否真的可利用
runtime-validation         → 对活目标验证发现
differential-review        → 基于变更的分析（PR 评审）
task-diff-analyse          → 定时任务比对
vpn-guide                  → 沙箱里预装的各类 VPN 客户端连接
```

**25 这个数字值得注意**——
呼应 `skill-composition-patterns.md`（**`skill-orchestration`**）的甜蜜点 5–8
与 `scale-effects.md` 的"装太多 description 会被压缩削掉关键词"：

```
技能数    适用
5–8       ⭐ 组合的甜蜜点
20–50     ⭐ 要做分组与裁剪
754       必须有 domain/tags 结构化检索
           （见 domain-taxonomy.md，**`skill-selection`**）
```

## 对自研技能的启示

**① 分阶段的工作要显式切换，不要全常驻**

```
✅ 侦察阶段：recon 技能
✅ 利用阶段：停用 recon，启用 exploitation
❌ 两个都在（利用阶段还在找资产，浪费且干扰）
```

**② 报告模板要独立成技能**

注意示例库里 `security-findings` 是独立的——
**报告的产出规范与发现的过程规范是两件事**。

呼应 `output-contract.md`（**`skill-crafting`**）：
输出契约应该独立可测。

**③ 大参考文档用"技能 + references"承载**

`android-security-guide` 有 **850 行**——
这远超 SKILL.md 的 500 行上限，说明它是**技能目录下的 references**，
而不是 SKILL.md 本身。

> ⭐ 印证了渐进式披露的实际用法：
> SKILL.md 做路由，850 行的细节留在 `references/` 按需读。

**④ 有些技能是给"产出成品"用的**

示例库里还包含 docx 和 pdf 输出技能——
**让 agent 能产出标准格式的交付物**，而不是只在终端里打印。

## 常见坑

| 坑 | 症状 | 修法 |
|---|---|---|
| 切换后丢失前阶段成果 | 新阶段不知道前面发现了什么 | ⭐ 切换前写盘，按路径引用 |
| 旧技能仍在干扰 | 写报告时还在找漏洞 | 显式停用，不只是激活新的 |
| 阶段边界模糊 | 不知道该切到哪个 | ⭐ 给可判定的阶段转换条件 |
| 全都常驻 | 上下文被 description 吃满 | 用 `/skill-doctor` 查未使用技能 |
| 参考文档超长撑爆正文 | 单次加载吃掉整个窗口 | 长文档放 references，按需读 |
