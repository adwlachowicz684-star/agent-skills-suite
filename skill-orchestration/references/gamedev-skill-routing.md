## 1. 三维结构

游戏开发技能库天然是三维的，很容易膨胀成一团：

```
① 引擎维   Unity / Unreal / Godot / Web / 移动端
② 学科维   物理 / 动画 / 音频 / 存档 / 程序化生成 / 相机 / 手感
③ 类型维   RPG / 平台跳跃 / Roguelike / 塔防 / 射击
```

> ⭐ 关键设计：**不是给每个组合写一个技能**，
> 而是三个维度各自独立，运行时组合。

## 2. ⭐ 加载顺序与归属规则

```
引擎基础 → 学科概念 → 类型编排 → 工作流
```

**重叠时的归属（这条最值得抄）**：

| 维度 | 拥有什么 | 让出什么 |
|---|---|---|
| **引擎技能** | ⭐ **API / 语法** | — |
| **学科技能** | ⭐ 可移植的概念/算法 | ⭐ **代码部分让给引擎技能** |
| **类型技能** | 结构 / 粘合 | ⭐ **链接出去，不重复教原语** |

> ⭐ 这是一条通用的分层原则：
> **谁更接近具体语法谁负责代码；谁更接近概念谁负责解释；
> 谁负责编排谁只做链接。**

**Hand-off 规则**：

```
类型技能的组合里命名了一个槽位（如 *-2d-movement）
→ ⭐ 绑定到识别出的引擎
→ 若该引擎没有对应技能，见兜底规则，⭐ 绝不编造技能名
```

## 3. 引擎识别

通过**指纹文件**判断：

```
Godot   → project.godot
Unity   → Assets/ + ProjectSettings/
```

另有次要信号与消歧规则（放在 `references/engine-detection.md`）。

> ⭐ 这是个很实用的通用模式：
> **用文件系统指纹做路由，而不是问用户。**
> 可迁移到任何"多技术栈"的技能库。

---

## 4. ⭐ 未识别引擎时的兜底（写得很克制）

```
① 先从请求里找明文引擎名（"in Unity"、"using Phaser"）
   → 找到就采用

② ⭐ 如果是纯概念/类型/工作流问题
   → 直接路由到引擎无关的学科技能，不需要引擎
     例："什么格式适合存档？" → save-systems

③ ⭐ 只有当引擎选择真的阻塞答案时，才问一个具体问题
   "哪个引擎——Godot、Unity、Unreal，还是 Web/其他？"

④ ⭐ 用户没偏好且必须有一个时，默认 Godot（覆盖最全）并说明

⑤ ⭐ 绝不臆造引擎，也绝不靠猜加载引擎技能
```

**引擎已知但无技能覆盖时**：

```
加载最接近的引擎技能 + 相关学科技能
⭐ 并坦白说明缺口
   例："没有专门的 Unity 2D 移动技能；使用 unity-csharp-scripting
        + unity-physics"
⭐ 绝不编造技能名
```

> ⭐ 这两段是全文最值得抄的——
> **它把"不知道怎么办"写成了明确的降级路径**。
> 多数技能库在这里是空白，于是模型自己编。

## 5. 路由示例表

| 请求 | 识别到的引擎 | 加载的技能（按顺序） |
|---|---|---|
| "给 Godot 玩家加二段跳" | Godot | `godot-2d-movement` → `platformer` |
| "给我的 Unity RPG 做背包" | Unity | `unity-scriptableobjects` → `rpg` → `save-systems` |
| "Godot 里做程序化地牢 roguelike" | Godot | `godot-tilemap` → `procedural-gen` → `roguelike` |
| "从 .yarn 文件做分支对话" | 无需引擎 | `dialogue-systems`（+ 引擎 UI 技能） |
| "存档槽怎么做迁移？" | 无 | `save-systems` 单技能 |
| ⭐ "我想做游戏但不知道用什么" | 未知 | ⭐ 问一次；默认 Godot |
| "让 Godot 游戏的打击感更爽" | Godot | `game-feel`（+ `camera-systems` 做震屏） |
| "我的 Unity 游戏掉到 30 FPS，优化一下" | Unity | ⭐ `performance-optimization`（先 profile）→ 引擎技能 |

> ⭐ 倒数第二条值得注意：
> **"先 profile" 是硬约束**——与 `performance-optimization.md`
> 的"先测量再优化"一致。

## 6. ⭐ 可迁移的四条设计

| 设计 | 通用化 |
|---|---|
| ⭐ **三维正交** | 组合爆炸时，拆成正交维度而不是写 N×M 个技能 |
| ⭐ **归属规则** | 重叠时明确谁拥有代码、谁拥有概念、谁只做链接 |
| ⭐ **指纹识别** | 用文件系统特征做路由，别问用户 |
| ⭐ **降级路径** | ⭐ 把"不知道/没覆盖"写成明确规则，⭐ 禁止编造 |

> 最后一条最重要，也最常被漏。
> 模型遇到没覆盖的情况**默认会编一个看起来合理的答案**——
> 必须显式禁止。

---

## 速查

```
□ 维度是否正交（引擎/学科/类型）
□ 重叠时归属是否写清
□ 引擎能否靠指纹识别
□ 未识别时的降级路径
□ ⭐ "绝不编造技能名" 是否写明
□ 性能类是否要求先测量
```
