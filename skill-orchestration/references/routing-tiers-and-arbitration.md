## 1. ⭐⭐⭐ 三级路由

三种思路，**复杂度从低到高，各有适用场景**：

```
① ⭐ 规则匹配
   维护关键词 / 正则，命中哪个调哪个
   例：消息含"快递/发货/物流" → order_status_inquiry
   优点：⭐ 零成本、稳定、可解释
   缺点：⭐ 只能处理预设表述，换个说法就抓瞎
   ⭐⭐ 适用：⭐ 技能数在 10 个以内完全够用

② ⭐ 向量召回
   所有 description 做 embedding，用户输入也做 embedding，取 Top-K
   ⭐ 解决了"换个说法就抓瞎"
   缺点：⭐⭐ 用户输入可能与多个技能都相似，⭐ 容易召回一堆不相关
   ⭐⭐ 定位：⭐ 当作"粗排"，先筛出 5 个候选

③ ⭐ 模型决策
   （见下节两个判据）
```

> ⭐⭐⭐ 这套三级正好接上了我们已有的两个数字：
>
> ```
> · trigger-tuning-loop.md：⭐ 超过 10 个技能，误触发成为主要负担
>   → 对应①的适用上限
> · collision-arbitration.md：⭐ 50 个技能上两步路由（先压到 2–3 候选）
>   → 对应②的"粗排筛 5 个"
> ```
>
> ⭐⭐⭐ 所以完整的规模阶梯是：
> **<10 规则匹配 · 10–50 向量粗排 · >50 模型精排 + 两步路由。**
> 这两个阈值此前是分散记的，这里串成了一条连续曲线。

## 2. ⭐⭐⭐ 两个优先级判据：危险度与明确度

模型决策那一级，两个判据（这是本份最原创的部分）：

```
① ⭐⭐ 业务危险度
   ⭐⭐⭐ 一个技能如果乱触发会导致⭐ 金钱损失、用户信息安全出问题，
   ⭐⭐⭐ 那它的⭐ 触发优先级应该被调低——⭐⭐⭐ 宁可漏接，不可错接

② ⭐⭐ 请求明确度
   ⭐ 用户消息里一旦出现⭐ 明确的业务动作词
      （"投诉"、"退钱"、"报警"）
   ⭐⭐ 动作词对应技能的优先级⭐ 应该高于查询类技能
```

> ⭐⭐⭐ 第 ① 条值得单独记，因为它**与我们此前所有"提高触发率"的建议方向相反**——
> 我们收集了大量"让技能更容易被触发"（强势描述、祈使句、加触发词），
> 而这条说的是⭐ **对危险技能要主动降低触发率**。
>
> ⭐⭐⭐ 仲裁方式：**这是 `disable-model-invocation: true` 在架构层的对应物**——
> 那个字段是二元的（完全禁止自动触发），
> 这里是⭐ 连续的（把优先级调低，仍可能触发但要更强信号）。
> 两者结合：危险技能既该设 `disable-model-invocation`，
> 又该在路由层被降权。

## 3. ⭐⭐ 兜底：得分都低时提问

> ⭐⭐ **当多个技能候选的得分⭐ 都低于阈值时，⭐ 不乱选，
> ⭐⭐ 而是走一个"提问澄清"分支。**

```
例：直接问用户"您是想查物流还是想申请退款"
```

**理由**（一句很有分量的权衡）：

> ⭐⭐⭐ **"多一次交互对用户体验的伤害，
> ⭐ 远小于⭐ 技能选错之后产生⭐ 错误操作的伤害。"**

> ⭐⭐ 这与 `skill-dependency-injection.md` 的降级路径
> （"只有引擎真的阻塞答案时才问，且只问一个具体问题"）
> 看似张力，实则一致：
> **前者是"信息不足时别问"（因为可以推断），
> 这里是"信息不足且后果严重时该问"（因为代价不对称）。**
> ⭐⭐⭐ 判据就是那句"伤害对比"——**问的成本 vs 猜错的后果，哪个大。**

## 4. ⭐⭐⭐ 仲裁链四条

一次请求同时命中多个技能时的优先级链（**按顺序，前面的赢**）：

```
① ⭐⭐ 精确匹配优先
   请求里关键词与某技能描述⭐ 高度重合 → 直接选它，⭐ 不再做模糊比较

② ⭐⭐⭐ 特异优先于通用
   两个都匹配时，选⭐ 限定语更多的那个
   例：scan-directory 比 list-files 更特异（前者限定了目录范围）

③ ⭐⭐⭐ 副作用的保守原则
   两个都能完成，但一个只读一个会写入
   → ⭐⭐ 默认选只读的那个，⭐ 把写操作交给后续显式确认

④ ⭐⭐ 无法判断时提问
   ⭐⭐ "宁可多一轮交互，也不要在两个都不错的选项里掷骰子"
```

**外加一条企业级的显式指定规则**：

```
⭐⭐ 用户已显式指定 Skill 名称 / skill_id → ⭐⭐⭐ 以指定为准
    ⭐ 最高优先级，⭐ 不参与后续匹配与澄清
    ⭐ 仅当名称不存在或无权访问时返回错误/提示
```

> ⭐⭐⭐ 这正好与 `priority-override-layers.md` 的
> "临时 Prompt > 技能内置规则 > 全局 Rule"一致——
> ⭐ **用户显式指定是最高优先级，路由层要给它开一条直通通道。**

**还有一条灰度场景的处理**（很实用）：

```
多个技能⭐ 触发词完全相同且功能相同（灰度多版本并存）
→ ⭐ 版本优先：取 version 最高的，低版本标记 deprecated

⚠️ 但：⭐⭐⭐ 若两个技能⭐ 功能不同却共用触发词
   → ⭐⭐ 视为⭐ 命名冲突，⭐ 强制细化触发词或走显式澄清
   → ⭐⭐⭐ ⭐ 不得以版本号隐式裁决
```

> ⭐⭐⭐ 最后半句很关键：**版本号只能裁决"同一功能的新旧"，
> 不能裁决"两个不同的功能"**——后者是命名问题，必须改名字。

## 5. ⭐⭐⭐ 把仲裁写成函数

> ⭐⭐⭐ **建议把仲裁规则写成一个⭐ 独立的仲裁函数，
> ⭐ 而不是塞进提示词里让模型自己推理。**
>
> ⭐⭐⭐ **"函数是确定的、可测的，模型推理是不确定的。
> ⭐⭐⭐ 能用代码解决的判断，别交给提示。"**

> ⭐⭐⭐ 这与我们此前三条是同一个结论的**第四个独立来源**：
>
> ```
> 1. Hooks 用于模型不可被信任去遵守的事（determinism-boundary）
> 2. 把破坏性拦截写进技能是表演（多份）
> 3. 反复被违反的书面规则应编码成校验器（feedback-loop-design）
> 4. ⭐⭐⭐ 仲裁规则写成函数，不交给提示（本份）
> ```
>
> ⭐ 而且这条更进了一步：前三条说的是"要强制"，
> 这条给了一个⭐ 更普适的表述——
> **确定性的判断就应该用确定性机制承载。**

---

## 6. ⭐⭐ 并行与串行的判据

> ⭐⭐ **两个技能都只声明了 `fs.read` 且⭐ 路径范围不交叉 → ⭐ 可安全并行；
> ⭐⭐⭐ 只要有一个声明了写权限 → ⭐ 退回串行。**

> ⭐⭐⭐ 这条把 `allowed-tools` 从"安全约束"变成了⭐ **调度依据**——
> 权限声明的第二个用途。
> 也和"先只读调查，修复阶段才给写权限"（systematic-debugging）呼应。

## 速查

```
□ ⭐⭐⭐ 三级路由：
   ① 规则匹配（零成本稳定，⭐ <10 个够用，换说法就抓瞎）
   ② 向量召回（解决换说法，⭐⭐ 只当粗排筛 5 个）
   ③ 模型决策
   ⭐⭐⭐ 规模阶梯：<10 规则 · 10–50 向量粗排 · >50 模型精排+两步路由

□ ⭐⭐⭐ ⭐ 危险技能应⭐ 主动降低触发优先级——"宁可漏接，不可错接"
   （与我们此前"提高触发率"的建议方向相反）
   ⭐ 与 disable-model-invocation 互补：二元 vs 连续
□ ⭐⭐ 明确动作词（投诉/退钱/报警）优先于查询类

□ ⭐⭐ 候选得分都低于阈值 → ⭐ 提问澄清，不猜
   ⭐⭐⭐ "多一次交互的伤害 < 选错产生错误操作的伤害"

□ ⭐⭐⭐ 仲裁链：显式指定 > 精确匹配 > ⭐ 特异优于通用
   > ⭐⭐ 只读优于写入 > ⭐ 无法判断就提问
□ ⭐⭐⭐ ⭐ 版本号只能裁决同功能新旧，不能裁决两个不同功能
□ ⭐⭐⭐ ⭐ 仲裁写成函数不写进提示——确定性判断用确定性机制承载
□ ⭐⭐ 并行判据：都只读且路径不交叉 → 并行；⭐ 有写权限 → 串行
```

**一句话**：

> ⭐⭐⭐ **冲突要在编排层用函数仲裁，不要塞进提示词让模型推理——
> 函数是确定的、可测的，模型推理不是；
> 而危险技能要主动降低触发优先级（宁可漏接不可错接），
> 这与此前"让技能更容易被触发"的方向相反但同样重要。**
