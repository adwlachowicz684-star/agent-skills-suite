## 1. 现象：相似技能互相抢占

```
技能数量超过十个之后，相似技能开始出现。
典型例子：同时有"合并重复代码"和"重构模块"两个技能。
```

> 这与 `library-size-effect.md` 的实测一致——
> **遮蔽是库规模效应的主要成分（占 68%）**。

## 2. ⭐ 仲裁规则（从简到繁）

**① 调 description**（最常用）

```
⭐ 让两边各自覆盖不同角度
⭐ 并在 description 里互相写明边界
```

对应 `description-by-collision-risk.md` 的 NOT 段要点名替代方案。

**② priority 字段**

```yaml
---
name: merge-duplicate-code
priority: 10
---
```

> ⭐ 评价很中肯：**这个方法不完美，但足够简单。**

**③ 两步路由**（规模上去了就该用）

```
第一轮  embedding 或规则匹配 → 缩小候选集
第二轮  主模型对候选的 description 做最终选择
```

> ⭐ **技能规模上了五十个，我建议直接上两步路由，
> ⭐ 不要指望单次 description 匹配能每次都做对。**

---

## 3. ⭐ 两步路由

```
大部分场景下，embedding 匹配这一层就能把候选集压缩到两三个技能
⭐ 主模型只需要做一个二选一或三选一的判断
⭐ 几乎不增加多余推理轮次
```

> ⭐ 这个设计同时解了两个问题：
> **遮蔽**（候选太多选错）和**延迟**（多一轮推理）。

> 与 `skill-vs-rag.md` 那条"用 RAG 检索技能"同源——
> 先把所有 description 做 embedding 预筛，再只加载 top-k。

---

## 4. ⭐ 延迟的真相

```
⭐ 技能加载本身不是瓶颈。
   几百个技能规模的目录里，预构建索引后单次加载延迟在几十毫秒内。
⭐ 模型的生成时间仍然占据整体延迟的绝大部分。

⭐ 真正拖慢速度的反而是一个常见设计：
   ⭐ "让模型先思考应该加载哪个技能，再执行主任务"
      = 多了一轮推理
```

> ⭐ 这是个很实用的反驳：
> 很多人担心"技能多了会慢"，**实际慢的是那个"先想一下用哪个"的设计**。
> 解法不是减少技能，是**用 embedding 层替掉那一轮推理**。

---

## 5. 权限不能由模型决定

```
技能可以调用工具，工具可能涉及危险操作——
写文件、执行命令、修改数据库配置。

⭐ 很多团队忽略的是：⭐ 工具调用权限不能由模型自己决定。
```

> ⭐ 与 `determinism-boundary.md` 那条完全一致：
> **技能里的权限声明不是安全边界，真正的边界在 hook 或 permission 规则。**

---

## 速查

```
仲裁三招（从简到繁）：
□ ⭐ 调 description + 互相写明边界
□ priority 字段（不完美但够简单）
□ ⭐ 两步路由（>50 个技能直接上）

□ ⭐ 第一轮 embedding/规则 → 压到 2-3 个候选
□ ⭐ 第二轮主模型只做二选一/三选一

□ ⭐ 加载不是瓶颈（几十毫秒）；模型生成才是
□ ⭐ "先想一下用哪个"才是真的慢——用 embedding 层替掉
□ ⭐ 权限不能由模型决定
```

**一句话**：

> ⭐ **别让模型多花一轮去想"该用哪个技能"——
> 用 embedding 先把候选压到三个，让它只做选择题。**
