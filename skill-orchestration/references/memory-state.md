# 跨会话记忆与状态

> **每次 API 调用都是无状态的**——关掉终端，记忆就没了。
> 技能解决这个问题的方式是：**把记忆外化成文件**。

## 状态存在哪

| 状态类型 | 存储位置 | 有效范围 |
|---|---|---|
| 对话历史 | 上下文窗口 | 当前会话，关闭后消失 |
| 中间文件 | 工作目录 | 当前会话，任务完成后可能清除 |
| 输出文件 | 持久化输出目录 | ✅ 持久化，用户可下载 |
| 已安装技能 | 技能目录 | ✅ **跨会话持久化** |

> ⚠️ **技能本身不具备数据库或持久存储能力。**
> 需要跨会话保存的数据，应由用户自己保存（如下载文件），
> 或写入持久化输出目录。

> 这个约束决定了设计：**记忆只能是"文件 + 约定"，不能指望技能自己记住。**

## 三种记忆模式

### 模式 1：会话内累积

最简单的形式——在单个对话窗口内累积上下文。

```
行动前：列出你打算触碰的所有文件及理由
维护一份决策日志：改了什么、为什么；试过什么没成；待确认问题
结束时：总结已做的决定与下一步
```

> **局限很明显：关掉终端，记忆就没了。**

### 模式 2：跨会话文件记忆

> ⭐ **技能通过在每次会话开始时读取的文件来外化记忆。**
> **技能文件本身就是契约**：它告诉 Claude 该记什么、存到哪、怎么用。

**对比**：

```
无记忆：「审查这个 PR」
  → 不了解过去的审查、团队的风格指南、已讨论过的问题

有记忆：「审查这个 PR」
  → 加载 project-memory/review-history.md
  → 看到最近 10 个 PR、团队反复出现的问题、上月确立的约定
  → 审查立刻变得有针对性
```

**典型结构**：

```
my-skill/
├── SKILL.md
├── context-log.md       # 跨会话记忆载体
└── project-state.json   # 当前任务状态
```

> 一个真实用法（日报生成）：
> 首次运行生成日报并把摘要写入 `standups.log`；
> 次日读取它做对比，自动产出**差异化的**报告
> ——"与昨天相比，今天新增了 X 功能，修复了 Y bug"。
> **既省了重复信息的 token，又给了 agent 长期的项目记忆。**

### 模式 3：工具介导的状态

最稳健——把记忆存在**为它设计的系统**里（数据库、KV 存储、版本控制的文件）。

```
读取当前 sprint 状态：gh project list --owner @me
读取任务详情：       gh issue view {issue_number}
```

> **agent 不管理存储格式，它调用工具，工具负责存储。**

## 交接班协议

> 在 SKILL.md 里写两条说明即可（像工作交接班）：

**每次会话开始时**：

```
□ 读取 context-log.md
□ 了解过往工作进度
□ 明确待完成任务
```

**每次会话结束时**：

```
□ 撰写已完成工作的总结
□ 罗列剩余待办任务
□ 标注重要注意事项
```

**价值**：

```
无状态：每次会话从零开始
有状态：每次会话承接上一次内容
        → 执行效率更高、输出稳定统一、无需重复下发指令
```

**一个成熟技能要支持三种能力**：

```
1. 多阶段项目（写书、做产品、内容流程）
   → 跟进进度、拆解为分阶段工作、无缝接续暂停的工作
2. 迭代式工作（不是所有工作都能一次完成）
3. 长期知识沉淀（技术债、哪个模块重构过——避免重犯旧错）
```

## 记忆文件的结构

> ⚠️ **扁平文件很快会变得难用。**
> 好的记忆 schema 要把三类东西**分开**：

| 类别 | 性质 | 内容 |
|---|---|---|
| **决策** | **不可变，带时间戳** | 架构选择、已接受的权衡 |
| **状态** | 可变 | 当前任务、进行中的工作、打开的 PR |
| **知识** | 演进中 | 代码库约定、团队偏好、反复出现的模式 |

> **用结构化 JSON 存状态**——便于从 Claude 外部检视和调试 agent 的记忆。

**分层决策树**（决定某段知识放哪一层）：

```
这段知识是否每次激活技能都需要？
├── 是 → SKILL.md（入口，每次必读）
└── 否 → 是否每次进入该模块时都需要？
    ├── 是 → 模块主文件
    └── 否 → 是否仅在某个特定 Step 才需要？
        ├── 是 → 对应 phase 文件
        └── 否 → 是否只在特定条件下查阅？
            ├── 是 → 参考文件
            └── 否 → 考虑是否还需要保留
```

> **核心原则：越频繁用到的知识，离入口越近；越偶尔查阅的，越往深处放。**

## 存储最佳实践

```
□ 隔离存储——不要把持久化数据混在代码目录里；
  用环境变量指向的稳定目录（如 ${CLAUDE_PLUGIN_DATA}）
□ 结构化格式——优先 JSON 或 YAML，便于模型解析和脚本处理
□ 版本兼容——升级技能逻辑时保持数据格式向后兼容，
  避免因 schema 变更导致历史数据读不出来
□ 增量更新——写入摘要而非全文，避免记忆文件无限膨胀
```

> ⚠️ **版本兼容那条最容易被漏**：
> 你改了 schema，历史数据就读不出来了——
> 记忆系统会在升级那天**静默失忆**。

## 自查

```
□ 是否需要跨会话（不需要就别引入记忆文件，那是负担）？
□ 记忆文件是否把"决策/状态/知识"三类分开了？
□ 是否有明确的交接班协议（会话开始读、结束写）？
□ 是否用了结构化格式（JSON/YAML）？
□ 是否做了 schema 向后兼容？
□ 存储位置是否与代码目录隔离？
□ 记忆文件是否有增长上限（增量更新而非全量追加）？
□ 是否测试过"关掉终端再打开"能接续？
```
