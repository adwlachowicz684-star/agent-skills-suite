# 步数、时间与花费上限：并且要 fail closed

> ⭐ **无界循环不是 bug，是一类威胁。**
> 卡在重试里或被诱导发起大量工具调用，会烧掉预算和配额。

## 三个维度

```
① 步数     ——最多多少次工具调用 / 多少次循环
② 时间     ——墙钟时间上限
③ 花费     ——token 或金额预算
```

三者都该有，因为**它们防的是不同情况**：

```
步数  防"逻辑死循环"
时间  防"每步都很慢"（单次不超限但总量失控）
花费  ⭐ 防"每步都很贵"（如反复读大文件）
```

> ⭐ 只设其中一个是不够的——
> 一个 3 步的流程如果每步都读 1MB，步数上限拦不住它。

## fail closed 是什么意思

> ⭐ **到达上限时是"停止"，不是"记录一下继续"。**

```
❌ 到达上限 → 记一条日志 → 继续跑
✅ 到达上限 → ⭐ 停止并上报
```

理由很直接：
**"记录了但继续"等于没有上限**——
它只是让你事后知道自己超了多少。

## 上限设在哪一层

```
① 工具层      ——单个工具的参数级约束（limit、timeout）
② ⭐ 运行层   ——每次运行的总步数/时间/预算
③ 会话层      ——跨多次运行的累计
④ 组织层      ——每人/每团队/每日
```

> ⭐ **运行层是必须有的**——
> 它对应"这一次任务"的自然边界，
> 也是唯一能在单次失控时止损的层。

工具层是 `least-privilege.md` 里
"narrow tools with typed, validated inputs" 的一部分；
会话层与组织层是成本治理（见 `cost-control.md`）。

## 数值怎么定

不要拍脑袋：

```
① ⭐ 先测量：正常任务实际用了多少步/多久/多少钱
② 取正常值的 2–3 倍作为上限
③ ⭐ 单独看尾部：P99 是多少？上限要高于它
④ 留出一次重试的余量
```

> ⭐ 常见错误是**上限设得接近平均值**——
> 结果正常的大任务被频繁中断，团队只好把上限调高，
> 最后调到等于没有。

配套：**按任务类型设不同的上限**，
不要全组织一个数字。

## 到达上限后

```
① ⭐ 停止（fail closed）
② 上报，并说明：
   · 在哪一步停的
   · 已消耗多少
   · ⭐ 已完成了什么（产物在哪）
   · 已排除什么
③ ⭐ 保留现场（transcript、中间产物）
④ 不要自动重试同一个任务
```

第 ④ 条容易做反：
**到达上限说明这次运行不正常，
自动重试只会再烧一遍。**

第 ② 条呼应 `escalation-rules.md`：
**升级包要带东西**，接手的人不该从零开始。

## 与重试的关系

```
重试要有上限            ——无限重试是挂死
⭐ 重试次数计入总步数    ——否则两者互相架空
抖动                    ——100 个 agent 同步重试会再次打垮刚恢复的服务
```

> ⭐ **重试预算必须是总预算的一部分**，
> 这是让两套上限真正生效的关键细节。

## 自查

```
[ ] ⭐ 三个维度都有上限（步数 / 时间 / 花费）？
[ ] ⭐ 到达上限是停止，不是记录后继续？
[ ] 运行层的上限存在？
[ ] 数值是基于实测（正常值 2–3 倍），不是拍的？
[ ] ⭐ 按任务类型分别设定，不是全局一刀切？
[ ] ⭐ 重试次数计入总步数？
[ ] 有抖动？
[ ] 到达上限后不会自动重试同一任务？
[ ] ⭐ 上报内容包含"已完成什么、已排除什么"？
[ ] 现场被保留？
```

## 一条提醒

> ⭐ **上限会让人不安，因为它会中断工作。**

所以要把上限配一个**清晰的报错**：

```
❌ "Execution limit exceeded"
✅ "已运行 40 步达到上限（该类任务正常为 8–15 步）。
    已完成：解析与校验（产物在 out/parsed.json）。
    未开始：汇总与报告。
    ⭐ 如需继续，请确认是否需要提高上限或缩小输入范围。"
```

后者让用户能**立刻决策**，
前者只会让人去翻文档猜发生了什么。
