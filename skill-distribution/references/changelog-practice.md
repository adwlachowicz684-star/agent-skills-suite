# 变更日志：记 why，不记 what

> ⭐ **`git log` 已经记了 what。
> 变更日志唯一不可替代的价值是 why。**

## 为什么 git log 不够

```
git log:    "update SKILL.md" / "fix description" / "tweak"
```

这些是真的，但没用——
**半年后没人记得为什么要把那条禁令加进去**。

后果很具体：

```
有人看到一条"看起来很怪的指令"
→ 不知道它为什么存在
→ ⭐ 删掉它
→ 那个被修复过的 bug 回来了
```

> ⭐ 这正是 `refactor-pass.md` 强调的：
> "没有记录理由的重构，会变成来回摆动。"

## 一条合格的条目

```
## [2.1.0] - 2026-09-23

### Changed
- 收紧 description 的触发范围，不再匹配 "加个测试"
  ⭐ Why: 它会抢 testing-skills 的触发词（共存测试里发现
         12 次请求中有 9 次选错）
  ⭐ 影响: 需要"加测试"的用户现在会走 testing-skills

### Fixed
- 第 3 步的路径改用 ${CLAUDE_SKILL_DIR}
  ⭐ Why: 从子目录调用时相对路径解析失败（issue #42）
```

关键成分：

```
① 改了什么（简短）
② ⭐ 为什么（这是核心）
③ ⭐ 影响（谁会因此受益/受损）
```

第 ③ 条尤其重要：
**收紧触发范围会改变谁被路由到哪里**——
不写出来，用户只会觉得"技能突然不灵了"。

## 分类方式

常用分类（可按需裁剪）：

```
Added      新增能力
Changed    ⭐ 行为改变（含收紧/放宽触发范围）
Deprecated 即将移除
Fixed      修 bug
Removed    已移除
Security   ⭐ 安全相关（单独列出）
```

> ⭐ **Security 单独列**——
> 安全变更需要被单独审阅，混在 Changed 里会被漏看。

## 什么时候写

```
□ ⭐ 每次版本发布（不是攒到年底）
□ ⭐ 行为改变时（尤其是触发范围变化）
□ 安全修复时
□ 废弃某项能力时
```

> **"改动进入 main 分支时写"** 比"发布时补"可靠得多——
> 补的时候你已经忘了当时的理由。

## 反面示例

**① 只有 what**

```
❌ "- 更新了描述"
```

**② 复制 commit message**

```
❌ "- fix: fix bug"
```

**③ 没有影响说明**

```
❌ "- 收紧了触发词"
   ⭐ 谁会受影响？不知道
```

**④ 把多行改动压成一条**

```
❌ "- 各种修复"
```

> 判据：**读者能根据这条条目做出决策吗**
> （要不要升级、升级后要改什么）？
> 不能 → 不合格。

## 对技能的特殊之处

技能的"行为"包含一些代码里没有的东西：

```
⭐ description 的措辞变化 = 路由行为的改变
```

所以在技能领域，Changelog 要特别记录：

```
□ ⭐ 触发词的新增/删除
□ ⭐ 触发范围的收紧/放宽
□ 步骤顺序的改变
□ ⭐ 新增或删除的 must / do not 规则
□ 输出格式的变化
```

前两条是**技能独有的**——
代码里没有对应物，但它们实实在在改变行为。

> ⭐ 一条实用规则：
> **凡是会改变"哪些请求会命中这个技能"的改动，
> 都必须在 Changelog 里写明影响。**

## 自查

```
[ ] 每条都写了 why？
[ ] ⭐ 行为改变都写了"影响"？
[ ] ⭐ 触发范围变化被单独记录？
[ ] 安全变更单独分类？
[ ] 改动时写，而不是事后补？
[ ] ⭐ 读者能据此决定"要不要升级"？
[ ] 没有把多行改动压成一条？
```

## 一条补充

变更日志还有一个隐性用途：

> ⭐ **它是"这个技能经历过什么"的唯一叙事。**

半年后接手的人读一遍 Changelog，
就能知道这个技能踩过哪些坑、为什么长成现在这样——
**这比读当前版本的 SKILL.md 信息量大得多**，
因为当前版本只显示结果，不显示被否决过的方案。
