# 优先级冲突：你的技能被谁盖住了

> 一个很容易被误诊为"技能坏了"的问题：
> ⭐ **它其实没坏，只是有一个同名的更高优先级技能。**

## 优先级顺序

```
企业（Enterprise）
  ↓
个人（Personal）
  ↓
项目（Project）
  ↓
插件（Plugins）
```

还有一个层级在更上面：**受管设置**（managed-settings.json）。

## 冲突长什么样

```
有一个企业级的 "code-review" 技能
你也有一个个人的 "code-review" 技能
→ ⭐ 企业版每次都赢，你的那份永远不会被用到
```

症状上看起来像"我的技能不生效"，
但验证器通过、文件名正确、手动调用也可能被拦
——因为**路由在第一轮就选了别人**。

## 两个选择

**① 改名（通常更省事）**

```
code-review → code-review-frontend
              code-review-security
```

> ⭐ 让名字更有区分度，顺带解决了 `library-size-effect.md`
> 里说的"遮蔽"问题——**同名和近义都会增加路由的不确定性**。

**② 找管理员谈企业版技能**

适合你确实想改的是企业版内容的场合。

## 插件技能不出现

装了插件但看不到它的技能：

```
① 清缓存
② 重启客户端
③ 重装
```

三步之后还不出现 → **插件结构可能有问题**，
这时候验证器才真正派上用场。

⚠️ 插件技能有命名空间（`plugin-name:skill-name`），
所以它们**不会**和用户/项目技能因为同名冲突——
如果你遇到了同名冲突，冲突方一定是企业/个人/项目这三档之一。

## 选中了错的技能

如果 agent 用错了技能，或在几个技能之间"犹豫"：

> ⭐ **原因几乎总是：几个 description 太像了。**

修法不是加更多关键词，而是**让它们彼此区分**：

```
❌ 两个技能都写 "分析代码"
✅ 一个写 "分析性能瓶颈"，另一个写 "分析安全漏洞"
```

一个反直觉但重要的点：

> ⭐ **写得尽可能具体，不只是帮你决定"何时用我的技能"，
> 也是在防止它和别的听起来相似的技能打架。**

## 一套排查顺序

遇到"技能不工作"，按这个顺序走，走到哪一层解决了就停：

```
① 结构层
   ├ SKILL.md 在具名目录里（不在 skills 根）
   ├ ⭐ 文件名恰好是 SKILL.md（大写 SKILL，小写 md）
   ├ YAML 前置正确（--- 顶格，无未闭合引号，无 tab/空格混用）
   ├ name 与目录名一致
   └ 跑验证器
   ⭐ 这一步过不了，不要往下看

② 触发层
   └ 手动强制调用："使用 XXX 技能处理这个"
     能执行 → description 问题
     没反应 → 回到第 ① 步（根本没加载）

③ 优先级层
   ├ 与全局规则冲突吗？
   ├ ⭐ 有同名的更高优先级技能吗？
   └ 关掉其他技能单独测，排除互相干扰

④ 环境层
   ├ 运行模式支持技能吗？
   ├ 依赖装了吗？脚本有 chmod +x 吗？
   └ ⭐ 路径分隔符：一律正斜杠，Windows 也是
```

经验分布：

```
~80%  在第 ① 层解决
~15%  在第 ② 层
~5%   在后两层
```

## 三个常被漏掉的运行期原因

```
① 依赖缺失
   ⭐ 外部包必须已安装
   ——把依赖信息写进技能，让 agent 知道需要什么

② 权限
   ⭐ 被引用的脚本需要 chmod +x
   ——加载成功但执行失败，就是这一类

③ 路径分隔符
   ⭐ 一律用正斜杠，即使在 Windows 上
```

## 一条元原则

> 很多人觉得"技能不稳定、容易出 bug，是 AI 技术不成熟"。
> 但真实情况是：**绝大多数问题是低级错误 + 认知偏差。**

认知偏差那部分，最典型的就是**用自己写 description 时的措辞去测试**——
见 `description-patterns.md` 与 `trigger-debugging.md`。
