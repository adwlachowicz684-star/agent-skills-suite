## 1. ⭐⭐⭐ 失败模式：deploy and pray

**典型剧本**：

```
评估供应商 → 跑试点 → 买了 license
⭐ 六个月后：utilization 20%
⭐⭐ 当初推动这个工具的 champion 已经去忙别的事了
```

> ⭐⭐⭐ **"这是 AI agent 部署最常见的失败模式——
> ⭐⭐⭐ 而且它几乎⭐ 与技术无关。"**
>
> ⭐⭐ **Adoption 是 agent 项目的生死线。**

**为什么"像软件部署那样做"不管用**：

```
⭐⭐ 多数团队把它当软件部署：配置 → 宣布 → 培训一次 → 完事
   这对"用更好的版本替换现有工作流"的工具是有效的
⭐⭐⭐ 但 agent ⭐ 改变的是"工作怎么做"，不只是"用哪个工具做"
   → ⭐⭐⭐ 那是⭐ 行为改变，行为改变需要的远不止一次午餐会
```

> ⭐⭐⭐ 这个区分很关键，且与我们此前记的一条完全对上：
> `worth-skillifying.md` 说"高频是必要条件不是充分条件"，
> `adoption-metrics.md` 说"测出席率等于什么都没测"——
> **同一件事在三个层面各说了一次：采用是行为改变问题。**

## 2. 三个真实原因

```
① ⭐⭐ 恐惧被替代
   "公司说要给你的工作流部署 agent"，很多人听到的是⭐ "要自动化掉你的岗位"
   ⭐⭐⭐ 即使本意不是这样，恐惧是真的，而且它会杀死采用
   ⭐⭐ 人们不会使用一个他们认为⭐ 设计来取代自己的工具
   → 他们会找到它不管用的理由、⭐ 不报告问题、⭐ 悄悄绕开它

② ⭐⭐⭐ 没有清晰的"对我有什么好处"
   ⭐⭐ "这能给公司省钱"⭐ 不是让个人贡献者改变工作流的充分理由
   ⭐⭐ 采用需要⭐ 个人收益：更少的枯燥活、更快的结果、
        更少的加班、⭐ 在他们被考核的指标上更好的表现

③ ⭐ 技能/工具本身（这也是有真实分量的，见下）
```

> ⭐⭐⭐ 第 ② 条特别值得记，因为多数推广材料都在讲"对公司多好"。
> ⭐⭐ 正确的转化是：**把组织收益翻译成个人收益**。

## 3. ⭐⭐ 六步

**Step 1：从痛点切入，而不是从工具切入**

```
⭐⭐ 在提到 AI agent 之前，先找出⭐ 团队已经在抱怨的具体工作流痛点
   "我每天花 3 小时给交易分类"
   "我的工单队列处理不过来"
   "每次通话前我都要做同样的调研"

⭐⭐ 产出时的话术：
   ⭐⭐⭐ "我们听说大家讨厌 X，这是我们正在做的"  ← 对
   ❌ "管理层要大家学一个新东西"                ← 错
```

> 动作：**访谈 3–5 位成员，问他们最枯燥的重复任务**，
> 然后把 agent 的能力⭐ 映射到这些具体抱怨上。

**Step 2：⭐⭐⭐ 第一个用例要 ruthlessly 挑**

四个条件（**必须同时满足**）：

```
① ⭐ 高频（每天或每周，不是每季度）
② ⭐⭐ 明显枯燥（⭐ 所有人都同意这是苦活）
③ ⭐⭐ 可度量（⭐ 能用团队已经在追踪的数字展示前后对比）
④ ⭐⭐⭐ 低风险（⭐ 错了只是烦人，不是灾难）
```

**理想例子**：交易分类 · 工单分诊 · 会议准备摘要 · 邮件初稿。

> ⭐⭐⭐ 第 ④ 条"低风险/错了只是烦人"与我们已有的一条⭐ 完全对上：
> `team-adoption.md` 说"工程师把 agent 用在手上最棘手的任务上——那个自己都解决不了的——
> 得到平庸结果，于是断定这工具还不行"。
> **两条独立来源给出同一条：第一个用例必须选"错了也无所谓"的。**

**Step 3：⭐⭐⭐ 让采用成为阻力最小的路径**

```
⭐⭐⭐ 如果用 agent 比老流程⭐ 多一步，采用就会失败
⭐ agent 应该在⭐ 团队已经在用的工具里，而不是：
   新开一个标签页 · 学一个新界面 · 在系统间复制粘贴
```

**具体**：
```
团队在 Slack → ⭐ 结果就在 Slack 里呈现，别让他们去登录 dashboard
用 Zendesk   → ⭐ agent 直接写进工单，别发邮件让他们审
在邮箱工作   → ⭐ 把简报做成日历事件备注或邮件摘要
```

**Step 4：⭐⭐ 造内部 champion，不是管理员**

```
⭐⭐ 找 2–3 位⭐ 对 AI 好奇的人（⭐ 不一定要最技术，⭐ 只要最愿意改变）
   给他们早期访问、征求反馈、让他们⭐ 按自己的工作流定制

⭐⭐⭐ "当更广的团队看到⭐ 是同伴而不是管理层在用，采用就自然发生了"
⭐⭐⭐ ⭐ champion 应该是在团队会议上汇报结果的人
   ⭐⭐⭐ "来自同伴的一句'我怎么用、省了多少'，
        ⭐⭐⭐ 比供应商演示有说服力 10 倍"
```

**Step 5：⭐⭐ 每周度量并分享 wins**

```
⭐⭐ 追踪团队⭐ 真正在乎的指标（不是抽象 ROI）：
   每人每周省多少小时 · 之前积压的任务完成了多少
   响应时间改善 · ⭐ 错误率（应该下降，不该上升）

⭐⭐ ⭐ 每周在团队已经在读的渠道里分享
⭐⭐⭐ 要⭐ 具体到人和数字：
   "Sarah 的团队这周多解决了 40% 的工单，AI 处理了首轮响应"
```

**Step 6：⭐⭐⭐ 直面恐惧**

```
⭐⭐⭐ 不要假装"被替代"的担忧不存在
⭐⭐ 在推广时直接说清楚：
   "这个 agent 处理【枯燥任务】。
    ⭐ 你的角色转向【更高价值的工作】。
    ⭐⭐ 具体是什么样子：……"
```

## 速查

```
□ ⭐⭐⭐ deploy and pray = 最常见失败模式，⭐ 与技术无关
   ⭐⭐⭐ agent 改变的是"工作怎么做"→ ⭐⭐ 行为改变 > 工具替换

□ ⭐⭐⭐ 恐惧被替代：人们不会用⭐ 他们认为设计来取代自己的工具
   → 不报告问题、⭐ 悄悄绕开
□ ⭐⭐⭐ ⭐ "给公司省钱"不是个人收益 → ⭐ 翻译成：少枯燥/快/不加班/指标好看

□ ⭐⭐ 六步：
   ① ⭐ 从痛点切入（访谈 3–5 人）话术"我们听说大家讨厌 X"
   ② ⭐⭐⭐ 第一个用例四条件：高频 · 明显枯燥 · 可度量 · ⭐⭐⭐ 低风险
   ③ ⭐⭐⭐ 采用必须是阻力最小路径（在 Slack 就在 Slack 里呈现）
   ④ ⭐⭐ champion（⭐ 好奇 > 技术；⭐⭐⭐ 同伴说服力 10×）
   ⑤ ⭐⭐ 每周分享，⭐⭐⭐ 具体到人和数字
   ⑥ ⭐⭐⭐ 直面恐惧，说明"你的角色转向什么"

□ ⭐⭐⭐ "第一个用例必须选错了也无所谓的"——两条独立来源一致
```

**一句话**：

> ⭐⭐⭐ **多数 agent 部署失败在采用不在技术——
> 因为 agent 改变的是"工作怎么做"而不是"用哪个工具做"；
> 所以第一个用例必须 ruthlessly 选高频、枯燥、可度量、且错了只烦人不灾难的那一个，
> 而且采用必须是阻力最小的那条路径。**
