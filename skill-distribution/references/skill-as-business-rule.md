## 1. ⭐⭐⭐⭐⭐ 一个真实的半天

```
一开始为了省事，技能文件直接覆盖更新。

某次运营同学改了"查售后政策"的 description，
线上模型于是把售后政策理解成"仅限某些品类"——
当天售后咨询的准确率掉了一截。

⭐ 我们花了半天才定位到：是描述改动引起的。
```

四件事值得单独拎出来：

| 观察 | 含义 |
|---|---|
| ⭐ 改动者是**运营**，不是工程 | ⭐⭐ 能改技能的人，往往不知道自己在改一条业务规则 |
| 改的是 **description**，不是正文 | ⭐⭐⭐ 看起来最无害的改动 |
| 影响是**当天**的 | 没有灰度、没有缓冲 |
| 定位花了**半天** | ⭐⭐⭐ 因为没有 diff 可查——文件被覆盖了 |

> ⭐⭐⭐ **最后一条是整份文档的题眼：
> 半天不是花在修上，是花在"找出改了什么"上。**

## 2. ⭐⭐⭐⭐⭐ 技能是业务规则的数字孪生

> ⭐⭐⭐ **技能就是业务规则的数字孪生。**
> **业务规则怎么管理，技能就该怎么管理——
> 不要因为它是一种"给模型看的文本"就降低标准。**

这句话的锋利处在于**它直接否定了最常见的豁免理由**：

```
"这不就是改几句话嘛，又不是改代码"
        ↓
⭐ 它承载的是"售后政策适用于哪些品类"这种实打实的业务规则
```

把这句话翻译成可执行的对照表：

| 业务规则怎么做 | 技能就该怎么做 |
|---|---|
| 变更要走审批 | ⭐ 改动走 PR |
| 有版本号与生效日 | ⭐ 有 version 与 Changelog |
| 上线前要回归 | ⭐⭐ 合并后自动触发回归测试 |
| 能回滚 | ⭐ 有上一版可切回 |
| 谁改的要有记录 | ⭐⭐ 不要直接覆盖文件——**覆盖就丢失了"谁改的、改了什么"** |

## 3. ⭐⭐⭐⭐ 为什么"改描述"最危险

结合已有素材，三个独立来源指向同一处：

```
① 本份：运营改 description → 当天准确率掉一截
② scope-multiplication：⭐ 70% 的技能线上事故来自"未经评估的 prompt 微调"
③ eight-practical-lessons：⭐ 只改描述就能带来 50% 效果提升
```

> ⭐⭐⭐ **把 ② 和 ③ 放在一起看才完整：
> description 是杠杆最大的地方——
> 所以它既能带来 50% 的提升，也能造成 70% 的事故。**

而它之所以"看起来无害"：

- 不是代码，不触发 CI
- 不是正文，不影响"流程"
- ⭐ **改完通常不跑评测**——因为没有"代码变了"这个信号

> ⭐⭐⭐ 对策只有一条：**把 description 的改动也纳入回归触发条件**
> （见 `ci-skill-validation.md` 的 path filter）。

## 4. ⭐⭐⭐⭐ 最小可用版本管理

原作者的落地方案，三步就够：

```
① 所有技能文件接入 Git（⭐ 不要再直接覆盖更新）
② 每次改动走 PR
③ ⭐ 合并后自动触发回归测试
```

> ⭐⭐ **"这看起来慢，实际上是把试错成本前移了。"**

对应到我们已有的工具链：

| 环节 | 用什么 |
|---|---|
| 结构校验 | `validate_skill.py`（CI 里能跑） |
| 行为回归 | `claude -p` 跑 eval 集（`ci-skill-validation.md`） |
| 灰度 | `stable/dev` 标签（`team-landing-seven.md`） |
| 回滚 | 切标签，指针移动 |

⚠️ 一个诚实提醒（来自 `ci-skill-validation.md` 的实测）：
**给 40 个已存在的技能补装 lint 花了一整个下午。**
所以"从第一天做"的真正理由不是规范，是**补装的成本非线性**。

## 5. ⭐⭐⭐ 四类改动的危险等级

不是所有改动值得同样的流程——按危险度分档才可持续：

| 改动 | 危险 | 理由 | 最低要求 |
|---|---|---|---|
| 错别字、格式 | 低 | 不改变语义 | 直接合 |
| 正文补充说明 | 中 | 可能影响行为 | PR + 跑一遍 |
| ⭐ **description** | ⭐⭐ **高** | ⭐ 杠杆最大，静默影响触发与理解 | ⭐ PR + 触发评测 |
| ⭐ **规则口径**（如"适用于哪些品类"） | ⭐⭐⭐ **最高** | ⭐⭐ 改的是业务规则本身 | ⭐ PR + 业务方确认 + 回归 + 灰度 |

> ⭐⭐⭐ **这张表的价值在于：它让"所有改动都走全套流程"变得不必要。**
> 只有把低危的放行，高危的严卡才守得住。

## 6. ⭐⭐ 一句该贴在墙上

> ⭐⭐⭐ **不要因为它是一种"给模型看的文本"就降低标准。**

配套一个自检问题，改技能前问一遍：

```
⭐ 这次改动，如果被改成错的，
   多久会被发现？谁能发现？有没有 diff 可查？
```

三个问题有一个答不上来 → 先补版本管理，再改。
