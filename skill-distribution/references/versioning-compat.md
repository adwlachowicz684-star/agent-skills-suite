# 版本、兼容与废弃

> ⭐ **默认假设必须是：对工具名称、描述或 schema 的任何改动都是潜在的破坏性变更。**
> **失败是静默的，爆炸半径不可预测，而传统 API 测试不足以捕捉"语义漂移"这一 AI 特有的失败类别。**

## 为什么提示词里的破坏性变更更隐蔽

```
改代码里的函数签名 → 类型错误，立刻可见
改技能里的指令措辞 → 可能微妙改变行为，静态分析抓不到
```

> ⚠️ **一个典型场景**：
> 一个原本返回结构化 JSON 的技能，现在多了一段散文解释——
> **对任何解析它输出的下游都是破坏性变更。**

**还有一类更隐蔽的——能力漂移**：

> 技能声明自己"会搜索 2023 年之后的文档"，
> 实现者为了性能悄悄加了"只搜最近 30 天"的逻辑。
> **声明没改，行为变了。CI 全绿，agent 继续调用，以为拿到了符合承诺的结果。**

## SemVer 在技能里的具体含义

| 级别 | 含义 | 例子 |
|---|---|---|
| **MAJOR** | 破坏性变更 | 删/改名/改数据类型的必填参数；**输出结构变了**；提示词语义改变到移动了模型的决策边界 |
| **MINOR** | 向后兼容的新增 | 新增**可选**参数（带合理默认值）；输出**追加**新键（原结构不变）；底层脚本升级但旧输入处理一致 |
| **PATCH** | 内部修复与优化 | 压缩 description 措辞省 token（不改核心指令）；优化查询降低延迟；加输入净化防注入（合法输入仍被接受） |

> ⚠️ **一个 AI 特有的扩展**：
> **不是每次 description 改进都是安全的**——
> 改 description 会改变**触发边界**，可能该触发的不再触发。
> 这类改动应按 MAJOR 或至少 MINOR 对待，并跑触发测试。

**MAJOR 版本必须包含**：

```
□ Breaking Changes 说明
□ Migration Guide（迁移指南）
□ 灰度发布计划
```

**CHANGELOG 格式**（Keep a Changelog 规范）：

```
六个分类：Added · Changed · Deprecated · Removed · Fixed · Security
```

## 如何做到向后兼容

**① Schema 可扩展设计**

> 一开始就为灵活设计。**慷慨地使用可选字段。**
> 新需求出现时，作为**带合理默认值的可选参数**引入，
> 而不是修改已有的必填字段。

**② 输出可加性（output additivity）**

> ⭐ **AI agent 解析工具输出时，是去找特定键来决定下一步。**
> 需要返回更全的数据时，**往 JSON 响应里加新键**，
> 而不是重构已有层级。
> **LLM 会直接忽略新键，直到你更新指令让它用。**

**③ 新工具策略**

> ⭐ **如果核心逻辑需要彻底改造，另起一个新技能（如 `CodeReview_v2`）
> 几乎总是比对原技能做行为改变更安全。**
> 这样可以逐步迁移 agent，观察性能与推理路径，再下线旧版。

**④ 输出信封版本化**

```json
{
  "_v": "2.1",
  "_schema": "candidate_evaluation",
  "data": { ... }
}
```

> 下游检查 `_v`，在迁移窗口期内可同时处理多种格式。

**⑤ 目录级版本化（当前现实）**

> ⚠️ **目前没有内置的版本系统**——
> "如果你更新了技能的行为，所有使用它的应用会立即用上新版本。"
> 当前的变通做法是 `skills/v1/`、`skills/v2/` 目录结构。
> 预计 H2 2026 会正式出现 lock file 工具。

## 废弃四阶段

> ⭐ **目的是防止"僵尸技能"占据 agent 的上下文窗口、
> 增加延迟、白白烧 token。**

**阶段 1：标记与文档**

```
□ 内部元数据标 @deprecated
□ ⭐ 更重要的：更新技能的 description（LLM 会读的那段），
   明确警告已废弃并指定替代方案
   ——这是上下文内的威慑，agent 读到就不会选它
```

**阶段 2：遥测与监控**

```
□ 分析审计日志，找出哪些 agent/工作流/用户仍在调用旧技能
□ 从而主动、定向地推动迁移，而不是被动救火
```

**阶段 3：软废弃（警告载荷）**

```json
{
  "status": "success",
  "data": { ... },
  "warning": "This skill will be removed on 2026-08-01. Please migrate to DatabaseQuery_v2."
}
```

> **正常处理请求，但在输出里附显著警告**——
> 提醒看日志的开发者，又不打断当前执行。

**阶段 4：硬废弃（下线）**

```
□ 从活跃路由注册表移除
□ agent 再调用应返回硬错误
□ ⭐ 错误信息要高度描述性：说明失败原因，
   并明确指示 LLM 如何用新版工具集恢复
```

## 三条互补防线

> 行业已收敛到这三条，缺一不可：

```
1. SemVer 纪律（含 AI 特有扩展：description 级别的 MAJOR 提升）
2. CI 里的工具表面哈希（tool surface hashing）
   ——最可靠的结构性闸门
   对向 agent 暴露类工具接口的技能，计算并存储"表面哈希"；
   表面变化需要显式确认与版本理由
3. CUJ 行为评测（critical user journey）
   ——唯一能捕捉语言级语义漂移的手段
   上线前跑一组关键工作流场景，任一场景回归即硬阻断
```

**另外两条实用建议**：

```
□ 过渡期并行维护 skill_v2 与旧版，迁移完成后再废弃旧版
□ 维护机器可读的工具清单 manifest：
   所有活跃工具/技能 + 当前版本 + 表面哈希 + 废弃状态
   ——这样在多个组件同时更新时能自动做兼容性检查
```

**灰度发布节奏**（参考）：

```
Day 1  灰度 5%  监控任务完成率·错误率·P95 延迟，与旧版同期对比
Day 3  无退化 → 20%
Day 5  无退化 → 50%
Day 7  无退化 → 100%
任意阶段出现退化 → 立即回滚
```

## 发布前检查表

```
□ Schema：是否删除/改名/改了类型的必填参数？（是 → MAJOR）
□ 输出完整性：是否保留了所有已有键与格式？（改了 → MAJOR）
□ 提示词语义：自然语言指令是否改变到移动了决策边界？
              （是 → MINOR 或 MAJOR，需人工测试）
□ 功能新增：是否严格实现为带默认值兜底的可选参数？（是 → MINOR）
□ 安全面：是否引入了新的文件系统改动、网络请求或提权？
□ 依赖：上游技能兼容性是否验证过？
□ 循环依赖：技能互相调用是否可能成环？
           （注册表需要环检测，不能只靠运行时发现）
□ 测试用例：升级后是否跑过完整测试？
□ 如果是 MAJOR：是否有 Breaking Changes 说明 + 迁移指南？
□ 是否规划了灰度与回滚？
```

## 自查

```
□ 是否默认假设"任何改动都是潜在破坏性变更"？
□ 是否用输出信封带了版本字段？
□ description 改动是否被视为可能影响触发边界？
□ 新增功能是可选参数还是改了必填参数？
□ 输出是追加键还是重构层级？
□ 彻底改造时是否选择了"另起新技能"而非改旧技能？
□ 废弃是否走了四阶段（尤其阶段 1 改 description）？
□ CI 里是否有工具表面哈希？
□ 是否有 CUJ 行为评测作为上线闸门？
□ 是否有工具清单 manifest？
□ 是否规划了灰度节奏与回滚？
```
