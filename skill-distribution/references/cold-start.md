## 1. ⭐ 别从最棘手的任务开始

> ⭐ 工程师常把 agent 用在**手上最棘手、自己都解决不了**的任务上，
> 得到平庸结果，于是断定"这工具还不行"。
>
> **他们选了最糟糕的第一个任务。**

这是团队推广的头号卡点（见 `team-adoption.md`）。
第一个技能的目的是**建立信任**，不是挑战最难的问题。

---

## 2. 三类适合的入门任务

agent 擅长的是：

```
⭐ 范围明确 · 机械化 · 高上下文
```

对应地，第一个技能应挑：

| 特征 | 例子 |
|---|---|
| 高频且烦人 | 每日站会同步、周报生成、依赖升级检查 |
| 有明确 SOP | 代码评审清单、发布检查表 |
| 上下文大但判断简单 | 大 diff 审查、日志归类 |

> ⭐ 让人感觉是**解脱**，而不是多了一套流程。

---

## 3. 按技能类型挑

九种类型里，官方建议挑**能立刻解阻塞**的：

```
⭐ 类型 4：流程自动化
⭐ 类型 1：库/API 参考
```

> ⭐ **不要一次把九种都建起来。**

一次做一个，加埋点，迭代。

---

## 4. 最小起步

```
① 选一个高频烦人的小任务
② 写最小可用 SKILL.md（不用一上来就完美）
③ 自己用一周
④ ⭐ 记录每次失灵，转成 Gotchas
⑤ 再考虑给团队
```

这与 `catalog-shape.md` 的"渐进复杂度三版本"一致：
**先让它能跑，再按测出来的缺口加层。**

---

## 速查

| 要做 | 不要做 |
|---|---|
| ✅ 高频烦人的小事 | ❌ 最棘手的问题 |
| ✅ 范围明确 | ❌ 边界模糊 |
| ✅ 一次做一个 | ❌ 一次建九种 |
| ✅ 用一周再推广 | ❌ 写完就发团队 |
