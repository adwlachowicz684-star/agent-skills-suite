## 1. 什么时候需要注册中心

```
<10 个技能      提交到仓库 .claude/skills/ 就够了
10–50 个        需要发现机制（否则重复建设）
⭐ >50 个        需要注册中心：版本、权限、审计
```

典型痛点（出现任意两个就该考虑）：

```
技能散落在各个团队，缺乏统一管理
版本混乱，难以追溯
缺乏权限控制，安全合规风险高
没有发现机制，重复建设严重
```

## 2. 四个必备能力

| 能力 | 具体要求 |
|---|---|
| **发布与版本** | 语义化版本 + 发布标签（beta / stable）+ 自动追踪 latest |
| **发现** | 多维搜索：按命名空间过滤、按下载量/评分排序、按时间筛选 |
| **访问控制** | 见第 3、4 节 |
| ⭐ **审计** | ⭐ **所有治理操作都要有完整审计日志**——不只是"记录"，是"可追溯" |

> 一个判断标准：**能不能回答"三个月前谁发布了这个技能的哪个版本、谁批准过"**。
> 答不上来，就不叫注册中心。

## 3. 命名空间：分类靠元数据，不靠目录

这是与 `packaging.md` 一致的原则，在注册中心里更重要：

```
❌ skills/security/...  skills/data/...     目录分类
✅ 扁平结构 + namespace 元数据字段
```

原因：目录分类会让**同一个技能只能属于一类**，
而注册中心需要的是多维检索（按团队 + 按领域 + 按成熟度）。

**可见性规则**也挂载在命名空间上：团队命名空间内可设"仅本团队可见 / 全公司可见"。

## 4. RBAC 四角色

```
平台管理员  →  全局策略制定
团队管理员  →  命名空间内审核
发布者      →  技能发布权限
使用者      →  技能安装权限
```

配套的成员角色（Owner / Admin / Member）决定**谁能改发布策略**。

> ⭐ **审核者的存在感决定注册中心的质量**——
> 没有审核环节，注册中心会退化成"共享文件夹"，
> 这正是 `team-sharing.md` 那句"没有治理流程的 monorepo 只是共享文件夹"的企业版。

## 5. 权限边界：别让技能继承人的全部权限

> ⭐ **不要让 Skill 天然继承人的全部权限。**

更安全做法：**为 Agent 和 Skill 分配独立身份，按任务申请最小必要权限。**
这样即使某个技能出问题，**影响范围被限制在授权边界内**。

权限边界应覆盖：**文件系统 · 数据库 · 网络 · API · 密钥 · 环境变量 · 外部服务**。

三条具体规则：

```
只需读知识库的技能      → 不允许写业务系统
只需生成草稿的技能      → 不允许自动发送正式通知
只需访问测试环境的技能  → 不具备生产环境权限
```

**高风险操作必须人工确认**——涉及**资金 · 合同 · 人员 · 生产配置 · 客户隐私 · 跨境数据传输**时，
Agent 可以负责分析、生成计划、准备材料，
⭐ **但真正执行前应暂停等待授权**。这与 `approval-gates.md` 一致。

> 治理的目标**不是让 AI 完全失去自主性**，而是让自主性在可接受边界内运行。

## 6. 个人技能转团队资产：七步

如果你手上有一个调教好的个人技能，按这个清单转成团队 SOP：

| 步骤 | 做什么 | 为什么 |
|---|---|---|
| 1 **参数化** | 把写死的路径、人名、项目名改成变量 | 让其他人能填自己的信息 |
| 2 **脱敏** | 删掉个人偏好、内部术语 | 避免泄露个人信息或造成误解 |
| 3 **规范命名** | 英文标识，避免中文和特殊字符 | 防止解析失败 |
| 4 **打包上传** | 按企业包结构打包，上传到企业库 | 进入统一管理流程 |
| 5 **设可见范围** | "所有成员"或"部分成员" | 控制谁能看到和使用 |
| 6 **配下发策略** | 白名单/黑名单限制使用范围 | 防止不该用的人误用 |
| 7 ⭐ **验证执行** | ⭐ **用其他成员的账号跑一遍** | 确认权限链路没问题 |

> ⭐ **第 7 步最容易翻车。**
> 有实践者总结："提前理清权限链路，可以省去后期大量沟通成本。"
>
> 你自己账号能跑 ≠ 别人能跑——**权限、环境变量、路径依赖都可能是你独有的**。

四道门槛一句话版：**规范打包 · 分类归属 · 权限控制 · 审计追溯**。

## 7. 分级自治

企业级治理的常见分层（从受控走向自主）：

| 级别 | 特征 |
|---|---|
| **L0 受控执行** | 人工主导、明确指令、强约束、全程可审计 |
| **L1 辅助自治** | 在策略边界内决策，建议为主，人机协同 |
| **L2 条件自治** | 目标导向自主规划，策略放行后自主执行 |
| **L3 高阶自治** | 跨域协同、自我优化、持续学习、价值对齐 |

> 落地建议：**从 L0/L1 起步**。
> 直接上 L2/L3 的团队，通常在第一次事故后回退到 L0——
> 但那时已经损失了信任（见 `team-adoption.md` 里"信任的负面对称性"）。

## 速查

| 问题 | 处置 |
|---|---|
| 技能散落、重复建设 | 上注册中心 + 发现机制 |
| 分类混乱 | ⭐ 扁平结构 + namespace 元数据 |
| 谁都能发布 | RBAC 四角色 + 审核 |
| 技能权限过大 | ⭐ 独立身份 + 最小授权，不继承人的权限 |
| 个人技能要共享 | 七步清单，第 7 步换账号验证 |
| 想直接上高自治 | 从 L0/L1 起步 |
