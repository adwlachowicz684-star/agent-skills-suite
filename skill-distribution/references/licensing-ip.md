# 许可与知识产权

> ⭐ **Skill 是一种"四不像"的新物种**——
> 不像传统软件（不需编译、不直接执行），
> 不像纯文档（塞满"按这个步骤做"的指令逻辑），
> 也不像配置文件（复杂度远超几行 YAML）。
>
> **它的法律属性至今没有定论。**

## 可版权性：连法务都不敢说死

> 开源倡议组织邮件列表里，Red Hat 资深法务的原话：
> **"至少有一部分 Skill 文件，很可能具有可版权性。"**
>
> ⭐ 关键词是"至少有一部分"——连法务大佬都不敢把话说死。

**为什么模糊**：

```
美国版权法 §102(b) 把
"想法、程序、流程、系统、操作方法"排除在版权保护之外。

而 Skill 文件的核心恰恰是"告诉 AI 怎么做"
——这到底是受保护的"表达"，还是不受保护的"方法"？
没人能给出确定答案。
```

**一个可用的判断梯度**：

```
简单技能（"帮我把代码格式化"）  → 大概率不受保护
经过精心打磨、包含个性化判断框架与策略逻辑的复杂技能
                              → 更可能跨过独创性门槛
```

> 中国司法已有相关判例：判决书明确，若用户撰写的是**具备文学独创性的文本**
> 并以此为基础让 AI 创作，此时提示词已超越纯粹的功能指令，
> **可能构成受保护的文字作品**。
> ⭐ **Skill 本质上就是一套系统化的提示词**，这个逻辑直接适用。

## 许可证地图：四种逻辑并存

> ⭐ **同一个生态圈，四种完全不同逻辑的许可证——这不是百花齐放，是法律上的定时炸弹。**

| 许可证 | 采用者 | 实际含义 |
|---|---|---|
| **限制性专有许可** | Anthropic 官方 Skills | 禁止复制、修改、在其他框架使用 |
| **MIT** | Tavily、OpenClaw、.NET 社区 | 随便用，后果自负 |
| **Apache 2.0** | Agent Skills 规范仓库 | 加上专利授权条款 |
| **CC-BY-4.0** | 部分技能内容 | 文档用知识共享许可 |

**争议焦点**：Anthropic 官方 Skills 仓库（GitHub Issue #100）
以"给社区做示范"为名，每个技能文件夹里却塞着极端限制性 LICENSE
——不允许本地副本、不允许修改、不允许在非 Anthropic 框架使用。
社区原话：*"把开源库拿来，加点指令和脚本，然后套一个限制性许可——品味很差。"*

> ⚠️ **对使用者的直接含义**：
> **装第三方技能前先看它文件夹里的 LICENSE**，
> 不要假设"仓库是 MIT 所以技能也是 MIT"。

**两级许可模型**：

```
仓库级    MIT（默认）
技能级    可在 frontmatter 用 license 字段单独声明
```

```
license: MIT            最大自由
license: Apache-2.0     含专利授权（算法类推荐）
license: BSD-3-Clause   学术/研究
license: CC-BY-4.0      纯文档内容
license: Proprietary    内部/商业，不应再分发
```

> ⭐ 规范支持任意 **SPDX 标识符**。
> **省略 license 字段即继承仓库许可**——所以不写不等于没许可，而是继承。

## 归属：雇主与员工的暗线

> ⭐ **这条线还没引爆，但比开源社区的争吵更实际。**

```
员工在雇佣范围内创建的 Skill
  → 自动归雇主（雇佣作品原则，17 U.S.C. §§ 101, 201(b)）

独立承包商创建的 Skill
  → 归承包商，⭐ 除非开发前签署书面转让协议

离职员工带走"一般性技能与知识"    → 合法
离职员工带走"保密的 Skill 文件"    → 若构成商业秘密且公司采取了保密措施，不合法
```

> ⚠️ **难点**：Skill 文件里"一般知识"与"商业秘密"的界线**比代码还模糊**。
>
> 一个律师花三个月打磨的"矿业并购尽调 Skill"——
> 封装了她的判断框架、风险点库、谈判策略——
> **这是她的一般知识，还是公司资产？**

**目前最实用的保护形式**：

> ⭐ **商业秘密可能是目前对 Skill 最强有力的保护形式**——
> 因为它保护的是"有价值且保密的信息"，
> **不依赖版权法对"表达 vs 想法"的纠结判断**。
>
> **前提是：公司确实采取了保密措施**（访问控制、不进公开仓库、保密协议）。

## 中国语境

**定性困境**：

```
《著作权法》第十六条、《计算机软件保护条例》第十三条
规定"特殊职务作品"的著作权（除署名权外）自动归单位。

⚠️ 但 Skill 算不算"计算机软件"？
   一个不需编译、不直接执行的 SKILL.md，跟传统软件差得远。

→ 若法院不认它是软件，只能适用"一般职务作品"：
   著作权归作者，⭐ 公司仅有两年优先使用权。
```

> 对花钱让员工开发 Skill 的企业，这个区别足够让法务失眠。

**额外的监管层**：

```
《生成式人工智能服务管理暂行办法》第七条：
训练数据处理活动"涉及知识产权的，不得侵害他人依法享有的知识产权"
GB/T 45652：开源数据"需具备开源许可协议或相关授权文件"
```

> ⭐ **中美的关键差异**：
> 在美国，许可证违规主要是**合同法问题**；
> **在中国，它同时是行政合规问题**——两条线同时触发。

**另一条可能的救济路径**：

```
参考 AI 漫画特效案：法院认定 AI 生成成像不构成作品，
但认定被告使用了原告投入大量人力物力形成的模型结构与参数，
构成不正当竞争，判赔 320 万元。

⭐ 这个裁判逻辑——保护具有竞争价值的经营成果——对 Skill 有参考意义。
即便内容不完全满足著作权或商业秘密的条件，
⭐ 创作者仍可能依反不正当竞争法寻求救济。
```

## 现在能做什么

**① 写清楚许可证**

```
□ Agent Skills 规范已在 frontmatter 预留 license 字段
□ 不管 MIT / Apache 2.0 / CC-BY-4.0，写上去再说
□ ⚠️ 不声明许可证 = 默认"保留所有权利"——别人连用都不敢用
```

**② 代码与内容分开许可**

> ⭐ **这不是多此一举，而是一旦出现纠纷时的清晰证据链。**

```
scripts/  里的代码脚本  → Apache 2.0 或 MIT
SKILL.md 里的指令文档  → CC-BY-4.0
```

> 理由：一个技能可能包含来自不同来源的组件
> （核心指令自写、脚本来自开源项目、模板来自第三方），
> **若许可证不兼容（如 GPL 与 MIT 混合），整个技能的法律状态就不确定。**

**③ 雇主要做的事**

```
□ 劳动合同与承包商协议里明确写：Skill 属于"雇佣作品"，IP 归公司
□ ⭐ 对核心 Skill 做访问控制，不要放在公开仓库
□ 保密协议比竞业限制更实用
□ ⭐ 采取实际保密措施——这是商业秘密保护成立的前提
```

**④ 使用者要做的事**

```
□ 装第三方技能前先看文件夹里的 LICENSE（不要假设继承仓库许可）
□ 注意限制性专有许可的技能——可能禁止修改与跨框架使用
□ 别把 GPL 技能的内容并入自己的商业技能
□ 若用于训练，确认许可是否允许（中美合规双线）
```

## 自查

```
□ 技能的 frontmatter 是否声明了 license？
□ 代码与内容是否考虑了分别许可？
□ 是否知道省略 license 即继承仓库许可？
□ 装第三方技能前是否看过它文件夹里的 LICENSE？
□ 是否有限制性专有许可的技能被混进了可自由分发的产品？
□ 组件来源是否记录（指令/脚本/模板各自的出处）？
□ 是否存在 GPL 与 MIT 混合的兼容性问题？
□ 雇主是否在合同中明确了 Skill 的归属？
□ 核心 Skill 是否做了访问控制（保密措施）？
□ 若用于训练，是否确认了许可允许（尤其中国合规）？
```
