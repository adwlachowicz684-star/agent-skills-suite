## 1. ⭐⭐ 14 步提交流程

```
1.  提交 Skill Proposal
2.  创建 draft Skill
3.  编写最小 SKILL.md
4.  添加测试 prompt
5.  完成安全自查
6.  小范围试用
7.  提交 PR
8.  领域 review
9.  安全 review
10. 发布 pilot
11. 收集反馈和失败案例
12. 达到稳定标准后发布 active
13. 定期复审
14. 废弃或归档
```

> ⭐⭐ 这份流程可以按团队规模缩减（小团队可合并步骤），
> ⭐⭐⭐ 但有五项⭐ 不能省（见下）。
>
> ⭐⭐ 与我们已有的 `retirement-pipeline.md` 四阶段对上——
> 第 14 步"废弃或归档"正是那份文档的内容，
> ⭐ 这里把它明确写成了⭐ **生命周期的正式一环**，而不是"出事后的补救"。

## 2. ⭐⭐⭐ 五项不可省略

```
⭐ owner
⭐ 测试
⭐ review
⭐⭐ 安全边界
⭐ 变更记录
```

> ⭐⭐⭐ 注意"⭐ 安全边界"这一项——
> 它不是"安全审查"（第 9 步已经有了），
> ⭐⭐ 而是⭐ 技能自身声明并实现的边界。
> 这与 `allowed-tools-least-privilege.md`、
> `script-security-boundary.md` 是同一条：
> ⭐⭐⭐ **边界是产物的一部分，不是流程的一个环节。**

## 3. ⭐⭐⭐ 准入标准（可直接抄）

一个技能进入团队 active 列表前，必须满足：

```
1.  ⭐⭐ 有明确 owner ⭐⭐ 和备份 owner
9.  ⭐⭐⭐ 没有真实密钥、token、cookie 或客户敏感数据
10. ⭐⭐⭐ ⭐ 有脚本时必须支持 --help，⭐⭐ 并⭐ 说明副作用
11. ⭐⭐⭐ ⭐ 有参考资料时必须⭐ 说明来源或更新时间
12. ⭐⭐⭐ 有 CHANGELOG.md ⭐ 或等价变更记录
13. ⭐⭐ 至少一名领域 reviewer 通过
14. ⭐⭐⭐ ⭐ 高风险技能⭐ 需要安全 reviewer 通过
```

**逐条说哪几条最值钱**：

**第 10 条**——`--help` + 说明副作用：

> ⭐⭐⭐ 这条把"脚本要能被理解"变成了⭐ 可检查的硬条件。
> 与 `script-cli-contract.md` 的退出码分级同一思路：
> **让脚本自己声明它是什么，而不是指望读它的人看懂。**

**第 11 条**——参考资料要说明来源或更新时间：

> ⭐⭐⭐ ⭐ 这条直接对应我们反复出现的那个失败模式
> ——`"Stale references：输出错得自信而正确"`（第五个来源）。
> ⭐⭐ **"更新时间"这个字段就是把腐烂从不可见变成可见的机制**，
> 与 `skill-decay-governance.md` 的 `review_after` 是同一招。

**第 1 条**——备份 owner：

> ⭐⭐ 一个技能只有一个 owner，他休假/离职时它就进入无人状态。
> ⭐⭐⭐ **备份 owner 是"技能不会变成孤儿"的最低保障。**

## 4. ⭐⭐⭐ 六个误区

**误区四：忽略负向测试**

```
⭐⭐⭐ ⭐ 团队技能⭐ 最怕误触发
⭐⭐ 负向测试可以发现⭐ 它是否抢了别的任务
```

> ⭐⭐ 这与 `prompt-vs-skill-failure-modes.md` 的"过触发"、
> `eval-set-two-dimensions.md` 的"至少覆盖误触发场景"
> 是⭐ 第三个独立来源。
> ⭐⭐⭐ 但这里的角度不同：**团队环境下误触发的代价是别人被抢活**
> ——不是你自己的输出变差，而是⭐ **别人的技能静默失效**。

**误区五：没有废弃机制**

```
⭐⭐⭐ 旧技能如果⭐ 一直留在 active 列表，⭐⭐⭐ 会误导用户
```

> ⭐⭐⭐ "误导用户"这个措辞值得注意——
> 它说的不是成本问题（虽然成本也确实存在），
> ⭐⭐⭐ 而是⭐ **用户会以为那个技能是当前的、被维护的、可信的**。
> 与 `outgrowth-regression-detection.md` 的"被追上要归档"同源。

**⭐⭐⭐ 误区六：安全说明只写给人看**（本份最有价值的一条）

> ⭐⭐⭐ **"安全说明也要写进⭐ Agent 会读取的流程里。"**
>
> 具体例子：
> ```
> · 默认 dry-run
> · 禁止生产写操作
> · ⭐⭐⭐ 不要请求用户贴密钥
> ```

> ⭐⭐⭐ 这条很妙，因为它指出了一个⭐ 双重失败：
> 你把安全说明写在了 README 里 → 人读了 → ⭐ 但 agent 不读 README
> （README 根本不在渐进式披露的加载链里）。
>
> ⭐⭐⭐ **结果：一条"已存在"的安全说明，实际上从未被执行。**
>
> ⭐⭐ 这与 `operator-card-style.md` 的
> "安装/贡献/隐私章节一律删"（那些是写给人看的噪音）
> 形成了⭐ 完美的呼应：
> ```
> 噪音章节   → 删（人看的、agent 不读、白占 token）
> 安全说明   → ⭐⭐⭐ ⭐ 移到正文流程里（否则等于没有）
> ```
> ⭐⭐⭐ **同一个判据的两个方向：这段内容，agent 会读到吗？**

**"不要请求用户贴密钥"这条尤其值得单独记**：

> ⭐⭐⭐ 技能的正文里如果写着"请提供你的 API key"，
> ⭐⭐ 那这个技能⭐ 就是在主动制造一次密钥泄露——
> 而且它会进聊天记录。
> ⭐⭐⭐ **这是"技能会诱导用户做不安全的事"的一个具体形态**，
> 此前没覆盖过。

## 5. ⭐⭐ 评审清单（开头两项）

```
## 目标和边界
- [ ] ⭐⭐⭐ 目标任务是否明确、重复、值得技能化？
- [ ] ⭐⭐ ⭐ 是否和已有技能重复？
```

> ⭐⭐⭐ 第一项对应 `worth-skillifying.md` 的三条硬标准，
> ⭐⭐ 第二项对应 `namespace-collision.md` 与"一技能一动词"——
> ⭐⭐⭐ **"是否与已有技能重复"应该是一道门禁，不是一次提醒。**

## 速查

```
□ ⭐⭐ 14 步：Proposal → draft → 最小 SKILL.md → 测试 prompt → 安全自查
   → 小范围试用 → PR → 领域 review → 安全 review → pilot
   → 收集反馈 → active → ⭐ 定期复审 → ⭐ 废弃或归档
□ ⭐⭐⭐ 不可省略五项：owner · 测试 · review · ⭐⭐ 安全边界 · 变更记录

□ ⭐⭐⭐ 准入标准（可抄）：
   ① ⭐ owner + ⭐ 备份 owner
   ② ⭐⭐⭐ 无真实密钥/token/客户敏感数据
   ③ ⭐⭐⭐ ⭐ 脚本支持 --help + ⭐ 说明副作用
   ④ ⭐⭐⭐ ⭐ 参考资料⭐ 说明来源或更新时间（把腐烂变可见）
   ⑤ ⭐⭐⭐ 有 CHANGELOG 或等价变更记录
   ⑥ 领域 reviewer；⭐⭐⭐ 高风险需安全 reviewer

□ ⭐⭐⭐ 六误区中最值钱的三条：
   · 忽略负向测试 → ⭐⭐⭐ 团队环境下代价是⭐ 别人的技能静默失效
   · 没有废弃机制 → ⭐⭐⭐ 旧技能留在 active ⭐ 会误导用户
   · ⭐⭐⭐⭐ 安全说明只写给人看 → ⭐⭐⭐ 要写进 agent 会读的正文流程
     （默认 dry-run / 禁止生产写 / ⭐⭐⭐ 不要请求用户贴密钥）
□ ⭐⭐⭐ 判据："这段内容，agent 会读到吗？"——噪音删掉，安全说明移进正文
```

**一句话**：

> ⭐⭐⭐ **准入标准里"脚本必须支持 --help 并说明副作用""参考资料必须说明来源或更新时间"这两条最实用（后者把腐烂从不可见变成可见）；
> 而六个误区中最关键的是"安全说明只写给人看"——写在 README 里的安全约束 agent 根本读不到，等于不存在，必须移进正文流程。**
