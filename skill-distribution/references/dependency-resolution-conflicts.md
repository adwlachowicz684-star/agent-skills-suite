## 1. ⭐⭐⭐ 声明必须是结构化的

> ⭐⭐ **元数据文件（skill.yaml 或 SKILL.md 的 frontmatter）
> 是⭐⭐⭐ 唯一权威声明源。**

需包含三样：

```
① ⭐ 版本约束
② ⭐ 可选标记（required vs optional）
③ ⭐⭐⭐ 冲突声明：conflicts: ["whisper-cpp"]
```

**一条硬性要求**（与"结构化"直接对应）：

> ⭐⭐⭐ **避免自然语言描述：依赖条件必须⭐ 结构化
> （如⭐ 语义化版本号），而不是仅用文字说明（如"需要 Python 环境"）。**

> ⭐⭐⭐ 这条解释了为什么"隐藏依赖"高达 36.6% 却只有 1.4% 被声明——
> ⭐ **因为多数声明是自然语言写的，解析器读不了**。
> "需要 Python 环境"不是声明，`python: ">=3.11"` 才是。
>
> 这与 `preflight-gate.md` 的"Prerequisites 要可判定"、
> `determinism-boundary.md` 的"确定性判断用确定性机制"
> 是同一原则在依赖层的版本。

## 2. ⭐ 语义化版本的强制应用

| 段 | 变更性质 | 用户动作 |
|---|---|---|
| MAJOR 2.0.0→3.0.0 | ⭐ 不兼容的接口修改 | ⭐⭐ **强制用户手动升级调用逻辑** |
| MINOR 2.1.0→2.2.0 | 向后兼容的功能新增 | ⭐ 允许自动升级 |
| PATCH 2.1.0→2.1.1 | 仅修复问题 | ⭐ 可静默更新 |

> ⭐ 这与 `iteration-three-levels.md` 的判据完全一致
> （"沿用旧版本仍能拿到正确结果 → MINOR"），
> 但这里给了一个⭐ 更可操作的补充：**每档对应不同的用户动作**——
> MAJOR 必须手动、MINOR 可自动、PATCH 可静默。
>
> ⭐⭐ 这直接决定了你的⭐ 升级策略该激进还是保守：
> **只锁 MAJOR 就能自动拿 MINOR/PATCH，是可以的；
> 不锁就能自动跨 MAJOR，是不行的。**

## 3. ⭐⭐ 版本锁定与环境隔离

```
⭐⭐ 依赖快照：通过 skill.lock 记录⭐ 精确依赖版本（如 python: "3.11.4"）
   ⭐⭐⭐ ⭐ 避免⭐ 动态解析导致的⭐⭐ 环境漂移

⭐⭐ 环境隔离：⭐ 为每个技能分配独立虚拟环境
   （如 ~/.skills/venvs/skill-name-1.2.0）
   ⭐⭐ 避免⭐ 全局依赖冲突
```

> ⭐⭐ "环境漂移"这个词很准：**同一个 lockfile 之外的解析，
> 今天和明天可能给出不同答案**——
> 这与 `deterministic-scripts.md` 的"跑两次 diff"是同一诉求
> （确定性），只是作用层不同。

**升级策略分环境**（很实用）：

```
⭐ 生产环境 → ⭐⭐ 精确版本锁定
⭐ 开发环境 → ⭐ 范围版本
   + ⭐ 自动升级检查（定期检查依赖更新）
   + ⭐ 灰度发布（新版本先小范围测试）
```

## 4. ⭐⭐⭐ 解析流程三步

```
① ⭐⭐ 预检环境
   技能执行⭐ 前，自动验证工具/环境依赖是否满足（如检查 ffmpeg 版本）

② ⭐⭐⭐ 拓扑排序
   对技能⭐ 依赖树做⭐⭐ 无环检测 + ⭐⭐ 加载顺序规划
   ⭐⭐⭐ ⭐ 确保父技能在子技能前加载

③ ⭐⭐⭐ 动态回退
   ⭐⭐ ⭐ 若可选依赖缺失 → ⭐ 自动降级功能
   例：无邮件服务时仅生成报告文件
```

> ⭐⭐⭐ 第 ③ 条最有价值，它给出了一条⭐ 我们此前没收过的原则：
> **可选依赖缺失不该导致技能不可用，而该导致⭐ 功能降级。**
>
> 这与 `preflight-gate.md` 的
> "前置条件失败 → 快速失败；运行时失败 → 优雅降级"要区分开：
> ⭐ **必需依赖缺失 = 前置失败（快速失败）；
> ⭐⭐ 可选依赖缺失 = 降级（继续跑，少一项功能）。**
> ⭐⭐⭐ 这就是为什么要⭐ 显式区分 required 与 optional——
> 不区分，就只能二选一。

**依赖图还有一个用途**：

```
⭐⭐ 维护技能依赖关系图 → ⭐⭐⭐ 快速定位⭐ 循环依赖或⭐ 高风险节点
```

> ⭐ 与 `deprecation-compat-strategy.md` 的
> "环的检测必须在（名字,版本）二维上做"配套——
> 那份给检测维度，这份给⭐ 可视化手段。

## 5. ⭐⭐⭐ 冲突解决两个机制

```
① ⭐⭐ 版本兼容矩阵
   定义技能间的兼容性规则
   例："v1.0.x" 兼容 ["1.0.0", "1.0.1"]
   ⭐⭐ 避免⭐ 不兼容版本共存

② ⭐⭐⭐ 显式冲突声明
   元数据标注⭐ 互斥依赖：conflicts: ["tool-legacy"]
   ⭐⭐⭐ ⭐ 阻止同时加载冲突技能
```

> ⭐⭐⭐ 第 ② 条与我们已有的一条直接咬合：
> `skill-overrides-audit.md` 的 deploy 事故——
> 三个同名 deploy 技能静默冲突。
> ⭐ **显式 `conflicts` 正是那个事故的结构性解法**：
> 不靠人去发现同名，而是⭐ 声明层就阻止共存。

**依赖最小化原则**（配套，很关键）：

```
⭐⭐⭐ 单一职责设计：每个技能⭐ 仅声明必需依赖
   ⭐⭐⭐ ⭐ 避免"全能型"技能因依赖过多导致⭐⭐ 调用失败率上升

⭐⭐ 可选依赖标注：明确区分 required 与 optional
   ⭐⭐⭐ ⭐ 确保核心功能在缺失可选依赖时仍可运行
```

> ⭐⭐⭐ "依赖越多，调用失败率越高"——这给"单一职责"
> 又添了一个⭐ 量化理由（此前的理由是触发更准、失败模式是笛卡尔积）。
> ⭐ **现在是第三个独立理由：每多一个依赖，就多一个失败面。**

## 6. ⭐⭐ 工程化：预检与 CI 卡点

```
⭐⭐ 安装前预检
   脚本自动检测环境依赖（如检查 ffmpeg 版本）
   ⭐⭐ 缺失时⭐ 提示安装或⭐ 跳过该技能

⭐⭐⭐ CI/CD 卡点
   流水线中加入⭐⭐ 依赖兼容性测试
   例：⭐⭐ 验证新版本技能是否破坏现有工作流
```

> ⭐⭐ "缺失时提示安装或跳过该技能"——这与 `four-layer-diagnosis-flow.md`
> 环境层的"依赖工具都安装了吗"对应，
> 但这里把它⭐ 前移到了安装时，而不是等运行时报错。
>
> ⭐⭐⭐ **禁止隐式依赖**：所有依赖必须显式声明，
> ⭐⭐ 避免技能因环境差异"⭐ 时好时坏"。
>
> ⭐⭐⭐ "时好时坏"这四个字是隐式依赖的⭐ 特征症状——
> 同一份技能，在这台机器能跑、那台不能，且没有报错规律。
