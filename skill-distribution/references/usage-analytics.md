## 为什么需要单独一层分析

"我觉得这个技能挺有用" 不是数据。
而"技能用得多"和"团队真的在用"是两件事：

```
装了 ≠ 被调用过
被调用过 ≠ 每次都对
```

> ⭐ **没有使用数据，你连"该治理哪些技能"都排不出优先级。**

## 能回答哪些问题

按价值排序：

```
① ⭐ 全组织范围内哪些技能用得最多
② 采用率逐日怎么变（增长 / 停滞 / 衰退）
③ 哪些用户与团队在调用每个技能
④ ⭐ 哪个入口在驱动使用（聊天 / Claude Code / Office agent）
⑤ 估算花费或归因价值与具体技能的关系
```

第 ④ 条常被忽略，但它能告诉你
**"应该在哪里推广"**——如果某个技能只在聊天里被用，
那在 IDE 里推它很可能是白费力气。

## 数据长什么样

以一个接入 Claude AI（Enterprise）技能分析 API 的实现为例：

```
同步粒度    ⭐ 一次同步一天
每条实体包含：
  · 调用次数
  · ⭐ 去重用户数
  · 分享状态
  · ⭐ 产品入口分布（product-surface breakdown）
  · 可选的花费字段

分组维度：
  groupBy 留空          → 组织级汇总
  user_id / rbac_group_id / product → 按人/团队/入口拆分
  ⭐ 一次只用一个维度
```

⚠️ "一次只用一个维度" 是实操约束，混用会得到难以解释的结果。

## 三个用法

**① 给治理排优先级**

```
不是所有技能都值得同等的审查力度
⭐ 调用量最高的前 20% 技能 → 值得投入正确性维护
```

**② ⭐ 退役没人用的技能**

```
调用次数为 0（且已上线超过观察期）
→ 它不产生收益，只进入候选池
   （见 library-size-effect.md：遮蔽是真实成本）
```

**③ 证明平台自有技能包的价值**

```
⭐ "我们做的这个包，被 12 个团队的 47 个人用了 1,800 次"
```

这条对平台团队争取资源是刚需——
没有数字，"平台价值"只能靠叙述。

## 清库：从数据到动作

一个可执行的流程：

```
① 拉最近 30/90 天的调用数据
② 分三档：
   高频（值得维护 + 值得写 eval）
   低频但不为零（观察，可能只对特定场景有用）
   ⭐ 零调用（候选退役）

③ ⭐ 零调用的先查"是不是压根没加载成功"
   ——加载失败表现为零调用，但问题在文件层
   （见 reload-debug.md / priority-conflict.md）

④ 确认真的没人用 → 标记 deprecated → 通知 → 归档
   （见 lifecycle.md）
```

> ⭐ 第 ③ 条是关键：**零调用有两种完全不同的原因**，
> 一种是"不需要"，一种是"根本没生效"。
> 直接按前者处理会误删。

另外，把"从未被调用"和"占多少上下文"放在一起看——
这正是 `/skill-doctor` 做的事（见 `runtime-controls.md`）。

## 自己搭最小版本

不一定需要平台。最小可用：

```
① 让每次技能调用写一行结构化日志
   {ts, skill_name, version, user, surface, outcome, tokens}

② 每天聚一次：调用次数 / 去重用户 / 入口分布

③ ⭐ 一定要记 version
   ——否则你无法把"变差了"归因到某次改动
```

三条纪律：

```
□ ⭐ 日志要记 skill 版本，不只是名字
□ 不要记 prompt 原文（见 telemetry-schema.md 的"什么不该记"）
□ ⭐ 保留原始 trace 供抽查
   ——聚合数字会掩盖"判分器绿但做错了"这种情况
```

## 一条提醒

> ⭐ **调用量高不等于技能好。**

一个技能可能被调用很多次，但每次都在降级路径上、
或每次都需要人工纠正。

所以**调用量要和结果指标一起看**：

```
调用次数  ×  成功率  ×  人工干预率
```

三者都好，才算真的有用。这也是为什么
`skill-evaluating` 里的 eval 不能省——
**使用数据告诉你"用没用"，eval 告诉你"用对没用"。**
