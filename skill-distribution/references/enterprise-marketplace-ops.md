## 1. 什么时候才需要这一层

> ⭐ **50+ 工程师时，共享 GitHub 仓库已经不够了。**

共享仓库要求每个开发者自己克隆并配置工具——
**有人入职、换机器、或仓库 URL 变了，就断一次**。

需要的是平台基础设施，不是写作技巧：

```
分发 · 使用埋点 · 质量维护流程
```

> ⭐ **三个阶段层层递进**：
> **没有可见性的分发 = 打完就忘**；
> **没有质量维护的可见性 = 让热门技能变成无人审查的技术债**。

## 2. 阶段一：托管分发

两条路径（MDM / 服务端）见 `distribution-three-ways.md` 第 4 节。

私有市场的四项控制：

| 控制 | 机制 | 效果 |
|---|---|---|
| ⭐ 限制来源 | `strictKnownMarketplaces` | 阻止未批准的插件安装 |
| **启动时自动装** | `enabledPlugins` | ⭐ 技能在启动时落到每台机器 |
| ⭐ **版本锁定** | `marketplace.json` 的 `sha` 字段 | 可复现部署，无静默更新 |
| 发布通道 | 不同 `ref` 值（stable / latest） | 灰度发布 |
| 容器预置 | `CLAUDE_CODE_PLUGIN_SEED_DIR` | 镜像构建期预置，运行时不克隆 |

> ⭐ 治理发生在 git 仓库层：
> **谁能合并到市场仓库，谁就决定了谁能向组织发布技能。**

⚠️ 一个绕过的口子：

> 技能也会从**你控制之外的市场**到达开发者——
> 例如 Vercel 通过其自有市场分发技能，
> **添加集成会顺带装上该提供方的技能**。

## 3. 阶段二：使用可见性

> ⭐ **没有使用数据，对技能的投入就是猜测。**

两个数据源：

| 源 | 提供什么 |
|---|---|
| **分析仪表盘** | 接受的代码行、建议接受率、DAU、有 Claude 协助的 PR、按人排行 |
| ⭐ **OpenTelemetry 事件** | ⭐ `claude_code.tool_result` 事件含 `skill_name`（需 `OTEL_LOG_TOOL_DETAILS=1`） |

```bash
# 按调用次数给技能排名
jq -r 'select(.name == "claude_code.tool_result") | .attributes.skill_name' \
  otel-export.jsonl | sort | uniq -c | sort -rn
```

> 路由到任何 OTel 兼容后端（Datadog、Honeycomb、Grafana），
> 用 `OTEL_RESOURCE_ATTRIBUTES` 按团队打标。

## 4. ⭐ 遥测的盲区

> ⭐ **平台记录技能"被调用了"，不记录"它干得好不好"。**

```
一个技能每周被调用 500 次
可能其中 30% 的调用产出都是微妙错误的
⭐ OTel 不会暴露这一点
```

> ⭐ **使用频率与输出质量是独立信号。**
> **高调用次数但没有质量审查 = 负债，不是成功指标。**

这条值得单独记住——它解释了为什么
"哪个技能最受欢迎"是个危险的排行榜。

## 5. 阶段三：质量维护

> ⭐ **Claude Code 平台没有内置的技能评估基础设施——
> 质量维护是人工实践，不是平台功能。**

实用节奏（按调用量分级）：

| 层级 | 调用/周 | 审查节奏 |
|---|---|---|
| 高 | >100 | ⭐ 每月 |
| 中 | 10–100 | 每季度 |
| 低 | <10 | 平台重大更新时 |

做法：

```
每个高流量技能维护一小组代表性测试输入与期望输出
手动跑，或配一个在技能文件变更时触发的 CI job
```

> 排序依据就是第 3 节那个 OTel 排名——
> **调用量决定质量维护的优先级**。

## 速查

| 问题 | 手段 |
|---|---|
| 分发断在入职/换机器 | ⭐ 托管分发（MDM 优先） |
| 怕静默更新 | ⭐ `sha` 字段锁版本 |
| 灰度 | 不同 `ref`（stable / latest） |
| 不知道谁在用 | ⭐ OTel `skill_name` |
| ⭐ 以为用得多=好 | ⭐ 频率 ≠ 质量，必须分开测 |
| 先审哪些 | ⭐ 按调用量排序，>100/周 月度审 |
