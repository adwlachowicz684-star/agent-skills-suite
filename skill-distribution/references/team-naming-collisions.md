## 1. ⭐ 五条防冲突约定

**① 一个技能一个用途**

```
⭐ 如果一个技能在做两件不同的事，就拆开。
```

> 例：`deploy-check` 同时又生成 release notes
> → 更难维护、更难推理。

**② ⭐ 范围有限时加小组前缀**

```
只对基础设施团队有用的 → infra-deploy-check，而不是 deploy-check
```

> ⭐ 这个前缀向所有人发出信号：**它可能不适用于你的工作**。
> 与 `skill-overrides-audit.md` 的"个人技能加 `my-` 前缀"是同一招。

**③ ⭐⭐ 绝不遮蔽官方技能名**

```
⭐ 平台自带内置技能。
⭐ 如果你的自定义工作流与之重叠，就要显式命名：
   pdf-internal · commit-team · review-security
```

> ⭐⭐ **通用名会造成静默冲突——错误的那个技能被调起，而你毫无察觉。**

**④ ⭐ 记录"为什么存在"，不只是"做什么"**

```
description 回答："这做什么？"
正文要另有一段回答："⭐ 为什么我们团队需要它，而不是用默认行为？"
```

> ⭐ 这段上下文能防止未来的维护者**删掉那些看起来冗余、其实不冗余的技能**。
> 这与 `write-reasons-not-rules.md` 同源：写原因。

**⑤ 约定评审周转时间**

```
⭐ 如果技能 PR 压两周，贡献者就不再提了。
⭐ 明确期望：Owner 在三个工作日内评审技能 PR。
```

> 理由：**技能是低风险改动，快速评审周期能保持仓库健康。**

## 2. ⭐ 按环境拆分技能集

```
⭐ 有些技能只应在特定环境运行。
⭐ 生产部署技能不该在本地开发时被随手调用。
```

建议布局：

```
claude-skills/
  local/       debug-local.md · scaffold-feature.md
  ci/          test-coverage.md · lint-report.md
  production/  deploy-check.md · rollback.md
```

> 开发者三套都装，但 **README 要明确写清哪些技能在哪种上下文是安全的**。
> 这对"初级工程师有本地权限但 CI/生产权限受限"的团队尤其重要。

**技能文件里也要写明**：

```
"本技能假设你已配置生产 AWS 凭证。请勿在纯本地环境调用。"
```

> ⭐ 这比"靠大家记住"可靠得多——
> 与 `preflight-gate.md` 的 STEP 0 前置门禁是同一思路。

## 3. ⭐ 四步上手（30 分钟内）

**Step 1** 给他们的 shell 配置加更新别名：

```bash
alias skills-update="cd ~/team-claude-skills && git pull &&   cp *.md ~/.claude/skills/ && echo Skills updated"
```

**Step 2** 走一遍上面的别名，确认能拉到。

**Step 3** ⭐ **在首次配对时由资深工程师现场调用两三个技能，并解释预期输出**

```
⭐⭐ 读技能文档，不如看它跑一次。
```

**Step 4** ⭐ **头两周内分配一个"改进技能"的任务**

> ⭐ 新人是最好的反馈来源——**他们能注意到资深工程师早已视而不见的问题**。
>
> 一个轻量任务就够：
> "用 `pr-review` 技能审三个 PR，记下任何感觉不对的地方"
> ⭐ 这能很快产出有用信号。

> 整套流程**不到 30 分钟**，却能显著提高新人真正采用共享技能的概率。

## 4. 季度审计三问

```
⭐ 团队会议上花 30 分钟就够，防止仓库积累废物。

每个技能问三个问题，快速决策：
   1. 还在用吗？
   2. 还准确吗？
   3. ⭐ Owner 还在团队里吗？
```

**配套的两条反馈机制**：

```
· ⭐ 在回顾会上问开发者实际用了哪些技能
  → ⭐ 没人调用的技能就删掉或简化
  → 小而维护良好的技能集，胜过庞大而混乱的

· ⭐ 追踪哪些技能产生的提问/修正最多
  → ⭐⭐ 一个总是产出需要人工修改的结果的技能，
     ⭐ 信号是"技能本身该改"，而不是"开发者用错了"
  → ⭐ 把这条反馈直接写进技能的"已知局限"章节，
     让别人不必重复踩同样的坑
```

> ⭐ 最后一条特别值得抄：**"已知局限"章节是团队的集体记忆**。
> 它把个人踩过的坑变成了下次不再踩的资产。

## 速查

```
防冲突：
□ 一技能一用途，做两件事就拆
□ ⭐ 范围有限加小组前缀（infra-deploy-check）
□ ⭐⭐ 绝不遮蔽官方技能名（pdf-internal / commit-team）
□ ⭐ 正文写"为什么需要它"，防后人误删
□ ⭐ 评审周转 ≤3 个工作日（技能是低风险改动）

按环境：
□ local/ ci/ production/ 三套分离
□ README 写明哪些在哪种上下文安全
□ ⭐ 技能里写明前提（"勿在本地调用"）

上手四步（30 分钟）：
□ ① 配更新别名
□ ② 验证能拉到
□ ③ ⭐ 资深现场跑两三个并解释输出（读文档不如看跑一次）
□ ④ ⭐ 头两周给一个改进任务（新人是最好的反馈来源）

季度审计三问：
□ 还在用吗？还准确吗？⭐ Owner 还在吗？
□ ⭐ 没人用的就删或简化
□ ⭐ 高提问率 = 技能该改，写进"已知局限"
```

**一句话**：

> ⭐ **通用名会造成静默冲突——错的那一个被调起，而你毫无察觉。**
