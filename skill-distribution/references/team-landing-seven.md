## 1. ⭐ 七原则

判断团队是否把技能当工程资产维护，看这七条：

```
① ⭐ 从高频返工点切入，而非单纯的技术创新
② ⭐ 单个技能聚焦解决一个明确问题，边界宜窄不宜宽
③ 主文件保持精简，细节与工具向子目录拆分
④ ⭐ 真实踩坑经验单独沉淀，逐步补厚技能能力
⑤ ⭐ 确定性工作通过脚本兜底，替代纯自然语言提醒
⑥ ⭐ 提前建设验证能力，降低后期纠错成本
⑦ ⭐ 基于使用日志与实际效果，筛选保留有价值的技能
```

> ⭐⭐ 第 ① 条是起点选择上最容易犯错的：
> **"技术创新"驱动的技能库往往没人用**，
> 而从"高频返工点"切入的会立刻见效。

第 ④ 条对应 Anthropic 的 Gotchas 章节（信号密度最高）；
第 ⑤ 条对应 `deterministic-scripts.md`；
第 ⑦ 条对应 `dead-skill-detection.md` 与 `skill-scope-tiering.md`。

> ⭐ 这七条其实是前面所有方法论的**落地浓缩版**——
> 每一条都能在主套件里找到对应的详细文档。

## 2. ⭐ 三层分发体系

一个已工程化落地的参考（OpenClaw 的三层 + 上层注册表）：

| 层 | 位置 | 用途 |
|---|---|---|
| **内置技能** | 随安装包发布 | 通用基础能力 |
| ⭐ **团队共享技能** | `~/.openclaw/skills` | 团队内部复用 |
| **项目级技能** | 工作区 `skills/` | 项目专属需求 |
| ⭐ 上层注册表 | 市场（如 ClawHub） | 安装、更新、同步 |

> ⭐ 三层结构本身不新鲜，值得学的是**"上层注册表"这一层**：
> 它把"安装/更新/同步"从手工复制变成了可管理的动作
> ——正是 `cross-agent-portability.md` 说的"绝不手抄副本"。

**治理流程**（接在注册表上的那道闸）：

```
⭐ 发布前检查：敏感信息、外部链接、危险命令
   → owner 处理误报或修改问题内容
⭐ 从外部市场导入的技能走同一条路径：
   先进注册中心 → 安全扫描 → owner 审核 → 才发布给团队
```

**版本与标签的节奏控制**（这个设计很实用）：

```
审核通过后发布为稳定版，绑定 stable 标签
   → 日常使用都走 stable（⭐ 保证每个 agent 读同一套规则）

要调整时：
   先发到 dev 标签 → 少量成员试用 → 确认稳定
   → ⭐ 再把 stable 指向新版本
   ⭐ 出问题 → 直接把 stable 切回上一版
```

> ⭐⭐ **"出问题就把 stable 切回上一版"** ——
> 这是把回滚做成了一个**标签指针的移动**，成本几乎为零。
> 比"重新发一个修复版本"快一个数量级。

生命周期状态机：

```
Draft → Review → Online v1.1.0 → ⭐ 灰度 Gray → 全量 Full rollout
                                  （版本锁定 · 灰度发布 · 可审计）
                              ↘ 回滚 Rollback v1.0.0
```

## 3. ⭐ 三步落地

**第一步：跑通最小闭环（1–2 周）**

```
① ⭐ 挑 3–5 件团队天天都要做的重复活
   （例：写周报、代码初审、需求文档初筛）做成第一批技能
② ⭐ 先把"识别 → 加载 → 执行"跑通
③ ⭐ 让大家立刻能看到好处，才愿意跟着用
```

> ⭐ 第 ③ 条解释了为什么选"天天做"的任务：
> **不是为了省最多时间，是为了让收益可见、从而形成正循环**
> ——呼应 `adoption-playbook.md` 的"工程师选了最糟糕的第一个任务"。

**第二步：完善体系、全团队铺开（1 个月左右）**

```
· 补全分层加载机制
· ⭐ 打通核心工具与知识库
· 定下贡献评审流程
· 各部门高频活慢慢往里加，从几个人用变成全团队用
```

**第三步：攒下团队核心能力（长期）**

```
· 把数据度量做起来：复用率、质量提升、人效变化
· ⭐ 最终效果：新人靠技能库快速上手，
  老员工经验通过技能不断沉淀，团队本事越滚越强
```

## 4. ⭐ 别做成死文档

> ⭐⭐ **很多团队的技能最后成了摆设，
> 就是因为⭐ 只做了"说明书"，没和干活的工具打通。**

```
技能定"按什么标准干"
⭐ 数据库、API、检测工具负责"具体动手干"

例：代码评审技能定好评判维度
   → ⭐ 具体扫代码、查问题交给工具去做
```

> ⭐ 这条与 `mcp-integration-patterns.md` 的"MCP 给能力、技能给护栏"、
> `script-engineering.md` 的"脚本兜底确定性工作"是同一条原则：
> **技能负责标准，执行交给确定性系统。**

**配套规矩**（有技术规范没用，得有协作规则）：

```
· ⭐ 谁都能贡献（开发或运营都能提交，走评审流程）
· ⭐ 统一评审标准（业务+技术一起过，防奇怪的私人技能混入）
· ⭐ 版本留痕可回滚（改坏能退回，不会全团队跟着踩坑）
· ⭐ 用数据说话（统计被调用次数、准确率、省了多少人工时间）
```

## 5. ⭐ 治理核心

```
⭐ 技能并非越多越好，每个技能都会增加模型的上下文负担
   → ⭐ 需要建立⭐ 筛选与淘汰机制
   → ⭐ 基于实际使用日志判断技能价值，清理低复用、无维护的资源
   → ⭐⭐ 为每个技能指定负责人，明确边界与审核标准
      ⭐ 如同治理内部脚手架与组件库
```

> ⭐⭐ "如同治理内部脚手架与组件库"这个比喻很好——
> 它直接告诉你该用什么样的严肃程度对待技能库。

**技能在更大的工程体系里的位置**（四条关联，值得记住这个视角）：

```
· 与工具设计：动作空间的拆解方法论 → 适用于技能的功能拆分与组织
· ⭐ 与缓存架构：技能的上下文开销，⭐ 直接受 Prompt Cache 设计影响
· ⭐ 与上下文治理：文件组织与渐进式披露，是上下文窗口优化的重要手段
· ⭐ 与反馈回路：验证类技能是 Harness Engineering 中反馈回路的具体落地
```

> ⭐ 这四条把技能从"几个 markdown 文件"提升到了
> **Agent 工程化体系的核心节点**。

```
⭐ 七原则：

□ ⭐ 踩坑经验单独沉淀 · ⭐ 确定性工作脚本兜底
□ ⭐ 提前建验证能力 · ⭐ 按使用日志筛选保留

⭐ 三层分发：
□ 内置 / ⭐ 团队共享 / 项目级 / ⭐ 上层注册表
□ ⭐ 外部导入走同一路径：扫描 → owner 审核 → 发布
□ ⭐⭐ stable/dev 标签：dev 试用 → stable 指向新版
   ⭐ 出问题 = 把 stable 切回上一版（成本几乎为零）
□ 状态机：Draft→Review→Online→⭐ 灰度→全量；可回滚

⭐ 三步落地：
□ 1–2 周：3–5 件天天做的活 → ⭐ 先跑通"识别→加载→执行"
□ ⭐ 让大家立刻看到好处，才愿意跟着用
□ 1 个月：分层加载 + 打通工具 + 定贡献评审流程
□ 长期：数据度量 → 新人靠技能库上手，老员工经验沉淀

□ ⭐⭐ 技能定标准，工具动手干（别做成死说明书）
□ ⭐ 谁都能贡献 + 统一评审 + 版本可回滚 + 用数据说话

□ ⭐⭐ 治理：技能非越多越好；⭐ 每个技能指定负责人
```
