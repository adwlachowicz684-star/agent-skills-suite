# 组织推广：让技能库活下来

> ⭐ **最难的部分很少是技能本身，而是让一个真实的团队
> ——有截止日期、有怀疑、有既有习惯——真的去用、去信任、并往回贡献。**
>
> **多数技能计划不是死在代码里，是死在组织里。**

## 为什么会卡住

> 常见的弧线：几个爱好者做出很棒的技能 → 产出可见成果 →
> **然后什么都没扩散**。六个月后技能过期，爱好者也走了。

**四个可预测的原因**（几乎没有一个是技术性的）：

**① 英雄问题**

```
一位有才华的工程师做出出色的技能，
然后成为所有这些技能的瓶颈，
团队其他人把它当作"那个人的爱好"而非共享基础设施。
```

**② 信任缺口**

```
有人试用了一次，结果在某个重要任务上出了微妙的错误，
于是悄悄退回手工做法，并告诉两个同事"别费劲了"。
```

> ⭐ **技能失败一次，传播的是两个人。** 负面对称性很强。

**③ 可发现性**

```
人们无法使用他们不知道存在的技能。
如果你的库放在一个没人浏览的文件夹里、取着没人认得的名字，
agent 也许能找到它们，但人类永远不会——
于是他们压根不会想到要把工作委托出去。
```

> ⭐ **采纳是一个搜索问题，和质量问题同等重要。**
> 呼应 `skill-refining` 的 `discovery-ux.md`。

**④ 期望错配**

```
早期采用者把 agent 当 infallible，在边缘 case 上栽了，
就过度矫正到"什么都不敢用"。
```

> ⭐ **第一周建立的框架会固化下来**——
> 所以值得有意地设定，而不是围着一次糟糕体验随机形成。
>
> 准确定位：**"定义良好的工作的可靠助手，高风险输出仍值得人类看一眼"**。

## 三个角色

> ⭐ 即使在小团队上，持久的采纳通常也需要三个非正式角色。
> **没有一个是全职工作。**

| 角色 | 职责 |
|---|---|
| **图书管理员 librarian** | 保持目录整洁、清理死技能、合并重复项 |
| **维护者 maintainer** | 高流量技能的正确性归属人 |
| **冠军 champion** | 通常是技术负责人——**示范那个"下意识动作"**，维持社交仪式 |

> 呼应 `library-ops.md`：清库是持续动作，不是一次性项目。

## 四条规范

**① 可发现性**

```
单一、可浏览、有文档的地方
每个技能有一行说明：做什么、什么时候该用它
```

> **隐藏的技能 = 未被使用的技能。**

**② 共享所有权**

```
□ 属于一个人的技能，会在他休假或转岗时死掉
□ 属于团队的技能，任何人都能修一个过期步骤
□ ⭐ 把高流量技能当作共享代码：评审、版本化、集体所有
```

**③ "先找技能"的下意识**

> ⭐ **这是习惯，习惯需要触发器。**

```
最有效的团队把"这个有技能吗？"变成
任何重复性任务开始时的下意识反应——
就像工程师在写一个工具函数前本能地先检查是否已存在。
```

> **这个下意识靠重复和资深者的示范来教，不靠政策文件。**

**④ 无摩擦的修正路径**

> ⭐ **这条最关键，也最常被漏掉**：

```
如果"技能输出不对"的唯一回应是放弃它、退回临时提示词
  → 你的库会腐烂
如果有一条快速的、无责怪的提交修复的路径
  → 每次失灵都变成一次小改进，信任会复利式增长而非侵蚀
```

## 推广节奏

**降低启动能量，让胜利可见**：

```
□ 先用 3–4 个"解决真正烦人、高频杂活"的技能种下库
  ⭐ 早期的价值应该感觉像"解脱"，而不是"多了一套流程"
□ 让采纳变得社交化
  ——站会上花几分钟、或专门频道里分享"这周哪个技能省了我时间"
  ⭐ 这比任何正式培训都有效
  ——它传递的信号是：用和建技能是这个团队里正常的、高地位的行为
□ ⭐ 人模仿他们尊敬的同行在做的事
```

> **不要用一封启动邮件把新习惯强加出来。**

**分阶段铺开**（避免全组织同时上）：

| 阶段 | 时间 | 重点 |
|---|---|---|
| **受控试点** | 第 1–4 周 | 选一个**高可见度、经理支持、工作流契合**的团队；指派专人收集反馈 |
| **扩展铺开** | 第 5–12 周 | 再扩 2–3 个团队；**试点团队的早期采用者做同伴导师** |
| **全组织部署** | 第 13 周起 | 此时应有充分证据、培训资源库、内部冠军网络 |

> ⭐ **试点团队应该知道自己是被当作"推广流程的共同设计者"，
> 而不是实验对象。** 这个措辞差别影响参与度。

**最容易失败的是第三阶段：强化**

```
启动带来兴奋，早期指标好看，
但两三个月内使用率见顶或下滑。
```

**有效的强化手段**：

```
□ 定期发布性能看板，展示对团队指标的影响
□ 公开庆祝快速胜利
□ 把"AI 协作能力"纳入绩效与职业发展对话
□ ⭐ 基于员工反馈持续迭代
□ 信息必须明确：这不是可能被回滚的试点，
   而是组织承诺持续改进的永久能力
```

## 新人 onboarding

**把 agent 当新员工**：

```
□ 写一张"角色卡"，说明范围、长处、局限、上报路径
□ ⭐ 明确列出 "agent 不能做什么"——清晰预期能防止误用并建立信任
□ 发布 Agent FAQ：数据从哪来、如何报问题、谁维护
```

**培训要分角色**：

```
一线客服   → 操作流畅度
主管       → 升级管理
分析师     → 理解 agent 生成的数据
```

**能力 ≠ 知识**：

```
□ 需要在低风险环境动手练（沙箱），
  让员工不怕犯"看得见的错"
□ 需要可及的支持渠道：专属频道、答疑时间、已经熟练的同伴导师
□ ⭐ 通过早期使用数据监测能力缺口
  ——如果某团队不用，先判断是动力问题还是能力问题，
    ⭐ 两者的干预方式根本不同
```

## 自查

```
□ 是否有"图书管理员/维护者/冠军"三个角色（哪怕兼任）？
□ 技能库是否单一、可浏览、每项有一行说明？
□ 高流量技能是否集体所有（而非绑定个人）？
□ 是否有无摩擦、无责怪的提交修复路径？（最关键）
□ 早期是否选了"真正烦人高频"的杂活做种子？
□ 是否有社交化的分享仪式（站会/频道）？
□ 是否有分阶段铺开计划（而非全组织同时上）？
□ ⭐ 是否有"强化"机制防两三个月后回落？
□ 是否有角色卡 + "agent 不能做什么"清单？
□ 培训是否按角色分层？
□ 是否有沙箱供低风险练习？
□ 不用的人，是否区分了"动力问题"还是"能力问题"？
```
