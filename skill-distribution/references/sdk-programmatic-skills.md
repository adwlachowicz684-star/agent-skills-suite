## 1. ⭐⭐⭐⭐⭐ 默认不加载：两个开关都要开

```python
options = ClaudeAgentOptions(
    setting_sources=["user", "project"],   # ⭐ 从文件系统加载
    skills="all",                          # ⭐⭐⭐⭐⭐ 加载全部技能
    allowed_tools=["Read", "Grep", "Glob"],
)
```

> ⭐⭐⭐⭐⭐ **"⭐ 对⭐ 项目级与⭐ 个人级技能，⭐⭐⭐⭐ ⭐⭐⭐ Claude Code ⭐ 会在
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ SDK 会话中⭐ 应用⭐ allowed-tools frontmatter 字段。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐ 你也可以通过⭐ query 配置里的⭐ `allowedTools` 选项
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 为这些技能⭐ 预批准工具。"**

```
⭐⭐⭐⭐⭐ 两个开关缺一不可：
   setting_sources=["user","project"] → ⭐⭐⭐⭐⭐ ⭐⭐⭐ 决定"从哪里读设置（含技能）"
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ skills="all"              → ⭐⭐⭐⭐⭐ ⭐⭐⭐ 决定"读哪些技能"
```

> ⭐⭐⭐⭐⭐ 这⭐ 是⭐ "⭐ SDK 里技能没生效"⭐ 的⭐ 第一个⭐ 排查点，⭐⭐⭐⭐⭐ ⭐⭐⭐ 而且⭐ 极隐蔽：
> ⭐⭐⭐⭐⭐ **技能文件⭐ 就在磁盘上、⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 内容完全正确、⭐⭐⭐⭐⭐ ⭐⭐⭐ 在交互会话里好好的，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 但⭐ 在 SDK 里⭐ 它就是⭐ 不存在——⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 因为没开这两个开关。**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这⭐ 与⭐ `nested-scope-discovery.md` 那份⭐ 记录的
> "⭐ 嵌套 .claude/skills/ ⭐ 只在⭐ 处理该子目录文件⭐ 时才被发现"⭐ 是⭐ 同一类⭐ 故障：
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ **文件在，⭐⭐⭐⭐⭐ ⭐⭐⭐ 但不在⭐ 可见集里。**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 排障口诀：⭐⭐⭐⭐⭐ **"在不在磁盘上"⭐ 与
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ "在不在可见集里"⭐ 是⭐ 两个问题。**

## 2. ⭐⭐⭐⭐ 技能名出现在 slash_commands 里

> ⭐⭐⭐⭐ **"⭐ 技能的⭐ 名字⭐ 也会⭐ 出现在⭐ init 消息的⭐ `slash_commands` 数组里。"**

```python
# init 消息里可直接检查
if "security-check" in init_message["slash_commands"]: ...
```

> ⭐⭐⭐⭐⭐ 这⭐ 是⭐ 一条⭐ 极实用的⭐ 可编程⭐ 检查手段：
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 我们⭐ 此前⭐ 记过⭐ 一条⭐ "⭐⭐⭐⭐⭐ 无法判断哪个版本生效时，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 直接问 Claude 'What skills are available?'"
> （`nested-scope-discovery.md`）——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 而⭐ 这里⭐ 是⭐ 它的⭐ **机器可读版本**：
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ **不需要问，⭐⭐⭐⭐⭐ ⭐⭐⭐ 直接读数组。**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 差别⭐ 很明确：
> ```
> 问 Claude     → ⭐⭐⭐⭐⭐ ⭐⭐⭐ 消耗一次推理，⭐⭐⭐⭐⭐ ⭐⭐⭐ 且答案可能被模型改写/概括
> ⭐⭐⭐⭐⭐ 读 slash_commands → ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 零成本，⭐⭐⭐⭐⭐ ⭐⭐⭐ 且是⭐ 系统的⭐ 实际生效列表
> ```
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 对 CI 来说⭐ 这⭐ 尤其⭐ 重要：⭐⭐⭐⭐⭐ ⭐⭐⭐ **可以写成一条断言**
> （⭐⭐⭐⭐⭐ ⭐⭐⭐ "部署前断言关键技能在 slash_commands 里"）。

## 3. ⭐⭐⭐⭐ 直接派发与预批准工具

```python
async for message in query(
    prompt="/security-check",
    options=ClaudeAgentOptions(max_turns=10)
): ...
```

```
⭐⭐⭐⭐ 两种方式触发技能：
   ① ⭐⭐⭐⭐⭐ 自然语言匹配（靠 description）
   ② ⭐⭐⭐⭐⭐ ⭐⭐⭐ 直接派发：prompt="/security-check"（与交互里输入斜杠命令一样）
```

> ⭐⭐⭐⭐⭐ 第 ② 种⭐ 对⭐ 评测⭐ 特别有用：⭐⭐⭐⭐⭐ ⭐⭐⭐ 它把
> "⭐ 技能有没有被正确触发"⭐ 这个⭐ 变量⭐ **从实验中排除掉**——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐ 你可以⭐ 单独测⭐ "加载之后⭐ 干得好不好"
> （⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 即测试金字塔的 L3/L4），
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 而⭐ 不被⭐ L2（触发）⭐ 的波动⭐ 污染。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 反过来：⭐⭐⭐⭐⭐ **想单独测⭐ 触发，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 就用自然语言 prompt 而不用斜杠命令。**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 这⭐ 给了⭐ 我们⭐ 测试金字塔⭐ 一个⭐ 此前没有的⭐ 隔离手段。
>
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 另有一条：
> ⭐⭐⭐⭐ **"⭐ 技能⭐ 运行在⭐ 会话的⭐ 工具集里。"**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 所以⭐ frontmatter 的 allowed-tools ⭐ 与
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ query 的 allowed_tools ⭐ 是⭐ 共同作用的
> （⭐⭐⭐⭐⭐ ⭐⭐⭐ 前者⭐ 在⭐ 技能激活时⭐ 应用，⭐⭐⭐⭐⭐ ⭐⭐⭐ 后者⭐ 是⭐ 会话基线）。

## 4. ⭐⭐⭐⭐⭐ 一次性 query() 每次都是空上下文

> ⭐⭐⭐⭐⭐ **"⭐ 一次⭐ 全新的⭐ one-shot `query()` 调用⭐ 以⭐ 空上下文 ⭐ 开始，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 所以⭐ 要在⭐ 有⭐ 先前轮次的⭐ 会话中⭐ 使用⭐ 这个模式——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐ 例如⭐ 流式输入模式，⭐⭐⭐⭐⭐ ⭐⭐⭐ 或⭐ 恢复一个会话。"**

> ⭐⭐⭐⭐⭐ **"⭐ `/clear` ⭐ 会⭐ 把对话⭐ 重置为⭐ 空上下文，⭐⭐⭐⭐ ⭐⭐⭐ 于是
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 后续提示⭐ 从⭐ 没有历史⭐ 的状态开始。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ **对 one-shot `query()` 调用而言，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 每一次调用⭐ 本来⭐ 就已经⭐ 是空上下文，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 所以⭐ 发 `/clear` ⭐ 没有实际效果。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 要开一个新的 `query()` 才对。**"**

```
⭐⭐⭐⭐⭐ query()          → ⭐⭐⭐⭐⭐ ⭐⭐⭐ 每次新建会话，空上下文（适合独立任务）
⭐⭐⭐⭐⭐ ClaudeSDKClient  → ⭐⭐⭐⭐⭐ ⭐⭐⭐ 维持上下文，多轮（适合交互应用）
```

## 5. ⭐⭐⭐⭐⭐ 副作用一：评估天然干净

> ⭐⭐⭐⭐⭐ **在 SDK 里做技能评估，⭐⭐⭐⭐ ⭐⭐⭐ 每一次 `query()` ⭐ 天然就是
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ "清过会话的⭐ 独立一次运行"。**

```
⭐⭐⭐⭐⭐ 我们此前的问题（output-stability-contract.md）：
   "跑一次 → /clear → 再跑一次"
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ 不清理就重跑，⭐⭐⭐⭐⭐ ⭐⭐⭐ 第二次会倾向于自洽，⭐⭐⭐⭐⭐ ⭐⭐⭐ 两次很像但什么都没证明

⭐⭐⭐⭐⭐ SDK 里：
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ 两次 query() 物理上就是两个会话
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐⭐ **不可能互相污染——⭐⭐⭐⭐⭐ ⭐⭐⭐ 不需要记得 /clear**
```

> ⭐⭐⭐⭐⭐ 这⭐ 是⭐ "⭐⭐⭐⭐⭐ **把纪律⭐ 变成⭐ 结构**"⭐ 的⭐ 又一个⭐ 样板——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 与 `skill-creator-meta-architecture.md` 那三条
> （⭐ 成对对比成为默认形状、⭐ 评审 eval 成为角色、⭐ evidence 成为必填字段）⭐ 完全同源。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 在交互环境里，⭐⭐⭐⭐⭐ ⭐⭐⭐ "跑两遍要清会话"⭐ 是一条⭐ 需要记住的纪律；
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ **在 SDK 里，⭐⭐⭐⭐⭐ ⭐⭐⭐ 它是环境的默认行为。**
>
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 配套的⭐ 具体建议：
> ⭐⭐⭐⭐⭐ **批量评估时，⭐⭐⭐⭐⭐ ⭐⭐⭐ 每个测试用例⭐ 开一个独立 `query()`，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 用 `max_turns` 限制步数——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这样⭐ 既⭐ 保证⭐ 隔离，⭐⭐⭐⭐⭐ ⭐⭐⭐ 又⭐ 天然⭐ 可并行。**

## 7. ⭐⭐⭐⭐ 遮蔽与来源差异

```

   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ → ⭐⭐⭐⭐⭐ ⭐⭐⭐ 它遮蔽了捆绑的 code-review 技能
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 且 slash_commands 里这个名字⭐ 只列一次
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ → ⭐⭐⭐⭐⭐ ⭐⭐⭐ **你无法从列表里看出被遮蔽的是哪一个**
```

> ⭐⭐⭐⭐⭐ 这⭐ 与⭐ 我们⭐ 已有的⭐ `skill-overrides-audit.md` 那份
> （⭐ 同名覆盖与冲突审计、⭐⭐⭐⭐⭐ ⭐⭐⭐ 那起 deploy 事故）⭐ 是⭐ 同一类⭐ 问题，

> ⭐⭐⭐⭐⭐ **"⭐ 只列一次"**——⭐⭐⭐⭐⭐ ⭐⭐⭐ 也就是⭐ 说，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐ **遮蔽⭐ 不会⭐ 留下⭐ 任何⭐ 痕迹。**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这⭐ 使⭐ 它⭐ 比⭐ "⭐ 两个同名技能⭐ 你不知道用哪个"⭐ 更隐蔽——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐⭐⭐ 后者⭐ 至少⭐ 你⭐ 知道⭐ 有⭐ 两个。

另一条来源差异：

```

```

> ⭐⭐⭐⭐⭐ 这⭐ 与 `argument-substitution.md` 那条
> "⭐ 从 claude.ai 账户同步的技能，⭐⭐⭐⭐⭐ ⭐⭐⭐ 不会在你的机器上运行 `!` 命令"⭐ 完全同源——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 两处⭐ 都在⭐ 说：⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ **同步来源的技能
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 与本地技能⭐ 不是⭐ 一回事，⭐⭐⭐⭐⭐ ⭐⭐⭐ 行为有差异。**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 推论：⭐⭐⭐⭐⭐ **跨来源⭐ 不要⭐ 假设行为一致。

## 8. ⭐⭐⭐⭐ SDK vs CLI：什么时候该用哪个

```
⭐⭐⭐⭐⭐ 用 SDK 的场景：
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ CI 流水线里 lint 并修复代码

   ⭐⭐⭐⭐⭐ ⭐⭐⭐ 文件在磁盘上 ≠ 在可见集里（与"嵌套 .claude/skills/ 才被发现"同类故障）

   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 批量评估：每个用例一个独立 query() + max_turns 限步 → 天然可并行
□ ⭐⭐⭐⭐⭐ 副作用二：slash_commands 可写成 CI 断言（"部署前断言关键技能在列表中"）

**一句话**：

> ⭐⭐⭐⭐ **在 SDK 里用技能要同时开 `setting_sources` 和 `skills="all"`（文件在磁盘上不等于在可见集里），而技能名会出现在 init 消息的 `slash_commands` 数组里，这让"确认技能是否可见"从一句排障提醒变成了 CI 里一条可写的断言；更重要的是，one-shot `query()` 每次都是空上下文，于是"跑两遍要清会话"这条纪律在 SDK 里变成了环境的默认行为——又一次把纪律变成结构。**
