## 1. ⭐⭐⭐⭐ 三层模型

| | ⭐ 它是什么 | ⭐⭐ 类比 |
|---|---|---|
| **技能** | ⭐⭐⭐ 一个目录里的 SKILL.md；agent 读了就获得能力 | ⭐ **内容** |
| **插件** | ⭐⭐⭐ 含一个或多个技能 +（可选）hooks / agents / MCP / 斜杠命令；由 `plugin.json` 定义 | ⭐ **容器** |
| **市场** | ⭐⭐⭐ 一个⭐ 根目录带 `marketplace.json` 的⭐ git 仓库 | ⭐ **分发渠道** |

> ⭐⭐⭐⭐⭐ 一句最干净的总结：
> ⭐⭐⭐⭐⭐ **"⭐ 插件是⭐ 分发格式，⭐⭐⭐⭐⭐ ⭐ 技能是⭐ 内容。"**
>
> ⭐⭐⭐⭐⭐ 以及一条⭐ 重要的澄清：
> ⭐⭐⭐⭐ **插件系统是⭐ 叠加的，不是替代**——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ `~/.claude/skills/` 和 `.claude/skills/` 里的技能⭐ 照旧工作，⭐ 什么都没变。
> ⭐⭐⭐⭐ ⭐⭐⭐⭐ 三种安装方式⭐ 可以共存：
> ```
> 手动丢文件 · /plugin install · curl 一行装
> ```

## 2. ⭐⭐⭐⭐⭐ 何时打包、何时独立

| | 独立技能 | 插件 |
|---|---|---|
| 内含 | ⭐ 一个 SKILL.md 目录 | ⭐ 技能 + 命令 + hooks + agents + MCP |
| ⭐ 命名空间 | ⭐⭐⭐ 无 | ⭐⭐⭐ 命令带插件名前缀 |
| 可用范围 | ⭐⭐⭐⭐ **任何读该格式的工具** | ⭐⭐⭐ **仅 Claude Code** |
| 最适合 | ⭐⭐⭐ 可复用知识与流程 | ⭐⭐⭐ 多组件工作流 |

**三条经验法则**：

```
① ⭐⭐⭐⭐ 组件互相依赖时才打包
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ "如果你的命令引用一个技能、⭐ 而一个 hook 又强制该命令的输出，
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 分开发布⭐ 就⭐ 保证会有人⭐ 只装了半个流程⭐ 然后来报 bug。"

② ⭐⭐⭐⭐⭐ 知识能独立存在就保持独立技能
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ "一份'我们怎么写迁移'的技能⭐ 不需要插件外壳——
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 外壳⭐ 只是⭐ 增加了安装摩擦，⭐⭐⭐ 并把它⭐ 锁在单一工具上。"

③ ⭐⭐⭐⭐⭐ 想清楚可移植性
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 插件是 Claude Code 专有的；⭐⭐⭐⭐⭐ ⭐⭐⭐ 技能是⭐ 可移植层——
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 同一份 SKILL.md ⭐ 对 Cursor / Windsurf / Copilot 都有用。
```

> ⭐⭐⭐⭐⭐ 一个⭐ 大多数团队适用的⭐ 干净切分：
> ⭐⭐⭐⭐⭐ **"⭐ 技能承载⭐ 知识，⭐⭐⭐⭐⭐ ⭐ 插件承载⭐ 消费这些知识的⭐ Claude Code 专属自动化
> ⭐⭐⭐⭐⭐ ⭐（hooks、命令、MCP 接线）。"**
>
> ⭐⭐⭐⭐⭐ 这条⭐ 与 `cross-agent-portability.md` 完全同源，
> ⭐⭐⭐⭐ ⭐⭐⭐ 但⭐ 给出了⭐ 组织层面的⭐ 落地方式：
> ⭐⭐⭐⭐ **把"可移植的部分"和"锁定的部分"⭐ 放在⭐ 不同的容器里，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这样⭐ 换工具时⭐ 你只丢掉后者。**

## 3. ⭐⭐⭐⭐⭐ `skills` 字段要指向父目录

```json
// plugin.json
{
  "name": "rails-upgrade",
  "version": "3.1.0",
  ⭐⭐⭐⭐⭐ "skills": "./"          ← ⭐ 指向"包含技能目录的父目录"
}
```

> ⭐⭐⭐⭐⭐ **"我一开始写的是 `"skills": "./rails-upgrade"`，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 它指向技能目录⭐ 自身——⭐⭐⭐⭐ ⭐ 那是错的。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 这个路径⭐ 应该指向⭐ 包含技能目录的⭐ 父目录。"**
>
> ⭐⭐⭐⭐⭐ 这是一个⭐ 极其具体的坑：
> ⭐⭐⭐⭐ ⭐⭐⭐ **写错了不会报错，⭐⭐⭐⭐⭐ ⭐⭐⭐ 只是⭐ 一个技能都找不到**
> ——又是"不报错的失败"那一族。
>
> ⭐⭐⭐⭐ 其余两个字段：
> ```
> marketplace.json 的 source = ⭐ 插件相对市场根目录的位置（"./" = 插件就是仓库本身）
> ⭐⭐⭐⭐⭐ 发布前可以：claude plugin validate /path/to/repo
> ⭐⭐⭐⭐ 本地开发可以跳过市场：claude --plugin-dir /path/to/repo
> ```

## 4. ⭐⭐⭐⭐ 一个技能一个市场的麻烦

```
三个互相配合的技能各自一个仓库：
  rails-upgrade / dual-boot / rails-load-defaults

⭐⭐⭐⭐⭐ 用户就要⭐ add 三次不同的市场
```

> ⭐⭐⭐⭐⭐ 这个⭐ 真实困境⭐ 此前完全没覆盖过，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 而它⭐ 揭示的是一个⭐ 结构性问题：
> ⭐⭐⭐⭐⭐ **"一个仓库 = 一个插件 = 一个市场" 的映射，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 与"⭐ 一组技能应该一起发布" ⭐ 是⭐ 冲突的。**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 修法显然是⭐ 合并到⭐ 一个仓库里多个插件目录 + 一份 marketplace.json。
> ⭐⭐⭐⭐ 这跟⭐ `reference-organization.md` 的"⭐ 按任务类型切、不按主题切"
> ⭐⭐⭐ ⭐ 是⭐ 同一个⭐ 组织原则的⭐ 打包层版本。

## 5. ⭐⭐⭐⭐ 安全面变大了

> ⭐⭐⭐⭐⭐ **一个技能只是⭐ 指令。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 一个插件⭐ 可以包含⭐ 自动在特定事件上运行的 hooks、
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ ⭐ 外部连接的 MCP 服务器、⭐⭐⭐ 和⭐ 可执行的斜杠命令。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 这⭐ 比 SKILL.md ⭐ 强大得多，⭐⭐⭐⭐⭐ ⭐ 因此⭐ 危险得多。**

```
安装前：
· ⭐⭐⭐ 查来源市场（官方 Anthropic 的经过验证；社区的没有）
· ⭐⭐⭐⭐ 读它里面有什么——⭐⭐⭐⭐⭐ 它含 hooks 或 MCP 服务器吗？
```

> ⭐⭐⭐⭐⭐ 这条⭐ 与 `toxicskills-13-4-percent.md` 同源，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 但⭐ 把⭐ 风险⭐ 分成了⭐ 两个层级：
> ```
> 技能 = 指令层（能改变模型行为）
> 插件 = 执行层（能自己跑脚本、连外部服务）← ⭐⭐⭐⭐⭐ ⭐ 攻击面大得多
> ```
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 所以⭐ "我读了一遍 SKILL.md" ⭐ 只覆盖了⭐ 前者——
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 而对插件，⭐ 你还得读⭐ plugin.json 和 hooks。
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这⭐ 也解释了⭐ 为什么⭐ `unicode-injection-defense.md` 那条
> ⭐⭐⭐⭐ ⭐⭐⭐⭐ "人类审查对隐藏 Unicode 失效" ⭐ 在插件场景下⭐ 后果更严重。

## 6. ⭐⭐⭐ 团队分发：不用每人手敲

```
⭐⭐⭐⭐⭐ "让每个人都手动跑 /plugin marketplace add ⭐ 是⭐ 无法扩展的。"
```

**两种更好的方式**：

**① 把市场配置提交进仓库**（推荐）

```json
// .claude/settings.json
{
  "extraKnownMarketplaces": {
    "acme-plugins": { "source": { "source": "github", "repo": "acme/claude-plugins" } }
  },
  "enabledPlugins": { "acme-workflow@acme-plugins": true }
}
```

> ⭐⭐⭐⭐⭐ **新同事⭐ 第一次打开仓库⭐ 就拿到插件——⭐⭐⭐⭐⭐ ⭐⭐⭐ 不需要入职文档。**
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 这条⭐ 与 `team-landing-seven.md` 的"阻力最小路径"⭐ 同源，
> ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 且⭐ 是最彻底的一种实现：⭐ **连"要做一件事"这个步骤都省了。**

**② 跑一个私有市场**

```
⭐⭐⭐⭐ 一个私有 git 仓库⭐ 开箱即用地⭐ 就能当市场：
⭐⭐⭐⭐⭐ ⭐ 任何有读权限的人⭐ 都能 add 它并安装
结构：⭐ 一个仓库含⭐ 多个插件目录 + ⭐ 一份 marketplace.json
⭐⭐⭐⭐ 把插件的版本升级⭐ 当成⭐ 任何其他需要评审的改动⭐ 来处理
```

**更新流程**：

```
改 plugin.json 里的版本 → 提交到市场仓库 → 用户跑 /plugin marketplace update
⭐⭐⭐⭐⭐ 如果市场是⭐ 通过 .claude/settings.json ⭐ 预注册的，
⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐ 更新⭐ 会从⭐ 一个合并的 PR ⭐ 流向⭐ 整个团队
```

> ⭐⭐⭐⭐ 一个⭐ 必须知道的⭐ 行为：
> ⭐⭐⭐⭐⭐ **"想改插件行为，⭐ 去市场仓库改源码并发新版本；
> ⭐⭐⭐⭐⭐ ⭐⭐⭐ ⭐ 对已安装副本的本地修改⭐ 会在更新时被覆盖。"**
> ⭐⭐⭐⭐ ⭐⭐⭐ 这与 `cross-agent-portability.md` 的"绝不手抄副本"
> ⭐⭐⭐ ⭐ 和 `retirement-pipeline.md` 的"别改本地副本"⭐ 完全同一条纪律。

## 速查

```
□ ⭐⭐⭐⭐ 三层：技能=内容 · 插件=容器(技能+命令+hooks+agents+MCP，plugin.json)
   ⭐ 市场=渠道(根带 marketplace.json 的 git 仓库)
   ⭐⭐⭐⭐⭐ 插件系统是⭐ 叠加的，不替代 skills 目录；三种装法可共存
□ ⭐⭐⭐⭐⭐ 切分：⭐ 技能承载知识（可移植），⭐ 插件承载 Claude Code 专属自动化
   ⭐⭐⭐⭐⭐ ⭐ 组件互相依赖才打包；⭐⭐⭐⭐⭐ ⭐ 知识能独立就不加壳（壳只增加摩擦并锁定工具）
   ⭐⭐⭐⭐ 命名空间：插件命令带前缀；⭐⭐⭐ 只在 Claude Code 可用
□ ⭐⭐⭐⭐⭐ plugin.json 的 skills 字段⭐ 指向"包含技能目录的父目录"（"./"），
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ 指向技能目录自身 = ⭐ 不报错，⭐⭐⭐⭐⭐ ⭐ 只是一个技能都找不到
   ⭐⭐⭐⭐ 发布前 claude plugin validate；本地 claude --plugin-dir
□ ⭐⭐⭐⭐⭐ 一技能一市场 = 用户要 add 三次 → ⭐⭐⭐ 合并成一仓库多插件目录 + 一份 marketplace.json
□ ⭐⭐⭐⭐⭐ 安全面：⭐ 技能只是指令；⭐⭐⭐⭐⭐ ⭐ 插件能跑 hooks、连 MCP、执行斜杠命令
   ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ ⭐ "我读了 SKILL.md" 只覆盖前者 → ⭐⭐⭐⭐⭐ ⭐⭐⭐ 插件还得读 plugin.json 和 hooks
□ ⭐⭐⭐⭐⭐ 团队分发：把 extraKnownMarketplaces + enabledPlugins 写进 .claude/settings.json
   ⭐⭐⭐⭐⭐ ⭐⭐⭐ 新同事开箱即得，⭐⭐⭐⭐⭐ ⭐⭐⭐⭐ 不需要入职文档
   ⭐⭐⭐⭐ 更新：改版本→提交→/plugin marketplace update（预注册则一个 PR 流向全队）
   ⭐⭐⭐⭐⭐ ⚠️ 对已安装副本的本地修改会在更新时被覆盖
```

**一句话**：

> ⭐⭐⭐⭐ **"技能承载知识、插件承载消费这些知识的 Claude Code 专属自动化"——插件只是分发格式、技能才是可移植内容，所以换工具时你只丢掉外壳；而 plugin.json 的 `skills` 字段必须指向包含技能目录的父目录，写错不报错、只是一个技能都找不到。**
