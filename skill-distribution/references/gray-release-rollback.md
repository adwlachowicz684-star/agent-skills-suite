## 1. ⭐⭐ 五步放量

```
① ⭐ 基线确认
   灰度前先记录当前线上版本的基线：
   P99 响应时间 · SuccessRate · 调用链路错误率 · 会话轮次均值
   ⭐⭐ 没有这些基线，灰度后的对比就是空中楼阁

② ⭐ 单机试点
   挑集群里最空闲的一台节点强制切新版，压测一轮
   确认无内存泄漏与崩溃级错误
   ⭐ 这一关过不了 → 直接打回重改，不用进灰度

③ ⭐ 小流量灰度（1% 会话，跑 4–8 小时）
   重点看 SuccessRate 是否下降

④ ⭐ 逐步放量 10% → 30% → 50%，⭐ 每档至少稳定观察 2 小时

⑤ 全量切换后再观察⭐ 一个完整业务周期，
   确认稳定才把旧版本标记为"待清理"
```

> ⭐ 第 ② 步（单机试点）是很多团队没有的——
> **它把"崩溃级错误"挡在灰度之外**，成本低而价值高。

**三种灰度方案**（按场景选）：

| 方案 | 实现 | 适用场景 |
|---|---|---|
| **用户分组灰度** | 按用户 ID 哈希取模，固定比例用户始终走新版 | ⭐ 需要保证同一用户体验一致 |
| **随机灰度** | 每次请求按概率随机选新旧 | 简单快速，适合初期验证 |
| ⭐ **场景灰度** | 低风险场景（查询类）先上，高风险（写入类）后上 | ⭐ 按风险等级分批 |

> ⭐ **场景灰度**最适合技能——因为技能的"写入类"操作
> （改代码、发部署、改数据）出错代价远高于"查询类"
> （呼应 `approval-gates.md` 的分级）。

## 2. ⭐⭐⭐ 跳档的代价：一个金融场景事故

> ⭐⭐ **最容易犯的错是跳档。**

```
事故复盘：
   1% 灰度没发现问题 → 直接跳到 50%
   （中间少了 10% 和 30% 的观察）
   → ⭐ 跳档后 40% 的活跃用户全部报错
```

**根因**（这段是全文最有价值的部分）：

```
⭐⭐⭐ 1% 灰度时，那 1% ⭐ 恰巧都是低活跃用户
   → 而 Bug 只影响高频用户（数据分布相关）
   → ⭐ 跳档后被瞬间放大
   ⭐⭐ 事后复盘：跳档才是罪魁祸首
```

> ⭐⭐⭐ **"1% 恰巧都是低活跃用户"** —— 这是对小流量灰度最深刻的警告：
> **1% 不是随机样本，它有偏**。当 Bug 与用户特征相关时，
> 小流量灰度会给你一个虚假的安全信号。
>
> ⭐ 推论：**放量不只是为了"逐步增加风险敞口"，
> 更是为了⭐ 逐步扩大样本的代表性**。

## 3. ⭐⭐⭐ 版本级指标拆分

> ⭐⭐⭐ **灰度期间，可观测性必须做到比平时更细。**

**做法**：

```
⭐ 每一次技能调用都附加上⭐ 版本号标签 + 会话 ID 链路
→ 监控系统就能⭐ 按版本维度做指标拆分
⭐ 灰度版本的全量日志单独落一份（避免被老版本日志淹没）
```

**为什么必须拆**（这段数学很关键）：

```
⭐⭐ 平时只看大盘可以掩盖掉灰度版本的问题：
   新版本只占 10% 流量
   ⭐ 即使它全挂了，⭐ 大盘平均下来可能只掉了 1–2 个点
```

> ⭐⭐⭐ **10% 的流量全挂 = 大盘掉 1–2 个点** ——
> 这个算术说明了为什么"看大盘"在灰度期等于没看。

**四类该关注的指标**：

```
① 调用成功率
② 耗时分布
③ ⭐ 技能内部的状态码分布（如工具调用失败次数）
④ ⭐⭐ 上下文长度峰值
```

> ⭐⭐ 第 ④ 条是技能特有的——**传统服务不会把"上下文长度"当监控指标**，
> 但技能会，而且它一旦飙升就会拖垮后续所有轮次
> （呼应 `token-bloat-audit.md` 的"一个 dump 500 行日志的命令会拖慢之后每一个响应"）。

**一个真实案例**（说明为什么要拆到更细的维度）：

```
凌晨 2 点，灰度了 5% 的新版导航技能
⭐ 平均错误率看起来正常
⭐⭐ 但按"进入来源"拆分后发现：
   "从商品详情页进入会话"的用户错误率飙到 23%
   原因：新版改了商品 ID 解析逻辑
   ⭐ 而这类流量只占总流量 5% 不到
⭐⭐⭐ 要不是做了维度拆分，这个问题根本不会被发现
```

> ⭐⭐⭐ 这个案例的教训比"要监控"深一层：
> **拆了版本还不够，还要拆到⭐ 业务维度**。
> 因为技能的 Bug 往往是"对某类输入才触发"——
> 这与 `three-failure-modes.md` 的"隐式上下文依赖"是同一类问题。

## 4. ⭐ 回滚的三个等级

```
一级回滚：崩溃级
   进程 Crash / CPU 跑满 / 内存持续增长
   ⭐ 不需要讨论策略，⭐ 直接全量回滚，优先级最高

二级回滚：指标退化
   SuccessRate 下降超过阈值
   → 回到上一档流量或全量回滚

三级回滚：长尾质量
   结构正确但内容错误的比例上升
   ⭐⭐ 最难发现，也最需要人工抽样（见 `comparator-ab-eval.md`）
```

> ⭐⭐⭐ **"回滚不能等到全挂了才执行，那样已经造成了不可逆的损失。"**

> ⭐ 一级那条"不需要讨论策略"很重要——**预先定级，
> 是为了在凌晨两点不需要开会决定要不要回滚**。
> 这与 `escalation-rules.md` 的"升级规则要预先写死"是同一思路。

## 5. ⭐ 灰度 vs A/B：问的问题不同

```
灰度发布  关注"⭐ 新版本是否比旧版本⭐ 差"
         ⭐ 无退化即通过

A/B 测试  关注"⭐ 新版本是否比旧版本⭐ 好"
         ⭐ 有显著提升才通过
```

**A/B 在技能场景的典型应用**：

```
场景：优化 description，看能否提升召回率
A 组（当前 description）：
   "When a CI/CD pipeline build fails, fetch the build logs,
    diagnose the failure type..."
B 组（优化后 description）：
   "Diagnose CI/CD pipeline build failures..."
```

> ⭐ 这个例子选得很好，因为**description 是最适合做 A/B 的部分**：
> 改动小、影响可测（触发率）、不涉及破坏性操作。

## 速查

```
⭐ 五步：
□ ⭐ 基线确认（P99/SuccessRate/错误率/会话轮次）
   ⭐⭐ 没基线 = 对比是空中楼阁
□ ⭐ 单机试点（最空闲节点，压测；过不了直接打回）
□ 1% 跑 4–8 小时，看 SuccessRate
□ ⭐ 10%→30%→50%，⭐ 每档稳定观察 ≥2 小时
□ 全量后再观察⭐ 一个完整业务周期

□ ⭐ 三种灰度：用户分组（体验一致）/ 随机（快速）
   / ⭐ 场景（⭐ 低风险查询先上，高风险写入后上）

□ ⭐⭐⭐ 跳档代价：1% 恰巧都是低活跃用户
   → Bug 只影响高频用户 → 跳档后 40% 活跃用户全错
   ⭐⭐ 1% 不是随机样本，它有偏

□ ⭐⭐⭐ 版本级拆分：每次调用带⭐ 版本号标签 + 会话 ID
   ⭐⭐ 10% 流量全挂 = 大盘只掉 1–2 个点
□ 四指标：成功率 · 耗时 · ⭐ 技能内部状态码 · ⭐⭐ 上下文长度峰值
□ ⭐⭐⭐ 光拆版本还不够，要拆到⭐ 业务维度
   （"从商品详情页进入"错误率 23%，但只占 5% 流量）

□ ⭐ 回滚三等级：崩溃级（⭐ 不讨论直接回滚）/ 指标退化 / ⭐ 长尾质量
□ ⭐⭐⭐ 别等全挂了才回滚

□ ⭐ 灰度问"有没有更差"（无退化即过）
   A/B 问"有没有更好"（有显著提升才过）
```

**一句话**：

> ⭐⭐⭐ **新版本只占 10% 流量时，即使它全挂了，大盘平均下来可能只掉 1–2 个点——
> 所以灰度期间必须做版本级指标拆分，而且还要拆到业务维度。**
