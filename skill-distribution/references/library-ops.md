# 技能库运维

> 前面所有章节都在讲**怎么做好一个技能**。
> 这一章讲另一件事：**当你有几百个技能时，谁来管这个库？**

⚠️ **来源说明**：本章方法来自 2026 年新近研究（SkillOps 等），
属于**早期成果**，数字请当作方向性参考而非定论。
但"技能库会积累技术债务"这个判断，与 `skill-evaluating` 的 `failure-modes.md` 里
候选池 5→100 精确率掉 10 倍的实测结论**相互印证**。

## 技能技术债务

技能库从十几个膨胀到几百上千个时，这些问题会自然出现：

```
□ 技能之间重复、冲突
□ A 依赖 B，但 B 的接口早已不兼容
□ 技能缺乏验证器——失败了也静默返回
□ 旧的没被淘汰，新的还在堆叠
```

> 现有研究大多关注 **agent 在任务时刻**如何检索、规划、修复，
> **没有人管库本身**。这就是技能技术债务。

**为什么这事现在才重要**：

> 候选池从 5 涨到 100，**实际使用精确率从 29.6% 掉到 3.3%**
> （见 `skill-evaluating` 的 `failure-modes.md`）。
> 库越大，检索越成为瓶颈——**而检索是独立于技能质量的第二个瓶颈**。

## 技能契约五元组

> 把每个技能建模为：

```
s = (P, O, A, V, F)

P  前置条件 Preconditions   —— 什么情况下这个技能才适用
O  可执行操作 Operations    —— 它能做什么
A  类型化工件 Artifacts     —— 它产出什么（有类型）
V  验证器  Validators       —— 怎么证明它做对了
F  已知失败模式 Failures    —— 它历史上怎么翻车过
```

> ⭐ **V（验证器）这一项最常被漏掉。**
> 没有验证器的技能，**失败了也没人知道**——
> 这正好对应 `skill-evaluating` 的 `metrics.md` 第 3 层"确定性契约"和
> **`skill-authoring` 的 `skill-crafting` 的 `grounding-verification.md`** 的核心主张。

**用这个五元组审查你自己的技能**：

| 缺哪项 | 后果 |
|---|---|
| 缺 P | 边界不清 → 与别的技能冲突、误触发 |
| 缺 A | 输出形状不稳 → 下游接不住 |
| **缺 V** | **静默失败** |
| 缺 F | 同样的坑反复踩 |

## 四种关系边（HSEG）

> 库不是列表，是**图**。四种边：

| 边 | 含义 | 处理 |
|---|---|---|
| **dep** | 依赖（A 需要 B） | 接口要兼容，否则插入适配层 |
| **comp** | 兼容（可组合） | 保留 |
| **alt** | 替代（可选其一） | 注意别同时触发造成"技能偷窃" |
| **red** | 冗余（干同一件事） | **合并** |

> `red` 边是技术债务的主要形态——
> 也直接对应 `skill-evaluating` 的 `triggering.md` 里"技能偷窃"的检测方法：
> 两个技能描述重叠时，模型会随机选一个，或干脆不选。

## 五维健康诊断

| 维度 | 含义 | **低分意味着** |
|---|---|---|
| **效用 U(s)** | 最近成功调用的比例 | 技能没用了 |
| **冗余 R(s)** | 等价技能集群的大小 | 太多人在干同样的事 |
| **兼容性 C(s)** | 依赖边中符合兼容的比例 | 接口四处断裂 |
| **失败风险 F(s)** | 经验性失败率 | 技能总翻车 |
| **验证缺口 G(s)** | 是否缺少验证器 | **失败了也没人知道** |

**怎么用**：

```
□ 效用低 + 冗余高  → retire（淘汰）
□ 冗余高           → merge（合并）
□ 兼容性低         → add_adapter（插适配层）
□ 失败风险高       → repair（用执行反馈重写）
□ 验证缺口         → add_validator（插验证器）
```

> ⭐ **这套诊断最大的价值**：它是**基于规则的**，
> 研究称维护操作**几乎不消耗 LLM token**——零推理成本。
> 也就是说，**清库这件事不该让 LLM 来做**。

## 五种维护操作

```
merge(sᵢ, sⱼ)        —— 合并冗余对
repair(s)            —— 用执行反馈重写操作
retire(s)            —— 淘汰过时或失败的技能
add_validator(s)     —— 为缺失验证器的技能插入验证器
add_adapter(sᵢ, sⱼ)  —— 在接口不兼容处插入类型转换层
```

> 研究称这套方法独立运行达 79.5%（比最强基线 +8.8pp），
> 作为增强插件 +0.68 ~ +2.90pp。
> 请当作方向性参考。

**落地建议**（不必等工具成熟）：

| 频率 | 做什么 |
|---|---|
| **每月** | 用 `/skill-doctor`（见 `skill-governance` 的 `runtime-controls.md`）找从未被调用的，从成本最高的开始关 |
| **每季度** | 查 `red` 边：把描述重叠的技能合并 |
| **每次改动** | 查 `dep` 边：被依赖的技能改了接口吗？ |
| **持续** | 每写一个新技能，问：现有库里有没有已经干这事的？ |

## 与相关方法的分工

> 三种方法**不是互斥，是互补**：

| 方法 | 解决什么 | 何时用 |
|---|---|---|
| **库运维（本章）** | **库本身**干不干净——无冗余、无失效、接口兼容 | 技能数 >20，出现冲突与重复时 |
| **训练单个技能**（见 `skill-orchestration` 的 `subagents.md` 附近的自进化章节） | 用数据驱动**深挖一个**关键技能 | 有明确任务、有 eval 集的单技能改进 |
| **组合选择** | 为当前任务挑**最具性价比的技能组合** | 成本敏感、技能多 |

**推荐顺序**：

```
1. 先清库（去冗余、补验证器、修接口）
2. 再训练关键技能
3. 最后做组合选择
```

> ⚠️ **顺序不能反**：在一个充满冗余技能的库上训练单个技能，
> 很可能只是在优化一个**本该被合并掉**的技能。

## 自查

```
□ 技能总数是否已超过 20（该考虑库级运维了）？
□ 每个技能是否都有验证器（V）？
□ 是否存在描述重叠的技能对（red 边）？
□ 被依赖的技能改接口时，是否检查了下游（dep 边）？
□ 是否有从未被调用、但仍占着上下文的技能？
□ 清理工作是否用了规则/工具而非 LLM（零推理成本）？
□ 新技能入库前是否查过"是不是已经有人干了这事"？
```
