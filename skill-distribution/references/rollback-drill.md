## 回滚的三种层次

```
① 内容回滚   ——恢复上一版 SKILL.md / references / scripts
② 启用回滚   ——不停内容，只是把它禁用（回到"没有这个技能"）
③ 依赖回滚   ——恢复它依赖的 MCP server / 工具 / 数据版本
```

⚠️ **第 ③ 条最常被漏**：

```
你把技能退回 v1.0
但它调用的 MCP server 昨天升级了
→ v1.0 的指令在新工具上跑不通
```

> ⭐ 所以**发布单元必须包含依赖**
> （见 `canary-release.md` 的 release manifest）。

## 为什么技能回滚更难

和代码相比：

```
代码  回滚 = 切回上一个 commit，行为完全确定
技能  ⭐ 回滚 = 切回上一版文件，但
       · 可能没保留上一版
       · ⭐ 模型行为本身有非确定性
       · "退回去了"不等于"表现回到从前"
```

最后一条值得强调：

> ⭐ **技能回滚的验收标准不是"文件是旧的"，
> 是"行为回到从前"。**
> 而后者只能通过跑 eval 确认。

## 演练怎么做

```
① 记录当前状态（版本、eval 结果基线）
② ⭐ 做一次"有意的坏改动"（或切到一个已知有问题的版本）
③ 宣布模拟事故
④ 执行回滚流程，计时
⑤ ⭐ 跑 eval 套件，确认结果回到基线
⑥ 记录耗时与异常
```

第 ⑤ 条是整个演练的**验收点**——
没有它，你只验证了"文件换回去了"。

## 常见的演练发现

按出现频率：

```
① ⭐ 不知道当前跑的是哪个版本
   ——于是不知道该退回哪里

② 上一版没有保留
   ——回滚变成"凭记忆重写"

③ 改完需要重载/重启才生效
   ——且这一步没人记得

④ ⭐ 依赖没一起回滚
   ——工具或数据版本对不上

⑤ 没有权限改配置
   ——要等另一个团队
```

第 ① 条最基础也最致命。修法很简单：
**让每个技能都能回答"我当前是 v几"**——
版本号写进 frontmatter 或单独文件，
并在每次报告里带上。

## 一个最小演练脚本

```bash
# 1. 记录当前版本与基线
git rev-parse --short HEAD > /tmp/before.sha
python scripts/validate_skill.py ./my-skill > /tmp/before.txt

# 2. 切回上一版
git checkout HEAD~1 -- ./my-skill

# 3. 重载（按你的运行时：/reload-skills 或重启）

# 4. ⭐ 验收：跑 eval，与基线比对
#    （不是看文件对不对，是看行为对不对）
python scripts/validate_skill.py ./my-skill > /tmp/after.txt
diff /tmp/before.txt /tmp/after.txt

# 5. 恢复
git checkout $(cat /tmp/before.sha) -- ./my-skill
```

⚠️ 注意第 4 步：这里用的是**结构校验**做示意，
真实演练应该跑 **eval 套件**（触发 + 输出），
因为结构相同不代表行为相同。

## 清单

```
[ ] ⭐ 每个版本都有标识（tag / 版本号 / 内容哈希）？
[ ] ⭐ 上一版随时可恢复（不是"应该能找回来"）？
[ ] 回滚后需要重载/重启吗？这一步写进文档了吗？
[ ] ⭐ 依赖（MCP / 工具 / 数据）也一起回滚了吗？
[ ] 回滚的验收标准是"eval 结果回到基线"？
[ ] ⭐ 从决策到生效的目标耗时是多少？实测过吗？
[ ] 有权限直接执行回滚（不用等别人）？
[ ] 回滚操作被记进审计日志？
[ ] ⭐ 演练过吗？本季度。
```

## 与 kill switch 的关系

```
kill switch  出事时立刻停（秒级）
回滚         停下之后退到可用状态（分钟级）
```

两者都要有，且**都要演练**——
见 `kill-switch.md`。

区别在于验收：

```
kill switch 验收 = 确认它真的停了（一条触发请求验证）
回滚       验收 = ⭐ 确认行为回到基线（跑 eval）
```

## 一条提醒

> ⭐ **回滚演练的价值不在"通过"，在"发现问题"。**

一次什么异常都没发现的演练，
通常说明演练设计得太温和——
试试在没有准备、由不熟悉流程的人执行的情况下做一次。
