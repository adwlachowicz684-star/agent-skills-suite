# 两级审核：命名空间与全局

> 一个可抄的治理流程：**团队内审核 + 提升到全局时再审一次**。

## 两级结构

| 层级 | 谁审 | 审什么 |
|---|---|---|
| **命名空间审核** | 团队管理员 | ⭐ 本命名空间内的技能包是否符合团队标准 |
| **平台审核** | 平台管理员 | ⭐ 从命名空间提升到全局范围的技能包 |

> 为什么要两级：
> **"符合团队标准"和"值得推给全组织"是两个不同的判断。**

一个技能可以完美满足某个团队的需求，
但命名、触发词或依赖方式不适合全局分发。

## 流程与状态

```
开发者发布技能包 → 进入 "待审核"
        ↓
管理员收到通知 → 查看技能包详情
        ↓
管理员决策 → 批准 / 拒绝
        ↓
批准 → 正式发布
拒绝 → 开发者收到反馈，可修改后重新提交
```

状态机：

```
PENDING    待审核
APPROVED   已通过
REJECTED   已拒绝
WITHDRAWN  已撤回
```

> ⭐ `WITHDRAWN` 这个状态很重要——
> **开发者在批准前发现问题可以自己撤回**，
> 这比"发出去再求管理员拒"体面得多，也能防止坏版本进库。

## 治理功能清单

一个完整的注册表至少要有：

```
□ ⭐ 审核工作流（多级、支持批量）
□ ⭐ 举报机制（用户可举报不当技能包）
□ 提升管理（命名空间 → 全局）
□ ⭐ 审计日志（所有治理动作都被记录）
```

第二项常被忽略，但它是最有效的**事后**发现机制——
管理员不可能在审核时抓到所有问题，
而使用者会在真实场景里先遇到。

## 四个典型场景

**① 命名空间管理员审核**——团队成员提交，管理员确认符合团队标准

**② 平台管理员审核提升**——从命名空间提升到全局

**③ 举报处理**——用户举报不当技能包，管理员调查并处置

**④ 批量审核**——管理员批量批准多个达标技能包

## 几条实操纪律

**① ⭐ 审核要能看全，不只是看元数据**

审核界面至少提供：

```
□ 审核元数据（名称、描述、版本）
□ 浏览文件列表
□ ⭐ 在线查看文件内容
□ ⭐ 下载完整包做本地测试
```

> 只能看元数据的审核等于没审——
> 恶意逻辑在 `scripts/` 和自然语言段落里（见 `supply-chain-audit.md`）。

**② 拒绝要给具体改进建议**

```
❌ "不符合标准"
✅ "请补充文档并增加示例"
```

理由和 eval 的失败信息一样：
**没有具体信息的拒绝会让下一次提交仍然是猜。**

**③ ⭐ 建议 24 小时内完成审核**

> 审核延迟会阻塞开发者。
> 而阻塞的后果是**绕过流程**（私下传文件、直接改生产），
> 这比慢本身糟糕得多。

**④ 撤回只能发生在 PENDING 状态**

```
WITHDRAWN 只在待审核时可用
```

**⑤ 权限收窄**

```
□ ⭐ 只有命名空间的 Admin 和 Owner 能审本命名空间的技能包
□ 平台管理员可以审所有
```

**⑥ 所有审核动作都进审计日志**

包括批准、拒绝、撤回、举报处理。

## 与技能内容的关系

这套流程决定了**技能该怎么写才能通过审核**：

```
□ ⭐ 描述与用途一致（审核员靠它判断作用域）
□ ⭐ 权限与声明用途匹配（权限过宽是最常见的拒绝理由）
□ 依赖要写明，⭐ 最好不在运行时拉取
□ ⭐ 有 evals/ 供审核员跑
□ 版本可 pin
```

最后一条值得强调：
**给审核员一个能跑的 eval 集，是最有力的"我这个技能是好的"证据**——
比 README 或任何描述都可信。

## 一条边界提醒

> ⭐ **审核通过 ≠ 安全。**

它意味着"在某个时间点有人看过一眼"。
之后每次更新都是新内容——
所以**版本化的重新审核**必须内置在流程里，
而不是靠审核员记得。

## 最小可用版本

没有注册表平台时，用 git 也能实现同样的两级：

```
① 命名空间级 = 团队仓库的 PR 审核
   （CODEOWNERS 指定审核人）

② 全局级 = 提升到公共仓库时的第二次 PR

③ 状态机 = PR 的 open / merged / closed / draft

④ 审计日志 = git log + PR 历史

⑤ ⭐ 举报 = issue 模板
```

> 关键差别：git 版本**没有强制力**（可以绕过），
> 但它对 5–20 人的团队通常够用，且零基础设施成本。
