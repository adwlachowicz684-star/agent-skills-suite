## 1. ⭐⭐⭐⭐⭐ 技能的默认读者是作者自己

绝大多数技能是这样被写出来的：

```
我遇到一个问题 → 我和 agent 来回几轮解决了 →
⭐ "把这个流程固化下来" → 写成技能
```

> ⭐⭐⭐⭐⭐ **问题在于：固化下来的不只是流程，
> 还有 ⭐⭐⭐ 当时对话里那些没有说出口的前提。**

那次成功的对话里，作者脑子里有：

```
这是哪个项目 · 用的什么约定 · 上次为什么改 ·
那个字段为什么这么命名 · 哪里是已知的坑
```

> ⭐⭐⭐⭐ **这些全都没进技能文件，因为当时它们不需要被说出来**
> ——agent 通过对话上下文、"看"项目文件、以及之前的轮次已经知道了。

对照我们已有的那条：⭐⭐⭐ **"鱼看不见水"**——
数据依赖如此，**语境依赖更是如此**。

## 2. ⭐⭐⭐⭐ 四种"只有我能用"

| 类型 | 表现 | ⭐ 暴露时机 |
|---|---|---|
| **① 语境依赖** | 用了项目里特有的简称、人名、历史决定 | ⭐⭐⭐ 别人一跑就错 |
| **② 路径依赖** | 硬编码了自己的目录结构 | 换机器就废 |
| **③ 口头依赖** | "按上次说的做法" | ⭐⭐⭐⭐ agent 完全无法执行 |
| **④ ⭐ 标准依赖** | "处理好一点""按规矩来" | ⭐⭐⭐ 每个人理解不同 |

> ⭐⭐⭐⭐ **第三类最离谱也最常见**：
> 因为技能是从对话里"固化"出来的，
> ⭐⭐⭐ **对话里的指代词会被原样带进来**
> ——"那个文件""上次那个方案""跟之前一样"。

第四类与含糊词黑名单同源，但更隐蔽：
**它看起来像是有标准，只是没写出来**——
于是 agent 会以为"标准存在，我应该知道"，然后凭先验填一个。

## 3. ⭐⭐⭐⭐⭐ 第二读者测试

不需要真的找人，自己做，三步：

**第一步 ⭐⭐⭐ 假装你不知道这个项目**

```
读一遍 SKILL.md，把每一个你"自动理解"的名词圈出来
```

> ⭐⭐⭐⭐ **判据**：圈出来的词，如果没在文件里被定义或解释，
> 就是语境依赖。

**第二步 ⭐⭐⭐⭐ 找一个干净环境**

```
全新克隆的仓库 / 没有 .env / 没有会话历史
```

> ⭐⭐⭐⭐ 这一步和数据依赖那份的"思想实验"是同一个动作——
> 两份文档的检查可以合并成一次做。

**第三步 ⭐⭐⭐⭐⭐ 让一个不了解背景的 agent 跑一遍，你只看它问了什么**

> ⭐⭐⭐⭐⭐ **这一步最关键，而且它的产出不是"通过/失败"：**
> ⭐⭐⭐⭐ **agent 提出的每一个澄清问题，都是一处缺失的语境。**
> 把那些问题的答案补进技能就行——
> **这是唯一一种"由使用者告诉你哪里不清楚"的机制。**

## 4. ⭐⭐⭐⭐ 一次性技能的正确处理

先分清两类（我们已有这个区分，这里补上动作）：

| | 一次性技能 | 复用性不足的技能 |
|---|---|---|
| 判断时机 | ⭐⭐⭐ 写它的那一刻就知道 | 跑一段时间才发现 |
| ⭐ 处理 | ⭐⭐⭐⭐ 立即删，不留 | 补语境或缩范围 |

> ⭐⭐⭐⭐ **一次性技能不该被"修好"**——
> 它本来就是为那一次任务做的，修成通用的成本远高于重写。

判据一句话：**如果它的 description 里必须出现具体的人名、日期、
issue 号才能说清楚，它就是一次性的。**

配套纪律（来自 `project-level-overload.md`）：
⭐⭐⭐ **用完就删，零延迟**。不需要等审计，因为它不需要数据就能判断。

## 5. ⭐⭐⭐ 三个低成本动作

按成本从低到高：

**① ⭐⭐⭐ 名词表**（最低成本，收益最大）

```
技能里出现的每个专有名词、简称、缩写，加一句括号解释。
```

**② ⭐⭐⭐⭐ 写清"为什么"，不只是"做什么"**

```
❌ "用 schema v2"
✅ "用 schema v2（v1 已停用，v3 尚未在 prod 生效）"
```

> ⭐⭐⭐⭐⭐ **这条一举两得**：
> 既消除了语境依赖，⭐⭐⭐ **又让第二个读者在情况变化时知道该怎么改**
> ——这正是 `write-reasons-not-rules.md` 说的"可迁移的判断依据"。

**③ ⭐⭐⭐⭐ 明确写出"本技能假定什么"**

```markdown
## 假定
- 项目使用 pnpm（非 npm）
- 数据库迁移由 `migrations/` 目录管理
- ⭐ 不满足任一假定 → 停止并说明，不要自行适配
```

> ⭐⭐⭐⭐ 最后一句是关键：
> **没有它，agent 会在不满足假定时默默"适配"**——
> 而那个适配多半是错的，且不会报错。

这与 `preflight-gate.md` 的 STEP 0 完全咬合：
⭐ **假定就是前置条件的一种**，不满足就该快速失败。

## 6. ⭐⭐⭐ 与"要给约束不给流程"的关系

表面上冲突：

```
"给约束不给流程" → 少写
"第二读者测试"   → 多写
```

> ⭐⭐⭐⭐ **不冲突，因为写的东西不同**：

| | 给约束不给流程 | ⭐ 这份 |
|---|---|---|
| **少写** | 步骤序列（怎么做） | — |
| ⭐ **多写** | — | 边界条件、假定、名词（**在什么前提下**） |

> ⭐⭐⭐⭐⭐ **少写"步骤"，多写"前提"。**
> 步骤是模型能自己推的（它有工具、能看文件）；
> ⭐⭐⭐⭐ **前提是它推不出来的**（那些只存在于作者脑子里）。

一句话收口：**你省的应该是"怎么做"，不是"在什么条件下"。**

---

## 一句可贴在墙上

> ⭐⭐⭐ **少写"怎么做"，多写"在什么前提下"——
> 前提是模型唯一推不出来的东西。**
