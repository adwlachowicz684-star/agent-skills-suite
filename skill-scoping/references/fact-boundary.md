## 事实边界：只写验证过的规则

> **只记录经多个项目验证过的规则。**

这是把"我觉得应该这样"和"确实是这样"分开的纪律。

| 能写进技能 | 不能写进技能 |
|---|---|
| 跨多个项目验证过的约定 | 只在一次任务里成立的做法 |
| 有明确来源的规范 | 你的推测或偏好 |
| 可检查的事实 | 无法证伪的判断 |

**检验问句**：*这条规则，我能在第二个项目里也指着它说"这里也该这样"吗？*

## 与活代码冲突时以活代码为准

> **技能与活代码冲突时，以活代码为准。**

这是防止技能**把过时约定固化下来**的关键一条。技能会沉淀，代码会演进——
当两者不一致，说明**技能过时了，而不是代码错了**。

**在技能里显式写这条**，让模型知道该怎么处理冲突：

```markdown
## 冲突处理
- 本技能的描述与仓库实际代码不一致时，以仓库实际代码为准
- 发现不一致时，在输出里指出"技能已过时，建议更新"
```

> 这和第 3 章讲的"沉淀"是同一个问题：
> **过时层级因为"添加感觉安全、删除感觉危险"而留下来。**
> 给一条明确的冲突裁决规则，等于给删除发了许可证。

## 项目上下文覆盖

一个可抄的机制：**技能读一份项目级上下文文件，它覆盖技能的通用规则**。

```markdown
读取 `.ai-factory/skill-context/<skill-name>/SKILL.md` —— 若存在则必读（MANDATORY）。
该文件包含由项目演进沉淀出的项目特定规则。

如何应用：
- 把它当作本技能通用指令的项目级覆盖
- 与 SKILL.md 通用规则冲突时，**项目上下文规则优先**（更具体的上下文优先，
  与嵌套 CLAUDE.md 同理）
- 无冲突时两者都应用
- **不要因为它看起来与本技能默认矛盾就忽略它**
  ——它存在是因为项目经验证明了默认规则不够用

强制：生成任何产物后，对照所有项目上下文规则验证。
      违反任何一条 → 在呈现给用户之前修好。
```

**降级策略**：上下文文件不存在时，只读最近 10 个相关的 patch 文件，
优先看 **Root Cause** 和 **Prevention** 两节。

## 建议不是约束：关键位置设门

> **"建议先写测试"和"测试失败前禁止进入实现"，完全是两套流程。**

以 TDD 为例，真正重要的是**顺序**：

```
先写测试 → 确认测试因预期原因失败 → 写最小实现 → 确认通过 → 再重构
```

> 如果测试没有先失败，就无法证明它真的覆盖了新增行为。
> **Agent 很容易先完成代码，再补一份天然会通过的测试**——
> 看起来流程完整，反馈闭环其实已经失效。

**门能放在很多位置**：

| 门 | 条件 |
|---|---|
| 需求未确认 | 不进入实现 |
| 发布检查未通过 | 不执行部署 |
| 事实来源未核验 | 不把厂商说法写成确定结论 |
| 测试未先失败 | 不进入实现（TDD） |

**写法**：用"**未……就不得……**"的句式，不要用"建议""最好"。

## 以命令通过为准

> **模型很可能"嘴上说遵守、实际没做到"。**
> 不要相信 Agent 告诉你"已按规范修改"，**要看它有没有真正运行命令验证**。

| ❌ 主观判断 | ✅ 可验证动作 |
|---|---|
| "代码风格看起来一致" | `npm run lint` 通过 |
| "应该没问题" | 构建通过 |
| "已检查过图片路径" | 命令输出里能看到检查记录 |

> **用可验证的动作替代主观判断，是让 Agent 遵守规范的底线手段。**

## 密钥不进技能

> **SKILL.md 是明文文件，还会被 Agent 自动加载——一旦写入历史记录或被日志捕获，
> 泄露面比普通文档大得多。**

| ❌ 不能写 | ✅ 该写 |
|---|---|
| `SECRET_KEY = "sk-xxxx"` | "从环境变量 `SECRET_KEY` 读取" |
| 真实内网地址、数据库连接串 | "使用配置里的数据库连接" |
| 具体 token 值 | "通过 `xxx login` 获取凭据" |

**原则**：指导 Agent **去哪拿**密钥，而不是**给**它密钥。

## 高危操作设人工确认门槛

涉及**删除、推送远端、发布上线**的动作，必须加确认门槛：

```markdown
## Critical Rules
- 执行 git push 或涉及删除文件的操作之前，必须先输出将要执行的命令清单，
  待用户确认后再执行。
```

> 这条规则有效避免了几次 Agent 自作主张推送的问题。

**哪些操作要设门槛**：

```
□ 删除文件 / rm -rf
□ git push（尤其 force push）
□ 部署、发布上线
□ 写生产数据库
□ 调用会产生费用的外部 API
□ 发送邮件/消息给他人
```

## 脚本权限边界

只要脚本会**写文件、访问网络、读环境变量、修改外部系统**，就必须再加权限边界：

```yaml
permissions:
  allow:
    - Read(src/**)
    - Exec(npm run test)
  deny:
    - Write(/etc/**)
```

并明确：

```
□ 允许访问哪些目录
□ 什么时候需要人工确认
□ 失败后能否重试
□ 有没有审计记录
```

> **技能可以规范步骤，却不能代替底层安全机制。**

```
□ 有没有硬编码的密钥、内网地址、连接串？
□ 删除/推送/发布是否设了人工确认门槛？
□ 脚本是否声明了权限边界？
```
