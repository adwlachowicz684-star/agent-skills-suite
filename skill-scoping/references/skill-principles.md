## 原则一览

```
 1. 问题要问"怎么做成"，不是"步骤是什么"
 2. 保持 SKILL.md 精简
 3. Bash 优先，散文其次
 4. 确定性推进代码
 5. 严格度匹配任务脆弱性（自由度）
 6. 建验证循环
 7. 行动前先查状态
 8. JIT 加载配显式指针
 9. 引用保持一层 + 长文件加目录
10. 记录输出格式
11. 完整度交给 --help
12. 组合原语，不捆绑工作流
13. 引用既有原则
14. 跨会话持久产物
15. 不重复教模型已知的东西
16. 不信任不熟悉的技能
```

## 问题要问"怎么做成"

> ⭐ 需求捕获时问 **"how do I make X work?"**，
> 而不是 **"what are the steps?"**。

前者导向目标与验收，后者导向一份你可能根本不需要的步骤清单。

## Bash 优先，散文其次

> **宁可用带行内注释的具体命令示例，也不要长篇散文。**

```bash
# ❌ 散文
首先需要确认项目依赖已安装，可以通过包管理器安装...

# ✅ 命令
npm ci                    # 严格按 lockfile 装，不要用 npm install
npm test -- --coverage    # 覆盖率低于 80% 会失败
```

## 确定性推进代码

> ⭐ **任何脆弱的、重复的、或"变化即 bug"的东西 → 脚本。
> Markdown 只留给需要判断力的部分。**

判据：这一步如果两次执行结果不一样就算错，那它必须是脚本。

## 严格度匹配任务脆弱性

（呼应 `guidance-forms.md` 与 `patterns.md`）

```
多种做法都可行（如 code review）  → 松散的自然语言启发式
有偏好模式但可接受变化（报告格式）→ 伪代码或模板
脆弱/易错/一致性关键（迁移、文档修补）→ 精确脚本 + 严格步骤清单
```

## 建验证循环

> ⭐ **显式写出 verify → fix → re-verify 循环。**

按技能类型指定"完成"的标准：

```
文档类技能 → 交付前做视觉 QA
代码类技能 → 测试通过 + 零类型错误
数据类技能 → 输出前做 schema 校验
```

## 行动前先查状态

> ⭐ **不要假设环境已经配好了。让 agent 先验证状态，再分支。**

```markdown
先检查 X 是否已配置：
  [命令]
如果没配，引导用户完成设置：
  [步骤]
```

这条能消掉一大类"agent 直接开干然后失败"的问题。

## JIT 加载配显式指针

> ⭐ **明确告诉 agent 何时读每个引用文件。**

```markdown
标准情况按下面步骤走。
遇到 [特定边缘情况]，先读 references/edge-cases.md。
```

比"详见 references/"有效得多——后者等于没说。

## 引用保持一层 + 长文件加目录

```
□ ⭐ 引用直接从 SKILL.md 出发；嵌套链有部分读取、漏指令的风险
□ 超过 100 行的引用文件要加目录（TOC）
```

## 记录输出格式

> **给出结构化输出示例，让其他工具能可靠解析。**

不只是"以 JSON 输出"，而是给一个真实的完整样例。

## 完整度交给 --help

```
□ SKILL.md 里只写常用操作
□ ⭐ 其余让 agent 去跑 tool --help
```

这条既是省 token，也是**防过时**——
工具变了，`--help` 会跟着变，写死的文档不会。

## 组合原语，不捆绑工作流

> ⭐ **每个技能只做一种能力或一个专业领域；
> 更大的工作流用聚焦的技能组合出来。**

反面：一个技能捆绑了设计、规划、实现、测试、部署。

## 引用既有原则

> ⭐ **命名既有方法的来源（TDD、DDD、red-green-refactor），
> 让 agent 和用户都能验证你指的是哪一种做法。**

一个词激活一整块训练共识，比三段自撰描述更准确。

## 跨会话持久产物

> **技能可以在仓库文件里保存持久上下文
> （CONTEXT.md、ADR、决策日志），供后续会话使用。**

呼应 `memory-state.md`（**`skill-orchestration`**）——
技能本身是无状态的，跨会话状态要显式写盘。

## 保持 SKILL.md 精简

> ⭐ **超过某个长度，你通常是在把本该放进脚本或引用文件的逻辑写成散文。**

判断信号：如果你发现自己在正文里描述一个 10 步流程，
那 10 步里大部分应该是脚本。

## 自查

- [ ] 需求是"怎么做成 X"式的吗？
- [ ] 具体命令多于散文吗？
- [ ] 脆弱/重复的部分进 `scripts/` 了吗？
- [ ] 约束强度匹配任务脆弱性吗？
- [ ] 写了 verify → fix → re-verify 循环吗？
- [ ] 有"行动前先查状态"的分支吗？
- [ ] 每个引用文件都写了"何时读"吗？
- [ ] 引用是一层吗？超 100 行的加了目录吗？
- [ ] 给了结构化输出的真实样例吗？
- [ ] 冷门操作交给 `--help` 了吗？
- [ ] 技能只做一件事吗？
- [ ] 引用了既有原则的名称吗？
