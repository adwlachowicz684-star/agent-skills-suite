## 1. 不要陈述显而易见

> ⭐ **Claude 已经会写代码，也能读你的代码库。**
> 一个只是复述 Claude 本来就会做的事的技能，**增加了上下文却没有增加价值**。

判据很简单：**这一段删掉，模型行为会变吗？** 不会变就该删。
（这与《skill-refining》的 `pruning.md` 里 no-op 测试是同一条。）

```
❌ "写代码时要遵循良好的命名规范"
❌ "修改文件前先读取文件内容"
✅ "subscriptions 表是 append-only，取 version 最高的那行，不是 created_at 最新的"
```

⚠️ **一个例外**：如果你发布的技能**主要是知识性的**，那它的价值必须来自
"把 Claude 推出它默认的思维方式"。官方举的例子是前端设计技能——
**它专门避开 Inter 字体和紫色渐变这类套路**，这才是增量。

## 2. 不要过度约束（Avoid railroading）

> ⭐ **Claude 通常会努力遵守你的指令，而技能又高度可复用——
> 所以在指令里过于具体是危险的。**

技能会在各种你没预想到的场景被复用。写死到"针对某一个确切用例"，
**上下文一变技能就失效**。

官方给的正反例非常有代表性：

```
❌ 过度约束（列了 6 步）
   Step 1: 运行 git log 找到 commit
   Step 2: 运行 git cherry-pick <hash>
   Step 3: 若有冲突，运行 git status 列出
   Step 4: 打开每个冲突文件
   Step 5: 对每个 <<< 标记决定保留哪边
   Step 6: 对已解决文件运行 git add，然后……

✅ 更好
   把 commit cherry-pick 到干净分支上。解决冲突时保留意图。
   如果无法干净落地，说明原因。
```

> 差别在于：前者是**教它按键顺序**，后者是**告诉它目标和判断标准**。

这与《skill-authoring》里的**自由度校准**是同一条原则：
**脆弱操作才给精确护栏，无危险的开阔地给大方向。**

## 3. 给模型它需要的信息，但别替它决定怎么做

配套的正面做法是**把判断标准写清楚，把执行路径留给模型**：

| 写什么 | 不写什么 |
|---|---|
| ✅ 目标与完成判据 | ❌ 每一步的具体命令序列 |
| ✅ Gotchas（真实踩过的坑） | ❌ 对模型已知概念的解释 |
| ✅ 领域里反直觉的事实 | ❌ 通用的"最佳实践" |

还记得 cherry-pick 那个例子吗——**"解决冲突时保留意图"** 就是判据，
**"无法干净落地就说明原因"** 就是异常出口。模型自己知道怎么执行。

## 4. 需要用户提供的配置：config.json 模式

有些技能需要用户的上下文才能工作（比如"把站会发到 Slack"，得知道发到哪个频道）。

官方推荐的模式：

```
skill/
├── SKILL.md
└── config.json      ← 存放用户的设置信息
```

**流程**：

1. 技能启动时读 `config.json`
2. ⭐ **配置缺失 → 主动询问用户，而不是猜一个默认值**
3. 若要让用户做结构化选择，用 `AskUserQuestion` 工具

> 这条与 `idempotency-resume.md` 的"缺参数就问，不猜"一致。
> 区别在于：这里的配置是**一次设置、长期复用**，所以落到文件里。

## 5. 跨会话状态存储

技能可以自带"记忆"。形式从简到繁：

```
追加写入的文本日志  →  JSON 文件  →  SQLite 数据库
```

官方例子（站会日志）：

```markdown
## ~/.claude/standups.log
2024-03-11
- shipped the cache invalidation fix
- started on the onboarding redesign
2024-03-12
- onboarding redesign: first two screens done
- reviewed Sarah's auth PR
```

> 这让 Claude "记得"上次评审过 Sarah 的 auth PR 这类历史事件。

### ⭐ 存储位置的关键细节

```
${CLAUDE_PLUGIN_DATA}   —— 稳定存储，⭐ 技能升级后仍然存活
技能目录内              —— 技能升级时可能被覆盖
```

**需要长期保留的状态放 `${CLAUDE_PLUGIN_DATA}`，不要放技能目录里。**

## 6. 按需安全钩子：/careful 与 /freeze

两个值得内建进**任何破坏性技能**的钩子：

| 钩子 | 作用 |
|---|---|
| `/careful` | 拦截 `rm -rf`、`DROP TABLE`、force-push、`kubectl delete` |
| `/freeze` | 锁定 Claude 只能编辑指定目录内的文件 |

**特点**：调用时激活，**在会话内持续有效**——不需要每步都提醒。

> ⭐ **运维和部署类技能没有借口不装这两个。**

这与《skill-governance》的 `sandbox-execution.md` 是互补的两层：
沙箱是**环境级隔离**，这两个钩子是**会话级闸门**。

---

## 7. 一句话总结

> ⭐ **差距不在"技能能不能跑"，而在"技能好不好维护"。**
>
> - **Gotchas 节** 就是你的测试套件
> - **文件系统结构** 就是你的架构
> - **description 字段** 就是你的 API 契约

官方还给了个选型建议：如果要给团队建技能，**从九种类型里挑一个能立刻解阻塞的**
（通常是流程自动化或库参考），**小而精、加埋点、迭代**，
**不要一次把九种都建起来**。

## 速查

| 要做 | 不要做 |
|---|---|
| ✅ 写模型不知道的（Gotchas） | ❌ 复述模型已知的东西 |
| ✅ 给目标与判据 | ❌ 给死板的按键顺序 |
| ✅ 状态存 `${CLAUDE_PLUGIN_DATA}` | ❌ 状态存技能目录（升级会丢） |
| ✅ 配置缺失就问 | ❌ 猜默认值 |
| ✅ 破坏性技能配 /careful、/freeze | ❌ 指望模型自己知道分寸 |
