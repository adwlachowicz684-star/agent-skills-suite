## 判定的是任务，不是自主程度

> ⭐ **最容易搞错的一点**：
> **不是"它有多自主"决定风险等级，而是"它执行的任务是什么"。**

```
Agent 在执行 Annex III 任务时成为高风险：
  评估求职者、准备信贷决策、为必要服务分类申请
```

**时间线**（EU AI Act, Regulation (EU) 2024/1689）：

| 时间 | 生效内容 |
|---|---|
| 2025-02-02 | 禁止性 AI 实践、AI 素养义务 |
| 2025-08-02 | GPAI 模型义务 |
| **2026-08-02** | **实施框架全面执行**；透明度规则生效 |
| 2027-12-02 | 独立 Annex III 高风险系统核心义务 |
| 2028-08-02 | 嵌入受监管产品的 Annex I 系统 |

**罚款梯度**（取固定金额与全球年营业额占比的**较高值**）：

```
第一档  禁止类高风险行为    ≤3500 万欧元 或 全球年营业额 7%
第二档  GPAI 违规          ≤1500 万欧元 或 全球年营业额 3%
```

## 六项最低控制

```
1. 收敛的权限（scoped permissions）
2. 记录在案的 in-the-loop / on-the-loop 选择
3. 日志
4. 一键关停（kill switch）
5. 定期复审
6. 登记入册（register entry）
```

> ⭐ **Article 14（人工监督）是设计原则**：
> 要确保监督者**有时间、有信息、有授权去干预**。
> 只写一个"有人会看"是满足不了这一条的。

**两份评估文书**（别混淆）：

| 文书 | 适用 | 依据 |
|---|---|---|
| **FRIA**（基本权利影响评估） | 公共机构、信贷与保险领域的部署者 | Article 27 |
| **DPIA**（数据保护影响评估） | 大规模处理个人数据、或做出自动化决策 | GDPR |

> 两者都**离不开完整清单**——
> **不在登记册里的 agent，对你的治理而言等于不存在。**

## 日志：从法律条文到架构

**Article 12（记录保存）**——高风险系统的提供者必须在系统生命周期内**自动记录事件**。

> 在 agent 语境里，"自动记录事件"具体意味着：
> **每一次工具调用、每一次 API 调用、每一次对内部系统的操作都要可追溯。**

**Article 26（部署者义务）**——部署者必须**将自动生成的日志保留至少六个月**。

**正在成形的四个设计模式**：

```
□ Per-agent identity —— 用每个 agent 独立的身份替代共享凭据，
  这样动作才具备可归属性
□ 防篡改的结构化日志 —— 覆盖每个工具调用与 API 调用
□ 至少 6 个月的留存期 —— 针对自动生成的日志
□ 有时限的凭据 —— 会过期、可撤销；
  并记录在案的撤销与遏制流程
```

> 来源背景：OWASP GenAI Exploit Round-up Q1 2026 记录了
> 生成式 agent 暴露敏感业务数据、或被提示注入操控的具体事件。
> 这些事件说明了**为什么**法规要这样设计——
> 不是为了走形式，而是因为**可重建性是识别与遏制风险的前提**。

**技能层面的对应动作**：

```
□ 技能里不要写共享密钥——用环境变量/密钥服务注入
  （呼应 security-review.md 的硬编码凭据风险）
□ 声明最小工具集，高危动作走审批（呼应 injection-defense.md）
□ 每次工具调用留下可归因记录：谁、哪个技能、哪个版本、做了什么
□ 日志记录"技能激活"这一事件本身——
  否则事后无法判断是哪个技能驱动了这次行为
```

## 责任划分

> **Provider / Deployer 的划分要在出事之前就定清楚，而不是之后。**

```
Provider（提供者）  开发并投放系统的角色
                    → 风险管理体系、上市后监控、严重事件报告
Deployer（部署者）  使用系统的角色
                    → 人工监督与监控、日志留存（≥6 个月）
```

> ⚠️ **一个务实的提醒**：
> 技能生态还应明确**技能插件开发者、平台运营者、终端用户**的责任边界——
> 现行规范主要规制服务提供者与用户的关系，
> **多方主体下的责任分配仍在演进中**。

## 中国语境

> 现行《生成式人工智能服务管理暂行办法》主要规制
> **服务提供者与用户**之间的关系。
> **智能体治理涉及开发者、技能插件开发者、平台运营者、终端用户等多方主体**，
> 需通过专门规范性文件明确各方安全责任边界，
> 尤其是**造成损害时的责任分配规则**。

**监管关注的方向**（可参考）：

```
□ 技能插件的多层安全审计
  第一层 自动化静态代码分析（已知恶意模式与漏洞）
  第二层 沙箱动态行为监测（识别隐蔽的数据外传与权限提升）
  第三层 社区信誉评分（开发者历史、用户反馈、同行评审）
□ 记忆数据与用户画像加密存储，用户有完全控制权
  （查看、修改不准确内容、删除不想保留的数据）
□ 记忆数据生命周期管理——超时自动脱敏或销毁，
  防止长期积累的画像成为高价值攻击目标
```

## 起步三步

```
1. 清点每一个 agent
   登记册里记录：用途、运行的模型与平台、
   能触达的工具与系统、责任人
   ⚠️ agent 往往快速、分散地被部署出来——
      没进登记册的就不会被治理到

2. 逐个分类与评估
   按"它执行的任务"对照风险阶梯与 Annex III，而不是按供应商
   触及高风险任务/大规模个人数据/有法律效力的自动化决策时，
   跑对应的 FRIA 或 DPIA

3. 落地控制与监督
   六项控制（见上）
   以 Article 14 人工监督为设计原则
```

## 自查

```
□ 是否按"执行的任务"而非"自主程度"做了风险分类？
□ 每个 agent 是否都在登记册里（含责任人、可触达的系统）？
□ 是否有 per-agent identity（而非共享密钥）？
□ 日志是否防篡改、结构化、覆盖每次工具/API 调用？
□ 自动生成的日志是否留存 ≥6 个月？
□ 凭据是否有时限、可撤销，且有记录在案的撤销流程？
□ 是否有 kill switch？
□ 是否做了 in-the-loop / on-the-loop 的明确选择并记录在案？
□ 人工监督者是否有时间、信息、授权去干预？
□ Provider 与 Deployer 的角色划分是否提前明确？
□ 触及高风险任务时是否跑了 FRIA 或 DPIA（别搞混）？
□ 技能里是否杜绝了硬编码凭据？
```
