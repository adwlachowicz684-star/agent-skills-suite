> **在批准部署任何技能之前，先做风险评级，再走审查清单。**
> （适用于第三方或内部贡献者的技能）

## 风险指标评级

| 风险指标 | 关注什么 | 级别 |
|---|---|---|
| **代码执行** | 技能目录中的脚本（`*.py` `*.sh` `*.js`） | 🔴 **高**：脚本以**完整的环境访问权限**运行 |
| **指令操纵** | 要求忽略安全规则、向用户隐藏操作、或有条件地改变行为的指令 | 🔴 **高**：可能绕过安全控制 |
| **MCP 服务器引用** | 引用 MCP 工具的指令（`ServerName:tool_name`） | 🔴 **高**：把访问范围**扩展到技能本身之外** |
| **网络访问模式** | URL、API 端点、`fetch` / `curl` / `requests` 调用 | 🔴 **高**：**潜在的数据外泄途径** |
| **硬编码凭据** | 技能文件或脚本中的 API 密钥、令牌、密码 | 🔴 **高**：机密暴露在 **Git 历史与上下文窗口**中 |
| **文件系统访问范围** | 技能目录之外的路径、宽泛 glob、路径遍历（`../`） | 🟡 中：可能访问非预期数据 |
| **工具调用** | 指示使用 bash、文件操作或其他工具的指令 | 🟡 中：审查所执行的操作 |

> ⚠️ 注意"硬编码凭据"那条：
> 泄露面是**双重的**——Git 历史（永久）和上下文窗口（每次运行）。

## 审查清单

> 部署前**逐条完成**：

```
1. 读完技能目录里的所有内容
   —— SKILL.md、所有被引用的 markdown、任何捆绑的脚本或资源

2. 验证脚本行为与其声明的用途一致

3. 在沙盒中运行脚本，确认输出与技能描述相符

4. 检查对抗性指令
   —— 要求忽略安全规则？向用户隐藏操作？外泄数据？依输入改变行为？

5. 检查外部 URL 获取或网络调用
   —— 在脚本和指令中搜索 http / requests.get / urllib / curl / fetch

6. 验证没有硬编码凭据
```

**快速预扫**（CI 里就能跑）：

```bash
if grep -rE "(api[_-]?key|secret|password|token)" .agent_skills/; then
  echo "检测到技能文件包含疑似敏感信息"; exit 1
fi
```

## 技能文件分区与脱敏

**不要**把普通技能、敏感技能、私有密钥混在同一目录：

```
skills/
├── public/         # 可对外开放
├── internal/       # 内部技能，需权限控制
├── admin/          # 管理员技能，仅限高权限角色
└── private_keys/   # ❌ 不该出现在仓库——必须由密钥管理服务注入
```

**"最小敏感原则"**：

```
□ 不写死真实 Token
□ 不写完整内部 API 地址——用环境变量或配置中心占位符
□ 不把用户手机号、身份证号等放进技能提示词
□ 示例数据尽量用假数据
```

**读取接口必须最小权限**：

```
□ 登录鉴权
□ 基于角色的访问控制（RBAC）
□ 返回值脱敏
□ 调用频率限制
□ 操作审计日志
□ 敏感技能二次确认
```

> ⚠️ **一条核心判断**：
> **不要把可见性当作安全性；不要用隐藏目录替代授权；
> 不要把"调用权限"和"读取权限"混为一谈。**

## 防技能内容被套出来

> ⚠️ **即使接口没有暴露技能读取入口，
> 攻击者仍可能通过提示注入让 agent 主动输出技能内容。**

**加固手段**：

```
□ 技能内容只用于工具调用，不直接返回给用户
□ 系统提示词中明确要求模型不得输出技能详情
□ 对输出做关键词过滤：技能文件名、内部 API 地址、Token 片段
□ 输出前二次校验，禁止技能原文出现在最终返回里
□ 对"读取技能 / 查看技能 / 列出技能"这类指令做特殊处理
```

> 呼应 `skill-orchestration` 的 `prompt-injection.md`：**技能不是安全主体**，
> 干净的顶层段落无法消除稍后获取的恶意内容。

## 审计与监控

**建议记录这些事件**：

```
□ 技能文件读取：谁、何时、读了哪个技能
□ 技能文件修改：谁、何时、改了什么
□ 技能文件对外输出：agent 返回值中是否含技能内容
□ 技能加载失败：可能是配置错误，也可能是被攻击者尝试读取
```

**告警**：检测到**内部技能文件名出现在外部请求或响应中**时，立即通知安全负责人。

**运行期持续检查**（不是只在发布时查一次）：

```
□ 开启技能调用审计日志（结构化字段）
□ 每月轮换技能调用所需的密钥和 Token
□ 监控高敏感技能文件的访问次数，异常时告警
□ 定期扫描模型输出，查找技能定义回显
□ 不再使用的技能及时下线并删除
```

**不同环境用不同配置**：

```
□ 测试环境用模拟技能目录，只含测试接口
□ 生产技能文件通过部署系统单独下发，不跟随代码仓库发布
□ 发布前检查技能目录权限是否被重置
□ 发布后立即查一次日志，确认没有加载敏感技能导致原文打印
```

## 供应链安全

> 若框架支持**动态加载远程技能**：

```
□ 来源必须可信——优先用带签名的技能包
□ 下载后必须校验哈希
□ 执行过程中不得赋予额外系统权限
□ 定期审计技能市场 / 第三方库的上传内容
```

**三层审计机制**（生态层面）：

| 层 | 手段 |
|---|---|
| 1 | 自动化静态代码分析——检测已知恶意模式与漏洞 |
| 2 | 动态行为监测——沙箱中运行并监控实际行为，识别隐蔽的数据外传与权限提升 |
| 3 | 社区信誉评分——基于开发者历史、用户反馈、同行评审 |

> 一条值得记住的原则：**架构的简洁性本身就是安全保障——
> 更少的代码意味着更少的潜在漏洞和更高的可审计性。**

## 治理清单

| 管控域 | 必做项 | 通过标准 |
|---|---|---|
| **资产** | 形成技能台账（来源、版本、责任人、适用范围） | 能回答"谁在用哪个版本" |
| **供应链** | 统一内部仓库，禁止直接安装未知技能 | 所有技能可追溯、可回滚 |
| **权限** | 按技能/用户/项目/工具配置 | 默认最小权限，高危需审批 |
| **数据** | 标记敏感数据，限制读取与上传 | 客户数据、密钥、生产配置不裸露 |
| **运行** | 沙箱、网络白名单、受控命令、独立身份 | 越界行为被限制在任务边界内 |
| **审计** | 保存工具调用、文件访问、网络请求、版本变更 | 事故后可复盘完整链路 |
| **应急** | 支持禁用、撤销、回滚、通知、复盘 | 发现恶意技能可快速止血 |

> ⭐ **真正成熟的技能使用方式，不是把 agent 武装到无所不能，
> 而是让每一种能力都有来源、有边界、有证据、有撤销路径。**

**事故响应要能回答**：

```
哪个技能被加载了？什么提示/任务触发的？读了哪些文件？
跑了什么命令？调了什么工具？改了什么？谁批准的？
```

> 日志要**把技能活动连到工作项和 commit**，而不只是聊天记录。
> **聊天记录是有用的上下文，但它本身不是合规级的控制手段。**

## 自查

```
□ 每个共享技能是否有 owner、来源、版本、风险评级？
□ 是否做过静态审查（SKILL.md + references + scripts + 安装说明）？
□ 是否按最小权限配置了工具/文件/网络？
□ 不可信技能与高危流程是否在隔离环境中跑？
□ 高危动作（部署、迁移、外部写入、数据导出）是否需人工批准？
□ 是否记录了技能激活、命令、触碰的文件、输出、commit？
□ 更新或策略变更后是否重新认证？
□ 是否有停用与移除机制（而非只增不减）？
□ 是否把技能当作 AI 软件供应链的一部分来管理？
```
